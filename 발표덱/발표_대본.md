## 03 설계 방향 (1분 10초, → 세 번으로 둘째 칸, 계획한 아키텍처, 관제 장면)

앞 장의 그 순간입니다. CPU가 임계치 60%를 넘자 AI가 위험을 알립니다. 여기까지는 규칙으로도 되지만, AI는 주문과 DB가 정상이고 조회 요청이 몰린 것이 원인이라고 짚습니다. 조회 서버 1대 추가를 승인하면 조회 서버가 켜집니다. 셋이 나눠 받아 응답이 정상으로 돌아옵니다. 주문은 DB 기록이 병목이라, 늘리는 건 조회 서버뿐입니다. **[→]**
DB는 예비 DB를 하나 더 두고, 주문을 두 DB에 모두 기록한 뒤에만 확인합니다. 주 DB가 멈추면 예비 DB가 스스로 이어받고, 옛 DB가 다시 붙으면 기다리던 주문이 이어집니다. 확인받은 주문은 잃지 않습니다. **[→]**
두 답을 합치면 이것이 계획한 아키텍처입니다. NAT 게이트웨이 없이 역할별 최소 서버만 두었습니다. **[→]**
혼자 운영하기 위해 관제 서버, Teams, 온프레미스 AI 서버를 붙였습니다. 예를 들어 관제 서버가 인증서 만료 14일 미만을 잡으면, AI가 원인을 분석하고 그 결과가 Teams로 보고됩니다. 조치는 AI가 제안하고 제가 승인합니다. **[→]**

## 04-4 AWS (50초)
AWS에서는 역할별 보안 그룹이 이 일을 맡고, 목록에 없는 길은 기본 거부입니다.
사용자는 웹 진입으로만 들어오고, DB 포트는 거래·조회·관제 서버에만 열었습니다. SSH 포트는 없고, 운영자는 AWS 원격 관리로만 접속합니다.
거래 서버와 DB는 데이터센터 두 곳에 나눠 두었습니다. NAT 게이트웨이는 한 달 비용이 커서 30만 원 예산에 맞춰 두지 않았습니다. **[→]**
사용자에서 거래 서버는 허용, **[→]** DB는 차단, **[→]** 거래 서버에서 DB는 허용입니다. **[→]**

## 04-5 Linux 운영 (45초)
학교 EC2에서는 구성 요소를 Linux에 직접 설치하고 OS 서비스로 운영했습니다. 설정만 하지 않고 동작으로 확인했습니다.
서비스는 로그인할 수 없는 전용 계정으로 돌고, systemd가 실패하면 다시 올립니다. 로그는 영구 보존으로 바꾼 뒤 재부팅해서 이전 기록이 남는 걸 확인했습니다.
앱은 서버 안쪽에서만 열고 HTTPS는 Nginx가 받으며, 디스크 경보는 시험용 파일시스템을 가득 채워 울리고 풀리는 것까지 봤습니다. **[→]**

## 말하는 요령
- **기획 배경은 짧게.** 한 문장만 말하고 말풍선은 청중이 읽게 둔다. 5번 "통장에 30만 원밖에"에서 멈추면 반 박자 기다렸다가 →로 6번을 부른다. 웃음이 나면 기다린다.
- **장마다 첫 문장이 제목이다.** 첫 문장을 말하고 나서 →를 누른다. 누르고 나서 말하지 않는다(청중 눈이 화면을 따라간 뒤 말이 들어가게).
- **숫자는 천천히, 하나만.** "23초", "0건", "3분의 1" 앞에서 반 박자 쉰다. 한 장에서 숫자는 두 개 넘게 강조하지 않는다.
- **한계를 먼저 말한다.** 로컬에서 잰 것, 부분 달성, 66초의 대가는 숨기지 말고 먼저 말한다. 교수님 질문을 막는 가장 좋은 방법이다.
- **'넘어가겠습니다'는 쓰지 않는다.** 대신 다음 장 제목을 바로 말한다("두 번째 장면, 주 DB가 멈췄을 때입니다").
- **시간이 밀리면** 04-5 Linux 운영과 05 테스트를 각각 15초로 줄인다(첫 문장만). 06-3 요약도 한 문장으로 줄일 수 있다.
- **리허설:** N 키로 발표자 노트 창을 띄우면 장마다 권장 시간과 경과 시간이 보인다. 12분 30초 안팎에 끝나는지 두 번 재 본다. 남는 시간은 질문 답변에 쓴다.

## 나올 만한 질문과 짧은 답
- **163달러인데 왜 30만 원인가?** 크레딧 163달러가 약 23만 원이고, 환율 변동과 초과 비용 여유를 더해 30만 원을 상한으로 잡았습니다.
- **수치가 다 로컬 아닌가?** 네, 장애·트래픽 수치는 같은 장애를 반복해서 재기 위해 로컬 Docker에서 쟀습니다. AWS에서는 운영과 알림을 확인했고, 개인 AWS에서 같은 시험을 다시 재는 것이 다음 단계입니다.
- **DB 자동 전환이 AWS에도 적용됐나?** 아직 아닙니다. 로컬에서 검증까지 마쳤고 AWS 적용은 다음 단계입니다.
- **임계치 60%는 확정값인가?** 설계 기본값입니다. 시연 영상은 50%로 맞춰 찍었고, AWS 값은 실제 시험으로 정합니다.
- **AI가 서버를 마음대로 늘리나?** 기본은 수동 모드라 AI는 제안까지만 하고 실행은 제가 승인합니다. 자동 모드를 켜도 조회 서버 켜기 같은 허용 목록 안에서 정해진 횟수만 합니다.
- **DB 두 대가 서로 주 DB라고 하면?** 주 DB·예비 DB·관제 서버 세 대가 투표해 과반을 얻은 쪽만 주 DB가 됩니다. 두 DB 사이 연결만 끊겨서는 예비 DB가 혼자 승격하지 않습니다.
- **조회 서버 자동 증설이 AWS에서 돌았나?** 아직입니다. 학교 계정에서는 자동 증설 그룹 조회와 시작 템플릿 만들기가 거부돼, 조회 서버를 켜고 끄는 시험은 로컬 Docker에서 했고 개인 AWS에서 다시 합니다.
- **AI가 실제 운영에서 판단했나?** 판단 흐름과 안전장치는 개발 PC에서 111회 평가했고, 기본은 사람이 승인해야 실행됩니다. 온프레미스 GPU 서버에서 같은 평가를 다시 재는 중입니다.
- **왜 NAT 게이트웨이가 없나?** 한 달 상시 비용이 예산에 비해 커서, 서버마다 공인 주소와 인터넷 게이트웨이를 쓰고 들어오는 길은 보안 그룹으로 막았습니다.
- **66초 동안 주문이 멈추는데 고가용성인가?** 확인받은 주문을 잃지 않는 쪽을 택한 결과입니다. 거래소에서는 잠깐 멈추는 것보다 기록이 어긋나는 것이 더 큰 문제라고 판단했습니다.
