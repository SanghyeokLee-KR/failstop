# 아키텍쳐 자료

교수님께 설명하고 보고한 구성도와 화면을 모았다. 2026-09-17에 사용자가 지정한 바탕화면의 `광명폴리텍_이상혁/프로젝트 아키텍쳐`에서 15개 파일을 복사했다. 원래 파일명과 내용을 유지했고 바탕화면 원본도 그대로 남겼다. 교수님께 보고했다는 사실과 모든 구현·검증이 끝났다는 판단은 구분한다.

전체 방향은 유지할 만하다. AWS 서비스와 로컬 장애 실험을 나누고, 거래소가 동작하는 모습뿐 아니라 장애와 부하에 어떻게 대응하는지 보여 주려는 구성이 현재 프로젝트와 맞는다. 구성도를 새로 갈아엎기보다 아래 차이를 설명하고, 실제 실행에서 얻은 영상과 캡처를 추가하는 편이 좋다. 현재 구조의 기준은 [0099](../docs/reference/adr/0099-current-architecture.md)다.

**2026-09-18 방향 변경:** 고객사의 IT 인프라를 구축·운영·관리하는 엔지니어의 역할을 수행한다. 약 3개월간 직접 개발한 거래소가 운영 대상이며, 가장 중요한 역량은 Linux 서버 운영이다. Docker 자료는 로컬 개발 검증 이력으로 둔다. 2026-09-19에는 [ADR 0029](../docs/reference/adr/0029-school-aws-first-personal-account-expansion.md)로 순서를 바꿔 학교 EC2에서 Linux 운영을 먼저 검증하고 10월 초 개인 계정에서 보강하기로 했다. VM 선행 단계는 보류했다. Linux의 계정·권한·서비스·로그·디스크·네트워크 운영을 바탕으로 DB 복구, EC2 자동 확장, AI 일일·장애 보고의 Microsoft Teams 전달을 검증한다. 아래 보고본의 수동 확장·카오스 화면은 과거 계획으로 보존한다. 현재 목표는 [ADR 0027](../docs/reference/adr/0027-msp-operations-and-autoscaling.md)을 따른다. 전체 프로젝트 제목은 「Linux 기반 AWS 인프라 구축 및 운영」으로 확정했으며, 개발 완료 후 인프라를 구축하는 시나리오와 소개 문장은 [프로젝트 이해하기](../docs/reports/프로젝트_이해하기.md)에 정리했다.

## 01 전체구성 v6 배포 계획도

2026-09-25에 교수님께 보고한 v5를 바탕으로 현재 결정을 반영한 v6을 같은 폴더에 더했다. v6은 개인 AWS 계정에 배포할 계획을 그린 도면이며 AWS 자원을 만들거나 검증한 결과가 아니다. 학교 EC2에서 실제로 운영 중인 구성은 [학교 AWS 실제 운영 구성도](교수님_보고본/07_학교AWS_운영환경/학교_AWS_실제_운영_구성도.png)를 비롯한 07 도면에서 확인한다.

v6에는 NAT Gateway가 없다. 모든 노드가 퍼블릭 서브넷에서 자기 공인 IPv4로 Internet Gateway를 거쳐 외부와 통신하고, 들어오는 연결은 역할별 보안그룹으로 제한한다([ADR 0030](../docs/reference/adr/0030-nat-free-lab-and-bounded-read-asg.md)). 리더 리스는 기본값인 PostgreSQL 리스를 쓰므로([ADR 0017](../docs/reference/adr/0017-leader-lease-out-of-commit-path.md)) v5의 선택형 DynamoDB 리스 상자는 뺐다. DB는 PostgreSQL 17 두 대를 Patroni로 자동 전환하고 동기 복제로 묶는다. Standby가 없으면 쓰기를 멈추고 거래 화면에 거래 일시 중단을 알리며, AI는 DB를 승격하지 않는다.

앱 계층은 평소 app-1과 app-2 두 대로 운영하고, 부하가 오르면 조회 전용 app-3 한 대가 Auto Scaling group(0~1대)으로 붙어 2~3대가 된다. 평소에 따로 켜 두는 조회 전용 노드는 없다(2026-09-25 사용자 정정). 로컬 카오스 스택이 chaos-api-1·api-2를 고정하고 조회 전용 증설 노드 chaos-api-3만 붙였다 떼는 방식과 같다([chaos Compose](../harness/docker-compose.chaos.yml)). app-1과 app-2는 마켓 파티션 p0과 p1을 나눠 맡는 매칭 리더이면서 조회도 받는다(ADR 0034). 두 리더는 AWS가 임의로 종료하거나 교체하지 않도록 ASG 밖에 고정한다(ADR 0030). ALB는 쓰기를 X-Exchange-Market 헤더에 따라 p0은 app-1, p1은 app-2로 보내고, 조회는 app-1·app-2와 켜져 있는 app-3에 나눈다. v5의 수동 확장 표기는 지웠고, 확장 지표와 임계는 AWS 시험으로 정한다([ADR 0027](../docs/reference/adr/0027-msp-operations-and-autoscaling.md)).

아직 정하지 않은 항목은 점선으로 표시했다. WebSocket 외부 브로커의 위치(ADR 0034), 앱의 SQL을 현재 Primary로 잇는 HAProxy의 위치(ADR 0036), 관제센터와 보고 서비스가 ai-1에 요청을 보낼 터널 경로, Databasus 백업의 배치(ADR 0037 예정)다. ai-1은 연구소에 둘 DGX Spark이며 2026-09-28 입고 예정이다(ADR 0038).

pfSense 방화벽은 VM 실습망에서 구성했고 AWS 경로에는 넣지 않았다. 사용자 트래픽이 방화벽 한 대를 지나면 단일 병목·장애점이 되므로, AWS 쪽 경계는 역할별 보안그룹으로 통제한다(사용자 결정 2026-09-25).

v6이 반영한 ADR 0034·0035·0036·0038은 이 브랜치에 없다. 이 브랜치의 [0099](../docs/reference/adr/0099-current-architecture.md)는 아직 DB를 비동기 복제와 수동 승격으로 설명하므로 그 결정들을 병합할 때 0099와 함께 검토한다. 앱 계층도 결정 문서와 다르다. ADR 0030 본문과 0099는 매칭 리더와 별도인 조회 전용 노드를 min 2 / desired 2 / max 3의 조회 ASG로 계획하므로, 2026-09-25 정정(app-1·app-2 고정, app-3만 0~1대 자동 증설)을 병합할 때 함께 고쳐야 한다. 도면의 VPC 대역 10.0.0.0/16은 사용자가 정한 값이다. 저장소 Terraform은 `vpc_cidr` 기본값이 10.42.0.0/16이고 DB를 앱과 같은 노드 서브넷에 두므로 배포 전에 한쪽으로 맞춘다. [Terraform 변수](../deploy/terraform/variables.tf)

PNG는 5122×3602 크기이고 SVG에는 글꼴을 넣지 않았다. 구조·문구·연결선은 `.drawio` 원본에서 고치고 PNG와 SVG를 함께 다시 내보낸다.

여섯 장은 같은 시각 기준을 쓴다. 캔버스는 16:9인 2560x1440이고 AWS 공식 아키텍처 아이콘과 그룹 컨테이너를 쓴다. EC2는 주황, DB는 자홍, 네트워크는 보라처럼 AWS가 정한 범주 색을 그대로 따르며 아직 만들지 않은 자원은 회색과 점선으로 구분한다. 처음 보는 사람이 짧은 시간에 구조를 읽을 수 있도록 상자에 문장을 넣지 않고, 아이콘 아래에는 이름 한 줄과 보조 두 줄까지만 둔다.

설명이 필요한 내용은 도면 위에 A·B·C 배지로 표시하고 아래 띠에서 한 줄씩 푼다. 흐름의 순서를 나타내는 번호는 숫자로 따로 쓴다. 아래 띠에는 그 배지 세 개와 '확인한 것', '아직 확인하지 못한 것' 두 줄을 둔다. 포트 전체 목록, 인스턴스와 볼륨 식별자, 파일 권한 같은 세부 값은 도면에서 빼고 [AWS 작업 안내](../docs/reports/AWS_작업.md)와 네트워크 접근제어도로 보냈다. 도면이 담지 못한 값을 찾을 때는 그쪽을 본다.

도면에 적은 값은 저장소의 설정 파일과 운영 문서에서 확인한 것이다. 실행 중인 서버에서 다시 조회한 값이 아니므로 현재 서버 상태와 다를 수 있다. 저장소에 근거가 없는 항목은 지어내지 않고 미확인으로 표시했다. 세 보안 그룹의 아웃바운드 규칙, app-1 외 노드의 공인 IPv4 부착 여부, SSM 접속의 VPC 엔드포인트 사용 여부, Nginx 로그 회전 설정, PostgreSQL과 Grafana의 실행 계정이 여기에 해당한다. 발표 전에 콘솔과 서버에서 확인해 [AWS 작업 안내](../docs/reports/AWS_작업.md)에 기록한 뒤 도면을 고친다.

읽을 때 혼동하기 쉬운 것이 두 가지 있다. 첫째로 DB 인스턴스의 EC2 이름표와 현재 역할이 반대다. `2026-ai-kopo-04-db-primary-01`이 지금은 Standby이고 `2026-ai-kopo-04-db-standby-01`이 Primary다. 2026-09-20 수동 전환의 결과이며 도면마다 이름표와 현재 역할을 함께 적었다. 둘째로 조회 ASG의 min 2, desired 2, max 3은 [ADR 0030](../docs/reference/adr/0030-nat-free-lab-and-bounded-read-asg.md)이 개인 계정 조회 노드에 계획한 값이다. 학교 계정에서는 ALB와 시작 템플릿 생성이 거부돼 이 계획을 적용하지 않았다.

배치는 AWS가 안내하는 도면 관례를 따랐다. 흐름은 왼쪽에서 오른쪽으로 두고, 그룹은 뜻이 분명할 때만 쓰며, 긴 설명은 배지로 빼고 연결선이 서로 엇갈리거나 빈 곳을 가리키지 않게 했다.

구조나 문구를 고칠 때는 `.drawio` 원본을 고치고 PNG와 SVG를 함께 다시 내보낸다. 내보내기는 draw.io 데스크톱의 명령줄을 사용하며, 보는 쪽의 다크 모드에 색이 흔들리지 않도록 `--theme light`를 적용하고 SVG에는 글꼴을 넣지 않는다. 내보낸 뒤에는 이미지를 열어 글자 잘림과 선 겹침을 확인한다.

이 도면은 그림 작업의 결과이며 AWS 검증 상태를 바꾸지 않는다. 실제 확인 범위는 [로드맵](../docs/ROADMAP.md), 실행 근거는 [증거본](../증거본/README.md)을 따른다.

## 월 40만 원 운영 예산과 촬영 방식

2026-09-18 사용자가 확정한 운영 예산은 **월 40만 원**이다. 이전의 총 지원금 40만 원 해석을 대체한다. 전액 사용은 사용자 설명에 포함된 조건이며 실제 월별 지급·정산 조건은 별도 확인한다. 예전 ADR의 50만 원 전제와 비용 여유 계산은 현재 예산 판단에 쓰지 않는다. 실제 입금, AWS 잔액과 청구액은 이번에 조회하지 않았다.

발표는 PPTX에 실제 녹화 영상과 캡처를 넣는 방식으로 준비한다. 로컬에서 실행 절차와 녹화를 연습한 뒤, AWS에서는 배포·검증·촬영을 모아서 진행하는 편이 비용 관리에 맞다. 학교 제한으로 적용하지 않은 자원은 명시하고 실제 학교 구성과 개인 계정 보강 구성을 나누어 설명한다. 부하 전용 노드와 추가 앱 노드는 해당 실험 시간에 맞춰 운영한다.

촬영과 결과 보관을 마친 자원은 철거를 계획한다. 다만 보고본에는 봇의 상시 운영이 있고 기존 배포 결정에는 외부 상시 접속 전제가 남아 있다. 영상 발표로 바꾸었다고 그 요구가 자동으로 면제된 것은 아니다. 요구되는 접속 기간을 정한 뒤 촬영 종료와 서비스 종료 시점을 나눈다. 교수님께 운영 기간 변경까지 승인받았다고 기록하지 않는다.

월 40만 원으로 충분한지는 아직 확정할 수 없다. 앱·DB의 인스턴스 규격, 볼륨, 가동 시간, 데이터 전송량과 남은 크레딧을 넣어 현재 견적을 계산해야 한다. EC2를 정지해도 남은 EBS 볼륨 등은 과금될 수 있고, NAT Gateway와 ALB도 생성된 채로 두면 요금이 발생한다. 종료 절차는 노드 정지뿐 아니라 사용하지 않는 유료 자원의 정리까지 포함한다. ## 영상과 함께 남길 장면

캡처는 필요하다. 영상은 장애 전후의 흐름을 보여 주고, 캡처는 교수님이 멈춰서 수치와 구조를 확인할 때 쓴다. 같은 실험의 영상·캡처·원자료가 연결돼 있어야 한다.

| 장면 | 화면에 보여 줄 것 | 함께 남길 근거 |
|---|---|---|
| AWS 배치와 정상 거래 | 실제 노드·역할, 접속 주소, 주문·체결과 정상 지표 | 환경, 커밋·이미지 digest, 리스 제공자, 부하 설정 |
| 앱 리더 장애 | 장애 전 리더, 주입 시각, 새 리더, 거래 재개 | 장애 도달 기록, RTO 시작·종료 기준과 판정 파일 |
| DB 중단 또는 수동 승격 | 어느 DB를 멈췄는지, 재시작인지 다른 DB 승격인지, 접속 전환 | 외부 ACK 목록과 복구 후 저널 대조, 유실 범위, 운영자 개입 시간 |
| 부하 증가와 자원 변경 | 같은 축의 요청량·처리량·지연·오류, 앱·DB 자원 변화 | 변경 전후 규격, 같은 부하 조건, 원자료와 판정 |
| AWS 자동 확장 | 부하 증가, ASG 활동, 새 EC2·ALB 등록, 부하 감소 후 축소 | 역할별 노드 수, 정책·준비 시간, DB 연결과 비용 범위 |
| Linux·네트워크 운영 | 서비스·로그·디스크·라우트·DNS·포트에서 문제를 좁히고 조치 | 관측값, 실제 확인·변경 내용, 조치 전후 상태 |
| Microsoft Teams 운영 보고 | 기본 알림, AI 장애 후속 보고와 일일 보고 | 같은 실험의 지표·로그 링크, 수신 시각, 분석·전송 실패 처리 |
| 최종 데이터 검사 | 실제 검사 대상 건수와 원장·잔고·주문 검사 결과 | SQL 성공 여부, 실험 식별자와 증거 폴더 |

장애부터 회복까지는 시간을 확인할 수 있는 원본 녹화를 보관한다. 발표용으로 잘라 쓰더라도 생략한 대기 구간과 측정한 RTO를 혼동하게 만들지 않는다. 비밀 값·토큰·개인정보가 화면에 나오지 않게 준비하고, 수치가 잘못 찍혔다고 결과를 합성하거나 고치지 않는다. 검증 원자료는 기존 [harness/evidence](../harness/evidence/)에 두고 영상·캡처의 설명에서 연결한다.

09-17 원본 정리에서는 PNG 10개와 drawio 4개의 도형 문구·연결을 읽었으며 Packet Tracer와 AWS를 실행하지 않았다. 이후 학교 AWS 조회 화면은 증거본에 별도 보관한다. 과거 도면을 새 실행 결과로 바꾸지 않는다.
