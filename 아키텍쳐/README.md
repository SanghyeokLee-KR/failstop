# 아키텍쳐 자료

교수님께 설명하고 보고한 구성도와 화면을 모았다. 2026-09-17에 사용자가 지정한 바탕화면의 `광명폴리텍_이상혁/프로젝트 아키텍쳐`에서 15개 파일을 복사했다. 원래 파일명과 내용을 유지했고 바탕화면 원본도 그대로 남겼다. 교수님께 보고했다는 사실과 모든 구현·검증이 끝났다는 판단은 구분한다.

전체 방향은 유지할 만하다. AWS 서비스와 로컬 장애 실험을 나누고, 거래소가 동작하는 모습뿐 아니라 장애와 부하에 어떻게 대응하는지 보여 주려는 구성이 현재 프로젝트와 맞는다. 구성도를 새로 갈아엎기보다 아래 차이를 설명하고, 실제 실행에서 얻은 영상과 캡처를 추가하는 편이 좋다. 현재 구조의 기준은 [0099](../docs/reference/adr/0099-current-architecture.md)다.

**2026-09-18 방향 변경:** 고객사의 IT 인프라를 구축·운영·관리하는 엔지니어의 역할을 수행한다. 약 3개월간 직접 개발한 거래소가 운영 대상이며, 가장 중요한 역량은 Linux 서버 운영이다. Docker 자료는 로컬 개발 검증 이력으로 두고, 이제 AWS 인프라와 관제 기반을 구축한다. Linux의 계정·권한·서비스·로그·디스크·네트워크 운영을 바탕으로 DB 복구, EC2 자동 확장, AI 일일·장애 보고의 Microsoft Teams 전달을 검증한다. 아래 보고본의 수동 확장·카오스 화면은 과거 계획으로 보존한다. 현재 목표는 [ADR 0027](../docs/reference/adr/0027-msp-operations-and-autoscaling.md)을 따른다. 전체 프로젝트 제목은 아직 미정이며, 추천 제목과 소개 문장은 [프로젝트 이해하기](../docs/reports/프로젝트_이해하기.md)에 정리했다.

## 보고한 내용과 현재 구현을 대조한 판단

| 자료에서 설명한 것 | 현재 판단과 발표할 때의 구분 |
|---|---|
| 서울 리전 2 AZ, CloudFront·S3·ALB, 앱, primary·비동기 standby, NAT 2개, 봇과 관측 | 채택한 방향과 맞다. AWS에 이 구성이 실제로 올라가 있다는 증거는 아직 확인하지 못했다. 보고본의 상자 하나를 구현 완료 하나로 세지 않는다. |
| Docker 검증 환경의 DynamoDB Local 리스 | 선택한 실험 구성으로는 가능하다. 다만 현재 chaos Compose의 기본값은 PostgreSQL이다. 촬영 때 실제 `CHAOS_LEASE_PROVIDER`를 기록하고 사용한 제공자에 맞춰 설명한다. |
| 시나리오 1의 DB 장애 | 단일 `chaos-pg`를 중단했다가 같은 DB를 재시작하는 계획이다. 앱 리더만 바뀌는 실험, 리더의 DB 프록시만 끊는 E2, AWS standby를 수동 승격하는 실험은 각각 다르다. |
| 시나리오 2의 수동 용량 변경 | 같은 요청과 부하에서 자원 변경 전후를 비교하는 방향이 맞다. 현재 Docker 기본 경로는 리더 한 대로 트래픽을 보낸다. 앱 컨테이너를 추가하는 것만으로 조회 분산이나 주문 처리량 증가가 보장되지는 않는다. |
| AWS에서 이어갈 자동 확장 | 현재 목표는 부하에 따라 EC2가 증가·감소하는 ASG다. 과거 수동 도면과 구분해 실제 확장 활동·ALB 등록·처리량을 촬영한다. 매칭 리더와 DB 복구를 조회 확장과 같은 동작으로 설명하지 않는다. |
| API 상태에 따른 NGINX 전달 | 현재 기본 설정은 우선 노드와 backup upstream, 요청 실패 시 재시도를 사용한다. 도식만 보고 별도의 능동 리더 탐색·헬스체크를 구현했다고 설명하지 않는다. |
| Packet Tracer 네트워크 | VLAN·라우팅·ACL을 설명하는 실습 자료다. AWS VPC·서브넷·보안 그룹이 구현됐다는 증거로 사용하지 않는다. 이번에는 PNG를 읽었으며 `.pkt`를 실행해 라우팅과 ACL을 시험하지 않았다. |
| 기존 거래·모니터링 캡처 | 화면 소개에는 쓸 수 있다. 거래 화면에는 데모 자산 표시가 있고, 모니터링에는 로컬 `chaos-*` 이름이 보인다. 날짜·커밋·환경·실험 번호가 연결되지 않아 현재 AWS 검증 수치로 인용할 수 없다. |

이 차이는 보고안 전체가 틀렸다는 뜻이 아니다. 특히 두 시나리오 그림은 이미 실측 결과가 아니라 실행 절차와 판정 항목이라는 점을 표시하고 있다. 그 구분을 유지한 채 실제 결과를 별도로 붙이면 된다.

구현 근거는 [chaos Compose](../harness/docker-compose.chaos.yml), [NGINX 설정](../harness/nginx/nginx.conf), [E2 주입 스크립트](../harness/scripts/e2-db-cut.ps1), [DB 수동 페일오버](../docs/reference/operations/DB_수동_페일오버.md), [배포 안내](../deploy/README.md)에 있다. 주문과 DB 복구의 남은 위험은 0099에서 이어서 관리한다.

## 지원금 40만 원과 촬영 방식

사용자가 밝힌 지원금은 **40만 원**이다. 월 40만 원 한도나 매달 지급되는 금액으로 해석하지 않는다. 예전 ADR의 50만 원 전제와 비용 여유 계산은 현재 예산 판단에 쓰지 않는다. 실제 입금, AWS 잔액과 청구액은 이번에 조회하지 않았다.

발표는 PPTX에 실제 녹화 영상과 캡처를 넣는 방식으로 준비한다. 로컬에서 실행 절차와 녹화를 연습한 뒤, AWS에서는 배포·검증·촬영을 모아서 진행하는 편이 비용 관리에 맞다. 보고한 2 AZ·DB 2노드·NAT 2개를 비용 때문에 임의로 줄여 다른 구조를 같은 실험처럼 보여 주지는 않는다. 부하 전용 노드와 추가 앱 노드는 해당 실험 시간에 맞춰 운영한다.

촬영과 결과 보관을 마친 자원은 철거를 계획한다. 다만 보고본에는 봇의 상시 운영이 있고 기존 배포 결정에는 외부 상시 접속 전제가 남아 있다. 영상 발표로 바꾸었다고 그 요구가 자동으로 면제된 것은 아니다. 요구되는 접속 기간을 정한 뒤 촬영 종료와 서비스 종료 시점을 나눈다. 교수님께 운영 기간 변경까지 승인받았다고 기록하지 않는다.

40만 원으로 충분한지는 아직 확정할 수 없다. 앱·DB의 인스턴스 규격, 볼륨, 가동 시간, 데이터 전송량과 남은 크레딧을 넣어 현재 견적을 계산해야 한다. EC2를 정지해도 남은 EBS 볼륨 등은 과금될 수 있고, NAT Gateway와 ALB도 생성된 채로 두면 요금이 발생한다. 종료 절차는 노드 정지뿐 아니라 사용하지 않는 유료 자원의 정리까지 포함한다. [EC2 중지 과금](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/how-ec2-instance-stop-start-works.html), [VPC 요금](https://aws.amazon.com/vpc/pricing/), [로드밸런서 요금](https://aws.amazon.com/elasticloadbalancing/pricing/)

## 영상과 함께 남길 장면

캡처는 필요하다. 영상은 장애 전후의 흐름을 보여 주고, 캡처는 교수님이 멈춰서 수치와 구조를 확인할 때 쓴다. 같은 실험의 영상·캡처·원자료가 연결돼 있어야 한다.

| 장면 | 화면에 보여 줄 것 | 함께 남길 근거 |
|---|---|---|
| AWS 배치와 정상 거래 | 실제 노드·역할, 접속 주소, 주문·체결과 정상 지표 | 환경, 커밋·이미지 digest, 리스 제공자, 부하 설정 |
| 앱 리더 장애 | 장애 전 리더, 주입 시각, 새 리더, 거래 재개 | 장애 도달 기록, RTO 시작·종료 기준과 판정 파일 |
| DB 중단 또는 수동 승격 | 어느 DB를 멈췄는지, 재시작인지 다른 DB 승격인지, 접속 전환 | 외부 ACK 목록과 복구 후 저널 대조, 유실 범위, 운영자 개입 시간 |
| 부하 증가와 자원 변경 | 같은 축의 요청량·처리량·지연·오류, 앱·DB 자원 변화 | 변경 전후 규격, 같은 부하 조건, 원자료와 판정 |
| AWS 자동 확장 | 부하 증가, ASG 활동, 새 EC2·ALB 등록, 부하 감소 후 축소 | 역할별 노드 수, 정책·준비 시간, DB 연결과 비용 범위 |
| Linux·네트워크 운영 | 서비스·로그·디스크·라우트·DNS·포트에서 문제를 좁히고 조치 | 관측값, 실제 확인·변경 내용, 조치 전후 상태 |
| Microsoft Teams 운영 보고 | 기본 알림, AI 장애 후속 보고와 일일 보고 | 같은 실험의 지표·로그 링크, 수신 시각, 분석·전송 실패 처리 |
| 최종 데이터 검사 | 실제 검사 대상 건수와 원장·잔고·주문 검사 결과 | SQL 성공 여부, 실험 식별자와 증거 폴더 |

장애부터 회복까지는 시간을 확인할 수 있는 원본 녹화를 보관한다. 발표용으로 잘라 쓰더라도 생략한 대기 구간과 측정한 RTO를 혼동하게 만들지 않는다. 비밀 값·토큰·개인정보가 화면에 나오지 않게 준비하고, 수치가 잘못 찍혔다고 결과를 합성하거나 고치지 않는다. 검증 원자료는 기존 [harness/evidence](../harness/evidence/)에 두고 영상·캡처의 설명에서 연결한다.

이번 정리에서는 PNG 10개와 drawio 4개의 도형 문구·연결을 읽었다. Packet Tracer 실행, 실제 서비스 접속, AWS 조회와 새 촬영은 하지 않았다.
