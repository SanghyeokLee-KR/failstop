# ADR 0012. 판정 대상이 없을 때 통과하는 공허 통과를 금지하고 양성 증거 축을 세운다

- 상태: 채택
- 날짜: 2026-08-30
- 결정자: harness-engineer(실험·부하 판정 축), backend-engineer(복구 API 판정 객체), 아키텍처 담당(정본 반영)

## 배경

기계 판정이 전부 단측이었다. "위반이 0행이다", "결번이 0건이다" 형태라 표본이 0이면 전건 통과한다. 관측 실패와 통과가 같은 신호를 낸다. 다음은 그 구조가 통과를 냈거나 낼 수 있었던 기록이다.

- E5(네트워크 분할, split-brain 반증)의 합격 게이트가 `[stale 쓰기 0 + epoch 상승 + 무결성 0]`뿐이었다. 무결성 체크 C01~C23이 전부 count 기반이라 쓰기가 0이면 이중 쓰기 0도 참이다. 반증이 목적인 실험이 무활동으로 PASS를 낼 수 있었다(923ee6d).
- WS 판정 축이 `count==0`·`count<N`뿐이라 존재하지 않는 마켓을 구독하면 MESSAGE 0건인데 세 임계가 다 통과하고 종료코드가 0이었다(`docs/contracts/하네스_검증설계.md:244`).
- 주문 경로도 같았다. 접수 0건·rate_limited 1,050건인 주행에서 HTTP 4축 전부 통과, exit 0이다(`harness/load/order_flow.js:146`).
- C16·C17은 판정 SQL과 읽는 쪽만 있고 기록 주체가 없어 두 표가 늘 0행이었다. LEFT JOIN이 0행을 내면 위반 0이라 통과한다. `recovery_runs`에 쓰는 코드가 저장소에 없었다(2f3251d, `docs/contracts/하네스_검증설계.md:250`, `:253`).
- `calibrate.js`의 임계가 전부 빈 배열이었다. 빈 배열은 실패 조건이 아니라 서브메트릭 생성 지시인데, `calibrate.ps1`의 C0가 그 종료코드를 판정 근거로 읽었다(c5d0f47).
- `/admin/v1/ha/recovery`가 배열 둘만 반환해, 대본이 복구 성공을 선언하는데 그 근거를 사람이 눈으로 세야 했다(9a0f977).
- `wsSubscribe`가 `ws.setTimeout`을 불러 전 VU가 즉시 죽었다. 그 상태에서 WS 임계 둘이 표본 없이 통과했다(6045575).

같은 주행에서 배선 결함 넷이 용량 문제로 오독되고 있었다. LB가 재생성 컨테이너의 옛 IP를 붙잡아 502가 10,239건, `k6_keys.json`이 현 DB에 없는 키를 담아 주문 전량 401, `client_order_id`가 주행 간 반복돼 78%가 멱등 재생으로 엔진에 닿지 않은 상태였다(6045575). 판정이 살아 있었다면 용량 결론에 도달하기 전에 걸렸을 것들이다.

판정 감도의 문제임을 확정한 사건이 하나 더 있다. `--env-file` 없이 재기동해 마스터키가 빈 값이 되면서 체결 경로가 3시간 49분간 죽었는데, 그동안 진입 조건 12행이 전부 green이었다(2f3251d).

## 결정

모든 기계 판정에 양성 증거 축을 함께 건다. 판정 대상이 실재했음을 같은 게이트가 증명하지 못하면 그 게이트는 통과를 선언하지 않는다.

- 페일오버 실험(E5·E7)에 서비스 재개와 리더 교체를 합격 조건으로 건다. epoch 단조 상승만으로는 반납 후 같은 노드 재승격과 구분되지 않는다. E5는 둘을 별도 항으로 추가했다. 서비스 재개는 첫 재개 체결의 실재와 체결 수 증가 둘 다이고, 리더 교체는 `leader_lease.holder` 변경이다(`harness/scripts/e5-net-partition.ps1:160`, `:153`, `:164`). E7은 리더 교체만 추가했다. RTO 게이트가 첫 재개 체결의 실재를 이미 요구해 서비스 재개 항을 따로 두지 않았다(`harness/scripts/e7-gray-pause.ps1:139`, `:140`, `:145`).
- 체결 준비 게이트를 누적에서 증분으로 바꾼다. 누적이면 앞선 실험이 남긴 체결만으로 즉시 통과해 봇이 죽은 상태에서도 주입한다(`harness/scripts/e5-net-partition.ps1:37`).
- 복구 API가 `verdict` 객체를 반환한다(schema_version 1.0에서 1.2). 표가 비거나 계측값이 NULL이면 UNKNOWN이고, FAIL이 UNKNOWN을 이긴다(`server/app/src/main/java/kr/exchange/admin/HaMonitoringController.java:261`, `:284`, `:293`).
- 집계는 응답 배열이 아니라 표에서 한다. 배열은 limit로 자른 창이라 그것을 세면 창 밖 실패가 안 보인다(`HaMonitoringController.java:223`, `:226`).
- k6 `ws_seq_observed`를 `dest`·`stream`으로 갈라 채널 사망을 잡고, `accepted_total`로 전량 429 주행을 잡는다(`harness/load/order_flow.js:177`, `:178`, `:150`).
- 계측 주행에 양성 증거 3축을 건다. 주문 발행·조회 발행·접수가 각각 `count>0`이다(`harness/load/calibrate.js:102`, `:103`, `:75`). 상위 판정에는 C0(완주)·C0b(발행량)·C0c(실패율)를 더한다(`harness/scripts/calibrate.ps1:521`, `:537`, `:544`).
- 배선을 증명하는 회귀 테스트를 함께 둔다. 실복구가 행을 남기는지, 재생 실패가 MISMATCH를 남기는지, `EngineConfig` 주입 한 줄이 살아 있는지를 본다(2f3251d).
- 대시보드 JSON 중복 키 검사를 CI에 넣는다. jq는 중복을 마지막 값으로 조용히 접어 유효 JSON 검사를 통과시킨다(`.github/workflows/ci-backend.yml:101`, `:105`).
- 신설 임계는 변이 주입으로 실패 재현을 확인한 뒤에만 등재한다(6045575). 판정이 통과한다는 것과 판정이 살아 있다는 것은 다르다.

## 근거

- 무결성 체크가 전부 count 기반이라는 사실이 구조적 원인이다. 술어를 바꾸지 않는 한 어떤 count 축도 무활동을 반증하지 못한다. 축을 하나 더 거는 것이 최소 변경이다.
- 양성 증거 축은 실패를 실제로 재현했다. 죽은 채널은 `ws_seq_observed`가 실패하고 정상 채널은 5축 전건 통과한다(`docs/contracts/하네스_검증설계.md:246`). orderbook 프레임 소실 변이에서 종전 축은 60건으로 통과했고 채널별 축은 realtime 0건으로 실패한다(`docs/contracts/하네스_검증설계.md:244`).
- `stream:realtime` 한정은 계약에서 나온다. 구독마다 orderbook 스냅샷 1건이 별도 경로로 오므로, 스냅샷을 세면 realtime 발행이 죽어도 구독 수만큼 채워져 하한이 무의미해진다(`docs/contracts/하네스_검증설계.md:244`).
- UNKNOWN을 PASS와 분리하는 근거는 0행 대조로 통과를 내면 그것이 C16·C17에서 잡은 공허 통과와 같은 함정이기 때문이다. 값을 못 읽은 것과 기준을 지킨 것은 다르다(9a0f977).
- 행의 `verdict` 컬럼을 판정에 편입한 이유는 하네스가 RTO·RPO 외에 무결성 clean과 epoch 단조도 보고 그 결론을 행에 박기 때문이다. 버리면 RTO만 정상인 실패 주행이 통과한다(`HaMonitoringController.java:256`).
- 임계를 기존 선언 옆에 새로 쓰지 않고 기존 `status:201` 선언에 직접 건 이유는 JS 객체 리터럴에서 같은 키를 아래에 다시 선언하면 뒤가 앞을 덮기 때문이다. 하네스 k6 스크립트 4개를 전수로 훑어 중복 키 0을 확인했다(c5d0f47).
- 선언과 판정을 분리해 셌다. `k6 inspect`로 계측 주행 선언 20개 중 실제 판정 3개임을 확인했다(c5d0f47).
- 원천 배선을 메운 뒤 두 체크가 판정 대상을 갖는 것을 실측으로 확인했다. C16은 ACK 6,065건 전량 적재에 위반 0, C17은 2026-08-30 15:40 기준 15건 전부 `matched=true`다(`docs/contracts/하네스_검증설계.md:252`, `:253`). C17의 건수는 재기동마다 늘어나는 시점 종속값이라 인용에 시각을 붙인다.
- 하한값은 실측에서 유도했다. 1VU가 20초 구독에서 57건(1.42/s)을 관측하고 판정 프로파일은 WS_VUS 300에 13분 이상이라, 하한 100은 정상 주행을 깨지 않으면서 관측 0을 잡는다(`docs/contracts/하네스_검증설계.md:244`). C0b 하한 90%는 id=1 주행이 제공 18,000에 접수 18,001로 100.0%이고 같은 주행 429 비율이 0.0인 데서 나온다(c5d0f47).

## 대안

- 단측 판정을 유지하고 운영 중 관찰로 보완한다. 기각. 위 일곱 사례 중 셋은 종료코드 0으로 확인됐고(`docs/contracts/하네스_검증설계.md:244`, `harness/load/order_flow.js:146`, `harness/load/calibrate.js:92`), `/ha/recovery`는 통과 여부를 아예 말하지 않아 사람이 눈으로 셌다. 관찰자가 볼 신호 자체가 없다.
- 표를 비우고 시작하는 테스트만 둔다. 기각. 배선 부재와 판정 대상 부재를 구분하지 못한다. 기록 주체가 없어도 그 테스트는 통과한다. 그래서 실복구가 행을 남기는지, 재생 실패가 MISMATCH를 남기는지를 증명하는 테스트를 함께 넣었다(2f3251d).
- k6 임계를 빈 배열로 둔 채 상위 스크립트에서만 판정한다. 기각. 빈 배열은 서브메트릭 생성 지시일 뿐 종료코드로 실패를 내지 않는데, 상위 판정 C0가 바로 그 종료코드를 보고 있었다(c5d0f47).
- 계측 주행에도 SLO를 건다. 기각. 상한 탐색이 목적이라 느린 것은 결과지 실패가 아니다. 이 축은 이 주행이 실제로 돌았는가만 본다. 시나리오 미기동·인증 실패·키 파일 손상이 여기 걸린다(c5d0f47).
- 판정을 콘솔에서 계산한다. 기각. 콘솔의 복구 판정이 최신 1행만 보아 서버의 전역 집계와 결론이 갈렸고, `recovery_runs`에 RPO 컬럼이 없는데 0을 박아 유실 없음을 단정했다. 판정 소유자가 둘이면 화면과 판정이 갈린다(2f3251d).
- C17에 새 결정론 검증기를 넣는다. 기각. 대조가 두 벌이 되면 둘이 어긋날 때 어느 쪽이 정본인지 규정이 없어진다. `ReplayService.rebuild`가 이미 이벤트 단위로 대조하므로 기록자는 그 결과만 남긴다(`docs/contracts/하네스_검증설계.md:253`).

## 영향

- 정본 반영이 부분이다. 복구 판정 객체는 `docs/contracts/하네스_검증설계.md` §1 ② 자동 복구 행의 1차 산출물 열이 `verdict.overall="PASS"`로 인용하고(`:46`), WS·계측 양성 축과 C16·C17 배선은 §2-4에 등재돼 있다(`:244`, `:250`~`:254`, `:261`). 반면 실험 합격 기준의 정본인 §3 카오스 매트릭스 합격 기준 열은 E5·E7 행이 개정 전 문구고(`:362`, `:364`), §1 ⓔ의 공통 PASS 정의(`:60`)에도 서비스 재개·리더 교체가 없다. 그 두 자리 개정이 선행 과제고, 그때까지 스크립트 게이트가 정본보다 엄격하다.
- 복구 API 스키마가 1.2다. 콘솔과 대본이 `verdict.overall`을 읽으므로 필드 제거는 소비자 동시 수정을 요구한다.
- C17의 판정력에 한계가 남는다. 기록자가 `fp_replay`와 `fp_live`를 같은 값으로 적으므로 그 비교로는 `matched`가 항상 true다. 실질 판정력은 재생이 예외로 끝났는가에 있고, 재생 0건도 `matched=true`로 남는다. `verified_events`를 실어 사후 구분만 가능하게 했다(`docs/contracts/하네스_검증설계.md:254`).
- 강화된 게이트로 실험을 재주행해 통과를 확인했다. E5는 RTO 11.99s에 리더 교체 확인, 체결 35,070에서 36,257이고, E7은 RTO 9.983s에 좀비 stale 0이다. 양쪽 C01~C23 전건 0위반이다(923ee6d).
- 실험 실행 전제가 생겼다. 종신 강등이 프로세스 내 플래그이고 서버에 자기 종료 경로가 없어, 실험 사이에 `down -v` + `up`이 없으면 다음 실험의 승격 후보가 0이 된다. 두 스크립트 헤더에 명문화했다(923ee6d).
- 진입 조건이 12건에서 14건이 됐다. 늘어난 둘은 이 작업 중 낸 사고다. 적용된 마이그레이션을 고쳐 체크섬이 깨진 것과 마스터키 공백으로 체결 경로가 죽은 것이다(2f3251d).
- 임계 등재 비용이 늘었다. 변이 주입으로 실패를 재현하지 못한 임계는 등재하지 않으므로, 새 축마다 실패 재현 주행이 하나씩 붙는다.
- 되돌리려면 `verdict` 객체 삭제와 스키마 되돌림, k6 양성 축 제거, E5·E7 합격 조건 축소, 정본 §1 ② 자동 복구 행(`docs/contracts/하네스_검증설계.md:46`)과 §2-4 개정이 함께 필요하다. 부분 되돌림은 판정과 문서를 다시 갈라놓는다.
- 남은 과제는 카오스 창 WS 판정 축 부재다. `ws_epoch_resync_fail`이 이름과 달리 창 밖 연결 오류만 재므로 지표명 분리와 창 판정 축 신설이 필요하다(`docs/contracts/하네스_검증설계.md:260`).
