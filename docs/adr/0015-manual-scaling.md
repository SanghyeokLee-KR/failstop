# ADR 0015. 조회 계층 확장에 수동 스케일링을 채택한다

- 상태: 채택
- 날짜: 2026-09-08
- 결정자: harness-engineer(구현·실측), 아키텍처 담당(정본 반영)

## 배경

정본에 확장 실행 주체가 없었다. `제출_20260901/기획안_원본.md` 6.11이 "조회는 늘려서 나누고 주문은 거절로 막는다"로 방향을 정했으나 그 나눔을 누가 언제 실행하는지는 비어 있다. 전문에서 "오토스케일링", "Auto Scaling", "ASG" 문자열이 0건이고 11.4 작업 항목 19개에도 배정이 없다.

2026-09-08에 완전 자동 오토스케일링을 구현해 로컬에서 전 구간 실측했다. Min 2 / Desired 2 / Max 3, Scale-Out CPU 60%, Scale-In CPU 30%, connection draining이다. 증거는 `harness/evidence/asg-scenario-20260908/`이고 컨트롤러는 `harness/asg/asg_controller.py`다. 시나리오를 두 번 완주했고 Scale-Out 17.0초, Scale-In 17.0초, 헬스 실패 감지 9.5초, 자동 복구 16.9~18.9초, 앱이 낸 5xx 0건이다.

그 실측 위에서 완전 자동 채택을 검토한 결과 네 곳이 막혔다. 4.4가 자동 재기동을 측정 오염으로 기각해 두었고, 9.10의 IAM Deny가 CloudWatch를 막는데 그 우회로인 알람 연동을 7.12가 이름으로 금지하며, 7.13이 임계 확정을 클라우드 착지 뒤로 미뤄 두었고, 13.6-a가 정지 노드의 CPU 소각을 실측해 판정 축의 분해능을 깎아 두었다.

이 ADR은 그 넷을 우회하지 않고 해소하는 형태를 채택한다.

## 결정

조회 계층 확장에 수동 스케일링(manual scaling)을 쓴다. 판정은 자동이고 실행은 사람이다.

수동 스케일링은 AWS EC2 Auto Scaling 이 규정한 세 확장 방식 중 하나다. 나머지 둘은 시각 기준 예약(scheduled)과 임계 기반 동적 확장(dynamic)이다. 동적 확장만 CloudWatch 알람을 요구하므로, 스케일링 정책을 만들지 않고 희망 용량을 직접 설정하는 방식은 9.10 의 IAM Deny 를 건드리지 않는다. 곧 이 결정은 자동화를 못 해서 손으로 하는 것이 아니라 문서화된 운영 방식 하나를 고르는 것이다.

Auto Scaling group 자체는 쓴다. 스케일링 정책만 두지 않는다. 그래서 다음 셋을 그대로 얻는다.

- 최소·희망·최대 용량. 사람이 잘못 입력해도 최소값이 막는다.
- 헬스 기반 노드 교체. 타겟그룹 헬스를 원천으로 쓰므로 CloudWatch 가 필요 없다.
- 그 교체를 실험 구간에만 끄는 수단. `suspend-processes` 의 `ReplaceUnhealthy` 가 그것이고 AWS 의 1급 기능이다. 카오스 관측 구간에 이 한 축만 정지시키고 관측이 끝나면 되살린다.

- 관측과 권고는 자동이다. Prometheus가 노드 지표를 모으고 Grafana가 보여주며, 임계를 넘으면 관리자 페이지에 "부하 높음, Scale-Out 권장"을 표시한다.
- 실행은 관리자가 관리 평면에서 버튼으로 한다. 그 요청이 관리 API를 지나 클라우드 API를 부르고 조회 노드가 한 대 는다. 이어서 타겟그룹 헬스체크를 통과하면 트래픽이 나뉜다.
- 축소도 같은 경로다. 드레이닝을 먼저 걸고 창이 끝난 뒤 노드를 내린다.
- 스케일링 정책을 만들지 않는다. 알람은 권고까지이고 조치로 이어지지 않는다.
- 카오스 실험 구간에는 권고 표시까지 끈다. 노드 자동 교체도 `ReplaceUnhealthy` 정지로 끈다. 노드를 죽인 뒤 L3와 L4와 L7의 전이 순서를 관측하는 동안 시스템 상태를 그대로 둔다. 관측이 끝난 시점에 관리자가 버튼을 눌러 복구를 시작한다.
- 확장 대상은 조회 계층뿐이다. 쓰기는 대상이 아니다.

## 근거

- 4.4의 기각 사유를 피하지 않고 해소한다. 그 절이 오케스트레이터를 기각하며 "스케줄러가 컨테이너를 자동 재기동해 kill 실험 관측을 오염시킨다. 오케스트레이터 미채택은 기능 축소가 아니라 측정 대상 보존이다"라고 적었다. 이 설계는 복구 시작 시점을 사람이 정하므로 관측 창을 사람이 소유한다. 실측이 그 필요를 뒷받침한다. 완전 자동에서는 자동 복구가 16.9~18.9초라 12.3 V1이 요구하는 전이 순서 판독 창이 그만큼 좁아진다.
- 7.12가 금지한 것에 걸리지 않는다. 그 절이 막는 것은 "알람에 자동 액션 연결"이고 사유가 "알람 15개 중 실제 발화를 확인한 것은 2건뿐이다. 나머지 13건은 정확도가 미검증이고, 미검증 신호에 롤백을 걸면 오탐이 곧 사고다"이다. 권고 표시는 오탐이 사고가 되지 않는다. 사람이 지표를 보고 거른다.
- 9.10의 IAM Deny를 건드리지 않는다. 판정을 Prometheus와 Grafana가 하므로 CloudWatch 알람이 필요 없다. 9.9가 CloudWatch 기각 사유를 비용이 아니라 "판정 임계를 직접 소유해야 한다"로 적었는데, 이 설계는 그 소유를 유지한다.
- CPU 단독 판정의 한계를 사람이 덮는다. 13.6-a가 "정지 노드는 처리량 0인데 CPU를 1.00~1.05 vCPU 태운다(HikariCP 하우스키퍼 스핀)"를 실측했고, 같은 항이 정상 과부하 노드의 CPU 최대를 94.0%로 적는다. t4g.small 2 vCPU 기준 정지 노드가 50.0~52.5%다. 곧 CPU 하나로는 부하와 정지와 과부하가 겹쳐 보인다. 사람은 CPU와 처리량과 큐 적체를 함께 본다.
- 증설이 답이 아닌 축을 사람이 가른다. 2026-09-07 실측에서 앱 노드를 1대에서 2대로 늘려도 주문이 56.8/s에서 54.3/s였다. 단일 라이터라 쓰기는 노드로 나뉘지 않는다. 자동 확장기는 이 구분을 하지 않으므로 쓰기 포화에 조회 노드를 붙이고 비용만 쓴다. 7.8의 판별 트리가 그 구분을 담당한다.
- 자동화로 줄어드는 시간이 작다. 증설 실행이 실측 17.0초인데 임계 초과에서 알람 발화까지가 규칙의 `for` 지속으로 1~2분이다. 반응 시간의 지배항이 알람 창이므로 실행을 자동화해 줄이는 몫이 전체의 일부다. 알람 창을 줄이면 순간 스파이크에 발동해 비용이 튄다.
- 7.13의 선행 조건과 충돌하지 않는다. 그 절이 "임계는 클라우드 착지 후 정상 구간을 관측해 정한다. 배포 전에 숫자를 박으면 로컬 값이 t4g.small 2노드에서 그대로 성립한다는 가정이 들어간다"라고 적는다. 권고 임계는 틀려도 사람이 거르므로 잠정값으로 시작할 수 있고, 착지 뒤 관측으로 조인다.
- 기존 관리 평면에 얹힌다. 신설이 아니라 확장이다. 관리 평면은 분리 포트 8443과 mTLS `client-auth: need`, 2인 승인, append-only 감사를 갖추고 있고(정본 4.2), 화면도 `web/app/admin/` 아래 12개 라우트가 이미 있다. 카오스 콘솔이 같은 형태의 파괴 액션 버튼을 이미 쓴다.

## 대안

- 동적 확장(dynamic scaling). 임계 기반 스케일링 정책을 붙이는 방식이다. 기각. 근거 절의 첫 다섯 항이 동시에 걸린다. 특히 4.4의 측정 대상 보존과 정면으로 부딪히고, 그 우회로가 7.12의 명시 금지다.
- 앱을 3대 고정으로 둔다. 기각. 세 번째 노드 시간 단가가 t4g.small 0.0208에 EBS 20 GiB 시간분을 더해 USD 0.0233이고, 달력 월 384시간이면 증분이 USD 8.95, 13,778원이다. 9.5 계획 실청구 97,318원에 얹으면 111,096원으로 자체 상한 100,000원의 111.1%다.
- 확장을 아예 하지 않고 거절로만 막는다. 기각. 6.11이 조회를 "늘려서 나누는" 축으로 규정했고 2026-09-07 실측이 그 효과를 확인했다. 1노드가 2,000~4,000 req/s에서 밀리고 2노드가 8,700 req/s를 낸다. 확장 수단이 없으면 그 축의 대응이 비어 있다.
- CloudWatch IAM Deny를 풀고 AWS 표준 스케일링 정책을 쓴다. 기각. 4.4, 6.3, 9.1, 9.9, 9.10 다섯 절을 함께 되돌려야 하고, 9.1이 CloudWatch 비채택을 자체 상한 제약의 직접 산물로 못 박는다. 되돌림이 비용 항목 하나가 아니라 관측 소유권 원칙의 철회다.
- 권고 없이 순수 수동으로 둔다. 부분 채택. 실행을 사람이 하는 것은 같으나 지표 관측과 임계 판정까지 사람에게 맡기면 대응이 늦고 재현되지 않는다. 판정을 자동화하고 실행만 사람에게 두는 쪽을 택한다.

## 영향

- 정본 개정이 넷이다.
  - 7.8. 조회 축 증설의 실행 주체가 관리자라는 사실과 소요 실측을 적는다. 컨테이너 생성 1.0초, 앱 기동 15.8초, 로드밸런서 투입 1.2초로 증설 한 번이 17.0초이고 축소는 드레이닝 15초를 포함해 17.0초다.
  - 6.11. 조회 타겟그룹의 구성원이 고정 2대가 아니라 2~3대 가변이라는 사실을 적는다.
  - 7.12. 자동화 격자에 "권고 표시"를 명시한다. 자동 조치가 아니라 표시이므로 기존 상한인 2층 자동 완화보다 아래다.
  - 6.5. 조회 노드 대수의 변동 범위를 사이징 표에 적는다.
- 새로 필요한 것이 넷이다.
  - 관리 API에 용량 조회와 증설과 축소 액션. 카오스 콘솔과 같은 형태이고 감사 적재와 역할 게이트를 그대로 탄다.
  - 관리자 화면에 권고 배너와 버튼. `web/app/admin/monitoring` 아래가 자연스러운 자리다.
  - Prometheus 수집 대상을 상시면 노드로 돌리고 노드가 늘고 줄 때 따라가게 한다. 현재 `harness/prometheus/prometheus.yml`의 scrape job이 정적 둘뿐이라 서비스 디스커버리가 선행이다.
  - 클라우드 API 호출 자격. 12.4 B4가 장기 액세스 키 0개를 요구하므로 인스턴스 프로파일 롤이어야 한다. 필요한 권한은 `autoscaling:SetDesiredCapacity` 와 `autoscaling:DescribeAutoScalingGroups` 이고, 카오스 구간을 위해 `autoscaling:SuspendProcesses` 와 `ResumeProcesses` 가 더 붙는다. 그 롤이 용량 변경 권한을 가지므로 앱이 자기 인프라를 바꿀 수 있게 된다. 권한 경계를 8장에 새로 적는다.
- 승인 정책을 정해야 한다. ADR 0014가 카오스 4종의 `approval_token`을 필수에서 선택으로 내렸다. 증설은 되돌릴 수 있으나 비용을 쓰는 액션이므로 같은 판단이 그대로 적용되지 않는다. 이 ADR은 정책을 정하지 않고 결손으로 등재한다.
- 접근 경로를 데모 전에 열어 둬야 한다. 관리 평면은 ALB 뒤에 두지 않는다(6.4). ALB가 TLS를 종단하면 클라이언트 인증서가 앱에 전달되지 않아 기동 검증에서 걸리기 때문이다. 접근이 SSM 포트 포워딩 단독이므로 발표 시연 전에 그 터널이 서 있어야 한다.
- 명시해야 할 사실이 하나 있다. 리더가 죽은 상태에서 노드를 늘려도 쓰기는 돌아오지 않는다. 증설되는 노드는 `exchange.engine.enabled=false`인 조회 전용이고 매칭엔진이 없다. 그 상황에서 복구되는 것은 조회 용량이며 쓰기 재개는 승격 축이다. 데모 대본과 화면 문구가 "서비스 복구"가 아니라 "조회 용량 복구"로 적어야 한다.
- 실측 자산이 이월된다. `harness/asg/asg_controller.py`의 판정부는 그대로 쓰고 실행부만 관리 API 뒤로 옮긴다. 지표 원천은 `docker stats`에서 앱이 이미 노출하는 `process_cpu_usage`로 옮긴다. 그 값이 할당 코어 대비 비율이라 로컬과 클라우드가 같은 축이다.
- 선행 조건이 넷이다. 이 넷이 서기 전에는 권고 임계를 확정하지 않는다.
  - 정지 노드의 CPU 소각을 해소한다. 해소 전에는 CPU가 부하와 정지를 구분하지 못한다(13.6-a).
  - 클라우드에 착지하고 t4g.small 실물에서 정상 구간을 관측한다(7.13). 현재 t4g.small 실물 실측은 0건이다.
  - 알람 정확도를 검증한다. 13개 중 발화 확인이 2건이다(7.12).
  - 클라우드 API 호출 롤을 설계하고 IAM 정책에 반영한다.
- 되돌리려면 위 정본 넷과 관리 API·화면을 되돌리고 조회 증설을 다시 미정으로 둔다. 되돌린 상태는 6.11이 규정한 조회 확장 축에 실행 수단이 없는 상태이므로, 되돌림은 그 축의 포기와 같다.
