# ADR 0007. 수용 제한을 인증 앞 전용 필터로 옮기고 쓰기·조회 두 버킷으로 나눈다

- 상태: 채택
- 날짜: 2026-07-28
- 결정자: backend-engineer(구현), harness-engineer(라이브 판정)

## 배경

E1(pg 지연 200ms·지터 100) 라이브에서 리더가 외부 장애 없이 스스로 죽었다. 실측은 cpu 463%, 체결 5275에서 정지, 강등 로그 0건, epoch 1 불변이다(docs/contracts/하네스_검증설계.md:35). 전 경로 타임아웃과 지연 해제 후 자력 회복 없음은 같은 장애의 별도 기록에 있다(docs/contracts/하네스_검증설계.md:31, server/app/src/main/resources/application.yml:51). 병목은 커넥션이 아니라 커넥션을 기다리는 스레드였다. 요청이 무제한 수용되고 dev 프로파일 HikariCP 획득 타임아웃이 기본 30초라, 요청마다 생긴 가상 스레드가 30초씩 대기하며 무한히 쌓였다(server/app/src/main/resources/application.yml:49~55 주석).

좀비 리더 판정 신호를 세 차례 재설계했으나 셋 다 같은 근본 원인을 별개 과제로 남겼다. 수용 제한 부재다(docs/contracts/하네스_검증설계.md:31).

리스 하드닝(전용 소형 풀 exchange-lease, max 2)까지 끝낸 뒤에도 E1의 미통과 게이트가 errOk(오류율<0.1%) 하나로 남아 있었다. 진단은 이미 나와 있었다. 리스와 무관한 요청 경로 용량 한계이며, 봇 부하 제어와 요청 백프레셔가 필요한 별개 항목이다(docs/contracts/하네스_검증설계.md:27). 이 ADR이 그 항목을 닫는다.

1차 교정은 1c67dbd다. 주문 쓰기 동시 처리 상한을 요청 풀의 75%(하한 4)로 두고 초과분을 무대기 429로 거절했으며, 게이트를 ApiAuthFilter 안에 배치했다. dev 요청 풀 connection-timeout을 30초 기본에서 3000ms 명시로 바꿨다.

1차의 라이브 결과가 이 ADR의 직접 근거다. 백프레셔 자체는 정확히 작동했다. `exchange_admission_limit` 24(풀 32에서 유도가 라이브에서 그대로 동작), `in_flight`가 1에서 23~24로 상한에 붙고 `rejected_total`이 0 -> 37 -> 195 -> 276으로 증가했다. epoch 1 불변, 무결성 위반 0이다. 그런데도 노드는 죽었다. 해제 10분 뒤 api-1 unhealthy, cpu 319%, 체결 1491에서 정지, status·prometheus 응답 불가, 리스만 붙잡은 좀비 리더가 재발했다. verdict FAIL, errorRate 0.858, recoverySec null, injectP99Ms 2789.5다(docs/contracts/하네스_검증설계.md:30).

쓰기 24를 실제로 막았는데 cpu 319%로 죽었다면 남은 부하는 조회다. 쓰기가 상한을 채워도 남는 커넥션은 생존 신호 전용이 아니라 모든 조회가 경합하는 공용 잔량이라, 봇의 다중행 시장 데이터 조회가 그것을 채우는 순간 status GET이 종전대로 굶는다.

## 결정

c27beda로 수용 제한을 다음과 같이 재설계한다.

- 게이트를 ApiAuthFilter(order 10)에서 떼어 전용 `AdmissionFilter`(order 6)로 둔다. RequestSizeLimitFilter(5) 뒤, 인증(10) 앞이다(c27beda의 ApiConfig.java:160~163·173·184, RequestSizeLimitFilter.java:21). 결정 시점에 order 7 필터는 없었다(`git grep -nE "@Order\(7\)|setOrder\(7\)" c27beda -- server/app/src/main/java/` 매치 0).
- `/api/v1/*` 요청을 쓰기·조회 두 버킷으로 갈라 각각 세마포어로 유계화한다. `order`는 `/api/v1/orders`의 POST·DELETE, `query`는 그 외 `/api/v1/**` 전부이며 공개 시장 데이터를 포함한다(c27beda의 AdmissionFilter.java:79~99).
- 요청 풀을 쓰기 40%·조회 40%·예비 20%로 배분한다. 하한 4다(c27beda의 AdmissionLimits.java:35~37). 0 이하 설정은 풀 크기에서 유도한다.
- 초과분은 대기열 없이 즉시 `429 too_many_requests` + `Retry-After: 1` + `detail {"bucket":"node","scope":...}`다. 신규 에러코드를 만들지 않고 기존 429의 위반 버킷 축을 `account`|`node`로 확장한다.
- 면제는 넷이다. `/actuator/**`와 `/harness/v1/**`는 게이트 URL 패턴 자체가 `/api/v1/*`이라 구조적으로 도달하지 않는다. `GET /api/v1/orders/by-client/{coid}`는 §7-6 UNKNOWN 재조회의 유일한 수렴 경로라 명시 면제한다. `OPTIONS` 프리플라이트는 DB를 건드리지 않는다.
- dev 요청 풀 connection-timeout 3000ms를 유지한다(application.yml:55). prod와 같은 값이고 카오스 스택이 dev 프로파일을 쓰므로 곧 라이브 적용값이다.

## 근거

- 합이 풀보다 작아야 한다. 쓰기+조회 = 80%이므로 수용된 요청은 커넥션을 기다릴 일이 없다. 풀이 게이트된 트래픽에 대해 대기 자원이 아니게 되고, DB에 블록된 스레드 수가 타임아웃이 아니라 설계로 유계가 된다. 죽음의 직접 원인이 대기 스레드였으므로 이 성질이 핵심이다.
- 무대기 성질의 전제는 게이트된 경로에 한정된다. 게이트된 요청 하나가 동시에 쥐는 커넥션이 최대 1개일 때만 성립한다. 면제 경로에는 반례가 있다. `/harness/v1/status`는 외부 질의의 RowMapper 안에서 스칼라 질의를 돌려 한 건이 커넥션 2개를 동시에 쥐므로 예비분 산정에 2로 계상한다(AdmissionLimits.java:22~24, docs/contracts/백엔드_DB_설계.md:2014). 이 한정은 c27beda 주석에 없었고 0bac329이 명문화했다.
- 예비 20%가 면제 경로와 백그라운드의 몫이다. actuator health의 DB 지표, `/harness/v1/status`, by-client 재조회, WS 퍼블리셔, 스냅샷 워커, 정산 루프, 불변식 스케줄러가 같은 풀을 쓰고 게이트가 없다. 게이트된 트래픽이 풀을 전량 점유할 수 있으면 이들이 굶는데, 그중 둘이 노드의 생존 신호다. 예비분은 "생존 신호는 막히지 않는다"를 필터 계층이 아니라 커넥션 계층에서 참으로 만든다.
- 쓰기 40·조회 40 대등 배분이다. 조회를 더 조이면 봇의 시장 데이터 조회가 실패해 호가 갱신이 멈추고 주문 흐름이 말라 '체결이 멈추지 않는다'를 조회 쪽에서 깬다. 쓰기를 더 조이면 체결 처리량이 직접 깎인다. 어느 쪽 근거도 더 세지 않아 대등으로 두고 비대칭이 필요하면 설정으로 덮는다.
- 인증 앞이어야 한다. 인증 뒤에서 막으면 이미 `api_keys` 조회로 DB를 탄 뒤라 실효가 없다. 바디 상한(5) 뒤인 이유는 반대편이다. 상한 앞에 두면 64KB 초과 요청이 슬롯을 소비한다(c27beda의 ApiConfig.java:160~163 주석).
- 429는 클라이언트가 이미 다루는 코드다. k6는 429를 실패로 세지 않고(order_flow.js `expectedStatuses`, readMarket의 ob_ok가 200|429), 봇의 조회는 비200을 캐시값·앵커 무효로 흡수하고 다음 사이클까지 쉰다. 어느 쪽도 429에 즉시 재시도로 반응하지 않아 거절이 폭주를 만들지 않는다. 주문 거절은 같은 client_order_id 재시도로 멱등 수렴한다(c27beda의 AdmissionControl.java `rejection()` 주석).
- 좀비 판정과 정합한다. 계측 순서가 [수용 판정(order 6) -> `recordAttempt`(order 10) -> 인증]이라 수용 거절은 좀비 판정의 수요 축에 계상되지 않는다. 거절을 수요로 세면 부하를 정상적으로 흘리는 건강한 노드가 분모만 키워 헛강등한다(docs/contracts/백엔드_DB_설계.md:2013).
- 하한 4는 통합테스트·로컬의 초소형 풀에서 상한이 0~1로 내려앉아 정상 경로까지 막는 것을 막는다. 그 구간에서는 합이 풀을 넘을 수 있고 무대기 성질이 성립하지 않는다. 의도된 교환이다.

## 대안

- 503 반환. 기각. 인그레스가 접수 경로 503을 노드 장애로 계상한다(harness/nginx/nginx.conf:39 `max_fails=1 fail_timeout=2s`, :74 `proxy_next_upstream error timeout http_502 http_503 non_idempotent`). 백프레셔를 503으로 내면 정상 리더가 업스트림에서 빠지고, 수요가 끊겨 좀비 판정의 분모까지 사라진다. 더해 503은 §2-3·§7-6의 재조회 계약을 발동시켜, 노드가 굶고 있는 순간에 불필요한 DB 읽기를 더 얹는다. 수용 거절은 접수 이전이라 저널·원장에 닿지 않으므로 상태가 UNKNOWN이 아니라 확정 미접수다. 재조회가 필요 없다.
- 대기열 생성(짧은 대기 후 통과 또는 거절). 기각. 무한 수용과 30초 획득 타임아웃이 대기 스레드를 쌓아 cpu 463%로 노드를 죽인 근본 원인이다. 큐를 두면 죽는 방식만 옮겨진다. '짧은 대기 후 무조건 통과'는 상한이 아니라 지연 추가일 뿐이라 동시성이 다시 무제한이 되고, '짧은 대기 후 거절'은 대기열(= arrival x wait)을 되살리면서 거절도 그대로 남는다. 세마포어를 비공정(barging)으로 두는 것도 같은 이유다. 공정 큐는 곧 대기열이다.
- 조회 미제한. 기각. 1차가 실제로 택했던 안이고 라이브에서 FAIL했다. 위 배경의 cpu 319%·errorRate 0.858·해제 후 미회복이 그 결과다.
- 쓰기·조회를 한 버킷으로 합치기. 기각. 한쪽이 다른 쪽을 굶긴다. 쓰기가 상한을 채우면 조회가 막히고, 그 반대도 성립한다. 두 부하의 실패 양상이 달라 상한 하나로는 어느 쪽도 보호되지 않는다.
- 인증 필터 내 배치 유지. 기각. `ApiAuthFilter.shouldNotFilter`가 공개 시장 데이터(markets·orderbook·ticker·trades·candles)와 auth·community 평면을 통째로 제외한다. 노드를 죽인 조회가 정확히 그 공개 시장 데이터 다중행 조회다. 인증 필터 안에 조회 게이트를 두면 정작 막아야 할 트래픽이 게이트 밖에 놓인다.
- 봇 부하(OPS)를 낮춰 회피. 성립하지 않는 안이다. 봇의 시장 데이터 조회는 OPS 거버너 대상이 아니라 target-ops를 낮춰도 줄지 않는다. 거버닝 대상은 주문·취소뿐이다(application.yml:195~196 주석). 결정 커밋에 이 안의 검토 기록은 없다. 인용한 주석도 결정 3주 뒤 26816d2(2026-08-18)가 남긴 것이라 사후 근거다.

## 영향

- 정본 문서 4종을 개정했다(`git show --stat c27beda`). API 설계 §2-5-a 재작성(v2.17)과 §2-5 표에 `scope=order`·`scope=query` 행 추가(docs/contracts/백엔드_API_설계.md:237~238·248), DB 설계 §5.4(v2.21), CICD §5-2 메트릭 scope 태그, 아래 항의 검증설계다. 엔드포인트·스키마·서명 규약은 무변경이고 새 에러코드도 없다.
- E1의 기대를 폐기하고 재정의했다. 종전 기대 "대기 증가 -> p99 상승하되 타임아웃 내 전량 처리"는 무제한 수용을 전제한 서술이었고 그 전제가 노드를 죽였다. 새 기대는 p99 유계·429 증가·주입 중 status·readiness 응답 유지·해제 후 자력 회복(60s 내 p99 기저 복귀)이다(docs/contracts/하네스_검증설계.md:358). 429는 백프레셔의 정상 동작이라 오류율 산정에서 제외한다.
- 관측축 3종이 늘었다. `exchange_admission_rejected_total`·`exchange_admission_in_flight`·`exchange_admission_limit`이며 전부 `scope` 태그를 갖는다. 기동 시 해석된 배분을 INFO로 남긴다.
- 부수 교정 하나가 같은 커밋에 붙었다. 인증 계층의 일시 DB 실패가 500으로 나가던 것을 503+`Retry-After`로 정정했다. 획득 타임아웃 3초 초과가 인증 필터와 컨트롤러 어드바이스 두 계층에서 발생하는데, 두 계층이 다 매핑해야 같은 사유가 경로에 따라 500과 503으로 갈리지 않는다.
- statement_timeout은 dev에 걸지 않은 채로 둔다. 걸면 슬롯 점유 시간이 유계가 되어 유리하지만, 같은 풀을 쓰는 Flyway 마이그레이션과 불변식 검증기의 대용량 집계가 슬로 윈도에서 취소된다. 슬롯 점유가 길어질 수 있음을 전제로 상한의 합을 풀보다 작게 잡는 쪽을 택했다(application.yml:56~59 주석).
- 라이브 검증은 통과했다. E1 verdict PASS, errorRate 0, epochStable true, recoverySec 2.06, 무결성 위반 0, 최종 cpu 22%다. 두 버킷 모두 포화한 상태(order 12/12, query 11~12/12, 거절 order 1246·query 2201)에서 노드가 살아남았다는 것이 실측됐다(docs/contracts/하네스_검증설계.md:29, docs/contracts/백엔드_API_설계.md:252).
- 카오스 스택은 요청 풀을 환경변수로 덮으므로 상한 유도가 곧 추종이다. 풀을 바꾸면 두 상한이 함께 움직인다(c27beda의 ApiConfig.java:151~157, 버킷 2개). 명시 고정이 필요하면 `exchange.admission.{order,query}-in-flight`로 덮는다.
- 이 ADR의 면제 목록 중 by-client 항목은 51분 뒤 0bac329(2026-07-29 00:45)이 교체했다. 완전 면제가 동시성·요청률 모두 무제한인 DB 접촉 경로를 남겼고, 그 경로는 하필 노드가 굶는 순간에 몰린다. 전용 소형 버킷(`scope=requery`, 풀의 10%·하한 2)으로 바꾸고 초과분을 거절이 아니라 판정 보류(`409 requery_deferred`)로 내보낸다. 현재 배분은 40/40/10이며 쓰기·조회 상한은 위 PASS 구성 그대로 보존된다. 이 ADR의 나머지 결정은 유효하다.
- 후행 변경으로 필터 사이에 공개 조회 IP 레이트리밋(order 7)이 들어갔다(26816d2, 2026-08-18). 현행 `/api/v1/*` 순서는 바디 상한(5) -> 수용 게이트(6) -> IP 버킷(7) -> 인증(10)이고 수용 게이트는 여전히 IP 버킷 앞이다. 백프레셔로 거절한 요청이 IP 토큰을 갉으면 장애 중에 정상 클라이언트의 예산이 깎이기 때문이다(ApiConfig.java:219~221·230, docs/contracts/백엔드_API_설계.md:246).
