# M2 회원 시스템 설계 (구현 착수판)

정본 의존: `docs/ROADMAP.md`(M2, 상시 게이트), `docs/백엔드_DB_설계.md`(users·api_keys·accounts·post_ledger_transaction·GENESIS), `docs/백엔드_API_설계.md`(§2 공통규약·§3 서명·§3-6 관리 평면·§3-7 데모세션), `docs/데스크톱_레이아웃설계.md`(HeaderNav·고정형), `docs/프론트_디자인시스템.md`(tokens.css), `docs/웹_화면명세서.pdf`(§3.3 DataSource·§6 수용 기준).

설계 대원칙: 회원 기능은 코어 경로(매칭·저널·정산)에 의존성을 더하지 않는다. 회원 인증·세션·프로필은 격리 모듈이고, 자금 프로비저닝만 기존 원장 단일 경로 `post_ledger_transaction`을 재사용한다. 회원 가입·자금 발급은 매칭 커맨드가 아니라 원장 트랜잭션이므로 `command_journal` 재생 경로에 진입하지 않는다.

이 문서는 API·DB 정본을 확장한다. 확장 항목은 §8에 선행 개정 목록으로 모아 두고, 본문 각 절은 그 항목을 참조한다.

## 0. 요약과 인증 3계층 관계 확정

기존 시스템에는 두 인증 경로가 있다. M2는 세 번째 경로(회원 세션)를 신설하고, 셋의 경계를 명확히 나눈다.

| 경로 | 대상 | 자격 증명 | 계정 모델 | 정본 |
|---|---|---|---|---|
| §3 HMAC 서명 | 봇·외부 클라이언트 | `access_key` + `secret_key`(AES-GCM 복호 후 HMAC-SHA256) | 봇별 개인 계정(`users.kind='BOT'`) | API 설계 §3-1~§3-5 |
| §3-7 데모 세션 | 무가입 브라우저 체험 | 없음(무인증 발급) | 시드된 공용 데모 계정 1개 | API 설계 §3-7 |
| 회원 세션(신설 M2) | 가입한 실사용자 | 이메일 + 데모 비밀번호 | 회원별 개인 계정(`users.kind='HUMAN'`) | 본 문서 |

경계 계약.

- 데모 세션은 공용 시드 계정 체험용으로 유지한다. 회원 세션과 상호 대체가 아니라 병존한다. 웹 최초 진입은 데모 세션으로 즉시 열람, 주문하려면 회원 가입으로 승격한다.
- 데모 세션은 읽기 전용이다(v2 개정). 시세·차트·호가·마켓 목록과 공용 데모 계정의 잔고·내역은 열람하되, 자금을 움직이는 쓰기(주문 생성·취소, 입출금, API 키 발급)는 회원 세션·API 키만 가능하다. 근거는 둘이다. 첫째, 데모 계정은 공용 1개라 방문자 누구나 주문을 내면 그 결과를 다음 방문자가 본다. 잔고와 미체결이 남의 조작으로 흐트러진 상태가 첫 화면이 된다. 둘째, 개인 자산·주문 이력이라는 회원 가입의 유인이 무가입 주문으로 사라진다. 봇·외부 클라이언트(API 키)는 영향이 없다. 하네스 부하와 라이브 데모는 API 키 경로라 그대로 돈다.
- 회원은 선택적으로 자기 API 키(scope `read_only`·`trade`)를 발급받아 §3 HMAC 경로로도 접근할 수 있다. 이때도 관리 평면(§3-6)·`withdraw`는 불가하다.
- 회원 세션 토큰은 브라우저 전용이다. §3 HMAC의 `secret_key`는 브라우저에 전달하지 않는다(웹 명세서 §6.1 #4 계약 유지).

## 1. 인증 모델

### 1-1. 가입 방식 확정: 이메일 식별자 + 데모 비밀번호

두 후보를 검토했다.

- (A) 데모 계정 즉시 발급(무비밀번호, 복구 코드): 가장 안전하나, 채점·재현 시 "이메일로 로그인" 기대와 어긋나고, 다기기 로그인이 복구 코드 재입력에 의존해 UX가 취약하다.
- (B) 실사용자 이메일 + 비밀번호: 표준적이고 채점 친화적이나, 사용자가 실제 비밀번호를 재사용할 위험이 있다.

확정안은 (B)를 정본으로 채택하되 데모 안전 가드를 명문화한 절충이다. 근거와 가드.

- 이메일은 식별자로만 쓴다. 런타임 외부 API 의존 금지 규칙상 실제 메일 발송·검증이 불가능하므로, 이메일 소유 검증은 하지 않는다(미검증 핸들). 이 한계를 UI와 문서에 표기한다.
- 비밀번호는 데모 전용이다. 가입·로그인 화면에 "실제로 쓰는 비밀번호를 입력하지 마세요" 경고를 상시 노출한다. 복잡도 강제(특수문자 등 연극적 규칙)는 두지 않고 최소 길이(8자)만 강제한다. 실제 금융 자격증명(카드·계좌·주민번호)은 어떤 화면에서도 수집·저장하지 않는다.
- 비밀번호 재설정은 미지원이다. 메일·SMS 발송이 런타임 외부 의존이라 불가하므로, 분실 시 신규 데모 계정 발급을 안내한다(선택 확장: 가입 시 1회 표시하는 복구 코드 테이블).

### 1-2. 비밀번호 저장 정책

- 알고리즘: Argon2id(메모리 하드). Spring Security `Argon2PasswordEncoder`. 파라미터는 인코딩 문자열에 내장(`$argon2id$v=19$m=...`)해 파라미터 진화를 허용한다. 폴백은 bcrypt(cost 12). `user_credentials.algo`로 알고리즘을 기록해 점진적 재해시를 지원한다.
- 솔트: 알고리즘 내장 per-user 랜덤 솔트. 추가로 서버 페퍼(pepper)를 시크릿 관리소(.env / K8s Secret)에서 주입해 해시 입력에 결합한다. 코드·저장소 평문 금지.
- 저장 금지: 평문·가역 암호화·단순 SHA 저장 금지. 저장 컬럼은 `password_hash` 하나이며 Argon2id 인코딩 문자열만 담는다.
- 온라인 브루트포스 방어: `user_credentials.failed_attempts`·`locked_until`로 계정 단위 지수 백오프 잠금. IP·access 단위는 기존 §2-5 `auth_throttled`(60초 20회) 재사용.

### 1-3. 세션 토큰과 서명 키 정책

회원 세션은 데모 세션(§3-7)과 동일한 Bearer 전용 검증 골격을 상속한다. 브라우저가 HMAC 서명을 못 하는 제약(§6.1)이 회원에게도 동일하기 때문이다. 차이는 계정 범위, 서명 알고리즘, 서명 키 수명이다.

서명 알고리즘 확정: 회원 액세스 토큰은 비대칭 서명(EdDSA, Ed25519)으로 발급한다. 데모 세션의 HS256(대칭)을 답습하지 않는다. 근거는 격리 원칙이다. 게이트웨이는 세 인증 경로 통과 후 동일하게 `(user_id, scope)` 컨텍스트를 주입하고, M3 게시판(community-api)은 별도 프로세스에서 같은 회원 토큰의 서명·`exp`·scope를 로컬 검증해 작성자 신원을 읽는다. 대칭 키였다면 검증 주체인 게시판이 서명 비밀을 보유하게 되고, 침해 시 코어가 수용하는 `scope=trade` 토큰을 위조할 수 있어 게시판 침해가 거래로 전파된다. 비대칭이면 개인키는 M2 인증 발급자에만 두고, 게이트웨이·community-api는 공개키로 검증만 한다. 검증자는 위조 능력을 갖지 못한다.

- 액세스 토큰: JWT EdDSA(Ed25519). payload = `{ "typ":"access", "alg":"EdDSA", "sub":"<user external_id>", "user_id":<BIGINT>, "scope":"TRADE", "kind":"HUMAN", "aud":["exchange","community"], "iat":<epoch s>, "exp":<epoch s, iat+900> }`. 개인키는 인증 발급자(M2 auth) 프로세스에만 상주하고 시크릿 관리소에서 주입한다. 공개키(JWK)는 게이트웨이·community-api에 배포한다(재기동 후에도 세션 유지). 만료 15분. `aud`로 토큰 수신 평면을 명시해, 새 평면 추가 시 무분별한 재사용을 좁힌다(방어 심화, 위조 차단의 주된 근거는 비대칭 키 보관이다).
- 리프레시 토큰: 불투명 256비트 랜덤. httpOnly·Secure·SameSite=Strict 쿠키 `rt`로만 전달. DB에는 raw가 아니라 SHA-256 해시만 저장한다. TTL 14일. SameSite 근거는 §6.
- 회전·재사용 탐지: refresh 호출마다 토큰을 회전(단회용, 사용 시 소각)하고 새 토큰을 같은 family로 발급한다. 이미 소각·폐기된 토큰이 재제출되면 그 family 전체를 폐기하고 `401 refresh_reuse`를 반환한다(도난 토큰 봉쇄).
- 게이트웨이 검증 분기(API 설계 §3-4 확장, §8 개정 항목): `Authorization: Bearer` 수신 시 JWT 헤더 `alg`와 payload `typ`으로 분기한다. `alg=HS256` + `typ="demo_session"` = §3-7(대칭 프로세스 키로 서명·exp·scope만). `alg=EdDSA` + `typ="access"` = 회원 세션(공개키로 서명·exp·scope·aud 검증 + `user_id` 주입, HMAC·nonce 미적용). `typ` 미존재 또는 `access_key` 클레임 존재 = §3 HMAC 경로(canonical·nonce·timestamp 전 검증). 세 경로 모두 통과 시 `(user_id, scope)` 인증 컨텍스트를 동일하게 주입하므로, 이후 주문·조회 핸들러는 인증 경로를 구분하지 않는다.

### 1-4. API 키 발급(봇·외부용과 분리)

- 회원 개인 API 키: 회원 세션 인증 상태에서 `POST /api/v1/keys`로 발급. 요청 wire scope는 API §3-2 어휘(`read_only`·`trade`)만 허용한다(`withdraw`는 데모 미사용, `admin`은 관리 평면 전용이라 발급 불가). 발급 서버는 wire scope를 DB `api_keys.scope` 저장 어휘로 매핑해 영속화한다(현재 두 정본의 어휘가 어긋나므로 통일이 선행 개정 대상이다, §8). `secret_key`는 발급 응답 1회만 평문 노출, 이후 `api_keys.enc_secret`에 AES-256-GCM 암호문으로 저장(기존 §3-2 모델 그대로). 회전·폐기는 기존 `POST /keys/{access_key}/rotate`·`DELETE /keys/{access_key}` 재사용.
- 봇 키와의 분리: 봇 키는 `users.kind='BOT'` 사용자에 귀속하고 시드 타임·관리 평면에서 발급한다. 회원 키는 `kind='HUMAN'`에 귀속한다. 두 종류 모두 `api_keys` 테이블을 공유하되 소유자 `kind`로 구분되고, rate limit 버킷(§2-5)도 계정 키 기준으로 동일 계상된다.

### 1-5. 회원 스코프·권한

- 회원 세션 scope 클레임은 `TRADE` 고정이다(§3-7 데모 세션 JWT의 scope 어휘를 상속). 자기 `user_id`의 주문 생성·취소·조회, 자기 계정·체결·원장 조회만 가능하다. 게이트웨이가 토큰의 `user_id`를 주입하고, 주문·계좌 핸들러는 바디·경로의 사용자 지정을 무시하고 주입된 `user_id`로만 조회·집행한다(타 회원 자원 접근 불가).
- 관리 평면(§3-6)은 별도 호스트·mTLS·`scope=admin` 키·2인 승인이라 회원 세션으로 도달 불가하다.
- `users.status`가 `SUSPENDED`·`CLOSED`면 로그인·주문을 거부한다(`403 account_suspended`). 상태 전이는 관리 평면 소관.

주의: 세션 scope 클레임(`TRADE`, 대문자, §3-7 상속)과 API 키 scope(`read_only`·`trade`, 소문자, §3-2)는 서로 다른 어휘 공간이다. 전자는 JWT payload 값, 후자는 키 발급 wire·DB 저장 값이다. 혼동을 막기 위해 두 어휘를 분리해 표기한다.

## 2. DB 추가

### 2-1. 마이그레이션 번호

다음 가용 V 번호로 추가한다. 로드맵상 인프라용으로 예약된 V 번호 뒤의 가용 번호다. 실제 번호는 마이그레이션 작성 시점의 최대 적용 버전+1로 확정하고 여기서 고정하지 않는다. 이하 편의상 `Vn__members.sql`로 표기한다. 기존 `users`·`api_keys`·`accounts`는 변경하지 않고, 신규 테이블만 더한다(코어 격리).

### 2-2. 신규 테이블 DDL

```sql
-- Vn__members.sql: 회원 인증·세션·프로필. 코어(매칭·저널·정산)와 격리.
SET timezone = 'UTC';

-- 자격 증명: users와 1:1 분리(인증 관심사 격리). 평문·가역 저장 금지.
CREATE TABLE user_credentials (
    user_id         BIGINT       PRIMARY KEY REFERENCES users(id),
    algo            VARCHAR(16)  NOT NULL DEFAULT 'ARGON2ID'
                    CHECK (algo IN ('ARGON2ID','BCRYPT')),
    password_hash   VARCHAR(255) NOT NULL,   -- Argon2id 인코딩 문자열(파라미터 내장). 가역 저장 금지
    pwd_updated_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    failed_attempts SMALLINT     NOT NULL DEFAULT 0 CHECK (failed_attempts >= 0),
    locked_until    TIMESTAMPTZ,             -- 온라인 브루트포스 백오프 잠금
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- 프로필: 표시명 등 비민감 정보.
CREATE TABLE user_profiles (
    user_id      BIGINT       PRIMARY KEY REFERENCES users(id),
    display_name VARCHAR(32)  NOT NULL,
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- 리프레시 토큰 패밀리(회전·재사용 탐지). raw 토큰은 저장하지 않고 SHA-256 해시만 저장.
CREATE TABLE auth_sessions (
    id          BIGINT       GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id     BIGINT       NOT NULL REFERENCES users(id),
    family_id   UUID         NOT NULL,          -- 로그인 1회 = 1 패밀리
    token_hash  CHAR(64)     NOT NULL UNIQUE,   -- SHA-256 hex
    prev_id     BIGINT       REFERENCES auth_sessions(id),  -- 회전 체인
    issued_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    expires_at  TIMESTAMPTZ  NOT NULL,
    used_at     TIMESTAMPTZ,                    -- 회전 시 소각 시각(단회용)
    revoked_at  TIMESTAMPTZ,                    -- 로그아웃·재사용 탐지 시 패밀리 폐기
    user_agent  VARCHAR(256),
    ip          INET,
    CONSTRAINT chk_expiry CHECK (expires_at > issued_at)
);
CREATE INDEX idx_auth_sessions_user   ON auth_sessions (user_id, expires_at);
CREATE INDEX idx_auth_sessions_family ON auth_sessions (family_id);

-- 가입 시 GENESIS 자금 발급의 멱등 기록. 재시도·복구 시 중복 발급 방지.
-- genesis_event_id는 시드 GENESIS와 서로소인 예약 네임스페이스(§2-4)에서 배정한다.
CREATE TABLE user_provisioning (
    user_id          BIGINT      PRIMARY KEY REFERENCES users(id),
    status           VARCHAR(16) NOT NULL DEFAULT 'PENDING'
                     CHECK (status IN ('PENDING','DONE')),
    genesis_event_id BIGINT      NOT NULL,   -- ledger_transactions.business_event_id로 사용. 예약 오프셋+user_id
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    completed_at     TIMESTAMPTZ,
    UNIQUE (genesis_event_id)
);
```

권한 경계: `app_role`은 위 4개 테이블에 SELECT·INSERT·UPDATE를 갖되, 잔고·원장 직접 DML은 여전히 없다(기존 §9 경계 유지). 자금 이동은 `post_ledger_transaction` EXECUTE 유일 경로.

### 2-3. 회원별 계정 프로비저닝과 초기 자금(GENESIS)

가입 트랜잭션은 다음 순서로 단일 DB 트랜잭션에서 실행한다. 자금 발급은 기존 원장 단일 경로를 그대로 쓴다.

1. `INSERT INTO users (email, kind) VALUES (:email, 'HUMAN') RETURNING id` (email UNIQUE가 중복 가입을 물리 차단).
2. `INSERT INTO user_credentials (user_id, password_hash, algo)`, `INSERT INTO user_profiles (user_id, display_name)`.
3. 전 ACTIVE 자산에 대해 회원 계정 2종 생성: `INSERT INTO accounts (owner_type,owner_id,purpose,asset_id) VALUES ('USER', :user_id, 'AVAILABLE', :asset), ('USER', :user_id, 'LOCKED', :asset)`. `trg_account_balance`가 각 계정의 `balances` 행(잔고 0)을 자동 생성한다.
4. `INSERT INTO user_provisioning (user_id, genesis_event_id) VALUES (:user_id, :genesis_event_id)`. `genesis_event_id`는 §2-4의 예약 오프셋 + `user_id`다(시드 GENESIS와 충돌 불가).
5. 초기 자금 게시: KRW만 시드한다.
   ```sql
   SELECT post_ledger_transaction('GENESIS', :genesis_event_id, jsonb_build_array(
       jsonb_build_object('account_id', :genesis_krw_account, 'asset_id', :krw,
                          'amount', '-100000000', 'entry_type', 'GENESIS'),
       jsonb_build_object('account_id', :user_krw_available, 'asset_id', :krw,
                          'amount',  '100000000', 'entry_type', 'GENESIS')));
   ```
   `ledger_transactions`의 `UNIQUE(business_event_type, business_event_id)`가 멱등을 물리 보증한다. 단, 이 보증은 `business_event_id` 네임스페이스가 시드 GENESIS와 서로소일 때만 성립한다(§2-4). 재시도로 같은 가입이 두 번 게시돼도 두 번째는 유니크 위반(23505)으로 차단돼 이중 발급이 불가능하다.
6. `UPDATE user_provisioning SET status='DONE', completed_at=now()`.

설계 결정.

- 시드 자산은 KRW 1억(데모 초기 자금)만. 암호화폐 계정은 잔고 0으로 선생성만 하고 GENESIS 발급은 하지 않는다(첫 매수로 획득). GENESIS·GATEWAY 소스 계정은 시스템 계정이라 `allow_negative`로 음수 보유가 정상이며(DB §6.1①), 회원 증가에 따라 GENESIS(KRW)가 누적 음수로 커지고 회원 AVAILABLE 합이 그만큼 양수로 커져 자산별 총합=0이 항상 성립한다.
- GENESIS 계정 경합: 다수 동시 가입이 단일 GENESIS(KRW) 행을 잠근다. 가입은 매칭 핫패스가 아니라 게이트 부하 대상이 아니지만, 대량 동시 가입이 관측되면 `FEE_INCOME`과 동일하게 `accounts.shard`로 GENESIS를 자산당 N샤드로 분산한다(발급 시 `hash(user_id)%N` 샤드 선택). 이는 계정 행 추가만으로 가능하고 원장·불변식에 영향이 없다.

### 2-4. GENESIS business_event_id 네임스페이스 예약

`ledger_transactions`의 멱등은 `UNIQUE(business_event_type, business_event_id)`다. `business_event_type='GENESIS'`는 시드 타임 초기 유동성 발급과 회원 가입 프로비저닝이 함께 쓰는 타입이므로, 두 발급원의 `business_event_id`가 겹치면 초기 회원 가입이 23505로 오작동한다. DB 정본은 GENESIS의 `business_event_id` 의미를 고정하지 않으므로, 여기서 네임스페이스를 예약해 서로소를 보장한다.

- 시드 GENESIS 범위: `business_event_id`를 `[1, SEED_GENESIS_MAX]`로 한정한다. `SEED_GENESIS_MAX`는 시드 스크립트가 발급하는 초기 유동성 이벤트 상한으로, 데모 규모에 여유를 둔 상수다(예: 1_000_000_000).
- 회원 프로비저닝 범위: `genesis_event_id = PROVISION_GENESIS_BASE + user_id`로 배정한다. `PROVISION_GENESIS_BASE`는 `SEED_GENESIS_MAX`를 넘는 예약 상수다(예: 1_000_000_000_000). `user_id`가 BIGINT 양수 identity이므로 두 범위는 서로소이고, `user_id` 단조 증가로 프로비저닝 내부 유일성도 성립한다.
- 이 예약을 DB 정본에 기록해야 "물리 보증" 주장이 네임스페이스 위에서만 성립하도록 성문화된다(§8 개정 항목). 대안은 `business_event_type` CHECK에 전용 타입(예: `PROVISION`)을 추가하는 마이그레이션이나, 이는 DDL CHECK 변경이라 예약 오프셋 방식보다 무겁다. 예약 오프셋을 정본으로 채택하고 CHECK 변경은 채택하지 않는다.

## 3. API 추가

공통: 모든 응답 `schema_version:"1.0"`. 리스트는 §2-2 엔벌로프. 에러는 §2-3 포맷. 신규 엔드포인트도 §2-5 rate limit·§2-1 규약(UTC ms, 금액 문자열, `application/json`)을 상속한다. 회원 인증 엔드포인트는 브라우저 전용이라 HMAC canonical·nonce를 요구하지 않는다(데모 세션과 동일).

### 3-1. 인증

| 기능 | 메서드·경로 | 인증 | rate limit |
|---|---|---|---|
| 가입 | `POST /api/v1/auth/signup` | 없음 | IP 5회/60s |
| 로그인 | `POST /api/v1/auth/login` | 없음 | IP·이메일 10회/60s + 계정 백오프 |
| 토큰 갱신 | `POST /api/v1/auth/refresh` | 쿠키 `rt` | IP 30회/60s |
| 로그아웃 | `POST /api/v1/auth/logout` | 쿠키 `rt` | 표준 |
| 내 정보 | `GET /api/v1/me` | 회원 세션 | 계좌 조회 버킷 |

가입 요청·응답.
```json
// POST /api/v1/auth/signup
{ "email":"trader@demo.local", "password":"demopass1", "display_name":"데모트레이더" }

// 201 (액세스 토큰 반환 + refresh는 Set-Cookie: rt=...; HttpOnly; Secure; SameSite=Strict)
{ "schema_version":"1.0",
  "access_token":"<JWT EdDSA>", "token_type":"Bearer", "expires_in":900,
  "user":{ "external_id":"9f2b7a4e-...", "email":"trader@demo.local",
           "display_name":"데모트레이더", "kind":"HUMAN" } }
```

로그인 응답은 가입과 동일 스키마(201 대신 200). 갱신은 쿠키 `rt` 제출로 새 `access_token` + 회전된 `rt` 쿠키를 받는다. 로그아웃은 제출된 refresh의 family를 폐기(`revoked_at`) 후 `204`. 인증은 쿠키 `rt` 기반이다. `/api/v1/auth/*`는 게이트웨이 인증 필터 제외 경로라 회원 세션 principal이 주입되지 않으므로, 로그아웃도 쿠키 `rt`로만 대상 family를 식별한다(쿠키가 `Path=/api/v1/auth`로 스코프돼 정상 흐름에 항상 실린다). `GET /me`는 `user` 객체 반환. `/me`는 회원 세션(EdDSA `kind=HUMAN`) 전용이라 데모·API 키 주체는 `403 out_of_scope`로 차단한다(비회원은 `user_profiles` 행이 없어 조회가 성립하지 않음).

### 3-2. 회원 API 키(선택)

| 기능 | 메서드·경로 | 인증 |
|---|---|---|
| 키 발급 | `POST /api/v1/keys` | 회원 세션 |
| 키 목록 | `GET /api/v1/keys` | 회원 세션 |
| 키 회전 | `POST /api/v1/keys/{access_key}/rotate` | 회원 세션(기존) |
| 키 폐기 | `DELETE /api/v1/keys/{access_key}` | 회원 세션(기존) |

```json
// POST /api/v1/keys  { "label":"my-bot", "scope":"trade" }
// 201 (secret은 이 응답에서만 평문 노출, 이후 조회 불가)
{ "schema_version":"1.0",
  "access_key":"AK_9f2b7a4e...", "secret_key":"<one-time-plaintext>",
  "scope":"trade", "label":"my-bot", "created_at":"2026-07-22T09:00:00.000Z" }
```
wire `scope`는 API §3-2 어휘 `read_only`·`trade`만 허용. 그 외는 `400 invalid_parameter`. 서버는 이를 DB `api_keys.scope` 저장 어휘로 매핑한다(어휘 통일은 §8 선행 개정).

### 3-3. 자산·거래내역(기존 재사용)

회원 세션 Bearer로 기존 인증 엔드포인트를 그대로 호출한다. 게이트웨이가 토큰 `user_id`를 주입하므로 스키마·엔벌로프 변경이 없다.

- `GET /api/v1/accounts`: 회원 전체 잔고(available·locked).
- `GET /api/v1/my/trades`: 내 체결(MAKER/TAKER·fee).
- `GET /api/v1/my/ledger`: 원장 내역. 가입 GENESIS 발급도 `entry_type='GENESIS'`로 이 목록에 노출된다(회원 관점 최초 입금).
- `GET /api/v1/orders/open`·`/orders/closed`: 미체결·체결완료 주문.
- `POST /api/v1/orders`·`DELETE /api/v1/orders/{id}`: 주문 생성·취소. `client_order_id` 필수 멱등키 규약(§2-4) 동일.

### 3-4. 신규 에러코드(§2-3 확장, §8 선행 개정)

기존 표에 회원 경로 코드를 추가한다. 관측성 필드(`trace_id`·`request_id`)는 동일.

| HTTP | name | 의미 |
|---|---|---|
| 400 | `weak_password` | 비밀번호 최소 길이(8자) 미달 |
| 400 | `invalid_email` | 이메일 형식 오류 |
| 401 | `invalid_credentials` | 이메일·비밀번호 불일치(존재 여부 비노출, 동일 메시지) |
| 401 | `refresh_reuse` | 소각·폐기된 리프레시 재사용, family 폐기 |
| 401 | `session_expired` | 리프레시 만료·부재 |
| 403 | `account_suspended` | `users.status` SUSPENDED·CLOSED |
| 409 | `email_taken` | 이메일 중복 가입 |
| 423 | `account_locked` | 로그인 실패 누적 백오프 잠금(+`Retry-After`) |
| 403 | `member_session_required` | 데모 세션으로 쓰기 시도(§0 읽기 전용 계약). 프론트는 이 코드를 받으면 오류 토스트가 아니라 로그인 유도를 띄운다 |

기존 `auth_throttled`(401)·`too_many_requests`(429)는 인증 엔드포인트에 그대로 적용한다. `invalid_credentials`는 계정 존재 여부를 드러내지 않도록 미가입 이메일과 오비밀번호를 동일 코드·동일 메시지·유사 지연으로 처리한다.

| `lib/store.ts` | `session: { user, accessToken } \| null` 슬라이스 + `setSession` 액션 신설. 세션 해제는 `setSession(null)`로 수렴(별도 clearSession 두지 않음) |
| `lib/api/datasource.ts` | `signup·login·logout·refresh·getMe` 메서드 추가. `subscribe`·REST 호출에 `Authorization: Bearer <access>` 자동 첨부. STOMP CONNECT 프레임에 동일 토큰. 401 수신 시 1회 silent `refresh` 후 재시도. refresh 실패 시 회원 세션 해제(`onMemberSessionChange`로 `setSession(null)` 통지). 회원 기원 쓰기(주문 생성·취소)는 데모 세션으로 재집행하지 않고 `session_expired`로 표면화해 재로그인을 유도하고, 읽기만 데모 세션으로 폴백해 둘러보기 연속성을 유지(§4-1) |
| `SimDataSource` | 로컬 가짜 세션(고정 데모 사용자) 반환. 인터페이스 동일 구현으로 화면은 sim·http 무관 동작 |
| `HttpStompDataSource` | 실제 Spring 인증 경로. refresh 쿠키는 브라우저가 자동 첨부(`credentials: 'include'`), access는 메모리 보관 |

토큰 보관: access는 자바스크립트 메모리(store)만, localStorage·sessionStorage 저장 금지(XSS 지속 노출 차단). refresh는 httpOnly 쿠키라 JS 접근 불가. 새로고침 시 `refresh`로 access를 재획득한다.

## 5. 상시 게이트 정합(다수 회원 + 봇 부하 동시 거래)

상시 게이트: 봇 부하·장애 주입에도 자산별 원장 합=0, 주문 중복·유실 0, 리더 kill 후 30초 내 자동 복구. 회원 다수가 동시 거래해도 이를 유지하는 근거.

- 계정 격리: 회원마다 독립 `account_id`의 AVAILABLE·LOCKED 계정을 갖는다. 거래가 만지는 상태는 해당 회원 계정 + 상대 계정 + FEE_INCOME + 마켓 오더북뿐이고, 회원 간 공유 가변 상태는 오더북 하나다. 오더북은 매칭 엔진 단일 라이터가 결정론으로 직렬화하므로, 회원 수·봇 수가 늘어도 체결 순서는 command_journal 순서로 유일하게 정해진다. 회원 트래픽은 봇 트래픽과 동일한 주문 커맨드 흐름이라 게이트 관점에서 부하원의 종류만 늘 뿐 경로가 갈라지지 않는다.
- 잠금 순서: 모든 자금 이동이 `post_ledger_transaction` 단일 경로를 지나고, 내부에서 `balances`를 `account_id` 오름차순으로 잠근다. 참여 회원·봇이 몇이든 전역 잠금 순서가 하나라 데드락이 없다. 가입 프로비저닝(§2-3)도 같은 함수를 경유해 동일 순서를 따른다.
- 자산 보존: 회원 자금은 전부 GENESIS 발급(소스 계정 음수, 회원 AVAILABLE 양수, 합=0)에서 시작하고, 이후 예약·체결·수수료도 전부 합=0 분개다. 반올림 잔차는 자산별 마지막 FEE leg가 흡수한다. 따라서 회원이 아무리 많아도 자산별 전 계정 원장 총합=0(DB §6.1①)이 항상 성립한다.
- 복구·재생 무영향: 가입·자금 발급은 매칭 커맨드가 아니라 원장 트랜잭션이라 `command_journal`에 들어가지 않는다. 복구는 스냅샷 + 저널 재생으로 오더북을 재구성하고, `balances`는 append-only 원장에서 재계산한다. GENESIS 발급은 원장에 영구 기록돼 재생·재빌드로 보존된다. 회원 세션·리프레시 테이블은 파생 데이터라 손실돼도 재로그인으로 복구되며, 코어 복구 RTO에 기여하지 않는다.
- 멱등 보증: 가입 자금 발급은 `ledger_transactions.UNIQUE(business_event_type, business_event_id)`로 멱등이라, 페일오버 중 가입 재시도가 있어도 이중 발급이 없다. 이 멱등은 §2-4의 네임스페이스 예약이 시드 GENESIS와 서로소를 보장할 때만 성립한다. 이 경로는 엔진 기원 쓰기가 아니므로 fencing(epoch)이 아니라 이 유니크 멱등이 정합성 보증 수단이다.

하네스 반영: 부하 프로파일에 "회원 계정 N명이 봇과 동시 주문" 시나리오를 추가하고, 기존 불변식 검증기(자산 합=0, 중복·유실 0)와 RTO 측정 체인을 그대로 상시 실행한다. 회원 경로는 새 불변식을 요구하지 않고 기존 게이트를 재사용한다.

## 6. 보안

- 인증 저장: 비밀번호는 Argon2id(+페퍼) 해시만(§1-2). 리프레시 토큰은 SHA-256 해시만 DB 저장, raw는 httpOnly·Secure·SameSite=Strict 쿠키로만 존재. 액세스 토큰은 브라우저 메모리만, 영속 저장 금지. API 키 `secret_key`는 AES-256-GCM 암호문 저장, 발급 1회만 평문 노출(기존 §3-2).
- 토큰 서명 키: 회원 액세스 토큰은 EdDSA 비대칭 서명이다. 개인키는 M2 인증 발급자 프로세스에만 상주하고 시크릿 관리소(.env / Docker Secret / K8s Secret)에서 주입한다. 게이트웨이·M3 community-api는 공개키(JWK)로 검증만 하므로 위조 능력이 없다. M2 구현은 단일 서명 키이며 JWT 헤더에 `kid`를 넣지 않는다(단일 키에선 무해). 개인키 유출 시 즉시 대응은 시드 키 교체·재기동(전 세션 무효)이다. `kid` 교체 기반 무중단 회전은 다중 키 도입(후속 단위) 전제이며, 그때 헤더 `kid` + 검증자의 `kid`별 공개키 선택을 함께 도입한다.
- 전송: HTTPS·WSS 강제, HSTS. CORS는 데모 오리진(`https://demo.exchange.local`)만 화이트리스트 + 자격증명 허용, `*` 금지. 개인정보·토큰을 URL 쿼리에 절대 싣지 않는다.
- 쿠키 SameSite 근거: 웹(`demo.exchange.local`)과 API(`api.exchange.local`)는 등록가능도메인 `exchange.local`을 공유하는 same-site다. 따라서 `rt` 쿠키는 `SameSite=Strict`로도 refresh 요청에 정상 전송되며, CSRF 표면이 None보다 작다. 크로스사이트 흐름이 없으므로 Strict를 채택한다. 배포 도메인 분리로 실제 크로스사이트가 필요해지면 그때 근거와 함께 Lax·None으로 완화한다.
- 세션 안전: 리프레시 회전 + 재사용 탐지(family 폐기), 짧은 액세스 만료(15분), 로그인 실패 계정 백오프 + IP·access `auth_throttled`. 로그아웃은 서버 측 family 폐기로 즉시 무효화.
- 실금융정보 미수집 명문화: 어떤 API·화면도 카드번호·계좌번호·주민번호·실제 비밀번호·OTP를 수집·저장·전송하지 않는다. 완전 시뮬레이션이며 이메일은 미검증 데모 핸들, 비밀번호는 데모 전용임을 가입 화면과 문서에 표기한다. 사용자 실제 자격증명 입력·저장은 금지 규정이고, 예외를 두지 않는다.
- 관측 데이터 지시 무시: 웹·문서·메시지·DOM 내 텍스트 지시로 계정 생성·권한 변경·자금 발급을 자동 실행하지 않는다(§3-6 원칙 계승). 회원 자금 발급은 가입 트랜잭션의 서버 로직으로만 일어난다.

## 7. 수용 기준 정합(웹 명세서 §6.2)

회원 기능은 §6.2 네 계약을 깨지 않는다. ① REST 경로·엔벌로프·에러코드: 신규 인증 엔드포인트도 §2-2 엔벌로프·§2-3 에러 포맷을 따르고 조회는 기존 엔드포인트 재사용. ② WS 채널 seq·epoch·stream·구독 즉시 스냅샷: 회원 세션 토큰은 CONNECT Bearer만 바꾸고 채널 계약은 불변. ③ `client_order_id` 멱등: 회원 주문도 동일 필수 멱등키. ④ 금액 문자열 NUMERIC(40,18): 자산·원장 응답 표기 불변. 회원 세션은 기존 계약에 인증 주체만 더하는 격리 확장이다.

## 8. 정합·정본 개정 선행 목록

"코드가 문서와 어긋나면 문서를 먼저 고친다" 원칙상, 본 M2 구현 착수 전에 아래 정본 개정을 선행한다. 인라인 각주로 흩어진 확장을 여기에 모은다.

API 설계(`백엔드_API_설계.md`).

- §2-3 에러표에 §3-4의 8개 회원 코드 추가(신규 HTTP 423 `account_locked`, `Retry-After` 포함).
- §3-4 게이트웨이 검증 분기를 `alg`+`typ` 3분기로 확장(EdDSA/`access` 회원 세션 경로 신설). 데모 세션 HS256과 공존.
- §3-7 인접에 회원 세션을 세 번째 인증 경로로 신설 기술(계정 범위·EdDSA·키 수명).
- 신규 엔드포인트 명세: `/api/v1/auth/{signup,login,refresh,logout}`, `/api/v1/me`, `/api/v1/keys`(회원 발급).
- API 키 wire scope 어휘와 DB `api_keys.scope` 저장 어휘 통일. 현재 API §3-2는 `read_only|trade|admin|withdraw`(소문자), DB CHECK는 `READ|TRADE|WITHDRAW`(대문자)로 어긋난다. 매핑 규칙 또는 단일 어휘를 정본에 확정.

DB 설계(`백엔드_DB_설계.md`).

- GENESIS `business_event_id` 네임스페이스 할당 기록(§2-4): 시드 GENESIS `[1, SEED_GENESIS_MAX]`, 회원 프로비저닝 `PROVISION_GENESIS_BASE + user_id`. 두 상수와 서로소 근거를 명시.
- 신규 테이블 4종(`user_credentials`·`user_profiles`·`auth_sessions`·`user_provisioning`)을 다음 가용 V 마이그레이션으로 등재. 기존 `users`·`api_keys`·`accounts` 무변경.

M3 게시판(`community` 설계).

- §2.4 community-api의 회원 토큰 검증을 공개키(EdDSA JWK) 검증으로 확정. 대칭 비밀 공유 금지. M2가 배포하는 공개키만 소비.
- (미결 이관) M3 `member_profile` 프로젝션의 표시명 갱신 소스. 현재 M2 가입 트랜잭션은 아웃박스 이벤트를 발행하지 않는다. M2에 회원 생성·변경 아웃박스 이벤트를 신설할지, M3가 다른 경로로 대체할지 M2·M3 상호 정합으로 확정. 본 M2 초안 범위에서는 아웃박스 미포함이므로, 도입 시 별도 개정으로 처리.

## 반영한 비평

- (high) 회원 토큰 HS256(대칭) 확정이 M3 community-api 로컬 검증과 충돌해 게시판이 TRADE 토큰 위조 키를 갖는 문제: 회원 액세스 토큰을 EdDSA(비대칭)로 변경(§1-3, §6). 개인키는 M2 발급자에만, 게이트웨이·community-api는 공개키 검증만. `aud`로 수신 평면 명시(방어 심화). §3-4 분기를 `alg`+`typ`로 확장. M3 §2.4 공개키 검증 정합을 §8에 선행 개정으로 등재.
- (medium) 가입 GENESIS 멱등을 `UNIQUE(GENESIS, user_id)`로 단언하나 시드 GENESIS와 `business_event_id` 네임스페이스 분리 근거 부재: §2-4 신설로 시드 범위 `[1, SEED_GENESIS_MAX]`와 회원 범위 `PROVISION_GENESIS_BASE + user_id`를 서로소로 예약. `genesis_event_id`를 예약 오프셋 값으로 배정하도록 §2-2 DDL 주석·§2-3 게시 호출·§5 멱등 근거를 수정. DB 정본 기록을 §8에 등재.
- (low) 영어 대화체 서문(AI 어투·개조식 위반): 삭제하고 제목·정본 의존부터 시작.
- (low) refresh 쿠키 `SameSite=None`이 과도: same-site 도메인(`exchange.local`) 근거로 `SameSite=Strict`로 조임(§1-3, §3-1 예시, §6). 크로스사이트 전환 시 완화 근거 명시 조건 병기.
- (low) API 계약 확장이 인라인 각주로 분산: §8 정합·정본 개정 선행 목록 신설(에러표·§3-4 분기·회원 세션 신설·신규 엔드포인트·DB 네임스페이스·scope 어휘·M3 정합).
- (low) 회원 API 키 scope 어휘 대문자(DB CHECK) 사용이 API §3-2 소문자와 불일치: wire scope를 API §3-2 어휘(`read_only`·`trade`)로 통일(§1-4, §3-2), DB 저장 어휘 매핑 명시, 두 정본 어휘 통일을 §8 선행 개정으로 등재. 세션 scope 클레임(`TRADE`, §3-7 상속)과 키 scope 어휘를 분리 표기(§1-5).

주: admin·board 문서 관련 비평(관리 BFF 반결탁, member_profile 이벤트 소스, popular 커서 안정성, 관리 역할 수 불일치, 세 문서 공통 영어 서문)은 각 문서 소관이므로 M2에는 반영하지 않았다. 단, member_profile 이벤트 소스와 community-api 공개키 검증은 M2와 상호 정합이 필요해 §8에 이관 항목으로 남겼다.
