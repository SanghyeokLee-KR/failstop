# 15분 라이브 데모 대본

> 이 대본의 명령은 `$env:EXCHANGE_HOME` 를 쓴다. 시작 전에 한 번 지정한다.
> `$env:EXCHANGE_HOME = 'C:\dev\exchange'` (설정 근거는 실행_가이드.md 1-1 절)


대상: 고가용성 가상 암호화폐 거래소 캡스톤 발표.

핵심 판정.

- 체결 무결성: 자산별 원장 합 0, 저널 gap 0, 중복 주문·중복 체결 0.
- 자동 복구: 리더 kill 후 epoch 정확히 +1, 사람 개입 없이 체결 재개, RTO 30초 미만.
- 판정 원천: DB 원본 SQL 위반 행 0, Prometheus 시계열, k6 exit code.

## 0. 대본 사용 조건

### 0-1. 문서 성격

- 15분 대본: M4 배선 완료 후 사용하는 최종 목표 대본.
- 7~8분 대본: 현재 저장소에서 검증된 E4·E9·SQL만 사용하는 오늘 버전.
- 15분 대본의 시각과 순서: 확정 타임라인 그대로 고정.
- 대시보드: 관찰 보조 수단. 최종 판정은 DB 원본과 exit code.

### 0-2. 현재 검증된 범위

- E4 리더 kill: epoch+1 승격, 저널 재생, 체결 재개, 구 epoch stale append 0행.
- 불변식: C01~C23 SQL과 앱 검증 카탈로그. C16·C17의 라이브 원천은 2026-08-30에 배선했다(실측(2026-08-30 15:40) `loadtest_acks` 6,065행, `recovery_runs` 15행. **재기동마다 늘므로 발표 당일 다시 받는다**). 0행은 미배선이 아니라 그 주행에 판정 대상이 없었다는 뜻이다.
- E9 멱등성: 커밋 응답 절단 뒤 중복 NEW 주문 0, 클라이언트 수렴.
- E8 앱 장애 격리: Chaos Monkey assault와 서킷브레이커 회귀 테스트.

키를 발급했으면 프리플라이트를 돌린다. 이것이 §0-3 진입 조건의 실행 경로다. 조회 200과 전 키의

만든다. 기능 실패와 용량 실패가 같은 지표(`http_req_failed`)에 합산되므로 이 단계를 건너뛰면
401·502를 용량 부족으로 오독한다(검증설계 §2-4 5항, 실측 2건).

```powershell
docker compose --env-file harness/.env.chaos --profile load run --rm chaos-preflight
"PREFLIGHT_EXIT=$LASTEXITCODE"
```

종료코드가 0이 아니면 부하를 돌리지 않는다. 401이면 키 재발급, 502·`no live upstreams`면

“무결하다는 표현을 한 숫자로 뭉개지 않습니다. 자산 보존은 C01, 잔고와 원장 정합은 C02, 명령·이벤트 유실은 C05·C06, 중복 접수는 C07·C07P, 중복 체결은 C08로 나눠 반증합니다. 정산은 PostgreSQL 복식부기 함수와 지연 제약 트리거를 거치므로 불균형 거래는 커밋 단계에서 롤백됩니다. 라이브 결과는 이 위반 쿼리들이 모두 0행일 때만 통과입니다.”

- SQL: C01 자산별 `SUM(amount) HAVING SUM(amount) <> 0`.
- SQL: `SELECT * FROM balance_ledger_check WHERE mismatch;`.
- SQL: C05·C06 gap 계산.
- SQL: C07P·C08 중복 조회.
- 패널: 대시보드 1 자산별 원장 합.

### 2-3. “왜 Redis 안 쓰고 DB 리스냐”

#### 30초 답변

“리더를 정하는 곳과 실제 돈을 쓰는 곳이 다르면 두 시스템 사이 원자성이 필요합니다. 이 프로젝트의 권위 데이터는 PostgreSQL 원장과 저널이므로 리더 리스와 fencing epoch도 같은 DB에 둡니다. 승격과 실제 쓰기가 같은 epoch 조건을 공유해 stale 쓰기를 0행으로 막습니다. Redis는 후보 조율이나 알림에는 쓸 수 있지만 리더십 권위는 아닙니다. Redis 장애가 거래 리더를 바꾸지 않게 한 선택입니다.”

#### 그 자리에서 띄울 증거

```sql
SELECT holder, epoch, lease_until, lease_until > clock_timestamp() AS alive
FROM leader_lease WHERE resource='matching-engine';

SELECT fencing_epoch, count(*)
FROM event_journal GROUP BY fencing_epoch ORDER BY fencing_epoch;
```

- 패널: 대시보드 2 `exchange_leader_epoch`, 리더 소유권.

### 2-4. “단일 라이터면 확장은?”

#### 30초 답변

“단일 라이터는 전체 서비스가 한 스레드라는 뜻이 아닙니다. API·조회·웹소켓 노드는 수평 확장하고, 한 주문 순서가 필요한 매칭 파티션만 단일 라이터로 둡니다. 현재 캡스톤은 전 마켓 하나의 라이터로 결정론과 장애 복구를 먼저 증명합니다. 다음 확장 단위는 마켓 샤드입니다. 샤드마다 단일 라이터와 독립 저널을 두면 순서 보장은 유지하면서 병렬 처리할 수 있습니다. 현재는 큐 상한과 429로 용량 초과를 명시적으로 제어합니다.”

#### 그 자리에서 띄울 증거

- 패널: 대시보드 3 요청률, 수용 요청 p99, 429, 큐 깊이.
- SQL: `SELECT max(seq), count(*) FROM command_journal;`.
- 설명: 마켓별 샤딩은 후속 확장안이며 현재 구현으로 주장하지 않음.

### 2-5. “CAP에서 뭘 포기했나”

#### 30초 답변

“거래 쓰기 경로는 네트워크 분할에서 일관성을 택합니다. 구 리더가 DB 권위를 잃으면 쓰기를 계속 받지 않고 503 또는 429로 거부합니다. 새 리더가 epoch를 올린 뒤에만 쓰기가 재개됩니다. 따라서 분할 순간의 일부 가용성을 포기하고, 이중 체결과 이중 원장 기록을 막습니다. 클라이언트는 같은 `client_order_id`로 재시도해 기존 결과로 수렴합니다.”

#### 그 자리에서 띄울 증거

- E5 출력: `이중 쓰기(stale): 0`, epoch 정확히 +1.
- SQL: 워터마크 이후 구 epoch 저널 행 수 0.
- 패널: 대시보드 2 리더 교대, 대시보드 3 503·429 구간.

### 2-6. “그거 그냥 재시작 아닌가”

#### 30초 답변

“재시작만으로는 누가 새 리더인지, 메모리 오더북이 이전 상태와 같은지, 구 리더가 다시 쓰지 못하는지 설명할 수 없습니다. 여기서는 다른 프로세스가 epoch를 1 올려 권위를 얻고, 스냅샷과 저널 tail로 상태를 복원한 뒤 체결을 재개합니다. 복귀한 구 프로세스는 이전 epoch라 쓰기 0행입니다. 재생 창이 비어 `recovery_runs`가 0행이면 `matched=true`를 현장 증거로 주장하지 않고, 스냅샷 등가 통합테스트 결과를 함께 제시합니다.”

#### 그 자리에서 띄울 증거

- SQL: `leader_lease` old/new epoch.
- SQL: `harness.failover_runs` RTO·RPO·verdict.
- SQL: `recovery_runs`의 `fp_replay`, `fp_live`, `matched`.
- 현재 축소판: `SnapshotEquivalenceIntegrationTest`, `SnapshotRecoveryIntegrationTest` 결과.

### 5-3. 실제 리더 확인 절차

1. DB 권위 행 조회.


판정.

- 행 1개.
- `alive=true`.
- holder 빈 문자열 아님.
- epoch 발표 사전 기록값과 일치.

2. holder UUID를 노드 로그와 대조.

```powershell

```

판정.

- 결과가 `chaos-api-1` 또는 `chaos-api-2` 중 하나.

3. 두 노드 상태와 로그를 대조.

```powershell

Invoke-RestMethod http://localhost:28080/harness/v1/status | ConvertTo-Json -Depth 4

```

4. kill 요청 target을 검출값으로 생성.

```powershell
$issueTarget = $leader
if (-not $issueTarget) { throw 'kill target 미확정' }
```

5. kill 직전 재확인.

```powershell
$leaderAgain = Get-LeaderContainer
if ($leaderAgain -ne $issueTarget) { throw "리더 변경 감지: $issueTarget -> $leaderAgain. 승인 토큰 재발급 필요" }
```

승인 토큰은 action과 target에 바인딩되므로 리더가 바뀌면 기존 토큰을 사용하지 않는다.

## 6. 발표자가 지켜야 할 표현

- “대시보드가 정상이다” 대신 “DB 위반 쿼리가 0행이다” 사용.
- “무손실이다”는 C16 원천 행수가 0보다 클 때만 사용.
- “재생이 동일하다”는 `recovery_runs`가 존재하고 `matched=true`일 때만 사용.
- “RTO”와 내부 downtime을 구분.
- “10배 처리했다” 대신 “10배 도착률에서 수용 요청 SLO와 명시적 429를 유지했다” 사용.
- “HA가 완성됐다” 대신 “단일 PostgreSQL 장애 도메인 안에서 앱 리더 페일오버를 증명했다” 사용.
- 실패·SKIP을 PASS로 바꾸지 않음.
