# 실서비스 준비도 감사

## 개요

### 방법

배포 준비도(production readiness) 렌즈로 코드·DDL·정본 문서·테스트를 대조했다. 데모·시뮬레이션에서는 은폐되나 실서비스 배포(다중 노드, `NEXT_PUBLIC_DATASOURCE=http`, LB·프록시 종단, 부하·페일오버 상시 발생) 조건에서 표면화되는 결함에 초점을 둔다. 렌즈는 인증·인가 경계, 입력 검증, 레이트리밋·남용, 데이터 무결성, 오류 복원력, HA 복구, 관측성·운영, 성능 핫패스, 시크릿·설정, API 계약 일관, 프론트 상태·UX다.

critical·high 후보는 인용 file:line을 원본과 직접 대조하고, 재현 경로·계약 조항·완화 수단·잔존 방어를 교차 확인하는 적대적 재검증을 거쳤다. 재검증에서 프레이밍 과장이 확인된 항목은 심각도를 하향했다(다수 항목 high→medium, 일부 →low). 심각도는 재검증 후 확정값이다.

### 검증 제약

읽기 전용·빌드 금지 제약으로 `gradle build`·`gradlew test`·`npm run build`·`check-style.ps1`은 실행하지 않았다. 판정은 소스·정본·테스트 소스의 정적 대조에 근거한다. 레이스·부하 계열은 코드 경로와 격리 수준으로 재현 시나리오를 구성해 확인했다.

### 원장 정합

확인된 결함 중 코어 원장·저널·자산 정합, 재생 결정론, RPO=0, 불변식에 닿는 것은 없다. 결함은 레이트리밋 약화·가용성·표시 피드 정지·관측성·설정 하드닝에 국한된다. 이 때문에 critical은 0건이다.

### 오류 복원력

- 가상 스레드 활성 + Hikari 풀 미튜닝으로 부하 시 커넥션 기아. spring.threads.virtual.enabled=true로 동시성이 사실상 무제한이나(:4) main 설정에 hikari 튜닝이 없어 maximumPoolSize 10·connectionTimeout 30s 기본. 수천 가상 스레드가 풀 10을 경합하면 30초 대기 후 획득 실패가 연쇄하고 위 항목대로 500으로 표출. awaitRow가 초당 약 50회 커넥션을 차용해 압박 배가. 제안: 운영 프로파일에 maximumPoolSize 명시·connectionTimeout 2~3s 하향, awaitRow 알림 기반 검토. - statement/lock 타임아웃·요청 타임아웃 부재로 잠금 대기가 스레드·커넥션 무한 점유. main 설정·JDBC 경로에 statement_timeout·lock_timeout·setQueryTimeout이 없다. ## 실서비스 배포 전 반드시 고칠 것

배포 승인 게이트로 취급한다. 아래는 데모에서 은폐되나 실 배포에서 즉시 사고로 이어지는 항목이다.

1. XFF 신뢰 경계 확립(High·Medium 다수의 공통 뿌리). forward-headers-strategy 또는 RemoteIpValve로 LB를 신뢰 프록시로 지정하고 원시 최좌측 파싱을 제거한다. 이것 하나로 signup·demo 레이트리밋 우회, inet 캐스트 500·고아 계정, 데모세션 남용이 함께 닫힌다. 채택 IP는 inet 사전 검증한다.
2. 주문 경로 계정 토큰버킷(High). 단일 라이터 엔진 앞 유일한 유량 방벽이다. batch는 원소 수만큼 차감한다. 관리 평면 버킷(Medium)도 함께.
3. http 어댑터 관리 응답 언랩·매핑(High). 미수정 시 실 배포 관리 콘솔 전체가 진입 즉시 크래시한다.
4. trade·candle 재동기화 seq 도메인 정합(High). 미수정 시 재연결마다 웹 메인 산출물의 체결·차트가 리로드 전까지 정지한다. 회귀 테스트를 ticker와 별도로 추가한다.
5. 시크릿 fail-fast + 프로파일 게이트(Medium). 비-dev 기동에서 마스터키·페퍼·세션 시드 미주입 시 부팅을 중단한다. 무성 인증 붕괴를 배포 시점에 차단한다.
6. 커넥션 풀·타임아웃 명시 + Transient 오류 503 매핑(Medium). maximumPoolSize·connectionTimeout·statement_timeout·lock_timeout을 설정하고 일시 DB 장애를 503+Retry-After로 신호한다. 세션 TZ는 connection-init-sql로 UTC를 고정한다. pgjdbc가 JVM 기본 zone(배포 KST)을 세션에 전파하면 Flyway가 빌린 커넥션의 파티션 경계 해석이 배포 zone에 의존한다. 세션 상한은 Flyway에도 상속되므로 데이터 무거운 마이그레이션(V8·V10)은 SET LOCAL로 트랜잭션 한정 해제한다.
7. actuator 노출 축소(Medium). 고객 평면 8080에서 prometheus·metrics를 제거하거나 포트를 분리한다. 자산 보존 신호·내부 지표 유출을 막는다.
8. 프론트 에러 상태·바운더리(Medium). history·assets·OrderPanel의 로드 실패 분기와 app/error.tsx·global-error.tsx를 추가한다. 정적 export 백지·영구 스켈레톤을 없앤다.

성능·HA 항목(trades feeStats 인덱스, tradeFee·depth·candles 재조회, 파티션 롤오버, 스냅샷·readiness 배선)은 프리론치 데이터 규모에서는 유예 가능하나, 저널·체결 누적이 시작되면 RTO SLO·조회 지연이 구조적으로 악화되므로 소크·부하 단계 전 배선하거나 SLO 초과 임계를 운영 한계로 명문화한다.
