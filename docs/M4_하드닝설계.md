## 1. 카오스 매트릭스 전체 E1~E9 실행 계획

공통 프로토콜(전 실험): ⓐ 사전 권위 run(`POST /harness/v1/invariants/run`, run_id=B) 전 체크 green + 워터마크(`max(command_journal.seq)`, `max(event_journal.event_seq)`) 기록 + `TRUNCATE harness.loadtest_acks` → ⓑ 주입(창 (t0,t1) 설정 파일 기록, Grafana annotation) → ⓒ 무개입 관찰 → ⓓ 사후 권위 run(run_id=A) + `recovery_runs.matched` + RTO 측정 → ⓔ PASS 판정.

판정 원천은 전부 기계다. 페일오버 계열(E2·E4·E5·E6·E7)은 `harness.failover_runs.verdict='PASS'`, 비페일오버 계열(E1·E3·E8·E9)은 사후 권위 run의 CRITICAL 체크 0행 + 실험별 지표.

심각도 카탈로그 권위(충돌 정정): CRITICAL/HIGH/WARN 분류의 정본은 `하네스_검증설계.md` §4-3(위반 시 처리 표)이며, 실제 구현은 `server/app/src/main/java/kr/exchange/harness/InvariantCheck.java`의 `Severity`·`Scope` 열거가 정본을 실체화한다. 구현된 카탈로그 기준.
- CRITICAL·SCHEDULED(상시·soak 대상): C01·C02·C05·C06·C07·C07P·C08·C13B·C17·C18.
- CRITICAL·AUTHORITATIVE_ONLY(실험 사후 권위 run 한정, 상시·soak 제외): C13A·C16. C13A는 append와 정산 물질화 사이의 비동기 창을 상시 스케줄이 오탐하므로 큐 드레인된 권위 run 한정이다(복구 RTO 설계 §3-c).
- HIGH: C14(SCHEDULED)·C19(AUTHORITATIVE_ONLY). WARN: C15/C90(파티션 가용성).
- 검증설계 §4-3이 CRITICAL로 열거하는 C04·C09는 현 구현에 미실현(enum 부재)이라 상시 판정 대상 아님. 구현되면 CRITICAL·SCHEDULED로 편입.
- `하네스_CICD_IaC.md` §5-6 알람 라우팅은 critical=C01·C02·C04~C09·C14로 열거해 §4-3과 충돌한다(C09·C14를 CRITICAL로 승격, C17·C18 누락). 이는 CICD_IaC 문서 레벨 정정 대상(§7-3 문서 동결에 반영). 본 M4의 CRITICAL 게이트는 §4-3·구현 enum을 따른다.

## 2. Soak 2시간 이상 장기 검증

목적: 파티션 성장·메모리 누수·워터마크 검증기 장기 안정성을 데이터로 확인. 야간 CI 또는 발표 전 리허설 세션에서 무개입 2h+ 구동.

### 2-1. 구동

- [ ] 프로파일: normal 구성(MM/TAKER/TREND/NOISE 140봇), 전역 300 OPS, 무주입 2h 이상.
- [ ] 부하 원천: k6 `constant-arrival-rate` steady + 봇 플릿. 스파이크·카오스 없음.
- [ ] 관측: Prometheus 2h retention 이상, Grafana 시간창 2h로 확장한 별도 soak 뷰.
- [ ] 실행 스크립트 `harness/scripts/soak.ps1`: 타임라인·시드·환경변수 파일 기록(재현), 시작·종료 워터마크 캡처.

### 2-2. 판정(장기 불변)

- [ ] 무결성: soak 전 구간 `invariant_checks`에서 CRITICAL·SCHEDULED 체크(1절 심각도 카탈로그: C01·C02·C05·C06·C07·C07P·C08·C13B·C17·C18) `ok=false` 0행. C13A·C16은 AUTHORITATIVE_ONLY라 상시·soak 대상 아님, C14/C19는 HIGH라 별도 추적(0행 게이트 대상 아님).
      SQL은 check_name 필터로 CRITICAL 한정(HIGH/WARN 위반이 soak를 오탈락시키지 않게):
      ```sql
      SELECT check_name, count(*)
        FROM invariant_checks
       WHERE ok = false
         AND checked_at >= :soak_start
         AND check_name IN ('C01_ASSET_CONSERVATION','C02_BAL_VS_LEDGER','C05_CMD_GAPLESS',
                            'C06_EVT_GAPLESS','C07_DUP_ORDER','C07P_DUP_ORDER_JOURNAL',
                            'C08_DUP_FILL','C13B_ORDER_JOURNALED',
                            'C17_REPLAY_DETERMINISM','C18_FILL_PRICE_MAKER')
       GROUP BY 1;   -- = 0행
      ```
- [ ] 파티션 성장: command_journal(seq range)·event_journal(event_seq range)·trades(월 range) 파티션이 사전생성(premake) 일정대로 증가. DEFAULT 파티션 유입 0.
      `SELECT * FROM check_default_partitions();`(C15/C90) 유입 행 0. 위반 시 `CALL partman.run_maintenance_proc()` 자동 실행 확인.
- [ ] 워터마크 검증기: 1분 증분 스캔이 2h 내내 지연 없이 완주. 스캔 소요 상승 추세 없음(마감 파티션 합 캐시 `harness.invariant_partition_sums` 적재로 전량 SUM 회피).
- [ ] 메모리: `jvm_memory_used_bytes{area="heap"}` GC 후 저점(baseline)이 2h에 걸쳐 상승 추세 없음(누수 0). 오더북 depth·시퀀서 큐 유계.
      판정: 선형 회귀 기울기 근사 0(발표 자료에 heap baseline 시계열 첨부). OOM 킬 0.
- [ ] 백프레셔: `exchange_sequencer_queue_size` 안정, `hikaricp_connections_pending` 정상.
- [ ] 저널·재생 비용(스냅샷 도입 전 리스크 계량): soak 종료 시점 `max(command_journal.seq) - min(...)` 규모에서 승격 재생 소요를 1회 측정(E4를 soak 말미에 붙여 RTO 관측). 스냅샷 도입 후 재측정해 RTO 저널 크기 탈동조 실증(3-3과 연계).

### 2-3. 산출물

- [ ] soak 리포트: 시작·종료 워터마크, 파티션 수 추이, heap baseline 시계열, 스캔 소요 추이, CRITICAL 위반 0 확인. `harness.calibration_runs.details` JSONB에 요약 적재.

## 3. 성능 캘리브레이션과 병목 개선

전제: 단일 Windows PC + WSL2. 스파이크 목표는 절대값이 아니라 "기저 대비 10배 폭주에서의 무결성·백프레셔 증명"(`하네스_검증설계.md` §2-4).

### 3-1. 캘리브레이션 프로토콜(리허설 필수)

- [ ] steady 300 OPS 30분 구동 후 판정: 호스트 전체 CPU<60%, k6 프로세스 CPU<1코어, k6 내부 지연(`iteration_duration - http_req_duration` 중앙값)<5ms, PG fsync 대기·HikariCP pending 정상.
- [ ] 전부 충족 시 스파이크 배수 10x 확정. 미충족 시 기저 OPS 하향(예: 200) 후 그 10x를 상한으로 재정의.
- [ ] 부하기 격리: 1순위 k6 별도 머신(같은 LAN). 불가 시 전용 코어셋 고정 + 관측 스택 스파이크 창 샘플링 축소.
- [ ] 서명 비용: JCS 템플릿 치환 방식이 k6 CPU 지배 항목 아님을 캘리브레이션에서 확인.
- [ ] 결과(기저 OPS·스파이크 상한·머신 배치)를 `harness.calibration_runs`(base_ops·spike_cap·k6_host·details)에 적재, 발표 실험 조건 각주로 사용.

### 3-2. SLO 목표치(합격 기준)

| 지표 | normal | spike 10x | 원천 |
|---|---|---|---|
| 주문 API p95/p99 | <200ms / <500ms | 수용(2xx) 기준 p99<500ms | `exchange:order_latency:p95_1m`/`p99_1m` |

### 3-3. 병목 후보와 개선 방향

**(a) WS 게시 팬아웃**
- [ ] 증상 계량: 체결/초 대비 STOMP 게시 건수, `exchange_ws_clients` 채널별, 게시 지연. 스파이크 창에서 팬아웃이 매칭 스레드를 블록하는지 확인.
- [ ] 개선: 오더북 depth 갱신을 코얼레싱(N ms 창 내 최신 1건만 게시), 체결 스트림과 depth 스트림 분리, 게시를 매칭 코어 밖 프로젝션 스레드로 격리(코어 순수성 유지, `하네스_CICD_IaC.md` §5-2 계측 위치 규율).
- [ ] 판정: 스파이크 중 p99<500ms 방어, WS `ws_seq_gap{phase:steady}==0`.

**(b) candles 스캔**
- [ ] 증상 계량: 차트 조회(`GET /candles`)가 trades를 재스캔하는지, candles 테이블 조회 지연. PK=(market_id, interval, bucket).

- [ ] 판정: candles 조회 p99가 부하·데이터 성장과 무관하게 상한 내(회귀 없음). 증분 upsert가 정산 핫패스를 블록하지 않음(별도 소비자).

- [ ] 증상 계량: `post_ledger_transaction`의 seal 커밋 지연(`exchange_journal_append_seconds`), idx_ledger_txn 파티션 프로브 비용(파티션 수 증가 시).

- [ ] 판정: 파티션 수 증가에 따른 seal 경로 성능 회귀 없음(T6-G green).

**(d) 승격 재생(RTO 병목)**
- [ ] 증상: 저널 전량 재생이 RTO에 선형 반영(0-2 한계 2). soak 말미 E4 RTO로 계량(2-2).
- [ ] 개선: 스냅샷 도입(주기 `state_checksum` 스냅샷 + 스냅샷 이후 tail만 재생). 승격 절차 R1(스냅샷 로드)→R3(tail 재생)로 재생량 최소화.
- [ ] 판정: 스냅샷 도입 전후 RTO 비교, 저널 크기 증가에도 RTO<30s 유지(탈동조 실증). `recovery_runs.duration_ms`·`replayed_from_seq/to_seq`로 재생 구간 축소 확인.

### 3-4. 리더 인지 LB 라우팅(하드닝)

## 4. 관측성 완성

4장 증명 대시보드와 6종 알람을 파일 프로비저닝으로 완성. 판정 주체는 사람 눈이 아니라 알람 발화(임계)와 pg-proof SQL 직조회.

### 4-1. 대시보드(`observability/grafana/dashboards/`)

- [ ] ① 체결 무결성 증명: Stat `max(abs(exchange_ledger_imbalance))`(0=정상) · 자산별 imbalance 수평선 Timeseries · Stat 3연(중복 체결 0·유실 0·시퀀스 갭 0, pg-proof 직조회) · Table `SELECT check_name, ok, violated_rows, checked_at FROM invariant_checks ORDER BY checked_at DESC LIMIT 20`.
- [ ] ② 자동 복구 증명: Gauge `harness.failover_runs.rto_seconds`(RTO=T5-T0, 체결 재개 기준) vs 30s를 판정 원천으로 pg-proof 직조회 · 보조로 Gauge `exchange_failover_downtime_seconds`(내부 downtime=T2-T1, 감지·승격 구간, RTO 아님. RTO보다 작으므로 판정 원천으로 쓰지 않고 참고) · State-timeline `exchange_leader_is_leader{node}` · `exchange_leader_epoch` 계단 + kill annotation · `exchange:trades_per_second:rate1m` 사멸→부활 · Table 2장(`recovery_runs` 재생 지문 = fp_replay/fp_live/matched, `harness.failover_runs` = rto_seconds/rpo_records/verdict 이력) · replay rate.
- [ ] ③ 부하·SLO: k6 Remote Write 계열 · `exchange:slo_500ms_ratio_1m` · p95/p99 · 429 비율 · `exchange_sequencer_queue_size` · Resilience4j CB/RateLimiter.
- [ ] ④ 시스템: HikariCP active/pending · JVM heap/GC(soak heap baseline) · `exchange_ws_clients` · orderbook depth · Kafka lag · `up`/readiness.
- [ ] 프리셋: refresh 5s, 시간창 15m(soak 뷰는 2h). `allowUiUpdates:false`, 변경은 파일 수정 후 reload.
- [ ] pg-proof 데이터소스: `grafana_ro`, `invariant_checks`/`recovery_runs`/`harness.failover_runs`/`admin_audit_log` SELECT만. 비밀번호는 datasource YAML `$__file` 표기.

### 4-2. 알람(`provisioning/alerting/rules.yaml`, 그룹 interval 10s)

- [ ] `LedgerImbalance`: `max(abs(exchange_ledger_imbalance))>0` for 0s, critical.
- [ ] `DuplicateFill`: `increase(exchange_duplicate_fills_total[5m])>0`, critical.
- [ ] `InvariantViolation`: `max by(check_name)(exchange_invariant_violations)>0` for 30s. 라우팅은 1절 심각도 카탈로그(검증설계 §4-3·구현 enum)를 따른다. critical(SCHEDULED)=C01·C02·C05·C06·C07·C07P·C08·C13B·C17·C18 / warning=C14·그 외. C13A·C16은 AUTHORITATIVE_ONLY라 상시 게이지에 미노출. `하네스_CICD_IaC.md` §5-6의 critical=C01·C02·C04~C09·C14 열거와 충돌하므로 CICD_IaC 문서 정정 후 규칙 파일을 이 카탈로그로 고정.
- [ ] `OrderP99SloBreach`: `exchange:order_latency:p99_1m>0.5` for 2m, warning.
- [ ] RTO 30s 게이트(권위): 판정 원천은 `harness.failover_runs.rto_seconds`(=T5-T0, 검증설계 §5-1)이며 `verdict='PASS'`가 이를 포함. pg-proof 직조회 `SELECT count(*) FROM harness.failover_runs WHERE rto_seconds > 30 AND created_at >= :window_start;` = 0행으로 확정한다.
- [ ] `FailoverDowntimeExceeded`(보조 조기 신호): `max(exchange_failover_downtime_seconds)>30`, critical. 이 게이지는 내부 downtime(T2-T1)이라 RTO를 과소평가한다. downtime만으로 30s 게이트를 판정하지 않고(RTO 초과 미탐 위험), 위 rto_seconds 게이트를 정본 판정으로 병행. `하네스_CICD_IaC.md` §4-3/§5-5의 downtime 게이지=RTO 서술은 §5-1 RTO=T5-T0 정의와 충돌하므로 CICD_IaC 문서 정정 대상.
- [ ] `LeaderAbsent`: `absent(exchange_leader_is_leader==1)` for 15s, critical.
- [ ] 알람 발화 검증: 각 카오스 실험에서 해당 알람이 발화(예: E4에서 LeaderAbsent 순간 발화 후 해소)하고, 정상·soak 구간에서 무결성 알람 발화 0건.

### 4-3. 메트릭·파이프라인 마감

- [ ] 커스텀 메트릭 노출 확인(`하네스_CICD_IaC.md` §5-2 표): `exchange_trades_total`·`exchange_order_latency_seconds_*`·`exchange_failover_downtime_seconds`·`exchange_leader_epoch`·`exchange_ledger_imbalance`·`exchange_invariant_violations{check_name}` 등.
- [ ] 카디널리티 규칙 강제: `user_id`·`client_order_id`·`bot_id` 태그 금지. `check_name` 표준명은 `invariant_checks.check_name`(예: `C01_ASSET_CONSERVATION`)과 게이지 태그 일치.
- [ ] C16 외부 ACK 파이프라인 실배선(0-2 항목): 봇/k6 ACK 로그 → NDJSON → `loadtest_accounts` 조인 → `\copy harness.loadtest_acks`. 실험 시작 훅 `TRUNCATE harness.loadtest_acks` 선행. C16 판정 SQL 0행 = rpo_records=0.
- [ ] 카오스 annotation: 실험 시작 `POST /api/annotations`(tags 포함) → 복구 시 `PATCH`로 region 승격. 4장 전 대시보드 태그 구독형 마커.

## 5. 빈 환경 일괄 기동 검증

목적: V0~최신 마이그레이션 체인이 빈 PG17에 단독 적용되고, compose 1커맨드 기동으로 최종 데모까지 도달함을 실증. 완료 기준(ROADMAP M4)의 핵심.

### 5-1. 마이그레이션 체인(빈 PG17)

- [ ] `V0__roles.sql` → `V1__init.sql` → `V2__gateway_counters.sql` → `V3__observability_tables.sql` → `V4__harness_schema.sql` 순 무오류 적용.
- [ ] 신설 객체 존재 단언: `invariant_checks`·`recovery_runs`(V3), `harness.loadtest_accounts/loadtest_acks/invariant_partition_sums/calibration_runs/failover_runs`(V4).
- [ ] 회귀 **T6-F**: 빈 PostgreSQL 17에 V0부터 최신까지 Flyway 체인 한 번에 적용 성공 + 신설 객체 존재 단언. Testcontainers로 CI 고정.
- [ ] 권한 경계(Flyway 체인 산물 한정): `app_role`은 public append + harness 스키마 TRUNCATE, `harness_role`은 SELECT만. app_role 커넥션으로 원장·저널 UPDATE/DELETE 42501 또는 P0001. `grafana_ro`는 V0~V4 체인이 생성하지 않고 initdb `infra/pg/initdb/01-roles.sql`이 만드는 별도 LOGIN 롤(`하네스_CICD_IaC.md` §8 3주체 분리)이므로 여기 콜드스타트 마이그레이션 경계 단언 대상 아님. grafana_ro SELECT-only 검증은 5-2 initdb 프로비저닝 항목에서 확인.

### 5-2. compose 일괄 기동

- [ ] 데모 스택: `docker compose --profile full up -d --wait` 전 서비스 healthy. flyway-migrate exit 0 → seed exit 0 → api·bots·frontend healthy.
- [ ] 격리 하네스 스택: `harness/scripts/up.ps1`(bootJar 빌드 → 이미지 → compose up --wait).
- [ ] seed 멱등: GENESIS 입금이 정본 회계 경로(ledger_transactions txn_type=GENESIS, 합=0 페어 분개) 경유 → C01이 첫 순간부터 0행. 재실행 시 `ON CONFLICT DO NOTHING`.
      `SELECT asset_id, SUM(amount) FROM ledger_entries GROUP BY asset_id HAVING SUM(amount)<>0;` = 0행(기동 직후).
- [ ] 인증: bots·k6가 seed 완료 후 기동 → 인증 실패 구조적 부재. k6는 seed 산출물 키(`secrets/k6_keys.json`) 로드.
- [ ] initdb 프로비저닝 검증: `infra/pg/initdb/01-roles.sql`이 만든 `grafana_ro` LOGIN 롤이 존재하고 SELECT만 가능(관측 테이블 SELECT 성공, 원장·저널 INSERT/UPDATE/DELETE 42501). Flyway 체인과 분리된 initdb 산물이므로 콜드스타트 단언에서 별도 확인.

### 5-3. 데모 리셋

- [ ] 전체 볼륨 파기만 허용(선별 리셋 금지, append-only 원장·저널 부분 삭제는 계약 위반). `down -v` → `up -d --wait`.
- [ ] Grafana 대시보드는 파일 프로비저닝이라 리셋과 무관 재현, annotation 이력만 소실(리허설·본번 사이 의도된 초기화).

### 5-4. 콜드 스타트 판정 체크리스트

- [ ] 빈 환경 → 일괄 기동 → 봇 30분 시장 형성 → 캘리브레이션 통과 → 최종 데모 시나리오 1회 완주 → 사후 권위 run 전 체크 green을 무편집으로 재현.
- [ ] 재현 실패 지점(마이그레이션·시드·인증·기동 순서) 원인을 기계 로그로 귀속, 수동 개입 절차 0.
