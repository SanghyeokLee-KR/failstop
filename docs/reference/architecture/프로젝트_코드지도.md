# 코드 지도

기능을 수정할 때 어디서 시작하고 어떤 테스트를 볼지 정리한 문서다. 전체 동작은 [프로젝트 이해하기](../../reports/프로젝트_이해하기.md), 남은 작업은 [로드맵](../../ROADMAP.md)에서 읽을 수 있다.

기존 거래 경로는 2026-09-17에 조사했고, 09-18에는 정본 `codex/docs-linux-operations`의 Linux 운영·역할별 배포·관측·보고 경로를 추가했다. 09-23에는 주문 접수의 V47 판정, 정산 일시 오류 재시도와 학교 백업·경보·워치독 템플릿 경로를 더했다. 09-24에는 작업 브랜치 `claude/per-market-leader`의 마켓별 리더 S1·S2 경로(접수 락 대기 상한, V48 파티션 리스와 시장 도출 fencing, 불변식 C29)와 S3 경로(V49~V52, 접수 시점 예약과 P2 전환 함수, 정산 분기, 불변식 C14'·C31)를 더했다. 09-25에는 같은 브랜치의 S4 경로(파티션 단위 리스·승격·강등·팔로워, 라이터 부분 설치, 접수 경합 응답, V53)와 그 보정 S4b 경로(DB 장애 분류와 응답, 판정 없이 끝난 재생의 기록, 재전송 안전 표식)를 더했고, 이어 S5 경로(소유권 선검사, 마켓 힌트 헤더, 파티션 밖 취소의 인계와 V54, 한 번 더 읽기, 하네스 파티션 LB 파일)를 더했다. 이 경로는 main에 합치기 전이다. 참고 문서이며, 실행 검증의 조건과 한계는 [09-18 기록](../../measurements/20260918.md)에 있다.

## 저장소와 실행 진입점

S4b부터 DB에 닿지 못한 실패는 [DbOutageErrors](../../../server/app/src/main/java/kr/exchange/journal/DbOutageErrors.java)가 획득 실패·연결 끊김·자원 부족으로 가르고, `OrderGateway`는 V47 판정마저 DB에 닿지 못하면 `503`, 닿으면 `429`·`409`로 끝낸다(API 설계 §2-5-c). S5부터 인증 키 조회와 접수 전 읽기는 연결 끊김이면 [DbReadRetry](../../../server/app/src/main/java/kr/exchange/journal/DbReadRetry.java)로 한 번 더 읽는다 |

저널 커밋이 끝난 뒤에만 엔진에 명령을 전달한다. HTTP 응답은 주문 조회 결과에 반영되기를 기다리므로, 커밋과 응답 완료는 같은 시점이 아니다. 이 차이는 `OrderGateway`와 `EngineBridge`를 함께 읽어야 보인다.

정산을 바꾸려면 Java 코드뿐 아니라 DB 게시 함수와 제약조건도 봐야 한다. [Flyway 마이그레이션](../../../server/app/src/main/resources/db/migration/)은 작업 브랜치에서 V0부터 V54까지 55개이며, [DB 설계](../contracts/백엔드_DB_설계.md)가 테이블과 금액 계산 규칙을 설명한다.

마켓 없는 일괄 취소와 회원 폐쇄는 S5부터 파티션별로 나뉜다. `OrderGateway`가 게이트를 연 파티션의 주문은 직접 취소하고, 그 밖은 [OrderCancelHandoff](../../../server/app/src/main/java/kr/exchange/api/order/OrderCancelHandoff.java)가 [V54](../../../server/app/src/main/resources/db/migration/V54__order_cancel_requests.sql)의 인계 표 `order_cancel_requests`에 넣고 최대 5초 기다린다. 표의 넣기·점유·포기·끝내기·만료 문장은 [OrderCancelHandoffRepository](../../../server/app/src/main/java/kr/exchange/api/order/OrderCancelHandoffRepository.java), 소유 노드에서 행을 가져가 취소하는 작업자는 [CancelHandoffWorker](../../../server/app/src/main/java/kr/exchange/api/order/CancelHandoffWorker.java), 결과 합치기는 [BulkCancelTally](../../../server/app/src/main/java/kr/exchange/api/order/BulkCancelTally.java), 설정은 [CancelHandoffProperties](../../../server/app/src/main/java/kr/exchange/config/CancelHandoffProperties.java)(`exchange.order.cancel-handoff.*`)다. 회원 폐쇄의 미완료 판정은 [MemberAdminService](../../../server/app/src/main/java/kr/exchange/admin/MemberAdminService.java)가 인계 사유까지 센다. 규칙은 [DB 설계](../contracts/백엔드_DB_설계.md) §3.9·§5.4-d와 [API 설계](../contracts/백엔드_API_설계.md) §4-B-3·§6-E다.

## 저장과 복구

복구를 읽는 순서는 [PromotionCoordinator](../../../server/app/src/main/java/kr/exchange/engine/PromotionCoordinator.java), [EngineRecovery](../../../server/app/src/main/java/kr/exchange/engine/EngineRecovery.java), [ReplayService](../../../server/app/src/main/java/kr/exchange/journal/ReplayService.java)다. 승격 중에는 접수를 막고, 마켓별 스냅샷과 저널을 대조·재생한 뒤 접수를 연다. 평소 대기 서버의 추적은 [FollowerCatchUp](../../../server/app/src/main/java/kr/exchange/engine/FollowerCatchUp.java)이 맡는다. 작업 브랜치의 S4부터 이 셋은 파티션 단위다. [PartitionPlan](../../../server/app/src/main/java/kr/exchange/engine/PartitionPlan.java)이 모드에 따라 파티션과 마켓 대응을 내고(P1·P2는 `matching-engine` 하나), [PartitionLeases](../../../server/app/src/main/java/kr/exchange/engine/PartitionLeases.java)가 파티션별 리스 서비스를, [PartitionRuntime](../../../server/app/src/main/java/kr/exchange/engine/PartitionRuntime.java)이 파티션의 강등·fresh 재구성·참여를, [PartitionBreaker](../../../server/app/src/main/java/kr/exchange/engine/PartitionBreaker.java)가 차단기를, [PartitionAcquirePolicy](../../../server/app/src/main/java/kr/exchange/engine/PartitionAcquirePolicy.java)가 선호·유예 획득을 맡는다. 쓰기는 획득 때 만든 기간 [LeaderTerm](../../../server/app/src/main/java/kr/exchange/engine/LeaderTerm.java)의 epoch로 판정받고, 강등 사유는 [DemotionReason](../../../server/app/src/main/java/kr/exchange/engine/DemotionReason.java)이다. 운영자 조작은 [PartitionsEndpoint](../../../server/app/src/main/java/kr/exchange/engine/PartitionsEndpoint.java)(`/actuator/partitions`, 쓰기는 loopback만)이고 설정은 [LeaderPartitionProperties](../../../server/app/src/main/java/kr/exchange/config/LeaderPartitionProperties.java)다([S4 설계](마켓분할_리더_S4_설계.md)). S4b부터 `EngineRecovery`는 DB 접근 실패나 리더 자격 상실로 판정 없이 끝난 재생을 `recovery_runs`에 불일치로 적지 않고, 강등 기록과 라이터 치명 로그는 SQLSTATE와 원인 사슬을 싣는다([S4b 설계](마켓분할_리더_S4b_설계.md)).

DB에서 먼저 볼 테이블은 다음과 같다.

- `command_journal`, `event_journal`, `snapshots`: 명령, 처리 결과, 복구 시작 상태.
- `ledger_transactions`, `ledger_entries`, `balances`: 회계 기록과 조회용 잔고.
- `orders`, `trades`, `idempotency_keys`: 주문·체결과 중복 요청 처리.
- `leader_lease`: 리더 자격과 세대 번호. [LeaderLeaseService](../../../server/app/src/main/java/kr/exchange/engine/LeaderLeaseService.java)와 [리스 구현](../../../server/app/src/main/java/kr/exchange/engine/lease/)을 함께 본다. [V48](../../../server/app/src/main/resources/db/migration/V48__market_partition_lease.sql)부터 행이 `matching-engine`과 파티션 행 둘이고, 쓰기 경로는 기록할 행의 마켓에서 리스 행을 찾는다. 단일 리더(P1)는 `matching-engine` 행만 쓴다([S2 설계](마켓분할_리더_S2_설계.md)). V50부터 모드 래치 `leader_protocol`을 소유자가 정지 창에서 전환 함수 `set_leader_protocol`로 바꾸고, [V49](../../../server/app/src/main/resources/db/migration/V49__revoke_lease_update_journal_insert.sql)는 앱 역할의 리스 행 UPDATE와 저널 직접 INSERT를 회수한다. [V52](../../../server/app/src/main/resources/db/migration/V52__lease_until_from_grant.sql)부터 획득한 리스의 만료는 행 잠금을 얻은 뒤부터 센다([S3 설계](마켓분할_리더_S3_설계.md)). S4부터 자원별 보관소는 [LeaseStoreProvider](../../../server/app/src/main/java/kr/exchange/engine/lease/LeaseStoreProvider.java)가 내고, [V53](../../../server/app/src/main/resources/db/migration/V53__failover_runs_resource.sql)은 `harness.failover_runs`에 그 사건의 리스 자원 열을 더한다.

순번을 다룰 때는 명령 순번, 마켓 이벤트 순번, WebSocket 채널 순번을 구분한다. 명령 채번은 DB의 `command_seq` 전환 기록에 따라 전역 모드와 마켓 대역 모드가 갈린다. 이 기록은 [V44](../../../server/app/src/main/resources/db/migration/V44__command_band_cutover_latch.sql), 이벤트 대역 확대는 [V46](../../../server/app/src/main/resources/db/migration/V46__event_seq_band_widen.sql)에 있다. 이번 분석에서는 실행 중인 DB의 적용 상태를 조회하지 않았다.

복구 기준도 마켓별이다. 다른 마켓의 최대 순번을 가져와 적용 완료 기준으로 삼으면 안 된다. 근거는 [ADR 0022](../adr/0022-market-partitioned-command-journal.md)와 [ADR 0023](../adr/0023-replay-bound-and-cursor-axis.md)에 있다. 리더 검증의 잠금과 인덱스를 수정할 때는 [V41](../../../server/app/src/main/resources/db/migration/V41__lease_key_share_lock.sql)과 [ADR 0026](../adr/0026-leader-lease-key-share-lock.md)을 함께 확인한다.

앱 리더 전환과 DB 승격은 별도다. DB의 비동기 복제와 수동 승격은 [ADR 0024](../adr/0024-async-two-node-replication.md), [운영 절차](../operations/DB_수동_페일오버.md), [DB 노드 설정](../../../deploy/compose.node-data.yml)을 따른다.

## 확인 범위와 남은 문제

주문 접수부터 매칭·정산·화면 갱신까지의 핵심 코드, 복구·리스 연결, 주요 DDL, 빌드·CI·로컬 실행 설정은 본문 또는 관련 구간을 읽었다. 회원·게시판·관리자·봇과 테스트는 구조와 대표 사례를 확인했으며, 모든 예외 처리를 검토한 것은 아니다.

과거 발표 자료, 과거 실험 원자료 전체, 모든 화면의 JSX/CSS, 시드 JSON 전체, 모든 마이그레이션 함수와 긴 설계 문서의 전 절은 읽지 않았다. 금액 계산 전체에 대한 정밀도 감사도 하지 않았다. 09-18의 서비스·DB·마이그레이션 검증은 날짜별 기록에 한정하며 실제 AWS 배포는 미검증이다.

후속 작업에서 주의할 문서 차이는 다음과 같다.

- 배포 계약 원본은 현재 저장소에 없다. 이전 엣지 설정과 실제 배포 계획의 차이도 남아 있다. 사용할 노드별 설정과 확인할 조건은 [배포 안내](../../../deploy/README.md)를 본다.
- [09-15 측정](../../measurements/20260915.md)에서 commit_delay 실험은 조건이 충족되지 않아 `NOT RUN`이다. 다른 단계의 통과 기록과 합쳐 전부 검증됐다고 해석하지 않는다.
- Terraform과 로컬 DB 승격·복원 러너를 추가했지만 AWS plan/apply·다중 호스트 장애·실제 ASG 증감은 아직 검증하지 않았다. 과거 E10 전수 재실행을 현재 완료 조건으로 삼지 않으며 [로드맵](../../ROADMAP.md)의 운영 시나리오를 따른다.

다음 수정에서는 해당 기능의 설계와 테스트를 다시 읽는다. 주문·원장·순번을 바꾸면 서버 코드, SQL, 실험 판정기를 함께 확인하고, API·WebSocket을 바꾸면 웹 통신과 상태 처리도 함께 확인한다.
