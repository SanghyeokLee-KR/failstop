# 마켓 분할 리더 S7 상세 설계: P3 전환과 파티션 실험

2026-09-25 작성. [ADR 0034](../adr/0034-market-partitioned-leadership.md)의 단계 S7(P3 전환과 파티션 카오스)을 현재 코드에 맞춰 구체화한 설계다. 범위와 관문은 [단계 계획](마켓분할_리더_단계계획.md) S7 절이 정했다. 기준 코드는 작업 브랜치 `claude/pml-s7`의 `d46d5073`(S5 위에 S6을 병합한 커밋)이고 인용한 줄 번호는 그 커밋 기준이다. 사용자는 2026-09-25 S7 설계·구현을 S6 관문 실험과 병렬로 진행하고, 폐기용 스택 실험은 S6 관문 뒤에 차례로 돌리기로 정했다. 같은 시각 S6 관문 실험이 ADR 0034 진행 표, 로드맵, 0099, S6 설계를 고치므로 이 단계는 그 문서의 S6 진행 문장을 건드리지 않고 S7 몫만 더한다.

계약은 코드보다 먼저 고쳤다. [DB 설계](../contracts/백엔드_DB_설계.md) v2.59(§3 V55 행, §3.5의 전환 함수 안내, §3.10 신설, §4.1·§4.4, §5.4-c 11·13, §5.4-e 신설, §6.4 ⑯·⑳), [API 설계](../contracts/백엔드_API_설계.md) v2.59(§0-2, §6-C ⑦과 `/admin/v1/ha/status` 설명), [하네스 검증설계](../contracts/하네스_검증설계.md)의 S7 패치 노트와 §2-3·§3·§4-1~§4-4·§5-1, [하네스 CI/CD](../contracts/하네스_CICD_IaC.md) §3-1·§3-3·§5-2·§6-3이다(8절). PostgreSQL·nginx·compose 동작 확인의 원자료는 [`harness/evidence/pml-s7-probe-20260925/`](../../../harness/evidence/pml-s7-probe-20260925/README.md)에 있다(3절). 같은 날 이 설계와 계약에 대한 검토 지적 14건을 반영했다(11절). 이어 2026-09-26 코드 단계에서 V55, 서버·하네스·웹 코드, 서버 관문 시험, 폐기용 스택 실행기와 판정기를 넣었다. 코드 단계에서 더하거나 다르게 한 것과 시험 결과는 12절에 있다. 같은 날 구현 검토 지적 일곱 건을 반영했다(13절). 같은 날 폐기용 스택 실험(5절 Q0~Q16)을 돌렸다. 서버 코드 결함은 나오지 않았고, 도구·판정기·카오스 스택 설정의 빈틈 여덟 곳을 고쳐 다시 쟀다. Q13(W7)이 웹 REST 축 하나로 FAIL이고 나머지 판정 실험은 PASS다(14절).

S7이 끝나도 운영 DB의 모드는 바뀌지 않는다. P3 전환은 로컬 Docker 폐기용 스택의 DB와 Testcontainers 일회용 DB에서만 한다(결정한 값 9·19). 학교 DB는 P1로 두고, 개인 AWS의 모드 전환은 S8에서 사용자 승인 뒤 따로 정한다.

설계를 맡은 AI가 2026-09-25에 정했고 사용자 확인이 필요한 것은 다음 스물이다. 단계 계획이나 계약 문서의 문장과 다르게 읽은 것은 11(E4 RTO '단일 모드 범위 수준'의 해석), 15(되돌리기를 실패 때만이 아니라 늘 한 번 수행), 16(S5가 넘긴 인계 스택 확인을 관문에 넣음)이다. 8·12·16은 검토 대응에서 고쳤고 19·20은 더했다(11절).

1. V55는 FEE_INCOME 샤드 1 계정을 모드와 무관하게 늘 둔다. 기존 자산은 V55가 만들고, 새 자산은 `accounts` 트리거가 샤드 0 행과 같은 트랜잭션에 만든다(4-1).
2. 선행 조건 함수 `leader_protocol_blockers(target)`을 두어 전환 함수와 전환 도구가 같은 정의를 쓴다. 3으로 올릴 때는 정산되지 않은 주문 생성 명령 외에 여덟 가지(명령 대역 래치, 대역 잎, 마켓 대응, 마켓 카운터, 파티션 리스 행, FEE_INCOME 샤드 0·1, `app_role`의 리스 UPDATE와 저널 INSERT 없음)를 본다(4-1).
3. 내리는 전이(2->1, 3->2)는 모두 확인 인자 `p_allow_downgrade => true`를 요구한다(4-1, 4-5).
4. S7 바이너리는 설정 스위치 없이 최고 모드 3을 넘긴다(`LeaseResources.MAX_PROTOCOL = 3`). 모드의 권위는 DB이고, 이 값은 획득 상한일 뿐이라 P1·P2 DB에서는 동작이 같다. 값을 게이지 `exchange.leader.protocol.max`로 낸다(4-2).
5. 전환 도구 `protocol_latch.py transition --target 3`은 한 정지 창에서 1->2(필요하면), 명령 대역 래치(`--latch-band`를 준 경우만, 폐기용 스택 가드 안에서만), 2->3을 부르고 두 노드를 함께 시작한 뒤 배정을 보고, 어긋나면 참여 끄기·켜기로 재배치한다(4-4).
6. 3->2 되돌리기는 두 노드를 멈춘 채 부르고 api-1을 먼저 시작한다. 샤드 1의 수수료 잔고는 옮기지 않는다(4-5).
7. 앱의 P3 RTO 기대에 비선호 획득 유예(만료를 본 뒤 1×TTL)를 더한다. 합격 기준 30초는 그대로다(4-6).
8. C22'는 프로토콜 구간을 `epoch_floor`로 갈라 시간 축 팔을 P3 구간에서 파티션별로 보고, 모드 전환 뒤 시작한 트랜잭션이 옛 구간 epoch로 `command_journal`·`snapshots`에 쓴 행을 세는 구간 경계 팔을 더한다. 앱 enum과 하네스 SQL은 같은 술어를 배열·`width_bucket` 수 판으로 센다(4-7).
9. C30(CRITICAL, 권위 run 한정)은 P3 구간 epoch로 기록된 명령·이벤트·체결·스냅샷 행 가운데 획득 이력이 없거나, 획득(ACQUIRE)이 아니거나, 획득 때 모드가 3이 아니거나, 획득 자원이 그 행 마켓의 파티션과 다른 행을 센다. N/A 조건은 C29와 같다(4-7).
10. P3 공통 판정의 '생존 파티션 ACK 간격'은 생존 파티션 마켓의 `command_journal` NEW 행 `created_at` 이웃 간격이고, 기준선은 주입 전 120초의 최대, 판정 창은 주입부터 영향 파티션 첫 체결 + 10초, 양성 축은 창 안 NEW 마켓마다 10건 이상이다(5-2).
11. 단계 계획 E4의 'p1 RTO가 단일 모드 범위(5.277~10.507초) 수준'은 'P2 기준 최대 10.507초 + 1×TTL(스택 6초) 이하'로 읽는다. 비선호 노드가 넘겨받는 P3 인계에는 유예가 설계상 더해지기 때문이다(4-6, 5-2 Q2).
12. P3 스택은 기본 파일, 중계 오버레이, P3 오버레이의 순서이고, chaos-lb는 두 LB 파일을 합친 `nginx.partition-relay.conf`를 쓴다. 접근 로그는 파티션 형식 하나로 두고 `s6_relay_axes.py`가 두 형식을 모두 읽게 고친다. P3 오버레이는 두 앱의 JDBC 주소에 Toxiproxy 주소를 지킨 채 `ApplicationName`을 컨테이너 이름으로 붙인다(4-9).
13. 수수료 행 결합 실험(Q8)은 파티션마다 다른 사용자 집합으로 부하를 주고, `pg-api1`에 지연 100ms를 넣고, api-1이 KRW 샤드 0 수수료 행을 쥔 순간을 pgrowlocks로 잡아 3초 멈춘다. 같은 사용자 집합의 대조 칸을 기록으로 둔다(5-2).
14. 한 마켓 치명 실험(Q10)은 소유자가 폐기용 DB에 비트랜잭션 시퀀스로 첫 호출만 실패하는 `trades` 트리거를 걸어 주입한다(5-2).
15. 되돌리기(P3->P2)는 단계 계획처럼 실패 때만이 아니라 관문에서 늘 한 번 실제로 수행하고, 같은 스택에서 2->3 재진입까지 본다(5-2 Q4).
16. S5가 스택 확인을 S7로 넘긴 두 파티션 인계(마켓 없는 일괄 취소, 회원 폐쇄, 멈춘 소유 노드)를 관문 실험 Q16으로 넣는다. api-2를 멈추기 전에 api-1의 p1 참여를 꺼 p1 소유 노드가 없게 한다(5-2).
17. 처리량(Q12)은 같은 날 P2·P3 칸을 번갈아 재는 기록이고 판정이 아니다. 무결성 축만 판정이다. 힌트 없는 쓰기(Q15)도 기록이다(5-2).
18. `/admin/v1/ha/status`의 `lease`와 스칼라 `epoch`는 P3에서 `matching-p0` 행의 값이고 응답 모양을 바꾸지 않는다. 관리 화면의 불변식 목록에 C30을 더한다(4-11).
19. 사후 감사(C22'·C30)가 세지 못하는 전환 경계, 곧 전환을 가로지른 트랜잭션과 옛 구간 epoch의 `event_journal`·`trades` 쓰기는 T4-2 전환 판(서버 시험 `CutoverStaleWriteTest`)과 P3 실험의 구간 경계 증분(전환 직후와 실험 끝에 센 네 표의 옛 구간 epoch 행 수가 같음)에 맡긴다(4-7, 5-2).
20. P3 스택의 E4 중계 판정은 W5 대신 W6이다. W6·W7 판정기를 `s6_relay_axes.py judge`에 더하고 생존·희생 노드와 영향·비영향 마켓을 인자로 받는다. 신선도 표본기는 P3에서 그 마켓 파티션의 소유 노드와 다른 노드를 짝짓는다. 웹 관찰 파일이 없으면 W6·W7은 NOT RUN(웹 관찰)이다(4-13).

## 1. 범위와 전제

범위는 단계 계획 S7 절과 작업 지시를 합친 것이다. P3 전환 함수와 선행 조건(`journal_cutover`의 `command_seq` 행, 모든 마켓의 대응·리스·카운터 행, 정산되지 않은 NEW 0, 두 노드가 파티션 가능 바이너리), 명령 대역 래치(폐기용 DB만, 결정 9), P3의 수수료 샤드 활성, C22'·C30, 하네스의 P3 구간 처리, chaos-api-1·2가 p0·p1을 쥐는 스택과 nginx 파티션 업스트림 활성, P3->P2 되돌리기 절차, 데모 재현 절차와 스크립트, 두 LB 파일의 합본(S6 병합이 남긴 일)이다.

전제는 여섯이다.

- 앱 계층은 app-1·app-2(p0·p1 리더이자 조회도 받음)와 app-3(조회 전용, 자동 확장 0~1, 로컬 chaos-api-3)이다. app-3은 엔진을 켜지 않으므로 P3에서도 역할이 같다.
- AWS에 접속하지 않는다. 이 워크플로는 `docker compose up`, 이미지 빌드·태그를 하지 않는다. 동작 확인은 이름이 `pml-probe-*`인 일회용 컨테이너와 `docker compose config` 해석으로만 했다(3절). 새 마이그레이션 V55는 Testcontainers 일회용 DB와 폐기용 스택(compose 프로젝트 `exchange-pml`)에만 적용한다.
- DB 연결 장애의 `503` 계약(S4b)은 2026-09-25 사용자가 확정했다. 회원 폐쇄의 `409`는 AI 선택으로 남아 있다(S5).
- Patroni(ADR 0036)는 범위 밖이다. DB 자동 페일오버는 여전히 없다.
- S6 관문(W0~W5)이 아직 돌지 않았다. S6 관문이 코드를 바꾸면 S7 코드는 그 위로 옮긴다(9절).
- 전환은 운영 중 무중단이 아니다. 정지 창(드레인과 두 노드 재시작)을 쓴다. 안전은 DB 전환 함수가 지키고 정지 창은 운영 규칙이다(DB 설계 §5.4-e 5).

## 2. 현재 코드에서 확인한 것

### 2-1. 바이너리 능력과 기동 모드

- 바이너리 능력은 `LeaseResources.MAX_PROTOCOL = 2`(`server/app/src/main/java/kr/exchange/engine/lease/LeaseResources.java:22`)다. 운영 리스 보관소가 이 값을 획득 함수에 넘기고(`config/LeaseStoreConfig.java:150-159`, `PostgresLeaderLeaseStore.java:45`), 게시도 넘긴다(`PostgresFencingEpochPublisher.java:87`). DB의 `lease_acquire_capped`(V50:318-354)는 현재 모드가 이 값보다 크면 55000으로 거부한다. 그래서 지금 바이너리는 P3 DB에서 어떤 파티션도 얻지 못한다(DB 설계 §5.4-c 13).
- 노드는 기동 때 모드를 한 번 읽는다. `exchange.leader.protocol.boot` 게이지가 그 값을 낸다(`config/EngineConfig.java:88-99`). 계획은 `PartitionPlan.forBoot`가 모드 3이면 파티션 계획, 아니면 단일 계획으로 만든다(`engine/PartitionPlan.java:53-58`). 파티션 계획의 대응은 지연 읽기이고 모르는 마켓은 다시 읽는다(`PartitionPlan.java:90-100`).
- DynamoDB 보관소는 모드 3이나 파티션 설정에서 기동을 멈춘다(`LeaseStoreConfig.java:115-146`). 게시 함수도 P3에서 늘 거부한다(V50:372-406).

### 2-2. 전환 함수

`set_leader_protocol`(V50:433-491)은 1->2와 확인 인자를 준 2->1만 받고 주석에 "2<->3은 S7이 이 함수를 개정하며 더한다"(V50:439)고 적었다. 모든 리스 행을 resource 순으로 `FOR UPDATE`, 이어 모드 행을 잠그고 함수 속성 `lock_timeout = '5s'`로 기다린다. 퇴역 순서는 `matching-p0`, `matching-p1`, `matching-engine`이다. 모드 행을 바꾸는 트리거가 `changed_at`을 `clock_timestamp()`로 찍고(V48:56-62) 이력 행에 그 시점의 `max(epoch)`를 `epoch_floor`로 남긴다(V48:66-82). 잠금을 얻은 뒤의 시각이라 전환이 기다려 준 쓰기의 `created_at`보다 늦다. C22'의 구간 경계 팔이 이 성질에 기댄다. 다만 `created_at`은 트랜잭션 시작 시각이라, 이 팔이 가를 수 있는 것은 전환 뒤에 시작한 트랜잭션뿐이다(4-7).

### 2-3. 선호·유예와 재배치

- 선호가 아닌 파티션은 획득을 미룬다. 기동 때 2×TTL, 그 뒤에는 만료를 볼 때마다 1×TTL이다(`engine/PartitionAcquirePolicy.java:54-72`). 정책은 파티션 계획이고 그 자원이 선호가 아닐 때만 건다(`EngineConfig.java:157-158`). 선호 목록은 `exchange.leader.partition.preferred`(`config/LeaderPartitionProperties.java:18-37`, `application.yml:90-96`)이고 환경 변수로는 `EXCHANGE_LEADER_PARTITION_PREFERRED`다(Spring 완화 바인딩, 쉼표 목록).
- 참여 끄기·켜기와 차단기 해제는 `POST /actuator/partitions`이고 loopback에서만 받는다(`engine/PartitionsEndpoint.java:28-95`). 하네스는 `docker exec <컨테이너> curl ... localhost:8080/actuator/partitions`로 부른다(`harness/scale/s5_route_probe.py:576-581`).

### 2-4. 수수료 샤드

- 정산의 수수료 샤드는 계획이 파티션이면 그 마켓 파티션의 번호, 아니면 0이다(`ledger/SettlementService.java:263-273`). 운영 배선은 `EngineConfig.java:274`가 계획을 넣는다. 그래서 P3에서 샤드 1 계정만 있으면 정산 코드는 바꿀 것이 없다. 계정이 없으면 `feeAccount`가 `IllegalStateException`을 던진다(`SettlementService.java:1145-1156`).
- 샤드 1 계정은 지금 어디서도 만들지 않는다. `AccountBootstrap`은 세 목적의 샤드 0만 `ON CONFLICT DO NOTHING`으로 넣고(`ledger/AccountBootstrap.java:26-41`, `:116-124`), 배포 시드도 같다(`deploy/linux/app/bootstrap-markets.sql:24-26`).

### 2-9. WS 중계와 P3

## 3. 동작 확인

원자료와 명령은 [확인 기록](../../../harness/evidence/pml-s7-probe-20260925/README.md)에 있다. 판정이 아니고 코드 없이 한 확인이다.

- **P7-0~P7-4 (PostgreSQL 17.10, 저장소 V0~V54 위에 V55).** V55가 오류 없이 올라가 기존 자산의 FEE_INCOME 샤드 1과 잔고 행을 만들고, 앱 로그인이 넣은 새 자산의 샤드 0에 샤드 1이 따라 생겼다. 1->3은 전이 거부, 1->2 뒤 3으로 올릴 때의 선행 조건 여덟 가운데 `lease_row_missing`을 뺀 일곱과 `unsettled_new`가 각각 한 줄씩 나왔고(`lease_row_missing`은 아래 R7-1), 모두 푼 뒤 2->3이 세 행을 퇴역시켰다. P3에서 최고 모드 2의 획득과 `matching-engine` 획득은 55000, 최고 모드 3은 두 파티션을 얻었다. p0의 holder·epoch로 p1 마켓 행을 넣으면 0행이었다. 3->1·3->3은 전이 거부, 확인 인자 없는 3->2는 되돌리기 거부였고, p1 행에 KEY SHARE가 있으면 3->2가 5.005초에 55P03으로 끝나며 아무것도 바꾸지 않았다. 계약 문서의 블록을 뽑아 돈 기록과 초안으로 돈 기록은 시각을 빼면 같다.
- **P7-5 (C22'·C30).** P3 행 다섯에서 종전 C22가 거짓 위반 2건, C22'는 0이었다. 주입 다섯(같은 파티션 역행, 다른 파티션 epoch 쓰기 네 표, 전환 뒤 옛 구간 epoch 쓰기, 퇴역 epoch 쓰기, 획득 이력 없는 epoch)을 C22'와 C30이 각각 맞는 팔로 셌고, 되돌리기 뒤 P2 행을 더해도 둘 다 0이었다.

## 4. 설계

### 4-1. V55 마이그레이션

파일은 `server/app/src/main/resources/db/migration/V55__partition_protocol_cutover.sql`이고 본문은 DB 설계 §3.10의 SQL 블록과 같다. 대조는 줄바꿈을 LF로 맞추고 끝 줄바꿈을 뺀 문자열로 한다. 그 정규화 문자열의 sha256 앞 16자리는 `7a75c805b58f1646`이고 §3.10 블록에서 뽑은 문자열과 같다. 초안 파일 `v55-draft.sql`의 바이트(끝 줄바꿈 하나 포함) 해시는 `f750f412d27be052`다. 세 가지를 한다.

- 샤드 1 계정. `seed_fee_income_shard()`(SECURITY DEFINER, `search_path` 고정, PUBLIC EXECUTE 회수)와 `trg_accounts_fee_income_shard`(AFTER INSERT, `owner_type = 'SYSTEM' AND purpose = 'FEE_INCOME' AND shard = 0`)가 샤드 0 행과 같은 트랜잭션에 샤드 1을 `ON CONFLICT DO NOTHING`으로 넣는다. 기존 자산은 V55가 한 번 채운다. 모드와 무관하게 늘 두는 이유는, 전환 때 계정을 만드는 절차를 따로 두면 P3 전환이 자산 카탈로그 변경과 섞이고, 되돌린 뒤 다시 올릴 때 이미 있는 행과 부딪치기 때문이다. 잔고 0 계정은 C01에 영향이 없다.
- 선행 조건 함수. `leader_protocol_blockers(target)`은 읽기 전용이고 `(blocker, detail)` 행을 낸다. 모든 목표에 `unsettled_new`, 3에는 여덟 가지를 더 본다(DB 설계 §3.10). 전환 함수가 잠금 뒤에 부르고, 전환 도구가 정지 창 전에 부른다. `harness_role`에 EXECUTE를 준다. `lease_row_missing`은 대응 표와 획득 이력이 외래 키로 리스 행을 참조해 보통 경로로는 나지 않는다. 트리거를 끄고(`session_replication_role = replica`) 적재하거나 지운 복원본을 막는 방어 항목이다(3절 R7-1).
- 전환 함수. `set_leader_protocol`을 CREATE OR REPLACE로 바꿔 1->2, 2->1, 2->3, 3->2만 받는다. 내리는 전이는 모두 확인 인자를 요구한다. 선행 조건이 한 줄이라도 있으면 모든 사유를 한 메시지로 모아 55000으로 끝난다. 잠금 순서, 5초 잠금 대기, 퇴역 순서와 이력은 V50 그대로다.

V55는 모드를 바꾸지 않는다. V55만 적용된 DB에서 S6 이전 바이너리의 운영 코드는 동작이 같다. 정산은 샤드를 조건으로 계정을 찾고(`SettlementService.java:1124-1156`) 부트스트랩은 샤드 0만 넣는다. 바뀌는 것은 SYSTEM 계정 수(자산 13개면 39에서 52)이고, 그것을 세는 스모크와 시험을 고친다(6-5).

### 4-2. 바이너리 능력과 지표

`LeaseResources.MAX_PROTOCOL`을 3으로 올리고 주석을 고친다. 설정 스위치는 두지 않는다. 모드는 DB가 정하고 이 값은 '이 바이너리가 이해하는 가장 높은 모드'라서 P1·P2 DB에서는 어떤 호출의 결과도 바뀌지 않는다(`lease_acquire_capped`는 현재 모드가 상한보다 클 때만 거부한다). 게시는 P3에서 늘 거부되므로 게시자의 값이 3이 되어도 P3 게시는 열리지 않는다(V50:372-406).

`EngineConfig`의 기동 모드 게이지 옆에 `exchange.leader.protocol.max`(Gauge)를 조회 역할이 아닌 노드에서만 등록한다. 전환 도구가 2->3 전에 두 노드의 이 값이 3인지 본다(4-4). 계약은 하네스 CI/CD §5-2다.

### 4-3. P3에서 달라지는 앱 동작

S4~S6이 파티션 코드 경로를 이미 넣었으므로 S7이 앱에서 켜는 것은 획득 상한 하나다. P3에서 보이는 동작은 이렇다.

- 두 노드는 팔로워로 기동하고 선호 파티션을 곧바로 노린다. api-1은 p0 마켓(1, 4, 5, 7, 9, 11), api-2는 p1 마켓(2, 3, 6, 8, 10, 12)을 매칭하고 정산한다. 쓰기 판정은 기록할 행의 마켓에서 리스 행을 찾는다(DB 설계 §5.4-b).
- 수수료는 p0 마켓이 샤드 0, p1 마켓이 샤드 1로 간다(`SettlementService.java:263-273`). 정산 잠금 계획이 그 샤드 계정을 넣는다(S4).
- 소유권 선검사(S5)가 소유하지 않는 파티션의 주문 쓰기를 아무것도 건드리지 않은 `503`으로 돌려보내고, LB가 다른 노드로 넘긴다.
- WS는 두 노드 모두 중계로 받는다. 각 노드의 호가·티커 REST는 쥔 마켓은 엔진 사본, 쥐지 않은 마켓은 미러 조건을 채우면 미러, 아니면 DB 집계와 `seq: 0`이다(S6).
- 한 노드가 죽으면 다른 노드가 만료와 유예 뒤 그 파티션을 넘겨받는다. 되살아난 노드는 되찾지 않는다(결정 4). 되돌려 놓는 것은 운영자의 재배치다(4-6).

### 4-4. 전환 절차와 전환 도구 (2->3)

절차의 정본은 DB 설계 §5.4-e 1이다. 도구는 `harness/scale/protocol_latch.py`를 넓힌다.

```
python harness/scale/protocol_latch.py transition --target 3 [--latch-band] --out <json>
python harness/scale/protocol_latch.py transition --target 2 --allow-downgrade --out <json>   # 3->2
python harness/scale/protocol_latch.py blockers --target 3 --out <json>                       # 읽기만
```

- 가드. 종전 가드(프로젝트 `exchange-pml`, 이미지 태그 `exchange-chaos-app:pml`, 떠 있는 `chaos-*`의 compose 라벨과 이미지 id)를 그대로 쓴다. 명령 대역 래치는 되돌릴 수 없으므로 `--latch-band`를 준 경우에만 부른다. 래치가 없고 인자도 없으면 BLOCKED(종료코드 4)다.
- 계획. `plan_transition`이 받는 쌍을 1->2, 2->1(확인), 2->3, 1->3(1->2를 먼저 부르는 두 단계), 3->2(확인)로 넓힌다. 3->1은 받지 않는다(먼저 3->2).
- 사전 확인. 두 노드의 `exchange_leader_protocol_max`가 3, `blockers(3)`이 `unsettled_new`·`band_latch_missing` 밖의 줄을 내지 않음, 두 노드 컨테이너의 선호 설정(`EXCHANGE_LEADER_PARTITION_PREFERRED`)이 api-1 `matching-p0`, api-2 `matching-p1`.
- 창. 봇 정지, 드레인(정산 전 NEW 0 표본 두 번, 상한 120초), api-2·api-1 정지, 필요하면 1->2, 필요하면 래치, 2->3, 노드를 시작하기 전에 구간 경계 표본(`segment-count`, 4-7). 3->2도 같은 자리에서 표본을 뜬다.
- 시작. 두 노드를 함께 시작한다. 종전처럼 api-1을 먼저 시작하면 api-2가 뜨기 전에 api-1의 기동 유예(2×TTL)가 끝나 p1까지 쥔다.
- 배정. 시작 뒤 90초 안에 api-1이 p0, api-2가 p1을 쥐어야 한다. 한 노드가 둘을 쥐었으면 그 노드에서 비선호 파티션의 참여를 끄고, 선호 노드가 얻은 것을 본 뒤 다시 켠다. 다시 켜지 않으면 그 노드가 선호 노드의 장애를 넘겨받지 못한다.
- 사후 확인. 두 노드의 `exchange_leader_protocol_boot` 3과 `exchange_order_inflight_enabled` 0, C29 0, 두 파티션 epoch가 마지막 퇴역 epoch보다 큼, 이력 행 `P3`. 봇을 되살린다.

도구의 출력 JSON에 사전 확인, 전환 호출 결과(퇴역 행, DB 시계로 잰 호출 시간), 전환 직후의 구간 경계 표본, 배정과 재배치, 사후 확인을 남긴다.

### 4-5. 되돌리기 (3->2)와 소프트 롤백

정본은 DB 설계 §5.4-e 2·3이다.

- 되돌리기. 같은 정지 창에서 `set_leader_protocol(2, true)`를 부른다. 두 노드를 멈춘 채 부르고, api-1을 먼저 시작해 `matching-engine`을 마지막 퇴역 epoch 뒤의 epoch로 얻는 것을 본 뒤 api-2를 시작한다(팔로워). P2 계획의 노드는 선호가 없어 종전 순서가 맞다. 데이터 이관은 없다. 예약은 P2와 P3가 같은 규칙이라 P3에서 접수한 주문도 P2 정산이 그대로 다룬다. 샤드 1의 수수료 잔고는 남고 새 수수료는 샤드 0으로 간다. 명령 대역 래치는 그대로다. 되돌린 뒤 이력은 `…, P3, P2`이고 C22'는 두 P2 구간을 따로 가른다.
- 소프트 롤백. 모드를 3에 둔 채 한 노드의 두 파티션 참여를 끄거나 그 노드를 멈추면 다른 노드가 두 파티션을 모두 쥔다. 리스 행은 둘이지만 한 노드가 모든 마켓을 쓴다. 되돌리기 전에 먼저 쓰는 단계다(ADR 0034 되돌리기 절).
- 재진입. 되돌린 DB는 다시 2->3으로 올릴 수 있다. 샤드 1 계정과 래치가 이미 있어 선행 조건은 드레인만 남는다.

### 4-6. 선호·유예·재배치와 RTO

P3 인계는 두 경우다. 선호 노드가 넘겨받으면(예: api-2가 쥐었던 p0를 되찾는 재배치) 만료 즉시 획득한다. 비선호 노드가 넘겨받으면(예: api-2가 죽어 api-1이 p1을 얻음) 만료를 본 뒤 1×TTL을 더 기다린다. 유예는 두 노드가 동시에 뜰 때 선호 배정을 지키려는 것이다(결정 4). 카오스 스택의 TTL은 6초라 P3 E4의 RTO는 같은 스택의 P2 E4보다 약 6초 길다. 합격 기준(RTO < 30초)은 그대로다. 단계 계획의 'p1 RTO가 단일 모드 범위 수준'은 'P2 기준 최대 10.507초 + 1×TTL 이하'로 읽는다(결정 11).

재배치는 운영자 조작이다. 선호 노드가 돌아온 뒤 두 파티션을 쥔 노드에서 그 파티션 참여를 끄면 선호 노드가 만료 즉시 얻고, 참여를 다시 켜면 그 노드가 백업이 된다. 한 번의 재배치에 그 파티션 쓰기가 TTL 동안 멈춘다. Q9가 이 동작을 부하 중에 잰다.

### 4-7. C22'와 C30

정의는 DB 설계 §6.4 ⑯·⑳, 판정 계약은 하네스 검증설계 §4-1이다.

- **구간.** `leader_protocol_history`의 행 k가 epoch 범위 (floor_k, floor_{k+1}]을 연다. 첫 행(V48 시드)은 아래 끝이 없다. 시계가 아니라 epoch로 가르는 이유는 V48 주석과 같다. 모드 전환 뒤 배정되는 epoch는 모두 그 행의 `epoch_floor`보다 크다.
- **C22' 세 팔.** 시간 축 팔은 P1·P2 구간 행을 전역 하나, P3 구간 행을 그 마켓 파티션별로 `lag(fencing_token) OVER (… ORDER BY created_at, seq)`로 본다. 마켓 안 팔은 종전 그대로다. 마켓 채번이 카운터 행을 커밋까지 잠그므로(`next_market_journal_value`, V46) 마켓 안 seq 순서는 커밋 순서다. 구간 경계 팔은 어떤 구간의 epoch로 기록된 `command_journal`·`snapshots` 행의 `created_at`이 다음 전환의 `changed_at` 이후인 행이다. 두 표의 `created_at`은 DB 서버의 트랜잭션 시작 시각이다(2-5). 전환 함수가 모든 리스 행을 잠가 진행 중 쓰기의 커밋을 기다린 뒤 모드를 바꾸고 모든 행을 퇴역시키므로, 전환 뒤에 시작한 트랜잭션은 옛 구간 epoch로 커밋할 수 없다(2-2). 전환 뒤 새 구간 행이 없던 마켓의 옛 epoch 쓰기는 앞 두 팔이 모두 놓치므로(3절 P7-5 V3) 이 팔을 더한다. 시간 축 팔과 구간 경계 팔은 DB 서버 시계 역행 뒤 거짓 양성을 낼 수 있다(ADR 0022 9-17). 목록 판의 열은 `(arm, tbl, subject)`다.
- **사후 감사의 범위와 나머지.** 사후 감사가 세지 못하는 전환 경계가 둘이다. (가) 전환 전에 시작해 전환 뒤 커밋한 트랜잭션. `created_at`이 `changed_at` 앞이라 구간 경계 팔이 보지 못하고, 같은 마켓에 먼저 커밋된 새 구간 명령 행이 있을 때만 마켓 안 팔이 센다(3절 R7-4). (나) 옛 구간 epoch로 쓴 `event_journal`·`trades` 행. 두 표의 `created_at`은 engine_ts 파생이라 전환 시각과 비교할 수 없고, 그 epoch가 P3 구간의 정상 획득 epoch이거나 P1·P2 구간 epoch이면 C30도 세지 않는다(3절 R7-5). 라이브 차단은 둘 다 막는다. 전환 전에 시작한 트랜잭션도 쓰기 판정이 리스 행을 잠근 뒤 새 값을 읽어 거부된다(DB 설계 §5.4-e 5). 두 빈틈은 사후 감사 대신 두 곳이 본다. T4-2 전환 판(`CutoverStaleWriteTest`, 6-2)은 전환 뒤 다시 시작하지 않은 옛 모드 노드의 접수·정산·스냅샷 쓰기와 전환을 가로지른 트랜잭션이 모두 거부되고, 네 표의 옛 구간 epoch 행 수가 늘지 않는 것을 본다. P3 실험의 구간 경계 증분(5-2 공통 판정)은 전환 직후(노드 시작 전)와 실험 끝에 네 표의 옛 구간 epoch(그 전환 이력 행의 `epoch_floor` 이하) 행 수를 세어 같아야 한다(확인 기록 `segment-old-rows.sql`). 전환 뒤 배정되는 epoch는 모두 `epoch_floor`보다 크므로 이 수는 늘 수 없고, 시계와 커밋 순서에 기대지 않는다. 판정기는 `s7_axes.py segment-count`·`segment-judge`다(4-13). 구간 경계를 커밋 순서로 가르는 방법, 곧 전환 함수가 마켓 카운터 행을 잠가 그 값을 이력에 남기는 방법은 쓰지 않는다. 쓰기는 카운터 행을 잠근 뒤 리스 행을 잠그므로(`append_command_prologue`의 채번 뒤 `append_command_journal_row`), 리스 행을 먼저 잠근 전환이 카운터를 기다리면 진행 중 쓰기와 교착이 난다.
- **C30.** P3 구간 epoch로 기록된 네 표의 행마다 그 epoch를 `lease_acquisitions`에서 찾는다. epoch는 모든 리스 행을 통틀어 한 번씩만 배정되고 획득 표는 추가 전용이라 epoch 하나가 자원 하나에 대응한다. 획득 이력이 없거나, ACQUIRE가 아니거나(게시·퇴역 epoch), 획득 때 모드가 3이 아니거나, 획득 자원이 그 행 마켓의 파티션과 다르면 센다. P3 구간은 V55 뒤에만 열리고 V49 뒤 모든 획득이 이력을 남기므로 '이력 없음'의 거짓 양성은 없다. 파티션을 넘는 쓰기(split-brain)는 파티션별로 나눈 C22' 시간 축 팔이 보지 못하므로 C30이 맡는다. 라이브 강제는 시장 도출 fencing이고 C30은 백스톱이다.
- **수 판.** 앱 enum(`C22_FENCING_MONOTONIC`, 이름 유지)과 하네스 SQL 두 벌은 같은 술어를 수로 센다. 구간 경계 배열(`lb`)을 `width_bucket`에 넘겨 구간을 한 번에 찾고, 대응 표를 마켓 id 위치의 배열로 읽는다. 기준은 확인 기록의 `c22p-count-r2.sql`(`cost-queries/q_6_c22p_arrays.sql`에 스냅샷 항을 더한 판)이다. 목록 판(DB 설계 §6.4)과 수 판의 행 수가 같은지는 시험이 고정한다(6-2). C30은 목록 판을 `count(*)`로 감싼다.
- **스키마 분기.** V48 객체가 없는 스키마(V47 이하)에서 하네스 SQL은 C22 종전 판을 쓰고 C30은 N/A다. V48 객체 다섯이 일부만 있으면 C30은 FAIL(없는 객체 수)이다. 앱 enum은 V48 뒤 DB에서만 돈다.
- **비용.** 하네스 검증설계 §4-1의 C22 비용 문턱(권위 run과 같은 읽기 전용 반복 읽기 트랜잭션, `EXPLAIN (ANALYZE, BUFFERS)`, 100만 행 이상, 1,500ms)을 C22' 수 판에 그대로 건다. 표본은 문턱 가까이(1.29~1.45초, 스냅샷 항 없는 판)라 Q14가 규칙대로 잰다. 스냅샷 항은 행이 적은 `snapshots`를 한 번 훑는다. Q14는 스냅샷 항을 넣은 판을 잰다. 넘으면 FAIL이고 대응은 ADR 0034 개정으로 정한다. 후보는 셋이다. (가) C31처럼 앱 판은 마켓마다 최근 N건 창으로 두고 전수 판은 하네스 SQL(psql, 문장 상한 없음)만 돈다. 창은 크래시 창과 인계 구간을 덮는 최근 활동에 한정된다. (나) 권위 run 트랜잭션에만 `SET LOCAL statement_timeout`을 늘린다. 운영 풀의 3초 상한을 권위 run에서 푸는 일이라 관리 경로가 느려질 수 있다. (다) `command_journal(created_at)` 인덱스. 대역 잎이 마켓마다 있어 잎마다 인덱스를 만드는 새 마이그레이션이고, 쓰기마다 인덱스 비용이 든다.

### 4-8. 수수료 샤드 P3 활성과 모드 경계

- 활성. 코드는 이미 있다(2-4). S7이 더하는 것은 계정(V55)과, P3 흉내 시험 배선이 정산에 계획을 넣는 것(`PartitionNode`)이다.
- 모드 경계. 전환 함수의 `unsettled_new`는 모든 목표에 걸리므로, 전환 전에 접수한 주문 생성 명령은 모두 전환 전 모드로 정산된다. 체결은 NEW 명령의 이벤트라 모드를 넘나드는 체결이 없다. 승격 재생의 크래시 창 재정산은 같은 모드 안에서만 일어나고 샤드는 마켓에서만 정해지므로(`feeShard`) 재정산이 같은 샤드를 고른다.
- 되돌린 뒤. 샤드 1 잔고는 남는다. 수수료 수입을 자산별로 합칠 때는 샤드를 모두 더한다. 저장소의 운영 코드에 FEE_INCOME 잔고를 합산하는 화면이나 보고는 없다(2-4 조사). C01은 모든 계정을 합하므로 영향이 없다.

### 4-9. P3 스택: 오버레이와 LB 합본

- **오버레이.** `harness/docker-compose.p3.yml`(초안 `docker-compose.p3-draft.yml`)은 서비스를 더하지 않는다. api-1·api-2에 `EXCHANGE_LEADER_PARTITION_PREFERRED`(`matching-p0`·`matching-p1`)와 `SPRING_DATASOURCE_URL`(기본 파일의 주소에 `?ApplicationName=chaos-api-1`·`chaos-api-2`)을 주고 chaos-lb에 합본을 마운트한다. `ApplicationName`은 Q8의 pgrowlocks 표본이 잠금을 쥔 노드를 가르는 데 쓴다(2-7). 세 연결 풀이 같은 주소를 쓰므로 모두 이름이 붙는다. 주소의 호스트·포트는 기본 파일의 Toxiproxy 주소(api-1 `chaos-toxiproxy:15432`, api-2 `:25432`)를 그대로 둔다. 바꾸면 Q6(E2)의 절단이 그 노드에 닿지 않는다. 첫 초안에는 이 줄이 빠져 있었고 검토 대응에서 넣어 다시 해석했다(3절 C7).
- **순서.** compose는 같은 컨테이너 경로의 마운트를 뒤 파일 것으로 바꾼다(3절 C7). `lib.ps1`에 `Set-P3Overlay`를 두어 `CHAOS_COMPOSE_OVERLAYS`를 `harness/docker-compose.relay.yml;harness/docker-compose.p3.yml`로 채우고, 다른 값이 있으면 멈춘다. `Test-P3Overlay`는 `Test-RelayOverlay`의 세 확인에 chaos-lb 마운트 원본이 `nginx.partition-relay.conf`인지, 두 앱의 선호 설정이 맞는지, 두 앱의 `SPRING_DATASOURCE_URL`이 Toxiproxy 주소를 지키고 `ApplicationName=<컨테이너 이름>`을 싣는지를 더한다. 환경은 `Test-RelayOverlay`처럼 변수 한 줄만 고르는 템플릿으로 읽는다. `up.ps1 -P3`와 실행기의 `-P3`는 `-Relay`를 함께 켠다.
- **합본.** `harness/nginx/nginx.partition-relay.conf`(초안 `nginx-p3-relay-draft.conf`)는 `nginx.relay.conf`의 블록 전부에 `nginx.partition.conf`의 파티션 업스트림 둘, 두 맵, 주문 쓰기 location을 더한다. 두 원본은 바꾸지 않는다. 접근 로그는 파티션 형식 하나다. `harness/scale/test_nginx_p3_conf.py`가 블록이 두 원본과 줄 단위로 같은지, 맵이 V48 시드와 같은지, 로그 형식을 대조한다. `nginx -t`는 폐기용 컨테이너(`pml-probe-*`)로 본다.
- **로그 형식 충돌.** 중계 형식의 `ups`는 상태 목록, 파티션 형식의 `ups`는 주소이고 상태는 `ust`다. `s6_relay_axes.lb_ws_retry_seen`은 `ups=503, 101`과 `ust="503, 101"`을 모두 증거로 센다. 파티션 형식을 고른 이유는 S5 판정기가 이미 `ups`를 주소, `ust`를 상태로 읽기 때문이다(`s5_route_probe.py:806-808`). 두 형식 모두 앞부분이 combined라 S4b의 LB 판정 정규식은 그대로 맞는다.
- **힌트 없는 쓰기.** 합본의 힌트 없는 경로는 종전 `exchange_write`다(1차 api-1). P3에서 api-1이 소유하지 않는 p1 마켓의 힌트 없는 쓰기는 1차의 선검사 `503`을 받고 1차를 `fail_timeout` 동안 빼므로, 그 뒤 2~3초 동안 백업(api-2)이 소유하지 않는 p0 마켓의 힌트 없는 쓰기가 `502`다(3절 N7-4). LB를 고치지 않고 모든 부하가 힌트를 싣게 한다. 웹·봇·k6는 S5부터 힌트를 싣는다. Q15가 힌트 없는 부하의 창을 기록한다.

### 4-10. WS 중계와 P3

P3에서는 두 노드가 모두 중계에 기댄다(2-9). 그래서 P3 스택은 중계 오버레이 위에서만 돌고, 브로커 장애 동안 두 노드가 모두 WS를 1013으로 닫고 핸드셰이크를 `503`으로 거절한다. REST는 그대로다. 이것은 S6 설계 4-11의 규칙대로이고, S6 E13의 '모든 마켓을 쥔 리더는 닫지 않는다'는 P3에서 해당 노드가 없다. P3의 브로커 장애 판정은 S7 관문에 넣지 않고 위험으로 적는다(9절).

S6이 S7로 넘긴 스택 판정은 둘이다. W6('그 마켓만 재동기화', p1 소유자 kill)은 Q2에 함께 싣고, W7(한 연결로 두 파티션 마켓 수신)은 Q13이다. 판정 기준은 S6 설계 7-2 그대로이고, 판정기와 실행기 배선은 4-13이 더한다. S6 실행기의 W5 판정은 P2 모양이라 P3에서 쓰지 않는다(2-6).

P3에서 p1 소유자가 죽으면 p1 리스는 TTL 뒤 만료된다. 중계 불능 판정의 `owner_silent`는 '유효한 리스를 쥔 소유 노드'의 하트비트만 보므로 만료 뒤에는 걸리지 않고, 생존 노드는 WS를 닫지 않는다. p1 마켓의 게시는 인계와 재생 뒤 새 epoch로 다시 시작하고, 클라이언트는 그 마켓만 다시 맞춘다. 이 흐름이 W6의 판정이다.

### 4-11. 관리 API와 관리 화면

- `/admin/v1/ha/status`의 `lease`와 스칼라 `epoch`는 P3에서 `leases[]`의 첫 행(`matching-p0`)이다. 응답 모양과 `schema_version`은 그대로다(API 설계 §6-C v2.59). P3의 상태는 `leases[]` 두 행과 노드마다 `GET /actuator/partitions`로 읽는다.
- 관리 화면의 불변식 목록(`web/lib/admin/catalog.ts`)에 `C30_FENCING_RESOURCE_MATCH`(권위 run 한정, '파티션 epoch 자원', 'P3 epoch 대 마켓 파티션')를 C29와 C31 사이에 넣고 C22의 설명을 C22'에 맞춘다. 화면 배치는 바뀌지 않는다.
- 관리 콘솔 시연 대본의 '앱 리더 전환'(`web/lib/admin/drills.ts`)은 P1·P2 전용이다. 용량 노드의 `leader`는 readiness 200이고, readiness는 파티션 하나라도 ACCEPTING이면 UP이다(`engine/HaAvailability.java:158`). 그래서 P3에서는 두 노드가 모두 리더로 보인다. 대본은 이것을 '리더 2대 관측'으로 읽어 멈추고, 다음 단계 설명은 두 리더를 결함이라고 적는다. 세대(`epoch`)도 `matching-p0` 한 행의 값이라 p1 인계를 보지 못한다. 안내 명령 `e4-leader-kill.ps1`은 `-Resource`가 없어 P3에서 멈춘다(2-6). 그래서 첫 단계가 `leases[]`에서 파티션 자원을 보면 '파티션 리스 matching-p0·matching-p1 · P1·P2 전용 대본'을 적고 멈추게 했다(13절 지적 2). 모의 데이터는 `matching-engine` 한 행이라 모의 화면은 그대로다. P3 시연은 4-12의 스크립트와 같은 화면 아래의 리스 표로 한다. 파티션마다 기준 리더와 세대를 잡는 P3 대본은 만들지 않았다.

### 4-12. 데모 재현 절차와 스크립트

발표는 PPTX와 사전 녹화 영상·캡처로 준비한다(AGENTS.md). S7은 녹화할 장면을 같은 결과로 다시 만드는 스크립트를 둔다.

- `harness/scripts/s7-p3-demo.ps1`. 가드(프로젝트 `exchange-pml`, 이미지 `exchange-chaos-app:pml`)를 확인하고 P3 스택을 세운 뒤(`up.ps1 -P3 -Obs`), 전환 도구로 P3에 올리고, 봇과 힌트를 실은 k6 부하를 켠다. 두 노드의 파티션 표와 리더 epoch를 화면에 적고, 약속한 시각에 api-2를 `docker kill`한 뒤 p1 RTO, p0 마켓 ACK 간격, 사후 권위 run 결과를 적는다. 판정은 Q2와 같은 판정기(`s7_axes.py`)를 부르므로 녹화 화면의 수치가 관문 수치와 같은 정의다. 스택은 녹화를 위해 남기고, `-Down`을 주면 `docker compose -p exchange-pml … down -v`로 내린다.
- 녹화 순서(사람이 한다). Grafana의 파티션 패널(S4의 `partition` 태그)과 관리 화면의 리스 표(시연 대본 화면 아래. 리더 전환 대본의 단계는 P3에서 첫 단계에 멈춘다, 4-11), 웹 거래 화면 두 마켓(KRW-BTC p0, KRW-ETH p1)을 띄운 채 스크립트를 돌린다. p1 마켓만 멈췄다 다시 도는 것과 p0 마켓이 끊기지 않는 것을 한 화면에 담는다.

### 4-13. 하네스의 P3 구간 처리

- `e4-leader-kill.ps1`과 `e6-spike-failover.ps1`에 `-Resource`를 더하고 모든 상태·포트 조회에 넘긴다. `Complete-FailoverExperiment`의 사후 run 포트 조회(`lib.ps1:523`)도 자원을 넘긴다.
- E4의 epoch 판정. P1·P2는 종전 그대로 '정확히 +1'이다. P3에서는 '옛 epoch 뒤 그 자원의 ACQUIRE 이력이 정확히 하나이고 holder가 생존 노드'다(하네스 검증설계 §5-1). `lib.ps1`에 `Test-P3AcquireOnce`를 둔다.
- `adr0022-stage5-chaos.ps1`의 `-Protocol`에 3을 더하고 `-P3`(오버레이)와 `-Resource`를 받는다. `-Protocol 3`이면 스택을 세운 뒤 전환 도구의 `--target 3 --latch-band`를 부른다. `-Protocol 3`은 `-P3`와 함께만, `-P3`는 `-Protocol 3`과 함께만 돈다. E2·E4·E5·E6·E7은 `-Resource`가 없으면 시작하지 않는다.
- 실행기의 가드와 `$Protocol -eq 2` 분기. `-PartitionAxes`·`-Relay`·`-WsGateAxes`의 가드(:616-617)를 `-Protocol 2` 또는 3으로 넓힌다. P2 전환(:224) 자리는 모드에 맞는 전환 도구 호출로, 공통 판정(:334), 이미지·프로젝트 가드(:613), 균형 표본기(:271), 공통 판정 반영(:520), rpo 축(:528), 주행 뒤 모드 상태(:419)는 `-ge 2`로 넓힌다.
- 중계 판정의 P3 판. `-Protocol 3`의 E4는 W5 대신 `s6_relay_axes.py judge --experiment W6`을 부른다. 인자는 `--victim`(콘솔의 `killed=` 노드), `--survivor`(다른 노드), `--affected-markets`(관찰 마켓 가운데 `-Resource` 파티션의 마켓), `--unaffected-markets`(나머지), `--kill-at`, `--rto-sec`이다. 영향·비영향 마켓은 실행기가 `market_lease_partition`과 `markets`에서 읽는다. 관찰 마켓 KRW-BTC·KRW-XRP·KRW-ETH에서 `-Resource matching-p1`이면 영향 마켓은 KRW-ETH다. 거짓이면 분리 판정은 종전처럼 'FAIL(중계 축)'이고, 웹 관찰 파일이 없으면 'NOT RUN(웹 관찰)'이다. `-WsGateAxes`의 broker 모드 판정(두 노드 게이트 열림과 101)은 P3에서도 그대로다.
- 신선도 표본기의 P3 판. `s6_relay_axes.py freshness`에 `--resource`를 더한다. 주면 그 자원을 ACCEPTING으로 쥔 노드를 소유 노드로, 다른 노드를 비교 노드로 짝짓는다(`owner_of`). P3 실행기는 표본 마켓(KRW-BTC)의 파티션 자원을 넘긴다. 주지 않으면 종전 `leader_from_partitions`다.
- W6 판정기(`judge_w6`). 생존 노드에 붙은 관찰자 연결의 재연결 0(`opens` 1), 생존 노드의 `exchange_ws_relay_degraded` 최대 0, 비영향 마켓마다 kill 뒤 epoch 상승 0과 조밀 결번 0, 영향 마켓마다 RTO + 5초 안에 epoch가 한 번 오르고 그 뒤 조밀 결번 0, 되살아난 희생 노드의 게이트 열림, 합류 뒤 신선도 쌍 모두 참이다. 웹 관찰(`s6-web-resync.mjs` 출력)이 있으면 창 안 티커 합류 요청의 `markets`가 영향 마켓만이고, 계좌·주문 REST가 한 번씩이며, 비영향 마켓의 WS epoch가 그대로이고 결번 0이다. 웹 관찰 파일이 없으면 `web_observed` 축이 거짓이다.
- W7 판정기(`judge_w7`). `--node`(관찰 노드 하나), `--window-from`·`--window-to`, `--p0-markets`·`--p1-markets`를 받는다. 그 노드 연결 하나(`opens` 1)로 두 파티션 마켓 모두 호가 실시간 100건 이상과 체결 10건 이상(W1과 같은 문턱)을 받고, p0 마켓과 p1 마켓의 epoch가 다르며, 창 안 epoch 상승 0, 조밀 결번 0이다. 웹 관찰이 있으면 첫 적재 뒤 REST 0이고 두 파티션 마켓의 epoch가 다르다.

(b) Q2처럼 api-1이 두 파티션을 쥐게 한 뒤(api-2 kill과 재기동) api-1을 45초 멈춘다. 판정: 두 파티션 모두 RTO < 30초(생존 파티션이 없어 ACK 간격 항은 빼고 기록), api-2가 선호 p1을 먼저, p0를 유예 뒤 얻음, 재개한 api-1의 두 파티션 모두 FENCED 강등·재구성.
- **Q4 되돌리기(P3->P2)와 재진입.** P3에서 봇 부하 5분 뒤 `protocol_latch.py transition --target 2 --allow-downgrade`. 판정: `leader_protocol` 2와 이력의 3->2 행, api-1 `matching-engine` 리더와 api-2 팔로워, 두 노드 `exchange_leader_protocol_boot` 2, 샤드 1 수수료 잔고가 전환 전과 같음, 되돌린 뒤 봇 부하 5분의 새 수수료가 샤드 0에만 쌓임, 공통 판정의 무결성 항과 C22'(구간 경계 팔 0)·C30 0, 구간 경계 증분 0(2->3·3->2 두 이력 행 모두, 3->2 직후 표본은 전환 도구가 뜬다). 이어 `transition --target 3`(래치 있음)으로 재진입해 Q0의 배정 판정과 재진입 이력 행의 구간 경계 증분을 다시 본다.
- **Q5 E5 분리.** `-Experiments E5 -Resource matching-p1`(api-2를 망에서 60초 뗀다). 판정: 공통 판정, 격리된 api-2가 복귀 뒤 p1만 강등·재구성, epoch 단조.
- **Q6 E2 DB 절단.** `-Experiments E2 -Resource matching-p1`(`pg-api2` 단절 20초와 블랙홀 20초). 판정: 공통 판정, p0 무영향(ACK 간격), E2 종전 판정.
- **Q7 E6 폭주 중 kill.** `-Experiments E6 -Resource matching-p1`. 판정: 공통 판정과 E6 종전 판정.
- **Q8 수수료 행 결합.** `python harness/scale/s7_fee_coupling.py --pause-s 3 --latency-ms 100 --out "$ev\Q8\fee.json"`. 봇을 멈추고 k6 개방 루프 둘(p0 마켓만, p1 마켓만, 키 파일을 나눠 사용자 집합이 겹치지 않음)을 돌린다. `pg-api1`에 지연 100ms를 넣고, DB 컨테이너 안에 띄운 psql 세션 하나가 20ms 간격으로 `pgrowlocks('balances')`를 `balances`에 ctid로 이어 계정을 가르고, KRW FEE_INCOME 샤드 0 잔고 행을 `application_name = 'chaos-api-1'` 세션이 쥔 순간을 잡으면 곧바로 `docker pause chaos-api-1`, 3초 뒤 `unpause`. 3초는 리스 TTL 6초에서 갱신 주기 2초를 뺀 4초보다 짧아 멈춘 동안 p0 리스가 만료되지 않고, 잠금 대기 상한 2초보다 길어 수수료 행을 기다렸다면 드러난다. 정산 배치는 첫 게시 전에 잠금 계획의 행을 한꺼번에 잡으므로(`lock_balance_rows`, V50) 수수료 행은 배치 내내 잠겨 있다. 멈춘 뒤 표본에 잠금이 없으면(배치가 먼저 끝났다) 풀고 10초 뒤 다시 하고, 다섯 번 모두 못 잡으면 NOT RUN이다. 판정: 멈춘 뒤 1초 표본에서 그 행이 멈춘 세션에 잠겨 있음(양성 축), 창 안 p1 마켓 체결 1건 이상과 KRW 샤드 1 잔고 증가, api-2의 `exchange_settlement_transient_exhausted` 증분 0과 파티션 치명 강등 0, p1 마켓 정산 지연(명령 `created_at`에서 체결 이벤트 `created_at`까지) 최대 ≤ 기준선 + 1초, 리스 인계 없음. 대조 칸(판정 아님): 같은 키 파일로 두 루프를 돌려 사용자 행이 겹치면 p1 정산 지연 최대가 멈춤 길이 가까이 느는지 기록한다(측정 감도).
- **Q9 부하 중 수동 인계.** `python harness/scale/s7_axes.py relocate …`가 봇 부하 중 api-2의 p1 참여를 끄고(api-1이 유예 뒤 얻음), 다시 켜도 돌아오지 않음을 보고, api-1의 p1 참여를 끄고(api-2가 되찾음) 다시 켠다. 판정: 두 인계 모두 p1 RTO < 30초, p0 ACK 간격, 구 쓰기 증분 0, 재배치 뒤 배정이 Q0과 같음.
- **Q10 한 마켓 치명.** `python harness/scale/s7_market_fatal.py --market KRW-ETH`. 소유자가 폐기용 DB에 `trades` INSERT 트리거를 건다. 트리거는 `NEW.market_id`가 KRW-ETH이고 비트랜잭션 시퀀스의 `nextval`이 1일 때만 사용자 정의 SQLSTATE `S7F01`로 실패한다. 이 값은 정산의 재시도 대상 넷(55P03, 57014, 40P01, 40001), 연결 오류(08xxx), 무결성 위반(23xxx, 정산 23514 지표와 섞이지 않게), fencing 거부(P0001) 어디에도 들지 않으므로 정산이 재시도하지 않고 그 마켓 라이터를 치명으로 올린다. 시퀀스는 롤백되지 않으므로 재구성 뒤의 재정산은 통과한다. 한 번 실패를 본 뒤 트리거를 지운다. 판정: p1만 `WRITER_FATAL` 강등·재구성, 차단기 미발동(강등 1회), p1이 30초 안에 다시 리더를 얻음, p0 ACK 간격, 사후 불변식 PASS. `S7F01`이 `TransientDbErrors.isRetryable`과 `DbOutageErrors.isOutage`에서 모두 거짓인지는 구현 때 단위 시험으로 고정한다.
- **Q11 두 노드 콜드 재시작.** 두 앱을 멈췄다가 함께 시작한다. 판정: 각 노드가 선호 파티션을 쥠(재배치 없음), 두 파티션 첫 체결까지 30초 이하, 기동 뒤 2×TTL 동안 비선호 획득 0.
- **Q12 처리량(기록).** 같은 날 P2 스택(중계 오버레이)과 P3 스택에서 `python harness/scale/roundtrip_probe.py --label <칸> --rate 600 --protocol-before-traffic <2|3>`을 P2a, P3a, P2b, P3b 순서로 돈다(부하 계정 16개). 칸 값은 기록이다. 판정은 무결성 축(주문 `400`·`429`·`500`의 사유별 수, 불변식)이다.
- **Q13 W7 두 파티션 수신.** 봇 부하 10분, 한 노드에 붙은 관찰자 하나가 KRW-BTC(p0)와 KRW-ETH(p1)를 받는다. 웹 관찰도 같은 창에 돈다. 판정은 `s6_relay_axes.py judge --experiment W7 --node chaos-api-1 --window-from <부하 시작 + 30초> --window-to <부하 끝> --p0-markets KRW-BTC,KRW-XRP --p1-markets KRW-ETH`이고 기준은 S6 설계 7-2 W7이다(4-13).
- **Q14 C22' 비용.** 폐기용 PostgreSQL(`pml-probe-*` 컨테이너나 실험 스택의 DB)에 합성 명령 100만 행 이상을 두고 하네스 검증설계 §4-1의 절차로 앱 enum의 C22' 수 판을 잰다. 판정: `Execution Time` ≤ 1,500ms. 행 수, 잎 수, 호스트 규격을 증거에 둔다.
- **Q15 힌트 없는 쓰기(기록).** k6 `MARKET_HINT=0`으로 12마켓 부하 3분. LB 로그의 `502` 수, 창 수와 길이, `ups`에 `exchange_write`가 든 줄 수를 기록한다.
- **Q16 두 파티션 인계.** S5 Z4r 판정을 P3에 옮긴다. 회원 하나가 p0·p1 마켓에 미체결 주문을 두고 api-1로 마켓 없는 일괄 취소를 보낸다. 이어 api-1의 `matching-p1` 참여를 끄고(`POST /actuator/partitions`), api-2를 `docker pause`한 채 같은 요청과 회원 폐쇄를 보낸다. 참여를 끄지 않으면 api-1이 p1 만료 뒤 1×TTL(스택 약 12초 뒤)에 p1을 넘겨받아 두 요청을 직접 처리하므로 판정이 요청 시각에 달린다(`PartitionAcquirePolicy.java:54-72`). 요청마다 그 시각과 `leader_lease`의 p1 holder·만료를 판정 파일에 적고, 요청 시점에 p1을 유효하게 쥔 노드가 api-2 밖에 있으면 그 회차는 NOT RUN이다. api-2를 재개한 뒤 인계 행을 보고, api-1의 p1 참여를 다시 켠다. 판정은 하네스 검증설계 §3 P3 실험 Q16이다.

### 5-3. 실행 순서 초안

코드 단계에서 `harness/evidence/pml-S7-gate-draft/`에 실행기와 README를 두고, 돌릴 때 `pml-S7-<YYYYMMDD-HHMM>/`로 옮겨 적는다. 순서는 판정 중요도다.

```powershell
. harness/scripts/lib.ps1
$gate = 'harness/scripts/s7-p3-gate.ps1'
# 1. E12
pwsh -NoProfile -File $gate -Experiment Q1 -EvidenceDir "$ev\Q1"     # 새 스택 -> Q0 -> s7_double_spend.py 1000회
# 2. E4 (+W6)
pwsh -NoProfile -File $gate -Experiment Q2 -EvidenceDir "$ev\Q2"     # adr0022-stage5-chaos.ps1 -Experiments E4 -Protocol 3 -P3 -Resource matching-p1
# 3. E7 a, b
pwsh -NoProfile -File $gate -Experiment Q3a -EvidenceDir "$ev\Q3a"
pwsh -NoProfile -File $gate -Experiment Q3b -EvidenceDir "$ev\Q3b"
# 4. 되돌리기와 재진입
pwsh -NoProfile -File $gate -Experiment Q4 -EvidenceDir "$ev\Q4"
# 5. 나머지
foreach ($q in 'Q5','Q6','Q7','Q8','Q9','Q10','Q11','Q16','Q13','Q15') {
    pwsh -NoProfile -File $gate -Experiment $q -EvidenceDir "$ev\$q"
}
pwsh -NoProfile -File $gate -Experiment Q12 -EvidenceDir "$ev\Q12"   # P2a, P3a, P2b, P3b
pwsh -NoProfile -File $gate -Experiment Q14 -EvidenceDir "$ev\Q14"   # 폐기용 PostgreSQL, 스택 불필요
```

실행기는 실험마다 `docker ps -a --filter "name=chaos-"`가 비었는지 보고, 스택을 세우고, Q0을 하고, 실험을 하고, 부하를 멈춘 뒤 드레인하고, 사후 권위 run과 `summary.sql`을 떠서 판정 파일을 남기고, `-p exchange-pml … down -v`로 내린다. 한 실험의 FAIL은 다음 실험을 막지 않는다. Q0이 BLOCKED이면 그 실험은 BLOCKED로 적고 넘어간다.

### 5-4. 판정 기록

주행 뒤 `harness/evidence/pml-S7-<YYYYMMDD-HHMM>/README.md`에 실험마다 PASS·FAIL·BLOCKED·NOT RUN, 판정 파일 경로, 실패 축을 적고, 이 문서에 결과 절을 더한다. 로드맵과 ADR 0034 진행 표는 S6 관문 기록과 겹치지 않게 S7 몫만 고친다.

## 7. 안전 논증

자산 보존, 주문 멱등성, 리더 권한 검사, 오래된 리더의 쓰기 차단을 약화하지 않는다는 근거다.

- **자산 보존.** V55는 잔고 0의 계정만 더하고 원장 거래를 만들지 않는다. 수수료 게시는 종전처럼 `post_ledger_transaction`의 이중부기이고 샤드만 모드가 정한다. 샤드는 마켓에서만 정해지므로 재생·재정산이 같은 샤드를 고른다. 모드 전환은 정산되지 않은 주문 생성 명령이 0일 때만 되므로(`unsettled_new`) 한 체결이 두 모드에 걸치지 않는다. 되돌리기는 잔고를 옮기지 않는다. C01은 모든 샤드를 합하므로 판정이 그대로다. 잔고 부족은 `balances`의 CHECK(23514)가 트랜잭션 전체를 롤백한다. P2 이상의 예약은 저널 append와 같은 트랜잭션이라 두 노드가 같은 계정을 동시에 써도 행 잠금이 직렬화하고, E12(Q1)와 `CrossNodeDoubleSpendTest`가 그것을 잰다.
- **주문 멱등성.** `client_order_id`의 유일성(`uq_orders_client`, 저널의 주문 생성 부분 유일)은 DB 전역이고 파티션과 무관하다. 소유하지 않는 노드의 선검사 `503`은 아무 상태도 건드리기 전이라 LB가 다른 노드로 넘겨도 한 번의 효과다(S5). 정산의 방출 레지스트리 멱등(§5.5 ②)과 1회 게시 제약은 바뀌지 않는다. nonce는 노드 로컬 그대로다(결정 14).
- **리더 권한 검사.** P3의 쓰기 판정은 기록할 행의 마켓에서 리스 행을 찾아 holder·epoch를 대조한다(`lease_resource_for_market`, DB 설계 §5.4-b). 한 노드는 쥔 파티션의 마켓에만 쓸 수 있다(3절 P7-3: p0 리스로 p1 마켓 0행). 바이너리 상한 3은 획득만 열고 판정 함수를 바꾸지 않는다. 최고 모드 2의 옛 바이너리는 P3 DB에서 획득하지 못한다. P3 게시는 늘 거부된다.
- **오래된 리더 쓰기 차단.** 전환 함수는 모든 리스 행을 잠가 진행 중 쓰기의 커밋을 기다린 뒤 모든 행을 퇴역시킨다. 그 뒤 이전 모드의 epoch는 어느 행과도 맞지 않아 쓰기가 0행이다. 전환 전에 시작한 트랜잭션도 쓰기 판정이 리스 행을 잠근 뒤 새 값을 읽으므로 옛 epoch로 커밋하지 못한다. 3->2도 같은 방식이다. 잠금을 5초 안에 얻지 못하면 아무것도 바꾸지 않는다(3절 P7-4). epoch는 모든 자원을 통틀어 한 번씩 배정되므로 한 파티션의 옛 epoch가 다른 파티션 행과 맞을 수 없다. 이 차단을 세 곳이 확인하고 범위가 다르다(DB 설계 §5.4-e 5). 사후 감사는 C22'(같은 파티션의 역행, 전환 뒤 시작한 트랜잭션이 옛 구간 epoch로 쓴 명령·스냅샷)와 C30(다른 파티션 epoch, 퇴역·게시·이력 없는 epoch, 네 표)이 맡고 둘 다 CRITICAL이다. 사후 감사가 세지 못하는 전환을 가로지른 트랜잭션과 옛 구간 epoch의 이벤트·체결 쓰기는 T4-2 전환 판(`CutoverStaleWriteTest`)과 실험의 구간 경계 증분이 본다(4-7, 3절 R7-4·R7-5). 파티션 인계는 여전히 TTL 만료로만 한다(0002의 '강등 시 리스 즉시 반납 기각' 유지).
- **되돌릴 수 없는 것.** 명령 대역 래치만 되돌릴 수 없다. 도구는 폐기용 스택 가드 안에서 `--latch-band`를 준 경우에만 부른다(결정 9).
- **금액.** 새 코드에 금액 계산이 없다. 실험 스크립트의 금액은 문자열 십진수로 다루고 부동소수점을 쓰지 않는다.
- **Flyway.** 적용된 파일을 고치지 않고 V55만 더한다.

- P3 RTO. 비선호 유예로 P2보다 약 1×TTL 길다. Q2의 상한(10.507초 + 6초)은 P2 최대가 다시 나오면 여유가 작다.
- 사용자 행 결합. 수수료 행은 샤드로 갈랐지만 두 파티션에서 거래하는 같은 사용자의 잔고 행은 여전히 공유다. 멈춘 노드의 트랜잭션이 그 행을 쥐면 다른 파티션 정산이 `idle_in_transaction_session_timeout`(카오스 10초)까지 기다리고, 그 사이 정산 재시도 한도(15초)를 넘기면 다른 파티션 라이터가 치명이 된다. 운영 DB의 그 설정 값은 확인하지 않았다. Q8은 사용자 집합을 나눠 수수료 축만 판정하고 대조 칸으로 감도만 기록한다. E7(Q3)이 실제 부하에서 이 결합을 함께 겪는다.
- 힌트 없는 쓰기. 힌트를 싣지 않는 외부 API 클라이언트는 P3에서 2~3초의 `502` 창을 만날 수 있다(N7-4). LB를 고치지 않았다.
- WS와 브로커. P3에서는 두 노드가 모두 중계에 기대므로 브로커 장애 동안 WS가 전부 거절된다. P3의 E13 판정은 관문에 없다.
- 전환 중 정지. 전환은 드레인(최대 120초)과 두 노드 재시작을 쓰므로 그동안 주문이 멈춘다.
- 계정 수 변화. SYSTEM 계정이 자산마다 는다. 배포 스모크 하나와 서버 시험 넷(2-4, 6-5)을 고치지만 저장소 밖 점검 스크립트(학교 서버의 수기 명령 등)가 39를 기대하면 어긋난다.
- 사후 감사의 빈틈. C22'·C30은 전환을 가로지른 트랜잭션과 옛 구간 epoch의 이벤트·체결 쓰기를 세지 못한다(4-7). 라이브 차단이 둘을 막고 T4-2 전환 판과 실험의 구간 경계 증분이 보지만, 실험 밖 운영 DB에서는 실험 표본이 없으므로 권위 run만으로는 이 둘을 알 수 없다. 운영 DB에서 전환할 때(S8, 사용자 승인 뒤)는 전환 직후와 다음 점검 때 `segment-old-rows.sql`을 떠 대조하는 절차를 더해야 한다.
- W6·W7의 웹 관찰. 판정에 웹 관찰을 넣었으므로 웹 빌드와 교차 출처 배선이 막히면 W6·W7이 NOT RUN(웹 관찰)으로 남는다(4-13). 코드 단계의 `next start` 배선은 정적 export에서 기동하지 않아 늘 NOT RUN이었다. 구현 검토에서 정적 서버와 관찰 브라우저 대체로 고쳤다. 스택 없이 빌드한 산출물을 띄워 관찰기가 거래 화면을 열고 설정한 API 주소로 REST를 내는 것까지만 확인했다(13절 지적 1). 교차 출처와 WS는 스택에서 처음 확인한다.
- 관리 콘솔의 리더 전환 대본. P3에서는 쓰지 않는다(4-11). 발표 녹화의 P3 장면은 `s7-p3-demo.ps1`, 리스 표, Grafana 파티션 패널, 웹 거래 화면으로 한다.
- 병렬 작업. S6 관문이 코드를 바꾸면 S7 코드를 그 위로 옮겨야 한다. ADR 0034 진행 표의 'S7~S8 시작 전' 행과 0099의 'S7 이후는 시작하지 않았다' 문장은 S6 관문 기록과 겹치지 않도록 이 단계에서 고치지 않았다. 0099에서는 대신 S7 문단에 그 문장이 S6 병합 시점 기준이라는 단서를 달았다(11절 지적 12). 통합 때 두 곳을 고친다.
- 주행 환경. 같은 호스트의 다른 작업과 겹치면 ACK 간격·RTO·처리량 표본이 흔들린다. Q12는 기록으로만 둔다.
- 스택의 앱 로그인. 카오스 스택의 앱은 소유자 로그인이라 V49 권한 선행 조건(`app_role_*`)의 효과를 스택에서 보지 못한다. 시험(`PartitionProtocolTransitionTest`)만 본다.
- 미확인. Q10의 주입 SQLSTATE가 정산 분류에서 치명으로 가는지, 두 노드 동시 기동에서 재배치가 얼마나 자주 필요한지, pgrowlocks 표본이 20ms 간격으로 수수료 행 잠금을 실제로 잡는지는 코드와 스택에서 확인한다.

## 10. 사용자 확인이 필요한 것

머리의 스무 항목이다(19·20은 검토 대응에서 더했다). 그 밖에 이 단계가 새로 드러낸 판단은 둘이다. 하나는 되돌린 DB에 남는 샤드 1 수수료 잔고를 그대로 둘지(지금 설계) 샤드 0으로 옮기는 원장 거래를 둘지이고, 다른 하나는 P3에서 브로커 장애 동안 WS를 모두 거절하는 S6 규칙을 발표 전 범위에서 그대로 받아들일지다.

## 11. 검토 대응 (2026-09-25)

같은 날 이 설계와 계약에 대한 검토 지적 14건을 받았다. 두 쌍(1·7, 3·13)은 같은 지적이다. 코드, 계약, 하네스 실행기와 폐기용 컨테이너 확인(3절 R7, C7 재해석)으로 대조했다. 모두 실제 문제로 판단해 고쳤다. 검토가 낸 고침과 다르게 고친 곳은 지적 2(이벤트·체결 표를 시각 팔에 넣지 않음), 지적 9(커밋 순서 표지를 쓰지 않음), 지적 11(`lease_row_missing`을 도달 불가로 보지 않음), 지적 12(S6 진행 문장 대신 S7 문단에 단서)이고 이유를 각 항에 적었다. 새 확인의 원자료는 [확인 기록](../../../harness/evidence/pml-s7-probe-20260925/README.md)의 '설계 검토 대응 확인' 절이다.

### 지적 1·7. SYSTEM 계정 39개를 단언하는 서버 시험이 수정 목록에서 빠졌다 (medium, medium)

지적대로다. `ReadRoleIntegrationTest.catalogSeedIsRepeatableAndCreatesNoUsersOrFunds`(`config/ReadRoleIntegrationTest.java:182`)는 Flyway로 저장소의 마이그레이션 전체를 올린 DB(:59-60)에서 시드 뒤 SYSTEM 계정 39개를 단언한다. V55의 트리거가 시드의 FEE_INCOME 샤드 0마다 샤드 1을 더하므로 설계대로 구현하면 서버 빌드가 이 시험에서 실패한다.

바꾼 것: 2-4의 목록을 다섯 곳(스모크 하나, 서버 시험 넷)으로 고치고 6-5에 이 시험을 넣어 샤드별로 단언하게 했다(샤드 0 39개, FEE_INCOME 샤드 1 13개, 합 52개). 9절의 '시험 넷'도 고쳤다. `owner_type = 'SYSTEM'`과 `FEE_INCOME`을 서버 시험, 배포, 하네스 스크립트에서 다시 찾았고 이 밖에 개수나 한 행을 단언하는 곳은 없었다(`SettlementLockPlanTest.java:164`는 목록으로 읽는다). 같이 본 배포 스모크의 마이그레이션 개수 검사는 이 브랜치에서 V48부터 이미 맞지 않고 main의 `9e3dae9b`가 고쳤으므로 병합 때 그 판을 따른다고 6-5에 적었다.

### 지적 2. 사후 감사가 옛 구간 epoch의 이벤트·체결·스냅샷 쓰기를 세지 않는데 센다고 적었다 (medium)

지적대로다. C22'의 세 팔은 `command_journal`만 읽고, C30은 P3 구간 epoch만 본다. 그래서 3->2 뒤 옛 P3 리더가 정상 획득한 epoch로 쓴 이벤트·체결·스냅샷 행과, 2->3 뒤 `matching-engine`의 P2 epoch로 쓴 같은 표의 행을 어떤 사후 감사도 세지 않는다. 폐기용 PostgreSQL에서 그대로 확인했다(3절 R7-5). 그런데 DB 설계 §5.4-e 5와 이 문서 7절, API 설계 §6-C ⑦은 사후 감사가 이것을 센다고 적었다. 종전 ⑯ 주석의 '(event_journal/trades/snapshots 동일 패턴)'도 실제 SQL과 달랐다. 종전 C22부터 SQL은 `command_journal`만 읽었다.

검토가 낸 '네 표의 합집합에 각 표의 `created_at`으로 구간 경계 팔을 건다'는 스냅샷에만 따랐다. `snapshots.created_at`은 명령과 같은 DB의 `now()`라(2-5) 같은 술어가 성립한다. 스냅샷 표는 행이 적어 비용도 거의 늘지 않는다. `event_journal`·`trades`의 `created_at`은 engine_ts 파생이고 DB `now()`를 금지한다(V1:613, :231). 정산은 명령의 engine_ts를 넣고 재정산도 그 값을 다시 쓴다(`SettlementService.java:857`, `:1018`). 앱 시계와 DB 시계를 비교하는 셈이라 전환 전에 접수한 명령의 늦은 정산은 거짓 음성, 앱 시계가 앞선 노드의 쓰기는 거짓 양성이 된다. 원 명령과 이벤트의 epoch를 잇는 팔(이벤트 epoch < 원 명령 epoch)은 이벤트 표와 명령 표를 전량 조인해야 한다. C22' 수 판이 이미 비용 문턱(1,500ms) 가까이라 앱 판에 넣을 수 없고, 넣더라도 옛 명령의 늦은 정산은 세지 못한다.

바꾼 것: 네 가지다. (1) ⑯의 구간 경계 팔에 `snapshots`를 더하고 목록 판의 열을 `(arm, tbl, subject)`로 바꿨다(DB 설계 §6.4, 수 판 `c22p-count-r2.sql`). (2) 감사 범위를 실제 술어대로 적었다. DB 설계 §5.4-e 5에 차단을 확인하는 세 곳(사후 감사, T4-2 전환 판, 실험의 구간 경계 증분)과 각 범위를, ⑯ 주석과 설명 문단, 4-7, 7절, API 설계 §6-C ⑦, 하네스 검증설계 C22' 주석과 §4-4 ⑦에 같은 범위를 적었다. (3) 사후 감사가 세지 못하는 전환 경계를 두 곳이 본다. 서버 시험 `CutoverStaleWriteTest`(T4-2 전환 판, 6-2)는 전환 뒤 다시 시작하지 않은 옛 모드 노드의 접수·정산·스냅샷 쓰기가 모두 거부되고 네 표의 옛 구간 epoch 행 수가 늘지 않는 것을 본다. P3 실험의 공통 판정에는 구간 경계 증분 0을 더했다(5-2). 전환 직후(노드 시작 전)와 실험 끝에 네 표의 옛 구간 epoch 행 수를 세어 같아야 한다. 전환 뒤 배정되는 epoch는 모두 그 이력 행의 `epoch_floor`보다 크므로 이 수는 늘 수 없고, 시계와 커밋 순서에 기대지 않는다(3절 R7-3~R7-5에서 새 주입마다 늘었다). (4) `HarnessSqlVerdictTest`에 3->2 뒤 P3 epoch의 이벤트·체결 행을 넣어 C22'·C30이 0이고 구간 경계 증분이 느는 것을 고정한다(6-2). 9절에 사후 감사의 빈틈을 위험으로 적었다.

### 지적 3·13. P3 오버레이 초안에 JDBC `ApplicationName`이 없다 (low, low)

지적대로다. 4-9와 결정 12는 두 앱의 JDBC 주소에 `ApplicationName`을 준다고 적었지만 초안에는 선호 파티션과 LB 마운트만 있었다. 초안대로 구현하면 Q8의 pgrowlocks 표본이 `application_name = 'chaos-api-1'` 세션을 찾지 못해 수수료 행 결합 판정을 잃는다. C7 해석도 설계의 오버레이를 확인한 것이 아니었다.

바꾼 것: 초안에 노드별 `SPRING_DATASOURCE_URL`을 넣었다. 기본 파일의 Toxiproxy 주소(api-1 `chaos-toxiproxy:15432`, api-2 `:25432`)를 지키고 `?ApplicationName=chaos-api-1`·`chaos-api-2`만 붙였다. Toxiproxy를 거치지 않으면 Q6(E2)의 절단이 그 노드에 닿지 않기 때문이다. 해석 스크립트가 JDBC 주소(비밀 값이 없다)를 함께 적게 고쳐 다시 돌렸다(3절 C7, `compose-s7-config-r2.log`). `Test-P3Overlay`와 Q0 기동 확인에 두 앱의 주소 확인을 더했다(4-9, 5-2). 하네스 검증설계와 하네스 CI/CD의 오버레이 문장도 고쳤다.

### 지적 4. Q16의 '멈춘 동안 409' 판정이 요청 시각에 달린다 (low)

지적대로다. api-2를 멈추면 p1의 비선호 백업인 api-1이 만료를 본 뒤 1×TTL을 더 기다려(`PartitionAcquirePolicy.java:54-72`, 스택 약 12초) p1을 얻는다. 그 뒤의 일괄 취소와 회원 폐쇄는 api-1이 직접 처리해 `200`이 된다. S5의 같은 실험은 두 노드의 참여를 모두 껐다.

바꾼 것: 검토의 (a)와 (b)를 함께 둔다. api-2를 멈추기 전에 api-1의 `matching-p1` 참여를 끄고 끝에 다시 켠다. 요청마다 시각과 p1 holder·만료를 판정 파일에 적고, 요청 시점에 p1을 유효하게 쥔 노드가 api-2 밖에 있으면 그 회차는 NOT RUN이다(5-2 Q16, 하네스 검증설계 Q16, 결정 16).

### 지적 5. V55 해시가 대조 규칙과 다른 정규화의 값이다 (low)

지적대로다. `f750f412d27be052`는 끝 줄바꿈 하나를 포함한 초안 파일 바이트의 해시다. 대조 규칙(LF, 끝 줄바꿈 제외)의 문자열 해시는 `7a75c805b58f1646`이고 DB 설계 §3.10 블록에서 뽑은 문자열과 같다. 같은 날 다시 계산해 확인했다.

바꾼 것: 4-1에 두 값과 각각 무엇의 해시인지 적었다. 확인 기록 README의 파일 표도 고쳤다.

### 지적 6. Q2(E4 + W6)와 Q13(W7)을 판정할 수단이 없고, P3에서 W5 판정이 E4를 뒤집는다 (high)

지적대로다. 실행기는 `-Relay`인 E4에 W5 판정을 고정 인자(생존 노드 api-2)로 걸고 거짓이면 'FAIL(중계 축)'로 바꾼다(2-6). W5는 모든 마켓의 epoch 상승을 요구하지만 P3의 p1 kill에서 p0 마켓 epoch는 오르지 않아야 하고, Q2에서 죽는 노드가 api-2다. 신선도 표본기는 P3에서 소유 노드를 찾지 못해 표본이 비고, 판정기에는 W6·W7이 없으며, 실행기 가드는 `-Protocol 2`만 받는다.

바꾼 것: 4-13에 넷을 정했다. (1) 실행기의 가드와 `$Protocol -eq 2` 분기를 P3까지 넓히고, `-Protocol 3`의 E4 중계 판정을 W6으로 바꾼다. 생존·희생 노드는 콘솔의 kill 대상에서, 영향·비영향 마켓은 `market_lease_partition`에서 실행기가 정해 넘긴다. (2) `s6_relay_axes.py judge`에 W6·W7을 더한다. 판정 기준은 S6 설계 7-2 그대로다. (3) 신선도 표본기는 `--resource`를 받아 그 파티션의 소유 노드와 다른 노드를 짝짓는다. ### 지적 9. 구간 경계 팔의 `created_at`은 커밋 시각이 아니라 트랜잭션 시작 시각이다 (medium)

지적대로다. `command_journal.created_at`은 `DEFAULT now()`이고 append가 넘기지 않는다. 전환 전에 시작해 전환 뒤 옛 epoch로 커밋한 트랜잭션은 `created_at`이 `changed_at` 앞이라 구간 경계 팔이 세지 못한다. 폐기용 PostgreSQL에서 3->2를 가로지른 트랜잭션(전환 전 BEGIN, 6초 뒤 쓰기 판정을 거치지 않은 소유자 INSERT와 커밋)의 두 행을 구간 경계 팔이 세지 못했다(3절 R7-4).

라이브 차단에는 이 빈틈이 없다. 전환 전에 시작한 트랜잭션도 쓰기 판정(`append_command_journal_row`, `assert_and_lock_market_leader`)이 리스 행을 `FOR KEY SHARE`로 잠근 뒤 새 값을 읽는다. 전환이 행을 쥐고 있으면 그 커밋을 기다렸다가 퇴역한 값을 읽어 거부된다. 판정을 전환 전에 마쳤다면 전환이 그 커밋을 기다린다. 그래서 이 빈틈은 쓰기 판정을 우회한 결함에서만 생기고, 그것을 잡는 것이 사후 감사의 몫이다.

검토가 낸 보완 술어 둘 가운데 첫째(같은 마켓에서 새 구간 첫 행보다 seq가 큰 옛 구간 행)는 마켓 안 팔이 이미 센다. 마켓 채번은 카운터 행을 커밋까지 잠그므로(V46 `next_market_journal_value`) 마켓 안 seq 순서가 커밋 순서다. R7-4에서 새 구간 행이 먼저 커밋된 마켓 1의 행은 마켓 안 팔이 셌다. 둘째(전환 때 배정된 seq·event를 기록해 대조)는 쓰지 않는다. 전환 함수가 마켓 카운터 행을 잠가 그 값을 남겨야 커밋 순서가 정확해지는데, 쓰기는 카운터 행을 잠근 뒤 리스 행을 잠그므로 리스 행을 먼저 잠근 전환이 카운터를 기다리면 진행 중 쓰기와 교착이 난다. 카운터를 잠그지 않고 값만 읽으면 전환 전에 채번한 트랜잭션을 여전히 놓친다.

바꾼 것: 셋이다. (1) 한계를 DB 설계 ⑯ 주석·설명 문단·§5.4-e 5, 하네스 검증설계 C22' 주석, 4-7, 7절에 적었다. (2) 이 빈틈도 지적 2의 두 곳이 본다. 구간 경계 증분은 커밋 순서와 무관하게 세므로 R7-4의 두 행을 모두 셌고(13에서 15), `CutoverStaleWriteTest`는 전환을 가로지른 트랜잭션이 쓰기 판정에서 거부되는 것을 본다. (3) `HarnessSqlVerdictTest`에 전환을 가로지른 트랜잭션을 음성 대조로 넣어 한계를 고정한다(새 구간 행이 없던 마켓은 C22' 0, 먼저 커밋된 새 구간 행이 있는 마켓은 마켓 안 팔 1, 6-2).

### 12-2. 설계와 다르게 하거나 더한 것

4. **Q3b의 두 파티션 판정을 위해 `s7_axes.py partition-rto`와 인계 순서 기록을 더했다.** 희생 노드가 `-Resource` 밖의 파티션도 쥐었으면 실행기가 그 파티션의 RTO를 따로 재고(`rto_<자원>.json`), `victim-writes`가 희생 파티션마다 다른 holder가 처음 쥔 표본의 주입 뒤 초(`takeover_after_inject_s`)를 적어 '선호 p1을 먼저, p0를 유예 뒤'를 본다.

### 지적 1. 웹 관찰 배선이 `next start`라 기동하지 않는다 (medium)

지적대로다. `web/next.config.ts`가 `output: "export"`이고, 설치된 Next 15.5.20은 이 설정에서 `next start`를 예외로 끝낸다. 작업 트리에서 `next start -p 39990`을 돌려 종료코드 1과 같은 문구를 확인했다. 그대로였다면 Q2(W6)·Q13(W7)은 늘 NOT RUN(웹 관찰)이었다. 같은 확인에서 막힘이 하나 더 나왔다. 관찰기 `s6-web-resync.mjs`는 playwright가 내려받은 chromium을 쓰는데, 이 PC에는 그 브라우저가 없어 `chromium.launch()`가 실행 파일 없음으로 끝났다.

바꾼 것은 넷이다. (1) 새 `harness/scale/web_out_server.py`가 `web/out`을 루프백(127.0.0.1과 ::1)에서 낸다. 경로 해석은 chaos-web nginx의 `try_files $uri $uri.html $uri/`와 같고, 루트 밖 경로는 404다. 주소 재사용을 켜지 않으므로 다른 프로세스가 쥔 포트에는 묶이지 않는다. (2) `s7-p3-gate.ps1`의 `Start-GateWeb`이 이 서버를 띄운다. 기동 조건은 서버 프로세스가 살아 있고 거래 화면(`/exchange/KRW-BTC`)이 200인 것이다. dev CORS가 허용하는 출처는 `http://localhost:3000` 하나다. 그래서 포트가 3000이 아니거나 3000번을 이미 누가 쓰면 사유를 적고 멈춘다. 빌드에 준 환경 변수는 빌드 뒤 되돌린다. (3) `s6-web-resync.mjs`는 내려받은 chromium이 없으면 설치된 Chrome, Edge 순으로 띄우고 결과의 `browser`에 적는다. 브라우저 내려받기(`npx playwright install`)는 사용자 허가가 필요한 일이라 대체를 골랐다(AI 선택, 사용자 확인 대상). (4) 4-13, 4-14, 9절, 12-4, 증거 초안 README를 고쳤다.

확인은 이렇다. `harness/scale/test_web_out_server.py` 12개와 `test_stage5_runner_args.py`의 원문 대조 1개가 통과했다. 스택 없이 한 번 돌려 보기도 했다. `NEXT_PUBLIC_API_BASE=http://localhost:39581`로 빌드한 산출물을 3917번에 띄웠다. 39581번에는 듣는 서버가 없다. `/exchange/KRW-BTC`는 localhost, 127.0.0.1, ::1에서 모두 200이었고 없는 경로는 404였다. 관찰기를 12초 돌리자 설치된 Chrome(`browser: chrome`)으로 거래 화면을 열었다. 정적 서버 로그 67줄은 모두 200이었다. 페이지는 `/api/v1/` REST 9건(markets, ticker, orderbook, trades, candles 등)을 냈다. API 주소에 서버가 없어 WS 프레임은 0이다. 교차 출처와 WS 수신은 스택에서 처음 확인한다. 확인용 빌드 뒤에는 기본 설정으로 다시 빌드했다.

### 지적 2. P3에서 관리 콘솔의 리더 전환 대본을 진행할 수 없다 (low)

지적대로다. P3에서는 두 노드가 모두 readiness 200이라 대본 첫 단계가 '리더 2대 관측'에서 멈춘다. 다음 단계 설명은 두 리더를 결함이라고 적는다. 세대는 `matching-p0` 한 행이라 p1 인계를 보지 못하고, 안내 명령 `e4-leader-kill.ps1`은 P3에서 `-Resource`가 없어 멈춘다. 발표 녹화가 이 화면의 리스 표를 쓰므로, 그대로 두면 P3 녹화 화면에 결함처럼 읽히는 문구가 뜬다.

바꾼 것: 검토가 낸 첫 방법을 따랐다. 첫 단계가 `leases[]`에서 `matching-engine` 밖의 자원을 보면 '파티션 리스 matching-p0·matching-p1 · P1·P2 전용 대본'을 적고 멈춘다. 한 노드가 두 파티션을 쥐어 리더가 한 대로 보일 때도 같다. 파티션마다 기준 리더와 세대를 잡는 P3 대본은 만들지 않았다(AI 선택, 사용자 확인 대상). 모의 데이터는 `matching-engine` 한 행이라 모의 화면은 그대로다. 4-11, 4-12, 4-14, 6-4, 9절과 [관리자 설계](../product/관리자_설계.md)의 대본 설명을 고쳤다. `web/tests/drills.test.ts`에 P3 사례를 더했고, 분기를 지우는 변이에서 이 사례가 실패하는 것을 봤다. 웹 시험 570개, 웹 빌드, 토큰 게이트가 통과했다.

### 지적 3. 백엔드 CI의 paths가 서버 시험이 읽는 계약 문서를 빠뜨렸다 (low)

지적대로다. 범위를 넓혀 보면 `server/app/build.gradle.kts`의 `test` 작업 입력 가운데 넷이 CI paths에 없었다. 계약 문서 폴더, `harness/sql`, `harness/relay`, VM 실습망의 `summary.sql` 사본이다. 계약 문서 밖의 셋은 S7 전부터 빠져 있었다.

바꾼 것: 계약인 하네스 CI/CD §2-1의 표와 설명을 먼저 고쳤다. 이어 `ci-backend.yml`의 두 paths 목록(pull_request, push)에 네 경로를 더했다. 이 목록이 시험 입력과 같아야 한다는 주석을 워크플로와 `build.gradle.kts`에 적었다. 원격 CI는 돌리지 않았다(푸시하지 않음). YAML을 파이썬으로 읽어 두 목록이 같은 것만 확인했다.

### 지적 4. 내리는 전이의 `unsettled_new`를 보는 시험이 없다 (medium)

지적대로다. 종전 시험은 P2에서 `blockers(2)`의 결과만 봤고, 전환 함수의 내리는 경로는 부르지 않았다.

바꾼 것: `PartitionProtocolTransitionTest.downgradesAreRefusedWhileANewCommandIsUnsettled`를 더했다. 두 경우를 본다. P2에서 정산 전 NEW를 둔 채 확인 인자를 준 2->1, P3에서 p1 마켓의 정산 전 NEW를 둔 채 3->2다. 둘 다 55000과 `unsettled_new`로 거부되고 모드·리스 행·이력·퇴역 행이 그대로여야 한다. 정산한 뒤에는 3->2와 2->1이 된다. 검토의 변이(선행 조건 호출을 오르는 전이에만 검)를 걸자 이 시험이 '2->1 가 정산 전 NEW 를 두고 됐다'로 실패했다. 3->2만 건너뛰는 변이에서는 '3->2 가 …'로 실패했다. 두 변이 모두 되돌렸고, V55 파일 해시(`f750f412d27be052`)가 원본과 같은 것을 확인했다.

### 지적 5. 최고 모드 주석이 옛 동작을 적고, 운영 배선으로 P3 획득을 보는 시험이 없다 (low)

### 지적 6. 12-2의 10번이 C30 범위 열의 이유를 틀리게 적었다 (low)

### 지적 7. 단계 계획의 S7 줄이 코드 단계를 반영하지 않았다 (low)

지적대로다. 단계 계획 S7 절의 '상세 설계' 줄에서 '코드, 관문 시험, … 아직 없다'를 설계 당시의 문장으로 고쳤다. 그리고 코드 단계와 이 대응의 결과를 한 문장으로 더했다. 12-4가 '고치지 않은 문서'로 든 것은 S6 관문 기록과 겹치는 곳(진행 표, 로드맵, 0099 앞 문단)이다. 단계 계획의 S7 절은 S7 몫이라 그 목록에 들지 않는다.

### 14-2. 주행 중 고친 것

서버 코드는 바꾸지 않았다. 자산 보존·멱등·펜싱 결함은 나오지 않았다. 판정 값도 바꾸지 않았다. 고친 여덟 곳은 모두 판정 규칙이 뜻하는 표본을 뜨지 못한 도구와 스택 설정이고, 고치기 전 회차는 통과 증거로 쓰지 않고 다시 쟀다. 자세한 경위는 관문 기록의 '주행 중 보정'이다.

1. 카오스 compose가 회원 세션 서명 시드와 비밀번호 페퍼를 넘기지 않아 api-2가 api-1의 회원 토큰을 `401`로 거절했다. 첫 Q1은 실패 쪽이 모두 `401`이라 경합 없이 '성공 하나'가 채워졌다(양성 축 미달로 NOT RUN). 앱 공통 환경에 두 값을 `.env.chaos`에서 넘기게 했고(비우면 종전 동작), 실행기와 판정기에 인증 거절 0의 전제를 더했다. 운영 기동은 `StartupSecretValidator`가 세 값을 요구하므로 카오스 스택만의 빈틈이다.
2. 생존 파티션 ACK 기준선에 P3 전환의 정지 창이 들어가 기준선이 21초까지 부풀었다. 기준선을 Q0 준비 시각 뒤로 자르게 했다(`s7_axes.py ack-interval --baseline-from`).
