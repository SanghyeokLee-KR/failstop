# 거래소의 조회·쓰기 비율 조사

2026-09-23 교수 상담에서 받은 질문을 정리한다. 거래소에서 조회 트랜잭션과 쓰기 트랜잭션 중 어느 쪽이 많이 일어나는지 논문 등으로 확인하라는 조언이었다. 사용자는 조회가 대부분이라면 주문 쓰기 경로를 마켓별로 나눌 필요가 없다는 판단 기준을 세웠다. 이 문서는 그 판단에 쓸 외부 근거와 우리 시스템의 실측값을 모은다. 결정은 아직 내리지 않았다.

결론부터 말하면, 거래 시스템은 요청 수나 DB 트랜잭션 수로 세면 조회가 많다. 공개 자료에서는 대체로 3:1에서 15:1 사이다. 다만 암호화폐 거래소 자체의 조회·쓰기 비율을 실측해 공개한 자료는 찾지 못했다. 조회가 많다는 사실만으로 쓰기 경로를 나누지 않아도 된다고 말하는 자료도 없었다. 대형 거래소가 매칭을 나눌 때 밝힌 이유는 조회 비율이 아니라 쓰기의 절대량, 한 종목에 몰린 주문의 격리, 급증 대비였다. 그래서 교수님께 드릴 답은 조건부다. 우리 엔진의 최대 쓰기 수요가 단일 리더 용량보다 충분히 낮고, 리더 전환 때 모든 마켓이 함께 멈추는 시간을 받아들일 수 있으면 단일 리더를 유지한다.

외부 자료는 조사 에이전트가 2026-09-23에 원문 페이지나 PDF를 직접 열어 수치를 확인했다. 인용은 짧게 줄이고 수치는 원문 그대로 옮겼다. 비율 가운데 원문에 없는 값은 원문 수치로 계산했다고 따로 적었다.

## 조회가 많다는 근거

| 자료 | 세는 단위 | 수치 |
|---|---|---|
| TPC-E 명세 v1.14.0 (TPC, 2015) | DB 트랜잭션, 정해진 혼합 비율 | 조회 전용 76.9%, 읽기·쓰기 23.1% |
| Chen, Ailamaki, Athanassoulis 외, SIGMOD Record 39(3):5~10, 2010 | 디스크 I/O 요청 | TPC-E 읽기 90.69%, 쓰기 9.31% (9.7:1). TPC-C는 1.9:1 |
| 한국은행 『2021년도 금융정보화 추진 현황』(2022) 표 I-16, I-18 | 증권사 MTS·웹 서비스 이용 건수, 일평균 | 아래 표 |
| Bronson 외, TAO, USENIX ATC 2013 (거래소 자료 아님) | 데이터 저장소 요청 | 읽기 99.8%, 쓰기 0.2% |

TPC-E는 증권사 업무를 본뜬 표준 벤치마크다. 거래 건수를 세면 조회가 약 3배 많다. 그러나 명세는 주문 접수(Trade-Order)와 체결 완료(Trade-Result)를 가장 무거운 등급으로 두고, 처리량 지표 tpsE도 완료된 체결만 센다. Chen 외의 논문은 같은 벤치마크를 상용 DBMS에서 돌려 디스크 I/O를 쟀다. 버퍼 풀 아래의 저장장치 트래픽이므로 사용자 요청 수가 아니다.

한국은행 자료는 국내 증권사 앱과 웹의 하루 평균 이용 건수를 서비스 종류별로 나눈다. 거래소 매칭 엔진이 아니라 증권사 창구의 수치다.

| 채널, 연도 | 조회 | 주식매매 | 조회 대 매매 (계산값) |
|---|---|---|---|
| 모바일 2019 | 92.3% | 6.0% | 15.4:1 |
| 모바일 2020 | 85.2% | 13.2% | 6.4:1 |
| 모바일 2021 | 87.8% | 10.9% | 8.0:1 |
| 웹 2021 | 98.1% | 1.4% | 약 69:1 |

거래가 급증한 2020년에는 매매 비중이 두 배로 올랐다. 평균 비율이 아니라 급증 구간의 비율로 용량을 잡아야 한다는 뜻이다. AWS 한국 블로그(2022-11-18)는 같은 자료를 87.7%와 89.9%로 옮겼지만 원문은 87.8%와 89.8%다. 원문을 인용한다.

## 쓰기 경로가 체결 수보다 무거운 이유

조회는 캐시, 복제본, 약간 늦은 값, 한 번 만든 시세를 여러 구독자에게 밀어 주는 방식으로 나눌 수 있다. 주문, 취소, 정정은 모두 매칭 엔진 하나가 순서를 정하고 저널이나 합의 커밋으로 영속한 뒤 잔고에 반영해야 한다. 게다가 주문 메시지는 체결보다 훨씬 많다.

미국 SEC의 2013년 자료에서 주식 체결량은 호가로 들어온 주문 수량의 3.2~3.7%였다. 거래 상위 10종목의 중앙값은 4.4%다. 단위는 주식 수이며 메시지 수가 아니다. Gould 외의 호가창 연구 정리(Quantitative Finance 13(11), 2013)는 조사한 시장에서 주문의 70%에서 80% 넘게가 체결 없이 취소됐고, 한 외환 연구에서는 99.99%를 넘었다고 적는다. 암호화폐에 한정한 검증된 수치는 Mizrach(arXiv 2201.01392 v2, 2023) 하나다. 스테이블코인 쌍에서 체결 한 건당 취소 건수가 바이낸스는 3 미만, 코인베이스의 DAI는 6 초과, 비트파이넥스의 DAI는 300을 넘었다. 거래소와 종목에 따라 두 자릿수 이상 차이가 나므로 봇이나 시장 조성자가 쓰기량을 좌우할 수 있다.

거래소들의 주문 한도도 이 부담을 겨냥한다. 바이낸스는 체결되지 않은 주문만 계정별 한도에 센다. 크라켄은 고객별·종목별 카운터를 두고, 5초 안에 취소한 주문에는 새 주문의 8배를 매긴다.

## 거래소 API 호출 한도

| 거래소 | 조회·시세 한도 | 주문 한도 |
|---|---|---|
| 바이낸스 현물 (2026-09-23 `exchangeInfo` 조회) | IP당 분당 요청 가중치 6,000 | 계정당 10초 100건, 하루 200,000건 |
| 업비트 | 시세 그룹마다 IP당 초당 10회 | 계정당 초당 12회 |
| 빗썸 (2026-08-26 개정 안내) | 공개 API 분류마다 IP당 초당 150회 | 개인 API 분류마다 IP당 초당 140회 |
| 코인베이스 Exchange | IP당 초당 10회 | 프로필당 초당 15회 |

이 값은 고객 한 명에게 허용하는 정책이며 실제 트래픽을 잰 것이 아니다. 조회와 주문의 한도가 비슷한 크기라서 한도만 보면 조회 위주 설계로 보이지 않는다. 실시간 시세는 요청으로 읽지 않고 웹소켓으로 밀어 주기 때문이다. 바이낸스 문서는 REST로 호가창 스냅샷을 한 번 받은 뒤 웹소켓 차분을 클라이언트에서 적용하라고 안내한다. 코인베이스는 시세 서비스가 한 원천을 받아 여러 구독자에게 흘려보내는 구조를 공개했다(엔지니어링 블로그, 2025-08-04). 시세 조회는 구독자 수에 따라 늘고 매칭 엔진에는 닿지 않는다.

## 매칭을 나누는 거래소와 나누지 않는 거래소

코인베이스 인터내셔널 거래소는 단일 스레드 매칭 엔진 하나를 5노드 Raft 클러스터로 운영한다(Frank Yu, QCon SF 2025, InfoQ 녹취). 조회는 게이트웨이 옆의 결정적 복제본이 처리해 쓰기 리더를 방해하지 않는다. 발표자는 초당 수백만 건을 넘어야 샤딩을 검토한다고 말했다. LMAX는 스레드 하나의 업무 처리기가 초당 약 600만 주문을 처리하고, 같은 입력을 처리하는 대기 처리기와 복제된 조회 모델을 따로 둔다(Martin Fowler, 2011).

매칭을 나누는 곳도 있다. CME Globex는 상품군을 마켓 세그먼트로 묶어 세그먼트마다 엔진 인스턴스를 둔다. 공개 문서에 이유는 적혀 있지 않다. 한국거래소 엑스추어 3.0(2023)은 특정 종목에 주문이 몰리는 상황에 대응하려고 시장별로 매매체결을 나눴다. 업비트는 2023년 매칭 엔진을 수평 확장할 수 있게 다시 만들어 초당 4만 건 넘게, 서버를 늘리면 10만 건 넘게 체결한다고 발표했다. 언론 보도에 실린 회사 주장이며 분할 방식은 밝히지 않았다. 크라켄은 2023년 1분기 주문·취소·정정 요청의 최대 처리량이 분당 100만 건을 넘었다고 밝혔다. 계산하면 초당 약 16,700건의 쓰기다. 매칭을 나눈 곳이 이유를 밝힌 경우 모두 쓰기량이나 종목 격리를 들었고, 조회 비율을 든 곳은 없었다.

국내 학술 자료(KCI, DBpia, RISS)에서는 암호화폐 거래소의 조회·쓰기 비율이나 시스템 구조를 잰 논문을 찾지 못했다. 웹 검색으로만 찾았고 각 사이트의 자체 검색은 쓰지 않았다. 2024년 12월 업비트·빗썸·코인원 접속 장애에 대해서는 금융감독원이 트래픽이 몰려 서버 용량이 부족했던 것을 원인으로 봤다는 보도가 있다(뉴시스, 2025-02-06). 업비트는 평소 동시 접속 용량이 50만 명인데 당시 54만 명이 몰렸다. 금감원 원문 자료는 확인하지 못했다.

## 우리 시스템에 대입한 값

교수님의 판단 기준을 우리 시스템에 적용하려면 두 조건을 우리 값으로 봐야 한다. 아래 값은 모두 로컬 Docker나 학교 AWS의 기록이며 서로 다른 시험의 값을 한 결과로 합치지 않는다.

첫째, 최대 쓰기 수요와 단일 리더 용량이다. 로컬 Docker에서 잰 단일 리더의 접수 천장은 초당 272~273건이었고 상한은 접수 락이었다([09-13 측정](../../measurements/20260913.md)). 이 천장은 fsync 속도에 따라 달라져서, fsync가 느렸던 09-14의 초당 112.45건과는 나란히 비교하지 않는다([09-14 측정](../../measurements/20260914.md)). 272/s 천장에서 DB CPU가 앱 리더 CPU의 약 두 배였고, 매칭 계산은 명령 처리 시간의 0.1% 미만이었다([접수 동시성 증거](../../../harness/evidence/accept-concurrency-20260913/README.md), [직렬 구간 분해](../../../harness/evidence/writer-breakdown-20260909/README.md)). 봇 목표를 초당 300건으로 올린 로컬 주행에서 체결은 초당 18.1건이었고 조회 계층 평균 사용률은 12% 아래였다([하네스 검증설계](../contracts/하네스_검증설계.md)). 학교 AWS의 시장 봇은 세 종목 합계 3 OPS로 돈다([로드맵](../../ROADMAP.md)). AWS에서의 단일 리더 천장은 아직 재지 않았으므로 로컬 천장을 클라우드 용량으로 쓰지 않는다.

둘째, 리더 전환 때 모든 마켓이 함께 멈추는 시간이다. 로컬 9단계 시험에서 E2·E4·E5·E6·E7의 복구 시간은 각 1회 5.979~10.134초였고, 리더 프로세스를 죽이는 E4는 7.925초였다([0099](../adr/0099-current-architecture.md)). 로드맵의 공통 완료 조건은 앱 리더 장애 후 사람 개입 없이 30초 안에 거래를 재개하는 것이다. 반복 안정성과 AWS 결과는 아직 없다.

이 값만 보면 두 조건 모두 지금 부하에서는 단일 리더 쪽을 지지한다. 남은 확인은 AWS에서 봇의 주문·취소를 포함한 급증 혼합으로 단일 리더 천장을 재는 일과, 리더 전환 시간을 여러 번 반복해 재는 일이다. 마켓별 리더 설계(ADR 0034 초안)를 계속할지는 이 조사와 위 두 측정을 보고 사용자가 정한다.

## 확인하지 못해 근거로 쓰지 않은 것

바이낸스의 초당 140만 주문 처리는 제3자 글에서만 봤다. 엑스추어 플러스(2014)의 절대 처리량은 검색 요약에서만 봤다. 코인베이스 Advanced Trade의 한도는 공식 페이지에서 수치가 빠져 코인베이스 Exchange의 한도로 대신했다. 나스닥 주문의 약 95% 취소와 주문의 1%만 체결된다는 수치는 검색 조각에서만 봤다. 2022년 1월 미국 주식의 체결 대비 취소 9.52는 Mizrach의 인용으로만 확인했다.
