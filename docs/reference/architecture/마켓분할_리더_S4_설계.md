# 마켓 분할 리더 S4 상세 설계: 파티션 단위 Java

2026-09-24 작성. [ADR 0034](../adr/0034-market-partitioned-leadership.md)의 단계 S4(파티션 단위 Java)를 현재 코드에 맞춰 구체화한 설계다. 단계의 범위와 관문은 [단계 계획](마켓분할_리더_단계계획.md) S4 절이 정했다. 기준 코드는 작업 브랜치 `claude/per-market-leader`의 `60be79e0`(S3 커밋)이다. 설계 중에 병행 작업의 `91813dd5`(S2 관문 재측정 기록)가 들어왔지만 문서와 증거만 바꿨고 서버 코드는 같다. 계약은 코드보다 먼저 고쳤다. 코드는 같은 날 이 설계대로 썼고 2026-09-25 문서 단계에서 작업 브랜치에 한 커밋으로 남겼다. 설계와 다르게 한 것, 시험 수, 폐기용 스택 실험 결과는 12절에 있다. 구현 검토 수정 뒤 이미지로 다시 돌린 폐기용 스택 관문은 E2·E1 FAIL로 통과하지 못했다(13-2). 고친 곳은 [DB 설계](../contracts/백엔드_DB_설계.md) v2.55 §3.8·§5.4-c, [API 설계](../contracts/백엔드_API_설계.md) v2.55 §2-3·§2-4·§2-5-b·§6-C, [하네스 검증설계](../contracts/하네스_검증설계.md)의 S4 패치 노트와 §2-2·§3·§5-1, [하네스 CI/CD](../contracts/하네스_CICD_IaC.md) §5-2·§5-6이다(8절). PostgreSQL과 nginx 동작 확인의 원자료는 [`harness/evidence/pml-s4-probe-20260924/`](../../../harness/evidence/pml-s4-probe-20260924/README.md)에 있다. 같은 날 이 설계와 계약에 대한 검토 지적 17건을 받아 설계와 계약을 고쳤다. 지적마다의 판단과 바꾼 것은 11절에 있다. S4 코드에 대한 구현 검토(라운드 1) 지적 12건의 판단과 고친 것은 13절에 있다.

S4가 끝나도 DB 모드는 P2다. S4 바이너리는 파티션 리더 모드(P3)의 코드 경로를 모두 갖지만, 리스를 획득할 때 최고 모드 2를 넘기므로 P3 DB에서는 어떤 파티션도 얻지 못한다(3절 G1). P3를 실제로 켜는 것은 S7이다. P1·P2에서는 파티션이 `matching-engine` 하나이고 모든 마켓을 덮는다. S4의 모든 코드가 이 한 파티션 계획으로 돌기 때문에, P2에서 돌리는 관문 실험이 곧 새 코드 경로의 시험이다.

단계 계획과 ADR이 적은 것과 다르게 정한 것이 일곱 있다. 모두 이 설계를 맡은 AI가 2026-09-24에 정했고 사용자 확인 대상이다(10절).

1. 마켓 접수 경합(접수 락 대기 초과, append 트랜잭션의 55P03·57014·40P01·40001)을 `503`으로 내지 않는다. 이 요청이 접수되지 않았음이 확정된 경우는 `429`(`detail.bucket=market`)다. 주문 생성에서는 이 요청이 멱등 키를 새로 넣었고 V47 판정이 그 키를 지운 경우(DISCARDED)이고, 취소는 늘 그렇다. 같은 키의 다른 요청이 관여했거나, 판정이 실패했거나, 이미 저널에 있는 주문을 다시 보낸 요청이면 `409 order_in_progress`다. ADR 결정 8은 예약 단계의 `lock_timeout` 초과를 `503`으로 돌린다고 적었고, 결정한 값 11과 API 설계 v2.54는 인그레스의 `max_fails`·`proxy_next_upstream`을 조정하면서 `503` 매핑을 켠다고 예고했다. 폐기용 nginx에서 리더의 `503` 한 건이 모든 마켓의 쓰기를 1초 넘게 `502`로 만들었고, 오픈소스 nginx에는 그것을 피하는 설정이 없었다. 그래서 인그레스를 바꾸지 않고 응답 코드를 바꿨다(4-12, 4-13).
2. 주문 생성·취소 밖 경로의 55P03은 S4에서도 `500`이다. 단계 계획은 S1이 미룬 55P03의 `503` 매핑을 S4에서 인그레스 조정과 함께 켠다고 적었다. 인그레스를 바꾸지 않으므로 이 매핑만 켜면 리더를 쓰기 업스트림에서 빼는 경로가 새로 생긴다. S5가 파티션별 업스트림을 만들 때 다시 본다(4-12).
3. 파티션 치명 강등 뒤 같은 프로세스의 재승격을 허용하면서 '기간 결속 쓰기'를 새로 둔다. 기간은 리스를 얻는 순간 만들고 승격 재생과 라이브 루프가 같은 기간을 쓴다(4-5). 재승격이 강등 전 스레드에 새 epoch를 빌려줄 수 있기 때문이다. ADR에는 없던 규칙이다.
4. 차단기는 10분 창 안의 파티션 치명 강등 3회다. 결정한 값 12가 S4에 남긴 값이다(4-7).
5. 획득 전용 커넥션 풀을 따로 두지 않는다. 획득은 기존 리스 풀(최대 2)에서 하고 획득 트랜잭션에만 `lock_timeout` 1000ms를 건다. 단계 계획의 '갱신 전용·획득 전용 연결 분리'는 풀 크기가 파티션 틱 스레드 수 이상이라는 조건과 획득 대기의 상한으로 채운다(4-3).
6. 좀비 판정의 수요에서 마켓 접수 경합으로 끝난 요청을 뺀다. 노드 층과 파티션 층 모두다. 접수 락을 쥔 요청이 상한보다 오래 쥐고 있어서 난 대기 초과만 수요로 남긴다(4-11). DB 설계 §5.4 v2.19의 수요 정의를 바꾼다.
7. 단계 계획의 종료 조건 'P2 동작 차이 0'을 '관문 판정 차이 0'으로 읽는다. S4의 범위 자체가 P2에서도 보이는 동작을 바꾸기 때문이다. 기동의 팔로워 시작, 종신 강등의 재구성 전환, 접수 경합의 `429`·`409`, 획득의 잠금 대기 상한이 그렇다. 이 차이는 4-21에 모았다. 관문의 판정 술어(RTO, 옛 epoch 쓰기, 불변식)는 S3와 같고, 경합 응답이 가용성 계산에서 빠지는 만큼 경합 상한을 판정에 더했다(7-2).

## 1. 범위와 전제

범위는 단계 계획 S4 절 그대로다. 파티션별 리스 서비스 인스턴스, 갱신 전용·획득 전용 연결 분리와 획득 `lock_timeout`, 파티션별 접수 게이트, 파티션별 승격 코디네이터와 재생 대상 M(P) 한정, `installFrom` 부분 설치와 `WriterRouter`의 대상 밖 샤드 덮어쓰기 제거, 마켓별 팔로워 엔진과 인계, 파티션 강등·fresh 재구성·차단기(결정 12), 단일 호출 강등, 파티션별 좀비 판정, `onLeadershipLost`의 파티션 리스너, 지표 `partition` 태그, `EpochSource.epoch(marketId)`, 관리 API의 리스 목록과 웹 관리 화면, 선호 표와 비선호 유예(결정 2·4), P3 전용 수수료 샤드 함수(결정 10), DynamoDB 공급자의 파티션 모드 차단(결정 18)이다. S1·S3가 S4로 미룬 것도 여기서 한다. 주문 생성·취소 경로의 일시 DB 오류(55P03 포함)의 응답과 원소별 처리, `accept-lock-wait`·`accept-lock-timeout` 값, 인그레스 판단이다. 비접수 경로 55P03의 `503` 매핑은 위 2처럼 S5로 넘긴다. 하네스는 `'matching-engine'` 직접 참조, `Get-FirstTradeSql`의 epoch 비교, `harness.failover_runs`의 자원 열을 파티션에 맞게 바꾼다.

전제는 다섯이다.

- DB 모드는 P2이고 S4 동안 바꾸지 않는다. 새 마이그레이션은 V53 하나다(DB 설계 §3.8). V53은 Testcontainers 일회용 DB와 폐기용 스택에만 적용한다. 보존 볼륨과 main 스택의 DB에는 적용하지 않는다.
- AWS에 접속하지 않는다. 검증은 로컬 Docker의 폐기용 스택에서 한다(결정한 값 19).
- main의 병행 커밋(`fdf5d53a` 트리거 함수 권한 회수, `9e3dae9b` 배포 스모크)은 이 단계에서 합치지 않는다. 9절에 합칠 때의 Flyway 순서 문제를 적었다.
- 같은 작업 트리에서 S2 관문 재측정 작업이 병행했고 `91813dd5`로 커밋됐다. 그 작업이 고친 파일(`docs/measurements/20260924.md`, `docs/measurements/README.md`, ADR 0034, 단계 계획, S2 설계, `harness/evidence/pml-s2-gate-20260924-0440/README.md`, `harness/evidence/pml-s2-gate-rerun-20260924-1553/`)은 이 설계가 건드리지 않는다. 단계 계획 S4 절에서 이 문서를 가리키는 문장, ADR 0034와 0099, 로드맵의 갱신은 문서 단계에서 한다. 이 설계의 계약 문서 변경은 아직 커밋하지 않았다.
- 단계 계획이 적은 대로 웹 관리 화면 파일은 다른 작업과 겹칠 수 있다. 코드 착수 때 `web/lib/admin/`과 드릴 화면의 담당을 나눈다.

## 2. 현재 코드에서 확인한 것

인용 줄 번호는 `60be79e0` 기준이다.

### 2-1. 리스와 강등은 노드에 하나다

`LeaderLeaseService`는 리스 하나를 필드로 쥔다(`server/app/src/main/java/kr/exchange/engine/LeaderLeaseService.java:48-94`). holder는 인스턴스마다 만든 UUID이고(:57), 종신 강등 표식 `demoted`(:66)가 서면 `tryAcquire`(:333-385)가 다시 획득하지 않는다. 갱신은 `renew`(:396-411)가 생존성 판정을 거치는 단일 경로 `extendLease`(:425-431)로 하고, 틱 스레드는 이름이 `leader-lease`인 하나다(:434-449, :475-486). 갱신 거부는 `markLost`(:488-515)로 가고, 승격 재생 구간이면 회복 가능 반납, 아니면 종신 강등이다. DB 접속 오류는 상실로 단정하지 않는다(:387-395 주석). `stop()`은 리스를 반납하지 않는다(:451-469).

보관소는 자원이 고정이다. `PostgresLeaderLeaseStore.RESOURCE`가 `matching-engine`이고(`engine/lease/PostgresLeaderLeaseStore.java:22`), 획득은 최고 모드 `LeaseResources.MAX_PROTOCOL = 2`를 넘기는 한 문장 자동 커밋이다(:36-45, `LeaseResources.java:16`). `MeteredLeaderLeaseStore`의 계수기 태그는 `outcome`이고 자원 태그가 없다(`MeteredLeaderLeaseStore.java:43-67`). 갱신과 획득은 같은 리스 전용 풀(최대 2)을 쓴다(`config/LeaseDataSourceConfig.java:63-74`, `application.yml`의 `exchange.engine.lease-datasource`). 서비스 빈도 하나다(`config/EngineConfig.java:67-93`). 획득 함수(V50 `lease_acquire_capped`, V52 교체)는 `lock_timeout`을 스스로 바꾸지 않는다.

그래서 파티션을 나누는 일은 이 필드들을 인스턴스로 떼는 데서 시작한다. 획득은 옛 리더의 KEY SHARE를 기다리는 동안 풀 커넥션을 쥐고 있으므로(DB 설계 §5.4-b), 파티션이 둘이 되면 막힌 획득과 다른 파티션의 갱신이 같은 풀을 나눠 쓴다.

### 2-2. 기동은 리스를 얻고, 승격은 모든 마켓을 다룬다

기동 수명주기는 상실 리스너로 모든 라이터를 멈추게 걸고(`EngineConfig.java:621`), `recoverAtBoot`(:645), `installFrom`(:648), `bootstrap`(:652), `lease.start`(:654), 팔로워 시작(:657) 순으로 돈다. `recoverAtBoot`는 크래시 창이 있으면 TTL 1.5배(상한 30초)까지 리스를 기다려 얻는다(`engine/EngineRecovery.java:152-158`, :185-191, :321-333, :464-490). 부팅 때 리더가 되면 `bootstrap`이 게이트를 바로 연다(`engine/PromotionCoordinator.java:121-144`).

승격 코디네이터의 게이트는 노드 전체에 하나다(:103-105). 획득 콜백은 DEMOTED이면 승격하지 않는다(:152-170). 재승격 금지 계약이다. 재생 생략 판정은 모든 마켓의 head를 읽고(:309) 모든 마켓이 닿았을 때만 생략하며(:319-331), 아니면 모든 마켓을 새 엔진에 복원한다(:337-339). 게이트는 모든 라이터가 돌 때만 연다(:237). 승격 재생은 라이브 루프와 같은 sink 계약으로 이벤트 재적재와 재정산을 DB에 쓰고(`EngineRecovery.java:55` 주석), 그 쓰기는 루프를 설치하기 전에 일어난다.

### 2-3. 설치는 대상 밖 샤드를 덮고, 루프 지표는 루프 객체에 묶인다

`WriterRouter.installFrom`은 복구 결과에 있는 마켓의 샤드에 엔진을 심고, 복구 결과에 없는 기존 샤드에는 빈 엔진을 심는다(`engine/WriterRouter.java:115-134`, 덮어쓰기는 :125-132). 파티션이 둘이면 이 두 번째 루프가 다른 파티션의 살아 있는 북을 지운다. `haltAll`(:137-141)과 `isRunning()`(:149-154)도 모든 샤드를 본다. 마켓 하나의 판정은 `isRunning(int)`(:162-168)다.

라이터 팩토리는 루프마다 `LoopFatalHandler(leaderLeaseService)`와 `SnapshotCapture(…, leaderLeaseService, …)`를 걸고(`EngineConfig.java:377-399`), 큐 깊이·직렬 구간 지표를 루프 객체에 묶어 등록한다(:400-433). Micrometer는 같은 이름과 태그의 미터를 다시 등록하면 기존 미터를 돌려주므로, 재구성으로 루프를 새로 만들면 지표가 옛 루프 객체에 묶인 채 남는다. `LoopFatalHandler`는 원인과 무관하게 종신 강등한다(`engine/LoopFatalHandler.java:29-32`). 승격 코디네이터는 `VirtualMachineError`만 재시도하지 않는다(`PromotionCoordinator.java:208`, :283). 루프는 sink 예외를 받으면 처리기를 부르고 멈춘다(`server/engine/src/main/java/kr/exchange/engine/core/SingleWriterLoop.java:246-252`).

### 2-4. 쓰기 경로는 리스 서비스의 현재 epoch를 읽는다

명령 저널 append는 `lease.requireLeader()`로 epoch를 얻고(`journal/CommandJournalAppender.java:176`), fencing 거부를 받으면 `demoteUnlessStillLeader`로 재확인한다(:221-230). 정산도 같다(`ledger/SettlementService.java:370`, :393-397). 정산의 일시 오류 재시도는 시도 사이에 잠들고(:314-361, :352), 시도마다 `requireLeader`를 다시 부른다. 스냅샷 캡처는 `lease.current()`로 epoch를 읽는다(`snapshot/SnapshotCapture.java:95`). 이벤트 저널 append도 같다(`journal/EventJournalAppender.java:66-75`). 승격 재생의 재적재 sink도 이 두 appender다.

지금은 종신 강등 뒤 같은 프로세스가 다시 리더가 되지 않으므로 문제가 없다. 강등 뒤 재승격을 허용하면, 강등 전 루프나 앞선 승격 재생의 스레드(예: 정산 재시도 대기 중)가 깨어나 리스 서비스의 새 epoch를 읽을 수 있다. holder도 같으므로 DB 판정을 통과한다(4-5).

### 2-5. 팔로워는 공유 엔진 하나이고 승격 뒤 다시 시작하지 않는다

`FollowerCatchUp`은 공유 엔진 하나를 쥐고(`engine/FollowerCatchUp.java:75`), 잠금 하나로 틱과 승격 정지를 가른다(:89). 승격 정지는 유계 대기 뒤 스케줄러를 끄고 다시 시작하지 않는다(:210-232). 틱은 `lease.isLeader()`를 보고(:235-266), 전진은 모든 마켓의 물질화 경계까지 한다(:269-299). 상태 게이지 값은 0 정지, 1 따라잡는 중, 2 리더라 쉬는 중, -1 어긋남이다(:69-72, :122-124). 파티션 강등 뒤 팔로워로 돌아오려면 파티션마다 다시 시작할 수 있어야 한다.

### 2-6. 접수 게이트와 오류 응답

`EngineBridge.submit`은 마켓 접수 락을 얻지 못하면 `AcceptBusyException`(:177-184), 마켓 라이터가 멈췄으면 `IllegalStateException`(:188), 노드 게이트가 닫혔으면 `NotReadyException`(:194)을 낸다(`engine/EngineBridge.java:171-226`). 게이트는 노드 하나다. 마켓 접수 락은 공정하지 않은 `ReentrantLock`이고 append 트랜잭션 전체 동안 쥔다(:50-56, :228-241).

`OrderGateway`는 append 예외 뒤 이 요청의 키를 잡았으면 V47 판정으로 저널에 있는지 보고(`api/order/OrderGateway.java:287-305`), 없으면 `submitFailure`(:572-591)로 응답을 고른다. 루프 정지는 `503`, 접수 락 대기 초과도 `503`, P2 잔고 부족 23514는 `400`이고, 나머지는 원래 예외로 올린다. 교착·직렬화 실패만 센다(:603-611). 일괄 취소는 `503`만 미완료로 센다(:705-731). 응답 epoch는 `matching-engine` 행에서 읽는다(:739-744, `api/common/EpochSource.java:22-32`). 취소 경로는 루프 정지·정지 마켓·접수 락 초과만 바꾼다(:746-760).

V47 판정(`resolve_failed_order_intake`)은 이 요청이 채번한 주문 id의 NEW만 찾는다(`V47__order_intake_failure_resolution.sql:65`). 기존 키에 공유 표시를 채운 요청은 `p_discard_key`가 거짓이라 자기 NEW가 없으면 곧바로 NOT_JOURNALED다(:71). 키를 새로 넣은 요청은 공유 표시가 없는 자기 해시 행을 지우면 DISCARDED, 공유 표시 때문에 남기면 KEPT, 행이 없으면 ABSENT다(:81-90). 곧 판정은 '이 요청의 명령이 저널에 없다'까지만 말한다. 같은 키로 다른 요청이 커밋했거나 커밋 중인지는 KEPT와 공유 표시로만 드러난다. 게이트웨이는 공유 표시를 채운 요청(`claimKey`의 SHARED)도 키를 잡은 요청으로 다룬다(`OrderGateway.java:251-254`).

`ApiExceptionHandler`는 접수 락 초과·루프 정지·분류된 일시 오류를 `503`으로 낸다(`api/common/ApiExceptionHandler.java:75-105`). 55P03은 Spring 6 기본 번역에서 `UncategorizedSQLException`이라(`AcceptLockTimeoutIntegrationTest.java:121-123`) 마지막 처리기의 `500`으로 떨어진다(:114-119). 인증 필터도 분류된 일시 오류만 `503`으로 바꾼다(`api/auth/ApiAuthFilter.java:113-120`). 접수 락 대기 상한과 append `lock_timeout`의 코드 기본값은 0(끔)이다(`config/EngineProperties.java:44-57`).

### 2-7. 관측·관리·하네스

HA 게이지는 `node` 태그만 갖는다(`engine/HaAvailability.java:50-61`). 관리 API는 `matching-engine` 행 하나를 읽는다(`admin/HaMonitoringController.java:96-116`). 하네스 상태는 보관소의 현재 리스 하나를 내고(`harness/HarnessController.java:50-72`), 페일오버 적재는 자원을 받지 않는다(:110-125, `harness/FailoverRecorder.java:33-48`). 불변식 상시 스캔은 리더 노드에서만 돈다(`harness/InvariantScheduler.java:30-34`).

dev 프로파일은 actuator를 8080에 두고(`application.yml:164-169`) prod만 8081 관리 포트로 뗀다(:224-231). 카오스 스택은 dev에 `chaos-monkey` 문서를 겹치고, 그 문서가 노출 목록을 다시 정의한다(:352-367). 하네스 nginx의 `location /`는 모든 경로를 쓰기 업스트림으로 보내고(`harness/nginx/nginx.conf:59-72`), api 노드는 호스트 포트 18080·28080으로도 열려 있다(`harness/docker-compose.chaos.yml:132`, :154). 그래서 카오스 스택에서는 actuator의 쓰기 연산(지금은 `admission`)에 LB와 호스트 포트로 인증 없이 닿는다.

하네스 스크립트는 `'matching-engine'`을 직접 쓴다. `harness/scripts/lib.ps1:602`(리더 컨테이너 판별), `e2-db-cut.ps1:85`, `e3-redis-outage.ps1:26-27`, `e5-net-partition.ps1:123-124`·`:152`, `e7-gray-pause.ps1:110`·`:112`·`:136`, `adr0022-stage7-cold-restart.ps1:164`, `probe-layers.ps1:64`, `up.ps1:65`, `harness/scale/s3_common_axes.py:76`, `protocol_latch.py:87`이다. `e1-pg-latency.ps1:99`는 함수 본문 검사라 리스 행 조회가 아니다. T5 술어는 epoch만 비교한다(`lib.ps1:277-282`). S3 공통 판정은 로그 문구(`종신 강등`, `리더십 상실`)로 실험 끝 리더 노드의 강등 여부를 본다(`s3_common_axes.py:79-84`).

### 2-8. 수수료 계정과 DynamoDB

체결 수수료 샤드는 상수 0이고(`SettlementService.java:88`), 계정 캐시는 자산 하나로 키를 잡으며(:200), 조회는 샤드 0을 넘긴다(:1071-1100). 정산 잠금 계획도 샤드 0의 수수료 계정을 넣는다(:527-528). 기동 시드는 샤드 0 계정만 만든다(`ledger/AccountBootstrap.java:34`). DynamoDB 보관소는 모드가 3이면 뜨지 않는다(`config/LeaseStoreConfig.java:101-117`).

### 2-9. 엔진을 끈 노드

봇 노드(`chaos-bots`), 조회 증설 노드(`chaos-api-3`), AWS 조회 노드(`prod,read`)는 엔진을 끈다(`harness/docker-compose.chaos.yml:190`, :226). `LeaderLeaseService` 빈은 조건 없이 뜨고(`EngineConfig.java:67-93`), 팔로워와 기동 수명주기는 `exchange.engine.enabled`일 때만 뜬다(:598-613). 그래서 엔진을 끈 노드에서 리스 서비스는 있지만 시작하지 않는다. `EpochSource`(`ApiConfig.java:426`), `InvariantScheduler`(`HarnessConfig.java:36`), `HarnessController`가 리스 서비스나 보관소를 받는다. 리스 보관소 빈은 공급자 조건만 있고 리스 풀 하나를 받는다(`LeaseStoreConfig.java:119-128`). 리스 풀과 요청 풀은 엔진을 끈 노드에도 있다(조회 역할의 리스 풀은 1). 조회 역할 노드는 로그인이 `leader_protocol`을 읽지 못해 기동 모드를 읽지 않는다(`EngineConfig.java:103-107`, `LeaderProtocolBoot.notRead`). 이 배선은 `EngineDisabledContextTest`와 `ReadRoleIntegrationTest`가 지킨다.

### 2-10. 하네스 실험의 전제

E4는 `docker kill`이 재기동 정책을 건너뛰어 옛 리더가 돌아오지 않는다(`harness/scripts/e4-leader-kill.ps1:6`, `adr0022-stage5-chaos.ps1:391`). 콜드 재기동은 두 노드를 멈춘 뒤 한 노드를 먼저 올려 새 epoch와 접수 재개를 본 다음에 다른 노드를 올린다(`adr0022-stage7-cold-restart.ps1:119-160`). 기동 완료는 liveness와 `exchange_follower_catchup_state`가 0이 아닌지로 본다(:32-46). epoch 판정은 E4만 정확히 +1이고(`e4-leader-kill.ps1:180`), E2·E5·E6·E7은 단조 증가와 holder 교체다(`e2-db-cut.ps1:95`, `e5-net-partition.ps1:167`, `e7-gray-pause.ps1:151`, `lib.ps1:420-423`). 승격 재생 실패의 회복 가능 반납으로 한 사건에서 epoch가 +2 이상 오를 수 있어서다. 오케스트레이터 `adr0022-stage5-chaos.ps1`은 E2·E4·E5·E6·E7·COLD만 부르고(:49-50) E1·E3은 따로 돈다. E3은 Redis 토폴로지가 없어 SKIP이 유효 판정이다(`e3-redis-outage.ps1:1-4`, :20-27). k6는 `429`를 정상 응답으로 선언하고 세기만 하며(`harness/load/order_flow.js:248`, :338-343), 주문 생성의 `409`는 정상 구간 실패로 센다. 봇은 `201`·`200`이 아니면 그 주문을 다시 보내지 않는다(`sim/MarketMakerBot.java:430-452`, `sim/TakerBot.java:368-374`). `harness/scale`의 시험은 unittest로 돈다(`test_s3_common_axes.py:3`).

## 3. PostgreSQL·nginx 동작 확인

설계 전에 불확실한 동작 두 묶음을 폐기용 컨테이너에서 확인했다. 명령과 원시 출력은 [`harness/evidence/pml-s4-probe-20260924/`](../../../harness/evidence/pml-s4-probe-20260924/README.md)에 있다. 카오스 스택, 실험 스택, 보존 볼륨에는 접근하지 않았다.

N은 nginx 1.29.8에서 쓰기 업스트림 두 형태를 흉내 낸 확인이다. 하네스 형태는 1차(리더)와 `backup max_fails=0`(팔로워)이고, 엣지 형태는 두 노드 `max_fails=1` 라운드로빈이다. 둘 다 `proxy_next_upstream error timeout http_502 http_503 non_idempotent`, `tries 2`, `fail_timeout=2s`다. 가짜 노드는 리더면 `200`, 팔로워면 `503`을 내고, 헤더로 한 요청에만 다른 코드를 낸다.

| 번호 | 사례 | 결과 |
|---|---|---|
| N-C1 | 하네스 형태, 리더가 한 요청에만 `503` | 그 요청은 백업으로 넘어가 `503`, 이어 보낸 여섯 건(0.22~1.26초)이 모두 `502`(`no live upstreams`), 3.47초에 회복 |
| N-C2 | 하네스 형태, 리더가 한 요청에만 `429` | 그 한 건만 `429`, 재시도·퇴출 없음, 다음 여섯 건 모두 리더 `200` |
| N-C3 | 하네스 형태, 1차가 팔로워 | 1차 `503` 뒤 백업 `200`, 종전 페일오버 동작 그대로 |
| N-C4 | 엣지 형태, 리더가 한 요청에만 `503` | 그 요청을 포함해 일곱 건(0.84~2.09초)이 모두 `502`, 4.50초에 회복 |
| N-C5 | 엣지 형태, 리더가 한 요청에만 `429` | 그 한 건만 `429`, 다음 여섯 건 모두 `200` |

오픈소스 nginx에서 `proxy_next_upstream`에 넣은 상태 코드는 곧 실패로 세어지고, 넣지 않은 코드는 재시도도 계상도 되지 않는다. 팔로워가 늘 `503`인 이 배치에서 리더의 일시 `503`은 살아 있는 업스트림을 없앤다. 그래서 S4는 리더가 `503`을 내는 경우를 새로 만들지 않는다. 접수 경합은 `429`나 `409`로 내고(4-12), `409`도 `proxy_next_upstream`에 없는 코드라 N-C2와 같은 쪽이다.

G는 PostgreSQL 17.10에 저장소의 V0~V52를 파일마다 한 트랜잭션으로 올리고 DB 설계 §3.8의 V53을 문서에서 그대로 뽑아 올린 확인이다.

| 번호 | 확인 | 결과 |
|---|---|---|
| G0 | 저장소 53개 파일과 V53 적용 | 오류 없음 |
| G1 | 소유자 UPDATE로 모드 3, 최고 모드 2의 p0 획득, `matching-engine` 획득, 최고 모드 3의 p0 획득 | 앞의 둘은 55000, 마지막은 epoch 1 |
| G2 | 다른 세션이 p1 행 KEY SHARE를 4초 쥔 동안 `lock_timeout` 700ms의 p1 획득, 같은 로그인의 p0 갱신, 다른 세션의 p1 새 KEY SHARE | 획득은 `transactionid` 대기 뒤 702.6ms에 55P03, p0 갱신 다섯 번 모두 0.9~2.9ms에 참, 새 KEY SHARE 1.2ms, 획득 이력·p1 행 불변, 남은 잠금 0 |
| G3 | KEY SHARE가 풀린 뒤 `lock_timeout` 없는 p1 획득 | epoch 2, 이력 두 행 |
| G4 | V53 열·CHECK·주석, 앱 로그인 적재, 목록 밖 이름, 조회 로그인 | `text` 널 허용 기본값 없음, 적재 성공(값 있음·NULL), `matching-p9`는 23514, 조회 로그인 읽기 |
| G5 | 마켓 둘의 대응과 모드별 도출, 파티션 한정 T5 술어 | 1은 p0, 2는 p1, P3 도출 각각, P2 도출 `matching-engine`, 술어 실행 |

G1은 S4 바이너리가 P3 DB에서 리더가 되지 못한다는 근거다. G2는 획득 `lock_timeout`의 근거다. 기다리는 FOR UPDATE는 다른 세션의 새 KEY SHARE를 막지 않았으므로(S2 설계 3절 Q3과 같은 성질), 획득을 끊어도 옛 리더 쓰기의 잠금 순서는 바뀌지 않는다. 55P03 뒤 아무것도 남지 않으므로 다음 틱이 다시 시도해도 된다. G2는 세션 단위 `lock_timeout`으로 확인했다. S4는 같은 상한을 트랜잭션 한정 설정(`set_config(…, true)`)으로 건다(4-3). 트랜잭션 한정 `lock_timeout`은 S1의 접수 append가 이미 같은 방법으로 쓰고 `AcceptLockTimeoutIntegrationTest`가 고정했다.

## 4. 설계

### 4-1. 파티션 계획

새 클래스 `PartitionPlan`이 파티션 목록과 마켓의 파티션을 낸다. 노드는 기동 때 한 번 읽은 모드(`LeaderProtocolBoot`, S3)로 계획을 만든다. P1·P2이면 파티션 `matching-engine` 하나이고 모든 마켓을 덮는다. P3이면 `matching-p0`(번호 0)과 `matching-p1`(번호 1)이고 마켓의 파티션은 `market_lease_partition`에서 읽는다. 조회 역할 노드는 모드를 읽지 않으므로(2-9) DB를 읽지 않고 `matching-engine` 하나의 계획을 만든다. 조회 역할이 서빙하는 경로(`markets`·`trades`·`candles`)는 epoch를 싣지 않으므로 P3에서도 이 계획으로 충분하다. 계획은 기동 뒤 바뀌지 않는다. 모드 전환은 앱을 멈춘 정지 창에서 하고(S3 설계 4-7), 전환이 모든 리스 행을 퇴역시키므로 옛 계획의 쓰기는 epoch 불일치로 거부된다.

앱의 대응은 라우팅과 수명주기에만 쓴다. 쓰기 판정은 DB가 기록할 행의 마켓에서 자원을 도출하므로(DB 설계 §5.4-b) 앱이 대응을 잘못 알아도 다른 리스로 쓰기가 통과하지 않는다. 대응 표는 추가 전용이라 앱이 읽은 대응과 DB가 달라지는 경우는 아직 읽지 않은 새 마켓뿐이고, 계획은 모르는 마켓을 만나면 그 자리에서 다시 읽는다. P3에서 대응이 없는 마켓은 DB가 55000으로 거부한다.

`PartitionPlan`은 `partitions()`, `partitionOf(marketId)`, `index(resource)`, `partitioned()`(P3 여부)를 낸다. P1·P2의 `partitionOf`는 DB를 읽지 않고 `matching-engine`을 돌려준다.

### 4-2. 파티션별 리스 서비스

`LeaderLeaseService`에 자원 필드를 더하고 파티션마다 인스턴스를 만든다. 틱 스레드 이름은 `leader-lease-<자원>`이다. holder는 노드 하나(`NodeIdentity`, 기동 때 UUID 하나)를 모든 파티션이 같이 쓴다. epoch가 자원을 통틀어 유일하므로 holder를 나눌 필요가 없고, 하네스의 리더 컨테이너 판별(`lib.ps1:600-622`)이 로그의 holder로 노드를 찾으므로 노드 단위 holder가 그 판별을 그대로 살린다. 기존 생성자는 자원 `matching-engine`과 자기 UUID를 기본으로 둬 시험과 단일 리스 배선을 그대로 쓴다.

새 인스턴스 묶음 `PartitionLeases`가 계획의 파티션마다 서비스를 들고, 빈으로 등록한다. 기존 단일 `LeaderLeaseService` 빈은 없앤다. 대신 쓰는 곳은 셋으로 나뉜다. 파티션을 아는 곳(쓰기 경로, 라이터, 코디네이터, 팔로워)은 파티션의 서비스를 받는다. 노드를 보는 곳(readiness, 불변식 스캔)은 `PartitionLeases`의 집계를 쓴다. 자원을 인자로 받는 곳(하네스·관리 API, `EpochSource`)은 자원으로 찾는다.

엔진을 끈 노드도 `PartitionPlan`과 `PartitionLeases`를 만든다. `EpochSource`·하네스·관리 API가 쓰기 때문이다. 그 노드에서는 파티션별 서비스를 시작하지 않는다. 틱 스레드가 없고 획득·갱신을 부르지 않는다. 서비스를 시작하는 것은 엔진 조건(`exchange.engine.enabled`)에서만 뜨는 기동 수명주기이고 지금과 같다(2-9). 보관소는 지금처럼 리스 풀 하나를 받는다(4-3). 그래서 엔진을 끈 노드의 풀 구성과 연결 수는 S3와 같다. `EngineDisabledContextTest`와 `ReadRoleIntegrationTest`에 이 성질의 단언을 더한다(6-3).

재구성이 끝나면 서비스는 다시 후보가 된다. 리스 서비스는 후보 표식 하나만 더 든다. 파티션 치명 강등은 종신 강등 표식 `demoted`를 세우지 않고 후보 표식을 내리며(`disarm()`), 재구성이 끝나면 `rearm()`이 다시 세운다. 표식이 내려가 있으면 틱은 획득하지 않는다. `demoted`는 노드 치명(`VirtualMachineError`)에만 쓰고, `rearm()`은 `demoted`를 풀지 않는다. `REBUILDING`·`BLOCKED`·`DEMOTED` 같은 파티션 상태는 리스 서비스가 아니라 파티션 수명주기(4-6)가 든다.

### 4-3. 획득의 잠금 대기 상한과 리스 풀

획득은 리스 전용 풀(`exchange.engine.lease-datasource`, 최대 2, 종전 값)에서 그대로 하고, 획득 트랜잭션에만 `lock_timeout`을 건다(DB 설계 §5.4-c 3). PostgreSQL 보관소는 리스 풀 위의 트랜잭션 하나에서 `SELECT set_config('lock_timeout', '<값>', true)` 다음에 `try_acquire_lease`를 부르고 커밋한다. 값은 `exchange.engine.lease-acquire-lock-timeout`(기본 1000ms)이고, `EngineProperties`가 0보다 크고 리스 틱 주기보다 작은지 기동 때 검사한다(기본 틱 3초, 카오스 틱 2초). 설정은 트랜잭션 한정이라 커밋·롤백 뒤 풀 커넥션에 남지 않으므로 갱신·반납·재확인은 S3와 똑같다. 외부 보관소 모드(P1·P2)의 게시(`publish_leader_epoch`)도 같은 방식으로 상한을 받고, 초과는 승격 실패(회복 가능)다. 획득이 왕복 하나와 커밋을 더 쓰지만 리더가 아닌 파티션의 틱마다 한 번이라 비용은 작다.

리스 풀을 쓰는 것은 셋이다. 파티션마다 하나인 틱 스레드(갱신이나 획득, 한 번에 연결 하나), fencing 거부 뒤의 재확인(쓰기 스레드, 드물고 몇 밀리초), 하네스 상태의 현재 리스 조회(`HarnessController`가 보관소로 읽는 짧은 읽기)다. 틱 스레드 수는 P3에서도 2라 풀 최대를 넘지 않는다. 한 파티션의 획득이 옛 리더의 KEY SHARE에 막혀 연결 하나를 쥐어도 다른 파티션의 갱신은 나머지 연결을 쓴다. 재확인이나 조회가 끼어 두 연결이 모두 찬 드문 순간에도 갱신이 기다리는 시간은 막힌 획득의 `lock_timeout`(1초) 이하이고 틱(2초)보다 짧다. 획득이 끊기지 않으면 틱 스레드가 옛 리더의 트랜잭션이 끝날 때까지(`idle_in_transaction_session_timeout` 카오스 10초) 묶이므로 상한은 그 파티션의 틱을 한 틱 단위로 되돌리는 역할도 한다.

설계 첫 판은 세션에 `lock_timeout`을 건 획득 전용 풀(최대 2)을 따로 뒀다. 검토에서 대조군이 S3의 실제 배선(리스 풀 2)이 아니라는 지적을 받고(11절 R14) 다시 따져 보니, 별도 풀의 근거였던 '막힌 획득이 갱신 커넥션을 쥔다'는 틱 스레드 수가 풀 크기 안이고 획득 대기가 1초로 끊기면 생기지 않는다. 별도 풀은 엔진 노드마다 연결 2를 늘려 scale 프로파일의 상한 합을 200 위로 올리고, 엔진을 끈 노드의 배선도 복잡하게 만든다. 그래서 두지 않는다. `RenewUnderBlockedAcquireTest`(6-2)가 이 배선에서 갱신 지연이 한 틱보다 작은지 확인한다. 한 틱을 넘으면 별도 풀 안을 다시 열고, 그때는 DB 설계 §5.4-c 3과 하네스 검증설계 §3의 연결 예산을 먼저 고친다.

55P03으로 끝난 획득은 오류가 아니라 '아직 못 얻음'이다. 틱은 `exchange.leader.lease.acquire.lock_timeouts{partition}`을 올리고 디버그 로그만 남긴다. 연속 30회(카오스 설정에서 약 1분)를 넘으면 경고 로그를 한 번 남긴다. 옛 리더의 쓰기 트랜잭션이 그만큼 오래 열려 있다는 뜻이고, 그 트랜잭션은 `idle_in_transaction_session_timeout`(카오스 10초)이 끊어야 한다.

### 4-4. 기동은 늘 팔로워로 한다

ADR 결정 7의 '부팅은 늘 팔로워로 시작하고 승격 경로를 런타임 경로 하나로 통일한다'를 따른다(DB 설계 §5.4-c 4). 기동 순서는 이렇다.

1. 계획을 만든다(4-1).
2. `EngineRecovery.recoverAtBoot`가 모든 마켓을 물질화 경계까지 대조만 한다. 리스를 얻지 않고 크래시 창을 재적재하지 않는다. `followerAllowed`가 참인 지금 경로(:321-333)에서 획득 시도를 뺀 것과 같다.
3. 대조한 엔진을 마켓별 팔로워 엔진으로 나눠 팔로워에 넘기고 팔로워를 시작한다(4-10). 팔로워 상태는 1이 된다.
4. 라이터 슬롯을 만든다(4-9). 루프는 승격이 기간과 함께 설치할 때 띄우므로, 그 전에는 게이트가 닫혀 있고 명령을 받는 루프도 없다.
5. 파티션마다 코디네이터를 FOLLOWER로 두고 리스 틱을 시작한다. 첫 획득은 런타임 승격(4-8)을 탄다.

`recoverAtBoot`의 대기(`BOOT_PROMOTION_WAIT_CAP`)와 `anotherLeaderRenewing`(:446-460), 부팅 획득 무시용 `arm`은 없어진다. 크래시 창이 있는 콜드 재기동은 기동 대조 한 번과 승격 재생 한 번을 하므로 재생을 두 번 할 수 있다. 스탠바이 승격과 같은 경로라 RTO 게이트(30초)는 그대로이고, X5(7-2)가 콜드 재기동 시간을 잰다. 유효한 리더가 있는 동안 되살아난 노드가 부팅 획득 없이 팔로워로 합류하는지는 X2의 합류 단계가 본다.

`BootPromotionRetryIntegrationTest`는 부팅 획득을 전제로 하므로 `BootAsFollowerIntegrationTest`로 바꾼다(6-3).

### 4-5. 기간 결속 쓰기

리스를 얻는 순간 기간 `LeaderTerm(resource, holder, epoch, generation)`을 만든다. 획득 콜백(4-8의 1단계)이 만들어 승격 워커에 넘긴다. 그 승격의 재생 sink(이벤트 재적재와 재정산), 설치할 루프의 sink, 스냅샷 훅, 치명 처리기, 그 파티션의 접수 게이트가 모두 이 기간 하나를 쓴다(DB 설계 §5.4-c 6). 승격 재생은 루프를 설치하기 전에 DB에 쓰므로(2-2), 기간을 설치 때 만들면 재생 구간의 쓰기가 어느 기간에도 묶이지 않는다(11절 R11). 세대는 획득마다 1씩 오르는 노드 안의 번호다. 같은 epoch를 두 번 얻는 일은 없지만, 앱 판정을 epoch 비교 하나에 기대지 않으려고 둘 다 본다.

- 쓰기는 `term.epoch()`로 DB 판정을 받는다. 리스 서비스의 현재 epoch를 다시 읽지 않는다.
- 쓰기 전에 `leases.isCurrent(term)`(리스 서비스가 지금 쥔 기간이 같은 epoch·세대인가)을 본다. 아니면 DB 왕복 없이 `NotLeaderException`이다.
- fencing 거부 뒤 재확인은 `term.epoch()`로 갱신을 부르고, 참이면 재시도, 거짓이면 `demote(term, …)`다.
- `demote(term, …)`와 `demoteUnlessStillLeader(term, …)`는 현재 기간과 다르면 아무것도 하지 않는다.
- 접수 경로의 append는 라이터가 아니라 요청 스레드에서 돈다. 접수 게이트는 열린 기간을 값으로 든다(닫히면 비어 있다). 접수 경로는 그 마켓 파티션 게이트의 기간을 읽어 그 epoch로 append한다. 게이트 검사와 append 사이에 기간이 바뀌면 옛 epoch라 DB가 거부하고, 그 거부의 재확인은 옛 기간이라 아무것도 강등하지 않는다. 요청은 페일오버 창의 `503`이다.
- 승격 재생이 실패해 회복 가능 반납을 하면 그 기간이 끝난다. 다음 획득은 새 기간이고 새 재생을 처음부터 한다. 앞 재생이 남긴 스레드(정산 재시도 대기 등)는 끝난 기간을 들고 있어 앱과 DB 양쪽에서 거부된다.

필요한 이유는 같은 holder의 재승격이다. 지금은 종신 강등 뒤 재승격이 없다. 회복 가능 반납 뒤의 재승격은 지금도 있지만, 그때 늦게 깨어나는 쓰기는 같은 저널에서 결정적으로 만든 앞 재생의 것이라 새 재생과 출력이 같고 레지스트리 멱등이 이중 게시를 막는다. 재구성 뒤 재승격을 허용하면, 강등 전 루프에서 정산 재시도로 잠들어 있던 스레드(`SettlementService.java:352`)나 스냅샷 캡처 대기열의 작업이 깨어나 새 epoch를 읽고 쓸 수 있다. holder가 같으니 DB 판정도 통과한다. 그 스레드가 쥔 것은 강등 전 엔진이 만든 이벤트이므로, 새 기간의 재생이 같은 명령을 정산하기 전에 끼어들면 정산 순서가 두 벌이 된다. 레지스트리 멱등이 같은 이벤트의 이중 게시는 막지만 두 엔진의 출력이 다를 때는 막지 못한다. 기간 결속은 그 스레드를 옛 epoch에 묶어 앱과 DB 양쪽에서 거부되게 한다.

`TermBoundWriteTest`(6-2)가 이 규칙을 고정한다. 사례는 둘이다. 라이브 사례는 강등 전 루프의 정산이 재시도 대기에 들어간 사이 같은 파티션을 재승격시키고, 깨어난 재시도가 새 epoch로 한 행도 쓰지 못하는지 본다. 재생 사례는 승격 재생 도중 갱신 거부로 회복 가능 반납을 일으킨 뒤 같은 노드가 다시 얻게 하고, 앞 재생의 늦은 정산이 한 행도 쓰지 못하며 새 재생은 정상으로 끝나는지 본다. 대조군은 `requireLeader()`를 쓰는 종전 경로이고 두 사례 모두 새 epoch로 쓰기가 통과해야 한다.

### 4-6. 파티션 강등과 fresh 재구성

강등을 한 번의 호출 `PartitionRuntime.demote(term, reason, cause)`로 모은다. 순서가 계약이다.

1. 그 파티션의 게이트를 닫는다. 이후 그 파티션 마켓의 접수는 저널 전에 `503`이다.
2. 리스 서비스의 기간을 비운다(`markLost`). DB에는 쓰지 않는다. 갱신만 멈추므로 다음 리더는 만료 뒤 새 epoch로 정해진다.
3. 그 파티션 마켓의 라이터를 멈추고 큐를 버린다(`router.halt(M(P))`).
4. 파티션 상실 리스너(관측·readiness)를 부른다.
5. 사유가 차단기 대상이면 센다(4-7).
6. 노드 치명이면 모든 파티션을 같은 순서로 종신 강등하고 상태를 `DEMOTED`로 둔 채 끝낸다. 아니면 재구성 작업을 파티션 작업 스레드에 넘긴다.

강등 사유는 DB 설계 §5.4-c 5의 넷이다. 종전 호출 지점은 이렇게 옮긴다. `LoopFatalHandler`는 그 루프의 기간으로 `WRITER_FATAL`이고, 원인이 `VirtualMachineError`면 `NODE_FATAL`이다. `AssertionError`처럼 VM 오류가 아닌 `Error`는 `WRITER_FATAL`이다. 승격 코디네이터가 재시도를 가르는 기준(`PromotionCoordinator.java:208`, :283)과 같다. 갱신 거부는 게이트가 열린 뒤면 `LEASE_LOST_WHILE_ACCEPTING`, 승격 재생 구간이면 종전 회복 가능 반납이다. 자발적 강등은 `STALL`이다. 승격 완료 시점의 라이터 정지는 `PROMOTION_LOOP_DOWN`이다. 운영자의 참여 끄기는 `PLANNED`다.

재구성은 그 파티션 마켓의 팔로워 엔진과 라이터 샤드를 버리고, 기동 복구와 같은 대조(스냅샷과 저널, 물질화 경계까지)로 팔로워 엔진을 새로 만든 뒤 팔로워를 다시 시작한다. 크래시 창은 재적재하지 않는다. 그것은 다음 리더의 승격 재생이 한다. 재구성이 끝나면 차단기가 닫혀 있고 참여가 켜져 있으면 `rearm()`한다. 재구성이 실패하면 1초에서 시작해 30초까지 두 배씩 늘어나는 간격으로 다시 한다. 격리된 옛 리더(E5)는 격리 중 재구성이 실패하다가 복귀 뒤 성공한다. 재구성 실패는 차단기에 세지 않고 `exchange.partition.rebuild{outcome="failure"}`로 센다. 재구성 중인 파티션은 후보가 아니다.

다른 파티션은 건드리지 않는다. 라이터 정지·게이트·리스·팔로워가 모두 파티션 단위이기 때문이다. 공유하는 것은 노드의 요청 풀과 append 풀, 리스 풀, 노드 층 좀비 판정(4-11)이다.

### 4-7. 차단기

파티션마다 강등 시각 목록을 들고, `WRITER_FATAL`·`LEASE_LOST_WHILE_ACCEPTING`·`STALL`·`PROMOTION_LOOP_DOWN`이 `exchange.leader.partition.demotion-window`(기본 10분) 안에 `exchange.leader.partition.max-demotions`(기본 3)에 이르면 그 파티션을 `BLOCKED`로 둔다. 차단된 파티션은 재구성해 팔로워로는 남지만 리스를 노리지 않는다. `POST /actuator/partitions {"resource":…,"reset_breaker":true}`나 재기동이 푼다. `exchange.partition.breaker.open{partition}`이 1이 되고 `PartitionBreakerOpen` 경보가 뜬다(하네스 CI/CD §5-6).

값의 근거는 이렇다. 같은 결함(예: 재생하면 늘 같은 자리에서 실패하는 명령)이 되풀이되면 두 노드가 번갈아 그 파티션을 얻었다가 치명 강등하고, 강등 사이 간격은 TTL과 재구성 시간이다(카오스 설정에서 수십 초). 10분에 3회는 그 반복이 두세 바퀴 돌았을 때 멈춘다. 일시 사고 한 번이나 운영자 조작으로는 걸리지 않는다. 차단은 가용성을 줄이는 쪽이라 두 노드가 모두 차단하면 그 파티션은 리더가 없다(`PartitionLeaderAbsent`). 무결성보다 가용성을 먼저 잃는 쪽을 골랐다. 그래서 차단기가 세는 강등에 페일오버로 풀리지 않는 원인이 섞이면 안 된다. 한 사용자의 잔고 행 잠금 같은 DB 쪽 경합이 `STALL`로 번지지 않게 한 것이 4-11의 수요 제외다.

### 4-8. 파티션별 승격 코디네이터와 재생 범위 M(P)

코디네이터를 파티션마다 둔다. 상태는 `FOLLOWER`, `PROMOTING`, `ACCEPTING`, `REBUILDING`, `BLOCKED`, `DEMOTED`(노드 치명, 재기동 전용)이고 게이트도 파티션마다 하나다. 승격 워커 스레드는 노드에 하나를 두고 파티션 사이의 승격을 줄 세운다. 두 파티션을 한꺼번에 얻은 노드(다른 노드가 죽은 경우)가 재생 두 벌을 동시에 돌려 요청 풀을 채우지 않게 하려는 것이다.

승격 한 번은 이렇다.

1. 획득 콜백은 기간을 만들고(4-5) 상태를 `PROMOTING`으로 둔 뒤 승격 워커에 넘기고 곧바로 돌아간다. 리스 틱 스레드를 막지 않는다. 상태가 `FOLLOWER`·`PROMOTING`이 아니거나 리스의 후보 표식이 내려가 있으면(재구성·차단·참여 끔과 엇갈린 획득) 승격하지 않고 그 기간을 곧바로 놓는다. 쥔 채 두면 갱신만 하고 접수하지 않는 반쪽 리더가 되기 때문이다(13절 C1). 워커 줄에서 기다린 승격은 시작할 때 세대·상태·기간이 자기 것인지 다시 보고, 아니면 인계·재생·설치를 하지 않는다(13절 C2). 워커가 그 파티션의 팔로워 인계를 한다(4-10). 인계는 마켓별 적용 잠금 안에서 하고 파티션 전체에 2초 상한을 둔다. 상한 안에 끝나지 않으면 그 마켓들에 정지 플래그만 세우고 fresh 재생으로 간다. fresh 재생은 팔로워 엔진을 쓰지 않으므로 늦게 끝나는 팔로워 틱이 만진 엔진은 버려진다.
2. M(P)의 모든 마켓에서 인계 엔진이 저널 head에 닿았으면 재생을 생략한다. 생략 근거인 불변식 M은 마켓마다 성립한다(`FollowerCatchUp` 전진이 물질화 경계까지만 적용한다). 설치 전에 인계 엔진의 마켓별 커서와 상태 해시(`OrderBookImpl.stateChecksum`)를 적고, 설치할 복사본의 해시와 비교한다. 다르면 생략하지 않는다.
3. 아니면 새 엔진에 M(P)만 복원한다. `EngineRecovery.recover(engine, scope, term)`이 스냅샷을 M(P)만 적재하고, 1단계 대조와 2단계 head 고정·재적재를 M(P)의 마켓만 한다. 재적재 sink는 1단계의 기간에 묶인다. 크래시 창 병합 순서(created_at, seq)는 M(P) 안에서 그대로다. P3에서는 파티션 사이 병합이 없어지는데, 자금 쪽은 접수 시점 예약이 그 순서 의존을 없앴다(ADR 0034 근거 절, S3).
4. M(P) 샤드만 같은 기간에 묶인 새 루프로 설치한다(4-9).
5. 게이트는 세대가 같고 상태가 `PROMOTING`이고 리스가 그 기간이며 M(P)의 라이터가 모두 돌 때 연다. 종전 개방 조건(:237)을 파티션에 적용한 것이다.

재시도 규칙(시도 3회, 첫 실패부터 5초 예산, `VirtualMachineError`는 종신)과 재생 표식 토큰, 회복 가능 반납은 종전과 같고 파티션 단위다(DB 설계 §5.4 v2.23·v2.24).

P1·P2에서는 M(P)가 모든 마켓이라 종전과 같은 재생이다. 스냅샷 적재·대조·재적재의 SQL도 같다. 달라지는 것은 마켓 집합과 기간을 인자로 받는다는 것뿐이다.

### 4-9. 라이터 부분 설치

`WriterRouter`의 샤드를 `ShardSlot`으로 바꾼다. 슬롯은 마켓마다 하나이고 생명주기 동안 바뀌지 않는다. 루프와 엔진은 슬롯 안에서 기간마다 바뀐다. 지표는 슬롯에 묶는다. 큐 깊이는 지금 루프를 읽는 게이지이고, 누적 나노초·호출 수는 루프가 끝날 때 슬롯의 누계에 더하는 단조 계수기다. Micrometer가 같은 이름의 미터를 다시 등록하지 않아도 되고 재구성 뒤에도 값이 이어진다. `SnapshotCapture`의 지표도 마켓별로 슬롯에 둔다.

설치 API는 둘이다.

- `install(term, scope, engines)`: `scope`의 마켓만 기존 루프를 멈추고, 기간에 묶인 새 루프에 엔진 복사본을 심어 시작한다. 새 루프의 sink·치명 처리기·스냅샷 훅이 그 기간을 쥔다. 그 밖의 슬롯은 건드리지 않는다.
- `halt(scope)`: `scope`의 루프만 멈추고 큐를 버린다.

`installFrom`의 두 번째 루프(:125-132)를 지운다. 그 루프가 하던 일(복구 결과에 없는 마켓을 커서 0 엔진으로 채우기)은 scope 안의 마켓에만 한다. scope 안인데 복구 결과에 없는 마켓은 그 파티션에서 명령을 적용한 적이 없는 마켓이므로 커서 0 엔진이 맞다. 지연 생성(`shard(marketId)`)은 그대로 두되, 그 마켓 파티션의 기간이 없으면 루프를 띄우지 않는다.

`isRunning(scope)`는 scope의 루프가 모두 돌 때 참이다. 노드 전체의 `isRunning()`은 쓰지 않는다.

`WriterRouterSubsetInstallTest`(6-2)가 scope 밖 슬롯의 루프·엔진·큐·커서가 그대로인지 본다. 대조군은 종전 `installFrom`이고 scope 밖 북을 비운다.

### 4-10. 마켓별 팔로워 엔진과 인계

`FollowerCatchUp`의 공유 엔진을 마켓별 엔진 지도로 바꾼다. 마켓마다 `MatchingEngineImpl` 하나와 적용 잠금 하나를 둔다. 틱은 이 노드가 리더가 아닌 파티션의 마켓만 전진시킨다. 물질화 경계도 따라잡는 파티션의 마켓만 읽고, 따라잡는 파티션이 없으면 틱은 DB에 가지 않는다. 인계한 마켓의 커서는 인계 시점에 멈춰 있어 그 경계 질의가 그 뒤 커밋된 명령을 매 틱 훑기 때문이다. 쉬는 파티션의 격차 게이지는 0이다(13절 C3). 파티션 상태가 `FOLLOWER`나 `BLOCKED`가 아니면 그 파티션의 마켓을 건너뛴다.

인계와 반환은 둘이다.

- `handOver(partition)`: 그 파티션 마켓의 적용 잠금을 차례로 잡아 엔진을 떼어 준다. 떼어 준 마켓은 틱이 만지지 않는다. 잠금 대기는 파티션 전체 2초가 상한이다. 지금 `stopForPromotion`(:210-232)의 유계 대기를 마켓 단위로 옮긴 것이다.
- `rebuild(partition, engines)`: 재구성(4-6)이 만든 새 엔진을 받고 그 파티션의 전진을 다시 켠다.

`FollowerHandoverRaceTest`(6-2)가 적용 도중 인계를 고정한다.

지표 `exchange.follower.catchup.*`에 `partition` 태그를 단다. 상태(`state`)는 파티션마다 내고 값의 뜻은 S3와 같다. 그 파티션이 `FOLLOWER`나 `BLOCKED`면 1(따라잡는 중), `PROMOTING`이나 `ACCEPTING`이면 2(리더라 쉬는 중), `REBUILDING`·`DEMOTED`이거나 팔로워를 아직 시작하지 않았으면 0(정지), 팔로워 엔진이 저널과 갈렸으면 -1이다. 콜드 재기동 스크립트의 기동 완료 판정(liveness와 상태 0 아님, 2-10)은 P2에서 파티션 하나의 값을 읽으므로 그대로 성립한다. 기동 직후 팔로워는 1이고 런타임 승격 뒤 2다. 갈림(-1)은 그 파티션의 인계를 막고(승격은 fresh 재생) 재구성을 예약한다. 갈림은 차단기에 세지 않는다.

### 4-11. 좀비 판정 두 층과 접수 경합

노드 층은 그대로 둔다. 인증 이전의 주문 쓰기 수요(`ApiAuthFilter.java:81`)와 리더 기원 쓰기 커밋을 센다(DB 설계 §5.4 v2.19). 파티션 층을 더한다. 수요는 `EngineBridge.submit` 진입에서 그 마켓 파티션의 게이트가 열려 있으면 센다(접수 락을 얻기 전이다). 완료는 그 파티션의 저널 append 커밋과 정산 커밋이다. 판정기는 노드 층과 같은 `LeaderStallDetector`를 파티션마다 하나 둔다(완료율 5%, 45초, 수요 하한 20건, 누적과 hold, 승격 경계 초기화).

파티션 리스의 갱신은 두 판정을 모두 통과해야 한다. 파티션 층 붕괴는 그 파티션만 `STALL`로 강등하고, 노드 층 붕괴는 그 노드가 쥔 모든 파티션을 `STALL`로 강등한다. 노드 층을 남기는 이유는 좀비의 가장 흔한 모양(요청 풀 고갈, CPU 폭주)이 인증 조회부터 막아 게이트까지 오지 못하기 때문이다(DB 설계 §5.4 v2.19 ①). 파티션 층은 한 파티션의 쓰기 경로만 막힌 경우를 잡는다. 예를 들어 그 파티션의 접수 락을 쥔 요청이 끝나지 않거나, 그 파티션의 append가 경합이 아닌 오류(연결 획득 실패 등)로 계속 실패하는 경우다.

마켓 접수 경합으로 끝난 요청은 두 층 모두 수요에서 뺀다. 경합은 접수 락 대기 상한을 넘긴 것(`lock_wait`)과 append 트랜잭션이 55P03·57014·40P01·40001로 롤백된 것이고, 응답이 `429`든 `409`든 같다(4-12). 이 요청들은 DB에 닿아 유계 시간 안에 확정적인 답을 받았으므로 노드가 일을 못 한다는 증거가 아니다. 원인은 대개 DB 쪽 잠금(멈춘 트랜잭션이나 운영자 세션이 쥔 잔고 행)이라 페일오버로 풀리지도 않는다. 수요로 세면 한 사용자의 잔고 행이 오래 잠긴 저트래픽 구간에서 그 사용자의 재시도만으로 완료율이 5% 밑으로 내려가 `STALL` 강등이 나고, 새 리더도 같은 행에 막혀 다시 강등한다. 강등은 차단기에 세어지므로 P2에서 두 노드가 10분에 3회씩 강등하면 둘 다 차단돼 리더가 없어진다(11절 R10).

예외가 하나 있다. 접수 락 대기 초과는 그 순간 락을 쥔 요청이 `accept-lock-wait`(2초)보다 오래 쥐고 있었으면 빼지 않는다. append의 잠금 대기는 `accept-lock-timeout`(1초)으로 끊기므로 정상 경합에서 보유 시간은 1초 남짓을 넘지 않는다. 그보다 한참 긴 보유는 DB 잠금이 아니라 끝나지 않는 보유자(응답 없는 연결, 앱 결함)다. 이때 대기 초과를 빼면 대기자가 모두 `429`로 빠져나가 수요가 쌓이지 않고, 대기가 무기한이던 S3에서는 수요로 쌓여 잡히던 좀비를 놓친다. `EngineBridge`는 마켓 접수 락마다 보유 시작 시각을 들고 있다가 대기 초과 때 보유 시간을 보고 예외에 표시한다. 계수기는 이 경우를 `cause="lock_wait_stuck"`으로 따로 센다.

제외는 두 층의 계측 단위에 맞춘다. 노드 층 수요는 인증 필터가 요청마다 한 번 세므로 제외도 요청 단위다. 게이트웨이가 경합으로 만든 API 예외에 표식을 달고, 예외 처리기가 응답을 쓰면서 그 표식을 요청 속성으로 옮긴다. 인증 필터는 체인이 끝난 뒤 그 속성이 있고 응답 코드가 `429`나 `409`이면 그 요청의 수요 하나를 되돌린다(`LeaderWriteProgress.recordExcluded`). 배치 주문과 일괄 취소는 응답이 `200`이라 되돌리지 않는다. 파티션 층은 submit마다 세므로 submit이 경합으로 끝날 때 그 파티션의 제외를 센다. 판정기는 수요에서 제외를 빼고, 표본 경계에서 새 수요가 음수가 되지 않게 0으로 자른다. 수용 거절(`AdmissionFilter`)은 종전처럼 두 층 모두 수요로 세지 않는다(DB 설계 §5.4 v2.20).

P3에서 노드 층 수요에는 이 노드가 쥐지 않은 파티션 마켓의 주문도 섞인다. S5가 인증 전에 소유권을 검사해 오배송 요청을 수요 전에 돌려보내기 전까지는(단계 계획 S5) 이 노드의 완료율이 낮게 보일 수 있다. S4는 P2에서만 운영하므로 해당하지 않고, 9절에 S5 선행 조건으로 적었다.

`PartitionStallDetectionTest`와 `ContentionStallExclusionTest`(6-2)가 두 층과 제외 규칙을 고정한다.

| 취소 경합(접수 락 대기 초과, append의 네 오류) | 같음 | `429`(bucket market) |
| 리더 아님, 승격 중, 라이터 정지 | `503` | `503` 그대로 |
| 주문 생성·취소 밖 경로의 55P03(컨트롤러·인증 필터) | `500` | `500` 그대로. S5에서 인그레스와 함께 다시 본다 |
| `ApiExceptionHandler`의 접수 락 초과 처리기(게이트웨이만 `EngineBridge.submit`을 불러 닿지 않는 방어용) | `503` | `429` |

`429`는 '이 요청이 접수되지 않았음이 확정됐다'는 뜻이다(API 설계 §2-3의 429 클라이언트 규약). 주문 생성에서 그것을 말할 수 있는 경우는 DISCARDED 하나다. V47은 같은 키의 append와 같은 어드바이저리 락 아래에서 이 요청의 NEW가 저널에 없음을 확인하고, 같은 키를 대조한 다른 요청의 공유 표시가 없을 때만 키를 지운다. 같은 키로 새 NEW를 커밋할 수 있는 요청은 키를 넣은 요청(이 요청)과 append 전에 공유 표시를 채운 요청뿐이다. 그래서 공유 표시가 없으면 그 순간 이 키로 커밋됐거나 커밋 중인 주문이 없다. 앞선 주문이 저널에 있으면 그 키 행이 남아 있어 이 요청이 키를 넣지 못했을 것이다(해시 보존 기한 삭제가 배선되기 전의 성질, API 설계 §2-4). 키를 지운 뒤에 도착한 같은 키 요청(클라이언트가 먼저 보냈으나 늦게 닿은 요청 포함)은 키를 새로 넣어 자기 접수를 하고 자기 응답을 받는다. 그래서 `429`는 앞서 결과를 모르게 된 같은 키 요청까지 미접수로 확정하지 않는다. 그 요청의 상태는 §7-6 재조회 규약을 따르고, 같은 키로 다시 보내면 어느 쪽이든 멱등으로 수렴한다. 이 한계는 API 설계 §2-5-b에 적었다.

그 밖의 경합은 같은 키의 다른 요청이 관여했거나(KEPT, 공유 표시를 채운 요청의 NOT_JOURNALED), 키가 사라졌거나(ABSENT), 판정을 못 했거나(V47 실패), 주문이 이미 접수돼 있다(재생). 어느 것도 확정 미접수가 아니다. 이 경우는 `409 order_in_progress`로 낸다. 주문 생성 경로에서 이 코드는 이미 '같은 키의 요청이 처리 중이니 `Retry-After` 뒤 같은 키로 다시 보내거나 재조회하라'는 비종결 응답이다(API 설계 §2-4). 접수됐다고도 안 됐다고도 말하지 않으므로 종전 `503`의 재조회 규약과 같은 안전 쪽이고, `proxy_next_upstream`에 없는 코드라 인그레스가 리더를 빼지 않는다. 설계 첫 판은 V47이 이 요청의 명령이 저널에 없다고 답하면 모두 `429`로 냈다. 같은 키의 다른 요청이 커밋했거나 커밋 중인데도 '확정 미접수'를 말하는 결함이라 고쳤다(11절 R1). 판정 실패와 재생을 `503`으로 두던 것도 리더를 빼는 경로라 `409`로 바꿨다(11절 R6).

취소는 네 오류가 모두 커밋 전에 롤백되고 대기 초과는 저널 전에 끝나므로 이 취소 명령이 저널에 없다는 것이 확정이다. 취소의 `429`는 그것만 뜻한다. 그 사이 다른 취소나 체결로 주문이 바뀌었을 수 있으므로, 같은 취소를 다시 보내 현재 상태를 받는다(이미 종결된 주문의 재취소는 `200` + 현재 상태, API 설계 §4-B-2).

`OrderGateway.submitFailure`는 예외와 함께 접수 결과 `IntakeOutcome`(재생, 판정 실패, DISCARDED, KEPT, ABSENT, 공유 표시 요청의 NOT_JOURNALED)을 받는다. 경합 예외이면 DISCARDED만 `429`이고 나머지는 `409`다. 경합이 아닌 예외의 응답(라이터 정지 `503`, 정지 마켓 `422`, P2 23514 `400`, 그 밖 원래 예외)은 결과와 무관하게 S3와 같다. `countTransient`는 네 상태를 모두 센다. 새 계수기 `exchange.order.intake.contention{cause,response}`가 경합 응답을 센다. `cause`는 `lock_wait`·`lock_wait_stuck`·`55P03`·`57014`·`40P01`·`40001`, `response`는 `429`·`409`다.

배치 주문은 `429`면 `in_progress`(`error.name=too_many_requests`, `retry_after=1`), `409`면 `in_progress`(`error.name=order_in_progress`)로 적는다. `ApiException`에 `Retry-After`가 있으면 `in_progress`로 적는 지금 규칙(`OrderController.java:146-150`) 그대로다. 일괄 취소는 `failed[].reason=too_many_requests`로 적고, `BulkCancelResult`는 `503`과 `429`(bucket market)를 미완료로 센다. 회원 폐쇄의 `pending_reasons`에 `too_many_requests`가 들어간다(API 설계 §6-E).

`ApiExceptionHandler`에 55P03 처리기를 더하지 않는다. 비접수 경로의 55P03은 S3처럼 마지막 처리기의 `500`이다. v2.54 계약은 55P03을 `503`으로 매핑한다고 적었지만, 그 적용 조건이 인그레스 조정이었고 S4는 인그레스를 바꾸지 않는다. 이 매핑만 켜면 prod-timeouts 요청 풀의 `lock_timeout`(2초)에 걸린 출금 같은 비접수 쓰기 한 건이 리더를 빼 약 1~3.5초 동안 모든 쓰기를 `502`로 만든다(3절 N-C1). 설계 첫 판은 이것을 'S4 이전부터 있던 위험'으로 적었으나, 55P03은 지금 `500`이라 리더를 빼지 않으므로 S4가 새로 만드는 위험이었다(11절 R7). `ApiAuthFilter`의 응답 매핑도 바꾸지 않는다. 인증 필터는 4-11의 수요 되돌리기만 더한다. 접수 락 초과 처리기는 `429`로 바꾼다.

값은 `accept-lock-wait` 2000ms, `accept-lock-timeout` 1000ms이고 `application.yml`의 dev·prod 문서에 넣는다. 코드 기본값 0은 그대로 두어 시험과 다른 배선은 켜지 않는다. append `lock_timeout` 1초는 사용자 잔고 행을 쥔 정산(보통 수 밀리초, 부하에서 수십 밀리초)보다 충분히 길다. 대신 마켓 접수 락이 append 동안 유지되므로, 멈춘 트랜잭션이 잔고 행을 쥔 경우(E7 pause, 운영자 세션)에는 그 행을 기다리는 주문 하나가 그 마켓의 접수 전체를 최대 1초 막는다. 그런 주문이 둘 이상 줄을 서면 뒤에 선 다른 사용자의 주문도 접수 락 대기 2초를 넘겨 `429`(`lock_wait`)를 받는다. 곧 한 사용자의 잔고 행 잠금이 그 마켓의 접수를 건당 최대 1초씩 직렬로 막는다. 설계 첫 판은 '그 사용자의 주문만 1초 안에 돌려보낸다'고 적었으나 틀렸다(11절 R3). DB 지연이 문장마다 수백 밀리초 붙는 경우(E1)에도 정산이 잔고 행을 1초 넘게 쥘 수 있어 같은 사용자의 접수가 `429`로 끝날 수 있다. 두 값은 이 증폭과 정상 경합 사이에서 고른 값이고, X6b가 증폭 크기를, X8 E1이 지연 아래의 경합 수를 잰다(사용자 확인 6).

### 4-13. 인그레스는 바꾸지 않는다

3절 N의 결과대로 `harness/nginx/nginx.conf`와 `deploy/nginx-edge.conf.template`의 쓰기 업스트림은 그대로 둔다. 이 판단의 전제는 S4가 리더의 `503`을 새로 만들지 않는다는 것이다. 접수 경합은 `429`나 `409`로 끝나고(4-12), 비접수 경로의 55P03은 `500` 그대로다. 리더가 `503`을 내는 것은 S3와 같이 둘이다. 하나는 페일오버 창(리더 아님·승격 중·라이터 정지, 기간이 바뀐 append)이고 원래 노드를 빼야 하는 신호다. 다른 하나는 S4 이전부터 `503`이던 DB 접근 실패다. 연결 획득 초과, 트랜잭션 시작 실패, 그리고 접수 append 밖(게이트웨이의 키·상태 조회, 비접수 경로)에서 난 57014·40P01·40001이다. 뒤의 것이 한 건으로 리더를 빼는 연쇄 위험은 S4 이전부터 있었고 S4가 늘리지 않는다(9절). X1과 X6이 LB의 `no live upstreams`와 `502`가 0인지 본다(7-2).

`max_fails=0`이나 `proxy_next_upstream`에서 `http_503`을 빼는 안은 쓰지 않는다. 앞의 것은 죽은 리더를 빼지 못하고, 뒤의 것은 팔로워의 `503`을 클라이언트에 그대로 돌려 페일오버 동안 모든 쓰기가 실패한다. S5가 파티션별 업스트림을 만들 때(단계 계획 S5) 이 판단과 비접수 55P03의 매핑을 다시 본다.

### 4-14. 선호와 유예, 운영자 조작

설정은 `exchange.leader.partition.preferred`(자원 목록, 기본 빈 목록)와 `exchange.leader.partition.participate`(자원 목록, 기본 계획 전체)다. P3에서만 뜻이 있고 P1·P2의 `matching-engine`에는 선호와 유예가 없다(DB 설계 §5.4-c 9).

비선호 파티션의 유예는 틱이 판정한다. 기동 시각에서 2×TTL이 지나기 전에는 획득하지 않는다. 그 뒤에는 틱 스레드가 그 파티션의 리스 행을 읽어(리스 풀) 만료를 처음 본 시각에서 1×TTL이 지난 뒤에만 획득을 시도한다. 만료를 본 시각은 보관소 시계로 잰다. 선호 노드가 살아 있으면 그 사이에 획득하고, 비선호 노드는 다음 만료까지 기다린다. 자동으로 되돌려 주지 않는다(결정 4).

운영자 조작은 actuator 엔드포인트 `partitions`다(API 설계 §6-C). `GET`은 파티션별 상태·epoch·참여·선호·강등 사유 이력·차단기 계수·마켓 목록을 낸다. `POST {"resource","participate"}`는 참여를 켜고 끈다. 끄면 `PLANNED` 강등이고, 리스는 반납하지 않고 만료시킨다(결정 2). `POST {"resource","reset_breaker":true}`는 차단기를 푼다. `DEMOTED`(노드 치명)는 풀지 않는다. 전환마다 WARN 한 줄(요청 원격 주소, 전후 값)을 남긴다.

`POST`는 요청의 원격 주소가 loopback(127.0.0.0/8, ::1)일 때만 받고 나머지는 `403`이다. 앱이 막는 이유는 배치마다 actuator 위치가 달라서다. prod는 8081 관리 포트라 SG가 막지만, 카오스 스택의 dev 프로파일은 actuator가 8080에 있고 하네스 nginx의 `location /`와 호스트 포트 18080·28080으로도 닿는다(2-7). 인그레스에 `location /actuator/`를 막는 규칙을 두는 안은 쓰지 않았다. 인그레스를 바꾸지 않는다는 결정과 부딪치고, 호스트 포트로 직접 오는 요청은 막지 못한다. 원격 주소는 신뢰 프록시 규칙을 거친 값(`getRemoteAddr()`)이다. dev의 신뢰 프록시는 loopback뿐이라 LB가 붙인 전달 헤더는 믿지 않는다. 하네스는 `docker exec <노드> curl -X POST http://localhost:8080/actuator/partitions`로 부른다. `GET`은 읽기라 막지 않는다. 기존 `admission` 쓰기 연산도 같은 노출이지만 S4 범위 밖이라 9절에 적었다.

노출 목록에 `partitions`를 더한다. dev·prod·bots 문서와 함께, dev 뒤에서 목록을 다시 정의하는 `chaos-monkey` 문서(`application.yml:352-367`)에도 넣어야 카오스 스택에서 보인다.

`PartitionAcquirePolicyTest`와 `PreferredAcquisitionIntegrationTest`(6-2)가 유예와 인계를, `PartitionsEndpointTest`(6-4)가 조작과 loopback 제한을 고정한다.

### 4-15. epoch, readiness, 불변식 스캔

`EpochSource.epoch(marketId)`는 그 마켓 파티션의 epoch다. 이 노드가 그 파티션을 쥐면 기간의 epoch이고, 아니면 그 자원의 리스 행을 요청 풀로 읽는다(지금과 같은 풀). 인자 없는 `epoch()`는 계획의 첫 자원 값이다. P1·P2에서는 둘 다 종전과 같다. 마켓을 아는 호출자(`MarketController.java:75`, :135, `OrderController.java:230`, :243, :313, `OrderbookSnapshotOnSubscribe.java:68`)는 마켓 인자판을 쓴다. `OrderGateway.currentEpoch`(:739-744)도 그 마켓 파티션을 읽는다. WebSocket 발행(`MarketDataPublisher.java:102`)의 마켓별 epoch는 S6에서 정한다(API 설계 §5-2).

readiness는 파티션 가운데 하나라도 `ACCEPTING`이면 ACCEPTING이다(DB 설계 §5.4-c 14). `HaAvailability`의 목표치를 파티션 상태의 집계로 바꾸고, 발행 정정 규칙(v2.27)은 그대로다.

불변식 상시 스캔은 계획의 첫 파티션을 쥔 노드에서만 돈다. P1·P2에서는 종전과 같다.

### 4-16. 지표와 경보

리더 축 지표는 모두 `partition` 태그를 단다(하네스 CI/CD §5-2). `HaAvailability`의 게이지 셋, `MeteredLeaderLeaseStore`의 획득·갱신 계수기(`outcome` 태그는 그대로)와 게이지 둘, 회복 가능 반납·자발적 강등 계수기, 팔로워 지표다. 새 지표는 여덟이다(같은 절). 파티션 상태 게이지 값은 0 `FOLLOWER`, 1 `PROMOTING`, 2 `ACCEPTING`, 3 `REBUILDING`, 4 `BLOCKED`, 5 `DEMOTED`다. 경보는 셋을 더한다. `PartitionBreakerOpen`(critical, 노드마다 보려고 `instance`와 `partition`으로 묶는다), `PartitionLeaderAbsent`(critical), `PartitionRebuildFailing`(warning)이다(§5-6). 규칙 파일(`harness/prometheus/rules/exchange-alerts.yml`)에 넣고, 규칙 시험(`harness/prometheus/tests/exchange-alerts.test.yml`)에 세 경보의 발화·미발화 사례를 더한다(6-4). 학교 배포 규칙(`deploy/linux/reporting/school-alerts.yml`)에는 넣지 않는다. 학교는 P1로 두고 S4 이미지를 올리지 않기 때문이다(결정한 값 19).

태그를 더하면 같은 이름의 태그 없는 시계열이 사라진다. `max(...)`와 `absent(...)`로 읽는 기존 규칙과 대시보드는 P2에서 결과가 같다. 하네스 스크립트의 지표 정규식(`Get-AppMetric`, E1의 `outcome` 정규식)은 태그가 늘어도 첫 매치를 읽으므로 P2에서 같은 값을 읽는다. S3 공통 판정의 로그 문구 축(2-7)은 S4 코드가 강등·승격 문구를 바꾸면 공허하게 통과하므로, 코드와 같은 변경에서 `s3_common_axes.py`의 문구를 고치고 E5·E7의 옛 리더 로그에서 강등 문구가 1 이상 잡히는지를 양성 대조로 둔다(7-2). 코드가 들어갈 때 규칙·대시보드·스크립트의 참조를 grep으로 다시 대조한다.

### 4-17. 관리 API와 웹 관리 화면

`/admin/v1/ha/status`에 `leader_protocol`과 `leases[]{resource, holder, epoch, lease_until, leader_alive, lease_remaining_ms, markets[]}`를 더한다(API 설계 §6-C). `leases[]`는 모드가 쓰는 자원만 담는다. 기존 `lease`는 첫 행과 같다. `/admin/v1/ha/recovery`의 `failover_runs[]`에 `resource`를 더한다.

웹은 `web/lib/admin/types.ts`의 `HaStatus`에 `leases?: HaLease[]`를 더하고, `httpAdmin.ts`의 `WireHaStatus`와 `getHaStatus`(:461-466, :949-972)가 이를 옮긴다. `leases`가 없는 옛 응답이면 `lease`로 한 행을 만든다. `simAdmin.ts`의 `getHaStatus`(:841-846)는 `matching-engine` 한 행을 낸다. 드릴 화면(`web/app/admin/(ops)/drill/page.tsx`)의 리더 단계 근거에 리스 표(자원, 보유 노드, epoch, 남은 시간, 마켓 수)를 더한다. 단계 판정(`web/lib/admin/drills.ts:321-415`)은 `ha.epoch`를 그대로 쓰므로 P2에서 바뀌지 않는다. 디자인 토큰과 레이아웃 계약을 따르고, 새 색·간격을 만들지 않는다.

### 4-18. V53과 하네스

V53은 DB 설계 §3.8의 SQL 그대로다(`server/app/src/main/resources/db/migration/V53__failover_runs_resource.sql`). `FailoverRecorder`가 `resource`를 적재하고, `HarnessController`의 `FailoverRequest`가 `resource`를 받는다. 없으면 P1·P2에서는 `matching-engine`이고 P3에서는 400이다. `GET /harness/v1/status`는 `?resource=`를 받고 `leases[]`를 더한다. 인자가 없으면 P1·P2에서는 종전 모양이고 P3에서는 400이다.

하네스 스크립트는 이렇게 바꾼다(하네스 검증설계 S4 패치 노트).

- `lib.ps1`에 `Get-LeaseResource`를 둔다. `leader_protocol`이 1·2면 `matching-engine`을 돌려주고, 3이면 `-Resource` 인자를 요구한다.
- `Get-LeaderContainer`와 `Get-FirstTradeSql`이 `-Resource`를 받는다. `Get-FirstTradeSql`은 자원이 `matching-engine`이 아니면 파티션 마켓 한정을 붙이고, `matching-engine`이면 문장이 종전과 바이트 단위로 같다(하네스 검증설계 §5-1).
- `Record-Failover`가 바디에 `resource`를 싣는다.
- 2-7의 직접 참조를 모두 `Get-LeaseResource`로 바꾼다. `e1-pg-latency.ps1:99`는 함수 본문 검사라 두고, `protocol_latch.py`의 퇴역 순서 검사(:340)도 세 행 모두를 보는 검사라 둔다. 바꾼 E1·E3 스크립트는 X8에서 한 번씩 실행한다.
- 파티션 관측 축 `harness/scale/s4_partition_axes.py`를 새로 둔다. 실험 창 전후로 노드별 `/actuator/partitions`, `exchange_partition_*`, `exchange_leader_lease_acquire_lock_timeouts_total`, `exchange_order_intake_contention_total`을 모아 JSON으로 남기고, 프로메테우스에서 장애 창 밖과 안의 접수 경합 증가를 나눠 읽으며, LB 로그(`docker logs chaos-lb`)에서 창 안팎의 `no live upstreams`와 `502` 줄 수를 센다.
- `adr0022-stage5-chaos.ps1`에 `-PartitionAxes` 스위치를 더해 실험마다 위 축을 모은다. E4이면 판정 뒤 옛 리더를 `docker start`로 되살려 합류를 본다(7-2 X2). 켜지 않으면 종전과 같다.
- 접수 경합 실험 스크립트 `harness/scripts/s4-intake-contention.ps1`을 새로 둔다(7-2 X6, 변형 a~d).
- k6 `harness/load/order_flow.js`는 `429` 바디의 `detail.bucket`이 `market`이면 비율 지표 `market_contention`과 계수 `market_contention_total`에 더하고, 정상 구간 임계 `market_contention{phase:steady}: rate<0.001`을 둔다(하네스 검증설계 §2-2). 창 안의 값은 기록만 한다.

### 4-19. 수수료 샤드

`SettlementService`의 `FEE_SHARD` 상수를 함수 `feeShard(marketId)`로 바꾼다. 계획이 P3이면 그 마켓 파티션의 번호, 아니면 0이다(DB 설계 §1.2, §5.4-c 11). 계정 캐시는 (자산, 샤드)로 키를 잡는다. 정산 잠금 계획은 그 배치 마켓의 샤드 계정을 넣는다. 샤드 1 계정은 S4가 만들지 않는다. S7 전환의 선행 조건이고 만드는 방법(새 마이그레이션이나 시드 단계)은 S7에서 정한다. P3 흉내 시험(`FeeShardFunctionTest`)은 픽스처가 계정을 만든다.

### 4-20. DynamoDB 공급자와 최고 모드

`LeaseStoreConfig`가 DynamoDB 공급자를 만들 때 모드 3을 거부하는 검사(:101-117)에 설정 검사를 더한다. `participate`나 `preferred`에 `matching-p0`·`matching-p1`이 있으면 기동을 멈춘다(DB 설계 §5.4-c 12). DynamoDB 보관소는 `matching-engine` 하나만 다룬다.

`LeaseResources.MAX_PROTOCOL`은 2 그대로다. 보관소 생성자가 최고 모드를 인자로 받게 하되 운영 배선은 이 상수를 넘긴다. P3 흉내 시험만 3을 넘긴다.

## 5. 안전 논증

S4는 DB의 판정 함수와 원장 함수를 바꾸지 않는다. V53은 하네스 측정 표에 열 하나를 더할 뿐이다. 그래서 아래 네 성질을 지키는 DB 쪽 장치(명령 저널 append의 KEY SHARE 판정, 정산 머리말 판정, 원장 게시의 합 0 검사, 잔고 CHECK, 멱등 제약)는 그대로다. 논증은 앱 쪽 변경이 그 장치를 우회하거나 약화하지 않는다는 것이다.

자산 보존. 원장 게시는 여전히 `post_ledger_transaction`만 하고, 자산별 합 0은 DB가 강제한다. 수수료 샤드 함수는 P1·P2에서 종전과 같은 샤드 0을 낸다. P3에서는 샤드 번호만 바뀌고 FEE_INCOME 계정끼리의 분배라 자산 합에 들어가는 항이 같다. 부분 설치(4-9)는 다른 파티션 샤드를 건드리지 않으므로, 종전 `installFrom`이 P3에서 만들었을 '다른 파티션 북 소거'(주문은 원장에 LOCKED로 남았는데 북에서 사라짐)가 없어진다. 재구성은 저널과 스냅샷에서 다시 만들 뿐 원장을 쓰지 않는다.

주문 멱등. 멱등 판정(어드바이저리 락, `client_order_id` 저널 조회, V47 판정)은 게이트웨이와 DB에 있고 S4는 바꾸지 않는다. 새 `429`는 두 경우에만 낸다. 주문 생성은 이 요청이 키를 새로 넣었고, V47이 같은 키의 append와 같은 어드바이저리 락 아래에서 이 요청의 명령이 저널에 없고 같은 키를 대조한 다른 요청도 없음을 확인해 키를 지운 경우(DISCARDED)다. 그 순간 이 키로 커밋됐거나 커밋 중인 주문이 없다. 취소는 네 오류가 모두 커밋 전 롤백이고 대기 초과는 저널 전이라 이 취소 명령이 저널에 없는 경우다. 같은 키의 다른 요청이 관여했거나 판정이 실패했거나 재생 요청이면 `409 order_in_progress`로 같은 키 재전송·재조회 규약에 남는다. 그래서 `429`가 이 키로 이미 접수됐거나 접수 중인 주문을 미접수라고 말하지 않고, `429` 뒤 같은 키로 다시 보내도 이중 접수가 없다. 키를 지운 뒤에 도착한 같은 키 요청은 자기 접수를 하고 자기 응답을 받으며, 키 단위의 유일성은 어드바이저리 락과 저널 조회가 계속 지킨다.

리더 권한 확인. 모든 엔진 기원 쓰기는 종전처럼 DB에서 기록할 행의 마켓으로 리스를 도출해 holder·epoch·만료를 판정받는다. 기간 결속(4-5)은 판정에 넘기는 epoch를 리스 서비스의 현재 값이 아니라 획득 때 만든 기간의 값으로 고정하고, 승격 재생과 라이브 루프가 같은 기간을 쓴다. 이것은 확인을 좁히는 쪽이다. 새 epoch로 통과할 수 있던 옛 스레드의 쓰기가 옛 epoch로 거부된다. 게이트는 파티션마다 기간이 유효하고 그 파티션 라이터가 모두 돌 때만 열리고, 종전 개방 조건을 파티션에 그대로 옮겼다.

오래된 리더의 쓰기 차단. 승격 규칙(만료 뒤에만, 옛 epoch의 쓰기가 끝난 뒤에만 새 epoch)은 DB가 강제하고 S4가 바꾸지 않는다. 획득 `lock_timeout`은 기다림을 끊을 뿐이다. 끊긴 획득은 트랜잭션째 롤백돼 리스 행과 이력에 아무것도 남기지 않고(3절 G2), 성공한 획득은 여전히 옛 KEY SHARE가 풀린 뒤다. 상한은 획득 트랜잭션에만 걸리므로 갱신·반납·재확인은 S3와 같다. 강등은 DB에 쓰지 않고 갱신만 멈추므로 다음 리더는 만료 구동으로만 정해진다. 재구성 뒤 같은 노드의 재승격은 새 epoch를 받으므로 옛 epoch의 쓰기는 DB가 계속 거부한다. 같은 holder의 옛 스레드가 새 epoch를 빌리는 길은 기간 결속이 닫는다. 파티션 사이에서는 각 리스 행의 KEY SHARE가 따로 걸리므로 한 파티션의 승격이 다른 파티션의 쓰기를 기다리지 않고(V41 인덱스가 resource를 포함한다), 한 파티션의 오래된 리더는 그 파티션 행에서 거부된다. 좀비 판정의 수요에서 경합을 빼는 것(4-11)은 강등 시점을 정하는 가용성 규칙이고, 강등하지 않은 노드의 쓰기도 여전히 이 DB 판정을 받는다.

금액 계산. S4는 금액 계산을 바꾸지 않는다. 새 코드에 금액 연산이 없고, 수수료 샤드 함수는 정수 샤드 번호만 고른다.

## 6. 시험

### 6-1. 원칙

새 시험은 먼저 실패하는 모양으로 쓴다. 가능한 곳마다 대조군(종전 배선이나 규칙을 뺀 배선)을 같은 시험에 두고, 대조군이 실제로 결함을 드러내는지도 단언한다. 대조군은 되도록 S3의 실제 배선으로 둔다. DB가 필요한 시험은 Testcontainers의 일회용 `postgres:17-alpine`에서 돈다. P3를 흉내 내는 시험은 소유자 연결로 `leader_protocol`을 3으로 두고 보관소에 최고 모드 3을 주입한다(3절 G1과 같은 방법). 흉내는 시험 안에서만 한다.

### 6-2. 관문 시험

단계 계획 S4 절의 관문과, 검토 대응으로 더한 안전 시험 셋(`TermBoundWriteTest`, `SameKeyContentionIntegrationTest`, `ContentionStallExclusionTest`)이다.

기존 관문 넷(`CrashWindowReinjectionOrderTest`, `PromotionRecoveryIntegrationTest`, `FollowerRejoinIntegrationTest`, `BandModeFailoverIntegrationTest`)은 통과해야 한다. 앞의 셋은 `EngineRecovery.recover(engine)`, 단일 리스 생성자, 공유 엔진 `FollowerCatchUp` 생성자를 쓴다. 이 셋을 '모든 마켓 한 파티션'으로 해석하는 호환 생성자를 남겨 시험을 고치지 않고 통과시키는 것이 목표다. `PromotionRecoveryIntegrationTest:336`의 단언은 6-3의 표대로 뜻이 바뀐다. `BandModeFailoverIntegrationTest`는 코디네이터의 옛 API(:237-242)를 쓰므로 파티션 코디네이터의 호환 API가 필요하다.

### 6-3. 고칠 기존 시험

종신 강등 뒤 재승격 금지를 단언하는 기존 시험은 강등 원인에 따라 S4에서 뜻이 달라진다. 파티션 치명은 재구성 뒤 후보로 돌아오고, 노드 치명은 종신 그대로이며, 재기동 흉내는 동작이 같다. 리스 서비스만 쓰는 시험은 `PartitionRuntime`이 없어 `rearm()`이 불리지 않으므로 `disarm()` 때문에 단언이 그대로 통과한다. 그러나 단언의 뜻은 '재기동 전 재승격 금지'에서 '재구성(rearm) 전 재획득 없음'으로 바뀐다. 이런 시험은 메시지를 고치고, `rearm()`과 리스 만료 뒤에는 새 epoch로 다시 얻는다는 양성 단언을 붙여 새 계약을 시험하게 한다.

| 시험:줄 | 강등 원인과 S4 분류 | 바꾸는 방법 |
|---|---|---|
| `EngineRuntimeIntegrationTest:332` | sink `IllegalStateException`, `WRITER_FATAL` | 메시지를 '재구성 전 재획득 없음'으로 고치고, `rearm()`과 만료 뒤 `tryAcquire()` 참, epoch 증가, 옛 appender 쓰기 거부를 더한다 |
| `LeaderLeaseIntegrationTest:151` | 접수 중 갱신 거부, `LEASE_LOST_WHILE_ACCEPTING` | 위와 같다. 새 인스턴스 승격 단언(:155-158)은 그대로 둔다 |
| `LeaderStanddownIntegrationTest:143`, :326 | 자발적 강등, `STALL`(:326은 fencing 재확인 경로) | 위와 같다. 강등 계수·게이지 단언은 그대로 둔다 |
| `LeaderStanddownIntegrationTest:373` | 재생 표식 해제 뒤의 상실, 파티션 치명 | 위와 같다. 회복 가능 반납 뒤 재승격 단언(:367)은 그대로 둔다 |
| `PromotionRecoveryIntegrationTest:336` | sink `AssertionError`(VM 오류 아님), `WRITER_FATAL` | 위와 같다. 같은 시험 파일에 `StackOverflowError`를 주입하는 사례를 더해 `NODE_FATAL`은 `rearm()` 뒤에도 재획득하지 않음을 단언한다 |
| `PromotionStandDownIntegrationTest:163` | 옛 리더의 `LoopFatalHandler`, `WRITER_FATAL` | 구 리더 모델의 뜻을 '재구성 전 후보가 아닌 노드'로 고친다. 스탠바이 쪽 단언은 그대로다 |
| `PromotionStandDownIntegrationTest:336`, :349 | `VirtualMachineError`, `NODE_FATAL` | 그대로 둔다. 코디네이터 상태 `DEMOTED`와 재승격 금지가 S4에서도 계약이다 |
| `PromotionStandDownIntegrationTest:398-415` | 승격 전 라이터 정지, `PROMOTION_LOOP_DOWN` | S4는 루프를 설치 때 기간마다 새로 만들므로 '미리 멈춘 루프' 장면이 성립하지 않는다. 새로 설치한 루프가 게이트 개방 전에 죽도록 주입하고, 게이트가 열리지 않음, `PROMOTION_LOOP_DOWN` 1회, `REBUILDING`을 거쳐 `FOLLOWER`, 같은 주입 세 번이면 `BLOCKED`, 주입이 없으면 재구성 뒤 새 epoch로 승격함을 단언한다 |
| `FollowerReadinessIntegrationTest:112` | 상실 콜백, 파티션 치명 | readiness 단언은 그대로 두고 상태 단언을 `REBUILDING` 또는 그 뒤 `FOLLOWER`로 바꾼다 |
| `CommandJournalIntegrationTest:240`, `InvariantVerifierIntegrationTest:177` | 재기동을 흉내 내려고 새 인스턴스를 쓴다 | 동작은 그대로이고 주석만 고친다 |

그 밖에 고칠 시험이다.

- `BootPromotionRetryIntegrationTest`: 부팅 획득 전제다. `BootAsFollowerIntegrationTest`로 바꿔, 옛 리스가 남은 상태로 기동한 노드가 팔로워로 뜨고 만료 뒤 런타임 승격으로 크래시 창을 재적재하는지 본다.
- `ApiExceptionHandlerTest`: `appendLockTimeoutStaysServerErrorUntilIngressDecision`(:82-87)은 비접수 55P03의 `500`을 계속 단언한다. 이름과 주석을 'S5 인그레스 판단 전까지 `500`'으로 고친다. `acceptBusyIsRetryableServiceUnavailable`은 `429`(bucket market)로 고친다. 무결성 위반 `500` 대조는 그대로다.
- `OrderGatewayReserveMappingTest`(:116-134): 55P03을 세지 않는다는 단언을 센다로 바꾼다. 경합 예외마다 결과별 응답을 단언한다. 키를 넣은 요청의 DISCARDED는 `429`, KEPT·ABSENT·공유 표시 요청·V47 실패·재생은 `409 order_in_progress`이고 어느 것도 `503`이 아니다.
- `AcceptLockDefaultsTest`: 코드 기본값 0은 그대로, dev·prod 문서 값(2000ms·1000ms)을 단언한다.
- `MemberCloseIncompleteTest`: `429` 사유가 `pending_reasons.too_many_requests`로 세어지는지 더한다.
- `AcceptLockTimeoutIntegrationTest`: append 55P03 뒤 강등이 없다는 단언은 그대로이고, 응답 쪽 단언은 게이트웨이 시험이 맡는다.
- `EngineDisabledContextTest`: `PartitionPlan`·`PartitionLeases` 빈이 있고, `leader-lease-` 이름의 스레드가 없으며, 리스 행의 epoch·holder가 기동 전후로 같음을 더한다. `bots` 프로파일로도 한 번 띄운다.
- `ReadRoleIntegrationTest`: 조회 역할의 계획이 DB를 읽지 않고 `matching-engine` 하나인지, 리스 틱 스레드가 없는지 더한다.

## 7. 폐기용 스택 실험

### 7-0. 안전 수칙

S3 설계 7-0을 그대로 따른다. 실험 스택은 compose 프로젝트 `exchange-pml`, 앱 이미지 태그 `exchange-chaos-app:pml`로만 띄우고 `exchange-chaos-app:local`을 덮어쓰지 않는다. 보존 볼륨 `exchange-chaos_chaos-pgdata`와 백업 볼륨 `failstop-keep-*`는 어떤 명령으로도 마운트·삭제·수정하지 않는다. 프로젝트 `exchange-chaos`에는 `down -v`, `volume rm`, `up`을 하지 않는다. `down -v`는 `-p exchange-pml`이 붙은 명령으로만 한다. 비밀 파일(`harness/.env.chaos`, `harness/load/secrets/k6_keys.json`)은 경로로만 넘기고 열지 않는다.

S4에 더하는 수칙은 셋이다.

- 병행 작업이 같은 프로젝트 이름과 이미지 태그를 쓴다. 시작 전에 `docker ps -a --filter "name=chaos-" --format '{{.Names}} {{.Label "com.docker.compose.project"}}'`가 비어 있을 때만 시작하고, 아니면 BLOCKED로 적고 기다린다. 다른 작업의 컨테이너를 멈추거나 지우지 않는다.
- S4 이미지를 굽기 전에 지금 `:pml`이 가리키는 S3 이미지 id(`sha256:0ff1d3c1…`, `harness/evidence/pml-S3-20260924-1351/images.json`)를 적어 둔다. X7의 S3 칸은 `docker tag <그 id> exchange-chaos-app:pml`로 되돌려 돌리고, 칸이 끝나면 S4 id로 다시 붙인다. 태그를 잃은 이미지를 지우는 명령(`docker image prune`)은 쓰지 않는다.
- (2026-09-24 코드 단계 정정) 이 PC의 Docker는 containerd 이미지 저장소를 쓴다. 이 저장소에서는 이름을 모두 잃은 이미지가 남지 않아, S4 이미지를 `:pml`로 굽는 순간 S3 이미지 `sha256:0ff1d3c1…`가 사라졌다(지우는 명령은 쓰지 않았다). 그래서 X7의 S3 칸은 S3 커밋 `60be79e0`의 서버 코드(HEAD `91813dd5`와 서버 코드가 같다)를 저장소 밖 폴더에서 다시 빌드해 참조 태그 `exchange-chaos-app:s3ref`로 두고 돌린다. S4 이미지에도 참조 태그 `exchange-chaos-app:s4ref`를 붙여 `:pml`을 옮겨도 사라지지 않게 한다. 실험 스택은 여전히 `:pml`로만 띄운다. 다시 구운 S3 이미지가 S3 관문 재주행 이미지와 같은 코드인지는 jar가 남지 않아 확인하지 못했고, S3 관문 재주행은 커밋 전 작업 트리로 구웠다(12절).
- 모든 주행의 앞뒤에 `docker volume inspect exchange-chaos_chaos-pgdata failstop-keep-chaos-pgdata-20260924 --format '{{.Name}} {{.CreatedAt}}'`를 증거에 남기고 생성 시각이 같은지 본다.

### 7-2. 실험 목록과 판정

공통 판정은 S3 관문의 판정에 S4 축을 더한 것이다. S3 판정은 사후 권위 run(`POST http://localhost:18080/harness/v1/invariants/run?runId=<id>&window=post`)과 드레인 뒤 `summary.sql`의 CRITICAL·HIGH가 모두 PASS, 정산 23514 0, 정산 잠금 계획 누락 0, 리더가 낸 접수 `500` 0, 접수 40P01 증가 0, `pg_stat_database.deadlocks` 증가 0, 드레인 뒤 정산 전 예약 0이다. S4 축(`s4_partition_axes.py`)은 넷이다.

- 접수 경합 상한. 장애 창 밖(스택을 세운 뒤부터 주입 전까지, 그리고 스크립트가 끝난 시각 + 30초부터 판정 시작까지)의 `exchange_order_intake_contention_total` 증가 합이 같은 구간 `exchange_journal_append_seconds_count` 증가의 0.1% 이하다. X1은 주행 전체가 창 밖이다. 창 안의 값은 `cause`·`response`별로 기록한다. 경합이 `429`로 옮겨 k6·5xx 판정에서 빠지는 만큼을 이 상한이 대신 본다.
- 창 밖 `PartitionBreakerOpen`·`PartitionRebuildFailing` 발화 0, 실험 끝 리더 노드의 강등 계수 0. 강등 계수는 노드·사유별로 기록한다.
- S3 판정의 로그 문구 축은 S4 문구로 고친 판을 쓰고, E5·E7에서는 옛 리더 로그의 강등 문구가 1 이상인지를 양성 대조로 본다. 0이면 문구가 코드와 어긋난 것이라 그 실험은 FAIL이다.
- 파티션 상태(`/actuator/partitions`), 획득 `lock_timeout` 계수, LB 로그의 `no live upstreams`·`502` 줄 수를 실험 전후로 남긴다. LB 값은 X1·X6에서 판정하고 X2~X5에서는 기록한다.

epoch는 각 스크립트의 규칙대로 판정한다(2-10). E4만 정확히 +1이고, E2·E5·E6·E7은 단조 증가와 holder 교체다.

- X1 P2 봇 부하(앱 역할 로그인). S3 X1과 같은 절차로 런타임 로그인과 `override-app-login.yml`을 겹치고 전환 뒤 봇 300 OPS로 10분 돈다. 판정: 공통 판정, 리더 epoch 불변, 세 컨테이너 로그의 `permission denied`·`42501` 0줄, 스냅샷 3마켓 이상, 접수 경합 상한(기대값 0), LB의 `no live upstreams`와 `502` 0. S4 축: 두 노드의 `/actuator/partitions`에서 `matching-engine`이 한 노드만 `ACCEPTING`이고 다른 노드는 `FOLLOWER`이며 강등 계수는 0이다. 획득 `lock_timeout` 계수를 기록한다. 만료되지 않은 리스 행은 획득 조건에 맞지 않아 잠그지 않으므로 0이 기대값이다. 연결 표본(`pg_stat_activity` 로그인별 수)의 최댓값을 기록하고 S3 X1과 같은지 본다.
- X2 E4 리더 kill과 합류: `pwsh -NoProfile -File harness/scripts/adr0022-stage5-chaos.ps1 -Image exchange-chaos-app:pml -Experiments E4 -Protocol 2 -PartitionAxes -EvidenceDir "$ev\X2" -LocalLogDir "$env:TEMP\pml-s4-logs"`. 판정: RTO < 30초, epoch 정확히 +1, 옛 epoch 쓰기 증분 0(C22 두 팔), rpo_records 0, 공통 판정. `docker kill`은 재기동 정책을 건너뛰어 옛 리더가 스스로 돌아오지 않는다(2-10). 그래서 `-PartitionAxes`가 켜진 E4 뒤에 합류 단계를 둔다. E4 판정이 끝나고 새 리더가 유효한 동안 옛 리더를 `docker start`로 되살리고 180초 안에 합류를 기다린다. 합류 판정: 되살린 노드가 liveness와 팔로워 상태 1을 내고 `/actuator/partitions`에서 `FOLLOWER`다. 그 노드 로그에 승격 문구가 없다(부팅 획득 없음). `leader_lease`의 holder·epoch가 되살리기 전과 같다. 그 노드의 강등 계수가 0이다. 이것이 '기동은 늘 팔로워'의 스택 확인이다. 공통 판정은 합류 단계 뒤에 돈다.
- X3 E7 리더 pause: 같은 명령에 `-Experiments E7 -EvidenceDir "$ev\X3"`. 판정: 스크립트 규칙(epoch 단조 증가와 holder 교체, RTO < 30초, 옛 epoch 쓰기 0, rpo_records 0, 사후 CRITICAL 0)과 공통 판정. 더해서 재개된 옛 리더가 재기동 없이 `REBUILDING`을 거쳐 `FOLLOWER`로 돌아오고, 그 노드의 `exchange_partition_demotions_total`에서 `LEASE_LOST_WHILE_ACCEPTING`과 `WRITER_FATAL`의 합이 1이며 차단기는 닫혀 있다. 강등 전 루프의 늦은 실패는 기간이 달라 두 번째 강등을 만들지 않는다(4-5). 새 리더의 획득 `lock_timeout` 계수와 획득까지의 시간을 기록한다. 멈춘 리더가 잔고 행을 쥐었다면 그 사용자의 접수가 `429`로 끝났는지와 같은 마켓의 다른 사용자 `429`(`lock_wait`) 수를 창 안 값으로 기록한다(판정 아님).
- X4 E2 DB 절단, E5 분리, E6 부하 중 kill: 같은 명령에 `-Experiments E2,E5,E6 -EvidenceDir "$ev\X4"`. 판정: 각 스크립트 규칙(RTO < 30초, 옛 epoch 쓰기 증분 0, epoch 단조 증가, 불변식 0)과 공통 판정. E5는 격리된 옛 리더가 복귀 뒤 재구성에 성공해 `FOLLOWER`가 되고, 격리 동안의 재구성 실패가 `PartitionRebuildFailing`을 띄워도 창 안이면 판정에 넣지 않는다. E6은 k6 임계에 `market_contention{phase:steady}` 비율 상한(0.1%)이 더해진 판으로 돈다. (2026-09-24 코드 단계 정정) E6 스크립트(`e6-spike-failover.ps1`)는 봇 목표를 올려 스파이크를 만들고 k6를 부르지 않는다. X7의 `roundtrip_probe.py`도 `calibrate.js`를 쓴다. 그래서 `order_flow.js`의 `market_contention` 임계는 이 관문의 어느 실험에서도 돌지 않는다. 코드 단계는 `k6 inspect`로 스크립트가 해석되고 임계가 등록되는지만 확인했고, 실제 주행 확인은 `order_flow.js`를 쓰는 부하 주행으로 남긴다(12절).
- X5 콜드 재기동: 같은 명령에 `-Experiments COLD -EvidenceDir "$ev\X5"`. 스크립트는 두 노드를 멈춘 뒤 한 노드를 먼저 올리고, 새 epoch와 접수 재개를 본 다음 다른 노드를 올린다(2-10). 판정: 먼저 올린 노드가 기동 대조를 마치고 팔로워 상태 1(기동 완료)을 낸 뒤 런타임 승격으로 새 epoch 리더가 되고 접수가 재개된다. 그 노드 로그에서 팔로워 시작 문구가 승격 문구보다 먼저다(부팅 획득 없음). 나중 노드는 팔로워 상태 1로 합류하고 강등 계수가 0이다. 재개와 첫 체결이 스크립트 상한(재개 90초) 안이고 사후 권위 run CRITICAL 0이다. 기록: 기동부터 기동 완료, 첫 획득, 승격 재생, 접수 재개까지의 분해. S3 이미지 COLD 결과(있으면 S3 증거)와 나란히 적는다.
- X6 접수 경합(새 `harness/scripts/s4-intake-contention.ps1`). X1 스택에서 봇이 쓰지 않고 미체결 주문이 없는 부하 계정 L(잠글 계정)과 M(다른 계정)을 고른다. L의 주문은 모두 KRW를 예약하는 매수라 그 행을 기다린다. 네 변형 모두에서 LB의 `no live upstreams`와 `502` 0, 리더 강등 0, 정산 재시도 소진 0이 공통 판정이다.
  - X6a 기본(봇 20 OPS, 30회). 잠금 5초 동안 L과 M이 같은 마켓에 주문을 하나씩 넣고, 잠금이 풀린 뒤 L의 주문을 같은 키로 다시 보낸다. 판정: L의 주문은 `429`(`detail.bucket=market`)이고 저널에 그 키의 행이 없으며, 다시 보내면 `201`이고 그 키의 NEW 행이 하나다. M의 주문은 `201`이다(지연 최대 1.5초 이하). `exchange_order_intake_contention_total{cause="55P03",response="429"}`이 30 이상이다.

M의 주문은 `201`이나 `429`(`bucket=market`의 `lock_wait`, 또는 `bucket=node`의 노드 수용 거절)이고 5xx가 없다. 기록: M의 `429` 버킷별 수, 노드의 주문 수용 거절 증가, `201` 지연 최댓값. 사용자 확인 6의 값 판단 근거다. 첫 판은 M의 `429`를 `lock_wait`만으로 적었다. 2026-09-24 첫 주행에서 접수 락 뒤에 줄 선 요청(L의 셋, M, 봇 주문)이 노드의 주문 수용 한도(카오스 스택 12)를 채워 M의 주문 둘이 `429`(`bucket=node`)로 즉시 거절됐다. 수용 거절은 처리 전에 끝나는 확정 미접수이고(API 설계 §2-5-a) 인그레스가 리더를 빼지 않으므로 판정에 더하고, 다른 마켓 주문까지 거절되는 증폭은 9절에 적었다(12절).

(ii)의 R은 `409 order_in_progress`나 `200`(재생)이고 `503`이 아니며, 그 뒤 by-client 재조회가 R을 돌려준다.

- X7 처리량 기록(판정 아님). ## 9. 남은 위험

- 비접수 경로의 `503` 연쇄. 주문 생성·취소 밖 경로와 게이트웨이의 키·상태 조회에서 나는 DB 접근 실패(연결 획득 초과, 57014·40P01·40001)는 리더에서도 `503`이고, 쓰기 업스트림은 그 한 건으로 리더를 뺀다. S4 이전부터 있던 위험이고 S4는 늘리지 않는다(비접수 55P03은 `500` 그대로). X1·X6이 LB의 `no live upstreams`·`502`를 판정한다. 파티션별 업스트림(S5)에서 다시 본다.
- 비접수 55P03의 응답. `500`으로 두므로 그 경로의 클라이언트는 `Retry-After` 없는 서버 오류를 받는다. S1부터 같은 상태이고, 계약상 `503` 적용은 S5로 미뤘다.
- 접수 경합의 증폭. 한 사용자의 잔고 행이 오래 잠기면 그 마켓의 접수가 건당 최대 1초씩 직렬로 막히고 다른 사용자도 `429`를 받는다(4-12). 멈춘 트랜잭션은 `idle_in_transaction_session_timeout`(카오스 10초)이 끊지만 운영자 세션은 끊지 않는다. X6b가 크기를 잰다. 2026-09-24 X6b 첫 주행에서 증폭이 마켓 밖으로도 번지는 것을 봤다. 접수 락을 기다리는 요청은 최대 2초 동안 노드의 주문 수용 자리(카오스 스택 12)를 쥐므로, 줄이 길어지면 노드 수용 제어가 새 주문을 마켓과 무관하게 `429`(`bucket=node`)로 거절한다. 그 노드가 리더인 모든 마켓의 주문이 그 동안 거절될 수 있다. 확정 미접수라 자금과 멱등에는 영향이 없고 인그레스도 리더를 빼지 않지만, 가용성 손실은 한 마켓에 머물지 않는다. `accept-lock-wait`를 줄이면 줄이 짧아지고 정상 경합의 `429`가 는다. 사용자 확인 6의 판단 근거에 더한다(12절).
- 좀비 판정의 제외 규칙. 경합을 수요에서 빼면 경합만 내며 일을 못 하는 노드는 판정에서 사라진다. 그 경우의 원인은 DB 쪽이라 페일오버가 고치지 못한다고 봤다. 멈춘 보유자 예외가 JVM 안의 정체를 남긴다. 보유 시간 기준(2초)이 맞는지는 `ContentionStallExclusionTest`와 X6d가 처음 확인한다.
- 콜드 재기동의 이중 재생. 크래시 창이 있는 콜드 재기동은 기동 대조와 승격 재생을 모두 한다. 스냅샷이 재생을 상한하므로 수십 초 안이지만, X5에서 S3와 나란히 잰다.
- 차단기의 가용성 손실. 두 노드가 모두 차단하면 그 파티션은 운영자가 풀 때까지 리더가 없다. 값(10분에 3회)은 AI 선택이다.
- 리스 풀 2의 충분성. 획득 전용 풀을 두지 않는 판단은 틱 스레드 수가 풀 크기 안이라는 조건에 기댄다. 파티션을 셋 이상으로 늘리거나 리스 풀에 새 사용처를 더하면 다시 따져야 한다. `RenewUnderBlockedAcquireTest`가 처음 확인한다.
- actuator 쓰기 노출. `partitions`의 `POST`는 loopback만 받지만, 기존 `admission`·`chaosmonkey` 쓰기 연산은 카오스 스택에서 LB와 호스트 포트로 닿는다. 카오스 스택은 로컬 폐기용이라 S4 범위 밖으로 둔다. 운영(prod)은 8081 관리 포트와 SG가 막는다.
- 노드 층 좀비 판정과 오배송. P3에서는 이 노드가 쥐지 않은 파티션의 주문도 노드 층 수요로 세어진다. S5의 인증 전 소유권 검사가 P3 전환(S7)의 선행 조건이다.
- 병합 순서. P3에서 파티션 사이의 크래시 창 병합이 없어진다. 자금 쪽 근거는 접수 시점 예약이다. P2 이상에서만 성립하므로 P1 DB에서 P3로 가는 경로는 없어야 한다(S7 전환 함수가 P2에서만 3을 받는다).
- main 병합의 Flyway 순서. main의 `V47_1`(버전 47.1)은 이 브랜치의 V48~V53보다 낮은 번호다. 브랜치 이미지를 한 번이라도 적용한 DB에 main을 합친 이미지를 올리면 Flyway 기본 설정이 `Detected resolved migration not applied to database`로 검증을 멈춘다(S3 설계 3절 P7). 합칠 때 V47_1의 내용을 V54 같은 새 번호로 옮기는 식의 방법을 정해야 한다. 이미 적용된 파일은 고치지 않는다.
- 계약 선행의 한계. 이 문서의 계약은 코드 전에 적었으므로 구현 중에 틀린 곳이 드러날 수 있다. 그때는 계약을 먼저 고치고 버전 규칙대로 패치 노트를 남긴다.
- 확인하지 못한 것. 3절 확인은 PostgreSQL과 nginx 동작만 봤다. 파티션 코드의 경합(인계, 재구성 중 획득, 기간 결속, 같은 키 경합)은 6절 시험과 7절 실험이 처음 확인한다.

## 10. 사용자 확인이 필요한 것

모두 2026-09-24 이 설계를 맡은 AI가 정했다.

1. 접수 경합을 `503`으로 내지 않는다. 확정 미접수(키를 넣은 요청의 DISCARDED, 취소)는 `429`(`bucket=market`), 그 밖은 `409 order_in_progress`이고 인그레스를 바꾸지 않는다(4-12, 4-13). ADR 결정 8과 결정한 값 11, API v2.54의 예고를 바꾼다.
2. 비접수 경로의 55P03을 S4에서도 `500`으로 두고 `503` 매핑은 S5로 미룬다(4-12). 단계 계획 S4 범위의 '55P03 503 매핑'을 줄인다.
3. 파티션 치명 강등 뒤 fresh 재구성으로 같은 노드의 재승격을 허용하고, 획득 때 만든 기간으로 쓰기를 결속한다(4-5, 4-6).
4. 차단기 10분에 3회(4-7).
5. 획득 전용 풀을 두지 않고 기존 리스 풀(최대 2)에서 트랜잭션 한정 `lock_timeout` 1000ms로 획득한다(4-3). 단계 계획의 '갱신 전용·획득 전용 연결 분리'를 풀 크기와 대기 상한으로 채운다고 읽는다.
6. `accept-lock-wait` 2000ms와 `accept-lock-timeout` 1000ms를 dev·prod에 켠다. 한 사용자의 잔고 행 잠금이 그 마켓 접수를 건당 1초씩 막는 증폭이 따른다(4-12). X6b와 X8 E1 결과를 보고 값을 다시 정할 수 있다.
7. 좀비 판정 수요에서 접수 경합을 빼고, 접수 락 보유가 2초를 넘은 대기 초과만 센다(4-11). DB 설계 §5.4 v2.19의 수요 정의를 바꾼다.
8. 종료 조건 'P2 동작 차이 0'을 4-21의 의도한 차이를 뺀 '관문 판정 차이 0'으로 읽는다. 경합이 `429`로 옮겨 가용성 판정에서 빠지는 만큼 경합 상한(append의 0.1%)과 k6 `market_contention` 임계를 더했다(7-2).
9. `POST /actuator/partitions`는 loopback만 받는다(4-14). 기존 `admission`의 같은 노출은 이번에 고치지 않는다.

## 11. 검토 대응 (2026-09-24)

같은 날 이 설계와 계약에 대한 검토 지적 17건을 받았다. 코드, 계약, 하네스 스크립트로 대조했다. 17건 모두 실제 문제로 판단해 설계와 계약을 고쳤다. 통째로 반박한 지적은 없다. 다만 사실 일부가 틀린 지적(R4의 LB 포트, R16의 시험 실행기)과 범위 판단이 다른 지적(R13)이 있어 그 부분을 적었다. R2와 R17은 같은 결함을 설계와 하네스 계약에서 짚은 것이라 함께 답한다. 번호 R1~R17은 받은 순서이고 심각도는 검토가 매긴 값이다.

### R1. 경합 `429`의 '확정 미접수'가 같은 키 동시 요청에서 거짓이다 (medium, API 설계 §2-5-b)

지적대로다. V47은 이 요청이 채번한 주문 id만 보고(2-6), 공유 표시를 채운 요청은 곧바로 NOT_JOURNALED를 받는다. 첫 판은 `journaled=false`면 `429`였으므로, 원본 B가 키를 넣고 느려진 사이 재전송 A가 공유 표시를 채우고 경합으로 끝나면 A는 '확정 미접수'를 받는데 B가 뒤이어 커밋할 수 있었다. 키를 넣은 요청이 KEPT를 받는 경우도 같다.

바꾼 것: `429`는 키를 넣은 요청의 DISCARDED(그리고 취소)만이다. KEPT, ABSENT, 공유 표시 요청의 NOT_JOURNALED, V47 실패, 재생은 `409 order_in_progress`다(4-12). `submitFailure`는 boolean 대신 접수 결과 `IntakeOutcome`을 받는다. DISCARDED가 충분한 근거는, 공유 표시 없이 같은 키로 커밋하는 길이 없어 V47이 키를 지우는 순간 그 키의 주문이 없다는 데 있다. 키를 지운 뒤 늦게 닿은 같은 키 요청은 자기 접수를 하고 자기 응답을 받으므로, `429`가 앞서 결과를 모르게 된 요청까지 미접수로 확정하지 않는다는 한계를 API 설계 §2-5-b에 적었다. 검토가 낸 선택지 가운데 `503`은 고르지 않았다. 재조회 규약은 같지만 인그레스가 리더를 빼기 때문이다(R6과 같은 이유). 취소의 `429` 문장 '주문 상태는 그대로다'도 동시 취소·체결이 있으면 거짓이라 고쳤다. 시험: `SameKeyContentionIntegrationTest`(6-2), `OrderGatewayReserveMappingTest`의 결과별 사례(6-3), X6c.

### R2·R17. 경합을 `429`로 옮기면 관문과 k6에서 보이지 않는다 (medium 설계, low 하네스 검증설계)

맞다. S3 이미지는 두 값이 0이라 경합이 지연으로만 나타났고, S4는 켜면서 `429`로 낸다. k6는 `429`를 실패로 세지 않고(2-10) 공통 판정에도 경합 상한이 없어, S4 회귀로 경합이 늘어도 모든 관문이 통과할 수 있었다. 첫 판의 '관문 판정 차이 0'은 판정의 실효가 바뀐 것을 가렸다.

바꾼 것: 공통 판정에 장애 창 밖 접수 경합 상한(같은 구간 append의 0.1% 이하, X1은 주행 전체)을 두고 창 안 값은 `cause`·`response`별로 기록한다(7-2). k6에는 bucket=market `429`를 따로 세는 비율 지표 `market_contention`과 정상 구간 임계(0.1%)를 더했다(4-18, 하네스 검증설계 §2-2). 4-21 표에 '경합이 판정에 보이는 곳' 행을 더했고, 사용자 확인 8에 이 변화를 적었다. 상한을 0이 아니라 0.1%로 둔 것은 호스트 잡음(사용자 PC에 다른 프로그램이 함께 돈다)으로 드문 1초 넘는 DB 정지가 경합을 만들 수 있어서다. 기대값은 0이고 값은 기록한다.

### R3. append `lock_timeout`의 격리 주장이 틀렸다 (low)

맞다. 마켓 접수 락이 append 동안 유지되므로 잠긴 행을 기다리는 주문 하나가 그 마켓 접수 전체를 최대 1초 막고, 둘 이상 줄을 서면 다른 사용자도 대기 2초를 넘겨 `429`를 받는다. 첫 판의 4-12 문장과 X6의 '다른 계정 지연 1초 남짓' 기록이 서로 어긋났다.

바꾼 것: 4-12의 문장을 '그 마켓의 접수가 건당 최대 1초씩 직렬로 막힌다'로 고치고, X6b(잠긴 계정이 주문 셋을 동시에 넣는 변형)로 다른 계정의 `429` 수와 지연을 잰다. 값 선택(사용자 확인 6)에 이 증폭과 E1 같은 지연 아래의 경합을 근거로 적었다. 값 자체는 바꾸지 않았다. 더 짧은 `accept-lock-timeout`은 막힘을 줄이지만, 정산이 부하나 호스트 잡음으로 잔고 행을 수백 밀리초 쥐는 정상 구간에서도 `429`를 만든다. 두 쪽의 크기를 잰 뒤 사용자가 정하게 했다.

### R4. `POST /actuator/partitions`가 dev에서 LB로 닿는다 (low, API 설계 §6-C)

맞다. dev는 actuator가 8080에 있고(2-7) 하네스 nginx의 `location /`가 모든 경로를 넘긴다. 사실 하나는 다르다. LB의 호스트 포트는 58080이고, 18080·28080은 api 노드의 호스트 포트다. 결론(인증 없이 리더를 강등하거나 차단기를 풀 수 있다)은 같다.

바꾼 것: `POST`는 원격 주소가 loopback일 때만 받고 나머지는 `403`이다(4-14). 앱에서 막았다. 하네스 nginx에 `location /actuator/`를 막는 규칙은 인그레스를 바꾸지 않는다는 결정과 부딪치고 호스트 포트로 오는 요청을 막지 못한다. 계약의 '내부 포트로만 부른다'는 prod의 배치 설명으로 남기고, 모든 프로파일에서 앱이 막는다고 고쳤다. 카오스 스택의 노출 목록은 `chaos-monkey` 문서가 다시 정의하므로 거기에도 `partitions`를 넣어야 한다는 것도 이 대조에서 찾아 4-14에 적었다. 기존 `admission`의 같은 노출은 9절에 적었다. 시험: `PartitionsEndpointTest`(6-4).

### R5. '기동은 늘 팔로워'를 확인할 스택 실험이 없다 (medium)

맞다. E4의 `docker kill`은 재기동 정책을 건너뛰어 옛 리더가 돌아오지 않으므로 첫 판 X2의 '재기동된 옛 리더' 판정은 관측할 수 없었고, 하네스 검증설계 패치 노트 (2)의 'compose 재시작으로 돌아온 노드'도 사실과 달랐다. X5의 '두 노드가 모두 팔로워로 뜬 뒤'도 콜드 스크립트의 순차 기동과 맞지 않았다. 파티션별 팔로워 상태 값도 정하지 않았다.

바꾼 것: `-PartitionAxes`가 켜진 E4 뒤에 합류 단계를 둔다. 새 리더가 유효한 동안 옛 리더를 `docker start`로 되살려 부팅 획득 없이 `FOLLOWER`로 합류하는지 본다(7-2 X2). E4 스크립트는 S3와 비교해야 하므로 고치지 않고 오케스트레이터에 단계를 더했다. X5 판정은 스크립트의 순서(먼저 올린 노드가 팔로워로 기동을 마친 뒤 런타임 승격, 나중 노드는 팔로워 합류)에 맞췄다. 팔로워 상태 값을 4-10에 고정했다(`FOLLOWER`·`BLOCKED` 1, `PROMOTING`·`ACCEPTING` 2, `REBUILDING`·`DEMOTED`·시작 전 0, 갈림 -1). 기동 완료 판정은 P2에서 그대로 성립한다. 하네스 검증설계 패치 노트 (2)를 고쳤다.

### R6. 인그레스 판단의 전제가 설계 안에서 모순이다 (medium)

맞다. 첫 판 4-13은 리더의 `503`이 페일오버 창과 비접수 일시 오류뿐이라고 전제했지만, 4-12 표는 V47 판정 실패와 재생 요청의 경합을 `503`으로 남겼다. 재생 요청은 접수 락과 append를 거치므로(`OrderGateway.java:287-291`) 대기 초과와 55P03을 똑같이 받는다.

바꾼 것: 재생 경합과 V47 실패 모두 `409 order_in_progress`로 낸다(4-12). 재생은 주문이 이미 접수돼 있어 재조회가 그 주문을 돌려주고, 판정 실패는 키를 남기므로 같은 키 재전송이 재생이나 새 접수로 수렴한다. 어느 쪽도 인그레스가 리더를 빼지 않는다. 4-13의 전제를 'S4는 리더의 `503`을 새로 만들지 않는다'로 다시 적고 남는 `503`을 열거했다. 검토가 낸 '200(기존 주문 반환)'은 고르지 않았다. 재생 경로가 접수 락과 머리말을 거치는 이유(DB 판정 아래의 재생 판정과 epoch)를 바꿔야 하기 때문이다. 시험: X6c의 재생 사례(LB `502` 0 판정).

### R7. 비접수 55P03의 `503`은 S4가 새로 만드는 리더 퇴출 경로다 (medium, API 설계 §2-3)

맞다. 55P03은 지금 `500`이고 `500`은 `proxy_next_upstream`에 없어 리더를 빼지 않는다. 첫 판이 이것을 'S4 이전부터 있던 위험'으로 적은 것은 틀렸다.

바꾼 것: 비접수 55P03은 S4에서도 `500`이다. v2.54 계약의 '55P03을 503으로 매핑'은 인그레스 조정과 함께 적용하기로 한 것이고 S4가 인그레스를 바꾸지 않으므로 S5로 미뤘다(4-12, API 설계 §2-3). `ApiExceptionHandlerTest`의 `500` 단언은 이름만 고쳐 유지한다. 단계 계획 범위를 줄이는 선택이라 사용자 확인 2로 올렸다. 검토의 다른 선택지(`503`으로 두고 판정을 더함)는 고르지 않았다. 판정은 문제를 드러낼 뿐 연쇄를 막지 못한다. 그래도 S4가 리더 `503`을 늘리지 않는다는 전제를 확인하려고 X1·X6에 LB의 `no live upstreams`·`502` 0 판정을 뒀다.

### R8. 엔진을 끈 노드의 배선이 정해지지 않았다 (medium)

맞다. 첫 판은 획득 풀을 엔진 노드에만 만들면서 보관소가 두 JdbcClient를 받게 했고, 조건 없이 뜨는 리스 서비스·보관소 빈과 그 소비자(`EpochSource`, `InvariantScheduler`, 하네스)를 다루지 않았다(2-9). 조회 역할 노드가 `leader_protocol`을 읽지 못한다는 점도 계획 생성에 반영하지 않았다.

바꾼 것: R14 대응으로 획득 전용 풀을 없애 보관소는 지금처럼 리스 풀 하나를 받는다. 엔진을 끈 노드도 `PartitionPlan`과 `PartitionLeases`를 만들되 리스 서비스를 시작하지 않는다(4-2). 조회 역할은 DB를 읽지 않는 한 파티션 계획을 쓴다(4-1). `EngineDisabledContextTest`(bots 프로파일 포함)와 `ReadRoleIntegrationTest`에 단언을 더한다(6-3).

### R9. 재승격 금지를 단언하는 기존 시험 대부분이 빠졌다 (medium)

맞다. 첫 판은 `PromotionRecoveryIntegrationTest:336` 하나만 적었다. 대조해 보니 리스 서비스만 쓰는 시험은 `disarm()` 때문에 단언이 우연히 통과하면서 뜻이 바뀌고, 코디네이터 상태 `DEMOTED`를 기다리는 시험(`PromotionStandDownIntegrationTest:398-415`, `FollowerReadinessIntegrationTest:112`)은 깨진다. `PromotionRecoveryIntegrationTest:336`의 원인은 `AssertionError`라 VM 오류가 아니다.

바꾼 것: 6-3에 강등 원인별 표를 두고 시험마다 단언을 어떻게 바꾸는지 적었다. 파티션 치명은 메시지를 고치고 `rearm()` 뒤 새 epoch 재획득의 양성 단언을 더한다. VM 오류(`NODE_FATAL`)는 그대로 두고 `rearm()`이 효과가 없음을 더한다. 루프 정지 장면은 S4에서 성립하지 않아 '새로 설치한 루프가 게이트 전에 죽는' 장면으로 바꾼다. 재기동 흉내 시험은 주석만 고친다.

### R10. 접수 경합 `429`를 파티션 층 수요로 세면 장기 행 잠금이 두 노드를 모두 차단한다 (medium, DB 설계 §5.4-c 8)

맞다. 행 잠금은 DB에 남아 페일오버로 풀리지 않고, 저트래픽에서 그 사용자의 1초 재시도만으로 45초에 수요 45건·완료 0건이 된다. 대조해 보니 노드 층도 같다. 노드 층 수요는 인증 이전의 모든 주문 요청이라 경합 응답을 받은 요청도 센다. P2에서는 두 층이 같은 모양이다.

바꾼 것: 경합으로 끝난 요청을 두 층 모두 수요에서 뺀다(4-11, DB 설계 §5.4-c 8). 빼기만 하면 JVM 안에서 접수 락을 쥔 채 멈춘 보유자를 놓치는 회귀가 생긴다. S3에서는 대기가 무기한이라 그 대기자가 수요로 쌓여 잡혔는데, S4에서는 2초 뒤 `429`로 빠져나가기 때문이다. 그래서 보유가 `accept-lock-wait`(2초)보다 길었던 대기 초과는 수요로 남긴다. 검토가 낸 두 선택지(경합을 수요에서 빼기, 원인이 행 잠금인 것만 양쪽에서 빼기)를 합친 모양이다. 시험: `ContentionStallExclusionTest`(6-2, 저트래픽 장기 잠금·멈춘 보유자·짧은 줄 머리 막힘), X6d(스택에서 70초 잠금과 1초 재시도, 강등 0).

### R11. 승격 재생의 쓰기가 어느 기간에 묶이는지 정하지 않았다 (low)

맞다. 재생은 설치보다 먼저 같은 sink 계약으로 DB에 쓰는데 첫 판은 기간을 설치 때 만들었다. 재생 sink를 `requireLeader`로 남기면 재생 중 회복 가능 반납 뒤 같은 holder가 다시 얻을 때 기간 결속이 막으려던 길이 재생 구간에 남는다.

바꾼 것: 기간을 획득 콜백(`PROMOTING` 진입)에서 만들고, 재생 sink와 설치 루프가 같은 기간을 쓴다(4-5, 4-8, DB 설계 §5.4-c 6). `TermBoundWriteTest`에 재생 중 회복 가능 반납 뒤 재획득 사례를 더했고, 안전 시험이라 관문 시험(6-2)으로 올렸다.

### R12. E7의 epoch 판정을 '정확히 +1'로 두었다 (low)

맞다. E5·E7·E2·E6 스크립트는 회복 가능 반납으로 epoch가 +2 이상 오르는 정상 경로 때문에 단조 증가와 holder 교체를 본다(2-10). S4는 재승격을 넓히므로 그 여지가 더 크다. 바꾼 것: epoch 판정은 스크립트 규칙을 따르고 정확히 +1은 E4(X2)에만 둔다(7-2). 하네스 검증설계 패치 노트 (1)의 같은 문장도 고쳤다.

### R13. 단계 계획의 E2~E7에서 E3가 빠졌고 E1·E3 스크립트를 돌리지 않는다 (low)

부분적으로 맞다. 단계 계획 문장은 'E2~E7'이지만 S1·S3 관문과 이번 작업 지시의 관문 목록은 E2·E4·E5·E6·E7이다. E3는 Redis 토폴로지가 없어 SKIP이 유효 판정이고(2-10) S3 기준값이 없으므로 'S3와 같다'로 비교할 대상이 아니다. 그래서 E3를 관문의 S3 비교에 넣지는 않는다. 그러나 S4가 두 스크립트의 리스 조회를 바꾸고, E1은 리스 풀 분리와 노드 층 판정이 겨냥한 실험이라 획득 경로와 STALL 비종신화의 회귀를 볼 자리라는 지적은 맞다. X8로 새 스택에서 한 번씩 돌린다(7-2). E1은 스크립트 판정 PASS와 강등 0, E3는 SKIP 판정 파일과 리스 조회 성공을 본다.

### R14. 획득 풀 시험의 대조군이 S3 배선이 아니고 풀 증설의 근거가 약하다 (low)

맞다. 첫 판의 대조군(한 풀 최대 1)은 실제 배선이 아니었다. 다시 따져 보니 파티션 틱 스레드는 노드당 둘이고 풀은 2라, 획득이 막혀도 다른 파티션의 갱신은 남은 연결을 쓴다. 획득 대기를 1초로 끊으면 드문 재확인·조회가 끼어도 갱신 대기가 한 틱보다 짧다.

바꾼 것: 획득 전용 풀을 없애고 기존 리스 풀에서 획득 트랜잭션에만 `lock_timeout`을 건다(4-3, DB 설계 §5.4-c 3). 연결 예산은 바뀌지 않는다(엔진 노드 48, 기본 스택 160, scale 프로파일 199). `RenewUnderBlockedAcquireTest`는 S4 배선에서 갱신 지연이 한 틱보다 작은지 보고, 대조군은 S3 배선(상한 없음)으로 두어 상한이 틱 스레드의 묶임을 끊는 효과를 본다(6-2). S4 배선에서 한 틱을 넘으면 별도 풀 안을 다시 연다. 검토가 권한 '10절 선택지'는 사용자 확인 5로 올렸다.

### R15. 지표·경보 계약이 코드와 어긋난다 (low, 하네스 CI/CD)

맞다. 리스 계수기의 태그는 `outcome`이고(`MeteredLeaderLeaseStore.java:43-62`, `e1-pg-latency.ps1:39`), 새 게이지에는 `node` 태그가 없어 `max by (node, partition)`이 노드를 가르지 못했다. 바꾼 것: 계약의 `{result}`를 `{outcome}`으로 고치고, `PartitionBreakerOpen`은 프로메테우스가 늘 붙이는 `instance`와 `partition`으로 묶는다(하네스 CI/CD §5-2·§5-6). 새 게이지에 `node` 태그를 더하는 안은 고르지 않았다. 스크레이프 대상 라벨로 충분하고 태그를 늘리면 시계열 이름 대조가 늘기 때문이다. 두 인스턴스 가운데 하나만 차단된 규칙 시험 사례를 6-4에 더했다.

### R16. 하네스 산출물의 시험 명령이 빠졌다 (low)

맞다. 경보 셋을 더하면서 promtool 검사·규칙 시험을, 두 파이썬 도구를 고치면서 기존 시험을 6-5에 두지 않았다. 사실 하나는 다르다. `harness/scale` 시험은 pytest가 아니라 unittest로 쓰였고(`test_s3_common_axes.py:3`), 이 PC의 파이썬에는 pytest가 없다. 바꾼 것: 6-5에 CI와 같은 promtool 두 줄(로컬 이미지 `prom/prometheus:v3.13.0` 확인)과 `python -B -m unittest discover -s harness/scale -p "test_*.py"`를 더하고, 6-4에 세 경보의 규칙 시험과 `test_s4_partition_axes.py`를 적었다.

### 12-1. 설계와 다르게 하거나 설계가 정하지 않은 것

모두 이 코드를 맡은 AI가 정했다. 동작과 안전 성질을 바꾸는 것은 없고 시험과 하네스를 만드는 방법이 대부분이다.

1. 인계 상한 주입점. `PromotionCoordinator`에 패키지 전용 `setHandoverLimit(Duration)`을 두었다. `FollowerHandoverRaceTest`가 회차마다 상한을 100ms나 400ms로 줄여, 상한 안에 인계하는 경로와 상한을 넘겨 fresh 재생으로 가는 경로를 200회 안에서 모두 밟게 하려는 것이다. 운영 배선은 2초 그대로이고 설정으로 바꿀 수 없다.
2. 강등 뒤 접수 거부의 예외. 4-6은 '게이트를 닫아 저널 전에 `503`'이라 적었다. `EngineBridge.submit`은 S3와 같은 순서로 라이터 정지 검사(`IllegalStateException`)를 게이트 검사(`NotReadyException`)보다 먼저 한다. 강등이 게이트를 닫고 라이터도 멈추므로 먼저 닿는 쪽이 거부하고, 게이트웨이는 둘 다 `503 service_unavailable`로 낸다. `PartitionLeaseIsolationTest`는 두 예외를 모두 저널 전 거부로 받고 그 마켓의 저널 행 수가 그대로인지 본다.
3. X6 구동기. 4-18과 7-2는 `harness/scripts/s4-intake-contention.ps1` 하나를 적었다. 잠금 세션을 쥔 채 같은 순간에 요청 여럿을 보내는 일을 파워셸로 맞추기 어려워, 변형 a~d의 구동과 변형별 판정은 `harness/scale/s4_intake_contention.py`가 하고 스크립트는 폐기용 스택 가드, 봇 부하, 공통 판정(LB의 `no live upstreams`·`502` 0, 리더 강등 0, 정산 재시도 소진 0)을 맡는다. 부하 계정 둘은 하네스 API로 새로 발급하고 키는 구동기 메모리에만 둔다.
4. 하네스의 자원 인자. 4-18은 `Get-LeaderContainer`·`Get-FirstTradeSql`의 `-Resource`를 적었다. 이 둘을 부르는 `Wait-FirstTradeAfter`, `Get-HarnessStatus`, `Get-LiveNodePort`, `Complete-FailoverExperiment`에도 `-Resource`를 더했고, 모드가 쓰는 자원 목록을 내는 `Get-ModeLeaseResources`를 두어 `up.ps1`·`probe-layers.ps1`이 쓴다. P1·P2에서는 값이 `matching-engine`이고 `Get-FirstTradeSql`의 문장은 종전과 바이트 단위로 같다.
5. k6의 경합 판별. 오류 바디는 `{"error":{"name","message","detail"}}` 모양이라 `order_flow.js`는 `error.detail.bucket`을 읽는다. 4-18의 `detail.bucket`은 이 필드를 줄여 적은 것이다.
6. `TermBoundWriteTest`의 장면. 라이브 사례의 '강등 전 루프의 정산이 재시도 대기에 들어간 사이 재승격'은 정산 트랜잭션 템플릿을 가로채 만들었다. 가로챈 템플릿은 첫 실행 전에 같은 파티션의 강등, 재구성, 재승격을 끝내고 55P03(`CannotAcquireLockException`)을 던져 정산을 재시도 대기로 보낸다. 깨어난 재시도는 강등 전 기간을 들고 있어 한 행도 쓰지 못한다. 대조군은 같은 장면에서 `requireLeader()`로 epoch를 읽는 종전 경로이고 새 epoch로 쓴다.

## 13. 구현 검토 대응 (2026-09-24, 라운드 1)

같은 날 12절의 코드에 대한 구현 검토 지적 12건을 받았다. 코드와 시험으로 대조했고 12건 모두 실제 문제로 판단해 고쳤다. 통째로 반박한 지적은 없다. 다만 제안된 방법을 그대로 쓰지 않은 곳이 셋 있어 이유를 적었다(C1의 보조 장치, C2의 시작 검사 조건, C8의 대조군). 번호 C1~C12는 받은 순서이고 괄호 안은 검토가 매긴 영역과 심각도다. 고친 뒤에는 결함을 코드에 잠시 되살리는 변이로 새 단언이 그 결함을 실제로 잡는지 확인했고, 변이는 모두 되돌려 파일 해시가 고친 판과 같음을 확인했다.

### C1. 리스가 얻은 기간을 승격 조율이 조용히 버린다 (safety, medium)

지적대로였다. 획득 콜백(`PromotionCoordinator.onTermGained`)은 상태가 `FOLLOWER`·`PROMOTING`이 아니면 그냥 돌아갔고, 후보 표식과 승격 조율의 상태는 서로 다른 락으로 바뀌었다. 그래서 세 경로에서 리스가 기간을 쥔 채 갱신만 이어 가고 게이트는 닫힌 반쪽 리더가 생길 수 있었다. 틱 스레드가 기간을 세운 뒤 콜백을 부르기 전에 팔로워 갈림이 재구성을 시작하는 경로, 참여 켜기의 상태 확인과 rearm 사이에 재구성이 끼는 경로, 승격 재생 구간(설치 뒤 게이트 개방 전)에 그 기간의 라이터가 치명으로 끝나 리스가 회복 가능 반납으로 기간만 놓고 후보 표식을 두는 경로다. P2에서는 이 노드가 리스를 계속 갱신해 다른 노드가 승격하지 못하고, 노드 층 좀비 판정이 풀어도 기간을 모르는 승격 조율이 재구성을 예약하지 않아 그 파티션의 후보로 돌아오지 못한다.

고친 것은 넷이다. 첫째, 획득 콜백은 상태가 `FOLLOWER`·`PROMOTING`이 아니거나 리스의 후보 표식이 내려가 있으면 받은 기간을 곧바로 놓는다(`LeaderLeaseService.relinquish`). 기간을 비우고 후보 표식을 내리며 리스 행에는 쓰지 않으므로 다음 리더는 만료 뒤 새 epoch로 정해진다. 상태 확인과 반납이 같은 락 안이라 재구성을 마친 rearm이 이 반납보다 앞서지 않는다. 둘째, `REBUILDING`으로 가는 두 전이(강등 시작 `beginDemotion`, 갈림의 재구성 시작 `beginRebuild`)가 같은 락 안에서 후보 표식을 내린다. 셋째, 재구성 완료·참여 켜기·차단기 해제의 rearm은 상태가 `FOLLOWER`일 때만 같은 락 안에서 한다(`rearmIfFollower`). 넷째, 획득의 관측 통지(`exchange_leader_is_leader`·epoch·다운타임 게이지)를 상태기계 통지보다 먼저 부른다. 곧바로 놓은 기간이나 승격 워커가 반납한 기간이 is_leader 1로 남지 않게 하려는 것이다.

제안의 보조 장치(반쪽 리더가 STALL 등으로 풀릴 때 후보 표식을 다시 세우거나 재구성을 예약)는 넣지 않았다. 위 변경 뒤에는 리스가 승격 조율이 모르는 기간을 쥐는 상태가 한 호출 안의 틈(기간 세팅과 획득 콜백 사이)밖에 없어, 그 장치가 도달할 상태가 없다. 도달할 수 없는 상태를 위한 방어 코드는 두지 않는다는 코드 기준을 따랐다.

시험은 `PartitionTermRaceTest`(DB 없음, 리스 틱 대신 `tryAcquire`를 직접 부르고 승격 워커를 손으로 돌린다)의 세 사례다. 기간 세팅과 획득 콜백 사이에 갈림 재구성을 끼운 사례, 재생 구간의 `WRITER_FATAL` 사례, 참여 끄기와 엇갈린 획득 사례이고, 모두 재구성·참여 켜기 뒤 다음 획득이 정상 승격으로 이어지는지도 본다. 변이 확인에서 획득 콜백을 종전처럼 돌아가게 하면 첫째·셋째 사례가 '기간을 쥐고 있다'로, 강등 시작의 후보 표식 내리기를 빼면 둘째 사례가 '재구성 중인 파티션이 후보다'로, 관측 통지 순서를 되돌리면 첫째 사례가 'is_leader 1'로 실패했다.

### C2. 워커 줄에서 기다린 승격이 강등과 재구성을 지나 팔로워를 인계한다 (safety, low)

지적대로였다. 승격 워커는 노드의 모든 파티션이 같이 쓰므로, 줄에서 기다리는 사이 그 기간이 강등되고 재구성까지 끝나도 늦은 `promote()`가 `follower.handOver`로 인계 표시를 다시 세우고 되돌리지 않았다. 고친 것은 둘이다. `promote()`는 시작할 때 같은 락 안에서 세대·상태(`PROMOTING`)·쥔 기간이 자기 것인지 보고, 아니면 인계·재생·설치 없이 돌아간다. 그리고 이 승격의 세대가 취소될 때(완료 시점 취소와 재생 실패의 회복 가능 반납) 상태가 무엇이든 인계를 되돌린다. 시작 검사를 지난 직후 강등이 들어와 재구성이 인계보다 먼저 끝나는 좁은 틈도 이것으로 닫힌다. 이 되돌리기는 노드 치명으로 파티션 작업 스레드가 멈춘 뒤에도 불릴 수 있어, 갈림 재구성을 예약하지 못하면 재구성 예약과 같이 경고만 남긴다.

제안의 시작 검사 조건 가운데 `lease.isCurrent(term)`은 넣지 않았다. 세대·상태·기간이 맞는데 리스만 잃은 경우는 승격 완료 시점의 취소가 상태를 `FOLLOWER`로 돌리고 인계를 되돌린다. 시작에서 그냥 돌아가면 상태가 `PROMOTING`에 남는다. 시험은 `PartitionTermRaceTest`의 넷째 사례다. 변이 확인에서 시작 검사를 빼면 '늦은 승격이 엔진을 설치했다'로, 시작 검사와 취소 때의 인계 되돌리기를 함께 빼면(종전 코드) '늦은 승격이 재구성을 마친 팔로워를 인계 상태로 멈췄다(상태 2)'로 실패했다.

### C3. 리더 노드의 팔로워 틱이 인계한 마켓의 저널을 매 틱 훑는다 (behavior, high)

지적대로였다. S3는 승격하면 따라잡기 틱을 멈췄지만 S4 코드는 틱을 계속 돌리고, 인계한 마켓까지 물질화 경계를 인계 시점 커서부터 매 틱 읽었다. 리더로 오래 있을수록 그 질의가 훑는 명령 수가 늘어난다. X1(10분)과 X7은 새 스택에서 짧게 돌아 드러나지 않았다. 고친 것. 따라잡는 파티션이 없으면 틱은 DB에 가지 않는다. 있으면 따라잡는 파티션의 마켓만 경계를 읽는다(`EventJournalReader`·`ReplayService.materializedThroughByMarket`의 마켓 판정 인자). 쉬는 파티션(이 노드가 쥐었거나 재구성 중·어긋남)의 격차 게이지는 0이고 하네스 CI/CD §5-2에 적었다. 시험은 `FollowerIdleLeaderTickTest`다. P2에서 인계 뒤 틱의 저널 왕복이 0이고 대조군(인계 전, 되돌린 뒤)은 왕복이 있다. P3 흉내에서 p0을 쥔 노드의 경계 대상은 p1 마켓뿐이고 둘 다 쥐면 왕복이 0이다. 변이 확인에서 조기 반환과 마켓 판정을 빼면 두 시험이 왕복 4, 경계 대상 [1, 2, 3]으로 실패했다.

### C4. 회원 폐쇄 경고에 `too_many_requests`가 원시 코드로 나온다 (behavior, low)

지적대로였다. `web/lib/admin/memberClose.ts`에 `too_many_requests`를 '접수 혼잡'으로 더하고 서버(`MemberAdminService`)와 같은 순서(일시 거부, 접수 혼잡, 정지 마켓)에 두었다. 곧바로 다시 요청하면 풀리는 사유라 안내 문구 분기는 그대로다. `web/tests/memberAdmin.test.ts`의 미완료 문구 시험에 이 사유의 두 사례를 더했다.

### C5. `FollowerHandoverRaceTest`가 '설치 뒤 팔로워가 그 마켓을 만지지 않는다'를 재현하지 못한다 (tests, medium)

지적대로였다. 저널은 `@BeforeAll`에서만 자라 인계 뒤 틱에 적용할 것이 없었다. 200회 회차는 저널을 공유하므로 거기서 저널을 키우지 않고, 같은 시험 클래스에 따로 만든 DB의 사례를 더했다. 팔로워를 head까지 올리고 인계한 뒤 명령을 더 저널에 적고 정산한다. 틱 두 번 뒤 인계 엔진의 커서와 북 해시가 인계 시점 그대로이고, 대조군으로 인계를 되돌린 같은 틱은 새 명령을 적용해 라이브 북과 같아진다. 검토가 쓴 변이(`Track.following()`에서 `!handedOver`를 뺌)로 이 사례가 '인계 뒤 틱이 인계 엔진을 전진시켰다(6에서 12)'로 실패했다.

### C6. 노드 층 좀비 판정의 경합 수요 제외를 실제 배선으로 거치는 시험이 없다 (tests, medium)

MockMvc에 실제 `ApiAuthFilter`, `OrderController`, `OrderGateway`(브리지만 경합을 낸다), `ApiExceptionHandler`를 운영 순서로 세우고, 인증 필터가 세는 수요를 시계를 주입한 노드 층 판정기(강등 기준 45초)가 읽는다. 확정 미접수 `429` 13건과 같은 키의 다른 요청이 관여한 `409`(KEPT) 13건 뒤 수요 26, 제외 26이고 46초 뒤에도 강등하지 않는다. 대조군은 표식을 남기지 않는 예외 처리기이고 같은 경합 25건으로 46초 뒤 불능이다. 멈춘 보유자 뒤의 대기 초과(`429`)는 수요로 남아 46초 뒤 불능이다. 검토가 쓴 변이(`apiException`의 `markDemandExcluded`를 뺌)로 첫 사례가 '경합 응답의 수요를 되돌리지 않았다(26 대 0)'로 실패했다. ### C7. 강등이 그 파티션의 라이터를 멈추는지 단언하는 관문 시험이 없다 (tests, low)

### C8. `SameKeyContentionIntegrationTest`가 대조군을 실행하지 않는다 (tests, low)

A는 공유 표시를 채운 요청이라 NOT_JOURNALED다. 이 입력에서 첫 판은 A와 B에 `429`를 준다. 6-2의 통과 기준 문구를 이것에 맞췄다.

### 13-2. 수정 뒤 폐기용 스택 재주행 (2026-09-25)

13절의 수정 뒤 작업 트리로 `exchange-chaos-app:pml`을 다시 구워(`sha256:5b8c279f…`, 참조 태그 `s4r1ref`, V0~V53, jar는 13-1 빌드의 산출물과 같은 파일) 7절의 X1~X8을 compose 프로젝트 `exchange-pml`의 폐기용 스택에서 다시 돌렸다(2026-09-25 00:13~01:47 KST). DB 모드는 P2이고 파티션은 `matching-engine` 하나다. 원자료와 판정 표는 [pml-S4-20260925-0012](../../../harness/evidence/pml-S4-20260925-0012/README.md), 측정 표는 [09-25 측정](../../measurements/20260925.md)에 있다. 보존 볼륨 두 개는 단계마다 생성 시각이 같았고 `exchange-chaos-app:local`은 건드리지 않았다.

관문은 통과하지 못했다. X1, X2 E4(합류 포함), X3 E7, X4 E5·E6, X5 COLD, X6 a~d는 PASS이고 RTO는 5.106~11.860초, 구 epoch 쓰기 증분 0, 불변식 위반 0이다. X3 E7에서 새 리더의 획득이 `lock_timeout`으로 두 번 끊긴 뒤 얻어, 12-3이 스택에서 보지 못했다고 적은 획득 상한이 처음 발동했다. X6d에는 13절 C6이 요청한 쓰기 완료율 표본을 더했다. 실패는 셋이다.

- X4 E2(첫 번째)는 드레인 뒤 C17 `REPLAY_DETERMINISM` 1행으로 FAIL이다. 절단 중 옛 리더의 라이터가 정산 I/O 오류와 롤백 실패로 `WRITER_FATAL` 파티션 강등을 했고, fresh 재구성의 재시도(4-6의 1·2·4·8초 간격)가 DB 복귀 순간 `CannotGetJdbcConnectionException`으로 끝났다. `EngineRecovery.replayRecorded`는 재생이 던진 모든 `RuntimeException`을 `recovery_runs`의 불일치로 적으므로 결정론 위반이 아닌 연결 실패가 C17에 남은 것으로 본다(로그 대조의 추론이다. DB가 지워져 그 행은 보지 못했다). 첫 주행(12-3)의 E2에서는 옛 리더가 DB 복귀 뒤 갱신 거부로 강등해 재구성이 한 번에 끝나 이 경로가 나오지 않았다.
- X4r E2(두 번째)는 옛 리더의 주문 접수 `500`으로 FAIL이다. `CommandJournalAppender.append`의 I/O 오류 뒤 롤백 실패(`TransactionSystemException`)가 `ApiExceptionHandler`의 매핑 밖으로 나갔고, DB 복귀 순간 `ApiAuthFilter`가 깨진 연결의 `DataAccessResourceFailureException`(08006)을 일시 오류로 보지 않아 인증 단계에서 `500`을 냈다. 단계 계획이 S4에 넣은 '게이트웨이 접수·취소 경로의 일시 DB 오류 per-item 처리'가 이 두 경로를 덮지 못한 것이다. 첫 번째 E2의 로그에도 같은 `500`이 있었지만 S3 공통 판정의 `orders_500_0` 축(Prometheus `increase()`)이 처음 생긴 계열의 첫 증가를 세지 못해 참으로 나왔다.
- X8 E1(세 번 가운데 첫 번째)은 지연 주입 중 리더가 `WRITER_FATAL: UncategorizedSQLException`로 파티션 강등해 epoch가 바뀌어 FAIL이다. 그 실행기가 컨테이너 로그를 남기지 않아 SQLSTATE를 보지 못했다. 로그 저장을 더한 재주행 두 번은 PASS다.

세 실패 모두 DB 일시 장애를 영구 실패나 서버 오류로 분류하는 경로에서 났고, 자금·멱등·권한 검사의 위반은 아니다. 그래도 단계 계획 S4의 관문 조건(P2에서 E2~E7 재실행 결과가 S3과 같다)을 채우지 못했으므로 S4 관문은 미통과다. X7은 판정이 아닌 기록이고, 1분 창 손실 0.20은 같은 창의 저널 행 수(S4/S3 1.001·0.989)와 맞지 않아 측정 창의 산물로 본다(추론).

### 13-3. 문서 단계와 남은 것 (2026-09-25)

문서 단계에서 ADR 0034(머리말 「S4 진행」, 결정한 값 8·11·12의 S4 선택, 단계 표), [단계 계획](마켓분할_리더_단계계획.md) S4 절, 0099, 로드맵, 코드 지도, 09-25 측정을 고치고 S4 코드·시험·하네스·증거와 함께 작업 브랜치에 한 커밋으로 남겼다. DB 설계 §3 표의 V49·V50 행에 남아 있던 '작성 전 계약이다'도 이때 고쳤다(12-4). `check-style` 기본 모드를 막던 S3 증거 README(`harness/evidence/pml-s3-gate-20260924-0830/README.md`)의 제목 줄 금지 대시 7개는 콜론으로 바꿨다. 판정 문구와 수치는 그대로다.

같은 날 최종 검토가 지적 하나(low)를 남겼다. 참여 여부(`participate`)를 후보 판정과 다른 락에서 읽어, 쥔 기간이 없는 파티션의 참여 끄기가 재구성 완료의 상태 전이와 rearm 사이에 끼면 참여를 끈 파티션의 후보 표식이 다시 선다(`PartitionRuntime`의 `rearmIfFollower` 호출과 `setParticipate`). 그러면 운영자가 참여를 끈 직후에도 이 노드가 다음 틱에 리스를 얻어 승격할 수 있다. 창은 좁고, 쓰기 권한은 여전히 DB 판정을 받으므로 자금·오래된 리더 차단과는 무관한 운영 조작의 결함이다. 고치지 않았고 시험도 없다.

S5로 넘어가기 전에 할 것은 다음과 같다.
