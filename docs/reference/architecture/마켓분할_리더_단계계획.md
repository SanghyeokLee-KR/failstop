# 마켓 분할 리더 단계 계획

[ADR 0034](../adr/0034-market-partitioned-leadership.md)를 코드로 옮기는 순서와 각 단계의 관문 시험을 정리한다. 결정의 이유와 대체 범위는 ADR에, 코드 전에 정한 20개 값은 ADR의 「결정한 값」에 있다. 이 문서의 "결정 N"은 그 번호다. 진행 상태는 [로드맵](../../ROADMAP.md)에서 관리한다.

2026-09-23 작성 당시 저장소를 읽기만 했고 빌드·Docker·AWS는 실행하지 않았다. 설계 판단은 "추론", 확인하지 못한 것은 "미확인"으로 표시했다. 2절 표의 "설계 0·1", "검토 0·1"은 이 계획을 만들 때 대조한 설계안 두 개와 적대 검토 두 건의 항목 번호다. 네 원문은 저장소에 두지 않았고 채택한 결과만 옮겼다. 인용한 코드 줄 번호는 main `5e59ff0` 기준이다.

## 1. 한 장 요약

**무엇이 바뀌나.** 지금은 `matching-engine` 리스 행 하나를 쥔 JVM 하나가 12개 마켓을 모두 쓴다(V1__init.sql:693-706). 바꾼 뒤에는 파티션 리스 두 행(p0, p1)을 두고 평소 app-1이 p0, app-2가 p1의 마켓을 쓴다. 마켓과 파티션의 대응은 DB의 추가 전용 표가 정한다. 쓰기 권한 검사는 DB가 기록할 행의 market_id로 리스를 찾아 하므로 앱이 틀린 파티션을 댈 수 없다. 가장 큰 변경은 자금이다. 지금은 잔고 차감이 ACK 뒤의 정산에서 일어나고 그 사이를 JVM 메모리의 `InflightReserves`가 막는다(OrderGateway.java:28-32, InflightReserves.java:13-14). 이것을 저널 append와 같은 트랜잭션의 `reserve_funds`로 옮긴다. 전환은 앱 설정이 아니라 DB의 프로토콜 래치(P1 오늘 → P2 단일 리더+DB 예약 → P3 파티션)로 하고 정지 창에서만 한다.

**왜 자산 보존이 깨지지 않나.** 원장 합 0과 잔고 CHECK는 앞으로도 DB가 강제한다(V38__ledger_balance_update_index_scan.sql:146-153, V1__init.sql:112-120). 두 노드가 같은 사용자의 KRW를 동시에 쓰면 두 append가 같은 잔고 행을 FOR NO KEY UPDATE로 줄 세우고, 뒤의 것이 CHECK에 걸려 저널 행·채번과 함께 롤백된다(V38:98-127). 클라이언트는 400을 받고 ACK는 나가지 않는다. 체결 정산은 LOCKED만 줄이므로(SettlementService.java:446-456) 정산 시점의 23514는 버그가 없는 한 도달하지 않는다(추론, 교차 노드 이중 지출 시험으로 고정). 오래된 리더의 쓰기는 파티션 리스 행의 KEY SHARE와 키 열 UPDATE 대기로 막힌다(V41__lease_key_share_lock.sql:7-11, :27). 주문 멱등은 client_order_id 필수(OrderGateway.java:83-86)와 DB 전역 어드바이저리 락·저널 조회(V44:50-66)로 노드를 넘어 유지된다. P2 이후 구 바이너리는 레거시 함수 거부로 리더가 될 수 없다. 금액은 전부 NUMERIC(40,18)이고 부동소수점을 쓰지 않는다. 적용된 Flyway 파일은 고치지 않고 새 마이그레이션의 CREATE OR REPLACE와 overload만 쓴다.

**무엇이 좋아지고 무엇이 아닌가.**

- 좋아지는 것: 앱 노드 하나가 죽어도 다른 노드가 쥔 마켓은 계속 접수한다(목표이며 미검증). 영향받은 마켓의 RTO는 오늘 단일 모드 실측 5.277~10.507초(docs/measurements/20260914.md:41-45)와 비슷할 것으로 본다(추론). 평소에는 앱 CPU가 두 노드로 나뉜다(결정 2). S3만 해도 단일 리더에서 "출금·동시 주문 → 정산 23514 → 영구 정지" 경로가 닫힌다(TransferService.java:94-97, SettlementService.java:43-46).
- 나아지지 않는 것: 쓰기 천장은 DB 커밋에 묶여 있다. 185/s에서 DB CPU 238.5%, api-1 143.5%였고(harness/evidence/accept-concurrency-20260913/README.md:121, :137) 대역 래치 뒤 214.12/s에서 커밋 1회 5.756ms였다(docs/measurements/20260914.md:62-66). 두 노드는 같은 프라이머리에 커밋하므로 클러스터 접수 천장은 그대로이거나 5~15% 낮아진다(추론). 예약이 접수 락 안으로 들어와 마켓당 접수 천장은 12~33% 낮아지고 ACK 지연이 1.4~2.6ms 이상 늘 수 있다(V38 이전 reserve_funds 실측 기반, 추론). 결정 5는 이 손실을 S3에서 재서 20퍼센트까지만 받아들인다. 앱 CPU는 노드당 절반 정도로 나뉘지만 앱 CPU는 병목이 아니다.
- 나빠질 수 있는 것: 수수료 계정(K=1, SettlementService.java:50-52)과 여러 마켓을 쓰는 사람 계정의 잔고 행을 두 노드가 함께 잠근다. 한 노드가 정산 도중 멈추면 다른 노드의 정산이 prod `lock_timeout 2000ms`(application.yml:191)에 걸려 fatal이 되고, 지금 코드에서는 건강한 파티션까지 강등된다(SingleWriterLoop.java:226-244). 오류 분류·타임아웃·수수료 샤드 보강 없이 파티션을 켜면 회색 장애(E5·E7)에서 오늘보다 나쁘다. 봇 계정은 마켓마다 따로라(BotFleet.java:67, :83) 봇 잔고 행은 파티션을 넘지 않는다.
- 그대로인 제약: 학교에는 app-2를 만들지 않기로 했고(docs/ROADMAP.md:77) 진입점은 app-1 nginx 하나다(deploy/linux/app/nginx-https.conf:60-83). 파티션 검증은 로컬 Docker(api-1, api-2)와 개인 AWS에서만 할 수 있다(결정 19).

**공수와 일정 위험.** 1인 기준 80~120인일로 본다(추론, 아래 3절 합계). 발표(2026-10-16)까지 23일이 남았고 그 사이 10월 초 개인 AWS 재배포와 백업·인증서·장시간 측정·PPTX가 남아 있다([로드맵](../../ROADMAP.md)의 「다음 작업의 시작점」과 「M4」). 파티션 모드를 발표 전에 완성하기는 어렵다고 본다(추론). 그래서 결정 1에 따라 발표 전에는 S0(ADR·결정 기록)과 S1(단일 리더 안전 보강, 로컬 검증)을 하고, 여유가 있으면 S2를 로컬에서 진행한다. S3 이후는 발표 뒤에 한다. 발표에서는 "설계와 선행 안전 수정, 로컬 증거"까지만 말한다.

## 2. 설계 병합 결과

두 설계안과 적대 검토 두 건을 대조해 다음처럼 골랐다.

| 쟁점 | 채택 | 근거 |
|---|---|---|
| 파티션 단위 | 2개 고정, 정적 표, 재매핑 금지(설계 0) | 노드 둘에서 마켓 1:1 리스 12행은 이득 없이 할당량 기아 경로를 만든다(검토 1의 6c) |
| 배정 | 선호표 + 비선호 획득 유예(부팅 2×TTL, 만료 관측마다 1×TTL) | 둘 다 만료되면 한 노드가 모두 가져가 장애 반경 이득이 사라진다(검토 0의 A6-4) |
| 인계 | TTL 만료 인계, 즉시 반납 없음 | ADR 0002:56 유지, 반납 뒤 새는 append 경로 제거(검토 1의 2c) |
| epoch | 전역 시퀀스, 마이그레이션에서 시드, 레거시 획득도 같은 규칙과 이력 | 시드 없이 두면 첫 획득 epoch가 역행하고 이력 PK가 충돌한다(검토 0의 A2-1) |
| fencing | DB가 market_id로 도출, 앱 인자 없음, 조건 없는 잠금 뒤 판정 | 앱 인자는 조용한 split-brain(리스 분석 B6), 조건부 잠금의 경계 구멍(검토 0의 F6) |
| 모드 전환 | 프로토콜 표 P1→P2→P3(설계 1), 모든 리스 행 FOR UPDATE 뒤 선행 조건 검사, 전 행 퇴역 | 검사 뒤 잠금이면 미예약 NEW가 새어 들어온다(검토 1의 1b) |
| 예약 기록 | `order_reservations` 표(설계 1) | C14'·C31 감사가 단순해지고 orders INSERT 경로를 바꾸지 않는다 |
| 예약액 권위 | DB가 payload와 scale로 계산, 앱 값은 대조만 | 앱 산식 불일치가 과소 예약과 마켓 정지로 이어진다(검토 0의 A1a, 검토 1의 1c) |
| REJECTED 해제 | 예약됨이고 orders 행이 없으면 모양과 무관하게 해제 | 조기 반환 위치에 따라 해제 누락이나 오해제가 생긴다(검토 0의 A1b) |
| C14' | 미정산 예약만 더한다 | 정산 뒤 남은 예약 누수를 가리지 않는다(검토 0의 A3-1) |
| 정산 오류 | 55P03·57014·40P01·40001 제한 재시도, fatal은 fencing·무결성만 | 교차 노드 잠금 결합이 강등으로 번진다(검토 0의 A6-1, 검토 1의 6a) |
| 접수 대기 | 예약 단계 SET LOCAL lock_timeout, 마켓 락 tryLock | 줄 머리 막힘으로 다른 노드 전체 접수가 멈춘다(검토 1의 6b) |
| 강등 | 파티션 단위, fresh 재구성, 차단기 | 종신 강등이면 한 번의 E2 뒤 후보가 0이 된다(검토 0의 A6-3) |
| 팔로워 | 마켓별 엔진 인스턴스, 인계 핸드셰이크 뒤 복사, 상태 해시 대조 | 공유 엔진 복사 중 데이터 경합(검토 1의 3a) |
| 좀비 판정 | 파티션별 진행 카운터, 수요는 소유 판정 뒤 계측 | 노드 합산이 한 파티션 정체를 가리거나 반대로 오판한다(검토 0의 A6-6, 검토 1의 6d) |
| 고아 멱등 키 | 어드바이저리 락 아래에서 저널에 없을 때만 삭제 | 교차 노드 재시도에서 남의 키를 지워 이중 주문 경로가 생긴다(검토 0의 A5-1, 검토 1의 3b) |
| cancelAll·관리 취소 | 서버가 파티션별로 팬아웃(결정 15) | 정지 회원의 다른 파티션 주문이 남는다(검토 1의 2d, MemberAdminService.java:222-225) |
| nonce | 노드 로컬 + 인증 앞 소유권 선검사 | coid 필수라 교차 노드 재생은 replayed가 된다(검토 0의 F1) |

## 3. 단계 계획

각 단계는 이전 단계의 종료 조건을 통과한 뒤 시작한다. 공수는 1인 기준 추론이다.

### S0. 문서와 결정 (2~3일, 되돌릴 수 있다)

- 내용: ADR 0034, 0099 현재 구조의 진행 표시, 0002·0022 대체 표시, DB 설계 §5.1 복귀안, API §5-1·§5-2, 하네스 검증설계의 C14'·C22'·C29~C31 초안. 20개 결정을 ADR에 기록한다.
- 진행: 2026-09-23에 ADR 0034와 이 계획, 0002·0022 대체 표시, 0099와 로드맵 갱신을 했다. 계약 문서 세 개의 개정은 남았고, 각 계약은 그 절을 쓰는 단계의 코드보다 먼저 고친다.
- 종료 조건: 20개 결정이 모두 기록됐다. `scripts/check-docs.ps1`, `check-doclinks.ps1`, `check-adr-current.ps1`, `check-style.ps1`이 통과한다. 0099 해시는 내용 검토 뒤 갱신한다.

### S1. 단일 리더 안전 보강 (5~8일, 되돌릴 수 있다, P1 그대로)

- 내용: 정산 sink의 오류 분류와 제한 재시도(레지스트리 멱등, SettlementService.java:232-241에 기댄다). 재시도 대상은 55P03·57014·40P01·40001이다(결정 11). 고아 멱등 키 조건부 삭제(OrderGateway.java:251-258). append 예약 전 단계에 쓸 lock_timeout과 마켓 락 tryLock 틀. prod 타임아웃을 쓰는 카오스 프로필(지금 카오스는 dev라 기본 풀에 lock_timeout이 없다, application.yml:100-112). 모호한 커밋 이중 주문 재현(docs/ROADMAP.md:161)은 선택이다.
- 관문 시험:
  - `SettlementRetryClassificationTest`: 잔고 행을 외부 세션이 쥐어 55P03을 일으키면 재시도로 흡수하고 강등 0. fencing 거부는 여전히 강등.
  - `OrphanKeyConditionalDeleteTest`: 검토 0 A5-1 인터리빙(키 INSERT 뒤 정지, 다른 요청이 커밋, 원 요청 실패)에서 커밋된 주문의 키가 남는다.
  - 카오스 E2·E4·E5·E6·E7 각 1회(prod 타임아웃 프로필): RTO < 30초, 구 epoch 쓰기 증분 0, C01·C02·C05·C13A·C14·C22 0. docs/measurements/20260914.md:41-45와 같은 표로 비교한다.
- 종료 조건: 위 시험 통과, `server`에서 `./gradlew.bat build` 통과. 학교 app-1 배포는 사용자 승인과 증거본 기록 뒤에만 한다.

### S2. 스키마와 시장 도출 fencing (10~13일, 되돌릴 수 있다, P1 동작 불변)

- 내용: 새 마이그레이션(착수 시 다음 가용 번호, 2026-09-23 현재 V46이 마지막). `leader_protocol`과 이력, `leader_epoch_seq` 시드, `lease_acquisitions`, 파티션 리스 두 행, `market_lease_partition`과 마켓 추가 트리거(배정은 결정 3), `lease_resource_for_market`, 3인자 판정·잠금·획득·갱신 함수, 2인자 레거시 함수 CREATE OR REPLACE(P1에서는 기존 의미, 획득은 시퀀스 규칙과 이력), 머리말 6인자 판의 판정 교체. 예약액 계산에 쓸 scale 열 위치 확인과, 없을 때의 카탈로그 scale 열 추가(결정 7). 함수가 모든 경로를 덮은 뒤 app_role의 `leader_lease` 직접 UPDATE 회수(결정 17). Java의 'matching-engine' 하드코딩 15곳 교체(CommandJournalAppender.java:41, OrderGateway.java:341, EpochSource.java:28, PostgresLeaderLeaseStore.java:56·66·96, FencingTokenAlignment.java:45, HaMonitoringController.java:100, SettlementService.java:81 등, 검토 입력 목록). 시험 코드 34파일 53줄은 헬퍼로 치환한다(검토 입력 집계, 미확인).
- 관문 시험:
  - `EpochSequenceSeedTest`: 마이그레이션 직후 첫 획득 epoch > 기존 최대. 구 2인자와 새 3인자 획득을 번갈아도 유일·행 안 단조·이력 누락 0.
  - `MarketDerivedFencingTest`: 시험 DB에서 P3을 흉내 내 마켓 A 리스로 마켓 B 행 INSERT 0행. 대응이 없는 마켓 쓰기 거부. 정산 머리말의 마켓 불일치 IllegalStateException.
  - `LeaderLeaseLockModeIntegrationTest` 3종의 파티션 행 판: p0 승격이 p1 쓰기를 기다리지 않는다.
  - fencing 주입 시험 이전: PromotionStandDownIntegrationTest.java:697-711을 3인자 함수 rename으로 바꾸고, 주입 전후 양성 대조로 실제 거부가 나는지 확인한다(V30:23-24가 기록한 무력화 사례).
  - 기존 통합 시험 전체 통과. 카오스 E4·E7 재실행이 S1 결과와 같다.
- 종료 조건: 위 통과, 빌드 통과, P1에서 동작 차이 0(같은 부하 주행의 불변식과 RTO 비교).

### S3. 접수 시점 예약과 P2 전환 (10~14일, P2 전환 뒤 되돌리기 제한)

## 4. 결정한 값

코드 전에 정할 20개 항목(범위, 목적, 마켓 배정, 인계, 천장 손실 한도, 예약 기록, 예약액 계산, P2→P1 되돌리기, 래치를 걸 DB, 수수료 샤드, 타임아웃, 파티션 fatal, WebSocket, nonce·레이트리밋, cancelAll, C14' 출금 항, 리스 UPDATE 권한, DynamoDB 공급자, 검증 장소, 문서 범위)은 [ADR 0034의 「결정한 값」](../adr/0034-market-partitioned-leadership.md#결정한-값)에 같은 번호로 기록했다. 값을 바꾸면 ADR과 이 계획의 해당 단계를 함께 고친다.

## 5. 확인하지 못한 것

- PostgreSQL 세부 동작: INSERT…SELECT와 `FOR KEY SHARE OF`의 조합, EvalPlanQual에서 SET 절 nextval 재계산, 튜플 잠금 대기열 순서.

- Spring user destination 브로드캐스트 요건, nginx 전원 퇴출 동작, ALB 503 비재시도.
- 기존 통합 시험 넷의 단일 리스 전제, deploy/vm-lab 셸 스크립트의 하드코딩.
