# ADR 0038. 온프레미스 AI 추론 서버를 한 대 둔다

- 상태: 채택(사용자 결정 2026-09-25). 구축 전이다. 장비 반입, 설치, 연결 경로, 모델 선택은 아직 하지 않았다.
- 날짜: 2026-09-25
- 관계: [ADR 0035](0035-ai-operations-authority.md)가 AI가 무엇을 할 수 있는지(권한)를 정하고, 이 문서는 그 판단 모델을 어디서 돌리는지(배치)를 정한다. 두 문서가 부딪치면 권한은 0035를 따른다. 번호 0036(Patroni 자동 전환)과 0037(Databasus)은 다른 작업이 쓸 예정이라 비워 두었다.

## 배경

0035는 관제센터의 AI가 상황을 판단하고 허용 목록 안의 조치안을 내게 했다. 그 판단을 만드는 AI 판단 서비스와 서버 정책 엔진은 2단계 구현 대상이고 아직 없다. 0035의 데이터 절은 판단 모델로 로컬 모델(DGX Spark)을 우선한다고만 적었고, 그 모델을 돌릴 장비를 어디에 몇 대 두는지는 정하지 않았다.

지금 학교 bot-1의 일일·장애 보고는 Gemini 3.1 Flash-Lite의 HTTPS API로 요약한다(0027). 판단까지 외부 API에 맡기면 운영 지표와 경보 문맥이 매번 외부로 나가고, 판단이 외부 서비스의 가용성과 과금에 묶인다. 사용자는 2026-09-25 AI 서버 한 대를 온프레미스로 구축하기로 정했다.

## 결정

온프레미스(연구소)에 AI 추론 서버 `ai-1` 한 대를 둔다. 장비는 NVIDIA DGX Spark 한 대이고 통합 메모리는 128GB다. 처음 실행기는 Ollama다. 어떤 모델을 올릴지는 평가로 정하며, 정하기 전까지 화면과 시뮬레이터는 모델 이름을 단정하지 않고 '평가 중'으로 적는다.

`ai-1`은 0035의 AI 판단(상황 판단, 근거, 원인 가설, 허용 목록 안의 조치안)을 추론하는 자리다. 조치를 실행하는 것은 0035대로 AI가 아닌 서버 정책 엔진이고, `ai-1`은 판단 요청을 받아 결과를 돌려줄 뿐이다. 일일·장애 보고의 요약 경로(0027)는 이 결정이 바꾸지 않는다. 보고 요약을 `ai-1`로 옮길지는 따로 정한다.

모델 평가의 참고 자료로 로컬 RTX 4090에서 간이 평가를 한 번 했다. 8개 상황을 16회 물었고 결과는 아래와 같다.

| 모델 | 정답 | JSON 형식 | 응답 p50 | 관찰 |
|---|---|---|---|---|
| gpt-oss:20b | 12/16 | 16/16 | 0.9초 | 해결할 수 없는 문제를 경보 보류로 덮는 오답이 있었다 |
| qwen3.6:35b-a3b | 10/16 | 16/16 | 3.5초(일부 CPU 적재) | 같은 종류의 오답이 있었고, 근거에 없는 수치를 이유에 썼다 |

이 수치는 개발 PC의 RTX 4090에서 얻은 것이며 DGX Spark의 결과가 아니다. 원자료는 저장소 밖에 있다. 모델 선택의 근거로 쓰려면 Spark에서 같은 상황으로 다시 잰다. 두 모델 모두 틀린 판단을 그럴듯한 조치안으로 내놓았다는 점은 0035의 허용 목록, 서버 정책 엔진의 재검사, JSON 스키마 강제가 필요한 이유이기도 하다.

### 보안

Ollama API에는 인증이 없다. 방화벽과 허용 주소로 관제 쪽 호출 주소만 받게 하고 인터넷에 열지 않는다. Ollama의 '-cloud' 원격 모델은 요청을 외부 클라우드로 보내므로 쓰지 않는다. 프롬프트에는 비밀 값과 개인정보를 넣지 않는다(0035 데이터 절과 같다).

### 연결 경로

AWS와 온프레미스 사이의 연결 경로는 정하지 않았다. 선택지는 둘이다.

1. WireGuard나 Tailscale 같은 터널로 두 쪽을 잇는다. 관제 쪽이 `ai-1`을 직접 부를 수 있지만 터널의 키 관리와 끊김 감시가 따른다.
2. 온프레미스 쪽이 바깥으로 나가 판단 요청을 가져가고 결과를 돌려준다. 연구소로 들어오는 포트를 열지 않아도 되지만 요청을 쌓아 둘 자리와 지연이 생긴다.

학교 계정의 제한([ADR 0029](0029-school-aws-first-personal-account-expansion.md))과 NAT 없는 실습 네트워크([ADR 0030](0030-nat-free-lab-and-bounded-read-asg.md))에서 각 방식이 되는지는 확인하지 않았다. 경로를 정할 때 이 둘과 연구소 네트워크의 조건을 함께 본다.

### 장애 시 동작

`ai-1`이 멈추거나 연결이 끊기면 AI 판단과 AI 조치가 없다. 자동 모드여도 조치는 일어나지 않는다. 기존 경보(Alertmanager와 Teams)와 조회 ASG의 AWS 지표 정책은 AI와 무관하게 그대로 동작한다. 이것은 0035의 자동 실행 전제 조건 6(AI가 응답하지 않거나 출력 형식이 맞지 않으면 조치하지 않는다)과 같다. 서버는 한 대라 이중화가 없고, 그 공백은 운영자가 수동으로 판단하는 것으로 메운다.

## 근거

판단에 쓰는 운영 지표와 경보 문맥이 연구소 밖 AI 서비스로 나가지 않는다. 호출마다 외부 과금이 붙지 않고 판단이 외부 서비스의 가용성에 묶이지 않는다. 0035가 이미 로컬 모델을 우선하기로 했으므로 그 모델을 돌릴 자리를 정한 것이다. 한 대만 두는 것은 AI가 거래나 기본 경보에 필요한 요소가 아니어서 멈춰도 운영이 이어지기 때문이다.

한계도 있다. 장비는 아직 없고, 4090 평가는 Spark 결과가 아니며, 연결 경로를 정하지 않았다. 한 대라 장비 고장이나 연구소 네트워크 장애 동안 AI 판단이 없다.

## 대안

아래 세 안은 이 문서를 쓰며 비교한 것이고 사용자가 따로 검토한 안은 아니다. 외부 AI API로 판단하는 안은 지금의 보고 경로와 같은 방식이라 바로 쓸 수 있지만, 운영 데이터가 외부로 나가고 판단이 외부 가용성에 걸린다. AWS의 GPU 인스턴스에 모델을 올리는 안은 학교 계정의 자원 생성 제한과 월 40만 원 예산을 넘는지 따져야 하고 상시 가동 비용이 붙는다. 평가에 쓴 개발 PC의 RTX 4090을 그대로 서버로 쓰는 안은 개발 장비라 상시 운영 자리가 아니다.

## 영향

[0099](0099-current-architecture.md)의 역할 표와 운영 보고 문단에 `ai-1`을 '예정, 구축 전'으로 적고 ADR 표에 이 문서를 더한다. 관리 콘솔은 같은 이름을 쓴다. 관제센터 인프라 칸의 '온프레미스' 묶음과 서비스 흐름의 온프레미스 틀은 [관리자 설계 4-4, 7-10 (i)](../product/관리자_설계.md), [레이아웃 §7](../contracts/데스크톱_레이아웃설계.md), [디자인 시스템 §12-9](../contracts/프론트_디자인시스템.md)가 정한다.

1단계 화면은 시뮬레이터 값이다. [관제 시뮬레이터](../../../web/lib/admin/opsSim.ts)가 `ai-1`의 GPU 사용률, 통합 메모리, 추론 지연 p50·p95, 초당 토큰, 대기 요청, 관제 연결 상태를 지어내고, AI 판단이 걸린 동안 대기 요청과 GPU가 잠깐 오른다. 실제 데이터 원천(http)에서는 이 칸이 '원천 연결 전'이다. 서비스 흐름의 판단 요청선은 연결을 뜻하지 않는 그림이고 이 화면은 `ai-1`에 아무것도 보내지 않는다.

구축할 때 할 일은 장비 반입과 OS·드라이버·Ollama 설치, 방화벽과 허용 주소, 연결 경로 결정과 시험, Spark에서의 모델 재평가, AI 판단 서비스(0035 2단계)와의 연결, `ai-1` 연결 끊김의 감시와 경보다. 이 결정은 학교 AWS의 배포 상태를 바꾸지 않는다.
