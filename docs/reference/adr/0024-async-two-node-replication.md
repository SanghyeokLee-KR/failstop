# ADR 0024. 동기 정족수를 버리고 비동기 2노드 복제로 내린다

- 상태: 채택
- 날짜: 2026-09-12
- 뒤집는 결정: `docs/reference/adr/0018-synchronous-quorum-any1.md`. 그 문서의 결정(primary 1 + standby 2, 동기 `ANY 1`)과 기각안 표 비동기 행을 대체한다
- 관련: ADR 0017(리스를 커밋 경로 밖으로), ADR 0004(비용과 무손실 요건), ADR 0020(증명 경로 근거)
- 근거 실측: `harness/evidence/replication-fault-20260908/`, `harness/evidence/sync-replication-20260908/`, `harness/evidence/failover-rpo-20260912/`
- 코드: `deploy/compose.node-data.yml`, `deploy/.env.example`, `deploy/pg-standby-entrypoint.sh`

## 맥락

ADR 0018 이 동기 복제를 `ANY 1` 정족수로 묶고 standby 를 2 대로 올렸다. 사유는 실측이었다.
동기 standby 1 대 구성에서 그 한 대를 죽이면 접수가 2 초 만에 0 이 되고 수요 전량이 거절로
바뀐다. primary 는 살아 있는데 동기 응답을 기다리며 논다.

그 결정은 옳은 문제를 봤으나 해법에서 한 축을 빼먹었다. **standby 한 대를 더 사서 여유를
만들었을 뿐 동기 복제가 쓰기 가용성을 standby 에 묶는다는 성질 자체는 그대로 남았다.** 같은
실측표의 마지막 행이 그것을 보인다. 두 대를 다 잃으면 다시 접수 0 이다. 정족수는 단일
장애점을 이중 장애점으로 옮긴 것이지 없앤 것이 아니다.

24시간 거래소에서 저장 계층의 보조 노드 장애가 주문 접수를 멈추는 구조를 받아들이지 않는다.
그것이 이 결정의 전부다.

## 결정

상시면 PostgreSQL 을 **primary 1 대 + standby 1 대, 비동기 스트리밍 복제**로 한다.

- `synchronous_standby_names` 를 쓰지 않는다. 비워 둔다.
- `synchronous_commit` 은 `on` 을 유지한다. standby 를 지목하지 않으면 이 값은 로컬 WAL
  flush 까지만 기다리므로 비동기 정책과 모순되지 않는다. 내리면 primary 급사 시 유실 창이
  더 커진다.
- standby 는 hot standby 로 띄운다. 읽기 오프로드의 여지를 남기되 이 판에서 라우팅을
  구현하지 않는다.
- 배치는 primary 가 AZ-a, standby 가 AZ-c 다.

**성능 확장이 목적이 아니다.** DB 대수를 늘려 쓰기 처리량을 얻는 구조가 아니다. 쓰기 상한은
`EngineBridge.submitLock` 이고 그 해소는 ADR 0022 가 다룬다. 이 결정은 그 축과 무관하다.

## 사유

### ADR 0018 이 비동기를 기각한 근거를 뒤집는다

그 문서의 기각 사유는 한 줄이고 실측이 아니다.

> 비동기 복제로 내린다. RPO 0 주장을 버려야 한다. 이 프로젝트의 명제가 장애 아래의 무결이라
> 그 주장이 곧 주제다.

두 가지가 빠졌다.

첫째, **가용성 대가를 같은 저울에 올리지 않았다.** 그 판단은 RPO 만 보고 write availability 를
보지 않았다. 같은 문서가 바로 위에서 "그 standby 가 쓰기의 단일 장애점" 이라고 적는다. 잃는
것을 하나만 세면 어떤 결정도 정당해 보인다.

둘째, **명제의 범위를 넓게 잡았다.** 이 프로젝트가 증명하는 명제 1 은 "폭주와 장애에도 자산별
원장 합 0, 주문 중복·유실 0" 이다. 그것은 체결 무결이지 저장 계층 무손실이 아니다. 매칭
멱등성, `client_order_id` 수렴, `assert_current_leader` fencing, 저널 재생은 전부 비동기 복제와
독립이다. RPO 0 은 그 명제의 일부가 아니라 그 위에 얹은 별개 주장이다.

### 되찾는 것

`sync-replication-20260908` 이 구간을 갈라 뒀다.

| 구간 | 처리량 변화 |
|---|---|
| 복제 없음 -> 비동기 | -13.6퍼센트 |
| 비동기 -> 동기 | -19.6퍼센트 |
| 동기 -> 동기 + AZ 왕복 2ms | -12.8퍼센트 |

비동기로 내리면 아래 두 구간이 사라진다. 절대값으로는 53.0/s 에서 65.9/s 다. 다만 이것은
2026-09-08 회차의 값이고, 천장 절대값은 회차를 넘겨 인용하지 않는다(기획안 한계 47). 인용할
수 있는 것은 방향과 비율이다.

처리량은 부수 효과이고 이 결정의 사유가 아니다. 사유는 standby 장애가 쓰기를 멈추지 않는다는
것 하나다.

### 리스 연쇄가 짧아진다

ADR 0017 이 기록한 연쇄의 1 단계가 동기 커밋 stall 이다. 커밋이 막히면 리스 갱신도 막히고,
막힌 동안 리스가 만료되고, 풀리는 순간 fencing 이 리더를 끌어내린다. `replication-fault-20260908`
이 그것을 세 회차에서 재현했고 "standby 를 되살려도 서비스는 되살아나지 않는다. 복구에
필요한 것은 앱 재기동이다" 로 적었다.

비동기는 그 연쇄의 진입 조건을 없앤다. ADR 0017 을 무효화하지는 않는다. 리스가 여전히
PostgreSQL 커밋이고 primary 자체가 멈추면 같은 연쇄가 돈다.

## 대가

**RPO 0 을 보장하지 않는다.** 이것이 이 결정이 파는 것이다.

- primary 급사 시 standby 에 아직 전달되지 않은 WAL 이 유실될 수 있다.
- `command_journal` 이 같은 PostgreSQL 에 있으므로 **그 구간은 저널 재생으로도 복원되지
  않는다.** 저널 자체가 유실 대상이기 때문이다. "저널 재생으로 RPO 0" 이라고 쓰지 않는다.
- 유실 창은 복제 지연이다. `failover-rpo-20260912` 가 그 값을 잰다. 정상 복제 중 급사에서는
  ACK 88 건 중 0 건을 잃었고, standby 를 8 초 얼린 뒤 급사에서는 ACK 122 건 중 36 건을 잃었다.
  **곧 유실량은 그 순간의 복제 지연과 같다.** 정상 구간의 0 을 무손실 보장으로 읽지 않는다.

그래서 정본에서 RPO 0 주장을 철회한다. 대체 문구는 "RPO 는 복제 지연만큼이고 지연이 있는
구간에서는 그만큼 잃는다" 이다.

**RTO 는 이 결정이 정하지 않는다.** 아래 미충족 참조.

## 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| ADR 0018 유지(standby 2 대 동기) | 두 대를 다 잃으면 다시 접수 0 이다. 단일 장애점을 이중 장애점으로 옮길 뿐이고, 노드 하나가 늘어 비용과 운영 대상이 함께 는다 |
| standby 1 대 동기 | ADR 0018 이 이미 실측으로 기각했다. 한 대 상실이 곧 전면 정지다 |
| standby 상실 시 `synchronous_commit` 자동 폴백 | 눈에 보이는 장애를 눈에 안 보이는 데이터 위험으로 바꾼다. 폴백이 도는 동안 무엇을 잃었는지 아무도 모른다. 명제 1 의 반대 방향이다 |
| Witness 노드 추가 | witness 는 WAL 이 없어 커밋 정족수를 채우지 못한다. 선출 정족수와 커밋 정족수는 다른 문제다. 그리고 이 프로젝트의 리더 권위는 이미 `leader_lease` 행에 있고 ADR 0002 가 외부 합의를 명시적으로 배제했다. 중재 기구가 둘이 된다 |
| 내구 저널을 PostgreSQL 밖으로(Kafka 계열) | 이 판의 범위가 아니다. 내구 저장소가 둘이 되면 "큐에는 ACK 됐는데 DB 에 없는 주문" 이라는 새 정합 문제가 생기고, 3 노드 브로커가 비용과 운영 대상으로 붙는다. M4 는 새 애플리케이션 구성요소를 붙이지 않는 구간이다 |

## 미충족

- **DB 자동 페일오버가 없다.** 저장소 전체에 `pg_ctl promote`, `pg_promote()`,
  `promote_trigger_file` 이 0 건이다. 이 결정은 그것을 만들지 않는다. 지금 있는 자동
  페일오버는 앱 리더 페일오버(`leader_lease`, fencing)뿐이고 그것은 DB 가 살아 있을 때의
  장치다. **"자동 failover" 라고 쓰지 않는다.** 수동 절차를 `docs/reference/operations/` 에 둔다.
- 그래서 **RTO 를 이 결정이 정하지 않는다.** `failover-rpo-20260912` 가 잰 1.697초와 1.886초는
  승격 명령의 실행 시간이다. 사람이 장애를 알아차리는 시간, 승격 여부를 판단하는 시간, 앱
  `DB_HOST` 를 바꿔 재기동하는 시간이 그 안에 없다. 운영 RTO 는 여전히 미측정이다.
  E5·E7 이 잰 4.265초와 10.176초는 앱 층 값이지 DB 페일오버 값이 아니다. (2026-09-13 주: V41 위 재주행 값은 E5 10.041초, E7 10.226초다. 현재 값은 `docs/ROADMAP.md` M1 달성 문단이 갖는다)
- **구 primary 재편입이 되감기로 끝나지 않는다.** 같은 회차에서 `pg_rewind` 가 실패했다.
  `wal_log_hints=on` 전제는 섰으나 되감기가 읽어야 하는 구간이 분기 지점부터가 아니라 마지막
  공통 체크포인트부터라, 분기보다 209.8MiB 앞의 WAL 이 이미 재활용된 뒤였다(`wal_keep_size`
  기본값 0). 실제 경로는 전량 베이스백업이고 428.7MiB 에 264.7초, 스트리밍 재개 확인까지
  272.5초다. 그 동안이 이중화 공백이다. 되감기를 사려면 `wal_keep_size` 를 체크포인트 간격만큼의
  소급 폭으로 올리거나 `archive_mode` 를 켜야 한다. 그 선택을
  `docs/reference/adr/0025-rejoin-by-basebackup-no-wal-retention.md` 가 받아 **둘 다 채택하지 않기로**
  결정했다. 이 항목은 해소가 아니라 결정된 상태다.
- 읽기 라우팅 미구현. standby 를 hot standby 로 띄우지만 조회를 보내는 코드가 없다.
- 실제 다중 호스트 기동 0 건. `deploy/` 전체가 미검증이고 이 변경도 같다. 로컬 한 호스트
  두 컨테이너로만 확인한다.

## 영향

- ADR 0018 의 결정과 기각안 비동기 행을 대체한다. 그 문서는 삭제하지 않는다. 왜 3 노드
  동기를 한 번 택했는지가 이 결정의 근거이기 때문이다.
- ADR 0004 의 비용 근거(DB 3 노드 전제)와 무손실 운영 요건(`ANY 1` 정족수 항목)을 개정한다.
- ADR 0020 이 증명 경로 근거로 건 ADR 0018 인용을 이 문서로 옮긴다.
- 정본의 RPO 0 주장과 도면의 DB 3 대 표기를 함께 고친다.
- `harness/` 의 3 노드 동기 실험 증거는 보존한다. 정책을 왜 바꿨는지 보이는 근거다.
