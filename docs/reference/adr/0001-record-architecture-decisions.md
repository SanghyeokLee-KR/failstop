# ADR 0001. 아키텍처 결정 기록(ADR) 관례를 도입한다

- 상태: 채택
- 날짜: 2026-07-22
- 결정자: 아키텍처 담당(정본 문서 관리자)

## 배경

이 프로젝트는 1년 주기 대규모 프로젝트다. 정본 계약 문서(DB 설계, API 설계, 하네스 설계)는 "무엇을 만드는가"의 현재 상태를 담는다. 그러나 문서는 결정의 결과만 남기고 "왜 그 결정을 했는가", "어떤 대안을 버렸는가"는 담지 않는다. 시간이 지나면 이 맥락이 소실되고, 같은 논쟁이 반복되거나 이미 기각된 대안이 다시 제안된다.

정본 문서의 버전 헤더(예: DB 설계 v2.10, API 설계 v2.8)는 패치 이력을 축적하지만, 개별 패치의 근거는 문서 본문에 흩어져 있어 추적이 어렵다. 결정 단위의 독립 기록이 필요하다.

## 결정

아키텍처에 영향을 주는 결정을 ADR(Architecture Decision Record)로 남긴다.

- 위치: `docs/reference/adr/`
- 파일명: `NNNN-title-with-dashes.md`(4자리 순번, 소문자 kebab-case 제목)
- 일반 결정의 순번은 단조 증가하며 재사용하지 않는다. 기각·폐기된 ADR도 번호를 유지한다. 아래의 예약 번호 0099를 제외한 마지막 결정 다음 번호를 쓴다.
- 이 문서(0001)가 첫 ADR이며 관례 자체를 시드한다.

각 ADR은 다음 형식을 따른다.

- 제목: `ADR NNNN. 결정 요약(명령형 또는 평서문)`
- 상태: 제안 / 채택 / 기각 / 폐기 / 대체됨(대체 ADR 번호 명시)
- 배경: 결정이 필요한 상황과 제약
- 결정: 채택한 안
- 근거: 그 안을 택한 이유
- 대안: 검토했으나 버린 안과 기각 사유
- 영향: 결정이 낳는 후속 작업·제약·비용

## 현재 구조를 읽는 곳: 0099

[0099 현재 구조](0099-current-architecture.md)는 지금 적용하는 결정을 한 번에 읽는 문서다. 여러 ADR의 결론을 현재 구조로 이어 설명하고, 대체된 결정과 남은 검증 한계를 표시한다. 0099는 이 용도로 예약한 번호이며 새 결정의 시간 순서나 마지막 번호를 뜻하지 않는다. 일반 ADR의 이력 형식 대신 현재 내용을 계속 갱신한다.

역할은 나누어 유지한다. 세부 조건은 해당 계약, 진행 상태는 [로드맵](../../ROADMAP.md), 결정의 이유와 이력은 개별 ADR이 맡는다. 0099는 이 자료를 연결하는 판단의 입구다. 계약을 복사하거나 상충하는 요구를 요약으로 덮지 않는다.

새 ADR을 추가하거나 구조·배포·검증 상태를 바꿀 때는 관련 원본과 0099를 같은 변경에서 검토한다. 현재 설명, 대체 관계, 검증 한계에 영향이 있으면 함께 고친다. 0099만 읽고 구현 완료나 검증 통과를 단정하지 않고 관련 코드와 증거를 확인한다.

`scripts/check-adr-current.ps1`은 0099의 ADR 누락, 번호 중복과 원자료 해시 변경을 검사한다. 내용의 타당성은 사람이 검토한다. 원자료와 0099를 대조한 뒤 `-PrintDigest`로 해시를 읽어 0099 말미의 `<!-- sources-sha256: ... -->`를 갱신한다. 이 옵션은 파일을 수정하지 않는다. 내용을 확인하지 않고 해시만 바꿔 검사를 통과시키지 않는다.

## 근거

- 결정 단위로 파일이 분리되어 개별 결정의 맥락을 독립 추적할 수 있다.
- 일반 ADR의 순번 단조 증가로 결정 순서를 추적할 수 있다. 0099는 현재 구조를 찾기 위한 예외다.
- 기각 대안을 명시하므로 같은 제안의 재부상 시 판단 비용이 줄어든다.
- Markdown 평문이라 CI 스타일 게이트(`scripts/check-style.ps1`)와 git 리뷰 흐름을 그대로 탄다.
- 정본 계약 문서와 역할이 다르다. 계약은 세부 구현 조건, 일반 ADR은 결정 이력의 기준이다. 상충하면 [공동 작업 절차](../../ai/workflow.md)의 정본 충돌 규칙에 따라 근거를 대조한다. ADR은 계약 변경의 이유를 남기고 0099는 현재 적용 관계를 설명한다.

## 대안

- ADR을 두지 않고 정본 문서 버전 헤더에만 이력을 남긴다. 기각. 패치 근거가 본문에 흩어져 결정 단위 추적이 안 된다.
- 커밋 메시지로만 결정을 남긴다. 기각. 커밋은 코드 변경 단위라 결정 단위와 어긋나고, 여러 커밋에 걸친 결정의 서사를 한곳에서 읽을 수 없다.
- 위키·외부 도구를 쓴다. 기각. 저장소 밖 산출물은 코드·CI와 분리되어 정합이 깨지고, 오프라인·인수인계에서 유실 위험이 있다.

## 영향

- 새 아키텍처 결정은 ADR 초안 작성 후 리뷰를 거친다. 사소한 구현 세부는 대상이 아니다. 판단 기준은 "되돌리기 비용이 크거나 여러 모듈에 파급되는가"다.
- 정본 계약 문서를 개정하는 결정은 해당 ADR에서 어느 문서 어느 절을 어떻게 바꿨는지 링크한다.
- 이 관례를 `docs/README.md` 문서 색인과 `docs/reports/프로젝트_이해하기.md`에서 참조한다.
