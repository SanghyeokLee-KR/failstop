# ADR 0028. Grafana를 기본 관제로 사용하고 별도 콘솔을 확장용으로 보존한다

- 상태: 채택
- 날짜: 2026-09-18
- 근거: 고객 서비스 중심의 관제 화면·사이드바·다크와 라이트 전환·일반 모니터의 정보 밀도 요구와, 실제 Grafana에서 구현하도록 확정한 후속 요청.

## 배경

[ADR 0027](0027-msp-operations-and-autoscaling.md)에서는 Linux 운영·DB 복구·관측·보고를 먼저 검증하고 별도 관제 UI는 이후 범위로 남겼다. 해당 로컬 기능을 검증한 뒤 사용자가 서비스·Spring·AWS·DB 화면과 운영·관리 메뉴를 하나의 디자인으로 구현하도록 요청했고, 기존 관측·인증·보고를 연결한 별도 콘솔을 만들었다. 이어 사용자는 실제 Grafana 자체를 기본 관제 화면으로 사용하도록 요청했다. 별도 화면의 구현 이력과 새 기본 접속 경로를 구분하고, Grafana 제품 소스나 안전하지 않은 표시 기능을 수정하지 않는 범위를 정한다.

## 결정

기본 접속은 기존 [Grafana MSP 네 화면](../../../deploy/observability/README.md#grafana-기본-관제-화면)으로 한다. 서비스 경로와 DB 복제는 Canvas, 관측 추이는 시계열·상태 이력, 등록 대상과 경보는 표 패널로 구성한다. 고객사·환경·기간·갱신·검색·패널 확대·계정·권한은 Grafana 기능을 사용한다. 한국어·서울 시간대·기본 홈·네 대시보드 즐겨찾기는 작업 공간 설정 도구로 적용한다. 다크·라이트 링크는 Grafana의 URL 테마 설정을 사용한다.

기존 사이드바를 유지하고 알림·데이터 소스·사용자 관리의 원본 메뉴를 연결한다. 임의 HTML·CSS 주입, Grafana 제품 소스 수정, 전체 사이드바의 별도 제품 메뉴 교체는 하지 않는다. 기본 대시보드는 파일로 생성·배포하며 원본은 [생성기](../../../deploy/observability/tests/build-msp-dashboards.py), [공통 질의](../../../deploy/observability/tests/msp_queries.py), [Canvas 구성](../../../deploy/observability/tests/msp_canvas.py)이다. 기존 Alertmanager를 데이터 소스로 연결하며 Teams 기본 알림과 보고 전송 경로는 유지한다.

앞서 만든 [별도 관제 콘솔](../../../deploy/console/README.md)은 비교·확장용으로 보존한다. 포트 53002의 선택적 컨테이너에서 정적 ES module·CSS·SVG와 같은 origin의 제한된 API를 사용한다. 저장된 사건·보고 파일·담당자 확인 이력을 연결하는 확장 화면이며 기본 Grafana 실행의 필수 요소가 아니다. 두 관제 화면 모두 [거래소 레이아웃](../contracts/데스크톱_레이아웃설계.md)의 거래 패널을 대체하지 않는다.

Prometheus는 기존 수집과 경보를 유지한다. Grafana 패널과 콘솔 API의 관제 질의는 고객·환경·역할 범위를 유지하고, AWS 관리형 지표는 Grafana CloudWatch 데이터 소스에 연결한다. 별도 콘솔 API는 임의 PromQL·URL 프록시를 제공하지 않는다. DB 실제 역할은 배치 라벨만으로 확정하지 않고 recovery 지표로 확인한다. 시계열 누락을 정상 0이나 이어진 정상 선으로 바꾸지 않으며, 로컬 운영 실습 자료를 미등록 AWS 자원으로 표시하지 않는다.

Grafana가 운영자 계정과 역할의 기준이다. 콘솔 세션은 인증된 조직을 제한하고 주기적으로 권한을 재확인한다. 사용자·데이터 소스·Grafana 대시보드 변경은 원본 관리 화면에서 해당 권한으로 수행한다. 알림 확인 기록은 콘솔의 SQLite에 두며 Alertmanager 경보 해제·mute와 구분한다.

보고 서비스는 기존 Bearer 인증 아래 고객·환경별 목록을 추가한다. 저장된 PDF·HTML만 서명 경로로 제공하고 콘솔이 인증 뒤 중계한다. 보고 조회에 AI·Teams·PDF 렌더링을 결합하지 않는다. 비밀 값과 보고 원자료 전체를 목록 API에 넣지 않는다.

## 근거와 대안

Grafana 기본 패널과 관리 기능을 사용하면 관제 화면과 실제 데이터 소스·계정의 위치가 일치한다. 참고 이미지의 배치와 밀도는 관제 정보 구성에 반영하지만 기존 제품의 메뉴 전체를 복제하지 않는다. 앞서 분리한 콘솔은 보고·확인 이력처럼 추가 API가 필요한 기능의 비교 자료로 유지한다. Grafana 제품 소스 수정은 업그레이드와 권한 유지 비용이 커 채택하지 않는다. 거래소 공개 웹에 관리 API를 붙이는 방법도 접근 경계가 달라 채택하지 않는다. 단순 정적 그림은 실제 오류·자료 공백·필터·파일 연결을 검증할 수 없어 결과물로 사용하지 않는다.

## 영향

기본 관제에는 기존 Grafana의 사설 접근·계정·권한과 파일 배포를 적용한다. 별도 콘솔을 실행할 때만 콘솔용 사설 접속·HTTPS·토큰 파일 읽기 권한과 영속 확인 기록을 추가로 관리한다. 콘솔에는 프로세스·세션·시계열·캐시 상한을 두고 서비스 중단 시 미확인 상태를 유지한다. 새 인프라를 제어하는 권한이나 자동 DB 승격은 추가하지 않는다. 선택한 Grafana 조직의 운영자가 고객 범위를 함께 조회하며 고객별 접근 권한을 격리한 멀티테넌트 제품을 주장하지 않는다. 기존 콘솔 검증과 새 Grafana 화면의 브라우저 검증, 실제 AWS 연결 완료는 각각의 실행 근거로 판단한다.
