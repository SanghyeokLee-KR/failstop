# ADR 0034. 매칭 리더십을 마켓 파티션 두 개로 나눈다

- 상태: 채택(방향) · 단계 진행 중. S0 문서는 작업 브랜치에서 끝났다. S1은 코드와 시험, 폐기용 스택의 관문 카오스(P1)를 마쳐 관문을 통과했다. S2는 코드와 시험을 마쳤고, 첫 A/B 부하 비교가 5xx 조건으로 FAIL이었으나 사용자 결정(5xx는 리더가 낸 것만 센다)으로 고친 규칙의 반복 재측정이 PASS라 폐기용 스택 관문을 통과했다. S3는 코드와 시험을 마쳤고, 폐기용 스택 재주행에서 관문 실험과 결정 5(마켓당 접수 천장 손실)가 로컬 판정으로 PASS라 S4로 넘어갔다. 결정 5의 로컬 판정과 E5·E7 사후 판정 시점 변경은 사용자 확인 대상이다. S4는 코드와 시험을 마쳤으나(서버 전체 빌드 app 834개 통과) 구현 검토 수정 뒤 폐기용 스택 재주행에서 E2가 두 번, E1이 세 번 가운데 한 번 FAIL이라 관문을 통과하지 못했다. 그 결함을 고친 보정 단계 S4b의 코드로 폐기용 스택 관문을 다시 돌려 통과했다(로컬 판정). S5는 코드와 시험을 마쳤다. 폐기용 스택 첫 주행은 라우팅 분할 실험이 판정식의 경계로, 판정식을 고친 재주행이 k6 WebSocket 결번으로 FAIL이었고, 같은 이미지의 둘째 주행에서 판정 실험이 모두 PASS라 관문을 통과했다(로컬 판정). S6(WebSocket 외부 브로커 중계)은 사용자 결정(2026-09-25)에 따라 S5와 같은 시각에 별도 브랜치 `claude/pml-s6`(기준 `9a6d2474`)에서 설계·코드·시험을 마쳤고, 같은 날 S5 위에 병합했다. 병합한 트리에서 폐기용 스택 관문(W0~W5)을 돌려, 결함 셋을 고친 셋째 이미지에서 모두 PASS라 S6 관문을 통과했다(로컬 판정). S7(P3 전환과 파티션 실험)은 사용자 결정(2026-09-25)에 따라 S6 관문과 병렬로 브랜치 `claude/pml-s7`에서 설계·코드·시험을 마쳤고 2026-09-26 작업 브랜치에 병합했다. S7 폐기용 스택 실험(Q0~Q16)은 NOT RUN이라 S7 관문은 통과하지 않았다. S4b의 DB 연결 장애 `503` 응답은 2026-09-25 사용자가 확정했다(사용자 확정(2026-09-25)). 정산 재시도 한도와 S5·S6·S7의 AI 선택은 사용자 확인 대상이다.
- 날짜: 2026-09-23 (2026-09-24 작업 브랜치로 옮기며 머리말을 고쳤고, 같은 날 사용자 결정을 반영했다. 2026-09-25 S4, S4b, S5 결과를 반영했고, 같은 날 브랜치 `claude/pml-s6`의 S6 코드 단계 결과를 반영한 뒤 그 브랜치를 병합했고 S6 관문 결과를 반영했다. 2026-09-26 브랜치 `claude/pml-s7`의 S7 코드 단계 결과를 반영한 뒤 그 브랜치를 병합했다)
- 현재 적용: 실행 중인 구조는 여전히 `resource='matching-engine'` 리스 행 하나를 쥔 단일 리더(P1)다. 작업 브랜치 `claude/per-market-leader`에는 S5까지의 코드(V48~V54, S4b는 새 마이그레이션 없음), 2026-09-25 병합한 S6 코드(새 마이그레이션 없음), 2026-09-26 병합한 S7 코드(V55)가 있다. S5는 주문 쓰기의 소유권 선검사, 마켓 힌트 헤더, 한 배치 한 마켓, 마켓 없는 일괄 취소와 회원 폐쇄의 DB 인계 표(V54), 하네스 파티션 LB 파일을 더했고 모드와 리스 자원은 바꾸지 않는다. S4 코드는 리스·게이트·승격·강등·팔로워를 파티션 단위로 돌리지만 P1·P2에서는 파티션이 `matching-engine` 하나이고 모든 마켓을 덮는다. V50을 적용해도 모드는 P1이고, 접수 시점 예약 모드(P2)는 소유자가 정지 창에서 전환 함수를 불러야 켜진다. P2 전환은 Testcontainers 일회용 DB와 로컬 Docker 폐기용 스택의 DB에서만 했다. main은 V47까지의 단일 리더다. 이 결정은 단계마다 관문 시험을 통과한 뒤에만 효력이 생긴다. 파티션 리더 모드(P3)의 앱 코드 경로는 S4에 들어왔고, S7 바이너리는 리스를 얻을 때 최고 모드 3을 넘겨 P3 DB에서도 파티션 리스를 얻는다. P3 전환(V55)은 Testcontainers 일회용 DB와 설계 단계의 폐기용 PostgreSQL 컨테이너에서만 했고, 폐기용 스택의 파티션 실험(Q0~Q16)은 돌리지 않아 P3 측정 결과는 없다(「S7 진행」). P2의 관문 주행과 처리량 측정은 폐기용 스택의 결과만 있다(「S3 진행」, 「S4 진행」, 「S4b 진행」, 「S5 진행」). WS 중계 모드의 기본값은 노드 내장 브로커(`exchange.ws.relay.mode=simple`)라 설정을 바꾸지 않으면 게시 경로가 종전과 같다. 외부 브로커 모드(`broker`)는 Testcontainers 시험과 로컬 Docker 폐기용 스택의 S6 관문 주행에서만 켰다(「S6 진행」).
- 결정자: 사용자가 2026-09-23 쓰기 분할 방식을 '앱 노드마다 일부 마켓의 매칭 리더를 맡기는 마켓별 리더'로 정했고, 로컬 Docker에서 완성·검증한 뒤 AWS에 배포하기로 했다. 자산 보존을 깨지 않는다는 조건도 사용자가 붙였다. 2026-09-24 새벽에는 대화로 결정 1(범위)을 '발표(2026-10-16) 전에 로컬 Docker에서 S6을 포함해 S7까지'로 정했고, 파티션 기능 검증 실험을 로컬 Docker의 폐기용 스택·폐기용 DB에서 하기로 했다(결정 13, 19). 같은 날 사용자는 S2~S7과 실험 전체를 AI에게 맡기며 실험까지 하라고 했고, 그래서 2026-09-23 밤 작업 범위에서 뺐던 카오스 E 시험도 폐기용 스택·폐기용 DB에서 돌리기로 바뀌었다. 결정 15의 회원 폐쇄 409(정지 마켓 미체결이 남으면 `409 orders_cancel_incomplete`)는 사용자 결정이 아니다. 2026-09-24 새벽 작업을 맡은 AI 세션이 안전한 쪽으로 고른 값이다(AI 선택(2026-09-24), 사용자 확인 필요). 나머지 「결정한 값」은 사용자가 하나씩 고른 값이 아니라 작업을 맡은 AI 세션이 [단계 계획](../architecture/마켓분할_리더_단계계획.md)의 권장 기본값으로 정한 것이고, 2026-09-24 현재도 AI 기본값이다. 사용자가 다른 값을 고르면 해당 항목과 계획을 함께 고친다.
- 번호: 이 문서의 번호 0034는 `deploy/vm-lab/databasus/04-ADR초안.md`가 적어 둔 Databasus 초안 번호와 겹친다. 그 초안은 채택하지 않았으므로 채택할 때 그 시점의 다음 빈 번호를 새로 받는다.
- S1 진행: 단일 리더 안전 보강 가운데 정산 일시 DB 오류의 제한 재시도(`TransientDbErrors`, `SettlementService`)와 주문 접수의 모호한 커밋 판정은 main `2ccc1fe`에서 V47 `V47__order_intake_failure_resolution.sql`과 함께 이미 들어왔다. 이 V47은 DB 시계(`created_at`)를 비교하지 않고 이 요청의 주문 id와 공유 표시로 판정하는 판이다. 2026-09-23 보존 태그 `wip/per-market-leader-20260923`(`f8184ef`)의 V47 `discard_orphan_idempotency_key`는 `created_at`을 비교하는 다른 판이며 가져오지 않는다. 태그에만 있던 나머지 S1(접수 락 대기 상한과 append `lock_timeout` 설정, 회원 폐쇄의 `409 orders_cancel_incomplete`, `prod-timeouts` 카오스 프로필, 정산 재시도 소진 경보)은 2026-09-24 작업 브랜치 `claude/per-market-leader`로 옮겼다. 잠금 대기 초과(55P03)를 503으로 바꾸는 응답 매핑은 결정 11에 따라 옮기지 않았다. S1 시험(`EngineBridgeAcceptLockWaitTest`, `AcceptLockTimeoutIntegrationTest`, `AcceptLockDefaultsTest`, `MemberCloseIncompleteTest`, `ProdTimeoutsProfileTest` 등)과 서버 전체 빌드는 Testcontainers 일회용 DB에서 통과했다. 같은 날 관문의 카오스 E2·E4·E5·E6·E7을 로컬 Docker 폐기용 스택에서 `prod-timeouts` 프로필(P1)로 한 번씩 돌려 모두 PASS였다(RTO 5.186~10.362초, [09-24 측정](../../measurements/20260924.md), 기록 커밋 `909af89`). 이미지는 S1 잔여와 S2 코드를 함께 담은 `b04acd5`다.
- S2 진행: 2026-09-24 작업 브랜치에 V48(`V48__market_partition_lease.sql`), 쓰기 경로 네 곳의 시장 도출 fencing, 리스 보관소의 V48 함수 호출, DynamoDB 보관소의 파티션 모드 기동 거부, 불변식 C29와 그 시험을 넣었다. 같은 날 구현 검토 다섯 건을 처리했다. 대응 뒤 서버 전체 빌드가 Testcontainers 일회용 DB에서 통과했다(app 723개, engine 67개, 합계 790개, 실패·건너뜀 0). 운영 코드에 변이를 넣어 새 P3 쓰기 경로 시험이 틀린 마켓을 잡는지도 세 회차 확인하고 되돌렸다. S2의 코드 구현은 여기서 끝났다. 같은 날 폐기용 스택의 관문 주행에서 앱 역할 로그인 종단 주행과 되돌림 주행은 PASS였다. 같은 날 A/B 부하 비교는 늘어난 5xx(모두 팔로워의 설계상 503과 nginx 502, 리더 5xx 0)가 사전 규칙의 "5xx 증가 없음"을 채우지 못해 FAIL이라 S2 관문은 통과하지 않았다. 과부하에서 S2 이미지의 접수 처리율이 main보다 약 12% 낮았고 원인은 특정하지 못했다([09-24 측정](../../measurements/20260924.md)). 같은 날 11시 사용자가 "5xx는 리더가 낸 것만 세고, 반복 측정 뒤 넘어간다"고 정해 S2 설계 6-4의 조건을 "리더 노드가 낸 5xx 증가 없음"으로 고쳤다. 15:55~16:34 KST에 A(main)와 B(`b04acd5`)를 A-B-A-B-A-B로 다시 돌린 결과, 불변식 위반 0, 리더 5xx 여섯 칸 모두 0, append 평균 증가 +0.998ms(A-A 차이 1.319ms)와 p95 증가 +2.970ms(A-A 4.380ms)로 PASS다. 접수/s는 B 평균이 A보다 6.5% 높고 범위가 겹쳐 12% 저하는 반복에서 나오지 않았다. 호스트가 조용하지 않았던 한계는 [재측정 기록](../../../harness/evidence/pml-s2-gate-rerun-20260924-1553/README.md)에 있다. V49는 V50보다 먼저 적용돼야 해서 S3의 첫 이미지에 함께 들어갔다(「S3 진행」). 구현 결과와 설계와 달라진 것, 구현 검토 대응은 [S2 설계](../architecture/마켓분할_리더_S2_설계.md) 11절에 있다.
- S3 진행: 2026-09-24 [S3 설계](../architecture/마켓분할_리더_S3_설계.md)를 쓰고 계약을 코드보다 먼저 고쳤다(DB 설계 v2.54 §3.5·§5.1, API 설계 v2.54 §2-3·§2-4·§6-E, 하네스 검증설계 C14'·C31과 판정 어휘 N/A). 계약 SQL은 폐기용 컨테이너에서 문서 원문으로 확인했다. 같은 날 작업 지시(사용자가 S2~S7 진행을 AI에 맡김)에 따라 작업 브랜치에 S3 코드와 V49·V50을 넣었다. 관문 이미지는 커밋하지 않은 작업 트리로 구웠다. 폐기용 스택 관문이 S3 이전부터 있던 결함 둘을 드러내 V51(앱 역할 로그인 검증기의 DEFAULT 파티션 잎 읽기)과 V52(획득이 `lease_until`을 행 잠금을 얻은 뒤의 시각에서 셈)를 더했다. 첫 주행의 최종 이미지로 X1~X4의 본 회차는 PASS였다. X3(E7)에 더 돌린 반복 세 회 가운데 둘은 사전 규칙의 rpo_records 0을 채우지 못해 FAIL이다(부하를 멈추지 않은 사후 판정 창이 물질화 전 NEW 1건을 센 것으로 본다). 결정 5는 단일 마켓 측정 PASS와 12마켓 600/s 측정 NOT RUN(같은 설정 칸의 잡음 n 0.485)이라 미판정이었다. 구현 검토 두 라운드 뒤 이미지를 다시 구운 재주행에서는 X1, E2·E4·E6·E7, X7이 PASS였고, E5는 첫 회가 부하 중 사후 권위 run의 C13A 1로 FAIL, 사후 run을 봇 정지·드레인 뒤로 옮긴 재주행이 PASS다(E7도 재주행 전에 같게 고쳤다). 결정 5는 12마켓(L = -0.162)과 단일 마켓(L = -0.417) 측정이 모두 PASS라 이 호스트의 판정으로 통과이고, 다음은 S4다([S3 설계](../architecture/마켓분할_리더_S3_설계.md) 12-6). 설계가 결정 6의 레거시 거부 범위를 넓히고(아래 결정 6), 결정 5의 측정에 단일 마켓 과포화 주행을 더했으며(아래 결정 5), 결정한 값 16을 확인했다. 같은 날 설계 검토 지적 아홉 건을 반영했다([S3 설계](../architecture/마켓분할_리더_S3_설계.md) 11절). 정산 배치가 원장 게시를 여러 번 하며 P2 접수 예약과 교착을 만드는 것을 폐기용 컨테이너에서 재현해, 정산이 첫 게시 직전에 잔고 행을 한 번에 오름차순으로 잡는 잠금 계획을 더했다. 전환 뒤 외부 보관소의 첫 게시가 퇴역 이력과 겹치던 결함, P2 빠른 거부와 재전송의 인터리빙, 감사 문장의 누적 행 비용도 고쳤다. 같은 날 병행 작업이 커밋한 관문 기록(`909af89`)에서 S2 관문은 A/B의 5xx 조건으로 통과하지 않았다. 설계는 그 판정이 정리된 뒤 S3 코드를 시작한다고 적었으나, 사용자가 S2~S7 진행을 AI에 맡겨 판정 정리(5xx를 어디까지 셀지의 사용자 확인, 약 12% 처리율 차이의 원인) 없이 S3 코드를 진행했다. 두 가지는 여전히 남아 있다. 같은 날 S3 구현 검토 두 라운드를 처리했고, 대응 뒤 서버 전체 빌드는 app 771개·engine 67개가 실패·건너뜀 없이 통과했다. - S4b 진행: 2026-09-25 S4 관문을 막은 결함을 고치는 보정 단계로 [S4b 설계](../architecture/마켓분할_리더_S4b_설계.md)를 쓰고 계약을 코드보다 먼저 고쳤다(DB 설계 v2.56 §3의 V47 행·§5.4·§5.4-c·§5.5·§6.4, API 설계 v2.56 §2-3·§2-4·§2-5-b·§2-5-c·§4-B-3·§4-B-6·§6-C·§6-E, 하네스 검증설계 S4b 패치 노트, 하네스 CI/CD §5-2). 같은 날 설계 검토 10건과 구현 검토 2건을 처리했다. 바꾼 것은 다섯이다. 판정 없이 끝난 재생(DB 접근 실패, 일시 오류, 리더 자격 상실)은 `recovery_runs`에 불일치로 적지 않고, 스냅샷 폴백은 획득 실패와 연결 끊김일 때 생략한다. 진짜 내용 불일치는 종전대로 `matched=false`다. 주문 접수의 DB 연결 장애는 V47 판정마저 DB에 닿지 못할 때만 `503` + `Retry-After`('재조회 후 판단 필요')이고 멱등 키를 남기며, 판정이 된 경우는 마켓 접수 경합과 같은 `429`·`409` 규칙이다. 연결이 끊긴 판정을 다시 부를 때는 키를 지우지 않는다. 인증 필터의 DB 연결 장애와 게이트를 닫은 노드의 fencing 거부도 `503`이고, 컨트롤러 계층의 연결 장애 `503`은 안전 메서드와 재전송 안전 표식을 단 주문·이체 처리기로 한정한다. 참여 끄기와 재구성 완료의 경합은 참여 여부와 후보 표식을 승격 조율의 상태 락 하나로 묶어 닫았다. 라이터 치명은 강등 기록과 로그에 SQLSTATE와 원인 사슬을 남긴다. 하네스의 `orders_500_0`은 LB 로그·프로메테우스 `max_over_time`·노드 누계 세 원천으로 보고, X7 칸 값은 k6 창의 저널 행 수로 셈한다. 새 마이그레이션은 없다. 폐기용 스택(P2, 파티션 하나)은 세 이미지로 돌렸다. 첫 이미지에서 E2 다섯 번이 모두 PASS였고 E1 다섯째가 S4의 E1 FAIL을 재현했다. 원인은 PG 지연 아래 정산이 잠금 대기 초과(55P03)를 거듭해 재시도 한도(4회·5초)를 넘긴 것이라, 한도를 8회·15초로 늘렸다(결정한 값 11). 다시 구운 이미지에서 E1 세 번, X1, E2, E4~E7, 콜드 재기동이 PASS였다. 구현 검토 보정(V47 재확인의 키 삭제)까지 넣은 셋째 이미지(09:40~11:13 KST)에서는 X1과 접수 경합 a~d, E2 다섯 번 연속, E1 다섯 번, E4(합류 포함)·E5·E6·E7·콜드 재기동이 모두 PASS였다(RTO 5.143~12.196초, 콜드 재기동의 첫 체결 12.225초, 불변식 위반 0, 구 epoch 쓰기 0, 세 원천의 주문 `500` 0, `recovery_runs` 불일치 0). 그래서 S4 관문을 이 호스트의 판정으로 통과했다. 이 판의 서버 전체 빌드는 app 870개가 실패·건너뜀 없이 통과했고 engine 67개는 `--rerun`으로 통과했다(Testcontainers 일회용 DB). 재생 도중 DB가 끊기는 분기와 V47 재확인이 판정을 내는 경로는 스택에서 나지 않아 시험과 변이로만 확인했다. X7 처리량은 호스트가 조용하지 않아 NOT RUN이다. 결과와 남은 것은 [S4b 설계](../architecture/마켓분할_리더_S4b_설계.md) 12~16절, 원자료는 [09-25 측정](../../measurements/20260925.md)이다. S4b 변경은 2026-09-25 문서 단계에서 브랜치에 한 커밋으로 남겼다. 같은 날 사용자가 S4b의 DB 연결 장애 응답(`500` 대신 `503` + `Retry-After` + '재조회 후 판단 필요', 멱등 키와 예약은 V47 규칙대로 보존)을 확정했다(사용자 확정(2026-09-25)).
- S5 진행: 2026-09-25 [S5 설계](../architecture/마켓분할_리더_S5_설계.md)를 쓰고 계약을 코드보다 먼저 고쳤다(DB 설계 v2.57 §3의 V54 행·§3.9·§3.2-a-5·§5.4-c 8·§5.4-d, API 설계 v2.57 §2-3·§2-5·§2-5-d·§3-3·§3-4·§4-B-1·§4-B-2·§4-B-3·§4-B-6·§6-E, 하네스 검증설계 S5 패치 노트와 §3 LB 배선, 하네스 CI/CD §3-3·§5-2). 같은 날 설계 검토 12건과 구현 검토 3건을 처리했다. 들어간 것은 이렇다. 바디 상한 필터 바로 뒤, 수용 제한·IP 버킷·인증 앞의 소유권 선검사 필터(`MarketRoutingFilter`)가 그 마켓 파티션의 접수 게이트를 열지 않은 노드의 주문 쓰기를 nonce·레이트리밋·멱등 키·예약을 건드리기 전에 `503` + `Retry-After: 1` + `X-Exchange-Route: not-owner`로 돌려보낸다. 마켓은 서명된 값(주문 바디, 일괄 취소 쿼리)을 먼저 보고 없을 때 서명 밖 힌트 헤더 `X-Exchange-Market`을 본다. 웹의 주문 생성·취소, 봇(`BotApiClient`), k6 부하 도구가 힌트를 싣고, 힌트가 요청의 마켓과 다르거나 둘 이상이면 `400`이다. 배치 주문은 한 마켓만 받는다(`400 batch_single_market`). 마켓 없는 일괄 취소와 회원 폐쇄는 게이트를 열지 않은 파티션의 주문을 새 인계 표 V54(`order_cancel_requests`)로 소유 노드의 작업자에게 넘기고 최대 5초 기다린다. 작업자는 자기 리스가 유효할 때만 행을 점유·완료하고, 끝나지 않은 행은 5분 뒤 만료로 닫힌다. V54는 작업 지시를 담는 표라 쓰기 권한 판정에 쓰이지 않는다. 인증 키 조회와 주문 접수 전 읽기는 연결 끊김이면 다른 연결로 한 번 더 읽는다. 하네스는 기존 `harness/nginx/nginx.conf`를 그대로 두고 파티션 업스트림 둘을 만드는 `harness/nginx/nginx.partition.conf`를 compose 변수 `CHAOS_LB_CONF`로 고른다(1차 `max_fails=2`). 조회 역할 노드의 라우팅은 바꾸지 않았다. 서버 전체 빌드는 구현 검토 대응 뒤 app 930개가 실패·건너뜀 없이 통과했고(engine 67개는 `--rerun`, Testcontainers 일회용 DB), 관문 시험 16개 클래스 58 사례와 변이 27개(모두 새 단언이 실패), 웹 시험 534개·빌드·토큰 게이트, 하네스 단위 시험 339개와 18개가 통과했다. 폐기용 스택(P2, 파티션 하나)은 같은 이미지로 두 번 돌렸다. 첫 주행(15:19~16:47 KST)은 선검사 무부작용, 힌트·배치 거절, 인계와 관리 폐쇄, 기본 LB와 파티션 LB의 E4, 파티션 LB의 E7·E2가 PASS였다. 그러나 라우팅 분할 실험(Z1)이 판정식의 경계에서 한 줄 차이로 FAIL, 판정식을 고친 재주행이 k6 WebSocket orderbook 결번 4건으로 FAIL이라 관문을 통과하지 못했다. 둘째 주행(17:54~18:57 KST)에서는 판정 실험이 모두 PASS였다. Z1은 주행 전에 정한 괄호 판정식과 설계의 본래 판정식이 모두 참이었고 k6 결번은 0이었다. 그래서 S5 관문을 이 호스트의 판정으로 통과했다. 불변식 위반, 구 epoch 쓰기, 주문 `500`, `recovery_runs` 불일치는 두 주행의 모든 실험에서 0이다. 첫 주행의 결번은 S5 이미지와 S4b 이미지의 k6 각 네 번에서 재현되지 않아 원인을 모르고, S6에서 먼저 잰다. B1 재기록(Z6)은 두 주행 모두 측정 두 회이고, 리더 `503` 두 건이 같은 파티션 업스트림에 몰리면 그 파티션이 약 2초 `502`인 것을 봤다. 라이터 치명의 7~9초는 S5가 바꾸지 않았다. `partition_pending`, 인계 작업자의 이어 하기·재점유·만료, 두 파티션에 걸친 폐쇄는 스택에서 나지 않아 시험과 변이로만 확인했다. 설계 10절의 AI 선택 열한 가지, 코드 단계의 AI 추가 결정, Z1의 괄호 판정식, 원인을 모르는 첫 주행 결번을 두고 관문 판정을 받아들일지는 사용자 확인 대상이다. 결과는 [S5 설계](../architecture/마켓분할_리더_S5_설계.md) 12절, 원자료는 [09-25 측정](../../measurements/20260925.md)이다. S5 변경은 2026-09-25 문서 단계에서 브랜치에 한 커밋으로 남겼다.
- S6 진행: 2026-09-25 사용자가 S6을 S5와 동시에 별도 작업 트리에서 진행하기로 정해, 브랜치 `claude/pml-s6`(기준 S4b 커밋 `9a6d2474`)에서 [S6 설계](../architecture/마켓분할_리더_S6_설계.md)를 쓰고 계약을 코드보다 먼저 고쳤다(API 설계 v2.58 §0-2·§1·§4-A-2·§4-A-4·§4-C-1·§5-1·§5-2·§5-5·§5-6, DB 설계 v2.58 §4.1, 하네스 검증설계 S6 패치 노트와 §3, 하네스 CI/CD §3-1·§5-2·§5-6·§7-1). 같은 날 설계 검토 14건과 구현 검토 8건을 처리했다. 구현한 것은 이렇다. 브라우저 세션마다 브로커 연결을 여는 세션 단위 중계(계약 §5-1 (A)안의 Spring `enableStompBrokerRelay`) 대신, 각 앱 노드의 내장 브로커가 자기 세션을 맡고 노드끼리 외부 STOMP 브로커(RabbitMQ 4.3 STOMP 플러그인)의 토픽 하나로 게시를 주고받는 노드 단위 중계를 넣었다. 폐기용 컨테이너 확인에서 세션 단위 중계는 브로커 메모리가 세션 수에 비례했고(세션당 약 0.65MiB) 브로커가 없으면 모든 WS 세션이 끊겼기 때문이다. 소유 노드는 쥔 파티션마다 짧은 간격의 하트비트(처음 1초, 관문 주행 뒤 200ms)를 보내고, 쥐지 않은 노드는 그 하트비트와 노드별 호가·티커 미러로 호가·티커 REST와 구독 스냅샷에 답하며 조건을 채우지 못하면 DB 집계와 `seq: 0`을 낸다. WS 게이트는 모든 마켓의 게시를 줄 수 있는 노드만 WS를 받게 해, 기본 모드(`simple`)에서도 다른 노드가 유효한 리스를 쥔 파티션이 있는 노드는 핸드셰이크를 `503`(`relay_required`)으로 거절하고, 브로커 모드에서 중계가 끊긴 노드는 세션을 1013으로 닫는다. 브로커가 멈춰도 REST와 쓰기 경로는 중계를 기다리지 않는다. 웹은 전역 epoch 비교를 마켓별 epoch 표로 바꿔 작은 epoch를 버리고 오른 마켓만 재동기화하며, 브로커 모드의 비공개 채널 seq 도메인은 user × market이고 myAsset과 계좌 조회에 잔고 판 `version`을 싣는다. 하네스 중계 오버레이(`harness/docker-compose.relay.yml`), 배포 엣지의 `/ws/` 전용 upstream, 실험 실행기와 판정 규칙 초안(`harness/evidence/pml-S6-gate-draft/`)은 파일로만 준비했고 띄우지 않았다. 새 마이그레이션은 없다. 실제로 실행해 확인한 것은 다음과 같다. 서버 전체 빌드는 구현 검토 대응 뒤 app 183개 클래스 929개가 실패·건너뜀 없이 통과했다(engine 67개는 바뀌지 않아 앞선 결과, Testcontainers 일회용 DB와 `rabbitmq:4.3.6-alpine` 브로커 컨테이너). 경합·시각 시험은 `--rerun`으로 세 번 더 통과했고, 웹 시험 567개, 하네스 파이썬 시험 345개, `nginx -t`, `promtool` 규칙 시험이 통과했다. 돌연변이 대조(웹 여섯, 서버 일곱)에서 의도한 시험이 실패하는 것을 보고 되돌렸다. 브로커 메모리와 nginx 재시도 동작은 폐기용 컨테이너로 확인했다([확인 기록](../../../harness/evidence/pml-s6-probe-20260925/README.md)). 폐기용 스택 관문 W0~W5는 코드 단계에서 NOT RUN이었고 S5를 병합한 트리에서 돌렸다(아래 관문 주행). '그 마켓만 재동기화'와 두 파티션 수신의 스택 판정(W6·W7)은 P3이 필요해 S7 관문으로 넘겼다. 설계를 맡은 AI가 정한 열세 항목은 사용자 확인 대상이다([S6 설계](../architecture/마켓분할_리더_S6_설계.md) 10절). 결과와 남은 것은 그 문서 12절이다. S6 변경은 2026-09-25 문서 단계에서 브랜치 `claude/pml-s6`에 한 커밋(`30c2d4c6`)으로 남겼고, 같은 날 이 브랜치의 S5 커밋(`3071a7c2`) 위에 병합했다. 두 브랜치가 같은 v2.56을 기준으로 계약 판 v2.57을 매겼으므로 병합하며 S6의 판을 v2.58로 옮겼다(내용은 그대로). 병합 때 겹친 곳과 S5 파티션 LB 파일과 S6 중계 LB 파일의 조합은 [S6 설계](../architecture/마켓분할_리더_S6_설계.md) 13절에 있다. 같은 날 병합한 트리에서 폐기용 스택 관문 W0~W5를 돌렸다([기록](../../../harness/evidence/pml-S6-20260925-1954/README.md), S6 설계 14절). 첫 이미지에서 브로커 멈춤(W3)·메모리 경보(W4) 때 팔로워가 발행이 멈춘 지 1~2초 뒤 리더보다 뒤처진 호가를 `seq`≠0 기준점으로 냈다. 5초에 하트비트 3개라는 조건이 발행이 멈춘 뒤 약 3초 더 참이었기 때문이라, 비소유 노드는 가장 최근 하트비트가 400ms 안일 때만 미러를 쓰고 하트비트 간격을 200ms로 줄였다. 둘째 이미지에서는 브로커 정지(W2) 뒤 연결 재개가 16.5초(판정 15초)라 재연결 상한을 10초에서 3초로 줄였고, 그 판의 서버 빌드가 드러낸 결함(STOMP `CONNECTED` 전에 닫힌 연결 시도를 끊김으로 알려 `link_down`이 켜지지 않던 것)도 고쳤다. 셋 다 자산·멱등·펜싱 경로를 바꾸지 않고, 시험을 더해 서버 전체 빌드(app 994개)를 통과했다. 셋째 이미지에서 W0~W5가 모두 PASS라 S6 관문의 스택 판정을 로컬 판정으로 통과했다. 판정 도구의 보정 여덟 가지(판정 값은 그대로)와 세 기본값은 AI가 정했고 사용자 확인 대상이다. S5 첫 주행의 WebSocket 결번은 구독 즉시 스냅샷이 내장 브로커의 구독 등록보다 먼저 카운터를 읽는 경합으로 보이며(이 주행에서 1건 관찰, 추정), 이 주행에서는 고치지 않았다. 2026-09-26 S7을 병합한 뒤 계약(API 설계 §5-2 '스냅샷을 읽는 시점')을 먼저 고치고, 스냅샷을 내장 브로커의 구독 등록 뒤에 읽고 중계 수신이 미러를 먼저 갱신하게 고쳤다. 재현 시험에서 구독 사건 시점의 대조군은 결번을 냈고 고친 경로는 0이었다. 스택 재측정은 S7 관문에서 한다([S6 설계](../architecture/마켓분할_리더_S6_설계.md) 15절).
- S7 진행: 2026-09-25 사용자가 S7 설계·구현을 S6 관문 실험과 병렬로 진행하기로 정해, 브랜치 `claude/pml-s7`(기준 S5·S6 병합 커밋 `d46d5073`)에서 [S7 설계](../architecture/마켓분할_리더_S7_설계.md)를 쓰고 계약을 코드보다 먼저 고쳤다(DB 설계 v2.59 §3의 V55 행·§3.5·§3.10·§4.1·§4.4·§5.4-c·§5.4-e·§6.4, API 설계 v2.59 §0-2·§6-C, 하네스 검증설계 S7 패치 노트, 하네스 CI/CD §2-1·§3-1·§3-3·§5-2·§6-3). 같은 날 설계 검토 14건을, 2026-09-26 구현 검토 7건을 처리했다. 들어간 것은 이렇다. V55가 전환 함수에 2->3과 확인 인자를 요구하는 3->2를 더하고, 선행 조건을 한 줄씩 내는 함수 `leader_protocol_blockers`(정산되지 않은 NEW, 명령 대역 래치와 대역 잎, 마켓 대응·카운터·파티션 리스 행, FEE_INCOME 샤드 0·1, `app_role`의 리스 UPDATE·저널 INSERT 없음)와 모드와 무관하게 늘 두는 FEE_INCOME 샤드 1 계정을 만든다. 바이너리는 획득 때 최고 모드 3을 넘기고(`LeaseResources.MAX_PROTOCOL`) 게이지 `exchange.leader.protocol.max`로 낸다. 모드의 권위는 DB라 P1·P2 DB에서는 동작이 같다. 불변식은 C22'(P3 구간의 시간 축 팔을 파티션별로 보고 전환 뒤 옛 구간 epoch로 쓴 행을 세는 구간 경계 팔)와 C30(P3 epoch 행의 획득 자원과 그 마켓 파티션의 대조)을 앱 enum과 하네스 SQL에 넣었다. 하네스에는 P3 오버레이(`harness/docker-compose.p3.yml`), 파티션 LB와 중계 LB를 합친 `harness/nginx/nginx.partition-relay.conf`, 전환 도구의 P3 전환·되돌리기, 실험 실행기와 판정기, 관문 실행기 `s7-p3-gate.ps1`, 발표 재현용 `s7-p3-demo.ps1`, 실험 초안([`harness/evidence/pml-S7-gate-draft/`](../../../harness/evidence/pml-S7-gate-draft/README.md))을 파일로 준비했다. 명령 대역 래치는 전환 도구에 인자를 준 경우에만, 폐기용 스택 가드 안에서만 건다(결정 9). 실제로 실행해 확인한 것은 Testcontainers 일회용 DB의 서버 관문 시험(전환과 선행 조건, 되돌리기, 수수료 샤드, 두 노드 파티션 분담, 교차 노드 이중 지출 1,000회, 전환 경계의 옛 epoch 쓰기 차단, 운영 배선의 P3 획득)과 변이 대조, 서버 전체 빌드(app 211개 클래스 1,010개가 실패·오류·건너뜀 없이 통과, engine 67개는 바뀌지 않아 앞선 결과), 하네스 파이썬 시험 469개(합친 LB 파일의 설정 시험 포함), 배포 시험 14개, 웹 시험 570개와 웹 빌드·토큰 게이트다. PostgreSQL·nginx·compose 동작은 설계 단계에 폐기용 컨테이너로 확인했다([확인 기록](../../../harness/evidence/pml-s7-probe-20260925/README.md)). 폐기용 스택 실험 Q0~Q16(E12, E4, E7, 되돌리기 실제 수행, E5·E2·E6, 수수료 행 결합, 수동 인계, 한 마켓 치명, 콜드 재시작 선호 배정, P2·P3 처리량, WS 중계의 두 파티션 수신)은 S6 관문 뒤에 메인 세션이 돌리므로 NOT RUN이고, 그래서 S7 관문은 통과하지 않았다. 브라우저 게이트와 원격 CI도 돌리지 않았다. 설계 머리의 스무 항목, 코드 단계 12-2의 열 항목, 구현 검토에서 AI가 고른 웹 관찰 브라우저 대체와 P3의 리더 전환 대본 중단은 사용자 확인 대상이다. 결과와 남은 것은 [S7 설계](../architecture/마켓분할_리더_S7_설계.md) 12·13절이다. S7 변경은 2026-09-26 문서 단계에서 브랜치 `claude/pml-s7`에 한 커밋(`7886b1b4`)으로 남겼고, 같은 날 S6 관문 기록 뒤의 작업 브랜치(`2f4fd1f7`)에 병합했다. 병합하며 S6 관문 보정(판정 창의 시작을 관찰자 기동 시각으로, 합류 뒤 미러 신선도를 합류 시각부터)을 W6 판정기와 실행기에도 옮겼고, S6 관문 수정의 하트비트·미러 신선도·재연결 값이 합친 LB 파일과 W6 판정의 중계 불능 축과 겹치지 않는 것을 코드로 대조했다([로드맵](../../ROADMAP.md) 「2026-09-26 S7 병합」).
- 2026-09-24 사용자 결정 가운데 이 ADR의 구현 범위 밖인 것: 관리 콘솔의 서비스 흐름 화면(`/admin/flow`)을 채택해 실제 값과 연동하고 발표 실험을 그 화면에서 하기로 했다. 상담에서 이 화면에 AI를 넣으라는 조언을 들었고, 사용자는 AGENTS.md의 'AI가 운영 조치를 직접 실행하지 않는다' 규칙을 바꿀 예정이다. 자동 모드가 아니면 AI는 조치안을 제시하는 방식이다. 규칙은 아직 바뀌지 않았으므로 현재는 기존 규칙을 따른다. 두 항목의 진행은 [로드맵](../../ROADMAP.md)에서 관리한다.
- 대체 범위: 각 항목은 적은 단계부터 효력이 있다. 그 전까지는 원래 ADR의 문장이 현재 동작을 설명한다.
  - [ADR 0002](0002-db-leader-lease-single-writer.md) 결정 절의 마켓별 리스 분할 금지(docs/reference/adr/0002-db-leader-lease-single-writer.md:29)와 대안 절의 마켓별 `leader_lease` 행 기각(같은 파일:53). P3 전환(S7)부터다.
  - [ADR 0022](0022-market-partitioned-command-journal.md)의 전역 `acceptGate`(docs/reference/adr/0022-market-partitioned-command-journal.md:379, 10-7 :1067-1069)와 9절 2·3의 노드 단위 재적재·강등 전제(같은 파일:895-896). 파티션 단위 Java(S4)부터다.
  - ADR 0022 6-2의 "C22 시간 축 팔을 마켓 안 팔로 대체하지 않는다"(같은 파일:547)와 10-8(:1071). P3 구간에서만 뒤집는다. P1·P2 구간의 판정은 그대로다.

- 유지하는 결정: ADR 0002의 "강등 시 리스 즉시 반납 기각"(0002:56). 파티션 인계도 TTL 만료로만 한다. DB 자동 페일오버는 선택·구현하지 않았다는 전제와 "매칭 엔진·DB를 ASG로 자동 확장하지 않는다"는 규칙(AGENTS.md)도 유지한다. 노드 수는 2로 고정하고 자동 증감하지 않는다.

## 배경

지금은 `leader_lease`의 `resource='matching-engine'` 한 행을 쥔 JVM 하나가 12개 마켓을 모두 쓴다(V1__init.sql:693-706). ADR 0022가 그 JVM 안의 접수 락과 채번을 마켓별로 나눴지만 리스와 승격 단위는 노드 하나로 남겼다(0022:379, :895-896).

리스를 둘로 나누는 데 가장 큰 걸림돌은 리스가 아니라 자금이다. 권위 있는 차감인 `reserve_funds`는 저널 커밋, 곧 ACK 뒤의 정산 트랜잭션에서 일어난다(SettlementService.java:43-46). ACK 전의 잔고 확인은 게이트웨이의 사전 가드와 JVM 메모리의 in-flight 누계(`InflightReserves`)가 맡는다. 코드 주석이 이 장치를 "단일 노드 전제"라고 적었다(OrderGateway.java:28-32, InflightReserves.java:13-14).

두 JVM이 서로 다른 마켓에서 같은 사용자의 같은 자산을 동시에 쓰면 두 주문이 모두 가드를 통과해 ACK된다. 늦게 정산되는 쪽이 `chk_balance_nonneg`(V1__init.sql:112-120)에 걸려 23514로 실패한다. 라이터는 어떤 sink 예외든 fatal로 처리하고(SingleWriterLoop.java:226-244) 노드를 강등한다(LoopFatalHandler.java:28-31). 명령은 이미 저널에 있으므로 다음 소유자가 재적재해도 같은 자리에서 실패하고 그 마켓은 영구히 멈춘다(0022:476). 원장 합과 CHECK는 DB가 지키므로 C01·C02는 깨지지 않는다. 대신 ACK 계약과 C13A, 가용성이 깨진다. 그래서 자금 예약의 권위를 DB로 옮기지 않은 채 리스만 나누는 안은 받아들일 수 없다.

## 결정

1. 파티션은 두 개로 고정한다. `leader_lease`에 `matching-p0`, `matching-p1` 두 행을 새 마이그레이션이 미리 넣는다. 마켓과 파티션의 대응은 추가 전용 표 `market_lease_partition(market_id PK → markets, resource → leader_lease)`에 둔다. 배정 값은 아래 「결정한 값」 3이다. UPDATE·DELETE·TRUNCATE는 V44의 `journal_cutover`처럼 트리거로 거부한다. 이 판에서는 마켓을 다른 파티션으로 옮기지 않는다. 마켓을 추가하면 기존 시드 트리거(V40:161-169, V36:87-89) 옆의 SECURITY DEFINER 트리거가 대응 행도 같이 넣는다. 대응이 없는 마켓은 쓰기가 거부된다.
2. 선호 소유자는 app-1이 p0, app-2가 p1이다. 선호는 힌트이고 권위는 리스 획득 하나뿐이다. 비선호 파티션은 부팅 직후 2×TTL, 그 뒤에는 만료를 볼 때마다 1×TTL을 기다린 뒤에만 획득을 시도한다. 한 노드가 죽으면 살아 있는 노드가 TTL 만료 뒤 두 파티션을 모두 쥔다. 자동으로 되돌려 주지 않는다. 되돌리기는 운영자가 정지 절차로 하고 리스는 반납하지 않고 만료시킨다(ADR 0002:56 유지).
3. epoch는 모든 리스 행과 획득 이력을 통틀어 한 번씩만 쓴다. 새 획득 함수와 CREATE OR REPLACE한 2인자 `try_acquire_leader`는 리스 행을 만료 조건으로 잠근 뒤 `leader_protocol` 행을 잠가 획득·게시·전환을 한 줄로 세우고, `max(leader_lease.epoch, lease_acquisitions.epoch) + 1`을 배정해 추가 전용 `lease_acquisitions(epoch PK, resource, holder, protocol, origin, acquired_at)`에 한 행을 남긴다. 그러면 epoch는 파티션 사이에서 유일하고 배정 순서대로 커지며, P1에서는 오늘처럼 승격마다 정확히 1 오른다. 이 유일성은 DB 타임라인 하나 안에서만 성립한다. 2026-09-23 초안은 전역 시퀀스(`leader_epoch_seq`)와 `GREATEST(nextval, epoch + 1)`이었다. 2026-09-24 [S2 설계](../architecture/마켓분할_리더_S2_설계.md)의 PostgreSQL 확인에서 시퀀스 값이 롤백, 행 잠금 재평가, 크래시 복구 때 건너뛰어 P1의 "승격마다 +1"을 깨고, `GREATEST`가 행 쪽 값을 고르면 시퀀스가 뒤처져 이력 PK가 충돌할 수 있어 바꿨다. 이 변경은 사용자 확인 대상이다.
4. 쓰기 권한 검사는 DB가 기록할 행의 `market_id`에서 리스 행을 찾는다. 앱은 resource를 넘기지 않는다. 함수 `lease_resource_for_market(market_id)`는 프로토콜 P3이면 대응 표의 값을, 그 전이면 `'matching-engine'`을 돌려준다. 저널 append는 market_id를 한 번만 바인딩하는 INSERT…SELECT로 바꾼다(지금은 CommandJournalAppender.java:35-44에서 resource를 하드코딩한다). 정산 머리말, 스냅샷 저장, 이벤트 저널 시험 경로도 같은 도출을 쓴다. 판정 함수는 V41처럼 행을 조건 없이 FOR KEY SHARE로 잠근 뒤 판정한다(V41__lease_key_share_lock.sql:32-52 형태).
5. 자금 예약은 저널 append 트랜잭션 안에서 한다. 새 머리말 함수는 순서대로 다음을 한다. 리스 행 KEY SHARE와 리더 판정, NEW 멱등 판정(V44:50-66 그대로), 예약액 계산과 `reserve_funds`, 채번, 예약 기록 `order_reservations` INSERT다. 예약액은 checksum이 덮는 payload 값과 카탈로그 scale로 DB가 계산하고, 앱이 넘긴 값은 대조에만 쓴다. 잔고가 부족하면 23514로 트랜잭션 전체가 롤백되어 저널 행과 채번이 남지 않고, 게이트웨이는 400 `insufficient_funds`를 돌려준다. 정산은 예약된 주문에 대해 `reserve_funds`를 다시 부르지 않고 `order_reservations.amount`를 권위로 쓴다.
6. 모드 전환은 DB의 단일 행 `leader_protocol`과 추가 전용 이력으로 한다. P1은 오늘과 같다. P2는 단일 리더에 시장 도출 fencing과 접수 시점 예약을 켠 상태다. P3은 파티션 리더다. 전환 함수는 소유자 계정만 실행하고, 정지 창에서만 부른다. 함수는 먼저 모든 리스 행을 FOR UPDATE로 잠가 진행 중인 쓰기가 끝나기를 기다린다. 그 뒤에 선행 조건을 검사하고, 모든 리스 행을 새 epoch로 퇴역시켜 이전 모드의 쓰기를 펜싱한다. P2 이상에서는 2인자 레거시 함수가 거부하거나 NULL을 돌려준다. 앱 설정은 참여 허용 스위치일 뿐이고 모드를 정하지 않는다(0022:17과 같은 원칙). 2026-09-24 [S3 설계](../architecture/마켓분할_리더_S3_설계.md) 4-6이 거부 범위를 S2 바이너리의 3인자 획득과 S2 이전 바이너리의 2인자 게시로 넓혔다. 두 바이너리도 P2의 예약 정산을 몰라 P2 리더가 되면 예약을 다시 걸거나(23505) 거부 주문의 예약을 풀지 않는다. 획득과 게시는 바이너리가 아는 최고 모드를 인자로 받는다. 이 수정은 사용자 확인 대상이다.
7. 게이트, 승격, 강등, 팔로워, 좀비 판정을 파티션 단위로 바꾼다. 부팅은 늘 팔로워로 시작하고 승격 경로는 런타임 경로 하나로 통일한다. 복구 대상은 획득한 파티션의 마켓 M(P)로 한정하고, 대상 밖 샤드를 빈 엔진으로 덮는 코드(WriterRouter.java:125-132)는 지운다. 팔로워 엔진은 마켓별 인스턴스로 나눈다. 파티션 fatal은 그 파티션만 멈추고 fresh 재구성으로 팔로워에 복귀시키며, 반복 fault에는 차단기를 둔다. VM Error만 노드 전체 강등으로 남긴다.
8. 노드 사이의 잠금 결합이 강등으로 번지지 않게 한다. 정산은 55P03, 57014, 40P01, 40001을 제한 재시도한다. 재시도 제한을 넘긴 일시 오류와 재시도 대상이 아닌 오류는 종전처럼 fatal이다. 후자는 fencing 거부와 무결성 위반, 커밋 여부를 알 수 없는 연결 오류(08xxx), 계약 위반(`IllegalStateException`)이다. 예약 단계에는 짧은 `lock_timeout`을 걸어 초과를 503으로 돌린다. 2026-09-24 [S4 설계](../architecture/마켓분할_리더_S4_설계.md) 4-12·4-13이 이 응답을 바꿨다. 폐기용 nginx에서 리더의 503 한 건이 모든 마켓의 쓰기를 1초 넘게 502로 만들었기 때문에, 접수 경합은 이 요청이 접수되지 않았음이 확정된 경우 `429`(`bucket=market`), 그 밖은 `409 order_in_progress`로 내고 인그레스는 바꾸지 않는다(AI 선택, 사용자 확인 필요). 앱 역할의 `idle_in_transaction_session_timeout`을 TTL 이하로 둔다. P3 이후의 체결 수수료는 파티션별 FEE_INCOME 샤드로 나눈다(지금은 K=1 박제, SettlementService.java:50-52).
9. 라우팅은 서버 안전성의 근거가 아니다. 잘못 보낸 요청은 503이나 fencing 거부로 끝난다. 웹과 봇은 `X-Exchange-Market` 힌트를 보내고 nginx는 파티션별 upstream 두 개로 보낸다. 서버는 인증 필터보다 앞에서 소유권을 검사해 비소유면 nonce·레이트리밋·멱등키·예약을 건드리기 전에 503과 Retry-After를 낸다. WebSocket은 외부 STOMP 브로커 릴레이가 필요하다. 이 릴레이는 S6에서 넣는다(결정 13). S6을 마치기 전까지 파티션 모드는 봇과 REST 부하 시험에만 쓴다.

## 결정한 값

계획이 코드 전에 정하라고 남긴 20개 항목의 값이다. 번호는 [단계 계획](../architecture/마켓분할_리더_단계계획.md)의 "결정 N"과 같다.

1. 범위. 사용자가 2026-09-24 대화로 정했다. 2026-10-16 발표 전에 로컬 Docker에서 S7까지 끝내고, S6(WebSocket 외부 STOMP 브로커 릴레이)도 포함한다. 순서는 2026-09-23에 정한 대로 로컬 Docker에서 완성·검증한 뒤 AWS에 배포하는 것이다(S8, 결정 19). 2026-09-23 초안의 AI 기본값('발표 전 S0·S1, 여유가 있으면 S2, S3 이후는 발표 뒤')은 폐기했다. 단계 계획의 공수 추정(76~112인일, 추론)은 남은 날짜보다 크므로 일정 위험은 그대로 남는다. 발표에서는 실제로 관문을 통과한 단계까지만 말한다.
2. 목적. 앱 노드 하나가 죽어도 다른 파티션의 마켓은 계속 접수하게 하는 가용성과, 앱 CPU를 두 노드에 나누는 것이다. 처리량 증가는 기대하지 않는다. 측정된 병목이 DB 커밋이기 때문이다(아래 근거 절).
3. 마켓 배정. 명시적인 정적 표로 둔다. 파티션은 p0(선호 app-1)과 p1(선호 app-2) 두 개다. 봇이 도는 세 마켓(application.yml:326-340)은 두 파티션이 모두 봇 부하를 받도록 나눠 KRW-BTC(1)와 KRW-XRP(4)는 p0, KRW-ETH(2)는 p1에 둔다. 나머지 아홉 마켓은 market_id 순서로 p1부터 번갈아 둔다. 그러면 p0은 1·4·5·7·9·11(BTC, XRP, DOGE, TRX, DOT, AVAX), p1은 2·3·6·8·10·12(ETH, SOL, ADA, LINK, MATIC, ATOM)로 여섯 개씩이다. id와 심볼은 InitialMarketCatalog.java:34-45를 따른다. S2 마이그레이션이 이 표를 시드한다.
4. 인계. TTL 만료로만 한다(ADR 0002:56 유지). 자동으로 선호 노드에 되돌려 주지 않는다. 재배치는 운영자가 정지 절차로 한다. 비선호 노드의 파티션 참여를 끄고 그 리스가 만료된 뒤 선호 노드가 획득하게 한다.
5. 마켓당 접수 천장 손실. S3에서 같은 날 같은 스택으로 P1과 P2를 재서 20퍼센트 이하이면 받아들인다. 넘으면 대안의 2단계 예약안을 고르고 S4로 넘어가지 않는다. 2026-09-24 [S3 설계](../architecture/마켓분할_리더_S3_설계.md) 4-17은 측정을 둘로 정했다. 아래 검증 절의 600/s 주행 비교와, 마켓 하나에 부하를 모은 단일 마켓 과포화 주행(요청률 300/s 고정)의 접수율 비교다. 600/s 주행에서는 마켓 하나의 접수 락 점유가 낮아 예약이 늘리는 락 보유가 드러나지 않기 때문이다. 첫 판은 두 번째 측정을 요청률 사다리의 천장으로 적었으나, 같은 날 검토에서 단 간격이 20퍼센트 판정보다 거칠다는 지적을 받아 연속값인 과포화 접수율로 바꿨다. 둘 다 20퍼센트 이하여야 받아들인다. 이 수정은 사용자 확인 대상이다. 2026-09-24 S3 재주행에서 두 측정이 모두 PASS였다(12마켓 L = -0.162, 단일 마켓 L = -0.417, 로컬 Docker 단일 호스트, [S3 설계](../architecture/마켓분할_리더_S3_설계.md) 12-6). P2 칸 사이 차이가 크고 호스트에 다른 프로그램이 돌았으므로 이 로컬 판정으로 확정할지도 사용자 확인 대상이다.
6. 예약 기록. `order_reservations` 표를 쓴다.
7. 예약액 계산. DB가 계산한다. 필요한 자산·마켓 scale 열의 위치는 S2에서 확인하고, 없으면 새 마이그레이션으로 카탈로그에 scale 열을 더한다. 적용된 Flyway 파일은 고치지 않는다.
8. P2에서 P1로 되돌리기. 정지 창에서 미정산 NEW가 0건일 때만 허용한다. 이 조건이 안전하다는 것을 시험 R1으로 확인하기 전에는 비가역으로 취급한다.
9. 명령 대역 래치. 폐기용 Docker DB에만 건다. 학교와 개인 AWS DB는 사용자가 승인한 뒤에 판단한다.
10. 수수료 계정. P3부터 FEE_INCOME을 파티션별 샤드로 나눈다.
11. 타임아웃과 재시도. 앱 역할의 `idle_in_transaction_session_timeout`을 리스 TTL 이하로 둔다. 학교 DB 설정은 지금 10초(deploy/linux/postgresql/exchange.conf:35)이고, 리스 TTL은 기본 10초·카오스 6초다(application.yml:140-141 주석). 정산은 55P03·57014·40P01·40001을 제한 재시도한다. S1에서 정한 재시도 제한은 첫 시도를 포함해 4회이고, 첫 시도 시작부터 5초가 지나면 새 시도를 열지 않으며, 대기는 50~100, 100~200, 200~400밀리초의 무작위 값이다(DB 설계 §5.4 v2.51). 2026-09-25 S4b 폐기용 스택의 E1(PG 지연) 다섯 번 가운데 한 번에서 정산이 잠금 대기 초과를 두 번 만나 7.3초 만에 이 한도를 넘겨 라이터가 치명으로 끝났다(S4 첫 E1 FAIL의 재현). 그래서 한도를 첫 시도 포함 8회, 첫 시도부터 15초, 대기 50~100·100~200밀리초 뒤 200~400밀리초로 늘렸다(DB 설계 §5.4 v2.56, [S4b 설계](../architecture/마켓분할_리더_S4b_설계.md) 4-6·13절). 한도를 넘기면 여전히 치명이다. 이 값은 AI 선택이고 사용자 확인이 필요하다. 접수 경로의 마켓 락 대기 상한(`exchange.engine.accept-lock-wait`)과 append 트랜잭션의 `lock_timeout`(`exchange.engine.accept-lock-timeout`)은 S1에서 설정만 넣고 기본값을 0(끔)으로 둔다. 락 대기 상한을 켜면 초과한 요청 하나가 503을 받고, `max_fails=1`인 nginx 업스트림(harness/nginx/nginx.conf:21, deploy/nginx-edge.conf.template:54-55)이 그 503으로 노드를 2초 빼 한 마켓의 정체가 모든 마켓의 쓰기 중단으로 번진다. 그래서 값은 줄 머리 막힘을 실제로 끊어야 하는 S3·S4에서 인그레스 설정과 함께 정한다. 같은 이유로 잠금 대기 초과(55P03)를 `ApiExceptionHandler`·`ApiAuthFilter`에서 503으로 바꾸는 매핑과, 게이트웨이 접수·취소 경로에서 일시 DB 오류를 per-item 503으로 바꾸는 처리도 S1에서 넣지 않고 S3·S4 과제로 둔다. 그때까지 append `lock_timeout`을 켜면 초과한 요청은 `500 server_error`를 받는다(API 설계 v2.52). 2026-09-24 S4에서 두 값을 `accept-lock-wait` 2000ms, `accept-lock-timeout` 1000ms로 dev·prod에 켰다(코드 기본값 0은 그대로). 주문 생성·취소의 접수 경합은 503이 아니라 `429`나 `409`로 끝나 인그레스의 `max_fails`·`proxy_next_upstream`은 바꾸지 않았다. 주문 생성·취소 밖 경로의 55P03은 `500` 그대로 두고 503 매핑은 S5에서 파티션별 업스트림과 함께 다시 본다([S4 설계](../architecture/마켓분할_리더_S4_설계.md) 4-12, 10절의 1·2·6, AI 선택, 사용자 확인 필요). 2026-09-25 S4 재주행의 E2에서 접수 경로의 롤백 실패(`TransactionSystemException`)와 인증 필터의 08xxx 연결 오류가 `500`으로 나가는 것이 드러났다. 게이트웨이 경로의 일시 DB 오류 처리가 이 둘을 덮지 못했다(S4 설계 13-2·13-3). 같은 날 S4b가 DB 연결 장애의 응답을 정했다. 주문 접수는 V47 판정마저 DB에 닿지 못할 때만 `503`과 `Retry-After: 1`이고 멱등 키를 지우지 않으며, 판정이 되면 접수 경합과 같은 `429`·`409`다. 인증 필터의 연결 장애는 `503`이고, 컨트롤러 계층의 연결 장애 `503`은 안전 메서드와 재전송 안전 처리기(주문, 이체)로 한정해 멱등 키가 없는 쓰기의 연결 끊김은 `500`으로 둔다. 이 `503`이 `max_fails=1` 업스트림에서 리더를 약 2초 빼는 비용은 폐기용 스택에서 쟀다(API 설계 v2.56 §2-5-c, [S4b 설계](../architecture/마켓분할_리더_S4b_설계.md) 4-3·4-4·13·15절). 이 응답 규칙은 AI가 고른 값이었고 2026-09-25 사용자가 확정했다(사용자 확정(2026-09-25)). 같은 날 S5는 인증 키 조회와 접수 전 읽기의 한 번 더 읽기, 하네스 파티션 업스트림 1차의 `max_fails=2`로 이 비용을 줄였다. 폐기용 스택에서 리더 `503` 한 건은 흡수됐으나 같은 파티션에 두 건이 몰린 회차는 약 2초 `502`였다([S5 설계](../architecture/마켓분할_리더_S5_설계.md) 4-6, 12-4, 12-7, AI 선택, 사용자 확인 필요). 주문 생성·취소 밖 경로의 55P03 매핑은 S5 설계가 다루지 않아 `500` 그대로다.
12. 파티션 fatal. 그 파티션만 멈추고 fresh 재구성으로 팔로워에 복귀시킨다. 같은 fault가 반복되면 차단기가 막는다. 차단기의 횟수와 시간 창은 S4에서 정한다. 2026-09-24 S4 설계 4-7이 10분 창 안의 파티션 강등 3회로 정했다(`exchange.leader.partition.demotion-window`, `max-demotions`). 세는 사유는 `WRITER_FATAL`, `LEASE_LOST_WHILE_ACCEPTING`, `STALL`, `PROMOTION_LOOP_DOWN`이고, 차단은 `/actuator/partitions`의 해제나 재기동이 푼다. 재구성 실패는 세지 않는다(AI 선택, 사용자 확인 필요). 차단기 열림은 Testcontainers의 P3 흉내 시험(`PartitionFatalIsolationTest`)으로만 확인했다.
13. WebSocket. 외부 STOMP 브로커 릴레이를 S6에서 채택한다. 2026-09-23 초안은 S6을 보류했으나 사용자가 2026-09-24 결정 1의 범위에 S6을 넣었다. S6을 마치기 전까지 파티션 모드는 REST와 봇 부하에만 쓴다. 브로커를 둘 노드와 자원 한도는 S6 착수 때 정한다. 2026-09-25 [S6 설계](../architecture/마켓분할_리더_S6_설계.md)가 다음처럼 정했다(AI 선택, 사용자 확인 필요). 중계는 세션 단위가 아니라 노드 단위이고 브로커는 RabbitMQ 4.3의 STOMP 플러그인이다. 같은 모양에서 Artemis보다 메모리가 절반 이하였다(80~125MiB 대 129~253MiB, 이 PC Docker의 짧은 표본). 설정 기본값은 종전 노드 내장 모드 `simple`이라 main과 학교의 게시 경로를 바꾸지 않는다. 조회 노드(app-3)는 WS를 받지 않는다. AWS에서는 bot-1 동거를 기본으로 하되 systemd `MemoryMax=320M`, 메모리 경보 수위 192MiB로 묶고, S8에서 봇·관측·보고와 함께 1시간 돌리는 동안 bot-1의 가용 메모리 최솟값 400MiB 이상, 커널 OOM 종료 0, 브로커 경보 0, 중계 유실 0을 채우지 못하면 별도 소형 노드(0.5GiB)로 옮긴다. 학교는 앱 노드가 하나라 브로커를 두지 않는다. v6 구성도의 '위치 미정'에 넣을 문장은 그 문서 4-18에 있다.
14. nonce와 레이트리밋. 둘 다 노드 로컬로 둔다. 노드를 넘는 NEW 재전송은 client_order_id 멱등이 막는다. 레이트리밋 한도는 S5에서 다시 본다. 2026-09-25 S5가 다시 봤다. 한도 값은 바꾸지 않고 nonce와 함께 노드 로컬에 둔다. 선검사가 소유하지 않는 노드의 주문 쓰기를 인증 전에 돌려보내므로 마켓을 찾는 요청은 소유 노드에서만 인증·차감된다. 두 노드가 파티션을 하나씩 쥔 P3에서는 두 파티션에 걸쳐 주문하는 계정의 실효 한도가 계약값의 최대 두 배다. S5의 인계 때문에 마켓 없는 일괄 취소를 다른 노드로 다시 보낸 서명 요청이 효과를 내게 됐는데, DB nonce 등록으로 막지 않고 인그레스의 힌트 없는 경로를 1차 고정으로 두어 좁힌다(API 설계 v2.57 §2-5·§3-4, [S5 설계](../architecture/마켓분할_리더_S5_설계.md) 4-7, AI 선택, 사용자 확인 필요).
15. 마켓 없는 cancelAll. 서버가 파티션별로 나눠 보낸다. 관리 경로의 취소도 같다. 한 파티션이 응답하지 못했을 때의 응답 계약은 S5에서 API 설계에 먼저 적는다. 회원 폐쇄(`close`)에서 정지 마켓의 미체결 주문이 남으면 폐쇄를 완료로 처리하지 않고 `409 orders_cancel_incomplete`를 낸다. 이 방침은 사용자가 정한 것이 아니라 2026-09-24 새벽 작업을 맡은 AI 세션이 태그 판의 동작을 유지하는 쪽으로 고른 값이다(AI 선택(2026-09-24), 사용자 확인 필요). 폐쇄를 완료로 덮지 않는 쪽이 안전하다고 봤다. 작업 브랜치의 S1 코드와 [API 설계](../contracts/백엔드_API_설계.md) v2.53 §6-E는 반대로, 저널에 닿지 못한 503만 미완료로 세고 정지 마켓의 `422 market_suspended`는 `200`에 남겼다(2026-09-23 main 규칙). S3에서 API 설계 v2.54 §6-E를 먼저 고친 뒤 코드와 시험(`MemberCloseIncompleteTest`, `OrderGatewayMarketHaltIntegrationTest`)과 웹의 409 표시를 맞췄다. 사용자가 다른 규칙을 고르면 이 항목을 먼저 고친다. 사용자 확인 항목은 [로드맵](../../ROADMAP.md) 인계에 남겼다. 2026-09-25 S5가 한 파티션이 응답하지 못했을 때의 계약을 API 설계 v2.57 §4-B-3·§6-E에 먼저 적고 구현했다. 요청을 받은 노드는 게이트를 연 파티션의 주문을 직접 취소하고, 그 밖은 V54 인계 표로 소유 노드에 넘겨 최대 5초 기다린다. 소유 노드가 기다림 안에 시작하지 않은 몫은 `partition_not_started`(포기로 표시해 아무것도 하지 않음), 시작했으나 끝내지 않은 몫은 `partition_pending`, 소유 노드의 예기치 않은 오류는 `server_error`로 원소별 결과에 적고 일괄 취소는 `200`이다. 회원 폐쇄는 이 세 사유를 미완료로 세어 `409 orders_cancel_incomplete`다. 엔진을 끈 관리 평면에서 폐쇄의 취소가 모두 저널 전에 거부되던 결함도 이 인계로 고쳤다. 이 규칙은 AI 선택이고 사용자 확인 대상이다([S5 설계](../architecture/마켓분할_리더_S5_설계.md) 4-4, 10절의 4·5).
16. C14'의 출금 항. 출금이 LOCKED를 쥐는 `transfer_requests` 상태 집합(V14__transfer_requests.sql:29-30)을 확인한 뒤 더한다. 2026-09-24 S3 설계 2-4에서 확인했다. 지금 흐름에서 잠금을 쥔 상태는 WITHDRAW·REQUESTED 하나이고(PENDING·FAILED는 만들지 않는다), C14'는 그 합을 더한다. 개정 전 C14는 대기 출금이 있는 계정을 위반으로 셌다.
17. `leader_lease` 직접 UPDATE 권한. S2에서 함수가 모든 경로를 덮은 뒤 app_role에서 회수한다(V1__init.sql:805). 2026-09-24 S2 설계에서 지금 함수로 덮이지 않는 경로 셋을 찾았다. 앱 append의 `FOR KEY SHARE`(행 잠금 절도 UPDATE 권한을 요구한다), 호출자 권한인 리스 함수들, `PostgresLeaderLeaseStore.release`의 직접 UPDATE다. 그래서 V48에서 이 경로를 소유자 권한 함수로 옮기고 대응 트리거 함수까지 PUBLIC EXECUTE를 회수한 뒤, 회수는 별도 마이그레이션 V49로 한다. 같은 날 설계 검토를 반영해 V49는 `command_journal` 직접 INSERT도 회수하고, S2 이미지가 아니라 S2 관문을 통과한 뒤의 다음 이미지에 넣는다. V48만 적용된 구간을 만들어 S2 이미지를 S2 이전 이미지로 권한 조치 없이 되돌릴 수 있게 하려는 것이다. V49는 앱과 봇 로그인이 함께 속한 app_role 안의 권한 경계가 아니며, 봇 전용 역할 분리는 별도 과제다([S2 설계](../architecture/마켓분할_리더_S2_설계.md) 4-7). 이 순서와 범위도 사용자 확인 대상이다.
18. DynamoDB 리스 공급자. 파티션 모드에서는 쓰지 못하게 막는다. P1·P2에서는 쓸 수 있다. 2026-09-24 S3 설계 검토에서 P2 전환 뒤 이 공급자의 첫 두 게시가 다른 리스 행의 퇴역 이력과 겹쳐 거부되는 것을 찾았다. 전환이 `matching-engine` 행을 마지막에 퇴역시키고 토큰 하한을 리스 행과 획득 이력의 최댓값으로 읽게 고쳤다(S3 설계 4-7, AI 선택, 사용자 확인 필요).
19. 검증 장소. 로컬 Docker에서 먼저 하고 개인 AWS에서 다시 한다. 학교는 P1로 유지한다. 학교에서는 2026-09-20 실행 범위에서 앱 이중화를 학교 허용 뒤로 미뤘고 추가 앱 인스턴스를 만들지 않았다([로드맵](../../ROADMAP.md)의 2026-09-20 실행 범위 문단). 마켓별 리더를 학교 app-2와 개인 계정 중 어디서 검증할지는 사용자가 아직 정하지 않았다. 파티션 기능 검증 실험은 로컬 Docker의 폐기용 스택과 폐기용 DB에서 한다(2026-09-24 사용자 결정). 2026-09-23 밤 작업 범위에서 뺐던 카오스 E 시험도, 사용자가 2026-09-24 S2~S7을 맡기며 실험까지 하라고 해서 같은 폐기용 스택·폐기용 DB에서 돌린다. 보존하기로 한 `chaos-pgdata` 볼륨과 main 스택의 DB에는 새 마이그레이션과 전환 함수를 적용하지 않는다.
20. 문서. 이 ADR, 0002·0022의 대체 표시, 0099, DB·API·하네스 계약의 해당 절을 고친다. AGENTS.md의 "단일 리더 매칭 엔진" 문구는 이번에 고치지 않고 사용자에게 물은 뒤 정한다. 0099와 로드맵은 2026-09-24 작업 브랜치에서 S2까지의 상태로 고쳤고, 같은 날 S3 구현 검토 뒤 S3까지의 상태로, S3 재주행 뒤 그 결과로 다시 고쳤다. 2026-09-25 S4 재주행 뒤 S4까지의 상태로, S4b와 S5 뒤 각 단계까지의 상태로 다시 고쳤다. 같은 날 브랜치 `claude/pml-s6`의 문서 단계에서 S6 코드 단계의 상태(관문 미실행)를 더했고, 그 브랜치를 병합하며 두 서술을 합쳤다.

## 근거

- 두 노드의 append가 같은 잔고 행을 다투면 `post_ledger_transaction`이 잔고 행을 account_id 오름차순 FOR NO KEY UPDATE로 잠그고 한 문장 UPDATE로 차감한다(V38__ledger_balance_update_index_scan.sql:98-127). 뒤에 온 트랜잭션은 앞 트랜잭션의 커밋을 기다린 뒤 최신 값에서 계산해 CHECK(V1__init.sql:112-120)에 걸린다(추론, READ COMMITTED 재평가. 격리 수준을 바꾸는 설정은 찾지 못했다). 노드를 가리지 않는 판정 지점이 DB의 한 곳이 된다.
- 체결 정산의 음수 leg는 매도자와 매수자의 LOCKED뿐이다(SettlementService.java:446-456). 주문별 상한은 `orders.locked_amount >= 0`(V1__init.sql:173)이다. 접수 시점에 LOCKED가 채워져 있으면 정산 시점 23514는 버그가 없는 한 도달하지 않는다(추론, 시험으로 고정). 그러면 마켓 사이 정산 순서가 음수 잔고와 무관해져 0022:476-491의 "한 노드가 전 마켓 크래시 창을 병합 재적재" 전제가 자금 측면에서 필요 없어진다.
- 출금도 `reserve_funds`를 직접 부르므로(TransferService.java:94-97, 299-306) 같은 CHECK에서 판정된다. 단일 리더에서도 열려 있던 "가드 통과 → 출금 → 정산 23514" 경로가 닫힌다.
- resource를 앱이 넘기면 두 노드가 같은 마켓의 파티션을 다르게 알 때 각자 다른 리스로 통과하는 조용한 split-brain이 된다. DB가 기록할 행의 market_id에서 찾으면 이 경우가 구조적으로 없다.
- 리스 행마다 KEY SHARE가 따로 걸린다. `uq_leader_lease_fencing_key(resource, holder, epoch)`가 이미 resource를 포함하므로(V41:27) "승격은 그 행의 진행 중 쓰기를 기다린다"는 논증(V41:7-11)이 파티션 행마다 독립으로 성립한다.
- 주문 멱등은 노드를 넘어도 유지된다. client_order_id가 필수이고(OrderGateway.java:83-86) 어드바이저리 락과 저널 조회가 공유 DB에서 마켓 없이 돈다(V44:50-66, 0022:381-386).
- 전역 시퀀스 epoch는 C22와 하네스의 epoch 집계가 파티션 사이 값 충돌 없이 동작하게 하고, `lease_acquisitions`로 "이 epoch는 어느 파티션의 것인가"를 사후에 증명할 수 있게 한다.
- 파티션을 2개로 둔 이유. 노드가 둘이면 마켓 12개 리스는 이득 없이 틱·승격 단위·할당량 규칙만 늘린다. 검토에서 할당량 규칙이 파티션을 무기한 무소유로 남기는 경우를 찾았다.

기대 효과는 가용성과 앱 CPU 분산이다. 앱 노드 하나가 죽어도 다른 노드가 쥔 마켓은 계속 접수하고, 평소에는 두 노드가 마켓을 나눠 매칭한다. 처리량은 늘지 않는다. 병목이 DB 커밋이기 때문이다. 185/s에서 DB CPU 238.5%, api-1 143.5%였고(harness/evidence/accept-concurrency-20260913/README.md:121, :137), 대역 래치 뒤 214.12/s에서 커밋 1회가 5.756ms였다(docs/measurements/20260914.md:62-66). 두 노드는 같은 프라이머리에 커밋하고 주문당 DB 일은 줄지 않는다. 이 수치는 모두 단일 리더의 로컬 Docker 측정이며 파티션 모드의 값이 아니다.

## 대안

- 리스만 나누고 InflightReserves를 유지한다. 기각. 배경의 영구 벽돌 경로가 그대로 열린다.
- 예약을 잔고 행 SELECT … FOR UPDATE로 확인만 한다. 기각. 차감이 기록되지 않아 직렬로 들어온 두 노드가 모두 통과한다.
- 2단계 예약(락 밖 별도 트랜잭션에서 예약, 락 안에서 확정, 회수기). 보류. 접수 락 보유 증가가 결정 5의 한도를 넘을 때만 고른다. 커밋이 하나 늘고 상태와 회수기가 필요하다.
- 접수 때 orders PENDING 행을 만든다. 선택지로 남긴다. C14를 바꾸지 않아도 되지만 정산의 INSERT가 UPDATE로 바뀐다.
- 마켓 1:1 리스 12행과 할당량 기반 동적 배정. 기각. 노드 둘에서는 이득이 없고 무소유 기아 경로가 생긴다.
- 앱 설정 파일로 파티션 맵을 둔다. 기각. 노드 사이 맵 불일치가 조용한 split-brain이 된다.
- 즉시 반납(`release_partition`)으로 인계 시간을 줄인다. 보류. 0002:56의 불변을 깨고, 반납 뒤 판정을 통과한 append가 새어 나오는 경로를 따로 막아야 한다.
- JVM 내부 전달이나 클라이언트 직접 라우팅. 기각. 요청 스레드를 원격 대기로 묶거나 노드 토폴로지를 외부에 드러낸다.
- nonce 공유 저장소. 기본안에서 제외. 503 재시도가 모두 401이 된다. NEW는 coid 멱등으로 이미 replayed가 된다.

## 불변식

지키는 것과 새로 거는 것을 나눈다. 라이브 강제는 DB 제약과 fencing이고, 아래 검사는 그 백스톱이다.

- C01·C02(InvariantCheck.java:19-26): 바꾸지 않는다. 파티션 시험의 1차 판정이다.
- C05, C23, C27, C28: 바꾸지 않는다. 대역과 seq 축이다.
- C13A(InvariantCheck.java:148): 정의를 유지한다. 하네스 드레인 판정은 두 노드 모든 파티션의 큐와 정산이 비었는지로 바꾼다.
- C14를 C14'로 바꾼다(InvariantCheck.java:160). LOCKED 잔고 = 열린 주문의 `locked_amount` 합 + 아직 정산되지 않은 예약의 합이다. 미정산은 `NOT EXISTS (SELECT 1 FROM event_emission_registry r WHERE r.source_cmd_seq = res.command_seq)`로 판정한다. 정산은 끝났는데 orders 행이 없는 예약은 누수로 센다. 대기 중 출금의 LOCKED 항은 결정 16에 따라 상태 집합을 확인한 뒤 넣는다. 열 이름은 `ledger_transactions.business_event_type`, `ledger_entries.transaction_id`, `accounts(owner_type, owner_id, purpose, asset_id, shard)`다(V1__init.sql:93-105, 270-287).
- C22를 C22'로 바꾼다(InvariantCheck.java:292). 마켓 안 팔은 그대로 둔다. 시간 축 팔은 프로토콜 이력으로 구간을 나눠 P1·P2 구간은 지금처럼 전역으로 보고, P3 구간은 파티션별로 본다. P3 구간의 마켓 사이 split-brain 탐지는 C30이 대신한다.
- 신규 C29_MARKET_PARTITION_MAP(CRITICAL, SCHEDULED): 대응 행이 없는 마켓 수와 리스 행이 없는 resource 수. 2026-09-24 S2 설계에서 `leader_protocol` 행이 한 개가 아니면 1을 더하는 항을 붙였다. 술어는 하네스 검증설계 §4-1에 있다.
- 신규 C30_FENCING_RESOURCE_MATCH(CRITICAL, AUTHORITATIVE_ONLY): P3 epoch로 기록된 command_journal, event_journal, trades, snapshots 행 중 `lease_acquisitions.resource`가 그 행 마켓의 파티션과 다른 건수.
- 신규 C31_RESERVATION_LINK(CRITICAL, SCHEDULED): 원장 RESERVE 거래가 없거나 금액·계정이 다른 예약, 예약 표식이 있는데 예약 행이 없는 NEW, 저널에 없는 예약 행의 합. 2026-09-24 [S3 설계](../architecture/마켓분할_리더_S3_설계.md) 4-12가 비용 때문에 범위를 바꿨다. 앱은 C31을 권위 run 한정(AUTHORITATIVE_ONLY)으로 마켓마다 최근 5,000건 창만 보고, 전수 판은 하네스 SQL(`invariants.sql`, `summary.sql`)과 복원 점검이 맡는다. 돈에 닿는 결과의 상시 감시는 C14'와 정산 23514 경보가 한다. 이 수정은 사용자 확인 대상이다.
- 운영 지표: 정산 23514 건수는 0이어야 하고 1 이상이면 경보다. 오래된 미정산 예약의 나이도 경보로 본다.

## 검증

아래는 계획한 시험이다. 2026-09-25 현재 실행한 것은 S1~S5의 단위·통합 시험(Testcontainers 일회용 DB)과 로컬 Docker 폐기용 스택의 S1~S5 관문 주행, 그리고 S6의 단위·통합 시험(Testcontainers 일회용 DB와 브로커 컨테이너)이다. S6의 스택 실험은 실행하지 않았다. 아래 교차 노드 이중 지출과 파티션 카오스는 P3(S7) 시험이라 실행하지 않았다. S3는 같은 JVM의 두 마켓으로 단일 리더 이중 지출(출금 섞기 포함)을 1,000회 돌렸고, P2의 카오스와 처리량은 폐기용 스택에서 쟀다(머리말 「S3 진행」). 파티션 모드의 측정값은 없다.

- 핵심 시험은 교차 노드 이중 지출이다. 같은 사용자 U의 KRW available=X에서 p0 마켓과 p1 마켓에 각각 X짜리 매수를 장벽 동기화로 1,000회 동시에 넣는다. 매 회 201 하나와 400 하나, 정산 23514·라이터 fatal·강등 0, C01·C02·C13A·C14'·C22'·C30·C31 0이어야 한다. 출금 동시 경합, 한쪽 노드 pause, 같은 coid의 교차 마켓 동시 전송(409와 replayed만 허용) 변형을 함께 돈다.
- 오래된 리더: 다른 파티션 리스로 쓰기 0행, 전환 중 진행 중이던 이전 모드 쓰기 0행, 레거시 2인자 함수 거부, fencing 주입 시험을 3인자 판으로 옮긴 뒤 양성 대조로 주입이 실제 거부를 낳는지 확인한다(PromotionStandDownIntegrationTest.java:697-711, V30:23-24).
- 카오스는 prod 타임아웃 프로필로 돈다. 카오스 스택의 기본값은 dev 프로필이라 기본 풀에 lock_timeout이 없어(application.yml:100-112) 교차 노드 잠금 결합이 강등으로 번지는 실패를 재현하지 못한다. prod 기본 풀에는 `lock_timeout 2000ms`가 있다(application.yml:191). S1이 넣은 `prod-timeouts` 프로필을 `CHAOS_SPRING_PROFILES`로 켜면 같은 세션 상한으로 돈다(harness/README.md).
- 가용성 판정에는 양성 축을 둔다. 한 파티션 소유자를 kill할 때 다른 파티션 마켓의 ACK 간격 최대가 기준선보다 1초 넘게 늘지 않아야 한다. 영향받은 파티션의 RTO는 단일 모드 실측 범위(5.277~10.507초, docs/measurements/20260914.md:41-45)와 비교한다.
- 처리량은 같은 날 같은 스택에서 P1·P2·P3의 600/s 주행을 비교하고 접수 락 보유와 커밋 지연을 함께 기록한다. P1과 P2의 비교가 결정 5의 판정 근거다. S3 설계가 여기에 단일 마켓 과포화 주행 비교를 더했다(결정한 값 5).

## 되돌리기

- S1, S2: 앱 롤백이 자유롭다. S2의 새 함수는 P1에서 오늘과 같은 결과를 내고, S2 이미지에는 V48만 들어 있어 S2 이전 이미지로 권한 조치 없이 돌아간다(2026-09-24 S2 관문의 되돌림 주행이 확인했다). S3 이미지에 V50~V52와 함께 들어간 V49(권한 회수) 뒤에 S2 이전 바이너리로 돌아가려면 소유자가 먼저 `GRANT UPDATE ON leader_lease TO app_role`과 `GRANT INSERT ON command_journal TO app_role`을 한다. 옛 append의 `FOR KEY SHARE`와 직접 INSERT가 그 권한을 요구하기 때문이다. V49 이미지에서 S2 이미지로 돌아갈 때는 필요 없다. V48과 V49를 한 번에 적용하는 배포(로컬에서 검증한 이미지를 AWS DB에 처음 올리는 경우)에서는 S2 이전 바이너리로 돌아갈 때 이 GRANT가 항상 선행 조건이다.
- P2 전환 뒤: 구 바이너리는 레거시 함수 거부로 리더가 될 수 없다. P2에서 P1로 되돌리기는 결정 8의 조건에서만 한다. 과거 예약 주문의 정산 경로는 두 갈래를 영구히 유지한다.
- P3 전환 뒤: 소프트 롤백은 한 노드만 두 파티션에 참여하도록 설정하는 것이다. 자원 형태가 오늘과 같아진다. 하드 롤백은 P3→P2 전환 함수로 하며 정지 창에서 모든 파티션 게이트를 닫고 비운 뒤에만 한다. 전환이 모든 리스 행을 퇴역시키므로 데이터 이관은 없다. 수수료 샤드는 P3 구간의 행만 파티션 샤드를 쓰고, P2로 돌아가면 새 행은 샤드 0으로 돌아간다(추론).
- 명령 대역 래치(V44)는 되돌릴 수 없다(0022:17). P3의 선행 조건이며 결정 9에 따라 폐기용 Docker DB에만 건다.

## 영향

- 개정할 문서: 0099의 현재 구조와 역할 문장 "리더·팔로워를 서로 다른 EC2"(docs/reference/adr/0099-current-architecture.md:39)는 P3 전환 때 고친다. DB 설계 §5.1, API 설계 §5-1·§5-2, 하네스 검증설계의 C14'·C22'·C29~C31은 해당 단계 코드보다 먼저 고친다. AGENTS.md의 "단일 리더 매칭 엔진" 문구는 결정 20에 따라 사용자에게 물은 뒤 고친다.
- 하네스: 'matching-engine' 직접 참조 5곳(e2-db-cut.ps1:85, e3-redis-outage.ps1:26-27, e5-net-partition.ps1:122-140, e7-gray-pause.ps1:110-125, adr0022-stage7-cold-restart.ps1:164)과 `Get-FirstTradeSql`(harness/scripts/lib.ps1:269)의 epoch 비교, `harness.failover_runs`의 resource 열.
- 발표 화면: 사용자가 2026-09-24 서비스 흐름 화면(`/admin/flow`)을 채택해 실제 값과 연동하고 발표 실험을 그 화면에서 하기로 했다. 이 화면의 구성도는 마켓별 리더 구현과 함께 파티션 두 개로 바꾼다. 연동과 AI 조치안 표시는 이 ADR의 단계에 들어 있지 않으며 별도 작업이다.
- 운영: 학교 진입점은 app-1 nginx 하나다(deploy/linux/app/nginx-https.conf:60-83). 파티션을 해도 app-1이 죽으면 외부 진입이 끊긴다. 개인 AWS에서 ALB를 쓰면 ALB는 503을 재시도하지 않는 것으로 알려져 있어(추론) ALB 뒤에 nginx 계층이 필요하다.
- 비용: 예약이 접수 락 안으로 들어와 락 보유와 ACK 지연이 늘어난다. reserve_funds 실측 1.444ms와 2.6ms는 V38 이전 값이다(harness/evidence/ledger-post-v27-20260906/README.md:31, harness/evidence/counter-20260907/README.md:68). 정산과 같은 잔고 행을 다투면 더 늘 수 있다.

## 확인하지 못한 것

- (2026-09-24 확인) PostgreSQL 동작 셋은 [S2 설계](../architecture/마켓분할_리더_S2_설계.md) 3절에서 폐기용 컨테이너(PostgreSQL 17.10)로 확인했다(harness/evidence/pml-s2-pg-probe-20260924/). INSERT…SELECT의 `FOR KEY SHARE OF l`은 파생 표와 함께 쓸 수 있다. EvalPlanQual 재평가는 SET 절 nextval을 다시 계산하고 대기 전 값을 버린다. 기다리는 FOR UPDATE 앞으로 새 KEY SHARE가 들어간다. 스탠바이 승격 뒤의 시퀀스 값과 앱 코드 경로는 확인하지 않았다.
- (2026-09-24 확인) 예약액 계산의 scale은 `assets.scale`(V1__init.sql:29)에 있고 `markets`는 `base_asset_id`·`quote_asset_id`(V1__init.sql:40-41)로 닿는다. 결정 7의 새 scale 열은 필요 없다. Java `setScale(s, UP)`과 같은 NUMERIC 식은 S3 시험으로 고정한다.
- (2026-09-24 확인) 출금이 LOCKED를 쥐는 상태 집합은 REQUESTED 하나다([S3 설계](../architecture/마켓분할_리더_S3_설계.md) 2-4).
- FEE_SHARD 변경이 follower catch-up의 샤드 배정 동일성에 주는 영향(SettlementService.java:51 주석).
- 두 노드에서 정산 교착 빈도, V38 이후 reserve_funds 실비용, 파티션마다 틱을 돌릴 때 리스 풀 크기.
- Spring user destination 브로드캐스트 요건, nginx 전원 퇴출 동작, ALB 503 비재시도. 2026-09-25 S6 설계가 세 가지를 좁혔다. 노드 단위 중계는 사용자 메시지를 각 노드의 `convertAndSendToUser`로 보내므로 user destination 방송이 필요 없다. nginx는 업그레이드 전 `503`을 다른 노드로 넘기고 그 노드를 `fail_timeout` 동안 뺀다는 것과, 재시도 목록의 응답이 같은 upstream 블록의 조회 분산으로 번진다는 것을 폐기용 nginx 1.29.8로 확인했다(S6 설계 3절 N1·N2). 두 노드가 모두 빠지는 `502`와 ALB 비재시도는 여전히 추론이다.
- (2026-09-24 확인) 기존 통합 시험 넷(CrashWindowReinjectionOrderTest, PromotionRecoveryIntegrationTest, FollowerRejoinIntegrationTest, BandModeFailoverIntegrationTest)은 S4 코드에서 호환 생성자 없이 통과했다. `PromotionRecoveryIntegrationTest`에는 사례와 단언을 더했다([S4 설계](../architecture/마켓분할_리더_S4_설계.md) 12-2, 13절 C11). 파티션 틱 두 개와 리스 풀 2의 갱신 지연은 `RenewUnderBlockedAcquireTest`가 Testcontainers에서만 확인했다.
