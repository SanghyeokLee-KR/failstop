# ADR 0028. AWS 구축 전에 인프라팀의 VM 검증 단계를 둔다

- 상태: 채택. VM 선행 조건은 2026-09-19 [ADR 0029](0029-school-aws-first-personal-account-expansion.md)가 대체했다(보류, 학교 EC2 선행). Linux 직접 설치·진단 원칙은 0029의 대체 범위 밖이라 유지한다. 아래 본문의 VM 선행 절차는 당시 결정 이력이며 현재 AWS 착수 조건으로 적용하지 않는다.
- 날짜: 2026-09-18
- 근거: 사용자가 개발팀의 Docker 검증 결과 확인, 인프라팀의 VM 검증, AWS 구축 순서로 진행하기로 확정했다. VM에서는 Linux에 직접 설치·설정하고 Docker는 꼭 필요한 항목에만 사용한다.
- 관계: [ADR 0027](0027-msp-operations-and-autoscaling.md)의 Linux·MSP 운영 범위에 VM 선행 단계를 추가한다. AWS 배치, 조회 ASG, DB 비동기 복제·수동 승격 정책은 유지한다.

## 배경

개발팀이 거래소와 대시보드를 완성한 상황을 가정한다. 인프라팀은 기존 Docker 시험 결과와 실행 조건을 확인하고, 운영 환경에서 필요한 OS 설정과 여러 호스트의 연결을 먼저 검증한다. 기존 Docker·WSL 검증은 재사용하되 별도로 구성한 VM에서 검증한 결과로 바꾸어 적지 않는다.

## 결정

프로젝트의 진행과 발표 흐름을 다음 세 단계로 구분한다.

| 단계 | 담당 역할과 확인할 내용 | 결과의 적용 범위 |
|---|---|---|
| Docker 검증 결과 확인 | 개발팀이 제공한 이미지·Compose·환경변수·데이터 경로·시험 결과를 인프라팀이 확인한다. | 기존 개발 환경의 기능·거래·복구 검증 |
| VM 사전 검증 | 인프라팀이 Linux를 설치하고 계정·서비스·로그·디스크·네트워크와 호스트 간 배포·복구를 확인한다. | 해당 VM의 OS·CPU·가상 네트워크와 자원 조건 |
| AWS 구축·검증 | VM에서 확인한 절차를 AWS에 맞춰 적용하고 실제 접속·부하·조회 ASG·DB 복구·관제·보고를 검증한다. | 실제 AWS 자원과 측정 조건 |

VM에서는 앱·DB·웹 제공·관측 도구를 Linux에 직접 설치하고 OS 서비스로 운영하는 방식을 기본으로 한다. 기존 Dockerfile·Compose는 버전·실행 인자·환경변수·포트·초기화 조건을 확인하는 자료로 사용한다. 애플리케이션 산출물, 설정의 의미와 검증 기준을 재사용하되 Compose 기동 자체를 VM 구축으로 대신하지 않는다. 과거 카오스 전체를 재실행하거나 애플리케이션을 VM 전용으로 다시 개발하는 단계로 확대하지 않는다.

처음에는 설치·계정·디렉터리·권한·설정·기동·로그 확인을 단계별로 직접 수행하고 원리를 설명할 수 있게 한다. 수동으로 확인한 절차는 이후 재현 가능한 설정이나 스크립트로 정리할 수 있다. 자동화가 직접 설치와 진단 경험을 대신하지 않게 한다.

Docker 예외가 필요하면 구성 요소, 직접 설치가 어려운 구체적인 이유, 컨테이너가 가리는 실습 범위와 종료 방법을 기록한다. 지금 확정된 Docker 예외는 없다. 편리하다는 이유만으로 DB나 관측 스택 전체를 다시 컨테이너로 구성하지 않는다. 사용자가 들은 회사의 Docker 미사용 상황을 전체 회사·팀·MSP 업계의 공통 정책으로 일반화하지 않는다.

직접 설치로 바뀌는 파일 경로·서비스 이름·인증·로그·백업 대상과 컨테이너 이름에 의존하는 시험 도구를 확인한다. PostgreSQL은 같은 메이저 버전과 필요한 확장·설정을 대조하고, 기존 Docker 데이터 볼륨을 덮어쓰지 않는다. 새 실습 DB 초기화 또는 검증 가능한 백업·복원으로 데이터를 준비한다. 실행 위치가 바뀌어도 DB·API 계약과 거래 무결성 기준은 유지한다.

이 직접 설치 원칙은 VM 단계에 적용한다. AWS의 실행 방식까지 이번 결정으로 일괄 변경하지 않는다. AWS로 옮길 때 직접 설치와 기존 컨테이너 배포의 차이, 운영 목적과 검증 결과를 바탕으로 실행 방식을 명시한다.

먼저 호스트의 CPU·메모리·가용 디스크, 가상화 지원과 사용할 하이퍼바이저를 확인한다. OS는 기존 Rocky Linux 10 계열의 AWS 계획과 맞추는 것을 우선 검토한다. 로컬 x86과 AWS Graviton ARM64의 차이는 이미지·기동 검증 대상으로 남긴다. VM 제품·대수·주소·메모리 배분은 실제 PC와 시험 범위를 확인한 뒤 배포 안내에 기록한다. 이 결정만으로 VM 5대나 특정 제품을 확정하지 않는다.

한 VM에서 기본 설정과 기동을 확인한 뒤 앱과 DB를 서로 다른 VM에 배치한다. DB 전환 시험에는 primary와 standby도 서로 다른 VM에 둔다. 대기 앱·조회·관측 역할의 추가 배치는 검증할 경로에 맞춰 정한다. 관리 접근과 서비스 통신의 허용 범위를 명시한다.

## AWS로 진행하기 전에 확인할 조건

1. 사용한 OS·아키텍처·패키지·애플리케이션 산출물·설정 버전과 VM 배치, 통신 경로를 기록한다. Docker 예외가 있다면 대상·필요성·검증 한계를 함께 남긴다.
2. 계정·SSH·sudo·파일 권한의 허용·거부를 확인하고, 실제 VM 재부팅 후 마운트·서비스·로그 보존과 정상 응답을 확인한다.
3. 서로 다른 VM 사이의 앱·DB·관측 통신을 확인한다. 필요한 접근은 되고 금지한 접근은 차단돼야 한다.
4. 별도 데이터 디스크의 마운트와 보존을 확인하고, 격리된 복원 대상에서 백업 복원과 서비스·데이터 검증을 수행한다. DB 전환은 기존 primary 격리와 수동 승격 절차를 따른다.
5. 확인한 문제·수정·재검증 결과와 AWS에서 남은 차이를 기록한다. 증거가 없는 항목은 완료로 표시하지 않는다.

실제 상태와 남은 일은 [로드맵](../../ROADMAP.md)에만 기록한다. VM 단계가 끝나기 전에도 AWS 견적·권한·설계 확인은 병행할 수 있다. VM 결과를 바탕으로 실제 AWS 배포·통합 검증으로 진행한다.

## 검증의 한계와 대안

한 물리 PC의 VM들은 장비를 공유한다. VM 프로세스 중단이나 가상 NIC 장애 시험을 물리 서버·스위치·AWS AZ 장애 검증으로 설명하지 않는다. VM 대수 변경은 실제 AWS ASG 검증이 아니며, AWS의 ARM64 실행·보안 그룹·ALB·ASG·IAM·SSM·성능·비용은 AWS에서 따로 확인한다.

Docker 검증 후 바로 AWS로 진행하는 대안도 가능하지만, 사용자는 Linux 운영과 호스트 배치를 VM에서 먼저 검증하는 단계를 선택했다. 추가 준비 시간이 필요하므로 기존 자산을 재사용하고 RAID·VMware 관리·Windows 실습까지 필수 범위로 늘리지 않는다. 이틀 내 모든 단계의 완료를 보장하지 않는다.
