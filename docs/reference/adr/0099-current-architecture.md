# 0099. 현재 구조와 AWS 배포 판단

이 문서만 읽어도 지금 채택한 구조, 실제 구현 범위, AWS에 올리기 전에 남은 일을 판단할 수 있도록 정리한다. 각 ADR은 선택 이유와 변경 이력을 보존하고, 이 문서는 그 결정들이 합쳐진 현재 모습을 계속 갱신한다. `0099`는 이를 위한 예약 번호다. 개별 결정의 번호는 0099를 제외하고 이어간다.

검토 기준일은 2026-09-26이다. 09-26에 마켓별 리더 브랜치를 main에 병합하면서 main의 V47.1(09-24, 소유자 권한 트리거 함수의 PUBLIC 실행 권한 회수)을 아래 학교 DB 문장과 전환 순서에 합쳤다. 09-26에는 이어 Patroni 브랜치 `claude/patroni`(기준 `9a6d2474`)를 병합하며 계약 절 번호를 API 설계 §2-5-e, DB 설계 §5.4-f, 판을 v2.60으로 옮겼다. 그 브랜치는 09-25에 사용자가 정한 DB 자동 전환([ADR 0036](0036-patroni-strict-sync-db-failover.md))의 설계와 계약(DB·API 설계 v2.60, 하네스 검증설계의 E-P 실험, CI/CD §3-5·§8-1, 관리자 설계 v1.6)과 폐기용 PostgreSQL 사전 확인 증거를 대조해 쓰기 구조 문단의 DB 문장, 역할 표, DB 장애 절, AWS 순서의 DB 연습, ADR 표를 고쳤다. 이어 그 설계의 검토 대응(설계 14절, 같은 판 안의 계약 보강, 사전 확인 3·4차와 경보 식 확인)을 대조해 DB 장애 절과 ADR 표를 다시 고쳤다. 그 뒤 같은 브랜치의 코드와 로컬 실험 스택, E-P 회차 기록(`harness/patroni/README.md`, `harness/evidence/patroni-EP-20260925-*`), 코드 검토 대응(설계 4-3~4-5·12절, API·DB 설계 v2.60 같은 판 안의 보강)을 대조해 DB 장애 절과 ADR 표(0017, 0036)를 다시 고쳤다. 이어 코드 검토 대응 뒤 이미지로 돌린 E-P1~E-P6 한 벌(`harness/evidence/patroni-20260925-1015/`)과 설계 15절, ADR 0036 상태를 대조해 DB 장애 절과 ADR 표(0036)를 고쳤다. 09-26에는 이어 관제센터 브랜치 `claude/msp-control`을 병합했다. 그 브랜치의 대조 기록은 이렇다. 09-25에는 관리 콘솔 관제센터 화면(`claude/admin-design`)과 관제센터 서버(`claude/msp-control`)를 한 브랜치로 병합했다. 병합 때 [ADR 0035](0035-ai-operations-authority.md)에 서버 쪽 사용자 결정(방향 전제 D3와 T6의 비대칭, D4 유지, 근거 자유 문장 제거 S8, 통지 개입 등급, DGX Spark 모델 후보)을 적고, 'AI는 운영 조치를 실행하지 않는다' 류의 문장을 0035의 대체 범위에 맞췄다(관리자 설계 v1.14, API v2.52.7과 대조). 병합 뒤 서버의 AI 조치 문구와 용량 권고를 app-3 켜기·끄기(앱 계층 2~3대)와 합니다체로 맞춰 판단 프롬프트 판이 `msp-ai/4`가 됐다. 아래 로컬 모델 평가는 그 전 판(`msp-ai/3`) 기준이라 다시 재야 한다(API v2.52.7, DB v2.51.5와 대조). 이어서 웹의 http 원천을 관제센터 서버 계약에 잇고 관리 콘솔 문단을 그 사실로 고쳤다(관리자 설계 v1.14, 디자인 시스템 v1.15, 레이아웃 v1.9와 대조). 같은 날 사이드바 전체를 MSP 관점에서 넓히는 3라운드 계약(관리자 설계 v1.15, 디자인 시스템 v1.16, 레이아웃 v1.10)을 관리 콘솔 문단에 적었다. 이어서 3라운드 구현 묶음 A(경보·사건, AI 판단, 서버·노드, 데이터베이스. 관리자 설계 v1.16, 디자인 시스템 v1.17, 레이아웃 v1.11), 구현 묶음 B(용량·부하 확장, 네트워크·보안, 변경·작업, 조치 기록, 런북. 관리자 설계 v1.17, 디자인 시스템 v1.18, 레이아웃 v1.12), 구현 묶음 C(SLA 월간 보고, 비용, 시나리오, 설정 확장과 단추 요구 역할의 서버 계약 맞춤. 관리자 설계 v1.18, 디자인 시스템 v1.19, 레이아웃 v1.13)를 관리 콘솔 문단에 반영했다. 같은 날 화면 쪽에서는 사용자 결정으로 ADR 0035를 보강했다. 0033](0033-no-virtual-threads-for-request-handling.md)). 09-23에는 관리 콘솔 개편과 로컬 조회 증설 경로를 반영하고, 전체 파악에서 찾은 결함을 고친 저장소 변경(주문 V47, 정산 재시도, 학교 경보·백업·워치독 템플릿, VM 실습망 기록)을 계약·배포 안내·로드맵과 대조했다. 이 저장소 변경은 학교 서버에 적용하지 않았으므로 아래에서 현재 구조와 구분해 적는다. 학교 안내 원문, MFA 재로그인 뒤 자원 생성과 Linux 설정, 별도 DB 두 대의 비동기 복제, HTTPS와 저속 봇 체결을 확인했다. **격리 DB 복원, 수동 DB 장애 복구와 앱·DB 상태를 포함한 Teams 보고는 검증했다. 장시간 운영 측정, 외부 보관·예약 백업, 관측 노드 자체 감시, ALB·ASG의 실제 자동 확장은 남아 있다.** 현재 계정 상태와 다음 작업은 [로드맵](../../ROADMAP.md)에 기록한다.

09-17에는 사용자가 교수님께 보고한 구성도와 화면을 확인했다. 원본 15개와 현재 구현과의 차이는 [아키텍쳐 자료](../../../아키텍쳐/README.md)에 있다. 2026-09-18 확정한 운영 예산은 **월 40만 원**이며, 발표는 PPTX에 실제 시연 영상과 캡처를 연결해 준비한다. 과거 문서의 50만 원 전제는 현재 예산 판단에 사용하지 않는다.

세부 필드와 불변 조건은 [계약 문서](../README.md), 진행 중인 작업은 [로드맵](../../ROADMAP.md), 실행 결과는 [측정 기록](../../measurements/README.md)이 기준이다. 이 문서에서 서로 다른 내용을 발견하면 해당 원본과 코드를 함께 고친다. 높은 ADR 번호나 이 요약만으로 기존 계약을 덮어쓰지 않는다.

학교 EC2의 관리 접속은 기존 Instance Connect와 SSM 경로를 유지한다. 2026-09-20 사용자 요청으로 EC2 RSA 키페어를 생성하고 기존 네 서버의 ec2-user에 공개키를 등록했다. 개인키는 PC의 PEM·PPK 파일로 보관하며 Git에 두지 않는다. 실제 SSH 인증은 SSM 경유로 검증했고, 직접 공인 IP 접속을 위한 22번 SG 확대는 하지 않았다. 인스턴스 생성 당시 키페어 표시와 서버의 현재 공개키 인증 설정을 구분한다. 사용법·근거는 [AWS 작업 안내](../../reports/AWS_작업.md#aws-키페어와-putty-접속-파일)를 따른다.

## 지금 판단할 내용

고객사의 IT 인프라를 구축·운영·관리하는 엔지니어의 역할을 수행한다. 약 3개월간 직접 개발한 가상 거래소를 대상으로 AWS 인프라와 관제 기반을 갖추며, 가장 중요한 역량은 Linux 서버 운영이다. 계정·권한·서비스·로그·네트워크·디스크를 직접 설정하고 장애 원인을 좁혀 복구한다. DB 복구와 조회 계층의 EC2 자동 확장도 검증한다. 일일·장애 보고는 AI가 수집한 근거를 정리해 Microsoft Teams로 보낸다. 전체 제목은 「Linux·AWS 기반 인프라 운영 및 온프레미스 AI 관제 시스템 구축」이며 페일스톱은 운영 대상 서비스명이다. 개발팀이 거래소와 기존 대시보드를 완성한 상황에서 인프라 담당자가 설계·구축·검증을 수행하는 시나리오다. 개발팀의 Docker 결과를 확인한 뒤 학교 EC2에서 Linux 운영과 서비스를 검증하고, 2026년 10월 초 개인 AWS 계정에서 제한됐던 부분을 보강한다. VM 선행 조건은 [ADR 0029](0029-school-aws-first-personal-account-expansion.md)로 보류했다. 발표에서는 구축 중 확인한 문제, 선택한 설정과 재검증 근거를 설명한다. 시나리오의 개발 완료 전제가 실제 AWS 검증 상태를 바꾸지는 않는다. [ADR 0027](0027-msp-operations-and-autoscaling.md)

Docker 카오스는 로컬에서 개발 검증을 했다는 자료로 보존한다. 새로운 카오스 기능·주입 화면이나 과거 실험 전수 재실행을 목표로 두지 않는다. AWS의 부하·장애 대응 시험은 계속하되 관제에서 진단·조치·보고까지 이어지는 과정으로 판단한다. 기존의 수동 확장 전용 정책은 현재 목표가 아니다.

MSP 업무와 연결할 계정·서비스·로그·스토리지·네트워크 설정과 실습 후보는 [Linux 운영 실무 조사](../../reports/Linux_운영_실무_조사.md)에 정리했다. 공식 자료를 바탕으로 한 제안이며 신규 설정 채택이나 구현·검증 완료를 뜻하지 않는다.

학교 EC2에서는 기존 역할별 인스턴스 분리를 유지한다. 먼저 생성한 t3.small·gp3 20GiB 한 대는 첫 앱 노드이며 접속·계정·권한·서비스·로그·디스크를 검증하는 출발점이다. DB와 관측을 이 서버에 먼저 설치하지 않는다. 각 역할의 Linux에 직접 설치하는 방식이며 Docker 예외는 이유를 기록한다. 50GiB는 학교 안내의 디스크 용량 조건이고 전체 시스템을 한 대에 넣으라는 제한이 아니다. 실제 할당량·추가 노드 생성 권한은 별도 확인한다. [ADR 0029](0029-school-aws-first-personal-account-expansion.md)

[VM 운영환경 구성도](../../../아키텍쳐/교수님_보고본/06_VM_운영환경/Linux_VM_운영환경_구성도.png)는 보류한 VM 단계를 설명하는 설계안으로 보존한다. 웹 진입·앱·DB·관제를 6개 역할로 나눈 예시이며 VM 대수 확정이나 구축 완료를 뜻하지 않는다. 편집 원본과 그림의 적용 범위는 [아키텍쳐 자료](../../../아키텍쳐/README.md)에서 확인한다.

2026-09-19에는 [VM 네트워크·접근제어도](../../../아키텍쳐/교수님_보고본/06_VM_운영환경/VM_네트워크_접근제어도.png)와 [VM DB 장애 복구 흐름도](../../../아키텍쳐/교수님_보고본/06_VM_운영환경/VM_DB_장애복구_흐름도.png)를 추가했다. 출발지별 허용 포트, SSH 터널을 통한 관리 화면 접근, 기존 DB 격리부터 수동 승격·거래 검증·복제본 재구성까지의 설계안이다. 접근제어 적용이나 복구 실습을 실행한 결과가 아니며, 실제 VM 주소·설정·운영 판단 조건은 구축할 때 확인한다.

0029가 보류한 것은 'VM에서 먼저 검증한 뒤 AWS로 간다'는 착수 조건이다. VM 실습망 자체는 그 조건과 별개로 `deploy/vm-lab`의 kickstart와 스크립트로 구축했다. VirtualBox VM 여섯 대(EDGE01·APP01·APP02·DB01·DB02·OPS01)에 Rocky Linux 10.2와 역할별 서비스를 직접 설치했고, 호스트 방화벽(nftables 기본 차단), DB 비동기 복제, OPS01의 Prometheus·Grafana·Alertmanager를 올렸다. 2026-09-26에는 pfSense CE 2.7.2 경계 방화벽을 더해 여섯 대를 경계형으로 옮겼다. 여섯 대는 `lab-lan` NIC 하나만 남고, 작업 PC의 관리 SSH와 웹 진입(`https://192.168.56.10`, 포트포워딩)과 외부 발신이 pfSense를 지나며 VM 사이는 각 VM의 nftables가 거른다. 실제 접속으로 허용·차단을 확인했고 차단 기록이 OPS01에 원격으로 남았다. 규칙을 끈 직후와 pfSense 재부팅 뒤 재시험은 하지 않았다([주소 계획](../../../deploy/vm-lab/build/00-주소계획.md), [pfSense 증거본](../../../증거본/2026-09-26_VM_pfSense/README.md)). 같은 날 OPS01의 Databasus(컨테이너 예외)로 주 DB의 논리 백업을 웹 진입 서버의 SFTP 전용 계정에 보관하고 복원 검증 에이전트로 되살아나는 것을 확인했다([Databasus 증거본](../../../증거본/2026-09-26_VM_Databasus/README.md)). VM DB에는 V47.1이 적용되지 않았다. VM의 DB 수동 승격과 OPS01 보고 역할은 만들지 않았다. 2026-09-23 재부팅 확인에서 기준선과 같았던 것은 DB01·DB02뿐이다. VM 결과는 한 PC의 가상망에서 얻은 근거이므로 학교·개인 AWS 검증으로 옮기지 않는다. [배포 안내의 VM 절](../../../deploy/README.md), [재부팅 검증](../../../deploy/vm-lab/캡처/재부팅검증-2026-09-23/README.md)

2026-09-20에는 학교 EC2의 현재 상태를 설명하는 발표용 도면 여섯 장을 [아키텍쳐 자료](../../../아키텍쳐/README.md)의 `07_학교AWS_운영환경`에 추가했다. 실제 역할별 배치, Linux 서비스와 권한, 장애 감지와 Teams 보고, 출발지·포트 기준의 접근 통제, 수동 DB 전환 절차, 조회 계층 확장 계획을 나눠 그렸고 미구축 자원은 점선으로 구분했다. 도면은 AWS 공식 아이콘을 쓰고 한눈에 읽히도록 글자를 줄였으므로, 포트 전체 목록과 식별자·권한 같은 세부 값은 도면이 아니라 [AWS 작업 안내](../../reports/AWS_작업.md)와 이 문서에서 확인한다. 도면의 값은 저장소 설정 파일과 운영 문서에서 확인한 것이며 실행 중 서버를 다시 조회한 결과가 아니다. 이 그림 작업으로 AWS 검증 상태가 달라지지는 않는다.

현재 거래 서버는 한 리더 안에서 마켓별로 주문을 처리한다. 사용자는 2026-09-23 마켓을 두 앱 노드의 리더로 나누는 마켓별 리더로 가기로 정했고, 로컬 Docker에서 구현·검증한 뒤 AWS에 옮긴다. 결정과 단계는 [ADR 0034](0034-market-partitioned-leadership.md)에 있다. 2026-09-24 사용자는 발표 전 범위를 로컬 Docker의 S7까지(WebSocket 브로커 릴레이 S6 포함)로 정했다. 구현은 작업 브랜치 `claude/per-market-leader`에만 있고, main과 학교 서버는 V47까지의 단일 리더다. 브랜치에는 S7 코드까지 들어 있다. V48이 파티션 리스 행 두 개, 마켓과 파티션의 대응 표, 모드 래치를 넣고, 쓰기 권한 검사가 기록할 행의 마켓에서 리스 행을 찾게 바꿨다. S3의 V50은 모드를 P2로 올렸을 때 주문 생성 명령의 잔고 예약을 저널 append와 같은 트랜잭션으로 옮긴다. 잔고가 모자라면 그 트랜잭션 전체가 롤백돼 주문은 `400 insufficient_funds`로 끝나고, 정산은 예약 기록 `order_reservations`를 권위로 써 예약을 다시 하지 않는다. V50을 적용해도 모드는 P1이고, P2는 소유자가 쓰기를 멈춘 창에서 전환 함수 `set_leader_protocol(2)`를 불러야 켜진다. 전환은 Testcontainers 일회용 DB와 로컬 Docker 폐기용 스택의 DB에서만 했다. 어느 모드든 리더는 여전히 `matching-engine` 행 하나를 쥐고 12개 마켓을 모두 쓴다. 파티션 리더(P3)는 S7이다. 같은 이미지에 V49(앱 역할의 리스 행 UPDATE와 저널 직접 INSERT 회수), 관문 주행이 드러낸 S3 이전 결함을 고친 V51(앱 역할 검증기의 DEFAULT 파티션 잎 읽기)과 V52(획득한 리스의 만료를 행 잠금을 얻은 뒤부터 셈)가 함께 들어간다. 확인 범위는 Testcontainers 시험과 서버 전체 빌드, 로컬 Docker 폐기용 스택의 관문 주행이다. S1 관문의 카오스 다섯(P1)은 PASS다. S2 관문은 같은 날 첫 A/B 부하 비교가 5xx 조건을 채우지 못했으나, 사용자가 리더가 낸 5xx만 세기로 정한 뒤의 반복 재측정이 PASS라 통과했다. S3 관문은 재주행에서 P2 봇 부하, P2 카오스(E2·E4·E5·E6·E7, E5는 사후 판정을 드레인 뒤로 옮긴 재주행), 처리량 조건(결정 5)이 모두 PASS다. 결정 5는 로컬 Docker 단일 호스트의 판정이고, 이를 확정할지와 E5·E7 판정 절차 변경은 사용자 확인 대상이다. P2에서 P1로 되돌리는 시험은 S2 이미지를 띄우는 스택 판을 하지 않았다([09-24 측정](../../measurements/20260924.md), [S3 설계](../architecture/마켓분할_리더_S3_설계.md) 12절). S4는 앱의 리스 서비스, 접수 게이트, 승격, 강등, 팔로워, 좀비 판정, 지표를 파티션 단위로 바꿨고 V53(하네스 페일오버 이력의 자원 열)을 더했다. P1·P2에서는 파티션이 `matching-engine` 하나이고 모든 마켓을 덮으므로 리더는 여전히 하나다. 그래도 P2에서 보이는 동작은 바뀐다. 노드는 늘 팔로워로 기동해 첫 획득 때 승격하고, 강등된 리더는 재기동 없이 재구성해 팔로워로 돌아오며(10분에 3회면 차단), 리스 획득은 1초 잠금 대기 상한으로 끊긴다. 접수 락 대기 상한 2초와 append `lock_timeout` 1초를 켜고 접수 경합은 `429`나 `409 order_in_progress`로 끝난다(AI 선택, 사용자 확인 필요). S4 서버 전체 빌드(app 834개)와 웹 검사는 통과했지만, 구현 검토 수정 뒤 폐기용 스택 재주행에서 E2가 두 번, E1이 세 번 가운데 한 번 FAIL이라 S4 관문은 통과하지 못했다. 원인은 DB 일시 장애를 재생 불일치나 `500`으로 분류하는 경로이고 자금·멱등·권한 검사 위반은 없었다([09-25 측정](../../measurements/20260925.md), [S4 설계](../architecture/마켓분할_리더_S4_설계.md) 13-2). 이 결함을 고치는 S4b는 같은 날 설계와 계약(DB·API 설계 v2.56, 하네스 검증설계)을 코드보다 먼저 고쳤다. 바뀐 계약은 이렇다. 재생이 DB 장애로 끝나면 C17 불일치로 적지 않는다. 주문 접수의 DB 연결 장애는 저널 확인마저 DB에 닿지 못할 때만 `503`이고 닿으면 `429`·`409`다. 멱등 키가 없는 쓰기의 연결 끊김은 다른 노드가 다시 실행하지 않도록 `500`으로 둔다. S4b 코드는 작업 브랜치에 커밋했고 새 마이그레이션은 없으며, 서버 전체 빌드(app 870개)를 통과했다. 첫 폐기용 스택 주행에서 E1 다섯 번 가운데 한 번이 S4의 FAIL을 재현했다. PG 지연 아래 정산이 잠금 대기 초과를 거듭해 재시도 한도(4회·5초)를 넘긴 것이 원인이라, 한도를 8회·15초로 늘렸다(한도를 넘기면 여전히 라이터 치명). 위의 응답 규칙은 2026-09-25 사용자가 확정했고, 이 한도는 AI 선택이라 사용자 확인이 필요하다. 구현 검토 보정(연결이 끊긴 V47 판정을 다시 부를 때 키를 지우지 않음)까지 넣은 마지막 이미지로 P2 봇 부하와 접수 경합, E2 다섯 번 연속, E1 다섯 번, E4~E7, 콜드 재기동이 모두 PASS였고, 불변식 위반, 구 epoch 쓰기, 주문 `500`, 재생 불일치는 모든 실험에서 0이었다. 재생 도중 DB가 끊기는 분기와 V47 재확인이 판정을 내는 경로는 스택에서 나지 않아 시험으로만 확인했다([S4b 설계](../architecture/마켓분할_리더_S4b_설계.md) 12~15절). 정리하면 구현 단계는 S5(REST 라우팅과 요청 경계), 그 위에 병합한 S6(WebSocket 외부 브로커 중계, 관문 통과), 2026-09-26 병합한 S7 코드(P3 전환, 관문 통과, 다음 문단)까지다. S4b 코드로 로컬 폐기용 스택의 S4 관문을 통과했다. S5는 설계와 계약을 먼저 고친 뒤 코드와 V54를 넣어 브랜치에 커밋했고, 구현 검토 대응 뒤 서버 전체 빌드(app 930 사례)를 통과했다. 폐기용 스택의 첫 주행은 라우팅 분할 실험이 판정식의 경계로 FAIL이었고, 판정식을 주행 뒤 고친 재주행도 k6 WebSocket orderbook 결번 임계로 FAIL이었다. 같은 이미지의 둘째 주행에서는 선검사, 힌트, 인계, 라우팅 분할, 기본 LB와 파티션 LB의 E4, 파티션 LB의 E7·E2 판정이 모두 PASS라 S5 관문을 로컬 판정으로 통과했다. 첫 주행의 결번은 둘째 주행의 k6 여덟 번에서 재현되지 않아 원인을 모르고, 주행 뒤 바꾼 판정식과 함께 이 판정을 받아들일지는 사용자 확인 대상이다. B1 재기록은 두 주행 모두 세 회 가운데 두 회만 측정했다([S5 설계](../architecture/마켓분할_리더_S5_설계.md) 12절). 계약은 주문 쓰기의 소유권 선검사(그 마켓을 접수하지 않는 노드가 아무 상태도 건드리기 전에 `503`), 서명 밖 마켓 힌트 헤더, 한 배치 한 마켓, 마켓 없는 일괄 취소와 회원 폐쇄의 DB 인계 표(V54), 하네스의 파티션 LB 파일이다. 인계는 엔진을 끈 관리 평면에서 회원 폐쇄의 취소가 모두 저널 전에 거부되던 결함도 고친다([S5 설계](../architecture/마켓분할_리더_S5_설계.md)). S6(WebSocket 외부 브로커 중계)은 사용자 결정(2026-09-25)으로 S5와 같은 시각에 별도 브랜치 `claude/pml-s6`(기준 S4b 커밋)에서 진행했고, 같은 날 이 브랜치의 S5 위에 병합했다. 각 앱 노드의 내장 브로커가 자기 WS 세션을 맡고, 노드끼리 외부 STOMP 브로커(RabbitMQ 4.3)의 토픽 하나로 게시를 주고받는 노드 단위 중계다. 소유 노드는 쥔 파티션마다 하트비트를 보내고, 마켓을 쥐지 않은 노드는 그 하트비트와 노드별 미러를 채울 때만 호가·티커를 미러에서, 아니면 DB 집계와 `seq: 0`으로 낸다. 웹은 마켓마다 epoch를 비교해 오른 마켓만 다시 맞춘다. 새 마이그레이션은 없고 설정 기본값은 종전 노드 내장 모드(`exchange.ws.relay.mode=simple`)다. 기본 모드에서도 달라지는 것이 있다. 다른 노드가 유효한 리스를 쥔 노드(두 노드 배치의 팔로워)는 WS 핸드셰이크를 `503`으로 거절하고, 팔로워의 호가·티커는 자기 카운터 대신 `seq: 0`과 DB 집계를 내며, myAsset·계좌 조회에 잔고 판 `version`이 붙는다. 앱 노드가 하나인 학교는 평상시 동작이 같다. S5의 소유권 선검사는 주문 쓰기에만 걸려 호가·티커 조회와 `/ws/v1`에는 걸리지 않으므로, 마켓을 쥐지 않은 노드도 선검사 `503` 없이 그 규칙으로 답한다. 브로커 모드는 Testcontainers 시험(일회용 DB와 브로커 컨테이너)과 로컬 Docker 폐기용 스택의 관문 주행에서만 켰다. 병합한 트리에서 `server`의 `.\gradlew.bat build`가 23분 16초에 통과했다. app 199개 클래스 989개 시험이 실패·오류·건너뜀 없이 통과했다. S5의 930개와 S6의 929개에서 공통 기준 S4b의 870개를 뺀 수와 같다. engine 67개는 바뀌지 않아 UP-TO-DATE로 앞선 결과를 썼다. Testcontainers 일회용 DB와 브로커 컨테이너를 썼고 빌드 로그에 `localhost:5432`·`55432` JDBC 주소는 0건이다. `npm --prefix web test` 569개, 하네스 파이썬 시험 356개(`python -m unittest discover -s harness/scale -p "test_*.py"`, `test_s6_relay_axes.py` 17개와 `test_s5_route_probe.py`·`test_nginx_partition_conf.py` 10개 포함), k6 판정 모듈의 node 시험 8개(`harness/load/tests/seq_baseline.test.mjs`), 문서 검사 네 가지도 통과했다. 웹 빌드·토큰·브라우저 게이트는 돌리지 않았다. 같은 날 병합한 트리에서 폐기용 스택 관문 W0~W5(P2, 기본 모드 회귀와 브로커 정지·멈춤·메모리 경보, 리더 kill)를 돌렸다. 첫 이미지에서 브로커 멈춤·메모리 경보 때 팔로워가 발행이 멈춘 소유 노드의 미러를 1~2초 동안 `seq`≠0 기준점으로 냈고, 고친 둘째 이미지에서 브로커 정지 뒤 연결 재개가 판정(15초)보다 늦었다. 비소유 노드는 가장 최근 소유 노드 하트비트가 400ms 안일 때만 미러를 쓰고(하트비트 간격 200ms), 중계 재연결 상한을 3초로 줄였으며, STOMP `CONNECTED` 전에 닫힌 연결 시도를 끊김으로 알리던 결함도 고쳤다. 셋째 이미지에서 W0~W5가 모두 PASS라 S6 관문을 로컬 판정으로 통과했고, 그 판의 서버 전체 빌드는 app 200개 클래스 994개가 통과했다([S6 설계](../architecture/마켓분할_리더_S6_설계.md) 14절). 판정 도구 보정과 세 기본값은 AI가 정했고 사용자 확인 대상이다. P3에서 WS를 쓰는 판정(W6·W7)은 S7 관문이므로, 그때까지 P3 파티션 모드의 WS는 쓰지 않는다. S5의 파티션 LB 파일과 S6의 중계 LB 파일을 합친 하네스 LB 파일은 두 노드가 파티션을 나누는 S7에서 만든다([S6 설계](../architecture/마켓분할_리더_S6_설계.md) 12·13절). 그 파일은 S7에서 만들어 병합했다(다음 문단). 현재 프로토콜 모드와 WS 중계 모드는 구현 단계와 별개다. 이 브랜치를 합친 시점에 영속 DB(학교 DB와 보존한 로컬 카오스 볼륨)에는 V48 이후가 적용되지 않아 모드 래치가 없고, 동작은 단일 리더(P1과 같다)다. P2는 Testcontainers와 폐기용 스택의 DB에서만 켰다. WS 중계 설정은 학교와 보존한 로컬 스택 어디에서도 바꾸지 않았으므로 `simple`이다. 파티션 리더 모드 P3의 앱 코드 경로는 S4에 있고, S7 바이너리는 획득 때 최고 모드 3을 넘기므로 P3 DB에서도 파티션 리스를 얻는다. P3은 Testcontainers 일회용 DB, 설계 단계의 폐기용 PostgreSQL 컨테이너, 로컬 Docker 폐기용 스택의 DB에서만 켰다(다음 문단). 그래서 이 문서의 나머지 설명은 단일 리더와 P1 기준이다. 판단 근거는 [조회·쓰기 비율 조사](../architecture/거래소_조회쓰기_비율_조사.md)와 [로드맵](../../ROADMAP.md)에 있다. DB는 primary 한 대와 standby 한 대의 비동기 복제다. 앱 리더 전환은 자동이지만 DB 승격은 수동이다. 따라서 앱 장애 복구 목표인 30초나 로컬 무손실 결과를 DB 장애 전체의 보장으로 설명하면 안 된다. 사용자는 2026-09-24~25 DB 자동 전환을 Patroni 엄격 동기 2노드로 하기로 정했다(ADR 0036). 작업 브랜치에 코드와 로컬 실험 스택이 있으나 적용 전이라 이 문단의 현재 동작은 그대로다(아래 DB 장애 절).

S7(P3 전환과 파티션 실험)은 2026-09-25 사용자 결정으로 S6 관문 실험과 병렬로 브랜치 `claude/pml-s7`(기준 `d46d5073`)에서 진행했고, 2026-09-26 S6 관문 기록 뒤의 작업 브랜치에 병합했다. 병합하며 S6 관문 보정을 W6 판정기와 실행기에 옮겼고, S6 관문 수정의 하트비트 200ms·미러 신선도 400ms·재연결 상한 3초는 노드 사이 브로커 경로의 값이라 합친 LB 파일과 겹치지 않는 것을 코드로 대조했다([로드맵](../../ROADMAP.md) 「2026-09-26 S7 병합」). S7은 설계와 계약(DB·API 설계 v2.59, [S7 설계](../architecture/마켓분할_리더_S7_설계.md))을 코드보다 먼저 썼다. V55는 전환 함수에 2->3과 확인 인자를 요구하는 3->2를 더하고, 선행 조건을 한 줄씩 내는 함수와 모드와 무관하게 늘 두는 FEE_INCOME 샤드 1 계정을 만든다. 바이너리는 리스를 얻을 때 최고 모드 3을 넘기고 그 값을 게이지로 낸다. 그래서 P3 DB에서도 파티션 리스를 얻는다. 모드의 권위는 DB라 P1·P2 DB에서는 획득 결과가 전과 같다. 불변식은 C22'(P3 구간의 시간 축 팔을 파티션별로 보고 전환 뒤 시작한 트랜잭션이 옛 구간 epoch로 쓴 명령·스냅샷 행을 세는 판)와 C30(P3 epoch로 기록된 행의 획득 자원을 그 마켓 파티션과 대조)을 앱 enum, 하네스 SQL, 복원·복구 점검에 넣었다. 사후 감사가 세지 못하는 전환 경계(전환을 가로지른 트랜잭션, 옛 구간 epoch의 이벤트·체결 쓰기)는 서버 시험과 실험의 구간 경계 증분이 본다. 하네스에는 P3 오버레이, 파티션 LB와 중계 LB를 합친 LB 파일, 전환 도구의 P3 판, 실험 실행기와 판정기, 발표 재현 스크립트가 있다. 현재 프로토콜 모드는 이 구현 단계와 별개다. 영속 DB(학교 DB와 보존한 로컬 카오스 볼륨)에는 V48 이후가 적용되지 않아 동작은 여전히 단일 리더(P1과 같다)다. P2와 P3은 Testcontainers 일회용 DB와 로컬 폐기용 스택의 DB에서만 켰다(P3은 설계 단계의 폐기용 PostgreSQL 컨테이너에서도). 병합 전 브랜치에서 확인한 범위는 Testcontainers 서버 관문 시험(전환과 선행 조건, 되돌리기, 수수료 샤드, 두 노드 파티션 분담, 교차 노드 이중 지출 1,000회에서 23514 0), 구현 검토 대응 뒤 서버 전체 빌드(app 1,010개가 실패·건너뜀 없이 통과, engine 67개는 앞선 결과), 하네스 파이썬 시험 469개, 배포 시험 14개, 웹 시험 570개와 웹 빌드·토큰 게이트다. 2026-09-26 병합한 트리에서 폐기용 스택 관문 Q1~Q16을 돌렸다([관문 기록](../../../harness/evidence/pml-S7-20260926-0300/README.md), [S7 설계](../architecture/마켓분할_리더_S7_설계.md) 14절). 두 앱 노드가 p0·p1을 하나씩 쥔 스택에서 교차 노드 이중 지출 1,000회(매 회 성공 하나, 주문 `400 insufficient_funds` 866·출금 `422` 134, 23514·치명 0), p1 소유자 kill(RTO 12.866초, p0 epoch 불변, 생존 파티션 주문 접수 간격 기준선 안), pause·망 분리·DB 절단·폭주 중 kill, 두 파티션 소유자 pause, P3->P2 되돌리기 실제 수행과 재진입, 수수료 행 결합, 부하 중 수동 인계, 한 마켓 치명, 콜드 재시작 선호 배정, 두 파티션 인계, C22' 비용이 PASS였고, 사후 불변식 위반은 모든 회차에서 0이었다. 서버 코드 결함은 없었고 도구·판정기·카오스 스택 설정의 빈틈 여덟 곳(가장 큰 것은 카오스 compose가 회원 세션 서명 시드를 넘기지 않아 한 노드의 회원 토큰을 다른 노드가 거절한 것)을 고쳐 다시 쟀다. W7(한 연결로 두 파티션 수신)은 결번 0이다. 웹의 계약된 설정 폴링이 '첫 적재 뒤 REST 0' 축에 걸린 주행 판정 FAIL은 사용자 확정(2026-09-26)에 따라 폴링을 빼고 같은 원자료를 다시 판정해 PASS다. 힌트를 싣지 않는 쓰기는 P3에서 부하 내내 39%가 `502`였다(기록). 로컬 판정이고 AWS 결과를 대신하지 않는다. 구현 검토에서 관문 실행기의 웹 관찰을 `next start` 대신 정적 export 서버로 띄우게 고쳤고, 관리 콘솔의 리더 전환 대본은 P3에서 첫 단계에 멈추고 사유를 적는다(S7 설계 12·13절). 병합 뒤 S6 관문이 드러낸 구독 즉시 스냅샷의 결번 경합을 고쳤다. 스냅샷은 내장 브로커가 구독을 등록한 뒤에 읽고, 비소유 노드의 중계 수신은 미러를 먼저 갱신한 뒤 세션에 전달한다([API 설계](../contracts/백엔드_API_설계.md) §5-2 '스냅샷을 읽는 시점', [S6 설계](../architecture/마켓분할_리더_S6_설계.md) 15절).

## 역할별 인스턴스 배치

학교 DB는 PostgreSQL 17을 OS 서비스로 실행한다. 공통 설정은 [exchange.conf](../../../deploy/linux/postgresql/exchange.conf), 사설 주소는 각 호스트의 `/etc/postgresql/node.conf`에 둔다. 복제 연결은 Standby의 사설 주소 한 개와 복제 전용 계정으로 제한하고 SCRAM 인증과 TLS `verify-full`을 적용한다. 자체 서명한 서버 인증서를 명시적으로 신뢰하며 ACM을 사용하지 않는다. 인증서 교체 시 신뢰 파일도 갱신해야 한다. 재편입은 ADR 0025의 베이스백업 기준을 유지하고 WAL 보존 확대·자동 승격은 추가하지 않았다. ADR 0036이 Patroni의 자동 승격과 자동 재합류를 채택했지만 학교 DB에는 적용하지 않았다. 적용 순서의 초안은 [Patroni 설계](../architecture/DB_자동전환_Patroni_설계.md) 9절이다.

앱·DB·관측을 한 대에 모았다가 나중에 나누는 방식은 사용하지 않는다. 배치는 [교수님께 보고한 전체 구성도](../../../아키텍쳐/교수님_보고본/01_전체구성/거래소_하이브리드_인프라_v5.png)를 기준으로 한다. 기본 역할은 app-1·app-2, DB primary·standby, bot-1의 다섯 노드이며 load-1은 별도 부하 시험 노드다. AI 판단 모델을 돌릴 `ai-1`은 AWS 밖 연구소에 두는 온프레미스 서버이고 예정이며 구축 전이다([ADR 0038](0038-on-prem-ai-inference-server.md)). 앱 계층은 2~3대다. app-1·app-2는 늘 켜진 매칭 리더이면서 조회도 받고, 조회 전용 app-3 한 대만 부하에 따라 Auto Scaling으로 켜고 끈다(ADR 0030 사용자 정정 2026-09-25). 도면의 app-3 자리가 이 자동 증설 노드다. 첫 앱 노드와 별도 DB 두 대, bot-1 서버를 생성했다. bot-1은 t3.small·암호화 gp3 20GiB로 AZ-c에 배치했다. 관측 프로그램과 BTC·ETH·XRP 세 종목의 저속 시장 봇(전체 3 OPS)을 Linux 서비스로 설치했으며 짧은 동시 기동을 확인했다. 장시간 자원 간섭은 검증해야 한다. 생성·검증 상태는 [로드맵](../../ROADMAP.md)에서 확인한다.

| 역할 | 배치 기준 |
|---|---|
| app-1·app-2 | 리더·팔로워를 서로 다른 EC2에 둔다. Java·거래 앱과 해당 호스트 수집 에이전트를 설치한다. PostgreSQL 서버나 중앙 관측 스택을 동거시키지 않는다. |
| DB primary | 앱과 분리한 전용 EC2에 PostgreSQL을 설치한다. 학교에서는 t3.small·암호화 gp3 50GiB, 기본 VPC의 AZ-a로 준비한다. 앱은 이 노드의 사설 주소로 접속한다. |
| DB standby | primary와 다른 EC2에 둔다. 학교에서는 t3.small·암호화 gp3 50GiB, 기본 VPC의 AZ-c로 준비한다. 비동기 복제·격리·수동 승격·재편입을 검증한다. ADR 0036을 적용하면 두 DB 노드에 Patroni와 etcd 멤버를 두고 이 노드는 엄격 동기의 동기 Standby가 되며, 전환과 재합류는 Patroni가 한다(개인 계정은 DB 두 대 t3.medium). |
| bot-1 | 도면과 ADR 0016에 따라 시장 봇과 Prometheus·Grafana 등 중앙 관측을 함께 둔다. 앱·DB·자동 축소 대상과 분리한다. 동거에 따른 자원 간섭과 노드 자체 감시는 검증해야 하며, 관측 전용 EC2 추가는 별도 변경 판단이다. ADR 0036을 적용하면 표만 던지는 etcd 세 번째 멤버와 HAProxy 사이드카가 더해진다. PostgreSQL은 두지 않는다. |
| app-3(조회 전용 자동 증설) | 부하가 오르면 켜져 분산 가능한 REST 조회를 app-1·app-2와 나눠 받고, 부하가 내려가면 꺼진다. Auto Scaling 그룹에는 app-3 한 대만 넣고(0~1대) 앱 계층은 app-1·app-2와 합쳐 2~3대다. 고정 매칭 리더나 DB를 함께 확장하지 않는다. 학교 콘솔에서 ASG 조회와 선행 시작 템플릿 생성이 거부됐다. ASG 생성 API 자체는 미확인이다. 운영자 권한 확인과 학교 배포·부하 검증이 필요하다. 조회 역할 코드와 Terraform 예제는 통합됐지만 AWS 적용 결과는 아니며, Terraform의 reader ASG(최소 1 이상 검증, 예제 1~2대)는 이 정정에 맞출 것이다. |
| load-1 | k6 부하 발생과 외부 계측을 담당한다. 앱·DB·bot-1과 별도 노드로 두며 시험할 때의 가동 시간과 비용을 계산한다. |
| ai-1(예정, 구축 전) | 연구소에 두는 온프레미스 AI 추론 서버다. DGX Spark 한 대(통합 메모리 128GB)에서 Ollama로 0035의 AI 판단 모델을 돌린다. AWS 밖이라 EC2가 아니며, 모델과 AWS와의 연결 경로는 정하지 않았다. Ollama는 인증이 없어 방화벽·허용 주소로만 받는다. 멈추면 AI 판단과 조치만 없고 경보와 ASG 정책은 그대로 동작한다. [ADR 0038](0038-on-prem-ai-inference-server.md) |

학교에서 사용할 정확한 추가 대수·규격·AZ·보안 그룹·가동 시간과 비용은 생성 전에 확정한다. 예산이나 권한 제약이 생겨도 역할을 임의로 합치지 않는다. 이 표는 분리 기준을 명확히 한 것이며 아직 없는 EC2·ASG를 구축 완료로 표시한 것이 아니다.

## 서비스가 연결되는 모습

학교의 시장 봇은 bot-1의 별도 Linux 사용자·systemd 서비스로 실행한다. BTC·ETH·XRP의 전체 주문·취소 목표는 3 OPS이며 매칭 엔진·Flyway를 끄고 공개 HTTPS 앱으로 주문을 보낸다. 봇의 DB 접근은 기존 앱 계정을 사용하되 Primary 인증을 봇 IP 하나로 제한하고 TLS `verify-full`로 검증한다. 봇 관리 API는 사설 8443에서 앱 SG의 mTLS 연결만 받고 관리 지표 8081은 루프백으로 유지한다. 관측과 동시 기동, 봇 정상 종료·재시작을 확인했다. 자동 시작과 제한된 재시도, 디스크 여유·관측 유효성을 기준으로 봇만 중지하는 점검을 적용했다. 장시간 운영·하루 디스크 증가량·호스트 재부팅은 추가 검증해야 한다. 세부 설정과 근거는 [AWS 작업 안내](../../reports/AWS_작업.md#시장-봇을-시작하고-확인하는-방법)를 따른다.

학교 앱의 현재 도메인은 가비아 DNS에서 `www.sang.it.kr`을 app-1의 공인 IP로 연결하고 Nginx가 Let’s Encrypt 인증서로 HTTPS를 처리하는 경로다. 사용자 승인으로 앱 SG의 80·443을 공개했다. 80은 ACME 검증과 HTTPS 이동에만 사용하며, 443은 사용자 웹·API·WebSocket을 제공한다. 443에서 Grafana 로그인과 봇 관리자 로그인을 제공한다. DB와 내부 관측 포트는 지정 SG만 허용한다. 인증서 갱신은 Certbot 타이머와 Nginx 재적용 훅으로 수행하며 모의 갱신에 성공했다. 개인 CloudFront·ACM 연결은 보류했다. 이 경로가 목표 CloudFront·ALB 구성을 대체하지는 않는다. 이후 저속 봇 체결을 확인했지만 고가용성 검증은 남아 있다. 재현 절차와 검증 범위는 [AWS 작업 안내](../../reports/AWS_작업.md)의 도메인 절을 따른다.

페일스톱은 실제 자금을 다루지 않는 가상 자산 거래소다. 사용자는 시세·호가·차트를 보고 주문하며, 회원별 거래 내역과 가상 자산을 확인한다. 게시판·댓글·공지·문의와 관리자 기능도 같은 프로젝트에 있다. 봇은 사용자와 같은 주문 API를 호출해 시장과 실험 부하를 만든다.

아래는 **서비스 연결의 목표 구조**다. 학교 계정에서 ALB·ASG 등을 실제 사용할 수 있는지는 동작별로 확인한다. 학교와 개인 계정의 네트워크 차이는 ADR 0029를 따르며 AWS 자원이 실제로 생성됐다는 뜻은 아니다. 관측 스택, 로드밸런서 경로와 여러 호스트의 연결은 배포 설정에서 마무리해야 한다.

```mermaid
    Report --> Teams
```

웹은 Next.js·React로 개발하고 정적 파일로 배포한다. 별도의 Next.js 런타임 서버는 두지 않는다. 기본 개발 설정은 브라우저 안의 시뮬레이터이므로 실제 거래 검증에는 `NEXT_PUBLIC_DATASOURCE=http`가 필요하다. 서버는 Java 21·Spring Boot, DB는 자체 운영 PostgreSQL 17 계열이다. 요청은 가상 스레드가 아니라 플랫폼 스레드 풀로 처리한다. 2026-09-21 학교 app-1에서 HikariCP가 반납한 연결을 가상 스레드 대기자에게 넘기지 못해 양보 루프에 갇히는 라이브락을 겪었고, 설정을 되돌린 뒤 같은 항목을 다시 측정해 정상화를 확인했다. 원인 경로를 막은 것이며 인계 실패 자체를 고친 것은 아니다. 이 조치는 app-1에만 적용했다. bot-1의 봇·관리 JVM은 설치된 JAR `3362117`의 기본값대로 가상 스레드를 쓰고 있을 가능성이 크지만 서버에서 확인하지 않았고, 끄는 값은 저장소 env 템플릿에만 넣었다. [ADR 0033](0033-no-virtual-threads-for-request-handling.md), [실행 증거](../../../증거본/2026-09-21_앱장애_행/README.md) `server/engine`은 매칭 규칙을 계산하고 `server/app`은 API·DB·정산·리더 전환을 연결한다. 현재 실행 구성에 Kafka나 Redis는 없다. 시작점과 테스트 위치는 [코드 지도](../architecture/프로젝트_코드지도.md), 웹 빌드는 [웹 안내](../../../web/README.md), 서버 실행은 [서버 안내](../../../server/README.md)를 따른다.

CloudFront는 정적 웹을 S3에서, API와 WebSocket을 ALB에서 받아 브라우저 주소를 하나로 유지한다. ALB가 HTTP·WebSocket과 리더 전환을 어떻게 연결할지 실제 대상 그룹·상태 확인·재접속으로 검증해야 한다. 학교는 Default VPC의 Public Subnet을 사용한다. 학교·개인 실습 모두 NAT Gateway를 제외하고 기존 IGW는 유지한다. 개인 계정의 앱 계층은 app-1·app-2 고정과 조회 전용 app-3 자동 증설을 합쳐 2~3대로 계획한다(ADR 0030 사용자 정정 2026-09-25). app-3은 Public Subnet·공인 IPv4·제한 SG를 전제로 하며 실제 배포·확장 정책은 미검증이다. Terraform 예제의 reader ASG는 이 정정에 아직 맞추지 않았다. 과거 nginx edge 설정과 옛 노드 수·비용표를 현재 배포안으로 사용하지 않는다. [ADR 0030](0030-nat-free-lab-and-bounded-read-asg.md), [배포 안내](../../../deploy/README.md)

교수님께 보고한 하이브리드 구성도도 서울 2 AZ, DB 2노드, NAT 2개와 봇·관측 동거라는 방향이다. 수동 확장 표시는 09-18에 설명한 자동 확장 요구로 바뀌었다. 로컬 Docker 도면의 DynamoDB Local은 현재 기본값이 아닌 선택 실험 경로다. DB 장애 시나리오는 단일 DB 중단·재시작이며 E2의 한 앱 접속 경로 차단이나 AWS standby 수동 승격과 구분한다. 원본은 보존하고 촬영 환경·실험 종류를 정확히 표시한다.

외부 시세·콘텐츠 API가 응답해야 거래나 화면이 동작하는 구조는 채택하지 않았다. 필요한 자료는 시드나 웹 빌드에 포함한다. AWS의 저장소·리스·관리 서비스와 통신하는 것까지 금지한다는 뜻은 아니다. 외부 데이터 수집 도구의 결과를 앱에 자동 적재하는 연결은 아직 없다. [외부 API 전략](../contracts/외부API_전략.md), [수집 도구](../../../seed-data/README.md)

운영 보고의 외부 AI·Teams 호출은 거래 처리와 분리한다. 모델이나 보고 작업이 실패해도 주문과 기본 알림은 유지해야 한다. ASG 기본 제어는 AWS 지표 정책이 맡는다. AI 운영 조치는 2026-09-24 사용자가 정한 [ADR 0035](0035-ai-operations-authority.md)의 수동·자동 모드와 허용 목록·한도 안에서만 하고, 서버 재시작·DB 승격을 포함한 금지 목록의 조치는 어느 모드에서도 하지 않는다. AI는 조치 요청만 만들고 AI가 아닌 서버 정책 엔진이 다시 검사해 실행한다. 이 엔진과 AI 판단 서비스는 2026-09-25 저장소에 구현했으나 기본으로 꺼져 있고 어디에도 배포하지 않았다(아래 관제센터 문단). 운영자는 두 모드 어디서든 승인 없이 'AI 즉시 정지'로 AI를 멈출 수 있고, 한도는 운영자가 1인 승인(`ops.ai.limits`)으로만 바꾸며 AI는 바꾸지 못한다. 지금 학교에서 도는 보고 서비스의 AI는 요약만 하고 조치를 실행하지 않는다. 사용자는 2026-09-24 서비스 흐름 화면에 AI를 넣고 이 규칙을 바꿀 예정이라고 했다. 자동 모드가 아니면 AI가 조치안을 제시하는 방식이다. 규칙을 바꾸기 전까지는 위 경계가 현재 기준이다. 학교 bot-1은 Gemini 3.1 Flash-Lite의 HTTPS API와 Teams Workflows를 사용한다. 정상 지표에서 근거 없는 장애 원인이나 조치를 만들어 내지 않도록 제한한다. AI 판단 모델은 2026-09-25 사용자 결정으로 연구소의 온프레미스 추론 서버 `ai-1`(DGX Spark, Ollama)에서 돌리기로 했다([ADR 0038](0038-on-prem-ai-inference-server.md)). 0035가 권한을, 0038이 배치를 정한다. 예정이며 구축 전이다. 모델은 평가로 정하는데 지금 있는 자료는 개발 PC의 RTX 4090 간이 평가뿐이고 Spark 결과가 아니다. AWS와의 연결 경로도 정하지 않았다. `ai-1`이 멈추거나 끊기면 AI 판단과 조치만 없고 경보와 ASG 정책은 그대로 동작한다. 이 결정은 학교 보고 서비스의 Gemini 요약 경로를 바꾸지 않는다.

학교 봇 운영자는 기존 HTTPS의 `/admin/bots`에 아이디·비밀번호로 로그인한다. Nginx가 한 운영자의 로그인만 검증하고 내부 mTLS 신원으로 단기 세션을 연결한다. 운영자 PC 인증서는 요구하지 않지만 Nginx가 추가 신뢰 경계가 된다. 기존 서버의 mTLS·세션·역할 검사는 유지하고 VIEWER·BOT_OPS만 부여한다. 실제 플릿 제어를 위해 관리 API와 봇은 같은 JVM에 둔다. 다중 운영자와 다른 배포 환경으로 이 예외를 자동 확대하지 않는다. [ADR 0031](0031-school-admin-password-gateway.md)

## 자동 확장과 관제를 구현할 때의 경계

먼저 DB에서 완결되는 markets·trades·candles 등의 REST 조회를 별도 ASG로 보내는 안을 검증한다. `engine.enabled=false`는 출발점이지만 모든 쓰기 API를 제거하는 역할 설정은 아니다. 주문·취소·WebSocket은 리더 경로에 유지한다. 호가·티커의 REST 순번도 노드 로컬 값이므로 WS와 같은 기준으로 재동기화할 수 있도록 리더 경로에 남기거나 순번 전달을 먼저 구현해야 한다. 브랜치 `claude/pml-s6`의 S6은 순번 전달을 앱 두 노드 사이에만 구현했다. 마켓을 쥐지 않은 앱 노드는 브로커 모드에서 소유 노드의 미러를 쓸 수 있을 때만 그 순번을 내고, 그 밖에는 기준점이 아니라는 `seq: 0`을 낸다. 조회 노드는 WS와 호가·티커 REST를 받지 않으므로(`ReadRoleFilter`의 404) S8의 ALB는 이 경로를 app-1·app-2로만 보내도록 설계했다(미구축, [S6 설계](../architecture/마켓분할_리더_S6_설계.md) 4-14·4-15). [엔진 구성](../../../server/app/src/main/java/kr/exchange/config/EngineConfig.java), [시장 API](../../../server/app/src/main/java/kr/exchange/api/market/MarketController.java)

인증 API 전체를 바로 분산하지 않는다. 공통 회원 시드 외에도 노드 로컬 데모·관리 키, nonce, 요청 제한의 범위를 확인해야 한다. ASG 준비 검사·최대 대수의 DB 풀·관측 대상 등록·축소 드레이닝을 설계하고, 기존 Docker 용량 조정기가 AWS 정책과 같은 대수를 동시에 제어하지 않게 한다. 현재 WS는 노드 내 브로커이므로 app-3을 켜는 것만으로 리더 이벤트가 전달되지 않는다. S6 브랜치의 브로커 모드도 앱 두 노드만 잇고 조회 노드는 WS를 받지 않는다. [WebSocket 설정](../../../server/app/src/main/java/kr/exchange/api/ws/WebSocketConfig.java), [API 계약](../contracts/백엔드_API_설계.md)

조회 역할은 원격 작업에서 구현돼 통합됐다. [read 프로파일](../../../server/app/src/main/resources/application-read.yml), [경로 제한 필터](../../../server/app/src/main/java/kr/exchange/api/common/ReadRoleFilter.java), [조회 Compose](../../../deploy/compose.node-read.yml)가 엔진·관리 쓰기를 끄고 markets·trades·candles의 GET/HEAD와 관리 상태 조회만 허용한다. 학교 AWS의 ALB·ASG 배포와 실제 부하·축소 검증은 아직 하지 않았다. ALB의 DB 연계 read health와 EC2/ASG의 liveness·교체 조건을 분리하는 설정을 실제 환경에서 검증해야 한다. [ADR 0027](0027-msp-operations-and-autoscaling.md)

2026-09-23에는 로컬 카오스 스택에 조회 전용 노드 한 대를 더 붙일 수 있게 했다. 로드밸런서의 업스트림을 쓰기와 조회로 가르고 조회만 세 노드에 나눈다. 쓰기 업스트림은 페일오버 실측의 전제라 종전 구성을 그대로 뒀다. 증설 노드는 compose 프로파일로 분리해 기본 기동에서 빼고, 용량 조정기가 로드밸런서 등록과 컨테이너 기동을 맞춘다. 조정기는 로드밸런서 설정의 조회 블록 안에서만 노드를 켜고 끄며, 헬스를 다시 통과한 노드만 등록하고 reload가 실패하면 설정 파일을 되돌린다(09-23 저장소 수정, 단위 시험만 확인). 증설 노드 `chaos-api-3`은 AWS 조회 노드 구성(prod,read 프로파일, `ReadRoleFilter`, 읽기 전용 풀)이 아니라 dev,chaos-monkey 구성으로 뜬다. 09-23 리허설은 관리 API와 조정기가 증설·축소를 끝까지 실행하는 절차를 확인한 것이다. 증설 요청부터 3대 관측까지 24.0초, 축소는 드레이닝 10초를 포함해 18.3초였다. 부하 전부터 증설 권고가 떠 있었고 조정기 두 개가 함께 돌았으므로 권고 임계나 분산 효과의 근거로 쓰지 않는다([09-23 측정](../../measurements/20260923.md)). 이것은 로컬 실행 근거이며 학교나 개인 AWS의 ALB·ASG 배포를 대신하지 않는다. 같은 조정기가 AWS 정책과 같은 대수를 동시에 제어하지 않게 한다는 위 경계는 그대로 유효하다. 2026-09-26에는 작업 브랜치에서 오버레이 `harness/docker-compose.read-node.yml`로 `chaos-api-3`을 AWS 조회 노드와 같은 `prod,read` 프로파일, 조회 전용 DB 로그인(`deploy/provision-runtime-roles.sql`로 폐기용 DB에 만듦), 풀 8로 띄워 P3와 파티션·중계 LB 파일(`nginx.partition-relay.conf`)의 조합에서 한 번 확인했다. 조회 GET은 세 노드에 약 3분의 1씩 나뉘었고 9/23과 같은 부하에서 오류가 0이었다. api-3은 LB의 쓰기·`/ws/`·호가·티커 경로를 한 번도 받지 않았고 직접 받은 쓰기는 `ReadRoleFilter`의 `404`로 끝나 아무것도 기록하지 않았다. 계획된 축소·증설과 예고 없는 kill 모두 조회 오류 없이 두 앱 노드로 넘어갔다가 돌아왔다. 조정기는 prod 관리 평면(8081)을 보지 않아 이 오버레이의 api-3을 등록하지 못하므로 그 확인은 실행기가 같은 순서를 직접 했다. 풀 8에서 유도한 조회 동시 처리 상한 4 때문에 9/23 부하의 약 13배에서는 요청의 7.4%가 api-3의 `429`였고 LB는 이를 다시 보내지 않는다. 로컬 단일 호스트의 한 회차이며 ALB·ASG 검증을 대신하지 않는다([기록](../../../harness/evidence/pml-app3-read-20260926-1220/README.md), [09-26 측정](../../measurements/20260926.md)). GitHub `6ee1179`의 Grafana MSP 6개 화면을 재사용하되 호스트 Linux의 파일시스템·inode·I/O·네트워크·서비스 상태를 보강한다. 학교 AWS에서는 호스트 4대와 DB 2대 지표를 연결했고 별도 디스크·용량 화면을 추가했다. 앱·DB의 수집 포트는 봇 SG로만 제한하고 DB 관측은 로컬 peer 인증과 통계 권한을 사용한다. 학교의 SQL 통계 확장·외부 사이트 프로브·CloudWatch는 미연결이다. 앱·DB·디스크 경보는 연결해 발생·해제 보고를 확인했다. 학교에 적용된 규칙은 10개이고 Linux 규칙은 app-1과 DB만 본다. 실제 원천과 조회식을 맞추고 미수집을 정상이나 지연 0으로 해석하지 않는다. 관측 노드 자체의 실패도 외부에서 감지해야 한다. 09-23 저장소에는 bot-1과 주문·정산 카운터를 포함한 학교 규칙 16개, DB 백업 경보, app-1과 bot-1이 서로 관측 경로를 확인하고 Teams로 직접 알리는 워치독과 데드맨 규칙을 만들었다. 학교에 적용하지 않았으므로 현재 구조로 보지 않으며, 적용 순서는 [AWS 작업 안내](../../reports/AWS_작업.md#관측-규칙을-서버에-적용하는-순서)를 따른다. 워치독도 두 노드가 함께 멈추거나 외부 관점이 필요한 장애는 감지하지 못한다. 기존 봇·관측 동거는 자원과 장애를 공유하므로 부하 발생과 보고 작업이 관제를 방해하지 않는 배치·자원 한도를 정한다. 사용자는 메모리가 부족하면 두 역할을 분리하도록 지시했다. 세 마켓의 저속 봇과 관측의 짧은 동시 기동은 확인했으며, 장시간 부하와 보고 작업까지 포함한 자원 여유는 별도 검증한다. S6 브랜치의 WebSocket 중계 브로커(RabbitMQ)는 AWS에서 bot-1 동거가 기본안이다. systemd `MemoryMax=320M`과 메모리 경보 수위 192MiB로 묶고, S8에서 봇·관측·보고와 함께 1시간 돌리는 동안 가용 메모리 최솟값 400MiB 이상, 커널 OOM 종료 0, 브로커 경보 0, 중계 유실 0을 채우지 못하면 별도 소형 노드로 옮긴다. bot-1의 서비스 상한 합이 이미 물리 메모리를 넘으므로 이 측정이 배치의 조건이다. 설계 판단이며 bot-1에 설치하지 않았다([S6 설계](../architecture/마켓분할_리더_S6_설계.md) 4-18). 2026-09-24 관리 콘솔 MSP 관제센터의 2단계 서버 설계를 구현보다 먼저 계약에 올렸다. Prometheus 고정 명명 질의와 Alertmanager 조회, 임계값 레지스트리와 경보 규칙의 지표 참조, 경보 사건과 확인·보류, AI 판단과 서버 정책 엔진을 다룬다. 09-25 그 가운데 읽기 조회, 임계값 레지스트리(V70)와 게이지 `exchange_ops_threshold`, 경보 사건과 확인·보류(V71), 학교 경보 규칙의 레지스트리 참조(게이지가 수집된 적이 없으면 종전 리터럴로 판정)를 저장소에 구현했다. 관리 JVM에서 `exchange.msp.enabled`를 켤 때만 동작하고 학교·로컬 스택에는 적용하지 않았다. 같은 날 AI 판단·조치 경로(V72: AI 신원, 모드와 AI 정지, AI 한도, 계획 작업 창, 판단 기록, 조치 요청)의 서버 쪽도 저장소에 구현했다. 모델은 조치 요청만 만들고, AI가 아닌 정책 엔진이 허용 목록 다섯 종, 한도, 쿨다운, 근거 신선도, 결정적 방향 전제를 다시 검사한다. 자동 실행은 SUPER가 1인 승인 티켓으로 켠 1·2·4·8시간의 자동 모드에서만 일어나고, LLM 주소(`exchange.msp.llm.base-url`)를 주지 않으면 판단 자체를 하지 않는다. 이 경로는 가짜 LLM 스텁과 Testcontainers로 시험했고, 09-25에는 로컬 RTX 4090의 Ollama 모델 두 개로 운영 코드의 근거 수집·출력 검증·정책 판정을 거쳐 평가했다(원천 값은 시험용이고 조치는 실행하지 않음, [측정 09-25](../../measurements/20260925.md)). 그 평가에서 모델이 경보 요약에 끼워 넣은 명령문을 따랐으므로, 모델에 가는 근거에는 경보 주석과 사람이 쓴 문장을 싣지 않고 경보명·라벨 값도 형식을 거른다. 형식 밖 값이 든 경보는 AI가 보류하지 않는다(S8). 자동 모드는 임계값을 민감한 방향(경보를 일찍 울리거나 증설을 일찍·축소를 늦게 하는 쪽)으로만 옮기고, 둔하게 하는 변경은 사람의 승인으로만 실행한다(T6, 사용자 결정 2026-09-25). 학교·로컬 스택에는 적용하지 않았으므로, 배포된 구조에서 AI는 여전히 운영 조치를 실행하지 않는다. 이어서 AI 상담, 요약 추세, 원천 공유 캐시, Teams 통지 보관함(V73), AI 서버 상태의 서버 쪽을 구현했다. 상담은 질문 시점의 근거로만 답하는 읽기 전용 경로이고 상태를 바꾸는 호출이 없다. 요청률·5xx 비율·응답 p95·가용성은 Prometheus 기록 규칙(학교 `school-alerts.yml`, 하네스 `exchange-recording.yml`)이 미리 계산하고 관제센터는 규칙 이름만 질의한다. AI 판단 주기는 매칭 리더와 무관한 DB 임대로 여러 관리 JVM 가운데 한 곳에서만 돈다. Teams 통지는 관리 JVM이 Teams를 직접 부르지 않고 보고 서비스(`deploy/reporting`)의 새 수신 경로로 넘겨 같은 카드 언어·보관함·재시도로 보내며, 모델의 자유 문장은 카드에 싣지 않는다. 이 부분도 가짜 LLM 스텁, Testcontainers, 보고 서비스 단위 시험으로만 확인했고 학교·로컬 스택에 적용하지 않았다. 사용자가 09-24 확정하고 09-25 보강한 [ADR 0035](0035-ai-operations-authority.md)가 이 자동 실행을 허용하고 ADR 0027의 해당 원칙을 대체한다. 09-25 화면과 서버를 병합하면서 이 문서의 운영 보고 문단, ADR 0027의 후속 표기, `AGENTS.md`의 AI 조치 문장을 그 범위로 맞췄다. 설계 중 저장소 설정에서 세 가지를 읽었다. 학교의 관리 API는 bot-1의 봇 JVM에 있어 같은 호스트 루프백의 Prometheus·Alertmanager에 SG 변경 없이 닿는다. 같은 이유로 용량 보호가 봇 서비스를 멈추면(어느 노드든 디스크 여유 20% 이하이거나 파일시스템 지표가 3분 남짓 빠짐) 지금의 관리 API도 함께 멈추고 자동으로 다시 시작하지 않는다. 관제센터 설계는 이 때문에 경보 규칙이 게이지의 마지막 값을 쓰게 했다. Flyway `out-of-order`를 켜지 않았으므로 V70 이후를 먼저 적용한 DB에는 마켓별 리더의 V48~V69를 넣을 수 없고, 로컬 스택은 이미지 태그 하나와 Flyway를 켠 `chaos-api-1`을 쓰므로 이 순서가 사람의 주의에만 달려 있다. 이 순서는 앱의 적용 전 점검(스프링 기동과 `MigrateSchema`)이 기계적으로 막고, 두 진입점이 V47.1까지 적용한 DB에서 적용 전에 멈추는 것을 시험으로 확인했다. ## 주문과 데이터의 흐름

주문에는 클라이언트가 만든 `client_order_id`가 필요하다. 응답이 늦거나 결과가 불명확하면 같은 키로 상태를 조회하고 재시도한다. 서버는 요청 제한과 인증을 거쳐 내용·잔고·멱등성을 검사하고, 해당 마켓의 접수 잠금 안에서 명령을 `command_journal`에 확정한다. 그다음 같은 리더 프로세스의 마켓별 라이터가 명령을 순서대로 매칭한다. 마켓을 나눴어도 회원 자산과 DB는 공유하므로 서로 완전히 독립된 시스템은 아니다.

정산은 한 명령의 처리 결과를 이벤트·주문·체결·원장·잔고에 같은 트랜잭션으로 반영한다. 저장 후 WebSocket으로 호가와 체결을 알린다. 웹은 연결이 끊기거나 메시지를 놓치면 REST 조회로 상태를 맞춘다. 명령 저장, 주문의 조회 반영, HTTP 응답 완료는 서로 다른 시점이다. `order_in_progress`나 타임아웃을 주문 부재로 판단하지 않는다. [주문 접수](../../../server/app/src/main/java/kr/exchange/api/order/OrderGateway.java), [엔진 전달](../../../server/app/src/main/java/kr/exchange/engine/EngineBridge.java), [정산](../../../server/app/src/main/java/kr/exchange/ledger/SettlementService.java)

금액·가격·수량은 서버에서 `BigDecimal`, DB에서 `NUMERIC(40,18)`, API에서 십진 문자열로 다룬다. 예약, 정산, 환급, 수수료의 반올림은 각각 계약을 따른다. 시간이나 통계까지 모든 숫자를 같은 타입으로 바꾸라는 규칙은 아니다. 부하 제한은 현재 쓰기·조회·재조회 세 버킷이며 풀 기준 비율은 40/40/10이다. ADR 0007의 제목만 보고 두 버킷으로 되돌리지 않는다. ## 앱 복구와 DB 장애는 다르게 처리한다

리더 권한은 클러스터당 하나다. 기본 제공자는 PostgreSQL 리스이고 DynamoDB 구현도 선택할 수 있다. 어느 쪽이든 거래 쓰기의 마지막 권한 검사는 PostgreSQL 트랜잭션 안에 남는다. 현재 검사 함수는 리스 행을 `FOR KEY SHARE`로 잠가 시간 갱신은 허용하고, holder·epoch 교체는 진행 중 쓰기와 직렬화한다. 이 동작에는 V41의 `(resource, holder, epoch)` UNIQUE 인덱스가 필수다. 작업 브랜치의 V48부터는 앱이 리스 이름을 넘기지 않고 DB가 기록할 행의 마켓으로 리스 행을 찾으며, P1에서는 그 행이 `matching-engine`이라 판정과 epoch 증가가 V47까지와 같다. 리스 함수는 소유자 권한으로 바뀌고, DynamoDB 리스는 파티션 모드(P3)에서 기동을 거부한다. 작업 브랜치의 V50부터 리스 획득과 epoch 게시는 바이너리가 아는 최고 모드를 받아, P2의 예약 정산을 모르는 S3 이전 바이너리가 P2 DB에서 리더가 되지 못하게 한다. 모드 전환 함수는 모든 리스 행을 잠가 진행 중 쓰기가 끝나기를 기다린 뒤 모든 리스 행을 새 epoch로 퇴역시키므로, 전환 전 epoch로는 어떤 쓰기도 통과하지 못한다. V52부터 획득한 리스의 만료 시각은 행 잠금을 얻은 뒤부터 센다. V1 이래의 획득(main과 학교 서버 포함)은 잠금 대기 전 시각에서 세므로, 멈춘 옛 리더의 쓰기를 TTL보다 오래 기다린 획득이 이미 만료된 리스를 받아 새 리더가 첫 쓰기에서 강등되고 리더가 없어질 수 있다. S3 관문의 E7(P2)에서 실제로 났고, 학교는 엔진을 켠 앱이 한 대라 이 승격 경로가 아직 없다([DB 설계 §3.7](../contracts/백엔드_DB_설계.md)). 작업 브랜치의 S4부터 리스 서비스는 파티션마다 하나이고 holder는 노드 하나를 공유한다. 획득 트랜잭션에만 `lock_timeout`을 걸어 옛 리더의 쓰기를 기다리는 획득을 1초마다 끊고, 쓰기는 획득 때 만든 기간의 epoch로만 판정받아 강등 전 스레드가 재승격한 새 epoch를 빌려 쓰지 못한다. 강등은 DB에 쓰지 않고 갱신만 멈추므로 다음 리더는 여전히 만료 뒤에만 정해진다([S4 설계](../architecture/마켓분할_리더_S4_설계.md) 4-3·4-5·5절, [DB 설계 §5.4-c](../contracts/백엔드_DB_설계.md)). 팔로워 앱은 평소 마켓별로 저널을 따라가며 엔진 상태를 검증한다. 승격 시 모든 마켓의 최신 위치에 도달해 있으면 재생을 생략하고 그 엔진을 설치한다. 복구가 필요하면 마켓별로 채택 가능한 스냅샷을 읽고 이후 명령을 재생한다. 이미 정산된 구간은 각 마켓의 연속 물질화 경계까지 검증하고 미완료 꼬리를 다시 처리한 뒤 접수를 연다. 손상된 스냅샷은 해당 마켓에서 제외하고 이전 스냅샷이나 전량 재생으로 돌아간다. 스냅샷 저장에도 같은 트랜잭션 안의 리더 권한 검사가 연결돼 있다. 과거 ADR의 “스냅샷 미배선”이나 “저장 시 권한 검사 없음”은 현재 상태가 아니다. [승격 분기](../../../server/app/src/main/java/kr/exchange/engine/PromotionCoordinator.java), [EngineRecovery](../../../server/app/src/main/java/kr/exchange/engine/EngineRecovery.java), [SnapshotStore](../../../server/app/src/main/java/kr/exchange/snapshot/SnapshotStore.java)

DB는 primary 한 대와 standby 한 대의 비동기 복제다. 동기 `ANY 1`의 3노드 안은 ADR 0024가 대체했다. primary가 사라지면 운영자가 옛 primary를 격리하고 standby를 승격한 뒤 앱의 DB 연결을 바꾼다. 돌아온 옛 노드는 전체 베이스백업으로 다시 편입한다. `pg_rewind`를 위한 추가 WAL 보존·아카이브는 채택하지 않았으며 재편입 동안 이중화 공백이 생긴다. 별도의 백업·복원 검증은 여전히 필요하다. [DB 수동 페일오버](../operations/DB_수동_페일오버.md)

2026-09-25 [ADR 0036](0036-patroni-strict-sync-db-failover.md)이 이 구성을 Patroni 엄격 동기 2노드(etcd 세 표: db-1·db-2·bot-1, 앱·봇 노드마다 HAProxy 사이드카)로 바꾸기로 했다. 그 구성에서는 확인된 커밋이 동기 Standby에도 있고 Patroni가 `/sync`의 동기 Standby만 승격하며 옛 Primary를 되감아(실패하면 자동 재초기화) 다시 붙인다. 동기 Standby가 없으면 PostgreSQL이 커밋을 끝없이 기다리므로, 앱은 WAL을 쓰는 탐지 커밋으로 이를 알아채 쓰기를 DB에 닿기 전에 `423 trading_suspended`로 거절하고 조회는 계속 받는다. 공개 상태 API `GET /api/v1/status`와 거래 화면의 '거래 일시 중단'이 그 상태를 보인다. 중단은 DB 쪽 확인(동기 설정 `'*'`나 탐지 커밋의 `SyncRep` 대기)이 있을 때만 판정해, 한 앱 노드의 경로만 느린 경우를 클러스터 중단으로 보지 않는다. `423`은 '이 시도는 쓰지 않았다'는 뜻이고, 인그레스가 다시 보낸 시도일 수 있어 클라이언트는 재개 뒤 같은 키로 다시 내거나 재조회한다. 리스 갱신만 로컬 커밋으로 해 2026-09-08의 리스 연쇄를 끊고, epoch를 바꾸는 획득은 동기 커밋이며 쓰기를 받는 동안에만 한다. 커밋 대기에 걸린 획득은 풀리는 순간 만료된 리스를 주기 때문이다. 대가로 DB 노드 하나를 잃으면 그 노드가 Standby로 돌아올 때까지 거래가 멈춘다. 호스트를 영영 잃으면 사람이 새 인스턴스와 etcd 멤버를 갖춰 새 Standby를 붙일 때까지 멈추고, 그 절차와 목표 시간(경보부터 60분, AI 제안)은 설계 9-5에 있다. 단일 노드 장애의 유실 0은 하네스 E-P1·E-P3·E-P5가 PASS한 환경에서만 주장하고, 두 노드를 함께 잃는 이중 장애는 WAL 보관이 없어 범위 밖이다. 이 주장은 동기 대기 서버가 될 수 있는 것이 Patroni 멤버뿐이라는 운영 조건도 전제한다. 사전 확인에서 Patroni가 동기 Standby를 잃었을 때 거는 `'*'`는 멤버가 아닌 복제 스트림(`pg_receivewal`, 임시 슬롯의 `pg_basebackup`)을 동기 대기 서버로 받아 한 사본만으로 커밋을 확인했다. 그래서 베이스백업과 학교 예약 백업 도구는 `--no-slot`으로 하고, 멤버가 아닌 복제 클라이언트를 금지하며, 경보로 잡는다. 폐기용 PostgreSQL 17.10 두 노드의 사전 확인에서 동기 대기는 `statement_timeout`으로 끝나지 않았고 취소 요청은 복제되지 않은 로컬 커밋을 성공으로 돌려줬다. 그래서 커밋 대기의 취소·종료를 금지 규칙으로 둔다. 커밋 대기 중에 postmaster가 크래시 재시작을 하면 기다리던 행이 복제 없이 보였으므로, 앱은 그 뒤 다시 확인된 탐지가 나오기 전에는 재조회·저널 확인의 확정 응답을 미룬다. 2026-09-25 현재 작업 브랜치에 앱의 탐지기·쓰기 게이트·상태 API·리스 규칙, 웹의 거래 일시 중단 화면, 로컬 실험 스택(`harness/patroni/`)과 판정 도구가 있다. 코드 검토 대응 뒤 이미지로 로컬 Docker에서 돌린 한 벌에서 E-P1, E-P2a, E-P2b, E-P3a, E-P3b, E-P4a, E-P4b, E-P5(두 번), E-P6(되감기와 재초기화)가 PASS였고, 모든 회차에서 DB 수준 ACK 유실, C16, 사후 불변식 위반, 구 epoch 쓰기, 주문 `500`이 0이었다. 그래서 단일 노드 장애의 유실 0은 로컬 Docker 한 호스트에 한해 확인됐다. E-P1b는 리더 키를 쥔 채 재기동한 노드를 Patroni가 다시 승격해 타임라인이 올라 처음 판정에서 '타임라인 불변' 축이 FAIL이었으나, 사용자가 타임라인 변경을 Patroni의 정상 동작으로 보고 기록 항목으로 확정해(2026-09-25) 기록된 회차를 다시 판정한 결과가 PASS다(유실 0·안전 축은 관문 그대로, '재연결 뒤 첫 확인 탐지 전 확정 응답 0'은 판정 도구에 축이 없음). E-P5는 V47 경로를 지나지 않았으며, E-P2c·E-P4c·E-P8·E-P9는 돌리지 않았다. AWS에는 적용하지 않았으므로 학교·개인 계정에서의 유실 0은 주장하지 않는다. 판정과 증거는 설계 15절, 남은 일은 [로드맵](../../ROADMAP.md)에 있다. AI는 어느 모드에서도 DB 승격·페일오버를 실행하지 않는다(ADR 0035, 다른 작업 브랜치). `AGENTS.md`의 '자동 DB 페일오버는 아직 선택·구현하지 않았다'는 이제 '선택했으나 구현하지 않았다'가 맞고, 문장 수정은 사용자 확인을 기다린다. [Patroni 설계](../architecture/DB_자동전환_Patroni_설계.md), [사전 확인](../../../harness/evidence/patroni-sync-probe-20260925/README.md)

비동기 복제에서는 이미 접수 응답을 받은 주문도 standby에 도착하기 전에 primary가 사라지면 잃을 수 있다. 저널도 같은 DB에 있으므로 유실된 저널을 재생으로 복원할 수 없다. 남은 기록을 정확히 재처리한다는 보장과 DB 교체 중 무손실 보장은 다르다.

## 회원·화면·운영 기능의 경계

회원은 세션과 API 키로 자신의 가상 자산·주문·거래 내역에 접근한다. 봇과 회원의 계정·권한은 구분한다. 관리 기능은 별도 인증과 관리 프로파일에서 실행하고 공개 웹 빌드에서는 관리 화면을 제거한다. 이 제거는 경로 이름 기준이라 공용 청크에 섞인 관리 코드는 남는다. 학교 빌드는 제거 단계를 거치지 않아 관리 화면 정적 파일 전체를 공개 번들에 싣고, ADR 0031의 예외는 `/admin/bots` 하나다. 공개 범위는 사용자 결정 대기다. 관리 API·관리 포트·하네스 실행 경로는 외부 사용자에게 열지 않는다. `prod,admin`을 실행할 때는 예시 인증서 대신 운영용 클라이언트 인증서를 준비해야 한다. [회원 설계](../product/회원_설계.md), [관리자 설계](../product/관리자_설계.md), [웹 배포 절차](../../../web/README.md)

운영 승인은 현재 1인이 수행할 수 있다. 승인 티켓의 유효시간, 단회 사용, 액션·대상·요청자 확인은 유지한다. 기존 카오스 API도 코드에 남아 있지만 AWS 단계의 새 개발 목표가 아니다. 수동 용량 API의 `desired_nodes` 변경은 현재 남아 있는 구현이며, 새 목표인 AWS 지표 기반 자동 확장과 실제 ASG 관측은 아직 연결해야 한다. [확장 API](../../../server/app/src/main/java/kr/exchange/admin/CapacityAdminController.java)

2026-09-23에 관리 콘솔을 운영 관제와 백오피스 두 평면으로 갈랐다. 2026-09-24 사용자 요구로 운영 관제 내비를 관제(관제센터, 경보·사건, AI 판단), 인프라(서버·노드, 데이터베이스, 용량·부하), 조치(임계값 관리, 봇 플릿), 시연(서비스 흐름, 지표 관제) 네 묶음으로 개편하고 상황별 대본 화면을 지웠다. 2026-09-25 사용자 요구로 사이드바 전체를 MSP 관점에서 넓히는 3라운드 계약을 구현보다 먼저 올렸다. 묶음은 관제·인프라·조치·보고·시연 다섯과 바닥 줄의 설정이고, 새 화면은 네트워크·보안, 변경·작업, 조치 기록, 런북, SLA 월간 보고, 비용, 시나리오다. 같은 날 구현 묶음 A로 경보·사건(담당 자동 배정과 지정, 5·15·30분 단계별 호출, 사후 분석), AI 판단(감사에서 읽는 모드·정지 이력, `ai-1` 상태, 모델 평가), 서버·노드(자산 표), 데이터베이스(복제 방식, DB 통계, 전환 절차)를 구현했다. 이어 구현 묶음 B로 용량·부하(CPU 크레딧과 크레딧 모드, 용량 전망, app-3 활동 기록, 부하 시험 기록), 네트워크·보안(설계 의도로 표시한 허용 경로 표, 인증서 만료, 관리 접근 기록), 변경·작업(계획 작업 창과 1인 승인 변경 요청, 달력), 조치 기록(감사에서 옮긴 사람·AI·시스템 조치, 상세, CSV), 런북(실행 단추 없는 절차와 명령 복사)을 구현했다. sim의 AI 경보 보류는 열린 계획 작업 창 안의 주의 경보만 내고 창 끝을 넘지 않는다([ADR 0035](0035-ai-operations-authority.md)의 창 정책). 이어 구현 묶음 C로 SLA 월간 보고(관제 판이 닿는 최근 날은 판의 사건 기록과 추세로, 그 앞은 시뮬레이터 예시로 센 달과 근거 수가 붙은 권고), 비용(크레딧 대비 계획 계산과 app-3 가동 비용. 실제 청구액은 두 계정 모두 원천 연결 전), 시나리오(관제 판과 따로 도는 재생 세계 아홉, 수동·자동·비교 보기, 사람 몫은 재생 대본), 설정 확장(호출 단계와 당번, 알림 채널, 역할·권한 행렬)을 구현했다. 같은 묶음에서 경보 확인·보류와 AI 조치안 승인·되돌리기 단추의 요구 역할을 서버 계약(봇 운영 이상, 조치 종류별)에 맞췄다. sim의 호출은 밖으로 보내지 않고 사건 기록에만 남긴다. 서버에 없는 경로(사건 담당·호출과 사후 분석, 변경 요청, 호스트 자산, DB 통계, 용량 전망, 인증서·공개 포트 점검, SLA, 비용)는 계약 초안이라 http 원천에서 원천 연결 전이고, 조치 기록은 기존 감사 로그와 조치 요청 목록을, 계획 작업 창은 기존 서버 경로(등록·조기 종료 포함)를 쓴다([관리자 설계 4-10](../product/관리자_설계.md)). 대본의 판정 기준은 [관리자 설계 4-5](../product/관리자_설계.md)로 옮겼다. 백오피스는 새 진입점 `/admin/back`(처리 대기)을 두고 기존 일곱 화면의 주소를 그대로 둔다. 웹의 카오스 주입 화면은 제거했고 서버 API는 남아 있다. 종합 관제 `/admin`은 같은 날 MSP AI 관제센터로 바꿨다. 관제센터는 추이 그래프 대신 현재값·임계 눈금·상태·조치·기록을 두고(상태 요약 칸의 작은 추세선만 예외다. 아래 09-25 개편), AI 판단과 조치 카드, 수동·자동 모드 스위치, 두 모드의 AI 즉시 정지와 재개, 경보 확인·보류, 1인 승인을 거치는 임계값 변경·되돌리기, Databasus 백업 판독을 싣는다. AI 판단 화면에서는 AI 한도를 1인 승인으로 바꾼다. 1단계라 값은 브라우저 시뮬레이터(`opsSim.ts`)가 만든다. http 데이터 원천은 관리 API의 한 판 조회(`GET /admin/v1/msp/overview`) 한 건을 읽어 환경과 원천 상태만 옮긴다. 그 서버는 09-25 병합으로 같은 트리에 들어왔고 기본으로 꺼져 있다(`exchange.msp.enabled`, 끈 배포는 404). 병합 뒤 http 원천을 그 서버 계약에 이었다. 한 판을 `ETag`로 15초마다 읽고 조치 요청·판단·한도·이력·사건·1시간 추세 같은 세부 조회는 한 판의 서명이 바뀌었거나 수명이 지났을 때만 한두 건씩 붙이며, 경보 확인·보류, 조치 승인·거절·나중에·되돌리기, 자동 모드(1인 승인), 즉시 끄기, 정지·재개, 임계값·한도 변경, 상담, 보고서 읽기를 서버 경로로 보낸다. 서버에 없는 값(거래 칸, 인증서, Databasus, 호스트별 마켓 묶음, `ai-1` 장비 정보, 연락 체계, Teams 연결 시험)은 원천 연결 전이고, 서버 칸의 실패는 불러오기 실패 모양으로 연결 전과 가른다. 서버 통합 시험이 낸 응답 스냅숏 53건으로 어댑터를 시험하고 그 스냅숏을 내는 가짜 관리 API 뒤에서 http 빌드를 캡처했을 뿐 실제 관리 JVM·원천·모델과는 붙여 보지 않았다. 확인은 sim 원천의 웹 단위 시험과 브라우저 캡처뿐이다. 서버 정책 엔진, 임계값 레지스트리, Alertmanager·Databasus 연결은 2단계 설계안이다([관리자 설계 4-4](../product/관리자_설계.md)). 콘솔은 추이를 그리지 않고 Grafana로 딥링크한다. 이 규칙과 두 평면 분리를 정한 ADR은 따로 없고, 근거로 들던 ADR 0032는 Grafana 기본 관제와 별도 운영 콘솔(`deploy/console`)만 다룬다([관리자 설계 7-10](../product/관리자_설계.md)). 서비스 흐름과 지표 관제 화면은 AWS 목표 구성을 로컬 Docker `exchange-chaos` 스택으로 대신해 측정 기록을 재생하는 시안이다. 지표 관제는 콘솔 안에 추이를 그려 위 규칙과 부딪친다. 2026-09-25 보정 A부터 두 화면은 재생하지 않는 동안 관제 시뮬레이터의 한 판에서 값을 옮겨(관제 값 모드) 관제센터와 같은 값을 그리고 화면 머리에 '시뮬레이션' 표식을 둔다. 로컬 측정 기록을 재생하는 동안에는 '재생 · 관제 값과 별개' 표식을 크게 둔다. 사용자는 2026-09-24 서비스 흐름 화면을 채택해 실제 값과 연동하고 발표 실험을 그 화면에서 하기로 정했다. 연동은 아직 하지 않았으므로 지금 화면은 여전히 재생 시안이고, 위의 추이 규칙과의 충돌도 그대로 남아 있다. 지표 관제 화면의 채택·보존·폐기는 사용자 결정 대기다([로드맵](../../ROADMAP.md)). 학교 공개 웹은 이 개편 전 묶음(`origin-20260920`)이라 삭제한 카오스·모니터링 화면 파일이 남아 있다. 이 변경은 저장소의 화면 구성이며 학교나 개인 AWS의 배포 상태를 바꾸지 않는다. [관제 시뮬레이터](../../../web/lib/admin/opsSim.ts), [관리 내비](../../../web/lib/admin/nav.ts) 2026-09-24 사용자가 관리 콘솔 디자인 개선 B안(관제센터형)을 골랐고, 서비스 흐름에 재생 출처 칩, 상황 자막, 상태 전이 강조, AI 운영 보고·Teams 자리(연결 전 표시, 조치 버튼 없음)를 두는 화면 규칙을 구현보다 먼저 계약에 적고 같은 날 웹에 구현했다([관리자 설계 7-10](../product/관리자_설계.md), [디자인 시스템](../contracts/프론트_디자인시스템.md)). 출처 칩의 보이는 문구는 위 보정 A의 표식으로 바뀌었고, 그 문구와 자리는 AI가 고른 뒤 2026-09-25 사용자가 기본값 유지로 확정했다. 이 선택은 표현 규칙이라 채택 결정과 추이 규칙의 충돌을 풀지 않는다. 2026-09-25 사용자 요구로 관제센터를 다시 다듬었다. 운영자 바에 관제 검색, 전체 상태(정상·주의·장애), 경보 종과 현재 시각을 두고, 상태 요약 칸에 앞 구간 대비 증감과 1·6·24시간 작은 추세선을 더했으며(탐색은 여전히 Grafana), 인프라 칸을 역할 묶음(앱 app-1·app-2, 데이터베이스 한 묶음, 조회 ASG, 관측 bot-1, 온프레미스 ai-1)으로 나눴다. 서비스 흐름은 Auto Scaling 상자가 조회 노드만 감싸게 고치고 온프레미스 `ai-1`과 '판단 요청 · 연결 경로 결정 전' 점선을 더했다. 추세선의 앞 구간과 `ai-1` 지표는 시뮬레이터가 지어낸 값이다. 같은 날 사용자 결정으로 관리 콘솔의 문장 문구를 합니다체로 바꾸고 라벨은 명사형으로 두었다([디자인 시스템 §10-1](../contracts/프론트_디자인시스템.md)). 같은 날 후반에는 조회만 하는 AI 상담 패널(조치를 부탁하는 말은 실행하지 않고 조치 카드와 승인 절차로 안내한다), bot-1 보고 서비스가 Teams로 보낸 보고를 읽는 보고서 화면, 연동 상태와 연락 체계를 보는 설정 화면을 더했다. 병합 뒤 http 원천에서 상담과 보고서는 서버 경로를 읽고, 보고서는 읽기 프록시가 목록 요약만 주어 본문이 연결 전이며, 연락 체계와 Teams 연결 시험은 서버 계약에 없어 연결 전이다. 관제 데이터 폴러와 시계는 콘솔 공용 박자 하나로 모아 숨은 탭에서 멈추고, 용량·부하 화면의 sim은 관제 시뮬레이터의 조회 ASG와 같은 모델로 맞췄다([관리자 설계 4-1, 4-6~4-8](../product/관리자_설계.md)). 같은 날 디자인 평가(63/100)의 신뢰·정합·배치 감점을 고친 보정 A에서 관제 시뮬레이터를 sim 화면들의 단일 원천으로 모았다. 봇 발행률, 파티션 리더(p0 app-1 · p1 app-2, 옛 engine-01 모델 제거), 조회 노드 대수와 CPU, 증설 임계, 복제, 수집 대상, Teams 전송과 구축 전 `ai-1`의 '시뮬레이션 가정'을 모든 화면이 같은 판에서 읽고, 그 일치를 웹 단위 시험(`web/tests/simWorld.test.ts`)으로 고정했다. 'AI 즉시 정지'는 상담 패널이 가리지 않게 운영자 바로 옮겼다. 세부 선택은 2026-09-25 사용자가 기본값 유지로 확정했다([관리자 설계 4-4, 7-10 (l)](../product/관리자_설계.md)). 같은 날 보정 B에서 한 대상을 깊이 보는 층 다섯(노드 상세, 주소 `?incident=`로 여는 사건 드로어, 정책 엔진의 규칙별 통과·막음 표를 싣는 AI 판단 상세, 보고서 카드, 조치 확인)을 더하고, 경보·승인·조치·되돌림·정지 순간에 움직임 줄이기 대체가 있는 전이를 두었으며, 용량·봇·백오피스를 관제 화면과 같은 부품(화면 머리, 상태 칩, 판독 묶음, 분절 조작)으로 모았다. 판단 과정의 검사표와 조치 카드의 대기 이유는 시뮬레이터의 한 검사표에서 나온다. 층은 조회와 기존 승인 절차만 열고 새 실행 경로를 만들지 않는다. 모두 sim 원천의 화면이고 세부 값은 사용자 확인 전이다([관리자 설계 4-9, 7-10 (m)](../product/관리자_설계.md)). 같은 날 사용자 정정([ADR 0030](0030-nat-free-lab-and-bounded-read-asg.md))으로 sim에서 read-1~3을 지우고 앱 계층을 app-1·app-2 고정과 조회 전용 app-3 자동 증설(2~3대)로 바꿨다. 관제센터 인프라 칸은 앱 계층 묶음 안에 app-3 Auto Scaling 띠를 두고, 서비스 흐름의 Auto Scaling 상자는 app-3 자리만 감싸며, AI 조치안은 'app-3 켜기(앱 2 → 3대)'와 'app-3 끄기'로 적는다. 앞 문장들의 조회 ASG·조회 노드는 이 정정 전 표현이다. 화면 간 일치 시험도 이 모델로 고쳤다.

게시판 설계에는 별도 DB·프로세스 격리가 남아 있지만 현재 앱 구성은 거래와 같은 DB 연결·회원 세션 서비스를 사용한다. 글·댓글 기능 완료와 물리 격리 완료를 구분한다. 요구를 유지해 구현을 분리할지, 현재 배치를 받아들이고 계약을 바꿀지 결정한 뒤 부하 간섭을 검증해야 한다. [게시판 설계](../product/게시판_설계.md), [ApiConfig](../../../server/app/src/main/java/kr/exchange/config/ApiConfig.java)

화면의 세부 동작과 표현은 [레이아웃](../contracts/데스크톱_레이아웃설계.md), [디자인 시스템](../contracts/프론트_디자인시스템.md), [대시보드](../product/대시보드_설계.md), [차트](../product/차트_기술적분석_설계.md), [체결 효과](../product/체결_시각효과_관리자제어_설계.md), [화면 명세](../contracts/웹_화면명세서.html)에 둔다. 이 문서에 모든 화면 필드와 SQL을 복사하지 않는다.

## AWS로 옮기는 순서

[ADR 0029](0029-school-aws-first-personal-account-expansion.md)에 따라 VM 선행 조건은 보류한다. 학교 EC2에서 직접 운영을 검증하고 10월 초 개인 계정으로 재배포한다. Docker·학교·개인 계정 결과에 각각 환경과 실제 실행 근거를 연결한다. 명령과 설정 변경 화면은 [증거본](../../../증거본/README.md)에 보관한다.

### 1. 유료 자원을 만들기 전에 배치와 권한을 확정한다

학교 실습은 t3.small 이하의 x86_64 환경이다. 기존 ADR 0010의 Rocky Linux 10·Graviton 계획에서 아키텍처 제한과 OS 선택을 구분한다. t3 제한이 Rocky 대신 Amazon Linux를 써야 한다는 뜻은 아니다. 첫 EC2 생성 후 차이를 설명했고 사용자가 학교 실습의 Amazon Linux 2023 사용을 확정했다. 현재 생성한 첫 앱 노드는 한 대와 gp3 20GiB이며 전체 시스템 규모가 아니다. 역할별 분리를 전제로 계정 전체 EBS 한도·추가 노드·패키지 지원·기존 역할·접속 경로를 확인한다. 실제 진행 상태는 [로드맵](../../ROADMAP.md)에서 확인한다.

앱·DB 2대·봇 및 관측 노드를 어느 AZ와 서브넷에 둘지, 어떤 포트로 통신할지 정한다. 허용된 CloudFront·S3·ALB·볼륨·로그 등의 규격과 사용 시간으로 비용을 산정한다. 학교 견적에 금지된 NAT를 넣지 않으며 개인 환경 견적은 따로 계산한다. 운영 예산은 월 40만 원이며, 이전의 총 지원금 해석을 대체한다. 전액 사용은 사용자가 설명한 조건이며 실제 지급·정산 조건·잔액·청구액은 미확인이다. ADR에 적힌 과거 가격과 잔액은 현재 견적이 아니다. 생성·변경·철거는 Terraform 또는 동등하게 재현 가능한 절차로 남긴다. 저장소에서 완성된 Terraform 배포 구성을 확인하지 못했으며, 이미지 빌드 CI가 곧 배포 자동화는 아니다. [CI·배포 계약](../contracts/하네스_CICD_IaC.md), [이미지 빌드](../../../.github/workflows/image.yml)

학교 EC2에서 운영 검증·촬영을 진행하고 개인 계정에서 제한됐던 부분을 보강한다. 학교 배치를 과거 보고본 전체의 구현으로 설명하지 않는다. 가동 시간과 재촬영 여유를 산정하고 필요한 외부 접속 유지 기간을 확인한 뒤 종료일을 정한다. 화면·명령·검증 원자료를 보관하고 보존할 데이터와 철거할 자원을 구분한다. EC2 중지 뒤에도 볼륨 등 비용이 남는 점은 [배포 안내](../../../deploy/README.md)에서 확인한다.

학교 계정은 Route 53·ACM·NAT·Private Subnet·VPC Endpoint 구성과 새 IAM 사용자·역할·Access Key 발급을 금지한다. 기존 인스턴스 프로파일의 연결 권한과 필요한 `iam:PassRole`을 확인한다. SG는 빈 인바운드로 생성한 뒤 username 자동 태그를 확인한다. SSM 접속은 에이전트·역할·네트워크가 모두 필요하며 실제 사용 가능 여부를 검증한다. 학교에서는 수동 배포를 따른다. MFA와 IAM 거부를 우회하지 않는다. [ADR 0029](0029-school-aws-first-personal-account-expansion.md), [EC2 역할 연결 권한](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/permission-to-pass-iam-roles.html), [SSM 준비 조건](https://docs.aws.amazon.com/systems-manager/latest/userguide/getting-started-launch-managed-instance.html)

첫 Linux 운영 설정은 journald 영구 저장과 실습용 보존 한도다. 재부팅 한 번 뒤 이전 부팅의 시험 로그·SSH 재접속·기본 서비스·루트 마운트를 확인했다. [설정과 재현 절차](../../../deploy/README.md), [실행 증거](../../../증거본/2026-09-19_학교AWS/README.md)에 연결한다. 이는 호스트 기본 동작의 확인이며 거래 앱·DB의 재기동과 데이터 복구를 검증한 것은 아니다.

첫 앱은 Java 21·로그인 불가 서비스 계정으로 별도 DB에 TLS 연결하며 systemd로 실행한다. 비공개 S3의 승인된 JAR을 기존 Role로 내려받아 해시를 대조했다. 신규 거래 DB에 V0~V46을 적용·검증했고 소유자 계정은 NOLOGIN, 실행 계정은 app_role을 상속한다. 저장소에는 2026-09-23에 V47, 09-24에 V47.1, 09-26 마켓별 리더 병합으로 V48~V55가 추가됐지만 학교 DB에는 어느 것도 적용하지 않았다. 실행 계정의 public 스키마 생성과 원장·잔고 직접 DML은 실제 거부됐다. 앱 호스트에는 DB 서버·중앙 관측을 설치하지 않았다. 현재 서비스·관리 포트는 루프백만 listen한다. 외부 공개·실제 거래·장애 복구 완료와 구분하며 다음 설치도 역할별 배치를 따른다. [서비스 설정](../../../deploy/linux/app/exchange-app.service), [비공개 기동 설정](../../../deploy/linux/app/app.env.school-private)

학교 사용자 콘솔에서 ALB와 ASG 목록 조회가 각각 DescribeLoadBalancers·DescribeAutoScalingGroups 권한 부족으로 거부됐다. 기존 EC2 Role도 ALB·CloudFront 목록 조회가 거부됐다. 사용자 콘솔의 CloudFront 목록은 정상 조회됐지만 생성 권한은 아직 검증하지 않았다. 학교 운영자 확인 전에는 ALB·ASG를 실행 가능한 구성으로 전제하지 않으며, 수동 증설을 자동 확장 성과로 바꾸어 기록하지 않는다.

추가 생성 시험에서 `elasticloadbalancing:CreateLoadBalancer`와 `ec2:CreateLaunchTemplate`이 모두 identity-based policy의 허용 부재로 거부됐다. ALB는 앱 연결 없는 고정 503 응답·기존 제한 SG로 요청했으며 생성되지 않았다. ASG는 선택할 시작 템플릿이 없고 템플릿 생성도 막혀 `CreateAutoScalingGroup` 요청까지 진행하지 못했다. ASG 생성 API 자체의 허용·거부는 미확인이다. 이번 시험으로 새 ALB·리스너·템플릿·ASG·EC2는 생성되지 않았다. 증거 258~262에 화면과 오류를 보관했다.

### 2. 여러 호스트에서 첫 실행을 할 수 있도록 설정을 맞춘다

| 먼저 해결할 것 | 현재 파일에서 확인한 문제와 완료 기준 |
|---|---|
| DB의 호스트 간 연결 | DB Compose에 포트 공개·host network·호스트 간 네트워크 정의가 없다. 다른 호스트의 앱과 standby가 지정한 DB 주소로 접속하도록 사설 경로를 마련하고 실제 접속을 확인한다. 보안 그룹만 열어서는 컨테이너 포트가 연결되지 않는다. [DB 노드](../../../deploy/compose.node-data.yml) |
| DB 연결 수 | 문서의 기본 풀 최대 합계는 앱당 48, 앱 2대와 엔진을 끈 봇을 합해 106이다. 실제 동시 사용량의 측정값은 아니지만 PostgreSQL 기본 100 및 일반 연결 한도 97을 넘는다. 리스·append·운영 여유까지 포함해 풀과 DB 설정을 함께 확정한다. 단순히 상한만 올려 메모리 문제를 만들지 않는다. [CI·배포 계약의 연결 예산](../contracts/하네스_CICD_IaC.md) |
| 실행 이미지와 DB 계정 | 학교 x86_64에 맞는 JAR·런타임과 prod 부팅을 확인한다. 컨테이너 예외를 쓰면 해당 아키텍처의 이미지 digest도 검증한다. 앱·봇 로그인 역할, 마이그레이션 소유자와 권한을 분리한다. 현재 `app_role`·`harness_role` 정의만으로 실제 접속 계정의 권한이 제한됐다고 볼 수 없다. [앱 노드](../../../deploy/compose.node-app.yml), [배포 변수](../../../deploy/.env.example) |
| 첫 prod 부팅에 필요한 값 | 마스터키·비밀번호 페퍼·세션 시드와 CORS·WebSocket 허용 오리진을 첫 기동 전에 준비한다. 앱·봇 사이의 비밀 값도 맞춘다. 이 값이 없으면 공개 여부와 관계없이 prod 부팅 검사를 통과할 수 없다. 실제 값은 문서에 넣지 않는다. |
| 스키마와 전환 순서 | 한 노드에서 마이그레이션을 완료한 뒤 나머지를 시작한다. V41 인덱스를 먼저 적용하고, V44 명령 래치는 ADR 0022 §7의 조건으로 판단한다. V46은 전체 엔진·API 버전을 맞춘 쓰기 정지 창에서 적용한다. 첫 이벤트 대역 행 이후 구버전 복귀는 허용되지 않으므로 롤백 범위를 미리 정한다. V47(`idempotency_keys.shared_at` 열과 판정 함수 추가)도 봇과 앱을 멈춘 쓰기 정지 창에서 한 노드가 먼저 적용한다. 기본값 없는 널 허용 열이라 표를 다시 쓰지 않지만 잠깐 배타 잠금을 잡으므로, 남은 세션이 있으면 앱 기동 중 적용은 실패하고 소유자 적용 도구는 잠금을 기다린다. 이전 JAR로 돌아갈 수는 있을 것으로 보이나 학교에서 확인하지 않았고(추정), 그때 V47 행을 지우거나 repair하지 않으며 모호한 커밋과 정산 재시도의 결함이 되살아난다. 보존 태그의 다른 V47 파일과 번호가 겹치며 그 파일은 쓰지 않는다. 같은 JAR의 V47.1은 소유자 권한 트리거 함수 넷의 PUBLIC 실행 권한을 회수한다. 회수 전에는 조회 로그인이 레지스트리·카운터 표에, 앱·봇 로그인이 INSERT 권한이 없는 레지스트리 표에 자기 임시 표 트리거로 행을 쓸 수 있었다. 트리거 발화에는 영향이 없고, 소유자가 아닌 계정으로 돌리면 파일 끝 확인이 멈추므로 함수 소유자로 적용한다. 학교 앱 env 템플릿은 Flyway를 끄고 소유자는 NOLOGIN이라 V47·V47.1 모두 앱 기동이 아니라 소유자 적용 단계가 필요할 것으로 보며, 실제 서버 env는 확인하지 않았다. 버전 47.1은 마켓별 리더 브랜치의 V48 이후와 겹치지 않게 사용자가 정했다. V47.1은 V48보다 낮은 판이라 V48 이상이 이미 적용된 DB(마켓별 리더의 폐기용 실험 DB뿐)에는 Flyway가 나중에 받지 않는다. 학교 DB(V46)와 새로 만드는 DB는 V47, V47.1, V48 순서로 받는다. V48(마켓 파티션 리스)도 리스 표와 마켓 표에 외래키와 트리거를 거는 동안 잠금을 잡으므로 쓰기를 멈춘 창에서 적용하고, 권한 회수 V49는 V48과 다른 이미지로 내보낸다. V50이 적용된 DB에는 Flyway가 낮은 번호를 나중에 받지 않으므로 V49~V52는 S3의 첫 이미지에 함께 싣는다. V53은 S4 이미지에 싣고 `harness.failover_runs`에 널 허용 열 하나를 더할 뿐이다. V54는 S5 이미지에 싣고 취소 인계 표 `order_cancel_requests` 하나를 새로 만든다. 이 표는 쓰기 권한 판정에 쓰이지 않는다([DB 설계](../contracts/백엔드_DB_설계.md) §3.9). 같은 이유로 main의 병행 커밋 `fdf5d53`이 넣은 V47_1은 브랜치의 V48 이후보다 낮은 번호라, 브랜치 이미지를 한 번이라도 적용한 DB에는 그대로 올라가지 않는다. 브랜치를 main에 합칠 때 그 내용을 새 번호로 옮기는 방법을 정한다(이미 적용한 파일은 고치지 않는다, [S4 설계](../architecture/마켓분할_리더_S4_설계.md) 9절). V50도 쓰기를 멈춘 창에서 적용하며 모드를 바꾸지 않는다. P2 전환은 소유자가 같은 창에서 따로 부르는 함수이고, 되돌림 시험 R1의 스택 판을 하지 않았으므로 P2로 올린 DB는 비가역으로 취급한다. V48 이후 마이그레이션과 P2 전환은 로컬 폐기용 스택의 관문을 통과하기 전에는 어떤 영속 DB에도 적용하지 않는다. S3 관문은 로컬 폐기용 스택의 재주행에서 결정 5까지 통과했지만 사용자 확인이 남았고, 영속 DB 적용은 로컬에서 S7까지 마친 뒤 S8(개인 AWS)에서 정한다. 브랜치의 하네스 `summary.sql`은 V48·V50 객체가 모두 없는 DB에서 CRITICAL C29·C31을 N/A로 내고, 같은 브랜치의 복원·복구 점검은 N/A를 실패로도 통과로도 세지 않고 따로 적는다(AI 방침, 사용자 확인 필요). 그래서 학교 DB가 V47인 동안 브랜치를 합친 뒤의 점검 도구와 `summary.sql`을 함께 설치하면 복원 점검이 C29·C31 때문에 실패하지 않는다. N/A를 모르는 이전 판 점검 도구에 새 `summary.sql`만 넣으면 형식 오류로 실패하므로 두 파일은 같은 릴리스의 것을 쓴다. [백업 안내](../../../deploy/backup/README.md), [적용 절차](../../reports/AWS_작업.md#주문-v47을-포함한-jar-배포), [DB 설계 §3.1·§3.4](../contracts/백엔드_DB_설계.md) |

### 3. 외부 사용자에게 열기 전에 거래와 접근 통제를 확인한다

주문 접수에는 저널 커밋 여부가 모호한 예외가 있다(ADR 0022 §9-13). 커밋 응답을 잃은 요청의 멱등 키를 지우면 같은 키 재시도는 대조할 수 없어 409가 되고, 새 키로 다시 내면 이중 주문이 된다. 잔고 예약까지 바로 풀면 다음 주문이 잔고 가드를 지나 정산의 제약 위반으로 라이터를 멈출 수 있다. 학교 app-1에서 도는 JAR `3362117`은 이 동작 그대로다. 2026-09-23 저장소 코드는 저널 제출이 예외로 끝나면 V47 함수 `resolve_failed_order_intake`로 판정한다. 함수는 같은 키의 접수와 같은 어드바이저리 락을 잡아 진행 중인 기록을 기다린 뒤, 이 요청이 채번한 주문의 NEW가 커밋됐는지 본다. 커밋됐으면 키를 남기고 라이터에 그 위치까지 회수를 요청한 뒤 정상 접수처럼 응답하고, 없으면 이 요청이 넣은 키를 지우고 원래 오류를 낸다. 같은 내용의 다른 요청이 그 키로 대조했다는 공유 표시(`shared_at`)가 있으면 지우지 않는다. 판정 호출마저 실패하면 키를 남기고 예약은 30초 TTL 뒤 회수한다. 판정에는 저장 시각 비교를 쓰지 않는다. 확인 범위는 Testcontainers 통합 시험(`OrderIntakeFailureResolutionTest` 11건 등)과 서버 전체 build이며 장애 주입과 학교 배포는 하지 않았다. 남은 창은 라이터 적체가 30초를 넘길 때 가드가 비는 일반 경로, 판정 호출 실패 뒤의 30초, 이전 코드가 이미 키를 지운 NEW에 대한 같은 키 재시도(409), 해시 퍼지를 켠 뒤의 옛 주문 재생이다. 퍼지는 아직 배선되지 않았다. 계약은 [API 설계 §2-4](../contracts/백엔드_API_설계.md)가 기준이다. [OrderGateway](../../../server/app/src/main/java/kr/exchange/api/order/OrderGateway.java), [V47](../../../server/app/src/main/resources/db/migration/V47__order_intake_failure_resolution.sql)

실제 공개 도메인·TLS와 웹의 API·WebSocket 주소, 서버의 허용 오리진이 일치하는지 확인한다. 공개 번들에서 관리 화면을 제거하고 관리 API·관리 포트는 사설 접근으로 제한한다. `prod,admin`을 사용할 때만 해당 운영 인증서 구성도 적용한다. ALB·CloudFront 뒤에서 클라이언트 주소를 올바르게 읽도록 신뢰 프록시 범위를 설정한다. 앱은 `EXCHANGE_TRUSTED_PROXIES`가 없으면 루프백만 신뢰한다. 노드 Compose는 이 값을 전달하며 기본값은 `127\.0\.0\.1`이고, Terraform 부트스트랩은 ALB 서브넷 범위를 계산해 넣는다. 학교 app-1은 같은 호스트의 Nginx가 루프백으로 전달하고 학교 env에는 이 값이 없어 앱 기본값을 쓴다. 학교 경로에서 클라이언트 주소가 실제로 올바르게 읽히는지는 확인하지 않았다. ALB·CloudFront 뒤로 옮길 때는 그 범위로 바꾸고 요청 제한이 프록시 주소 하나에 몰리지 않는지 확인해야 한다. [앱 설정](../../../server/app/src/main/resources/application.yml), [배포 안내](../../../deploy/README.md)

### 4. AWS에서 연결·관측·복구를 확인한 뒤 최종 실험을 한다

먼저 주문·조회·WebSocket이 올바른 노드로 전달되는지, 팔로워의 생존 확인과 리더의 요청 수용 판단이 맞는지 확인한다. 실제 지표 수집과 알림 전달, 재배포와 롤백, 백업에서의 복원을 시험한다. 학교는 [학교 관측 설정](../../../deploy/linux/observability/prometheus.yml)으로 사설 주소와 앱 관리 지표 경로를 수집한다. [로컬 관측 설정](../../../harness/prometheus/prometheus.yml)은 chaos 서비스 이름과 포트를 쓰므로 개인 계정 배포에도 그대로 옮기지 않는다.

그다음 옛 primary 격리, standby 승격, 앱 DB 주소 전환, 리더 회복, 옛 노드 베이스백업 재편입을 여러 호스트에서 끝까지 연습한다. ADR 0036을 적용한 환경에서는 이 연습이 Patroni의 계획 전환(`patronictl switchover`)과 예고 없는 장애의 자동 전환·재합류, 거래 일시 중단과 자동 재개의 관찰로 바뀌고, DB 호스트를 영구히 잃었을 때의 사람 절차(새 인스턴스, etcd 멤버 교체, `--no-slot` 베이스백업, 설계 9-5)를 더한다. 사람의 판단 시간과 앱 연결 전환까지 포함해 DB 복구 시간을 잰다. `pg_promote` 명령 소요만 운영 RTO로 제시하지 않는다.

최종 발표는 Linux·네트워크 문제의 관측과 조치, DB 복구, ASG 인스턴스 증가·감소, Teams 기본 알림과 AI 보고를 실제 근거로 보여 준다. AWS에서 부하를 다시 캘리브레이션하고 거래 기록·자산합·복구 시간도 확인한다. 과거 E10이나 카오스 전수 재실행을 현재 필수 목표로 두지 않으며, 커널 장애를 시험한다면 격리 환경에서만 수행한다. 스냅샷 최적화·`commit_delay` 튜닝·별도 관제 UI보다 운영 흐름을 우선한다. [로드맵 M4](../../ROADMAP.md)

## 각 ADR이 현재 구조에 남긴 것

이 표는 옛 문서의 모든 문장이 여전히 유효하다는 표시가 아니다. 당시 결정 중 현재 적용하는 부분과 후속 변경을 함께 적었다. 최신 기록을 읽어도 모순이 남으면 본문의 미확인 사항으로 드러내고 해당 원본을 대조한다.

E-P2c·E-P4c·E-P8·E-P9와 AWS 적용은 하지 않았다. 같은 날 설계 검토 13건을 반영해 베이스백업 `--no-slot`과 멤버가 아닌 복제 클라이언트 금지, DB 쪽 확인이 있을 때만의 중단 판정, 쓰기를 받는 동안만의 리스 획득, `423`의 뜻 좁히기, 크래시 재시작 뒤 확정 응답 보류, DB 호스트 손실 절차를 더했다. 코드 검토 뒤에는 쓰기 게이트의 대상을 필터 등록 경로로 가리게 고쳤고, 이체 재생 `200`의 확정 응답 보류와 다른 필터의 원시 URI 경로 검사를 남은 일로 적었다. HAProxy 위치, 리스 갱신 로컬 커밋, `423`, 탐지 임계, `failsafe_mode`, 목표 시간 60분 등 스물일곱 항목은 AI 선택이라 사용자 확인 대상이다. E-P1b 판정 조건(13절 26)은 사용자가 2026-09-25에 확정했다. |

학교 DB의 현재 역할은 AZ-c `172.31.33.195`가 Primary, AZ-a `172.31.1.229`가 Standby다. 수동 전환에서 쓰기 중단·복제 완료·옛 Primary의 서비스 중지와 mask·접속 거부를 확인한 다음 승격했다. 앱·봇은 새 공개 인증서를 검증하는 TLS 연결로 전환했다. 기존 데이터 디렉터리를 보존하고 베이스백업 검증 후 옛 Primary를 Standby로 재편입했으며 기존 복제 슬롯 참조는 해제했다. 복제 계정의 비밀번호는 재사용하고 postgres 전용 0600 passfile로 연결한다. 현재 복제는 비동기·슬롯 없음이며 단절 중 필요한 WAL이 사라지면 다시 베이스백업한다. 실측 결과와 제한은 로드맵·실행 증거를 따른다. 앱 한 대인 현재 구성을 고가용성 완성으로 표현하지 않는다.

학교에서 작성한 Grafana 기본 관제 결정은 [0032](0032-operator-console.md)로 보존한다. 원격 브랜치의 0028과 학교 AWS 준비에서 사용한 VM 결정 0028이 겹쳐 관제 결정을 0032로 재배정했다. 별도 운영 콘솔은 선택적 확장 자료이며 학교 EC2의 기본 화면은 기존 Grafana다. 원격의 Docker·Terraform·조회 노드·예약 백업·운영 콘솔 구현을 저장소에 통합했지만, 해당 코드가 있다는 사실을 학교 AWS에서 배포·검증했다는 뜻으로 쓰지 않는다. 학교의 실제 배포는 deploy/linux와 AWS 작업 안내를 따르며 로컬 실행 근거는 [09-18 기록](../../measurements/20260918.md)으로 구분한다.

## 이 문서를 갱신하는 방법

백업 검증은 운영 데이터와 분리한 Unix socket 전용 PostgreSQL에서 수행한다. 동일 스냅샷의 주요 건수와 정합성 검사를 대조하고 시험 클러스터를 종료한다. 원본 운영 데이터를 지우지 않으며 로컬 백업 검증을 외부 보관·예약 백업 또는 장애 복구 완료로 해석하지 않는다.

학교 app-1은 PC 제한 HTTP 미리보기에서 공개 HTTPS 경로로 전환했다. 사용자 요청에 따라 Let’s Encrypt 인증서와 자동 갱신을 적용했으며 초기에는 관리 경로를 차단했다. 이후 사용자 승인으로 Grafana와 봇 관리자 로그인을 HTTPS에 연결했다. 빈 DB 카탈로그에 개발 코드와 같은 종목·마켓 기본값을 등록하고 데모 조회·WebSocket 연결을 확인했다. 세 마켓의 시장 봇 체결은 확인했고 회원 주문 검증은 남아 있다. 봇 SG는 EIC용 22와 앱 SG 전용 3000·8443·9088만 허용한다. Grafana는 사설 주소에 바인딩하고 사용자 인증을 유지한다. 학교 사용자 CloudShell과 PC의 SSM 포트 포워딩에 성공했고 PC에서 Grafana 로그인 화면을 확인했다. 운영자가 최초 관리자 비밀번호를 직접 설정한 뒤 로그인과 bot-1 지표의 패널 렌더링을 확인했다. 이후 GitHub `codex/docs-linux-operations`의 `6ee1179`에서 MSP 화면 6개를 AWS용 사본으로 연결했다. 로컬 구버전 배포를 정정했다. 당시에는 필요한 파일만 가져왔고 이번 정리에서 원격 브랜치 전체를 병합했다. 앱 지표는 봇 SG만 허용한 Nginx 사설 9101 경로로 수집하며 앱 8081은 루프백을 유지한다. 이후 앱·DB의 Linux 수집과 DB 통계를 연결했다. 외부 사이트 프로브는 남아 있다. 앱·DB·디스크 경보와 보고 연결은 검증했으며 미수집을 정상으로 표시하지 않는다. 목록 조회 거부, StartSession 허용, TerminateSession 거부를 구분한다.

학교 작업의 최신 실행 범위는 DB 백업·복원, 장애 감지·Teams 보고, DB 수동 복구 시연이다. 앱 이중화와 ALB·ASG는 학교 허용 후로 보류한다. 부하 시험·ASG 실행은 사용자가 이번 범위에서 제외했다. 전체 목표의 자동 확장을 폐기한 것은 아니다. bot-1에 Prometheus·Linux 지표 수집기·Grafana를 직접 설치했다. Prometheus와 관리 지표는 루프백으로 제한하며 Grafana 익명 접근은 차단했다. Grafana의 사설 3000은 앱 Nginx만 허용한다. 초기 보고 서비스는 bot-1만 대상으로 했으며 첫 수신을 사용자가 확인했다. 이후 사용자가 승인한 앱·DB 운영 지표 범위로 별도 보고 서비스를 연결했다. 기존 카드와 PDF·HTML 모듈을 재사용하며 서명 링크는 7일 후 만료된다. 보고 포트 9088은 앱 SG만 허용하고 내부 관리 API는 HTTPS로 노출하지 않는다. 일일 보고는 매일 09시 KST timer로 실행한다. 기존 2분 폴링은 비활성화했고 Prometheus 15초 평가와 규칙별 지속 시간·Alertmanager로 상태 변화를 전달한다. AI는 운영 조치를 실행하지 않는다. 앱의 사설 지표 수집과 SSM을 통한 Grafana 관리자 로그인·화면 접근은 확인했다. DB 수집과 앱·DB를 포함한 AI 시험 보고의 웹훅 접수·파일 응답을 확인했다. 장애 발생·해제 검증 상태는 로드맵을 따른다. 기존 bot-1 전용 timer는 비활성화했다. 디스크 화면의 임계 색상은 경보 발송이나 자동 삭제를 뜻하지 않는다. 실제 EC2 실행 역할은 기존 프로파일에 연결된 `SafeRole-2026-ai-kopo-04`다.

학교 DB·관측과 개인 계정 앱·ALB·ASG를 연결하는 안은 학교 허용을 기다린다. 학교 사용자로 피어링 생성·라우트 추가를 dry-run 검사했고 두 권한 모두 거부됐다. 실제 요청이 없어 수락 권한은 미검사다. 개인 서울 기본 VPC도 `172.31.0.0/16`으로 겹치므로 그대로 연결할 수 없다. 겹치지 않는 개인 VPC와 운영자가 허용한 왕복 경로·SG가 선행 조건이며 현재 연결 요청이나 네트워크 변경은 하지 않았다. 사용자는 30일 상시 운영과 `www.sang.it.kr`, 0030의 NAT 제외·앱 계층 2~3대 기준(2026-09-25 정정)을 지정했다. 월요일 상담 항목과 비용·어드민 유지보수 검토는 AWS 작업 안내를 따른다. 연결이 불가하면 0029의 개인 독립 재배포 경로를 유지한다.

구조를 바꾸거나 구현·검증 상태가 달라지면 관련 계약·ADR·로드맵·측정 원본을 먼저 확인하고, 같은 변경에서 이 문서의 해당 설명과 위 표를 갱신한다. 현재 설명을 고칠 때마다 `0099-v2` 같은 파일을 만들지 않는다. 변경 이력은 Git에 남긴다. 기존 ADR의 옛 측정이나 반박을 현재 사실처럼 복사하지 않는다.

`scripts/check-adr-current.ps1`은 개별 ADR 링크 누락·번호 중복과 원자료 변경 후 검토 표시 누락을 검사한다. 대상은 개별 ADR, 로드맵, 상세 설계·계약·운영 Markdown, 측정 Markdown, 배포 안내와 노드 Compose, 아키텍쳐 안내다. 자료가 바뀌면 0099에 영향이 있는지 검토한 뒤 `-PrintDigest`로 읽은 값을 아래 표시 한 곳에 반영한다. 내용은 그대로 둔 채 검사만 통과하려고 해시를 바꾸지 않는다.

이 검사는 내용을 자동으로 요약하지 않으며, 소스만 바뀌었을 때 구조 설명이 맞는지까지 증명하지 않는다. Claude와 Codex는 코드 변경도 [공통 작업 규칙](../../../AGENTS.md)에 따라 관련 문서와 대조해야 한다. 이번 검토에서 읽지 않은 개별 테스트 전체와 서비스 배포·DNS·청구 상태는 미확인이다. 본인 SG·첫 EC2 생성, 기존 프로파일 연결, 제한된 EC2 Instance Connect SSH와 Linux 기본 점검은 확인했다. SSM 조회 권한은 부족하며 이를 모든 서비스의 허용으로 확대하지 않는다. 비밀 값은 증거에 저장하지 않는다.
