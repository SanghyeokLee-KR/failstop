# 관리자 설계 (v1.5)

관리 콘솔과 관리 API의 인증, 권한, 기능과 화면을 설명한다. 인증과 권한은 1절, 기능은 2절, API는 3절, 화면은 4절에 있다. 관리 기능은 거래 API와 별도 접근 경계를 사용한다.

요청·응답은 [API 설계](../contracts/백엔드_API_설계.md), 저장 규칙은 [DB 설계](../contracts/백엔드_DB_설계.md), 실험 판정은 [하네스 검증 설계](../contracts/하네스_검증설계.md)를 따른다. 이 문서는 기능 설계이며, 모든 항목이 현재 배포 환경에서 검증됐다는 뜻은 아니다. 계약·구현과 어긋나는 지점과 사람이 정해야 할 항목은 7절에 모았다.

현재 상태에서 먼저 알아야 할 것은 네 가지다.

- 파괴 액션의 승인은 1인 승인이다([ADR 0019](../adr/0019-single-operator-approval.md)). 승인 티켓의 별도 발급 단계, TTL 5분, 단회 소각, 액션·대상·요청자 바인딩, 역할 게이트, append-only 감사는 남아 있고, 발급자와 사용자가 서로 달라야 한다는 제약만 없다.
- 2026-09-23 웹 콘솔을 운영 관제 `(ops)`와 백오피스 `(back)` 두 평면으로 나눴다. 웹의 카오스 주입 화면 `/admin/chaos`와 모니터링 화면 `/admin/monitoring`은 제거했고 서버의 카오스 API는 남아 있다(2-2절). 화면 구성은 4절에 있다.
- 서비스 흐름 `/admin/flow`와 지표 관제 `/admin/monitor`는 로컬 측정 기록을 재생하는 채택 전 시안이다. 백엔드에 연결하지 않았고 채택 여부는 결정 대기다(4-2절, 7-10).
- 이 문서의 화면 설명은 저장소의 웹 코드 기준이다. 학교 AWS에 배포된 웹이 어느 판인지는 [AWS 작업 안내](../../reports/AWS_작업.md)와 [로드맵](../../ROADMAP.md)에서 확인한다.

2026-09-20 학교 배포 예외: 봇 운영자 한 명은 HTTPS 비밀번호 로그인으로 접속하고, 앱 Nginx가 해당 운영자의 인증서로 봇 노드에 mTLS 연결한다. PC 인증서 설치는 요구하지 않는다. 내부 세션·권한 검사는 유지하며 `VIEWER`·`BOT_OPS`만 부여한다. 같은 인증서에 여러 운영자를 연결하지 않는다. 아래 직접 mTLS 접속을 설명한 절과 다른 신뢰 경계, 적용 범위와 제한은 [ADR 0031](../adr/0031-school-admin-password-gateway.md)을 따른다.

2026-09-18 적용 범위: 현재 [ADR 0027](../adr/0027-msp-operations-and-autoscaling.md)은 카오스 화면 추가 개발 대신 MSP 관제, AWS 조회 자동 확장과 Teams·AI 운영 보고를 우선한다. 아래 수동 용량 API는 현재 남아 있는 구현이며 새 ASG 정책을 대신하지 않는다. 관측값이나 AI 문장을 임의 운영 명령으로 실행하지 않는 원칙은 유지하고, 사전에 정한 AWS 확장 정책의 자동 실행은 허용한다.

## 0. 원칙

- 관리 API는 격리 모듈이다. 봇·용량·카오스·HA 조회·회원·게시판·고객 응대 API는 배포단위 C(`exchange-admin`, 분리 포트·분리 네트워크·mTLS)에서만 동작한다. 코어 경로(매칭·정산·저널)에 새 의존성을 추가하지 않는다. 관리 화면은 거래 웹과 같은 Next.js 앱에 있고 공개 번들에서 제거한다(§4-1).
- 관측 데이터는 판단 근거일 뿐 실행 트리거가 아니다. 지표·로그·불변식 결과가 어떤 상태를 보여도 파괴 액션을 자동 실행하지 않는다.
- 데모 환경 한정이다. 실거래·실자산·실명·실금융자격증명은 없다.
- 관리자 평면은 거래 평면(§3)·데모 세션(§3-7)과 자격·키·세션을 공유하지 않는다. 데모 세션은 `scope=TRADE` 고정이고 관리 평면 사용 불가다(API §3-7).

## 1. 관리자 인증·권한 모델

### 1-1. 관리 평면 격리(정본 §3-6 소비)

관리 API는 다음 4중 방어를 그대로 상속한다. 신규 설계는 이를 재정의하지 않고 소비한다.

- 네트워크 격리: `admin.exchange.local` 별도 호스트·포트, 방화벽으로 운영자 네트워크만 접근. mTLS 필수(클라이언트 인증서 검증).
- 서명: JWT(HS256) + canonical(SHA512) + nonce + timestamp를 재사용하되 `scope=admin` 키 + 별도 `admin_secret`로 서명. `/admin/v1/**` path가 canonical에 포함되어 거래 서명과 교차 재사용 불가. 중첩 바디는 JCS(RFC 8785) canonical(§3-3(b))을 상속.
- 비가역 액션 승인: `approval_token`(1인 승인·단회용·TTL 5분·action+대상+요청자 바인딩, ADR 0019). 필수 대상은 API §3-6 완결 열거이고 카오스 주입·해제 4종은 v2.34에서 빠졌다(§2-2). 빠진 4종도 토큰을 제시하면 같은 규칙으로 검증·소각한다.
- 감사·rate limit: 전 요청 `admin_audit_log` 적재, 관리 버킷 60토큰/60초(§2-5). 요청 한 건이 10토큰을 쓰므로 계약 기본값의 실효 한도는 60초에 6요청이다(`AdminAuthFilter`). 화면 확인용 로컬 프로파일 `admin-local`과 `admin-chaos`는 버킷 용량을 6000으로 올린다(`application.yml`).

정본 §3-6은 승인 판정에 쓰는 operator_id를 자가신고 바디 값이 아니라 인증 주체(access_key·mTLS 인증서 CN)에서 도출한다. 1인 승인이라 발급 요청과 사용 요청의 인증 주체가 같아도 승인이 성립한다. 이 도출 규칙이 막는 것은 결탁이 아니라 감사 기록의 신원 위조와 남의 티켓 사용이다. 티켓은 발급 때 지정한 요청자와 같은 인증 주체만 쓸 수 있다.

### 1-2. 운영자·권한(RBAC) 모델

관리자 계정은 회원(`users`)·봇 계정과 분리된 운영자(operator) 개념이다. `api_keys.scope=ADMIN` 키가 운영자 1인에 1:1 바인딩된다(API §7-1 admin 키 규약).

권한은 역할 기반이다. 최소 권한 원칙으로 5역할을 둔다.

| 역할 | 권한 범위 |
|---|---|
| `VIEWER` | 조회 전용. 상태·감사 로그·대기열 열람. 어떤 변경도 불가 |
| `BOT_OPS` | 봇 플릿 제어(생성·정지·OPS·시나리오·파라미터). 카오스 불가 |
| `CHAOS_OPS` | 서버 카오스 API의 주입·해제와 봇 제어. 서버 `AdminPrincipal`과 웹 `roles.ts`가 이 역할에 `BOT_OPS`를 포함시킨다. 웹에는 카오스 화면이 없고 화면 표기는 '실험 운영'이다 |
| `MEMBER_MOD` | 회원·게시판·고객 응대 운영(정지·복구·폐쇄 요청, 글 숨김·삭제, 신고 처리, 출금 승인·거절, 문의 답변) |
| `SUPER` | 전 권한 + 운영자·권한 관리. 1인 승인이라 승인 필수 액션의 요청과 발급을 혼자 할 수 있다 |

- 승인 티켓은 역할과 독립이다. 역할 게이트를 통과해도 승인 필수 액션(§3-2)은 티켓을 요구한다. 티켓은 요청 운영자 본인이 발급해도 되고 다른 운영자가 발급해도 된다(ADR 0019).
- 권한 검사 실패는 `403 admin_forbidden`(API §2-3), 승인 부족도 동일 코드에 `detail.reason`으로 구분.

### 1-3. 브라우저 관리자 UI 인증 흐름(mTLS 운영자 세션)

브라우저는 `admin_secret`으로 HMAC 서명을 만들 수 없다. `secret_key`(및 `admin_secret`)를 브라우저에 전달하지 않는 계약(웹 화면명세서 §6.1, API §3-7) 때문이다. 거래 UI가 데모 세션으로 우회하는 것과 달리 관리 평면은 데모 세션을 쓸 수 없다(§3-7 범위 제한: `scope=TRADE` 고정). 관리 평면 브라우저 접속은 운영자별 mTLS 클라이언트 인증서로 1차 인증하고, 그 인증서 신원에서 유래한 단기 관리자 세션으로 후속 요청을 인증한다. 서명 비밀을 브라우저나 단일 서버 컴포넌트에 모으지 않는다.

```
[운영자 워크스테이션 브라우저]
   │  ① 운영자 네트워크 전제 + 운영자별 mTLS 클라이언트 인증서(브라우저 설치, CN=operator_id)
   │     사설키는 각 운영자 워크스테이션에만 존재. 서버는 CA 공개키로 검증만 한다.
   ▼  mTLS(1차 인증)
[exchange-admin 관리 평면 (admin.exchange.local, 별도 호스트·컨텍스트)]
   │  ② mTLS 통과 후 인증서 CN=operator_id에 바인딩된 단기 관리자 세션 발급
   │     (세션 토큰은 mTLS 신원에서 유래, 자가신고 금지·관리 평면 전용·짧은 TTL)
   │  ③ 조회는 단독 운영자 세션으로 수행
   │  ④ 승인 필수 액션은 approval_token 동반(1인 승인이라 본인 세션 발급도 허용)
   ▼
[/admin/v1/** (§3-6 검증: operator_id는 mTLS 인증 주체 유래)]
```

- 1차 인증: mTLS 클라이언트 인증서 검증. 인증서 CN이 operator_id의 권위 소스이며 자가신고 바디 값이 아니다(§3-6 v2.4).
- 세션: mTLS 통과 시 서버가 인증서 신원에 바인딩된 단기 관리자 세션 토큰을 발급한다. 세션은 mTLS 신원에서 유래하고 운영자가 신원을 신고하지 않는다. 관리 평면 전용이며 거래 평면·데모 세션과 자격을 공유하지 않는다(§0).
- 조회(상태·감사·대기열 열람)는 단독 운영자 세션으로 가능하다(`VIEWER` 이상).
- 승인 필수 액션(§3-2)은 approval_token 필수다. 요청 운영자 자신이 자기 세션으로 `POST /admin/v1/approvals`를 호출해 발급해도 되고, 다른 운영자가 자신의 mTLS 세션으로 발급해도 된다. 발급자와 요청자의 operator_id는 각 요청의 mTLS 인증 주체에서 도출해 감사에 남는다. 카오스 4종은 필수 대상이 아니다(§2-2-a).
- 키 보관 분리: 사설키는 각 운영자 워크스테이션에만 있고 어떤 단일 서버 컴포넌트도 전 운영자 키를 보유하지 않는다(서버는 CA 공개키만 보유). 1인 승인에서도 이 분리를 유지하는 이유는 감사에 남는 신원이 실제 키를 가진 사람과 일치해야 하기 때문이다. 학교 배포는 게이트웨이가 운영자 한 명의 인증서를 대신 제시하므로 이 분리가 성립하지 않는다(서두, ADR 0031).
- 세션 만료·mTLS 실패는 `401 jwt_verification`, 권한·승인 부족은 `403 admin_forbidden`.
- BFF(존재 시)는 mTLS 종단·세션 중개면일 뿐 서명 비밀 보관면이 아니다. 운영자 사설키를 보관하지 않는다. mTLS 클라이언트 인증이 운영자 워크스테이션에서 관리 평면까지 종단으로 성립하도록 구성한다.
- 관리 세션 매개는 관측 데이터를 렌더만 하고, 응답 본문 텍스트를 지시로 해석해 파괴 액션을 생성하지 않는다(§6 안전 규약).

운영자별 HMAC 서명키를 하드웨어에 봉인하는 방식은 쓰지 않는다. mTLS 사설키가 곧 운영자 키이므로 별도 서명키 봉인이 필요 없다.

### 1-3-a. 게이트웨이 종단 토폴로지와 바인딩 강제(v2.7 신설)

`exchange.admin.mtls.trusted-forwarding=true`는 §1-3의 1차 인증을 앱 밖으로 내보내는 스위치다. 앱은 인증서를 직접 검증하지 않고, 앞단 게이트웨이가 mTLS를 종단한 뒤 실어 주는 `X-Operator-Cn` 헤더를 신원으로 받는다. 이 헤더는 검증 결과가 아니라 자가신고 값이다. 게이트웨이가 없는 곳에서 이 스위치가 켜지면 §1-3이 세운 "인증서 CN이 operator_id의 권위 소스"가 무너지고, 서버에 닿는 누구나 임의 CN으로 관리 평면에 닿는다.

- **이 스위치가 켜진 배포는 루프백에만 바인딩한다.** `server.address`가 루프백이 아니면 기동을 중단한다. 게이트웨이는 같은 호스트에서 루프백으로 프록시한다.
- **판정은 기동 시점에 한다.** 요청 시점 차단은 이미 열린 뒤라 늦다.
- **판정축은 프로파일이 아니라 주소다.** 프로파일 조건은 조합에 따라 꺼질 수 있고, 실제로 `RequireSecretsCondition`이 `dev`가 포함된 조합에서 꺼진다. 주소는 배포가 감출 수 없는 사실이다.
- **주소 미지정은 위반이다.** 미지정은 전 인터페이스 바인딩이고, 루프백 전용이 아니다.
- **판정은 문자열이 아니라 `InetAddress`로 한다.** `127.0.0.0/8` 전역과 `::1`, IPv4 매핑 표기가 모두 루프백이다. 문자열 비교는 `127.0.0.2`를 놓친다.

구현은 `server/app/src/main/java/kr/exchange/admin/AdminConfig.java`의 `adminForwardingBindingGuard`이고, 계약은 `AdminForwardingBindingGuardTest`가 고정한다. 이 토폴로지를 재현하는 통합 테스트도 `server.address=127.0.0.1`을 선언한다. 선언하지 않으면 테스트가 실제 배포에 금지된 조합을 모델링하게 된다.

### 1-4. 승인 티켓(approval_token) 수명주기(정본 §3-6 소비, ADR 0019)

- `POST /admin/v1/approvals`(mTLS + `scope=admin` 서명)로 발급한다. 발급자(approver)와 요청자(requester)는 같아도 된다(V34). 두 operator_id는 자가신고 값이 아니라 인증 주체(access_key·인증서 CN)에서 서버가 도출한다(§3-6 v2.4).
- 발급 시 `action` + 대상 식별자(`node`·`bot_id`·`toxic` 등)와 요청자에 바인딩한다. 단회용(검증 성공 즉시 소각)·TTL 5분이다.
- 바인딩된 action·대상·요청자와 다른 요청, 만료·기소각 재사용은 `403 admin_forbidden`이다. 정적·재사용 토큰은 금지다.
- 발급·사용·만료·거부 전부 `admin_audit_log`에 기록한다.
- 웹은 발급 전 의도를 로컬에만 둔다. 원장 state는 `ISSUED`·`CONSUMED`·`EXPIRED`·`REJECTED` 넷이고 화면은 `ISSUED`를 '실행 대기'로 적는다(`web/components/admin/ApprovalList.tsx`).

### 1-5. 관리 평면 스키마

DB 정본의 `users`·`api_keys`·`accounts`에 관리 평면용 항목을 더했다. 아래 항목은 `V5__admin.sql`로 적용됐고, 이후 바뀐 부분은 항목마다 적었다.

- `api_keys.scope` CHECK 어휘에 `ADMIN` 추가. scope 정본 어휘는 대문자 `READ|TRADE|WITHDRAW|ADMIN`이다(API §3-2 v2.10 통일). 소문자·`read_only` 표기는 폐기.
- `admin_operators`: 운영자 정체(`external_id UUID`, 표시명, 상태 `ACTIVE|DISABLED`, `created_at`). `api_keys`와 1:1(운영자 키 바인딩).
- `operator_roles` / `operator_role_grants`: 역할 어휘(§1-2 5역할)와 운영자·역할 매핑. append 이력 보존.
- `admin_approvals`: 승인 토큰 원장. `action`, 대상 식별자, `requester_operator_id`, `approver_operator_id`, `issued_at`, `expires_at`, `consumed_at`, `state`. **state 정본 어휘는 `ISSUED|CONSUMED|EXPIRED|REJECTED`**(V5__admin.sql CHECK, DEFAULT `ISSUED`). 단회 소각을 `consumed_at`·`state`로 강제. 1인 승인이므로 `requester_operator_id`와 `approver_operator_id`는 같을 수 있다(V34, ADR 0019). V5의 `chk_approval_two_person` CHECK는 V34가 DROP했다. 두 operator_id는 인증 주체 유래 값으로만 기록한다(§3-6). 웹 타입 `ApprovalState`도 같은 네 값을 쓴다(`web/lib/admin/types.ts`).
- `admin_audit_log`: 관리 액션 append-only 감사(API §7-1이 이름을 명시). 범용 `audit_log`와 별도인 관리 전용 테이블이다. `forbid_mutation` 트리거로 UPDATE·DELETE·TRUNCATE 차단(기존 `audit_log` 패턴 재사용). 컬럼: `operator_id`(인증 주체 유래), `action`, 대상, `request_id`, `approval_id`(있으면), 요청 요지 JSONB, `created_at`.
- `system_config`: 마켓 halt·수수료 등 운용 상태 키·값. 관리 액션이 갱신하고 게이트웨이·매칭 접수가 소비한다(원장·저널 무접촉).
- `notices`: 공지 게시(제목·본문·`severity`·`active`·`published_at`·`published_by`). **severity 정본 어휘는 대문자 `INFO|WARNING|CRITICAL`**(V5__admin.sql CHECK, DEFAULT `INFO`). 와이어 값도 대문자다(웹 소문자 표기는 송신 시 대문자화·수신 시 소문자 정규화로 정합, API §4-D). 삭제는 소프트(`active=false`)이며 `app_role`에 DELETE 미부여(§1-4·DB 설계 §9).
- 회원·게시판 운영 대상 컬럼: `users.status`는 이미 `ACTIVE|SUSPENDED|CLOSED`를 가지므로 재사용. 게시판 모듈(M3 별도 설계)의 글·댓글 상태를 소비만 한다. 관리 평면은 게시판 테이블에 물리 의존을 만들지 않고 상태 전이 API로만 접근한다.

### 1-6. 데모 mTLS 인증서 운영 절차

관리 평면 mTLS는 운영 프로파일에서 강제한다. dev/demo 프로파일은 로컬 접속용 데모 CA와 운영자 클라이언트 인증서로 mTLS 요건을 충족시켜 브라우저 관리 콘솔이 실제로 뜨게 한다. 운영 인증서는 이 절차 밖(운영 PKI)에서 발급하며, 아래는 데모 한정이다.

- 프로파일 게이트: 관리 API는 `admin.exchange.local` 별도 호스트·컨텍스트에서만 서빙하고 고객 평면(`/api/v1`)과 분리한다(§0). 관리 화면은 거래 웹과 같은 앱이지만 공개 번들에서 제거한다(§4-1). mTLS 클라이언트 인증서 검증은 운영 프로파일에서 무조건 요구한다. dev/demo 프로파일은 데모 CA를 신뢰 앵커로 로드해 로컬 데모 인증서로 통과한다.
- 데모 CA: 데모 전용 루트 CA를 1회 생성한다(운영 CA와 분리, 데모 네임스페이스 한정). 개인키는 데모 환경 밖으로 반출하지 않는다. 서버는 이 CA 공개 인증서만 신뢰 앵커로 보유한다(사설키 미보유).
- 운영자 클라이언트 인증서: 운영자 1인당 1장 발급하고 `CN=operator_id`(또는 SAN에 operator_id)로 신원을 못박는다. CN은 §3-6 operator_id 도출의 권위 소스다. 사설키는 해당 운영자 워크스테이션에만 두고 브라우저 인증서 저장소에 설치한다.
- 발급 스크립트·산출물: 데모 CA 생성, 서버 인증서 발급, 운영자별 클라이언트 인증서(PKCS#12) 발급을 재현 가능한 스크립트로 문서화한다. 산출물은 데모 CA 공개 인증서, 서버 키·인증서, 운영자별 `.p12`(브라우저 임포트용). `.p12`는 데모 배포물에만 포함하고 운영 자격과 섞지 않는다.
- 운영자 수와 승인: 1인 승인이므로(ADR 0019) 인증서가 1장인 배포에서도 발급 주체와 사용 주체가 같은 채로 승인 필수 액션이 실행된다. 운영자별 인증서는 감사에 남는 신원을 가르는 수단이다. 여러 운영자가 서로 승인하도록 운용하려면 운영자마다 다른 인증서를 발급한다. 데모 인증서 2종(`op-01`, `op-02`)은 그 경로를 위해 그대로 둔다.
- 폐기·회전: 데모 인증서는 데모 리셋 시 재발급한다. 유출·만료 시 데모 CA로 재발급하며 서버 신뢰 앵커 교체 없이 클라이언트 인증서만 회전한다.

## 2. 기능 명세

### 2-1. 봇 플릿 제어(정본 §6-A 소비)

기존 엔드포인트를 UI로 노출한다. 신규 API 없음.

- 생성: `POST /admin/v1/sim/bots`(유형 `MARKET_MAKER|TAKER|TREND|NOISE`, 수, 마켓, `params`, `seed`). `operator_id` 필수, approval 불요.
- 제거: `DELETE /admin/v1/sim/bots/{id}`. approval 불요.
- 파라미터 변경: `PATCH /admin/v1/sim/bots/{id}/params`. approval_token 필수(실행 중 파라미터 변경은 §3-6 필수 열거 항목).
- 전체 제어: `POST /admin/v1/sim/start|stop|pause`. approval 불요.
- 시나리오: `POST /admin/v1/sim/scenarios/{name}/activate`(`steady|volatile|spike|ramp|selloff|thundering-herd`).
- 전역 OPS: `PUT /admin/v1/sim/rate`.
- 대수 set-point: `PUT /admin/v1/sim/scale`(마켓·유형별 목표 봇 대수. 개별 생성/제거 위에 얹는 상위 제어). approval 불요.
- 방향성 set-point: `PUT /admin/v1/sim/bias`(마켓별 목표 net bias -1~+1·자동균형 강도). approval 불요.
- 효과 강도: `PUT /admin/v1/sim/effects`(체결 시각효과 `trade_flash`. 공개 `GET /api/v1/exchange-config`에 반영). approval 불요.
- 상태: `GET /admin/v1/sim/status`(봇 수·현재 OPS·성공률·평균지연·`duplicate_fill_total`. schema 1.1에서 마켓별 bias·유형별 대수·`fill_ratio`·`trade_flash` additive 확장).
- 텔레메트리: `WS /admin/v1/ws/sim/telemetry`. 현재 웹 화면은 이 채널을 구독하지 않고 `sim/status`를 30초마다 읽는다(§4-2).

set-point 3종(scale·bias·effects)은 파괴 액션이 아니라 approval_token 불요이고 감사만 적재한다(API §6-A v2.10, §3-6 필수 완결 열거 불변). 봇 유형·자동균형 동작은 봇_방향성_거버넌스_설계, 효과 강도 단계·토큰은 체결_시각효과_관리자제어_설계가 상술한다.

### 2-2. 카오스 API(정본 §6-B, 웹 화면 제거)

웹 콘솔의 카오스 주입 화면은 2026-09-23에 제거했다(커밋 `186570f`). 프로젝트 범위가 거래소 앱의 장애 주입이 아니라 Linux·AWS 운영이기 때문이다(ADR 0027). 서버 `ChaosAdminController`의 API 여섯 개는 그대로 있다. 카탈로그 조회(`GET /admin/v1/chaos/experiments`), 주입 이력(`GET /admin/v1/chaos/runs`), 주입·해제 4종(`POST /kill-node`, `POST /network`, `POST /app`, `DELETE /network/{toxic}`)이다. 새 개발 목표가 아니다.

API는 주입을 직접 하지 않는다. 주입·해제 요청은 감사에 적재된 뒤 `chaos_commands` 큐(V21)에 지시로 남고, `harness/scripts/chaos-consumer.ps1`이 그 행을 소비해 실제로 주입한다. 응답은 `experiment_id`와 `state: PENDING`이다. API 계약 예시의 `grafana_annotation` 필드는 현재 응답에 없다. 저장소의 웹과 하네스 실험 스크립트는 이 API를 부르지 않는다. 하네스 실험은 스크립트가 컨테이너와 Toxiproxy를 직접 조작한다. 감사 로그 화면은 과거 `chaos.*` 행을 읽을 수 있게 용어집 항목을 유지한다.

카탈로그 응답은 아래 9종이다. 카오스 주입·해제 4종은 approval_token 불요이고(API §3-6·§6-B v2.34), 토큰을 제시하면 같은 계약으로 검증·소각한다.

| ID | 실험 | 주입 경로 | approval |
|---|---|---|---|
| E1 | PG 지연·지터 | `POST /admin/v1/chaos/network`(latency) | 불요(제시 시 검증·소각) |
| E2 | PG 단절·블랙홀 | `POST /admin/v1/chaos/network`(down·timeout) | 불요(제시 시 검증·소각) |
| E3 | Redis 장애 | network toxic·app | 불요(제시 시 검증·소각) |
| E4 | 매칭 리더 kill | `POST /admin/v1/chaos/kill-node` | 불요(제시 시 검증·소각) |
| E5 | 네트워크 분할(split-brain 유도) | network disconnect | 불요(제시 시 검증·소각) |
| E6 | 폭주 + 리더 kill 복합 | 봇 스파이크 + kill-node 조합 | 불요(제시 시 검증·소각) |

| E9 | 커밋 응답 절단(멱등성 증명) | network toxic(limit_data·reset_peer) | 불요(제시 시 검증·소각) |

- toxic 해제: `DELETE /admin/v1/chaos/network/{toxic}`(approval 불요, 제시 시 검증·소각).
- 카탈로그와 이력: `GET /admin/v1/chaos/experiments`, `GET /admin/v1/chaos/runs`(조회, `VIEWER` 이상).
- 승인 발급: `POST /admin/v1/approvals`(1인 승인). 카오스에는 불요이고 §3-2 승인 필수 액션에 쓴다.
- 웹 화면이 없으므로 확인 다이얼로그 단계도 없다. API를 직접 부르는 운영자는 역할 게이트(`CHAOS_OPS`), 대상 문자열 검증, 감사만 거친다. 관측 값이 특정 임계를 넘어도 자동 주입하지 않는다(§6).

### 2-2-a. 카오스 승인 완화(v2.34 소비)

카오스 주입·해제 4종은 approval_token 없이 실행된다(API §3-6·§6-B v2.34, ADR 0014, 커밋 `89b1e40`). 근거는 운영 규율이 아니라 운영 인원이다. 카오스 실행 주체가 1인인 배포에서 발급자와 사용자를 가르는 2인 승인은 운영자 계정을 하나 더 만들어 혼자 두 역을 하는 형식만 남겼다. ADR 0019가 같은 근거로 나머지 파괴 액션의 2인 제약도 뗐으므로, 지금 카오스 4종과 승인 필수 액션의 차이는 티켓 발급 단계가 있느냐 하나다. 구현은 `server/app/src/main/java/kr/exchange/admin/ChaosAdminController.java`의 `consumeIfPresent`이고, 토큰이 없으면 `approval_id`가 null인 채 진행한다.

완화의 대가는 다음과 같다.

- 카오스 4종에는 실행 전에 의도를 한 번 더 적는 발급 단계가 없다. 남는 것은 역할 게이트(`CHAOS_OPS`)·대상 문자열 검증(`requireSafeTarget`)·사후 감사뿐이다.
- 관리 키 또는 관리 세션 하나가 탈취되면 그 주체 단독으로 리더 kill과 네트워크 단절을 주입할 수 있다.
- 오조작을 거르는 단계가 대상 검증 하나다. 웹 화면을 제거했으므로 확인 다이얼로그도 없다.
- `admin_audit_log.approval_id`에 null 행과 값 있는 행이 섞인다. 카오스 4종의 null은 승인 우회가 아니라 계약이며, 감사 판독에 이 구분이 필요하다.
- 승인 요구를 설정으로 되돌리는 스위치가 없다. `consumeIfPresent`에 조건이 없어 티켓을 필수로 되돌리려면 코드 변경이 필요하다.

파괴성 자체는 줄지 않았고 승인 요구만 줄었다.

### 2-3. 노드·지표 조회(정본 §6-C + 하네스 소비, 파괴 액션 버튼 미노출)

소비 소스와 화면 대응. 전용 모니터링 화면은 2026-09-23에 제거했다(커밋 `51a3c0d`). 아래 조회 API는 종합 관제와 상황별 대본이 읽는다(§4-2).

- 헬스·복구: `GET /actuator/health/liveness|readiness`, `GET /admin/v1/ha/status`(`lease{holder,epoch,lease_until,leader_alive,lease_remaining_ms}`·워터마크·`snapshot_seq`·`trades_count`·`recovery_runs_count`·`last_failover`. **`role`·`node`·`follower_lag_seq`·`matching_market_owner`는 방출하지 않는다.** 노드 팔로워 레지스트리와 복제 큐가 단일 라이터 구조에 없다. API§6-C), `GET /admin/v1/ha/recovery`(`verdict{}` 판정 객체 + `recovery_runs[]` + `failover_runs[]`. 불변식은 `GET /admin/v1/ha/invariants`가 `invariant_checks`의 `check_name`별 최신 행으로 낸다. 저장 행 조회이지 호출 시점 재검증이 아니다. API§6-C v2.33). 시퀀서 큐·주문 지연 p99·원장 불균형·Hikari 대기는 이 응답에 없으므로 웹이 0으로 채우지 않는다.
- 불변식 이력: `invariant_checks` 테이블(직조회 또는 admin 조회 API). `check_name`·`ok`·`violated_rows`·`details`.
- 복구 이력: `recovery_runs` 테이블(재생 소요 `duration_ms`·`replayed_from/to_seq`·`matched`·재생 창 식별자 `fp_replay`/`fp_live`). 판정은 `matched`이고 fp는 창 표시다(DB§5.5).
- Prometheus 지표: `exchange_ledger_imbalance{asset}`(자산 보존, 수평선 0), `exchange_invariant_violations{check_name}`, `exchange_leader_epoch`, `exchange_failover_downtime_seconds`, `exchange_sequencer_queue_size`, `exchange_order_latency_seconds`(p99), `hikaricp_connections_pending`, `exchange_trades_total`. 콘솔은 이 지표의 추이를 그리지 않고 판단이 필요한 자리에 Grafana 딥링크를 둔다(`web/components/admin/GrafanaLink.tsx`). 주소는 빌드 때 `NEXT_PUBLIC_GRAFANA_BASE`로 넣고, 값이 없으면 링크를 그리지 않는다. iframe 임베드는 하지 않는다. 예외는 채택 전 시안 `/admin/monitor`다(7-10).
- 용량 권고·증설 버튼(구현됨): 정본 7.5가 "판정은 자동이고 실행은 사람"으로 확정했고 정본 7.4 표가 조회 애플리케이션의 노드 수 증감 방식을 "관리 화면 버튼"으로 적었다. 관리 API가 노드별 지표를 직접 긁어 조회를 받는 노드의 평균 CPU 비율을 내고, 그 값이 임계를 넘으면 응답의 `advice[]`가 "조회 부하 높음" 권고를 낸다. 운영자가 버튼을 누르면 관리 API는 `capacity_plan.desired_nodes`를 바꿀 뿐이고 노드를 직접 띄우거나 내리지 않는다(API §6-A-a). 그 값을 실현하는 것은 조정기(`harness/asg/capacity_reconciler.py`)다. 그래서 호출 직후에는 계약과 관측이 어긋난 창이 실재하고 응답의 `reconciled`가 그 사실을 그대로 낸다. 권고는 표시일 뿐 자동 조치가 아니다. 지표를 직접 긁는 것과 노드를 직접 띄우지 않는 것 두 축은 정본 7.5 서술과 어긋난다. 정본 개정 소요이고 §7-9에 등재했다. 엔드포인트는 §3-1, 화면 규정은 §4-2이고 구현은 `server/app/src/main/java/kr/exchange/admin/CapacityAdminController.java`·`web/app/admin/(ops)/capacity/page.tsx`·`V32__capacity_plan.sql`이다. 수동 확장 전용 정책을 정한 ADR 0015는 ADR 0027의 AWS 자동 확장으로 대체됐다. 이 버튼은 남아 있는 로컬 구현이며 AWS ASG 정책을 대신하지 않는다.
- 권고 임계는 설정값이다(`CapacityProperties`의 `scale-out-cpu`·`scale-in-cpu`). 기본값은 조회를 받는 노드의 평균 CPU 비율 기준 증설 0.60, 축소 0.30이다. 로컬 카오스 스택용 `admin-chaos` 프로파일은 워밍된 스택에서 조회 평균 사용률이 0.33 근처에 머물러 0.60에 닿지 않으므로 0.25, 0.10으로 내린다(`application.yml` 주석의 2026-09-23 로컬 측정). 이 값들은 확정값이 아니다. ADR 0015는 선행 조건 넷(정지 노드 CPU 소각 해소, t4g.small 실물 정상 구간 관측, 알람 정확도 검증, 클라우드 API 호출 롤 설계)이 서기 전에는 임계를 확정하지 않는다고 적었고, AWS 조회 ASG의 지표·임계도 ADR 0030이 실제 AWS 시험으로 정한다고 남겼다.
- 증설 대상은 조회 축뿐이다. 증설 노드는 `exchange.engine.enabled=false`인 조회 전용이라 리더가 죽은 상태에서 노드를 늘려도 쓰기는 돌아오지 않는다. 화면 문구는 "서비스 복구"가 아니라 "조회 용량 복구"로 적는다(ADR 0015).
- 지표·헬스·불변식·복구 이력 항목은 읽기 전용이다. 조회 화면에서 파괴 액션 버튼을 노출하지 않는다(§6 안전). 용량 증설·축소는 가역 조작이라 파괴 액션이 아니고 이 제한 밖이다.

### 2-4. 회원·게시판·고객 응대 운영

- 회원: 목록·상세 조회, 정지(`SUSPENDED`)·복구(`ACTIVE`)·폐쇄(`CLOSED`). 정지·복구는 가역이므로 `operator_id`만, 폐쇄는 비가역이므로 승인 티켓(1인 승인)을 거친다(API §3-6 v2.32).
- 게시판: 코인별 게시판의 글·댓글에 대해 숨김·숨김 해제·삭제(`HIDE|UNHIDE|DELETE`, 삭제는 soft)를 한다. 신고 목록을 읽고 처리 결과(`REVIEWED|ACTIONED|DISMISSED`)를 남긴다. 대상 상태 변경과 신고 종결은 별개 엔드포인트라 원자적이지 않다(API §6-D). 하드 퍼지(영구 삭제)는 데모 범위에서 제공하지 않는다(영구 삭제는 금지 액션군).
- 입출금: 회원이 요청한 출금을 승인하거나 사유와 함께 거절한다. 요청 주체가 회원이라 승인 티켓 대신 확인 다이얼로그를 거친다. 승인하면 잠긴 금액이 빠져나가 되돌릴 수 없다(API §4-E).
- 문의: 회원 문의에 답변한다(API §4-G).
- 모든 운영 액션은 `admin_audit_log`에 대상·사유·운영자를 남긴다.
- 게시판 모듈은 매칭 핫패스와 격리되어 있어야 하므로(ROADMAP M3), 운영 액션이 실패해도 거래 상시 게이트에 영향이 없어야 한다. 운영 API는 게시판 모듈 경계 안에서만 동작한다. 현재 앱은 게시판을 거래와 같은 DB 연결로 운영하므로 물리 격리는 완료가 아니다(0099).

## 3. API 설계(관리 평면 확장)

기존 `/admin/v1/**`(§6-A/B/C)를 재사용하고, 회원·게시판·고객 응대·운영자·감사 조회를 추가한다. 조회 노드 용량 조작 3종은 신규가 아니라 API 정본 §6-A-a "용량 API"를 소비한다. 전 엔드포인트는 §3-6 보안(mTLS·서명·rate limit·감사)을 상속한다.

게시판 운영의 요청·응답은 API 설계의 `/admin/v1/community` 절이 정본이다. 관리 경로에는 글·댓글 목록 API가 없다. 웹의 커뮤니티 신고 화면은 신고 목록에 실린 대상 요약을 보고 모더레이션한다.

- 용량 3종은 카오스 API와 같은 형태로 감사 적재와 역할 게이트를 그대로 탄다(ADR 0015). 다만 적재 주체가 둘로 나뉜다. 증설·축소의 도메인 action 값(`capacity.scale_out`·`capacity.scale_in`)은 컨트롤러가 적재하고, 조회(`GET /admin/v1/capacity`)는 컨트롤러가 아니라 `AdminAuthFilter`가 `/admin/v1/*` 전 요청을 요청 단위로 적재한다. 그래서 조회도 예외가 아니다(§3-2 말미). 경로·역할·응답 축은 API 정본 §6-A-a가 이미 확정했고 본 표는 그것을 소비한다. 역할은 조회가 `VIEWER` 이상, 증설·축소가 `SUPER`다. 응답 축은 `plan`·`nodes[]`·`advice[]`이고 경계를 넘는 요청은 409 `CAPACITY_OUT_OF_BOUNDS`다(§7-9).
- 용량 조작의 승인 등급은 잠정 확정이다. API 정본 §6-A-a가 증설·축소를 `SUPER` 역할에 `불요(잠정)`으로 등재했고 구현도 `principal.require(AdminRole.SUPER)` 하나만 건다. 잠정인 이유는 ADR 0015가 카오스 4종의 완화(ADR 0014)를 들면서 "증설은 되돌릴 수 있으나 비용을 쓰는 액션이므로 같은 판단이 그대로 적용되지 않는다"고 적고 정책을 결손으로 등재했기 때문이다. 표의 `불요(잠정)`은 그 결손이 풀리면 API 정본과 컨트롤러를 함께 고친다는 뜻이다. 정책 판정 자체는 사람이 정할 미결 항목이다(§7-9).
- 클라우드 API 호출 자격은 인스턴스 프로파일 롤이다. 장기 액세스 키를 두지 않는다(정본 12 B2 "장기 접근 키가 0개", ADR 0015). 그 자격을 쓰는 것은 관리 API가 아니라 조정기다. ADR 0015가 적은 `autoscaling:SetDesiredCapacity`·`autoscaling:DescribeAutoScalingGroups`는 조정기·롤 소요이지 엔드포인트 규격이 아니다. 그 롤이 용량 변경 권한을 가지므로 앱이 자기 인프라를 바꿀 수 있게 되고, 권한 경계는 정본 8장 개정 대상이다.
- 모든 리스트는 §2-2 엔벌로프 + opaque 커서(§2-6), 페이로드 `schema_version` 포함.
- 회원 조회 응답은 데모 계정 자산·상태만 노출한다. 실명·실금융정보는 존재하지 않으므로 노출 대상 자체가 없다.
- 공지 삭제는 소프트 삭제다. `app_role`에 `notices` DELETE 권한이 없어(DB 설계 §3.1, V5 GRANT는 SELECT/INSERT/UPDATE) 하드 DELETE는 운영 롤에서 상시 실패한다. `active=false` UPDATE로 노출만 내리고 게시 원본·감사 이력을 보존한다. 없는 id는 404, 이미 비활성이면 멱등 200.

### 3-2. 파괴·비가역 액션 승인·감사 매트릭스

approval_token 필수 액션(API §3-6 완결 열거).

- 봇: `sim/bots/{id}/params`.
- 운영 확장: `members/{external_id}/close`, `operators/{id}/roles`, `operators.create`, `operators.status`, `config.market.halt`, `config.market.resume`, `config.market.fees`. API §3-6 완결 열거(v2.12 config·operators, v2.32 회원 폐쇄)와 §6-D 표에 승인 필수로 등재돼 있다.
- 승인 불요(감사만)이지만 파괴 액션: 카오스 주입·해제 4종(`chaos/kill-node`, `chaos/network` POST·DELETE, `chaos/app`). API §3-6·§6-B v2.34가 필수 열거에서 뺐다. 토큰을 제시하면 아래 바인딩 규칙으로 검증·소각하고, 제시하지 않으면 `approval_id`가 null인 채 감사에 적재된다. 완화 근거와 대가는 §2-2-a에 있다.
- 승인 불요(확인 다이얼로그)이지만 비가역: 출금 승인. 요청 주체가 운영자가 아니라 회원이라 티켓을 걸지 않는다(§2-4).
- 승인 불요(감사만)이고 비파괴: `config.notice.publish`, `config.notice.update`, `config.notice.delete`(소프트). 공지는 원장·매칭에 닿지 않는 운용 상태라 SUPER 단독으로 처리한다.
- 승인 불요(감사만)이고 등급은 잠정: 용량 증설·축소(`capacity.scale_out`, `capacity.scale_in`, §3-1). 이 두 문자열이 구현의 감사 action 값이다(`CapacityAdminController`, `web/lib/admin/simAdmin.ts`). API 정본 §6-A-a가 `SUPER` 역할에 `불요(잠정)`으로 등재했고, 잠정인 이유는 ADR 0015가 "증설은 되돌릴 수 있으나 비용을 쓰는 액션이므로 같은 판단이 그대로 적용되지 않는다"고 적고 정책을 결손으로 등재했기 때문이다. 본 설계는 등급을 지어내지 않고 정본의 잠정값을 소비하며, 정책 판정은 사람이 정할 미결 항목으로 남긴다. 용량 조회(`GET /admin/v1/capacity`)는 조회라 다른 GET과 같이 불요다. 결손이 풀릴 때까지 역할 게이트와 append-only 감사가 유일한 통제다.
- 각 액션의 파괴 액션 바디 필드와 발급·소각 `target` 문자열 형식은 API §3-6 "바인딩 target·바디 필드 확정표"(v2.13)가 정본이다. 요지: 자원 스코프는 `target`=자원 식별자(node·name·assault·toxic·symbol·bot_id·new_operator_id), 전이 스코프 `operators.status`는 `{id}:{STATUS}`·`operators.roles`는 `{id}:{GRANT|REVOKE}:{ROLE}`(대문자 정규화). `operators.create`는 수행자 `operator_id`와 생성 대상 `new_operator_id`를 분리한다.

전 관리 엔드포인트(조회 포함)는 예외 없이 `admin_audit_log` 적재 대상이다. 승인 필수 액션은 요청 바디에 `operator_id` + `approval_token`을 포함하고, 누락·불일치·만료는 `403 admin_forbidden`. 카오스 4종은 `operator_id`만 필수이며, 토큰을 실었는데 불일치·만료면 같은 코드로 거부한다. `operator_id`의 권위는 바디 자가신고 값이 아니라 인증 주체 유래 값이다(§3-6 v2.4).

## 4. 프론트 설계(관리자 화면)

### 4-1. 라우트·레이아웃 분리

관리 화면은 별도 앱이 아니라 거래 웹과 같은 Next.js 앱의 `web/app/admin/` 아래 라우트다. 정적 export가 전 라우트를 함께 내보내므로 공개 번들에서는 `scripts/prune-admin-bundle.mjs`가 관리 라우트 산출물을 지우고 `--check`로 잔존 여부를 판정한다. 이 정리는 경로 이름 기준이라 공용 청크로 옮겨진 관리 코드는 잡지 못한다고 스크립트가 스스로 적는다. 학교 배포 빌드(`deploy/linux/app/build-web.ps1`)는 이 정리 단계를 거치지 않고, 앱 Nginx는 `/admin/` 정적 파일을 그대로 서빙한다(`deploy/linux/app/nginx-admin.conf`). 0099의 공개 빌드 제거 원칙, ADR 0031의 접속 범위(`/admin/bots`)와 어긋나는 상태이며 범위 결정은 7-10에 남겼다.

세션 게이트는 `web/app/admin/layout.tsx`의 `AdminGate` 하나이고 두 평면이 공유한다. 평면을 건너갈 때 세션 확인이 다시 돌지 않게 하려는 배치다. 평면은 Next 라우트 그룹 두 개로 나뉘고, 라우트 그룹은 주소에 나타나지 않으므로 기존 주소는 그대로다. 각 평면의 셸(`AdminShell`)이 좌측 내비, 상단 운영자 바와 다른 평면으로 가는 링크를 갖는다. 거래 UI의 `HeaderNav`를 재사용하지 않고 고정형 데스크톱 전제(최소 1280px, 데스크톱 레이아웃 §4)를 유지한다. 내비 정의는 `web/lib/admin/nav.ts`에 있다.

운영 관제 `web/app/admin/(ops)/`는 인프라 상태와 조작, 시연을 맡는다.

| 주소 | 화면 | 갱신 방식 |
|---|---|---|
| `/admin` | 종합 관제 | idle(30초) |
| `/admin/capacity` | 용량·부하 | manual |
| `/admin/bots` | 봇 플릿 | idle(30초) |
| `/admin/drill` | 상황별 대본 | idle(30초), 주행 중 live(3초) |
| `/admin/flow` | 서비스 흐름(채택 전 시안) | 백엔드 호출 없음, 화면 안 재생 |
| `/admin/monitor` | 지표 관제(채택 전 시안) | 백엔드 호출 없음, 화면 안 재생 |

백오피스 `web/app/admin/(back)/`는 제품 운영을 맡는다. 진입점 `/admin/back`(처리 대기)과 출금 승인 `/admin/transfers`, 문의 답변 `/admin/support`, 커뮤니티 신고 `/admin/community`, 회원 운영 `/admin/members`, 마켓·공지 `/admin/config`, 운영자·역할 `/admin/operators`, 감사 로그 `/admin/audit`이 있다. 백오피스 화면의 조회는 모두 manual이고, 승인 목록을 싣는 회원·마켓·운영자 화면은 아래 승인 원장 폴러를 함께 쓴다.

카오스 화면 `/admin/chaos`와 모니터링 화면 `/admin/monitoring`은 리다이렉트 없이 삭제했으므로 현재 빌드에는 그 주소가 없다. 이전 빌드를 배포한 환경에는 남아 있을 수 있다.

갱신 방식은 화면이 밀리초를 직접 적지 않고 세 리듬 중 하나를 고른다(`web/components/admin/useAdminResource.ts`). manual은 진입 1회와 새로고침만 하고, 값이 언제 것인지 보이도록 화면 머리에 최종 실측 시각과 새로고침 버튼을 둔다(`ResourceStamp`). idle은 30초, live는 3초이며 live는 시연 구간에만 쓴다. 승인 원장은 단일 폴러가 구독자 수로 켜고 끄며 30초마다 읽는다(`web/lib/admin/approvals.ts`). 시연 구간에 원장을 5초로 올리던 함수는 부르는 화면이 없어 지웠으므로 원장은 항상 30초로 읽는다. 상황별 대본의 live(3초)는 대본이 읽는 자원에만 적용되고 원장 주기를 바꾸지 않는다(7-10). 조작 직후에는 주기를 기다리지 않고 한 번 더 읽는다. 폴링 실패는 마지막 값을 유지하고 stale 표시를 세우며, 세션 만료는 값 유무와 무관하게 오류로 올린다. 429를 받으면 `Retry-After`만큼 폴링을 쉬고, 그 값이 없으면 10초를 쉰다. 폴링 주기는 서버가 관리 요청 한 건마다 운영자 버킷에서 10토큰을 빼는 기준으로 잡았다(§1-1). 계약 기본 버킷(60초에 60토큰)으로는 분당 6건이라 콘솔을 쓰는 배포는 버킷을 올린다. 요청 수가 줄었다는 것은 구성으로 성립하는 판단이고 측정한 값은 아니다.

`PanelCard`·`DataTable` 등 레이아웃 프리미티브는 재사용 가능하나, 거래 도메인 컴포넌트(OrderPanel·OrderbookPanel 등)는 가져오지 않는다.

### 4-2. 화면 구성

- 종합 관제: "지금 손댈 것이 있나"에 답하는 읽기 전용 요약이다. 상단 판정(`HealthHero`)은 불변식을 한 줄로 판독한다. 분모는 서버 응답 행 수가 아니라 기대 검사 수이고, 행이 없으면 통과가 아니라 미수집, 일부만 있으면 부분 수집으로 적어 주의로 표시한다. 위반은 장애다. 마지막 페일오버 복구 시간과 판정도 여기에 있다. 아래에 매칭 리더·선출 세대, 활성 봇, 중지 마켓 타일과 승인 대기 목록, Grafana 딥링크가 있다. 노드 목록은 그리지 않고 용량 화면에서 본다. 종합 데이터는 어댑터가 여러 조회를 합성한 것이다.
- 용량·부하: 계약 대수와 관측 대수, 노드별 상태, 권고를 보이고 증설·축소는 확인 다이얼로그를 거친다(§2-3). 봇 발행률을 바꾸는 부하 레버도 이 화면에 있다. 한 번 읽을 때 서버가 노드마다 readiness·read·prometheus를 찔러 텍스트를 파싱하므로 manual로 둔다. 주문을 처리하는 노드는 한 대뿐이고 늘릴 수 없다는 사실과, 리더가 죽으면 증설로 조회 용량만 돌아온다는 사실을 화면이 적는다.
- 봇 플릿: 플릿 요약(활성 봇·현재 OPS·성공률·평균지연·`duplicate_fill_total`), 시나리오, OPS, 봇 생성, 실행 중 파라미터 변경(승인 티켓 동반). 시장 생동감 컨트롤(정본 §6-A set-point 소비)로 마켓·유형별 대수(`sim/scale`), 방향 바이어스(Blue~중립~Red, 부호·화살표·수치 병기, 색 단독 표현 금지)와 자동균형(`sim/bias`), 효과 강도 4단계(`off|subtle|normal|strong`, `sim/effects`)를 둔다. 셋 다 approval 불요·감사만이다. 상태는 `sim/status`를 30초마다 읽고 텔레메트리 WS는 구독하지 않는다.
- 상황별 대본: 네 상황을 단계로 펴고 각 단계의 충족을 지금 읽은 값에서만 판정한다(`web/lib/admin/drills.ts`). 대본은 트래픽 임계와 조회 증설, 앱 리더 전환, DB 수동 복구, 디스크·메모리 압박이다. 단계 상태는 `MET`(지금 값에서 확인), `PENDING`(원천은 읽었고 아직 미충족), `MISSING`(이번에 못 읽음), `BLOCKED`(앞 단계 미완료), `NO_SOURCE`(이 환경에 수집기 없음)다. 리더 중단이나 DB 승격처럼 관리 API에 없는 조작은 버튼이 아니라 복사할 명령 문자열로 적는다. DB 수동 복구는 별도 실습 스택에서 돌아 이 콘솔이 읽을 값이 없으므로 절차와 명령만 싣고 서버 호출을 하지 않는다. 디스크·메모리 압박은 모든 단계가 `NO_SOURCE`다. 대본은 필요한 축만 읽고, 주행을 켜면 live로 바뀌며 이번 주행의 충족 기록을 저장하지 않는다. 충족 시각은 앞 단계를 지난 단계에만, 주행을 켠 뒤이면서 앞 단계 기록보다 늦게 요청한 관측에서만 기록한다. 리더 대본은 선출 세대가 올랐는지 확인하고, 복구 판정은 주행 시작 이후 적재된 행만 읽는다(`since`). 증설 대본의 '사용률 하락'은 단일 표본으로 판정하고 부하가 증설 전과 같은지는 확인하지 못한다(7-10 (c)).
- 서비스 흐름(시안): AWS 목표 구성의 역할과 요청 경로를 한 화면에 그리고, 로컬 Docker 측정 기록의 사건 순서와 간격을 재생한다. 사건 사이의 값은 지어낸 것이다. 값은 `web/lib/admin/flowSim.ts`가 만들고 주행 상태는 `web/lib/admin/flowRun.ts`가 지표 관제와 공유한다. 컨테이너에 명령을 보내지 않고, 같은 일을 실제로 일으키는 호스트 명령은 대화상자에서 복사만 할 수 있다. 화면에 보이는 시뮬레이션 표식은 없고 보조기술용 문구에만 남아 있다(7-10).
- 지표 관제(시안): 서비스 흐름과 같은 재생 주행을 시계열 여섯 장과 인스턴스 표로 보인다. 머리 설명에 "값은 시뮬레이션 · 실제 추이는 Grafana"가 보인다. 콘솔이 추이를 그리지 않는다는 원칙과 충돌하므로 채택 전이다(7-10).
- 백오피스 처리 대기: 출금·문의·신고 세 큐의 첫 쪽 건수만 읽는다. 상한을 채우면 그 이상이라고 적는다. 큐는 따로 읽고 따로 판정한다(`web/lib/admin/queueCounts.ts`). 권한 거절은 '권한 없음', 읽기 실패는 미수집으로 적어 0건과 구분하고, 세션 만료이거나 권한과 무관하게 세 큐가 모두 실패했을 때만 화면 전체를 오류로 올린다. 큐에 일이 있는 것은 정상 업무라 건수에 경고 색을 붙이지 않는다.
- 회원·게시판·고객 응대: `DataTable` 기반 목록·필터·상세와 정지·복구·폐쇄 요청, 숨김·삭제, 신고 처리, 출금 승인·거절, 문의 답변(가역/비가역 시각 구분). 폐쇄 판단에 미체결 주문 수가 필요해 회원 상세를 옆에 세운다. 문의 답변은 긴 답을 쓰는 동안 원문이 가려지지 않게 다이얼로그 없이 같은 화면에 나란히 둔다.
- 마켓·공지와 운영자·역할: 마켓 halt·resume·수수료와 운영자 생성·상태·역할은 SUPER와 승인 티켓을 거친다. 공지는 SUPER가 즉시 발행하고 소프트 삭제·active 토글을 제공한다.
- 감사 로그: append-only 조회 테이블(운영자·action·대상·시각, 클라이언트 필터: 운영자·액션·결과·기간). 표시층은 액션 코드에 한국어 주해를 병기하되 원문 코드를 상시 노출한다. 기록 원문은 불변이다. 필터는 받아 온 행에서만 걸리므로 범위 한계를 캡션이 알린다.

### 4-3. 시스템 헬스 색 도메인(시세색과 분리)

- 헬스 상태는 `--color-success`(green)·`--color-warning`(orange)·`--color-danger`(crimson)와 대응 `-bg`·`-text` 토큰을 쓴다. 상태 전이 플래시는 `--color-health-flash-success|warning|danger`를 쓴다(디자인시스템 §시스템 헬스).
- 시세색(상승 Red `--color-up`, 하락 Blue `--color-down`)을 헬스 도메인에 차용하지 않는다. green은 시스템 성공 전용이며 가격 방향에 쓰지 않는다(디자인시스템 규칙 13).
- 상태 표현은 색 단독 금지. 점·아이콘·라벨 텍스트를 병기한다(danger는 항상 아이콘+라벨 동반). 대비 4.5:1, 탭 타깃 44px, reduced-motion 준수.
- 상태(로딩·빈·에러) 설계: 각 패널은 스켈레톤 로딩, 데이터 없음 빈 상태, 조회 실패 에러 상태를 명시 렌더한다. WS 단절은 헤더에 연결 상태 점(연결 green·단절 crimson)으로 노출하되 시세 도메인과 색을 분리한다.
- 실시간 갱신은 시각 소음 없이 전달한다. 지표 급변은 플래시 1회로 제한하고 스크롤·리플로우를 유발하지 않는다.

## 5. 하드코딩·토큰 규약

- 프론트 하드코딩 hex 금지(코인 브랜드색 데이터만 예외). 헬스 색은 전부 토큰 소비.
- 금액·수량은 문자열(`NUMERIC(40,18)`), float 금지. 봇 파라미터·시드도 문자열 표기(정수·불리언 필드만 예외, §3-3(b)).
- 관리자 UI도 런타임 외부 API 의존 금지. Grafana·Prometheus는 운영자 네트워크 내부 스택이며 외부 시세·외부 데이터에 의존하지 않는다.

## 6. 안전 규약

- 관측 데이터 지시 자동 실행 금지: 지표·로그·불변식 결과·게시글 본문 등 관측 경로로 들어온 텍스트를 명령으로 해석해 API를 호출하지 않는다. 서명 매개는 프록시·렌더만 하고 파괴 액션 생성 권한이 없다.
- 파괴 액션은 운영자 명시 요청 전제: kill-node·network·app·파라미터 변경·회원 폐쇄·역할 변경은 운영자의 직접 조작이 있어야 실행된다. 파라미터 변경·회원 폐쇄·역할 변경은 승인 티켓(1인 승인)도 필요하고, 카오스 4종은 v2.34 완화로 직접 조작만 전제한다(§2-2-a). 임계 초과·경보 발생만으로 실행되지 않는다.
- 금지 액션군: 실금융자격증명 입력, 계정 실인증, 영구 삭제(하드 퍼지·감사 로그 삭제), 자금 이동·거래 체결. 데모 시뮬레이션 범위 밖 요청은 거부한다.
- 데모 한정: 전 기능은 시드된 데모 환경에서만 유효하다. 데모 리셋 시에만 네임스페이스가 초기화된다(§2-4 보존 정책).
- 최소 권한과 승인 티켓: 조회는 `VIEWER`, 변경은 역할별, 승인 필수 액션(§3-2)은 승인 티켓을 요구한다. 1인 승인이라 `SUPER` 한 명이 요청과 발급을 모두 할 수 있고, 단독 운영자의 고의는 사전에 막히지 않고 사후 감사로만 드러난다(ADR 0019). 카오스 4종은 티켓도 요구하지 않고 역할 게이트와 사후 감사만 남는다(§2-2-a).

## 7. 정본 정합·미결

정본과 어긋나거나 사람이 정해야 하는 지점이다. 계약이 틀렸으면 계약을 먼저 고친 뒤 코드를 맞춘다.

1. API §3-6 approval 필수 열거 확장(해소): 본 설계가 승인 필수로 둔 회원 폐쇄·운영자·마켓 설정 액션은 API §3-6 완결 열거에 들어갔다(v2.12 config·operators, v2.32 `members/close`).
2. `api_keys.scope` ADMIN 확장(해소, v1.2): V5__admin.sql이 CHECK를 `('READ','TRADE','WITHDRAW','ADMIN')`로 확장하고 `(scope='ADMIN') = (operator_id IS NOT NULL)` 바인딩 CHECK를 추가해 API §3-2/§7-1 전제를 충족한다. scope 정본 어휘는 대문자 4종이며 API §3-2 v2.10이 소문자·`read_only` 표기를 폐기했다.
3. `admin_audit_log` 테이블(해소): V5__admin.sql이 관리 전용 append-only 테이블로 만들었다.
4. 관리 UI 인증 방식(확정): 운영자별 mTLS 클라이언트 인증서(`CN=operator_id`)로 1차 인증하고, 그 신원에서 유래한 단기 관리자 세션으로 후속 요청을 인증한다(§1-3). 세션은 자가신고를 금지하고 관리 평면 전용이다. 조회는 단독 운영자 세션으로 가능하고, 승인 필수 액션은 승인 티켓이 필요하며 1인 승인이라 본인 발급도 된다(ADR 0019). 카오스 주입은 v2.34 완화로 단독 운영자 세션에서 실행된다(§2-2-a). 학교 배포는 비밀번호 게이트웨이 예외다(ADR 0031). API §3-6의 브라우저 관리 콘솔 세션 절 가운데 "요청 운영자와 다른 운영자가 발급", "발급 주체 ≠ 사용 주체 검증" 문장은 ADR 0019 이전 서술로 남아 있어 API 정본 정리가 필요하다.
5. 게시판 테이블 의존: 회원·게시판 운영은 M3 게시판 모듈(별도 설계)의 글·댓글 상태를 소비한다. 관리 평면은 게시판 테이블에 물리 FK를 만들지 않는다(격리). 게시판의 DB·프로세스 격리 요구 자체가 아직 결정 대기다(0099).
6. V 번호(부분 해소, v1.2): 관리 평면 스키마(scope 확장·운영자·승인·역할·system_config·감사)는 V5__admin.sql로 배정·적용됐다. 잔여 신규 마이그레이션은 착수 시점 다음 가용 V로 배정하며 본 문서에서 고정하지 않는다.
7. ApprovalState 어휘 정합(해소): 웹 `web/lib/admin/types.ts`의 `ApprovalState`가 정본과 같은 `ISSUED|CONSUMED|EXPIRED|REJECTED`를 쓴다. 발급 전 의도는 서버 상태가 아니라 화면의 로컬 상태다(§1-4).
8. 카오스 승인 완화 정합(해소, v1.3): API §3-6·§6-B v2.34가 카오스 주입·해제 4종을 approval_token 필수 열거에서 뺐고(커밋 89b1e40) 본 문서가 그 계약으로 정합했다(§2-2·§2-2-a·§3-2). 이후 ADR 0019(V34)가 `chk_approval_two_person`을 포함한 2인 제약을 모든 승인에서 뗐다. 카오스 카탈로그 응답(`ChaosAdminController.catalog`)의 `approval_required`는 `false`다. 카탈로그 9종이 전부 카오스 4종 액션이라 완화 대상이다. 서버 `ApprovalService` 클래스·`consume` 주석과 `ChaosAdminController.consumeIfPresent` 주석은 아직 2인 승인과 "사용 주체 == 발급 주체 거부"를 적고 있어 코드와 맞지 않는다.
9. 용량 조작 엔드포인트(계약·구현 해소, 정책 미결, v1.4): 정본 7.4·7.5와 ADR 0015가 조회 노드 증감을 "관리 화면 버튼"으로 확정했고, API 정본 §6-A-a "용량 API"가 경로 3종·역할·응답 축(`plan`·`nodes[]`·`advice[]`)과 409 `CAPACITY_OUT_OF_BOUNDS` 규약을 확정했다. §3-1은 그 계약을 소비만 하고 확정하지 않는다. 구현도 서 있다. 서버 `CapacityAdminController`, 스키마 `V32__capacity_plan.sql`, 조정기 `harness/asg/capacity_reconciler.py`, 화면 `web/app/admin/(ops)/capacity/page.tsx`다. 남은 미결이 셋이고 전부 정책 축이다. (a) 승인 등급을 ADR 0015가 결손으로 남겼고 API 정본은 `불요(잠정)`으로 둔다(§3-2). (b) 권고 임계값을 ADR 0015가 선행 조건 넷 전에는 정하지 않기로 했고 구현은 설정 기본값 0.60·0.30과 로컬 프로파일 값 0.25·0.10을 든다(§2-3). (c) 클라우드 API 호출 롤과 권한 경계가 정본 8장 개정 대상이다. 그 자격을 쓰는 것은 관리 API가 아니라 조정기다(§3-1). 셋 다 사람이 정해야 하고 본 설계가 값을 지어내지 않는다. 정책 미결과 별개로 정본 7.5가 두 축에서 스테일하다. (가) 실행 경로. 정본 7.5는 관리자가 버튼을 누르면 요청이 관리 API를 지나 클라우드 API를 부른다고 적으나, API 정본 §6-A-a와 구현은 관리 API가 `capacity_plan.desired_nodes`만 바꾸고 실현은 조정기가 맡는다고 적는다. (나) 지표 원천. 정본 7.5는 Prometheus가 노드 지표를 모은다고 적으나, 구현은 관리 API가 노드별 액추에이터를 직접 물어본다(`NodeProbe`). 본 설계 §2-3은 계약·구현 쪽을 적었고 정본 7.5 개정이 남은 소요다. 판정은 자동이고 실행은 사람이라는 정본 7.5의 규정 자체는 그대로 산다.
10. 2026-09-23 콘솔 개편 뒤 남은 불일치와 결정(코드 판독 기준, 브라우저 실주행으로 재현하지 않은 항목 포함).
    - (a) 결정 근거: 두 평면 분리와 "콘솔은 추이를 그리지 않고 Grafana로 딥링크한다"는 규칙을 정한 ADR이 없다. `GrafanaLink`와 0099는 ADR 0032를 근거로 드는데, 0032는 Grafana 기본 관제와 `deploy/console`을 다루고 `web/app/admin`을 다루지 않는다.
    - (b) 시안 채택: `/admin/monitor`는 콘솔 안에서 시계열 여섯 장을 그려 (a)의 규칙과 충돌하면서 운영 관제 내비에 노출돼 있다. `/admin/flow`에는 보이는 시뮬레이션 표식이 없고 보조기술용 문구에만 남아 있어, 같은 시뮬레이터의 머리 주석 "화면이 늘 시뮬레이션임을 표시해야 한다"(`flowSim.ts`)와 어긋난다. 코드 주석은 표식 제거를 2026-09-23 사용자 결정으로 적는다. 구성도의 ASG 상자가 매칭 리더까지 감싸는지, compose에 없는 자원을 '실행'으로 그리는지도 채택 판단에 포함한다. 채택·보존·폐기는 사용자 결정 대기다.
    - (c) 대본 판정(대부분 해소, 2026-09-23, 웹 단위 시험만 확인했고 실제 스택과 학교에서는 주행하지 않음): 같은 날 웹 수정으로 다섯 가지를 고쳤다. 게이트에 막혀 `BLOCKED`로 보이는 단계의 원시 `MET`까지 기록해 일어나지 않은 단계를 '완료'로 남기던 판정, 최대 대수에서 증설 권고가 사라지면 사용률과 무관하게 충족되던 '사용률 하락', 선출 세대를 보지 않고 복구 판정을 주행 창으로 좁히지 않던 리더 대본, `chaos-api-1`로 고정된 옛 리더 복귀 명령, 학교에서는 판정한다고 적던 디스크·메모리 대본 주석이다(`web/lib/admin/drills.ts`, `web/app/admin/(ops)/drill/page.tsx`, 4-2절). 남은 한계는 '사용률 하락' 하나다. 콘솔이 노드별 조회 요청률을 읽지 않아 부하가 증설 전과 같은지 확인하지 못한다. 부하 잔존, 조회 노드 증가, 평균 하락을 한 표본에서 보므로 흔들린 표본 하나로도 충족이 기록될 수 있다. 연속 표본을 요구하려면 판정 상태 구조를 바꿔야 한다.
    - (d) 레이트리밋 가정(해소, 2026-09-23, 코드 판독과 웹 단위 시험·빌드만 확인): 웹이 관리 버킷을 요청 1건당 1토큰으로 가정하던 폴링 예산을 서버와 같은 10토큰 기준으로 고쳤고, 승인 원장 폴러를 30초 단일 주기로 줄였다(`useAdminResource.ts`, `approvals.ts`, 4-1절). 로컬 관리 프로파일은 버킷을 6000으로 올려 두 가정의 차이가 드러나지 않으므로, 학교 버킷에서 폴링이 조작 요청에 얼마를 남기는지는 측정하지 않았다.
    - (e) 권한과 화면(부분 해소, 2026-09-23, 웹 단위 시험만 확인했고 학교 관리 평면에서는 확인하지 않음): `/admin/back`이 세 큐 가운데 하나만 실패해도 화면 전체를 오류로 만들던 문제를 고쳤다. 이제 큐를 따로 판정한다(`web/lib/admin/queueCounts.ts`, 4-2절). 남는 것은 권한 설계다. 신고 목록은 `MEMBER_MOD`를 요구하므로 `VIEWER`·`BOT_OPS`만 가진 학교 봇 운영자(`deploy/linux/bot/register-bot-operator.sql`)에게는 출금·문의 건수는 보이지만 신고 큐가 '권한 없음'으로 보인다. 이 역할에 신고 건수를 보여 줄지는 정하지 않았다.
    - (f) 학교 공개 범위: 학교 빌드는 관리 화면 정적 파일 전체를 공개 번들에 싣는다(§4-1). 관리 화면 전체 공개를 결정으로 받아들일지, `/admin/bots`만 남기도록 빌드를 나눌지는 사용자 결정 대기다.
    - (g) 호출되지 않던 원장 승격(해소, 2026-09-23, 웹 단위 시험·빌드만 확인): 부르는 화면이 없던 `approvals.ts`의 `setApprovalLedgerLive`(5초)를 지웠다. 대본은 용량·봇 상태·리더·복구 응답만 읽고 승인 원장을 읽지 않으므로 원장 주기를 올릴 이유가 없다. 대본이 승인 상태를 판정하게 되면 그때 주기를 다시 정한다.
    - (h) 불변식 목록 대조의 범위: 종합 관제의 불변식 분모는 서버 `InvariantCheck` 목록에 맞췄고, `web/tests/invariants.test.ts`가 서버 Java enum을 읽어 웹 카탈로그와 대조한다. 그러나 `.github/workflows/ci-web.yml`은 `web/**`와 웹 빌드 스크립트·워크플로 자신이 바뀔 때만 돌므로 서버 enum만 바꾼 변경은 이 대조 없이 통과한다. 트리거 경로에 `InvariantCheck.java`를 넣을지는 CI 규칙에 관한 사용자 결정으로 남아 있고, 그 전까지 두 목록의 어긋남은 웹 시험을 돌릴 때만 드러난다.
