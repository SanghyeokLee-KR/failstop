# 차트·기술적분석 설계

버전 v1.0. 트레이딩 화면(`/exchange/[market]`)의 메인 차트를 캔들·지표·그리기·실시간을 갖춘 기술적 분석 차트로 확정한다. 프론트 통합과 백엔드 캔들 파이프라인 계약을 한 문서에 담되 파트를 구분한다.

정본 관계. 색·타이포·모션·간격은 `docs/reference/contracts/프론트_디자인시스템.md`(tokens.css 계약)를 따른다. 그리드·패널은 `docs/reference/contracts/데스크톱_레이아웃설계.md`를 따른다. 캔들 REST·WS 스키마는 `docs/reference/contracts/백엔드_API_설계.md`(§4-A-5, §5-3, §5-4)를 미러한다. 데이터 소스 원천·집계는 `docs/reference/contracts/백엔드_DB_설계.md`(§4 trades, §6.2 event_journal, §7 candles 로드맵)를 따른다. 본 문서가 정본과 어긋나면 정본을 먼저 고치고 본 문서를 맞춘다. 본 문서가 정본 개정을 요구하는 지점은 §7에 모아 표기한다.

## 1. 목표·범위

### 1.1 "제대로 된 차트"의 정의

- 메인 pane에 OHLC 캔들과 거래량을 겹쳐 표시한다. 크로스헤어 이동 시 해당 봉의 OHLCV·등락을 툴팁으로 읽는다.
- 가격 오버레이 지표(MA, EMA, 볼린저밴드)와 보조 pane 지표(MACD, RSI, 스토캐스틱)를 내장한다.
- 타임프레임을 전환한다(1s, 1m, 3m, 5m, 15m, 30m, 60m, 240m, 1d, 1w. 서버 unit 집합 전량. §3.2). UI 라벨 "1시간"·"4시간"은 계약 unit `60m`·`240m`에 매핑한다.
- 그리기 도구를 제공한다(추세선, 수평선, 피보나치 되돌림).
- 실시간으로 마지막 캔들을 갱신하고, 시간 경계에서 새 캔들로 롤오버한다. 갱신 중 레이아웃 시프트는 0이다.

### 1.2 토이와의 경계

- 가짜 데이터를 그리지 않는다. 캔들은 우리 백엔드의 체결(trades)에서 파생한 OHLCV거나, 정적 export 데모에서는 SimEngine이 같은 규약으로 생성한 값이다(§8). 지표는 이 캔들에서 계산한다. 외부 시세·차트 데이터를 런타임에 가져오지 않는다.
- 런타임 외부 API 의존이 0이다. 차트 라이브러리는 번들에 포함해 자족한다. 외부 CDN·위젯·폰트·타일 서버를 로드하지 않는다.
- 금액·수량의 신뢰값은 문자열(`NUMERIC(40,18)`)로 다룬다. 픽셀 스케일·지표 계산에만 숫자 변환을 허용한다(§3.6).

### 1.3 범위 밖

- 차트 이미지 내보내기, 다중 심볼 비교, 사용자 지표 스크립팅은 본 버전 범위 밖이다.
- 모바일·반응형은 하지 않는다. 데스크톱 고정형(최소 1280px)만 대상이다.

## 2. 라이브러리 선택

### 2.1 후보 판정

| 후보 | 라이선스 | 렌더 | 지표 | 그리기 | 외부 호출 | 판정 |
|---|---|---|---|---|---|---|
| **klinecharts** | Apache-2.0 | 순수 canvas | 내장(MA·EMA·BOLL·MACD·RSI·KDJ 등) | 내장(추세선·수평선·피보나치 등) | 0 | **권고** |
| TradingView Lightweight Charts | Apache-2.0 | 순수 canvas | 없음(직접 구현) | 없음(프리미티브로 직접 구현) | 0 | 대안(현 미니 차트에 잔존) |
| TradingView Advanced(프로 위젯) | 상용·브랜드 | iframe·위젯 | 내장 | 내장 | 있음(위젯 로드) | 탈락 |

### 2.2 최종 권고: klinecharts

메인 기술적 분석 차트는 klinecharts로 구현한다. 근거는 다음과 같다.

- **자족성.** 순수 canvas 렌더러이고 런타임 네트워크 호출이 없다. npm 패키지를 번들에 포함하면 정적 export(`out/`)만으로 오프라인 동작한다. 페이지가 넘긴 `--font-sans`로 텍스트를 그리며 웹폰트를 외부에서 가져오지 않는다.
- **기능 내장.** 지표(이동평균·지수이동평균·볼린저밴드·MACD·RSI·스토캐스틱)와 그리기 도구(추세선·수평선·피보나치)가 라이브러리에 포함돼 있다. "제대로 된 차트" 요건을 직접 구현 없이 충족한다.
- **테마 주입.** 색·폰트·격자·크로스헤어·축을 스타일 객체로 전면 오버라이드한다. tokens.css 값을 `getComputedStyle`로 읽어 주입하면 라이트·다크 전환과 방향색(Red/Blue) 매핑을 계약대로 강제할 수 있다(§4).
- **라이선스·브랜드.** Apache-2.0이고 attribution 의무가 없다. 레퍼런스 브랜드 마크·색·모양을 차용하지 않는다는 프로젝트 규칙(docs/ai/engineering.md §16)과 충돌하지 않는다.

### 2.3 대안과 트레이드오프

- **Lightweight Charts.** 이미 저장소에 있고(`web/package.json` `lightweight-charts ^5.0.0`) 미니 차트(`web/components/CandleChart.tsx`)가 이를 쓴다. 순수 canvas·Apache-2.0로 자족성은 동일하다. 단 지표·그리기 도구가 없어 MA·EMA·BOLL·MACD·RSI·스토캐스틱과 추세선·피보나치를 전부 직접 구현해야 한다. 메인 차트를 이 위에 올리면 구현·유지 비용이 klinecharts 대비 크게 늘어난다. attribution 로고는 `attributionLogo:false`로 끌 수 있고 Apache-2.0가 이를 허용하나, TradingView 브랜드 가이드가 로고 제거 시 텍스트 attribution을 권고한다. 브랜드 차용 금지 규칙과 마찰 소지가 있어 메인 차트 기준으로는 klinecharts가 깔끔하다.
- **TradingView Advanced 위젯.** 지표·그리기가 완비돼 있으나 위젯을 런타임에 로드하고 상용 라이선스·브랜드 의존을 동반한다. "런타임 외부 API 의존 금지"와 "레퍼런스 브랜드 차용 금지"를 동시에 위반한다. 탈락한다.

### 2.4 두 라이브러리 공존과 번들 규율

- 메인 기술적 분석 차트(트레이딩 화면) = klinecharts. `web/components/chart/`에 신설한다.
- 미니 캔들(대시보드 `web/components/dashboard/SpotlightPanel.tsx`) = 기존 `CandleChart`(Lightweight Charts) 유지. 지표·그리기가 필요 없고 이미 성능이 검증돼 재작성 이득이 없다.
- 미니 추세선(대시보드 요약 스트립 `web/components/dashboard/Sparkline.tsx`) = 무의존 SVG 유지.
- 두 캔들 라이브러리는 코드 스플릿으로 격리한다. 메인 차트는 `next/dynamic` + `ssr:false`로 로드하므로 대시보드 방문자는 klinecharts를, 트레이딩 화면 방문자는 Lightweight Charts를 각각 내려받지 않는다.

### 2.5 자족성·번들 검증 절차

착수 시 다음을 실측·기록한다.

- klinecharts 버전 고정. 지표·오버레이 API가 안정된 라인을 선택하고 정확한 버전을 `package.json`에 박제한다.
- 번들 크기. `npm run build` 후 번들 애널라이저로 klinecharts 청크의 gzip 크기를 측정해 기록한다. Lightweight Charts와 동일 수준(순수 canvas, 런타임 의존 0)임을 확인한다.
- 외부 호출 0. 빌드 산출물(`out/`)에서 외부 URL·`fetch`·웹소켓·웹폰트 참조를 grep으로 확인한다. 차트가 우리 DataSource(§5) 외 어떤 엔드포인트도 부르지 않음을 오프라인 로드로 실증한다.

## 3. 프론트 설계 (frontend 파트)

### 3.1 컴포넌트 구조·폴더

신규 `web/components/chart/`.

| 파일 | 책임 |
|---|---|
| `TradingChart.tsx` | 메인 풀 TA 차트. 클라이언트 전용, `ssr:false` 동적 로드. init·resize·dispose 수명주기, 데이터·실시간 배선, 테마 반영을 담당 |
| `ChartToolbar.tsx` | 타임프레임 `SegmentedTab`(A-9 재사용) + 지표 토글 메뉴 + 그리기 도구 버튼 + 초기화. 상단 툴바 1행 |
| `chartTheme.ts` | tokens.css → klinecharts 스타일 객체 매핑(캔들·거래량·격자·크로스헤어·축·지표선). 하드코딩 hex 없음, 토큰 이름만 소비 |
| `useChartTheme.ts` | `getComputedStyle`로 토큰 해석, `[data-theme]` MutationObserver + `prefers-color-scheme` matchMedia로 테마 전환 시 재주입. 기존 `CandleChart.tsx`의 패턴을 재사용 |
| `candleStream.ts` | DataSource 캔들 배선. 초기 REST 로드 + 캔들 채널 구독을 klinecharts `applyNewData`/`updateData`로 연결(§3.5). 화면 코드는 여기만 통해 데이터에 접근 |
| `indicators.ts` | 지표 레지스트리(오버레이·보조 pane 구성)와 지표선 색 토큰 바인딩 |
| `drawingTools.ts` | 그리기 도구 목록과 klinecharts overlay 이름 매핑, 스냅·삭제 정책 |

재사용 인벤토리(신규 컴포넌트 중복 방지).

- `SegmentedTab`(A-9): 타임프레임 탭. 신규로 만들지 않는다.
- `PanelCard`: 차트 패널 셸. 기존 트레이딩 그리드 패널과 동일 셸.
- `Skeleton`(A-15, `variant="chart"`): 로딩.
- 빈 상태: 기존 `.empty-state` 패턴 재사용.
- `format.ts`: 축·툴팁 숫자 포맷은 기존 `formatKRW`·`formatPrice`·`formatDirectional`을 그대로 쓴다.

### 3.2 패널 배치

`web/components/trade/ChartPanel.tsx`가 `CandleChart` 대신 `TradingChart`를 렌더한다. 데스크톱 레이아웃(`docs/reference/contracts/데스크톱_레이아웃설계.md` §2.2, §2.5)의 chart 영역(`minmax(380px, 1fr)`)을 그대로 채운다. 툴바는 카드 상단 1행, 차트 canvas가 잔여 높이를 `height: 100%`로 채운다. 압축 스펙(높이 820px 이하, 차트 min 300)에서도 canvas가 자연 수축한다.

기존 `ChartPanel`의 타임프레임 목록을 TA 세트로 교체한다.

```
1초 → 1s, 1분 → 1m, 3분 → 3m, 5분 → 5m, 15분 → 15m,
30분 → 30m, 1시간 → 60m, 4시간 → 240m, 1일 → 1d, 1주 → 1w
```

v2.5부터 서버 `unit` 집합 10종을 전부 노출한다. 종전 판은 6종만 냈고 `1w`를 옵션으로 두었다.
근거와 실물 거래소 대조는 §5.5에 있다. 초 단위 축 표기는 `1s`에서만 켠다. 판정축을 라벨 패턴으로
두면 라이브러리가 분봉 축에도 같은 패턴(`HH:mm`)을 쓰므로 전 주기에 초가 붙는다.

### 3.3 메인 pane와 보조 pane

- **메인 pane.** OHLC 캔들 + 거래량. 거래량은 캔들 하단 서브 영역(가격 스케일 분리)에 히스토그램으로 겹친다. 크로스헤어 이동 시 OHLCV 툴팁을 표시하고, 봉 등락(종가 대비 시가)을 부호·화살표로 병기한다(§4.4).
- **가격 오버레이 지표.** MA(단기·중기·장기 기간 세트), EMA, 볼린저밴드(상·중·하 밴드 + 밴드 채움). 메인 pane 가격축에 겹친다.
- **보조 pane.** MACD(DIF·DEA 선 + 히스토그램), RSI(기준선 병기), 스토캐스틱(%K·%D). 각 지표는 메인 pane 아래 독립 pane으로 쌓이고 사용자가 토글로 켜고 끈다.

지표 파라미터(MA 기간, RSI 길이 등)는 klinecharts 기본값을 초깃값으로 두고 지표 설정 메뉴에서 조정한다. 계산은 라이브러리 내장 알고리즘을 쓰며 우리가 재구현하지 않는다.

### 3.4 그리기 도구

`ChartToolbar`의 그리기 버튼으로 klinecharts overlay를 생성한다.

| UI 도구 | klinecharts overlay(개념) | 정책 |
|---|---|---|
| 추세선 | 두 점 직선 | 두 점 지정 후 확정, 드래그로 이동 |
| 수평선 | 가격 수평선 | 한 점 지정, 가격축에 값 라벨 |
| 피보나치 되돌림 | 되돌림 레벨 | 두 점(고·저) 지정, 레벨 비율 라벨 |

- 그리기 객체 색·선폭은 토큰에서 가져온다(§4.2). 브랜드 계열 중립색을 쓰고 방향색(Red/Blue)은 쓰지 않는다. 방향색은 캔들·등락 전용이라 그리기 객체에 쓰면 의미가 충돌한다.
- 선택·삭제·전체 지우기를 툴바에서 제공한다. 그리기 객체는 세션 로컬 상태다. 영속화는 본 버전 범위 밖이다.

### 3.5 실시간 배선

원칙. 화면 코드는 SimEngine·`fetch`를 직접 부르지 않는다. `getDataSource()` 한 곳만 쓴다(`web/lib/api/datasource.ts`). `candleStream.ts`가 이 규율의 단일 통로다.

초기 로드.

- `getDataSource().getCandles(market, unit, count)`로 과거 캔들을 받는다. 계약은 시각 내림차순이므로(§4-A-5) 오름차순으로 뒤집어 `applyNewData`에 넣는다.
- **빈 응답과 조회 실패를 가른다(v2.6 개정).** 종전 규약은 둘을 어댑터가 `[]`로 합쳐 흡수했고 차트가 둘을 같은 빈 상태로 그렸다. 그 합침을 걷어낸다. 200 + 0행만 빈 상태이고, 조회 실패는 사유를 상위로 올린다.
- **429는 실패가 아니라 지연이다.** 서버가 `Retry-After`로 회복 시각을 함께 주므로 종결 실패로 적지 않는다(API 설계 §2-3). 마지막 성공값이 있으면 그 값을 유지한 채 지연을 표시하고, 없으면 아래 에러 상태로 간다.
- **마지막 성공값은 `(market, unit)` 키로 든다.** 키를 두지 않으면 15분봉을 성공적으로 받은 뒤 1분봉으로 전환하다 실패했을 때 15분봉 OHLC가 1분봉 라벨 아래 남는다. 지연 표시가 거짓 데이터를 정당화하게 된다.

라이브 갱신(권고 경로: 캔들 채널 구독).

- 선택된 단위의 캔들 채널을 구독한다. `getDataSource().subscribe(dest.candle(unit, market), cb)`. destination은 `/topic/candle.{unit}.{market}`(§5-3, `lib/types.ts` `dest.candle`).
- 서버가 계산한 OHLCV가 오므로 차트가 집계를 직접 하지 않는다. 이것이 경계 롤오버 정확성을 서버로 위임하는 핵심이다.
- **update 대 append 판정은 `candle_time` 경계로 한다.** 마지막으로 받은 `candle_time`과 같으면 형성 중 캔들 갱신(`updateData`), 더 새로우면 이전 봉 확정 + 새 봉 시작(`updateData`가 새 timestamp면 append). 별도 "확정" 이벤트 필드 없이 `candle_time` 단조성만으로 "현재 캔들 갱신"과 "새 캔들 확정" 두 의미를 도출한다. 계약 스키마 변경이 필요 없다.
- 타임프레임 전환 시 이전 캔들 채널을 구독 해제하고 새 단위를 구독한다. 연결당 구독 상한 50(§5-1)에 여유가 크다.

라이브 갱신(폴백 경로: 체결 채널 합성).

- 캔들 채널이 아직 없거나(백엔드 단계적 착수 중) SimEngine이 캔들을 아직 방출하지 않는 구성에서는 체결 채널을 구독해 마지막 캔들을 합성한다. `dest.trade(market)` 구독 → `bucketMs = floor(ts/unitMs)*unitMs` 계산 → 같은 버킷이면 high·low·close·volume 갱신, 새 버킷이면 새 봉 시작. 이는 현 `CandleChart.tsx`가 이미 쓰는 방식이며 미니 차트의 기본 경로다.
- 두 경로는 `candleStream.ts` 내부에서 선택한다. 화면(`TradingChart.tsx`)은 어느 경로인지 몰라도 된다.

경로 판단. 초기 착수에서는 폴백(체결 합성)으로 시작해 메인 차트를 즉시 동작시키고, 백엔드 캔들 채널·Sim 캔들 방출(§8)이 준비되면 캔들 채널 구독으로 승격한다. 승격은 `candleStream.ts` 내부 교체만으로 끝난다.

### 3.6 숫자·정밀도 규율

- 캔들 원본 OHLCV는 문자열이다(계약 `Candle`, `lib/types.ts`). 픽셀 스케일·지표 계산 입력으로 넘길 때만 `toNum`으로 변환한다(`format.ts`). 신뢰값(주문·잔고)에는 이 변환값을 쓰지 않는다.
- `parseFloat` 직접 호출 금지. 변환은 `format.ts`의 `toNum`을 경유한다.
- 축 눈금·크로스헤어 가격 라벨·툴팁 금액은 `Intl.NumberFormat('ko-KR')` 기반 포맷터를 klinecharts 축·툴팁 커스텀 포매터에 연결한다. `formatPrice`(1000원 미만 코인 소수 허용)·`formatKRW`를 재사용한다. 숫자는 `tabular-nums`로 렌더한다.

### 3.7 상태 설계

- **로딩.** `Skeleton variant="chart"`로 canvas 영역을 덮는다. `next/dynamic` 로딩 폴백과 초기 데이터 대기 모두 동일 스켈레톤.
- **빈.** 캔들 0건이면 "차트 데이터 준비 중" 안내. `role="status"`, `--text-tertiary`.
- **에러.** 디자인시스템 A-8이 규정한 `error` 상태를 쓴다. 요약 텍스트를 유지하고 재시도 버튼을 낸다. 종전 규약은 어댑터가 흡수해 빈 상태로 수렴시켰고 차트가 별도 에러 화면을 띄우지 않았는데, 그 규약이 A-8과 정면으로 어긋난 채 둘 다 ACTIVE 였다(11절 충돌). A-8 쪽으로 확정한다.
  - **근거는 §2-3이 상위 계약이라는 것이다.** 429 처리 규약은 화면 표현 규약보다 넓고, "조회 429를 종결 실패로 적지 않는다"를 빈 상태 흡수가 어긴다.
  - **그리고 두 상태가 구분되지 않으면 원인을 못 찾는다.** 실제로 봇이 도는 마켓(체결 12만 건)의 429 빈 차트를 데이터 부재로 오진한 사례가 있다. 화면이 둘을 같게 그리면 개발자도 같은 오진을 한다.
- **지연.** 429로 갱신이 밀린 상태다. 마지막 성공값을 그대로 두고 배지로 지연만 알린다. 자동 재조회를 유계 조건으로 1회 건다. `Retry-After` 존중, 단일 in-flight, 최대 1회, 상한 클램프다(API 설계 §2-3 자동 재요청 유계 조건). 대기 초 해석은 `store.clampRetrySec`과 `httpDatasource.delay`를 재사용한다. 두 곳이 다르면 같은 헤더가 화면마다 다르게 해석된다.
- **연결 끊김.** WS 단절 시 마지막 캔들이 갱신을 멈춘다. 패널 헤더의 연결 표시(기존 `HeaderNav` 연결 점, store `connected`)가 상태를 알린다. 차트 자체는 마지막 값을 유지한다.

배경은 투명(`transparent`)으로 두어 `PanelCard` surface가 비치게 한다.

### 4.2 지표선 색(방향색·green 금지)

지표선은 가격 방향이 아니라 계열 구분이다. 방향색(Red/Blue)은 캔들·등락 전용이라 지표선에 쓰면 의미가 충돌한다. green은 가격 방향 표현에서 전면 금지다. 따라서 지표선은 방향색·green을 피한 팔레트를 쓴다.

권고 매핑(기존 토큰만 소비).

| 지표 | 선 | 토큰 |
|---|---|---|
| MA/EMA(기간 다중) | 단기→중기→장기 | 차트 계열 토큰 `--chart-series-1` → `-2` → `-3` → `-4`. 같은 지표의 기간 차이를 명도 차로 표현. 라이트는 `--brand-400~700`, 다크는 `--brand-200~500` 미러(다크 surface 위 600·700이 그래픽 최소 3:1 미달, 실측 2.76·2.12:1) |
| 볼린저 중앙선 | 중앙 | `--brand-primary` |
| 볼린저 상·하 밴드 | 밴드선 | `--border-strong`, 밴드 채움 `--surface-sunken`(옅은 톤) |
| MACD DIF/DEA | 두 선 | `--brand-primary`, `--text-secondary` |
| MACD 히스토그램 | 양(+)/음(−) 막대 | 양 `--color-up`, 음 `--color-down`. 부호가 막대 위치에 내재해 색 단독이 아님 |
| RSI 선 | 선 | `--brand-primary` |
| RSI 과매수·과매도 기준선 | 수평 기준선 | `--border-strong` 파선 |
| 스토캐스틱 %K/%D | 두 선 | `--brand-primary`, `--text-secondary` |

MA·EMA를 브랜드 명도 램프로 묶으면 방향색·green을 피하면서 계열을 구분한다. 램프는 §7-1이 예고한 `--chart-series-1..4` 토큰(tokens.css §6)으로 소비한다. primitive 직접 소비는 다크에서 그래픽 대비(WCAG 1.4.11, 3:1)를 깨므로 금지. 신규 hex 없이 기존 브랜드 primitive의 테마별 재배치만 허용한다.

### 4.3 라이트·다크·테마 전환

`useChartTheme.ts`가 토큰을 해석해 스타일 객체를 만든다. `[data-theme]` 속성 변경(명시 토글)과 `prefers-color-scheme` 변경(시스템)을 모두 관찰해 klinecharts `setStyles`를 재호출한다. 현 `CandleChart.tsx`의 MutationObserver + matchMedia 패턴을 그대로 옮긴다. 거래량 막대처럼 데이터에 색이 박히는 요소는 전환 시 재세팅한다.

### 4.4 색 단독 금지 준수

캔들 차트는 본질적으로 색으로 방향을 보인다. 규칙("방향은 색 단독 금지, 부호·수치 병기")을 다음으로 충족한다.

- **패널 헤더 등락 판독.** 차트 상단에 현재가 + 등락을 A-6 PriceChange 패턴으로 표시한다. `formatDirectional`로 ▲/▼ + 부호 + 수치 병기(`format.ts`). 색과 무관하게 방향을 읽는다.
- **크로스헤어 툴팁.** 지정 봉의 시가 대비 종가 등락을 부호·화살표로 병기한다.
- **마지막 가격 라벨.** 방향색 배경 + 부호·화살표 텍스트 병기.
- **캔들 형태 보조 단서(옵션).** 상승 봉과 하락 봉의 몸통 채움 방식(솔리드 대 중공)을 달리해 색 외 형태 단서를 더할 수 있다. 채택 여부는 시각 확인 후 정한다.

### 4.5 접근성·모션

- **대비.** 축·툴팁·라벨 텍스트는 4.5:1 이상 토큰(`--text-secondary` 이상, 틴트 위는 `-strong`)을 쓴다. 방향 소형 텍스트는 `-text`(600단계) 규칙을 따른다(디자인시스템 §6).
- **reduced-motion.** `prefers-reduced-motion:reduce`에서 klinecharts 애니메이션(마지막 가격 점멸·전환)을 끈다. 마지막 가격 라벨 플래시는 셀 단위 300ms throttle을 적용하고 reduced-motion에서는 값 갱신만 남기고 플래시 배경을 무력화한다(디자인시스템 §5 킬스위치와 동형).
- **레이아웃 시프트 0.** canvas는 ResizeObserver 기반 고정 크기이고 갱신은 canvas 재그리기라 DOM 리플로우가 없다. 헤더 판독 숫자는 `tabular-nums` 고정폭이라 자리수 변동이 폭을 흔들지 않는다.
- **스크린리더.** canvas는 리더 접근이 안 되므로 컨테이너에 `role="img"` + 요약 aria-label을 준다("{market} {unit} 캔들 차트, 양봉 빨강 상승·음봉 파랑 하락, 하단 거래량"). 현재 봉 OHLC·등락 요약 텍스트를 시각적 비노출(sr-only)로 병기해 값을 읽게 한다.
- **키보드.** 타임프레임·지표·그리기 토글은 `SegmentedTab`·버튼이라 키보드 접근이 된다. 인터랙티브 요소에 접근성 라벨을 단다. 크로스헤어는 포인터 기반이나 같은 데이터를 헤더 판독·요약 텍스트로 제공해 정보 접근을 보장한다. 탭 타깃 44px를 지킨다.

## 5. 백엔드 캔들 파이프라인 계약 (backend 파트)

이 절은 backend-engineer가 구현한다. 프론트는 DataSource(§5.4)를 통해서만 소비한다.

### 5.1 집계 원천과 결정성

- 캔들은 파생 프로젝션이다. 정본은 `trades`(체결)이고 그 원천은 `event_journal`(§6.2, DB 설계). 캔들은 언제든 재계산 가능해야 하며 저장은 선택이다.
- **V1·데모: 별도 테이블 없이 trades 실시간 집계.** `docs/reference/contracts/백엔드_API_설계.md` §4-A-5(v2.8)·부록 X2가 확정한 규약을 따른다. 조회 시 trades를 unit 구간으로 집계해 응답한다. 저장하지 않는다. 재구축 가능하다.
- **구간 경계.** epoch 정렬 `floor(epoch/sec)*sec`. `1d`는 UTC 자정, `1w`는 목요일 기준 주 정렬.
- **OHLCV 산출.** `open`·`close`는 구간 내 `(executed_at, id)` 정렬의 최초·최종 체결가. `high`·`low`는 구간 최대·최소가. `volume`은 수량 합. `trade_count`는 체결 수. `seq`는 구간 내 최대 `event_seq`(구간 간 단조 증가, 채널 seq 도메인 = market × unit).
- **sparse.** 체결이 없는 구간은 응답에 넣지 않는다. 클라이언트가 갭을 처리한다.
- **결정성.** `executed_at`·`id`가 체결의 `engine_ts`·`event_seq` 파생 결정값이라(§4 trades DDL) 같은 trades에서 같은 캔들이 재현된다. DB `now()`를 쓰지 않는다.
- **스캔 경계.** 집계 대상 trades를 `count`·`unit` 창 근방으로 제한한다(X2 후속). 희소 이력에서 반환 캔들 수가 `count`보다 적을 수 있고 이는 sparse 규약과 정합한다.

### 5.2 REST 계약

`GET /api/v1/candles/{unit}` (§4-A-5). 신규 엔드포인트가 아니라 기존 계약의 구현이다. 현재 미구현이라 프론트 어댑터가 실패를 `[]`로 흡수 중이다(§5.4).

- **경로.** `unit ∈ {1s,1m,3m,5m,15m,30m,60m,240m,1d,1w}`. 과제 표기 `interval=&from=&to=`는 계약상 `{unit}` 경로 + `to` + `count`에 대응한다. 별도 `interval` 쿼리·`from`은 계약에 없다.
- **쿼리.** `market`(필수), `count`(≤200), `cursor` 또는 `to`.
- **응답(리스트 엔벌로프 §2-2).**

```json
{ "data":[
  { "market":"KRW-BTC","candle_time":"2026-07-21T09:00:00.000Z",
    "open":"50000000","high":"50020000","low":"49990000","close":"50005000",
    "volume":"12.34","trade_count":345,"seq":8801 } ],
  "pagination":{"next_cursor":"eyJ0cyI6...","has_more":true} }
```

- **정밀도.** `open`·`high`·`low`·`close`·`volume`은 문자열(`NUMERIC(40,18)` 정합). JSON float 금지. quote/base scale은 markets 메타를 따른다.
- **정렬·커서.** `candle_time` DESC. 커서 id 축은 `(candle_time, market)` 자연키(§2-6 U5). 이 미러 타입은 `lib/types.ts`의 `Candle`이 이미 표현한다.

### 5.3 WS 계약

`/topic/candle.{unit}.{market}` (§5-3, §5-4). 공개 채널, 인증 불요.

- **메시지 스키마(§5-4).**

```json
{ "schema_version":"1.0","type":"candle","unit":"1m","market":"KRW-BTC","epoch":42,"seq":8802,
  "candle_time":"2026-07-21T09:00:00.000Z","open":"50000000","high":"50020000",
  "low":"49990000","close":"50005000","volume":"12.34" }
```

- **두 이벤트 의미.** 과제가 요구하는 "현재 캔들 갱신"과 "새 캔들 확정"을 별도 필드 없이 `candle_time`으로 구분한다. 형성 중 구간은 같은 `candle_time`으로 갱신 메시지를 반복 방출한다. 구간이 끝나 다음 버킷이 열리면 `candle_time`이 새 값으로 바뀌며, 이 전이가 직전 봉의 확정 신호다. 클라이언트는 `candle_time` 단조성만으로 update/append를 판정한다(§3.5).
- **seq 도메인.** 채널(market × unit) 독립 단조 증가. epoch는 리더 세대. 변경 시 클라이언트가 강제 재동기화(§5-2)한다. 프론트 어댑터(`httpDatasource.ts`)는 이미 candle 채널의 seq·epoch 검사와 재동기화(`getCandles(market, unit, 1)`)를 구현했다.
- **선택 개선(권고, 필수 아님).** 형성·확정 구분을 명시하려면 candle 메시지에 orderbook의 `stream: snapshot|realtime`과 유사한 판별 필드(예: `state: "forming"|"closed"`)를 추가할 수 있다. 추가 시 계약(§5-4)과 `lib/types.ts` `CandleMessage`를 함께 고쳐야 한다(§7). 미추가여도 `candle_time` 경로로 동작하므로 이는 견고성 향상 항목이다.

### 5.4 구독 모델·DataSource 정합

- 프론트 미러는 `web/lib/api/datasource.ts`의 `DataSource.getCandles`·`subscribe`다. 이미 계약과 정합한다.
- `HttpStompDataSource`는 candle destination 파서·초기 로드·재동기화를 이미 갖췄다. 백엔드가 REST·WS를 구현하면 프론트 수정 없이 켜진다.
- 구독 흐름은 §5-6 규약을 따른다. 부분 실패는 해당 subscription만 거절하고 연결은 유지한다.

### 5.5 interval enum·마이그레이션

- **enum.** 캔들 단위는 API `unit` 집합을 정본으로 한다(`1s,1m,3m,5m,15m,30m,60m,240m,1d,1w`). UI는 v2.5부터 10개 전부를 노출한다(§3.2). 종전에는 6개만 냈다. 나머지 넷(`1s`·`3m`·`30m`·`1w`)은 서버 `UNIT_SECONDS`·DB·프론트 타입에 이미 다 들어 있어 노출만 하면 되는 상태였다. 집합의 근거는 실물 거래소다. 업비트가 초·1·3·5·10·15·30분·1·4시간·일·주·월·년을 내고 그중 초는 1초 하나뿐이다. 빗썸은 초봉이 없고, 국내 증권사 HTS(키움·미래에셋·삼성)는 초 대신 틱(1·3·5·10·30틱)을 쓴다. 이 저장소는 암호화폐 거래소이므로 업비트 관행을 따르되 서버가 받는 것만 낸다. 10분·월·년은 서버 unit 집합에 없어 범위 밖이다.
- **V1·데모 마이그레이션.** 불필요하다. trades 실시간 집계는 새 테이블·마이그레이션을 요구하지 않는다.
- **materialized projection(후속, 선택).** 대량 캔들 조회 성능이 문제가 되면 `candles` 비정규화 프로젝션을 도입한다(DB 설계 §7 로드맵). 이때 신규 Flyway 마이그레이션이 필요하다.
  - **버전 번호.** 착수 시점의 다음 가용 V로 배정한다. 현 순서상 로드맵(V2 partition, V3 partition triggers, V4 audit) 다음에 관리 평면 마이그레이션(scope·operator·audit 확장)이 V5로 내려가므로(관리자 설계 §문서 상태·비고), 캔들 프로젝션은 **V6+**를 예약한다. 정확한 번호는 착수 시점에 고정한다.
  - **enum 정합 필수.** DB 로드맵 `candles.interval` CHECK는 현재 `('1m','5m','15m','1h','1d')`로 API `unit`과 어긋난다(`1h` 대 `60m`, `240m`·`3m`·`30m`·`1w`·`1s` 누락). 프로젝션 도입 마이그레이션은 CHECK 어휘를 API `unit` 토큰에 맞춰 확장해야 한다. 이 불일치는 §7에 개정 요청으로 표기한다.
  - **갱신 방식.** 조회 시 집계 대비 프로젝션 사전 계산의 트레이드오프(신선도 대 조회 비용)를 착수 시 결정한다. trades INSERT 트리거로 증분 갱신하거나 주기 배치로 재계산한다. 어느 쪽이든 trades가 정본이라 프로젝션은 재구축 가능해야 한다.

## 6. 통합·테스트 계획

### 6.1 프론트 테스트

- **렌더·수명주기.** init → 데이터 로드 → dispose가 누수 없이 도는지. 마운트/언마운트 반복에 canvas·구독·옵저버가 정리되는지.
- **테마 전환.** 라이트↔다크 토글, 시스템 스킴 변경에서 캔들·격자·지표선 색이 토큰대로 재주입되는지. 하드코딩 hex가 남지 않았는지 grep 게이트.
- **타임프레임 전환.** 단위 변경 시 이전 캔들 채널 구독 해제 + 새 단위 구독, 데이터 교체가 깜빡임·잔상 없이 되는지.
- **실시간.** 형성 중 캔들 갱신과 경계 롤오버가 `candle_time` 판정으로 정확한지. 폴백(체결 합성) 경로와 캔들 채널 경로가 같은 결과를 내는지 대조.
- **레이아웃 시프트.** 갱신 중 CLS 0. 헤더 판독 숫자 폭 불변.
- **접근성.** aria-label·요약 텍스트 존재, reduced-motion에서 애니메이션·플래시 비활성, 축·툴팁 대비 4.5:1, 탭 타깃 44px.
- **정적 export.** `npm run build` 통과, `out/` 산출물에서 외부 URL·fetch·웹폰트 참조 0, 오프라인 로드 동작.

### 6.2 백엔드 테스트

- **집계 정확성.** 알려진 trades 시퀀스에서 OHLCV·trade_count·seq가 구간 규약대로 산출되는지. `1d` UTC 자정·`1w` 목요일 경계 정렬.
- **sparse.** 체결 없는 구간이 응답에서 빠지는지.
- **재구축 결정성.** 같은 trades에서 같은 캔들이 재현되는지(재생 동일성).
- **seq·epoch.** 채널 seq 단조 증가, epoch 변경 시 프론트 재동기화 유발.
- **정밀도.** 응답 금액·수량 문자열, NUMERIC 정합, 반올림 규약.

### 6.3 시각 확인

시각 결과가 중요한 변경이므로 dev 서버로 직접 확인 후 완료를 선언한다. 라이트·다크, 각 타임프레임, 지표 on/off, 그리기 도구, 실시간 롤오버를 육안 검증한다.

## 7. 정본 개정 요청

본 문서 구현이 요구하는 정본 변경. 이 작업 범위 밖(코드·기존 docs 미편집)이라 별도 워크플로로 처리한다.

## 8. Sim 데이터소스 캔들 생성 (정적 export 데모)

정적 export 데모는 기본 데이터소스가 SimEngine이다(`NEXT_PUBLIC_DATASOURCE` 미설정 시 sim). 메인 차트가 데모에서도 실시간으로 살아 있어야 한다.

현황.

- `SimEngine.getCandles`(engine.ts)는 현재가에서 역방향 GBM 백필로 과거 캔들을 시드 PRNG로 재현성 있게 생성한다. 이미 REST 초기 로드를 만족한다.
- SimEngine은 매 틱 `trade`·`ticker`·`orderbook`·`myOrder`·`myAsset`를 방출하나 **`candle` 채널은 방출하지 않는다.** 그래서 현 차트가 체결 채널로 캔들을 합성한다.

설계.

- **폴백 경로(즉시 동작).** 메인 차트는 체결 합성 경로(§3.5)로 시작한다. Sim 변경 없이 데모가 실시간으로 롤오버한다. 초기 착수 단계의 기본값이다.
- **캔들 채널 방출(승격).** SimEngine에 캔들 방출을 추가한다. 매 틱마다 현재 형성 중 캔들을 `dest.candle(unit, market)`로 publish한다. 값은 `getCandles`와 같은 규약(같은 버킷이면 high·low·close·volume 갱신, 새 버킷이면 새 봉 시작)으로 산출해 REST 백필과 라이브가 이어지게 한다. 구독자가 있는 unit만 방출해 비용을 억제한다.
- 승격 후 `candleStream.ts`가 캔들 채널 경로로 전환하면 데모와 실서버가 동일 경로(`subscribe(dest.candle(...))`)를 탄다. 화면 코드는 그대로다.
- Sim 캔들은 시드 PRNG 결정성을 유지한다. 새로고침해도 같은 시드에서 같은 형태가 재현된다.

## 9. 단계적 착수 순서

1. **C-1 차트 골격.** `web/components/chart/TradingChart.tsx`(klinecharts, `ssr:false` 동적) + `chartTheme.ts` + `useChartTheme.ts`. 캔들 + 거래량 + 크로스헤어 툴팁. `ChartPanel`이 `CandleChart` 대신 렌더. 초기 로드는 `getCandles`, 실시간은 체결 합성 폴백. 타임프레임 10종(§3.2). `npm run build` 통과.
2. **C-2 지표.** `indicators.ts` + `ChartToolbar` 지표 토글. MA·EMA·BOLL 오버레이, MACD·RSI·스토캐스틱 보조 pane. 토큰 색 바인딩(§4.2).
3. **C-3 그리기.** `drawingTools.ts` + 툴바 그리기 버튼. 추세선·수평선·피보나치. 선택·삭제.
4. **C-4 접근성·모션 마감.** reduced-motion, 마지막 가격 플래시 throttle 300ms, aria 요약 텍스트, 대비·탭 타깃 검수. dev 서버 시각 확인.
5. **B-1 백엔드 캔들(별도, backend-engineer).** `GET /api/v1/candles/{unit}` trades 실시간 집계 구현(§5). `/topic/candle` WS 방출.
6. **C-5 캔들 채널 승격.** 백엔드 준비 후 `candleStream.ts`를 캔들 채널 경로로 전환. Sim 캔들 방출 추가(§8). 폴백은 유지.

착수 순서 원칙은 공동 작업 절차의 API 계약 선행 원칙가 아니라, 프론트가 폴백 경로로 먼저 완결(C-1~C-4)하고 백엔드 캔들(B-1)이 준비되면 승격(C-5)하는 병렬 구조다. 프론트가 백엔드 미구현에 막히지 않는다. 각 단계 후 `npm run build`로 정적 export를 확인한다. `generateStaticParams`(exchange·coin·order 라우트)는 삭제하지 않는다.
