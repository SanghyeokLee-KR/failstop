## 5.7.21 7단계 스냅샷 경계 재생 검증

ADR 0022 7단계다. 7단계 이미지(`0a2d8d7`)로 전역 모드와 대역 모드(트래픽 전 래치)에서 E2·E4·E5·E6·E7 과 콜드 재기동 칸을 실험마다 새 스택에서 한 번씩 돌렸다. 판정 규약은 `docs/contracts/하네스_검증설계.md` §2-4 끝의 ADR 0022 7단계 스냅샷 경계 재생 판정 규약이고, 증거는 `harness/evidence/adr0022-stage7-snapshot-20260915/` 다.

**판정은 스냅샷 경계 재생 성립이다.** 두 모드 모두 콜드 재기동 칸이 성립했고 장애 칸 성립은 전역 3칸, 대역 2칸이다. FAIL 과 증거 불완전 칸은 없다.

| 모드 | 성립 | 재생 생략(판정 제외) | RTO(초) |
|---|---|---|---|
| 전역 | E2, E4, E7, COLD | E5, E6 | 4.910~10.506 |
| 대역 | E4, E7, COLD | E2, E5, E6 | 5.503~10.296 |

- 성립 칸은 승격이나 부팅 복구가 활성 마켓마다 스냅샷을 채택하고, 마켓별 적용 건수가 채택 seq 초과 저널 행 수와 같으며, 폴백이 0 이고 C17 이 matched 라는 뜻이다. 7단계 전에는 복구가 항상 seq 0 부터 전량 재생이었다.
- 재생 생략 칸은 새 리더가 승격 때 이미 모든 마켓 head 에 닿아 재생 없이 설치만 한 칸이다. 2026-09-15 규약 보강 전 규칙이었다면 이 5칸 때문에 최종 판정이 NOT RUN 이었다.
- 12칸 모두 실험 판정 PASS, 분리 판정 PASS 다.
- 대역 모드 한계 둘(2026-09-15 reviewer). 판정기의 활성 마켓이 주입 전 채집 기준이라 칸마다 1~2개였고, 세 마켓 채택은 원자료로 확인했다. 스냅샷이 샤드마다 첫 명령 직후 캡처돼(`SnapshotCapture.java`:86-94) 대역 장애 칸의 꼬리는 사실상 전 이력이었고, 이력 중간 경계를 거친 대역 증거는 COLD 칸 한 노드뿐이다. 캡처 기준 수정과 재측정은 후속이다.

**비교하지 않는 것.** RTO 를 5.7.18·5.7.20 과 나란히 놓지 않는다. 실험마다 한 번이다.

**재지 않은 것.** 클라우드 스택, 긴 꼬리 뒤의 복구 시간 이득, 콜드 재기동의 다른 순서다.

## 5.7.22 8단계 commit_delay 격자

ADR 0022 8단계다. 7단계 이미지 위 8단계 도구(주행 커밋 `053e6a8`. 재배치 전 해시라 브랜치에 남지 않고, 서버 코드와 8단계 도구 파일은 `1c60d93` 과 같다)로 commit_delay·commit_siblings 여덟 칸을 칸마다 새 스택, 트래픽 전 래치, 요청 600/s 로 돌렸다. 판정 규약은 `docs/contracts/하네스_검증설계.md` §2-4 끝의 ADR 0022 8단계 commit_delay 격자 판정 규약이고, 증거는 `harness/evidence/adr0022-stage8-commit-delay-20260915/` 다.

**판정은 NOT RUN 이다.** 기준 칸 base-1 의 커밋 동시성이 1.184 로 전제(1.2 초과)를 채우지 못했고, 기준 칸 둘의 접수가 210.47/s 와 150.34/s 로 드리프트 허용 0.05 를 넘었다(차 비 0.333).

| 칸 | 접수/s | 커밋 1회(ms) | 커밋 동시성 | 묶음 비 | WAL fsync/s |
|---|---:|---:|---:|---:|---:|
| base-1 (0, 5) | 210.47 | 5.620 | 1.184 | 2.251 | 290.5 |
| d3000-s1 | 188.63 | 8.295 | 1.566 | 3.972 | 148.6 |
| d1000-s1 | 202.68 | 6.196 | 1.257 | 2.990 | 211.9 |
| d3000-s5 | 195.60 | 7.888 | 1.545 | 3.628 | 168.3 |
| base-2 (0, 5) | 150.34 | 8.360 | 1.257 | 2.218 | 213.5 |

- 나머지 칸과 칸별 범주는 증거 README 에 있다. 최종 판정이 NOT RUN 이라 범주를 결론으로 쓰지 않는다.
- commit_delay 3000µs 칸은 fsync 를 묶었다(묶음 비 1.6~1.8배, WAL fsync/s 42~49% 감소). 그러나 접수는 늘지 않고 커밋 1회가 길어졌다.
- base-2 는 fsync 건당이 base-1 과 비슷한데 커밋 1회와 락 보유 1회가 48~49% 길었다. 원인은 가르지 않았다.

**재지 않은 것.** 클라우드 저장소 격자와 반복 주행이다. 채택 판단은 클라우드 재측정 뒤로 남는다.
