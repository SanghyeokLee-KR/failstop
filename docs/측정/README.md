# 측정 기록

시스템을 어떻게 쟀고 그 값을 믿어도 되는지를 날짜별로 남긴다. 2026-09-14 에 옛
`제출_20260901/테스트_정본.md` 의 실측 절을 이 폴더로 옮겼다. 그 정본은 2026-09-13 제출본
정리(커밋 `af90bca`)로 삭제됐고 원문은 커밋 `d0ac993` 이 갖는다.

## 가르는 규칙

- 파일 하나가 날짜 하나다. 이름은 `YYYYMMDD.md` 다.
- 새 측정은 그 측정을 한 날짜의 파일에 적는다. 파일이 없으면 만든다. 같은 날 회차가 여럿이면
  한 파일에 절을 더한다.
- 옮겨 온 절은 그 절이 옛 정본에 처음 오른 커밋의 날짜로 갈랐다. 본문은 삭제 직전 판이라
  뒤 날짜의 개정이 섞여 있을 수 있다.
- 절 번호는 옛 정본의 번호를 그대로 쓴다. 다른 문서가 인용한 "정본 5.7.9" 는 이 폴더에서
  같은 번호의 절이다. 새 절은 마지막 번호 다음부터 잇는다.
- 본문의 "기획안 한계 N" 은 삭제된 기획안 원본 13절의 번호다. 원문은 `d0ac993` 에서 본다.
- 원자료는 `harness/evidence/` 가 갖는다. 이 폴더는 판정과 표만 적는다.
- 옛 정본 1절(검증의 구조)은 측정 결과가 아니라 옮기지 않았다. 게이트와 불변식 계약은
  `docs/contracts/하네스_검증설계.md` 와 `docs/contracts/하네스_CICD_IaC.md` 가 소유한다.

## 실험 평면

실험은 검증면에서 돈다. 단일 호스트의 도커 컨테이너 16개다. 비용이 0이라 회차를 여러 번
돌 수 있고 커널 계층 주입까지 허용된다. 대가는 둘이다. 컨테이너가 한 대에 있어 진짜 노드
분리가 아니고 자원을 공유한다.

### 부하를 만드는 것과 재는 것을 나눈다

| 도구 | 역할 | 루프 | 위치 |
|---|---|---|---|
| 봇 플릿 | 시장을 만든다. 호가와 체결을 낸다 | 닫힘 | 시스템 안 |
| k6 | 천장을 잰다 | 열림 | 시스템 밖 |

이 구분이 실측으로 증명됐다. 봇은 목표를 초당 400으로 올려도 수용 거절을 한 건도 만들지 못하고 시퀀서 큐도 0이었다. k6는 초당 20에서 게이트를 때린다.

이유는 구조이다. 봇은 애플리케이션 안에서 도는 스레드라 애플리케이션이 느려지면 봇도 같이 느려진다. 자기 자신을 자로 잴 수 없다. k6는 시스템 밖에서 개방 루프로 주입하므로 서버가 밀려도 계획대로 나간다.

## 계측 규약

### 지표가 무엇을 세는지 먼저 확인한다

같은 이름처럼 보이는 지표가 다른 것을 센다.

| 지표 | 세는 것 |
|---|---|
| `http_server_requests_seconds_count{uri="/api/v1/orders",method="POST",status="201"}` | 실제 접수 |
| `exchange_order_latency_seconds_count` | 체결된 주문만. 접수가 아니다 |
| `exchange_journal_append_seconds_count` | 모든 명령. 주문과 취소 전부 |
| `exchange_trades_total` | 체결 |

접수 17.63에 취소 2.35를 더한 19.98이 저널 18.79와 맞다. 명령 하나당 저널 한 번이다.

`http_server_requests` 에는 두 가지가 빠진다. 수용 단계에서 거절된 요청과 인증에 실패한 요청이다. 둘 다 Micrometer 필터보다 앞에서 끊기기 때문이다. 그래서 이 지표만으로는 제공 부하를 알 수 없다. 제공 부하는 접수에 `exchange_admission_rejected_total` 을 더해야 나온다.

봇도 앱 안에서 직접 엔진을 부르지 않고 `BotApiClient` 로 HTTP 를 친다. 그래서 접수에는 봇 몫이 섞여 있다. 부하 발생기가 얼마를 넣었는지 보려면 봇 기저를 빼야 한다.

### 컨테이너 자원 규약

`container_cpu_percent`는 코어 수를 곱한 값이다. 100이 1코어이고 4코어 컨테이너의 상한은 400이다. 비율이 아니라 절대값이므로 코어 수를 모르면 포화 여부를 판정할 수 없다.

메모리는 회수 가능한 캐시를 뺀 값이다. 빼지 않으면 상한 근접 판정이 일찍 울린다.

### 회차마다 기록해야 하는 것

- 데이터 상태. 주문 수와 체결 수와 데이터베이스 크기
- 설정 적용 여부. 기대값과 실제 지표값의 대조
- 부하 발생기가 실제로 낸 양. 요청한 양이 아니다

셋 중 하나라도 빠지면 그 회차는 나중에 재해석할 수 없다.

셋째 항목은 이 문서에 먼저 적혀 있었는데도 2026-09-09 회차에서 지키지 못했다. 규약을 글로만 두고 러너가 강제하지 않았기 때문이다. 러너가 발생기의 종료 코드와 제공 부하를 보고, 요청량의 절반에 못 미치면 그 칸을 무효로 표시하도록 고쳤다. **규약은 검사로 옮기지 않으면 지켜지지 않는다.**
