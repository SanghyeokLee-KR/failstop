# 봇 방향성·거버넌스 설계

상태: 설계 확정(코드 미착수). 코드는 관리자 평면 완료 후 별도 구현.
정본 관계: 본 문서는 `docs/백엔드_API_설계.md`(§6-A 봇 제어), `docs/관리자_설계.md`(§2-1 봇 플릿 제어), `docs/백엔드_DB_설계.md`(system_config)를 소비한다. 본 설계가 정본 표를 확장하는 지점은 §8에 미결로 명시하고, 문서 개정을 코드보다 먼저 한다.

용어: 양전 = 매수 쏠림 = 상승 압력(상승 Red). 음전 = 매도 쏠림 = 하락 압력(하락 Blue). net bias는 -1(완전 음전) ~ +1(완전 양전).

## 1. 목표·범위

### 1-1. 목적
데모 시장의 생동감(가격이 한 방향으로 흐르거나, 매수·매도가 팽팽한 상태)을 운영자가 관리자 콘솔에서 조절한다. 조절 축은 셋이다.

- 방향성: 마켓별 목표 net bias. 양전이면 가격 상승 압력, 음전이면 하락 압력.
- 대수 스케일: 타입별(마켓메이커·테이커·양전·음전 프리셋) 목표 봇 대수.
- 자동 균형: 관측 net bias가 목표에서 벗어나면 느슨하게 되돌리는 제어. on/off + 강도.

부수적으로 체결 시각효과 강도(트레이딩 UI 표현)를 운영자 설정으로 저장한다. 이 값은 봇 파라미터가 아니라 UI 프레젠테이션 설정이며 system_config에 둔다(§5-3).

### 1-2. 범위 밖
- 매칭엔진(engine 모듈) 변경 없음. 봇은 외부 서명 클라이언트로만 시장에 영향을 준다(`server/app/.../sim/BotApiClient.java:44`, `BotSeeder.java:9` 주석: 봇=외부 관점).
- 원장·잔고 직접 DML 없음. 봇 주문은 정상 주문 경로(`OrderGateway`)를 통과하고 정산은 단일 원장 경로만 사용한다.
- 런타임 외부 API 의존 없음. 방향·대수·자동균형 입력은 전부 운영자 콘솔에서 들어온다.

### 1-3. 안전 경계(폭주 방지)
정확성 > 고가용성 > 성능 > 편의성 순서를 지킨다. 생동감은 편의성이므로 안전 경계 아래에 둔다.

- 전역 OPS 상한: 모든 봇 주문·취소는 단일 `OpsGovernor` 토큰버킷을 통과한다(`OpsGovernor.java:9`, `acquire:33`). 방향 바이어스는 매수·매도 비율만 바꾸고 총 OPS를 올리지 않는다. 따라서 방향 쏠림이 처리량 상한을 넘길 수 없다.
- 봇 수 상한: 타입별·마켓별·전역 하드캡. 캡 초과 요청은 클램프 후 감사(§5-1).
- 가격 밴드: 자동 균형은 기준가 대비 최대 이탈(기본 ±40%)을 넘으면 목표와 무관하게 effective bias를 0으로 강제한다(평균 회귀, §4-4).
- bias 하드캡: effective bias는 [-0.7, +0.7]로 클램프해 시장이 완전 일방향이 되지 않게 한다. MM fair value 하한 가드(`MarketMakerBot.java:72`)로 가격이 0 이하로 내려가지 않는다.
- 백프레셔 불변: 유계 시퀀서 큐·rate limit 토큰버킷·503 페일오버 흡수는 그대로다(`OrderGateway.java:117`, 하네스 spike 시나리오 `docs/하네스_검증설계.md:45`, `:105`).

## 2. 방향성 봇 모델

### 2-1. 판정: 기존 봇에 bias 파라미터를 얹는다. DirectionalBot 신설하지 않는다.
근거.

- 주입점이 이미 존재한다. 테이커의 매수·매도 결정은 `TakerBot.java:52`의 `boolean buy = rng.nextBoolean()`(50/50)이고, 마켓메이커의 fair value 랜덤워크는 `MarketMakerBot.java:70`의 대칭 `rng.nextLong(-drift, +drift)`다. bias는 이 두 지점만 편향시키면 된다.
- 코드 표면 최소화. 신규 클래스는 결정론·시드 배선·재기동 수명주기를 중복시킨다. 방향은 파라미터 하나로 두 경로에 매핑하는 것이 격리·검증에 유리하다.
- 정본 봇 유형과 정합. API §6-A "봇 유형"은 `MARKET_MAKER|TAKER|TREND|NOISE`를 열거한다. 코드 경로는 둘이다(MarketMakerBot·TakerBot). TREND·NOISE는 신규 클래스가 아니라 TakerBot의 프리셋으로 실현한다. 광고된 4유형 어휘를 지키면서 코드 경로는 둘로 유지한다.

### 2-1-a. TREND 페르소나: momentum·mean-revert 이원(r7)
초기 실현은 TREND를 "강한 정적 bias 프리셋"으로 뒀으나, §6-A "TREND(모멘텀)" 의도에 미달한다. TakerBot에 `DirectionSource` 차원을 주입해 방향 스칼라 d의 산출원만 바꾼다(`DirectionSource.java`, `TakerBot.directionScalar`). 신규 BotType·캡·scale 키 확장 없음.

- STATIC: `d = fleet.effectiveBias(market)`. TAKER·NOISE 기존 프리셋 그대로.
- MOMENTUM: 공개 `GET /api/v1/ticker`의 `change`(부호 권위) * `change_rate`(절대 크기)로 추세 스칼라. 상승 -> 매수(추세추종).
- MEAN_REVERT: 공개 `GET /api/v1/trades` 최근 N건 SMA 대비 편차의 반대 부호. 고평가 -> 매도(역추세).

TREND 코호트는 index 결정론으로 이분한다(`DirectionSource.of`: 짝수 MOMENTUM, 홀수 MEAN_REVERT). 신호는 `SIGNAL_READ_EVERY` 주기마다 캐시해 읽기 부하를 억제하고, 전부 공개 GET이라 서명·자금 경로에 닿지 않는다. 매핑 `signal->d->p_buy`는 순수 함수이고 rng 소비 순서(방향 draw·sizeSteps·burstCount)는 STATIC과 동일해 페르소나 무관하게 rng 스트림이 동일하다. 신호는 external market state이므로 도메인 B 재현성은 auto-balance measured 피드백과 동일 프레이밍으로 relax된다(§2-4). 도메인 A(엔진 재생)는 무영향.

### 2-2. bias 정의역·표기
- 정의역: bias ∈ [-1, +1]. 문자열로 전송·저장한다(봇 파라미터 문자열 규약, `docs/관리자_설계.md:228`. 정수·불리언만 예외이고 bias는 분수이므로 문자열).
- 내부 처리: 확률·드리프트 오프셋 계산에만 쓰는 스칼라로 파싱한다. bias는 가격·수량 산술에 절대 들어가지 않는다. 가격·수량은 틱·로트 정수 배수 + BigDecimal을 유지한다(`MarketMakerBot.java:79` 참조). 확률 계산은 자금 경로가 아니므로 float 금지 규약의 대상이 아니다. 다만 bias가 어떤 경로로도 NUMERIC 값에 곱해지지 않음을 코드 리뷰 체크 항목으로 둔다.

### 2-3. bias -> 주문 방향·크기·빈도 매핑
테이커(결정 1건마다).

- 매수 확률 `p_buy = 0.5 + 0.5 * clamp(bias,-1,1) * k_dir`. `k_dir`은 확신 게인(기본 0.8). bias=+1에서도 양면성을 약간 남겨(p_buy 0.9) 한쪽 호가만 소진하며 가격을 가드까지 밀어붙이는 극단을 피한다.
- `buy = rng.nextDouble() < p_buy`로 `TakerBot.java:52`를 대체한다.
- 크기·빈도 realism은 Wave B에서 기본 on이다. 크기 분포(r6 반정규+고래 꼬리)·버스트(r13)가 상시 적용된다. 방향은 여전히 확률로만 편향하고, 크기·버스트는 방향과 독립이라 원장·정밀도 표면을 넓히지 않는다(정수 스텝·BigDecimal 유지).

마켓메이커.

- fair value 드리프트를 비대칭화한다. 대칭 랜덤워크에 `b = round(bias * driftTicks * k_mm)`(기본 `k_mm` 0.5)를 더한다(`MarketMakerBot.driftOffset`). 미드가 bias 방향으로 서서히 이동하므로 양측 호가가 함께 밀리고 지속 압력이 생긴다.
- 하한 가드는 유지·강화한다. bias 음전·앵커 하강에서도 fair value가 최저 사다리 레벨(halfTicks + 다단 오프셋)+1 아래로 내려가지 않는다(r12 스프레드 배수·다단 사다리 인지형 하한, `MarketMakerBot.run`). 사다리 빌더도 비양수 bid 틱을 제외한다(`buildLadder`).
- 재고 스큐(r11 호가 중심 비대칭)는 Wave B 기본 on이다. 초과 재고를 음의 스큐로 소진한다(`inventorySkewTicks`).

순효과. 양전 -> 매수 테이커 증가 + MM 상방 드리프트 -> 가격 상승(Red). 음전 -> 반대(Blue). 한국 관례와 일치한다.

### 2-4. 시드 결정성 보존
결정성 도메인을 둘로 분리한다.

- 도메인 A(엔진 재생 결정론, 불변식 ⑥ `docs/백엔드_API_설계.md:849`): 엔진은 command_journal의 박제된 시각·id를 재생한다. 봇 결정이 아니라 저널된 커맨드를 재생하므로, 봇에 bias를 얹어도 엔진 재생 결정론은 무관하다. 봇 프로세스는 external이며 엔진 결정론 규약(`§7-2 :880`)의 대상이 아니다.
- 도메인 B(플릿 재현성, 하네스 부하 재현): 같은 시드 = 같은 결정 열. bias가 고정이면 `p_buy`·`b`는 (bias, rng 추출)의 순수 함수이므로 `(seed, bias)`가 같으면 결정 열이 동일하다. 추가 난수원·벽시계를 쓰지 않는다.
- 런타임 bias 변경은 운영자 입력이며 외부 시장 조건 변화와 같다. 감사 로그에만 남고 도메인 B 재현성은 그 시점부터 relax된다(예상된 개입). 도메인 A는 영향 없다. 자동 균형 on 시 도메인 B 재현성은 relax되고, off + bias 고정 시 엄격 재현성이 성립한다(§4-5).

### 2-5. 플릿 초기 대수·반응 지터
- 초기 대수(r4): TREND·NOISE 초기 목표를 0에서 양수로 상향해 페르소나가 상시 구동한다. 소스는 `MarketSpec.trendCount`·`noiseCount`, 미지정 시 taker 수에서 파생한다(`BotFleet.start`). poolPerType·캡은 불변이고 initialTargets만 상향한다(active = min(target, pool)). 등록 경로(`BotFleetGovernor.registerMarket`)는 타입별 캡(typeCap)만 클램프한다. marketCap·globalCap은 런타임 스케일 경로(`BotFleetGovernor.scale`, §5-1)에서만 클램프하므로, 초기 목표는 마켓별 4유형 합 <= marketCap·전 마켓 합 <= globalCap을 구성 단계에서 충족해야 한다(등록이 되돌리지 않는다).
- 반응 지터(r17): 봇마다 생성 시드에서 순수 해시로 팩터 [0.6, 1.6]을 산출해 재호가·도착 주기를 상이하게 만든다(`BotReaction.reactionJitter`). rng 스트림·벽시계 미소비라 방향·크기 결정 열은 불변이고, 팩터는 sleep 상수 배율로만 쓰여 OPS 상한·정밀도에 닿지 않는다.

### 2-6. realism 카탈로그(코드 상수 1:1 매핑)
Wave B realism 파라미터의 의도·경계·기본값을 코드 상수와 대응시킨다. 전부 스칼라 의사결정 전용이라 NUMERIC 산술에 유입되지 않고, 순수 함수는 단위 테스트로 결정성·경계를 고정한다. r 인덱스는 코드 주석의 사실상 정본이다(백로그 카탈로그 부재).

| r | 의도 | 코드 앵커 | 기본값·경계 |
|---|---|---|---|
| r1 | 앵커 회귀(fair -> 시장 last) | `MarketMakerBot.anchorPull`·`K_ANCHOR` | 게인 0.2(<1, 오버슈트 없음) |
| r2 | 증분 재호가 diff | `MarketMakerBot.ladderDiff` | 이탈·누락 레벨만 교체 |
| r3 | 다단 사다리 | `MarketMakerBot.buildLadder`·`LEVEL_COUNT` | 3레벨, 간격 1틱, 비양수 bid 제외 |
| r5 | 변동성 레짐 전이 | `BotFleetGovernor.Regime`·`nextRegime` | CALM/TREND/SHOCK, 시드 전이 |
| r6 | 크기 분포 꼬리 | `TakerBot.sizeSteps` | sigma 1.2, pWhale 0.03, whale 6x, cap 8x |
| r7 | 방향 페르소나 | `DirectionSource`·`TakerBot.momentumScalar`/`meanRevertScalar` | momentum gain 8, mean-revert gain 20, SMA 20, 조회 4주기 |
| r11 | 재고 스큐 | `MarketMakerBot.inventorySkewTicks`·`K_INV` | 게인 0.5, scaleTicks 경계 |
| r12 | 레짐 스프레드 반폭 | `MarketMakerBot.spreadHalfTicks` | 최소 1틱 |
| r13 | 버스트 스윕 | `TakerBot.burstCount` | pBurst 0.05, maxBurst 3 |
| r14 | 마켓별 레짐 프로파일 | `BotFleetGovernor.RegimeProfile`·`nextRegimeMeme` | STANDARD 폴백, MEME 편향·증폭 |
| r17 | 반응 지터 | `BotReaction.reactionJitter` | [0.6, 1.6] |

r14는 마켓마다 변동성 개성을 준다. `MarketSpec.regimeProfile`(설정, 미지정 STANDARD 폴백)로 지정하고 `BotFleetGovernor.registerMarket`가 마켓 상태에 고정한다. STANDARD는 기존 전이 행렬·배수를 그대로 쓴다. MEME는 고변동 밈 자산용으로 TREND/SHOCK 진입·잔류 확률을 올린 전이 행렬(`nextRegimeMeme`)과 증폭 배수(drift 1.6·spread 1.4·lambda 1.3·pWhale 1.8)를 쓴다. 프로파일은 전이 임계값 해석과 배수 증폭만 바꾼다. 마켓별 PRNG 시드(`regimeSeed ^ stableSalt(market)`)와 controlStep당 소비량(`nextDouble` 1회)은 불변이라 rng 순서·레짐 시퀀스 재현이 보존되고, 배수는 봇 의사결정 스칼라 전용이라 NUMERIC 산술·엔진 재생에 유입되지 않는다. 데모 로스터는 KRW-DOGE만 MEME로 지정한다(`application.yml`).

## 3. 대수 스케일

### 3-1. 현재 상태
`BotFleet.start()`가 부팅 시 `SimProperties`의 고정 대수로 가상 스레드를 기동한다(`BotFleet.java:54` MM 루프, `:64` TAKER 루프, `:61`·`:71` 가상 스레드). 런타임 증감 경로는 없다.

### 3-2. 판정: 파킹 게이트 방식(주 경로), 스레드 재조정은 대안
타입별·마켓별 목표 대수를 `BotFleetGovernor`(신설, `OpsGovernor` 옆)의 volatile 필드로 둔다.

- 주 경로(파킹 게이트): 부팅 시 타입별 최대 풀을 기동하되, 각 봇 루프 선두에서 "내 인덱스 <= 현재 목표 대수"인지 확인한다. 목표를 초과하는 봇은 파킹(주문·취소·OPS 토큰 미소비)한다. 목표를 올리면 파킹 봇이 즉시 활동을 재개한다.
  - 이유. 봇 정체성·시드가 스케일에 따라 안 바뀌므로 재현성이 유지된다(봇 i는 결정론적으로 `i<=target`일 때만 활성). 스레드 수명 churn이 없어 카오스·페일오버 하에서 안정적이다. 파킹 봇은 자원을 안 먹으므로 백프레셔 친화적이다.
- 대안(스레드 재조정): `FleetSupervisor`가 주기적으로 실제 대수 대 목표를 비교해 신규 봇 스폰·초과 봇 종료를 조정한다. 더 "제대로"지만 스레드 churn·시드 재배치를 유발한다. 최대 풀이 과도하게 커질 때만 채택한다.

### 3-3. 증감 방식·안전
- 증감은 `PUT /admin/v1/sim/scale`(§5-1)로 `BotFleetGovernor` 목표를 갱신한다. OpsGovernor 런타임 훅(`OpsGovernor.setTargetOps:22`)과 같은 패턴이다.
- 핵심 안전 논증: 전역 OPS 버킷은 봇 수와 무관하게 고정이다. 봇을 늘려도 총 처리량은 안 오르고 동시성·다양성만 는다. 즉 대수 스케일은 구조적으로 백프레셔에 무해하다.
- 상한(폭주 방지 밴드): 타입별 캡·마켓별 캡·전역 캡을 둔다. 기본 전역 캡은 하네스 normal 구성(140봇, `docs/하네스_검증설계.md:44`)을 기준으로 여유를 둔 하드캡(예 500)으로 잡는다. 캡 초과 요청은 캡으로 클램프하고 `applied` 값과 함께 감사에 남긴다(거부가 아니라 클램프. 데모 운영 편의).
- 최대 풀(파킹 방식)은 캡과 같게 잡아 캡 상향이 재기동을 요구하지 않게 한다. 캡 자체 상향은 `SimProperties` 변경 + 재기동으로만 가능(운영 안전 상한).

## 4. 자동 균형 거버넌스("대충")

목표 net bias를 느슨하게 유지하는 외부 제어 루프. 비례 제어 + 밴드 + 히스테리시스. 봇 프로세스(bots 프로파일) 안에서 단일 스레드로 돈다.

### 4-1. 측정
관측 net bias는 데모 생동감 프록시다. 정산 수치가 아니다.

- 소스: 플릿 자신의 롤링 어그레서 집계(최근 창의 매수개시 대 매도개시 테이커 건수·수량). in-process라 외부 폴링·관측 지표 소비가 없다.
- `measured_net_bias = (buy_agg - sell_agg) / max(buy_agg + sell_agg, 1)`, 값 [-1, +1].
- 안전 규약 준수: 균형기는 불변식·원장·헬스 지표를 입력으로 읽지 않는다(`docs/관리자_설계.md:235` 관측 데이터 지시 자동 실행 금지). 오직 자체 주문 흐름만 읽고 bias만 미세 조정한다. 주문·카오스를 직접 주입하지 않는다.

### 4-2. 제어(비례 + 밴드)
- 오차 `error = target_net_bias - measured_net_bias`.
- 데드밴드: `|error| < band`(기본 0.1)면 조정 안 함. 지터·자기순환 억제.
- 그 외: `effective_bias += Kp * error`, `Kp` 작게(기본 0.2, 느슨). `effective_bias`를 [-0.7, +0.7]로 클램프.
- 제어 주기: 고정 간격(기본 3s)의 느린 외부 루프. 봇은 매 결정마다 최신 `effective_bias`를 읽는다(최종 일관성. 느슨 제어라 허용).

### 4-3. 히스테리시스
- 최소 조정 간격 이후에만 재조정하고, 방향 반전은 오차가 밴드를 일정 마진 넘길 때만 허용한다. 목표 부근에서의 플래핑을 막는다.

### 4-4. 폭주·자기순환 방지
- bias 하드캡(§1-3): effective_bias 절대 [-0.7, +0.7].
- 가격 밴드: 기준가 대비 이탈이 최대치(기본 ±40%)를 넘으면 목표·오차와 무관하게 effective_bias를 0으로 강제(평균 회귀). 상승 폭주·하락 붕괴를 차단한다.
- OPS 불변: 균형기는 OPS 버킷을 못 만진다. 방향 조정은 비율만 바꾸므로 처리량이 안 는다.
- 단일 루프: 균형기는 단일 스레드·단일 마켓 상태만 갱신해 자기 피드백 발산을 막는다.

### 4-5. 자동 off 시 동작
- 자동 균형 off면 운영자 수동 bias를 그대로 반영한다. `effective_bias = manual_target_bias`(클램프만, 제어 루프 없음).
- off + bias 고정이면 §2-4 도메인 B 엄격 재현성이 성립한다.

### 4-6. 원장·불변식 무해 논증
- 균형기는 주문을 직접 내지 않는다. 시장 영향은 전부 정상 서명 주문 경로(`BotApiClient -> OrderGateway -> 엔진 -> 정산`)로 흐른다. 원장 게시는 단일 경로만 쓴다. 원장·잔고 직접 DML 없음.
- 불변식 무영향(`docs/백엔드_API_설계.md:849`): ④ 자산 보존·⑤ 체결 정합은 정산 경로의 성질이며 주문 방향 분포와 독립이다. ⑥ 재생 결정론은 엔진이 저널 커맨드를 재생하므로 무관(§2-4 도메인 A). ⑦ fencing은 페일오버 시 봇이 503을 흡수(`OrderGateway.java:117`, `MarketMakerBot.java:63`·`TakerBot.java:74` catch)하므로 리스 우회 없음.
- 백프레셔: 유계 큐·429·503이 그대로 상한을 건다. 방향 쏠림은 비율만 바꾸고 rate를 못 올린다.

## 5. 관리 API 계약

`/admin/v1/sim/*`(정본 경로, `SimAdminController`) 확장. 방향·대수·자동균형 변경은 파괴 액션이 아니므로 approval_token 불요, 감사만 적재한다(`docs/관리자_설계.md:190` 완결 열거 + `:1040` R3 근거: sim 제어·rate는 approval 제외 확정). §3-6 approval 필수 완결 열거를 넘지 않으므로 열거 개정은 불필요하다(신규 필수 액션 추가 없음). 단 §6-A 표에 행 추가는 필요(§8).

### 5-1. 대수 스케일: `PUT /admin/v1/sim/scale`
```json
// 요청. 역할 BOT_OPS. approval 불요.
{ "market":"KRW-BTC",
  "targets": { "MARKET_MAKER":40, "TAKER":30, "TREND":20, "NOISE":50 } }
// 200
{ "schema_version":"1.1", "market":"KRW-BTC",
  "applied": { "MARKET_MAKER":40, "TAKER":30, "TREND":20, "NOISE":50 },
  "clamped": false, "fleet_present": true }
```
- 검증: 각 target 정수 ≥ 0(대수는 정수 예외). 마켓별 합 ≤ 마켓 캡, 전역 합 ≤ 전역 캡. 초과는 캡으로 클램프하고 `clamped:true` + 감사.
- 반영: `BotFleetGovernor` 타입별 목표 갱신. 봇 미기동 배포(bots 프로파일 off)는 `fleet_present:false`로 의도만 감사(SimAdminController가 OpsGovernor에 쓰는 방식과 동일, `SimAdminController.java:60` ObjectProvider 부재 허용).

### 5-2. 방향·자동균형: `PUT /admin/v1/sim/bias`
```json
// 요청. 역할 BOT_OPS. approval 불요.
{ "market":"KRW-BTC", "target_net_bias":"0.30",
  "auto_balance": true, "strength":"0.5" }
// 200
{ "schema_version":"1.1", "market":"KRW-BTC",
  "target_net_bias":"0.30", "auto_balance": true, "strength":"0.5",
  "effective_bias":"0.24", "fleet_present": true }
```
- 검증: `target_net_bias` 문자열, 파싱 후 [-1, +1]. `strength` 문자열 [0, 1](또는 off/subtle/normal/strong 별칭 -> Kp 게인 매핑). `auto_balance` 불리언(예외 필드).
- `auto_balance:false`면 `strength` 무시, `effective_bias = target_net_bias` 클램프값 직접 반영(§4-5).
- 반영: `BotFleetGovernor`의 마켓별 bias·자동균형 상태 갱신. 균형기 루프가 다음 주기부터 소비.

### 5-3. 체결 시각효과 강도: system_config 저장(운영자 설정)
효과 강도는 봇 파라미터가 아니라 UI 프레젠테이션 설정이다. 봇 결정에 영향을 주지 않고 트레이딩 UI 표현만 바꾼다. 저장소는 system_config(V5, `V5__admin.sql:115`), 제어 표면은 sim 평면에 둔다(운영자 관점 일관).

```json
// PUT /admin/v1/sim/effects  역할 BOT_OPS. approval 불요.
{ "trade_flash":"normal" }   // off | subtle | normal | strong | auto
// 200
{ "schema_version":"1.1", "trade_flash":"normal" }
```
- 저장: `system_config` 행 `config_key='ui.trade_flash_intensity'`, `value` = JSONB 문자열. `updated_by` = operator_id. 스키마 변경 불필요(generic key/value, app_role에 SELECT/INSERT/UPDATE 이미 부여 `V5__admin.sql:143`).
- `auto`: UI가 자체 관측 체결률로 강도를 파생하라는 지시값. 백엔드는 열거값만 저장한다("저장만" 요구 충족).
- 대안: `/admin/v1/config/effects`(config 평면, 역할 SUPER). ConfigAdminController의 halt/notice가 SUPER인 것과 정합하나 효과 강도는 비파괴 cosmetic이라 과중하다. 본 설계는 sim 평면 + BOT_OPS를 채택하고 최종 역할은 reviewer 판정에 위임한다.

### 5-4. 트레이딩 UI 읽기 경로(공개): `GET /api/v1/exchange-config`
효과 강도는 트레이딩 UI(공개 오리진, admin 오리진 아님)가 읽어야 한다. UI 안전 키 화이트리스트만 노출하는 공개 조회를 신설한다.
```json
// GET /api/v1/exchange-config  무인증(공개, /markets와 동급)
{ "schema_version":"1.0", "trade_flash":"normal" }
```
- 화이트리스트 전용. 운영·보안 config 키는 절대 노출 안 함(system_config를 통째로 열지 않는다).
- 이 엔드포인트는 거래 평면 신규 공개 API라 API 정본 §4/§5 추가가 선행이다(§8).

### 5-5. 상태 조회 확장: `GET /admin/v1/sim/status`
기존 응답(`SimAdminController.java:45`, schema 1.0: fleet_present·target_ops)에 마켓별 방향·대수·측정치를 additive로 더하고 schema를 1.1로 올린다. 기존 소비자 무영향.
```json
{ "schema_version":"1.1", "fleet_present": true, "target_ops":"20",
  "markets": [
    { "market":"KRW-BTC",
      "target_net_bias":"0.30", "measured_net_bias":"0.22", "effective_bias":"0.24",
      "auto_balance": { "enabled": true, "strength":"0.5" },
      "scale": { "MARKET_MAKER": {"target":40,"active":40}, "TAKER": {"target":30,"active":28} },
      "fill_ratio":"0.61", "trade_flash":"normal" } ] }
```

## 6. 관측성

### 6-1. 관리자 모니터링 노출
- `GET /admin/v1/sim/status`(§5-5)와 `WS /admin/v1/ws/sim/telemetry`(정본 §6-A `docs/백엔드_API_설계.md:785`)로 마켓별 target·measured·effective bias, 자동균형 상태, 타입별 활성 대수, 체결률을 실시간 노출한다.

### 6-2. Prometheus 지표(§6-C·하네스 정합)
sim/데모 지표는 무결성 불변식과 이름 도메인을 분리한다. 균형기가 이 지표를 입력으로 되먹이지 않게 하고(§4-1 안전), 모니터링 대시보드가 생동감과 정합성을 혼동하지 않게 한다.

- `exchange_sim_net_bias{market}` gauge(-1..1, 측정)
- `exchange_sim_target_bias{market}`, `exchange_sim_effective_bias{market}`
- `exchange_sim_active_bots{market,type}`
- `exchange_sim_fill_ratio{market}`

`exchange_invariant_*`·`exchange_ledger_imbalance`(`docs/관리자_설계.md:150`)와 접두어를 구분해 상관 분석에서만 겹치고 의미는 안 섞이게 한다.

### 6-3. 색·표기 규약
net bias 표시는 시세색을 쓴다(양전 상승 Red `--color-up`, 음전 하락 Blue `--color-down`). net bias는 가격 방향 개념이므로 시세색이 정당하다. 시스템 헬스 green을 차용하지 않는다(`docs/관리자_설계.md:218`). 색 단독 금지, 부호·화살표 병기(상승 ▲ 하락 ▼).

## 7. 마이그레이션

### 7-1. 주 설계는 마이그레이션 불필요
- 효과 강도: system_config generic 행(§5-3). V5 테이블 재사용, DDL 변경 없음.
- 봇 방향·대수·자동균형 상태: `BotFleetGovernor` 인메모리 volatile(OpsGovernor와 동일 규율, `OpsGovernor.java:11`). 봇은 재기동 시 `SimProperties`·시드로 복원되므로 durable 저장이 필수는 아니다.
- 결론: 신규 코어 마이그레이션 없이 관리자 평면·sim 확장만으로 구현 가능. 기존 마이그레이션(V0~V11) 미수정.

### 7-2. 마이그레이션 예약(선택, reviewer 판정 시)
아래를 원하면 다음 가용 버전으로 배정한다(현재 최신 V11__sim_run_ordinal.sql, 다음 가용 V12).

- (a) system_config 키 어휘 CHECK: `config_key IN (...)` 화이트리스트로 오타·비인가 키 차단.
- (b) durable 플릿 설정 테이블 `sim_fleet_config(market, type, target_count, target_bias, auto_balance, strength, updated_by, updated_at)`: 재기동 후 운영자 의도 복원.
- (c) sim 텔레메트리 이력 테이블: net bias·체결률 시계열 보존(대시보드 장기 조회).

전부 append 또는 신규 테이블이라 기존 마이그레이션(V0~V10) 미수정으로 성립한다.

## 8. 정본 정합·미결(문서 개정 선행)

코드보다 문서를 먼저 고친다. 아래는 본 설계가 정본 표를 넘어서는 지점이다.

1. API §6-A(`docs/백엔드_API_설계.md:774`) 행 추가: `PUT /admin/v1/sim/scale`, `PUT /admin/v1/sim/bias`, `PUT /admin/v1/sim/effects`, `GET /admin/v1/sim/status` schema 1.1. 전부 approval 불요라 §3-6 approval 필수 완결 열거는 불변(신규 필수 액션 없음). 표 개정만 필요.
2. 거래 평면 공개 조회 신설: `GET /api/v1/exchange-config`(§5-4). API 정본 §4/§5(공개 조회 절)에 화이트리스트 config 노출 행을 추가한다.
3. 관리자 설계 §2-1(`docs/관리자_설계.md:108`)·§4-2(`:207`) UI 행 추가: 방향(net bias 슬라이더)·대수(타입별 목표)·자동균형(on/off + 강도)·효과 강도 컨트롤. 프론트 설계와 컨트롤 표면·스키마를 1:1 정합시킨다.
4. TREND·NOISE 실현 방식 확정: API §6-A `:799`가 4유형을 열거하나 코드는 MM·TAKER만 있다(`BotFleet.java:54`,`:64`). 본 설계는 TREND=강한 정적 bias 프리셋, NOISE=bias 0 고분산 프리셋으로 실현(§2-1). 유형 어휘는 유지하되 구현 경로가 둘임을 문서에 명시한다.
5. DB 설계 §3 V 로드맵 표(`docs/백엔드_DB_설계.md:334`) 낙후: 표는 V2=partition_automation·V3=ledger_triggers·V4=audit_triggers로 적었으나 실제 파일은 V2__gateway_counters·V3__observability_tables·V4__harness_schema·V5__admin이다. 본 설계 범위 밖이나(문서 편집 금지 제약), V6 배정 전 DB 정본 표를 실제 파일과 맞추는 별도 개정이 필요하다. 감사 리포트 항목으로 남긴다.
6. 효과 강도 write 역할: sim 평면 BOT_OPS 채택(§5-3). config 평면 SUPER 대안 대비 비파괴·데모 도메인 근거. reviewer가 SUPER로 상향할 수 있음.

## 9. 리스크·테스트 계획

방향 편향이 불변식·백프레셔·RTO에 무해함을 하네스 V3 통합테스트로 증명한다.

| 항목 | 시나리오 | 수용 기준 |
|---|---|---|
| 불변식 무해 | bias +1·-1 극단 + 자동균형 on 하 V3 무작위 회귀 | 불변식 ④⑤⑥⑦ 전부 PASS. 자산합 0, 체결 정합, 재생 해시 일치, fencing 위반 0(`docs/백엔드_API_설계.md:849`) |
| 백프레셔 무해 | bias +1 + spike 시나리오 동시 | 총 OPS ≤ target_ops(방향 쏠림이 rate 미증가). 429 `Retry-After` 100%, 유계 큐 상한 도달 시 거부·OOM 0(`docs/하네스_검증설계.md:105`). 수용 요청 p99 방어 |
| RTO 무해 | 편향 흐름 중 kill-node -> 페일오버 | 봇 503 흡수, 새 리더에서 편향 흐름 재개. RTO는 bias와 직교(변화 없음) |
| 폭주 방지 | 자동균형 target +1(적대적) | 가격 밴드 클램프 발동 -> effective_bias 0 강제. 무한 상승·음수가 없음(MM 하한 가드). OPS 폭주 없음 |
| 결정성 | 고정 (seed, bias, 자동균형 off) 2회 실행 | 테이커·MM 결정 열 동일(도메인 B). 단위 테스트로 `p_buy`·드리프트 오프셋 순수성 검증 |
| 멱등 | 편향 흐름 중 봇 재시도 | client_order_id는 botId-seq 단조 유지(`TakerBot.java:106`,`MarketMakerBot.java:82`). 재시도 동일 키 재사용. bias가 키 스킴 불변 |
| 정밀도 | bias 경로 정적 검사 | bias가 price·qty 산술에 미유입. 자금 경로 float 0. 가격·수량 틱·로트 정수 배수 유지 |
| 대수 스케일 | 런타임 목표 증감 + 캡 초과 | 활성 대수 = min(목표, 캡). 총 OPS 불변. 파킹 봇 자원 미소비 |
| 자동균형 수렴 | target 0.3, 초기 measured 0 | measured가 밴드 내로 수렴, 플래핑 없음(히스테리시스). off 전환 시 수동 bias 즉시 반영 |
