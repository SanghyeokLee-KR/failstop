1. 개요

1.1 문서 목적

본 문서는 프론트엔드 구현 계약을 고정한다. 데스크톱 레이아웃 설계 v1.1이 "어떻게 보이는가"(그리드·패널·색 규약)를 정의했다면, 본 문서는 "어떻게 동작하고 무엇과 연결되는가"(라우트·컴포넌트 트리·상태·데이터 바인딩·이벤트·백엔드 전환 지점)를 정의한다.

1.2 화면 정책 (고정형 데스크톱 전용)

항목규칙
기준 화면업비트 동형의 고정형 데스크톱 웹. 거래 화면 /exchange/[market]가 메인. 차트·호가·체결·주문·마켓 목록을 한 화면에 동시 노출

1.4 핵심 설계 결정

DataSource 추상화. 모든 화면은 DataSource 인터페이스만 소비한다. 현재 구현 SimDataSource(클라이언트 GBM 시뮬레이터, 런타임 외부 의존 0)를 HttpStompDataSource(Spring REST + STOMP)로 화면 코드 수정 없이 교체한다(§6). getDataSource() 팩토리가 NEXT_PUBLIC_DATASOURCE=sim|http로 구현체를 선택하며 기본은 sim이다.
정적 export. next.config.ts가 output:"export". 산출물 out/을 Nginx, Spring 정적 리소스로 서빙한다. 서버 redirects()·서버 리다이렉트가 동작하지 않으므로 모든 경로 이관은 클라이언트 router.replace로 처리하고, 동적 라우트는 generateStaticParams로 전 마켓 경로를 사전 생성한다.

2.2 정적 export 리다이렉트 전략

output:"export"는 서버 리다이렉트를 지원하지 않는다. 구 라우트는 페이지 파일과 generateStaticParams를 유지한 채 본문을 클라이언트 리다이렉트 컴포넌트로 교체해 딥링크를 보존한다. /order는 서버 redirect로 쿼리 승계가 불가하므로 반드시 useSearchParams 클라이언트 처리로 side·price를 넘긴다. useSearchParams를 쓰는 컴포넌트는 정적 프리렌더에서 Suspense 경계로 감싼다.

2.3 통합 배경

구 /market(목록)·/coin/[market](상세)·/order/[market](주문)을 거래 화면 하나로 통합했다. 마켓 목록·주문 폼이 거래 화면의 상주 패널이 되어 독립 페이지의 존재 이유가 사라졌다. 업비트 /exchange 단일 화면 모델과 동형이다.

SimEngine (GBM 틱, 시드 PRNG)                 ← 현재: 클라이언트 시뮬레이터
   │ WsMessage {type, market, seq, epoch, stream:"snapshot"|"realtime", …}
   ▼
DataSource.subscribe(dest, cb) ──→ store.apply(msg) ──→ 화면 selector 구독
                                                        │ (셀 단위 리렌더 최소화)
                                                        ▼

규약구현
채널별 seq단조 증가 검사. gap 감지 시 REST 스냅샷 재호출로 재동기화. HttpStompDataSource가 담당(§6)

레이아웃 시프트실시간 갱신은 시프트 0. 호가는 10+10 슬롯 고정(빈 슬롯은 자리행). 틱 플래시는 셀별 throttle 300ms

6. Spring 백엔드 연동 전환 계획

전환 원칙: 화면 코드 무수정. HttpStompDataSource(lib/api/httpDatasource.ts)가 DataSource 인터페이스를 구현하고 getDataSource() 팩토리가 NEXT_PUBLIC_DATASOURCE로 선택한다. 어댑터는 이미 구현돼 있고 시뮬레이터와 동일 계약을 미러한다.

6.1 전환 체크리스트

#항목내용
1환경 변수NEXT_PUBLIC_DATASOURCE=sim|http(기본 sim), NEXT_PUBLIC_API_BASE, NEXT_PUBLIC_WS_BASE
2REST 어댑터§3.3 매핑대로 fetch. 리스트 엔벌로프({data})·표준 에러({error:{name,message,retry_after}} → ApiError) 파싱. 금액은 문자열 유지(NUMERIC(40,18)). 캔들 조회 실패는 빈 배열로 흡수(표시 전용 피드)
3STOMP 어댑터@stomp/stompjs로 /ws/v1 연결. subscribe(dest, cb) → SUBSCRIBE. 재연결 시 전 채널 재구독 + REST 재동기화. 신규 구독자에 초기 스냅샷 1건 합성 전달(deliverInitialSnapshot)
4인증데모 세션(POST /api/v1/demo/session) 단기 JWT를 메모리에만 보관. 401 시 재발급 후 1회 재시도. 비공개 채널 구독 시 Bearer CONNECT로 승격. 브라우저에 secret 저장 금지
5seq/epoch채널별 seq 단조 검사·gap REST 재동기화·epoch 변경 강제 재동기화를 어댑터가 담당. 재동기화 중 도착분은 버퍼링 후 seq 오름차순 flush. store에는 연속화된 도메인 이벤트만 전달(raw seq/epoch/stream 미노출)
6주문 멱등client_order_id 생성·재시도 재사용은 OrderPanel에 구현 완료. 어댑터 무관. 취소는 order.id(UUID) 정규 라우트
7시스템 화면/system 데이터 소스를 내부 시뮬레이션 → 헬스/메트릭 API 폴링(5s)으로 교체
8검증전환 후 하네스 봇 플릿·k6 시나리오가 동일 API 사용. E2E 스모크: 마켓 조회 → 주문 → 체결 Toast → 거래내역 반영

6.2 백엔드에 요구되는 계약 (수용 기준 4가지)

Spring 구현이 지켜야 프론트가 무수정으로 붙는 것: ① API v2.5의 REST 경로·엔벌로프·에러코드 ② WS 채널 경로(§5-3)·seq/epoch/stream 필드·구독 즉시 스냅샷 1건(§5-2) ③ client_order_id 멱등(§2-4) ④ 금액 문자열 표기(NUMERIC(40,18)). 이 4가지는 SimDataSource가 이미 미러하고 HttpStompDataSource가 검증하므로, 백엔드 구현의 수용 테스트 기준으로 그대로 사용한다.

본 문서는 프로젝트/web 구현(데스크톱 그리드 + 서브 3화면 + 온보딩)과 1:1 정합하며, 이후 코드 변경 시 함께 갱신한다. 웹 화면 명세서 v2.0 끝.
