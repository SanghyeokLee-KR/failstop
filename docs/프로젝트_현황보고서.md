# 프로젝트 현황·성과 보고서

작성일 2026-07-22. 대상 고가용성 가상 암호화폐 거래소. 발표·평가 제출용.
근거는 README, ROADMAP, 아키텍처_개관, 문서감사_리포트, server/README, M4_하드닝설계, harness/README, 실제 코드 계측.

## 1. 요약

- 정의: 봇 플릿이 실시간 매매하는 완전 시뮬레이션 거래소. 실거래·실자산 없음. 1년 주기, 웹(정적 export 데스크톱 트레이딩 화면)이 메인 산출물, 앱은 후순위. 백엔드 Spring Boot.
- 최상위 목표(반증 가능한 두 명제):
  - 증명 ① 체결 무결: 트래픽 폭주·장애에도 자산별 원장 합 0, 주문 중복·유실 0.
  - 증명 ② 자동 복구: 서버를 죽여도 사람 개입 없이 복구, 체결 재개. RTO 30초 이내.
- 판정은 사람 눈이 아니라 SQL 위반 행 0, 메트릭 임계, exit code로만 한다.
- 현재 도달점: 로드맵 M1(코어 거래 + 고가용성 증명 1차) 구현 도달. 리더 kill 후 자동 복구를 격리 카오스 스택에서 실측으로 증명. M2·M3·M4는 계약 문서 설계 완료, 구현 대기.

## 2. 마일스톤 진행

로드맵은 4개 분기 마일스톤. 상시 게이트(봇 부하에서 불변식 전 항목 통과, 리더 kill RTO 30초 이내, CI green)를 모든 마일스톤 종료 조건에 포함한다.

## 3. 핵심 증명 성과

### 자동 복구 실측 (M1-6 E1 리더 kill 실험)

격리 카오스 스택(chaos-api-1 리더 / chaos-api-2 스탠바이)에서 `docker kill` 주입 후 무개입 관찰. 판정 프로토콜은 사전 권위 run(C01~C19 green) → 주입 → 무개입 관찰 → 사후 권위 run.

| 지표 | 실측 | 목표 |
|---|---|---|
| RTO(체결 재개, T5-T0) | 약 11.4초 | 30초 이내 |
| epoch | 정확히 +1 | +1 |
| 자산합 위반(C01) | 0 | 0 |
| 중복 접수(C07·C07') | 0 | 0 |
| 중복 체결(C08) | 0 | 0 |
| 저널 gap(C05·C06) | 0 | 0 |
| 주문 유실(C13a 물질화) | 0 | 0 |

- RTO는 페일오버 후 최초 신규 TRADE의 engine_ts(T5)에서 kill 시각(T0)을 뺀 값. 게이지 다운타임(감지·승격 구간)보다 넓은 권위 창.
- verdict PASS 조건: 사후 권위 run CRITICAL 0행 ∧ epoch +1 ∧ RTO < 목표. failover_runs에 적재.

### 그 밖의 증명 축

- 복식부기 총자산 보존: 정산이 SettlementService 단일 트랜잭션(event append + 정산 + trades + orders + outbox 원자 커밋). C01 자산별 원장 합 0을 기동 직후부터 유지(GENESIS 입금도 회계 경로 경유).
- 재생 결정론: 매칭 코어가 벽시계·난수·I/O·락을 쓰지 않고 비결정 입력을 명령 payload에 박제. 저널 재생 결과가 원본과 비트 동일. recovery_runs.matched로 판정(스냅샷 지문 배선은 M4).
- 멱등: 주문 생성 client_order_id 필수(미제공 400, 서버 생성 fallback 없음). 재시도는 동일 키 재사용, 멱등 replay로 수렴.
- 검증기 반증: verifierCatchesInjectedViolations가 위반을 고의 주입해 검증기가 잡아내는지 확인. "항상 통과하는 검증기" 가능성 배제.
- 라이브 봇 거래·웹 연동: 봇 플릿이 외부 클라이언트 규약(서명·자체 HTTP)만으로 접속, 내부 직호출 없음. 웹이 REST·WS로 실제 백엔드에 바인딩.

## 6. 기술 스택·아키텍처 요약

- 스택: Spring Boot 3.5.16 + Java 21, 매칭 코어 순수 Java, REST(MVC+Virtual Threads), 실시간 WebSocket+STOMP, JPA·jOOQ, PostgreSQL 17, Flyway, Resilience4j, Kafka(KRaft), 웹 Next.js 정적 export(고정형 데스크톱 1280px), 부하·카오스 k6·Toxiproxy·Chaos Monkey·Pumba, 관측 Prometheus·Grafana.
- 3계층 SoT: ① 복구 원천(command_journal·event_journal·snapshots, append-only 재생 가능), ② 회계 원천(ledger_entries, 복식부기 자산별 합 0), ③ 파생 프로젝션(balances·orders·trades, 언제든 재계산). 증명 ②는 ①의 명령 재생, 증명 ①은 ②의 자산 보존 불변식.
- 고가용성: 단일 라이터를 DB leader_lease 행으로 보장(resource=matching-engine 단일). 승격마다 epoch +1. 자산 변경 트랜잭션은 커밋 전 assert_current_leader(holder·epoch·리스 만료)로 stale 쓰기를 롤백. command_journal은 fencing_token, event_journal·trades·snapshots는 fencing_epoch에 승격 epoch 저장으로 split-brain을 데이터로 감사.
- 배포 단위 분리: A 거래 평면(다중 인스턴스), B 봇 플릿(외부 클라이언트 규약만), C 관리 평면(분리 포트·네트워크·mTLS), 코어 exchange-core(Spring·락·I/O·벽시계·난수 금지). 분리는 카오스 실험(거래소만 죽이고 봇은 살림)의 전제.

## 7. 리스크·남은 일

### 문서 감사 미해결 계약 공백 (2026-07-22, high 13건)

- scope enum 불일치: DB CHECK(READ/TRADE/WITHDRAW, ADMIN 없음) vs API(read_only/trade/admin/withdraw). admin 키 INSERT 불가로 관리 평면 인증이 저장 계층에서 성립 불가.
- api_keys.operator_id 컬럼이 DB DDL에 부재. 2인 승인의 권위 소스 저장 근거 없음.
- taker 수수료 기본값 드리프트: DB DEFAULT 0.0010 vs API 권위 값 0.0005. 시드 정본 미확정(어느 문서에도 시드 DDL 부재).
- 프론트 데스크톱 전환 잔재: 디자인시스템·레이아웃 문서에 모바일 IA(TabBar·BottomSheet·767px·safe-area)와 반응형 분기가 부분 편집 누락으로 잔존.
- 버전 핀 드리프트: 하네스 2문서와 CLAUDE.md 계약 인덱스가 DB v2.10 / API v2.8 정본을 따라오지 못해 이미 해소된 충돌(NUMERIC·secret_hash·fee 모델)을 미해결로 인용.
- 판정: DB 설계만 조건부 통과, 나머지 5문서 수정 후 재검토. 근본 원인은 버전 핀 드리프트와 데스크톱 전환 잔재 두 축.

### 환경·운영 리스크

- 한글 경로 테스트 이슈: 프로젝트가 한글 경로에 있으면 gradlew test가 ClassNotFoundException으로 실패(Windows 매니페스트 jar 클래스패스 손상). ASCII 정션(C:\dev\exchange) + PowerShell에서 실행해야 통과. Git Bash에서는 재현 실패 사례 있음. CI 러너는 ASCII 경로라 무관.
- RPO=0은 단일 PostgreSQL 인스턴스 범위에서만 성립. failover 포함 무손실은 동기 standby·synchronous_commit·클러스터 STONITH 운영 요건 전제.
