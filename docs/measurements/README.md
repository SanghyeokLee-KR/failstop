## 먼저 확인할 조건

현재 기록된 실험은 로컬 Docker 환경에서 수행했다. 컨테이너가 같은 호스트 자원을 공유하므로 AWS의 호스트·가용영역 장애나 처리량을 그대로 설명하지 못한다.

각 회차에서 다음을 확인한다.

- 실행한 코드와 설정, 실제 적용된 값.
- 주문·체결 수와 DB 크기 등 시작 데이터 상태.
- 계획한 부하와 발생기가 실제로 보낸 요청량.
- 장애가 실제 대상에 도달했는지와 판정에 사용한 표본.

실행하지 않은 실험은 `NOT RUN`, 조건을 만족하지 못한 회차는 유효한 통과 결과에서 제외한다. 예를 들어 09-15의 `commit_delay` 실험은 사전 조건이 충족되지 않아 `NOT RUN`이다.

## 봇과 k6의 역할

봇은 실제 API를 호출해 호가와 체결을 만든다. 응답이 느려지면 봇이 보내는 속도도 영향을 받는다. k6는 정해진 도착률로 요청을 넣어 서버가 처리하지 못한 부하까지 관찰한다. 둘은 역할이 다르며, 봇만으로 처리량 상한을 측정했다고 단정하지 않는다.

봇은 거래 서버와 별도 프로세스로 실행한다. 봇이 엔진을 직접 호출하거나 거래 서버와 같은 JVM에서만 동작한다는 과거 설명은 현재 구성과 맞지 않는다. 구현은 [BotApiClient](../../server/app/src/main/java/kr/exchange/sim/BotApiClient.java), 부하는 [k6 안내](../../harness/load/README.md)를 본다.

## 지표의 범위

| 지표 | 의미 |
|---|---|
| `http_server_requests_seconds_count`의 주문 POST·201 | 신규 주문 접수 응답. 봇의 주문도 포함한다. |
| `exchange_order_latency_seconds_count` | 체결된 주문의 지연 표본. 접수 건수와 다르다. |
| `exchange_journal_append_seconds_count` | 주문·취소 등을 포함한 명령 기록. |
| `exchange_trades_total` | 체결 수. |

인증이나 수용 단계에서 거절된 요청이 HTTP 지표의 집계 범위에 포함되는지 확인한다. 제공 부하는 발생기의 기록과 거절 지표도 함께 봐야 한다. 이름이 비슷하다는 이유로 다른 지표를 더하거나 같은 수로 비교하지 않는다.

컨테이너 CPU 100%는 한 코어 사용량이다. 여러 코어를 할당한 컨테이너의 포화 여부는 할당량과 함께 판단한다. 메모리도 캐시 포함 여부가 같은 지표인지 확인한다.

## 재현

러너와 판정기는 [harness/scale/](../../harness/scale/)에 있다. 각 실험의 시작 조건과 출력 파일을 확인한 뒤 실행한다. `clean_suite.py`는 회차 사이 볼륨을 초기화하므로 보존할 데이터가 있는 환경에 그대로 실행하지 않는다. 2026-09-24부터 이 초기화와 그것을 쓰는 `roundtrip_probe.py`, `harness/scripts/adr0022-stage5-chaos.ps1`은 compose 프로젝트가 보존 스택 `exchange-chaos`(`CHAOS_PROJECT` 미설정 포함)이면 시작하지 않는다. 모드 전환 경로(`protocol_latch.py`, `-Protocol 2`, `--protocol-before-traffic 2`)는 폐기용 스택(`CHAOS_PROJECT=exchange-pml`, `CHAOS_APP_IMAGE=exchange-chaos-app:pml`)에서만 돈다([하네스 검증설계](../reference/contracts/하네스_검증설계.md) §2-4, [S3 설계](../reference/architecture/마켓분할_리더_S3_설계.md) 7-0).

새 결과는 실행한 날짜의 파일에 덧붙인다. 결과를 요약할 때도 코드 버전, 조건, 판정과 원자료 위치를 함께 남긴다. 검사 기준 자체는 [하네스 검증 설계](../reference/contracts/하네스_검증설계.md)와 [CI·CD·인프라 설계](../reference/contracts/하네스_CICD_IaC.md)를 따른다.
