원자료는 [pml-S4-20260925-0012](../../harness/evidence/pml-S4-20260925-0012/README.md)다. [S4 설계](../reference/architecture/마켓분할_리더_S4_설계.md) 13절(구현 검토 라운드 1)의 수정 뒤 작업 트리(HEAD `91813dd5` 위의 커밋하지 않은 S4 변경)로 `exchange-chaos-app:pml`을 다시 구워(`sha256:5b8c279f…`, 참조 태그 `s4r1ref`, V0~V53) 7절의 X1~X8을 다시 돌렸다. jar는 13-1의 전체 빌드(시험 834개 통과)가 만든 것과 같은 파일이다. **관문은 통과하지 못했다. E2(리더 DB 절단)가 두 번 모두 공통 판정에서 FAIL이고, E1(PG 지연)이 세 번 가운데 첫 번째에서 FAIL이다. 나머지는 PASS다. 자산·원장 불변식 위반과 구 epoch 쓰기는 어느 실험에서도 없었다.**

- X2 E4는 RTO 6.958초로 PASS이고, 되살린 옛 리더는 부팅 획득 없이 13.2초 만에 `FOLLOWER`로 합류했다. X3 E7은 RTO 11.860초로 PASS이고, 새 리더의 획득이 `lock_timeout`(1초)으로 두 번 끊긴 뒤 얻었다. 획득 상한이 스택에서 발동한 첫 기록이다. X4 E5(5.587초), E6(5.106초), X5 콜드 재기동(재개 15.279초, `-S4Boot` 참)도 PASS다.
- X4 E2(RTO 12.148초)는 스크립트 판정이 PASS였지만 드레인 뒤 `summary.sql`의 C17 `REPLAY_DETERMINISM`이 1행이라 FAIL이다. 절단 중 라이터 치명으로 파티션 강등한 옛 리더의 fresh 재구성이 DB 복귀 순간 `CannotGetJdbcConnectionException`으로 끝났고, `EngineRecovery.replayRecorded`가 이 연결 실패를 재생 불일치(`matched=false`)로 적은 것으로 본다(로그 대조의 추론, DB가 지워져 행은 보지 못했다).

- X8 E1은 첫 번째에서 리더가 `WRITER_FATAL: UncategorizedSQLException`로 파티션 강등해 epoch가 5에서 6이 됐다(FAIL). 그 실행기는 컨테이너 로그를 남기지 않아 SQLSTATE를 보지 못했다. 로그 저장을 더한 재주행 두 번은 PASS다. E3은 Redis 토폴로지가 없어 SKIP이고 그것이 유효 판정이다.

## S4b 관문 주행 (05:14~08:34 KST)

원자료는 [pml-S4b-20260925-0456](../../harness/evidence/pml-S4b-20260925-0456/README.md)이고 판정 해석은 [S4b 설계](../reference/architecture/마켓분할_리더_S4b_설계.md) 13절이다. **첫 이미지에서 E2 다섯 번과 X1·X6은 PASS였고, E1 다섯째가 S4의 E1 FAIL을 재현했다. 원인을 고친 둘째 이미지에서는 E1 세 번과 X1, E2, E4~E7, 콜드 재기동이 PASS였다(E6은 하네스 판정을 고친 재실행).**

E1은 1~4회 PASS(정산 재시도 5·5·4·1회, 소진 0), 5회 FAIL이다. 리더 정산이 잠금 대기 초과(55P03)를 두 번 만나 첫 시도부터 7,323ms에 재시도 한도(4회·5초)를 넘겼고 `WRITER_FATAL: UncategorizedSQLException sqlstate=55P03`로 강등해 epoch가 5에서 6이 됐다. 무결성 위반, 구 epoch 쓰기, 주문 `500`은 없었다.

- X7(선택, 기록). 칸 값 '접수/s(k6 저널 행)'은 S3 칸 171.1·103.3, S4 칸 148.5·142.8이다. S3 두 칸의 잡음 0.49가 커서 손실은 판단하지 않았다.

## Patroni DB 자동 전환 E-P 실험 (16:32~23:30 KST)

작업 브랜치 `claude/patroni`(기준 `9a6d2474`에 커밋하지 않은 변경)의 [ADR 0036](../reference/adr/0036-patroni-strict-sync-db-failover.md) 실험이다. 판정 해석은 [Patroni 설계](../reference/architecture/DB_자동전환_Patroni_설계.md) 15절이다. 스택은 compose 프로젝트 `exchange-patroni`(PostgreSQL 17.11, Patroni 4.1.5, etcd v3.5.34 세 멤버, HAProxy 3.0.27, 앱 두 노드, 봇, DB 수준 ACK 기록기)이고, 엄격 동기(`synchronous_mode`·`synchronous_mode_strict`, `synchronous_node_count 1`), `failsafe_mode` 켬, Patroni 시간 값 20·5·5, 앱 리더 모드 P2(파티션 `matching-engine` 하나)다. 회차마다 스택을 새로 세워 끝에 볼륨과 함께 지웠고, 보존 볼륨 두 개는 시작과 끝의 생성 시각이 같았다. 호스트는 Windows 11, Docker Desktop(16 CPU, 16GB)이고 같은 PC에서 마켓별 리더 S5·S6 작업이 번갈아 돌았다.
