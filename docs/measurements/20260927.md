# 측정 20260927

## 정산 전 예약 감시 질의의 계획과 전후 시간 (21:31~21:59 KST)

원자료는 [reservation-backlog-plan-20260927](../../harness/evidence/reservation-backlog-plan-20260927/README.md)이고 설계 해석은 [S3 설계](../reference/architecture/마켓분할_리더_S3_설계.md) 3절 P8의 2026-09-27 문단이다. 로컬 시연 스택(compose 프로젝트 `exchange-chaos`, Patroni 엄격 동기 두 노드, DB 컨테이너 2코어·2GiB, PostgreSQL 17.11)에서 부하가 없는 구간에도 주 DB CPU가 주기적으로 2코어를 가득 썼다. 사용자 관찰로는 약 10초 간격이었고, 12:58~12:59 UTC 표본에서는 약 20초 간격으로 3~6초씩 채웠다. 원인은 조회 역할이 아닌 모든 앱 노드가 15초마다 도는 정산 전 예약 게이지 질의(`ReservationBacklogMonitor.QUERY`)였다. 주 DB `chaos-db-1`에서 통계 초기화 뒤 45분 동안 396회, 평균 4,910ms, 실행 시간 합 1,944초였고, 이 질의 하나가 평균 약 0.72코어를 썼다.

데이터는 명령 약 60만~62만 행이 모두 옛 전역 seq 잎(`command_journal_p0`)에 있고, 이벤트는 옛 잎(p0)에 세 마켓이 섞인 행과 마켓 대역 잎(b1·b2·b4)에 한 마켓씩 담긴 행으로 나뉘어 있었다. 12개 마켓 가운데 명령과 이벤트가 있는 마켓은 셋이고 셋 다 커서 위 NEW가 0건이었다. P1이라 예약 행은 0이다. 계획기는 명령 조회에 명령 PK를, 커서 조회에 대역 잎 b1·b4의 `idx_evt_src`를 골라 `market_id`를 필터로 걸렀고, 그래서 명령이 없는 마켓마다 명령 옛 잎 전체를, 그 잎의 마켓이 아닌 마켓마다 b1·b4 전체를 훑었다. 마켓 조건을 `BETWEEN m.id AND m.id`로 쓰고 `(market_id, …)` 순서로 정렬해 `idx_cmd_market`·`idx_evt_market_cmd`만 순서를 주게 했다. 값은 같고 새 색인이나 마이그레이션은 없다. 같은 모양인 C14' 정산 전 예약 항도 같이 고쳤다.

같은 주 DB에서 읽기 전용 트랜잭션으로 `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)`를 문장마다 다섯 번 돌린 실행 시간이다(12:43:12~12:44:03 UTC).

| 문장 | 고치기 전 | 고친 뒤 | 공유 버퍼(첫 회) |
|---|---|---|---|
| 게이지, JIT 끔(감시 빈 조건) | 2,311~5,620ms | 0.32~0.87ms | 2,677,880 → 452 |
| C14' 전체, JIT 켬(상시 run 조건) | 2,668~5,141ms | 39~59ms | 2,679,064 → 598 |
| C14' 전체, JIT 끔(권위 run 조건) | 2,246~5,728ms | 0.78~2.16ms | 2,679,405 → 662 |

**재지 않은 것과 한계.** 고친 코드를 시연 스택에 올리지 않았으므로 배포 뒤 DB CPU는 NOT RUN이다. 배포 전 표본(30회)은 `chaos-db-1` 평균 62.9%, 150% 초과 7회였다. 새 모양의 계획이 비용 설정에 흔들리는지는 `random_page_cost` 1.1·4·20과 비트맵·증분 정렬 끔에서 계획만 봤고, 100에서만 p0 순차 스캔으로 바뀌었다. 운영 프로필의 문장 상한 3초에 고치기 전 문장이 걸렸을지는 설정과 위 시간에서 낸 추론이며 prod 프로필에서 재지 않았다. 느린 모양을 합성한 Testcontainers 시험(`ReservationBacklogMonitorTest`)은 고치기 전 코드에서 먼저 검사한 게이지 문장이 공유 버퍼 71,013으로 실패했고(기준 1,449 미만) 고친 뒤 통과한다. 같은 합성 데이터에서 옛·새 문장 넷을 한 번에 잰 값은 게이지 71,013에서 446, C14' 71,015에서 448이고 값은 같았다. 같은 등호 모양인 C31 앱 판(권위 run 전용)은 고치지 않았고, 같은 스택에서 JIT 끔 4.3초로 운영 풀의 문장 상한 3초를 넘는다.
