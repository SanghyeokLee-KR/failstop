# 운영 검증 20260918

정본 `codex/docs-linux-operations`에서 Linux 운영·역할별 배포·DB 복구·관제·Teams 보고를 구현하고 로컬 실행을 검증했다. 기준은 `3362117` 이후 이 기록과 함께 커밋하는 변경이다. Windows 11, Ubuntu 26.04 WSL·x86_64, Docker Desktop의 단일 호스트 환경이며 AWS 계정에는 접속하지 않았다. 서비스와 역할·실험별 원본은 아래 링크에서 확인한다. 현재 진행 상태와 다음 작업은 [로드맵](../ROADMAP.md)에만 둔다.

## 실행 환경과 배포

Docker Linux 실행 환경을 복구하고 서버 빌드·테스트, 웹 의존성 설치·440개 테스트·빌드와 기본 페이지 응답을 확인했다. Linux 실습에서는 운영 계정, 별도 SSH, 제한된 sudo, systemd, 로그, 호스트 점검과 방화벽을 설치했다. root·비밀번호·잘못된 키 접속, 비밀 파일 읽기와 임의 sudo 거절을 검사했다. 재설치와 WSL 재시작 뒤의 계정 접근·수집 파일 권한·보고 서비스·예약은 [재설치 검사](../../artifacts/operations-20260918/reporting-install-check.json)에 남겼다. 실제 EC2 재부팅이나 Windows 종료 후 상시 운용 검증은 아니다.

[역할별 배포 smoke](../../artifacts/operations-20260918/deploy-smoke/checks.json)는 47개 마이그레이션, 초기 카탈로그와 잔고 0의 시스템 계정, 로그인 역할 분리, DB 연결 상한, 인용 문자를 포함한 복제 비밀번호를 확인했다. 조회 노드는 엔진 리더가 되지 않고 허용한 조회만 제공했다. DB 중단 시 조회 준비 상태 503과 생존 상태 200을 구분했고 복구 후 조회가 회복됐다. 이미 적용한 Flyway 파일을 수정하거나 repair하지 않았다.

## DB 수동 복구와 백업

거래를 만든 뒤 쓰기를 멈추고 standby가 따라잡은 상태에서 primary 격리, 수동 승격, 앱 연결 전환, 새 볼륨의 standby 재편입과 백업 복원을 수행했다. [첫 DB 실습](../../artifacts/operations-20260918/db-recovery-drill.json)의 앱 준비까지 11.688초, [별도 프로젝트 재실험](../../artifacts/operations-20260918/failstop-ops-repeat-5f5d0d824ec0.json)의 9.688초는 사람의 판단 시간을 포함하지 않는다.

재실험에서는 주문 ACK 2건과 체결 1건을 보존했다. 전환·복원 전후 명령 2건, 이벤트 3건, 원장 항목 22건, 주문 2건을 대조했으며 세 시점의 불변식 각 30개에서 CRITICAL/HIGH 실패가 없었다. 이 조건의 통과를 급작스러운 다중 호스트 장애에서의 무손실 보장으로 해석하지 않는다. 임시 프로젝트의 컨테이너·볼륨은 정리하고 백업과 판정 자료를 보존했다.

[별도 백업 복원](../../artifacts/operations-20260918/backup-restore-check.json)은 DB 내용과 불변식을 검사했으며 그 회차의 앱 기동 검사는 수행하지 않았다. Linux 백업 도구의 실행·복원은 확인했지만 WSL에서 Windows DB로 가는 직접 연결 문제로 정기 백업 timer는 설치하지 않았다. 백업 성공 시각과 실제 복원 확인은 별도 근거다.

## 보고서와 파일 제공

Teams 카드는 역할별 대상, KST 시각, 영향, 담당자 조치를 먼저 표시한다. PDF는 2쪽 고정 양식으로 사건·개입 여부·조치·종결 조건과 실측 그래프 4개를 바인딩한다. [실제 장애 보고 원자료](../../artifacts/operations-20260918/report-template/standby-v2-report.json), [카드](../../artifacts/operations-20260918/report-template/standby-v2-card.json), [PDF 표본](../../output/pdf/failstop-standby-incident.pdf), [HTML 표본](../../output/pdf/failstop-standby-incident.html)을 함께 보존한다. 저장된 장애 당시 자료를 나중의 정상 지표로 바꾸지 않았다.

파일은 별도 서명 키로 기본 7일 동안 제공하며 변조한 링크의 403 응답을 확인했다. 현재 링크는 이 PC에서만 열리는 루프백 주소다. Teams 파일 탭 등록이나 외부 관계자용 HTTPS 제공을 검증한 것은 아니다. PDF 글꼴 오류가 발생해도 카드와 다음 보고가 전송되는 회귀 시험을 추가했다. PDF 생성 시각의 UTC 메타데이터 오류도 수정했다.

실제 보고에서 확인한 P95 수집 실패는 무요청 histogram의 정의되지 않은 값이 섞인 경우였다. 쿼리에서 해당 구간을 제외하고 실제 업무 요청 표본이 있는 구간만 남겼다. 5xx는 업무 요청 카운터가 존재할 때만 0을 보완하며, 카운터 자체가 없으면 미수집으로 유지한다. 실제 전송 표본의 과거 수집 결과는 그대로 보존하고 이후 보고에 수정한 조회를 적용했다.

현재 상시 분석은 `facts-only`다. 앞서 Gemini 인증과 생성 1회를 확인했지만 보강한 지시의 실측 재검증과 상시 활성화는 완료하지 않았다. 일일 timer는 09:00 Asia/Seoul이며 Windows·WSL이 실행 중이어야 한다.

## 별도 운영자 콘솔

`d2d0b2b` 이후 작업에서 사용자 예시의 정보 밀도와 전체 사이드바를 별도 관제 웹으로 구현했다. 거래소 웹이나 Grafana 제품 소스 대신 `deploy/console/`을 추가하고 기존 Prometheus·Grafana 인증·보고 서비스를 연결했다. 보고 목록은 저장된 고객과 환경의 근거가 일치하는 항목만 반환하며, PDF·HTML 조회에 AI 호출이나 Teams 전송을 수행하지 않는다.

[실제 연결 검사](../../artifacts/operations-20260918/console/runtime-check.json)에서 고정 Prometheus 지표 조회 40개에 수집 오류가 없었고 고객 대상 4개 모두 응답했다. Grafana 사용자 1명·대시보드 4개·데이터 소스 1개와 저장 보고·이벤트 각 6건을 조회했다. 보고 PDF 115,667바이트와 HTML 15,816바이트는 인증된 경로에서 HTTP 200으로 내려받고 파일 형식을 확인했다. AWS용 8개 지표는 미등록 상태였으며 로컬 값으로 대신하지 않았다.

## Grafana 기본 관제 적용

사용자의 후속 확정 요청에 따라 기존 Grafana 53001의 네 대시보드를 기본 관제로 구성했다. Canvas 서비스 경로·DB 복제, 시계열·상태 이력·표 패널을 사용하고 한국어·서울 시간대·기본 홈과 네 즐겨찾기를 적용했다. 기존 Prometheus와 Alertmanager를 기본 경고 메뉴에 연결했으며 별도 콘솔 53002는 비교·확장용으로 보존했다. 제품 소스나 전역 CSS를 변경하지 않았다.

[기능 검사](../../artifacts/operations-20260918/grafana/interactions-check.json)는 홈·사이드바·조회 기간·화면 이동·기본 경보 연결·테마와 Canvas 상태를 포함한 8개 검사를 통과했다. Prometheus 규칙 3그룹·55개와 Alertmanager 조회 응답을 확인했다. 서비스·DB 구성도의 정상·장애·미수집 전환 12개는 브라우저 응답 표본으로만 검사했으며 실제 DB 중단이나 Teams 추가 전송은 없었다. 아이콘·문구의 색상 일치와 이전 정상 표시 잔류 없음, WAL 0 B의 올바른 수치 표시를 확인했다.

[패널 질의 검사](../../artifacts/operations-20260918/grafana/query-check.json)는 실제 Prometheus 질의 85개를 확인했다. 관측 Python 검사 29개를 모두 실행해 통과했으며 실제 promtool의 35개 조건·83개 기대값을 포함한다. 오래된 대상·부분 수집·다른 고객 격리·복수 Primary·실제 DB 역할과 요청 없음 조건을 검사했다. AWS·고객 호스트 미등록은 미수집으로 유지한다.

조회 검증 중 Grafana의 종전 384MiB 한도에서 381.2MiB 사용과 연결 중단·재시작을 확인했다. 현재 cgroup 기록만으로 OOM 원인을 확정하지 않았으며 한도를 768MiB로 조정한 후 화면 검사를 다시 수행했다. AWS에서는 관측 노드의 전체 메모리와 봇·Prometheus 동거 조건을 별도 산정해야 한다. CloudWatch 질의는 고객별 리소스 매핑과 실제 IAM 확인 전 비활성 상태다. 고객 경보 패널은 고객·환경·역할 라벨이 있는 경보만 표시하며 하네스의 미분류 집계 경보는 기본 경고 메뉴에서 확인한다.

## DB 관제 재검토와 조회 부하

후속 검토는 현재 DB 화면과 실제 PromQL·SQL을 대조했다. 화면 검사는 배치 오류·연결·상태 전환의 검사이며 DB 진단 설계의 완성도를 보증하지 않는다. 검토자의 평가 점수는 58/100이다. 용어·계산 14/25, 진단 범위 14/30, 정보 배치 10/20, 가독성 11/15, 자료 공백 구분 9/10으로 나눴으며 외부 기관의 평가 기준은 아니다.

`WAL 위치 증가율`은 LSN 차이를 시간으로 나눈 현재 구현을 옮긴 명칭이다. 운영 화면에는 `WAL 생성량 (MiB/s)`과 `복제 미적용량 (bytes)`을 구분하고, 생성량은 PostgreSQL 17의 `pg_stat_wal.wal_bytes`를 수집하는 방향을 제안했다. 현재 값을 이름만 바꾸어 동일 지표라고 선언하지 않았다. 복제 위치 차이를 실제 유실량이나 RPO로 단정해서도 안 된다.

현재 TPS는 commit과 rollback의 합이며 조회 트랜잭션·수집 질의도 포함한다. SQL 호출 수나 주문 처리량과 같지 않다. `state=active` 세션에는 대기도 포함하며, 현재 쿼리는 wait-event별 시계열을 노드 단위로 합치지 않고 같은 범례로 표시할 수 있다. 전체 잠금 수는 차단 세션 수가 아니다. 조회·변경 SQL 호출량, 실행·대기·유휴 세션, 장기 트랜잭션과 차단 관계를 따로 수집해야 한다. 실제 PostgreSQL 17.11의 shared_preload_libraries는 비어 있고 설치 확장은 plpgsql·pgcrypto뿐이어서 pg_stat_statements 기반 조회는 아직 없다. 정의 근거는 [PostgreSQL 통계](https://www.postgresql.org/docs/17/monitoring-stats.html)와 [pg_stat_statements](https://www.postgresql.org/docs/17/pgstatstatements.html)다.

제안 배치는 상단의 서비스 영향·접속·복제 요약, 같은 행의 조회·쓰기 처리량과 지연, 다음 행의 세션·연결 풀·잠금 대기, 그 아래의 WAL 생성·전송·재생 상태 순이다. 작은 구성도에는 실제 노드와 역할을 표시하고 `정상` 반복과 빈 공간을 줄인다. 테이블 크기·백업 상세·복원 이력은 상세 영역으로 옮긴다. 이 절은 평가와 개선안이며 대시보드 개편을 추가 완료했다는 기록이 아니다.

19:15:33~19:20:39 KST에 기존 Docker 실습에서 공개 조회만 수행했다. 앱 한 대의 메모리 한도는 1GiB, CPU quota는 없으며 Docker 호스트는 12 CPU·약 15.46GiB로 관측 도구·DB·부하 생성기가 공유했다. 주문 4건·체결 2건의 작은 DB이며 시장 봇은 정지 상태였다. 기존 IP 버킷 300 tokens/10s를 유지했다. k6 1.4.0 한 컨테이너에서 호가·체결·1분 캔들을 같은 비율의 고정 순서로 호출했으며 비용은 각각 1·2·2 token이다. 부하 생성기는 2 CPU·512MiB, 단계별 VU 상한은 40으로 제한했다.

## DB 관제 지표 보강과 상세 화면 분리

앞 절의 평가 이후 기존 Grafana 디자인을 유지하면서 DB 요약, SQL·세션, 복제·복구로 내용을 나눴다. 서비스·Spring·AWS/서버를 포함한 생성 대시보드는 여섯 개다. DB 요약은 역할·연결·차단·복제 상태와 처리 부하를 연결하고, 상세 화면은 명령별 SQL 실행량·평균 시간·세션 대기와 WAL·복구 준비를 구분한다. 초기 네 화면의 검사와 58점 평가는 당시 결과이며 이번 개편의 최종 점수나 검증 결과로 바꾸지 않는다.

19:35:59~19:36:12 KST의 [SQL 통계 활성화 근거](../../artifacts/operations-20260918/grafana-db/sql-statistics-activation.json)에서 PostgreSQL 17.11 두 노드의 빈 preload에 `pg_stat_statements`를 추가했다. 현재 primary인 `failstop-ops-lab-standby-1`과 replica인 `rejoined-1`의 역할을 유지하고 양쪽 감시 계정의 통계 조회를 확인했다. 전후 주문 4건·체결 2건·원장 40건·명령 4건이 일치했다. 이 행 수 대조는 보존된 대상의 확인이며 모든 거래 정합성 검사를 다시 수행했다는 뜻은 아니다. 실행 도구는 [로컬 활성화 스크립트](../../deploy/observability/enable-local-sql-statistics.py)이며 AWS나 다른 DB 배치에 공통 적용하는 도구가 아니다.

[원천 질의](../../harness/prometheus/pg-queries.yaml)는 `pg_stat_wal.wal_bytes`를 primary에서만 읽어 WAL 생성량을 산출한다. LSN 차이는 전송·쓰기·영속화·재생 단계별 대기량으로 남기고 실제 데이터 유실량으로 해석하지 않는다. 세션은 수집 연결과 감시 계정을 제외한 client backend를 상태별로 구분한다. 대기 이벤트 없는 active도 CPU 실행을 입증하지 않으며, 잠금 차단은 `pg_blocking_pids`, 최장 잠금 대기는 `pg_locks.waitstart`, 장기·유휴 트랜잭션은 `xact_start`를 사용한다.

SQL 통계는 감시 계정 외 top-level 성공 완료 호출을 SELECT·INSERT·UPDATE·DELETE·MERGE·WITH·OTHER로 집계한다. WITH를 읽기로 추정하지 않고 SELECT의 쓰기 함수 가능성도 남긴다. SQL 원문·query ID·사용자 식별자는 지표로 내보내지 않는다. 평균 실행 시간은 초기화·수집 오류 노드를 제외한 유효 표본의 호출 수로 가중하며 API 응답 시간이나 SQL P95가 아니다. 제외된 노드가 있을 때 전체 노드의 성능으로 확대하지 않는다. 관리자 질의도 포함될 수 있고, 기본 DB TPS·행·캐시 통계에는 수집 작업 자체가 포함된다. 확장 미설치·미로드·권한 부족은 SQL 통계 미수집이며 0 calls/s로 대체하지 않는다. 초기화·항목 퇴출·집계 counter 감소와 수집 오류가 포함된 rate 구간도 제외한다.

[격리 통합 검사](../../deploy/observability/tests/test_pg_ops_metrics.py)를 PostgreSQL 17과 postgres_exporter v0.17.1에서 실행해 세 테스트와 12개 실제 조건을 통과했다. 확장 미설치·설치 후 preload 누락, 통계 권한·뷰 SELECT·스키마 USAGE 부족, 변경 CTE 분리, 감시 SQL 제외, 실제 두 세션의 잠금 차단·해제, 표준 WAL 값과 exporter 출력이 포함된다. 시험용 DB·네트워크만 사용하고 기존 실습 DB를 변경하지 않았다. 이후 실제 primary·replica에서 `failstop_monitor`로 열 개 질의를 읽기 전용 실행해 모두 성공했으며, WAL 생성 지표는 primary 한 행·replica 영 행으로 확인했다.

컨트롤러 도달 전에 요청 제한 필터가 거절한 공개 조회에도 정해진 URI 템플릿을 기록하도록 [HTTP 관측 규칙](../../server/app/src/main/java/kr/exchange/config/PublicRequestObservationConvention.java)을 추가했다. 임의 경로나 query string을 라벨로 만들지 않는다. 서버 전체 build는 9분 51초에 성공했고 app 테스트 624개를 실제 실행해 실패 없이 통과했다. engine 테스트 65개는 기존 결과가 UP-TO-DATE였으며 이번에 다시 실행한 수로 합산하지 않는다. 새 앱 이미지만 기존 실습에 적용했다.
