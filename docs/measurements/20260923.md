# 측정 20260923

2026-09-23 새벽(02:46~05:01 KST)에 로컬 카오스 스택에서 조회 증설 노드 `chaos-api-3`을 붙였다 떼는 경로를 재고, 이어서 E4 한 회차를 돌렸다. 로드밸런서는 쓰기와 조회 업스트림으로 갈린 뒤의 구성이다(`60cb3de`). 조회 증설 원자료와 시간 순서는 [scale-rehearsal-20260923](../../harness/evidence/scale-rehearsal-20260923/README.md), E4 판정 파일은 [E4-20260923-045947.json](../../harness/evidence/chaos-runs/E4-20260923-045947.json)에 있다. 일부 수치는 그날 작업한 세션의 기록에만 있고 저장소로 옮기지 않았다. 그런 값은 '세션 기록'이라고 표시했다.

환경은 Windows 11의 Docker Desktop 단일 호스트다. 앱 노드는 compose 한도로 1 vCPU·1 GiB이고 `chaos-pg`에는 CPU 한도가 없다. DB 볼륨 `chaos-pgdata`는 09-13에 만든 것을 지우지 않고 썼다. 체결은 04:28에 12만 2,539행, E4 직전에 13만 5,969행이었다. 이 기록은 학교나 개인 AWS의 ALB·ASG 동작을 대신하지 않는다. 앞 날짜의 처리량·복구 수치와 나란히 놓지 않는다.

## 코드와 이미지

02:45에 스택을 다시 올리고 02:46:34에 `chaos-api-3` 컨테이너를 만들었다. 그 컨테이너의 이미지(`sha256:89d58c77…`)는 지금 로컬 이미지 저장소에 없다. 이때 권고 임계는 서버 코드 상수 0.60/0.30이었다.

04:36에 작업 트리에서 이미지(`sha256:d157dc3a…`)를 다시 빌드하고 api-1·api-2·chaos-admin을 새로 만들었다. 이 빌드에서 임계가 설정으로 옮겨졌고 `admin-chaos` 프로파일이 0.25/0.10으로 내렸다. 작업 트리는 04:53에 `5767517`로 커밋됐다. `chaos-api-3`은 scale 프로파일이라 다시 만들어지지 않았으므로 04:37 리허설에서는 02:46의 옛 이미지로 떴다. 증설 노드는 AWS 조회 노드 설정(`prod,read`, ReadRoleFilter, 읽기 전용 풀)이 아니라 api-1 환경을 물려받은 `dev,chaos-monkey` 구성이다. 구성과 DB 연결 예산은 [검증 설계 §3](../reference/contracts/하네스_검증설계.md)에 적었다.

## 조회 분산 (02:50, 조회 부하 없음)

3대가 모두 조회 업스트림에 들어간 상태에서 로드밸런서로 같은 경로를 연속 호출하고 노드별 `http_server_requests_seconds_count{uri=...}` 증가분을 셌다. 노드 전체 요청 수는 봇 쓰기 트래픽이 섞여 조회 몫을 읽을 수 없어 쓰지 않았다. 스크립트는 `readsplit3.py`이고 출력은 세션 기록이다.

| 경로 | 호출 | api-1 | api-2 | api-3 |
|---|---:|---:|---:|---:|
| `/api/v1/markets` | 90 | 29 | 30 | 31 |
| `/api/v1/trades` | 90 | 31 | 30 | 30 |
| `/api/v1/orderbook` (쓰기 경로) | 60 | 65 | 0 | 0 |

체결 조회의 노드 합은 91이다. 같은 창에 다른 체결 조회 1건이 섞였다. 봇 중 평균 회귀 추세 봇이 체결 조회로 신호를 읽으므로 봇 요청도 조회 업스트림에 일부 들어간다. 호가는 쓰기 업스트림으로만 갔고 api-1의 65에는 같은 창의 봇 호가 조회가 들어 있다.

## 봇 발행률만 올린 주행 (04:27~04:31, 세션 기록)

조회 부하 없이 봇 목표만 초당 300건으로 올렸다. 처음 약 100초 동안 조회 계층 평균 표본 7개는 4~12%(최대 12.4%)였고, 그 사이 잰 체결은 초당 18.1건이었다. 당시 임계 0.60에서 권고는 뜨지 않았다. 그 뒤 표본은 같은 시각에 따로 돌린 조회 부하 시험이 섞여 21~34%로 올랐으므로 봇만의 값으로 읽지 않는다. 봇 요청 대부분은 주문·취소·계좌 조회와 쓰기 경로에 남는 호가·티커라 조회 계층을 거의 움직이지 않는다.

관리 API로 희망 대수와 봇 발행률만 바꾸고 컨테이너는 조정기가 움직였다. 부하는 `read-load.py` 20 작업자 420초(04:37:22부터)와, 리허설 9.9~42.2초 구간의 봇 목표 초당 300건이 겹쳤다. 420초 동안 200은 14만 5,078건(초당 345건)이고 그 밖의 응답은 0이었다(세션 기록).

| 항목 | 값 |

## E4 리더 kill (04:59:47)

리허설의 두 조정기가 모두 끝난 뒤 `harness/scripts/e4-leader-kill.ps1`을 한 번 돌렸다. 설정은 `harness/config/e4.env`(워밍업 30초, 봇 40 OPS, 목표 RTO 30초)이다. 판정 파일은 `E4-20260923-045947.json`이다.

| 항목 | 값 |
|---|---|
| 판정 | PASS |
| RTO(kill부터 체결 재개) | 6.133초 |
| `failover_runs`의 다운타임 | 7.266초 |
| epoch | 8에서 9 |
| RPO 기록 | 0 |
| 중복 주문·중복 체결·자산합·명령/이벤트 간격 | 모두 0 |
| 체결 | 13만 5,969행에서 13만 6,041행 |
| 불변식 행 | 58(사전 29, 사후 29), 위반 0 |

판정 파일의 `code`는 커밋 `5767517`에 미커밋 경로 1개다. 그 경로는 `chaos-pg`에 `shm_size: 256m`을 더한 compose 파일이고 05:04에 `3297345`로 커밋됐다. 04:55의 첫 E4 시도는 사전 권위 run의 불변식 배치가 공유 메모리 부족(`could not resize shared memory segment`)으로 500을 받아 판정 전에 끝났고 판정 파일이 없다(세션 기록). 그 뒤 `chaos-pg`를 공유 메모리 256 MiB로 다시 만들고 api-1·api-2·chaos-admin·chaos-bots를 재시작한 스택에서 이 회차를 돌렸다. 볼륨을 새로 만든 스택이 아니다.

C16은 `harness.loadtest_acks`가 0행인 상태의 통과다. 이 회차에는 k6 ACK 원장이 없으므로 RPO 0의 근거는 C05·C06·C13a 저널 무결이다. 한 회차이므로 RTO를 다른 날짜의 E4와 나란히 놓지 않는다. 리스 TTL은 compose 기본값이 6초이고 env 파일이 덮어썼는지는 확인하지 않았다.

## 재지 않은 것

로드밸런서를 쓰기와 조회로 가른 뒤 E5·E7은 다시 돌리지 않았다. 조정기를 띄운 채 장애 실험을 막는 장치는 없고, 이 회차는 순서로만 떼어 놓았다. 증설 노드를 `prod,read` 구성으로 띄운 측정, 노드별 사용률, 부하 없는 상태의 권고 임계 확인도 하지 않았다.
