# 측정 20260924

2026-09-24 새벽(04:41~05:31 KST)에 ADR 0034 마켓 분할 리더의 S1·S2 관문 주행을 로컬 Docker의 폐기용 스택에서 했다. 작업 브랜치 `claude/per-market-leader`의 `b04acd5`(S1 잔여와 S2 코드)로 이미지를 구웠고, 비교 기준은 main `ec8ef8e`다. compose 프로젝트는 `exchange-pml`이고 볼륨·망이 보존 스택 `exchange-chaos`와 갈린다. 보존 볼륨 `exchange-chaos_chaos-pgdata`와 백업 볼륨 `failstop-keep-chaos-pgdata-20260924`는 마운트하지 않았고 주행 전후 그대로다. 환경은 Windows 11의 Docker Desktop 단일 호스트이고 앱 노드는 1 vCPU·1 GiB다. 이 기록은 AWS의 장애나 처리량을 대신하지 않는다.

## S1 관문 장애 주행 E2·E4·E5·E6·E7

원자료는 [pml-s1-gate-20260924-0440](../../harness/evidence/pml-s1-gate-20260924-0440/README.md)이다. `b04acd5` 이미지를 `dev,chaos-monkey,prod-timeouts` 프로필로 띄우고 `adr0022-stage5-chaos.ps1`로 실험마다 스택을 새로 세워 한 번씩 돌렸다. 앱 로그인은 카오스 스택 기본인 스키마 소유자다. 모드는 P1이다.

**다섯 실험 모두 PASS 다.** 단계 계획 S1의 판정(RTO < 30초, 구 epoch 쓰기 증분 0, C01·C02·C05·C13A·C14·C22 0)을 채웠다.

| 실험 | RTO(초) | rpo_records | C22 두 팔 | created_at 역행 | 09-14 RTO(초) |
|---|---:|---:|---|---:|---:|
| E2 DB 연결 절단 | 10.362 | 0 | 0, 0 | 0 | 10.507 |
| E4 리더 kill | 5.186 | 0 | 0, 0 | 0 | 5.866 |
| E5 네트워크 분리 | 5.794 | 0 | 0, 0 | 0 | 10.079 |
| E6 부하 급증 중 kill | 7.882 | 0 | 0, 0 | 0 | 5.277 |
| E7 리더 pause | 10.155 | 0 | 0, 0 | 0 | 10.024 |

- 다섯 실험 모두 epoch가 1에서 2로 오르고 보유자가 바뀌었다. 사후 권위 run의 C01·C02·C05·C13A·C14·C22와 C29는 모두 0이고 연결 고갈은 없었다.
- 구 epoch 쓰기 증분은 E5·E7만 직접 잰다(둘 다 0). E4·E6는 구 리더를 kill 하고 E2는 DB 연결을 끊으므로 증분을 따로 세지 않으며, C22 두 팔 0으로 대신한다.
- 오른쪽 열은 [09-14](20260914.md) 5.7.18(ADR 0022 4단계 이미지, dev 프로필)이다. 이미지·프로필·날짜가 달라 차이를 코드 효과로 해석하지 않는다.
- E 스크립트는 고치지 않고 돌았다. 리스 조회가 모두 `resource='matching-engine'` 조건이라 V48 뒤 P1에서 맞는다. 하네스에는 폐기용 스택 지원(프로젝트 이름, 망 이름, 셸 이미지 태그 우선, 증거 폴더 지정)만 더했다.

**재지 않은 것.** 실험별 반복, 앱 역할 로그인에서의 장애 주행, 클라우드 스택이다.

## S2 관문 폐기용 스택 주행

원자료는 [pml-s2-gate-20260924-0440](../../harness/evidence/pml-s2-gate-20260924-0440/README.md)이다. [S2 설계](../reference/architecture/마켓분할_리더_S2_설계.md) 6-4의 세 주행을 설계 순서대로 했다.

**S2 관문은 통과하지 않았다.** 종단 주행과 되돌림 주행은 PASS, A/B 비교는 사전 규칙의 "5xx 증가 없음"을 채우지 못해 FAIL이다.

- 앱 역할 로그인 종단 주행(PASS). S2 이미지를 배포와 같은 런타임 로그인(`app_role` 소속, 수퍼유저 아님, Flyway 끔)으로 띄웠다. 리더가 서고 새 epoch로 주문·체결·스냅샷을 썼으며, api 연결은 모두 앱 로그인이었고 권한 거부는 0줄이다. 하네스 SQL의 C01~C29 31행이 모두 PASS다. V49를 적용하지 않은 권한 상태다.
- 되돌림 주행(PASS). A/B의 B 칸이 남긴 V48 DB에서 main 이미지의 배포용 마이그레이션 진입점과 Spring Flyway가 모두 "DB 버전 48이 이미지의 최신 47보다 새롭다" 경고 뒤 적용 없이 끝났다. 그 이미지를 앱 역할 로그인으로 띄우자 리더가 되어 주문·체결·스냅샷을 썼고 C01~C29가 모두 PASS다.
- A/B 비교(FAIL). `roundtrip_probe.py` 600/s를 칸마다 새 스택에서 A1(main), A2(main), B(S2) 순으로 돌렸다.

| 칸 | 접수/s | append 평균(ms) | append p95(ms) | 서버 5xx | 리더 5xx | 불변식 |
|---|---:|---:|---:|---:|---:|---|
| A1 | 146.7 | 11.096 | 51.76 | 3,309 | 0 | 0 |
| A2 | 163.0 | 10.247 | 50.10 | 2,726 | 0 | 0 |
| B | 136.9 | 10.982 | 52.50 | 4,137 | 0 | 0 |

append 평균 증가 +0.310ms와 p95 증가 +1.565ms는 A-A 차이(0.849ms, 1.664ms)보다 작다. 5xx 증가 +1,119.5는 A-A 차이 583을 넘는다. 5xx는 모두 팔로워의 설계상 503과 nginx의 502(주 업스트림 연결 시간 초과 뒤 백업 거절)이고 리더가 낸 5xx는 0이다. 판정은 설계가 범위를 정하지 않은 5xx를 가장 넓게 셌다.

원인 좁히기로 B2·A3을 더 돌렸다(판정에 쓰지 않음). B2 접수 138.0/s·5xx 3,673, A3 160.0/s·2,493으로 같은 모습이 되풀이됐다. S2 이미지의 접수 처리율이 과부하(제공 부하가 능력의 약 4배)에서 약 12% 낮다. 접수 락 안의 DB 구간(머리말·저널 삽입·커밋)과 락 보유 시간은 이 차이를 설명하지 못했고, 원인은 특정하지 못했다.

**재지 않은 것.** 6-1·6-3 서버 시험의 재실행, V49 이미지 관문, 포화 전 부하의 A/B, 프로파일링이다. A/B는 칸마다 1회라 12% 차이의 신뢰구간이 없다.
