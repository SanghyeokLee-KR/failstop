# 역할 체계 운영 기록

1인 프로젝트에서 4인 팀의 역할 분담표를 대체하는 문서다. `CLAUDE.md` 6절이 이 문서를
그 대체물로 지정한다.

기준 커밋 `c39cef8`.

## 역할 구조

정의 정본은 `.claude/agents/` 넷이다. 미러를 두지 않는다.

| 역할 | 담당 | 산출물 트리 | 도구 권한 |
|---|---|---|---|
| backend-engineer | 매칭엔진, 원장, 저널, API | `server/` | 전체 상속 |
| frontend-engineer | 화면, 실시간 바인딩, 접근성 | `web/` | 전체 상속 |
| harness-engineer | 검증과 운영 기반 | `harness/`, `deploy/`, `.github/`, `scripts/` | 전체 상속 |
| reviewer | 독립 판정 | 없음 | `Read, Grep, Glob, Bash, PowerShell` |

reviewer의 수정 불가는 선언이 아니라 구조다. 정의 파일 넷 중 `tools` 행을 가진 것은
reviewer 하나뿐이고 그 목록에 Edit과 Write가 없다. 나머지 셋은 필드가 없어 전체 도구를
상속한다. 따라서 reviewer가 직접 고쳐 두는 경로가 존재하지 않고, 지적은 반드시 구현
역할의 다음 변경으로만 해소된다.

## 위임 규칙

`CLAUDE.md` 5절과 7절이 정한다.

구현 역할이 만든 변경은 reviewer 판정을 받아야 병합한다. 판정은 PASS, PASS WITH FOLLOW-UP,
FAIL 셋뿐이고 필수 테스트 실패나 계약 불일치가 남으면 FAIL이다.

역할 간 이견은 정본 문서가 판정한다. 문서가 틀렸으면 문서를 먼저 고친다. 정본끼리
충돌하면 구현을 중단한다.

`scripts/measure-role-system.ps1`이 산출한다. 원본은 `artifacts/verification/role-system/`.

2건은 빈 커밋이다. 단독 커밋의 분포는 web 79, server 32, docs 31, harness 30이다.

역할 경계가 커밋 단위로 완전히 지켜지지는 않았다. 복수 트리 커밋 141건은 한 커밋이 두
역할의 범위를 동시에 건드린 경우를 포함한다.

## 4인 팀 분담과의 대응

| 4인 팀 | 이 프로젝트 |
|---|---|
| 팀원별 담당 모듈 | 역할 하네스 넷의 담당 트리 |
| 담당자 기입 | 변경 트리로 귀속 |
| 팀 리뷰 승인 | reviewer 판정. `docs/records/검토_판정기록.md` |
| 역할 간 협의 | 정본 문서 판정. 어긋나면 문서를 먼저 고친다 |

## 한계

- 실제 사람 간 협업을 재현하지 않는다. 일정 병렬화 효과가 없고 1인은 직렬이다.
- 판정자와 구현자가 다른 사람이 아니다. 다른 지시문과 다른 도구 권한을 받은 같은 모델
  계열이라 공통 오류 모드를 공유할 수 있다.
- 정본 문서도 같은 주체가 썼다. 처음부터 틀리게 쓴 전제는 판정 단계에서 걸러지지 않는다.
- 그래서 최종 판정을 기계 게이트에 싣는다. SQL 0행, 메트릭 임계, 종료코드, 스타일 게이트,
  문서 링크 게이트. 기계가 못 잡는 층에서는 검출력이 낮다.
- 도구 권한 분리가 reviewer 하나에만 적용된다. 구현 역할 셋은 서로의 트리를 고칠 수 있고
  그 경계는 지시문 준수에만 의존한다.
