> 동시 접속 2000 명. 그 위는 메모리가 말라 거래소가 죽는다.

### 2-2. 로드밸런서는 조회만 나눈다

정본 `deploy/nginx-edge.conf.template` 의 규약을 그대로 세워 확인했다.

| 상황 | 조회 | 쓰기 |
|---|---|---|
| 두 노드 정상 | 52% 대 48% 로 나뉨 | 리더 단독 (접수 181 건, 실패 0) |
| 리더 정지 | **200 (30/30)** | **502 (30/30)** |

조회는 리더가 죽어도 안 끊긴다. 쓰기는 멈춘다. 단일 라이터 구조에서 리더 없는 쓰기는 순서를
깨므로 **받아서 틀리는 것보다 거절하는 것이 맞다.** 다만 자동 승격이 없어 사람이 재기동해야
한다.

### 2-3. DB 는 4 vCPU 가 경계선이다

| DB 규격 | 60 OPS 에서 주문 P95 | 대기열 |
|---|---|---|
| 4 vCPU | 130ms | 0 |
| 2 vCPU | **1136ms** | **76** |

2 vCPU 의 실용 상한은 약 30 OPS 다. **절반으로 줄이면 처리량도 절반이 된다.**

25 회차의 `DB 를 올려도 천장이 안 오른다` 와 모순이 아니다. 4 vCPU 가 경계선이고 그 아래는
DB 가, 그 위는 단일 라이터가 병목이다.

메모리는 세 구간 모두 26% 이하다. **줄여야 할 것은 메모리고 줄이면 안 되는 것은 코어다.**

### 2-4. 읽기 복제본은 42% 만 덜어낸다

| 성격 | DB 시간 비중 |
|---|---|
| 쓰기 | **58%** |
| 읽기 | 42% |

행 수로 보면 읽기가 쓰기의 471 배다(271646/s 대 574/s). **행 수로 판정하면 결론이 뒤집힌다.**
시간으로 재야 한다.

판정은 `DB CPU 가 문제면 복제본보다 스펙 업이 먼저` 다.

### 2-5. WS 는 몰려오면 62 배 느리다

| 2000 명이 | 첫 메시지 p50 |
|---|---|
| 한꺼번에 붙으면 | 1243ms |
| 90 초에 걸쳐 붙으면 | **20ms** |

구독 하나마다 서버가 호가 집계를 한 번 돈다(`OrderbookSnapshotOnSubscribe`). 몰려오면 그
집계가 몰린다.

### 2-6. 판별식을 3 행으로 고쳤다

전날 판별식은 `응답이 없는데 CPU 가 낮으면 고장, 높으면 부하` 였다. 오늘 힙 소진 사망은
CPU 99% 라 그 판별식이 부하로 오판한다. 증설해도 살아나지 않는다.

| 응답 없음 + | CPU | 송신 | 원인 | 대응 |
|---|---|---|---|---|
| | 낮음 | 0 | 고장 | 재기동 |
| | 높음 | 있음 | 부하 | 거절 또는 증설 |
| | 높음 | **0** | **힙 소진** | **재기동 + 메모리 증설** |

**CPU 는 GC 가 도는 것도 100% 로 보인다.** 일한 결과가 나가는지는 송신량만 안다.

## 3. 관제 화면

### 3-1. 구조

고객 -> 서비스 -> 자원 3 단이다. **값을 클릭하면 그 축의 상세로 넘어간다.** 사이드바를 열지
않는다. Grafana 는 `fieldConfig.defaults.links` 에 링크를 하나 두면 stat 패널 전체가 링크가
된다. 시간 범위와 고객사 변수는 `$__url_time_range` 로 넘겨 유지한다.

| 파일 | uid | 내용 |
|---|---|---|
| `10-msp-overview.json` | `msp-overview` | 서비스 6 칸, 자원 4 칸, DB 4 칸, 발화 알람 표 |
| `11-msp-service.json` | `msp-service` | 들어오는 양, 실패, 느림 |
| `12-msp-infra.json` | `msp-infra` | 노드별 CPU·메모리·망·스레드, JVM, 리더 여부 |

상단 순서는 서비스가 먼저고 CPU 가 나중이다. **CPU 20% 인데 커넥션이 말라 사이트가 죽는
경우가 있어서 자원부터 보면 장애를 놓친다.**

`05-ops.json` 에서 `이 화면 읽는 법` 문단과 `한계까지 얼마나 남았나` 행을 걷어냈다. 설명이
화면을 차지하면 정작 값이 안 보인다.

### 3-3. 자원 수집기 결함 정정

`docker stats` 의 `"123MiB / 1GiB"` 를 가를 때 뒤에 `" / 0B"` 를 덧붙인 뒤 첫 구분자로 잘라
상한 쪽에 `"1GiB / 0B"` 가 남았다. 단위 정규식이 그것을 못 읽어 **상한이 0 이 되고 메모리
사용률이 무한대로 표시됐다.** 네트워크 송신도 같은 이유로 0 이었다.

## 4. 오늘 겪은 함정

전날 함정 다섯은 `인수인계_20260903.md` 3-3 절에 있다. 오늘 새로 겪은 것만 적는다.

1. **STOMP 하트비트를 빠뜨리면 연결이 끊긴다.** `WebSocketConfig` 가 양방향 10 초를 고정한다.
   10 초 안에 아무것도 보내지 않으면 서버가 세션을 닫는다. WS 부하 도구는 8 초 주기로 개행을
   보내야 한다. 이것을 빠뜨려 60 초 유지가 전부 조기 종료로 계상됐다.
2. **부하 계단을 한 실행에 몰아넣으면 종료가 실패로 계상된다.** 시험이 끝날 때 모든 연결이
   강제 종료되고 그 종료가 오류로 잡힌다. VU 하나가 한 번만 돌고 유지 시간이 차면 스스로 닫는
   구조여야 성공과 실패가 갈린다(`per-vu-iterations`).
3. **램프 시간이 유지 시간보다 길면 목표 인원이 동시에 겹치지 않는다.** 90 초 램프에 60 초
   유지면 먼저 붙은 연결이 나중 연결이 붙기 전에 끊긴다. 게이지가 588 로 나와 알았다.
   유지 시간이 램프 시간보다 길어야 한다.
4. **Grafana 파일 프로비저닝이 Docker Desktop 바인드 마운트에서 변경을 늦게 본다.** 검증 중에는
   `/api/dashboards/db` 로 밀어 넣는다. 저장소 정본은 어디까지나 파일이다.
5. **PowerShell 로 중괄호가 든 PromQL 을 넘기면 깨진다.** 질의를 파이썬 파일에 넣고 그 파일을
   실행한다.
6. **파이썬 heredoc 으로 자바스크립트를 고칠 때 `'\n'` 이 실제 개행이 된다.** `String.fromCharCode(10)`
   을 쓴다. `lib/stomp.js` 가 이미 그 방식이다.
7. **`docker run -w /load` 가 `MSYS_NO_PATHCONV=1` 없이는 `D:/Git/load` 로 변환된다.**

## 6. 이어가기

전날 문서 3-2 절의 환경 세우기 절차가 그대로 유효하다. 오늘 추가된 컨테이너만 적는다.

로드밸런서.

```
docker run -d --name ex-lb --network exnet -p 18888:80 \
  -v <검증본 nginx.conf>:/etc/nginx/nginx.conf:ro nginx:1.29
```

관측 보강.

```
docker run -d --name ex-blackbox --network exnet \
  -v <blackbox.yml>:/config/blackbox.yml:ro \
  prom/blackbox-exporter:v0.28.0 --config.file=/config/blackbox.yml

docker run -d --name ex-pgexp --network exnet \
  -e DATA_SOURCE_NAME="postgresql://exchange:exchange@ex-pg:5432/exchange?sslmode=disable" \
  quay.io/prometheuscommunity/postgres-exporter:v0.17.1
```

WS 용량 측정.

```
docker run --rm --network exnet --memory 12g \
  -v <repo>/harness/load:/load -w /load \
  -e BASE_URL=http://ex-app:8080 -e WS_HOST=ex-app -e MARKET=KRW-BTC \
  -e WS_VUS=2000 -e WS_RAMP_MS=90000 -e HOLD_MS=150000 \
  grafana/k6:1.4.0 run ws_capacity.js
```

`HOLD_MS` 는 `WS_RAMP_MS` 보다 길어야 목표 인원이 동시에 겹친다.
