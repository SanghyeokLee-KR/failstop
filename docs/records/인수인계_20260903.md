## 2. 발표에 쓸 수치

전부 실측이다. 지어낸 값이 없다.

### 2-1. 결함과 그 효과

`InflightReserves.tryReserve` 와 `EngineBridge.submit` 이 `synchronized` 안에서 DB 를 왕복했다.
JDK 21 에서 그 조합은 가상 스레드를 캐리어에 고정하고, 캐리어 수는 가용 코어 수다.
2 vCPU 에서 캐리어 2개가 고정되면 스케줄링이 통째로 멈춘다. `ReentrantLock` 으로 바꿨다.
상호 배제 계약은 그대로이고 고정만 사라진다.

같은 부하(주문 16건/s) 전후 대조다.

| 항목 | 고치기 전 | 고친 후 |
|---|---|---|
| 접수 | 427 / 1440 (30%) | 1441 / 1440 (100%) |
| p95 | 59997ms | 1190ms |
| 실패율 | 13.1% | 0% |
| 노드 | 영구 정지. 회복 없음 | 정상 |

### 2-2. 용량 상한 (2 vCPU, 게이트 OFF, 봇 3마켓 동시 가동)

| 주문/s | 접수 | p95 | 판정 |
|---|---|---|---|
| 12 | 100% | 824ms | 정상 |
| 20 | 100% | 1616ms | 정상. 여기까지가 용량 |
| 26 | 95% | 4748ms | 접수는 되나 쓸 수 없는 응답 |
| 40 | 8% | 9446ms | 포화. 그래도 죽지 않는다 |

고치기 전에는 16건/s 에서 영구 정지였다. 고친 뒤에는 절벽이 사라지고 지연 상승으로 바뀐다.

### 2-3. CPU 는 이 사고를 보지 못한다

16건/s 주행에서 죽는 과정의 인스턴스 CPU 다.

| 시각 | CPU | 상태 |
|---|---|---|
| 09:39:19 | 18% | 정상. 마지막 응답 |
| 09:39:25 | 16% | 정지 |
| 09:39:34 | 12% | 정지. 최저 |
| 09:39:53 | 54% | 정지. 최고 |

읽는 법이 셋이다. 죽기 직전이 18% 라 어떤 임계 알람도 걸리지 않는다. 죽는 순간 12% 로
내려간다. 최고점 54% 는 정지 시작 28초 뒤에 온다. 그 54% 도 일이 아니라
`HikariPool-1:housekeeper` 가 고갈된 풀에서 `Thread.yield()` 로 헛도는 몫이다.

### 2-4. 게이트를 켜면 지연이 평탄해진다

| 주문/s | p95 게이트 OFF | p95 게이트 ON |
|---|---|---|
| 26 | 4748ms | 272ms |
| 32 | 8245ms | 267ms |
| 40 | 9446ms | 240ms |

초과분은 전부 429 로 나가고 5xx 는 0 이다. 거절이 답이라는 것을 보여주는 표다.

### 2-5. 확장은 해법이 아니다

정지한 노드가 리더 리스를 계속 갱신하므로, 같은 DB 에 두 번째 노드를 띄우면 승격 대기
15초를 소진하고 기동을 거부당한다(크래시 창에 재적재할 이벤트가 남아 있을 때).
Auto Scaling 은 무효한 정도가 아니라 기동 크래시루프가 된다.

## 3. 다른 기계에서 이어가기

### 3-1. 필요한 것

Docker Desktop, JDK 21, Git. 저장소는 `main` 최신을 받는다.

### 3-2. 실험 환경 세우기

한글 경로에서 `gradlew test` 가 실패한 이력이 있다(기획안 13.6). 저장소를 영문 경로에 둔다.

```bash
docker run -d --name exchange-pg-gateoff -p 5433:5432 \
  -e POSTGRES_DB=exchange -e POSTGRES_USER=exchange -e POSTGRES_PASSWORD=exchange \
  postgres:17-alpine

cd server && ./gradlew.bat :app:bootJar
```

2 vCPU 모사는 `-XX:ActiveProcessorCount=2` 와 프로세서 어피니티 2코어를 함께 준다.
PowerShell 에서 `$p.ProcessorAffinity = 3` 이다. 어피니티 설정이 `Access is denied` 로
실패할 때가 있는데 기동 직후 경합이 원인이고 재시도하면 된다.

거래소 노드.

```bash
java -XX:ActiveProcessorCount=2 -jar app/build/libs/app-0.1.0-SNAPSHOT.jar \
  --spring.profiles.active=dev --server.port=8090 \
  --spring.datasource.url=jdbc:postgresql://localhost:5433/exchange
```

봇 노드(엔진 끄고 리더 경쟁에서 뺀다).

```bash
java -jar app/build/libs/app-0.1.0-SNAPSHOT.jar \
  --spring.profiles.active=bots --server.port=8092 \
  --spring.datasource.url=jdbc:postgresql://localhost:5433/exchange \
  --spring.datasource.username=exchange --spring.datasource.password=exchange \
  --spring.flyway.enabled=false --exchange.engine.enabled=false \
  --exchange.sim.base-url=http://localhost:8090
```

### 3-3. 오늘 겪은 함정 다섯

1. **마스터키를 두 노드가 공유해야 한다.** `EXCHANGE_AUTH_MASTER_KEY_BASE64` 를 주지 않으면
   각 프로세스가 서로 다른 임시 키를 쓴다. 봇이 발급한 시크릿을 거래소가 복호화하지 못해
   주문이 전건 인증 실패하고, 45초 뒤 `LeaderStallDetector` 가 정상인 거래소를 강등시킨다.
   복구는 재기동뿐이다. 오설정된 봇 노드가 멀쩡한 거래소를 죽인다.

2. **기동 중에 하네스 키를 발급하면 앱이 죽는다.** `POST /harness/v1/loadtest-keys` 를 봇
   프로비저닝이 끝나기 전에 부르면 GENESIS 채번이 충돌해 `botFleetLifecycle` 기동이 실패한다.
   로그에 `Started ExchangeApplication` 이 뜬 뒤 30초 더 두고 부른다.
   `readiness` 200 은 Tomcat 이 먼저 열려 조기 참이 되므로 기동 완료 판정에 쓸 수 없다.

3. **프로세스를 스레드 수로 가르면 반대로 짚는다.** 봇 노드가 428~461 개, 거래소 노드가
   59~62 개다. 거래소는 요청을 가상 스레드로 처리하므로 플랫폼 스레드가 늘지 않는다.
   포트로 식별한다(거래소 8090, 봇 8092). 이 착각으로 주행 하나를 버렸다.

4. **Docker 가 내려가 있으면 통합테스트 46건이 실패한다.** Testcontainers 환경 문제이지
   코드 결함이 아니다. Docker 를 올리고 다시 돌리면 436건 전건 통과한다.

5. **`Start-Process` 로 띄운 JVM 의 로그가 잘린다.** 버퍼가 안 비워져 사인이 안 보인다.
   원인을 볼 때는 `nohup ... > log 2>&1 &` 로 띄우거나 포그라운드로 돌린다.

### 3-4. 관측 스택 띄우기

printf '%s' 'DISCORD_웹훅_URL' > harness/alertmanager/secrets/discord_webhook_url

우선순위 순으로 셋이다.

1. Discord URL 을 넣고 실제 알림이 뜨는지 확인한다. 발표 영상에 들어갈 장면이다.
2. 상시면 컴포즈 3종에 관측 스택을 얹는다. 지금 배선이 격리 하네스 전용이라 실제 배포에서
