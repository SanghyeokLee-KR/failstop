## 3. 발표에 쓸 수치

### 3-1. 주문 천장은 99/s 다

봇 정지, 앱 2 vCPU / 1GB, DB 4 vCPU / 4GB.

| 요구 OPS | 실제 주문 | 지연 | 수용 거절 | 그 시점 미체결 |
|---|---|---|---|---|
| 100 | **98.2/s** | 54.1ms | 1.8/s | 21445 |
| 150 | **99.5/s** | 56.6ms | 50.5/s | 35252 |
| 200 | **97.1/s** | 59.4ms | 103.0/s | 48808 |

**부하를 두 배로 올려도 처리량이 평평하고 지연도 54~59ms 로 거의 같다. 초과분은 전부 거절이다.**
설계된 백프레셔가 그대로 보이는 그림이다.

**미체결이 2 만에서 4.9 만으로 늘어도 처리량이 떨어지지 않는다.** 종전에는 쌓일수록 천장이
내려갔다(ADR 0013 의 2.2 배 흔들림).

| 시점 | 상태 | 주문 |
|---|---|---|
| 09-04 | 봇 켬, 잔여 누적 | 60/s |
| 09-07 오전 | 미체결 8 만 | 75~86/s |
| **09-07 최종** | **미체결 2~4.9 만** | **99/s** |

천장을 정하는 것은 자원이 아니다. 앱 CPU 61~88%, DB CPU 72~79% 로 둘 다 여유가 있다.
**주문 수용 정원 6 칸과 단일 라이터 처리율이 정한다.** 6 칸 나누기 지연 55ms 가 초당 109 건이고
실측이 99 건이다.

## 4. 오늘 내린 판단 중 설명이 필요한 것

### 4-1. 커넥션을 늘려도 주문이 안 늘어난다

풀 16 을 48 로 올려도 주문이 86.5/s 에서 83.1/s 로 제자리였고 지연만 67ms 에서 227ms 로 늘었다.
그 구간의 커넥션 상태가 이유를 말한다. **48 개 중 2 개만 쓰고 20 개가 놀았다.** 밀려 있던 것은
시퀀서 큐 17 건이다. 병목이 커넥션이 아니라 단일 라이터라 커넥션을 늘리면 큐에 더 많이 들어갈
뿐이다.

**수용 정원 6 은 처리량을 깎는 것이 아니라 지연을 지킨다.** 같은 86/s 에 지연이 67ms 냐 227ms
냐의 차이다.

### 4-2. Redis 를 넣지 않았다

조회 전용 노드에 호가창을 전파하는 것이 후보였다. 정본이 공개 토픽을 Redis Pub/Sub 릴레이로
잡아 두었다(API 설계 §5-1).

**넣기 전에 쟀다.** 읽기 노드 하나가 초당 7684 건을 내면서 DB 에 쓰는 시간이 **초당 47ms** 다.
Redis 의 대가(새 의존성, 정본 M2 개정, 장애 경로 추가)가 그 이득보다 크다.

정본의 계획을 부정하는 것은 아니다. 그것은 WS 팬아웃용이고 이 측정이 다룬 REST 조회와 목적이
다르다. 다중 노드 WS 가 필요해질 때 그 축에서 다시 판단한다.

채번에 Redis 를 쓰는 방안도 검토했고 기각했다. `INCR` 로 받은 번호는 DB 롤백에서 회수되지
않아 gapless 가 깨지고, ADR 0002 가 같은 이유로 Redisson 리더선출을 이미 기각했다.

### 4-3. DB 스케일 업 시나리오에는 조건이 있다

DB 를 1 vCPU 로만 조였을 때는 스케일 업 효과가 나오지 않았다. DB CPU 98% 인데 주문 지연이
128ms 였고 4 vCPU 로 올려도 120ms 로 8ms 만 줄었다. 09-05·06 의 DB 작업 절감으로 **1 vCPU 로도
DB 가 병목이 아니게 됐기 때문**이다.

0.3 vCPU 로 조여야 그림이 나온다. 발표에서는 **저사양 DB 인스턴스를 가정했다고 밝혀야 한다.**

## 5. 오늘 겪은 함정

앞 문서의 함정 일곱은 `인수인계_20260904.md` 4 절에 있다. 새로 겪은 것만 적는다.

1. **시험이 설계를 고쳤다.** fencing 왕복을 합칠 때 검증 로직을 새 함수에 복사했더니
   `PromotionStandDownIntegrationTest` 의 split-brain 시험이 깨졌다. 그 시험은
   `assert_current_leader` 를 갈아끼워 거부를 주입하는데, 복사본은 그 주입을 비껴간다.
   위임으로 바꿔 규칙이 한 곳에 남게 했다. **복사본이었다면 라이브까지 갔다.**
2. **DB 가 인덱스로 하던 일을 자바 루프로 옮기면 느려진다.** 호가를 메모리에서 내는 첫 구현이
   단마다 주문을 순회했다. 가격 단은 17 개인데 미체결이 73073 건이라 배치마다 7 만 번 덧셈을
   단일 라이터가 했고, 천장이 98.6/s 에서 88.7/s 로 내려갔다. 증분 유지로 고쳤다.
3. **캐시는 만료 순간에 몰린다.** 1 초 TTL 인데 호가 쿼리가 초당 10.8 회 나갔다(이론 상한 2 회).
   동시 요청이 전부 부재를 보고 각자 DB 를 친다. 키별 채움 잠금으로 5.7 배 줄였다.
4. **부하 도구가 먼저 무너지면 서버 능력이 아니라 도구의 포기를 잰다.** k6 의
   `constant-arrival-rate` 는 느려지면 반복을 버린다. 1 노드 대조가 그것 때문에 오염됐다.
   용량을 잴 때는 고정 VU(폐쇄 루프)를 쓴다.
5. **총량만 보면 끊김을 못 본다.** WS 폭주에서 수신량이 대조군과 4% 차이라 무사해 보였는데,
   흐름이 끊긴 창을 세는 축을 따로 넣어야 판정이 섰다.
6. **`ALTER SYSTEM` 은 트랜잭션 블록 안에서 못 돈다.** `psql -c` 에 두 문장을 넣으면 묶인다.
   따로 보낸다.
7. **`pg_stat_statements` 의 `round()` 는 double 을 못 받는다.** `::numeric` 캐스팅이 필요하다.

## 7. 이어가기

### 7-1. 스택 세우기

```bash
docker network create exnet

docker run -d --name ex-pg --network exnet --cpus 4 --memory 4g -p 5433:5432 \
  -e POSTGRES_DB=exchange -e POSTGRES_USER=exchange -e POSTGRES_PASSWORD=exchange \
  postgres:17-alpine -c shared_preload_libraries=pg_stat_statements \
  -c pg_stat_statements.track=all -c shared_buffers=1GB -c max_connections=200
```

앱 이미지는 `bootJar` 산출물을 `eclipse-temurin:21-jre` 에 얹고 `JAVA_TOOL_OPTIONS` 로
`-XX:MaxRAMPercentage=75` 를 준다.

```bash
docker run -d --name ex-app --network exnet --cpus 2 --memory 1g -p 8080:8080 \
  -e EXCHANGE_AUTH_MASTER_KEY_BASE64="<두 노드 공유 키>" failstop-app:wslimit \
  --spring.profiles.active=dev \
  --spring.datasource.url=jdbc:postgresql://ex-pg:5432/exchange \
  --spring.datasource.username=exchange --spring.datasource.password=exchange \
  --exchange.harness.enabled=true \
  --exchange.order.rate-limit.capacity=1000000 --exchange.public.rate-limit.capacity=1000000
```

조회 전용 노드는 `--exchange.engine.enabled=false --spring.flyway.enabled=false` 를 더한다.

봇은 `--spring.profiles.active=bots` 에 `--exchange.sim.base-url=http://ex-app:8080` 이다.
**마스터키를 거래소와 같은 값으로 줘야 한다.** 안 주면 봇이 발급한 비밀을 거래소가 복호화하지
못해 주문이 전건 실패하고 멀쩡한 거래소가 강등된다.
