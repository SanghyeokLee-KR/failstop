# 15분 라이브 데모 대본

> 이 대본의 명령은 `$env:EXCHANGE_HOME` 를 쓴다. 시작 전에 한 번 지정한다.
> `$env:EXCHANGE_HOME = 'C:\dev\exchange'` (설정 근거는 실행_가이드.md 1-1 절)


대상: 고가용성 가상 암호화폐 거래소 캡스톤 발표.

핵심 판정.

- 체결 무결성: 자산별 원장 합 0, 저널 gap 0, 중복 주문·중복 체결 0.
- 자동 복구: 리더 kill 후 epoch 정확히 +1, 사람 개입 없이 체결 재개, RTO 30초 미만.
- 판정 원천: DB 원본 SQL 위반 행 0, Prometheus 시계열, k6 exit code.

## 0. 대본 사용 조건

### 0-1. 문서 성격

- 15분 대본: M4 배선 완료 후 사용하는 최종 목표 대본.
- 7~8분 대본: 현재 저장소에서 검증된 E4·E9·SQL만 사용하는 오늘 버전.
- 15분 대본의 시각과 순서: 확정 타임라인 그대로 고정.
- 대시보드: 관찰 보조 수단. 최종 판정은 DB 원본과 exit code.

### 0-2. 현재 검증된 범위

- E4 리더 kill: epoch+1 승격, 저널 재생, 체결 재개, 구 epoch stale append 0행.
- 불변식: C01~C23 SQL과 앱 검증 카탈로그. C16·C17 SQL은 구현됐지만 라이브 원천은 미배선.
- E9 멱등성: 커밋 응답 절단 뒤 중복 NEW 주문 0, 클라이언트 수렴.
- E8 앱 장애 격리: Chaos Monkey assault와 서킷브레이커 회귀 테스트.

### 0-5. 스택 기동

루트 `compose.yaml`이 검증된 카오스 토폴로지를 들이고(include) 웹·관리 평면·k6를 얹는다.
프로젝트명이 `exchange-chaos`로 같아 컨테이너명·포트·네트워크가 기존 실험 자산과 그대로 맞물린다.

사전 조건. `harness/app.jar`(bootJar 산출물), `web/out`(정적 export), `harness/.env.chaos`.
`harness/scripts/up.ps1`이 앞의 둘을 만들어 준다.

```powershell
Set-Location $env:EXCHANGE_HOME
docker compose --env-file harness/.env.chaos --profile full up -d --wait
```

프로파일은 셋이다. 기본(프로파일 없음)은 카오스 실험용 코어 7개로 e1~e9 스크립트가 쓰던
것과 같다. `full`은 여기에 웹·관리 평면·관측을 더한 발표용이다. `load`는 k6이고 상시 기동이
아니라 `run --rm`으로 한 번 돌린다. full에 넣으면 콜드 스타트가 부하 종료를 기다린다.

### 0-7. 카오스 소비기 기동

관리 API는 주입을 수행하지 않는다. 승인된 지시를 `chaos_commands`에 남기고, 아래 소비기가
그 행을 점유해 실제 `docker kill`·toxic 주입을 수행한 뒤 컨테이너 id를 증빙으로 되쓴다
(하네스 CICD §6-2). 발표 시작 전에 별도 터미널에 상주시킨다.

```powershell
Set-Location $env:EXCHANGE_HOME\harness
pwsh -File .\scripts\chaos-consumer.ps1
```

소비기를 띄우지 않으면 콘솔 버튼이 승인·감사만 남기고 컨테이너는 멀쩡히 산다. 그 상태는
`GET /admin/v1/chaos/runs`의 `exec_state`가 `PENDING`으로 보인다.

### 0-8. 발표 전 변수

```powershell
$env:DEMO_API = 'http://localhost:58080'
$env:ADMIN_API = 'https://localhost:8443'
$env:PG_CONTAINER = 'chaos-pg'
$env:DEMO_RUN_ID = "DEMO-$((Get-Date).ToString('yyyyMMdd-HHmmss'))"
# 운영자 인증서는 chaos-admin 컨테이너에 /pki로 마운트돼 있다(compose.yaml). 호스트 경로는
# 브라우저 인증서 임포트용으로만 남긴다.
$env:OP_CERT_DIR = '$env:EXCHANGE_HOME\server\config\admin-demo'
```

관리 API 호출은 `chaos-admin` 컨테이너 안에서 한다. Windows의 curl은 Schannel 백엔드라
`--cert-type P12`를 쓰지 못한다(실측: `schannel: disabled automatic use of client certificate`,
exit 35). PowerShell HttpClient도 같은 지점에서 핸드셰이크가 깨진다. 컨테이너 curl은 OpenSSL
빌드라 그대로 된다(실측 200). 브라우저 콘솔은 Windows 인증서 저장소를 쓰므로 영향받지 않는다.

관리 세션은 발표 시작 전에 발급한다. 인증서 CN이 운영자 신원의 권위다.

```powershell
$op01 = docker exec chaos-admin curl -sS -k --cert-type P12 --cert /pki/op-01.p12:changeit `
  -X POST "https://localhost:8443/admin/v1/session" | ConvertFrom-Json
$op02 = docker exec chaos-admin curl -sS -k --cert-type P12 --cert /pki/op-02.p12:changeit `
  -X POST "https://localhost:8443/admin/v1/session" | ConvertFrom-Json
```

## 1. 15분 본 대본

### 00:00~02:00 정상 상태

- `exchange_ledger_imbalance{asset}` 자산별 선.
- `invariant_checks` 최근 결과 표.
- 우측 하단 k6 터미널, steady 300 req/s 시작 로그.

#### 실행할 명령

터미널 A.

```powershell
Set-Location $env:EXCHANGE_HOME\harness\load
$env:K6_PROMETHEUS_RW_SERVER_URL = 'http://localhost:59090/api/v1/write'
$env:K6_WEB_DASHBOARD_EXPORT = 'artifacts\demo-report.html'

```

터미널 C, 발표 시작 시점의 DB 권위 상태를 짧게 확인한다.

```powershell
docker exec $env:PG_CONTAINER psql -U exchange -d exchange -P pager=off -c `
  "SELECT holder, epoch, lease_until > clock_timestamp() AS alive FROM leader_lease WHERE resource='matching-engine';"
```

#### 실제 발화 대사

“오늘 보여드릴 것은 기능 목록이 아니라 두 가지 실패 가능성입니다. 첫째, 주문이 몰리거나 서버가 죽어도 돈이 생기거나 사라지지 않는가. 둘째, 리더가 사라졌을 때 사람이 손대지 않아도 거래가 다시 시작되는가입니다.

지금 k6가 초당 300개 요청을 개방 루프로 넣고 있습니다. 왼쪽의 자산별 원장 합은 모든 자산에서 0입니다. 이 값은 잔고 화면을 더한 것이 아니라 append-only 복식부기 원장을 직접 집계한 값입니다. 한 자산이라도 0을 벗어나면 데모는 실패입니다.

오른쪽 DB 조회에서 현재 리더와 epoch를 확인할 수 있습니다. 리더십 권위는 Redis가 아니라 PostgreSQL의 `leader_lease` 한 행입니다. 정상 구간 2분 동안 이 기준선을 먼저 고정하겠습니다.”

#### 이 구간이 증명하는 명제

- 정상 부하에서 거래가 진행되고, 원장 불변식의 기준선이 0으로 유지됨.

### 02:00~04:30 폭주 10x

#### 화면에 띄울 것

- 대시보드 3, 부하·SLO.
- 요청률 300 -> 3,000 req/s.
- 429와 `Retry-After` 포함률.
- 시퀀서 큐 깊이.
- 수용 요청 p99.
- 작은 보조 패널로 대시보드 1의 원장 합 0 유지.

#### 실행할 명령

- k6 stage가 자동으로 램프업.
- spike 프리셋으로 시장 국면 전환.

```powershell
$spikeBody = @{ operator_id = 'op-02' } | ConvertTo-Json -Compress
docker exec chaos-admin curl -sS -k --cert-type P12 --cert /pki/op-02.p12:changeit `
  -H "Authorization: Bearer $($op02.token)" -H 'Content-Type: application/json' `
  -d $spikeBody -X POST "https://localhost:8443/admin/v1/sim/scenarios/spike/activate"
```

프리셋은 두 축을 함께 민다(API §6-A v2.31). 전역 목표 OPS 상한을 기저의 10배(60에서 600)로, 테이커 도착률(λ)도 10배로 올리고 목표 bias를 +0.6으로 고정한다. 하네스 §2-1 spike 행의 두 값과 같다. 봇 대수는 건드리지 않는다(동일 플릿). 상한만 올리면 수요가 그 아래여서 처리량이 안 오르고 수요만 올리면 상한이 막으므로 둘을 같이 올린다. 마켓메이커 호가 주기는 그대로라 호가가 먹히는 속도가 공급을 앞질러 스프레드가 벌어진다. k6 요청률 램프업은 별개 축이고, 두 축이 겹치는 구간이 E6 폭주다. 되돌릴 때는 같은 경로에 `steady`를 쓴다. 같은 프리셋을 두 번 눌러도 결과가 같으므로 시연 중 재실행이 안전하다.

#### 실제 발화 대사

“2분이 지나면서 요청률이 초당 300에서 3,000으로 올라갑니다. 이때 모든 요청을 억지로 받는 것이 목표가 아닙니다. 큐가 한계를 넘기 전에 일부 요청을 429로 거부하고, 클라이언트에 `Retry-After`를 돌려주는 것이 백프레셔입니다.

여기서 p99는 전체 요청이 아니라 수용된 요청만 계산합니다. 수용 요청 p99는 500밀리초 아래에 있고, 큐는 상승한 뒤 상한 안에서 안정돼야 합니다. 429가 늘어나는 것은 장애 은폐가 아니라 과부하를 명시적으로 거절한 결과입니다.

부하 패널이 움직이는 동안 원장 합 선은 그대로 0입니다. 처리량을 위해 회계 불변식을 완화하지 않았다는 점을 같이 보겠습니다.”

#### 이 구간이 증명하는 명제

- 10배 폭주에서 무제한 큐 적재 대신 429 백프레셔로 시스템을 보호하고, 수용 요청과 원장 무결성을 유지함.

### 04:30~05:30 승인 절차

#### 화면에 띄울 것

- 관리자 승인 화면.
- op-02 요청 의도.
- op-01 승인 발급 결과의 `approval_id`, 만료 시각.
- `admin_audit_log` 최근 행.
- 토큰 원문은 발표 화면에 노출하지 않음.

#### 실행할 명령

1. 실 리더를 확인한다.

```powershell
Set-Location $env:EXCHANGE_HOME\harness
. .\scripts\lib.ps1
$leader = Get-LeaderContainer
if (-not $leader) { throw '실 리더 판별 실패' }
"KILL_TARGET=$leader"
```

2. op-02가 토큰 없이 kill을 요청해 403을 확인한다. 이 호출은 실제 주입 전에 수행한다.

```powershell
$denyBody = @{ operator_id='op-02'; node=$leader; method='docker_kill'; expect_failover=$true } |
  ConvertTo-Json -Compress
docker exec chaos-admin curl -i -sS -k --cert-type P12 --cert /pki/op-02.p12:changeit `
  -H "Authorization: Bearer $($op02.token)" -H 'Content-Type: application/json' `
  -d $denyBody -X POST "https://localhost:8443/admin/v1/chaos/kill-node"
```

3. op-01이 op-02 요청에 바인딩된 승인 토큰을 발급한다.

```powershell
$issueBody = @{
  requester_operator_id = 'op-02'
  action = 'chaos.kill_node'
```

### 2-4. “단일 라이터면 확장은?”

#### 30초 답변

“단일 라이터는 전체 서비스가 한 스레드라는 뜻이 아닙니다. API·조회·웹소켓 노드는 수평 확장하고, 한 주문 순서가 필요한 매칭 파티션만 단일 라이터로 둡니다. 현재 캡스톤은 전 마켓 하나의 라이터로 결정론과 장애 복구를 먼저 증명합니다. 다음 확장 단위는 마켓 샤드입니다. 샤드마다 단일 라이터와 독립 저널을 두면 순서 보장은 유지하면서 병렬 처리할 수 있습니다. 현재는 큐 상한과 429로 용량 초과를 명시적으로 제어합니다.”

#### 그 자리에서 띄울 증거

- 패널: 대시보드 3 요청률, 수용 요청 p99, 429, 큐 깊이.
- SQL: `SELECT max(seq), count(*) FROM command_journal;`.
- 설명: 마켓별 샤딩은 후속 확장안이며 현재 구현으로 주장하지 않음.

### 2-5. “CAP에서 뭘 포기했나”

#### 30초 답변

“거래 쓰기 경로는 네트워크 분할에서 일관성을 택합니다. 구 리더가 DB 권위를 잃으면 쓰기를 계속 받지 않고 503 또는 429로 거부합니다. 새 리더가 epoch를 올린 뒤에만 쓰기가 재개됩니다. 따라서 분할 순간의 일부 가용성을 포기하고, 이중 체결과 이중 원장 기록을 막습니다. 클라이언트는 같은 `client_order_id`로 재시도해 기존 결과로 수렴합니다.”

#### 그 자리에서 띄울 증거

- E5 출력: `이중 쓰기(stale): 0`, epoch 정확히 +1.
- SQL: 워터마크 이후 구 epoch 저널 행 수 0.
- 패널: 대시보드 2 리더 교대, 대시보드 3 503·429 구간.

### 2-6. “그거 그냥 재시작 아닌가”

#### 30초 답변

“재시작만으로는 누가 새 리더인지, 메모리 오더북이 이전 상태와 같은지, 구 리더가 다시 쓰지 못하는지 설명할 수 없습니다. 여기서는 다른 프로세스가 epoch를 1 올려 권위를 얻고, 스냅샷과 저널 tail로 상태를 복원한 뒤 체결을 재개합니다. 복귀한 구 프로세스는 이전 epoch라 쓰기 0행입니다. 라이브 C17 배선 전에는 `matched=true`를 현장 증거로 주장하지 않고, 스냅샷 등가 통합테스트 결과만 제시합니다.”

#### 그 자리에서 띄울 증거

- SQL: `leader_lease` old/new epoch.
- SQL: `harness.failover_runs` RTO·RPO·verdict.
- SQL: `recovery_runs`의 `fp_replay`, `fp_live`, `matched`.
- 현재 축소판: `SnapshotEquivalenceIntegrationTest`, `SnapshotRecoveryIntegrationTest` 결과.

1. DB 권위 행 조회.

판정.

- `alive=true`.
- holder 빈 문자열 아님.
- epoch 발표 사전 기록값과 일치.

2. holder UUID를 노드 로그와 대조.

```powershell

```

판정.

- 결과가 `chaos-api-1` 또는 `chaos-api-2` 중 하나.

3. 두 노드 상태와 로그를 대조.

```powershell

```

4. kill 요청 target을 검출값으로 생성.

```powershell
$issueTarget = $leader
if (-not $issueTarget) { throw 'kill target 미확정' }
```

5. kill 직전 재확인.

```powershell
$leaderAgain = Get-LeaderContainer

```

승인 토큰은 action과 target에 바인딩되므로 리더가 바뀌면 기존 토큰을 사용하지 않는다.

## 6. 발표자가 지켜야 할 표현

- “대시보드가 정상이다” 대신 “DB 위반 쿼리가 0행이다” 사용.
- “무손실이다”는 C16 원천 행수가 0보다 클 때만 사용.
- “재생이 동일하다”는 `recovery_runs`가 존재하고 `matched=true`일 때만 사용.
- “RTO”와 내부 downtime을 구분.
- “10배 처리했다” 대신 “10배 도착률에서 수용 요청 SLO와 명시적 429를 유지했다” 사용.
- “HA가 완성됐다” 대신 “단일 PostgreSQL 장애 도메인 안에서 앱 리더 페일오버를 증명했다” 사용.
- 실패·SKIP을 PASS로 바꾸지 않음.
