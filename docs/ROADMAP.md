# 로드맵

고객사의 IT 인프라를 구축·운영·관리하는 엔지니어의 역할에서, 2026년 6월부터 약 3개월간 직접 개발한 가상 거래소의 AWS 운영 환경을 만든다. 가장 중요한 역량은 Linux 서버 운영이며, 계정·권한·서비스·로그·네트워크·디스크의 설정과 장애 진단을 먼저 갖춘다. 이를 바탕으로 관제, DB 복구, EC2 자동 확장, AI 운영 보고를 구현한다. 최종 발표는 2026-10-16이고 전체 프로젝트 제목은 미정이다.

발표 자료는 PPTX와 사전 녹화한 시연 영상, 이미지 캡처로 준비한다. 별도 제출 보고서나 날짜별 작업 인수인계 문서는 만들지 않는다. 진행 상태와 남은 작업은 이 파일에서 관리한다.

현재 채택한 전체 구조와 ADR의 대체 관계, AWS 착수 조건은 [0099 현재 구조와 AWS 배포 판단](reference/adr/0099-current-architecture.md)에 모았다. 구조나 검증 상태가 바뀌면 관련 원본과 0099를 함께 검토한다.

## 현재 상태

2026-09-18 기준이다. [ADR 0027](reference/adr/0027-msp-operations-and-autoscaling.md)의 운영 범위를 정본 `codex/docs-linux-operations`에서 구현하고 로컬 실행을 검증하고 있다. 당일의 조건·판정·원자료는 [09-18 운영 검증](measurements/20260918.md)에 모았다. M1~M3의 과거 측정과 이번 실행 근거를 구분한다. AWS 계정은 아직 제공되지 않았으며 실제 자원·권한·비용은 확인하지 않았다.

| 단계 | 상태 | 범위 |
|---|---|---|
| M1. 거래와 앱 복구 | 완료 | 주문 접수, 매칭, 정산, 실시간 화면, 봇, 리더 전환 |
| M2. 회원 | 완료 | 가입·로그인, 세션·API 키, 회원별 계정과 가상 자산 |
| M3. 게시판과 관리자 | 완료 | 글·댓글, 운영자 인증, 봇·장애 실험 제어, 모니터링 |
| M4. AWS 운영과 MSP 관제 | 진행 중 | Linux·네트워크·DB 운영, 관제, 자동 확장, Teams·AI 보고, 발표 자료 |

현재까지 문서에 기록된 부하·카오스 수치는 로컬 Docker 환경에서 얻었다. 클라우드 성능으로 인용하지 않는다. 사용자가 밝힌 지원금은 40만 원이며, 월 한도나 입금 확인으로 확대해석하지 않는다. AWS 인스턴스, 도메인 위임, 실제 잔액과 청구액은 이번 작업에서 조회하지 않았다.

교수님께 보고한 구성도와 기존 화면 15개는 [아키텍쳐 자료](../아키텍쳐/README.md)에 보존했다. 해당 안내에서 보고안과 현재 구현의 차이, 녹화·캡처할 장면을 확인할 수 있다. 로컬에서 준비한 뒤 AWS 검증·촬영을 집중해서 진행한다. 기존의 외부 상시 접속 전제가 있어, 발표 방식과 별개로 필요한 접속 유지 기간을 확인하고 종료 시점을 정해야 한다.

Docker 카오스는 로컬 개발 검증 이력으로 남긴다. 새로운 카오스 기능·관리 화면을 개발하거나 기존 실험 전부를 재실행하는 것이 M4의 목적은 아니다. 부하 도구·데이터 검사·관측 자산은 재사용하고, AWS에서는 운영자가 진단·복구할 실제 상황을 골라 검증한다. 운영 일일 보고는 새 제품 기능이며 작업 인수인계 문서를 다시 만드는 것이 아니다.

## 다음 작업의 시작점

먼저 [배포 안내](../deploy/README.md)의 역할별 설정과 실제 실행 근거를 확인한다. 아래 로컬 검증은 Ubuntu 26.04 WSL·x86_64와 Docker Desktop에서 수행했다. 기존 [ADR 0010](reference/adr/0010-onprem-to-aws-deployment.md)의 Rocky Linux 10·Graviton ARM64를 실제 검증한 결과가 아니다.

| 6. AWS·보고 준비 | Terraform validate·모의 계획 6건, 일일/장애 영속 보고와 09:00 KST timer. 역할별 Teams 카드·2쪽 PDF/HTML 자동 제공, 사용자 PDF 열기 확인, Gemini API·호출 상한 구현 | AWS plan/apply·증설/축소, 개선한 AI 지시의 실제 응답 재검증과 상시 활성화, 외부 관계자의 HTTPS 보고 접근 |

원본은 [배포 smoke](../artifacts/operations-20260918/deploy-smoke/checks.json), [DB 실습](../artifacts/operations-20260918/db-recovery-drill.json), [별도 백업 복원](../artifacts/operations-20260918/backup-restore-check.json), [Teams 보고 접수](../artifacts/operations-20260918/reporting-live-pipeline.json)에 남긴다. DB 실습은 쓰기를 멈추고 standby를 따라잡게 한 조건이며 급작스러운 장애의 무손실 보장이 아니다. 앱 정상화 시간 11.688초에는 사람의 판단 시간이 없다.

같은 날 [별도 프로젝트 재실험](../artifacts/operations-20260918/failstop-ops-repeat-5f5d0d824ec0.json)에서도 primary 정지 확인, standby 수동 승격, 앱 연결 전환, 새 standby 재편입과 백업 복원을 통과했다. 주문 ACK 2건과 체결 1건이 보존됐고 전환·복원 전후 명령 2건·이벤트 3건·원장 항목 22건·주문 2건이 일치했다. 세 시점의 불변식 각 30개에서 CRITICAL/HIGH 실패는 없었다. 격리 시작부터 앱 준비까지 9.688초이며 사람의 판단 시간은 제외했다. 이번 임시 컨테이너·볼륨은 정리하고 백업과 근거를 보존했으며, 기존 고객 실습 앱과 DB 복제·관측은 정상 상태를 유지했다. 반복 명령은 [DB 실습 안내](../deploy/lab/README.md)의 `drill --repeat`다.

Linux 백업 실행과 실제 복원은 통과했지만 WSL에서 Windows DB로 가는 직접 연결이 되지 않아 정기 백업 timer는 설치하지 않았다. 보고 timer는 설치했으며 Windows·WSL이 실행 중이어야 한다. Teams 해제 사건 보고는 한 번 재시도한 뒤 접수됐고, 최초 시도의 오류 종류와 채널의 실제 게시·중복 여부는 확인하지 못했다. 이후 전송 시도는 오류 종류를 보존한다.

사용자가 제공한 Google 키로 Gemini 3.1 Flash-Lite 인증과 실제 생성 1회를 확인했다. 첫 응답은 DB 연결 수에서 정상 여부를 단정하는 문제가 있어 지시를 보강했다. 추가 실측 시험은 내부 운영 자료의 Google 전송에 대한 자동 승인 심사에서 차단되어 사용자 동의를 기다린다. 현재 설치한 보고 서비스는 `facts-only`이며 Google을 호출하지 않는다. 보고는 2쪽 고정 양식에 결론·담당자 개입·역할별 조치와 완료 조건·실측 그래프·지표표를 바인딩한다. 담당자 개입은 최신 근거와 자료 공백으로 판정하며 AI 문장으로 위험을 낮추지 않는다. 백업 예약·복원 확인은 보호된 파일에서 선택적으로 받으며 없는 결과는 미확인으로 남긴다. [보고 원자료](../artifacts/operations-20260918/report-template/report.json)와 [양식 바인딩](../artifacts/operations-20260918/report-template/report-bindings.json)은 AI 원인 분석의 검증 결과가 아니다.

[최신 관측 확인](../artifacts/operations-20260918/observability-runtime.json)에서 C: 드라이브 여유는 약 15%다. 부족 경보를 유지하며 임의로 파일을 지우지 않았다. Windows 재부팅 뒤에는 [로컬 관측 bridge](../deploy/observability/README.md)를 다시 시작해야 한다. 보고 재설치와 Ubuntu 재시작 뒤 운영 SSH·수집 파일 권한·보고 기록·다음 일정을 [재설치 검사](../artifacts/operations-20260918/reporting-install-check.json)에서 확인했다.

이후 고객 관측 범위를 Spring과 고객 AWS 인프라로 한정했다. 로컬 고객 대상은 Spring·DB 2개·접속 검사이며 별도 Ubuntu 운영 실습·관측 도구·부하 봇은 고객 집계에서 제외한다. C드라이브 경고는 실습 Prometheus에 남기되 고객 장애로 전송하지 않는다. 기존 MSP 4개 화면과 보고 조회에 고객 역할 필터를 적용하고, AWS 서버 자료가 없으면 로컬 호스트 값으로 대신하지 않는다. [고객 범위 확인](../artifacts/operations-20260918/customer-scope/runtime-check.json)은 실제 PromQL 73개와 Grafana 반영을 확인한 로컬 결과이며 AWS 검증은 아니다.

로컬과 AWS의 [공통 관측 설정](../deploy/observability/README.md#로컬과-aws의-관측-경로를-맞춘다)을 추가하고 보고 조회·알림 묶음에 고객사와 환경을 함께 적용했다. AWS EC2 탐색은 지정 cluster만 등록하며 고객 Spring 목록에서 봇을 제외한다. 실제 등록된 로컬 standby를 중단해 `pg_up=0`과 Prometheus 경보를 확인한 뒤 재기동했다. 2026-09-18 14:17 KST의 장애 보고와 14:22 KST의 해제 보고가 각각 첫 시도에 Teams 웹훅에서 접수됐고, 사용자가 두 보고의 채널 표시를 확인했다. 복제 streaming·Spring readiness와 고객 대상 4개를 포함한 scrape 7개 정상 상태도 확인했다. [실행 근거](../artifacts/operations-20260918/prometheus-standby-delivery.json)에 사건 ID·전송 결과·사용자 확인을 보존했다. 이 검사는 replica 중단·복구이며 앞선 수동 승격 시험과 다르다. AWS 대상의 실제 수집은 아직 확인하지 않았다.

이어서 Teams·PDF와 관제 화면을 개편한 뒤 [Standby 관측·보고 재검증](../artifacts/operations-20260918/prometheus-standby-pdf-delivery.json)을 통과했다. 수집기가 응답하지만 DB 접속이 실패하는 `DatabaseConnectionFailed`와 수집기 장애를 분리했다. 14:54 KST 장애 및 14:59 KST 해제 보고는 각각 첫 시도에 접수됐으며, 사용자가 두 버튼 표시와 PDF 열기를 확인했다. Primary 중단 없이 replica 복제와 Spring 정상 상태로 복귀했다. 2쪽 PDF는 저장한 근거로 자동 생성하며 파일 링크의 서명·만료와 변조 거절을 확인했다. 현재 다운로드 주소는 이 PC의 루프백이며 Teams 파일 탭 첨부나 외부 관계자 접근을 뜻하지 않는다. PDF 오류에도 카드와 다음 보고를 계속 처리하고 별도 실패 지표를 남긴다.

관제 화면은 고객 역할과 두 시나리오 중심으로 정리했다. 명사형 표시, 미수집 회색, 역할별 DB 상태, 요청·응답 지연·복제 추이와 장애 구간을 브라우저에서 확인하고 카드 높이·헤더 잘림을 수정했다. [읽기 요청 확인](../artifacts/operations-20260918/monitoring-http-smoke.json)의 120건은 모두 HTTP 200이며 성능 한계나 AWS 자동 확장의 검증 결과는 아니다. AWS 전용 CloudWatch 데이터 소스와 ALB·ASG·EBS 패널, Terraform 식별자 출력·관측 bot의 IMDSv2 설정을 준비했다. 실제 AWS 조회와 비용은 미확인이다.

계정이 준비되면 기존 역할·iam:PassRole·SSM·리전과 AMI·ARM64 digest·도메인/ACM을 확인한다. 실제 규격·가동 기간·ASG 상한·보존 데이터로 40만 원 예산을 계산한 뒤 비공개 환경부터 배포한다. IAM 제약을 우회하거나 기존 로컬 성능을 AWS 결과로 사용하지 않는다.

후속 DB 관제 검토에서 조회·쓰기 처리량, 세션 대기·차단 관계, WAL 명칭과 진단 순서에 따른 배치를 보강 과제로 확인했다. 기존 화면·쿼리 검사를 통과했어도 관제 설계가 완성된 상태는 아니다. 작은 실습 DB에서 기존 IP 요청 제한을 유지한 조회 부하 시험과 거래소 웹 기동을 [당일 측정](measurements/20260918.md)에 기록했다. 약 18 req/s의 혼합 조회는 거절이 없었고 이후 단계는 IP 정책에 의해 거절됐다. 실제 데이터 규모·복수 클라이언트의 처리 한계와 AWS 확장은 별도 검증 대상이다.

후속 구현에서는 기존 디자인을 유지하고 DB 요약·SQL/세션·복제/복구로 진단 정보를 나눴다. 로컬 primary와 standby에 `pg_stat_statements`를 활성화하고 전용 감시 계정의 SQL 집계, 표준 WAL 생성량, 실제 차단 세션과 대기 시간을 연결했다. [활성화 근거](../artifacts/operations-20260918/grafana-db/sql-statistics-activation.json)에서 두 DB 역할과 주문·체결·원장·명령 행 수 보존을 확인했으며 격리된 DB/exporter의 12개 원천 지표 시나리오를 통과했다. HTTP 429 경로 관측 보강을 포함한 서버 build와 app 테스트 624개를 통과했다. 기존 요청 제한을 유지한 1,800건의 GET에서 899건 성공·901건 제한을 확인하고 실제 Prometheus의 경로 라벨과 SQL 수집을 대조했다. 여섯 화면의 1440×900·1920×1080 다크/라이트 조합 24개와 기능 검사 12개를 통과했다. Canvas 상태 12개·미수집 패널 52개는 브라우저 표본으로 검증했으며 실제 서비스 중단이나 Teams 추가 전송은 없었다. 실제 패널 질의 124개 중 104개에 유효 표본이 있었고 AWS·고객 호스트·백업 미등록은 그대로 표시했다. 앞선 58점 평가와 부하 결과는 당시 상태의 기록으로 보존한다.

## 공통 완료 조건

- 봇 부하와 10배 스파이크 중 자산별 원장 합이 0이고 주문 중복·유실이 없어야 한다.
- 앱 리더 장애 후 사람 개입 없이 거래를 재개해야 한다. 복구 시간 목표는 30초 이내다.
- 해당 변경의 빌드, 테스트, CI 검사를 통과해야 한다.

실험 번호와 판정 조건은 [하네스 검증 설계](reference/contracts/하네스_검증설계.md)를 따른다. 앱 리더 전환과 PostgreSQL 승격은 다르다. DB 승격은 수동이며 비동기 복제에서의 기록 유실 가능성이 있다.

## M1. 거래와 앱 복구

명령을 DB에 기록한 뒤 마켓별 엔진에서 매칭하고, 이벤트·원장·잔고를 함께 정산한다. 웹은 HTTP/STOMP로 연결한다. 자세한 흐름과 소스 위치는 [코드 지도](reference/architecture/프로젝트_코드지도.md)에 있다.

2026-09-13에는 V41 적용 코드(`2a818b6`)에서 E1·E2·E4·E5·E6·E7을 통과했다. 페일오버 실험의 복구 시간은 5.116~10.226초였다. E9의 이전 결과는 판정기 수정 전이라 이 완료 근거에 포함하지 않는다.

E1에서 발견한 리스 갱신 잠금 문제는 [ADR 0026](reference/adr/0026-leader-lease-key-share-lock.md)과 [재현 기록](../harness/evidence/e1-lease-starvation-20260913/)에 있다. 회차별 판정은 [chaos-runs/](../harness/evidence/chaos-runs/)의 09-13 결과를 확인한다.

## M2. 회원

가입·로그인, 세션과 API 키 발급, 회원별 자산·거래 내역을 구현했다. 실제 금융 자격증명이나 실명 정보는 받지 않는다. 회원과 봇의 계정·권한을 구분한다.

완료 조건은 여러 회원이 봇과 동시에 거래해도 위 공통 조건을 만족하는 것이다. 기능 범위는 [회원 설계](reference/product/회원_설계.md)에 있다.

## M3. 게시판과 관리자

종목별 게시판과 댓글, 공지·문의, 관리자 기능을 구현했다. 관리자는 별도 인증을 거쳐 봇과 장애 실험을 제어하고 상태를 확인한다.

게시판이나 관리자 요청이 거래 처리에 불필요한 의존성을 추가하지 않아야 한다. 해당 기능에 부하나 장애가 생겨도 거래 조건을 유지하는 것이 완료 기준이다. [게시판 설계](reference/product/게시판_설계.md)와 [관리자 설계](reference/product/관리자_설계.md)를 따른다.

게시판 설계의 별도 DB·프로세스 분리와 현재 앱 구성에는 차이가 있다. 위의 기능 완료 기록과 별개로, 이 물리 격리 요구가 현재도 필요한지와 실제 검증 범위를 대조해야 한다.

## M4. AWS 운영과 MSP 관제

관제 화면에서 문제를 보고 원인을 좁힌 뒤 조치하고 보고하는 흐름을 완성한다. 거래 기능의 추가 개발보다 Linux·네트워크·DB 운영과 그 근거를 우선한다. 다만 거래 정합성이나 공개 전 안전성 문제를 방치한다는 뜻은 아니다. AWS 서비스와 기존 역할의 실제 사용 권한은 배포 전에 확인한다. 설정과 제약은 [배포 안내](../deploy/README.md)에 있다.

남은 작업은 다음과 같다.

1. AWS의 Linux 노드·네트워크·접근 경로를 구성한다. DB 노드 간 연결, 연결 수, 계정·권한, 스키마·이미지 적용 순서를 맞추고 생성·재배포·철거 절차를 재현할 수 있게 한다.
2. 기존 Grafana MSP 화면과 Prometheus를 AWS에 연결한다. 호스트의 파일시스템·inode·디스크 I/O·네트워크·서비스 상태를 추가한다. 복제 지표 미수집을 정상 0으로 표시하는 문제를 고치고 Microsoft Teams 기본 알림의 발화·해제를 확인한다.
3. Linux 서비스, 디스크, 네트워크와 DB 장애를 관측에서 조치까지 연결한다. DB는 옛 primary 격리·수동 승격·앱 연결 전환·재편입을 여러 호스트에서 연습하고 백업도 실제로 복원한다. 자동 DB 전환 여부는 별도 설계 판단으로 남아 있다.
4. 분산 가능한 REST 조회를 ALB·EC2 ASG로 확장한다. 주문·취소·WebSocket과 재동기화용 조회의 경로를 먼저 구분한다. 부하 증가→EC2 증가→정상 등록→지연·오류 변화→부하 감소 후 축소를 확인한다. 단일 매칭 엔진이나 DB를 ASG로 무작정 늘리지 않는다.
5. 구현한 보고 서비스를 AWS 근거와 연결한다. 일일 시각은 사용자 선택으로 09:00 Asia/Seoul이다. Google 전송 동의 후 Gemini 3.1 Flash-Lite의 보강한 지시로 실측 응답을 다시 검토하고 활성화한다. 기본 상한은 분당 4회·하루 50회·달력월 1,000회다. Teams HTTP 접수와 채널 게시를 대조하고 실제 AI 실패·자료 부족·중복·재전송을 운영 환경에서도 확인한다.
6. 위 운영 과정의 원본 영상·캡처·판정 자료를 연결해 PPTX를 만든다. 로컬과 AWS 장면을 구분하고, 재촬영과 접속 유지 기간을 확인한 뒤 보존 데이터와 철거 자원을 정한다.

비공개 시험 환경 준비와 외부 공개는 구분한다. 공개 전에 모호한 주문 커밋 후 멱등 키 삭제·새 키 재시도 경로를 재현하고 처리 계약을 고쳐 검증한다. 신뢰 프록시와 관리 접근 통제도 확인한다. 현재 코드에서 확인한 위험과 단계별 선행 조건은 [0099의 AWS 준비 순서](reference/adr/0099-current-architecture.md)에 있다.

M4는 외부 서비스 접속, 근거가 있는 관제·Linux·네트워크 진단, ASG 증설·축소, DB 복구·백업 복원, Teams 기본 알림과 AI 일일·장애 보고를 실제로 확인해야 완료다. 자료 수집 실패를 정상으로 표시하지 않고 실제 조치 전후와 검증 범위를 남긴다. 기존 거래 무결성과 앱 리더 복구 목표는 유지하지만 DB 복구를 자동·무손실이라고 확대하지 않는다. [M4 하드닝 설계](reference/architecture/M4_하드닝설계.md)는 이전 세부 점검 자료이며 현재 범위는 이 로드맵과 ADR 0027을 따른다.

화면 구현 요청에 따라 먼저 [별도 관제 콘솔](../deploy/console/README.md)을 구현하고 Docker에서 실행했다. 서비스·Spring·AWS·DB 화면과 고객 현황·알림·이벤트·보고·설정·관리 메뉴 12개, 다크·라이트 전환을 제공한다. [실제 연결 검사](../artifacts/operations-20260918/console/runtime-check.json)에서 고객 대상 4개, 지표 조회 40개, 저장 보고 6건과 PDF·HTML 다운로드를 확인했다. [브라우저 검사](../artifacts/operations-20260918/console/browser-check.json)는 화면 배치·조회 기간·서비스 범위·검색·확대·설정 저장과 장애 표시를 검증한다. 장애 표시 시험은 브라우저 응답 표본이며 추가 DB 중단을 뜻하지 않는다. 이 구현은 포트 53002의 비교·확장용 이력으로 보존한다.

후속 확정 요청에 따라 기존 Grafana를 기본 관제로 적용했다. 포트 53001의 [MSP 네 화면](../deploy/observability/README.md#grafana-기본-관제-화면)에 Canvas 서비스 경로·DB 복제, 실측 시계열·표와 명사형 상태를 구성했다. 한국어·서울 시간대·홈·네 즐겨찾기를 적용하고 기존 Alertmanager를 기본 경고 메뉴에 연결했다. [화면 검사](../artifacts/operations-20260918/grafana/browser-check.json)에서 1440×900·1920×1080의 다크·라이트 16개 화면과 테마 링크를, [기능 검사](../artifacts/operations-20260918/grafana/interactions-check.json)에서 사이드바·기간·화면 이동·경보 연결과 장애·미수집 표시를 확인했다. 주요 패널은 한 화면에 배치하고 긴 표는 내부 스크롤을 사용한다. DB 복수 Primary와 역할 일부 미확인을 정상으로 판정하지 않는다. Grafana 자원 한도를 보강했으며 실제 DB 중단이나 Teams 추가 전송 없이 화면 상태를 검증했다.

현재 고객의 CloudWatch·호스트 자료가 없으면 미수집으로 표시한다. 실제 AWS 연결, 미등록 로그·트레이스 수집, 사설 HTTPS 배포는 별도 검증으로 남는다. 선택적인 RAID 실습, 거래 부가 기능, 과거 카오스 전수 재실행은 뒤로 두며 Linux·네트워크 운영과 관제 신뢰성·AWS 자동 확장·DB 복구·Teams 보고의 검증 범위는 유지한다.

## 최근 변경에서 이어갈 것

[ADR 0022](reference/adr/0022-market-partitioned-command-journal.md)의 마켓별 주문 접수·채번 변경은 0~9단계 구현이 09-15까지 main에 병합됐다. 결과는 [09-14 측정](measurements/20260914.md)과 [09-15 측정](measurements/20260915.md)에 있다.

6단계 채번 전환과 9단계 이벤트 순번 확대는 로컬 시험 DB에 적용했다. 클라우드 DB 적용은 ADR 0022 7절의 사전 확인을 거쳐 별도로 판단한다. 8단계 `commit_delay` 실험은 조건이 충족되지 않아 `NOT RUN`이다.

2단계 후속 정리로 전역 재생 진입점 제거, 인자 없는 `lastAppliedSeq()`의 이름 변경, 순번 축 검사가 남아 있다. 구체적인 범위는 해당 ADR을 따른다.
