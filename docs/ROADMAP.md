# 로드맵

2026-09-24 트리거 함수 권한 회수: 소유자 권한 트리거 함수 넷(`create_balance_for_account`, `register_trade_seq`, `register_event_emission`, `seed_market_journal_counters`)에 PUBLIC 기본 실행 권한이 남아 있었다. 그래서 조회 로그인은 레지스트리·카운터 표에, 앱·봇 로그인은 INSERT 권한이 없는 레지스트리 표에 자기 임시 표 트리거로 행을 쓸 수 있었다. 새 마이그레이션 V47.1(`V47_1__revoke_trigger_function_public_execute.sql`)이 이 권한을 회수한다. 트리거 발화는 실행 권한을 보지 않으므로 계정 생성, 체결·이벤트 적재, 마켓 생성은 그대로다. 번호 47.1과 DB 설계 v2.51.1은 마켓별 리더 브랜치의 V48 이후, 문서 v2.52~v2.54와 겹치지 않게 사용자가 정했다. 확인한 범위는 `MigrationSmokeTest`의 새 시험(두 로그인의 실행 권한 거짓, 임시 표 `CREATE TRIGGER`의 42501, 앱 로그인 쓰기의 트리거 발화)과 V47_1을 뺀 대조 실행의 실패, [폐기용 컨테이너 기록](../harness/evidence/revoke-trigger-fn-20260924/probe.log), ASCII 정션에서 돌린 서버 전체 build다. 별도 검토 지적을 반영한 마지막 build는 8분 3초 만에 통과했다. app 시험 669건은 새로 실행했고 engine 67건은 바뀌지 않아 이전 실행 결과를 재사용했으며 실패·건너뜀이 없다. 학교 DB에는 적용하지 않았다. 학교 앱 env 템플릿은 Flyway를 끄고 소유자는 NOLOGIN이라, 앱 기동 전에 소유자가 `MigrateDatabase`로 적용하는 단계를 AWS 절차에 넣었다. 실제 서버 env는 확인하지 않았다([절차](reports/AWS_작업.md#주문-v47을-포함한-jar-배포)). 별도 검토 판정은 PASS WITH FOLLOW-UP이다. 남은 후속은 둘이다. 첫째, 이 변경 전부터 있던 결함으로, 소유자 권한 함수가 `SET search_path = public`만 두고 `pg_temp`를 명시하지 않았다. 그래서 앱·봇 로그인이 같은 이름의 임시 표로 실제 표를 가릴 수 있다. V47.1을 올린 폐기용 DB에서 임시 `trade_seq_registry`로 가린 뒤 같은 체결 id 두 건이 모두 커밋되고 실제 레지스트리는 0행이었다([기록](../harness/evidence/revoke-trigger-fn-20260924/search-path-probe.log)). 원장 게시 함수 경로는 시험하지 않았다. 모든 소유자 권한 함수에 `public, pg_temp`를 주는 새 마이그레이션이 필요하고 번호는 사용자와 정한다. 둘째, 배포 스모크 시험(`deploy/tests/smoke_deployment.py`)은 V47부터 맞지 않던 47개 고정 검사를 저장소 마이그레이션 파일의 버전 목록과 `flyway_schema_history`의 성공 버전 목록을 대조하는 검사로 바꿨다. 47.1 같은 소수 버전도 문자열로 비교한다. Docker 스택을 띄우는 스모크 전체는 아직 실행하지 않았다.

2026-09-21 앱 무응답 복구: 학교 app-1의 공개 `/api/*`가 30초 뒤 504를 반환했다. 프로세스는 살아 있었고 메모리·디스크·DB 연결과 CPU 크레딧(steal 0)은 모두 정상이었다. 8분 간격 스레드 덤프 두 번이 같은 세 지점에서 `Thread.yield` 루프에 갇혀 있었고, HikariCP가 반납한 연결을 가상 스레드 대기자에게 인계하지 못해 생긴 라이브락이었다. 컨텍스트 스위치는 초당 459,033~573,169회, 시스템 시간은 57~64%였다. `SPRING_THREADS_VIRTUAL_ENABLED=false`를 적용하고 재시작해 12.7초 만에 기동했다. 엔진 복구는 마켓별 스냅샷 채택 후 83건을 재생했고 리더는 epoch=6으로 승격했다. 조치 후 컨텍스트 스위치 초당 78~1,227회, 시스템 시간 1~2%, 양보 프레임 0건, 공개 API 200/33ms와 봇 체결 재개를 확인했다. 저장소 기본값도 [ADR 0033](reference/adr/0033-no-virtual-threads-for-request-handling.md)으로 맞췄다. 원인 경로를 막은 것이며 인계 실패 자체를 고치거나 장애를 재현해 확정한 것은 아니다. Java 21·로그인 불가 exchange 계정과 경로별 권한을 준비한 뒤, 비공개 S3에서 기존 Role로 JAR을 받아 SHA-256을 대조했다. 별도 Primary에 전용 소유자 계정으로 V0~V46 총 47개 마이그레이션을 적용·검증하고 소유자 로그인을 잠갔다. 앱은 제한된 exchange_app 계정으로 TLS 1.3 연결하며 systemd로 기동한다. 재시작 후 readiness·조회 헬스 UP, API 응답, root 0600 비밀 파일을 확인했다. 8080·8081은 루프백만 listen한다. 이후 Nginx를 통해 사용자 PC에 HTTP 80 조회 화면을 제공했다. 최초 배포에서는 종목·거래 데이터가 비어 있었다. 이후 종목 기본값을 등록하고 HTTPS 연결을 확인했다. 이후 시장 봇 거래와 수동 DB 복구를 검증했으며 실제 회원 주문과 부하 검증은 남아 있다. 앱 호스트에는 DB 서버·중앙 관측을 설치하지 않았다.

## 다음 작업의 시작점

2026-09-26 main 병합 인계다. 병렬로 진행한 네 브랜치를 main에 병합했다. 순서는 마켓별 리더(`claude/per-market-leader`, S2~S7, W7 재판정과 app-3 조회 분산 확인까지) → Patroni DB 자동 전환(`claude/patroni`) → 관제센터(`claude/msp-control`, `claude/admin-design` 포함) → v6 구성도(`claude/arch-v6`)다. 계약 문서의 번호 충돌은 먼저 병합한 쪽을 기준으로 풀었다. Patroni가 따로 매긴 API 설계 §2-5-d, DB 설계 §5.4-d, v2.57은 §2-5-e, §5.4-f, v2.60으로 옮겼고 관리자 설계 v1.6은 v1.21로 옮겼다(Patroni 브랜치에서 더한 줄만 기계적으로 바꿈). main의 V47.1과 마켓별 리더의 V48~V55, 관제센터의 V70~V73이 한 트리에서 처음 함께 돌았고 새 마이그레이션은 더하지 않았다. 쓰기 게이트 필터는 바디 상한(4)과 소유권 선검사(5)보다 앞인 order 3으로 옮겼다. 상황별 대본 화면은 관제센터의 삭제를 따랐고, P3 리스 표시는 관제센터 거래 요약 띠로, Patroni의 DB 관찰 규칙은 관리자 설계의 데이터베이스 화면 설명으로 옮겼다. 대본의 P3 리더 멈춤 판정은 옮길 화면이 없어 없어졌다. 병합 단계마다 서버 전체 빌드, 웹 시험·빌드(관제센터 병합 뒤 `check:tokens` 포함), promtool 규칙 시험, 문서 검사 4종을 돌려 통과했다. `check:browser`는 이 PC에 Playwright 브라우저가 없어 돌리지 못했다.

병합을 맡은 AI가 고른 것은 다음과 같고 사용자 확인 대상이다. 쓰기 게이트를 소유권 선검사 앞에 둬 DB에 닿지 못할 때의 `503`이 이 노드가 소유하지 않는 마켓의 쓰기도 노드 층 수요로 센다. by-client 재조회에는 접수 전 읽기의 한 번 더 읽기를 쓰지 않는다. `423`으로 끝난 로컬 취소는 일괄 취소의 로컬 제출 수에 넣지 않는다. 파티션 밖 취소 인계의 작업자 취소와 행 넣기에는 세대 재확인을 넣지 않아 거래 일시 중단 중에는 커밋 대기에 막힌다. 관제 시뮬레이터의 리스는 파티션 두 행으로 낸다.

S4b에서 AI가 정해 사용자 확인이 필요한 것은 [S4b 설계](reference/architecture/마켓분할_리더_S4b_설계.md) 10절의 여덟 항목 가운데 첫째(DB 연결 장애 `503`, 2026-09-25 사용자 확정)를 뺀 일곱이다. 판정이 된 연결 장애의 `429`·`409`, 컨트롤러 `503`의 재전송 안전 처리기 한정, 배치·일괄 취소의 조기 종료, 판정 없는 재생의 기록 규칙, 응답을 쓸 수 없는 요청의 렌더, 하네스 판정 규칙, 정산 재시도 한도 8회·15초(라이터가 치명 전에 멈출 수 있는 시간이 약 17~18초로 는다)다. 첫 주행의 DB 흔들림에서 리더 라이터가 쓰던 연결이 끊기면 치명과 재승격까지 약 7~9초 쓰기가 `502`였던 비용은 S5가 바꾸지 않았다. 줄이는 두 길(커밋 여부를 모르는 라이터 쓰기를 다시 읽어 판정한 뒤에만 치명으로 올리기, 파티션 치명 강등 때 리스를 DB에서 반납하기)은 S4의 안전 규칙을 바꾸므로 사용자 결정이 먼저다([S5 설계](reference/architecture/마켓분할_리더_S5_설계.md) 4-6). S4에서 AI가 정해 사용자 확인이 필요한 것은 [S4 설계](reference/architecture/마켓분할_리더_S4_설계.md) 10절의 아홉 항목(접수 경합의 `429`·`409`, 비접수 55P03 `500` 유지, 재구성 뒤 재승격과 기간 결속, 차단기 10분 3회, 획득 전용 풀 없음, 접수 값 2초·1초, 좀비 판정 수요의 경합 제외, 종료 조건의 해석, actuator 쓰기 loopback 한정), 12-1의 열세 항목, 하네스 절차 변경(X6b 기준, LB 로그 저장, 참조 이미지 태그 `s3ref`·`s4ref`·`s4r1ref`, X6d 완료율 기록, X8 로그 저장)이다. S3 때부터 남은 확인 항목은 다음과 같다. 결정 5를 이 로컬 판정으로 확정할지(재주행의 P2 두 칸이 95.0·140.0/s로 벌어졌고 주행 동안 호스트에서 다른 프로그램이 돌았다), E5·E7 사후 권위 run을 드레인 뒤로 옮긴 판정 절차 변경과 E5 첫 회 FAIL을 절차 결함으로 보는 해석을 받아들일지, 그리고 S3에서 AI가 정한 방침(V51·V52 추가, 회원 폐쇄 409의 정지 마켓 포함, 하네스 C29·C31의 N/A 판정, V49를 S7 전환의 선행 조건으로 두기, 공용 러너의 보존 스택 가드)이다. 결정 5를 확정하지 않으면 S5 전에 다른 부하가 없는 환경에서 다시 재고, FAIL이면 2단계 예약안을 검토한다. V52가 고친 리스 획득 결함은 main과 학교 서버 코드에도 있으므로, app-2를 만들기 전에 main에서 새 번호 마이그레이션으로 따로 고칠지 브랜치 병합으로 해결할지 정한다([S3 설계](reference/architecture/마켓분할_리더_S3_설계.md) 10절, 12-3, 12-6).

2026-09-25 DB 자동 전환(Patroni) 설계: 사용자는 2026-09-24~25 DB 자동 전환을 Patroni로 하기로 정했다. DB는 두 대를 유지하고, etcd 세 표를 db-1·db-2·bot-1에 두며, 앱은 HAProxy로 현재 Primary에 붙는다. 유실 0을 앞에 두어 엄격 동기 복제를 쓰고, 동기 Standby가 없으면 쓰기를 멈추고 거래 화면을 '거래 일시 중단'으로 바꾼다. AI는 DB 승격·페일오버를 실행하지 않는다. 결정은 [ADR 0036](reference/adr/0036-patroni-strict-sync-db-failover.md)이고 0024·0025를 적용 환경부터 대체한다. 이 PC의 worktree `C:\dev\exchange-patroni`, 브랜치 `claude/patroni`(기준 `9a6d2474`, 마켓별 리더 S4b)에서 설계와 계약을 코드보다 먼저 썼다([Patroni 설계](reference/architecture/DB_자동전환_Patroni_설계.md), DB 설계 v2.60 §5.4-f·§7, API 설계 v2.60 §2-5-e·§4-A-7, 하네스 검증설계 E-P1~E-P9). 설계 전에 폐기용 PostgreSQL 17.10 두 노드로 커밋 대기 동작을 확인했다. 동기 대기는 `statement_timeout`으로 끝나지 않았고, 취소 요청은 복제되지 않은 로컬 커밋을 성공으로 돌려줬으며, `pg_logical_emit_message` 탐지 커밋은 일반 역할로 동기 대기를 탔다([사전 확인](../harness/evidence/patroni-sync-probe-20260925/README.md)). 같은 날 설계 검토 지적 13건을 모두 받아들여 설계와 계약을 고쳤다(설계 14절). 검토 뒤 같은 폐기용 구성에서 더 확인한 것은 셋이다. Patroni가 동기 Standby를 잃었을 때 거는 `'*'`는 멤버가 아닌 복제 스트림(`pg_receivewal`, 임시 슬롯의 `pg_basebackup`)을 동기 대기 서버로 받아 한 사본만으로 커밋을 확인했고, 베이스백업은 시작하자마자 그때까지 기다리던 커밋을 모두 풀었다. `--no-slot` 스트림은 그러지 않았다. 커밋 대기 중에 백엔드 하나가 죽어 postmaster가 크래시 재시작을 하면 기다리던 행이 복제 없이 보였다. 경보 식 둘은 promtool에서 구문 오류이거나 발화하지 않았다. 그래서 베이스백업과 백업 도구를 `--no-slot`으로 하고, 거래 중단은 DB 쪽 확인(`'*'`나 `SyncRep` 대기)이 있을 때만 판정하며, 리스 획득은 쓰기를 받는 동안에만 하고, `423`은 '이 시도는 쓰지 않음'으로 좁혀 새 키 재발급을 금지하고, 쓰기 게이트를 수용 제한 앞으로 옮겼다. DB 호스트를 영구히 잃었을 때의 사람 절차를 설계 9-5에 두고, 경보부터 거래 재개까지 60분 이내를 AI 제안 목표로 적었다(사용자 확인 필요).

2026-09-25 Patroni 코드 단계와 첫 E-P 회차: 같은 브랜치에 코드와 로컬 실험 스택을 만들었다. 앱에는 쓰기 가능 탐지기(탐지 연결과 확인 연결), 쓰기 게이트(`423`·`503`), 공개 상태 API, 리스 갱신의 로컬 커밋과 획득 규칙, 세대 재확인과 확정 응답 보류, 재개 때 따라잡기가 있고, 웹에는 거래 일시 중단 배너와 버튼 차단, 봇·k6에는 `423` 처리가 있다. 하네스에는 PostgreSQL 17.11·Patroni 4.1.5·etcd v3.5.34·HAProxy 3.0.27 실험 스택(`harness/patroni/`), 실행기(`harness/scripts/ep-*.ps1`), DB 수준 ACK 기록기와 판정 도구가 있다. Docker 실험은 E-P1(두 회차), E-P2a, E-P3b, E-P4b, E-P7(두 회차)을 돌렸다. E-P4b(etcd 과반 상실 동안 `failsafe_mode`로 Primary를 지키고 쓰기가 멈추지 않음) 한 회차만 PASS다. E-P2a, E-P1 둘째, E-P3b, E-P7 둘째는 시간 축이 아닌 축(DB 수준 ACK 유실 0, C16 0, 사후 권위 run 위반 0, 구 epoch 쓰기 0, 앱 epoch 축(전환 실험은 정확히 1 증가, E-P2a는 불변) 등)이 모두 PASS였지만 같은 PC의 다른 작업(Gradle 프로세스) 때문에 시간 축을 판정에서 뺀 INCONCLUSIVE다. E-P2a의 중단 탐지는 6.43초로 상한 5초를 넘었는데 `docker stop`의 정상 종료 동안 Standby가 복제를 이어 가 커밋이 6.53초에 멈춘 탓이다. E-P1 첫 회차는 실행기 psql이 매달려 유지 시간이 어긋난 규약 이탈이고, E-P7 첫 회차의 FAIL은 실행기의 계수 파싱 결함에서 났다. 회차 기록은 [실험 스택 README](../harness/patroni/README.md)다. 이 첫 회차들 때는 E-P1b, E-P2b, E-P2c, E-P3a, E-P4a, E-P4c, E-P5, E-P6(b), E-P8a, E-P8b, E-P9를 돌리지 않았다(그 뒤의 한 벌은 아래 문단). 같은 날 코드 검토 지적 8건을 처리했다. 쓰기 게이트가 원시 요청 URI로 대상을 가려 `;` 매개변수나 퍼센트 인코딩으로 적은 쓰기가 게이트를 비껴가던 것을 필터 등록으로 가리게 고치고 실제 Tomcat 시험을 더했다. 커밋 대기를 확인한 탐지의 소켓 제한을 불통으로 세어 긴 중단 동안 UNREACHABLE로 튀던 것을 고쳤다. 리스 획득 게이트와 재개 따라잡기를 고정하는 시험을 더했고, 설계·계약의 상태 문장과 실험 스택과 다른 설계 값(`wal_keep_size` 16MB, Grafana 없음, 관측 파일 위치, 승격 뒤 확인 커밋 축의 끝, 느린 노드의 UNREACHABLE)을 실제에 맞췄다. 같은 키 재전송의 재생 `200`에 확정 응답 보류를 걸자는 지적은 재생 트랜잭션도 리스 행을 잠가 WAL을 쓰고 동기 커밋을 기다리므로 받아들이지 않고 그 성질을 시험으로 고정했다. 같은 원시 URI 검사가 수용 제한·인증·관리 인증 필터에 남아 있어 별도 과제로 두고, 이체의 같은 키 재생 `200`은 읽기만 한 행을 돌려줘 재확인 전 창에 복제되지 않은 행을 확정할 수 있어 사용자 확인 대상으로 남긴다([설계](reference/architecture/DB_자동전환_Patroni_설계.md) 12절). AWS에는 적용하지 않았고 학교와 main의 현재 구조는 여전히 비동기 복제와 수동 승격이다.

사용자는 2026-09-24 새벽 대화로 다음을 정했다.

- 범위(ADR 0034 결정 1): 발표(2026-10-16) 전에 로컬 Docker에서 S7까지 끝내고 S6(WebSocket 외부 STOMP 브로커 릴레이)도 넣는다. 태그의 'S0·S1만' 기본값은 폐기했다. 단계 계획의 공수 추정(S0~S7 71~104인일, 추론)은 남은 날짜보다 크므로 관문을 건너뛰지 않고, 발표에서는 관문을 통과한 단계까지만 말한다.
- 실험: 파티션 기능 검증 실험은 로컬 Docker의 폐기용 스택과 폐기용 DB에서 한다. 보존하기로 한 `chaos-pgdata` 볼륨과 main 스택의 DB에는 V48과 이후 마이그레이션, 전환 함수를 적용하지 않는다. 카오스 E 시험(E1~E9)은 2026-09-23 밤 작업 범위에서 뺐지만, 사용자가 이날 S2~S7을 맡기며 실험까지 하라고 해서 폐기용 스택과 폐기용 DB에서 돌리기로 바뀌었다. 같은 날 S1 관문(P1)과 S3 관문(P2)에서 E2·E4·E5·E6·E7을 폐기용 스택에서 돌렸다(위 관문 문단). S4 관문(P2)에서는 여기에 E1·E3을 더했다. E8·E9와 파티션 실험(S7)은 실행하지 않았다(NOT RUN).
- 서비스 흐름 화면(`/admin/flow`): 채택해 실제 값과 연동하고 발표 실험을 이 화면에서 한다. 시스원 연구소장이 이 화면을 좋게 평가했고 여기에 AI를 넣으라고 했다. 사용자는 AGENTS.md의 'AI가 운영 조치를 직접 실행하지 않는다' 규칙을 바꿀 예정이며, 자동 모드가 아니면 AI가 '이렇게 하라'고 조치안을 말해 주는 방식이다. 규칙은 아직 바뀌지 않았고, 화면 연동과 AI 조치안은 이번 단계의 구현 범위가 아니다.

회원 폐쇄 규칙은 사용자 결정이 아니다. 정지 마켓의 미체결이 남으면 폐쇄를 완료로 처리하지 않고 `409 orders_cancel_incomplete`(태그 판)를 낸다는 방침(ADR 0034 결정 15)은 2026-09-24 새벽 작업을 맡은 AI 세션이 안전한 쪽으로 고른 값이다(AI 선택(2026-09-24), 사용자 확인 필요). S1 코드와 API 설계 v2.53 §6-E는 정지 마켓의 `422 market_suspended`를 미완료로 세지 않아 `200`을 냈다. S3에서 API 설계 v2.54 §6-E를 먼저 고친 뒤 코드와 시험(`MemberCloseIncompleteTest`, `OrderGatewayMarketHaltIntegrationTest`)을 맞췄다. 이제 브랜치에서는 정지 마켓 미체결도 미완료로 세어 폐쇄가 `409 orders_cancel_incomplete`로 끝나고, 에러 `detail`의 `pending_reasons`가 사유별 수를 싣는다. 폐쇄 자체는 이미 커밋된 상태라 웹 관리 화면은 이 409를 실패가 아니라 '폐쇄 확정, 미완료 n건' 경고로 보이고, 정지 마켓을 재개한 뒤 새 승인으로 다시 요청하라고 안내한다. 사용자가 `200` 유지를 고르면 계약·코드·웹을 함께 되돌린다.

인계에 더할 것은 다음과 같다.

- 부하: 사람 행동을 흉내 내는 부하 시나리오는 새로 만들지 않는다. 조회 부하는 [read-load.py](../harness/scripts/read-load.py)를, 차트 급등 시연은 봇 시장 국면 프리셋 `spike`([SimScenario](../server/app/src/main/java/kr/exchange/sim/SimScenario.java))를 쓴다.
- 학교 백업 설치와의 관계: S2 판의 `harness/sql/summary.sql`은 V48 표가 없는 DB에서 C29를 SKIP으로 내 복원 점검이 실패했다. S3 판은 V48·V50 객체가 모두 없는 DB에서 C29·C31을 N/A로 내고, 같은 브랜치의 복원·복구 점검 여섯 곳은 N/A를 실패로도 통과로도 세지 않고 `not_applicable`에 따로 적는다(AI 방침, 사용자 확인 필요). 그래서 학교 DB가 V47인 동안 브랜치를 합친 뒤의 점검 도구와 `summary.sql`을 함께 설치하면 복원 점검은 C29·C31 때문에 실패하지 않는다. N/A를 모르는 이전 판 점검 도구에 새 `summary.sql`만 넣으면 형식 오류로 실패하므로 학교 백업 도구([백업 안내](../deploy/linux/postgresql/backup/README.md))는 두 파일을 같은 릴리스에서 설치한다.
- AI 서버: 2026-09-28(월) 메모리 128GB의 DGX Spark AI 서버가 들어온다. 쓰임새와 연결 방식은 아직 정하지 않았다.
- 상담 과제: 시스원 연구소장이 준 미션은 pfSense와 Databasus를 VM으로 구성해 오는 것과 관제센터(서비스 흐름 화면)에 AI를 넣는 것이다. 상담에서 들은 조언이며 회사의 공식 평가 기준이 아니다. Databasus 초안(`deploy/vm-lab/databasus/04-ADR초안.md`)의 번호 0034는 마켓별 리더와 겹치므로 채택할 때 새 번호를 받는다.

2026-09-24~25 대화에서 사용자가 더 정한 것은 다음과 같다. 위에 이미 적은 것(S2~S7 위임과 완료 뒤 할 일, 부하 시나리오, AI 서버 입고, 상담 과제, 서비스 흐름 화면 채택)은 되풀이하지 않는다. 다른 브랜치에서 진행한 것은 그 브랜치에만 있고 이 브랜치의 코드와 문서에는 들어 있지 않다.

- S2 A/B 판정: 5xx는 리더 노드가 낸 것만 세고, 반복 측정한 뒤 넘어간다(재측정 PASS, `91813dd5`).
- 빌드 절약: S5~S7은 라운드 중 관련 시험만 반복하고 서버 전체 빌드는 라운드 끝에 한 번, 보정이 있으면 한 번 더 한다. S4까지는 종전 방식이었다.
- S5~S7은 여러 에이전트 워크플로로 이어 돌려도 된다(2026-09-24 22시).
- S4b의 DB 연결 장애 응답: `500` 대신 `503` + `Retry-After` + '재조회 후 판단 필요'로 내고 멱등 키와 예약은 V47 규칙대로 남긴다(2026-09-25 확정, 위 S5 문단).
- 관리 콘솔 디자인은 관제센터형 B안을 채택했다(`claude/admin-design`의 `32d00ad9`).
- 종합 관제는 MSP 관제로 가고 방식 B(MSP 요약과 Grafana 딥링크)로 한다. 디자인 완성도를 우선해 AI 관제센터처럼 보이게 하고, 임계값 수정처럼 Grafana가 못 하는 조치는 관제센터에서 한다. 2026-09-25 정한 시각 방향은 사용자가 준 참고 시안을 따른다. 요약 카드의 아이콘·추세선·증감, 상단의 검색·전체 상태·알림·기간 선택, 인프라 상태 집계, AI 판단 요약 네 칸, 세로 타임라인을 두고, DB 두 대(primary·standby)는 한 곳에 묶는다. 화면 문구는 합니다체로 쓰고, 사이드바 쪽에 현재 상태를 묻는 'AI 상담' 대화창을 둔다.
- AI 조치 권한: 수동 모드(AI는 제안만)와 자동 모드(AI가 판단해 자동 적용) 두 가지를 두고 규칙은 엄격하게 한다. `claude/admin-design` 브랜치의 ADR 0035로 채택했다. AGENTS.md의 'AI가 운영 조치를 직접 실행하지 않는다' 문장을 ADR 0035 기준 문장으로 바꾸는 것도 2026-09-25 확정했으나, 이 브랜치의 AGENTS.md는 아직 종전 문장이다. 두 모드에 공통으로 'AI 즉시 정지'를 보인다(판단 중지, 대기 중인 조치안 만료, 재개는 수동으로만. 이 해석은 AI 선택). 한도는 AI 권장값으로 확정했다(확신도 80%, 자동 실행 5회, 임계값 항목당 2회, 봇 쿨다운 10분, 백업 디스크 여유 30%). 수동에서 자동으로 다시 켤 때 횟수를 초기화하고 쿨다운과 관찰 창은 유지하는 것, 운영자가 승인 티켓 `ops.ai.limits`로 한도를 고칠 때의 하드 범위와 적용 시점(낮춤은 즉시, 높임은 다음 활성부터)은 AI 선택이다. 같은 날 메인 세션의 추천도 그대로 확정했다. 자동 모드의 임계값 변경은 민감하게 하는 쪽만 자동이고 완화는 사람 승인만 받는다. 봇 부하 줄이기는 bot-1 CPU가 용량 보호 기준 이상일 때만 한다. Teams 카드 등급은 관찰 실패·결과 모름 P1, 자동 되돌림 P2, 그 밖의 자동 실행 P3, 모드 변경·만료·재개 P4다. 학교 보고 카드의 표기 버그('기록 y:날짜' 잘림, 자동 조치가 늘 '없음')는 저장소에서 고치고 학교 적용은 승인 뒤에 한다. 화면 세부 값은 AI 기본값을 둔다.
- AI 모델: 이 PC의 RTX 4090에 Ollama v0.34.4를 설치하고 `gpt-oss:20b`, `qwen3.6:35b-a3b`를 받는 것을 승인했다. `-cloud` 모델은 쓰지 않는다. DGX Spark에서는 `qwen3.6:35b-a3b`(think=false)를 1순위로 두고 `gpt-oss:120b`와 비교한다.
- DB 자동 전환: Patroni(MIT)를 쓰고 DB는 두 대를 유지하며 etcd 세 표(DB 둘과 판정용 bot-1)와 HAProxy를 둔다. 사용자는 유실 0을 우선했고 엄격 동기 복제로 확정했다(2026-09-26). Standby가 없으면 쓰기를 멈추고 거래 화면을 '거래 일시 중단'으로 바꾼다. S7 뒤 Docker에서 먼저 하고 그다음 AWS다. ADR 0024·0025를 대체하는 새 ADR(번호 0036 예정)이 필요하다. AI는 여전히 DB를 승격하지 않고 Patroni 규칙만 전환한다.
- 서비스 흐름 화면: 실제 값과 연결하고 발표 실험을 그 화면에서 하는 2단계는 S7 뒤에 한다. 구성도의 ASG 상자는 조회 노드만 감싼다.
- 앱 계층(2026-09-25 정정): read-1·read-2는 없다. 앱 계층은 늘 켜진 매칭 리더 app-1·app-2(조회도 처리)와 부하 때 자동 증설하는 조회 전용 app-3의 세 대다. ADR 0030의 '조회 ASG min 2/desired 2/max 3'은 앱 계층 전체 대수로 읽는다. 기술 구현은 AI 제안으로, 매칭 리더는 ASG 밖에 고정하고 ASG는 app-3(0~1)만 관리한다. 로컬 카오스 스택의 api-1·api-2와 api-3이 같은 모양이다. 이 정정은 디자인 화면, ADR 0030·0035·0099, v6 도면, MSP 서버 문구, Terraform의 조회 ASG min 0 허용에 각 작업에서 반영한다.
- 개인 AWS: 학교가 ALB를 허용하지 않으면 개인 계정(크레딧 $172)으로 간다. 2026-09-28에 ALB 생성 가능 여부, vCPU 할당량, 예산 경보, 크레딧이 적용되는 제품을 미리 확인하고, 착수는 10월 2일을 권하며, 10월 16일 발표 뒤 destroy한다. DB는 t3.medium(4GiB) 두 대로 올릴 계획이다.
- pfSense는 AWS에 넣지 않는다(v6 도면에도 그리지 않는다). VM 실습망에서는 pfSense로 방화벽을 구성했고, AWS에서는 단일 병목·장애점이 될 수 있어 역할별 보안 그룹으로 통제한다. 마켓플레이스 pfSense Plus 요금은 크레딧 대상이 아니다. 아래 '사용자가 정해야 할 일'의 pfSense 항목은 이것으로 정해졌다.
- v6 현재 배포 계획도(drawio)를 요청했다(`claude/arch-v6`).

이 목록에서 확인을 기다리던 AI 선택 둘은 모두 정해졌다. 연동 전까지 출처 칩에 '시뮬레이션'을 보이는 것은 2026-09-25 기본값 유지로, 엄격 동기 복제(Standby가 없으면 쓰기 정지)는 2026-09-26 사용자가 확정했다. 비동기로 강등하는 설정은 쓰지 않는다.

Terraform은 아직 맞추지 않았다. sim 원천의 웹 시험, 빌드와 헤드리스 브라우저 측정으로만 확인했고 학교 AWS 배포 상태는 바꾸지 않았다.

2026-09-25 MSP 관제센터 2단계(서버): 사용자는 관리 콘솔의 '종합 관제'를 'MSP AI 관제센터'로 바꾸기로 했고(Grafana는 보는 곳, 관제센터는 판단·조치·기록하는 곳), 2026-09-24에 ADR 0035로 AI 운영 조치 권한을 정했다. 수동 모드가 기본이고, 자동 모드는 1인 승인 티켓과 사유로 최대 8시간만 켜지며 즉시 끄기는 승인 없이 된다. 이 결정에 따른 서버 쪽을 브랜치 `claude/msp-control`(기준 `claude/admin-design` `32d00ad9`)에 만들었고 main에는 아직 합치지 않았다. 마이그레이션 V70~V73(임계값 레지스트리, 경보 사건, AI 모드·한도·판단·조치 요청·계획 작업 창, 통지 보관함과 실행 임대)과, V48~V69가 빠진 채 V70 이후를 적용하려 하면 멈추는 적용 순서 점검을 넣었다. 관제 API(`/admin/v1/msp/*`)는 Prometheus 명명 질의와 Alertmanager를 읽어 한 판·호스트·경보·사건·추세를 보여 준다. 임계값 변경과 경보 확인·보류는 기존 역할과 1인 승인 흐름을 쓴다. AI 쪽은 모델이 조치 요청만 만들고, AI가 아닌 서버 정책 엔진이 허용 목록·한도·쿨다운·근거 신선도(60초)·연속 2회 판단을 다시 검사한 뒤 실행한다. 실행 뒤에는 관찰 창과 악화 시 자동 되돌림, 감사 기록이 붙는다. AI 상담, AI 서버 상태 조회, 보고 서비스(`/msp/events`)를 거친 Teams 통지도 만들었다. 설계와 구현 기록은 [MSP 관제센터 2단계 설계](reference/architecture/MSP_관제센터_2단계_설계.md)에 있다. 용량 계획의 잃어버린 갱신(겹친 두 증설이 둘 다 성공)도 수정 전 코드로 재현한 뒤 행 잠금으로 고쳤다. 학교·하네스 경보 규칙 일부는 레지스트리 게이지를 읽는다. 실행해 확인한 것은 다음과 같다. ASCII 작업 트리에서 `.\gradlew.bat build`를 시험 재실행으로 돌려 10분 18초에 통과했다(app 132개 클래스 906건, engine 67건, 실패·건너뜀 0, 새 관제센터 시험 24개 클래스 226건과 적용 순서 점검 6건 포함, 시험 로그의 localhost 5432·55432 JDBC 0건). promtool 3.13으로 학교·백업·워치독·하네스 규칙 검사와 규칙 시험을, amtool 0.34로 학교 Alertmanager 설정을, Python으로 관측 연결 10건과 보고 서비스 통지 7건을 확인했다. 통합 시험은 Testcontainers(PostgreSQL, Prometheus, Alertmanager)와 가짜 LLM·보고 서비스 스텁으로만 했다. 남은 일은 네 가지다. 첫째, 웹 http 어댑터 연결이다. 둘째, 학교 서버 적용인데 V48~V69 병합 순서와 보고 서비스 재설치·토큰 전달을 먼저 정해야 한다. 셋째, 실제 LLM 연결이다. 2026-09-25 로컬 RTX 4090의 Ollama에서 `gpt-oss:20b`와 `qwen3.6:35b-a3b`로 운영 코드의 판단·상담 경로를 평가했다. 경보 요약에 끼워 넣은 명령문을 따른 봇 부하·임계값 조치가 정책을 지나던 문제를 프롬프트, 근거 카탈로그, 봇 부하의 방향 전제(D4)로 줄여 자동 모드였다면 잘못 실행됐을 조치가 111회 가운데 9회와 0회에서 2회와 0회가 됐다([측정 09-25](measurements/20260925.md)). 남은 2회는 D3가 허용하는 임계값 변경이었다. 이 대응 뒤 ASCII 경로의 작업 트리에서 `.\gradlew.bat build`를 돌려 10분 11초에 통과했다(app 134개 클래스 922건, 실패·건너뜀 0. engine은 입력이 바뀌지 않아 다시 돌지 않았다. 시험 로그에 localhost 5432·55432 JDBC와 Ollama 11434 접속은 0건). 이어서 모델에 가는 근거에서 경보 주석과 사람이 쓴 문장을 빼고(경보는 이름·등급·허용한 라벨·연결된 임계와 서버가 잰 값만), 형식 밖 값이 든 경보의 AI 보류를 막았다(S8). 사용자 결정에 따라 자동 모드는 임계값을 민감한 방향으로만 옮기고 둔하게 하는 변경은 사람 승인으로만 실행한다(T6, API v2.52.6). 같은 조건의 재평가에서 주입 시나리오는 두 모델 모두 조치하지 않았고, 구조화 필드에 이상한 값을 넣은 I01~I07도 두 모델 모두 21/21 정답이었다. 37개의 잘못 실행될 조치는 `gpt-oss:20b` 2회, `qwen3.6:35b-a3b` 0회이고, 남은 2회는 T6이 받는 민감한 방향의 임계 변경이다([측정 09-25](measurements/20260925.md) '재평가' 절). 이 대응 뒤 `.\gradlew.bat build`는 9분 48초에 통과했다(app 135개 클래스 938건, 실패·건너뜀 0). 2026-09-28 들어오는 DGX Spark에서는 API 형식과 스키마 강제 지원을 확인하고, 사용자가 정한 대로 `qwen3.6:35b-a3b`(`think=false`)를 1순위 후보로, `gpt-oss:120b`를 견줄 모델로 같은 실행기(`:app:llmEval`)를 돌린다. 넷째, 실제 Teams 카드 확인이다. 자동 모드는 기본으로 꺼져 있고 어디에도 배포하지 않았다. AGENTS.md의 AI 조치 문장과 ADR 0027의 해당 문장은 09-25 병합 때 ADR 0035의 대체 범위에 맞췄다.

아래는 2026-09-23 밤 인계다. 위 09-24 문단에서 바뀐 것(브랜치 재생성, 서비스 흐름 화면 채택)은 그쪽을 따른다. 이어서 작업할 때는 이 문단부터 '서비스 흐름 화면' 문단까지 먼저 읽는다. 이날 저녁에는 관리 콘솔 개편, 서비스 흐름·지표 관제 시안과 관리 화면 수정 세 건(회원 목록 버튼, 모달 포커스, 로그인 뒤 브라우저 게이트)을 main(`b6905cc`)에 합쳤다. 밤에는 그 위에서 프로젝트 전체를 다시 파악했다. 웹·서버·보존 태그·문서 검사를 실제로 돌리고 코드와 문서를 대조해 운영과 발표에 걸리는 결함을 찾았고, 저장소 안에서 고칠 수 있는 것을 영역별로 고쳤다. 고친 결과는 이 PC 저장소의 작업 트리에 있고 커밋은 사용자 확인 뒤에 한다. 이 문단을 쓰는 시점에는 커밋하지 않았다. 학교 AWS와 학교 DB에는 접속하지 않았다. 학교 서버는 여전히 JAR `3362117`, 웹 `origin-20260920` 묶음과 2026-09-20~21의 설정으로 돌고 있으며 아래 수정은 하나도 적용되지 않았다.

사용자는 이날 밤 두 가지를 정했다. 첫째, 쓰기 분할은 앱 노드마다 일부 마켓의 매칭 리더를 맡기는 마켓별 리더(태그의 ADR 0034 초안 방향)로 간다. 아직 구현과 병합 전이므로 0099의 현재 구조 설명은 단일 리더 그대로다. 둘째, 로컬 Docker에서 전부 완성하고 검증한 뒤 AWS에 배포한다. 학교 AWS 담당자가 추석 연휴라 회신과 권한 확인은 2026-09-28(월) 이후이고, 그전에는 학교 서버에 아무것도 적용하지 않는다.

그래서 다음 작업은 로컬 Docker에서 이 순서로 한다.

1. 로컬 카오스 스택 복구: 09-23 07시 무렵부터 DB 계층(chaos-pg, chaos-toxiproxy, chaos-dynamodb)이 멈췄고 앱 컨테이너는 재시작을 반복한다. `chaos-api-3`는 이미지 저장소에서 사라진 옛 이미지로 만들어졌다. 09-13부터 쌓인 `chaos-pgdata`(약 1.32GB)를 보존할지 정한 뒤 다시 세운다. 문서화된 재실행 경로 대부분이 이 볼륨을 지운다.
2. 마켓별 리더 구현: 태그 `wip/per-market-leader-20260923`에서 브랜치를 다시 만들고, 아래 문단의 V47 번호 충돌과 키 보존 흐름부터 main 판에 맞춘다. 앱 두 대 구성의 Docker 스택에서 검증한다. 카오스 E 시험은 이때(2026-09-23 밤) 사용자가 뺀 범위였다. (2026-09-24 브랜치를 main 기준으로 새로 만들어 S3 코드까지 진행했고, 같은 날 사용자가 실험까지 맡겨 E 시험도 폐기용 스택에서 돌렸다. 위 09-24 문단들을 따른다.)
3. 서비스 흐름 화면 2단계: 시안을 채택하면 Docker 스택에 Standby를 붙여 버튼과 차트를 실제로 연결하고, 구성도를 마켓별 리더로 바꾼다. (사용자가 2026-09-24 채택을 정했다. 연동은 아직이다.)
4. 2026-09-28 이후 AWS: 학교 담당자의 답에 따라 ALB·ASG와 app-2 허용을 확인하고 아래 순서로 학교 서버에 옮긴다. 개인 계정 재배포는 원래대로 10월 초다.

저장소에서 고친 내용은 영역별로 다음과 같다.

- 거래 웹: http 모드의 입출금 요청이 `Idempotency-Key` 헤더를 빠뜨려 서버에서 모두 400으로 거절되던 결함을 고쳤다. 주문 패널의 총액 역산·한 호가 이동·가격 표기와 입출금 빠른 금액이 금액을 JavaScript number로 바꾸던 경로를 십진 문자열 함수로 옮기고 시험으로 고정했다.
- 관리 콘솔: 시연 대본이 게이트를 지나지 않은 단계까지 '완료'로 기록하던 판정을 고쳤다. 증설 대본의 '사용률 하락'은 최대 대수에서 늘 충족되던 조건 대신 부하 잔존, 조회 노드 증가, 평균 하락을 모두 요구한다. 리더 대본은 선출 세대가 올랐는지 확인하고 주행 시작 이후의 복구 판정만 읽는다. 불변식 분모를 서버 검사 목록에 맞췄다. `/admin/back`이 큐 하나의 권한 거절로 화면 전체가 실패하던 문제, 승인 목록의 포커스, 만료된 승인까지 세던 대기 수, 용량 화면의 계산과 낡은 주석도 고쳤다.
- 서버 주문·정산: 정지 마켓의 주문 생성과 취소가 500 대신 422 `domain_rejected`(`market_suspended`)로 끝난다. 저널 커밋 여부가 모호한 예외 뒤 멱등 키를 지우고 잔고 예약을 바로 풀던 경로는 새 마이그레이션 V47(`resolve_failed_order_intake` 판정과 `idempotency_keys.shared_at` 공유 표시)과 라이터 회수 요청으로 고쳤다. 정산은 잠금 대기·문장 시간 초과 같은 일시 오류(SQLSTATE 55P03·57014·40P01·40001)에서 바로 강등되지 않고 5초 안에서 최대 네 번 시도한다. 관리 서버에 남아 있던 2인 승인 주석을 1인 승인에 맞췄다.
- 학교 운영 템플릿: 앱·봇·관리 env 템플릿에 가상 스레드 끄기를 넣었다. node_exporter 유닛 필터의 오타와 누락을 고치고 textfile 수집기를 켰다. 학교 경보 규칙은 bot-1을 포함해 16개가 됐다(보고 서비스·일일 보고·봇 중지와 주문·정산 카운터 추가). Alertmanager에는 Watchdog 전용 빈 경로와 억제 규칙을 넣었고, 용량 보호는 판정을 마치면 정상 종료한다. MSP 화면의 경보 패널을 원래 조회식으로 되돌렸다.
- 백업과 관측 노드 감시: 현재 Primary에서만 물리 베이스백업을 만들고 선택적으로 비공개 S3에 보관하는 Docker 없는 백업 도구와 systemd 타이머, 경보 7개를 만들었다([백업 안내](../deploy/linux/postgresql/backup/README.md)). app-1과 bot-1이 관측 경로를 서로 확인하고 Alertmanager를 거치지 않고 Teams로 직접 알리는 워치독과 데드맨(Watchdog) 규칙도 만들었다([워치독 안내](../deploy/linux/watchdog/README.md)).
- 그 밖: Terraform은 NAT Gateway를 기본으로 만들지 않는다(ADR 0030). 하네스 조정기는 헬스를 다시 확인한 노드만 등록하고 reload가 실패하면 설정 파일을 되돌린다. 09-23 증설 리허설 원자료를 저장소로 옮겨 [09-23 측정](measurements/20260923.md)을 남겼다. VM 문서의 과장과 스크립트 판정을 고쳤지만 VM에는 적용하지 않았다. 관리자 설계, 조회·쓰기 비율 조사, ADR 상태 줄, 0099, 코드 지도, AWS 작업 안내를 코드와 맞췄다. `check-style.ps1`은 검사한 줄이 없으면 통과 대신 종료 코드 2를 낸다.

이날 실제로 돌린 검사와 결과는 다음과 같다. 서버는 한글 경로에서 테스트가 0건 실행되는 환경 문제가 있어 ASCII 정션 `C:\dev\exchange\server`에서 `.\gradlew.bat build`를 돌렸고 8분 5초 만에 통과했다. app 668건은 이번에 새로 실행했고 engine 67건은 Gradle 캐시 결과이며, 합계 735건에 실패·건너뜀이 없다. 여기에는 새 시험인 모호한 커밋 판정 11건, 정지 마켓 2건, 정산 재시도 분류 5건, 일시 오류 판별 15건, 용량 권고 11건이 들어 있다. 웹은 통합한 작업 트리에서 마지막 보정 뒤에 다시 돌려 단위 시험 525건, tsc, 빌드(정적 페이지 80개), 토큰 검사(파일 234개·계약 96쌍), 브라우저 게이트(sim 원천, 화면 33개·뷰포트 2종·테마 2종·검사 132회)가 모두 통과했다. Python 시험은 Linux 컨테이너에서 백업 25건, 워치독과 관측 연결 시험을 포함한 deploy/linux 시험 68건, 학교 보고 13건, 용량 보호 7건이, Windows에서 하네스 조정기 18건이 통과했다. promtool 3.13으로 학교·백업·워치독·점검 규칙 26개의 문법과 세 규칙 시험을, amtool 0.34로 Alertmanager 설정과 Watchdog 경로를 확인했다. 문서 검사 네 가지(check-docs, check-doclinks, check-adr-current, check-style)는 이 인계와 0099 갱신 뒤 통과했다. systemd 실동작, 실제 S3 업로드와 Teams 전송, Terraform 검사, 로컬 http 스택에서의 실제 입출금은 실행하지 않았다. 카오스 E 시험(E1~E9)과 로컬 카오스 스택 조작은 사용자가 이날(2026-09-23 밤) 범위에서 뺐다.

학교 서버에 옮기는 일은 Docker 검증을 마치고 2026-09-28 이후에 모두 사용자 승인 뒤 한 단계씩 하고, 명령과 출력을 증거본의 새 날짜 폴더에 남긴다. 제안하는 순서는 아래와 같으며 절차는 [AWS 작업 안내의 09-23 절](reports/AWS_작업.md#2026-09-23-저장소와-학교-서버의-차이)에 있다.

교수 상담의 후속도 남아 있다. 교수님은 거래소에서 조회와 쓰기 중 어느 쪽이 많은지 논문 등으로 확인하라고 했고, 사용자는 조회가 대부분이면 쓰기 경로를 나누지 않는다는 기준을 세웠다. [거래소 조회·쓰기 비율 조사](reference/architecture/거래소_조회쓰기_비율_조사.md)는 공개된 거래 시스템 자료에서 요청 수나 DB 트랜잭션 수로 세면 조회가 대체로 3:1에서 15:1로 많다고 정리했다. 다만 암호화폐 거래소 자체의 비율을 실측해 공개한 자료는 찾지 못했고, 조회 비율만으로 쓰기 분할 여부를 정한 자료도 없었다. 그래서 조사 문서는 쓰기 분할 여부를 우리 최대 쓰기 수요와 단일 리더 용량, 리더 전환 시간으로 정하자고 적었다. 사용자는 이 조사를 본 뒤 2026-09-23 밤 마켓별 리더로 가기로 정했고, 두 측정은 그 구현을 검증하는 자료로 남는다. 학교 구성은 엔진을 켠 앱이 한 대뿐이라 노드 간 리더 전환을 잴 수 없다. 태그의 ADR 0034 초안은 병목이 DB 커밋이라 처리량 증가를 기대하지 않는다고 적었으므로, 천장 측정보다 장애 반경이 실제 판단 기준이 될 수 있다.

마켓별 리더 작업(ADR 0034 초안)은 main에 합치지 않고 태그 `wip/per-market-leader-20260923`(커밋 `f8184ef`)으로 원격에 보존했다. 2026-09-24에는 이 문단의 안내와 달리 태그가 아니라 main `ec8ef8e`에서 브랜치를 만들고 태그의 문서와 S1을 손으로 옮겼다(위 09-24 문단). 09-23 당시 안내는 이어서 하려면 `git switch -c claude/per-market-leader wip/per-market-leader-20260923`으로 브랜치를 다시 만든다. 태그에는 S0 문서(ADR 0034 초안, 단계 계획)와 S1 단일 리더 보강이 있다. S1은 정산 일시 오류 재시도, 고아 멱등 키 조건부 삭제 V47, 접수 락 대기 상한(기본 0), 폐쇄 409, 55P03을 503으로 바꾸는 매핑, prod-timeouts 카오스 프로필이다. 태그 커밋 메시지와 이전 인계가 남았다고 적은 두 문제(V47이 오래된 주문의 키를 남기는 회귀, 접수 락 3초 기본값)는 태그 코드에 이미 반영돼 있다. 태그의 V47은 `created_at` 비교로 옛 주문을 가르고 접수 락 상한의 기본값은 0이다. 이날 ASCII 경로에서 태그의 test를 돌려 729건이 모두 통과했다(bootJar와 전체 build는 돌리지 않았다). 이전 인계의 '656개'는 근거를 찾지 못했고, 두 검토의 FAIL 판정 원문은 이 PC에 없다.

S1 중 모호한 커밋 처리와 정산 일시 오류 재시도는 이날 main으로 옮겼다. main의 V47(`V47__order_intake_failure_resolution.sql`)은 시계를 비교하지 않고 자기 커밋은 채번한 주문 번호로, 다른 요청의 커밋은 공유 표시로 가르는 다른 판이다. 태그의 `V47__discard_orphan_idempotency_key.sql`과 번호가 겹치므로, 태그를 되살릴 때는 태그의 V47을 버리거나 V48 이후로 옮기고 태그 `OrderGateway`의 키 보존 흐름을 main 판에 맞춰 다시 짠다. 태그를 그대로 main에 합치면 로드맵, 상세 자료 안내, 0099 해시 줄도 충돌한다. 접수 락 대기 상한, 55P03의 503 매핑, 폐쇄 409, prod-timeouts 프로필과 ADR 0034 문서는 태그에만 남는다(2026-09-24 55P03 매핑을 뺀 나머지를 작업 브랜치로 옮겼다. 55P03 매핑은 ADR 0034 결정 11에 따라 S3에서 API 계약 문구를 먼저 고쳤고 코드는 S4 과제다). 55P03을 503으로 바꾸면 쓰기 업스트림의 `max_fails=1`과 겹쳐 잠금 대기 초과 한 건이 리더를 2초 빼므로, 옮길 때는 로드밸런서 설정을 함께 정한다. 태그의 카오스 게이트(E2·E4·E5·E6·E7)는 `compose up` 실패로 모두 BLOCKED였고 통과 기록이 없다. 카오스 E 시험은 2026-09-23 밤 사용자가 그 작업 범위에서 뺐다(2026-09-24 폐기용 스택에서 돌리기로 바뀌었다). 태그의 V47은 어떤 영속 DB에도 적용하지 않는다. 태그 문서는 ADR 0034를 '채택'으로 적는다. 사용자가 마켓별 리더로 정했으므로 main에 옮길 때도 채택으로 두되, 결정 날짜(2026-09-23)와 구현 전이라는 사실을 함께 적고 0099와 같은 변경에서 맞춘다.

웹 재배포에서 로컬 `.env.local`의 `localhost:8080`이 번들에 들어간 오류를 수정했다. HTTPS·WSS 주소를 명시하는 빌드 도구와 로컬 주소 잔존 검사를 추가했고, `origin-20260920` 배포에서 연결됨·실제 시세를 확인했다. 봇은 BTC·ETH·XRP 15개, 3 OPS 가동을 유지한다.

Primary의 백업 `20260919T162452010003Z`를 TCP 접속 없는 별도 PostgreSQL 클러스터에 복원했다. 동일 스냅샷의 명령 12,733·이벤트 20,746·체결 6,710·원장 항목 68,686건이 일치했고, 정합성 검사 30개 중 CRITICAL·HIGH 실패는 없었다. 시험 클러스터는 종료했으며 운영 거래 데이터는 유지했다. 백업은 전환 전 Primary였던 AZ-a 서버의 로컬 디스크에만 있으므로 호스트·볼륨 상실 대비와 예약 백업 완료로 확대하지 않는다. 원본 근거는 [이번 증거](../증거본/2026-09-20_백업_복구_보고/README.md)를 따른다.

기존 Teams 카드·PDF·HTML 모듈을 같은 원격 커밋에서 가져와 학교 AWS 범위로 설치했다. 봇 SG 9088은 앱 SG만 허용하며 `/operations/reports/`는 7일 만료 서명 링크로 파일을 제공한다. 앱·DB 경보 10개, Alertmanager, Gemini 보고 서비스와 오전 9시 timer를 연결했다. 기존 bot-1 전용 보고 timer는 중복 방지를 위해 비활성화했다. 시험 보고 1건의 웹훅 접수와 PDF·HTML HTTPS 200·저장 내용 일치를 확인했다. 사용자가 채널의 카드와 두 보고서 열람을 확인했다. Standby 정지, 복제 단절, 앱 정지, 별도 128MiB 시험 파일시스템의 공간 부족으로 경보 발생을 확인했고, 복구 후 해제 보고도 전송됐다. 운영 루트·DB 디스크를 채우거나 거래 데이터를 삭제하지 않았다.

사용자는 시장 봇 기동 전에 어드민 연결·용량 관리와 학교/개인 계정 연결·월 비용부터 정하도록 요청했다. 30일 상시 운영과 `www.sang.it.kr`, 조회 ASG min 2 / desired 2 / max 3, 학교·개인 실습 NAT Gateway 제외를 지정했다. 2026-09-25 사용자 정정으로 2~3대는 앱 계층 전체(app-1·app-2 고정과 조회 전용 app-3 자동 0~1대)이고, Terraform 예제의 reader ASG(최소 1 이상 검증, 예제 1~2대)는 이 정정에 맞춰야 한다. 이 기준은 [ADR 0030](reference/adr/0030-nat-free-lab-and-bounded-read-asg.md)이며 실제 ASG는 미구축이다. 학교 피어링 생성·라우트 추가 dry-run은 권한 부족으로 거부됐다. 월요일 학교 운영자에게 연결·왕복 경로·SG·공개 시연·비용·이전 조건을 확인받는다. 전달할 대상과 대안은 [AWS 작업 안내](reports/AWS_작업.md)에 준비했다. 개인 기본 VPC도 학교와 같은 대역이므로 허용 후 겹치지 않는 VPC를 확정한다. 관리자 초기화는 기존 원장 삭제 제한을 유지하는 별도 유지보수 흐름부터 설계하며 실제 삭제는 하지 않는다.

GitHub `codex/docs-linux-operations`의 `6ee1179`에서 가져온 MSP 화면 6개에 **07 · 디스크·용량**을 추가했다. 당시에는 필요한 파일만 가져왔고 기존 작업 파일은 보존했다. 이번 정리에서는 원격 브랜치 전체를 병합했다. 앱·DB 두 대에 native node_exporter, DB 두 대에 postgres_exporter를 설치했다. 봇의 기존 Linux 수집을 포함해 호스트 4대와 DB 2대가 연결됐으며 Prometheus 전체 8개 대상이 UP이다. 앱 SG의 9100·9101과 DB SG의 9100·9187은 봇 SG만 허용한다. PostgreSQL은 로컬 peer 인증의 통계 전용 계정을 사용하고 거래 테이블 접근 거부를 확인했다.

7개 화면의 PromQL 133개는 오류 없이 실행됐고 113개에 데이터가 있었다. 용량 화면의 12개 쿼리는 모두 값을 반환했다. DB 두 볼륨은 각각 50GiB이며 마지막 측정에서 각각 약 4.4% 사용·47.7GiB 여유였다. DB·WAL 크기와 inode도 표시한다. 70·85·95%는 화면 표시 기준이다. 이후 여유 15% 미만 5분 지속 경보를 Teams에 연결했으며 자동 삭제는 하지 않는다. 파일·거래 데이터 삭제는 수행하지 않았다.

다음 관측 작업은 외부 사이트 프로브와 장시간 측정이다. 앱·DB·디스크 경보의 발생·해제는 위 시험에서 확인했다. SQL 통계 확장은 미적재라 해당 수치는 미수집이며, 이를 연결하려면 DB 재시작 영향을 먼저 판단해야 한다. CloudWatch 연결과 시장 봇의 장시간 동시 운영은 남아 있다. AI 보고는 앱·DB 지표까지 확장했다. 설치·원복·용량 진단은 [AWS 작업 안내](reports/AWS_작업.md), 실제 화면과 명령은 증거 344~373을 따른다.

Grafana의 초기 384MiB 상한에서 OOM 종료가 발생했고, 중간 512/640MiB 설정도 메모리 회수 지연을 일으켰다. 서버 여유를 확인해 최종적으로 Go 회수 목표 512MiB·서비스 High 768MiB·Max 896MiB로 조정했다. EC2 사양·대수는 유지했다. 이후 BTC 저속 봇을 추가하고 동시 기동 직후의 메모리를 측정했다. 사용자는 메모리가 부족하면 봇과 관측 노드를 분리하도록 지시했다. 짧은 동시 기동 확인만으로 한 달 상시 운영 가능성을 확정하지 않는다.

app-1의 Nginx와 실제 API 모드 정적 웹은 처음에 PC 한 개의 HTTP 미리보기로 배포했다. 이후 사용자 승인으로 기존 앱 SG에 공개 80·443을 추가하고 HTTPS·인증된 사용자 API·WebSocket 경로를 연결했다. 80은 ACME 검증과 HTTPS 이동에만 쓴다. 초기 관리 경로는 403, 무인증 자산 API는 401이며 데모 세션의 자산 조회는 200을 확인했다. 자산·마켓 기본값을 등록한 뒤 브라우저의 연결 끊김이 해소됐다. 이후 시장 봇의 실제 체결과 1분 차트 갱신을 확인했다. 회원 거래와 장시간 운영 검증은 남아 있다. 이후 봇 인바운드에 앱 SG 전용 3000·8443을 추가했다. 인터넷에 관리 포트를 직접 열지 않는다. 명령과 화면은 증거 386~401에 있다.

학교 사용자 CloudShell과 PC에서 `AWS-StartPortForwardingSession`으로 bot-1의 Grafana 3000에 연결했다. 콘솔 대상 조회는 거부되지만 StartSession은 허용된다. Edge의 콜백 차단 화면과 달리 PC의 AWS CLI 로그인은 성공했고 STS에서 학교 사용자를 확인했다. 공식 서명을 확인한 Session Manager 플러그인을 설치해 PC의 `127.0.0.1:13000`에서 Grafana 로그인 화면을 열었다. 사용자가 직접 비밀번호를 입력해 관리자 계정 dltkdgur를 만들고 로그인했다. bot-1의 CPU·메모리·디스크·네트워크 그래프와 서비스 상태 표시를 확인했다. 임시 비밀번호 파일 0개, 익명 API 401, Grafana 헬스 정상을 확인했다. CloudShell의 TerminateSession 요청은 거부돼 종료 권한을 별도로 확인해야 한다. 절차는 [AWS 작업 안내](reports/AWS_작업.md), 화면과 명령은 증거 291~311을 따른다.

초기 실행 범위는 사용자가 선택한 거래 검증·앱 이중화, 봇·관측, 두 대시보드 외부 접근, Linux·DB 복구, AI·Teams 보고 범위로 진행한다. 부하 시험과 자동 확장은 이번 실행 범위에서 제외하며, 개인 계정 보강 목표는 유지한다. 사용자가 제공한 제미나이 키와 Teams Workflows 웹훅으로 bot-1의 실측 지표 요약을 시험 전송했고 사용자가 채널에서 수신을 확인했다. 모델은 Gemini 3.1 Flash-Lite다. 사용자 승인으로 매일 한국 시간 오전 9시 보고와 2분마다 상태 변화 확인을 활성화했다. 당시에는 bot-1 지표만 대상으로 했으며 현재는 위의 확장 보고 서비스로 대체했다. 하루 전체 통계의 축적 여부는 별도로 확인한다.

봇 노드의 STS 조회로 실제 실행 역할이 `SafeRole-2026-ai-kopo-04`임을 확인했다. EC2에 연결한 프로파일 이름은 `SafeInstanceProfile-2026-ai-kopo-04`다. Prometheus 3.13.3·node_exporter 1.12.1·Grafana 13.1.0·Java 21을 직접 설치했다. Prometheus 준비 상태, Linux 수집기 15개 성공, Grafana DB 헬스·데이터 원본·대시보드 프로비저닝 로그와 11개 쿼리 실행을 확인했다. 최초 설치 당시 3000·9090·9100은 루프백이었고 Grafana 익명 API는 401이다. 이후 최초 관리자 생성과 PC의 SSM 터널을 통한 로그인·패널 렌더링을 확인했다. 다른 호스트·DB 지표는 이후 연결했으며 위의 최신 결과를 따른다. 이 기록은 앞의 봇 노드 생성 직후 설치 전 상태에 이어지는 결과다.

운영 보고 수집기는 미수집·오래된 지표·서비스 중지를 정상과 구분하며 AI 요약 실패 때 실측값을 남긴다. Teams 응답이 불확실하면 자동 재전송을 멈추고 확인을 기다린다. 같은 날짜의 일일 보고 재실행과 같은 상태의 장애 확인에서 중복 전송 억제를 확인했다. 관련 로컬 테스트는 9개 통과했다. 첫 AI 요약의 수집 주기 해석 오류를 보완하고 AWS에서 재호출해 정상 범위 요약을 확인했다. 의도적인 장애·회복 알림, 보고 노드 자체 장애, 재부팅 후 복구는 아직 검증하지 않았다. 증거 263~290과 보고 소스는 [AWS 작업 안내](reports/AWS_작업.md)에서 이어간다.

학교 콘솔에서 VPC 피어링 목록 조회와 타 계정 요청 양식 접근은 성공했다. 이후 학교 사용자로 CreateVpcPeeringConnection·CreateRoute를 `--dry-run` 검사했고 모두 허용 정책 부재로 거부됐다. 수락 권한과 실제 새 피어링 경로는 미검사다. 기존 라우트는 local과 IGW 두 개이며 공유 기본 테이블이다. 연결 요청·라우트 변경은 하지 않았다. 증거 374~378을 보관했고 운영자 허용 전에는 두 계정 분산 배치를 진행하지 않는다.

진행 순서는 **Docker 검증 결과 확인 → 학교 EC2의 Linux 운영·서비스 검증 → 2026년 10월 초 개인 AWS 계정 재배포·보강**이다. VM 선행 조건은 보류했다. 과거 Docker·WSL 결과는 재사용하되 이번 EC2 시험으로 기록하지 않는다.

1. 본인 EC2의 EC2 Instance Connect 브라우저 SSH로 재접속해 기본 점검 기록에서 이어간다. SSM 화면의 조회 거부는 `ssm:DescribeInstanceInformation`, `ssm:GetConnectionStatus`, `ssm:GetServiceSetting`, `iam:GetInstanceProfile`이다. 이후 bot-1의 SSM 포트 포워딩은 성공했다. 조회·세션 시작·종료 권한을 구분하고 거부된 API는 학교 운영자에게 확인한다. 새 서버를 중복 생성하지 않는다.
2. 생성된 서버는 앱 1대·DB 2대·봇·관측 1대다. 앱과 봇은 각각 gp3 20GiB, DB는 각각 gp3 50GiB다. 50GiB는 학교 안내의 디스크 용량 조건이며 메모리나 EC2 대수 제한이 아니다. 계정 전체 EBS 할당량과 추가 볼륨 허용 범위는 별도로 확인한다. 생성된 서버는 가동 비용이 발생하며 중지 후에도 남은 볼륨 비용을 관리한다.
3. 현재 보안 그룹의 제한된 SSH 규칙을 유지한다. `iam:GetRole` 조회는 IAMBasicAccess 정책으로 거부됐지만 프로파일 연결과 브라우저 SSH는 성공했다. 일반 SSH/PuTTY가 추가로 필요하면 접속자 IP와 키 관리 조건을 따로 정한다. DB·관리 포트를 인터넷 전체에 공개하지 않는다.
4. 먼저 [0099의 역할별 배치](reference/adr/0099-current-architecture.md#역할별-인스턴스-배치)에 맞춰 학교용 노드별 규격·AZ·서브넷·SG 통신·비용을 대조한다. 앱·DB primary·DB standby·bot-1·load-1의 역할을 임의로 합치지 않는다. 학교의 제한을 근거로 단일 인스턴스 구성으로 바꾸지 않는다.
5. 첫 앱의 systemd 상태·준비 상태와 DB 복제 상태를 읽고 이어간다. 앱 사설 IP 한 개만 hostssl로 허용했고 TLS 신뢰 파일도 배치했다. 요청·append·리스 풀 설정은 16+14+2이며 요청 16·리스 2는 실제 지표로 확인했다. 봇 풀 상한 6개를 합한 현재 앱·봇 상한은 38개다. 추가 앱·관측·관리 연결을 합산해 DB 예산을 재검토한다. 종목 기본값, WebSocket과 세 마켓의 봇 거래는 확인했다. 회원 거래, 두 번째 앱과 장애 복구는 남았다. 관측의 호스트·DB 연결은 완료했다. 기존 로컬 Grafana 익명 Admin 설정은 외부 배포에 사용하지 않는다.
6. 학교에서 허용된 범위를 마무리하고 제한됐던 부분을 개인 계정에서 보강한다. 10월 초 재배포 전에 잔액·만료·견적, 설정과 백업의 반출 조건을 확인한다. 코드·설정·패키지·명령 기록을 재사용하되 새 환경에서 거래·관측·복구·확장을 다시 검증한다.

2026-09-23에는 로컬 브랜치에서 관리 콘솔을 다시 세웠다. 운영 관제와 백오피스를 갈랐고, 카오스 주입 화면을 걷어낸 자리에 상황별 시연 대본을 두었으며, 카오스 스택에 조회 증설 노드를 붙였다 떼는 경로를 열었다. 로컬 Docker에서 관리 API와 조정기가 증설과 축소를 끝까지 실행하는 절차를 확인했다. 증설 요청부터 3대 관측까지 24.0초, 축소는 드레이닝 10초를 포함해 18.3초, 단발 증설은 10.8~10.9초였다. 증설 노드 `chaos-api-3`은 AWS 조회 노드 구성(prod,read)이 아니라 dev,chaos-monkey 구성으로 떴고, 부하 전부터 증설 권고가 떠 있었으며 조정기 두 개가 함께 돌았다. 그래서 이 회차를 권고 임계나 분산 효과의 근거로 쓰지 않는다. 원자료와 조건은 [09-23 측정](measurements/20260923.md)에 있다. AWS는 건드리지 않았고 이 작업이 학교 배포 상태를 바꾸지 않는다.

남은 카피 작업이 하나 있다. 서버 java 문자열 가운데 존댓말 종결로 끝나는 한글 문구는 최대 138건(29개 파일)이다. 이 수는 로그·예외 메시지처럼 사용자에게 보이지 않는 문자열까지 센 상한값이다. 웹 게이트는 `ㅂ니다` 어미까지 넓혔지만 서버는 종전 `습니다` 기준을 그대로 두었다. 이것을 바꾸면 전 평면의 API 오류 문구가 바뀌므로 [API 계약](reference/contracts/백엔드_API_설계.md)과 서버 테스트를 함께 보는 별도 변경으로 진행한다.

선택한 환경과 재현 절차는 [배포 안내](../deploy/README.md), 실제 진행 상태는 이 파일에서 관리한다. 기존 보고 도면은 목표 또는 과거 계획으로 보존하고 환경별 검증 증거와 대조한다. 계획을 세웠다는 이유로 도면 전체가 검증됐다고 쓰지 않는다.

## 공통 완료 조건

- 봇 부하와 10배 스파이크 중 자산별 원장 합이 0이고 주문 중복·유실이 없어야 한다.
- 앱 리더 장애 후 사람 개입 없이 거래를 재개해야 한다. 복구 시간 목표는 30초 이내다.
- 해당 변경의 빌드, 테스트, CI 검사를 통과해야 한다.

실험 번호와 판정 조건은 [하네스 검증 설계](reference/contracts/하네스_검증설계.md)를 따른다. 앱 리더 전환과 PostgreSQL 승격은 다르다. DB 승격은 수동이며 비동기 복제에서의 기록 유실 가능성이 있다.

## M1. 거래와 앱 복구

명령을 DB에 기록한 뒤 마켓별 엔진에서 매칭하고, 이벤트·원장·잔고를 함께 정산한다. 웹은 HTTP/STOMP로 연결한다. 자세한 흐름과 소스 위치는 [코드 지도](reference/architecture/프로젝트_코드지도.md)에 있다.

2026-09-13에는 V41 적용 코드(`2a818b6`)에서 E1·E2·E4·E5·E6·E7을 통과했다. 페일오버 실험의 복구 시간은 5.116~10.226초였다. E9의 이전 결과는 판정기 수정 전이라 이 완료 근거에 포함하지 않는다.

E1에서 발견한 리스 갱신 잠금 문제는 [ADR 0026](reference/adr/0026-leader-lease-key-share-lock.md)과 [재현 기록](../harness/evidence/e1-lease-starvation-20260913/)에 있다. 회차별 판정은 [chaos-runs/](../harness/evidence/chaos-runs/)의 09-13 결과를 확인한다.

## M2. 회원

가입·로그인, 세션과 API 키 발급, 회원별 자산·거래 내역을 구현했다. 실제 금융 자격증명이나 실명 정보는 받지 않는다. 회원과 봇의 계정·권한을 구분한다.

완료 조건은 여러 회원이 봇과 동시에 거래해도 위 공통 조건을 만족하는 것이다. 기능 범위는 [회원 설계](reference/product/회원_설계.md)에 있다.

## M3. 게시판과 관리자

종목별 게시판과 댓글, 공지·문의, 관리자 기능을 구현했다. 관리자는 별도 인증을 거쳐 봇과 조회 노드 대수를 제어하고 상태를 확인한다. 2026-09-23에 웹 관리 화면을 운영 관제와 백오피스로 나누고 장애 주입 화면을 걷어냈다. 서버의 장애 주입 API는 코드에 남아 있다.

게시판이나 관리자 요청이 거래 처리에 불필요한 의존성을 추가하지 않아야 한다. 해당 기능에 부하나 장애가 생겨도 거래 조건을 유지하는 것이 완료 기준이다. [게시판 설계](reference/product/게시판_설계.md)와 [관리자 설계](reference/product/관리자_설계.md)를 따른다.

게시판 설계의 별도 DB·프로세스 분리와 현재 앱 구성에는 차이가 있다. 위의 기능 완료 기록과 별개로, 이 물리 격리 요구가 현재도 필요한지와 실제 검증 범위를 대조해야 한다.

## M4. AWS 운영과 MSP 관제

관제 화면에서 문제를 보고 원인을 좁힌 뒤 조치하고 보고하는 흐름을 완성한다. 거래 기능의 추가 개발보다 Linux·네트워크·DB 운영과 그 근거를 우선한다. 다만 거래 정합성이나 공개 전 안전성 문제를 방치한다는 뜻은 아니다. AWS 서비스와 기존 역할의 실제 사용 권한은 배포 전에 확인한다. 설정과 제약은 [배포 안내](../deploy/README.md)에 있다.

발표 목표 기준의 관리상 추정치는 약 80% 완료·20% 남음이다. 체크리스트의 정량 측정값이나 고가용성 달성률은 아니다. ALB·ASG, 장시간 측정, 백업 운영화, 발표 산출물이 남아 있어 권한 승인만으로 완료 처리하지 않는다.

1. 기존 네 호스트의 Linux 서비스·접근 제어·로그·관측과 DB 수동 전환·재편입, 격리 백업 복원은 실행했다. 반복 가능한 절차를 유지하고 초기 설치 명령을 운영 서버에 다시 실행하지 않는다.
2. 현재 백업을 서버 외부에 보관하고 새 Primary의 예약 백업·격리 복원 성공을 확인한다. 현재 로컬 백업을 볼륨 상실 대비 완료로 쓰지 않는다. 2026-09-23에 이를 위한 Docker 없는 백업 도구를 저장소에 만들고 로컬 컨테이너에서 확인했지만 학교에는 설치하지 않았다.
3. 실제 회원 주문과 하루 DB 증가량·메모리·CPU 크레딧·인증서 만료·관측 노드 자체 장애를 확인한다. 앱·DB·디스크의 발생·해제 보고는 검증했지만 외부 사이트 프로브는 남았다. 관측 노드를 감시하는 워치독과 bot-1을 포함한 경보 규칙은 저장소 템플릿만 있고 학교에 적용하지 않았다.
4. 학교 허용 후 조회 계층 ALB·ASG min 2 / desired 2 / max 3을 구성한다. 부하 증가·정상 등록·축소와 지연·오류·DB 연결 수를 측정한다. 현재 단일 쓰기 앱의 고가용성과 HTTPS 진입 조건도 따로 검토한다.
5. 다음 오전 9시 보고의 실제 예약 실행과 Teams 수신을 확인하고 AI 실패·전송 실패·중복 억제의 AWS 운영 조건을 점검한다. 이미 확인한 시험 전송과 로컬 회귀 테스트를 구분한다.
6. [사람용 보고서의 15분 구성](reports/프로젝트_이해하기.md#15분-발표-구성)을 발표 13분·시연 7분에 맞춰 다시 나누고, 실제 DB 복구·관제·보고 영상과 허용 후 ASG 영상을 준비해 HTML 발표 자료(PDF 백업)를 마감한다. 기존 PPTX는 도입 4장 초안이며 HTML 자료의 참고로만 쓴다.

비공개 시험 환경 준비와 외부 공개는 구분한다. 학교 사이트는 2026-09-19부터 공개돼 있다. 모호한 주문 커밋 뒤 멱등 키를 지우고 잔고 예약을 바로 풀던 경로는 2026-09-23 저장소 코드에서 V47 판정으로 고쳤고 Testcontainers 통합 시험으로 확인했다. 학교 app-1에는 아직 배포하지 않았고 장애 주입으로 확인하지도 않았다. 배포는 쓰기 정지 창이 필요하다. 신뢰 프록시와 관리 접근 통제도 확인한다. 현재 코드에서 확인한 위험과 단계별 선행 조건은 [0099의 AWS 준비 순서](reference/adr/0099-current-architecture.md)에 있다.

M4는 외부 서비스 접속, 근거가 있는 관제·Linux·네트워크 진단, ASG 증설·축소, DB 복구·백업 복원, Teams 기본 알림과 AI 일일·장애 보고를 실제로 확인해야 완료다. 자료 수집 실패를 정상으로 표시하지 않고 실제 조치 전후와 검증 범위를 남긴다. 기존 거래 무결성과 앱 리더 복구 목표는 유지하지만 DB 복구를 자동·무손실이라고 확대하지 않는다. [M4 하드닝 설계](reference/architecture/M4_하드닝설계.md)는 이전 세부 점검 자료이며 현재 범위는 이 로드맵과 ADR 0027을 따른다.

일정이 부족하면 별도 관제 UI 신설, 선택적인 RAID 실습, 거래 부가 기능, 과거 카오스 전수 재실행을 뒤로 둔다. Linux·네트워크 운영, 관제 신뢰성, AWS 자동 확장·DB 복구, Teams 보고의 핵심 흐름을 먼저 완성한다.

## 최근 변경에서 이어갈 것

[ADR 0022](reference/adr/0022-market-partitioned-command-journal.md)의 마켓별 주문 접수·채번 변경은 0~9단계 구현이 09-15까지 main에 병합됐다. 결과는 [09-14 측정](measurements/20260914.md)과 [09-15 측정](measurements/20260915.md)에 있다.

6단계 채번 전환과 9단계 이벤트 순번 확대는 로컬 시험 DB에 적용했다. 학교의 신규 빈 DB에는 V46까지 적용했다. 이전 앱·거래 행이 없었고 마이그레이션의 검사가 통과했다. 명령 축 래치는 적용하지 않았으며 향후 전환은 ADR 0022 7절의 조건으로 판단한다. 8단계 `commit_delay` 실험은 조건이 충족되지 않아 `NOT RUN`이다.

2단계 후속 정리로 전역 재생 진입점 제거, 인자 없는 `lastAppliedSeq()`의 이름 변경, 순번 축 검사가 남아 있다. 구체적인 범위는 해당 ADR을 따른다.

관리 콘솔의 `/admin/flow` 서비스 흐름과 `/admin/monitor` 지표 관제 화면은 시안이다. 구성도는 AWS 목표 구성처럼 그리고 로컬 Docker `exchange-chaos` 스택이 그 역할을 대신한다. 재생하는 사건의 순서와 간격은 로컬 측정 기록(stage9 E4, 09-23 증설 리허설, 09-12 Primary·Standby 전환)을 따르고 사건 사이의 값은 시뮬레이션이다. 09-12 전환 수치는 앱 없이 별도 스택에서 잰 값인데 화면은 앱이 멈추지 않는 것처럼 재생한다. compose에 없는 db-2와 CloudFront를 '실행'으로 그린다. 2026-09-24 사용자가 고른 관리 콘솔 디자인 개선 B안(관제센터형)을 구현해 서비스 흐름에 출처 칩, 상황 자막, 노드 핵심 수치, ASG 임계 막대, 상태 전이 강조, AI 운영 보고·Teams 자리(연결 전)를 더했다. 이 개편은 sim 데이터 원천의 웹 검사와 브라우저 캡처로만 확인했고 실값 연결과 발표 환경에서는 보지 않았다. 2026-09-25 보정 A부터 두 화면은 재생하지 않는 동안 관제 시뮬레이터의 한 판을 옮겨 관제센터와 같은 값을 그리고(관제 값 모드) 화면 머리에 '시뮬레이션' 표식을 둔다. 노드를 눌러 측정 기록 재생을 걸면 '재생 · 관제 값과 별개' 표식이 크게 서고, 초기화하면 관제 값으로 돌아온다. 두 화면은 관리 API를 거치지 않으므로 http 빌드에서도 지어낸 값을 보인다. 1단계는 이 시안이고, 채택하면 2단계에서 Docker 스택에 Standby를 붙여 버튼과 차트를 실제로 연결한 뒤 같은 화면을 AWS로 옮긴다. [0099](reference/adr/0099-current-architecture.md)는 관리 콘솔이 추이를 그리지 않고 Grafana로 딥링크하며 웹의 카오스 주입 화면을 제거했다고 적는다. 이 추이 금지 규칙을 정한 ADR은 따로 없고, 근거로 들던 [ADR 0032](reference/adr/0032-operator-console.md)는 Grafana 기본 관제와 별도 운영 콘솔만 다룬다([관리자 설계 7-10](reference/product/관리자_설계.md)). 이 시안은 그 규칙과 카오스 화면 제거 방향과 부딪치므로 채택하려면 규칙부터 다시 정한다. 사용자는 2026-09-24 서비스 흐름 화면을 채택해 실제 값과 연동하고 발표 실험을 그 화면에서 하기로 정했다(위 09-24 문단). 그러므로 연동 전에 추이 금지 규칙부터 다시 정해야 한다. 지표 관제 화면의 채택·보존·폐기는 사용자 결정 대기다. 학교 AWS에는 ALB·ASG·앱 2·3번 노드가 없어 같은 상황을 그대로 보일 수 없다.
