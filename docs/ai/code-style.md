# 코드와 주석 작성 기준

소스 코드나 코드 주석을 바꿀 때 읽는다. 기존 26절의 세부 기준을 보존했다. 사람용 설명 문서를 쓸 때는 `docs/ai/writing.md`를 따른다.

## 26. 코드와 주석 작성 기준

코드는 사람이 직접 유지보수하는 저장소의 기존 코드처럼 작성한다.

목표는 코드가 복잡해 보이는 것이 아니라 요구사항을 가장 작은 변경으로 정확하게 해결하는 것이다.

추상화, 주석, 방어 코드, 리팩터링은 필요성이 있을 때만 추가한다.

### 우선순위

정확성, 기존 계약과 일관성, 단순성, 읽기 쉬움, 변경 범위 최소화, 재사용성 순이다.

미래의 가능성을 이유로 현재 필요하지 않은 구조를 만들지 않는다. 현재 요구사항을 해결하는
가장 단순한 구조를 먼저 선택한다.

### 기존 코드 우선

새 코드를 작성하기 전에 주변 코드를 읽는다.

이름, 파일 구조, 함수 크기, 예외 처리, 상태 관리, 테스트 방식, 로깅, 의존성 사용을
기존 저장소와 맞춘다.

같은 문제를 기존 코드가 이미 해결하고 있으면 그 방식을 따른다. 개인적으로 더 좋아 보이는
패턴이 있다는 이유로 주변 코드를 재작성하지 않는다.

### 변경 범위

요청한 문제와 직접 관련된 코드만 변경한다.

금지. 관련 없는 리팩터링, 파일 전체 포맷 변경, 이름 일괄 변경, 사용하지 않는 코드 정리,
주변 코드 스타일 통일, 미래 기능을 위한 선행 구조 추가.

리팩터링이 현재 수정의 안전성을 위해 반드시 필요하면 그 범위만 수행한다.

### 추상화

중복이 있다는 이유만으로 즉시 추상화하지 않는다.

다음 중 하나 이상을 만족할 때 만든다.

- 같은 규칙이 실제로 여러 곳에서 반복됨
- 하나의 변경이 여러 구현에 동시에 반영돼야 함
- 도메인 개념으로 독립된 이름을 가짐
- 테스트 경계를 분리할 실질적 이유가 있음
- 의존성 방향을 지키기 위해 필요함

한 번만 쓰는 추상화는 특별한 이유가 없으면 만들지 않는다.

금지 예. 한 번 쓰는 interface, 한 번 쓰는 factory, 단순 전달 wrapper, 이름만 바꾼 helper,
getter를 감싼 getter, 의미 없는 manager·handler·processor 계층.

추상화보다 명확한 직접 구현을 우선한다.

### 함수와 이름

함수는 하나의 명확한 책임을 가진다. 줄 수를 줄이려고 분리하지 않는다.

handle, process, execute, manage, perform, doWork, helper, util 같은 이름을 남용하지 않는다.
도메인 동작을 이름에 드러낸다. `processOrder()` 보다 `matchLimitOrder()` 다.

변수는 짧지만 의미가 분명한 이름을 쓴다. 주석이 있어야 이해되는 이름을 만들지 않는다.
지나치게 긴 설명형 이름도 피한다.

정본의 용어와 코드의 용어를 다르게 만들지 않는다.

### 제어 흐름

정상 경로가 눈에 잘 보이게 쓴다. 불필요한 중첩을 줄인다. 예외 조건은 조기에 반환할 수 있다.

한 번만 쓰이고 자체로 읽기 쉬운 조건을 변수로 분리하지 않는다.

### 방어 코드

실제로 발생 가능한 실패를 처리한다. 근거 없는 가능성을 가정해 방어 코드를 추가하지 않는다.

금지 예. 계약상 null이 불가능한 값에 반복적인 null 처리, 도달할 수 없는 상태에 대한 임의
fallback, 원인을 숨기는 catch-all, 실패를 정상값으로 바꾸는 처리, 문제를 숨기는 빈 catch,
근거 없는 재시도.

계약 위반은 조용히 보정하기보다 명확하게 실패시키는 것을 우선한다.

### 예외 처리

예외를 잡을 이유가 있을 때만 잡는다. 잡은 예외는 복구, 도메인 예외로 변환, 컨텍스트를
추가해 재전파, 호출자가 요구하는 계약으로 변환 중 하나를 한다.

로그만 남기고 같은 예외를 다시 던지는 코드는 특별한 이유가 없으면 만들지 않는다.

원래 원인을 잃지 않는다.

### 로그

운영자가 판단할 정보가 있을 때만 남긴다. 함수 진입과 종료를 습관적으로 남기지 않는다.
성공 경로의 반복 로그를 만들지 않는다.

가능하면 어떤 사건인가, 어떤 객체와 관련됐는가, 실패나 상태 변경의 원인은 무엇인가를 담는다.

비밀번호, 토큰, 서명 원문, 개인정보는 로그에 남기지 않는다.

### 금지 패턴

필요 없는 abstraction, wrapper 위의 wrapper, 의미 없는 interface, 한 번 쓰는 factory,
거대한 util 파일, 모든 값을 config로 만드는 구조, 실제 요구 없는 확장 포인트, 과도한 builder,
단순 DTO를 위한 불필요한 mapper 계층, 예외를 숨기는 fallback, 의미 없는 catch,
한 메서드마다 한 줄짜리 주석, 모든 public 함수에 동일한 형식의 docstring,
파일 시작부의 장문 설명, 코드보다 긴 주석, 리뷰 과정을 설명하는 주석.

### 의존성 추가

새 라이브러리, npm 패키지, Gradle 의존성을 필요 없이 추가하지 않는다.

추가 전 확인한다.

- 기존 의존성으로 해결 가능한가
- 직접 구현보다 의존성이 실제로 단순한가
- 유지보수되고 있는가
- 라이선스 문제가 없는가
- 정적 export 또는 현재 런타임과 호환되는가

한 기능 때문에 무거운 프레임워크를 추가하지 않는다.

의존성 버전 변경은 해당 변경에 필요한 범위로 제한한다.

### 생성물과 임시 파일

자동 생성 파일을 사람이 직접 수정하지 않는다.

빌드 결과, 로그, 패킷 캡처, 테스트 결과를 소스 디렉터리에 흩어 놓지 않는다.

임시 검증 산출물은 `artifacts/` 또는 지정된 증거 디렉터리에 저장한다.

재생성 가능한 파일은 정본으로 취급하지 않는다. 불필요한 생성물은 커밋하지 않는다.
명시적으로 정본으로 지정한 생성 문서는 예외다. [문서 작성 기준](writing.md)의 원본·재생성 절차를 따른다.

### 테스트 독립성

테스트는 실행 순서에 의존하지 않는다. 다른 테스트가 만든 데이터에 의존하지 않는다.
실제 인터넷 연결에 의존하지 않는다.

시간, 난수, 포트, 외부 환경 때문에 간헐적으로 성공하거나 실패하는 테스트를 정상으로
취급하지 않는다.

flaky 테스트를 단순 재시도로 숨기지 않는다. 원인을 찾고 제거한다.

### 삭제와 폐기

사용하지 않는 코드를 무기한 남기지 않는다.

현재 쓰이지 않고 복구가 Git으로 가능한 코드는 삭제한다.

죽은 코드에 주석을 붙여 보존하지 않는다. 주석 처리한 대규모 코드를 남기지 않는다.

현재 구현에서 쓰지 않는 파일을 혹시 몰라서 유지하지 않는다.

### 리팩터링 판단

코드가 동작한다는 이유만으로 리팩터링하지 않는다.

변경하기 어려움, 같은 버그가 반복됨, 중복된 규칙이 서로 달라짐, 테스트가 불가능함,
의존성 경계가 깨짐, 현재 작업을 안전하게 구현하기 어려움 중 하나가 실제로 발생할 때 한다.

"더 깔끔해 보인다"는 이유만으로 구조를 바꾸지 않는다.

### 주석의 목적

코드는 가능하면 이름과 구조만으로 읽히게 작성한다. 주석은 예외적으로 쓴다.

주석의 목적은 코드를 번역하는 것이 아니라, 코드만 보고는 알 수 없는 이유나 제약을
보존하는 것이다.

### 반드시 주석을 검토할 상황

다음 코드는 주석이 필요한지 반드시 검토한다. 필요하면 이유만 짧게 남긴다.

**동시성.** 락, fencing, 트랜잭션 순서처럼 실행 순서를 잘못 바꾸면 안전성이 깨지는 코드.

허용. `// 커밋 직전에도 리더 권한을 확인해 승격 중 stale write를 막는다.`

`lock 획득`, `transaction 시작` 같은 동작 설명은 쓰지 않는다.

**데이터 무결성.** 겉으로는 불필요해 보이지만 멱등성, 원장 보존, 중복 방지를 위해 필요한 코드.

허용. `// 재시도는 새 주문이 아니라 기존 client_order_id로 수렴해야 한다.`

**보안 경계.** 인증, 권한, 서명, secret 처리처럼 제거하거나 우회하면 경계가 깨지는 코드.

허용. `// 관리자 권한 검사는 UI가 아니라 서버 경계에서 다시 수행한다.`

보안 구현의 상세 원리나 공격 방법을 장황하게 기록하지 않는다.

**외부 제약과 런타임 특성.** 프레임워크, 브라우저, DB, 클라우드의 비자명한 제약 때문에
평범하지 않은 구현을 쓴 경우.

허용. `// 정적 export에서 런타임 route 처리를 쓸 수 없어 빌드 시 경로를 생성한다.`
`// outline은 overflow 컨테이너에서도 포커스 링이 잘리지 않는다.`

**성능상 의도적 선택.** 비효율로 보이지만 측정 결과 때문에 의도적으로 선택한 구현.

허용. `// 전체 재계산보다 이 경로가 병목 구간의 lock 보유 시간을 줄인다.`

**단위와 경계값.** 숫자의 의미를 이름만으로 알 수 없고 잘못 변경하기 쉬운 경우.

나쁜 예. `// 30초`
좋은 예. `// 리더 장애 RTO 계약 상한`

가능하면 숫자의 의미를 변수명과 타입으로 표현하고 주석은 마지막 수단으로 쓴다.

**호환성 우회.** 버그, 라이브러리 제약, 브라우저 차이 때문에 일반적이지 않은 우회가 필요한 경우.

무엇을 피하기 위한 코드인지, 제거 가능한 조건이 있다면 그 조건만 적는다.
변경 과정이나 조사 일지는 적지 않는다.

### 금지하는 주석

- 코드 동작을 그대로 설명, 함수명이나 변수 의미를 다시 설명
- 작업 과정, 검토 과정, 스스로 한 판단 과정
- 변경 이력, 이전 구현 설명, 수정 전후 비교
- 리뷰 severity
- 당연한 문법 설명

금지 예. `// 주문을 저장한다` `// 배열을 순회한다` `// 에러가 있으면 반환한다`
`// critical 반영` `// 초안에서는 이 값을 사용했다` `// 검토자가 발견한 문제를 교정했다`

### 변경 이력 표현 금지

Git이 보존하는 정보를 코드에 다시 기록하지 않는다.

주석에서 다음 표현을 쓰지 않는다. 초안, 수정, 수정본, 기존, 이전, 폐기, 반영, 교정,
v1에서, v2에서, 1차, 2차, reviewer, critical, high.

판단 기준은 Git이 아는 것을 주석이 다시 말하는가다. 현재 상태 서술은 정당하고
이력 서술이 위반이다.

### 길이

일반 주석은 한 줄이 기본이고 두 줄까지 허용한다.

세 줄 이상 필요한 설명은 셋 중 하나로 처리한다. 코드를 더 명확하게 변경, 정본 문서에
이유 기록, 짧은 주석에서 정본 위치 참조.

코드에 설계 문서를 복사하지 않는다.

### 숫자 근거

모든 측정값을 주석에 적지 않는다. 수치가 현재 값을 선택하는 직접적인 이유일 때만
최소한으로 기록한다.

좋은 예. `/* 다크 surface에서 3:1을 확보하기 위한 경계색 */`
과한 예. `/* 기존 2.07:1이었고 1차 검토에서 실패했으며 새 값은 surface 3.68:1... */`

상세 실측 결과는 설계 또는 검증 문서에 둔다.

### public API 문서화

모든 public 함수에 기계적으로 Javadoc이나 docstring을 달지 않는다.

다음 경우에만 문서화를 우선한다.

- 호출자가 지켜야 하는 사전 조건이 있음
- 반환값에 비자명한 의미가 있음
- 예외 계약이 중요함
- 멱등성 또는 트랜잭션 의미가 있음
- 외부 모듈이 사용하는 안정된 API임

함수 이름과 타입만으로 충분한 내용은 반복하지 않는다.

### TODO

실제 후속 작업이 존재할 때만 쓴다. 가능하면 이슈나 조건을 붙인다.

허용. `// TODO(#142): WebSocket 재연결 정책 적용 후 fallback 제거`
금지. `// TODO: 나중에 개선` `// TODO: 최적화` `// TODO: 리팩터링`

### 테스트

테스트 내부에 긴 시나리오 설명을 주석으로 반복하지 않는다.

given, when, then 주석을 기계적으로 붙이지 않는다. 테스트 이름이 검증하는 동작을 표현하면
주석이 필요 없다.

하나의 테스트에서 너무 많은 독립 동작을 검증하지 않는다. mock은 필요한 경계에만 쓴다.
구현 세부사항보다 계약과 관측 가능한 동작을 검증한다.

### CSS

섹션 제목과 비자명한 토큰 선택 이유만 남긴다.

허용. `/* 시스템 성공 전용. 가격 방향에 쓰지 않는다. */`
`/* overflow 컨테이너에서 포커스 링 클리핑을 피하려고 outline을 쓴다 */`

색상 변경 역사, 접근성 실측 전체 표, 검토 과정은 CSS에 기록하지 않는다.

### SQL

쿼리만 보고 알 수 없는 데이터 의미와 검증 의도만 남긴다. SELECT, JOIN, GROUP BY 문법을
설명하지 않는다.

검증 SQL은 무엇을 위반으로 보는지 남길 수 있다.

허용. `-- 결과가 존재하면 하나의 client_order_id가 둘 이상의 주문으로 확장된 상태다.`

### 주석의 신뢰성

코드 변경으로 주석의 전제가 바뀌면 같은 변경에서 주석도 수정하거나 삭제한다.

주석을 사실처럼 남겨두고 구현만 변경하지 않는다.

검증되지 않은 추측을 주석으로 고정하지 않는다.

주석이 계약을 서술하면 그 내용이 정본과 일치해야 한다. 어긋나면 `docs/ai/workflow.md` 11절의 정본 충돌이다.

틀린 주석은 주석이 없는 것보다 위험하다.

### 주석 제거 기준

코드를 수정할 때 기존 주석도 함께 검토한다. 다음 상태의 주석은 삭제하거나 수정한다.

- 현재 코드와 불일치
- 현재 정본과 불일치
- 이미 코드 구조로 명확해짐
- Git 이력을 설명하고 있음
- 더 이상 존재하지 않는 제약을 설명함
- TODO가 해결됐는데 남아 있음

### 소유 분리

같은 내용을 여러 곳에 복제하지 않는다.

- 왜 현재 코드가 이 형태여야 하는가: 필요한 경우 코드 주석
- 전체 설계가 왜 이렇게 됐는가: `docs/`
- 과거에 무엇이 바뀌었는가: Git
- 실제 측정값이 무엇인가: 검증 산출물

### 최종 자가 검토

코드 작성 후 확인한다.

- 이 변경에 필요 없는 코드가 추가됐는가
- 한 번만 쓰는 추상화를 만들었는가
- 이름으로 설명할 수 있는 부분에 주석을 달았는가
- Git이 보존할 변경 이력을 주석에 썼는가
- 계약에 없는 방어 코드를 추가했는가
- 실제 요구보다 범위를 넓혔는가
- 기존 저장소 스타일보다 지나치게 정교한 구조를 만들었는가
- 같은 내용을 코드, 주석, 문서에 반복했는가

해당하면 완료 전에 줄이거나 제거한다.
