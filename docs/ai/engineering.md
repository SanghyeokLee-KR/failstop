# 구현과 검증 기준

코드, 배포 설정, 장애 시험을 바꿀 때 읽는다. 아래 절 번호는 기존 작업 지침에서 유지했다.

현재 진행 상황은 `docs/ROADMAP.md`, 기술 계약은 `docs/reference/contracts/`에서 확인한다. 문서의 목표와 실제로 검증한 결과를 구분한다.

## 1. 최우선 판단 기준

현재 역할은 고객사의 클라우드·서버 등 IT 인프라를 구축·운영·관리하는 엔지니어다.
약 3개월간 직접 개발한 가상 거래소를 운영 대상으로 삼고 Linux 서버 운영을 가장 중요하게 다룬다. 최신 범위는
[ADR 0027](../reference/adr/0027-msp-operations-and-autoscaling.md)과 로드맵을 따른다.

1. Linux 계정·권한·서비스·로그·디스크·네트워크의 설정과 장애 진단, 이를 바탕으로 한 외부 접속 가능한 AWS 서비스.
2. 원자료가 맞는 관제, 수집 실패 감지와 운영자에게 도달하는 알림.
3. DB·스토리지 운영, 백업 복원과 장애 진단·복구.
4. 분산 가능한 조회의 EC2 자동 확장과 축소 검증.
5. 근거를 정리한 AI 일일·장애 보고와 Microsoft Teams 전달.

모든 단계에서 데이터 무결성, 보안·접근 통제, 지원금 40만 원의 비용 제약을 지킨다.
이 조건을 점수 가중치로 상쇄하지 않는다. 거래 안전성에 필요한 수정은 계속하되,
부가 기능과 화면 장식, 새 카오스 기능이 위 운영 업무보다 앞서지 않게 한다.
기존 Docker 카오스와 검증 자산은 보존하고 필요한 부분을 재사용한다.


## 2. 시스템 엔지니어링 원칙

이 프로젝트는 애플리케이션 구현만으로 완료하지 않는다.

최종 산출물은 다음 질문에 근거로 답할 수 있어야 한다.

- 서비스는 실제로 어디에 배포되는가
- 외부 사용자는 어떻게 접속하는가
- 서버가 죽으면 어떻게 되는가
- 대표 노드가 고립되면 어떻게 되는가
- 복구에는 몇 초가 걸리는가
- 장애 중 데이터가 유실되지 않는가
- 같은 주문이 중복 처리되지 않는가
- 이전 대표가 복귀해 잘못된 쓰기를 하지 않는가
- 장애를 어떻게 탐지하는가
- 로그와 메트릭은 어디에서 확인하는가
- 장애 원인을 어느 계층으로 좁히는가
- 배포에 실패하면 어떻게 복구하는가
- 백업 데이터는 실제로 복원 가능한가
- 비밀 정보는 어떻게 관리하는가
- 월 운영 비용은 얼마인가
- 비용이 증가하면 어느 자원이 원인인가
- 부하가 증가하면 어느 지점이 먼저 한계에 도달하는가

문서에 설계가 존재한다는 이유만으로 완료로 판정하지 않는다.

검증 가능한 항목은 실제 실행 결과, 로그, 메트릭, 패킷, 데이터 조회 결과로 증명한다.


## 14. 핵심 불변 규칙

다른 구현 편의를 위해 완화하지 않는다.

### 금액과 수량

DB 타입은 `NUMERIC(40,18)`이다.

백엔드 금액 계산에 float, double을 쓰지 않는다.

프론트에서는 금액과 수량을 문자열로 전달하고 보존한다. JavaScript `number` 기반 금액 계산 금지.

### 주문 멱등성

주문 생성에는 `client_order_id`가 필수다.

같은 논리적 주문을 재시도할 때 같은 키를 쓴다. 응답을 받지 못했다는 이유로 새 키를 만들지 않는다.

동일 키 요청은 하나의 논리적 주문으로 수렴해야 한다.

### 리더 안전성

앱 리더는 하나이며, 각 마켓의 매칭은 단일 라이터가 처리한다.
서로 다른 마켓의 처리 루프를 하나의 전역 라이터로 오해하지 않는다.
동시에 둘 이상의 쓰기 가능한 앱 리더가 존재하면 안 된다.

전 쓰기 경로가 `assert_current_leader(holder, epoch)`를 통과해야 커밋된다. 저널 삽입에
한정되지 않는다. 체결, 취소, catch-up, 스냅샷을 포함한 모든 엔진 기원 쓰기가 대상이다.

split-brain 차단 주장은 이 계약이 성립할 때에 한한다.

복귀한 구 대표의 stale write는 허용하지 않는다.

### 데이터 무결성

장애와 재시도 때문에 자산 생성, 자산 소실, 이중 체결, 이중 주문, 원장 불일치가 발생하면 안 된다.

관련 불변식은 `docs/reference/contracts/하네스_검증설계.md`를 따른다.

### 외부 API

런타임 외부 API 의존을 금지한다. 외부 데이터 수집은 허용된 seed 단계에서만 한다.

외부 서비스 장애가 거래소 런타임 필수 경로에 영향을 주면 안 된다.

### 시간

비즈니스 로직에서 시스템 현재 시각을 직접 읽지 않는다. 시간이 결과에 영향을 주는 로직은
주입 가능한 시간 소스를 쓴다.

DB, JVM, 컨테이너, 클라우드의 시간대 차이를 가정하지 않는다. 저장과 전송의 시간 기준은
정본 계약을 따른다.

매칭엔진의 결정론을 현재 시각으로 깨지 않는다.

### 랜덤

재현성이 필요한 로직에서 숨은 난수를 쓰지 않는다.

테스트와 시뮬레이션에서 난수를 쓰면 seed를 고정하거나 기록한다.

매칭, 원장, 재생 결과에 비결정적 난수가 영향을 주지 않는다.

### 설정값

환경마다 달라지는 값을 소스 코드에 박지 않는다. 주소, 포트, timeout, 외부 접속 URL,
인프라별 값, 비밀 정보는 설정 또는 정본이 소유한다.

반대로 모든 값을 설정으로 만들지 않는다. 도메인 불변식과 변경할 이유가 없는 상수는
코드 또는 정본에 둔다.


## 15. 프론트엔드 규칙

웹은 고정형 데스크톱 전용이다. 최소 폭 1280px. 그보다 좁으면 가로 스크롤을 허용한다.

반응형 리플로우, 모바일 대응, 모바일 전용 컴포넌트를 구현하지 않는다.

`docs/reference/contracts/프론트_디자인시스템.md` 본문에 남은 `모바일:` 하위 항목은 폐기 표기다. 구현 근거로 삼지 않는다.

Next.js 정적 export와 호환되지 않는 기능을 추가하지 않는다. `npm run build` 후 `out/`이
생성돼야 하고, 배포된 웹은 Node 서버를 요구하지 않는다.

`NEXT_PUBLIC_*` 값은 빌드 타임에 번들로 인라인된다. 도메인이 정해지기 전에는 배포용 웹을
빌드할 수 없다.

프론트 코드의 하드코딩 hex 색상을 금지한다. 색상은 디자인 토큰을 쓴다. 코인 브랜드 색을
데이터로 표현하는 경우만 예외이며, 그 데이터를 UI 스타일 토큰으로 재사용하지 않는다.


## 16. 디자인 기준

특정 상용 서비스는 품질 참고 자료로만 쓴다. 브랜드 색상, 로고, 고유한 형태, 카피, 명칭,
브랜드 말투를 복제하지 않는다.

프로젝트 아이덴티티는 `tokens.css`로 정의한다.

검토 기준. 정보 위계, 화면 밀도, 여백, 로딩 상태, 빈 상태, 오류 상태, 실시간 갱신의 시각적
안정성, 키보드 접근성, 색 대비, reduced-motion.

일반 텍스트 대비는 4.5:1 이상을 기준으로 한다.

상승과 매수는 Red 계열 토큰, 하락과 매도는 Blue 계열 토큰을 쓴다.

색만으로 표현하지 않는다. 부호, 화살표, 텍스트, 아이콘 중 하나 이상을 함께 쓴다.


## 17. 인프라 및 배포 필수 조건

외부에서 실제 접속 가능해야 한다. 학교 필수 조건이고 §1 우선순위 1번이다.

다음을 구현 또는 검증한다.

- HTTPS
- DNS 또는 외부 접속 주소
- 애플리케이션 이미지
- 환경 설정 분리
- 비밀 정보 분리
- 자동 또는 재현 가능한 배포
- 배포 실패 대응
- 서비스 재시작
- 장애 복구
- 로그 수집
- 메트릭 수집
- 백업
- 복원
- 비용 산정

수동으로 한 번 성공한 배포만으로 완료하지 않는다. 다시 수행 가능한 절차가 있어야 한다.

상시 서비스와 파괴 실험의 실행 환경을 구분한다. 커널 계층 주입은 검증 환경에서만 한다.
상시 서비스에서 리더를 종료하는 시험은 사용자에게 승인된 대상과 범위에서만 수행한다.
복구 목표 시간이 짧다는 이유로 장애 주입이 자동 승인되지는 않는다.


## 18. 보안 기준

다음을 저장소에 커밋하지 않는다.

- 실제 비밀번호, API 키, 개인 키
- 클라우드 자격 증명, 운영 토큰
- 실제 개인정보

비밀 정보는 환경 변수 또는 지정된 비밀 관리 수단을 쓴다. 예제 값은 실제 자격 증명과
구별 가능해야 한다.

운영 서버의 공인 IP를 문서나 도면에 박지 않는다. 심사자 제출 자료에도 넣지 않는다.

관리 기능에는 일반 사용자와 구분된 접근 통제를 적용한다.

HTTPS를 쓴다. 필요 이상의 포트를 외부에 노출하지 않는다. 관리 평면, actuator, 하네스 API는
외부에 노출하지 않는다. 관리 접속은 배포 절차에 정의된 비공개 경로를 사용한다.
SSM 포트 포워딩을 사용할 때는 해당 계정과 인스턴스의 실제 권한을 확인한다.
권한이 없다는 이유로 관리 포트를 공개하지 않는다.

권한은 최소 권한 원칙을 따른다.

"설정했다"는 증거가 아니다. 금지된 조작을 실제로 시도해 거부 코드가 나온 기록만 증거로 인정한다.
예. DB 롤 분리는 앱 계정 DDL 시도에서 SQLSTATE 42501이 나와야 한다.


## 19. 관측성 기준

서비스 상태를 외부에서 확인할 수 있어야 한다.

최소한 다음을 관측할 수 있어야 한다.

- 애플리케이션 생존 상태
- 요청 오류
- 응답 지연
- 주요 시스템 자원
- 대표 노드 상태
- 장애 전환
- 주요 데이터 오류

장애 시험에서 로그만 남았다는 이유로 원인이 증명됐다고 판정하지 않는다. 필요하면 메트릭,
DB 조회, 패킷 캡처를 함께 쓴다.

장애 원인을 계층으로 좁힐 수 있어야 한다. L3 도달, L4 연결, L7 응답을 각각 재는 프로브를 둔다.
"안 돼요"를 계층으로 번역하는 것이 이 축의 목적이다.


## 20. 백업과 복구

백업 파일이 생성된 것만으로 PASS로 판정하지 않는다. 실제 복원 시험을 수행해야 한다.

복원 후 다음을 확인한다.

- 서비스 기동
- 주요 데이터 존재
- 데이터 무결성
- 거래 관련 불변식

복원하지 않은 백업은 복구 가능성이 검증되지 않은 상태로 기록한다.


## 21. 비용 기준

클라우드 자원에는 비용 근거를 남긴다.

최소 기록 항목. 컴퓨팅, 데이터베이스, 스토리지, 네트워크, 로드밸런서, 로그 및 모니터링,
도메인, 백업.

월 예상 비용을 산정한다. 고비용 구조를 선택한 경우 선택 이유를 기록한다.

현재 규모보다 과도한 인프라를 사용하지 않는다. 고가용성과 비용 사이의 절충 근거를 남긴다.

단가는 공식 요금표 판본을 근거로 한다. 3자 요약 사이트 수치를 쓰지 않는다.

크레딧이 곧 가용성이다. 소진되면 서비스가 멈춘다. 비용 계획은 현재 배포 구성과
공식 요금표를 기준으로 갱신한다. 폐기한 기획안의 금액을 현재 비용으로 인용하지 않는다.

AWS는 사용자 설명에 따라 IAM 외 서비스를 사용할 수 있을 것으로 예상한다.
IAM Deny를 직접 설정할 수 있다고 가정하지 않는다. 실제 권한과 비용 통제 수단은 배포 전에 확인한다.


## 22. 증거 규칙

성능, 데이터 무결성, 복구 성공은 실행 결과와 기계 판정으로 뒷받침한다.
수치를 쓸 때는 어떻게 쟀는지 함께 남긴다. 설계 의도와 아직 시험하지 않은 목표를
실행 결과처럼 쓰지 않는다.

### 상태 어휘

`명령을 실행했다`와 `통과했다`를 구분한다.

- PASS: 실행 후 성공 확인
- FAIL: 실행 후 실패 확인
- NOT RUN: 실행하지 않음
- BLOCKED: 외부 조건 때문에 실행 불가
- N/A: 해당 검증이 구조적으로 적용되지 않음. 근거를 남긴다

SKIP을 PASS의 의미로 쓰지 않는다.

### 공허 통과 금지

판정 대상이 없는데 통과로 나오는 구조를 만들지 않는다.

빈 테이블에 LEFT JOIN을 걸면 위반 0행이 나오고 통과로 보인다. 부하가 실리지 않은 주행도
임계를 넘지 않아 통과로 보인다. 둘 다 아무것도 판정하지 않은 것이다.

모든 판정에 양성 증거 축을 함께 건다. `count > 0` 형태의 하한이다. 그 주행이 실제로 돌았고
판정 대상이 존재했다는 것을 먼저 증명한다.

실제 사고에서 나왔다. 계측 결함 다섯 건이 전부 통과로 보인 적이 있다.

### 판정 경로 우선 의심

실험이 FAIL이면 구현과 함께 판정 경로도 확인한다. 판정기를 의심한다는 이유로
실제 실패를 무시하거나 기준을 완화하지 않는다.

판정기 결함이 반복해서 나왔다. 반환값이 파이프라인에 섞여 비교가 항상 참이 된 적, 임계가
빈 배열이라 종료코드로 실패를 못 낸 적, 하한이 50%라 51% 주행도 통과시킨 적이 있다.

### 인용 확인

커밋 해시, 파일 경로, 절 번호를 인용할 때는 실재를 확인하고 쓴다.
`git cat-file -e <해시>`, 파일 존재 확인, 해당 절 열어보기.

### 미확인 표기와 해제

재현되지 않은 값은 `미확인`으로 적는다. 측정 술어가 바뀌면 이전 수치는 인용 자격을 잃는다.

반대 방향 실패도 있었다. E4 RTO는 실측이 끝났는데 정본이 08-25 시점에 멈춰 있어 오래
미확인으로 남았다. 증거 파일이 저장소에 있는데 문서가 모르는 상태였다.

미확인 표기는 실측이 들어오면 즉시 해제한다. 실험 실행과 정본 갱신을 같은 작업으로 묶는다.


## 23. 장애 검증 기준

장애를 주입했다는 사실만으로 시험이 성립하지 않는다.

1. 장애가 목표 계층에 실제 도달했는가
2. 시스템이 계약된 방식으로 반응했는가
3. 복구 시간이 기준을 만족했는가
4. 데이터 무결성이 유지됐는가
5. 장애 제거 후 자력 복구했는가

필요하면 로그, 메트릭, DB 조회, tcpdump, 재전송, RST, 타임아웃, 프로세스 상태,
컨테이너 상태를 증거로 남긴다.

원인 계층을 확인할 수 없는 장애 시험은 증거가 불완전한 것으로 판정한다.

프록시 모사와 커널 주입을 구분해 적는다. Toxiproxy는 프록시 레벨이라 커널 큐 거동을
재현하지 않는다. `tc netem`은 커널이다. 둘을 같은 말로 쓰면 증명 범위를 과장하게 된다.


## 24. reviewer 판정

판정은 셋만 쓴다.

### PASS

병합을 차단하는 문제가 없음. 병합 가능.

### PASS WITH FOLLOW-UP

현재 변경의 정확성과 안전성에 문제가 없음. 비차단 후속 작업만 존재함.

후속 작업은 별도 이슈 또는 작업 항목으로 기록한다.

다음이 남아 있으면 쓸 수 없다. FAIL로 판정한다.

- 변경 범위에 필요한 테스트 실패 또는 미실행
- 계약 불일치
- 데이터 무결성 위험
- 보안 문제
- 장애 복구 기준 미충족
- 필수 검증 누락
- 스타일 게이트 실패

### FAIL

수정 전 병합 금지. 수정 후 reviewer 재검토가 필요함.

### 판정의 조건

통과도 판정이다. 결함이 없으면 억지로 만들지 말고 통과 사유를 적는다.

증거 없는 지적을 하지 않는다. 모든 지적에 파일 경로, 행, 실제 인용을 붙인다. 추측이면
추측이라고 쓴다.

동작하는 코드를 취향으로 반려하지 않는다.

구현 역할은 자기 점검을 독립적인 reviewer 판정으로 기록하지 않는다.
별도 검토의 적용 범위와 역할 분리의 한계는 `docs/ai/workflow.md` 5절과 7절을 따른다.


## 30. 실행 환경

Windows와 PowerShell을 기준으로 개발한다. 정확한 빌드 명령과 도구 버전은
`server/README.md`, `web/README.md`, 각 빌드 설정에서 확인한다.

- 서버 빌드·테스트는 현재 체크아웃의 `server/`에서 PowerShell로 실행한다.
  한글 경로를 거친 클래스패스 오류가 있었으므로 경로 문제가 의심되면 `C:\dev\exchange` 등
  실제 프로젝트를 가리키는 ASCII 경로를 사용한다. 설정되지 않은 환경 변수에 의존하지 않는다.
- 하네스 `.ps1`은 pwsh 7 기준이다. PowerShell 5.1은 BOM 없는 UTF-8 한글을 오독한다.
- PowerShell 고급 함수에 `[Parameter()]`를 붙이면 단문자 플래그가 `-Verbose`, `-Debug`에
  접두 일치해 소리 없이 사라진다. CLI 래퍼에 쓰지 않는다.
- 카오스 스택 기동에는 `--env-file harness/.env.chaos`가 필수다. 빠뜨리면 마스터키가 비어
  전면 500이 난다.
- dev 서버와 빌드가 같은 체크아웃의 `.next`를 동시에 사용하지 않게 한다.
  실행 중인 서버를 확인하고 빌드 전 종료하거나 별도 체크아웃에서 빌드한다.
  현재 정적 export 설정에서는 `distDir` 변경이 dev 작업 디렉터리 격리 수단이 아니다.
  `web/next.config.ts`의 제약을 확인한다.

Flyway는 체크섬을 검증한다. 이미 적용된 마이그레이션 파일을 수정하지 않는다. 주석 한 줄도
안 된다. 고치면 전 노드가 기동하지 않는다. 실제로 그렇게 됐다. 스키마 변경은 새 마이그레이션으로
추가한다.

체크섬이 어긋나면 적용 이력, 원래 파일, 실제 DB 상태를 먼저 대조한다.
`flyway repair`는 스키마를 원래 상태로 복구하는 명령이 아니다. 빌드를 통과시키기 위해
자동 실행하거나 이력 행을 지우지 않는다. 복구 조치가 필요하면 영향과 승인 범위를 확인한다.


## 31. 빌드 검증

변경한 담당 영역의 필수 검증이 실패한 상태로 완료 처리하지 않는다.

### server

```
.\gradlew.bat build
```

현재 체크아웃의 `server/`에서 PowerShell로 실행한다. Linux에서는 `./gradlew build`를 쓴다.
통합 테스트는 Testcontainers를 사용하므로 Docker 실행 상태도 확인한다.

### web

```
npm run build
```

`web/`에서 실행하고 `web/out/` 생성 여부를 확인한다. 동작 변경은 `npm test`,
전체 TypeScript 검증은 `npx tsc --noEmit`으로 확인한다. UI 표현을 바꿨으면 실제 화면도 본다.

### style

```
pwsh -NoProfile -File scripts/check-style.ps1
pwsh -NoProfile -File scripts/check-doclinks.ps1
```

문서만 바꾼 작업은 관련 링크, 문체, 기술 사실의 보존을 검사한다.
서버와 웹 빌드, 장애 시험은 변경이 영향을 주는 경우에 실행한다.
새 파일은 Git diff 기반 스타일 검사에서 빠질 수 있으므로 경로를 지정해 함께 검사한다.
CI의 실제 명령은 `.github/workflows/`를 따른다. 문서의 명령 목록만으로 전체 게이트를
실행했다고 주장하지 않는다.


## 32. 완료 정의

작업 완료는 코드 작성 완료를 의미하지 않는다.

- 관련 정본 확인
- 구현 완료
- 정본과 구현 일치
- 필요한 테스트 실행
- 변경에 필요한 담당 영역 빌드 통과
- 스타일 게이트 통과
- 관련 불변식 위반 없음
- 7절 작업 절차가 요구하는 별도 검토 완료(`docs/ai/workflow.md`)
- 검증 증거 기록

프로젝트 전체 완료에는 다음을 추가한다.

- 외부 접속 가능한 실제 배포
- HTTPS
- 재현 가능한 배포 절차
- 장애 전환 검증
- RTO 측정
- 데이터 유실 검증
- 중복 처리 검증
- stale write 검증
- 부하 시험
- 카오스 시험
- 관측성
- 백업
- 실제 복원 시험
- 보안 검토
- 월 운영 비용 산정


## 33. 완료로 판정하지 않는 경우

- 변경에 필요한 테스트를 실행하지 않음
- 최신 코드가 아닌 과거 결과 사용
- 판정기 변경 후 재시험하지 않음
- 정본 변경 후 관련 검증을 다시 하지 않음
- 장애가 실제로 주입됐는지 확인하지 않음
- 판정 대상이 없는 통과를 통과로 계상
- 백업만 만들고 복원을 시험하지 않음
- 측정값을 추정값으로 대체
- archive 문서를 현재 계약 근거로 사용
- 필수 별도 검토 없이 병합
- 외부 접속이 불가능한 상태를 최종 배포로 간주


## 35. 규칙 추가 기준

새 규칙은 실제로 반복되는 문제를 막을 필요가 있을 때만 추가한다.

다음 이유만으로 추가하지 않는다.

- 한 번 발생한 사소한 실수
- 개인 취향
- 특정 파일 하나의 특수 상황
- 기존 정본으로 이미 해결 가능한 문제
- CI 또는 테스트로 해결하는 편이 나은 문제

가능하면 다음 순서로 해결한다.

1. 코드 구조
2. 타입과 계약
3. 자동 테스트
4. CI 검사
5. 문서
6. 이 문서의 규칙

AI 지침 문서를 모든 문제의 해결책으로 쓰지 않는다.

규칙이 늘면 읽히지 않는다. 읽히지 않는 규칙은 없는 규칙이다.

새 규칙을 넣을 때는 담당 문서의 기존 절에 들어갈 수 있는지 확인한다.
이 문서의 번호는 이전 지침을 찾는 용도로 유지한다. 기존 절을 옮기거나 이름을 바꾸면
참조하는 문서와 역할 파일도 함께 고친다.
