# 프런트엔드 구현 역할

Claude와 Codex가 웹 작업에 공통으로 사용하는 역할이다. [AGENTS.md](../../../AGENTS.md)를 먼저 읽는다. 화면의 최소 폭, 대비·입력 영역·모션 수치와 토큰 이름은 해당 설계에서 확인한다.

## 담당 범위와 시작할 자료

`web/`의 데스크톱 화면, 컴포넌트, HTTP·WebSocket 연결, 화면 상태, 접근성과 정적 export를 담당한다. 사용자 요청 없이 모바일 UI나 반응형 재배치를 추가하지 않는다. 백엔드 계약이나 디자인 토큰을 변경해야 한다면 관련 구현과 영향을 함께 확인한다.

기본 자료는 [디자인 시스템](../../reference/contracts/프론트_디자인시스템.md), [데스크톱 레이아웃](../../reference/contracts/데스크톱_레이아웃설계.md), [웹 화면 명세서](../../reference/contracts/웹_화면명세서.pdf), [API 설계](../../reference/contracts/백엔드_API_설계.md)다. 디자인 문서에 폐기된 `모바일:` 항목이 남아 있더라도 현재 구현 근거로 사용하지 않는다. 실제 파일 위치와 실행 방법은 [웹 안내](../../../web/README.md)를 확인한다.

화면에서 필요한 API 필드나 상태를 추측해서 추가하지 않는다. 계약과 구현이 다르면 [작업 절차](../workflow.md) §9~11에 따라 근거를 확인하고 허용된 변경 범위를 정한다. 확인 가능한 오기는 바로 정리하며, 해결되지 않은 동작 변경에 의존하는 작업만 보류한다.

## 레이아웃과 디자인

현재 웹은 고정형 데스크톱 화면이다. 최소 폭과 그 미만에서의 동작은 레이아웃 설계를 따른다. 모바일 breakpoint, 모바일 전용 컴포넌트와 임의의 반응형 재배치를 넣지 않는다.

색상·글꼴·간격·모션에는 디자인 토큰을 쓴다. 하드코딩한 hex 색상은 계약에 명시한 예외만 허용한다. 상승·하락·매수·매도의 표현을 유지하고, 상태를 색만으로 전달하지 않는다. 부호나 텍스트·아이콘 등 다른 구분을 함께 제공한다.

실시간 갱신 때문에 숫자 폭이나 패널 배치가 흔들리지 않게 한다. 자릿수 정렬과 고정 폭 등 기존 방식을 활용하고, 과도한 깜빡임·반복 애니메이션을 피한다. 모션의 값과 동작은 디자인 시스템을 따른다. 공통 기준은 [구현과 검증 기준](../engineering.md) §15~16에 있다.

## 데이터와 화면 상태

- API가 전달한 금액·수량 문자열의 정밀도를 보존한다. 실제 금액 계산에 JavaScript `number`나 `parseFloat`를 사용하지 않는다. 값의 계산과 표시용 포맷을 나누고 포맷은 표시 직전에 적용한다.
- 화면은 기존 데이터 접근 계층을 사용한다. 컴포넌트 안에 별도의 API 경로나 중복 통신 로직을 만들지 않는다.
- 브라우저 시뮬레이터와 실제 HTTP/STOMP 연결을 구분한다. 번들에 어댑터 코드가 있다는 사실만으로 실제 연결 방식을 판단하지 않고 빌드 설정과 동작을 확인한다.
- 공유 데이터는 기존 store에서 관리하고 지역 UI 상태와 구분한다. 편의를 위해 같은 데이터를 여러 상태에 중복 저장하지 않는다.
- 메시지 순서, 리더 세대, 중복 체결과 재연결 후 재조회 처리를 유지한다. 실시간 갱신이 전체 화면의 불필요한 렌더링을 유발하지 않게 한다.
- 정상·로딩·빈 상태·오류를 구분한다. 요청 실패를 빈 데이터로 숨기거나 시뮬레이터의 성공을 실제 API 성공으로 대신하지 않는다.

## 접근성과 시각 검증

키보드로 조작할 수 있고, 대화형 요소에는 접근 가능한 이름과 확인 가능한 포커스 표시가 있어야 한다. 양수 `tabindex`로 탭 순서를 강제로 바꾸지 않는다. 색 대비와 입력 영역 크기는 디자인 시스템을 따르며 `prefers-reduced-motion`을 고려한다.

화면 배치나 스타일을 바꾸면 실제 렌더링을 확인한다. 변경과 관련된 정상·로딩·빈 상태·오류, 긴 값, 실시간 갱신과 최소 지원 폭을 본다. 스크린샷이나 눈으로 본 결과만으로 통신·재시도·상태 처리 테스트를 대체하지 않는다. 실행하지 못한 브라우저 검사는 미실행 이유를 남긴다.

## 정적 export와 빌드

웹은 정적 export를 유지하며 빌드 결과에 `out/`이 생성되어야 한다. Next.js 런타임 서버가 필요한 기능을 임의로 추가하지 않는다. 동적 경로도 정적으로 생성할 수 있어야 한다.

`NEXT_PUBLIC_*` 값은 빌드할 때 들어간다. 배포용 API·WebSocket 주소를 확정하고 해당 값으로 빌드한다. 이후 주소를 바꿀 때는 다시 빌드해야 한다. 공개 결과물에서 관리자 화면을 제거하고 검사하는 절차도 [웹 안내](../../../web/README.md)를 따른다.

개발 서버와 빌드를 같은 체크아웃에서 동시에 실행하면 산출물이 섞일 수 있다. 개발 서버를 중지하거나 별도 체크아웃에서 빌드한다. `distDir`만 바꾸면 충돌이 모두 격리된다고 가정하지 않는다.

## 검증과 보고

웹 로직을 변경하면 관련 테스트와 `npm run build`를 실행한다. 배치·스타일 변경에는 토큰·브라우저 검사도 적용한다. 필요한 명령과 조건은 [구현과 검증 기준](../engineering.md) §30~31, 완료 판단은 같은 문서 §32~33을 따른다. 문서 수정만 한 경우에는 문서 검사를 실행한다.

코드·주석은 [코드 작성 기준](../code-style.md) §26, 설명서는 [문서 작성 기준](../writing.md)을 따른다. 안전성이나 계약에 영향을 주는 변경은 [작업 절차](../workflow.md) §7에 따라 별도로 검토한다. 진행 중에는 새로 확인한 사실을 짧게 알리고, 최종 보고에는 변경·검증·미확인 사항을 §34에 맞춰 적는다.
