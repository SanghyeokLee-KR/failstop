# 백엔드 구현 역할

Claude와 Codex가 서버 작업에 공통으로 사용하는 역할이다. [AGENTS.md](../../../AGENTS.md)를 먼저 읽고, 이 문서는 백엔드 변경에 필요한 기준으로 사용한다. 수치·버전·실험 목록을 역할 문서에 복사하지 않고 해당 설계에서 확인한다.

## 담당 범위와 시작할 자료

`server/`의 매칭 엔진, 주문·체결, 원장·잔고, 명령·이벤트 저널, REST·WebSocket, DB 연동과 리더 전환·복구를 담당한다. 화면 디자인, 인프라 구조와 실험 판정 기준까지 필요 없이 넓히지 않는다. 다른 영역의 수정이 필요하면 호출 관계와 영향을 확인해 해당 담당자와 범위를 나눈다.

주문이나 저장 경로를 바꾸기 전에 [DB 설계](../../reference/contracts/백엔드_DB_설계.md), [API 설계](../../reference/contracts/백엔드_API_설계.md), [하네스 검증 설계](../../reference/contracts/하네스_검증설계.md)의 관련 절을 읽는다. 웹 연동의 수용 조건은 [웹 화면 명세서](../../reference/contracts/웹_화면명세서.pdf) §6.2에서 확인한다. 파일 위치는 [코드 지도](../../reference/architecture/프로젝트_코드지도.md)를 이용하되 실제 구현과 테스트를 직접 읽는다.

계약과 코드가 다르면 [작업 절차](../workflow.md) §9~11에 따라 차이를 확인한다. 경로 오류와 확인 가능한 오기는 바로 고칠 수 있다. 동작이나 안전성 기준의 변경이 필요하면 근거와 영향을 제시하고, 사용자 요청에 포함된 범위에서 설계와 구현을 함께 정리한다. 해결되지 않은 충돌에 의존하는 수정은 보류하되 독립된 작업은 계속한다. 실패한 구현을 통과시키려고 계약을 사후에 낮추지 않는다.

## 거래 처리에서 지킬 것

판단 기준은 [구현과 검증 기준](../engineering.md) §1, 핵심 규칙은 같은 문서 §14를 따른다.

- 금액과 수량은 계약의 정밀도를 유지한다. Java에서 `BigDecimal`을 사용하고 반올림에는 `RoundingMode`를 명시한다. `float`·`double`이나 묵시적인 반올림으로 바꾸지 않는다.
- 같은 논리적 주문의 재시도는 같은 `client_order_id`를 쓴다. 동일 키의 다른 내용, 처리 중인 주문, 응답 유실을 구분하고 API 계약대로 처리한다.
- 명령 저널을 커밋한 뒤 엔진에 전달한다. 한 명령의 이벤트·주문·체결·원장·잔고는 계약에 정한 트랜잭션으로 함께 정산한다. WebSocket 발행은 정산 커밋 이후에 한다.
- 엔진에서 시작한 모든 DB 쓰기는 현재 리더 자격을 확인한다. 새 경로를 추가할 때 저널뿐 아니라 체결·취소·복구·스냅샷과 따라잡기 중 발생하는 쓰기를 확인한다. 오래된 리더의 쓰기를 막는 fencing을 우회하지 않는다.
- 원장과 잔고는 계약에 정한 게시 경로로만 변경한다. 직접 갱신으로 정산을 우회하거나 자산을 임의로 생성·소실시키지 않는다.
- 같은 명령을 재생하면 같은 결과가 나와야 한다. 매칭 엔진 안에서 현재 시각·비결정적 난수·순서가 보장되지 않는 순회로 거래 결과를 바꾸지 않는다. 필요한 입력은 명령에 보존한다.
- 명령 순번, 마켓 이벤트 순번과 WebSocket 순번을 구분한다. 마켓별 복구 범위와 적용 완료 위치에 다른 마켓의 최대 순번을 사용하지 않는다.
- 수용 상한과 거절 정책은 계약과 측정 근거를 따른다. 부하 시험을 통과시키려고 상한을 무작정 늘리거나 거절을 숨기지 않는다.

엔진 모듈의 의존성 경계를 유지한다. 앱 리더의 자동 전환과 PostgreSQL의 수동 승격은 별개이며, 비동기 DB 복제에서 저널 자체가 유실될 가능성도 보존한다.

## DB와 실행 환경

DDL의 컬럼·타입·인덱스·제약은 실제 마이그레이션과 DB 설계를 읽어 확인한다. 스키마 변경은 새 Flyway 파일로 추가한다. 이미 적용한 마이그레이션은 주석도 수정하지 않으며, 체크섬 오류를 숨기기 위해 임의로 repair하지 않는다.

빌드와 테스트는 현재 체크아웃의 `server/`에서 실행한다. Windows에서는 `./gradlew.bat build`, Linux에서는 `./gradlew build`를 사용한다. 테스트 워커의 클래스패스 문제가 의심되면 실제 저장소를 가리키는 ASCII 경로를 확인한다. 설정되지 않은 환경 변수나 다른 체크아웃에 의존하지 않는다.

통합 테스트의 Docker·DB 조건은 [서버 안내](../../../server/README.md)를 따른다. 카오스 Compose를 직접 실행할 때는 `harness/.env.chaos`가 전달되는지 확인한다. 비밀 값 자체를 출력하지 않는다. 자세한 환경 조건과 검증 명령은 [구현과 검증 기준](../engineering.md) §30~31에 있다.

## 검증과 마무리

거래 로직은 정상 경로뿐 아니라 중복 요청, 응답 유실, 동시 주문, 리더 교체와 재생에 미치는 영향을 검사한다. 새 쓰기 경로와 마이그레이션은 별도 검토 대상이다. 코드 변경에는 영향받는 테스트와 백엔드 빌드를 실행하며, 문서 표현만 바꾼 작업에는 문서 검사를 적용한다. 완료 범위는 [작업 절차](../workflow.md) §7과 [구현과 검증 기준](../engineering.md) §32~33으로 결정한다.

실패하면 제품 코드, 실행 환경, 판정 경로를 함께 확인한다. 테스트나 판정기를 무조건 옳다고 가정하지 않으며, 제품 결함을 환경 문제로 단정하지도 않는다. 검증 상태는 구현과 검증 기준 §22의 `PASS`, `FAIL`, `NOT RUN`, `BLOCKED`, `N/A`를 구분해 기록한다.

코드와 주석은 [코드 작성 기준](../code-style.md) §26, 문서는 [문서 작성 기준](../writing.md)을 따른다. 진행 중에는 새로 확인한 사실과 다음 판단을 짧게 알린다. 최종 보고에는 실제 변경, 실행한 검증과 미실행 이유, 남은 위험을 적으며 [작업 절차](../workflow.md) §34를 따른다.
