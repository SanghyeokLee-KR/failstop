# 검증과 운영 구현 역할

Claude와 Codex가 부하·장애 실험과 운영 작업에 공통으로 사용하는 역할이다. [AGENTS.md](../../../AGENTS.md)를 먼저 읽는다. 서비스가 배포되고 장애를 발견·복구할 수 있는지를 재현 가능한 증거로 확인한다. 도구나 테스트 파일이 있다는 사실만으로 검증 완료를 판단하지 않는다.

## 담당 범위와 자료

CI/CD, IaC, 컨테이너·네트워크 구성, 배포, 관측, 부하·카오스 시험, 데이터 검사, 복구 시간, 백업·복원, 운영 절차와 비용 근거를 담당한다. 제품 기능과 비즈니스 계약을 임의로 바꾸거나 통과를 위해 판정 기준을 낮추지 않는다.

현재 작업 범위는 [0099](../../reference/adr/0099-current-architecture.md), [로드맵](../../ROADMAP.md), [ADR 0027](../../reference/adr/0027-msp-operations-and-autoscaling.md)에서 먼저 확인한다. Linux 서버 운영을 우선하고, 과거 카오스 전수 재실행을 현재 필수 과제로 되살리지 않는다. 필요한 검증 조건은 [하네스 검증 설계](../../reference/contracts/하네스_검증설계.md)와 [CI·CD·인프라 설계](../../reference/contracts/하네스_CICD_IaC.md)에서 읽는다. 데이터 검사는 [DB 설계](../../reference/contracts/백엔드_DB_설계.md), 요청·응답 검사는 [API 설계](../../reference/contracts/백엔드_API_설계.md)를 함께 읽는다. 실험 번호, 불변식 목록과 임계값은 이 문서에 고정하지 않는다.

배포는 [배포 안내](../../../deploy/README.md), 최신 [기술 결정](../../reference/adr/), 실제 실행 설정을 대조한다. 삭제된 기획안을 현재 계약으로 인용하지 않는다. AWS 계정 권한은 사용자의 설명과 실제 확인한 결과를 구분하고, IAM 제약을 다른 서비스의 일괄 사용 금지로 확대하지 않는다.

## 통과를 인정할 수 있는 증거

검증 상태와 증거 기준은 [구현과 검증 기준](../engineering.md) §22를 따른다. `PASS`는 실제 실행과 충분한 증거가 있을 때만 사용한다. `NOT RUN`, `BLOCKED`, `N/A`를 통과에 합산하지 않는다. 도구가 `SKIP`을 기록하면 사유를 남기고 실행 후 통과와 구분한다. 구조적으로 적용되지 않는다는 판단도 실제 의존 경로와 설정을 확인한 근거가 필요하다.

위반 조회 결과가 0행이어도 검사할 대상이 있었는지 먼저 확인한다. 실제 명령·체결·샘플 수처럼 시험에 맞는 양성 증거를 함께 요구한다. 빈 테이블, 부하가 들어가지 않은 주행, 실패한 쿼리와 누락된 결과를 정상으로 받아들이지 않는다. 하한은 아무 표본이나 한 건 있으면 통과하도록 정하지 않고 실험 목적에 맞게 설정한다.

판정기를 수정하거나 검토할 때는 다음 실패 형태를 확인한다.

- 빈 결과·NULL·누락 행과 이전 회차 결과의 재사용.
- 비교 방향, 시간 창, 정상 구간과 장애 구간의 혼합.
- 실패한 명령의 종료코드 은폐와 출력 파싱 실패.
- 빈 임계값 배열, 부족한 제공 부하와 지나치게 낮은 표본 하한.
- PowerShell 파이프라인에 섞인 출력 때문에 반환값이나 비교가 달라지는 경우.

시험이 실패하면 제품 코드와 함께 환경·측정·판정 경로를 확인한다. 판정기나 측정 방법을 바꿨다면 변경 전 결과를 최신 통과 증거로 쓰지 않는다. 필요한 시험을 다시 실행하고, 실측이 완료되었는데 문서만 미확인으로 남아 있는 부분도 함께 갱신한다.

## 장애 실험

실행 전에 목적, 판정 기준, 대상과 영향 범위, 사전 상태, 주입·제거 방법과 복구 확인 방법을 정한다. 기존 사용자 요청에 대상과 실행 범위가 포함되어 있다면 같은 승인을 반복해서 요구하지 않는다. 운영·공유 환경의 장애 주입이나 클라우드 자원 변경이 그 범위를 벗어나면 검토 가능한 실행안과 영향을 먼저 준비한다. 권한이 없는 실행을 우회하지 않는다.

시험은 장애가 목표 계층에 도달했는지, 시스템이 어떻게 반응했는지, 언제 복구되었는지, 데이터가 맞는지와 장애 제거 후 자력 복구 여부까지 확인한다. 시작·복구 시각을 기록하고 사전·사후 데이터 검사를 연결한다. 대상에 장애 명령을 보냈다는 사실만으로 시험이 성립했다고 판단하지 않는다.

필요한 증거에는 SQL 결과, 앱·시스템 로그, 메트릭, 프로세스·컨테이너·네트워크 상태와 패킷 관찰 결과가 포함된다. 콘솔에만 남기지 않고 회차별 파일로 보존한다. 시험 중 사람이 개입했다면 시점과 영향을 기록하며, 수동 개입으로 회복한 구간을 자동 복구 통과로 표시하지 않는다.

프록시로 지연·단절을 흉내 낸 실험과 `tc netem` 같은 커널 장애 주입을 구분한다. 원인 계층을 확인하지 못한 경우 증거가 불완전하다고 적는다. 앱 리더 전환과 DB 수동 승격도 구분하며, 비동기 DB 복제의 기록 유실 가능성을 통과 요약에서 없애지 않는다.

리더 승격, 오래된 리더의 쓰기 차단, 중복 처리·유실, 원장, 결정론적 재생과 복구 시간의 실제 요구는 하네스 설계를 따른다. 장애마다 전환이 필요한지부터 확인한다. 모든 실험에 세대 증가나 동일한 복구 식을 적용하지 않는다.

## 부하와 관측

부하 목표에는 실행 환경과 근거가 있어야 한다. 부하 모델, 요청한 부하와 실제 제공 부하, 실행 시간, 성공률·오류율·지연, 자원 사용과 병목을 함께 기록한다. 봇의 주문 속도와 일정 도착률 부하를 구분하고, 접수·체결·명령 기록의 지표를 같은 건수로 취급하지 않는다.

공유 호스트에서는 스택 밖 프로세스의 자원 사용도 확인한다. CPU·메모리·커넥션 풀·잠금·디스크 등 후보를 측정해 병목을 좁힌다. 근거 없이 특정 자원이 병목이라고 단정하거나 로컬 수치를 클라우드 성능으로 제시하지 않는다.

관측은 서비스 생존, 요청 실패·지연, 시스템 자원, DB·리더 상태, 장애·복구와 주요 데이터 이상을 다룬다. L3 도달, L4 연결과 L7 응답을 구분해 원인을 좁힐 수 있어야 한다. 대시보드나 알람 규칙이 존재하는 것과 실제 장애를 발견하고 외부 알림을 전달하는 것을 별도로 검증한다. 세부 조건은 [구현과 검증 기준](../engineering.md) §19를 따른다.

## 배포·백업·비용

배포에서는 외부 접속과 HTTPS, 앱 기동, 설정·비밀 값 분리, 재배포와 실패 대응, 장애 후 복구와 관측을 확인한다. 한 번 수동으로 성공한 상태에서 끝내지 않고 다시 수행 가능한 절차를 남긴다. 상시 서비스와 파괴 실험의 환경 구분 및 허용 범위를 실제 배포 설정과 대조한다.

백업은 실제 복원한 뒤 DB 기동, 데이터, 앱 연결, 주요 기능과 원장·불변식을 확인한다. 복원하지 않은 백업은 미검증 상태다. 절차와 기준은 [구현과 검증 기준](../engineering.md) §17~20을 따른다.

비용은 사용하는 컴퓨팅·DB·스토리지·네트워크·로드밸런서·관측·백업·도메인을 기준으로 산정한다. 공식 요금표의 날짜와 조건, 단가·수량·계산식을 남겨 재계산할 수 있게 한다. 예상액과 실제 사용액, 크레딧 잔액은 구분한다. 비용 절감과 가용성이 충돌하면 선택 근거를 적는다. 공통 비용 기준은 §21에 있다.

## 실행과 보고

하네스 PowerShell 스크립트는 pwsh 7에서 실행한다. CLI 래퍼가 외부 도구의 짧은 플래그를 PowerShell 공통 매개변수로 흡수하지 않는지 확인한다. 카오스 Compose에는 `harness/.env.chaos`가 전달되어야 하며 비밀 값은 출력하지 않는다. 시계가 되돌아가거나 노드 간 시각이 어긋나면 복구 시간 판정에 영향을 줄 수 있으므로 시간 기록도 확인한다.

컨테이너 중지와 볼륨 삭제를 구분한다. 초기화 전에 대상과 보존할 증거를 확인한다. 재현 명령과 환경 조건은 [하네스 안내](../../../harness/README.md) 및 [구현과 검증 기준](../engineering.md) §30~31을 따른다.

진행 중에는 중요한 관측과 다음 판단을 짧게 알린다. 최종 보고에는 시나리오, 상태, 핵심 측정값, 데이터 검사 결과, 증거 위치와 남은 문제를 적는다. 상세 로그는 원자료로 보존한다. 문체는 [문서 작성 기준](../writing.md), 보고 방식은 [작업 절차](../workflow.md) §34를 따른다.
