# 문서 작성 기준

Claude와 Codex가 문서를 쓰거나 정리할 때 함께 따르는 기준이다. 읽기 편하게 고쳐도 계약, 수치, 근거와 불확실성은 유지한다. 문서에 사람이 작성했다고 허위로 표시하는 것이 목적은 아니다.

## 독자에 따라 위치를 정한다

| 위치 | 독자와 용도 | 담을 내용 |
|---|---|---|
| `docs/reports/` | 프로젝트를 처음 읽는 사람, 발표를 준비하는 사람 | 무엇을 만들었고 어떻게 동작하는지, 왜 이렇게 만들었는지, 어디까지 확인했는지 |
| `docs/reference/` | 구현·검토 중인 개발자와 AI | API·DB 계약, 조건, 실패 처리, 상세 설계와 기술 결정 |
| `docs/reference/adr/0099-current-architecture.md` | 현재 구조를 한 번에 판단하는 사람과 AI | 현재 적용하는 결정, 대체 관계, 구조와 검증의 한계 |
| `docs/ai/` | 저장소에서 작업하는 AI | 읽을 자료, 작업 순서, 수정 범위, 검증과 보고 기준 |
| `docs/measurements/` | 시험 결과를 확인하는 사람과 AI | 측정 날짜·환경·코드·부하·판정·증거 위치 |
| `docs/ROADMAP.md` | 현재 작업 상태를 확인하는 사람과 AI | 완료한 범위, 진행 중인 일과 남은 검증 |

상세 설계를 AI 전용 언어로 쓰지 않는다. 개발자가 읽고 검토할 수 있어야 한다. 보고서에 API 필드 표나 SQL 전체를 복사하지 않고 상세 자료로 연결한다. AI 행동 지시는 설계 본문에 섞지 않고 이 폴더에 둔다.

## 사람이 읽는 설명을 쓴다

첫 문단에서 독자가 알아야 할 내용을 말한다. 프로젝트 설명이라면 무엇을 만들었는지, 장애 설명이라면 무엇이 멈췄고 어떻게 복구하는지부터 쓴다. 배경을 길게 쌓은 뒤 결론을 숨기지 않는다.

문단 하나에는 이어지는 생각 하나를 담는다. 주어와 동사를 써서 누가 무엇을 하는지 밝힌다. 명사만 이어 붙이거나 모든 문장을 짧게 끊지 않는다. 문장 길이는 내용에 맞춘다.

용어는 실제 동작을 설명한 뒤 붙인다. 예를 들어 'fencing을 보장한다'에서 멈추지 않고, 예전 리더가 복귀해도 새 거래를 기록할 수 없게 현재 리더의 권한을 검사한다고 설명한다. 용어 정의가 이미 가까이에 있으면 반복하지 않는다.

목록은 여러 항목을 나열하거나 절차의 순서가 중요할 때, 표는 같은 기준으로 대상을 비교할 때 쓴다. 설명이 길어지는 표 셀은 문단으로 바꾼다. 모든 절을 '목적·배경·정책·결론' 같은 틀로 맞추지 않는다.

자연스러운 평서문을 기본으로 쓴다. 설명서와 기술 문서에서 '한다'와 '합니다'를 섞지 않는다. 발표 자료의 청중에게 직접 설명하는 문장은 존댓말을 사용할 수 있다. 사용자가 지정한 어조가 있으면 그것을 따른다.

강조는 독자가 놓치면 오해할 조건에만 쓴다. 문단마다 굵은 글씨, 경고 상자, 요약을 붙이지 않는다. 앞에서 한 말을 마지막에 다시 나열하지 않는다.

## 같은 사실을 다르게 설명하는 예

읽기 어려운 설명:

> 리더 장애 대응을 위한 자동 승격 및 epoch 기반 fencing 정합성 검증 체계를 구축한다.

읽기 쉬운 설명:

> 주문을 처리하던 앱 서버가 멈추면 대기 서버가 리더 권한을 얻어 거래를 이어간다. 이전 서버가 돌아와도 쓰기를 재개할 수 없도록 DB에 저장된 권한 번호를 확인한다. 이 번호를 epoch라고 부른다.

두 번째 설명도 실제 코드와 계약이 그런 경우에만 쓴다. 독자가 이해하기 쉽다는 이유로 없는 동작을 만들어 넣지 않는다. DB 승격까지 자동이라고 확대해서도 안 된다.

## 사실과 근거를 지킨다

설계 요구, 코드에서 확인한 동작, 실행으로 검증한 결과를 구분한다. 설계에 적혔다고 구현 완료로 쓰지 않는다. 코드가 있다고 장애 상황에서 검증됐다고 쓰지 않는다.

수치에는 해석에 필요한 조건을 붙인다. 처리량이라면 환경과 부하, 복구 시간이라면 어떤 장애와 어떤 회복 시점을 쟀는지가 필요하다. 출처가 없거나 서로 다른 실험의 값은 한 결과처럼 합치지 않는다.

확인하지 못한 것은 확인하지 못했다고 쓴다. 문서와 구현이 다르면 어느 파일의 어떤 내용이 다른지 적고, 자연스러운 문장을 만들려고 모순을 지우지 않는다. 이미 증거가 있는 결과를 무조건 미확인으로 낮추지도 않는다.

근거는 주장 가까이에 실제 파일 링크로 붙인다. 같은 파일을 문장마다 반복하지 않고 관련 문단 끝에 묶을 수 있다. 보고서를 읽기 위해 링크를 전부 열어야 한다면 본문 설명이 부족한 것이다.

문체 수정 전후에는 숫자, 단위, 버전, 오류 코드, 식별자, 파일 경로, 부정 조건과 의무 표현을 대조한다. 상세 계약의 '필수'를 보고서에서 '권장'으로 바꾸지 않는다. 본문에 긴 로그를 붙이는 대신 원자료 위치와 핵심 결과를 적는다.

## 문서를 늘리기 전에 확인한다

현재 내용을 설명하는 문서는 한 곳에서 갱신한다. 같은 내용을 사람용·AI용으로 각각 전체 복사하지 않는다. 보고서는 이해를 돕는 설명이고, 세부 조건의 기준은 상세 설계다.

0099는 현재 구조를 이어 읽는 문서로 유지한다. 새 ADR이나 구조·배포·검증 상태 변경 때 관련 원본과 함께 검토해 적용 관계와 설명을 갱신한다. 세부 계약과 로드맵의 진행 상태를 통째로 복사하지 않고 판단에 필요한 내용과 근거를 연결한다. 결정 이력과 예약 번호의 관례는 [ADR 0001](../reference/adr/0001-record-architecture-decisions.md)을 따른다.

기존 문서에 자연스럽게 들어갈 내용이면 파일을 추가하지 않는다. 독립된 독자·목적·유지 책임이 있을 때만 새 문서를 만든다. 새 파일은 [문서 안내](../README.md)나 해당 분야 색인에서 찾을 수 있게 연결한다.

파일명에 '최종', '진짜최종', '수정본', 'v2'를 붙이지 않는다. 설계 버전은 본문에서, 과거 내용은 Git에서 확인한다. 재현에 필요한 측정 기록은 날짜를 유지한다. 삭제한 대본과 인수인계, WBS, 폐기 기획을 정리 명목으로 되살리지 않는다.

길이는 독자가 필요한 내용을 찾을 수 있는지로 판단한다. 긴 계약을 짧게 만들려고 조건을 지우지 않는다. 대신 처음에 어떤 문제를 다루는지 안내하고 필요한 절로 연결한다. 사람용 설명서의 길이는 핵심 흐름을 한 번에 읽을 수 있는 정도로 정한다.

문서의 상태는 역할로 구분한다. `reference/contracts`는 구현 계약, 그 밖의 설계·코드 지도는 해당 주제의 설명, `reports`는 이해용 설명, 날짜별 측정은 그 환경에서의 증거다. 폐기 자료는 현재 구현 근거로 삼지 않는다.

## 원본과 생성물을 구분한다

HTML에서 만든 PDF, 빌드 결과와 생성 보고서는 원본을 수정하고 다시 만든다. 생성 절차와 원본 경로를 함께 유지한다. 직접 편집하는 PPTX는 그 파일 자체가 원본이다.

[웹 화면 명세서](../reference/contracts/웹_화면명세서.pdf)의 원본은 같은 폴더의 [HTML](../reference/contracts/웹_화면명세서.html)이다. PDF §6.2의 백엔드 수용 기준을 바꿀 때 원본과 PDF를 함께 확인한다. 문서 이동만 하는 작업에서는 PDF 내용과 적용된 DB 마이그레이션을 다시 쓰지 않는다.

## 작성과 검토 순서

1. 요청한 독자와 수정 범위를 확인한다. 이미 정해져 있으면 다시 묻지 않는다.
2. 관련 원본, 코드, 측정 결과를 읽고 확인 범위를 정한다. 기존 문서의 요약만 다시 요약하지 않는다.
3. 독자가 이해해야 할 흐름에 맞춰 작성한다. 기존 파일로 충분하면 그 파일을 고친다.
4. 숫자·조건·실패 처리·근거가 보존됐는지 원문과 대조한다.
5. 처음 읽는 사람이 주어와 용어를 이해할 수 있는지, 링크 없이도 핵심 설명이 이어지는지 다시 읽는다.
6. 경로와 문체 검사를 실행하고 실제로 고친 범위와 남은 문제를 보고한다.

저장소 루트에서 `pwsh -NoProfile -File scripts/check-docs.ps1`, `pwsh -NoProfile -File scripts/check-doclinks.ps1`, `pwsh -NoProfile -File scripts/check-adr-current.ps1`, `pwsh -NoProfile -File scripts/check-style.ps1`을 실행한다. 새 파일은 diff 검사에 빠질 수 있으므로 스타일 검사를 경로 인자로도 실행한다.

원자료 해시가 바뀌면 0099와 해당 자료를 대조한다. 검토와 필요한 수정을 마친 뒤 `check-adr-current.ps1 -PrintDigest`의 읽기 전용 출력으로 0099 말미의 `<!-- sources-sha256: ... -->`를 갱신한다. 해시는 원자료의 변경을 알리는 장치이며, 내용 검토 없이 값만 바꾸어 통과시키지 않는다.

검사는 깨진 경로와 일부 표현을 잡는다. 문장이 자연스러운지, 기술 설명이 맞는지는 원문과 실제 동작을 대조해 판단한다. 검사 통과만으로 문서 품질이 보장됐다고 쓰지 않는다.

기존 산출물의 금지 문자 규칙을 유지한다. 이모지와 U+2014·U+2013은 쓰지 않는다. 홍보성 수식, 근거 없는 최상급, 독자에게 말을 거는 생성 완료 문구와 도구 서명은 넣지 않는다. 단어 몇 개를 바꾸는 것으로 문체 수정을 끝내지 않는다.
