# 최종 통합·보안 감사

## 개요

### 대상과 렌즈

회원 인증·게시판·관리·거래 평면이 하나로 합류한 시점의 통합 결함과 신규 코드 결함을 대상으로 한다. 세 렌즈로 교차 검토했다.

- 평면 경계: 회원·거래·게시판·관리 평면 간 토큰 격리, 세션 수명, 데이터 격리.
- 신규 코드: 게시판(community) 패키지, 회원 인증(member) 패키지, V6·V7 마이그레이션, 프론트 community·store·httpDatasource.
- 통합: 단일 기능 안에서는 정상이나 두 기능·두 평면이 결합할 때만 드러나는 결함.

critical·high 후보는 코드·DDL·정본 문서·테스트를 직접 대조하는 적대적 재검증을 거쳤다. 재검증에서 프레이밍 오류가 확인된 항목은 심각도를 조정했다(예: 세션 스토어 잔존, HTTP 어댑터 Idempotency-Key 폐기 모두 high→medium 하향).

### 검증 제약

읽기 전용·빌드 금지·candles 작업 동시 실행 제약으로 gradlew test·npm run build·check-style.ps1은 실행하지 않았다. 판정은 소스·정본·테스트 소스의 정적 대조에 근거한다. 레이스 계열 결함은 READ COMMITTED 격리와 코드 경로로 재현 시나리오를 구성해 확인했다.

### 원장 정합

확인된 결함 중 코어 원장·저널·자산 정합에 닿는 것은 없다. 게시판 comment_count·인기순 스냅샷 등 표시용 집계와 보안 보증(재사용 탐지, 로그아웃 즉시성)에 국한된다.

## medium 영역별

### A. 회원 인증·세션(평면 경계)

- 회원 액세스 토큰 서버측 취소·상태 재검증 부재. verify·verifyCommunity가 서명·exp·typ·aud·kind만 확인하고 세션 폐기·정지 상태를 조회하지 않는다(MemberSessionService.java:94-152). logout·재사용 탐지는 refresh family만 폐기하고 발급된 access(TTL 15분)는 두 평면에서 만료까지 유효. AdminSessionService.verify(:115-123)는 매 요청 revoked_at·expires_at을 조회하는데 회원 평면만 이 재검증이 빠졌다. 정지·강제 로그아웃 기능이 통합되면 최대 15분 잔존 창. 제안: users.status=ACTIVE 매 요청 확인 + 토큰 epoch·jti allowlist 대조, 또는 15분 잔존을 정본에 명시. (MemberSessionService.java:94)
- refresh 회전 경합을 도난으로 오판해 family 전체 폐기. 같은 rt를 동시 제출한 두 요청(멀티탭·병렬 401 refresh)이 모두 초기 판독을 통과하면 패자가 RotationRaceException→revokeFamily(:275)를 호출해 승자의 자식 토큰까지 무효화, 정상 사용자가 refresh_reuse로 강제 로그아웃. 설계 §1-3 재사용 탐지는 이미 소각된 토큰 재제출을 전제하나 여기서는 미소각 동시 제출까지 도난 판정. 제안: prev_id 체인·grace로 양성 경합과 진성 재사용 구분, 프론트 single-flight 계약 명문화. (MemberAuthService.java:262)
- X-Forwarded-For 최좌측을 클라이언트 IP로 채택해 signup IP 스로틀 우회. clientIp()가 XFF 첫 값을 신뢰(MemberAuthController.java:127, :234-241). signup은 무인증 Argon2id(16MiB 메모리 하드)+GENESIS 게시라 IP당 5회/60s가 유일 방어인데, XFF 회전으로 버킷 키가 매번 달라져 무제한 대량 가입·해시 유발. 제안: 신뢰 프록시 홉 수 고정 후 우측 기준 채택, 또는 remoteAddr만 신뢰.

### B. 게시판 멱등 계약(계층 통합)

프론트·백엔드·정본이 세 갈래로 어긋난다. 실질 하나의 결함이 세 렌즈에서 보고됐다.

- 백엔드: createComment가 @RequestHeader Idempotency-Key를 받지 않고(CommunityController.java:127-141) 서비스에 멱등 파라미터가 없어(CommunityService.java:246-286) 매 호출이 INSERT+comment_count 증분. 같은 파일 createPost는 replay 처리하므로 비대칭이 오구현임을 확증. 응답 유실 후 재전송 시 댓글 중복·comment_count 이중 증가.
- 프론트: request()가 headers를 새로 만들며 `{ ...init, headers }` 스프레드 순서상 init.headers를 덮어써(web/lib/community/httpDatasource.ts:82) createPost·createComment가 넣은 Idempotency-Key가 전송 전 폐기. Sim 경로가 자체 맵으로 정상 동작해 데모에서 결함이 가려진다.
- 정본: 게시판_설계.md §4.2는 글·댓글 모두 멱등을 규정하나 §4.1 표·백엔드_API_설계.md §4-D:717 댓글 행은 Idempotency-Key 미기재. 정본 내부·정본 간 상충.
- 제안: 정본을 먼저 정합(API §4-D 댓글 행에 반영 권장), request()가 init.headers를 명시 병합, createComment에 @RequestHeader+validKey+userId:key 캐시 추가. 프론트가 이미 키를 보내므로 백엔드 수용이 자연스럽다.
- 심각도 근거: 정본이 멱등을 best-effort로 규정하고 커뮤니티는 비금전이라 high 아닌 medium. (관련 file: CommunityController.java:127, community/httpDatasource.ts:82)

### C. 게시판 comment_count 동시성(회원×관리 교차)

- deleteComment가 loadCommentRef로 status를 락 없이 읽고(CommunityService.java:296) status 가드 없는 UPDATE 후 사전 읽은 VISIBLE만 보고 감산. 소유자 이중 삭제, 또는 delete와 report 자동숨김(autoHide :426) 경합 시 두 경로가 각자 감산해 이중 감산. greatest(count-1,0)은 음수만 막고 저평가 영구 잔존, 복구 잡 없음.
- applyModeration도 같은 결함. moderateComment가 loadCommentRef를 tx 밖(:456)에서 읽고 stale currentStatus로 delta 산출(:483-489).
- 제안: togglePostLike(:319-334)가 쓰는 rowcount 구동 패턴으로 통일. `UPDATE ... WHERE id=? AND status='VISIBLE'` rowcount==1일 때만 감산, 모더레이션은 대상 행 FOR UPDATE 후 status 판정.

### D. 관리 모더레이션 상태 전이(회원 수명주기×관리)

- HIDE·DELETE가 소스 상태를 검사하지 않는다(applyModeration은 UNHIDE만 가드, CommunityService.java:473). 회원 자가 삭제(status=DELETED, deleted_at 설정) 글에 HIDE 적용 시 status=HIDDEN·deleted_at 잔존으로 불일치, 이어 UNHIDE(이제 가드 통과)로 status=VISIBLE 완전 부활, detailView가 원본 노출. 주석(:471-472)이 우려한 자가삭제 마스킹 해제가 HIDE→UNHIDE 2단계로 우회.
- applyModeration 상태 판정 자체가 tx 밖 무잠금 읽기(:461) 기반이라 회원 자가삭제와 교차 시 status·deleted_at 역동기화. ConfigAdminController.transition(:87 FOR UPDATE)과 달리 read-modify-write가 한 트랜잭션·행잠금에 모이지 않음.
- 제안: DELETED를 종료 상태로 두어 HIDE/UNHIDE/DELETE 모두 거부하거나, 판정을 쓰기 tx 내 SELECT ... FOR UPDATE로 재조회하고 UPDATE 술어에 기대 status 조건.

### E. 프론트 세션 공존(다화면 통합)

- setSession(s)가 session 슬라이스만 갱신하고 assets·openOrders·closedOrders를 비우지 않는다(store.ts:161-163). onMemberSessionChange 구독처(:232-241)도 setSession만 호출. 스토어가 싱글턴(:81)이라 SPA 내비로 신원 전환에도 존속. assets/page.tsx:120-121이 loading을 스토어 내용에서 파생해 HTTP 모드 신규 마운트 시 loadAccounts 완료 전 이전 회원 holdings가 서브초 flash. /history(:50,:56)는 자체 loaded 플래그로 방어하는 처리 불일치. 공유 단말에서 A 로그아웃 후 다음 이용자에게 A 포트폴리오 노출. 제안: external_id 변경·null 전이에서 사설 슬라이스 소거를 단일 지점에 수렴.
- 심각도 근거: 재검증에서 지속 노출·거래 화면 미보정 프레이밍이 오류로 확인(OrderPanel.tsx:89가 myAsset 구독, reconnectWs로 보정, 기본 Sim은 전역 계정이라 누출 없음). HTTP 모드 /assets flash로 한정되어 high→medium.
- WS 재연결 fire-and-forget 경합. reconnectWs가 `void (async...deactivate().activate())`로 대기 없이 던져(httpDatasource.ts:539) setMember·clearMember 근접 발생 시 두 IIFE가 stompConnected=true를 각자 캡처해 동시 deactivate→activate, 이중 활성·유휴 연결 잔존 가능. 가드가 호출 시점 스냅샷이라 경합 미방어. 제안: 재연결을 단일 프라미스 큐로 직렬화, 최신 토큰 기준 coalesce.
- 커뮤니티 어댑터 refresh·401 재시도 부재(플레인 비대칭). 트레이드 어댑터는 선제 refresh(api/httpDatasource.ts:324-332)·401 후 1회 재시도(:309-313)를 하나 커뮤니티는 refresh 미호출, 401을 needsLogin으로 매핑(community/httpDatasource.ts:77). refresh 쿠키 유효·access만 만료 상태에서 게시판 쓰기 시 트레이드와 달리 강제 로그아웃. 같은 aud=member인데 플레인별 세션 수명이 갈린다. 제안: 커뮤니티 어댑터에도 401 후 1회 refresh 재시도, 또는 identityProvider가 신선 토큰 보장.

### F. 게시판 신규 코드(인기순·에러코드·자원)

- 인기순 스냅샷 영구 고정. listPopular가 max(generation) null일 때만 ranks.rebuild 호출, rebuildAll이 어떤 스케줄러·컨트롤러에도 미연결(CommunityService.java:109). 최초 1회 산출 후 신규 글·like_count 변동이 영원히 미반영. 제안: snapshot_at TTL 초과·max(generation) 노후 시 요청 경로 재산출 또는 rebuildAll 스케줄 훅 연결.
- post_rank_snapshot PK가 세대 공존 금지. PK가 (market_symbol, post_id)라 post당 1행, rebuild ON CONFLICT DO UPDATE가 generation 제자리 덮어씀(CommunityRankService.java:34). 두 세대 공존 불가라 페이징 중 rebuild 시 옛 세대 커서가 0행→has_more=false 조용한 절단. DDL idx_rank_snapshot_board는 다세대 공존을 전제해 내부 모순. 제안: PK를 (market_symbol, generation, post_id)로 확장·INSERT 전용·retention, 또는 세대 고정 커서 계약 철회.
- latest 커서 타임스탬프 파싱 실패가 400 아닌 500. decodeLatest가 base64·필드 실패는 badCursor로 감싸나 OffsetDateTime.parse의 DateTimeParseException은 미포장(CommunityCursors.java:33)→generic 핸들러(ApiExceptionHandler.java:78-83)가 500. 조작 가능 입력으로 500 유발, 다른 잘못된 커서는 400이라 계약 불일치. 제안: parse를 try/catch로 badCursor 정규화.
- 잘못된 UUID external_id가 404 아닌 500. 경로 변수를 검증 없이 `WHERE external_id=?::uuid`로 넘겨 22P02가 DataAccessException으로 전파, generic 핸들러가 500. getPost·loadPostRef(:550)·loadCommentRef(:561) 경유 다수 무인증 GET이 퍼징으로 쉽게 500·error 로그 스팸 유발. 제안: 캐스팅 전 UUID.fromString·정규식 파싱, 공통 파서로 404/400 정규화.
- 작성 멱등 검사-삽입 비원자성. createPost가 idempotency.get 확인 후 INSERT·사후 rememberIdempotency(CommunityService.java:166), 확인·삽입 비원자적이고 DB 유니크 없음. 동일 키 동시 2요청이 각각 INSERT해 글 중복. 제안: putIfAbsent 선점, 또는 (author_id, idempotency_key) 유니크+ON CONFLICT.
- 쓰기 pre-auth 스로틀 부재로 서명검증 CPU DoS. 읽기 GET은 인증 전 readThrottle, 쓰기는 requireMember(Ed25519 검증) 후에야 writeThrottle(CommunityController.java:74). 커뮤니티가 ApiAuthFilter 우회라 위조 토큰 홍수가 어떤 IP 스로틀도 없이 매 요청 base64+Ed25519 검증 유발, 인증 실패는 writeThrottle 미도달. 제안: requireMember 이전 IP 스로틀, 업스트림 게이트웨이 중복 여부 확인.

### G. 관리·시뮬레이션 계약

- SimAdminController 캐치올이 정본 POST /sim/bots를 섀도잉.
