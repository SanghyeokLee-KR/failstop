# M3 관리자 페이지 설계서 (v1.3)

> 범위: M3 관리자 페이지의 인증·기능·API·프론트·안전 설계. 문서 산출물이며 구현이 아니다. 정본(API 설계 v2.10, DB 설계 v2.11, 디자인시스템, 데스크톱 레이아웃, 하네스 검증설계, ROADMAP)을 소비하고 그 위에 얹는다. 정본과 어긋나는 지점은 §7에 분리해 표기하고, 문서를 먼저 고친 뒤 코드를 맞춘다.

---

## 0. 원칙

- 관리자 기능은 격리 모듈이다. 봇·카오스·모니터링·회원·게시판 운영은 배포단위 C(`exchange-admin`, 분리 포트·분리 네트워크·mTLS)에서만 동작한다. 코어 경로(매칭·정산·저널)에 새 의존성을 추가하지 않는다.
- 관측 데이터는 판단 근거일 뿐 실행 트리거가 아니다. 지표·로그·불변식 결과가 어떤 상태를 보여도 파괴 액션을 자동 실행하지 않는다.
- 데모 환경 한정이다. 실거래·실자산·실명·실금융자격증명은 없다.
- 관리자 평면은 거래 평면(§3)·데모 세션(§3-7)과 자격·키·세션을 공유하지 않는다. 데모 세션은 `scope=TRADE` 고정이고 관리 평면 사용 불가다(API §3-7).

## 1. 관리자 인증·권한 모델

### 1-1. 관리 평면 격리(정본 §3-6 소비)

관리 API는 다음 4중 방어를 그대로 상속한다. 신규 설계는 이를 재정의하지 않고 소비한다.

- 네트워크 격리: `admin.exchange.local` 별도 호스트·포트, 방화벽으로 운영자 네트워크만 접근. mTLS 필수(클라이언트 인증서 검증).
- 서명: JWT(HS256) + canonical(SHA512) + nonce + timestamp를 재사용하되 `scope=admin` 키 + 별도 `admin_secret`로 서명. `/admin/v1/**` path가 canonical에 포함되어 거래 서명과 교차 재사용 불가. 중첩 바디는 JCS(RFC 8785) canonical(§3-3(b))을 상속.
- 비가역 액션 이중 승인: `approval_token`(2인 승인·단회용·TTL 5분·action+대상 바인딩). 필수 대상은 §3-6 완결 열거이고 카오스 주입·해제 4종은 v2.34에서 빠졌다(§2-2). 빠진 4종도 토큰을 제시하면 같은 규칙으로 검증·소각한다.
- 감사·rate limit: 전 액션 `admin_audit_log` 적재, 관리 버킷 60토큰/60초(§2-5).

정본 §3-6은 2인 승인의 판정 근거를 자가신고 `operator_id`가 아니라 인증 주체(access_key·mTLS 인증서 CN) 유래 operator_id로 못박는다. 발급 요청의 인증 주체와 approval_token 사용 요청의 인증 주체가 서로 달라야 승인이 성립하며, 단일 키 보유자가 발급 시 `op-02`, 사용 시 `op-01`로 신고를 바꿔 혼자 2인 승인을 완성하는 경로를 물리 차단한다. 본 설계의 브라우저 인증 흐름(§1-3)은 이 반결탁 불변식을 보존하는 것을 최우선 제약으로 둔다.

### 1-2. 운영자·권한(RBAC) 모델

관리자 계정은 회원(`users`)·봇 계정과 분리된 운영자(operator) 개념이다. `api_keys.scope=ADMIN` 키가 운영자 1인에 1:1 바인딩된다(API §7-1 admin 키 규약).

권한은 역할 기반이다. 최소 권한 원칙으로 5역할을 둔다.

| 역할 | 권한 범위 |
|---|---|
| `VIEWER` | 조회 전용. 모니터링·상태·감사 로그 열람. 어떤 변경도 불가 |
| `BOT_OPS` | 봇 플릿 제어(생성·정지·OPS·시나리오·파라미터). 카오스 불가 |
| `CHAOS_OPS` | 카오스 주입·해제. 봇 제어 포함. 카오스 4종은 승인 불요이고 봇 파라미터 변경은 이중 승인 별도 필요 |
| `MEMBER_MOD` | 회원·게시판 운영(정지·복구·글 숨김·삭제) |
| `SUPER` | 전 권한 + 운영자·권한 관리. 단독으로 승인 필수 액션의 승인·요청 겸임 불가(2인 원칙 유지) |

- 이중 승인은 역할과 독립이다. `BOT_OPS`가 봇 파라미터 변경을 요청해도 승인 토큰은 다른 운영자가 발급한다(§3-6). `SUPER` 1인이 요청·승인을 겸할 수 없다. 승인 필수 액션 목록은 §3-2가 갖는다.
- 권한 검사 실패는 `403 admin_forbidden`(API §2-3), 승인 부족도 동일 코드에 `detail.reason`으로 구분.

### 1-3. 브라우저 관리자 UI 인증 흐름(mTLS 운영자 세션, 반결탁 보존)

브라우저는 `admin_secret`으로 HMAC 서명을 만들 수 없다. `secret_key`(및 `admin_secret`)를 브라우저에 전달하지 않는 계약(웹 화면명세서 §6.1, API §3-7) 때문이다. 거래 UI가 데모 세션으로 우회하는 것과 달리 관리 평면은 데모 세션을 쓸 수 없다(§3-7 범위 제한: `scope=TRADE` 고정). 관리 평면 브라우저 접속은 운영자별 mTLS 클라이언트 인증서로 1차 인증하고, 그 인증서 신원에서 유래한 단기 관리자 세션으로 후속 요청을 인증한다. 서명 비밀을 브라우저나 단일 서버 컴포넌트에 모으지 않으므로 §3-6 반결탁 불변식이 보존된다.

```
[운영자 워크스테이션 브라우저]
   │  ① 운영자 네트워크 전제 + 운영자별 mTLS 클라이언트 인증서(브라우저 설치, CN=operator_id)
   │     사설키는 각 운영자 워크스테이션에만 존재. 서버는 CA 공개키로 검증만 한다.
   ▼  mTLS(1차 인증)
[exchange-admin 관리 평면 (admin.exchange.local, 별도 호스트·컨텍스트)]
   │  ② mTLS 통과 후 인증서 CN=operator_id에 바인딩된 단기 관리자 세션 발급
   │     (세션 토큰은 mTLS 신원에서 유래, 자가신고 금지·관리 평면 전용·짧은 TTL)
   │  ③ 조회는 단독 운영자 세션으로 수행
   │  ④ 승인 필수 액션은 다른 운영자의 mTLS 세션으로 발급한 approval_token 동반
   ▼
[/admin/v1/** (§3-6 검증: operator_id는 mTLS 인증 주체 유래)]
```

- 1차 인증: mTLS 클라이언트 인증서 검증. 인증서 CN이 operator_id의 권위 소스이며 자가신고 바디 값이 아니다(§3-6 v2.4).
- 세션: mTLS 통과 시 서버가 인증서 신원에 바인딩된 단기 관리자 세션 토큰을 발급한다. 세션은 mTLS 신원에서 유래하고 운영자가 신원을 신고하지 않는다. 관리 평면 전용이며 거래 평면·데모 세션과 자격을 공유하지 않는다(§0).
- 조회(모니터링·상태·감사 열람)는 단독 운영자 세션으로 가능하다(`VIEWER` 이상).
- 승인 필수 액션(§3-2)은 approval_token 2인 승인 필수. approval_token은 요청 운영자와 다른 운영자가 자신의 mTLS 세션으로 `POST /admin/v1/approvals`를 호출해 발급한다. 승인 서명(발급 요청)은 승인자 자신의 mTLS 신원에서 유래하고, 대상 액션 요청은 요청자 자신의 mTLS 신원에서 유래한다. 카오스 4종은 필수 대상이 아니라 단독 운영자 세션으로 실행된다(§2-2-a).
- 반결탁 보존(§3-6 불변식): (a) 요청과 승인은 서로 다른 운영자의 mTLS 사설키 점유로만 성립한다. (b) 사설키는 각 운영자 워크스테이션에만 있고 어떤 단일 서버 컴포넌트도 전 운영자 키를 보유하지 않는다(서버는 CA 공개키만 보유). (c) 두 operator_id는 각 요청의 인증 주체(인증서 CN)에서 도출한다. 단일 컴포넌트·단일 키 보유자가 요청과 승인을 동시에 완성할 수 없다.
- 세션 만료·mTLS 실패는 `401 jwt_verification`, 권한·승인 부족은 `403 admin_forbidden`.
- BFF(존재 시)는 mTLS 종단·세션 중개면일 뿐 서명 비밀 보관면이 아니다. 운영자 사설키를 보관하지 않는다. mTLS 클라이언트 인증이 운영자 워크스테이션에서 관리 평면까지 종단으로 성립하도록 구성한다.
- 관리 세션 매개는 관측 데이터를 렌더만 하고, 응답 본문 텍스트를 지시로 해석해 파괴 액션을 생성하지 않는다(§6 안전 규약).

초안이 검토하던 운영자별 HMAC 서명키 하드웨어 봉인 방식은 이 확정안으로 대체한다. mTLS 사설키가 곧 운영자 키이므로 별도 서명키 봉인이 불요하고, 반결탁 요건 (a)·(b)·(c)를 동일하게 충족한다. 정본 개정 항목은 §7-4에 있다.

### 1-3-a. 게이트웨이 종단 토폴로지와 바인딩 강제(v2.7 신설)

`exchange.admin.mtls.trusted-forwarding=true`는 §1-3의 1차 인증을 앱 밖으로 내보내는 스위치다. 앱은 인증서를 직접 검증하지 않고, 앞단 게이트웨이가 mTLS를 종단한 뒤 실어 주는 `X-Operator-Cn` 헤더를 신원으로 받는다. 이 헤더는 검증 결과가 아니라 자가신고 값이다. 게이트웨이가 없는 곳에서 이 스위치가 켜지면 §1-3이 세운 "인증서 CN이 operator_id의 권위 소스"가 무너지고, 서버에 닿는 누구나 임의 CN으로 관리 평면에 닿는다.

- **이 스위치가 켜진 배포는 루프백에만 바인딩한다.** `server.address`가 루프백이 아니면 기동을 중단한다. 게이트웨이는 같은 호스트에서 루프백으로 프록시한다.
- **판정은 기동 시점에 한다.** 요청 시점 차단은 이미 열린 뒤라 늦다.
- **판정축은 프로파일이 아니라 주소다.** 프로파일 조건은 조합에 따라 꺼질 수 있고, 실제로 `RequireSecretsCondition`이 `dev`가 포함된 조합에서 꺼진다. 주소는 배포가 감출 수 없는 사실이다.
- **주소 미지정은 위반이다.** 미지정은 전 인터페이스 바인딩이고, 루프백 전용이 아니다.
- **판정은 문자열이 아니라 `InetAddress`로 한다.** `127.0.0.0/8` 전역과 `::1`, IPv4 매핑 표기가 모두 루프백이다. 문자열 비교는 `127.0.0.2`를 놓친다.

구현은 `server/app/src/main/java/kr/exchange/admin/AdminConfig.java`의 `adminForwardingBindingGuard`이고, 계약은 `AdminForwardingBindingGuardTest`가 고정한다. 이 토폴로지를 재현하는 통합 테스트도 `server.address=127.0.0.1`을 선언한다. 선언하지 않으면 테스트가 실제 배포에 금지된 조합을 모델링하게 된다.

### 1-4. 이중 승인·approval_token 수명주기(정본 §3-6 소비)

- 요청 operator와 다른 operator가 `POST /admin/v1/approvals`(mTLS + `scope=admin` 서명)로 발급. "다른 operator"는 자가신고 값이 아니라 인증 주체(access_key·인증서 CN) 유래 operator_id로 서버가 판정한다(§3-6 v2.4).
- 발급 시 `action` + 대상 식별자(`node`·`bot_id`·`toxic` 등)에 바인딩, 발급 주체 operator도 함께 바인딩. 단회용(검증 성공 즉시 소각)·TTL 5분.
- 바인딩된 action·대상과 다른 요청 사용, 만료·기소각 재사용은 `403 admin_forbidden`. 정적·재사용 토큰 금지.
- 발급·사용·만료·거부 전부 `admin_audit_log` 기록.

### 1-5. 스키마 추가(다음 가용 V 번호)

DB 정본은 `users`·`api_keys`·`accounts`를 이미 갖는다. `api_keys.scope` CHECK는 현재 `('READ','TRADE','WITHDRAW')`이며 `ADMIN`이 없다. 관리 평면용으로 다음 항목을 다음 가용 Flyway V 번호(현재 로드맵상 V4 이후)로 추가한다. 번호는 착수 시점 가용값으로 확정하고 여기서 고정하지 않는다.

- `api_keys.scope` CHECK 어휘에 `ADMIN` 추가(어휘 확장 마이그레이션, V5__admin.sql 반영 완료). scope 정본 어휘는 대문자 `READ|TRADE|WITHDRAW|ADMIN`이다(API §3-2 v2.10 통일). 소문자·`read_only` 표기는 폐기.
- `admin_operators`: 운영자 정체(`external_id UUID`, 표시명, 상태 `ACTIVE|DISABLED`, `created_at`). `api_keys`와 1:1(운영자 키 바인딩).
- `operator_roles` / `operator_role_grants`: 역할 어휘(§1-2 5역할)와 운영자·역할 매핑. append 이력 보존.
- `admin_approvals`: 승인 토큰 원장. `action`, 대상 식별자, `requester_operator_id`, `approver_operator_id`, `issued_at`, `expires_at`, `consumed_at`, `state`. **state 정본 어휘는 `ISSUED|CONSUMED|EXPIRED|REJECTED`**(V5__admin.sql CHECK, DEFAULT `ISSUED`). 단회 소각을 `consumed_at`·`state`로 강제, `requester_operator_id <> approver_operator_id` CHECK. 두 operator_id는 인증 주체 유래 값으로만 기록한다(§3-6). 웹 타입(`web/lib/admin/types.ts` `ApprovalState`)이 쓰는 `PENDING`/`APPROVED`는 이 어휘와 다르며 정본에 맞춰 `ISSUED`/(소각)`CONSUMED`로 수렴해야 한다(§7 W2).
- `admin_audit_log`: 관리 액션 append-only 감사(API §7-1이 이름을 이미 명시). DB 정본에는 범용 `audit_log`(V4 로드맵)만 있으므로 관리 전용 테이블을 신설한다. `forbid_mutation` 트리거로 UPDATE·DELETE·TRUNCATE 차단(기존 `audit_log` 패턴 재사용). 컬럼: `operator_id`(인증 주체 유래), `action`, 대상, `request_id`, `approval_id`(있으면), 요청 요지 JSONB, `created_at`.
- `system_config`: 마켓 halt·수수료 등 운용 상태 키·값. 관리 액션이 갱신하고 게이트웨이·매칭 접수가 소비한다(원장·저널 무접촉).
- `notices`: 공지 게시(제목·본문·`severity`·`active`·`published_at`·`published_by`). **severity 정본 어휘는 대문자 `INFO|WARNING|CRITICAL`**(V5__admin.sql CHECK, DEFAULT `INFO`). 와이어 값도 대문자다(웹 소문자 표기는 송신 시 대문자화·수신 시 소문자 정규화로 정합, API §4-D). 삭제는 소프트(`active=false`)이며 `app_role`에 DELETE 미부여(§1-4·DB 설계 §9).
- 회원·게시판 운영 대상 컬럼: `users.status`는 이미 `ACTIVE|SUSPENDED|CLOSED`를 가지므로 재사용. 게시판 모듈(M3 별도 설계)의 `board_posts.status`·`board_comments.status`(`VISIBLE|HIDDEN|DELETED`)를 소비만 한다. 관리 평면은 게시판 테이블에 물리 의존을 만들지 않고 상태 전이 API로만 접근한다.

### 1-6. 데모 mTLS 인증서 운영 절차

관리 평면 mTLS는 운영 프로파일에서 강제한다. dev/demo 프로파일은 로컬 접속용 데모 CA와 운영자 클라이언트 인증서로 mTLS 요건을 충족시켜 브라우저 관리 콘솔이 실제로 뜨게 한다. 운영 인증서는 이 절차 밖(운영 PKI)에서 발급하며, 아래는 데모 한정이다.

- 프로파일 게이트: 관리 평면은 `admin.exchange.local` 별도 호스트·컨텍스트에서만 서빙하고 고객 평면(`/api/v1`)·거래 웹과 물리 분리한다(§0, §4-1). mTLS 클라이언트 인증서 검증은 운영 프로파일에서 무조건 요구한다. dev/demo 프로파일은 데모 CA를 신뢰 앵커로 로드해 로컬 데모 인증서로 통과한다.
- 데모 CA: 데모 전용 루트 CA를 1회 생성한다(운영 CA와 분리, 데모 네임스페이스 한정). 개인키는 데모 환경 밖으로 반출하지 않는다. 서버는 이 CA 공개 인증서만 신뢰 앵커로 보유한다(사설키 미보유).
- 운영자 클라이언트 인증서: 운영자 1인당 1장 발급하고 `CN=operator_id`(또는 SAN에 operator_id)로 신원을 못박는다. CN은 §3-6 operator_id 도출의 권위 소스다. 사설키는 해당 운영자 워크스테이션에만 두고 브라우저 인증서 저장소에 설치한다.
- 발급 스크립트·산출물: 데모 CA 생성, 서버 인증서 발급, 운영자별 클라이언트 인증서(PKCS#12) 발급을 재현 가능한 스크립트로 문서화한다. 산출물은 데모 CA 공개 인증서, 서버 키·인증서, 운영자별 `.p12`(브라우저 임포트용). `.p12`는 데모 배포물에만 포함하고 운영 자격과 섞지 않는다.
- 반결탁과 정합: 데모에서도 운영자별로 서로 다른 클라이언트 인증서를 발급해야 2인 승인이 성립한다(§1-3 (a)·(c)). 단일 운영자 인증서만으로는 approvals 발급과 요청이 같은 인증 주체가 되어 승인 필수 액션이 반려된다(`403 admin_forbidden`). 인증서가 1장인 배포에서 카오스 4종만 실행되는 것은 이 제약의 우회가 아니라 §2-2-a 완화의 귀결이다.
- 폐기·회전: 데모 인증서는 데모 리셋 시 재발급한다. 유출·만료 시 데모 CA로 재발급하며 서버 신뢰 앵커 교체 없이 클라이언트 인증서만 회전한다.

## 2. 기능 명세

### 2-1. 봇 플릿 제어(정본 §6-A 소비)

기존 엔드포인트를 UI로 노출한다. 신규 API 없음.

- 생성: `POST /admin/v1/sim/bots`(유형 `MARKET_MAKER|TAKER|TREND|NOISE`, 수, 마켓, `params`, `seed`). `operator_id` 필수, approval 불요.
- 제거: `DELETE /admin/v1/sim/bots/{id}`. approval 불요.
- 파라미터 변경: `PATCH /admin/v1/sim/bots/{id}/params`. approval_token 필수(실행 중 파라미터 변경은 §3-6 필수 열거 항목).
- 전체 제어: `POST /admin/v1/sim/start|stop|pause`. approval 불요.
- 시나리오: `POST /admin/v1/sim/scenarios/{name}/activate`(`steady|volatile|spike|ramp|selloff|thundering-herd`).
- 전역 OPS: `PUT /admin/v1/sim/rate`.
- 대수 set-point: `PUT /admin/v1/sim/scale`(마켓·유형별 목표 봇 대수. 개별 생성/제거 위에 얹는 상위 제어). approval 불요.
- 방향성 set-point: `PUT /admin/v1/sim/bias`(마켓별 목표 net bias -1~+1·자동균형 강도). approval 불요.
- 효과 강도: `PUT /admin/v1/sim/effects`(체결 시각효과 `trade_flash`. 공개 `GET /api/v1/exchange-config`에 반영). approval 불요.
- 상태: `GET /admin/v1/sim/status`(봇 수·현재 OPS·성공률·평균지연·`duplicate_fill_total`. schema 1.1에서 마켓별 bias·유형별 대수·`fill_ratio`·`trade_flash` additive 확장).
- 텔레메트리: `WS /admin/v1/ws/sim/telemetry` 실시간 구독.

set-point 3종(scale·bias·effects)은 파괴 액션이 아니라 approval_token 불요이고 감사만 적재한다(API §6-A v2.10, §3-6 필수 완결 열거 불변). 봇 유형·자동균형 동작은 봇_방향성_거버넌스_설계, 효과 강도 단계·토큰은 체결_시각효과_관리자제어_설계가 상술한다.

### 2-2. 카오스 실험 콘솔(정본 §6-B + 하네스 E1~E9)

실험 카탈로그를 콘솔에서 선택·주입·해제한다. 카오스 주입·해제 4종(`chaos/network` POST·DELETE, `chaos/app`, `chaos/kill-node`)은 approval_token 불요다(API §3-6·§6-B v2.34). 토큰을 제시하면 종전 계약대로 검증·소각한다. E1~E9는 전부 이 4종 위에서 돌므로 실험 단위 승인 요구도 없다.

| ID | 실험 | 주입 경로 | approval |
|---|---|---|---|
| E1 | PG 지연·지터 | `POST /admin/v1/chaos/network`(latency) | 불요(제시 시 검증·소각) |
| E2 | PG 단절·블랙홀 | `POST /admin/v1/chaos/network`(down·timeout) | 불요(제시 시 검증·소각) |
| E3 | Redis 장애 | network toxic·app | 불요(제시 시 검증·소각) |
| E4 | 매칭 리더 kill(핵심 데모) | `POST /admin/v1/chaos/kill-node` | 불요(제시 시 검증·소각) |
| E5 | 네트워크 분할(split-brain 유도) | network disconnect | 불요(제시 시 검증·소각) |
| E6 | 폭주 + 리더 kill 복합(최종 증명) | 봇 스파이크 + kill-node 조합 | 불요(제시 시 검증·소각) |
| E7 | 그레이 장애(pause) | kill-node method 확장 | 불요(제시 시 검증·소각) |
| E8 | 앱 내부 지연·예외 폭풍 | `POST /admin/v1/chaos/app` | 불요(제시 시 검증·소각) |
| E9 | 커밋 응답 절단(멱등성 증명) | network toxic(limit_data·reset_peer) | 불요(제시 시 검증·소각) |

- toxic 해제: `DELETE /admin/v1/chaos/network/{toxic}`(approval 불요, 제시 시 검증·소각).
- 진행 중 실험·blast radius: `GET /admin/v1/chaos/experiments`(조회, approval 불요).
- 승인 발급: `POST /admin/v1/approvals`(2인 승인). 카오스에는 불요이고, 2인 운영 배포가 토큰을 실을 때와 §3-2 승인 필수 액션에 쓴다.
- 각 실험은 Grafana annotation을 자동 삽입해 지표 귀속(§6-B). 콘솔은 실험 실행 시 반환된 `experiment_id`·`grafana_annotation`을 표시한다.
- 콘솔은 실험 카탈로그를 정적 데이터로 제시하고, 주입은 운영자의 명시 클릭과 확인 다이얼로그 2단계를 거친다. 관측 값이 특정 임계를 넘어도 자동 주입하지 않는다.

### 2-2-a. 카오스 승인 완화(v2.34 소비)

완화 근거는 운영 규율이 아니라 운영 인원이다. 2인 승인은 발급 주체와 사용 주체가 서로 달라야 성립하는데(반결탁 CHECK `chk_approval_two_person`) 이 배포의 카오스 실행 주체는 1인이다. 1인 운영에서 그 조건을 만족시키려면 운영자 계정을 하나 더 만들어 혼자 두 역을 해야 하고, 그것은 2인 통제를 형해화하면서 형식만 남긴다. 규정을 사실에 맞춘 결정이며 근거는 커밋 89b1e40과 API §6-B v2.34 패치 노트에 있다.

완화 범위는 카오스 4종뿐이다. 2인 승인 체계와 반결탁 불변식은 그대로 살아 있고 §3-2의 승인 필수 액션(봇 파라미터 변경, 마켓 halt·resume·수수료, 운영자 생성·상태·역할, 회원 폐쇄)에 계속 적용된다. 2인 운영 배포는 카오스에도 토큰을 실어 종전 계약대로 쓴다. 구현은 `server/app/src/main/java/kr/exchange/admin/ChaosAdminController.java`의 `consumeIfPresent`이고, 토큰이 없으면 `approval_id`가 null인 채 진행한다.

완화의 대가는 다음과 같다.

- 카오스 4종에서 사전 통제가 사라진다. 남는 것은 역할 게이트(`CHAOS_OPS`)·대상 문자열 검증(`requireSafeTarget`)·사후 감사뿐이다.
- 관리 키 또는 관리 세션 하나가 탈취되면 그 주체 단독으로 리더 kill과 네트워크 단절을 주입할 수 있다. 종전에는 두 번째 운영자의 승인 발급이 추가로 필요했다.
- 오조작을 거를 두 번째 눈이 없다. 잘못된 노드 지정은 확인 다이얼로그와 대상 검증만 통과하면 실행된다.
- `admin_audit_log.approval_id`에 null 행과 값 있는 행이 섞인다. 카오스 4종의 null은 승인 우회가 아니라 계약이며, 감사 판독에 이 구분이 필요하다.
- 승인 요구를 설정으로 되돌리는 스위치가 없다. `consumeIfPresent`에 조건이 없어 2인 운영 배포로 옮길 때 필수화는 코드 변경을 요구한다.

파괴성 자체는 줄지 않았고 승인 요구만 줄었다. 화면은 이 액션들을 계속 파괴 액션으로 표시한다(§4-2).

### 2-3. 노드·지표 모니터링(정본 §6-C + 하네스 소비, 읽기 전용)

소비 소스와 화면 대응.

- 헬스·복구: `GET /actuator/health/liveness|readiness`, `GET /admin/v1/ha/status`(`lease{holder,epoch,lease_until,leader_alive,lease_remaining_ms}`·워터마크·`snapshot_seq`·`trades_count`·`recovery_runs_count`·`last_failover`. **`role`·`node`·`follower_lag_seq`·`matching_market_owner`는 방출하지 않는다.** 노드 팔로워 레지스트리와 복제 큐가 단일 라이터 구조에 없다. API§6-C), `GET /admin/v1/ha/recovery`(`verdict{}` 판정 객체 + `recovery_runs[]` + `failover_runs[]`. 불변식은 `GET /admin/v1/ha/invariants`가 `invariant_checks`의 `check_name`별 최신 행으로 낸다. 저장 행 조회이지 호출 시점 재검증이 아니다. API§6-C v2.33).
- 불변식 이력: `invariant_checks` 테이블(직조회 또는 admin 조회 API). `check_name`·`ok`·`violated_rows`·`details`.
- 복구 이력: `recovery_runs` 테이블(재생 소요 `duration_ms`·`replayed_from/to_seq`·`matched`·재생 창 식별자 `fp_replay`/`fp_live`). 판정은 `matched`이고 fp는 창 표시다(DB§5.5).
- Prometheus 지표: `exchange_ledger_imbalance{asset}`(자산 보존, 수평선 0), `exchange_invariant_violations{check_name}`, `exchange_leader_epoch`, `exchange_failover_downtime_seconds`, `exchange_sequencer_queue_size`, `exchange_order_latency_seconds`(p99), `hikaricp_connections_pending`, `exchange_trades_total`. 대시보드는 Grafana를 iframe 임베드하거나 Prometheus 쿼리 결과를 패널로 렌더한다.
- 전 항목 읽기 전용이다. 모니터링 화면에서 파괴 액션 버튼을 노출하지 않는다(§6 안전).

### 2-4. 회원·게시판 운영

- 회원: 목록·상세 조회, 정지(`SUSPENDED`)·복구(`ACTIVE`)·폐쇄(`CLOSED`). 정지·복구는 가역이므로 `operator_id`만, 폐쇄는 비가역이므로 이중 승인(§4-2, §7 정합 주의).
- 게시판: 코인별 게시판의 글·댓글에 대해 숨김(`HIDDEN`)·복구(`VISIBLE`)·삭제(`DELETED`, soft). soft delete는 가역이므로 `operator_id`만. 하드 퍼지(영구 삭제)는 데모 범위에서 제공하지 않는다(영구 삭제는 금지 액션군).
- 모든 운영 액션은 `admin_audit_log`에 대상·사유·운영자를 남긴다.
- 게시판 모듈은 매칭 핫패스와 격리되어 있으므로(ROADMAP M3), 운영 액션이 실패해도 거래 상시 게이트에 영향이 없어야 한다. 운영 API는 게시판 모듈 경계 안에서만 동작한다.

| POST | `/admin/v1/operators/{id}/roles` | 역할 부여·회수(SUPER 전용) | 필수 |
| PATCH | `/admin/v1/config/markets/{symbol}/fees` | 마켓 수수료 변경(부분 갱신, SUPER 전용) | 필수 |
| PATCH | `/admin/v1/config/notices/{id}` | 공지 부분 갱신(제목·본문·severity·active 토글) | 불요 |
| DELETE | `/admin/v1/config/notices/{id}` | 공지 소프트 삭제(`active=false`, 하드 삭제 금지) | 불요 |
| GET | `/admin/v1/chaos/runs` | 카오스 주입 이력 프로젝션(토큰 미노출) | 불요 |
| GET | `/admin/v1/audit` | 감사 로그 조회(운영자·action·기간 필터) | 불요 |

- 모든 리스트는 §2-2 엔벌로프 + opaque 커서(§2-6), 페이로드 `schema_version` 포함.
- 회원 조회 응답은 데모 계정 자산·상태만 노출한다. 실명·실금융정보는 존재하지 않으므로 노출 대상 자체가 없다.
- 공지 삭제는 소프트 삭제다. `app_role`에 `notices` DELETE 권한이 없어(DB 설계 §3.1, V5 GRANT는 SELECT/INSERT/UPDATE) 하드 DELETE는 운영 롤에서 상시 실패한다. `active=false` UPDATE로 노출만 내리고 게시 원본·감사 이력을 보존한다. 없는 id는 404, 이미 비활성이면 멱등 200.

### 3-2. 파괴·비가역 액션 이중 승인·감사 매트릭스

approval_token 필수 액션(§3-6 필수 열거 + 본 설계 확장분).

- 기존(§3-6 완결 열거): `sim/bots/{id}/params`.
- 신설 확장: `members/{external_id}/close`, `operators/{id}/roles`, `operators.create`, `operators.status`, `config.market.halt`, `config.market.resume`, `config.market.fees`. API §3-6 완결 열거·§6-D 표에 승인 필수로 등재한다.
- 승인 불요(감사만)이지만 파괴 액션: 카오스 주입·해제 4종(`chaos/kill-node`, `chaos/network` POST·DELETE, `chaos/app`). API §3-6·§6-B v2.34가 필수 열거에서 뺐다. 토큰을 제시하면 아래 바인딩 규칙으로 검증·소각하고, 제시하지 않으면 `approval_id`가 null인 채 감사에 적재된다. 완화 근거와 대가는 §2-2-a에 있다.
- 승인 불요(감사만)이고 비파괴: `config.notice.publish`, `config.notice.update`, `config.notice.delete`(소프트). 공지는 원장·매칭에 닿지 않는 운용 상태라 SUPER 단독으로 처리한다.
- 확장은 §3-6의 "완결 열거"를 넘어서므로 API 정본을 먼저 개정해야 한다(§7-1 참조). 개정 전에는 본 설계의 승인 요구가 코드에 반영될 수 없다.
- 각 액션의 파괴 액션 바디 필드와 발급·소각 `target` 문자열 형식은 API §3-6 "바인딩 target·바디 필드 확정표"(v2.13)가 정본이다. 요지: 자원 스코프는 `target`=자원 식별자(node·name·assault·toxic·symbol·bot_id·new_operator_id), 전이 스코프 `operators.status`는 `{id}:{STATUS}`·`operators.roles`는 `{id}:{GRANT|REVOKE}:{ROLE}`(대문자 정규화). `operators.create`는 수행자 `operator_id`와 생성 대상 `new_operator_id`를 분리한다.

전 관리 엔드포인트(조회 포함)는 예외 없이 `admin_audit_log` 적재 대상이다. 승인 필수 액션은 요청 바디에 `operator_id` + `approval_token`을 포함하고, 누락·불일치·만료는 `403 admin_forbidden`. 카오스 4종은 `operator_id`만 필수이며, 토큰을 실었는데 불일치·만료면 같은 코드로 거부한다. `operator_id`의 권위는 바디 자가신고 값이 아니라 인증 주체 유래 값이다(§3-6 v2.4).

## 4. 프론트 설계(관리자 화면)

### 4-1. 라우트·레이아웃 분리

- 거래 UI(`/exchange/**`)와 물리적으로 분리한다. 관리자 UI는 별도 오리진(`admin.exchange.local`)에서 서빙되며 거래 앱 번들·라우트를 공유하지 않는다.
- 관리자 라우트 예: `/admin/overview`(대시보드), `/admin/bots`, `/admin/chaos`, `/admin/monitoring`, `/admin/members`, `/admin/board`, `/admin/audit`.
- 레이아웃: 좌측 사이드 내비 + 상단 운영자 바(운영자명·역할 배지·세션 만료 표시·로그아웃). 거래 UI의 `HeaderNav`를 재사용하지 않는다. 고정형 데스크톱 전제(최소 1280px, 데스크톱 레이아웃 §4)는 유지.
- `PanelCard`·`DataTable` 등 레이아웃 프리미티브는 재사용 가능하나, 거래 도메인 컴포넌트(OrderPanel·OrderbookPanel 등)는 가져오지 않는다.

### 4-2. 화면 구성

- 봇 제어판: 플릿 요약(활성 봇·현재 OPS·성공률·평균지연·`duplicate_fill_total`), 시나리오 선택 SegmentedTab, OPS 슬라이더, 봇 생성 폼, 실행 중 파라미터 변경(승인 토큰 입력 동반). 실시간은 `sim/telemetry` WS.
- 시장 생동감 컨트롤(정본 §6-A set-point 소비): 마켓·유형별 대수 set-point(`sim/scale`), 방향 바이어스 슬라이더(Blue~중립~Red, 부호·화살표·수치 병기, 색 단독 표현 금지)와 자동균형 토글(`sim/bias`), 효과 강도 4단계 세그먼트(`off|subtle|normal|strong`, `sim/effects`). 셋 다 approval 불요·감사만. 현재값은 `sim/status` schema 1.1로 표시.
- 카오스 콘솔: E1~E9 카탈로그 카드, 각 카드에 blast radius와 파괴 액션 표시. 주입은 명시 클릭과 확인 다이얼로그 2단계다. 승인 토큰 입력란은 선택이며 2인 운영 배포에서만 채운다. 진행 중 실험 목록과 해제 버튼.
- 모니터링 대시보드: HA 상태(리스 보유자·epoch·워터마크. `follower_lag`는 방출도 렌더도 없다), `invariant_checks` 최신 행 배지(실측 26종. 검증설계 §4-4가 수용 기준 7종과 이 항목들을 잇는다. 저장 행이라 갱신 시각을 함께 띄운다), `verdict{}` 집계 판정(재생 축·페일오버 축·전체), `recovery_runs` 최근 재생 표(창·`matched`·재생 소요·재생 창 식별자·유실은 미측정 표기), `invariant_checks` 이력 테이블. 읽기 전용.
  - 페일오버 RTO는 이 화면에 없다. 원천이 `harness.failover_runs`이고 종합 화면(`HealthHero`)이 띄운다. 모니터링의 재생 소요와 축이 다르므로 한 표에 섞지 않는다.
  - Grafana 임베드 패널은 미구현이다. 화면에 `iframe`이 없다. §2-3이 규정한 임베드는 후속 과제다.
- 회원·게시판 관리: `DataTable` 기반 목록·필터·상세, 정지·복구·폐쇄·숨김·삭제 액션(가역/비가역 시각 구분).
- 감사 로그: append-only 조회 테이블(운영자·action·대상·시각, 클라이언트 필터: 운영자·액션·결과·기간). 표시층은 액션 코드에 한국어 주해를 병기하되 원문 코드를 상시 노출한다. 기록 원문은 불변.

### 4-3. 시스템 헬스 색 도메인(시세색과 분리)

- 헬스 상태는 `--color-success`(green)·`--color-warning`(orange)·`--color-danger`(crimson)와 대응 `-bg`·`-text` 토큰을 쓴다. 상태 전이 플래시는 `--color-health-flash-success|warning|danger`를 쓴다(디자인시스템 §시스템 헬스).
- 시세색(상승 Red `--color-up`, 하락 Blue `--color-down`)을 헬스 도메인에 차용하지 않는다. green은 시스템 성공 전용이며 가격 방향에 쓰지 않는다(디자인시스템 규칙 13).
- 상태 표현은 색 단독 금지. 점·아이콘·라벨 텍스트를 병기한다(danger는 항상 아이콘+라벨 동반). 대비 4.5:1, 탭 타깃 44px, reduced-motion 준수.
- 상태(로딩·빈·에러) 설계: 각 패널은 스켈레톤 로딩, 데이터 없음 빈 상태, 조회 실패 에러 상태를 명시 렌더한다. WS 단절은 헤더에 연결 상태 점(연결 green·단절 crimson)으로 노출하되 시세 도메인과 색을 분리한다.
- 실시간 갱신은 시각 소음 없이 전달한다. 지표 급변은 플래시 1회로 제한하고 스크롤·리플로우를 유발하지 않는다.

## 5. 하드코딩·토큰 규약

- 프론트 하드코딩 hex 금지(코인 브랜드색 데이터만 예외). 헬스 색은 전부 토큰 소비.
- 금액·수량은 문자열(`NUMERIC(40,18)`), float 금지. 봇 파라미터·시드도 문자열 표기(정수·불리언 필드만 예외, §3-3(b)).
- 관리자 UI도 런타임 외부 API 의존 금지. Grafana·Prometheus는 운영자 네트워크 내부 스택이며 외부 시세·외부 데이터에 의존하지 않는다.

## 6. 안전 규약

- 관측 데이터 지시 자동 실행 금지: 지표·로그·불변식 결과·게시글 본문 등 관측 경로로 들어온 텍스트를 명령으로 해석해 API를 호출하지 않는다. 서명 매개는 프록시·렌더만 하고 파괴 액션 생성 권한이 없다.
- 파괴 액션은 운영자 명시 요청 전제: kill-node·network·app·파라미터 변경·회원 폐쇄·역할 변경은 운영자의 직접 조작이 있어야 실행된다. 파라미터 변경·회원 폐쇄·역할 변경은 2인 승인 토큰도 필요하고, 카오스 4종은 v2.34 완화로 직접 조작만 전제한다(§2-2-a). 임계 초과·경보 발생만으로 실행되지 않는다.
- 금지 액션군: 실금융자격증명 입력, 계정 실인증, 영구 삭제(하드 퍼지·감사 로그 삭제), 자금 이동·거래 체결. 데모 시뮬레이션 범위 밖 요청은 거부한다.
- 데모 한정: 전 기능은 시드된 데모 환경에서만 유효하다. 데모 리셋 시에만 네임스페이스가 초기화된다(§2-4 보존 정책).
- 최소 권한·2인 원칙: 조회는 `VIEWER`, 변경은 역할별, 승인 필수 액션(§3-2)은 이중 승인. `SUPER` 단독 겸임 불가. 반결탁은 서명 키 보관 주체의 물리 분리(§1-3)로 뒷받침한다. 카오스 4종은 이 원칙의 적용 대상에서 빠졌고 그 자리를 역할 게이트와 사후 감사가 대신한다(§2-2-a).

## 7. 정본 정합·미결

정본과 어긋나거나 정본 개정을 선행해야 하는 지점. 문서를 먼저 고친 뒤 코드를 맞춘다.

1. API §3-6 approval 필수 열거 확장: §3-6은 approval_token 필수 액션을 "완결 열거"로 못박고 "그 외 전부 불요"로 규정한다. 본 설계는 `members/close`·`operators/roles`를 승인 필수로 확장한다. 이는 §3-6 개정(열거 항목 추가) 없이는 성립하지 않는다. API 문서를 먼저 개정한다.
2. `api_keys.scope` ADMIN 확장(해소, v1.2): V5__admin.sql이 CHECK를 `('READ','TRADE','WITHDRAW','ADMIN')`로 확장하고 `(scope='ADMIN') = (operator_id IS NOT NULL)` 바인딩 CHECK를 추가해 API §3-2/§7-1 전제를 충족한다. scope 정본 어휘는 대문자 4종이며 API §3-2 v2.10이 소문자·`read_only` 표기를 폐기했다.
3. `admin_audit_log` 테이블 부재: API §7-1은 `admin_audit_log`를 명시하나 DB 정본에는 범용 `audit_log`(V4 로드맵)만 있다. 관리 전용 append-only 테이블을 신설한다(다음 가용 V).
4. 관리 UI 인증 방식 확정(v1.1): §3-6은 관리 클라이언트의 mTLS + HMAC 서명을 전제하나 브라우저는 HMAC 서명 불가이고, §3-7 데모 세션은 관리 평면 사용 불가(`scope=TRADE` 고정)로 명시된다. 브라우저 관리 콘솔 인증을 다음으로 확정한다(이 결정이 정본 개정 승인이다). 운영자별 mTLS 클라이언트 인증서(`CN=operator_id`)로 1차 인증하고, 그 신원에서 유래한 단기 관리자 세션으로 후속 요청을 인증한다(§1-3). 세션은 mTLS 신원 유래이며 자가신고를 금지하고 관리 평면 전용이다. 조회는 단독 운영자 세션으로 가능, 파괴 액션(마켓 halt/resume, 봇 정지·파라미터, 운영자 관리)은 다른 운영자의 mTLS 세션으로 발급한 approval_token 2인 승인 필수다. 카오스 주입은 v2.34 완화로 단독 운영자 세션에서 실행된다(§2-2-a). 반결탁 요건 충족: (a) 요청·승인은 서로 다른 운영자의 mTLS 사설키 점유로만 성립한다. (b) 사설키는 각 운영자 워크스테이션에만 존재하고 단일 서버 컴포넌트가 전 운영자 키를 미보유한다(서버는 CA 공개키만 보유). (c) 2인 승인 판정은 §3-6 v2.4대로 인증 주체(인증서 CN) 유래 operator_id로만 한다. 초안의 운영자별 HMAC 서명키 하드웨어 봉인 방식은 이 확정안으로 대체한다(mTLS 사설키가 곧 운영자 키). 데모 mTLS 인증서 운영 절차는 §1-6, API 명문화는 §3-6 브라우저 관리 콘솔 세션 절(항목 1의 API 개정과 함께).
5. 게시판 테이블 의존: 회원·게시판 운영은 M3 게시판 모듈(별도 설계)의 `board_posts.status`·`board_comments.status`를 소비한다. 게시판 설계가 확정되면 상태 어휘·전이 API를 정합한다. 관리 평면은 게시판 테이블에 물리 FK를 만들지 않는다(격리).
6. V 번호(부분 해소, v1.2): 관리 평면 스키마(scope 확장·운영자·승인·역할·system_config)는 V5__admin.sql로 배정·적용됐다. 잔여 신규 마이그레이션(범용 `audit_log` 감사 트리거 등)은 착수 시점 다음 가용 V(현재 V6 이후)로 배정하며 본 문서에서 고정하지 않는다.
7. ## 반영한 비평

- (high) 관리 BFF 반결탁 결함: 단일 BFF가 전 운영자 `admin_secret`·키를 보유하고 세션 기준으로 대신 서명하면 그 컴포넌트 하나가 요청 서명과 승인 서명을 모두 재현할 수 있어, §3-6(operator 신원 바인딩 v2.4, line 370)이 물리 강제한 반결탁 불변식이 무너진다. §1-3을 개정해 서명 키 보관을 운영자별로 물리 분리(하드웨어 토큰·인증서 봉인)하고, 단일 컴포넌트의 전 키 보유를 금지했다. 요청 서명과 approval 서명이 서로 다른 운영자 키 점유로만 생성되도록 못박고, §1-1·§1-4·§3-2·§6에 인증 주체 유래 operator_id 판정을 명시했으며, §7-4에 반결탁 정본 개정 요건 3항(a·b·c)을 추가했다.
- (medium) 역할 수 불일치: §1-2 서두의 "4역할"이 5행 표·§1-5 "5역할"과 모순이었다. 표 기준으로 "5역할"로 정정했다.
- (low) 영어 메타 서문: 초안 첫 행의 영어 대화체 서문("I have full context from the canonical docs...")을 삭제하고 제목부터 시작하도록 했다(CLAUDE.md 규칙 3·4).

- (v1.1) 브라우저 관리 콘솔 인증 확정: §7-4 미결(관리 UI 인증 방식)을 사용자·워크플로우 권한으로 확정 개정했다. 운영자별 mTLS 클라이언트 인증서(CN=operator_id) 1차 인증 + mTLS 신원 유래 단기 관리자 세션 + 파괴 액션 2인 승인(승인 서명은 승인자 mTLS 신원 유래)으로 정한다. 초안의 운영자별 HMAC 서명키 하드웨어 봉인 방식은 mTLS 사설키가 곧 운영자 키이므로 대체했다. 반결탁 요건 (a)·(b)·(c)는 동일하게 충족한다. §1-3 흐름을 mTLS 세션 모델로 다시 쓰고, §1-6 데모 mTLS 인증서 운영 절차를 추가하고, §7-4를 미결에서 확정으로 바꿨다. API §3-6에 브라우저 관리 콘솔 세션 경로를 명문화하는 개정을 동반한다.
