# M3 종목 토론 게시판 설계서 (v0.3, 문서 산출본)

> 대상 마일스톤: M3(커뮤니티·관리자). 본 문서는 설계만 확정한다(구현 아님). 정본은 `docs/ROADMAP.md`(M3 범위·상시 게이트), `docs/백엔드_DB_설계.md`(스키마·타입·V 이력 규칙), `docs/백엔드_API_설계.md`(엔벌로프·에러·인증), `docs/프론트_디자인시스템.md`(tokens.css), `docs/데스크톱_레이아웃설계.md`(고정형 1280·HeaderNav·DataSource). 코드가 이 정본과 어긋나면 정본을 먼저 고친다.
> 최상위 제약(ROADMAP §원칙): 게시판은 코어 경로(매칭·정산·저널)에 의존성을 추가하지 않는다. 게시판 부하·장애가 거래 상시 게이트(자산합 0, 주문 중복·유실 0, RTO 30초)에 영향 0이어야 M3 완료다. 본 설계의 모든 결정은 이 격리 제약에서 역산한다.

---

## 0. 설계 원칙

- 게시판은 거래의 부가 기능이다. 코어가 게시판을 알지 못하고, 게시판이 코어의 런타임 자원을 건드리지 않는다. 방향은 단방향 소비(회원 신원)만 허용한다.
- 격리는 논리 분리(스키마·모듈 경계)에 그치지 않고 물리 분리(별도 DB 인스턴스·별도 프로세스·별도 커넥션 풀)까지 간다. 논리 분리만으로는 커넥션 풀 경쟁·WAL·vacuum·잠금 전파를 막지 못한다.
- 회원 신원은 M2가 발급한 인증 토큰의 검증만으로 취득한다. 검증은 비대칭 공개키로 하며(§2.4), 게시판은 코어 `users` 테이블을 런타임에 조회하지 않는다.
- 격리는 인증 자격까지 관통한다. 게시판이 코어가 그대로 수용하는 토큰을 위조할 수 있는 대칭 비밀을 보유하면 침해가 거래로 전파될 수 있으므로, 대칭키 공유는 채택하지 않는다(§2.4, §7).
- 금액·수량 타입 규칙(NUMERIC(40,18), float 금지)은 게시판에 해당 없다. 게시판 수치는 카운트(정수)뿐이다.
- 산출물 스타일 규칙(em dash·en dash·이모지·AI 어투 금지, 개조식 평서문)을 코드·주석·문서·커밋에 적용한다.

## 1. 도메인 모델

### 1.1 개념

| 개념 | 정의 | 키 |
|---|---|---|
| Board(게시판) | 코인(마켓)별 토론 공간. 물리 테이블 없이 `market_symbol` 값으로 분할 | `market_symbol`(예: `KRW-BTC`) 문자열 |
| Post(글) | 회원이 작성하는 제목·본문 단위 | `external_id`(UUID) |
| Comment(댓글) | 글에 달리는 1뎁스 댓글. 대댓글은 `parent_comment_id`로 1단계까지만 | `external_id`(UUID) |
| Like(좋아요) | 회원·대상 1:1 토글. 글·댓글 각각 | `(target, member)` 유니크 |
| Report(신고) | 글·댓글 신고. 최소 운영용 | `id` |
| MemberProfile(회원 프로젝션) | 표시명 등 회원 식별의 로컬 복제본. M2에서 비동기 동기화(계약 조건 §2.4·§7) | `member_external_id`(UUID) |
| RankSnapshot(인기 순위 스냅샷) | 인기순 페이징용 불변 순위. 주기적 산출 | `(market_symbol, post_id)` |

- Board는 별도 테이블을 두지 않는다. `market_symbol`은 코어 `markets`로의 물리 FK가 아니라 문자열 값이다(격리 §2.2). 유효 마켓 검증은 게시판이 보유한 로컬 마켓 목록 캐시(시드 타임 주입 또는 M2/시드 이벤트로 갱신)로 수행하고, 미존재 마켓은 `404`로 거른다.
- 작성자는 회원(M2)이다. 게시판은 작성자를 `member_external_id`(UUID)로만 참조한다. 표시명(handle)은 작성 시점 토큰 클레임에서 취득해 denormalize 저장하고, 변경은 `member_profile` 프로젝션으로 갱신한다.
- 작성자 권위는 회원 식별자(`member_external_id`)다. handle은 동명이인·변경 가능한 표시 스냅샷이라 소유권 판정 근거가 아니다. 공개 조회는 작성자 식별자를 노출하지 않고, 소유권은 서버가 선택 인증으로 산출한 `mine` 불리언으로만 전달한다(§4). 프론트의 수정·삭제 어포던스는 handle 대조가 아니라 이 `mine`으로 판정한다.

### 1.2 목록·페이징·정렬

- 페이징은 커서 단일 축(API 설계 §2-6 계승). `cursor`는 `(정렬키, id)` 복합키를 base64url로 인코딩한 opaque 값이다. 경계는 exclusive(중복 방지), 오프셋(page) 방식은 실시간 삽입 시 중복·누락으로 미채택.
- 정렬 옵션 2종.
  - `latest`(기본): `created_at DESC, id DESC`. 커서 축 = `(created_at, id)`. 정렬키가 불변이므로 커서가 안정적이다.
  - `popular`(인기): 가변 집계값 `like_count`를 커서 축에 직접 쓰지 않는다. `like_count`는 페이징 도중 증감해 경계가 이동하고, 이는 같은 절이 오프셋 방식을 배격한 근거(실시간 변동 시 중복·누락)와 동일한 불안정성을 낳기 때문이다. 대신 주기적으로 산출한 순위 스냅샷 `post_rank_snapshot`(§3)을 페이징 축으로 쓴다. 커서 축 = `(rank_score, post_id)`이며 스냅샷 한 세대 안에서 불변이라 안정적이다. 실시간 `like_count`는 응답에 표시용으로만 싣는다. 스냅샷 갱신 주기·집계 창(예: 24시간)은 운영 파라미터(§7). 스냅샷 세대가 페이징 도중 교체되면 다음 요청부터 새 세대를 반영하되, 한 커서 시퀀스 내에서는 커서에 인코딩된 세대를 고정해 정합을 유지한다.
- 응답 엔벌로프는 API 설계 §2-2 그대로: `{ schema_version, data:[...], pagination:{ next_cursor, has_more } }`. 페이지 없어도 `pagination:{next_cursor:null,has_more:false}`로 통일.
- `count`는 기본 20, 최대 50. 목록 조회는 비로그인 허용.

### 1.3 상태·삭제

- Post·Comment status: `VISIBLE`, `HIDDEN`(운영자 숨김), `DELETED`(soft). 물리 삭제(하드 delete) 없음. `deleted_at` 세팅으로 soft delete하고 본문과 제목 모두 같은 문자열로 마스킹 응답("삭제된 글입니다", 댓글은 "삭제된 댓글입니다").
- 삭제·숨김은 목록·집계에서 제외한다. 댓글이 달린 글의 soft delete는 트리 유지를 위해 본문만 마스킹, 자식 댓글은 존치.
- `DELETED`는 종료 상태다. 운영 모더레이션(HIDE·UNHIDE·DELETE)은 `DELETED` 대상에 전이를 적용하지 않고 거부한다. 회원 자가삭제 글에 HIDE→UNHIDE 2단계로 마스킹을 푸는 부활을 막는다. `UNHIDE`는 직전 `HIDDEN`만 `VISIBLE`로 복구한다. 상태 판정·전이·집계 갱신은 대상 행 잠금(FOR UPDATE) 아래 한 트랜잭션에서 수행한다.
- like_count·comment_count는 denormalize 컬럼이며 게시판 DB 내부 트랜잭션·트리거로만 정합을 맞춘다(코어 원장과 무관).

## 2. 격리 설계 (핵심)

목표: 게시판 DB 부하·장애가 거래에 전파되지 않는다. 코어 트랜잭션·자원과 경쟁하지 않는다. 아래 5개 층에서 물리·논리 격리를 강제한다.

### 2.1 배포·프로세스 격리

- 신규 배포 단위 D = `community-api`를 추가한다. 기존 멀티모듈(common-dto / exchange-core / exchange-api(A) / exchange-admin(C) / bot-simulator(B), API 설계 §0-1)에 `community-api`를 D로 병렬 추가한다.
- `community-api`는 별도 JVM·별도 컨테이너로 배포한다. 매칭 JVM(exchange-api·exchange-core)과 프로세스·힙·GC·CPU 자원을 공유하지 않는다. 게시판의 GC 스톱·메모리 압력·스레드 폭주가 매칭 루프 시간에 물리적으로 전파될 수 없다(API 설계 §0-1의 "같은 JVM이면 자동 복구 관찰 불가" 근거와 동일 논리).
- 코드 경계는 ArchUnit로 빌드 게이트한다. `community-api`가 `exchange-core`·`exchange-api` 패키지 심볼을 import하면 빌드 실패. 반대 방향(코어가 community를 참조)도 금지. 공유 허용은 `common-dto` 중 순수 DTO·enum에 한정.

### 2.2 데이터 격리

- 별도 PostgreSQL 인스턴스 `community-db`를 둔다. 원장(`ledger_entries`·`ledger_transactions`)·저널(`command_journal`·`event_journal`)·`orders`·`balances`가 있는 거래 DB와 물리 분리한다.
- 크로스 DB 물리 FK는 두지 않는다(불가). 게시판 테이블은 코어 테이블과 어떤 FK·조인·트리거로도 연결되지 않는다. 게시판은 거래 DB 커넥션을 단 하나도 열지 않는다. 따라서 게시판 쓰기 폭주가 거래 DB의 커넥션 풀·row lock·WAL flush·autovacuum·체크포인트에 경쟁을 만들 수 없다.
- 회원 신원의 코어 종속 제거: 작성자 검증은 §2.4 인증 토큰 서명 검증(로컬 공개키 연산)만으로 끝낸다. 표시명은 `member_profile` 프로젝션(§2.4)에서 읽고, 프로젝션은 M2 아웃박스 이벤트로 비동기 갱신한다(계약 조건 §2.4·§7). 런타임에 코어를 향한 동기 호출·조회는 0이다.
- 데모 편의상 단일 PostgreSQL 인스턴스에 동거시키는 축소 구성일 때만, 별도 데이터베이스(또는 최소한 별도 스키마 `community`) + 별도 커넥션 풀로 둔다. 이 경우에도 게시판 마이그레이션은 코어 V 이력과 섞지 않는다.

### 2.3 커넥션 풀·마이그레이션 격리

- `community-api` 전용 HikariCP 풀을 둔다. 코어 풀과 분리되어 게시판 풀 고갈은 게시판 내부에 국한한다. 게시판 풀 max size는 거래 DB와 무관한 값으로 별도 산정한다.
- 마이그레이션은 `community-api` 자체 Flyway 이력(`community-api/src/main/resources/db/migration/`)으로 관리한다. 코어의 V0~V1(구현)·V2~V4(로드맵) 이력과 분리된 독립 라인이다. 게시판 신규 테이블은 이 독립 라인의 다음 가용 버전에 추가한다. 버전 번호는 고정하지 않는다(코어 DB 설계의 V 부여 규칙과 동일 원칙). 데모 동거 구성일 때만 코어 인스턴스의 별도 스키마에 다음 가용 V 번호로 얹되, 번호는 착수 시점 가용 값으로 정한다.

### 2.4 회원 인증 소비 (M2)

- 쓰기 엔드포인트는 회원 인증을 요구한다. 브라우저 데모 경로는 M2 세션 토큰(Bearer)을 소비한다. 봇·외부 클라이언트가 게시판 쓰기를 하지 않으므로 §3 HMAC 서명 경로는 게시판 API 계약에 포함하지 않는다.
- 검증은 비대칭 공개키로만 한다. `community-api`는 M2 발급자의 공개키로 토큰의 서명·`exp`·scope를 검증하고, 개인키(서명 발급 능력)는 보유하지 않는다. 대칭키(HS256) 공유는 채택하지 않는다. 격리 대상인 게시판 모듈이 대칭 비밀을 보유하면, 코어 게이트웨이가 그대로 수용하는 TRADE 토큰을 게시판 침해로 위조할 수 있어 ROADMAP 격리 원칙과 충돌하기 때문이다. 대안으로 게시판 전용 audience로 scope를 좁혀 코어가 거부하는 별도 토큰을 발급하는 방식도 허용한다. 어느 쪽이든 M2 토큰 계약이 이를 확정해야 한다(§7 미결).
- 서명 검증은 원격 의존이 없어 코어·M2로의 런타임 호출을 만들지 않는다. 검증 실패는 `401 jwt_verification`.
- 신원 취득: 검증 통과 토큰의 `sub`(회원 external_id UUID)을 작성자로 확정하고 글·댓글에 denormalize 저장한다.
- 표시명 동기화(계약 조건): `member_profile`(member_external_id, handle, status, updated_at)은 M2가 회원 생성·변경 아웃박스 이벤트를 발행한다는 전제에 선다. 현재 M2 설계(§2-3)의 가입 트랜잭션은 users·credentials·accounts·GENESIS만 단일 DB 트랜잭션으로 처리하고 아웃박스 이벤트를 발행하지 않아, 표시명 변경 전파 소스가 아직 정의돼 있지 않다. 이 계약 공백은 M2가 아웃박스 이벤트를 신설해 메우거나, 게시판이 다른 정의된 경로로 handle 갱신 소스를 대체해 해소한다(§7 미결). 어느 쪽이든 denormalize된 작성 시점 handle이 보장 렌더 경로이며, 프로젝션 부재·지연이 게시판 가용성을 낮추지 않는다.

### 2.5 장애 격벽·회복탄력성

- L7 LB에서 `community-api` 업스트림을 독립 라우팅한다(`/api/v1/community/**` 경로 기반, 별도 upstream). 게시판 다운·과부하 시 게시판 경로만 5xx를 반환하고 거래 경로(`/api/v1/**` 코어)는 무영향이다. LB readiness 프로브로 게시판 인스턴스만 제외한다.
- Resilience4j를 게시판 내부 경계에 적용한다: 게시판 DB 접근에 Bulkhead(동시 실행 상한)·TimeLimiter·CircuitBreaker, 쓰기 그룹에 RateLimiter. 게시판 DB 지연이 게시판 스레드를 무한 점유하지 못하게 격벽으로 차단한다.
- 프론트 격리: 게시판은 독립 DataSource(`CommunityDataSource`, §5)로 로드한다. 게시판 요청 실패는 에러 바운더리에 가둬 거래 화면 렌더·실시간 시세 바인딩에 영향을 주지 않는다.
- 관측성 분리: 게시판 전용 SLO·대시보드·트레이스 네임스페이스를 둔다. 게시판 지표와 코어 지표(ledger sum, journal append latency, matching loop time)를 같은 그래프 축에서 상관 없이 비교할 수 있게 태깅한다(§6 증명에 사용).

## 3. DB 추가

- 위치: `community-api` 독립 Flyway 라인의 다음 가용 버전(§2.3). 아래는 논리 스키마다. 정본은 실제 마이그레이션 SQL이 된다.
- 타입 규약: 식별자 BIGINT GENERATED ALWAYS AS IDENTITY PK + external_id UUID UNIQUE(코어 DB 설계의 orders·users 패턴 계승). 시각 TIMESTAMPTZ, UTC. 카운트 INTEGER. 게시판 테이블은 원장·저널과 어떤 FK·트리거로도 무관하다.

```sql
-- community 라인 init (버전 번호는 착수 시점 다음 가용 값)
CREATE TABLE member_profile (
    member_external_id UUID        PRIMARY KEY,           -- M2 users.external_id 논리 참조(물리 FK 없음)
    handle             VARCHAR(32) NOT NULL,
    status             VARCHAR(16) NOT NULL DEFAULT 'ACTIVE'
                       CHECK (status IN ('ACTIVE','SUSPENDED')),
    updated_at         TIMESTAMPTZ NOT NULL DEFAULT now()  -- M2 이벤트 upsert 기준
);

CREATE TABLE posts (
    id            BIGINT      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    external_id   UUID        NOT NULL DEFAULT gen_random_uuid() UNIQUE,
    market_symbol VARCHAR(24) NOT NULL,                   -- 코어 markets.symbol 값 참조(FK 아님, 격리)
    author_id     UUID        NOT NULL,                   -- member_external_id 논리 참조
    author_handle VARCHAR(32) NOT NULL,                   -- 작성 시점 표시명 denormalize
    title         VARCHAR(120) NOT NULL,
    body          VARCHAR(4000) NOT NULL,
    status        VARCHAR(16) NOT NULL DEFAULT 'VISIBLE'
                  CHECK (status IN ('VISIBLE','HIDDEN','DELETED')),
    like_count    INTEGER     NOT NULL DEFAULT 0 CHECK (like_count >= 0),
    comment_count INTEGER     NOT NULL DEFAULT 0 CHECK (comment_count >= 0),
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at    TIMESTAMPTZ
);
-- 목록(최신순): 보드별 가시글 커서 페이징
CREATE INDEX idx_posts_board_latest  ON posts (market_symbol, created_at DESC, id DESC)
    WHERE status = 'VISIBLE';
-- 내 글 조회
CREATE INDEX idx_posts_author        ON posts (author_id, created_at DESC);

CREATE TABLE comments (
    id                BIGINT      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    external_id       UUID        NOT NULL DEFAULT gen_random_uuid() UNIQUE,
    post_id           BIGINT      NOT NULL REFERENCES posts(id),   -- 커뮤니티 DB 내부 FK만 허용
    parent_comment_id BIGINT      REFERENCES comments(id),         -- 1뎁스 대댓글만(앱 가드로 깊이 제한)
    author_id         UUID        NOT NULL,
    author_handle     VARCHAR(32) NOT NULL,
    body              VARCHAR(1000) NOT NULL,
    status            VARCHAR(16) NOT NULL DEFAULT 'VISIBLE'
                      CHECK (status IN ('VISIBLE','HIDDEN','DELETED')),
    like_count        INTEGER     NOT NULL DEFAULT 0 CHECK (like_count >= 0),
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at        TIMESTAMPTZ
);
CREATE INDEX idx_comments_post ON comments (post_id, created_at, id) WHERE status <> 'DELETED';

CREATE TABLE post_likes (
    post_id    BIGINT      NOT NULL REFERENCES posts(id),
    member_id  UUID        NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (post_id, member_id)          -- 토글 멱등, 중복 좋아요 물리 차단
);
CREATE TABLE comment_likes (
    comment_id BIGINT      NOT NULL REFERENCES comments(id),
    member_id  UUID        NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (comment_id, member_id)
);

-- 인기순 페이징용 순위 스냅샷: 가변 like_count를 커서 축에서 분리(§1.2)
CREATE TABLE post_rank_snapshot (
    market_symbol VARCHAR(24) NOT NULL,
    post_id       BIGINT      NOT NULL REFERENCES posts(id),
    rank_score    INTEGER     NOT NULL,          -- 스냅샷 시점 집계 창 내 like_count
    generation    BIGINT      NOT NULL,          -- 스냅샷 세대. 커서에 인코딩해 시퀀스 내 고정
    snapshot_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (market_symbol, post_id)
);
-- 세대별 보드 인기순 커서 스캔
CREATE INDEX idx_rank_snapshot_board
    ON post_rank_snapshot (market_symbol, generation, rank_score DESC, post_id DESC);

CREATE TABLE reports (
    id          BIGINT      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    target_type VARCHAR(8)  NOT NULL CHECK (target_type IN ('POST','COMMENT')),
    target_id   BIGINT      NOT NULL,           -- posts.id 또는 comments.id (타입별 논리 참조)
    reporter_id UUID        NOT NULL,
    reason      VARCHAR(32) NOT NULL CHECK (reason IN ('SPAM','ABUSE','ILLEGAL','ETC')),
    detail      VARCHAR(500),
    status      VARCHAR(16) NOT NULL DEFAULT 'PENDING'
                CHECK (status IN ('PENDING','REVIEWED','ACTIONED','DISMISSED')),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (target_type, target_id, reporter_id)   -- 동일 대상 중복 신고 차단
);
CREATE INDEX idx_reports_pending ON reports (status, created_at) WHERE status = 'PENDING';
```

- 카운트 정합: like_count·comment_count는 좋아요·댓글 INSERT/soft-delete와 같은 커뮤니티 DB 트랜잭션에서 갱신하거나 트리거로 유지한다. 정합 검증은 커뮤니티 DB 내부 대조 쿼리로 상시 점검한다. 코어 원장 불변식과 완전히 분리된 도메인이다.
- 인기 순위 스냅샷: `post_rank_snapshot`은 커뮤니티 DB 내부 배치(또는 스케줄러)로 주기적으로 재산출한다. 새 세대를 `generation` 증가로 적재하고, 인기순 커서는 첫 페이지에서 고른 세대를 시퀀스 끝까지 유지한다. 산출·조회 모두 커뮤니티 DB 내부 연산이며 코어 자원과 무관하다.
- 파티셔닝: 글·댓글 볼륨이 커지면 `created_at` 기준 시간 파티션을 도입할 수 있으나 M3 범위에서는 단일 테이블 + 부분 인덱스로 충분하다. 도입 시에도 코어 파티션 자동화(V2 로드맵)와 무관한 커뮤니티 라인에서 진행한다.

## 4. API

- 경로 접두: `/api/v1/community/**`. LB가 이 접두를 배포 단위 D(`community-api`)로 라우팅한다(§2.5). 브라우저는 same-origin으로 접근하므로 CORS는 코어와 동일 화이트리스트(`https://demo.exchange.local`)를 재사용한다.
- 공통 규약 상속: 엔벌로프(§2-2), 에러 포맷·코드(§2-3), 커서 페이징(§2-6), rate limit 토큰버킷(§2-5). schema_version "1.0" 항상 포함.
- 인증: 읽기(GET 목록·단건·댓글)는 비로그인 허용이되 선택적으로 M2 Bearer를 받는다(optional-auth). 유효 토큰이 있으면 응답 각 항목에 서버 산출 `mine`(요청자=작성자 여부) 불리언을 additive로 싣는다. 토큰 부재·무효·만료는 조회를 막지 않고 `mine=false`로 강등한다(조회 가용성 보존). 작성자 식별자(`member_external_id`)는 공개 응답에 노출하지 않는다(세션 `sub` 재사용 값이라 최소 노출). 쓰기(POST/PATCH/DELETE)는 M2 Bearer 필수. 미인증 쓰기는 `401 jwt_verification`, 타인 리소스 수정·삭제는 `403 out_of_scope`(작성자 불일치).

### 4.1 엔드포인트

| 기능 | 메서드·경로 | 인증 | 비고 |
|---|---|---|---|
| 글 목록 | `GET /api/v1/community/boards/{market}/posts` | 선택 | `sort`(latest\|popular), `cursor`, `count`(≤50). 항목에 `mine` |
| 글 작성 | `POST /api/v1/community/boards/{market}/posts` | 필요 | `Idempotency-Key` 헤더 권장(재시도 중복 작성 차단) |
| 글 단건 | `GET /api/v1/community/posts/{externalId}` | 선택 | soft-deleted는 마스킹 본문 반환. 응답에 `mine` |
| 글 수정 | `PATCH /api/v1/community/posts/{externalId}` | 필요 | 작성자 본인만 |
| 글 삭제 | `DELETE /api/v1/community/posts/{externalId}` | 필요 | soft delete. 본인만 |
| 댓글 목록 | `GET /api/v1/community/posts/{externalId}/comments` | 선택 | `cursor`, `count`. 항목에 `mine` |
| 댓글 작성 | `POST /api/v1/community/posts/{externalId}/comments` | 필요 | `parent_comment_id` 선택(1뎁스) |
| 댓글 삭제 | `DELETE /api/v1/community/comments/{externalId}` | 필요 | soft delete. 본인만 |
| 글 좋아요 토글 | `POST` / `DELETE /api/v1/community/posts/{externalId}/like` | 필요 | PK 유니크로 멱등 |
| 댓글 좋아요 토글 | `POST` / `DELETE /api/v1/community/comments/{externalId}/like` | 필요 | 멱등 |
| 신고 | `POST /api/v1/community/reports` | 필요 | 대상·사유. 대상별 1인 1회 |

- 소유권 표시(`mine`): 공개 GET(글 목록·단건·댓글 목록)은 optional-auth다. 유효 회원 Bearer 동봉 시 응답 각 항목에 `mine`(불리언)을 additive로 싣는다. 서버가 토큰 `user_id`와 작성자 내부 id를 대조해 산출하며 요청자가 작성자면 true다. 토큰 부재·무효·만료는 조회를 막지 않고 `mine=false`로 강등한다. 작성자 식별자는 응답에 노출하지 않는다. 기존 필드·엔벌로프는 불변이다(§1.1 작성자 권위=member_external_id 정합).
- 신고 요청 본문은 `{ target_type, target_id, reason, detail? }`. `target_type`은 `POST`·`COMMENT`. `target_id`는 대상의 external_id(UUID)다. 서버가 external_id를 내부 `reports.target_id`(BIGINT)로 해석해 저장한다. 프론트는 내부 수치 id를 알지 못하므로 항상 external_id를 보낸다.
- 운영(숨김·삭제·신고 처리)은 관리 평면(API 설계 §3-6, 별도 호스트·mTLS)에서 수행한다. 관리 요청은 배포 단위 C(exchange-admin)가 받되 커뮤니티 서비스에 위임한다. 관리자 조작이 게시판 도메인 밖(원장·저널)에 닿지 않는다.

### 4.2 멱등·에러

- 글·댓글 작성은 `Idempotency-Key`(1~36자, `[A-Za-z0-9_-]`) 헤더로 재시도 중복을 차단한다. 코어 주문의 `client_order_id` 멱등(§2-4)과 같은 사상이되, 게시판은 금전 사고가 없으므로 필수가 아닌 권장이며 키 미제공 시에도 작성은 허용한다. 동일 키 재요청은 기존 리소스를 반환(`200`, `X-Idempotent-Replay: true`).
- 좋아요 토글은 PK 유니크로 자연 멱등(이미 좋아요면 `POST`가 `200`, 없으면 `DELETE`가 `200`).
- 에러 코드는 §2-3 재사용: `400 invalid_parameter`(제목·본문 길이 위반, 잘못된 sort), `401 jwt_verification`, `403 out_of_scope`(작성자 불일치), `404 (board/post/comment not_found)`, `409`(신고 중복 등), `429 too_many_requests`(+Retry-After).

### 4.3 rate limit·스팸 방지 (최소)

- rate limit은 §2-5 토큰버킷을 게시판 전용 버킷으로 추가한다. 예: 게시판 쓰기 = 회원 계정당 10 토큰/60초, 게시판 조회 = IP당 300 토큰/10초. 버킷 헤더 노출 규약 동일. 버킷은 코어 주문 버킷과 별개라 게시판 폭주가 주문 rate limit 예산을 갉아먹지 않는다.
- 스팸 최소 방어.
  - 작성 최소 간격: 동일 회원 연속 글 작성 최소 간격(예: 15초), 댓글 최소 간격(예: 5초).
  - 동일 본문 반복 차단: 최근 창(예: 5분) 내 동일 본문 재게시 스로틀.
  - 신규 회원 쿨다운: `member_profile.status`·가입 경과가 짧으면 쓰기 빈도 하향(M2 신원 소비).
  - 길이·형식 가드: 제목 ≤120자, 글 본문 ≤4000자, 댓글 ≤1000자. 링크 수 상한 등은 앱 가드로 추가.
  - 신고 임계 자동 숨김: 동일 대상 신고 수가 임계 초과 시 자동 `HIDDEN` 후 운영 검토 큐 적재. 하드 삭제는 하지 않는다.

## 5. 프론트 화면

- 정책: 고정형 데스크톱 전용, 최소 폭 1280px, 반응형 리플로우 없음(데스크톱 레이아웃 §4). tokens.css만 소비, 하드코딩 hex 금지. 방향색(Red 상승·Blue 하락) 규약은 게시판 본문에는 직접 쓰이지 않으나 종목 시세를 함께 노출할 때 준수한다.
- 진입·라우트: 거래 화면(`/exchange/[market]`)의 tradeGrid는 이미 무스크롤로 가득 차므로 토론을 그리드에 끼우지 않고 별도 라우트 `/community/[market]`로 둔다. 진입점은 SummaryBar의 종목명 인접 "토론" 링크. 딥링크·정적 export 대응으로 `generateStaticParams`로 전 마켓 사전 생성(레이아웃 §1.2 패턴 계승). 글 상세는 같은 마켓 라우트의 쿼리 파라미터 `/community/[market]?post={externalId}`로 연다. 별도 경로 세그먼트 `[postId]`는 정적 export에서 성립하지 않는다. 글 external_id가 런타임(작성 시) 생성 UUID라 `generateStaticParams`로 사전 열거할 수 없고, 미열거 경로는 export 산출물에 HTML이 없어 딥링크·클라이언트 내비가 404가 된다. 쿼리 파라미터는 마켓 라우트 단일 HTML 위에서 클라이언트가 상세를 로드하므로 열거 없이 딥링크가 성립한다. 마켓 축은 12종 유한이라 세그먼트 사전 생성을 유지한다.
- 레이아웃: 서브 화면 와이드 규격(레이아웃 §3) 적용. HeaderNav 아래 max-width 1200px 중앙 컨테이너, 좌우 패딩 24px, 페이지 배경 `--bg-muted`, 세로 스크롤 허용.
  - 목록: 좌측 본문(1fr) = 정렬 탭(SegmentedTab: 최신·인기) + 글 리스트(DataTable 또는 ListRow 변형: 제목·작성자 handle·좋아요·댓글수·시각) + 커서 페이징(더 보기). 우측 레일(약 320px) = 게시판 안내·인기 글·로그인 상태.
  - 글 상세: 제목·작성자·시각·본문 카드 + 좋아요 토글 + 댓글 목록·작성 폼. 카드는 `--surface-default`, `--radius-lg`, `--shadow-1`.
  - 글쓰기: 제목·본문 입력 + 등록 버튼(Button primary). 비로그인 시 읽기만, 작성 클릭 시 로그인 유도.
- 상태 설계(디자인 시스템 §각 화면 상태 규약 계승).
  - 로딩: Skeleton(listRow·card).
  - 빈: EmptyState "아직 글이 없어요. 첫 글을 남겨보세요"(해요체 마이크로카피).
  - 에러: 상단 ConnectionBanner(warning) + 재시도. 게시판 장애가 거래 화면을 깨지 않도록 게시판 라우트·위젯 단위 에러 바운더리로 격리.
- DataSource 격리(프론트): `web/lib`에 `CommunityDataSource`를 신설한다. 거래용 DataSource·zustand 스토어와 독립이며 게시판 요청 실패가 시세 스토어·WS 연결 상태에 영향을 주지 않는다(레이아웃 §5 DataSource·store 재사용 원칙의 격리 확장). HeaderNav·WS 연결 점 등 거래 프레임은 게시판과 무관하게 동작.
- 접근성: 대비 4.5:1, 탭 타깃 44px, reduced-motion 준수(디자인 시스템 §0·§5). 좋아요·삭제 등 액션은 아이콘+라벨 병기.

## 6. 완료 기준 (격리 증명)

M3 완료 판정은 기능 개수가 아니라 상시 게이트 유지다(ROADMAP §상시 게이트·§M3 완료 기준). 게시판에 부하·장애를 주입해도 거래 상시 게이트(자산별 원장 합 0, 주문 중복·유실 0, 리더 kill 후 RTO 30초 이내 자동 복구, CI green)에 영향 0임을 데이터로 증명한다. 아래 하네스 실험을 검증 설계(`docs/하네스_검증설계.md`)의 카오스 매트릭스에 추가 항목으로 제안한다.

| 실험 | 주입 | 관측·통과 조건 |
|---|---|---|
| B1 게시판 DB 장애 | `community-db`에 kill·네트워크 지연·패킷 손실(Toxiproxy) 주입 | 거래 상시 게이트 전 항목 유지. 매칭 루프 시간·저널 append latency·ledger sum 무편차. 게시판만 5xx |

## 7. 미결·후속

- 회원 토큰 검증 방식(정본 개정 선행): 본 설계는 비대칭 공개키 검증(§2.4)을 전제로 격리를 성립시킨다. M2 설계가 회원 액세스 토큰을 대칭(HS256)로 확정하면 게시판이 위조 가능한 대칭 비밀을 보유하게 돼 격리가 깨진다. M2 토큰 계약을 비대칭(RS256/EdDSA, 개인키는 M2 발급자 전용) 또는 게시판 전용 audience로 좁힌 별도 토큰으로 확정해야 한다. M2·M3 문서를 상호 정합시킨다.
- 회원 표시명 동기화 계약 공백(정본 개정 선행): `member_profile` 프로젝션은 M2 아웃박스 이벤트를 소비한다는 전제이나, 현재 M2 가입 트랜잭션(§2-3)은 아웃박스 이벤트를 발행하지 않는다. M2에 회원 생성·변경 아웃박스 이벤트를 신설하거나, 게시판 handle 갱신 소스를 다른 정의된 경로로 대체한다. 확정 전까지 denormalize된 작성 시점 handle이 보장 렌더 경로다.
- M2 회원 인증의 정확한 세션 토큰 계약(만료·갱신·scope)은 M2 설계가 확정한다. 본 설계는 Bearer 토큰 서명·exp·scope 검증 인터페이스만 소비하며, M2 확정 시 §2.4를 그 계약에 맞춘다.
- 인기순 정렬의 스냅샷 갱신 주기·집계 창(전체·기간)·rank_score 산식은 운영 파라미터로 두고 관리 평면에서 조정 가능하게 한다. 세대 교체 정책(보존 세대 수·GC)도 함께 확정한다.
- 마켓 목록 로컬 캐시의 갱신 주기·시드 경로는 시드 파이프라인 설계와 맞춘다(런타임 외부 의존 금지 원칙 유지).
- 신고 자동 숨김 임계값은 운영 파라미터로 두고 관리 평면에서 조정 가능하게 한다.

## 반영한 비평

- (medium, board) 인기순 커서 축을 가변 집계값 `like_count`에서 분리. `post_rank_snapshot`(세대 기반 불변 순위) 테이블·인덱스를 §3에 신설하고, §1.2 커서 축을 `(rank_score, post_id)`로 정정. 실시간 `like_count`는 표시용으로만 응답에 싣도록 명시. 오프셋 배격 근거와의 자기모순 제거.
- (medium, board) `member_profile` 프로젝션과 M2 아웃박스 이벤트 사이 계약 공백을 명시. §2.4를 "M2가 아웃박스를 발행한다는 전제(현재 미발행)"로 정정하고, denormalize handle을 보장 렌더 경로로 확정. §7 미결에 정본 개정 선행 항목으로 등재.
- (high, M2 → board §2.4 직접 관련) 회원 토큰 대칭키(HS256) 공유가 게시판 격리를 깨는 문제를 반영. §2.4 검증을 비대칭 공개키 전용으로 변경(개인키 미보유), 대칭키 공유 배격 근거를 §0·§2.4에 명시. 검증 실험 B7 추가, §7에 M2 토큰 계약 개정 선행 항목 등재.
- (low, 문서 서두) 영어 대화체 메타 서문 행 삭제, 제목·정본 의존부터 시작.
