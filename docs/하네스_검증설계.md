### 2-2. k6 시나리오 (외부 SLO 계측기 + CI 게이트)

- **버전/모듈**: k6 **v2.1.0** 공식 바이너리(확장 빌드 불요). WS는 stable `k6/websockets`(부재 시 `k6/experimental/websockets` 폴백, §0 사전 게이트) 위에 STOMP 1.2 프레임(`CONNECT`/`SUBSCRIBE`/`MESSAGE`/`\0`)을 순수 JS ~100줄로 구현. 서명은 `k6/crypto` HMAC-SHA256 + JCS(RFC 8785) canonical(API§3-3), 봇과 동일 규약. 전용 부하 계정 발급(계정 키 버킷 API§2-5 적용, IP 버킷 우회 아님), **발급 시 `(access_key → user_id)` 매핑을 `harness.loadtest_accounts`에 고정 적재**(§2-5, C16 조인 키의 원천).
- **서명 비용 절감(§2-4 캘리브레이션 연동)**: 주문 바디는 `client_order_id`·`price`·`volume`만 변하는 고정 템플릿이므로, 매 iteration 전체 JCS 라이브러리 호출 대신 **사전 정규화된 JCS 문자열 템플릿에 값만 치환**(키 정렬·이스케이프가 불변임을 이용)한 뒤 SHA512+HMAC만 수행한다. nonce/timestamp는 요청마다 신규(서명 자체는 생략 불가, API§3-4 nonce 계약).
- **부하 모델**: 주문·조회는 **open model**(`ramping-arrival-rate`, 응답 지연과 무관하게 도착률 유지, coordinated omission 회피), WS는 `constant-vus`.
- **429 처리(명문화)**: `setup()` 이전 init 단계에서 `http.setResponseCallback(http.expectedStatuses({min:200,max:399}, 429))` 선언, 429는 `http_req_failed`에 실패로 계상되지 않는다(k6 기본값은 429=실패이므로 이 선언이 없으면 가용성 지표가 오염됨). 429 표본의 지연 제외는 `http_req_duration` 필터가 아니라 **수용 응답 전용 커스텀 Trend `accepted_req_duration`**(2xx일 때만 add)으로 구현한다.
- **phase 태그(카오스 창 제외 규약)**: 실험 오케스트레이터가 k6와 카오스 주입을 **동일 타임라인 설정(환경변수)으로 구동**한다. `-e CHAOS_T0_S=<주입 시각(초)> -e CHAOS_T1_S=<주입시각+60s(RTO 30s의 2배 마진)>`. 스크립트는 경과 시간이 이 창 안이면 샘플에 `phase:chaos`, 밖이면 `phase:steady`를 태깅한다. 카오스 창 내 seq gap은 재동기화 성공(`ws_epoch_resync_fail==0`)으로만 판정하고, steady 창의 gap은 0이어야 한다. E3의 "gap 감지→재동기화 흡수" 정상 경로가 FAIL로 오판되지 않는다.
- **ACK 원장 적재**: 각 2xx 신규 접수 ACK를 `console.log('ACK|' + JSON.stringify({ak, coid, oid, t}))`로 stdout에 구조화 출력 → §2-5 파이프라인이 DB로 적재.
- **출력**: `-o experimental-prometheus-rw`(Prometheus remote write) → 기존 Grafana 합류(공식 대시보드 19665) + `K6_WEB_DASHBOARD_EXPORT`로 HTML 리포트 보존.

### 2-4. 용량 예산·캘리브레이션 (단일 PC 데모 전제, 신설)

단일 Windows PC에서 PG17(주문당 fsync)+Redis+Kafka+RabbitMQ(STOMP 릴레이)+api×2+admin+봇 140+관측 스택+Toxiproxy를 전부 구동하므로, **스파이크 목표치가 서버 백프레셔가 아니라 호스트/부하기 포화를 측정하는 오염**을 사전 배제해야 한다.

1. **캘리브레이션 단계(리허설 필수 절차)**: steady 300 OPS에서 30분 구동 후 판정, 호스트 전체 CPU<60%, k6 프로세스 자체 CPU<1코어, `http_req_duration`의 k6측 내부 지연 기여(`iteration_duration - http_req_duration` 중앙값)<5ms, PG fsync 대기(`pg_stat_wal`)·HikariCP pending 정상. **전부 충족 시에만 스파이크 배수 10x 확정**. 미충족이면 기저 OPS를 낮춰(예: 200) 그 10x를 스파이크 상한으로 재정의한다. 목표는 "**기저 대비 10배 폭주에서의 무결성·백프레셔 증명**"이지 절대값 3,000이 아니다(§2-3 표의 명목치는 이렇게 확정된 값으로 치환).
2. **부하기 격리**: 1순위, k6를 **별도 머신**(같은 LAN)에서 실행. 불가 시, k6에 전용 코어셋 고정(Windows `start /affinity`), 관측 스택은 스파이크 창 동안 Tempo 샘플링 1%·Loki 수집 레벨 WARN으로 축소(compose 프로파일 `--profile load-test`로 전환).
3. **서명 비용**: §2-2 JCS 템플릿 치환 방식 적용(측정상 서명 경로가 k6 CPU의 지배 항목이 되지 않아야 함, 캘리브레이션 항목에 포함).
4. 캘리브레이션 결과(기저 OPS·스파이크 상한·머신 배치)는 `harness.calibration_runs`에 기록하고 발표 자료의 실험 조건 각주로 사용한다.

### 2-5. 하네스 데이터 파이프라인·전용 테이블 (신설, DDL 소유 명시)

**소유/마이그레이션**: 하네스 전용 객체는 전부 **`harness` 스키마**에 두고, 별도 Flyway location(`db/harness`)의 `H1__harness_tables.sql`로 관리한다(앱 `V*` 체인과 분리, 계약 스키마 오염 0). `harness` 스키마는 ①②계층이 아니므로 `app_role`에 INSERT/SELECT/**TRUNCATE**를 GRANT한다(실험 리셋 허용).

    user_id         BIGINT      NOT NULL,

    order_id        BIGINT,
    acked_at        TIMESTAMPTZ NOT NULL,

);
CREATE TABLE harness.invariant_partition_sums ( -- C01 증분 검증용 마감 파티션 합 캐시 (§4-2)
    partition_name VARCHAR(64) NOT NULL,

## 4. 불변식 검증기 (SQL 상시 검증)

### 4-1. 체크 카탈로그 (DB§6 ①~⑫ 승격 + 보강 C13~C23)

전 SQL은 DB v2.5 실제 스키마 컬럼명 기준. **모두 0행(또는 명시 조건)이어야 정상.**

```sql
-- ══ C01 [CRITICAL] 자산 보존: 자산별 전 계정 원장 총합 = 0  (DB§6.1 ①)
SELECT asset_id, SUM(amount) AS net
FROM ledger_entries GROUP BY asset_id HAVING SUM(amount) <> 0;               -- 0행

-- ══ C02 [CRITICAL] balances 프로젝션 = 원장 재계산 (시스템·LOCKED·GENESIS 포함 전 계정, DB§6.1 ②)
SELECT b.account_id, b.balance, COALESCE(SUM(l.amount),0) AS ledger_sum
FROM balances b LEFT JOIN ledger_entries l ON l.account_id = b.account_id
GROUP BY b.account_id, b.balance
HAVING b.balance <> COALESCE(SUM(l.amount),0);                               -- 0행

-- ══ C03 [HIGH] 미봉인 잔존 거래 (DB§6.2 ③)
SELECT id FROM ledger_transactions
WHERE status='OPEN' AND created_at < now() - interval '1 min';               -- 0행

-- ══ C04 [CRITICAL] SEALED인데 불균형 (DB§6.2 ④)
SELECT l.transaction_id, l.asset_id, SUM(l.amount)
FROM ledger_entries l JOIN ledger_transactions t ON t.id = l.transaction_id AND t.status='SEALED'
GROUP BY l.transaction_id, l.asset_id HAVING SUM(l.amount) <> 0;             -- 0행

-- ══ C05/C06 [CRITICAL] 저널 gapless (유실 0 · RPO=0, DB§6.3 ⑤⑥, COALESCE는 v2.5 규정)
SELECT COALESCE((max(seq)-min(seq)+1) - count(*), 0)             AS gaps FROM command_journal;  -- 0
SELECT COALESCE((max(event_seq)-min(event_seq)+1) - count(*), 0) AS gaps FROM event_journal;    -- 0

-- ══ C07 [CRITICAL] 중복 주문 접수 0, 프로젝션 축 (DB§6.3 ⑦)
SELECT user_id, client_order_id, count(*) FROM orders
WHERE client_order_id IS NOT NULL GROUP BY 1,2 HAVING count(*) > 1;          -- 0행

-- ══ C07' [CRITICAL, 신규] 중복 주문 접수 0, 저널 축 (API§6-C ③-(i)·§7-1 v2.5의 판정 축과 동일)
--  command_journal은 PARTITION BY RANGE(seq)라 (user_id, client_order_id) 전역 UNIQUE 인덱스가
--  물리적으로 불가(파티션 키 미포함, 부록 A #8). 실보증은 §5.1 원자 트랜잭션의 uq_orders_client
--  전이 차단이며, 본 SQL이 그 성립을 저널 레벨에서 상시 실증한다(멱등 게이트웨이 우회 탐지).
--  CANCEL 커맨드가 동일 coid를 동반할 수 있으므로 command_type='NEW' 필터 필수.
SELECT user_id, client_order_id, count(*) FROM command_journal
WHERE command_type = 'NEW' AND client_order_id IS NOT NULL
GROUP BY 1,2 HAVING count(*) > 1;                                            -- 0행

-- ══ C08 [CRITICAL] 중복 체결 0 (DB§6.4 ⑧⑧' + API§6-C ③-(ii))
--  체결 seq는 trades의 컬럼 id다(trade_id = event_seq, DB§3.1). id가 파티션 키 포함 PK라
--  전역 유일 대조에 쓴다. trade_seq_registry.seq = trades.id.
SELECT id, count(*) FROM trades GROUP BY id HAVING count(*) > 1;             -- 0행
SELECT t.id FROM trades t LEFT JOIN trade_seq_registry r ON r.seq = t.id
WHERE r.seq IS NULL;                                                         -- 0행 (registry 1:1)

-- ══ C09 [HIGH] trades.id ⊆ event_journal(TRADE) (DB§6.4 ⑨)
SELECT t.id FROM trades t
LEFT JOIN event_journal e ON e.event_seq = t.id AND e.event_type='TRADE'
WHERE e.event_seq IS NULL;                                                   -- 0행

-- ══ C10 [HIGH] 체결 합 = filled_qty (수량기반, 90일 retention 하한, DB§6.4 ⑩)
SELECT o.id FROM orders o
LEFT JOIN trades t ON t.maker_order_id = o.id OR t.taker_order_id = o.id
WHERE o.quantity IS NOT NULL AND o.created_at >= now() - interval '90 days'
GROUP BY o.id, o.filled_qty

--  라이브 중 프로젝션 지연이 순간 교차처럼 보일 수 있어 상시 판정 금지, 권위 run(R5)·실험 사후

       max(price) FILTER (WHERE side='BUY')  AS best_bid,
       min(price) FILTER (WHERE side='SELL') AS best_ask
FROM orders
WHERE status IN ('OPEN','PARTIAL') AND price IS NOT NULL
GROUP BY market_id
HAVING max(price) FILTER (WHERE side='BUY')
       >= min(price) FILTER (WHERE side='SELL');                             -- 0행

-- ══ C20 [HIGH, 신규] orders 수수료 물질화 = trades 자기측 fee leg 합 (V10 프로젝션 드리프트)
--  paid_fee·trades_count는 trade INSERT와 동일 정산 트랜잭션의 누적 프로젝션. 자기측 fee는
--  maker면 maker_fee, taker면 taker_fee. 90일 윈도는 ③ 규약(주문 생성이 체결보다 앞선다).
SELECT o.id FROM orders o
LEFT JOIN (
    SELECT maker_order_id AS oid, maker_fee AS fee FROM trades
    WHERE created_at >= now() - interval '90 days'
    UNION ALL
    SELECT taker_order_id AS oid, taker_fee AS fee FROM trades
    WHERE created_at >= now() - interval '90 days'
) legs ON legs.oid = o.id
WHERE o.created_at >= now() - interval '90 days'
GROUP BY o.id, o.paid_fee, o.trades_count
HAVING o.paid_fee <> COALESCE(SUM(legs.fee), 0)
    OR o.trades_count <> COUNT(legs.oid);                                    -- 0행

-- ══ C21 [CRITICAL, 신규] 이벤트 방출 레지스트리 1:1 (DB§6.4 ⑮, P0-4)
--  event_journal ↔ event_emission_registry 양방향 anti-join. AFTER INSERT 트리거 실패·저널

--  event_journal.created_at(engine_ts 파생) 한쪽에만 걸고 존재 검사측은 무윈도라 경계 오탐 불가.
--  SQL 정본은 DB§6.4 ⑮. 90일 retention 지평(③).
-- ══ C22 [CRITICAL, 권위 run 한정] fencing_token 단조 (DB§6.4 ⑯)
--  command_journal의 fencing_token(= 리더 epoch 값)이 seq 순으로 비감소. 승격 epoch 역행 =
--  split-brain 흔적. 컬럼명은 실DDL 기준 command_journal.fencing_token(§5-1 T5와 정합).
--  append-only 저널이라 상시 판정은 권위 run에서만(C16·C19와 동류 스코프). SQL 정본 DB§6.4 ⑯.
-- ══ C23 [CRITICAL, 권위 run 한정] 채번 카운터 = 저널 최대 seq (DB§6.4 ⑰)
--  journal_counters.value가 command_journal·event_journal 실 최대 seq와 일치. 채번 UPDATE와

```

## 5. RTO/RPO 측정 방법

### 5-1. RTO · 타임스탬프 체인 (감지 → 승격 → 재생 → 체결 재개)

| 체인 | 타임스탬프 | 원천(기록 위치) |
|---|---|---|
| **T0** 주입 | kill 발행 시각 | `/admin/v1/chaos/kill-node` 응답 `killed_at` + `admin_audit_log` + Grafana annotation |
| **T1** 최종 심박 | 구 리더 마지막 heartbeat = **승격 트랜잭션이 선캡처한 구 `lease_until` − 10s**(리스 간격 역산, DB§5.4 heartbeat 주기) | 아래 **선캡처 승격 SQL**의 `old_lease_until`. 승격 UPDATE가 lease_until을 덮어쓰기 **전에** 같은 문장에서 원자 캡처해 `recovery_runs`/`/admin/v1/ha/recovery`에 적재. 보조: Prometheus가 `leader_lease.lease_until`을 상시 게이지(`exchange_leader_lease_until_seconds`) 스크레이프, 덮어쓰기와 무관한 시계열 이력 |
| **T2** 감지·승격 | 승격 UPDATE 커밋(epoch N→N+1) | 신 리더가 `RETURNING` 수신 직후 벽시계 기록 → `/admin/v1/ha/status` + `exchange_leader_epoch` 계단 |
| **T3** 재생 완료 | snapshot 로드 + tail replay + catch-up 종료 | `recovery_runs.created_at` + `duration_ms`, `exchange_journal_replay_commands_total` rate 종료점 |
| **T4** 트래픽 재개 | readiness UP → LB 재편입 | `/actuator/health/readiness` 전이 로그 + k6 관측(마지막 2xx ~ 최초 2xx 갭) |
| **T5** 체결 재개 | 페일오버 후 **최초 신규 TRADE** | **승격 시점 이벤트 워터마크 기준**: R0에서 `W_event = max(event_journal.event_seq)` 기록 → `SELECT min(created_at) FROM event_journal WHERE event_seq > :W_event AND event_type='TRADE'`. 검산(동치 판정): `SELECT min(e.created_at) FROM event_journal e JOIN command_journal c ON c.seq = e.source_cmd_seq WHERE e.event_type='TRADE' AND c.fencing_token = :new_epoch`. `fencing_token`은 **command_journal의 컬럼**이므로 반드시 조인 경유(event_journal에는 해당 컬럼 없음) |

**T1 선캡처 승격 SQL(명세, DB§5.4 승격문과 술어·효과 동일, 구값 캡처만 추가. 계약 문서 반영 권고=부록 A #10)**:

```sql
WITH old AS (
    SELECT lease_until AS old_lease_until
    FROM leader_lease WHERE resource = :r FOR UPDATE
)
UPDATE leader_lease l
   SET holder = :me, epoch = l.epoch + 1, lease_until = now() + interval '10 s'
  FROM old
 WHERE l.resource = :r AND l.lease_until < now()
RETURNING l.epoch AS my_epoch, old.old_lease_until;   -- 0행 = 유효한 타 리더 존재(DB§5.4와 동일 해석)
```

- **RTO 정의(권위)**: `RTO = T5 − T0` (체결 재개 기준, "체결 곡선 부활"과 일치). 내부 게이지 `exchange_failover_downtime_seconds = T2 − T1`과 **외부 관측치(k6 2xx 갭, 봇 텔레메트리)를 병기**해 3원 대조한다. 대시보드·`/admin/v1/ha/recovery`의 `rto_seconds`·k6 리포트가 같은 사건의 같은 수치를 가리키는 것이 발표 증명 포인트. 유휴 구간 kill(T1 과소평가 리스크)은 선캡처 `old_lease_until` 채택으로 원천 해소, `command_journal.created_at` 역산은 폐기.
- 합격: `RTO < 30s`(API§7-4). 세부 분해(감지 T2−T0 / 재생 T3−T2 / 재개 T5−T3)를 `recovery_runs`와 함께 리포트해 병목 귀속.
- **시계 동기 전제조건(페일오버 승격 실험, 조사 #58)**: T0(호스트 벽시계)·T5(chaos-pg `event_journal.created_at`) 뺄셈으로 정의한 RTO와, 만료 구동 승격(`lease_until < clock_timestamp()`)은 chaos-pg 시계와 호스트 시계의 동기를 전제한다. Docker Desktop VM 시계가 호스트 슬립 등으로 비단조 스큐를 내면 승격이 지연돼 승격 게이트(E5는 `epoch+1` 정확 승격, RTO는 증거로만)·RTO 게이트(E2·E4·E6·E7의 `RTO < 30s`)가 거짓 FAIL을 낸다(코드·HA는 정상). 페일오버 승격 게이트 실험(E4·E6·E5·E7·레거시 E2)은 주입 직전 `|host − chaos-pg clock_timestamp|`(ms)을 재 임계(`CHAOS_CLOCK_SKEW_TOLERANCE_MS`, 기본 2000) 초과 시 **주입 없이 verdict `SKIP`**(스큐값·임계 기록)으로 조기 종료(exit 0, FAIL 아님)한다. SKIP은 전제 미충족(E3 Redis 토폴로지 부재·E8 Chaos Monkey 미노출과 동일 어휘)으로 PASS/FAIL과 구분되는 비판정 상태이며 `failover_runs`에 적재하지 않는다. 재실행 전 WSL2/Docker Desktop 시계 재동기(`wsl --shutdown` 후 재기동)를 권고한다. 비페일오버 실험(E1 지연·E3 Redis·E8·E9)은 승격을 기대·측정하지 않아 대상 아님.

### 5-2. RPO · 정의와 판정

- **RPO=0 정의**: "클라이언트가 ACK(2xx) 받은 명령은 장애 후에도 전부 `command_journal`에 존재" (fsync 후 ACK 계약, DB§5.1 (a')).
- 판정: `rpo_records` = **C16 쿼리 결과 행 수**(harness.loadtest_acks LEFT JOIN command_journal 누락 건수) = **0**. 보조: C05 gaps=0(저널 자체 무결), C13(a)=0행(물질화 누락 0).
- 미ACK 명령(5xx/timeout)은 유실이 아니라 **미접수**로 분류, API§7-6 상태머신으로 봇/k6가 재조회(404=안전 재전송 / 200=재전송 금지)하며, 이 경로가 이중 접수를 만들지 않음은 C07·C07'·`dup_ack_order==0`이 증명.

### 5-3. 복구 리컨실리에이션 런북 R0~R7 (E4/E6 자동 절차)

R0 격리·승격(readiness=REFUSING_TRAFFIC, §5-1 선캡처 승격 SQL, `old_lease_until`·`W_event`·`max(command_journal.seq)` 워터마크 기록, RTO 타이머 시작) → R1 스냅샷 로드(`state_checksum` 불일치 시 이전 스냅샷 fallback) → R2 결정론 검증 재생(S_prev→S, **동일 seq끼리** fp 비교 → `recovery_runs` 적재, `matched=false`면 자동 절차 중단·수동 개입) → R3 tail 재생(전 마켓 통합·전역 seq 단일 패스, disposition은 event_journal에서 판독, DB§5.5 STEP2) → R4 이벤트 catch-up 재정산(`(source_cmd_seq, 방출 순번)` prefix 판정, W+1부터 연속 배정, `trade_seq_registry` 23505=멱등 스킵) → R5 전 불변식 권위 run(**C01~C14 + C18 + C19**, C19는 이 정지 시점이 유효 평가점) → R6 미발행 outbox 재발행(`published_at IS NULL`, 소비자 `processed_events` dedup) → R7 재개·리포트(`/admin/v1/ha/recovery`: rto_seconds, rpo_records, **invariants 6종 = §4-4 매핑 표로 산출**, old/new epoch, **verdict PASS = matched ∧ CRITICAL 0행 ∧ rpo=0 ∧ rto<30s**).

R5 불일치 분류: A(프로젝션 지연, R4가 해소) / B(프로젝션 오염, C02·C10·C14 잔존이나 C01·C04~C06 정상 → 섀도 재빌드 자동 허용) / C(원천 손상, C01·C04·C05·C06·C08 위반 → **서비스 재개 금지**, 수동 포렌식 + REVERSAL만).
