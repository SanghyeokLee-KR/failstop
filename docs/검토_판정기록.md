# 검토 판정 기록

문서 버전 v1.1. 대상 범위는 기준 커밋 30bdc27까지의 저장소 이력 312커밋이다.
HEAD는 움직이므로 아래 명령은 전부 30bdc27을 명시해 건다.
모든 주장에 커밋 해시, 파일 경로, 정본 절 번호 중 하나를 근거로 붙였다.

## 1. 배경

1인 프로젝트라 병합을 승인할 제3자가 없다. 4인 팀이라면 PR 리뷰 승인 이력이
남을 자리가 비어 있다. 그 자리를 `.claude/agents/reviewer.md`가 정의한 검토자
역할이 대신한다.

reviewer 하네스가 정한 것은 셋이다.

- 판정 등급: 통과 / 조건부 통과(수정 후 재검토 불요) / 반려(수정 후 재검토 필요).
- severity 기준: critical은 자산 정합·복구·보안이 깨짐, high는 계약 위반·구현
  차단·오해석 유발, medium은 실질 내부 불일치, low는 표기.
- 권한 경계: "파일을 고치지 않는다. 결함을 찾고, 근거를 대고, 수정 방향을 제시한다."
  수정 권한이 없으므로 판정과 구현이 같은 커밋에 섞이지 않는다.

루트 CLAUDE.md는 이것을 병합 조건으로 못박는다. "구현 역할이 만든 변경은
reviewer 판정(통과 또는 조건부 통과)을 받아야 병합한다."

이 문서가 증명하려는 것은 그 절차가 형식이 아니었다는 것이다. 근거는 검토가
잡아낸 결함과 그 교정 커밋이다.

## 2. 판정 통계

측정 기준 커밋 30bdc27(2026-08-30 21:20 +0900). 전체 커밋 수.

```
git rev-list --count 30bdc27
-> 312
```

유형별 분포.

```
git log --format="%s" 30bdc27 | sed -E 's/^([a-z]+)(\(.*\))?:.*/\1/' | sort | uniq -c | sort -rn
-> fix 148, feat 74, docs 44, test 18, chore 12, refactor 9, style 3, perf 2, merge 2
```

교정 커밋(fix) 비율은 148/312 = 47.4%다. 신규 기능(feat) 74건보다 교정이 두 배 많다.

본문에 실재하는 커밋 해시를 인용한 커밋 수.

```
git log --format="%H" 30bdc27 | while read h; do
  git log -1 --format="%b" $h | grep -oE '\b[0-9a-f]{7}\b' | sort -u | while read r; do
    git cat-file -e "$r^{commit}" 2>/dev/null && echo $h && break; done; done | sort -u | wc -l
-> 13
```

13은 자기 회귀 지목 건수가 아니다. 13건의 본문을 읽으면 인용 용도가 갈린다.
선행 커밋이 만든 결함을 그 해시로 지목한 것은 6건이다. 2b3ce40 -> dcaf1a6,
4933e30 -> eece91a, 4d09dff -> 6ec9f23, e038924 -> ae40c35, f8ff71f -> 992e59b,
4db2623 -> 65585d0.

나머지 7건은 다른 용도다. 전방 포인터(1cb16a5 "코드는 56ccd6a에서 선행"),
검증 결과 기록(6bd3b62 "서버 리스 전용 커넥션(커밋 992e59b) 적용 후 E1을 정본
200/100으로 재실행"), 병합 선행 조건(c8eb71b "선행 조건인 정본 등재(0ad368b ...)가
먼저 들어가"), 관련 표기(bfb6472 "관련 커밋 b82143f"), 정본 서술이 낡은 원인 표기
(facd1d3 "V13은 c8eb71b로 병합됐고"), 선행 커밋에 섞여 들어간 변경의 이력 정정
(9831f0d "f11f016에 섞여 들어갔다"), 그리고 1ecb8ee는 원인을 "직전 커밋"으로만 적고
본문 해시 f8ff71f는 판정 신설 시점을 가리킨다.

이 셈은 본문에 해시가 있는 커밋만 잡는다. 교정 커밋 본문에 해시가 없어 도입
커밋을 `git log -S`로만 특정한 사례는 빠진다. b34f1b4와 c9b0a15는 본문의 실재
커밋 해시가 0건이고, 그 도입 커밋은 3절 말미 명령으로 특정했다.

공허 통과를 명시한 커밋 수.

```
git log --grep="공허 통과" --format="%h %s" 30bdc27 | wc -l
-> 6 (fix 5, feat 1)
```

3절 표 18행의 severity 분포는 critical 8, high 10이다. 표에 실은 항목의 분포이지
저장소 전체 결함의 분포가 아니다. medium·low는 싣지 않았다.

## 4. 자기 회귀 사례

가장 값진 기록은 교정이 새 결함을 만들고 다음 검토가 다시 잡은 연쇄다.
이 문서가 싣는 것은 다섯 갈래다. 전수는 아니다. 이력에는 선행 커밋을 해시로
지목하지 않은 후속 교정도 있다(92e6758 "reviewer 조건부 통과가 남긴 후속 항목을
닫는다").

### 4-1. 좀비 리더 판정, 신설 뒤 5라운드

리스 하트비트를 전용 풀로 격리한 992e59b가 하트비트 생존성을 서비스 생존성에서
분리했다. 요청을 하나도 처리 못 하는 노드도 하트비트만은 성공해 스탠바이가
승격하지 않는다. f8ff71f 본문 축어: "라이브 실측에서 좀비 리더가 체결 0인 채
30분 이상 지속되고 재기동으로만 해소됐다."

그 뒤 판정 하나를 두고 다섯 번 고쳤다. f8ff71f는 신설이라 라운드에서 뺀다.

- 신설 f8ff71f: [요청 풀 전량 점유 AND 리더 쓰기 커밋 진행 0]으로 판정 신설.
- 1라운드 6ec9f23: 조회 부하만으로도 점유가 성립한다는 지적을 받아 쓰기 시도 축을
  더한 3축 논리곱으로 변경. 시도 축 계측기 `recordAttempt`를 이 커밋이 넣었다.
- 2라운드 1ecb8ee: 그 시도 축이 좀비에서 도달 불가능한 지점에 있었다. 계측을 인증
  앞으로 이동. 본문 축어: "좀비에서는 append에 진입조차 못 해 시도가 0으로 관측되고,
  매 표본 누적이 초기화돼 강등이 영원히 발동하지 않았다." 같은 커밋이 완료 축을
  "계정 조회·append 커밋·정산 커밋"으로 넓혔다(OrderGateway `requireActiveUser`).
- 3라운드 f05198e: 라이브에서 여전히 미발동. 필수 조건이던 풀 점유 자체가 장애와
  무관했다(cpu 463%). 조건을 제거하고 증상만 본다. 본문 축어: "인증 api_keys 왕복과
  인증 단계 확정 거절을 완료로 추가해" 완료 축을 한 번 더 넓혔다(ApiAuthService
  `findActive`, ApiAuthFilter catch).
- 4라운드 2a3ee53: 라이브 2차 미발동. 이진 조건을 누적 완료율 비율 신호로 교체.
- 5라운드 3bebb0a: 라이브 3차 미발동. 넓어진 완료 축이 원인. 읽기 완료 계상
  3곳(ApiAuthFilter catch, ApiAuthService findActive, OrderGateway
  requireActiveUser)을 제거해 커밋 축으로 축소.

2라운드와 3라운드가 나눠 넓힌 완료 축을 5라운드가 되돌린 것이 회귀의 본체다.
3bebb0a가 지운 세 지점의 귀속은 갈린다. `git show <커밋> | grep -E
'^(\+\+\+ b/.*\.java|\+.*recordCompletion)'`로 확인하면 OrderGateway는 1ecb8ee가,
ApiAuthService와 ApiAuthFilter는 f05198e가 넣었다. 두 라운드 모두 옳은 이유로
넓혔고(도메인 거절만 반복하는 노드의 오탐 방어), 5라운드는 그 넓힘이 신호를
눈멀게 한다는 실측을 근거로 좁혔다. 5라운드가 그 교환을 사각으로 문서에 명시했다.

2라운드부터 라운드마다 뮤테이션 확인을 붙인 것이 이 연쇄의 안전장치다. 1ecb8ee
본문: "계측을 인증 뒤로 되돌리면 이 테스트가 실패한다(뮤테이션 확인)." f05198e
본문: "풀 점유 조건을 되돌리면 이 테스트 5건이 깨진다." 2a3ee53 본문: "완료 1건이
누적을 초기화하는 규칙을 되돌리면 이 테스트 3건이 깨진다." 3bebb0a 본문: "읽기
완료 계상을 되살리면 이 테스트가 깨진다." 1라운드 6ec9f23 본문에는 같은 문장이
없다(`git log -1 --format=%b 6ec9f23 | grep -E "되돌리면|뮤테이션"` 0행).

### 4-2. readiness 정정기, 같은 커밋에서 갈라진 두 번째 회귀

6ec9f23은 4-1의 1라운드이면서 동시에 readiness 오보를 고친 커밋이다. 그 교정이
도입한 정정기가 종료 경로에서 새 오보를 만들었고 4d09dff가 잡았다.

주목할 점은 4d09dff가 원천을 코드가 아니라 문서로 지목한 것이다. 본문 축어:
"정본은 v2.19 서술이 대칭이라 코드가 아니라 문서가 이 결함의 원천이었다.
DB 설계 §5.4에 비대칭 계약을 명문화하고 v2.27로 순증한다." CLAUDE.md의
"문서가 틀렸으면 문서를 먼저 고친다"가 실제로 적용된 사례다.

### 4-3. 게이팅 제외 목록

3644dbc는 실행 전 판정 경로 감사에서 위양성 6건을 교정한 커밋이다. 그중 하나가
게이팅 제외 목록을 서버 카탈로그와 1:1로 맞춘 것이다. 3644dbc 본문 축어:
"서버의 AUTHORITATIVE_ONLY는 다섯인데 스크립트는 셋만 제외해 C22·C23이 부하 중에
게이팅됐다."

b34f1b4가 그 1:1 정렬 자체를 결함으로 판정했다. 두 목록은 축이 다르다. 서버
스코프는 평가 시점을 정하고 스크립트 목록은 게이팅 사용 여부를 정한다.
b34f1b4는 제외 목록을 3건으로 줄이면서 면제 사유를 체크별로 분리 기술하고
정본 §4-2 ④·§4-3 각주를 주석에 병기했다. 같은 실수가 다시 나오지 않게 하는 것은
목록 값이 아니라 사유의 개별화다.

### 4-4. 웹 epoch 기준점

코드에서 실패함을 확인했다."

### 4-5. 승격 재생 강등 등급

dcaf1a6(2026-07-29 "fix: 승격 재생 실패를 회복 가능 강등으로 분리")이 강등을
종신·회복 가능 두 등급으로 갈랐다. 그 커밋이 닫은 것은 정확성 결함이 아니라 등급
판정 결함이다. 본문 축어: "무결성은 유지됐으므로 결함은 정확성이 아니라 강등 등급
판정에 있었다."

그 교정에 reviewer가 조건부 통과를 냈고, 남은 항목을 2b3ce40("fix: 승격 재생 강등
등급의 정합성 결함 5건 교정")이 닫았다. 본문 첫 줄 축어: "reviewer 조건부
통과(dcaf1a6)가 남긴 항목."

닫은 항목 중 둘이 등급 축 자체의 역전이다. 재시도 예산 기준이 승격 진입에 걸려
있어 시도 1회가 5초를 넘기면 재시도가 0회가 됐다. 본문 축어: "재승격 비용이 가장
큰 상황에서 정확히 재시도가 사라지는 역전이다." 승격 재생 표식도 시도별이 아니라서
"낡은 해제가 새 시도의 표식을 지우면 그 시도의 재생 실패가 종신으로 잘못 내려간다." 이 갈래를 만든 판정은 반려가 아니라 조건부 통과다. CLAUDE.md 역할 체계절이
조건부 통과를 병합 가능 판정으로 두므로, 남은 항목을 닫는 커밋이 뒤따라야 한다.

## 5. 검증 장치 자체의 결함

가장 위험한 결함은 기능이 아니라 판정에 있었다. 판정 대상이 없는데 통과가 나오는
계열이다. 3절 6·8·16·17번과 4-3이 전부 여기 속한다.

공통 구조는 하나다. 무결성 체크가 전부 count 기반이라 "위반 0건"이 두 가지를
동시에 뜻한다. 위반이 없거나, 셀 대상이 없거나. 923ee6d 본문 축어: "종전 게이트는
[stale 0 + epoch 상승 + 무결성 0] 뿐이라 아무 일도 일어나지 않으면 전부 참이 됐다."

교정 방향은 세 갈래로 수렴했다.

- 활동 존재를 게이트에 넣는다. 28e63e7이 다섯 실험에 BASE_OPS=40을 배선하고 체결
  게이트를 누적 비교에서 워밍업 이후 증분 비교로 바꿨다. 누적 비교는 앞 실험이
  남긴 체결만으로 즉시 참이 된다.
- 관측 실패를 통과 신호로 바꾸지 않는다. e9d7cfe가 Get-Scalar에 -Required를 넣어
  집계·count 축은 빈 결과를 throw하게 했다. `[long]$null`이 0이 되므로 캐스팅 전
  null 검사를 뒀다.
- 판정 불능을 판정한다. 6b02b9c가 Test-ExperimentIntegrity에 공허·형상 가드를
  넣어 체크 0건이거나 checkName이 비면 판정 불능으로 떨어뜨린다.

6b02b9c는 이 절의 성격을 잘 보여준다. 인라인 사본을 걷어내자 그 사본이 우연히
제공하던 공허 통과 차단이 함께 사라졌다. 본문 축어: "빈 응답에 Measure-Object가
`$null`을 내던 우연한 공허 통과 차단이 사라져, Test-ExperimentIntegrity에
공허·형상 가드를 넣었다." 우연히 성립하던 안전성은 안전성이 아니다.

"실험 FAIL은 판정 경로부터 의심한다"는 원칙은 3644dbc에서 나왔다. 본문 축어:
"라이브 실행 전 판정 경로를 감사해 찾은 결함이다. 전부 시스템이 정상인데 실험이
FAIL로 보이거나 클러스터를 망가뜨리는 경로다." 6b02b9c가 같은 문장을 반대편에서
확인한다. "C15는 가용성 전조이지 무결성 위반이 아니므로 그 FAIL은 판정 결함이다."

원칙에는 대칭이 있다. FAIL이 판정 결함일 수 있다면 PASS도 그렇다. 923ee6d,
5826471, 28e63e7이 후자를 다룬 커밋이다.

4번(outbox 파티션)은 시간축 변형이다. 결함이 달력 구동이라 그 달이 오기 전까지
전 테스트가 green이었다. e5c6471이 PartitionCoverageIntegrationTest를 신설하며
선행 커버리지 단언을 현 지평 6개월 전에 의도적으로 깨지게 설계한 것이 대응이다.
green이 검증의 부재를 뜻할 수 있다는 것을 테스트 자체에 새겼다.

## 6. 한계

판정자와 구현자는 분리돼 있지만 둘 다 사람이 아니다. 같은 모델이 두 역할을 맡으면
같은 사각을 공유할 수 있다. 그래서 판정의 하한을 사람이 아닌 자동 게이트에 둔다.

하한을 이루는 것은 셋이다. CLAUDE.md 빌드 검증절의 `gradle build`와
`npm run build`, 스타일 게이트(`scripts/check-style.ps1`과
`.github/workflows/style.yml`), 그리고 불변식 검증(C01~C25)이다. 이 셋이 통과하지
않으면 판정 결과와 무관하게 병합하지 않는다.

하한에는 두 가지 한계가 이미 실측으로 드러났다.

- 게이트가 있어도 돌지 않으면 없는 것과 같다. dfef6d7(3절 18번)이 그 사례다.
  ci-backend가 6커밋 연속 실패한 것을 아무도 보지 않았다. 이 커밋은 실행 비트만
  세운 것이 아니라 "로컬 통과를 CI 통과로 읽지 않고 푸시 후 결론을 확인하는
  절차가 필요하다"를 검증설계 남은 과제에 등재했다.
- 게이트는 시점 종속이다. e5c6471(3절 4번)이 그 사례다. 클린 HEAD에서 어제까지
  green이던 테스트가 달이 바뀌자 실패했다.

게이트가 잡지 못하는 층은 다음과 같다.

- 계약 해석의 충돌. 3절 1번은 API 정본과 DB 정본이 각각 자기 안에서는 정합한데
  겹치는 구간에서 어긋난 사례다. 두 문서를 함께 읽어야만 보인다.
- 판정 자체의 공허. 5절 전체가 여기다. 통과하는 게이트를 늘려도 그 게이트가 무엇을
  재고 있는지는 게이트가 판정하지 못한다.
- 라이브 거동. 3절 9~12번은 전부 단위·통합 테스트가 green인 상태에서 라이브
  카오스 실행으로만 드러났다. 네 번 연속으로 그랬다.

이 세 층은 여전히 읽는 사람이 필요하다. 이 문서는 그 층에서 나온 판정 18건의
기록이고, 자동 게이트가 대신할 수 있는 부분과 그렇지 않은 부분의 경계선이다.
