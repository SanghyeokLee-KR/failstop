## 1. 카오스 매트릭스 전체 E1~E10 실행 계획

공통 프로토콜(전 실험): ⓐ 사전 권위 run(`POST /harness/v1/invariants/run`, run_id=B) 전 체크 green + 워터마크(`max(command_journal.seq)`, `max(event_journal.event_seq)`) 기록 + `TRUNCATE harness.loadtest_acks` → ⓑ 주입(창 (t0,t1) 설정 파일 기록, Grafana annotation) → ⓒ 무개입 관찰 → ⓓ 사후 권위 run(run_id=A) + `recovery_runs.matched` + RTO 측정 → ⓔ PASS 판정.

판정 원천은 전부 기계다. 페일오버 계열(E2·E4·E5·E6·E7)은 `harness.failover_runs.verdict='PASS'`, 비페일오버 계열(E1·E3·E8·E9·E10)은 사후 권위 run의 CRITICAL 체크 0행 + 실험별 지표.

심각도 카탈로그 권위(충돌 정정): CRITICAL/HIGH/WARN 분류의 정본은 `하네스_검증설계.md` §4-3(위반 시 처리 표)이며, 실제 구현은 `server/app/src/main/java/kr/exchange/harness/InvariantCheck.java`의 `Severity`·`Scope` 열거가 정본을 실체화한다. 구현된 카탈로그 기준.
- CRITICAL·SCHEDULED(상시·soak 대상): C01·C02·C05·C06·C07·C07P·C08·C13B·C17·C18·C21·C27·C28.
- CRITICAL·AUTHORITATIVE_ONLY(실험 사후 권위 run 한정, 상시·soak 제외): C13A·C16·C22·C23. C13A는 append와 정산 물질화 사이의 비동기 창을 상시 스케줄이 오탐하므로 큐 드레인된 권위 run 한정이다(복구 RTO 설계 §3-c).
- HIGH: C03·C09~C12·C14·C20(SCHEDULED)·C19(AUTHORITATIVE_ONLY). WARN: C15(SCHEDULED, 파티션 가용성)·C24·C25(AUTHORITATIVE_ONLY).
- 검증설계 §4-3이 CRITICAL로 열거하는 C04는 enum에 없다. DB 지연 제약 트리거가 강제하므로 러너가 평가하지 않는다.
- `하네스_CICD_IaC.md` §5-6 알람 라우팅은 `InvariantViolation` 템플릿이 위반 체크의 enum 등급을 severity 라벨로 옮긴다(`harness/prometheus/rules/exchange-alerts.yml`). 체크 목록을 따로 열거하지 않으므로 이 카탈로그와 갈라질 자리가 없다. 본 M4의 CRITICAL 게이트는 §4-3·구현 enum을 따른다.

## 2. Soak 2시간 이상 장기 검증

목적: 파티션 성장·메모리 누수·워터마크 검증기 장기 안정성을 데이터로 확인. 야간 CI 또는 발표 전 리허설 세션에서 무개입 2h+ 구동.

### 2-1. 구동

- [ ] 프로파일: normal 구성(MM/TAKER/TREND/NOISE 140봇), 전역 OPS는 `하네스_검증설계.md` §2-1 normal 행이 정본(2026-08-29 확정 10 OPS), 무주입 2h 이상. soak는 폭주가 아니라 장기 안정성 실험이라 기저를 그대로 쓴다. 노드 주문 커맨드 천장이 약 40~42/s(§2-4)라 그 위 값은 2h 내내 429만 쌓는다.
- [ ] 부하 원천: k6 `constant-arrival-rate` steady + 봇 플릿. 스파이크·카오스 없음.
- [ ] 관측: Prometheus 2h retention 이상, Grafana 시간창 2h로 확장한 별도 soak 뷰.
- [ ] 실행 스크립트 `harness/scripts/soak.ps1`: 타임라인·시드·환경변수 파일 기록(재현), 시작·종료 워터마크 캡처.

### 2-2. 판정(장기 불변)

- [ ] 무결성: soak 전 구간 `invariant_checks`에서 CRITICAL·SCHEDULED 체크(1절 심각도 카탈로그: C01·C02·C05·C06·C07·C07P·C08·C13B·C17·C18·C21·C27·C28) `ok=false` 0행. C13A·C16·C22·C23은 AUTHORITATIVE_ONLY라 상시·soak 대상 아님, HIGH·WARN은 별도 추적(0행 게이트 대상 아님).
      SQL은 check_name 필터로 CRITICAL 한정(HIGH/WARN 위반이 soak를 오탈락시키지 않게):
      ```sql
      SELECT check_name, count(*)
        FROM invariant_checks
       WHERE ok = false
         AND checked_at >= :soak_start
         AND check_name IN ('C01_ASSET_CONSERVATION','C02_BAL_VS_LEDGER','C05_CMD_GAPLESS',
                            'C06_EVT_GAPLESS','C07_DUP_ORDER','C07P_DUP_ORDER_JOURNAL',
                            'C08_DUP_FILL','C13B_ORDER_JOURNALED',
                            'C17_REPLAY_DETERMINISM','C18_FILL_PRICE_MAKER',
                            'C21_EVENT_EMISSION_REGISTRY','C27_CMD_DEFAULT_PARTITION',
                            'C28_CMD_LEGACY_AFTER_CUTOVER')
       GROUP BY 1;   -- = 0행
      ```
- [ ] 파티션 성장: command_journal(seq range)·event_journal(event_seq range)·trades(월 range) 파티션이 사전생성(premake) 일정대로 증가. DEFAULT 파티션 유입 0.
      `SELECT * FROM check_default_partitions();`(C15/C90) 유입 행 0. 위반 시 `CALL partman.run_maintenance_proc()` 자동 실행 확인.
- [ ] 워터마크 검증기: 1분 증분 스캔이 2h 내내 지연 없이 완주. 스캔 소요 상승 추세 없음(마감 파티션 합 캐시 `harness.invariant_partition_sums` 적재로 전량 SUM 회피).
- [ ] 메모리: `jvm_memory_used_bytes{area="heap"}` GC 후 저점(baseline)이 2h에 걸쳐 상승 추세 없음(누수 0). 오더북 depth·시퀀서 큐 유계.
      판정: 선형 회귀 기울기 근사 0(발표 자료에 heap baseline 시계열 첨부). OOM 킬 0.
- [ ] 백프레셔: `exchange_sequencer_queue_size` 안정, `hikaricp_connections_pending` 정상.
- [ ] 저널·재생 비용(스냅샷 도입 전 리스크 계량): soak 종료 시점 `max(command_journal.seq) - min(...)` 규모에서 승격 재생 소요를 1회 측정(E4를 soak 말미에 붙여 RTO 관측). 스냅샷 도입 후 재측정해 RTO 저널 크기 탈동조 실증(3-3과 연계).

### 2-3. 산출물

- [ ] soak 리포트: 시작·종료 워터마크, 파티션 수 추이, heap baseline 시계열, 스캔 소요 추이, CRITICAL 위반 0 확인. `harness.calibration_runs.details` JSONB에 요약 적재.

- [x] 결과(기저 OPS·스파이크 상한·머신 배치)를 `harness.calibration_runs`(base_ops·spike_cap·k6_host·details)에 적재, 발표 실험 조건 각주로 사용.

### 3-2. SLO 합격 기준의 관측 원천 매핑

합격 값은 `하네스_검증설계.md` §2-3 표(부하 지표)와 §5(RTO)가 정본이다. 이 문서는 값을 옮겨 적지 않고 지표를 M4 관측 원천에 매핑만 한다. 종전에는 값을 복제해 뒀다가 §2-3이 실측으로 치환된 뒤에도 옛 명목치가 남아 두 문서가 갈렸다(체결 처리량 ≥150·≥300 trades/s 대 §2-3 확정 ≥5 trades/s).

| 지표(§2-3·§5) | 판정 원천 |
|---|---|
| 주문 API p95/p99 | k6 `accepted_req_duration`(수용 요청 HTTP 왕복). §2-3 각주가 판정 축 정본 |
| 체결 전파 지연(SLO 판정 밖, 관측 보조) | `exchange:order_latency:p95_1m`/`p99_1m`. 접수에서 체결확정 발행까지라 주문 API 지연이 아니다 |
| 체결 처리량 | `exchange:trades_per_second:rate1m` |
| 2xx 가용성 | k6 `http_req_failed` + expectedStatuses |
| 429 비율·`Retry-After` | `exchange_orders_rejected_total{reason="rate_limited"}` |
| RTO | `harness.failover_runs.rto_seconds` |
| 무결성 | `invariant_checks` |

### 3-3. 병목 후보와 개선 방향

**(a) WS 게시 팬아웃**
- [ ] 증상 계량: 체결/초 대비 STOMP 게시 건수, `exchange_ws_clients` 채널별, 게시 지연. 스파이크 창에서 팬아웃이 매칭 스레드를 블록하는지 확인.
- [ ] 개선: 오더북 depth 갱신을 코얼레싱(N ms 창 내 최신 1건만 게시), 체결 스트림과 depth 스트림 분리, 게시를 매칭 코어 밖 프로젝션 스레드로 격리(코어 순수성 유지, `하네스_CICD_IaC.md` §5-2 계측 위치 규율).
- [ ] 판정: 스파이크 중 수용 p99<500ms 방어(k6 `accepted_req_duration`), WS `ws_seq_gap{phase:steady,dest:orderbook}==0`, `ws_stale_discarded{dest:orderbook}<200`·`{dest:trade}<10`, 양성 증거 `ws_seq_observed{dest:orderbook,stream:realtime}>100`·`{dest:trade}>10`.

**(b) candles 스캔**
- [ ] 증상 계량: 차트 조회(`GET /candles`)가 trades를 재스캔하는지, candles 테이블 조회 지연. PK=(market_id, interval, bucket).
- [ ] 개선: 체결 시 candles 증분 upsert(버킷 O·H·L·C·volume·trade_count 갱신, trades 재스캔 제거). 조회는 candles PK 프리픽스 스캔만. 장기 리텐션은 오래된 저해상도 버킷 아카이브.
- [ ] 판정: candles 조회 p99가 부하·데이터 성장과 무관하게 상한 내(회귀 없음). 증분 upsert가 정산 핫패스를 블록하지 않음(별도 소비자).

**(c) 정산 핫패스**
- [ ] 증상 계량: `post_ledger_transaction`의 seal 커밋 지연(`exchange_journal_append_seconds`), idx_ledger_txn 파티션 프로브 비용(파티션 수 증가 시).
- [ ] 개선: DB §5 P1 주석의 현재 파티션 fast-path 유지. 파티션 수가 수백 규모로 커져 프로브 비용이 관측되면 idx_ledger_txn을 created_at 포함 복합으로 조정. **T6-G**(수년치 파티션 상태 seal 지연 회귀)로 임계·측정치를 `harness.calibration_runs`에 기록.
- [ ] 판정: 파티션 수 증가에 따른 seal 경로 성능 회귀 없음(T6-G green).

**(d) 승격 재생(RTO 병목)**
- [ ] 증상: 저널 전량 재생이 RTO에 선형 반영(0-2 한계 2). soak 말미 E4 RTO로 계량(2-2).
- [ ] 개선: 스냅샷 도입(주기 `state_checksum` 스냅샷 + 스냅샷 이후 tail만 재생). 승격 절차 R1(스냅샷 로드)→R3(tail 재생)로 재생량 최소화.
- [ ] 판정: 스냅샷 도입 전후 RTO 비교, 저널 크기 증가에도 RTO<30s 유지(탈동조 실증). `recovery_runs.duration_ms`·`replayed_from_seq/to_seq`로 재생 구간 축소 확인.

### 6-3. 발표 자료 구성

- [ ] 1장: 증명 명제 3개(체결 무결·자동 복구·병목 이동과 안정화)를 반증 가능 형태로. 판정=SQL 0행/메트릭 임계/exit code. 명제 표 정본은 `제출_20260901/기획안_원본.md` 1.3이다.

- [ ] 3장: E1~E10 매트릭스 결과 표(각 verdict·RTO·위반 0). 미실시 실험은 미실시로 적는다(현재 E10).

- [ ] 5장: 성능 캘리브레이션 근거(단일 PC 전제·기저 대비 10x·`calibration_runs` 각주).

- [ ] 7장: 대시보드 ①② 캡처("총자산 선 수평, 체결 곡선 수초 부활").

- [ ] 한 줄 결론: 판정 전부가 사람의 주장이 아니라 SQL 0행과 exit code.

## 7. 릴리스와 태깅

절단 순서를 미리 정한다(`ROADMAP.md` M4). 밀리면 E8 앱 assault, E1 프록시 지연 재실행, E9 재실행 순으로 뺀다.
셋 다 애플리케이션 계층이라 시스템 엔지니어 관점의 증거 기여가 낮다. E10은 자르지 않는다.
E4는 로컬 스택 1회차 실측이라 클라우드에서 한 번 더 돌린다. 자르는 대상이 아니라 재현 대상이다.

### 7-1. 사전 게이트

- [ ] CI green: ci-backend(빌드·ArchUnit), integration(V3 T1~T6 전건), nightly-slo(k6 thresholds·exit 0), style.yml.
- [ ] 로컬 스타일 게이트: `scripts/check-style.ps1` 통과(본 문서 포함).
- [ ] E1~E10 최소 1회 실측 PASS 기록(`harness.failover_runs`·`invariant_checks` 잔존). E10은 현재 미실시라 이 게이트의 미결 항목이다.
- [ ] soak 2h 1회 통과 리포트.
- [ ] 빈 환경 콜드 스타트 1회 완주(5절).

위 다섯은 로컬 검증면 게이트다. M4 완료 판정은 이것으로 닫히지 않는다. 완료 기준은 `제출_20260901/기획안_원본.md` 12절이 정본이며 여덟 행이 전부 참이어야 한다. 비용 상한값(B1)은 12절에서 읽고 여기에 복제하지 않는다. 아래 A2·A3·A4·B2의 값은 12절 발췌이고, 어긋나면 12절이 정본이다.

- [ ] A1 외부에서 도메인으로 접속되는 상태 성립(클라우드 배포·도메인·TLS).
- [ ] A2 불변식 위반 행 0. 세는 단위는 SQL 판정 블록이고 총수는 C27·C28을 포함해 29개다(`harness/sql/invariants.sql`의 `== Cxx` 블록, 세는 방법은 `하네스_CICD_IaC.md` §6-3).

- [ ] A4 세대 번호가 정확히 1 증가하고 구 리더 쓰기 0행.
- [ ] A5 실험 판정 파일이 저장소 경로로 산출.
- [ ] B1 2026년 9월·10월 달력 월 실청구가 각각 정본 12절 상한 이하(계획값은 정본 9.3).
