# 2026-09-28 VM 실습망 투명 방화벽 전환

작업 PC(DEV-PC, Windows, VirtualBox 7.2.8)에서 VM 실습망의 방화벽을 연구소장님 숙제대로 투명 방식으로 바꾼 기록이다. 시간대는 KST이고, 마지막 캡처는 2026-09-29 새벽이다. 기존 경계 방화벽 pfsense-fw(NAT·라우터)를 복제해 브리지 방화벽 pfsense-tp를 만들고, 서버 여섯 대의 주소·경로·DNS를 바꾸지 않은 채 구역(DMZ·APP·DATA·OPS)을 나눴다. 그 위에 L2 포트 보안, 구역 간 L3·L4 규칙, L7 입구(HAProxy, 웹 진입 서버 인증서로 TLS를 풀고 다시 암호화)와 IDS(Suricata)를 붙이고, 두 방화벽의 기록을 관제 서버(OPS01)로 모았다. 이 기록은 로컬 VM 실습 결과이며 학교·개인 AWS의 검증 결과가 아니다.

관리자 비밀번호와 웹 진입 서버 개인 키는 사용자가 직접 입력했고 캡처하지 않았다. Teams 웹훅 주소는 기록하지 않는다. 기존 라우터의 별칭 화면(웹훅 호스트가 보임)은 캡처하지 않았다.

## 관찰

- 투명 방화벽은 서버 쪽에서 보이지 않는다. 서버 여섯 대의 주소·경로·DNS를 한 줄도 바꾸지 않았고(12·36), 경로 추적에도 나타나지 않는다(43). 09-26 경계형 전환 때는 여섯 대의 경로·DNS와 sshd·Nginx·인증서·앱 허용 주소를 모두 바꿔야 했다(증거본 2026-09-26_VM_pfSense 16·18).
- 브리지는 학습한 MAC을 포트에 고정(sticky)하므로, 서버를 다른 포트로 옮기면 옛 항목이 남아 통신이 끊긴다(27, 약 70초). 옮긴 뒤에는 `ifconfig bridge0 flushall`을 작업 순서에 넣는다.
- 이 버전(FreeBSD 14)에서 `ifconfig bridge0 static`은 항목을 VLAN 1로 넣어 태그 없는 프레임과 맞지 않는다(32). 포트 보안은 sticky와 ifmaxaddr로만 건다.
- 투명 방화벽이 멈추거나 끊기는 동안(구역 이동 약 70초, static 시도 약 50초, 재부팅 약 82초) 앱 → DB가 끊겨 매칭 리더가 넘어갔다. 설계대로 리더를 잃은 앱 서버는 스스로 재승격하지 않고, 재기동하면 대기 노드로 돌아왔다. 투명 방화벽 한 대는 단일 장애 지점이다.
- L7 검사는 입구 요청만 본다. 웹 진입 서버 → 앱 8080은 원래 HTTP 구간이라 평문이 선로에 있고(51), 이 구간을 Suricata가 경보 모드로 본다. 스크립트 삽입은 일부러 입구에서 막지 않고 IDS 탐지를 보이는 데 썼다.
- pfsense-tp의 시계가 처음에 9시간 앞서 있었다(RTC를 현지 시각으로 읽음). 시각을 맞추고 재부팅 때 `--rtc-use-utc on`으로 바꿨으며, syslogd·filterlog를 다시 띄워 기록 시각을 맞췄다.

## 남은 일

- 투명 방화벽 이중화는 하지 않았다. 운영이라면 유지보수 시간을 잡거나 두 대 구성을 따로 설계해야 한다.
- Suricata는 IDS(막지 않음)로만 켰다. 차단 모드(IPS)와 규칙 오탐 조정은 하지 않았다.
- L7 입구는 작업 PC 주소(ADMIN_PC)에서만 연다. 여러 사용자를 받는 구성과 인증서 갱신 절차는 정하지 않았다.
- 저장소 VM 실습 문서(주소 계획, 방화벽 계획)에 이 전환을 아직 반영하지 않았다.
