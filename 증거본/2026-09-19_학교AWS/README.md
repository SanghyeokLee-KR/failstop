조회에서 확인한 작업명은 `ec2:DescribeInstanceStatus`와 `autoscaling:DescribeAutoScalingGroups`다. EC2 세부 정보에는 `an identity-based policy explicitly denies the action`, ASG 오류에는 `with an explicit deny in an identity-based policy`와 정책명 `DenyAllWithoutMFA`가 표시됐다. 이것으로 ALB·ASG의 최종 허용 여부를 판정하지 않는다. MFA 인증 후 다시 확인해야 한다.

이 회차에는 인스턴스 생성·보안 그룹 변경·서버 접속·Linux 명령 실행을 하지 않았다. 따라서 서버 명령 캡처와 실행 로그는 없다. 캡처 요청 이전의 행동은 소급해 만들어 넣지 않았다. 파일 수정 시각은 저장 시각이며 장애 시작 시각이나 운영 RTO가 아니다.

[학교 안내 원문](https://rowan-cupboard-1fe.notion.site/AWS-Management-Console-Credentials-AIKOPO-Detailed-3dd2156ceb5f8096a9cbf02253b18f2a)의 로그인·EC2·RDS·S3·제한 사항을 읽었다. 자격증명 표는 캡처·파일 저장에서 제외했다. EC2는 별도 SG 생성 후 자동 태그를 확인하고 생성 화면에서 기존 SG를 선택해야 한다. 50GiB는 스토리지 설정의 상한이다. RDS 안내는 본문 gp2와 최종 표 gp3가 서로 달라 RDS 선택 시 관리자 확인이 필요하다. 현재 프로젝트는 자체 운영 PostgreSQL을 유지한다. 기본 제공 목록에 ALB·ASG는 명시돼 있지 않아 생성 권한을 단정하지 않는다.

프로파일 안내 한 곳의 `SafeInstanceProrile` 표기는 콘솔에서 확인한 `SafeInstanceProfile`과 다르다. 실제 본인 프로파일을 선택했고 다른 사용자의 프로파일은 사용하지 않았다. 연결 권한과 SSM 사용 여부는 별도 실행 검증 대상이다.

첫 서버의 초안은 Amazon Linux 2023 x86_64, t3.small 1대, 암호화 gp3 20GiB다. 기존 서브넷 `subnet-0525d8f575f6529ec`(ap-northeast-2a, 172.31.0.0/20)에서 퍼블릭 IPv4 자동 할당을 사용한다. SSH 키 페어와 인바운드 규칙은 없으며 SSM 연결은 아직 검증하지 않았다. IMDSv2 필수, 사용자 데이터 없음, gp3 기본 3,000 IOPS·125MiB/s, 종료 시 루트 볼륨 삭제가 초안의 조건이다.

CPU 크레딧 Standard는 Unlimited의 추가 크레딧 과금을 피하기 위한 선택이다. 크레딧이 소진되면 CPU 성능이 제한될 수 있으므로 이후 부하 결과에는 크레딧 잔액도 함께 기록해야 한다. 콘솔에 표시된 t3.small Linux 가격은 시간당 0.026달러이며, [AWS VPC 가격](https://aws.amazon.com/vpc/pricing/)의 퍼블릭 IPv4 한 개는 시간당 0.005달러다. 두 항목만 계산하면 시간당 0.031달러, 730시간에 22.63달러다. EBS·전송·로그·세금은 별도이며 전체 월 견적이나 실제 청구액이 아니다.

034의 `iam:GetRole` 거부로 프로파일 내부 역할의 정책은 검증하지 못했다. 이 결과는 인스턴스 프로파일 연결이나 SSM까지 거부된다는 뜻은 아니다. 생성과 접속을 실행한 뒤 각각 판단한다. EC2 생성 직전에는 기존 프로파일 연결로 새 서버가 AWS API 권한을 받는 점에 대해 사용자 확인을 요청했다. 이 기록 시점에는 생성 버튼을 누르지 않았고 Linux 명령도 실행하지 않았다.

이전 부팅 ID는 `751759fb-94a2-4ffb-9bd2-a861232c5a83`, 이후 ID는 `c97eaec5-07bd-46de-b7ee-a5c85b4f445a`다. 이전 부팅에서 09:24:08 UTC에 기록한 시험 메시지를 재부팅 후 조회했다. 설정 파일 SHA-256은 `5b1d5a88358944bd90353927848f7c36536e67c2514b350fbb0080b4831a0eb3`이며 로컬 `Get-FileHash` 결과와 일치했다. 새 부팅의 journal 시작은 09:24:40 UTC지만 이 시간 차이를 업무 복구 시간으로 해석하지 않는다.

PASS 범위는 호스트 한 대의 계획된 재부팅 뒤 로그 보존·기본 서비스·루트 마운트·SSH 재접속이다. 실제 디스크 한도 도달·7일 경과·비정상 전원 종료는 시험하지 않았고 거래 앱과 DB도 아직 설치하지 않았다. 보존 용량에 먼저 닿으면 7일치가 모두 남지 않을 수 있다.

사용자는 110 이후 종료 코드 출력 문구를 붙이지 말라고 요청했다. 이후 명령은 실제 명령만 입력하며 도구가 종료 코드를 제공하지 않으면 미수집으로 기록한다. 111 이후 화면은 이 방식을 적용한 실제 추가 실행이며 이전 증거를 편집한 이미지가 아니다.

[111 화면 정리](111_확인화면_정리.png)는 `clear` 실행 결과다. [112 이전 부팅 로그 확인](112_이전부팅_시험로그_확인.png)은 `sudo journalctl -b -1 -t exchange-lab --no-pager`를 종료 코드 문구 없이 다시 실행한 화면이다. 시험 메시지 존재로 보존을 확인했으며 두 명령의 종료 코드는 미수집이다.
