# 2026-10-10 개인 AWS 주 DB 장애 시험

발표덱 마지막 장의 'DB 승격 41.6초 · 주문 재개 92.9초 · 유실 0건(개인 AWS)'은 원자료가 저장소에 없어, 사용자 결정으로 개인 AWS(서울 리전, Patroni 엄격 동기 db-1 · db-2, etcd 3표)에서 다시 쟀다. 두 회차를 돌렸고 발표에는 갑작스러운 장애를 만든 2회차 값을 쓴다. AWS CLI · SSM 명령과 출력은 [명령기록.txt](명령기록.txt)에, 관측 원자료는 `raw/`(1회차) · `raw2/`(2회차)에 있다. DB 조회는 DB 서버에서 postgres 계정 peer 인증으로 했고 비밀 값은 다루지 않았다. 시각은 모두 AWS 서버 시계(UTC, KST는 +9)다.

시험 도구는 `영상/03_클로드_AWS시연/0_도구/`의 `db_failover_test.sh`(1회차), `db_failover_test2.sh`(2회차), `status_watch.mjs`(공개 상태 API `/api/v1/status`를 0.25초마다 기록)다. 저장소의 로컬 시연 도구(`harness/scripts/demo-db-failover.ps1`)와 같은 대조 방법을 쓴다. 주입 직전 60초 동안 주 DB에서 커밋이 보인 주문(`command_journal`의 NEW)과 체결(`trades`)을 적어 두고, 장애 뒤 새 주 DB에 모두 있는지 센다. 엄격 동기에서 다른 세션에 보인 커밋은 동기 예비가 이미 받은 것이다.

## 2회차(발표에 쓰는 값): 주 DB 전원 즉시 차단

주 DB db-2에서 시각을 디스크에 적고 `sync`한 뒤 `echo o > /proc/sysrq-trigger`로 전원을 즉시 끊었다. OS 종료 절차가 없어 Patroni가 리더 키를 놓지 못한다(서버가 갑자기 죽은 경우). 승격을 본 뒤 인스턴스가 stopped 가 된 것을 확인하고 다시 켰다.

## 1회차: EC2 강제 종료(정상 종료 절차가 돈 경우)

주 DB db-1을 `aws ec2 stop-instances --force`로 껐다. 그런데 db-1의 OS가 종료 절차를 밟아(02:03:17 Postgres · Patroni 정지, 02:03:24 전원 끔) Patroni가 리더 키를 놓았고, db-2가 02:03:18.292에 바로 승격했다. 예비 쪽 로그의 'replication terminated by primary server'(02:03:17.219)에서 1.07초 뒤다. 그래서 이 회차는 갑작스러운 장애가 아니라 '정상 종료로 내려간 주 DB'를 잰 것이다.

대조는 주문 211건 · 체결 127건이 모두 새 주 DB에 있었다(유실 0건, `raw/verify_run1.txt`). 주문 재개 시간은 쓸 수 없다. 시험 도구가 db-1이 아직 stopping 일 때 켜기를 보내 'IncorrectInstanceState'로 거절됐는데, 도구가 이 오류를 확인하지 않아 약 10분 뒤에 다시 켰다. 그동안 거래가 일시 중단됐다(공개 상태 API 11:03:17 ~ 11:14:20 KST). 2회차 도구는 stopped 를 확인한 뒤 켜고 성공 응답을 확인한다.

## 한계

- 대조는 주입 직전 60초 동안 커밋이 보인 주문 · 체결이다. 기록 뒤 주입까지의 약 4초 사이 커밋은 대조에 들지 않는다.
- 클라이언트가 응답을 받은 주문 하나하나를 대조한 것은 아니다(로컬 E-P1 의 ACK 기록기 · k6 대조는 개인 AWS 에서 돌리지 않았다).
- 한 회차 값이다. 반복 측정 분포는 없다.
- 시험 뒤 주 DB 는 db-1 이다.
