# 2026-09-29 VM 실습망 nftables 중앙 관리

작업 PC(DEV-PC, Windows, PowerShell 7.6, OpenSSH 9.5)에서 VM 실습망 여섯 대의 호스트 방화벽(nftables) 규칙을 저장소 원본 하나로 관리하는 도구 [`deploy/vm-lab/nft-central/`](../../deploy/vm-lab/nft-central/README.md)를 만들고 실제 VM에서 시험한 기록이다. 연구소장님 숙제 가운데 'VM 실습망 여섯 대의 nftables를 작업 PC에서 중앙으로 자동 관리'에 해당한다. 시간대는 KST다. 기준선을 가져오고, 손으로 바꾼 규칙·파일을 거치지 않은 커널 규칙 변경·원본에 없는 이름의 파일을 찾아 원본대로 되돌렸다. 문법 오류가 있는 원본의 적용은 거부됐다. 여섯 대(앱·DB 포함)에 해가 없는 규칙을 한 대씩 올렸다가 지웠고, 확인에 실패한 EDGE01 적용은 VM이 90초 뒤 스스로 되돌렸다. 이 기록은 로컬 VM 실습 결과이며 학교·개인 AWS의 검증 결과가 아니다. pfSense 두 대는 건드리지 않았다.

비밀 값은 입력하거나 출력하지 않았다. 캡처에 보이는 것은 사설 실습 주소, 포트, 파일 해시와 서비스 계정 이름뿐이다. 원본으로 가져온 규칙 파일 28개에 비밀 값 형태의 문자열이 없다는 것은 자동 검사(02)와 파일을 직접 읽어 확인했다.

캡처 창은 `term-evidence.ps1`이 연 Windows PowerShell 5.1 콘솔이고, 도구는 그 안에서 `pwsh -NoProfile -File`로 PowerShell 7을 불러 실행했다. 5.1은 외부 명령에 넘기는 인자 안의 큰따옴표를 제대로 전달하지 못하므로, 캡처 창에서 ssh로 보낸 원격 명령 안에는 큰따옴표를 넣지 않았다(04의 규칙 주석을 따옴표 없이 쓴 이유). 01~17 캡처에는 도구의 종료 코드가 남지 않았다(미수집). 19부터는 도구가 마지막 줄에 결과와 종료 코드를 직접 알린다. 21·22·28은 출력이 길어 캡처 창 대신 작업 도구에서 실행하고 화면 출력 원문을 기록 파일로 남겼으며, pwsh의 종료 코드를 따로 적었다. 이 세 기록에는 캡처가 없다.

## 사전 시험

증거 촬영 전(02:12~02:15)에 도구 사본을 임시 폴더에서 돌려 경로마다 한 번씩 시험했다. OPS01 시험에 쓴 사본은 01~17을 찍을 때의 저장소 파일과 sha256 앞 12자리가 같다(`nft-central.ps1` `C1CD8B9CC4AE`, `nft-central-remote.sh` `39F6FAF45015`). EDGE01 되돌리기 시험에는 그 사본에서 되돌리기 시간만 20초로 줄이고 가짜 확인을 넣은 변형을 따로 만들어 썼다. 01~17을 찍는 동안 저장소 파일은 바꾸지 않았다. 이 시험의 기록은 17·27과 03~08의 '마지막 적용' 열에 남아 있다.

- 02:12: 임시 원본으로 `-Pull`, `-Audit`, `-Plan`. VM에서는 읽기만 했다.
- 02:13:42 EDGE01: 되돌리기 경로 시험. 적용 뒤 반드시 달라지는 가짜 확인(`date +%s%N`)으로 확인이 실패하게 했다. 카운터만 있는 규칙을 올렸고 02:14:02에 VM이 스스로 되돌렸다(`result=ok`). 파일·규칙이 원래대로 돌아왔고 SELinux 거부 기록이 없었다. SSH는 막지 않았다.
- 02:14:20·02:14:44 OPS01: 확인 통과 경로 시험. 카운터만 있는 규칙을 올려 확인 4/4로 예약을 취소했고, 원본에서 지워 다시 적용해 기준선으로 돌렸다.

## 검토와 고친 것

01~17을 찍은 뒤 코드를 고치지 않는 별도 검토(reviewer 역할)를 받았고 판정은 FAIL이었다. 지적과 처리는 다음과 같다. 19~27은 고친 코드로 실행했다.

- **적용 전후 비교 확인의 공허 통과(차단).** Prometheus 조회가 오류를 내도 오류 문구가 적용 전후 같으면 통과했다. 적용 전 값과 비교하는 확인마다 값의 형식(`13/13`처럼 대상 1개 이상, `{"status":"..."}`)을 정해 형식이 아니면 적용 전이든 뒤든 실패로 하고, Prometheus 조회는 종료 코드도 보게 했다. 함수만 불러 오류 문구·빈 값·대상 0개·리더 바뀜 등 22가지를 넣어 보는 단위 시험을 임시 폴더에서 돌렸고 모두 통과했다(저장소에 넣지 않았다).
- **파일 목록 해석(차단).** VM이 보낸 목록에서 공백이 든 이름의 줄을 버리고, 대소문자만 다른 이름을 한 칸으로 합쳐 거짓 '일치'를 낼 수 있었다. 대소문자를 가리는 사전에 이름 전체를 담고 형식이 틀린 줄은 실패로 했다. 19·20에서 실제 VM으로 확인했다.
- **앱·DB 적용(범위 결정).** 앱·DB 적용 증거가 없고 90초 되돌리기가 앱의 50초 리더 조건보다 길다는 지적이다. 요청에 적힌 90초 되돌리기 동작은 바꾸지 않았다. 앱·DB에는 해가 없는 규칙의 확인 통과 경로만 시험했고(21·22, 리더 전환 0건), 확인 실패 때 곧바로 되돌릴지는 '남은 일'의 결정 필요로 남긴다.
- **검사 결과 전달.** 문서·스타일 검사는 실행했지만 결과가 검토자에게 전달되지 않았다. 마지막에 다시 실행했다.
- **낮은 지적.** 확인 전달 실패를 '이미 되돌렸다'로 잘못 알리던 곳, 확인과 타이머 만료가 겹칠 때의 경합, `-Vm ','`로 대상 필수 검사를 건너뛰던 곳, 예약 전 거절에도 150초를 기다리던 곳, 되돌린 뒤 대조가 빈 목록으로 통과하던 곳, 되돌리는 중의 새 적용과 같은 ID 백업, 비밀 값으로 보이는 줄을 화면에 찍던 곳, `-Plan` 종료 코드, 라벨 복구 실패가 규칙 재적재를 막던 곳을 고쳤다. 설명서에는 확인하지 않는 경로, DB 승격 스크립트, 공통 기반이 만드는 `firewall.nft`, 적용 기록이 남는 범위를 보탰다.
- **증거의 약점.** 13의 기존 SSH 세션 기록은 차단 구간 안의 응답이 없어 근거가 약했다. 23에서 차단 구간 안에 두 번 응답한 기록으로 보강했다. 01~17의 도구 종료 코드는 기록하지 않았다(미수집).

고친 결과를 같은 역할로 다시 검토받았고 판정은 PASS WITH FOLLOW-UP이었다. 차단 두 건은 해결, 앱·DB 범위는 결정 필요로 남긴 처리로 병합 가능하다는 판단이다. 재검토가 새로 짚은 낮은 지적은 다음처럼 고쳤고, 28에서 최종 코드로 확인했다.

- 도구 오류의 종료 코드. 원본 오류나 인자 오류가 처리되지 않은 예외로 끝나 '어긋남'과 같은 1이 나올 수 있었다. 이제 결과 줄과 함께 2로 끝나고, `-Apply`는 VM을 건드리기 전에 대상 원본을 모두 읽어 검사한다. 적용 뒤 확인 중 VM 응답 형식이 틀리면 도구가 멈추지 않고 확인 실패로 처리해 예약된 되돌리기가 진행된다.
- 설명서의 리더 전환 근거. '50초'는 2026-09-28 사례의 관찰값이지 임계가 아니었다. 앱 설정값(리스 TTL 10초, 스스로 물러나는 시간 45초)을 근거로 다시 적었다.
- 수치와 표기. OPS01 확인 소요 시간을 VM 기록 기준 11~16초로, 18의 EDGE01 확인 수를 6/6으로 바로잡았다.
- 가져오기의 대소문자. 대소문자만 다른 이름이 VM에 있으면 가져오지 않고, 대소문자만 바뀐 이름은 옛 원본 파일을 먼저 지운 뒤 VM의 이름으로 쓴다.
- 확인 응답만 잃은 경우. 되돌리기 기록과 함께 확인 기록도 찾아, 취소가 VM에 닿았으면 그렇게 알린다.
- 틀린 주석. 사전을 돌려줄 때 쓴 단항 쉼표와 그 이유 주석은 사실과 달라(PowerShell은 사전을 풀지 않는다) 지웠다.

재검토가 코드로만 확인했다고 밝힌 경로(예약 전 거절, 되돌리는 중 새 적용 거절, 같은 ID 백업 거절, 확인과 타이머 만료의 경합, 라벨 복구 실패 기록)는 VM에서 따로 일으켜 보지 않았다.

## 관찰

- 파일 해시만으로는 `nft add rule`처럼 파일을 거치지 않은 변경을 볼 수 없다(09에서 해시는 그대로였다). VM의 파일을 격리된 네트워크 이름공간에 올려 만든 규칙과 지금 커널 규칙을 비교해야 잡힌다.
- 원본 전체를 VM에서 먼저 `nft -c`로 검사하므로 문법 오류는 VM의 파일과 규칙을 건드리기 전에 멈춘다(11).
- 시험 규칙은 작업 PC의 새 SSH 연결만 막았다. 미리 맺어 둔 SSH 세션은 차단 구간 안에서도 명령에 응답했고(23), 규칙의 대상이 아닌 L7 입구 → 웹 진입 443은 두 번의 시험 모두 2초 관찰 73회가 전부 200이었다. 확인에 실패한 변경은 작업 PC가 VM에 새로 접속할 수 없는 동안에도 VM이 예약대로 되돌렸다(13·14는 타이머 시작부터 90초, 23·24는 91초).
- 앱·DB를 포함한 여섯 대를 한 대씩 두 번 적용하는 동안 확인이 모두 통과했고, 웹 진입, Prometheus 수집, OPS01 원격 로그 수신, 앱 리더 상태에 변화가 없었다(21·22·26).
- 앱·DB에서 확인이 실패하는 경우와 되돌리기는 시험하지 않았다.
