# 동기 복제가 사 주는 장애 내성 실측 (2026-09-08)

증거 `sync-replication-20260908` 이 동기 복제의 값을 쟀다. 복제 없음 76.3 주문/s 에서 동기
53.0 주문/s 로 천장이 30.5% 내려간다. 그 회차는 대가만 재고 끝났다. 이 회차는 그 대가로
무엇을 샀는지 잰다.

## 결론

| 판정 | 내용 | 실측이 뒷받침하는가 |
|---|---|---|
| A | 단일 sync standby 는 standby 장애 시 commit availability 를 훼손한다 | 그렇다 |
| B | `ANY 1` 과 standby 2대는 단일 standby 장애를 견딘다 | 그렇다 |
| C | 동기 standby 전부 상실 시 commit availability 문제가 다시 생긴다 | 그렇다 |
| D | Admission Control 이 5xx 와 자원 고갈 대신 계획된 429 로 보호한다 | 그렇다 |

측정하지 않은 결론이 하나 더 나왔고 이것이 이 회차에서 가장 중요하다.

**standby 를 되살려도 서비스는 되살아나지 않는다.** 복제가 `streaming` 으로 복귀한 뒤에도
readiness 는 503 에 머문다. 리더 리스 갱신이 그 자체로 커밋이라 stall 구간에 함께 막히고,
막힌 동안 리스가 만료되며, 커밋이 풀리는 순간 fencing 이 리더를 끌어내리기 때문이다.
복구에 필요한 것은 standby 가 아니라 앱 재기동이다. 세 회차에서 독립적으로 재현했다.

## PostgreSQL 복제 설정

standby 는 둘 다 슬롯을 동반한 base backup 으로 세웠다. 슬롯 없이 만들면 primary 가
WAL 세그먼트를 먼저 지워 standby 가 따라붙지 못한다.

```
docker run --rm --network exnet -v ex-pg-sb2:/d -e PGPASSWORD=exchange postgres:17-alpine \
  pg_basebackup -h ex-pg -U exchange -D /d -R -X stream -C -S standby_2 -c fast
```

`application_name` 은 `primary_conninfo` 에 직접 넣는다. 이 이름이 곧
`synchronous_standby_names` 가 지목하는 대상이다.

설정 변경 전후 값을 남긴다.

| 시점 | `synchronous_commit` | `synchronous_standby_names` |
|---|---|---|
| PHASE 1 | `on` | `standby_1` |
| PHASE 2 | `on` | `ANY 1 (standby_1, standby_2)` |
| 실험 종료 후 복구 | `on` | 빈값 |

`ANY 1 (...)` 은 PostgreSQL 17.11 에서 유효하다. 적용 후 `pg_stat_replication.sync_state` 가
두 standby 모두 `quorum` 으로 바뀌는 것으로 실증했다. `sync` 가 아니라 `quorum` 으로 표시되는
것이 정족수 모드가 실제로 걸렸다는 표지다.

`ALTER SYSTEM` 과 `pg_reload_conf()` 는 반드시 psql 호출을 나눠 실행한다. 한 `-c` 에 묶으면
`ALTER SYSTEM cannot run inside a transaction block` 으로 조용히 실패하고, 그러면 동기라고
믿으면서 비동기를 재게 된다.

## 실행 명령

드라이버는 `run.sh` 다. 한 부하 안에서 정상과 장애와 복구를 잇는다. 회차를 나누면 조건이
흔들리기 때문이다.

```
bash run.sh p1   ex-pg2            ex-pg2  ex-pg2          PHASE 1
bash run.sh p2b  ex-pg2            ex-pg2  ex-pg2,ex-pg3   PHASE 2-A/2-B/2-C
bash run.sh p2d  ex-pg3            ex-pg3  ex-pg2,ex-pg3   PHASE 2-D
bash run.sh p2e  "ex-pg2 ex-pg3"   ""      ex-pg2,ex-pg3   PHASE 2-E, Admission A
bash run.sh p2eb "ex-pg2 ex-pg3"   ""      ex-pg2,ex-pg3   Admission B
```

집계는 `harness/replication/analyze.py` 가 한다.

```
python harness/replication/analyze.py --samples samples/p2b.jsonl --marks samples/p2b_marks.txt \
  --window 04:03:50,04:05:05,2-A --window 04:05:07,04:06:30,2-B --window 04:06:40,04:07:34,2-C
```

구간을 사건 사이로 자르지 않고 `--window` 로 지정하는 이유가 있다. 부하 도구는 235초를 돌고
`LOAD_END` 표시는 251초에 찍히므로 마지막 구간에 부하가 이미 멈춘 17초가 섞인다. 그대로 읽으면
회복 구간이 실제보다 낮게 나온다.

## 여섯 질문에 대한 답

**1. 동기 standby 가 한 대뿐일 때 그 standby 가 죽으면 주문 commit 은 어떻게 되는가.**

전면 정지한다. kill 2초 뒤 접수가 97.2/s 에서 0/s 가 되고 회차가 끝날 때까지 한 건도 커밋되지
않았다. 부분 저하가 아니라 전부 아니면 전무다.

**2. Primary 자체는 살아 있어도 commit 이 stall 되는가.**

그렇다. primary 프로세스는 살아 있고 psql 조회도 계속 응답한다. 다만 CPU 가 133% 에서 **7%**
로 떨어진다. 과부하로 느려진 것이 아니라 동기 응답을 기다리며 놀고 있는 것이다. 같은 일이
2-E 에서 66% 에서 8% 로 재현됐다.

**3. 이때 throughput 과 latency 와 429 는 어떻게 변하는가.**

| 지표 | 정상 | kill 후 |
|---|---:|---:|
| 접수 | 97.2/s | 0.0/s |
| 429 | 17.6/s | 125.2/s |
| 앱 측정 평균 지연 | 38.6ms | 5,049.7ms |
| 5xx | 0.0/s | **0.0/s** |

수요 전량(약 125/s)이 계획된 거절로 전환됐다. 지연 5,049ms 는 처리된 요청의 값이 아니라
게이트를 잡고 있던 소수 요청이 타임아웃으로 풀린 값이다.

**4. standby 를 2대로 늘리고 `ANY 1` 로 구성하면 한 대 장애 시 주문 처리가 계속되는가.**

계속된다. 그리고 처리량이 **떨어지지 않는다**.

| 회차 | 정상 | kill 중 | 차 |
|---|---:|---:|---:|
| 2-B standby_1 kill | 54.7/s | 56.0/s | +2.4% |
| 2-D standby_2 kill | 52.5/s | 56.9/s | +8.4% |

두 회차 모두 5xx 0.0/s 이고, 부하 도구의 주행 전체 503 카운트도 **0** 이다. 곧 "무중단" 이라는
표현이 측정으로 뒷받침된다. 처리량이 오히려 오르는 것은 죽은 standby 가 쓰던 호스트 자원이
풀리기 때문이며 이는 같은 호스트에서 돌린 이 실험의 성질이지 클라우드에서 기대할 값이 아니다.

standby_1 kill 과 standby_2 kill 의 결과가 대칭이다. 정족수가 특정 대수에 치우쳐 있지 않다.

복구는 재기동 **6초** 만에 `streaming` 과 `quorum` 으로 돌아왔고 그 사이 서비스는 중단된 적이
없다.

**5. standby 가 모두 사라지면 어떤 상태가 되는가.**

PHASE 1-B 와 같은 상태로 돌아간다. 접수 0/s, 거절 115.0/s, 5xx 0.0/s 로 166초 동안 유지됐다.
곧 `ANY 1` 이 사 준 것은 **한 대분의 여유**이지 동기 복제 자체의 성질 변경이 아니다.

여기에 더해 이 회차가 처음 드러낸 사실이 있다. 리더 리스 갱신이 그 자체로 커밋이므로 stall 에
함께 막힌다. 그래서 리스는 kill 9.6초 뒤 이미 만료됐는데 아무도 그것을 알 수 없었고, standby 가
돌아와 커밋이 풀리는 순간 fencing 이 리더를 끌어내렸다. **standby 복구가 곧 서비스 복구를
뜻하지 않는다.** 서비스를 되돌린 것은 앱 재기동이다.

**6. Admission Control 이 이 상황에서 어떻게 시스템을 보호하는가.**

stall 전 구간에서 5xx 가 0.0/s 이고 Hikari 대기가 0.00 이다. 요청 풀 16 중 붙잡힌 것은 주문 정원
6 에 리스 갱신 1 을 더한 7 뿐이고 9 개가 그대로 남았다. 게이트가 없었다면 초당 125건의 요청이
커넥션을 기다리며 쌓였을 자리다. 자세한 비교는 다음 절에 있다.

## Admission Control 연계 실험

동기 standby 를 전부 잃은 같은 조건에서 주문 정원만 바꿔 두 번 돌렸다.

정확히 0 은 설정으로 표현되지 않는다. `exchange.admission.order-in-flight` 는 0 이하를 "풀에서
유도" 로 읽으므로 명시 가능한 최솟값이 1 이다. 코드를 고치지 않기로 했으므로 B 는 정원 1 이다.

| 지표 | A. 정원 6 | B. 정원 1 |
|---|---:|---:|
| 정상 구간 접수 | 54.6/s | 30.2/s |
| 정상 구간 429 | 63.3/s | 84.1/s |
| 정상 구간 평균 지연 | 105.9ms | 30.1ms |
| 정상 구간 p95 와 p99 | 161.6ms / 193.2ms | 37.3ms / 65.7ms |
| stall 구간 접수 | 0.0/s | 0.0/s |
| stall 구간 429 | 115.0/s | 115.3/s |
| stall 구간 5xx | 0.0/s | 0.0/s |
| stall 구간 Hikari 활성 | **6.73** | **1.03** |
| stall 구간 Hikari 대기 | 0.00 | 0.00 |
| stall 구간 앱 CPU | 0.071 | 0.074 |
| stall 구간 primary CPU | 8% | 10% |
| 주행 전체 503 | 0 | 0 |

읽는 법은 이렇다.

- **정원을 줄여도 위험 구간의 거절률과 5xx 는 달라지지 않는다.** 115.0/s 대 115.3/s 이고 둘 다
  5xx 0 이다. 수요가 정원을 훨씬 넘으므로 정원이 6이든 1이든 초과분은 똑같이 429 가 된다.
- **줄여서 얻는 것은 붙잡힌 커넥션 6개다.** 7 에서 1 로 준다.
- **줄여서 잃는 것은 정상 구간 처리량 45% 다.** 54.6/s 에서 30.2/s 로 내려간다.
- 이 시스템에서 정원 6 은 이미 풀 16 중 9 를 남긴다. 고갈이 애초에 일어나지 않는다. 그러므로
  **정원을 더 줄일 실익이 없다.** 정원 6 이 이미 D 판정의 보호를 제공한다.

정원을 6 으로 되돌린 뒤 정상 주문이 다시 수용되는 것을 확인했다. 71.5 접수/s, 5xx 0.0/s,
주행 전체 503 0 건이다.

## 실패와 예외

- **슬롯 없는 base backup 이 실패한다.** `WAL segment already removed` 로 standby 가 따라붙지
  못한다. `-C -S <슬롯이름>` 을 붙여 해결했다.
- **`ALTER SYSTEM` 과 `pg_reload_conf()` 를 한 psql `-c` 에 묶으면 조용히 실패한다.** 이 회차 이전
  `sync-replication-20260908` 의 첫 측정이 그래서 동기가 아니라 비동기였다. 나눠 호출하고
  `sync_state` 를 눈으로 확인한 뒤 측정하는 절차로 바꿨다.
- **부하 중 base backup 이 리더 리스를 만료시킨다.** `-c fast` 로 체크포인트를 당기면 부하가 걸린
  primary 에서 리스 갱신이 밀린다. 03:39:12 회차에서 0.16초 초과로 리더가 내려앉았다. standby 는
  부하를 끊고 세워야 한다.
- **기본 체크포인트는 최대 5분을 기다린다.** `-c fast` 없이 돌리면 `waiting for checkpoint` 에서
  멈춘 것처럼 보인다. 부하를 끊은 뒤 `-c fast` 를 쓰는 것이 맞다.
- **집계기가 429 를 주문 URI 에서 세면 0 으로 읽힌다.** 거절은 컨트롤러 앞 필터에서 나가므로
  요청이 주문 경로 라벨을 얻지 못하고 `uri="UNKNOWN"` 으로 계상된다. 이 때문에 첫 회차에서
  "요청이 그냥 매달린다" 는 잘못된 결론을 냈다. `exchange_admission_rejected_total` 을 원천으로
  바꿔 고쳤다.
- **PHASE 1 과 PHASE 2 의 절대 처리량을 직접 비교하면 안 된다.** PHASE 1 정상이 97.2/s 이고
  PHASE 2 정상이 54.7/s 인데, 이 차는 정족수 때문이 아니라 12 코어 호스트에 4 vCPU standby
  컨테이너가 하나 더 들어왔기 때문이다. 유효한 비교는 각 PHASE 내부의 상대차뿐이다.

## 로컬 실험의 한계

- **같은 호스트의 컨테이너 사이 왕복은 매우 작다.** 이 회차의 `flush_lag` 은 1.4ms 에서 3.5ms 다.
  AWS Multi-AZ 왕복은 재지 않았다. 이 결과를 Multi-AZ 성능이라고 읽으면 안 된다. AZ 지연이
  붙으면 동기 대기가 늘고 정상 구간 처리량이 더 내려간다. 그 방향의 값은
  `sync-replication-20260908` 이 toxiproxy 왕복 2ms 로 -12.8% 를 쟀다.
- **호스트가 12 코어이고 과할당 상태다.** primary 4, standby 4씩, 앱 2씩, 봇과 부하기가 그 안에서
  경쟁한다. 절대 처리량을 클라우드 값으로 읽지 않는다.
- **회차가 조건마다 하나다.** 분산을 재지 않았다.
- **구간별 백분위를 재지 않았다.** 부하 도구가 주행 요약만 주기 때문이다.
- **standby 를 읽기에 쓰지 않았다.** 정본이 standby 를 페일오버 대기로 규정한다.
- **승격과 switchover 를 재지 않았다.** 이 회차는 primary 를 죽이지 않았다.
- **Admission 정원 0 을 재지 않았다.** 설정으로 표현되지 않아 1 로 대신했다.

## 다음 단계

1. **리스 갱신을 커밋 경로에서 떼는 것을 검토한다.** 이 회차가 드러낸 가장 큰 결함이다. 리스
   갱신이 동기 커밋을 타는 한, 동기 standby 상실은 언제나 리더 상실로 번진다. standby 가
   돌아와도 앱 재기동이 필요하다는 뜻이고, 이는 자동 복구를 원천적으로 막는다.
2. **`ANY 1` 을 상시면 기본값으로 검토한다.** 단일 sync 대비 얻는 것이 크고 잃는 것이 이 회차
   범위에서는 관측되지 않았다. 다만 standby 2대의 비용은 별도 계산이 필요하다.
3. **AZ 지연을 넣고 `ANY 1` 을 다시 잰다.** 정족수는 둘 중 빠른 쪽을 기다리므로 AZ 지연 아래에서
   단일 sync 보다 유리할 수 있다. 이 회차는 그 효과를 볼 수 없는 조건이었다.
4. **Primary Discovery 는 별도 단계다.** `spring.datasource.url` 이 고정 primary 를 본다. 이 회차는
   그 문제를 건드리지 않았다.
