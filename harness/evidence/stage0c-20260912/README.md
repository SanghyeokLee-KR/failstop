# 접수 락 임계구역 3분할과 fsync 재측정 (2026-09-12)

`인수인계_20260911.md` §6-1 이 남긴 과제다. 접수 락 보유 시간 중 설명되지 않던 구간을
`f4ba7ca` 가 넣은 계측으로 셋으로 가른다. 커넥션 획득과 경계 시작, 커밋, 정리와 반납이다.

이미지는 `06b4031` 코드로 구웠다. `06b4031` 은 `f4ba7ca` 위의 문서 커밋이라 서버 코드가
`f4ba7ca` 와 같다.

산출물 셋. `probe.json`(240/s), `probe_saturated.json`(600/s), `probe_wired.json`(240/s
재주행, fsync 배선 검증분). k6 원본은 `harness/evidence/k6-rt-stage0c*.log` 와
`k6-rt-stage0d.log` 이고 `.gitignore` 가 `harness/evidence/k6-*.log` 를 빼므로 저장소에
올라가지 않는다. 로컬에만 있다.

## 1. 결론

**그 구간은 커밋이다.** 커넥션 획득과 반납은 비용이 아니다. 두 동작점에서 같다.

| 구간 | 240/s | 600/s |
|---|---:|---:|
| 커넥션획득·경계시작 | 0.005ms | 0.006ms |
| 커밋 | 0.901ms | 1.154ms |
| 정리·반납 | 0.004ms | 0.006ms |
| 합 | 0.910ms | 1.165ms |
| 커밋 몫 | 99.0% | 99.1% |

§6-2 의 두 갈래 중 JDBC 와 트랜잭션 배선은 축이 아니다. 내구성 설정이 축이다. 현재 값은
`commit_delay=0`, `commit_siblings=5`, `synchronous_commit=on`, `wal_sync_method=fdatasync`,
`synchronous_standby_names` 는 빈 값이다.

## 2. 09-11 과 절대값이 갈린다

같은 요청 OPS 에 결과가 1.62배 다르다. 양쪽 다 왕복 프로브 산출물이라 같은 술어끼리 맞춘
대조다.

| 항목 | 09-11 `append-fastpath/probe_after` | 09-12 `probe.json` |
|---|---:|---:|
| 요청 OPS | 240 | 240 |
| 제시 부하(접수+거절) | 259.3/s | 256.6/s |
| 접수 | 157.47/s | 255.36/s |
| 수용거절 | 101.87/s | 1.24/s |
| 락 보유 점유 | 0.974 | 0.508 |
| 락 보유 1회 | 6.166ms | 1.977ms |
| 커넥션·경계·커밋 | 4.239ms | 0.910ms |

제시 부하가 거의 같은데 한쪽은 포화하고 한쪽은 절반만 쓴다. 240/s 가 더는 임계구역을
포화시키지 못해 600/s 로 다시 걸었고 그때 점유 0.906 에 접수 373.82/s 가 나왔다. 600/s 칸의
373.82 는 240/s 칸의 값과 나란히 놓지 않는다. 요청이 다르다.

**같은 날 안에서는 재현된다.** 배선 검증을 겸해 240/s 를 한 번 더 걸었다(`probe_wired.json`).

| 항목 | `probe.json` | `probe_wired.json` |
|---|---:|---:|
| 접수 | 255.358/s | 255.164/s |
| 락 보유 1회 | 1.977ms | 2.003ms |
| 락 보유 점유 | 0.508 | 0.515 |
| 커밋 | 0.901ms | 0.922ms |
| fsync 건당 | 0.419ms | 0.417ms |

접수가 0.08퍼센트 안에서 맞는다. 곧 09-11 과의 1.62배 차이는 주행 간 산포가 아니다. 날짜를
넘는 변동이다.

정본 5.7.12 표의 240/s 칸 160.25 는 사다리 주행(`ceiling_after.json`) 값이고 위의 157.47 은
같은 날 같은 요청의 왕복 프로브 값이다. 둘은 다른 주행이다.

## 3. 코드는 원인이 아니다. 다만 같은 커밋도 아니다

09-11 대조군 `probe_after.json` 은 `5c37787` 산출물이다. 09-12 이미지는 `f4ba7ca` 다.
`git diff 5c37787 HEAD -- server/` 가 `EngineConfig.java` 6행, `CommandJournalAppender.java`
62행 추가 2행 삭제를 낸다. 내용은 `System.nanoTime` 표식과 `LongAdder` 뿐이고 `f4ba7ca`
커밋 본문도 "계측만 더한다. 동작을 바꾸지 않는다" 로 적는다.

계측은 비용을 더하는 방향이다. 더 많은 일을 하는 쪽이 더 빨랐으므로 코드 차이로는 이 단축을
설명할 수 없다.

## 4. 저장 계층은 움직인다. 다만 09-11 값이 없다

`pg_test_fsync -s 5`, 8kB 한 번 쓰기. 09-07 과 같은 기준이다. PGDATA 를 `-f` 로 직접
지정한 값과 기본 경로 값이 같아 측정 위치 차이가 아니다.

| 회차 | fdatasync | 건당 |
|---|---:|---:|
| 2026-09-07 (`wal-fsync-20260907`) | 311.9 ops/s | 3.206ms |
| 2026-09-11 | 미측정 | 미측정 |
| 2026-09-12 PGDATA 지정 | 2389.3 ops/s | 0.419ms |
| 2026-09-12 기본 경로 | 2381.2 ops/s | 0.420ms |

09-07 과 09-12 사이가 7.7배다. `wal-fsync-20260907` 이 3.2ms 의 정체를 하드웨어가 아니라
WSL2 저장 계층으로 지목한 그 계층이다.

**09-11 에 3.206ms 를 대입하면 안 된다.** 그날 재지 않았고, 같은 날 다른 실측이 그 값을
배제한다. `stage0-20260911/stage0.json` 이 `synchronous_commit=on` 과 `fdatasync` 에서 단일
세션 749.8 커밋/s, 평균 1.334ms 를 쟀다. 장치 플러시가 3.206ms 였다면 단일 세션이 초당 312
를 넘을 수 없는데 749.8 은 그 2.4배다. 곧 09-11 의 플러시는 1.334ms 이하였다. 다만 그 상한은
무부하 창의 값이다. `stage0` 은 `chaos-pg` 단독 기동이고 대조군 `probe_after` 는 부하 주행이라 부하
중 같은 장치가 그 상한 안에 있었다는 보장은 없다. 그날의 값은 모른다.

**따라서 이번 차이의 원인을 저장 계층으로 확정하지 않는다.** 코드로 설명되지 않고 저장
계층이 날짜마다 움직인다는 것까지가 실측이다. 호스트 동시 부하와 WSL2 가상 디스크 상태도
배제하지 못했다.

## 5. 모형은 유지된다

락 보유 1회의 역수가 단일 락의 산술 상한이다. 09-11 은 6.166ms 로 162/s 이고 실측 157.47
이다. 오늘은 2.420ms 로 413/s 이고 실측 373.82 다. 두 회차 모두 모형과 맞으므로 상한이
접수 락이라는 판정 자체는 유지된다. 움직인 것은 그 락 안의 커밋 시간이다.

## 6. 이 회차가 바꾸는 것

- **천장 수치의 절대값은 회차를 넘겨 인용하지 않는다.** 72.2 에서 160.25 까지의 사다리는
  회차 안의 전후 대조라 변화율은 유효하다. 설명되지 않는 1.62배 변동이 있는 한 절대값은
  회차 밖에서 의미를 갖지 못한다. 기획안 한계 47 에 등재했다.
- **`인수인계_20260911.md` §6-1 의 "약 3.0ms 가 설명되지 않는다" 는 오늘 재현되지 않는다.**
  포화 상태에서도 버킷 전체가 1.165ms 이고 커밋이 1.154ms 다. 그 구간이 09-11 에 무엇이었는지는
  모른다. 그날은 3분할 계측이 없었고 fsync 도 재지 않았다. 재현할 방법도 없다.

## 7. 함께 발견한 계측 결함

`표별 쓰기` 에서 `command_journal` 과 `event_journal` 의 삽입/명령이 두 회차 모두 0.000 이다.
접수마다 저널 행이 한 건씩 들어가므로 1.0 근처여야 한다. 둘 다 파티션 표라 부모 표의
통계에 삽입이 잡히지 않는다. 09-11 증거에도 같은 값이 있어 새 결함은 아니다. 그 표를
명령당 쓰기 근거로 인용하면 저널 쓰기만큼 과소 집계된다.

## 8. 남은 것

`commit_delay` 와 `commit_siblings` 격자가 다음 조치다. 0단계 (a) 가 동시 커밋이 선형으로
는다는 것을 이미 보였으므로 그룹 커밋이 도는 조건이다. 다만 오늘 fsync 가 0.419ms 라 얻을
여지가 09-11 보다 작다.

저장 계층 변동을 회차마다 함께 재도록 `clean_suite.fsync_state` 를 배선했다. k6 주행 직전
1회이고 왕복 프로브(`roundtrip_probe`)와 사다리 주행(`clean_suite --suite`, `k6_ceiling`)
셋 다에 걸었다.

배선은 주행으로 확인했다. `probe_wired.json` 이 `fsync fdatasync/s` 2398.252 와
`fsync 건당(ms)` 0.417 을 담고 `k6_rc` 가 0 이다. `probe.json` 과 `probe_saturated.json` 은
배선 이전에 돌아서 그 키가 없다.

남은 조건 하나를 적어 둔다. 측정 시점에 봇 기저가 이미 돌고 있어 완전한 무부하가 아니다.
09-07 기준값이 어떤 조건에서 나왔는지 증거에 없으므로 그 값과의 조건 동일성은 미확인이다.
회차 간 비교는 조건이 같아 성립한다.
