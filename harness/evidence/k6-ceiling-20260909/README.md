# k6 천장 재측정 (2026-09-09)

봇이 상한이라는 판정(`../load-ceiling-20260909/`) 뒤에 개방 루프 계측기로 다시 잰 회차다.

## 왜 다시 쟀는가

봇은 앱 안에서 도는 스레드다. 앱이 느려지면 봇도 같이 느려지는 닫힌 루프라 시스템이 밀리면 주입도 밀린다. 자기 자신을 자로 잴 수 없다.

k6 는 시스템 완전 외부에서 `constant-arrival-rate` 로 주입한다. 서버가 밀려도 계획대로 나간다.

## 판정

**천장은 첫 구간 아래다.** 요청 20/s 에서 이미 접수가 15.8/s 이고 거절이 101.6/s 다. 요청을 올리면 접수가 오르지 않고 오히려 줄며 거절만 는다. 40/s 에서 7.4, 80/s 이상에서 3 안팎으로 주저앉는다.

**막는 것은 수용 게이트다.** 거절이 요청과 함께 단조 증가해 350/s 에서 303/s 에 이른다. 같은 구간에서 커넥션 풀 활성이 1에서 2 이고 대기가 0 이므로 커넥션이 모자란 것이 아니다. 게이트가 정원 밖 요청을 기다리게 하지 않고 즉시 거절하는 설계가 그대로 동작한 것이다.

**시퀀서 큐가 처음으로 쌓였다.** 13에서 18 사이다. 봇 회차에서는 전 구간 0 이었다. 단일 라이터가 실제로 밀린 첫 관측이다.

**지연이 첫 구간에서 최악이다.** p99 971ms 다. 이후 구간에서 오히려 낮아지는데, 거절이 늘어 실제로 처리하는 양이 줄기 때문이다. 곧 이 시스템은 과부하에서 지연을 늘리는 대신 거절을 늘린다. 백프레셔 설계 의도와 맞는다.

봇은 목표를 400 으로 올려도 거절을 한 건도 만들지 못했다. k6 는 20 에서 게이트를 때린다. 부하 발생기를 시스템 밖에 두는 설계의 근거가 이 대조다.

## 이 회차가 드러낸 결함

**부하 계정 키가 만료돼 있었다.** `harness/load/secrets/k6_keys.json` 의 `access_key` 가 `api_keys` 에 0건이었다. 카오스 볼륨을 새로 만들 때 키가 갈렸는데 파일은 그대로였다. k6 주문이 전량 401 이었고, 서버가 받은 것은 봇 것뿐이라 요청을 20 에서 350 으로 올려도 접수가 12/s 에 고정됐다. `POST /harness/v1/loadtest-keys` 로 재발급해 해소했다.

이 결함은 조용하다. k6 는 임계 위반으로 종료코드만 남기고 접수 지표는 봇 값으로 그럴듯하게 채워진다. 상태 코드를 쪼개 보기 전에는 드러나지 않는다.

**계측 시점이 틀려 있었다.** 종전 러너가 k6 종료 뒤에 표본을 잡아 1분 창에 조용한 구간이 섞였다. 기저보다 낮은 값이 나왔다. 주행 중 표집으로 고쳤다.

## 남은 것

정원 설정이 맞는지는 아직 모른다. 거절이 이렇게 이른 구간에서 시작하는 것이 의도한 보호인지 과보호인지 판정하려면 정원을 바꿔 가며 같은 사다리를 돌려야 한다. 정본 한계로 등재한다.
