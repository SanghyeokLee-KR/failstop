# 오토스케일링 시나리오 실측 (2026-09-08)

정본에 오토스케일링이 없었다. 채택도 기각도 아니고 결정 자체가 없었다. 그 자리를 재고 채운다.

시나리오는 아래 순서다. 전 구간을 로컬 도커에서 돌렸고 두 번 완주했다.

```
App 2대 정상 -> 부하 증가 -> DB 병목 -> DB Scale-Up -> DB CPU 하락
-> App CPU 상승 -> ASG 2 -> 3 -> 서버 1대 강제 종료 -> 서비스 지속
-> ASG 자동 복구 -> 부하 감소 -> 3 -> 2 Scale-In
```

## 무엇이 확장 대상인가

**쓰기는 대상이 아니다.** 매칭엔진이 단일 라이터라 노드를 늘려도 주문 천장이 오르지 않는다.
2026-09-07 실측에서 1 대를 2 대로 늘려도 56.8/s 에서 54.3/s 였고 커넥션 풀을 3 배로 늘려도
86.5/s 에서 83.1/s 였다. 그래서 ASG 는 조회 계층에만 건다. 리더는 그룹 밖 고정 구성원이다.

AWS 로 옮기면 정본 6.11 의 조회 타겟그룹에 걸린 ASG 에 해당한다. 쓰기 타겟그룹은 그대로 둔다.

## 운영값

| 항목 | 지정 | 이 회차 |
|---|---|---|
| Min / Desired / Max | 2 / 2 / 3 | 같음(리더 1 + 조회 1~2) |
| Scale-Out | CPU 60% 이상 3 분 | 60% 이상 **30 초** |
| Scale-In | CPU 30% 이하 10 분 | 30% 이하 **90 초** |
| Connection draining | 적용 | 15 초 |
| 쿨다운 | | 20 초 |

**시간만 1/6 로 압축했고 판정 로직은 같다.** 그대로 쓰면 한 회차가 20 분을 넘어 관측 창이
실용적이지 않다. `--out-for 180 --in-for 600` 으로 운영값 그대로 돌릴 수 있다.

## 환경

| 노드 | 규격 | 역할 |
|---|---|---|
| `ex-app` | 1 vCPU / 1GB | 리더. 매칭엔진 보유. ASG 밖 |
| `ex-app2` | 1 vCPU / 1GB | 조회 전용. 엔진·flyway OFF |
| `ex-app3` | 1 vCPU / 1GB | ASG 가 만들고 지운다 |
| `ex-pg` | 0.3 ~ 4 vCPU | 시나리오 중 런타임 변경 |
| `ex-lb` | nginx 1.29, 2 ~ 6 vCPU | 시험 장비 |
| `ex-bot` | 2 vCPU | 배경 체결. `target-ops 60` |

컨트롤러는 `harness/asg/asg_controller.py` 다. 판정 로그는 같은 폴더의
`asg_decisions_1.jsonl`(Scale-Out 회차)과 `asg_decisions_2.jsonl`(종료·복구·Scale-In 회차)이다.

## 1단계. DB 병목

`docker update --cpus 0.3 ex-pg` 로 저사양 DB 를 모사했다. 주문 100 OPS 주입 90 초.

| 지표 | 값 |
|---|---|
| 주문 접수 | **16.2/s** |
| 429 거절 | 83.8/s |
| 주문 p95 | **802ms** |
| 주문 p99 | 1,280ms |
| 앱 CPU | 12~27% |

**DB 가 병목일 때 앱 CPU 는 낮다.** 앱은 대부분 기다린다. 이 그림을 보고 앱을 늘리면
아무것도 나아지지 않는다.

## 2단계. DB Scale-Up

`docker update --cpus 4 ex-pg`. 재기동 없다. 같은 부하로 대조했다.

| 지표 | 1단계 | 2단계 | 변화 |
|---|---|---|---|
| 주문 접수 | 16.2/s | **76.3/s** | **4.7 배** |
| 429 거절 | 83.8/s | 23.7/s | 1/3.5 |
| 주문 p95 | 802ms | **99.5ms** | **8 배 빠름** |
| 앱 CPU | 12~27% | 40~48% | 오른다 |

**DB 를 풀자 앱 CPU 가 오른다.** 병목이 앱으로 옮겨 온 것이고 그때부터가 ASG 의 자리다.
순서가 중요하다. DB 가 막힌 상태에서 앱을 늘리면 늘린 만큼 같이 기다린다.

## 3단계. Scale-Out 2 -> 3

조회 부하를 넣어 앱 CPU 를 임계 위로 올렸다.

| 시점 | 사건 | 값 |
|---|---|---|
| t+18.4s | 임계 초과 시작 | 평균 CPU 99.8% |
| t+48.7s | 지속 조건 충족 | **31.3 초** 연속 (설정 30 초) |
| t+49.9s | 컨테이너 생성 | **+1.0 초** |
| t+64.7s | 헬스 통과 | **+15.8 초** |
| t+65.9s | LB 등록 완료 | **+17.0 초** |

2 회차는 컨테이너 1.1 초, 헬스 16.9 초, 등록 **18.2 초**로 같은 값이다.

**대부분이 앱 부팅이다.** 컨테이너 생성 1 초와 LB 투입 1.3 초는 무시할 만하다.
2026-09-07 회차의 8.8 초보다 느린 이유는 노드를 2 vCPU 에서 1 vCPU 로 낮췄기 때문이다.
Spring 기동은 CPU 에 비례한다.

실제 오토스케일링은 여기에 두 가지가 더 붙는다. 임계 초과에서 알람 발화까지 1~2 분,
클라우드 인스턴스 프로비저닝은 **미측정**이다. 로컬에서 잴 수 없다.

## 4단계. 강제 종료와 자동 복구

`docker kill ex-app2` 를 부하 중에 넣었다. 3 회 반복했다.

| 항목 | 1회 | 2회 | 3회 |
|---|---|---|---|
| 헬스 실패 감지 | **9.5 초** | 15.5 초 | 14.5 초 |
| 복구 완료 | **18.9 초** | 16.9 초 | 18.5 초 |

감지는 헬스체크 연속 2 회 실패 기준이고 폴링 간격이 3 초이므로 최소 6 초 최대 12 초 안에
든다. 1 회차 9.5 초가 그 범위다. 2~3 회차가 긴 것은 그 시점에 컨트롤러가 다른 조치
중이었기 때문이다.

### 서비스는 지속됐다

| 축 | 값 |
|---|---|
| 앱이 낸 5xx (500·502·503) | **0 건** |
| LB `no live upstreams` (종료 창 3 회 전부) | **0 건** |
| 종료 순간 끊긴 진행 중 연결 | 84 건 (1 초 구간) |
| k6 조회 요청 | 194,253 건, 2,772/s |
| k6 실패율 | 17.2% |

**17.2% 는 5xx 가 아니라 429 다.** 리더의 상태코드 누적이 200 이 1,837,493, 429 가 30,417,
500·502·503 이 전부 0 이다. 429 는 앱의 IP 레이트리밋이 낸 부하 차단이고 노드 사망과 무관하다.
이 회차에서 레이트리밋을 풀지 않은 것이 측정 설계의 결함이다. 다음 회차에서는
`exchange.public.rate-limit.capacity` 를 풀고 다시 잰다.

종료 순간의 84 건은 그 노드에 이미 실려 있던 요청이다. nginx 가 `proxy_next_upstream` 으로
다른 노드에 재시도하므로 오류 로그에 남는 것이 곧 클라이언트 실패는 아니다.
**클라이언트가 실제로 본 5xx 는 0 이다.**

## 5단계. Scale-In 3 -> 2

부하를 끄고 기다렸다.

| 시점 | 사건 | 값 |
|---|---|---|
| t+0 | 부하 종료 | |
| t+90s | 지속 조건 충족 | CPU 30% 이하 **90 초** |
| | 드레이닝 시작 | `down` 표시 + reload |
| | 드레이닝 창 | **15 초** |
| | 컨테이너 정지 | |
| | 완료 | **17.0 초** |

2 회차도 **17.0 초**로 같다.

**드레이닝은 2 단계여야 한다.** `down` 을 붙여 reload 하면 새 요청이 그 노드로 가지 않고
진행 중 요청은 옛 워커가 마저 처리한다. 그 창이 끝난 뒤에 컨테이너를 내린다. 한 번에 지우고
바로 정지시키면 옛 워커가 아직 그 노드의 응답을 기다리는 중일 수 있다.

## 이 회차가 새로 확인한 것

### resolve 가 없으면 로드밸런서가 기동하지 못한다

ASG 는 노드가 오간다. 그 상태에서 nginx 는 기동 시점에 업스트림 이름을 풀고 실패하면
통째로 뜨지 않는다. 같은 설정을 이름 하나만 없는 호스트로 두고 A/B 했다.

| upstream 지시자 | `nginx -t` |
|---|---|
| `server ex-nonexistent:8080 resolve max_fails=1 fail_timeout=2s;` | **통과** |
| `server ex-nonexistent:8080 max_fails=1 fail_timeout=2s;` | `[emerg] host not found in upstream` |

`resolve` 는 `zone` 과 `resolver` 가 짝이다. 실제 회차에서도 ex-app3 가 생기기 전
`ex-app3 could not be resolved (3: Host not found)` 를 15 초마다 남기면서 nginx 는 계속 돌았다.

**정본 6.11 에 2026-09-08 에 적은 "앱 노드 둘이 선 뒤에 엣지를 올린다" 는 제약은 `resolve` 를
쓰지 않을 때만 참이다.** 그 절과 `deploy/nginx-edge.conf.template` 을 함께 고쳐야 한다.

### max_fails=1 이 스스로 전면 장애를 만든다

이 회차에서 가장 값비싼 발견이다. 강제 종료 구간이 아니라 **부하기를 3 대로 늘려 호스트를
과구독시킨 구간**에서 나왔다.

| 구간 | 조건 | `no live upstreams` |
|---|---|---|
| 01:12:32 ~ 01:14 | 부하기 3 대. 12 코어 호스트에 LB 6 + 앱 4 + DB 4 + 부하기 | **2,788,607 건** |
| 01:19 종료 창 | 부하기 1 대 | 0 건 |
| 01:25 종료 창 | 부하기 1 대 | 0 건 |
| 01:29 종료 창 | 부하기 1 대 | 0 건 |

같은 창의 로그 279 만 줄 중 99.9% 가 이 오류다. 곧 **로드밸런서가 모든 요청에 502 를 냈다.**

원인은 업스트림 설정이다. `max_fails=1 fail_timeout=2s` 는 실패 한 번에 그 노드를 2 초간
빼 버린다. 호스트가 과구독되면 두 노드가 거의 동시에 느려지고, 그러면 **둘 다 빠져 살아 있는
업스트림이 0 이 된다.** 노드는 멀쩡히 떠 있는데 로드밸런서가 전부 거절한다.

이 설정은 2026-09-07 회차에서 "죽은 노드를 빨리 빼려고" 넣은 값이고, 그때는 노드를 실제로
죽이는 시험이라 부작용이 드러나지 않았다. 부하가 노드를 동시에 느리게 만드는 상황에서는
같은 값이 정반대로 작동한다.

정정안은 재지 않았다. 후보는 `max_fails` 를 2 이상으로 올리는 것, `fail_timeout` 을 줄이는 것,
그리고 nginx OSS 에는 없는 능동 헬스체크를 ASG 컨트롤러의 헬스 판정으로 대신하는 것이다.
**어느 쪽도 이 회차에서 검증하지 않았으므로 값을 바꾸기 전에 재야 한다.**

### 로드밸런서가 앱보다 먼저 포화한다

조회 부하를 올리는데 앱 CPU 가 21% 에서 더 오르지 않았다. 원인은 nginx 였다. 2 vCPU 상한에
177% 로 붙어 있었고 그것이 처리량을 정하고 있었다.

2026-09-07 에 호가를 엔진 메모리에서 서빙하면서 조회가 싸졌다. 그래서 이 스택에서는
**조회 경로의 비용 중심이 앱이 아니라 프록시로 옮겨 갔다.** AWS ALB 는 관리형이라 이 한계가
없으므로 시험 장비 쪽을 6 vCPU 로 올려 계속했다.

같은 이유로 앱 노드를 2 vCPU 에서 1 vCPU 로 낮췄다. 2 vCPU 에서 60% 임계에 닿으려면 노드당
약 6,400 req/s 가 필요한데 12 코어 호스트에서 부하기와 프록시가 그 자원을 함께 쓴다.
t4g.small 의 지속 기저가 0.40 vCPU 이므로 1 vCPU 는 그 2.5 배이고, 임계는 할당량 대비라
판정 로직이 바뀌지 않는다.

### 컨트롤러 결함 둘을 이 회차에서 잡았다

- **Min 이 아니라 Desired 를 지켜야 한다.** 처음에는 최소 대수 미만일 때만 복구하도록 짰다.
  그러면 3 대에서 1 대가 죽어도 2 대가 최소 이상이라 교체가 걸리지 않는다. AWS ASG 는
  Desired 를 유지한다. 스케일링 정책이 Desired 를 움직이고 그 사이에는 그 수를 지킨다.
- **헬스 대기를 반복 횟수로 세면 안 된다.** 죽은 노드는 매 회 연결 타임아웃을 다 쓰므로
  "120 회 x 0.5 초" 가 60 초가 아니라 300 초가 된다. 실제로 그 버그로 컨트롤러가 판정을
  4 분간 멈췄다. 벽시계로 끊도록 고쳤다.

## 한계

- **클라우드 실측이 아니다.** EC2 Auto Scaling group 을 쓴 것이 아니라 같은 판정 규칙을
  로컬 도커에 얹었다. 인스턴스 프로비저닝 시간, 쿨다운 뒤 예열, AZ 균형 재조정은 들어 있지 않다.
- **RDS 를 쓰지 않았다.** 참조 아키텍처는 RDS Multi-AZ 를 적지만 정본 6.2 가 RDS 를 기각한다.
  장애를 주입할 권한이 없는 계층은 증명 대상에서 빠지기 때문이다. DB 는 자체 운영
  PostgreSQL 그대로 뒀다.
- **레이트리밋을 풀지 않아 k6 실패율이 오염됐다.** 5xx 가 0 인 것은 앱 카운터로 확인했으나,
  클라이언트 관점의 실패율은 이 회차 숫자로 인용하면 안 된다.
- **리더를 죽이는 회차는 하지 않았다.** 조회 노드만 죽였다. 리더를 죽이면 쓰기가 멈추고
  자동 승격이 필요한데, 그 축은 정본 13.1 한계 30 이 여전히 미관측으로 두고 있다.
- **시간을 압축했다.** 임계 지속을 1/6 로 줄였다. 운영값 그대로의 회차는 아직 없다.
- 앱 노드 1 vCPU 는 상시면 규격(t4g.small 2 vCPU)이 아니다. 판정 로직 검증용 규격이다.
- **`max_fails` 정정안은 미측정이다.** 위 전면 장애의 원인은 확인했으나 고친 값으로 다시 재지
  않았다. 그 전까지 이 업스트림 설정을 배포 경로로 승격하지 않는다.
- 호스트가 12 코어다. 부하기와 프록시와 앱과 DB 가 그 안에서 경쟁하므로 절대 처리량은
  이 회차의 판정 대상이 아니다. 재는 것은 컨트롤러의 판정과 조치 소요다.
