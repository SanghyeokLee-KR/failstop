## V28-2 주기 갱신과 엔진 방어선 (채택)

전용 데몬 스레드가 1초마다 카탈로그 전량을 다시 읽어 스냅샷을 통째로 교체한다. 카탈로그가
12마켓 13자산이고 전량 조회가 평균 0.1296ms 최대 0.1473ms(20회 반복)라 초당 0.13ms 다.

`EngineBridge.submit` 이 저널 append 직전에 로컬 스냅샷으로 정지 여부를 본다. 정지 반영이
최대 5초에서 1초로 줄었다.

측정 도중 결함을 하나 냈다. 미스 재적재를 `byId` 에도 걸었더니 DB 총 시간이 69,923 에서
84,325ms 로 올랐고 두 회차에서 재현됐다. `byId` 는 `MarketDataPublisher` 가 이벤트마다,
`EngineBridge` 가 `submitLock` 안에서 부르는 경로다. `reserve_funds` 평균이 1.523 에서
2.135ms 로 올랐는데 내부 SQL 은 그대로여서 함수가 자기 SQL 밖에서 기다린 것이 드러났다.
`byId` 를 스냅샷 전용으로 되돌려 70,339ms 로 복귀했다.

## V28-3 원가 프로젝션 조기 종료 (폐기)

`apply_position_cost` 는 호출 13,099 중 루프 본문이 102 회(0.78%)만 돈다. 나머지는 드라이빙
쿼리 값만 치른다. 그 앞에 결과 집합과 동치인 `EXISTS` 를 두어 무효 호출을 걷으려 했다.

드라이빙 쿼리는 13,099 에서 101 회로 줄었다. 그런데 `EXISTS` 자체가 회당 0.3221ms 로 원래
드라이빙 쿼리 0.2691ms 보다 비쌌다. `HAVING` 이 붙은 `EXISTS` 는 그룹핑을 끝내야 판정되므로
조기 종료가 성립하지 않는다. 같은 일을 한 번 더 시킨 셈이고 12,509 회에 4,030ms 를 더 썼다.

## V28-4 견적 자산 전용 거래의 호출 제거 (폐기)

`pg_stat_statements` 차분으로는 함수 오버헤드가 64% 로 보였으나 직렬 벤치마크 3,000회가 그
귀속을 뒤집었다. 함수 전체 0.5192ms, 드라이빙 쿼리만 0.4794ms, 빈 함수 호출 0.0010ms 다.
비용의 92% 가 드라이빙 쿼리이고 호출 오버헤드는 무시할 수 있다.

그래서 SQL 안에서 거르는 대신 `post_ledger_transaction` 이 부르지 않게 했다. 판정은 입력
JSONB 의 `asset_id` 와 `cost_quote_assets` 만 본다. 드라이빙 쿼리의 최종 필터가 비견적 자산만
남기므로 분개가 전부 견적 자산이면 결과가 반드시 빈다.

| 항목 | V28-2 | V28-4 |
|---|---:|---:|
| `apply_position_cost` 호출 | 14,582 | 6,446 |
| `apply_position_cost` 시간 | 9,745ms | 5,013ms |
| DB 총 시간 | 72,339ms | 64,669ms |
| TPS | 120.7 | 106.4 |
| p95 | 113.3ms | 129.8ms |

**의도는 그대로 됐다.** 호출이 55.8% 줄고 DB 시간이 10.6% 줄었다. 그런데 TPS 가 11.9% 내려갔다.

## 두 폐기가 함께 가리키는 것

DB 일을 줄였는데 처리량이 준다. 이 구성에서 DB 는 병목이 아니다.

| 단계 | DB CPU 평균 | 앱 CPU 평균 | 앱 CPU 최대 | 풀 pending |
|---|---:|---:|---:|---:|
| V28-2 | 42.6% | 51.8% | 206% | 0 |
| V28-3 | 41.6% | 56.5% | 202% | 0 |
| V28-4 | 42.5% | 56.5% | 202% | 0 |

앱이 2 vCPU 상한인 200% 를 치고 DB 는 42% 에 머문다. 곧 이 구성의 천장은 앱 CPU 가 정한다.
DB 왕복을 줄이면 응답이 빨리 돌아와 앱에 일이 더 몰리고, 이미 포화한 앱에서는 그것이 이득으로
바뀌지 않는다.

TPS 가 유지가 아니라 하락한 이유는 이 회차가 가르지 않는다. 앱 CPU 평균이 51.8 에서 56.5% 로
오른 것과 같은 방향이나 인과는 미측정이다. 스레드 덤프로 어느 스레드가 그 CPU 를 쓰는지 재는
것이 다음 작업이다.

## 다음 병목

DB 단독 최적화로는 이 구성의 TPS 가 오르지 않는다. 남은 축은 둘이다.

- 앱 CPU 자체를 줄인다. 24회차 스레드 덤프에서 요청 파싱·서명 검증·JSON·JDBC 가 67.8% 이고
  매칭은 6% 였다. 그 비중이 지금도 같은지 다시 재야 한다.
- 앱을 늘린다. 조회는 로드밸런서로 갈리지만(27회차, 09-05 회차) 주문은 단일 라이터라 갈리지
  않는다.
