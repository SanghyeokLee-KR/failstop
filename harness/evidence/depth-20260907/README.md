# 호가 집계 비용 절감 (2026-09-07)

증거 `counter-20260907` 이 우연히 드러낸 표적이다. 채번을 37 배 싸게 만들었는데 종단 처리량이
오르지 않았고, 원인이 호가 집계였다.

## 무엇이 문제였나

호가 응답은 두 쿼리로 만든다.

| 쿼리 | 무엇 | 종전 건당 | 종전 누적 |
|---|---|---|---|
| `SELECT price, SUM(remaining_qty) ... GROUP BY price LIMIT 15` | 15 단 호가창 | 12.8ms | 29278ms |
| `SELECT COALESCE(SUM(remaining_qty),0) ...` | 총 잔량 요약 | **25.0ms** | **137167ms** |

둘을 합치면 166445ms 다. 같은 창의 쓰기 경로(`reserve_funds` 30072ms + 원장 25421ms)의 3 배다.
**화면이 쓰기보다 DB 를 더 먹는다.**

비싼 쪽이 요약 숫자라는 것이 핵심이다. 15 단은 `LIMIT 15` 라 상위만 보면 되지만, 총 잔량은 그
마켓·방향의 미체결 전체를 더한다. 측정 시점에 한 방향이 87746 건이었다.

실행 계획은 이미 최적이다.

```
Aggregate (actual time=21.111..21.112 rows=1 loops=1)
  ->  Index Only Scan using idx_orderbook_open on orders (actual rows=87746)
        Index Cond: ((market_id = 1) AND (side = 'BUY'))
        Heap Fetches: 11200
```

인덱스 전용 스캔이고 인덱스도 이미 부분 인덱스다. **쿼리로 더 줄일 여지가 없다.** 남은 축은
얼마나 자주 다시 세느냐뿐이다.

## 무엇을 바꿨나

15 단과 총 잔량의 캐시 TTL 을 갈랐다. 15 단은 1 초를 유지하고 총 잔량은 5 초로 늘렸다.

갈라도 되는 근거.

- **매칭·주문 검증·정산은 이 값을 쓰지 않는다.** 매칭 엔진은 자기 메모리 호가창을 쓴다. 이
  쿼리를 쓰는 곳은 `MarketController`(REST)와 `MarketDataPublisher`(WS) 뿐이다.
- **계약이 총 잔량의 신선도를 규정하지 않는다.** API 설계 §4-A-2 는 `total_ask_size`·
  `total_bid_size` 를 응답 예시에 적을 뿐 갱신 주기를 말하지 않는다.
- 15 단은 사용자가 보고 주문을 내는 값이라 신선해야 한다. 총 잔량은 화면 위쪽 요약 숫자다.
  미체결 8 만 건 규모에서 1 초 동안의 체결·취소가 총량을 바꾸는 폭은 소수점 아래다.

## 결과 (명령당 정규화)

| 지표 | 종전 | 현행 | 변화 |
|---|---|---|---|
| 총 잔량 호출 | 0.42 회/명령 | **0.039 회/명령** | 11 배 감소 |
| 총 잔량 DB 시간 | 10.56 ms/명령 | **3.68 ms/명령** | **65% 감소** |
| 15 단 DB 시간 | 2.25 ms/명령 | 1.12 ms/명령 | |
| **호가 합계** | **12.81 ms/명령** | **4.80 ms/명령** | **62% 감소** |
| DB CPU | 132~146% | **87.2%** | |
| 주문 처리 | 70.5~71.2/s | **74.7/s** | |

TTL 을 5 배로 늘렸는데 호출이 11 배 준 이유는 종전 창의 호출 빈도가 캐시 하한보다 높았기
때문이다. 하한이 초당 6 회에서 초당 1.2 회로 내려갔다.

## 이 회차가 말하지 않는 것

- **15 단의 TTL 은 바꾸지 않았다.** 표의 15 단 감소는 두 창의 부하 타이밍 차이지 이번 변경의
  효과가 아니다.
- 주문 처리량 74.7/s 는 종전 창(70.5~71.2/s)보다 높지만, 두 창 사이에 `orders` 가 계속 자라고
  있어 깨끗한 전후 대조가 아니다. 확정한 것은 호가 쿼리의 명령당 비용이다.
- 5 초라는 값을 실측으로 고르지 않았다. 미체결 규모에서 유도한 판단이다. 더 큰 값이 더 나은지는
  재지 않았다.

## 남은 위험과 다음 표적

- **근본은 미체결 누적이다.** 87746 건이 쌓여 있어서 한 번의 집계가 25ms 다. 실서비스는 취소·
  체결로 정리되지만 부하 시험은 쌓기만 한다. ADR 0013 이 잔여 주문이 천장을 2.2 배 흔든다고
  이미 등재했고, 이번 측정이 그 구간에 들어갔다. 캐시는 증상을 덮을 뿐 원인을 없애지 않는다.
- **읽기 노드를 늘리면 이 비용이 곱해진다.** 캐시가 노드마다 따로라 노드 수만큼 DB 조회가 는다.
  시나리오 4 단계에서 노드를 하나 붙였을 때 DB CPU 가 110% 에서 205% 로 오른 것이 이 경로다.
  조회 확장과 DB 부하가 이 지점에서 맞선다.
- 다음 표적은 캐시가 아니라 **미체결 정리**이거나, 노드마다 따로 도는 캐시를 공유로 바꾸는 것이다.
