# 증설 소요 시간과 커넥션 풀 실사용 (2026-09-07)

증거 `scenario-20260907` 이 "오토스케일링 자체는 재지 않았다. 노드를 사람이 붙였다" 를 남겼다.
그 구간을 잰다.

## 증설 타임라인 (실측)

노드를 새로 띄워 로드밸런서에 넣기까지다.

| 시각 | 사건 | 누적 |
|---|---|---|
| t0 | 증설 결정 | 0 |
| t1 | 컨테이너 생성 완료 | **+0.7 초** |
| t2 | 새 노드가 조회에 응답 시작 | **+8.8 초** |
| t3 | 로드밸런서 투입 완료(reload) | **+9.2 초** |

Spring 기동 로그는 `Started ExchangeApplication in 7.083 seconds` 다. **8.8 초의 대부분이 앱
부팅이다.** 컨테이너 생성(0.7 초)과 LB 투입(0.4 초)은 무시할 만하다.

## 앞뒤에 붙는 것

위는 우리가 통제하는 구간이고 실제 오토스케일링은 앞에 두 가지가 더 붙는다.

| 구간 | 값 | 근거 |
|---|---|---|
| 임계 초과 -> 알람 발화 | **1~2 분** | 규칙의 `for` 지속. 아래 표 |
| 클라우드 인스턴스 프로비저닝 | **미측정** | 로컬에서 잴 수 없다 |
| **앱 기동 + LB 투입** | **9.2 초** | 위 실측 |

현행 알람 규칙의 `for` 지속이다. 증설 판단에 쓸 만한 축만 옮긴다.

| 알람 | for |
|---|---|
| `OrderRejectSpike` | 2m |
| `OrderP99SloBreach` | 2m |
| `SequencerQueueBackpressure` | 1m |
| `WsConnectionsNearLimit` | 2m |

**우리가 줄일 수 있는 것은 9.2 초뿐이고 나머지는 알람 창과 클라우드가 정한다.** 알람 창을
줄이면 순간 스파이크에 증설이 발동해 비용이 튄다. 그 균형이 정책 문제이지 구현 문제가 아니다.

## 증설 경로에서 걸린 함정 둘

- **nginx 는 기동 시 upstream 호스트를 해석하고 없으면 기동을 거부한다.** 2 번 노드가 없는
  상태에서 LB 를 세우려다 `host not found in upstream "ex-app2:8080"` 로 기동에 실패했다.
  오토스케일링은 노드가 오갈 때마다 이 문제를 만난다. 정본
  `deploy/nginx-edge.conf.template` 이 리더 upstream 을 별도 파일로 빼고 사이드카가 갱신하도록
  한 이유가 이것이다.
- **upstream 이름에 밑줄을 쓰면 Tomcat 이 400 을 낸다.** `proxy_set_header Host` 를 빠뜨리면
  nginx 가 upstream 이름(`exchange_read`)을 Host 로 보내는데, 밑줄은 호스트명으로 유효하지
  않아 거부된다. 프록시 설정에서 Host 를 명시해야 한다.

## 커넥션 풀 실사용

천장을 두 배 넘긴 부하(200 OPS)에서 추적했다.

| 지표 | 값 |
|---|---|
| 풀 상한 | 16 |
| 실제 생성된 커넥션 | **8** |
| 동시 사용 최대 | **3** |
| 획득 대기 | **0** (전 구간) |

**천장의 두 배를 걸어도 커넥션 3 개면 된다.** HikariCP 가 상한 16 중 8 개만 만들었고 그중
최대 3 개가 동시에 쓰였다. 기다린 요청은 없다.

### 왜 이렇게 적게 쓰나

요청은 자기 수명 내내 커넥션을 쥐지 않는다. 필요할 때 빌리고 즉시 돌려준다. 주문 경로는
시간의 큰 몫을 프로젝션 반영 신호를 기다리는 데 쓰고 그동안 커넥션을 들지 않는다.

### 그래서 풀을 줄여도 되는가. 안 된다

**풀 크기가 수용 정원의 입력이다.** `AdmissionLimits` 가 풀에서 유도한다.

```
주문 정원 = 풀 x 0.40 = 16 x 0.40 = 6
조회 정원 = 풀 x 0.40 = 6
재조회 정원 = 풀 x 0.10 = 2
```

풀을 실사용(3)에 맞춰 줄이면 정원이 하한(4·2)으로 내려가 처리량이 떨어진다. 둘이 묶여 있어
따로 조일 수 없다.

### 그 유도가 가정하는 것과 실측의 어긋남

유도는 "동시 처리 중인 요청 하나가 커넥션 하나를 쥔다" 를 가정한다. 실측은 다르다.

| | 값 |
|---|---|
| 주문 정원 in-flight | **6/6 (포화)** |
| 같은 순간 커넥션 사용 | **3** |

**정원이 꽉 찬 순간에도 커넥션은 절반만 쓴다.** 유도가 보수적이라는 뜻이고, 그래서 정원을
풀에서 유도하는 한 커넥션은 항상 남는다.

풀을 48 로 올려 정원을 19 로 만들어 본 구간에서도 커넥션은 2 개만 쓰였고 처리량은 오르지
않았다(증거 `scenario-20260907` 5 단계). **정원이 커져도 단일 라이터가 천장이라 늘지 않는다.**

### 제대로 잡는 법

1. **풀은 실측 피크에 여유를 더해 잡는다.** 여기서는 최대 3 이므로 8~16 이면 충분하고 현재
   설정이 이미 그 범위다. 유휴 커넥션의 비용은 작다.
2. **정원은 풀이 아니라 실측으로 잡아야 한다.** 지금은 풀에서 유도하므로 풀을 건드리면 정원이
   함께 움직인다. 다만 정원을 키워도 처리량이 안 오르는 것을 이미 쟀으므로, 이 분리는 지금
   이득이 없다. 단일 라이터 처리율이 오른 뒤에 의미가 생긴다.
3. **지금 손댈 이유가 없다.** 대기 0, 여유 충분, 정원을 키워도 이득 없음이 모두 실측이다.

## 남은 위험

- 증설 타임라인을 한 번만 쟀다.
- 클라우드 프로비저닝 시간은 측정하지 않았다. 로컬에서 잴 수 없다.
- 커넥션 사용량을 6 초 간격 표본으로 봤다. 그 사이의 더 높은 순간 피크를 놓쳤을 수 있다.
- 조회 부하가 더 크면 조회 정원 쪽 커넥션 사용이 달라질 수 있다. 이번은 주문 위주 부하다.
