# 읽기 노드의 DB 부담 실측과 캐시 몰림 제거 (2026-09-07)

다음 후보는 조회 전용 노드에 호가창을 전파하는 것이었다. 정본이 공개 `/topic/**` 을 Redis
Pub/Sub 릴레이로 잡아 두었으므로(API 설계 §5-1) 그 위에 얹는 그림이었다.

**넣기 전에 얼마나 필요한지 쟀다.**

## 왜 재고 시작했나

시나리오 4 단계에서 노드를 하나 붙였을 때 DB CPU 가 110% 에서 205% 로 올랐다. 캐시가 노드마다
따로라 조회 확장이 DB 부하를 곱한다는 관찰이었다.

그러나 그 측정은 호가 캐시 분리(`depth-20260907`)와 메모리 서빙(`inmemory-depth-20260907`)
이전이다. 두 변경 뒤에는 상황이 다를 수 있다.

## 실측. 읽기 노드 하나가 DB 에 얼마나 쓰나

조회 전용 노드(`exchange.engine.enabled=false`)에만 조회 부하를 걸었다. 90 초, 고정 VU 250.

| 항목 | 값 |
|---|---|
| 노드가 처리한 조회 | **7684 req/s** |
| 그 노드 CPU | 137.8% |
| 호가 쿼리 | 974 회 / **4225ms** |
| **초당 DB 시간** | **47ms** |

**읽기 노드 하나가 초당 7684 건을 내면서 DB 에 초당 47ms 를 쓴다.** 같은 창의 DB CPU 67.2% 는
대부분 봇의 쓰기다.

### 판정

Redis 릴레이를 넣는 대가는 새 의존성, 정본 M2 개정, 장애 경로 추가다. 얻는 것은 초당 47ms 다.
**지금 데이터로는 정당화되지 않는다.** 4 단계의 관찰은 앞선 두 변경으로 이미 해소됐다.

정본의 Redis 릴레이 계획 자체를 부정하는 것은 아니다. 그 계획은 WS 팬아웃(공개 토픽의 노드 간
브로드캐스트)을 위한 것이고 이 실측이 다룬 REST 조회와 목적이 다르다. 다중 노드 WS 가 필요해질
때 그 축에서 다시 판단한다.

## 대신 진짜 잔여를 찾았다. 캐시 몰림

호가 15 단 캐시는 TTL 1 초다. 1 마켓 두 면이면 초당 2 회여야 하는데 실측이 초당 10.8 회였다.
**5.4 배가 몰림이다.**

TTL 이 만료되는 순간 동시 요청이 전부 캐시 부재를 보고 저마다 DB 를 친다. 종전 구현은 만료를
본 스레드가 각자 loader 를 돌렸다. 부하가 셀수록, TTL 이 짧을수록 배수가 커진다.

키마다 채움 잠금을 두어 한 스레드만 DB 를 치고 나머지는 그 결과를 기다리게 했다.

| 지표 | 종전 | 단일 채움 |
|---|---|---|
| 호가 쿼리 호출 | 974 회 | **171 회** |
| DB 시간 | 4225ms | **438ms** |
| 초당 호출 | 10.8 회 | **1.9 회** |
| 처리한 조회 | 7684/s | 6958/s |

**5.7 배 줄었고 초당 1.9 회는 이론 상한 2 회와 맞는다.** 몰림이 사라졌다는 뜻이다.

기다린 쪽이 얻는 값은 방금 채운 값이라 최신이다. 잠금 구간이 DB 왕복 한 번이라 대기도 그만큼
이고, 몰림으로 왕복을 여러 번 하는 것보다 짧다.

## 남은 위험

- 조회 처리량이 7684 에서 6958 req/s 로 9% 낮게 나왔다. 잠금 대기 때문일 수도 있고 두 창의
  봇 부하 차이일 수도 있다. 가르지 않았다.
- 응답 지연 최대값이 305ms 에서 1.61s 로 늘었다. 채움을 기다리는 요청이 생기기 때문이다.
  중앙값(13.4 -> 14.6ms)과 p95(91.3 -> 96.8ms)는 거의 같아 꼬리에만 나타난다. 그 꼬리가
  허용 범위인지는 SLO 로 판정해야 하고 이번에 하지 않았다.
- 리더 노드는 호가를 메모리에서 내므로 이 캐시를 쓰지 않는다. 이 측정은 조회 전용 노드 한정이다.
- 한 번씩만 쟀다.
