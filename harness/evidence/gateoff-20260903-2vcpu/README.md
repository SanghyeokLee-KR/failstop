# 게이트 OFF 2 vCPU 실측 (2026-09-03)

전날 실측(`../gateoff-20260902/`)은 12코어 워크스테이션에서 쟀다. 배포 대상은 2 vCPU 인스턴스다.
가상 스레드 캐리어 수가 `Runtime.availableProcessors()` 라서 코어 수는 이 장애의 임계에 직접 걸린다.
그래서 코어 수만 바꾸고 나머지를 고정해 다시 쟀다.

## 조건

전날과 같은 것: jar, 프로파일(dev·bots), 요청 풀 16, connection-timeout 3000ms, JDK 21.0.12,
격리 Postgres 17(5433), 봇 3마켓, k6 demo 프로파일(주문 10/s, 조회 17/s, WS 300 VU, 폭주 100 OPS),
게이트 OFF.

바꾼 것 하나: `-XX:ActiveProcessorCount=2` 와 프로세서 어피니티 2코어(마스크 0x3).
기동 뒤 `jcmd Thread.print` 로 `ForkJoinPool-1-worker` 가 2개임을 확인했다(전날은 12개).

CPU 백분율 단위. `jvm_cpu_1core_pct` 는 1코어=100% 다. 2 vCPU 인스턴스 기준 사용률은 그 절반이다.
`vcpu_pct` 열은 전 행 무효다(PS 5.1 형변환 결함). 인용하지 않는다. 판단에는 `jvm_cpu_1core_pct / 2` 를 쓰고, 그 나눗셈은 계측기가 아니라 수기 계산이다. 측정 기계도 t4g.small 실물이 아니라 어피니티로 2코어에 묶은 12코어 워크스테이션이다.

## 결과

### 1. 2 vCPU 에서는 폭주가 아니라 기저 부하에서 죽는다

접수 ACK 5건, DB 주문 21건. k6 시작 15초 뒤가 마지막 접수다. 100 OPS 구간에 도달하지 못했다.
전날 12코어는 게이트를 끈 뒤 같은 기저를 최소 93초 견디고(20:50:54 게이트 OFF, 20:52:27 폭주 램프) 폭주 8초 만에 죽었다. 93초는 관측된 하한이지 정상 상태의 증명이 아니다. 코드도 부하도 같고 코어 수만 다르다.

기저 부하에는 WS 300 VU 동시 접속이 들어 있다. 붕괴를 당긴 것이 주문율인지 WS 동시 접속인지는
이 주행이 가르지 못한다. 그 분리는 `run3`(WS 없는 캘리브레이션)이 한다.

### 2. CPU 는 이 장애를 가리키지 못한다

| 구간 | JVM CPU (1코어=100%) | 2 vCPU 인스턴스 사용률 |
|---|---|---|
| 붕괴 직전 | 112.7 | 56% |
| 붕괴 직후 | 19.4~54.9 | 10~27% |
| 정지 지속 | 92.6~105.8 | 46~53% |

정지 상태가 정상 상태보다 CPU 를 더 쓴다. 그리고 그 값은 건강한 중간 부하와 구별되지 않는다.
CPU 임계 알람(통상 70~80%, 2주기 지속)은 발화하지 않는다. 낮은 임계로 내려도 붕괴 직후
11~15% 구간에서 해제됐다가 다시 오르므로 지속 조건을 채우지 못한다.

### 3. 그 CPU 는 일이 아니다

`jcmd Thread.print` 로 OS 스레드 단위 CPU 를 귀속했다. 코어 하나를 태우는 것은 스레드 하나다.

```
"HikariPool-1:housekeeper" #26 [20804] daemon cpu=185140.62ms elapsed=333.16s runnable
   java.lang.Thread.State: RUNNABLE
	at java.lang.Thread.yield0(java.base@21.0.12/Native Method)
	at java.lang.Thread.yield(java.base@21.0.12/Thread.java:445)
	at com.zaxxer.hikari.util.ConcurrentBag.unreserve(ConcurrentBag.java:322)
	at com.zaxxer.hikari.pool.HikariPool$KeepaliveTask.run(HikariPool.java:887)
```

가동 333초 중 CPU 185초. 10초 창 측정에서 97.7~98.0%. HikariCP 킵얼라이브가 고갈된 풀에서
커넥션 상태 전이를 기다리며 `Thread.yield()` 로 헛돈다. 처리량 0 인데 CPU 는 반 코어를 넘는다.

### 4. 헬스체크는 응답하지 않는다. "초록 거짓말"은 이 주행이 재지 못했다

이 주행에서 readiness 200 표본은 0건이다. readiness 프로브를 09:21:52 에 시작했는데 붕괴가
09:21:28 이라 이미 늦었고, 첫 표본부터 전량 5초 타임아웃이다(`run2_readiness.csv`).

풀 고갈 중에 200 을 반환한 것은 `/actuator/prometheus` 다(09:21:24 표본, pending 154, active 16/16,
158ms). readiness 도 같은 커넥터 위에 있고 `readinessState` 만 포함하므로(`application.yml:36-37`)
같은 구간에 200 을 낼 수밖에 없는 구조이나, **그것은 코드에서 유도한 것이지 이 주행이 잰 것이
아니다.** "헬스체크가 초록인데 노드는 죽어 있다"를 실측으로 주장하려면 readiness 프로브를
부하 시작 전에 걸어 붕괴 창을 덮는 주행이 따로 필요하다.

측정된 것은 이것이다. 붕괴 이후 readiness 는 5초 타임아웃으로 영구 무응답이고, ALB 관점에서
이 대상은 unhealthy 로 빠진다.

### 5. 노드를 늘리면 기동을 거부당한다

정지 노드가 살아 있는 채로 같은 DB 에 두 번째 노드를 띄웠다.

```
WARN  kr.exchange.engine.EngineRecovery : 리더 승격 실패(유효한 타 리더 존재). 리스 만료 대기
ERROR o.s.boot.SpringApplication        : Application run failed
Caused by: java.lang.IllegalStateException:
    크래시 창 이벤트 8건 재적재 불가: 리더 승격 실패(대기 15000ms 소진)
```

readiness 는 그 전에 503 OUT_OF_SERVICE 였고, 15초 뒤 프로세스가 종료됐다.
정지 노드가 리더 리스를 계속 갱신하기 때문이다(epoch 1 불변, `lease_until` 이 항상 now 보다 앞).
`EngineRecovery` 는 이것을 기동 거부로 처리한다. 의도된 분기다(주석 참조).

크래시 창에 재적재할 이벤트가 있을 때의 거동이다. 이벤트가 0건인 경우는 이 주행이 재지 않았다.

### 6. 소켓은 단조 증가한다

서버측 CLOSE_WAIT 은 붕괴 4초 뒤(09:21:28) 1 로 시작해 관측 종료 시각 09:26:44 에 2686 까지 갔다
(1회차 12코어는 5107). 60초 구간 09:24:44~09:25:44 에 1264 에서 1975 로 늘었다. 다만 **단조는
아니다.** 325 에서 164, 565 에서 554 로 줄어드는 구간이 섞인다. 알람을 임계가 아니라 추세로
걸어야 하는 이유다.

ESTABLISHED 는 붕괴와 동시에 30 에서 754 로 뛰고 이후 222 까지 내려갔다가 09:23:44 부터
1424 근방에 고착된다. "전 구간 고정"이 아니라 그 시각 이후의 고착이다.
앱 지표가 죽은 뒤에도 밖에서 보이는 유일한 단조 신호다.

## 확정하지 못한 것

- 붕괴를 당긴 것이 주문율인지 WS 300 동시 접속인지 가르지 못했다.
- 크래시 창 이벤트가 0건일 때 두 번째 노드가 팔로워로 기동하는지 재지 않았다.
- 메모리는 이번 변수에서 뺐다(최대 힙 8.5GB 그대로). 2GB 인스턴스 모사는 별도 주행이 필요하다.
- 게이트 ON 상태의 같은 부하(429 흡수, 복구 시간)는 아직 재지 않았다.

### CPU 곡선. 최고점은 죽은 뒤에 온다

16 주문/s 주행의 5초 샘플이다. 괄호 안은 2 vCPU 인스턴스 사용률(측정값의 절반)이다.

|---|---|---|---|---|---|---|
| 09:39:06 | 16% | 0 | 10 | 0 | 200 | 정상 |
| 09:39:19 | 18% | 0 | 13 | 0 | 200 | 정상. 마지막 응답 |
| 09:39:25 | 16% | 판독 불가 | 판독 불가 | 1 | 무응답 | 정지 |
| 09:39:34 | 12% | 판독 불가 | 판독 불가 | 14 | 무응답 | 정지. CPU 최저 |
| 09:39:44 | 39% | 판독 불가 | 판독 불가 | 17 | 무응답 | 정지 |

셋을 읽는다. 죽기 직전 CPU 는 16~18% 다. 죽는 순간 12% 로 내려간다. 최고점 54% 는 정지 시작
28초 뒤에 온다. CPU 임계 알람은 이 장애를 예고하지 못하고, 발화한다면 끝난 장애를 뒤늦게 알린다.

pending 은 이 주행에서 경고를 주지 못했다. 마지막 정상 샘플의 pending 이 0 이고 그 다음 샘플이
판독 불가다. 5초 간격으로는 그 사이에 아무 값도 잡히지 않았다. 2회차(12코어)에서 한 샘플만
154 를 보인 것과 다르다. 앱 내부 지표는 이 인스턴스에서 더 빨리 죽는다.

정지 뒤 스레드 귀속은 2회차와 같다. `HikariPool-1:housekeeper` 가 `ConcurrentBag.unreserve` 의
`Thread.yield()` 루프에서 코어 하나를 태운다. 리더 리스도 계속 갱신됐다(epoch 1 불변, 유효).
두 주행이 같은 기전으로 재현됐다.

## 3회차가 2회차에 대해 알려주는 것

2회차는 주문 10/s + 조회 17/s + WS 300 VU 에서 죽었다. 3회차는 주문 12/s + 조회 20/s 를
WS 없이 견뎠다. 곧 2회차를 넘긴 것은 주문율이 아니라 WS 300 동시 접속이 더한 몫이다.
그 몫의 크기는 재지 않았다(WS 축 계단은 미실시).

## 부수 발견. 기동 중 하네스 키 발급이 기동을 죽인다

`POST /harness/v1/loadtest-keys` 를 봇 프로비저닝이 끝나기 전에 호출하면 GENESIS
`business_event_id` 채번이 충돌해 `botFleetLifecycle` 기동이 실패하고 애플리케이션이 죽는다.
2 vCPU 에서 재현했다(`Failed to start bean 'botFleetLifecycle'`,
`duplicate key value violates unique constraint "uq_ledger_business_event"`).
readiness 200 은 Tomcat 이 먼저 열려 조기 참이 되므로 기동 완료 판정에 쓸 수 없다.
로그의 `Started ExchangeApp` 를 기다린 뒤 호출해야 한다. 하네스 엔드포인트가 애플리케이션
기동을 막을 수 있다는 뜻이라 별도 등재 대상이다.

## 탐지. 이미 배선된 알람 기준

정본은 CloudWatch 를 기각하고 Prometheus·Grafana 자체 운영을 쓴다(기획안 338행). RDS 도 기각이고
DB 는 EC2 자체 운영 PostgreSQL 17 이다(333행·6.2). 앱 노드는 t4g.small 2 vCPU 이고 c7g.large 는
부하 발생기 전용이다(483·544·1304행). 아래는 `harness/prometheus/rules/exchange-alerts.yml` 의
기존 알람 11건을 이 실측에 대조한 결과다.

| 알람 | 조건 | 이 장애에서 | 판정 |
|---|---|---|---|
| LeaderAbsent | `absent(exchange_leader_is_leader == 1)` for 15s | 정지 노드가 스크레이프에 응답하지 못해 시계열이 소멸한다 | **발화. 정지 15~20초 뒤** |
| SequencerQueueBackpressure | `exchange:sequencer_queue:avg1m > 8192` for 1m | 죽기 직전 큐는 13~18 이다 | 미발화 |

스크레이프 간격은 핵심 잡 2초, 평가 간격 5초다(`harness/prometheus/prometheus.yml:2,13`).
Prometheus 는 팔로워 노드에서 돈다(기획안 486행)므로 리더가 죽어도 관측면은 산다.

두 가지가 남는다.

1. `LeaderAbsent` 의 설명이 "승격 지연·양쪽 스탠바이 의심"이다. 이 장애에서 리더는 부재하지 않는다.
   리스를 계속 갱신하는 좀비다. 문구를 따라가면 운영자는 승격을 기다리고 런북 §2 의 "리스 TTL
   만료 대기(10초 내)" 분기로 들어가 풀리지 않는 대기를 한다. 판별은 `leader_lease` 의
   `lease_until > now()` 한 줄이고, 그때의 조치는 대기가 아니라 정지 노드 재기동이다.
2. 선행 경보는 없다. 가장 이른 신호가 정지 15~20초 뒤다. 그 앞을 원하면 축을 새로 만들어야 하고
   후보는 `up{job="exchange"} == 0`(스크레이프 실패 자체)과 좀비 판별(`up == 0` 인데 리스 유효)이다.
   둘 다 미배선이다.

| 축 | 이 장애에서의 거동 | 리드타임 | 배선 |
|---|---|---|---|
| 앱 내부 지표 | `/actuator/prometheus` 가 09:21:24 를 마지막으로 죽는다. 업무면(마지막 접수 ACK)은 09:21:35 까지 살아 있다 | **-11초.** 관측면이 먼저 죽는다 | 배선됨 |
| `hikaricp_connections_pending` | 3회차에서 마지막 정상 표본 0, 다음 표본 판독 불가 | 사실상 0초 | 배선됨. 알람 없음 |
| `exchange_sequencer_queue_size` | 죽기 직전 13~18. 알람 임계는 8192 | 미발화 | 알람 있으나 임계 미달 |
| Prometheus `LeaderAbsent` | 스크레이프 실패로 시계열 소멸, `absent()` 발화 | 정지 +15~20초 | 배선됨 |
| `up{job="exchange"} == 0` | 스크레이프 실패 즉시 | 정지 +5~10초 | 미배선. 대시보드 패널만 |
| DB 호스트 CPU | 두 회차 모두 68% 에서 0.1% 미만으로 붕괴 | 정지와 동시 | **수집기 0건** |
| DB 직조회(`leader_lease` 전진 + `command_journal` 최대 seq 정지) | 좀비 리더를 유일하게 확정 판별한다. 앱이 죽어도 영구 관측 가능 | 상시 | 미배선 |
| 수용 게이트 지표(admission 3종) | 게이트를 켜도 그 방어가 도는지 볼 수 없다 | - | 대시보드·알람 모두 없음 |
| 봇 플릿 | 합성 트랜잭션 카나리아가 될 수 없다. 같은 JVM 이라 피검체와 함께 죽는다 | - | 해당 없음 |

두 가지가 이 표의 결론이다.

첫째, 앱 내부 지표는 이 장애에 쓸 수 없다. 리드타임이 음수다. 관측면이 업무면보다 11초 먼저
죽으므로 "지표가 급등하는 것을 보고 대응한다"는 순서 자체가 성립하지 않는다.

둘째, 앱 밖에서 영구히 답을 주는 축은 DB 직조회 하나다. `leader_lease.lease_until` 은 전진하는데
`command_journal` 최대 seq 가 전진하지 않으면 좀비 리더다. 이 조합이 이 장애의 유일한 확정
판별식이고 지금은 미배선이다. postgres_exporter 나 상시면 스캐너가 필요하다.

## 좀비 판정기가 발화하지 않는 이유는 버그가 아니라 설계된 사각이다

`LeaderStallDetector` 는 완료율이 낮으면 리더가 스스로 물러나게 하는 두 번째 방어다.
두 회차 모두 발화하지 않았다. 원인은 수요 축에 있다. 판정기의 `attempts` 가 `ApiAuthFilter`
진입부에서만 증가하는데, 전방 문(커넥터·수용 경로)이 막히면 요청이 그 지점에 도달하지 못한다.
그래서 `windowDemand` 가 임계 아래에 머물고 판정기는 "수요가 없으니 정상"으로 읽는다.

곧 이 방어는 노드가 요청을 받아들이면서 처리하지 못할 때만 작동하고, 요청을 아예 받지 못하게
되면 눈을 감는다. 이 장애는 후자다. 임계를 조정해서 될 일이 아니라 수요 축을 문 바깥
(커넥터 수용 수 또는 TCP accept 수)으로 옮겨야 하는 문제다.

## 재현성

이 주행의 절차 스크립트는 이 디렉터리에만 있고 `harness/scripts` 에 등재돼 있지 않다.
`stair.sh`(용량 계단), `sampler2.ps1`(5초 샘플러), `topthreads.ps1`(OS 스레드 CPU 귀속),
`readiness_probe.ps1`(ALB 조건 프로브)이 전부다. 기동 순서에 함정이 하나 있다.
`Started ExchangeApp` 를 기다린 뒤 30초를 더 두고 하네스 키를 발급해야 한다. 그 전에 부르면
기동이 죽는다. 정식 하네스 절차로 승격하려면 이 순서를 스크립트에 넣어야 한다.

## 7회차. 봇 노드 분리 실증 (2026-09-03 13:14~13:18)

봇 플릿을 거래소 본체에서 떼어 별도 프로세스로 돌렸다. 목적은 둘이다. 봇이 피검체와 함께
죽지 않게 해 합성 트랜잭션 감시를 성립시키는 것, 그리고 그 분리가 실제로 되는지 확인하는 것.

### 코드 변경이 필요 없었다

`exchange.engine.enabled` 가 이미 배선돼 있다. `EngineConfig` 의 `engineRuntimeLifecycle` 빈에
`@ConditionalOnProperty(prefix = "exchange.engine", name = "enabled", matchIfMissing = true)` 가
걸려 있고, 주석이 "봇 전용 노드는 엔진을 끄고 리더 경쟁에서 빠진다"고 적는다.
이 빈이 리스 시작·라이터 시작·부팅 복구를 하는 유일한 지점이므로, 이것만 꺼지면 노드는
리더 경쟁에 참가하지 않는다. 카오스 스택의 `chaos-bots` 서비스가 이미 이 값을 쓴다.

### 구성

| 노드 | 프로파일 | 엔진 | 기타 |
|---|---|---|---|
| 거래소 | `dev` | 켬 | 봇 프로파일 없음 |
| 봇 | `bots` | `exchange.engine.enabled=false` | `spring.flyway.enabled=false`, `exchange.sim.base-url` 로 거래소 지정 |

두 노드가 같은 DB 를 본다. 봇 노드의 DB 접속은 계정·키 시드와 제어 명령 수신용이고,
주문은 전부 HTTP 로 나간다(`BotApiClient`).

### 결과 (3분, 15초 간격 12표본)

| 항목 | 값 |
|---|---|
| 리스 소유자 | 전 표본 동일. epoch 1 불변, 유효 true |
| 봇 노드의 리스 경합 | 없음. 로그에 승격·리스 관련 행 0 |
| 주문 | 538 에서 3969. 초당 19.3건 |
| 체결 | 376 에서 2906. 초당 14.2건 |
| 거래소 노드 메모리 | 385~416 MB, OS 스레드 457~461 |
| 봇 노드 메모리 | 393~432 MB, OS 스레드 59~61 |

### 인스턴스 크기 판정

봇 노드가 정상 상태에서 약 430 MB 를 쓴다. t4g.nano 는 총 0.5 GiB 라 OS 를 빼면 들어가지 않는다.
정본 550행이 정한 512 MiB 제한에는 들어가나 여유가 84% 점유로 얇다.
독립 노드로 갈 경우 1 GiB 등급(t4g.micro) 이상이 필요하다.

### 마스터키를 공유하지 않으면 거래소가 강등된다

첫 시도에서 두 노드에 `EXCHANGE_AUTH_MASTER_KEY_BASE64` 를 주지 않았다. 그러면 각 프로세스가
서로 다른 임시 키를 쓰므로, 봇 노드가 발급·암호화한 API 시크릿을 거래소 노드가 복호화하지
못한다. 봇 주문이 전건 인증 실패로 끝나고, 거래소는 수요만 있고 완료가 0 인 상태가 된다.
45초 뒤 `LeaderStallDetector` 가 이것을 서비스 불능으로 판정해 리더십을 포기했다.

```
LeaderStallDetector : 리더 처리율 붕괴 관측 시작: 완료율 0.0000(0/36), 45초 더
LeaderStallDetector : 서비스 불능 지속 판정: 완료율 0.0000(0/108), 지속 45190ms
LeaderLeaseService  : 리더십 상실(재승격 금지, 복귀는 재기동)
HaAvailability      : readiness 전이: REFUSING_TRAFFIC
```

곧 **오설정된 봇 노드가 정상인 거래소를 죽인다.** 복구는 재기동뿐이다(재승격 금지).
두 노드가 같은 마스터키를 쓰는 것이 분리 배치의 전제 조건이다. 카오스 스택은 이미 두 서비스에
같은 `CHAOS_MASTER_KEY_BASE64` 를 주입한다.

### 분리가 거래소 부하를 줄이지는 않는다

봇 주문율이 동거 구성의 초당 9~12건에서 분리 뒤 초당 19.3건으로 올랐다. 봇이 CPU 를 다투지
않게 되어 더 빨리 주문을 던진 결과로 보인다. 곧 분리는 거래소가 받는 주문량을 줄이지 않고
오히려 늘릴 수 있다. 부하를 줄이려면 `exchange.sim.target-ops` 나 `requote-ms` 를 따로 조정해야
한다. 이 주행에서 그 조정은 하지 않았다.
