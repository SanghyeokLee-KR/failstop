# WS 동시 연결 수용 제어 실측 (2026-09-07)

증거 `gateoff-20260903-2vcpu` 31회차가 등재한 결함을 고치고 그 고침을 확인한다.

## 고치기 전에 무엇이 문제였나

`AdmissionFilter.shouldNotFilter` 가 `!uri.startsWith("/api/v1/")` 라 `/ws/v1` 핸드셰이크가
수용 제어를 통과했다. 주문과 조회는 정원이 차면 거절해 노드를 지키는데 WS 는 그 방어가 없어
오는 대로 받았다.

31회차 실측에서 컨테이너 1GB 노드에 3,500 연결을 걸면 2,702 연결에서 힙이 말라
`java.lang.OutOfMemoryError: Java heap space` 가 났고 `matching-engine-writer` 스레드까지 죽어
주문과 조회가 모두 멈췄다. 컨테이너는 Up 인데 거래소가 응답하지 않는 상태였다.

## 무엇을 고쳤나

동시 연결 상한을 최대 힙에서 유도하고(`WsConnectionLimit`), 상한을 넘는 연결을 종료 코드
1013(SERVICE_OVERLOAD)으로 즉시 닫는다(`WsConnectionLimitHandler`).

상한을 요청 수용 제어에 얹지 않은 이유는 수명이 다르기 때문이다. 요청 수용 제어는 요청 수명에
슬롯을 매어 두므로 핸드셰이크가 끝나는 순간 슬롯을 놓는다. 연결은 그 뒤로도 몇 시간을 산다.

유도 계수는 실측에서 옮겼다. 31회차에서 최대 힙 768MB 노드가 정상이었던 지점이 2,000 연결이라
힙 1MB당 2.6 연결로 둔다. 정본의 3,000 은 천장으로 유지한다.

## 환경

| 항목 | 값 |
|---|---|
| 앱 | 컨테이너 1GB, 2 vCPU, `MaxRAMPercentage 75` |
| 최대 힙 | 742MB |
| 유도된 상한 | **1929** (742 x 2.6) |
| DB | 컨테이너 4 vCPU / 4GB |
| 부하 | `harness/load/ws_capacity.js` |

기동 로그가 유도 결과를 남긴다.

```
INFO kr.exchange.config.ApiConfig : 수용 제한 상한 해석: WS 동시 연결 상한 1929 (최대 힙 742MB)
```

## 실측 1. 게이트 ON, 3,500 연결 (죽었던 지점)

45초 간격 관측이다.

| 시각 | in_flight | limit | rejected | ws_clients | health |
|---|---|---|---|---|---|
| 09:26:16 | 1746 | 1929 | 0 | 1746 | **200** |
| 09:27:01 | **1929** | 1929 | **1571** | 1929 | **200** |
| 09:27:47 | 1929 | 1929 | 1571 | 1929 | **200** |
| 09:28:32 | 737 | 1929 | 1571 | 737 | **200** |

**상한 1929 에서 멈추고 1571 건을 거절했다.** 1929 + 1571 = 3500 으로 회계가 정확히 맞는다.
노드는 전 구간 health 200 이다.

k6 쪽 결과.

| 항목 | 값 |
|---|---|
| `ws_open` | 3500 |
| `ws_error` | 1571 |
| `ws_closed_early` | 1571 |
| `ws_silent` | 1571 |
| `first_msg_p50` | 4ms |
| `first_msg_p95` | 9ms |

거절된 1571 건이 세 계수에 모두 같은 값으로 잡힌다. 수용된 1929 건은 침묵 0 이고 첫 메시지가
p95 9ms 다. **거절이 수용된 연결의 품질을 해치지 않는다.**

부하가 끝난 뒤 `in_flight` 와 `ws_clients` 가 모두 0 으로 돌아왔다. 슬롯이 새지 않는다.

| 확인 | 값 |
|---|---|
| `OutOfMemoryError` | **0건** |
| 종료 뒤 in_flight | 0 |
| 종료 뒤 ws_clients | 0 |
| 컨테이너 메모리 | 527MiB / 1GiB |

## 실측 2. 게이트 OFF, 2,200 연결 (상한 위)

수용 게이트를 끄면 상한이 사라져야 한다. 사고를 재현하는 스위치이기 때문이다.

| 시각 | in_flight | rejected | ws_clients |
|---|---|---|---|
| 09:31:54 | 0 | 1571 (증가 없음) | **2200** |
| 09:32:44 | 0 | 1571 (증가 없음) | 1703 |

`ws_open` 2200, `ws_error` 0, `ws_silent` 0 이다. **상한 1929 위인 2200 이 전부 통과한다.**
슬롯을 잡지 않으므로 `in_flight` 는 0 이고 거절도 늘지 않는다.

게이트 하나로 방어가 있는 상태와 없는 상태를 재기동 없이 오간다.

## 실측 3. actuator

```json
{"enabled": true,
 "buckets": {"order": {"limit": 6, "inFlight": 0},
             "query": {"limit": 6, "inFlight": 0},
             "requery": {"limit": 2, "inFlight": 0},
             "ws": {"limit": 1929, "inFlight": 0}}}
```

종전에는 `ws` 버킷이 없었다. 게이트 하나가 넷을 함께 여닫는데 버킷이 빠져 있으면 게이트를
껐을 때 무엇이 풀렸는지 알 수 없다.

## 남은 위험

- 유도 계수 2.6 연결/MB 는 최대 힙 768MB 한 점에서 옮긴 값이다. 더 큰 힙에서 선형인지는
  재지 않았다. 31회차의 앱 2GB 실측 한 점(3,000 연결 생존)이 간접 근거일 뿐이다.
- 거절된 연결이 즉시 재접속하는 경우를 재지 않았다. 클라이언트가 백오프 없이 재시도하면
  거절이 반복되고 그 자체가 부하가 된다. 웹 클라이언트의 재연결 정책 확인이 필요하다.
- 인증 세션(`/user/**` 구독)은 재지 않았다. 익명 공개 채널만 쟀다.
- 알람 `WsConnectionsNearLimit`·`WsConnectionsRejected` 는 규칙 검사만 통과했고 실제 발화와
  통지는 확인하지 않았다.

원자료는 `ws_guard3500.json`, `ws_gateoff2200.json`.
