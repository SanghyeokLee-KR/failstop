# ADR 0022 0단계 계측 (2026-09-11)

착수 게이트다. 러너는 `harness/scale/stage0_probe.py` 이고 인자 없이 같은 값을 다시 낸다.

## 조건

| 항목 | 값 |
|---|---|
| 대상 | `chaos-pg` 단독 기동. 앱과 봇과 k6 는 안 돌린다 |
| 설정 | `synchronous_commit=on`, `wal_sync_method=fdatasync`, `commit_delay=0`, `shared_buffers=128MB` |
| 저널 | `command_journal` 170,388행, 파티션 잎 3개 |
| 도구 | `pgbench` 17.11 (컨테이너 동봉) |

## (a) 동시 커밋 확장성

`pgbench` 가 스크립트 1회 실행을 트랜잭션 하나로 감싼다. 곧 초당 트랜잭션이 곧 초당 커밋이다.

| 동시 | 커밋/s | 평균 지연 |
|---|---|---|
| 1 | 749.8 | 1.334밀리초 |
| 2 | 799.4 | 2.502밀리초 |
| 4 | 641.4 | 6.236밀리초 |
| 8 | 1,280.6 | 6.247밀리초 |
| 12 | 1,850.1 | 6.486밀리초 |
| 24 | 3,743.9 | 6.410밀리초 |

**게이트 판정이 뒤집힌다.** ADR 0022 0단계 (a)가 "N=12 가 N=1 의 3배 미만이면 직렬 장치"
로 문턱을 잡았고 실측 배수가 2.47 이라 기계적으로는 분기 A 다. 그러나 그 문턱이 잘못
잡혔다. 두 가지가 그것을 보인다.

- **N=1 기준선 자체가 이미 충분하다.** 749.8 커밋/s 이고 명령 하나가 커밋을 둘 요구하므로
  단일 세션만으로도 명령 374/s 를 낸다. 관측 천장 128/s 의 2.9배다.
- **8에서 24 구간은 사실상 선형이다.** 1,280.6 에서 3,743.9 로 2.92배이고 동시성은 3배다.
  저장소가 동시 플러시를 흡수한다. 2.47 이라는 배수는 분자가 작아서가 아니라 분모(N=1)가
  커서 나온 값이다.

**`wal-fsync-20260907` 의 311.9회/s 를 처리량 상한으로 읽으면 안 된다.** 그 값은
`pg_test_fsync` 의 8KB 직렬 플러시이고, 실제 커밋은 N=1 에서도 그 2.4배다.

곧 저장소는 이 판의 구속이 아니다. ADR 0022 8-2 가 세운 분기 A(상한 156/s, 1.18배)는
성립하지 않는다.

## (e) 파티션 잎당 팬아웃

`findExistingNew` 와 같은 모양의 조회다. 술어가 `(command_type, user_id, client_order_id)`
뿐이라 파티션 프루닝이 0 이고 잎 전부의 부분 인덱스를 훑는다. 매치 0건이 최악이고 신규
주문마다 그 경로다. 잎마다 15,000행을 넣었다.

| 잎 | 중앙값 | 최대 | 스캔 노드 |
|---|---|---|---|
| 3 | 0.329밀리초 | 0.386밀리초 | 3 |
| 15 | 0.584밀리초 | 1.029밀리초 | 15 |
| 67 | 3.265밀리초 | 3.440밀리초 | 67 |

**V39 가 대역 파티션 63개를 미리 만들면 안 된다.** 이 조회는 어드바이저리 락 안, append
트랜잭션 안, 곧 상한 그 자체인 락 보유 6.879밀리초 안에 있다. 잎 3에서 67로 가면
2.94밀리초가 더 붙어 보유가 9.8밀리초가 되고 천장이 144/s 에서 102/s 로 **내려간다.**
락 분할은 뒤 단계이므로 그 사이 내내 이 비용만 먼저 문다.

마켓 생성 시 잎을 만들면 12마켓에 레거시 잎 셋을 더해 열다섯이고 비용이 0.26밀리초다.
ADR 0022 3-1(6)이 선생성으로 얻으려던 "마켓 id 상한의 구조적 차단" 은 채번 함수의 가드로
옮긴다.

## 락 보유 6.879밀리초의 분해

같은 회차에서 함께 쟀다. 앱과 같은 자리(카오스 망의 다른 컨테이너)에서 잰 값이다.

| 항목 | 값 | 재는 법 |
|---|---|---|
| 컨테이너 사이 왕복 | 0.124밀리초 | `pgbench` `SELECT 1`, 동시 1 |
| 같은 컨테이너 안 왕복 | 0.065밀리초 | 같은 방법, `docker exec` |
| 커밋 fsync | 약 1.2밀리초 | 동시 1 커밋 1.334 에서 왕복 하나를 뺀 값 |
| 멱등 조회(잎 3, 17만행) | 0.350밀리초 | `EXPLAIN ANALYZE` 중앙값 |
| 어드바이저리 락 | 0.016밀리초 | 같은 방법 |
| 전역 카운터 읽기 | 0.086밀리초 | 같은 방법 |
| 데이터베이스 실행 합계 | 약 0.5밀리초 | 위 셋에 리더 검증 점 조회를 더한 어림 |
| 왕복 일곱 | 약 0.87밀리초 | 0.124 x 7. BEGIN 과 COMMIT 포함 |
| **설명되는 몫** | **약 2.6밀리초** | |
| **실측 락 보유** | **6.879밀리초** | `submit-lock-20260911` |
| **설명 안 되는 몫** | **약 4.3밀리초 (62퍼센트)** | |

**곧 락 보유의 3분의 2가 데이터베이스 밖에 있다.** 후보는 커넥션 획득, 트랜잭션 경계,
페이로드 직렬화, 체크섬 계산, 그리고 부하 구간의 CPU 경합이다. 락 보유는 벽시계 시간이라
보유자가 스케줄에서 밀리면 함께 늘어난다. 같은 창에서 앱 CPU 가 118에서 300퍼센트였다.

**이 몫은 어느 설계안도 다루지 않는다.** 장부를 쪼개도 마켓별로 같은 4.3밀리초를 문다.
0단계 (b)를 임계구역 안 계측으로 확장해 이 몫을 먼저 갈라야 한다.
