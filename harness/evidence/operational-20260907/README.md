# 봇을 켠 운영 수치 (2026-09-07)

증거 `final-ceiling-20260907` 은 봇을 끄고 주문 축만 격리했다. 체결이 0 이라 접수 경로의
천장이었다. 봇을 켜면 체결이 돌고 봇도 같은 단일 라이터를 쓴다. 그 조건의 수치를 남긴다.

## 환경

| 구성 | 규격 |
|---|---|
| 앱(리더) | **2 vCPU / 1GB** |
| 조회 전용 노드 | 2 vCPU / 1GB (부하 없음) |
| DB | 4 vCPU / 4GB |
| 봇 | 2 vCPU / 1GB, `target-ops: 60`, 3 마켓 |

## 결과

| 부하 | 주문 처리 | 주문 지연 | 수용 거절 | 초당 체결 | DB CPU | 앱 CPU |
|---|---|---|---|---|---|---|
| 봇만 | 25.8/s | 35.9ms | 0 | **19.1** | 31.0% | 11.3% |
| 봇 + k6 60 | 73.4/s | 53.4ms | 9.0/s | 13.1 | 69.1% | 48.0% |
| 봇 + k6 100 | 86.4/s | 64.4ms | 38.2/s | 6.6 | 72.4% | 79.0% |
| 봇 + k6 150 | **91.3/s** | 62.0ms | 80.3/s | 5.4 | 81.3% | 84.3% |

**운영 천장은 약 91/s 다.** 봇을 끈 91.3 대 99 의 차이는 봇이 자기 주문과 취소로 같은 단일
라이터를 쓰기 때문이다.

체결이 부하와 함께 줄어드는 것(19.1 -> 5.4/s)은 k6 주문이 봇 호가와 잘 교차하지 않아서다.
k6 부하가 늘수록 전체 주문 중 교차 비율이 떨어진다. 체결 자체가 막힌 것이 아니다.

## 경과

| 시점 | 조건 | 주문 |
|---|---|---|
| 2026-09-04 | 봇 켬, 잔여 누적, 2 vCPU | 60/s |
| **2026-09-07** | **봇 켬, 같은 규격** | **91/s** |

**같은 조건에서 52% 올랐다.** 오늘의 변경 일곱(fencing 왕복, 채번 시퀀스, 호가 캐시 분리,
메모리 서빙, 증분 유지, 시세 통계 캐시, 캐시 몰림 제거)이 쌓인 결과다. 각 기여를 따로 가르지는
못했다.

## 커넥션 풀은 병목이 아니다

측정 내내 커넥션 풀이 상한 16 에 사용 중 2, 대기 0 이었다. 풀을 48 로 올려 본 구간에서도
사용 중 2, 유휴 20, 대기 0 이었다(증거 `scenario-20260907` 5 단계).

**커넥션을 기다리는 요청이 없다.** 밀리는 곳은 시퀀서 큐이고 그것은 단일 라이터가 만든다.
그래서 풀을 늘려도 주문 처리량이 오르지 않고 지연만 늘어난다.

## 남은 위험

- 각 단계를 한 번씩만 쟀다.
- 조회 전용 노드가 떠 있으나 부하를 받지 않았다. DB 를 공유하므로 완전한 격리는 아니다.
- 봇의 `target-ops` 는 60 이고 실측 기저가 25.8/s 다. 봇이 예산을 다 쓰지 못하는 이유는
  이번에 보지 않았다.
- 체결률이 부하와 함께 떨어지는 것을 교차 비율로 해석했으나 직접 재지는 않았다.
