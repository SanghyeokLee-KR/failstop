# 동기 복제가 주문 천장에서 가져가는 몫 (2026-09-08)

정본 6.3 이 상시면에 2 AZ primary/standby 스트리밍 복제를 잡고 RPO 0 을 주장한다. RPO 0 은
동기 복제를 요구하고 동기 복제는 커밋마다 standby 의 응답을 기다린다. 증거
`instance-sizing-20260907` 이 그 대가를 적으면서 **"얼마나 내려가는지는 재지 않았다"** 로
끝났다. 그 값을 잰다.

## 왜 이 축이 특히 아픈가

주문 천장을 단일 라이터의 커밋이 정한다. 그 커밋 시간의 63% 가 이미 fsync 다
(증거 `wal-fsync-20260907`). 동기 복제는 그 위에 standby 왕복을 더한다. 곧 이 시스템에서
동기 복제의 대가는 일반적인 경우보다 크다.

## 환경

| 항목 | 값 |
|---|---|
| primary | `postgres:17-alpine`, 4 vCPU / 4GB |
| standby | 같은 이미지·규격. `pg_basebackup -R -X stream` 으로 세움 |
| 앱 | 리더 1 대 + 조회 1 대, 각 2 vCPU / 1GB |
| 봇 | 가동. `target-ops 60` |
| 부하 | `calibrate.js` `BASE_OPS=100` 90 초. 네 회차 같은 조건 |
| 호스트 | 12 코어 |

AZ 지연은 toxiproxy 로 만들었다. standby 의 `primary_conninfo` 를 프록시로 돌리고
상행과 하행에 각각 1ms 를 걸어 왕복 2ms 다. primary 가 보는 `client_addr` 가 프록시
주소인 것으로 경유를 확인했다.

## 결과

| 구성 | 주문/s | p95 | p99 | 429/s | 복제 없음 대비 |
|---|---|---|---|---|---|
| 복제 없음 | 76.3 | 99.5ms | 216.8ms | 23.7 | |
| A 비동기 | 65.9 | 116.0ms | 150.0ms | 34.1 | **-13.6%** |
| B 동기, 왕복 약 0 | 53.0 | 145.2ms | 173.9ms | 47.0 | **-30.5%** |
| C 동기, 왕복 2ms | 46.2 | 169.3ms | 190.2ms | 53.9 | **-39.5%** |

standby 의 `flush_lag` 이 함께 움직인다. B 에서 2.787ms, C 에서 6.323ms 다.

## 세 구간을 갈라 읽는다

한 표에 세 가지 다른 비용이 섞여 있다. 인접 구간의 차로 가른다.

| 구간 | 차 | 무엇의 비용인가 |
|---|---|---|
| 복제 없음 -> A | **-13.6%** | standby 가 존재하는 비용. WAL sender 와 호스트 자원 경합 |
| A -> B | **-19.6%** | 동기 대기 자체 |
| B -> C | **-12.8%** | AZ 간 왕복 2ms |

**첫 구간은 이 회차의 호스트 사정이 섞였다.** 12 코어 호스트에 standby 컨테이너가 4 vCPU 를
더 잡는다. 클라우드에서는 별도 인스턴스이므로 이 몫은 더 작을 것이다. 다만 WAL sender 가
primary 의 CPU 를 쓰는 몫은 남는다.

**둘째와 셋째가 이 회차의 판정 대상이다.** 둘을 합쳐 동기 복제의 대가가 **-30%** 다.

## 주문당 라이터 시간으로 환산

| 구성 | 주문당 라이터 시간 |
|---|---|
| 복제 없음 | 13.1ms |
| A 비동기 | 15.2ms |
| B 동기, 왕복 약 0 | 18.9ms |
| C 동기, 왕복 2ms | 21.6ms |

명령 하나가 커밋을 두 번 한다. A 에서 B 로 3.7ms 늘었으므로 커밋당 1.85ms 다. 같은 창의
`flush_lag` 이 2.787ms 이므로 대기 전액이 그대로 붙지는 않는다. 커밋이 파이프라인으로 겹치는
몫만큼 흡수된다.

## 거절이 함께 늘어난다

429 가 23.7/s 에서 53.9/s 로 늘었다. 처리량이 39.5% 떨어지는 동안 p95 는 70% 만 올랐다.
초과분이 대기열에 쌓이지 않고 수용 정원에서 거절되기 때문이다. 설계된 백프레셔가
동기 복제 구간에서도 그대로 작동한다.

**곧 동기 복제를 켠 대가는 지연 폭증이 아니라 접수량 감소로 나타난다.** 받은 주문은 여전히
170ms 안에 처리되고 못 받는 주문이 는다.

## 이 수치를 어디에 쓰나

- 정본 6.3 의 RPO 0 주장에 값을 붙인다. RPO 0 은 공짜가 아니고 이 구성에서 천장의 30% 다.
- 정본 6.5 의 천장 서술과 함께 읽어야 한다. 지금 적힌 99 주문/s 는 복제가 없는 값이다.
  상시면이 2 AZ 동기 복제를 켜면 그 값이 그대로 성립하지 않는다.
- ADR 0015 의 수동 스케일링과는 무관하다. 확장 축은 조회이고 이 축은 쓰기다.

## 한계

- **AZ 간 지연 실측이 아니다.** 왕복 2ms 는 toxiproxy 로 만든 값이고 ap-northeast-2 의
  실제 AZ 간 왕복은 재지 않았다. 그 값이 2ms 보다 크면 C 보다 더 내려간다.
- **호스트가 12 코어다.** primary 4, standby 4, 앱 2 x 2, 봇 2, 프록시와 부하기가 그 안에서
  경쟁한다. 절대 처리량을 클라우드 값으로 읽지 않는다. 이 회차가 재는 것은 네 구성의 상대차다.
- **t4g.small 실물이 아니다.** 상시면 DB 규격은 2 vCPU 이고 이 회차는 4 vCPU 다.
- **회차가 구성마다 하나다.** 분산을 재지 않았다.
- **standby 를 읽기에 쓰지 않았다.** 정본이 standby 를 페일오버 대기로 규정하므로 조회 분산
  효과는 이 회차의 대상이 아니다.
- **승격은 재지 않았다.** 이 회차는 복제 켠 상태의 정상 구간만 잰다. switchover 소요와 그 창의
  주문 거절은 별도 축이다.
