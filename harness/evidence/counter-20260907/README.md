# 주문 id 채번 잠금 제거 (2026-09-07)

증거 `fencing-20260907` 이 지목한 다음 표적이다. fencing 은 총 DB 실행 시간의 0.4% 였고, 같은
창에서 `next_journal_value('order_id')` 가 그 12 배였다.

## 무엇이 문제였나

`next_journal_value` 는 카운터 한 행을 `UPDATE ... RETURNING` 으로 잠근다. 그 잠금은 호출
트랜잭션이 끝날 때까지 유지되므로 같은 카운터를 쓰는 호출자가 직렬화된다.

`command_seq` 와 `event_seq` 는 단일 라이터 스레드가 쓰므로 어차피 직렬이라 문제가 되지 않는다.
`order_id` 는 다르다.

| 축 | command_seq / event_seq | order_id |
|---|---|---|
| 부르는 곳 | 단일 라이터 스레드 | **접수 경로 API 스레드** |
| 동시 호출자 | 1 | **수용 정원만큼** |
| 트랜잭션 | 저널 트랜잭션 안 | **없음. 이 한 문장이 곧 트랜잭션** |

`OrderGateway` 에는 `TransactionTemplate` 도 `@Transactional` 도 없다. 그래서 채번 한 문장이
자기 트랜잭션이고, **주문마다 id 채번만을 위한 커밋과 WAL 플러시가 한 번 더 일어났다.**

## 정본이 이미 허락했다

`V2__gateway_counters.sql` 이 스스로 적었다.

> gapless는 요구되지 않으나 채번 경로는 journal_counters 단일 방식으로 통일한다.

`order_id` 가 그 테이블에 있던 이유는 **통일성**이고 정확성이 아니다. 실제 사용처를 확인하면
전부 조인 키와 존재 검사다(`harness/sql/invariants.sql:79,91`,
`orders.id = command_journal.assigned_order_id`). 연속성을 가정하는 곳이 없다.

저장소에 선례도 있다. `V11__sim_run_ordinal.sql` 이 시퀀스를 쓰고 그 이유를 적었다.

> 시퀀스는 비트랜잭션이라 롤백에서 되감기지 않고 크래시에서도 앞으로만 튀므로 재발급이 없다.
> 엔진 기원 쓰기·리더 리스·원장 게시와 무관한 봇 클라이언트측 채번이라 journal_counters와 분리한다.

**같은 성질이 축에 따라 부호가 뒤집힌다.** 되감기지 않는 것이 저널 seq 에서는 영구 결번이라
결함이고, 게이트웨이 id 에서는 장점이다.

## 무엇을 바꿨나

`order_id` 를 전용 시퀀스 `order_id_seq`(V31, CACHE 20)로 옮겼다. `command_seq` 와 `event_seq` 는
그대로 둔다. 그 둘은 재생 결정론의 축이고 gapless 가 계약이며, 특히 `event_seq` 는
`trade_id` 로 API·WS 에 나가므로 제약이 더 세다.

## 결과 (pg_stat_statements, 같은 부하)

| 채번 문장 | 종전 | 현행 |
|---|---|---|
| `next_journal_value('order_id')` | **3202ms** | 없음 |
| `nextval('order_id_seq')` | 없음 | **86ms** |

**37 배 싸다.** `UPDATE journal_counters` 도 명령당 4.09 회에서 2.00 회로 준다. order_id 가 그
테이블을 더 이상 건드리지 않기 때문이다.

## 종단 처리량은 격리하지 못했다

같은 부하에서 주문 처리량이 75.7/s 에서 70.5~71.2/s 로 오히려 조금 내려갔다. 채번 때문이
아니라 **측정 창 사이에 데이터가 자랐기 때문**이다.

측정 시점의 `orders` 는 373967 행이고 그중 미체결이 163779 행이다. 그 상태에서 호가 집계가
지배 비용이 된다.

| 문장 | 총 실행 | 건당 |
|---|---|---|
| `SELECT COALESCE(SUM(remaining_qty), 0) FROM orders ...` | **92250ms** | **35ms** |
| `SELECT reserve_funds(...)` | 30072ms | 2.6ms |
| `nextval('order_id_seq')` | 86ms | 0.007ms |

호가 집계 하나가 채번의 **1000 배**다. 잔여 주문이 천장을 흔든다는 것은 ADR 0013 이 이미
등재한 성질이고, 이번 측정이 그 구간에 들어갔다.

**그래서 이 회차가 확정하는 것은 채번 문장의 비용(3202ms -> 86ms)이지 종단 처리량 이득이
아니다.** 종단 효과를 재려면 같은 데이터 상태에서 전후를 각각 돌려야 하고 그것은 하지 않았다.

## 남은 위험

- 종단 처리량 이득 미측정. 깨끗한 DB 에서 전후 A/B 가 필요하다.
- CACHE 20 이라 세션 종료·재기동 때 잡아 둔 나머지가 버려진다. 커넥션 풀 16 기준 최대 320 의
  구멍이다. 구멍이 허용되는 축이라 성립하지만 값을 실측으로 고른 것은 아니다.
- `journal_counters` 의 `order_id` 행을 남겼다. 되돌릴 수 있게 두었고 아무도 읽지 않는다.
  다만 읽지 않는 행이 남아 있다는 것 자체가 다음 사람에게는 혼동거리다.
- 다음 표적은 채번이 아니라 **호가 집계와 잔여 주문 누적**이다. 이번 측정이 그것을 우연히
  드러냈다.
