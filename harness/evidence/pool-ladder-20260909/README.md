## 왜 무효인가

**같은 설정의 앞선 회차와 값이 크게 다르다.** 풀 32 가 오늘 오후에는 체결 초당 13 에서 19 였는데 이 회차에서는 2.7 이다. 5 에서 7 배 차이다.

원인은 누적 데이터다. 회차 종료 시점에 주문 61.7만 건, 체결 28.2만 건, 데이터베이스 크기 2.15 기가바이트다. 하루 종일 부하를 건 누적분이고, 초기 회차는 그보다 훨씬 작은 상태에서 쟀다.

곧 이 사다리의 칸 사이 차이에 **풀 효과와 데이터 증가 효과가 섞여 있다.** 칸을 순서대로 돌았으므로 뒤 칸일수록 데이터가 더 많다. 실제로 체결이 2.4 에서 4.0 으로 완만히 오르는데, 이것이 풀 효과인지 다른 무엇인지 이 자료로는 가릴 수 없다.

## 그래도 남는 사실

**풀은 지배 변수가 아니다.** 풀을 8 배(16 에서 128) 벌려도 체결이 2.4 에서 4.0 사이에 머문다. 데이터 증가가 섞였어도 그 폭이 이렇게 좁으면 풀이 정점을 만드는 축은 아니다. 종전에 세운 "풀이 지배 변수" 라는 가정도 함께 흔들린다.

**풀 대기가 전 칸 0 이다.** 커넥션이 모자란 상태가 한 번도 없었다. 풀을 키우는 이유가 대기 해소라면 그 근거가 없다.

**DB CPU 가 64 칸부터 178 퍼센트로 뛴다.** 4코어 기준 45 퍼센트다. 그 전 칸들은 82 퍼센트(4코어 기준 20 퍼센트)였다. 풀이 커지면 데이터베이스가 더 바빠지는데 체결은 안 는다.

## 이 회차가 드러낸 절차 결함

**측정 조건이 회차 사이에 변한다.** 데이터가 계속 쌓이므로 오전 회차와 오후 회차를 직접 비교할 수 없다. 오늘 여러 판정을 그런 비교 위에 세웠고 그중 하나는 이미 뒤집혔다(정원 격자).

사다리처럼 여러 칸을 순서대로 도는 실험은 특히 취약하다. 뒤 칸일수록 데이터가 많아 축의 효과와 시간의 효과가 같은 방향으로 섞인다.

대책은 둘이다. 칸마다 데이터베이스를 초기 상태로 되돌리거나, 칸 순서를 무작위로 섞어 시간 효과를 분산시키는 것이다. 전자가 정확하나 비용이 크다.
