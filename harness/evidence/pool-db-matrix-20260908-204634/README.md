# 커넥션 풀·수용 정원과 DB 규격 교차 실측 (2026-09-08)

묻는 것은 하나다. 정본 6.10 이 "DB 를 올려도 정원 6 칸이 그대로라 천장이 움직이지
않습니다" 로 적었는데, 풀과 정원을 함께 올리면 DB 규격 상향이 값을 갖는가.

손잡이는 실은 하나다. `AdmissionLimits` 가 쓰기 정원을 `floor(poolSize x 0.40)` 으로
유도하므로 풀만 올리면 정원이 따라 오른다. 풀 16 이면 쓰기 6, 풀 48 이면 쓰기 19 다.

- 생성기: `harness/scale/pool_db_matrix.py`
- 오버레이: `harness/docker-compose.scale.yml`
- 분석: `harness/scale/analyze_matrix.py`

## 무엇이 나왔나

### 1. DB 코어 증설은 지연을 절반 이하로 줄인다

| 비교 | p95 | p99 |
|---|---|---|
| A -> B (풀 16, 40 OPS) | 138 -> 86ms (-38%) | 318 -> 121ms (-62%) |
| C -> D (풀 48, 40 OPS) | 223 -> 108ms (-52%) | 382 -> 146ms (-62%) |
| E -> F (풀 16, 200 OPS 목표) | 232.6 -> 96.2ms (-59%) | 415.6 -> 126.8ms (-69%) |

세 쌍 모두 같은 방향이고 p99 개선이 p95 개선보다 크다. 꼬리가 먼저 줄어든다.

### 2. DB CPU 는 줄지 않는다

40.6 -> 49.3 (+8.7), 48.0 -> 42.9 (-5.1), 45.9 -> 42.8 (-3.1). 방향이 일관되지 않고
크기도 표본 산포 안이다. 코어를 늘리면 같은 일을 넓게 펴는 것이지 일이 줄지 않는다.

곧 "DB CPU 부하를 줄인다" 와 "지연을 줄인다" 는 같은 조작으로 달성되지 않는다.

### 3. 풀과 정원 상향은 지연을 악화시킨다

| 비교 | p95 | p99 |
|---|---|---|
| A -> C (DB 1 코어) | 138 -> 223ms | 318 -> 382ms |
| B -> D (DB 4 코어) | 86 -> 108ms | 121 -> 146ms |
| E -> G (DB 1 코어, 200 OPS 목표) | 232.6 -> 260.9ms | 415.6 -> 523.4ms |

세 쌍 모두 나빠졌다. 풀 대기가 전 회차 0 이므로 커넥션이 모자란 상태가 아니었고,
정원을 6 에서 19 로 늘리면 동시에 도는 요청이 늘어 DB 안에서 경합만 커진다.

이것은 `AdmissionLimits` 주석의 설계 의도와 맞는다. 그 게이트의 목적은 많이 통과시키는
것이 아니라 통과한 요청이 커넥션을 기다리지 않게 하는 것이다.

### 4. PostgreSQL 커넥션 한도는 병목이 아니었다

풀 48 구간에서 잰 값이다. `max_connections` 100 에 실제 43 접속, 그중 활성 6.
대기 사유는 38 개 중 35 개가 `Client/ClientRead` 로, DB 가 앱의 다음 요청을 기다리는
상태다. 밀려서 막힌 것이 아니라 일이 없어서 노는 것이다.

## 한계

- **부하가 계획대로 오르지 않았다.** 회차 2 는 봇 목표를 200 OPS 로 올렸는데 DB CPU 와
  체결률이 회차 1(40 OPS)과 같거나 낮다. 실효 부하가 오르지 않았다는 뜻이고, 따라서
  "포화 상태에서의 비교" 는 이 증거로 성립하지 않는다. 무엇이 상한을 만들었는지는
  이 회차가 판정하지 않는다.
- **같은 호스트에 컨테이너가 많았다.** 측정 내내 카오스 스택 12 개가 같은 기계에서 돌았고
  앞선 구간에는 Testcontainers 임시 DB 가 최대 27 개까지 겹쳤다. 절대값이 아니라 같은
  주행 안의 상대 비교로만 읽어야 한다.
- **H 회차가 없다.** 풀 48 + DB 4 코어를 고부하에서 확인하지 못했다.
- **로컬 도커다.** t4g.small 실물이 아니고 저장 계층도 다르다. 클라우드 착지 후 재측정
  대상이다.

## 남는 질문

- 실효 부하 상한을 만든 축이 무엇인가. 봇 자체인지, 인증인지, 레이트리밋인지.
- 지연 개선분이 유효 천장 상승으로 이어지는가. 정원 한 칸의 점유 시간이 1/3 이 되면
  같은 정원으로 더 통과시킬 수 있어야 하는데 이 회차에서는 수요가 없어 드러나지 않았다.
- 동기 standby 에 읽기를 얹으면 primary 커밋이 느려지는가. 준비만 했고 돌리지 못했다
  (`harness/scale/standby_read.py`, `standby_up.sh`, `standby_down.sh`).
