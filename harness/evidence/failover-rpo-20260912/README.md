# primary 급사의 유실량, 수동 승격 시간, 재편입 (2026-09-12)

ADR 0024 가 미충족으로 남긴 셋에 값을 붙인다. 셋이 한 장애 사건에서 순서대로 나오므로 한
주행으로 묶었다. 스크립트는 `harness/scale/failover_rpo_check.py`, 원자료는 `result.json` 이다.

## 결론

| 항목 | 값 |
|---|---|
| RPO, 정상 복제 중 급사 | ACK 88 건 중 **0 건 유실** |
| RPO, standby 8 초 정지 후 급사 | ACK 122 건 중 **36 건 유실**(29.5%) |
| 승격 명령 시간 | **1.697초**와 **1.886초**. 사람의 감지와 판단은 뺀 값이다 |
| 재편입 | `pg_rewind` **실패**. 전량 베이스백업 **264.717초**, 스트리밍 재개 확인까지 합 **272.549초** |

## 무엇을 유실로 셌나

**클라이언트가 ACK 받은 행 중 승격한 노드에 없는 것.** 유실은 디스크에서 사라진 것이 아니라
클라이언트가 받았다고 믿는데 없는 것이다. 구 primary 볼륨이 살아 있어도 그것을 버리고 standby
를 승격하면 그 차이가 그대로 유실이다.

프로브는 한 트랜잭션에 한 행이고 `INSERT ... RETURNING n` 으로 받는다. 서버가 값을 돌려준
것이 곧 커밋 성공이다. 묶어 쓰면 어디까지 ACK 됐는지 경계가 흐려진다. 대조는 ACK 받은 번호
집합을 그대로 승격 노드에 물어 없는 것을 센다. 최댓값까지의 구간으로 세면 중간에 실패한 요청이
유실로 계상된다.

## 판정 대상이 존재했다는 증거

빈 테이블을 승격 노드에서 조회하면 유실 0 이 나오고 통과로 보인다. 그래서 주행마다 하한을
먼저 건다(22절).

| 축 | natural | lagged |
|---|---:|---:|
| ACK 받은 프로브 행 | 88 | 122 |
| 소음 배치(20만 행 INSERT) | 58 | 82 |
| 구간 WAL 생성량 | 697.9 MiB | 991.7 MiB |

standby 에 프로브 테이블이 실제로 복제됐는지를 쓰기 창 진입 전에 확인하고, ACK 가 0 건이면
주행을 중단한다. 승격이 서지 않으면 그 회차의 시간은 대기 타임아웃이므로 역시 중단한다.

첫째 가드는 실제 사고에서 나왔다. 공식 이미지가 초기화 스크립트를 임시 서버에서 돌리고 그
서버를 한 번 내리는데, 그 창에 걸린 DDL 이 소리 없이 실패해 프로브 테이블이 없는 채로 주행이
돌았고 유실 0 이 공허하게 나왔다.

## 회차 두 개를 가른 이유

natural 에서 0 이 나와도 그것은 이 호스트 이 부하의 값이지 RPO 0 이 아니다. 지연이 곧 유실
창이라는 것을 보이려면 지연을 만든 회차가 있어야 한다.

lagged 는 `docker pause` 로 standby 프로세스를 8 초 얼렸다. 그 창에 쓰인 것이 거의 그대로
유실됐다. ACK 속도가 약 4.4 행/s 이므로 8 초는 약 35 행이고 실측 유실이 36 행이다.

**곧 이 구성의 RPO 는 복제 지연과 같다.** 복제가 따라오는 동안에는 0 이고 밀리는 만큼 잃는다.
정상 구간에서 0 이 나온 것을 무손실 보장으로 읽지 않는다.

## 승격 시간을 RTO 라고 부르지 않는 이유

**이 저장소에 DB 자동 페일오버가 없다.** 1.7초에서 1.9초는 `docker kill` 시각부터 승격한
노드가 쓰기를 받은 시각까지이고, 그 안에 사람이 장애를 알아차리는 시간, 승격할지 판단하는
시간, 앱 `DB_HOST` 를 바꿔 재기동하는 시간이 하나도 들어 있지 않다. 명령 실행 시간이다.

같은 이유로 E5·E7 이 잰 앱 리더 페일오버 값과 더하거나 비교하지 않는다. 그쪽은 DB 가 살아
있을 때 앱 사이에서 도는 장치다.

승격 명령은 `-u postgres` 가 필요하다. `docker exec` 의 기본 사용자가 root 이고 `pg_ctl` 은
root 실행을 거부한다. 이 회차 전의 절차 문서에 그 플래그가 없었고 실행하면
`pg_ctl: cannot be run as root` 로 끝난다.

## 재편입이 되감기로 끝나지 않았다

`wal_log_hints` 는 급사 시점에 `on` 이다. 전제는 섰고 `pg_rewind` 는 다른 데서 멈췄다.

```
pg_rewind: servers diverged at WAL location 0/2F1BFFF0 on timeline 1
pg_rewind: error: could not open file ".../pg_wal/000000010000000000000021": No such file or directory
pg_rewind: error: could not find previous WAL record at 0/21FFFFC0
```

**되감기가 읽어야 하는 구간은 분기 지점부터가 아니라 마지막 공통 체크포인트부터다.** 없어진
세그먼트 `...0021` 이 덮는 구간은 분기 지점 `0/2F1BFFF0` 보다 209.8 MiB 앞이다. 구 primary 는
그만큼 거슬러 올라간 WAL 을 들고 있어야 했고 이미 재활용한 뒤였다. `wal_keep_size` 가 기본값
0 이고 `max_wal_size` 가 1GiB 인데 이 회차의 대상 노드가 28 초에 991.7 MiB 를 썼다.

이 실패는 쓰기량에 달린 것이지 되감기가 구조적으로 불가능하다는 뜻이 아니다. 이 회차의 WAL
생성 속도는 35.4 MiB/s 이고 소음 부하가 만든 값이라, 이 거래소의 실측 주문 천장에서 나오는
값보다 훨씬 크다. 그래서 아래 둘 중 무엇을 살지가 남는다.

- `wal_keep_size` 를 올린다. 디스크를 주고 되감기를 산다. 산정 기준은 분기 창이 아니라 체크포인트
  간격만큼의 소급 폭이고, 이 회차 값이 209.8 MiB 다.
- `archive_mode` 를 켜고 `pg_rewind -c` 로 보관된 WAL 을 끌어온다. 현재 기본값은 off 다.

둘 다 이 회차가 정하지 않는다. 정책 변경이라 ADR 이 소유한다.

## 대안 경로의 실측

되감기가 안 되면 남는 것은 전량 베이스백업이고 그것을 실제로 돌렸다.

| 단계 | 초 |
|---|---:|
| 구 primary 크래시 복구 후 정상 정지 | 3.777 |
| `pg_rewind` 시도와 실패 | 1.278 |
| 볼륨 비우고 전량 베이스백업(428.7 MiB) | 264.717 |
| 기동 후 스트리밍 재개 확인 | 1.234 |
| 그 밖(제어 파일 조회, 슬롯 생성) | 1.543 |
| 합 | **272.549** |

264 초의 상당 부분은 데이터 전송이 아니라 체크포인트 대기로 **추정**한다. `pg_basebackup` 이
`waiting for checkpoint` 를 먼저 찍고 기본값이 `--checkpoint=spread` 이며 `checkpoint_timeout`
이 300 초다. 단계별 분할은 재지 않았다. `deploy/pg-standby-entrypoint.sh` 가 그 기본값을
그대로 쓰므로 실제 배선의 값이고, `-c fast` 를 주면 이 대기가 사라진다.

**이 시간이 곧 이중화 공백이다.** 그동안 새 primary 가 홀로 돌고 그 사이 primary 를 또 잃으면
복구 대상이 없다.

재편입이 끝난 뒤 새 primary 의 `pg_stat_replication` 에 `application_name=rejoined` 가
`state=streaming` 으로 서고 재편입 노드의 `pg_is_in_recovery()` 가 `t` 인 것까지 확인했다.
종료코드 0 은 파일을 맞췄다는 뜻이지 복제가 붙었다는 뜻이 아니라서 이 확인을 따로 건다.

## 환경

| 항목 | 값 |
|---|---|
| 배선 | `deploy/compose.node-data.yml` 그대로. 프로젝트명 `pgha` |
| 노드 | `postgres:17-alpine` 2 대, 각 메모리 512MiB |
| 복제 | 비동기 스트리밍, 슬롯 `standby_1`, `synchronous_commit=on` |
| 호스트 | 단일 호스트 도커. 같은 창에 카오스 스택 7 컨테이너가 함께 돌았다 |
| `REPL_CIDR` | 검증 스택만 `0.0.0.0/0`. 도커 브리지가 172 대역이라 배포 기본값 `10.0.0.0/16` 이 맞지 않는다 |

승격한 노드가 `wal_log_hints=on` 으로 돌고 있는 것을 주행 뒤 그 컨테이너에서 직접 확인했다
(`SELECT setting, source FROM pg_settings WHERE name='wal_log_hints'` 가 `on|command line`).
`result.json` 에는 이 값이 없다. primary 쪽 값만 남긴다.

## 한계

- **단일 호스트다.** primary 와 standby 가 같은 커널, 같은 디스크를 쓴다. AZ 간 왕복이 0 이라
  정상 구간 유실 창이 실제보다 좁게 나온다. 다중 호스트 기동은 여전히 0 건이다.
- **부하가 합성이다.** 소음 INSERT 가 만든 WAL 속도는 이 거래소의 주문 부하가 만드는 값이
  아니다. 되감기 실패 판정은 그 위에 있다.
- **회차가 조건마다 하나다.** 분산을 재지 않았다. 저장된 원자료는 이 `result.json` 하나다.
- **되감기 성공 경로는 NOT RUN 이다.** 스크립트의 `pg_rewind` 성공 뒤 경로(복제 접속 문자열
  주입, `standby.signal` 생성)가 이 회차에서 한 번도 실행되지 않았다. 되감기 전제 자체가 없을
  때 타는 분기도 마찬가지로 NOT RUN 이다. 이 회차는 전제가 섰고 되감기를 시도했다.
- **절차 전체를 돌린 것이 아니다.** 잰 것은 승격과 재편입이고, 구 primary fencing, 앱
  `DB_HOST` 전환, 리스 재획득은 이 주행 밖이다. `docs/reference/operations/DB_수동_페일오버.md` 참조.
- **앱을 붙이지 않았다.** 프로브가 직접 psql 로 쓴다. 주문 경로의 유실량이 아니라 저장 계층의
  유실량이다.
