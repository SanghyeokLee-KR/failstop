# 호가를 엔진 메모리에서 서빙 (2026-09-07)

증거 `depth-20260907` 은 호가 집계를 캐시로 덜 자주 돌게 했다. 증상 완화였고 원인은 남았다.
미체결이 다시 쌓이면 건당 25ms 가 돌아온다. 원인을 없앤다.

## 왜 DB 에서 셀 이유가 없나

엔진이 호가창을 이미 메모리에 들고 있다(`OrderBookImpl` 의 `bids`·`asks` TreeMap). 조회 경로는
그 사실을 쓰지 않고 `orders` 테이블에서 다시 집계했다.

| 축 | 값 |
|---|---|
| 호가 두 쿼리 DB 시간 | 166445ms |
| 같은 창 쓰기 경로 | 55493ms |

**화면이 쓰기의 3 배를 먹었다.** 매칭·주문 검증·정산은 이 쿼리를 쓰지 않는다. 쓰는 곳은
`MarketController`(REST)와 `MarketDataPublisher`(WS) 뿐이다.

## 어떻게 안전하게 읽나

TreeMap 은 동시 수정에 안전하지 않다. API 스레드가 책을 직접 읽으면 안 된다.

그래서 **단일 라이터 스레드가 배치마다 불변 스냅샷을 떠서 넘긴다.** 읽는 쪽은 그 참조만
가져가므로 잠금이 없고 라이터와 경합하지 않는다. 스냅샷이 없으면(조회 전용 노드, 리더의 첫
배치 전) 종전 DB 집계로 내려간다.

## 첫 구현이 오히려 느렸다

단별 합을 그때그때 세도록 만들었다. 가격 단은 17 개뿐이라 싸 보였는데, 그 17 단에 미체결이
73073 건 걸려 있었다. **배치마다 7 만 번 덧셈을 단일 라이터가 했다.**

| 미체결 4 만 | 순회 방식 | 종전 DB 방식 |
|---|---|---|
| 100 OPS | 88.7/s, 앱 CPU 69% | 98.6/s, 앱 CPU 53% |
| 150 OPS | 76.8/s, 앱 CPU 79% | 94.9/s, 앱 CPU 76% |

**DB 가 인덱스로 하던 일을 자바 루프로 옮긴 것이었다.** DB 부하는 줄었으나 그 일이 처리량을
정하는 단일 라이터로 옮겨가 천장이 내려갔다.

## 증분으로 고쳤다

단별 잔량을 잔량이 드나드는 자리에서 함께 갱신한다. 갱신 지점은 셋뿐이다. 신규 안착, 제거,
체결·STP 감액이다. 그러면 스냅샷이 가격 단 수에 비례할 뿐 주문 수와 무관해진다.

| 미체결 7.3 만 | 증분 방식 |
|---|---|
| 100 OPS | **96.5/s**, 지연 54.2ms, 앱 CPU 57% |
| 150 OPS | **97.9/s**, 지연 57.6ms, 앱 CPU 72% |

**미체결이 두 배인데 순회 방식보다 빠르고, 종전 DB 방식의 깨끗한 상태 수치와 같다.**

## 전후 대조

| 상태 | 방식 | 주문 처리 |
|---|---|---|
| 미체결 8 만 | DB 집계 | 75~86/s |
| 미체결 0~3.6 만 | DB 집계 | 94.9~98.6/s |
| 미체결 4 만 | 메모리 순회 | 76.8~88.7/s |
| **미체결 7.3 만** | **메모리 증분** | **96.5~97.9/s** |

**천장이 미체결 수에 더 이상 좌우되지 않는다.** 그것이 이번 변경의 핵심이다. 종전에는 잔여가
쌓일수록 천장이 내려가 부하 시험을 반복할수록 결과가 나빠졌다(ADR 0013 이 등재한 2.2 배 흔들림).

## 검증

- 호가 집계 쿼리가 사라졌다. 봇 가동 90 초 창에서 `SUM(remaining_qty)` 호출이 8 회 0ms 다.
  기동 직후 스냅샷이 차기 전의 폴백뿐이다.
- 값이 DB 와 정확히 같다. 거래를 멈추고 대조했다.

| | 메모리 | DB |
|---|---|---|
| total_ask | 44.195 | 44.195 |
| total_bid | 52.568 | 52.568 |

- 단위 검증 8 건을 더했다(`OrderBookDepthTest`). 모든 시험이 스냅샷을 책 원본과 대조한다.
  증분은 갱신 지점을 하나만 빠뜨려도 조용히 어긋나므로 부분 체결, 완전 체결, 취소, 부분 체결 뒤
  취소, 스냅샷 복원, 혼합 순서를 각각 고정한다.

## 남은 위험

- **체결이 0 인 조건에서 쟀다.** 봇을 끄고 k6 주문이 교차하지 않는 상태다. 체결이 활발하면
  증분 갱신 호출이 늘어 비용이 다르다. 다만 그 비용은 체결 수에 비례하고 미체결 수와 무관하다.
- 조회 전용 노드는 여전히 DB 집계를 쓴다. 엔진이 꺼져 있어 책이 없다. 그 노드에 책을 전파하는
  것은 별도 작업이다(정본이 M2 Redis 릴레이로 잡았다).
- 스냅샷은 배치가 건드린 마켓만 갱신한다. 거래가 없는 마켓은 마지막 값이 남는데, 책이 바뀌지
  않았으므로 값은 옳다. 다만 그 성질을 시험으로 고정하지는 않았다.
- 각 계단을 한 번씩만 쟀다.
