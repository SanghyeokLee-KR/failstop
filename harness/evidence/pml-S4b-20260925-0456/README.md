# S4b 관문 폐기용 스택 주행 (2026-09-25 05:14~08:34 KST)

[S4b 설계](../../../docs/reference/architecture/마켓분할_리더_S4b_설계.md) 7절의 실험을 S4b 코드(커밋 전)로 돌린 기록이다. S4 재주행([pml-S4-20260925-0012](../pml-S4-20260925-0012/README.md))에서 FAIL이던 E2·E1을 고친 뒤의 관문이다. 스택은 compose 프로젝트 `exchange-pml`의 폐기용 스택이고 DB 모드는 모든 실험에서 P2, 파티션은 `matching-engine` 하나다. 이미지를 두 번 구웠다. 첫 이미지로 X1·X6·B1·E2 다섯 번·E1 다섯 번을 돌았고, 다섯째 E1이 S4의 E1 FAIL을 재현해 정산 재시도 한도를 고친(F1) 뒤 다시 구운 이미지로 E1 세 번과 설계 7-2 Y3·Y4가 정한 재확인을 돌았다.

절차는 [run-s4b-gate.ps1](run-s4b-gate.ps1)(S4 재주행 실행기를 복사해 설계 7-1의 일곱 곳과 다시 굽기를 고쳤다), 단계별 시각과 종료 코드는 [commands.log](commands.log), 보존 볼륨 확인은 [volumes.txt](volumes.txt), 실행 전후 다른 세션의 Testcontainers 컨테이너 수는 [host-concurrency.txt](host-concurrency.txt)다(F1 뒤 주행부터 실행기를 부른 감싸개가 `docker ps --filter label=org.testcontainers=true`로 센 값이다. 이 세션은 실험 동안 Testcontainers를 돌리지 않았으므로 모두 다른 세션의 것이다). 단계마다 실행기 출력은 `<하위 폴더>-runner.log`에 있다.

## 결론

관문을 통과했다. E2는 여섯 번(첫 이미지 다섯, 다시 구운 이미지 하나) 모두 PASS다. E1은 첫 이미지의 다섯 번 가운데 넷이 PASS이고 다섯째가 S4의 E1 FAIL을 재현했다. 원인은 정산 재시도 한도 소진(55P03 두 번, 7.3초)이었고, 설계 4-6의 판단표대로 한도를 늘린(F1) 이미지로 E1 세 번이 모두 PASS다. 같은 이미지로 X1과 E4·E5·E7·COLD도 PASS다. E6은 첫 실행이 판정 결함(kill한 채 둔 옛 리더의 노드 누계를 읽지 못한 원천으로 침)으로 FAIL(공통 판정)이었고, 하네스 계약과 판정을 고친 뒤 다시 돌아 PASS다. 어느 실험에서도 자산·원장 불변식 위반, 구 epoch 쓰기, 주문 `500`(LB 로그, Prometheus `max_over_time`, 노드 누계 세 원천), `recovery_runs` 불일치, '처리되지 않은 예외'·'인증 처리 실패로 500' 로그는 나오지 않았다.

## E1 재현과 F1

첫 이미지의 다섯째 E1(06:33~06:39)에서 06:37:42 리더 api-1의 정산(`cmd_seq=1450`)이 잔고 행 잠금 대기 초과(55P03)를 두 번 만나 첫 시도부터 7,323ms가 지났고, 재시도 한도(시도 4회, 기한 5초)를 넘겨 라이터가 치명으로 끝났다. 로그는 '정산 일시 DB 오류를 재시도 제한 안에서 흡수하지 못했다 ... 시도=2/4, 경과_ms=7323'과 '단일 라이터 루프 정지(fail-fast): resource=matching-engine, epoch=5, sqlstate=55P03'이고, 파티션 스냅샷의 강등 기록은 `WRITER_FATAL: UncategorizedSQLException sqlstate=55P03`이다. 옛 리더는 4.7초 뒤 재구성해 `FOLLOWER`로 돌아왔고 api-2가 epoch 6으로 승격했다. 이 회차도 무결성 위반, 구 epoch 쓰기, 주문 `500`은 없었다.

설계 4-6 판단표의 첫 행(정산 재시도 소진)이므로 F1을 적용했다. DB 설계 §5.4·§6.4와 ADR 0034 결정한 값 11을 먼저 고치고, `SettlementService`의 한도를 시도 8회, 첫 시도부터 15초, 대기 50~100·100~200밀리초 뒤 200~400밀리초로 바꿨다. 한도를 넘기면 여전히 치명이다(설계 13-3). 다시 구운 이미지의 첫째 E1에서 한 정산(`cmd_seq=1412`)이 55P03을 두 번 만나고 셋째 시도에서 끝났다. 두 실패 사이가 3.96초이고 첫 시도도 잠금 대기 초과(2초)까지 걸렸으므로, 종전 한도였다면 둘째 실패에서 기한을 넘겼을 장면이다.

## B1 DB 흔들림 (기록 실험)

새 스택(P2, 봇 300 OPS, 2분 예열)에서 리더의 pg 프록시에 toxiproxy `reset_peer`를 걸었다 지우기를 60초 간격으로 세 번 했다. 첫 주행(500ms)에서 세 번 가운데 둘이 epoch가 올라 설계 7-2 Y6대로 100ms로 줄여 다시 돌았다([B1](B1/result.json), [B1-r2](B1-r2/result.json)). 두 주행 모두 안전 축(불변식 위반 0, 세 원천 `orders_500_0`, '처리되지 않은 예외'·'인증 처리 실패로 500' 0줄, 드레인)이 참이었고 `recovery_runs` 불일치는 0이다.

다시 구운 이미지로 한 번씩 돌았다([regress](regress/summary.json)). 판정은 S4 설계 7-2의 X2~X5와 같고 공통 판정의 S4b 축(세 원천 `orders_500_0`, `recovery_runs` 불일치 0과 성공 양성 축, 두 api 로그의 '처리되지 않은 예외'·'인증 처리 실패로 500' 0줄)을 더했다.

## X7 처리량 기록 (선택, 판정 아님)

S3 이미지(`s3ref` = `sha256:6d97e047…`)와 다시 구운 이미지를 번갈아 칸마다 새 스택에서 돌았다. 러너와 조건은 S4 재주행과 같다([roundtrip_probe.py](../../scale/roundtrip_probe.py), 12마켓 600/s, 부하 계정 16개, 봇 20 OPS 예열 뒤 k6 130초, 프로필 `dev,chaos-monkey`와 append 분포 오버레이). 칸 이름의 S4a·S4b는 S4 이미지의 첫째·둘째 칸이라는 뜻이다. 판정 보조는 [X7/judge.json](X7/judge.json)이다.

잡음 n = |171.1 - 103.3| / 137.2 = 0.49가 0.10을 넘어 판정 보조는 '칸 추가 필요'다. 손실 L = 1 - 145.6/137.2 = -0.06은 판단에 쓰지 않는다. S3b 칸 뒤 호스트 표본은 전체 CPU 46~69%에 도구 밖의 바쁜 프로세스 1개였고, 그 칸의 append(46.2ms)와 직렬 시간(27.1ms/명령)이 다른 칸보다 컸다. 범위를 중앙값으로 나누는 잡음 식은 칸을 더해도 이 한 칸의 이탈을 지우지 못하므로 더 돌지 않았다. 칸 값은 네 칸 모두 나왔고, 1분 창 값은 저널 행 기준보다 6~40% 낮았다(S4 재주행이 본 오르막 창 문제). 모든 칸에서 400은 0건, 드레인 뒤 `summary.sql` CRITICAL·HIGH PASS, 교착 증가 0, 리더 주문 접수 5xx 0이다. S4 칸 리더의 `429`는 접수 경합(55P03 18, 잠금 대기 상한 12·14)이다.

## 끝 상태

Final 단계(08:34)에서 `-p exchange-pml` 스택을 `down -v --remove-orphans`로 지웠다. 남은 `chaos-*` 컨테이너와 `exchange-pml` 볼륨은 없다([docker-ps-after.txt](docker-ps-after.txt), [volume-ls-end.txt](volume-ls-end.txt)는 빈 파일). `:pml`은 다시 구운 이미지(`e7baeb2f…`, `s4b2ref`)를 가리킨다. 참조 태그 `s4bref`(첫 이미지), `s4r1ref`, `s3ref`와 `:local`은 그대로다. 컨테이너 로그 원문은 저장소 밖 `%TEMP%\pml-s4b-logs`의 하위 폴더(`B1`, `B1-r2`, `E2-r1`~`E2-r5`, `E1-r1-E1`~`E1-r5-E1`, `E2-f1`, `E1-f1-r1-E1`~`E1-f1-r3-E1`, `regress`, `regress-E6r`)에 있다. X1과 X7은 로그 원문을 남기지 않고 문구 수만 결과 파일에 남겼다.

## 한계

- 실험마다 로컬 Docker Desktop 단일 호스트의 결과이고 AWS의 장애나 처리량을 대신하지 않는다. DB 모드는 P2이고 파티션은 하나다.
- 원인 A 가운데 재생 도중 DB가 끊기는 분기는 스택에서 타지 않았다. E1의 F2 경로(재확인이 참인 fencing 거부)도 나오지 않아 적용하지 않았다.
- B1은 기록 실험이라 판정 기준값이 없다. 흔들기의 절반이 라이터 치명으로 N/A였다.
- 다시 구운 이미지의 앞부분에는 다른 세션의 서버 시험이 함께 돌았다. 시간 축에서 FAIL한 실험은 없었다.
- X7은 잡음(0.49)이 커서 손실을 판단하지 못했다. S7 전에 조용한 호스트에서 다시 잰다.
- E6 첫 실행의 FAIL은 이 주행에서 고친 판정 결함이다. 고친 판정으로 E6만 다시 돌았다.
- 실행기, `judge_x7.py`, B1 단계, F1 값은 AI가 정했고 사용자 확인 대상이다. 코드와 증거는 커밋하지 않았다. `docs/measurements/`는 고치지 않았다(문서 단계).
