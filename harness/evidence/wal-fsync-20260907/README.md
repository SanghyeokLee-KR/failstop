# WAL fsync 실측과 저장소 규격 요구 (2026-09-07)

증거 `scenario-20260907` 이 `synchronous_commit=off` 로 주문 처리가 77.1 에서 128.8/s 로
오르는 것을 쟀다. 커밋 플러시가 단일 라이터의 지배 비용이라는 뜻이다. 그 비용의 정체를 잰다.

## 이 저장소의 fsync 실력

`pg_test_fsync -s 5`, 8kB 한 번 쓰기 기준.

| 방식 | 초당 | 건당 |
|---|---|---|
| **fdatasync (현재 설정)** | **311.9** | **3.206ms** |
| open_datasync | 298.5 | 3.350ms |
| fsync | 147.2 | 6.794ms |
| open_sync | 142.8 | 7.004ms |

**현재 설정이 이미 가장 빠른 방식이다.** `wal_sync_method` 를 바꿔 얻을 것이 없다.

## 산술. fsync 가 천장을 정한다

명령 하나가 최소 두 번 커밋한다. 저널 적재 한 번, 정산 한 번이다.

| 항목 | 값 |
|---|---|
| 천장 | 99 주문/s |
| 요구 fsync | 99 x 2 = **초당 198 회** |
| 저장소 능력 | 초당 312 회 |
| **사용률** | **63%** |
| 주문당 fsync 시간 | 2 x 3.206 = **6.41ms** |
| 천장에서 주문당 라이터 시간 | 1000/99 = **10.1ms** |
| **fsync 가 차지하는 몫** | **63%** |

**저장소 사용률 63% 와 라이터 시간 점유 63% 가 같은 값으로 만난다.** 그리고 `synchronous_commit`
을 껐을 때의 +67% 와도 맞는다. 세 경로가 같은 결론을 가리킨다.

## 3.2ms 는 하드웨어가 아니라 WSL2 다

| 저장 위치 | fdatasync | 건당 |
|---|---|---|
| WSL2 VHDX (현재 볼륨) | 313.2 ops/s | **3.193ms** |
| 별도 도커 볼륨 | 322.5 ops/s | 3.101ms |
| **RAM(tmpfs)** | **641097 ops/s** | **0.002ms** |

**RAM 과 1600 배 차이다.** 3.2ms 의 거의 전부가 저장 계층 지연이고 PostgreSQL 이 하는 일이
아니다.

별도 볼륨으로 빼도 3% 차이로 오차 범위다. Docker Desktop 의 볼륨이 전부 같은 WSL2 VHDX 안에
있어 물리적으로 분리되지 않기 때문이다. **이 PC 에서는 WAL 디스크를 개선할 방법이 없다.**

## 그래서 클라우드에 무엇을 요구해야 하나

이 실측이 주는 것은 절대 성능이 아니라 **규격 요구**다.

| 목표 | 필요 fsync |
|---|---|
| 현재 천장 99/s 유지 | 초당 198 회 |
| 천장 2 배(200/s) | 초당 400 회 |
| 천장 3 배(300/s) | 초당 600 회 |

WSL2 의 312 회로는 현재 천장이 63% 사용이라 두 배로 가면 부족하다. **클라우드 스토리지는
쓰기 IOPS 가 아니라 fsync 지연으로 골라야 한다.** 같은 IOPS 라도 지연이 크면 직렬 커밋이
그만큼 밀린다.

배포 시 그 저장소에서 `pg_test_fsync` 를 먼저 돌려 이 표와 대조하는 것이 순서다.

## 코드로 줄이는 길

저장소를 못 바꾸는 구간에서도 **fsync 횟수 자체를 줄일 수 있다.**

명령 하나가 두 번 커밋하는 것을 한 번으로 묶으면 요구가 절반이 된다. 여러 명령을 한 저널
트랜잭션에 묶는 방식이고, 앞선 조사에서 `T6-E` 회귀(`next_value == max(seq)+1`)가 그것을 막지
않음을 확인했다. 한 트랜잭션에서 N 개를 채번하고 N 개를 전부 넣으면 그 단언이 그대로 성립한다.

기대 효과는 실측이 아니라 산술이다. fsync 가 라이터 시간의 63% 이고 그 절반을 없애면 약 31%
가 줄어 천장이 약 1.4 배가 된다. **재보지 않았다.**

## 하면 안 되는 것

| 설정 | 왜 안 되나 |
|---|---|
| `synchronous_commit = off` | 크래시에 최근 커밋을 잃는다. 원장에서 돈이 어긋난다 |
| `fsync = off` | 위와 같고 더 나쁘다 |
| `full_page_writes = off` | 부분 페이지 쓰기에 데이터 파일이 깨진다 |

`synchronous_commit=off` 가 +67% 를 주는 것은 실측했으나 **성능 수단이 아니라 진단 수단으로만
썼다.** 그 값이 fsync 의 몫을 알려준 것이지 채택 가능한 설정이라는 뜻이 아니다.

## 남은 위험

- `commit_delay` 는 재지 않았다. 커밋이 단일 라이터에서 직렬화되어 동시 커밋자가 적으므로
  효과가 없을 것으로 보았으나 확인하지 않았다.
- 체크포인트 영향을 분리하지 않았다. `checkpoints_timed 15, requested 1` 로 요청 체크포인트가
  드물어 큰 축은 아니라고 보았다.
- 클라우드 스토리지의 실제 fsync 지연은 문헌값도 인용하지 않았다. 배포 시 직접 재야 한다.
- 커밋 횟수를 절반으로 줄이는 방안의 기대 효과는 산술이고 측정이 아니다.
