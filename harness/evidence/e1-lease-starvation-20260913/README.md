# E1 리스 갱신 잠금 굶김 (2026-09-13)

## 결론

E1(리더 DB 경로 지연 200ms, 지터 100ms)이 현 코드에서 세 번 연속 FAIL 이다. 셋 다 epoch 1 -> 2 로
페일오버가 났다. E1 은 페일오버가 없어야 하는 실험이다.

원인은 리더 자신의 정산 트랜잭션이 리스 갱신을 막는 것이다. 정산 머리말의
`assert_and_lock_leader`(V30)가 `leader_lease` 행을 FOR SHARE 로 잡고 커밋까지 쥔다.
`renew_leader_lease`(V1)는 같은 행의 UPDATE 다. 지연이 걸리면 정산 트랜잭션이 길어지고, 공유
잠금을 쥔 트랜잭션이 교대로 이어져 갱신 UPDATE 가 TTL 6초 안에 잠금을 얻지 못한다.

## 한계

- 표본 간격이 0.5초이고 실행 중인 갱신 문장만 본다. 잠금 그래프 전체를 뜨지 않았다.
- 단일 라이터 코드(마켓별 라이터 배선 cd2e026 이전)로 같은 조건을 다시 돌려 대조하지 않았다.
  FOR SHARE 는 저장소 첫 커밋부터 있었고 E1 최종 PASS 는 2026-08-07 이다. 라이터가 12개로 늘어
  공유 잠금이 끊김 없이 겹친다는 설명은 막은 쪽 pid 가 바뀌는 관측에서 나온 추정이다.
- 갱신이 대기 전 시각으로 만료 시각을 박는다는 해석은 수치 일치에서 나온 추정이다.
  PostgreSQL 재평가 규칙을 따로 재현하지 않았다.
- `log_lock_waits` 가 off 라 DB 로그에는 대기 기록이 없다.

## 재현

카오스 스택을 `harness/scripts/up.ps1` 로 올린 뒤 chaos-pg 안에서 `lease-locks.txt` 를 만든 표본
질의를 0.5초마다 돌리고 `harness/scripts/e1-pg-latency.ps1` 을 실행한다. 표본 질의는
`pg_stat_activity` 에서 `renew_leader_lease` 를 실행 중인 행의 대기 유형, 경과, `pg_blocking_pids` 와
막은 쪽 질의 앞 60자를 뽑는다.
