X3의 판정은 사전에 정한 본 회차(rpo_records 0)의 PASS이고, 반복 재현성은 주장하지 않는다. 실행기는 이제 `-Protocol 2`의 분리 판정에 rpo_records와 사후 창 C13A 축을 건다(`FAIL(rpo_records)`). 이 변경은 이 폴더의 주행 뒤에 넣었고 스택으로 돌려 보지 않았다. 원자료 `X3-r1/summary.json`·`X3-r2/summary.json`의 분리 판정 PASS는 그때 실행기가 낸 값이라 고치지 않았다. - 재적재된 예약 명령. E7 반복 r2에서 멈춘 리더가 저널에 적은 예약 명령 1건을 새 리더가 승격 재생에서 정산했다(`reserved_settled_by_later_epoch` 1, 드레인 뒤 정산 전 예약 0, C31·C14' 0). 나머지 실험에는 그런 명령이 없어 그 축을 주장하지 않는다.
- 멈춘 리더의 트랜잭션. 본 회차와 r1·r3은 pause가 트랜잭션 밖에서 걸려 승격 획득이 기다리지 않았다. r2는 멈춘 리더의 트랜잭션 하나가 `idle_in_transaction_session_timeout`(10초)으로 끊길 때까지 획득이 약 4초 기다렸다. TTL보다 짧아 V52 전 판에서도 결과가 같았을 경우다. 잠금 대기 백엔드는 표본에서 최대 1이었고, 잔고 행 tuple 잠금을 기다린 백엔드는 표본에 없었다(2초 간격).

run2 X3(V52 전 이미지)은 FAIL이다([run2-5fdc5b95/X3](run2-5fdc5b95/X3/)). 멈춘 리더의 세션 둘이 10초와 20초에 끊겼고(pg 로그), 승격 획득은 약 14.5초를 기다린 뒤 이미 만료된 리스(epoch 6, lease_until이 승격 8초 전)를 받았다. 새 리더는 첫 접수에서 `fencing 위반: 리스 만료`로 종신 강등했고 실험 끝까지 리더가 없었다(RTO 없음, 503 3,420건). 폭발 반경은 가용성이다. 강등된 리더의 첫 접수는 거부됐고 사후 권위 run과 드레인 뒤 `summary.sql`의 불변식은 0이다. X3의 최종 판정은 V52 이미지의 본 회차와 반복 세 회다.

| P1c | 86.7 | 9.46 | 12.48 | 2.16 | 3.21 | 62.4/87.8 | 35.05 | 4,798 | 0 |
| P2c | 106.9 | 20.38 | 26.80 | 1.88 | 3.54 | 83.6/115.6 | 17.14 | 3,794 | 22,879 |

P1a·P1b의 잡음 n = 0.106이 0.10을 넘어 규칙대로 P1c·P2c를 더 돌렸다. 세 칸 중앙값은 P1 138.1/s, P2 120.1/s, L = 0.131이고 n = (153.6 - 86.7) / 138.1 = 0.485라 이 측정은 NOT RUN이다. 첫 두 칸의 값(138.1, 153.6)만으로도 범위/중앙값이 0.101보다 작아질 수 없어, 셋째 칸이 어떤 값이어도 NOT RUN이었다. P1c는 같은 이미지·설정의 P1a보다 37% 낮았고 라이터 직렬 시간도 25ms에서 35ms로 늘었다. 원인은 재지 않았다. 참고 구간 [L - n, L + n] = [-0.354, 0.615]는 0.20을 걸친다.

판정과 별개로 구조적인 차이는 되풀이됐다. 12마켓에서 P2의 명령당 접수 락 보유는 세 칸 모두 19~21ms로 P1(8~9.5ms)의 두 배를 넘었고, 대부분 머리말(22~27ms)이다. 부하 계정 16개가 12마켓에 모두 주문하므로, 한 마켓의 접수가 다른 마켓 접수가 쥔 같은 사용자의 잔고 행을 기다리는 동안 자기 마켓의 접수 락을 쥔다(추론, 아래 잠금 대기 표본이 뒷받침한다). 잠금 대기 백엔드 평균이 P2 칸 1.7~3.3, P1 칸 0.7~1.1이었다. 반대로 라이터의 명령당 직렬 시간은 P2가 13.6~17.1ms로 P1(24.4~35.1ms)보다 짧았다. 이 주행에서 api-1 CPU 표본은 P2c(23%)를 빼고 약 100%였다. 두 차이가 12마켓 합 접수율로 어떻게 번지는지는 잡음 속에서 가려지지 않았다.

결정 5는 두 측정이 모두 PASS여야 통과이고 NOT RUN이 남으면 판정하지 않은 것이다(설계 7-3). 그래서 결정 5는 미판정이고 S4로 넘어가지 않는다. FAIL은 아니므로 설계 4-17의 2단계 예약 검토는 규칙상 시작 조건이 아니다. 다만 12마켓의 접수 락 보유 증가가 되풀이됐으므로, 조용한 환경에서 600/s 측정을 다시 할 때 FAIL이면 그 검토가 바로 필요하다.

## X7 감사 문장의 누적 행 비용: PASS

스택 없이 폐기용 `postgres:17-alpine` 컨테이너 하나(`--rm`, 127.0.0.1 무작위 포트, 이름 `pml-probe-s3scale-x7-*`)에서 [X7/s3-scale-probe-12m.sh](X7/s3-scale-probe-12m.sh)를 돌렸다. 저장소의 V0~V52를 올리고 12마켓 시드([X7/seed-12m.sql](X7/seed-12m.sql)) 위에 P2 epoch의 합성 주문 생성 명령을 넣었다. 명령마다 예약 행, SEALED RESERVE 거래와 분개 둘을 두고, 마켓마다 마지막 300건을 뺀 나머지는 정산된 것처럼 두었다([X7/s3-scale-apply-12m.sh](X7/s3-scale-apply-12m.sh)). 트리거를 끄고 넣은 합성 행이라 원장 균형과 잔고 정합은 성립하지 않고 시간만 본다(C14' 값 12는 그 결과다). 문장은 문서 사본이 아니라 코드에서 뽑았다([extract_sql.py](extract_sql.py): 앱 C14'·C31 앱 판·C05, `ReservationBacklogMonitor` 게이지, 하네스 C31 전수 판, 전환 선행 조건). 권위 run과 같은 `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY` 안에서 `EXPLAIN (ANALYZE, BUFFERS)`를 두 번 돌려 둘째 `Execution Time`을 썼다([stmt_timing.py](stmt_timing.py)). 컨테이너가 보는 CPU는 16, 메모리는 약 15.2GiB이고 PostgreSQL 17.10 기본 설정(shared_buffers 160MB, work_mem 4MB, JIT 켬)이다.

## X6 R1 스택 판: NOT RUN

설계 7-3 X6은 S2 이미지를 이미지 id로 띄워야 한다. 이 단계의 규칙은 실험 스택을 `exchange-chaos-app:pml` 태그로만 띄우는 것이고, 그 태그는 S3 이미지로 옮겨졌다. 이미지 id로 띄우는 것도 태그 규칙 밖이라 돌리지 않았다. 6-2의 `ProtocolRollbackR1Test`가 Testcontainers 일회용 DB에서 일부를 대신한다. 그 시험은 P2 -> P1 되돌림 뒤 S3 바이너리의 P1 경로와 전량 재생 결정론을 보고, 구현 검토 뒤에는 S2 바이너리의 SQL(3인자 획득, 6인자 머리말, 저널 행 함수, 정산 머리말, 2인자 게시)로 리더가 되어 P2 예약 주문과 체결·취소하는 단계를 더했다. 정산 본체는 S3 바이너리의 P1 정산이라 S2 이미지 자체를 띄운 판은 아니다(부분 대체).
