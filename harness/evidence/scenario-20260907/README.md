# 사고 대응 시나리오 전구간 실측 (2026-09-07)

기획한 이야기를 한 번에 이어서 돌린다.

```
DB 과부하 -> DB 스케일 업 -> DB 안정화, 처리량 상승
-> 앱 CPU 과부하 -> 노드 증설과 로드밸런서 분산 -> 정상 가동
```

## 환경

| 구성 | 값 |
|---|---|
| 앱 1번(리더) | 2 vCPU, 1GB |
| 앱 2번(읽기 전용) | 2 vCPU, 1GB, `exchange.engine.enabled=false` |
| DB | 단계마다 조정 |
| 로드밸런서 | nginx. 조회는 `least_conn` 두 노드, 쓰기는 리더 단독 |
| 부하 | k6. 주문은 `calibrate.js`, 조회는 `reads_only.js` |

부하는 전부 로드밸런서를 지난다. 노드 증설은 upstream 의 `down` 표시를 지우고 `nginx -s reload`
하는 것이 전부다. 재기동은 없다.

레이트리밋을 `exchange.{order,public}.rate-limit.capacity=1000000` 으로 풀었다. 계약 기본값이면
부하가 429 로 막혀 용량이 아니라 방벽을 재게 된다.

## 1단계. DB 과부하

DB 를 0.3 vCPU 로 묶었다. 저사양 인스턴스를 모사한다.

| 지표 | 값 |
|---|---|
| DB CPU | **29.8% (상한 30% 포화)** |
| 주문 처리 | **13.1/s** |
| 주문 지연 | **459.5ms** |
| 수용 거절 | **118/s** |
| 초당 체결 | 0.6 |

DB 가 느려 주문 하나가 오래 걸리고, 주문 수용 정원 6 칸이 계속 차 있어 초과분이 429 로
거절된다. **거절은 고장이 아니라 노드를 지키는 설계된 백프레셔다.**

## 2단계. DB 스케일 업

`docker update --cpus 4 ex-pg` 로 재기동 없이 올렸다.

| 지표 | 1단계 | 2단계 | 변화 |
|---|---|---|---|
| DB CPU | 29.8% (포화) | 90~101% (여유) | |
| 주문 처리 | 13.1/s | **84.9/s** | **6.5 배** |
| 주문 지연 | 459.5ms | **66.2ms** | **7 배 빠름** |
| 수용 거절 | 118/s | 57.9/s | 절반 |
| 초당 체결 | 0.6 | 6.5 | 10 배 |

**DB 를 올리자 처리량이 6.5 배가 됐다.** 이야기의 첫 매듭이다.

### 다만 이 단계에는 조건이 있다

DB 를 1 vCPU 로만 조였을 때는 이 그림이 나오지 않았다. 그때 DB CPU 는 98% 였는데 주문 지연이
128ms 였고, 4 vCPU 로 올려도 120ms 로 8ms 만 줄었다.

원인은 2026-09-05·06 의 DB 작업 절감이다(`6041f4a` 원장 게시의 재조회 셋 제거, `2d0978d` 마켓
카탈로그 TTL 캐시). 주문 하나가 DB 에 하는 일이 줄어 **1 vCPU 로도 DB 가 병목이 아니게 됐다.**
그 상태에서 병목은 주문 수용 정원 6 칸이었다(`admission` 엔드포인트 실측: order inFlight 6/6,
주문 HTTP 평균 72ms, 6/0.072 = 초당 83 건이 천장).

**즉 DB 스케일 업 시나리오는 DB 가 실제로 부족할 때만 성립한다.** 0.3 vCPU 는 그 상태를 만들기
위한 설정이고, 현행 코드의 실제 DB 여유는 그보다 훨씬 크다.

## 3단계. 앱 CPU 과부하

DB 를 4 vCPU 로 둔 채 조회 부하를 6300/s 까지 올렸다.

| 지표 | 값 |
|---|---|
| 앱 1번 CPU | **197~200% (2 코어 포화)** |
| 앱 1번 처리 | 6434 req/s |
| 앱 2번 | 0 req/s (로드밸런서에서 제외 상태) |
| 주문 처리 | 75.6 -> **59.7/s** |
| 주문 지연 | 72.5 -> **91.8ms** |
| 초당 체결 | 9.2 -> 4.6 |

**조회 부하가 앱 CPU 를 다 먹자 주문까지 느려진다.** 두 축이 같은 CPU 를 쓰기 때문이다.
DB 는 이 구간에서 99% 로 여유가 있었다. 병목이 DB 에서 앱으로 넘어간 순간이다.

## 4단계. 노드 증설과 분산

upstream 의 `down` 을 지우고 reload 했다. 걸린 시간은 1 초 미만이다.

| 지표 | 증설 전 | 증설 후 |
|---|---|---|
| 앱 1번 CPU | **198.8%** | **159.0%** |
| 앱 2번 CPU | 0.2% | **131.7%** |
| 앱 1번 처리 | 6434 req/s | 3430 req/s |
| 앱 2번 처리 | 0 req/s | **2941 req/s** |

**조회가 54 대 46 으로 나뉘고 1 번 노드의 CPU 여유가 돌아왔다.**

### 총 처리량은 늘지 않았다

증설 전후 합계가 6434 와 6371 로 같다. 부하가 고정이라 한 노드가 이미 그 전부를 처리하고
있었고, 증설이 준 것은 처리량이 아니라 **여유**다.

용량이 실제로 늘었는지는 부하를 1 대의 한계 위로 올려 확인했다.

| 조회 9000/s, 2 노드 | 값 |
|---|---|
| 앱 1번 | 3761 req/s @ 116% |
| 앱 2번 | 3784 req/s @ 119% |
| 합계 | **7545 req/s** |

1 대가 199% 로 포화해 낸 값이 6434 req/s 였다. 2 대는 각각 118% 로 7545 req/s 를 낸다.
**용량이 늘고 여유도 함께 생겼다.**

## 이 시나리오가 말하지 않는 것

**주문 처리량은 증설로 늘지 않는다.** 4 단계에서 주문이 56.8/s 에서 54.3/s 로 오히려 조금
줄었다. 쓰기는 단일 라이터 한 대로만 가고, 늘어난 조회가 DB 를 더 쓰면서 주문 경로와 경합하기
때문이다(DB CPU 110% -> 159~205%).

그래서 대응이 축마다 갈린다.

| 축 | 늘어나는 트래픽에 | 근거 |
|---|---|---|
| 조회 | **노드를 늘려 나눈다** | 4 단계 |
| 주문 | **거절로 막는다** | 1 단계 수용 거절 118/s |
| DB | **스펙을 올린다** | 2 단계 6.5 배 |

발표 문장은 이렇게 쓴다.

> 조회는 늘려서 나누고, 주문은 거절로 막고, DB 는 올린다. 세 축의 대응이 다르다.

## 실측이 실패한 부분

- **1 노드 대 2 노드 대조가 오염됐다.** 조회 9000/s 를 걸어 둔 채 2 번 노드를 빼자 지연이 늘어
  k6 의 `constant-arrival-rate` 가 `maxVUs` 를 넘겨 반복을 버리기 시작했다. 그래서 1 노드
  구간의 요청 수(3224/s)는 서버 능력이 아니라 부하 도구가 던지기를 멈춘 값이다. 위 표의 1 대
  수치 6434 req/s 는 그 구간이 아니라 3 단계에서 잰 값이다.
- **처음 시도한 조회 11700/s 는 부하 도구가 먼저 무너졌다.** k6 컨테이너가 8GB 상한에 붙고
  VU 가 28000 개까지 늘었다. 조회 전용 경량 스크립트와 VU 상한으로 바꿔 다시 쟀다.

## 남은 위험

- 2 번 노드가 `/actuator/health` 에 `OUT_OF_SERVICE` 를 낸다. 리더가 아니라서다. nginx 는 실제
  요청 실패로만 노드를 빼므로 이 구성에서는 문제가 없지만, **AWS ALB 였다면 헬스체크에서
  탈락해 조회 분산 자체가 성립하지 않는다.** 읽기 전용 노드용 헬스 경로가 필요하다.
- 3 단계와 4 단계 사이에 부하를 바꾸지 않았으나, 5 단계(9000/s)는 별도 실행이라 앞 구간과
  같은 창에서 잰 값이 아니다.
- 각 단계를 한 번씩만 쟀다. 반복 분산은 모른다.
- 오토스케일링 자체는 재지 않았다. 노드를 사람이 붙였다. 자동 판단·기동·투입의 소요 시간은
  미측정이다.

원자료는 `lb_nginx.conf`(로드밸런서 설정), `reads_only.js`(조회 전용 부하).
