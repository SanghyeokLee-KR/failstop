# 사고 대응 시나리오 전구간 실측 (2026-09-07)

기획한 이야기를 한 번에 이어서 돌린다.

```
DB 과부하 -> DB 스케일 업 -> DB 안정화, 처리량 상승
-> 앱 CPU 과부하 -> 노드 증설과 로드밸런서 분산 -> 정상 가동
```

## 환경

| 구성 | 값 |
|---|---|
| 앱 1번(리더) | 2 vCPU, 1GB |
| 앱 2번(읽기 전용) | 2 vCPU, 1GB, `exchange.engine.enabled=false` |
| DB | 단계마다 조정 |
| 로드밸런서 | nginx. 조회는 `least_conn` 두 노드, 쓰기는 리더 단독 |
| 부하 | k6. 주문은 `calibrate.js`, 조회는 `reads_only.js` |

부하는 전부 로드밸런서를 지난다. 노드 증설은 upstream 의 `down` 표시를 지우고 `nginx -s reload`
하는 것이 전부다. 재기동은 없다.

레이트리밋을 `exchange.{order,public}.rate-limit.capacity=1000000` 으로 풀었다. 계약 기본값이면
부하가 429 로 막혀 용량이 아니라 방벽을 재게 된다.

## 1단계. DB 과부하

DB 를 0.3 vCPU 로 묶었다. 저사양 인스턴스를 모사한다.

| 지표 | 값 |
|---|---|
| DB CPU | **29.8% (상한 30% 포화)** |
| 주문 처리 | **13.1/s** |
| 주문 지연 | **459.5ms** |
| 수용 거절 | **118/s** |
| 초당 체결 | 0.6 |

DB 가 느려 주문 하나가 오래 걸리고, 주문 수용 정원 6 칸이 계속 차 있어 초과분이 429 로
거절된다. **거절은 고장이 아니라 노드를 지키는 설계된 백프레셔다.**

## 2단계. DB 스케일 업

`docker update --cpus 4 ex-pg` 로 재기동 없이 올렸다.

| 지표 | 1단계 | 2단계 | 변화 |
|---|---|---|---|
| DB CPU | 29.8% (포화) | 90~101% (여유) | |
| 주문 처리 | 13.1/s | **84.9/s** | **6.5 배** |
| 주문 지연 | 459.5ms | **66.2ms** | **7 배 빠름** |
| 수용 거절 | 118/s | 57.9/s | 절반 |
| 초당 체결 | 0.6 | 6.5 | 10 배 |

**DB 를 올리자 처리량이 6.5 배가 됐다.** 이야기의 첫 매듭이다.

### 다만 이 단계에는 조건이 있다

DB 를 1 vCPU 로만 조였을 때는 이 그림이 나오지 않았다. 그때 DB CPU 는 98% 였는데 주문 지연이
128ms 였고, 4 vCPU 로 올려도 120ms 로 8ms 만 줄었다.

원인은 2026-09-05·06 의 DB 작업 절감이다(`6041f4a` 원장 게시의 재조회 셋 제거, `2d0978d` 마켓
카탈로그 TTL 캐시). 주문 하나가 DB 에 하는 일이 줄어 **1 vCPU 로도 DB 가 병목이 아니게 됐다.**
그 상태에서 병목은 주문 수용 정원 6 칸이었다(`admission` 엔드포인트 실측: order inFlight 6/6,
주문 HTTP 평균 72ms, 6/0.072 = 초당 83 건이 천장).

**즉 DB 스케일 업 시나리오는 DB 가 실제로 부족할 때만 성립한다.** 0.3 vCPU 는 그 상태를 만들기
위한 설정이고, 현행 코드의 실제 DB 여유는 그보다 훨씬 크다.

## 3단계. 앱 CPU 과부하

DB 를 4 vCPU 로 둔 채 조회 부하를 6300/s 까지 올렸다.

| 지표 | 값 |
|---|---|
| 앱 1번 CPU | **197~200% (2 코어 포화)** |
| 앱 1번 처리 | 6434 req/s |
| 앱 2번 | 0 req/s (로드밸런서에서 제외 상태) |
| 주문 처리 | 75.6 -> **59.7/s** |
| 주문 지연 | 72.5 -> **91.8ms** |
| 초당 체결 | 9.2 -> 4.6 |

**조회 부하가 앱 CPU 를 다 먹자 주문까지 느려진다.** 두 축이 같은 CPU 를 쓰기 때문이다.
DB 는 이 구간에서 99% 로 여유가 있었다. 병목이 DB 에서 앱으로 넘어간 순간이다.

## 4단계. 노드 증설과 분산

upstream 의 `down` 을 지우고 reload 했다. 걸린 시간은 1 초 미만이다.

| 지표 | 증설 전 | 증설 후 |
|---|---|---|
| 앱 1번 CPU | **198.8%** | **159.0%** |
| 앱 2번 CPU | 0.2% | **131.7%** |
| 앱 1번 처리 | 6434 req/s | 3430 req/s |
| 앱 2번 처리 | 0 req/s | **2941 req/s** |

**조회가 54 대 46 으로 나뉘고 1 번 노드의 CPU 여유가 돌아왔다.**

### 총 처리량은 늘지 않았다

증설 전후 합계가 6434 와 6371 로 같다. 부하가 고정이라 한 노드가 이미 그 전부를 처리하고
있었고, 증설이 준 것은 처리량이 아니라 **여유**다.

용량이 실제로 늘었는지는 부하를 1 대의 한계 위로 올려 확인했다.

| 조회 9000/s, 2 노드 | 값 |
|---|---|
| 앱 1번 | 3761 req/s @ 116% |
| 앱 2번 | 3784 req/s @ 119% |
| 합계 | **7545 req/s** |

1 대가 199% 로 포화해 낸 값이 6434 req/s 였다. 2 대는 각각 118% 로 7545 req/s 를 낸다.
**용량이 늘고 여유도 함께 생겼다.**


## 5단계. 커넥션 풀을 키우면 주문이 늘어나는가 (아니다)

2 단계에서 DB 를 4 vCPU 로 올려도 주문이 84.9/s 에서 멈췄다. 그 지점의 병목은 주문 수용 정원
6 칸이고, 그 6 은 커넥션 풀 16 에서 유도된다(`AdmissionLimits`, 16 x 0.40). 그래서 물었다.
**DB 가 커졌으면 앱도 커넥션을 더 열어 그 자원을 쓰면 되지 않는가.**

풀을 16 에서 48 로 올려 쟀다(정원 6 -> 19).

| 지표 | 풀 16 (정원 6) | 풀 48 (정원 19) |
|---|---|---|
| 주문 처리 | 86.5/s | **83.1/s** |
| 주문 지연 | 67.4ms | **226.8ms** |
| 수용 거절 | 179/s | 181/s |
| 앱 CPU | 53% | 49% |
| DB CPU | 93% | 98% |

**처리량이 오르지 않았다.** 정원을 3.2 배로 늘렸더니 지연이 3.4 배가 됐다. 정원 나누기 지연이
그대로다.

풀 48 구간의 커넥션 상태가 이유를 말한다.

| 지표 | 값 |
|---|---|
| `hikaricp_connections_active` | **2** |
| `hikaricp_connections_idle` | **20** |
| `hikaricp_connections_pending` | **0** |
| `exchange_sequencer_queue_size` | **17** |

**커넥션은 남아돈다.** 48 개 중 2 개만 쓰고 대기는 0 이다. 밀려 있는 것은 시퀀서 큐 17 건이다.
병목이 커넥션이 아니라 단일 라이터 매칭 엔진 루프라는 뜻이다. 주문은 한 스레드를 통과해야
하고 그 스레드의 처리율이 고정이라, 커넥션을 늘리면 큐에 더 많이 들어갈 뿐 나가는 속도는
같다. 늘어나는 것은 대기 시간뿐이다.

이 결과는 수용 정원의 설계를 뒷받침한다. **정원 6 은 처리량을 깎는 것이 아니라 지연을 지킨다.**
같은 86/s 를 내면서 지연이 67ms 냐 227ms 냐의 차이다.

주문 처리량을 올리려면 커넥션이 아니라 단일 라이터의 처리율을 올려야 한다. 저널 적재가
1 건당 5.15ms 로 그 스레드 시간의 44% 를 쓴다.

## 6단계. 한 대로 못 버티는 부하에서 증설이 무엇을 하는가

4 단계는 부하가 고정이라 한 노드가 이미 전부를 처리하고 있었고 증설이 준 것은 여유뿐이었다.
**한 대로는 버틸 수 없는 부하**를 걸어야 증설이 정상화를 만드는 장면이 나온다.

부하 방식을 바꿨다. 도착률 방식은 서버가 느려지면 k6 가 반복을 버려 서버 능력이 아니라 부하
도구가 포기한 값이 찍힌다(4 단계 대조가 그것 때문에 오염됐다). 고정 VU 600 개가 응답을 기다렸다가
다음을 보내는 폐쇄 루프로 바꿨다. 나온 처리량이 곧 서버가 낸 값이다.

| | A. 2 노드 | B. 1 노드 | C. 증설 회복 |
|---|---|---|---|
| 앱 1번 처리 | 4364 req/s | 3982 -> **1916 req/s** | 4195 req/s |
| 앱 2번 처리 | 4336 req/s | 0 | 4200 req/s |
| **합계** | **8700 req/s** | **1916~3982 req/s** | **8395 req/s** |
| 앱 1번 CPU | 153% | **204% (포화)** | 141% |
| 앱 2번 CPU | 149% | 0.1% | 150% |
| 주문 지연 | 78.7ms | **155.4ms** | 107.6ms |

**같은 사용자 수요에서 2 노드는 8700 req/s 를 내고 1 노드는 2000~4000 req/s 에서 포화한다.**
1 노드 구간은 CPU 가 204% 로 두 코어를 다 쓰고도 처리량이 불안정하게 흔들린다. 주문 지연도
78.7ms 에서 155.4ms 로 두 배가 된다. 조회 부하가 같은 CPU 를 먹기 때문이다.

노드를 다시 붙이면 8395 req/s 로 돌아온다. **한 대로는 장애, 두 대면 정상이다.** 이것이
`부하 분산 -> 정상 가동` 이 성립하는 조건이다.

### 그래서 4 단계의 질문에 대한 답

`부하 분산 -> 정상 가동` 을 보이려면 DB 를 더 조일 필요가 없다. **사용자를 더 부르면 된다.**
DB 과부하는 1~2 단계의 레버이고, 증설은 3~6 단계의 레버다. 둘은 다른 축이다.

## 이 시나리오가 말하지 않는 것

**주문 처리량은 증설로도 커넥션으로도 늘지 않는다.** 4 단계에서 주문이 56.8/s 에서 54.3/s 로
오히려 조금 줄었고(늘어난 조회가 DB 를 더 써 주문 경로와 경합한다. DB CPU 110% -> 159~205%),
5 단계에서 커넥션 풀을 3 배로 늘려도 86.5/s 에서 83.1/s 로 제자리였다. 쓰기는 단일 라이터 한
스레드를 통과해야 하고 그 처리율이 천장이다.

다만 증설은 주문의 **지연**을 지킨다. 6 단계에서 1 노드 포화 구간의 주문 지연이 155.4ms 이고
2 노드 구간이 78.7ms 다. 조회를 나눠 CPU 를 비워 주면 주문이 그만큼 빨라진다.

그래서 대응이 축마다 갈린다.

| 축 | 늘어나는 트래픽에 | 근거 |
|---|---|---|
| 조회 | **노드를 늘려 나눈다** | 4 단계 |
| 주문 | **거절로 막는다** | 1 단계 수용 거절 118/s |
| DB | **스펙을 올린다** | 2 단계 6.5 배 |

발표 문장은 이렇게 쓴다.

> 조회는 늘려서 나누고, 주문은 거절로 막고, DB 는 올린다. 세 축의 대응이 다르다.

## 실측이 실패한 부분

- **1 노드 대 2 노드 대조가 오염됐다.** 조회 9000/s 를 걸어 둔 채 2 번 노드를 빼자 지연이 늘어
  k6 의 `constant-arrival-rate` 가 `maxVUs` 를 넘겨 반복을 버리기 시작했다. 그래서 1 노드
  구간의 요청 수(3224/s)는 서버 능력이 아니라 부하 도구가 던지기를 멈춘 값이다. 위 표의 1 대
  수치 6434 req/s 는 그 구간이 아니라 3 단계에서 잰 값이다.
- **처음 시도한 조회 11700/s 는 부하 도구가 먼저 무너졌다.** k6 컨테이너가 8GB 상한에 붙고
  VU 가 28000 개까지 늘었다. 조회 전용 경량 스크립트와 VU 상한으로 바꿔 다시 쟀다.

## 남은 위험

- (해소) 2 번 노드가 `/actuator/health` 에 `OUT_OF_SERVICE` 를 내는 것은 설계다. 그것을 조회
  분산 대상 헬스로 쓰면 ALB 가 팔로워를 빼 분산이 성립하지 않는다. 조회 전용 그룹
  `/actuator/health/read` 를 신설해 닫았다. 실측에서 팔로워가 readiness 503, read 200,
  조회 200 이다.
- 4 단계 끝의 조회 9000/s 측정은 앞 구간과 별도 실행이라 같은 창에서 잰 값이 아니다. 6 단계가
  같은 질문을 폐쇄 루프로 다시 재므로 용량 판정은 6 단계를 쓴다.
- 5 단계는 커넥션 풀만 바꾸고 노드 수와 DB 는 고정했다. 풀을 48 보다 더 키운 구간은 재지 않았다.
- 각 단계를 한 번씩만 쟀다. 반복 분산은 모른다.
- 오토스케일링 자체는 재지 않았다. 노드를 사람이 붙였다. 자동 판단·기동·투입의 소요 시간은
  미측정이다.

원자료는 `lb_nginx.conf`(로드밸런서 설정), `reads_only.js`(조회 전용 부하).
