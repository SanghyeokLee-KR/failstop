# WS 재접속 폭주 실측 (2026-09-07)

증거 `ws-admission-20260907` 이 남긴 위험을 닫는다. 그 회차는 상한을 넘는 연결을 거절해 노드를
지키는 것까지 확인했고, 거절당한 클라이언트가 곧바로 다시 붙는 경우를 재지 않았다.

## 왜 이것을 재야 하는가

거절은 클라이언트를 없애지 않는다. 다시 붙는다. 재시도 간격이 짧으면 거절 처리 자체가 부하가
되고, 상한이 노드를 지키는 대신 다른 방식으로 무너뜨릴 수 있다.

재시도 간격은 실제 웹 클라이언트를 따랐다. `web/lib/api/httpDatasource.ts:209` 의 STOMP 설정이
`reconnectDelay: 2000` 이고 **지터도 지수 백오프도 없다**. 거절이 한꺼번에 나면 재시도도
한꺼번에 온다. 그것이 최악의 경우이고 실제 값이다.

## 방법

도구는 `harness/load/ws_reconnect_storm.js` 를 새로 만들었다. 두 무리를 같이 돌린다.

| 무리 | 수 | 하는 일 |
|---|---|---|
| holders | 1900 | 상한 안에 자리를 잡고 끝까지 버틴다. 폭주 중에도 계속 받아야 한다 |
| stormers | 1600 | 거절당하고 2초 뒤 다시 붙기를 반복한다 |

**판정 축은 노드 생존이 아니라 holders 다.** 노드가 살아도 기존 접속자가 굶으면 장애다.

봇 노드를 함께 띄워 체결이 도는 상태에서 쟀다. 체결이 없으면 holders 가 받을 것이 없어 굶었는지
알 수 없다.

환경은 앱 컨테이너 1GB · 2 vCPU, 최대 힙 742MB, 유도된 상한 1929 다.

## 결과 1. 노드는 견딘다

| 시각 | in_flight | rejected 누계 | health | CPU | 메모리 |
|---|---|---|---|---|---|
| +55s | 1900 | 0 | 200 | 150% | 576MB |
| +110s | **1929** | 18082 | 200 | 133% | 873MB |
| +165s | 1929 | 62452 | 200 | 141% | 993MB |
| +220s | 1900 | **94026** | 200 | 146% | 983MB |

거절이 120 초에 약 94000 건이다. **초당 약 785 건**이다. 그동안 health 는 200 을 유지하고
`OutOfMemoryError` 는 0 건이다. 부하가 끝나면 `in_flight` 가 0 으로 돌아온다.

메모리가 993MB 로 1GB 상한에 다가가지만 넘지 않는다. 상한이 그 지점을 묶는다.

## 결과 2. 기존 사용자는 무사하다

| 항목 | 값 |
|---|---|
| `holder_lost` (소켓 끊김) | **0** |
| `holder_stall_window` (10초 이상 무수신 창) | **0** |
| `holder_stalled_any` (한 번이라도 끊긴 사용자) | **0** |
| `holder_msg` | 5900601 |
| 첫 메시지 p50 | 6ms |

**1900 명 중 단 한 명도 10 초 이상 끊긴 적이 없다.** 폭주가 없는 대조군의 수신량이 6142070 이고
폭주 중이 5900601 이라 4% 차이다.

거절이 초당 785 건 나가는 동안에도 이미 붙은 사용자는 계속 받는다. 상한이 노드만이 아니라
기존 사용자도 지킨다.

## 결과 3. 폭주가 지표 결함을 드러냈다

이것이 이번 회차의 가장 큰 소득이다.

폭주 중 `exchange_ws_clients` 게이지가 무너졌다.

| 시각 | ws_clients | in_flight | holder 끊김 |
|---|---|---|---|
| +55s | 1900 | 1900 | 0 |
| +110s | 1610 | 1929 | 0 |
| +165s | **782** | 1929 | 0 |
| +220s | **159** | 1900 | 0 |

**게이지는 접속자가 1900 에서 159 로 사라졌다고 말하는데 실제로는 아무도 끊기지 않았다.**
`holder_stall_window` 가 0 이고 수신량도 대조군과 같다.

### 원인

`WsSessionMetrics.onDisconnect` 가 올린 적 없는 세션에도 값을 내렸다.

```java
// 종전
public void onDisconnect(SessionDisconnectEvent event) {
    active.updateAndGet(n -> n > 0 ? n - 1 : 0);
}
```

Spring 은 STOMP CONNECT 를 마치지 못하고 끝난 세션에도 `SessionDisconnectEvent` 를 낸다. 그
세션은 `SessionConnectedEvent` 를 낸 적이 없다. 평시에는 그런 세션이 드물어 드러나지 않지만
폭주는 그 경로를 초당 수백 건 만든다. `n > 0` 하한은 음수만 막을 뿐 이 어긋남을 막지 못한다.

### 확인 절차

VU 수가 원인일 수 있어 대조군을 따로 두었다. 부하 도구의 VU 를 3500 으로 같게 두고 stormers 가
연결을 맺지 않고 쉬기만 하게 했다(`WS_STORM_IDLE=1`).

| | VU | 서버 폭주 | ws_clients |
|---|---|---|---|
| 폭주군 | 3500 | 있음 | 1900 -> **159** |
| 대조군 | 3500 | 없음 | 1900 -> **1900** |

VU 수가 같은데 폭주군만 무너진다. 부하 도구가 아니라 서버 쪽 계수가 원인이다.

### 고친 뒤

세션 id 로 짝을 맞춘다. 올린 적 있는 세션만 내린다.

| 시각 | ws_clients |
|---|---|
| +55s | 1900 |
| +110s | **1900** |
| +165s | **1900** |
| +220s | **1900** |

같은 폭주(거절 94026 건)에서 게이지가 미동도 없다.

### 왜 이것이 중요한가

이 게이지는 정본이 WS 연결 관측 채널로 지정한 값이다(하네스 CICD·IaC §3-3, §5-2). 폭주 중에
접속자가 92% 사라진 것처럼 보이면 **운영자가 없는 장애를 좇는다.** 이 프로젝트가 다루는 오진이
정확히 그 모양이다. 노드는 멀쩡하고 사용자도 멀쩡한데 화면만 재난을 그린다.

## 결과 4. 클라이언트에 지터와 백오프를 붙였다

노드는 견디지만 초당 785 건의 거절은 아무 일도 하지 않는 순수 낭비다. 줄이려면 서버가 아니라
클라이언트를 고쳐야 한다.

`web/lib/api/httpDatasource.ts` 를 고쳤다.

| 항목 | 종전 | 현행 |
|---|---|---|
| 출발 지연 | 2000ms 고정 | 기준의 0.5~1.5 배에서 뽑음 |
| 실패 시 | 그대로 2000ms | 두 배씩(EXPONENTIAL) |
| 상한 | 없음 | 30000ms |

지터를 접속마다가 아니라 클라이언트마다 준다. stompjs 7.3.0 은 다음 지연을 private 필드에 들고
그 값을 activate 시점과 접속 성공 시점에만 `reconnectDelay` 에서 다시 읽는다. 매 시도에 끼어들
공개 지점이 없다. 대신 클라이언트마다 출발점이 다르면 이어지는 지수 수열도 갈라져 무리가
흩어진다.

같은 폭주(holders 1900, stormers 1600, 120 초)를 두 정책으로 쟀다.

| | 고정 2 초 | 지터 + 백오프 |
|---|---|---|
| 시도 | 95775 | **11998** |
| 거절 | 94026 | **11776** |
| 초당 거절 | 785 | **98** |
| 앱 CPU | 133~150% | 98~123% |
| 앱 메모리 최고 | **993MB** | **868MB** |
| `holder_lost` | 0 | 0 |
| 무수신 창 | 0 | 0 |
| 수신량 | 5900601 | 6082123 |

**시도가 87.5% 줄었다.** 메모리 최고점이 993MB 에서 868MB 로 내려가 1GB 상한과의 여유가 두 배가
됐다. 기존 접속자는 두 정책 모두 무사하다.

거절이 사라지지는 않는다. 상한을 넘는 인원이 있는 한 누군가는 거절당한다. 줄어드는 것은
거절의 빈도이고, 그것이 클라이언트가 할 수 있는 전부다.

## 도구를 만들며 겪은 것

- **k6 의 experimental/websockets 는 close 이벤트에 종료 코드를 싣지 않는다.** 실측으로 확인했다
  (`keys=type,target,timestamp`). 그래서 수용과 거절을 1013 으로 가르지 못하고 메시지 수신 여부로
  가른다. 수용된 연결은 구독 직후 호가 스냅샷을 반드시 한 건 받는다.
- **판정을 타이머와 close 두 곳에 두면 안 된다.** 첫 실행에서 서버가 117825 건을 거절했는데
  클라이언트 거절이 0 건으로 나왔다. `sleep` 이 이벤트 루프를 막는 동안 타이머와 close 가 함께
  큐에 쌓여 타이머가 먼저 돌았다. 판정을 close 한 곳으로 모아 고쳤고, 상한 3 인 노드로 검증했다
  (시도 200 = 거절 200, 미판정 0).
- **총량만 보면 끊김을 못 본다.** 폭주군과 대조군의 수신량이 4% 차이라 그것만으로는 무사한지
  알 수 없었다. 흐름이 끊긴 창을 세는 축이 있어야 갈린다.
- **봇과 거래소는 마스터키를 공유해야 한다.** 안 하면 봇이 발급한 비밀을 거래소가 복호화하지
  못해 주문이 전건 실패하고 `write_completion_ratio` 가 0 이 되어 멀쩡한 거래소가 강등된다
  (실측에서 재현했다). `EXCHANGE_AUTH_MASTER_KEY_BASE64` 를 두 노드에 같은 값으로 준다.

## 남은 위험

- 지터가 클라이언트 단위다. 같은 브라우저가 연속으로 거절당하면 그 수열은 정해져 있다.
  매 시도 지터는 stompjs 의 공개 API 로 불가능하다.
- 지터 효과를 VU 번호 기반 모사로 쟀다. 실제 브라우저의 `Math.random()` 분포와 같지 않다.
  분산이 목적이라 방향은 같지만 값은 다를 수 있다.
- 재시도 간격 2 초 한 점만 쟀다. 더 짧은 간격의 곡선은 모른다.
- 상한을 넘는 인원이 1600 명 한 점이다. 더 큰 폭주는 재지 않았다.
- 인증 세션(`/user/**` 구독)은 재지 않았다. 익명 공개 채널만 쟀다.
- 게이지 수정 뒤의 장시간 거동은 재지 않았다. 세션 id 집합이 오래 도는 노드에서 새지 않는지는
  상한이 묶는다는 논증일 뿐 측정이 아니다.
