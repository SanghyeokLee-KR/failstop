# VM 실습망 nftables 중앙 관리

VM 실습망 여섯 대(웹 진입 서버 EDGE01, 앱 서버 APP01·APP02, DB01·DB02, 관제 서버 OPS01)의 호스트 방화벽 규칙 파일을 이 폴더의 원본 하나로 관리하는 작업 PC 도구다. 지금까지 규칙은 구축·전환 스크립트(`build/scripts`의 00번, 역할별 10~41번, 전환 50~63번)가 VM마다 `/etc/vm-lab/firewall.d/`에 차례로 놓은 파일에 흩어져 있었다. 그래서 어느 VM에 무엇이 열려 있는지 보려면 여섯 대에 하나씩 들어가야 했고, 누가 서버에서 손으로 규칙을 바꿔도 알아챌 방법이 없었으며, 규칙을 고치다 SSH를 막으면 콘솔로 가야 했다. 이 도구는 여섯 대의 지금 파일을 저장소로 가져와 기준선을 만들고(`-Pull`), 원본과 VM이 어긋난 곳을 한 번에 찾고(`-Audit`, `-Plan`), 원본을 한 대씩 구문 검사·백업·자동 되돌리기 예약과 함께 배포한다(`-Apply`).

2026-09-29에 실제 VM 여섯 대에서 기준선을 만들고, 손으로 바꾼 규칙을 찾아 되돌리고, 여섯 대에 해가 없는 규칙을 한 대씩 올렸다가 지웠다. 확인에 실패한 적용을 VM이 90초 뒤 스스로 되돌리는 시험은 EDGE01에서만 했고, 앱·DB 네 대에서는 확인이 통과하는 적용만 했다. 기록은 [2026-09-29 증거본](../../../증거본/2026-09-29_VM_nftables_중앙관리/README.md)에 있다. 로컬 VM 실습 결과이며 학교·개인 AWS의 검증 결과가 아니다.

## 관리 대상

각 VM의 방화벽은 `table inet vmlab` 한 계통이다([정본 결정](../build/02-정본결정.md) 4절). `/etc/vm-lab/firewall.nft`가 테이블을 만들어 비운 뒤 기본 체인(input·forward 기본 차단)을 세우고, 마지막 줄에서 `/etc/vm-lab/firewall.d/*.nft`를 이름 순서로 불러 역할별 규칙을 붙인다. 부팅 때는 `vm-lab-firewall.service`가 같은 파일을 올린다. 이 도구가 다루는 것은 이 두 경로의 파일과 그 파일이 만드는 `inet vmlab` 테이블뿐이다. OPS01에서 Docker가 만든 iptables-nft 테이블, pfSense 두 대의 규칙, 서비스의 바인딩 주소는 건드리지 않는다.

| 경로 | 내용 |
|---|---|
| `nft-central.ps1` | 작업 PC에서 실행하는 도구. pwsh 7 |
| `nft-central-remote.sh` | 도구가 ssh로 VM에 보내 root로 실행하는 부분. 직접 실행하지 않는다 |
| `rules/<vm>/firewall.nft` | VM의 `/etc/vm-lab/firewall.nft` 원본 |
| `rules/<vm>/firewall.d/*.nft` | VM의 `/etc/vm-lab/firewall.d/*.nft` 원본 |

원본 파일은 VM에 설치되는 바이트 그대로다. 줄바꿈은 LF만 쓰고 BOM을 넣지 않는다. nft는 CRLF나 BOM이 있으면 구문 오류로 멈추므로, 도구는 원본에 CR이나 BOM이 있으면 VM에 보내기 전에 멈춘다. 저장소 루트의 `.gitattributes`(`* text=auto eol=lf`)가 체크아웃 때 LF를 지킨다.

## 사용법

작업 PC에 pwsh 7과 OpenSSH가 있고, `~/.ssh/config`에 `edge01`~`ops01` 별칭이 `ops` 계정 키로 잡혀 있어야 한다. VM의 `ops`는 암호 없는 sudo가 있어야 하고, 적용 뒤 확인을 위해 작업 PC에서 L7 입구 `https://192.168.10.10`에 닿아야 한다. 명령은 저장소 루트에서 실행한다.

```powershell
$nc = '.\deploy\vm-lab\nft-central\nft-central.ps1'
pwsh -NoProfile -File $nc -Pull                  # 여섯 대의 지금 파일을 원본으로(기준선)
pwsh -NoProfile -File $nc -Audit                 # 여섯 대 점검표
pwsh -NoProfile -File $nc -Plan -Vm ops01        # 적용하면 바뀔 파일과 커널 규칙
pwsh -NoProfile -File $nc -Apply -Vm ops01       # 한 대 적용
pwsh -NoProfile -File $nc -Apply -All            # 여섯 대를 정해진 순서로 한 대씩
```

`-Vm`에는 쉼표로 여러 대를 줄 수 있다(`-Vm edge01,ops01`). `-Pull`, `-Audit`, `-Plan`은 `-Vm`이 없으면 여섯 대를 모두 본다. `-Apply`는 대상을 빠뜨리지 않도록 `-Vm`이나 `-All`을 반드시 준다.

규칙을 바꾸는 순서는 다음과 같다.

1. `rules/<vm>/firewall.d/`의 파일을 고치거나 새 파일을 만든다. 형식은 `add rule inet vmlab roles ...`이고, 파일 이름 앞의 번호가 체인 안의 순서를 정한다.
2. `-Plan -Vm <vm>`으로 파일 차이, 구문 검사 결과, 지금 커널 규칙과 적용 뒤 규칙의 차이를 본다.
3. `-Apply -Vm <vm>`으로 올린다. 적용 뒤 확인이 모두 통과해야 끝난다.
4. `-Audit`로 여섯 대가 모두 '일치'인지 본 뒤 원본을 커밋한다.

`-Pull`은 VM 파일로 원본을 덮어쓴다. VM에만 있는 파일은 원본에 새로 생기고, VM에 없는 원본 파일은 지운다. 기준선을 처음 만들 때와 VM에서 의도적으로 바꾼 것을 원본으로 받아들일 때만 쓰고, 가져온 뒤 `git diff`로 무엇이 바뀌었는지 본다. 원본은 저장소에 올라가므로 `password`, `secret`, `token`, `webhook`, `powerplatform` 같은 문자열이 든 파일이 있으면 그 VM은 가져오지 않고, 파일 이름과 줄 번호만 알린다. 문자열 패턴 검사라서 모든 비밀 값을 잡는다고 보장하지는 않는다. Windows는 대소문자만 다른 두 파일을 한 폴더에 둘 수 없으므로, VM에 그런 이름이 있으면 역시 가져오지 않는다. 대소문자만 바뀐 이름은 옛 원본 파일을 지우고 VM의 이름으로 다시 쓴다.

## 점검이 보는 것

`-Audit`는 한 줄에 VM 하나를 보여 준다.

| 열 | 뜻 |
|---|---|
| 파일 | VM의 `firewall.nft`와 `firewall.d/*.nft` 목록과 sha256이 원본과 같은지 |
| 커널 규칙 | 지금 커널의 `inet vmlab` 규칙이 VM의 파일로 만든 규칙과 같은지 |
| 규칙 수 | `inet vmlab` 규칙 수 / `nft list ruleset` 전체 규칙 수. OPS01은 Docker 테이블이 전체 수에 들어간다 |
| 서비스 | `vm-lab-firewall.service` 상태 |
| 마지막 적용 | VM의 `/var/log/vm-lab/nft-central.log` 마지막 줄의 시각과 동작 |

'커널 규칙' 열은 파일을 거치지 않은 변경을 잡는다. 누가 `nft add rule`로 규칙을 바로 넣으면 파일 해시는 그대로라서 파일 비교만으로는 보이지 않는다. 도구는 VM 안에 빈 네트워크 이름공간을 만들어 VM의 파일을 실제로 올려 보고, 그 결과와 지금 커널 규칙을 카운터를 뺀 형태(`nft -s list table inet vmlab`)로 글자 단위 비교한다. 이 비교는 호스트의 규칙을 바꾸지 않는다. 파일, 커널 규칙, 서비스가 모두 맞으면 '일치', 하나라도 다르면 '어긋남'이다. 파일 이름은 대소문자와 공백까지 그대로 비교하므로, VM에 `20-edge01 copy.nft`처럼 원본에 없는 이름의 파일이 생기면 nft가 그 파일도 불러 들이는 것과 같이 '어긋남'으로 잡힌다.

네 동작 모두 마지막 줄에 결과와 종료 코드를 알린다. `-Audit`는 모두 일치 0, 어긋남 1, 접속·VM 명령 실패나 응답 형식 오류 2다. `-Plan`은 바꿀 것 없음 0, 바뀔 것 있음 1, 구문 검사나 VM 명령 실패 2다. `-Apply`는 모두 끝나면 0, 한 대라도 실패해 멈추면 1이다. `-Pull`은 모두 가져오면 0, 한 대라도 가져오지 못하면 1이다. 인자 오류, 원본 오류(이름 규칙, CR·BOM)와 예상하지 못한 도구 오류는 네 동작 모두 2다. `-Apply`는 VM을 건드리기 전에 대상 원본을 모두 읽어 이런 오류를 먼저 찾는다.

## 적용 순서와 안전 장치

`-Apply`는 한 대씩 아래 순서로 진행하고, 한 대라도 실패하면 거기서 멈춘다. `-All`의 순서는 OPS01, EDGE01, DB02, DB01, APP01, APP02다. 다른 VM의 적용 뒤 확인이 OPS01에서 출발하므로 OPS01을 먼저 올리고, DB는 대기 쪽을 먼저 한다. 앱 두 대나 DB 두 대를 동시에 바꾸는 일은 없다.

1. **원본 검사(작업 PC).** 파일 이름 규칙과 CR·BOM을 본다.
2. **계획과 구문 검사(VM).** 원본을 VM의 임시 디렉터리로 보낸다. 개인 마운트 이름공간에서 그 디렉터리를 `/etc/vm-lab` 자리에 겹쳐 보이게 한 뒤 `nft -c -f /etc/vm-lab/firewall.nft`로 `firewall.nft`와 새 `firewall.d` 전체를 검사한다. 실패하면 아무것도 바꾸지 않고 멈춘다. 파일도 커널 규칙도 원본과 같으면 건너뛴다.
3. **적용 전 확인.** 아래 역할별 확인을 먼저 돌린다. 이미 실패하는 항목이 있으면 적용하지 않는다. 적용 뒤 실패가 이번 변경 때문인지 원래 있던 문제인지 섞이지 않게 하려는 것이다.
4. **백업과 되돌리기 예약(VM).** 같은 VM에서 다른 적용이 진행 중이거나, 확인을 기다리거나 되돌리는 중인 이전 적용이 있으면 거절한다. 같은 시각 ID의 백업이 이미 있어도 거절한다. 설치할 파일로 구문 검사를 한 번 더 한 뒤, 지금 파일과 `nft list ruleset` 사본을 `/var/lib/vm-lab/nft-backup/<시각>/`에 남기고, `systemd-run --on-active=90`으로 되돌리기 일회성 유닛(`nft-central-rollback-<시각>`)을 예약한다. 예약이 서지 않으면 설치하지 않는다. 예약 전에 거절됐으면 작업 PC는 기다리지 않고 '아무것도 바꾸지 않았다'고 알린다.
5. **설치와 적재(VM).** 파일을 `root:root 0600`으로 설치하고 `nft -f /etc/vm-lab/firewall.nft`로 올린다. 이 파일은 테이블 비우기와 새 규칙 적재를 한 트랜잭션에 담고 있어 규칙이 비는 순간이 없다. 연결 추적(conntrack) 항목은 그대로이고 input 체인의 두 번째 규칙이 `ct state established,related accept`이므로, 이미 맺은 연결은 새 규칙과 관계없이 계속 지나간다. 올린 뒤 설치한 파일이 원본과 같은지, 커널 규칙이 원본으로 만든 규칙과 같은지 VM 안에서 대조하고 다르면 그 자리에서 되돌린다.
6. **적용 뒤 확인(작업 PC).** 작업 PC에서 새 SSH 연결을 열고 역할별 확인을 다시 돌린다. 모두 통과하면 되돌리기 예약을 취소한다. 하나라도 실패하거나 SSH가 끊기면 예약을 그대로 두고, VM이 90초 뒤 스스로 백업 파일을 되돌리고 규칙을 다시 올린다. 확인은 모두 통과했지만 취소 명령이 VM에 닿지 못한 경우도 같다. 작업 PC는 3초마다 새 SSH로 그 적용의 되돌리기 기록을 찾고, 찾으면 적용 전 파일과 같아졌는지 보여 준다. 취소 명령이 VM에 닿은 뒤 응답만 잃었으면 되돌리기 대신 확인 기록이 남아 있으므로 그렇게 알린다.

확인과 되돌리기가 겹치지 않도록 둘 다 백업 디렉터리에 `decided` 디렉터리를 먼저 만들고, 먼저 만든 쪽만 진행한다. 확인이 늦어 되돌리기가 먼저 시작되면 도구가 그 사실을 알린다. 적용 기록은 VM의 `/var/log/vm-lab/nft-central.log`에 한 줄씩 남는다. `apply`, `confirm`, `rollback`이 있고, 적용 단계에서 VM의 구문 검사가 실패하면 `check`가 남는다. 계획 단계에서 구문 검사가 실패해 멈춘 경우는 VM에 아무것도 쓰지 않으므로 기록이 없다. `rollback` 줄의 `label=`은 SELinux 라벨 복구(`restorecon`) 결과이며, 라벨 복구가 실패해도 규칙은 되돌린다. 기록의 `set=` 값은 올린 원본 묶음의 짧은 해시다.

역할별 확인 가운데 값이 정해진 항목(200, `open`, `streaming` 등)은 그 값과 같아야 한다. readiness와 Prometheus처럼 적용 전 값과 비교하는 항목은 먼저 값의 형식(`{"status":"UP"}`, `13/13`처럼 대상이 1개 이상)이 맞아야 하고, 적용 뒤에는 적용 전 값과도 같아야 한다. 조회가 실패해 오류 문구가 나오면 적용 전이든 뒤든 실패다.

| VM | 적용 뒤 확인 |
|---|---|
| 여섯 대 공통 | 작업 PC에서 새 SSH 연결, VM의 파일과 커널 규칙이 원본과 같음 |
| EDGE01 | 작업 PC에서 L7 입구 경유 `/api/v1/markets` 200, OPS01에서 443 200(합성 프로브 경로), 22 연결(백업 SFTP), 9100 200 |
| APP01·APP02 | OPS01에서 본 8081 readiness가 적용 전과 같음(리더·대기 유지), EDGE01에서 8080 연결, OPS01에서 9100 200, L7 입구 200 |
| DB01 | APP01·APP02·DB02에서 5432 연결, OPS01에서 9187·9100 200, 앱 두 대 readiness가 적용 전과 같음, L7 입구 200 |
| DB02 | WAL 수신 상태 `streaming`, OPS01에서 9187·9100 200 |
| OPS01 | 모든 Prometheus 대상이 적용 뒤 다시 수집되고 up 수가 적용 전과 같음, L7 입구에 보낸 표식 요청이 OPS01의 `/var/log/pfsense/haproxy.log`에 도착 |

확인까지 끝난 적용을 되돌리려면 원본을 이전 커밋으로 돌린 뒤 다시 `-Apply`한다. 백업의 `rollback.sh`는 확인도 되돌리기도 일어나기 전, 곧 `decided`가 없을 때만 동작한다.

## 한계

- 되돌리기까지 90초가 걸리고, 이는 앱의 리더 전환보다 느리다. 앱 설정의 기본값은 리스 TTL 10초(`server/app/src/main/java/kr/exchange/config/EngineProperties.java`), 리더가 갱신하지 못할 때 스스로 물러나는 시간 45초(`server/app/src/main/resources/application.yml`의 `lease-standdown-after`)다. VM 예시 설정(`app.env.vm.example`)은 이 값을 바꾸지 않는다. VM의 실제 설정 파일은 비밀 값이 있어 읽지 않았다. 두 앱이 모두 DB를 잃은 2026-09-28 투명 방화벽 작업에서는 약 54초 만에 리더가 넘어갔다. 리더 쪽만 DB를 잃으면 대기 앱이 리스 TTL 뒤에 더 빨리 가져갈 수 있다(설정값으로 본 추정). 그래서 DB01이나 앱 서버에 앱 → DB를 막는 규칙을 올리면 되돌리기 전에 리더 전환이 일어날 수 있다. 다만 역할 규칙은 새 연결만 판정한다. input 체인의 `ct state established,related accept`가 `jump roles`보다 앞에 있으므로, 이미 열린 연결 풀은 역할 규칙을 잘못 올려도 유지된다. 확인은 몇 초 안에 실패를 잡지만 이 도구는 요청대로 예약 시각에 되돌린다. 리더를 잃은 앱은 `sudo systemctl restart exchange-app`으로 재기동해야 대기로 돌아온다.
- 확인 항목에 없는 경로가 막히면 확인이 통과해 되돌리지 않는다. ICMP, OPS01 Databasus 컨테이너의 forward 경로, DB01의 OPS01 → 5432(Databasus 백업), EDGE01의 OPS01 → 80, 기존 라우터(192.168.10.1)에서 오는 원격 로그는 확인하지 않는다.
- 'L7 입구 경유 웹 443' 확인이 EDGE01에 새 TCP 연결을 여는지는 투명 방화벽 HAProxy의 연결 재사용 설정에 달려 있고 확인하지 않았다. EDGE01의 새 연결 허용은 OPS01에서 바로 여는 443 확인이 본다.
- 되돌리기 예약은 일시 유닛이라 90초 안에 VM이 재부팅되면 사라지고, 새 파일이 부팅 때 그대로 올라간다. 그때는 VM 콘솔에서 `sudo bash /var/lib/vm-lab/nft-backup/<시각>/rollback.sh /var/lib/vm-lab/nft-backup/<시각>`을 실행한다.
- 적용 뒤 확인은 90초 안에 끝나야 한다. OPS01의 Prometheus 확인은 새 수집을 최대 30초 기다린다. 2026-09-29 시험에서 적용부터 예약 취소까지(VM 적용 기록 기준) OPS01은 11~16초, 나머지 다섯 대는 1~2초가 걸렸다.
- 되돌리기는 파일 기준이다. 백업의 `ruleset.nft`는 사람이 보는 사본이며 자동으로 올리지 않는다. OPS01의 사본에는 Docker 테이블이 섞여 있어 그대로 올리면 겹친다.
- 2026-09-29에 앱·DB 네 대에는 판정 없는 카운터 규칙을 `-Apply -All`로 한 대씩 올렸다가 지우는 적용만 했다. 앱은 리더의 리스 갱신과 대기의 1초 주기 따라잡기로 DB 연결을 늘 쓰는 구조인데(2026-09-28 투명 방화벽 증거본의 앱 로그), 두 번의 DB01 적재 전후로 확인이 모두 통과했고 리더 전환 기록은 0건이었다. 적재하는 순간에 흐른 질의를 따로 재지는 않았다. 앱·DB에서 확인이 실패하는 경우와 되돌리기는 시험하지 않았다. 적재 중에도 이미 맺은 연결이 끊기지 않는다는 것은 EDGE01에서 확인했다. 시험 규칙이 작업 PC의 새 SSH 연결을 거절하는 동안에도 미리 연 SSH 세션은 명령에 응답했다.
- 적용 기록과 백업은 지우지 않고 쌓인다. 로그 로테이션도 두지 않았다.
- 원본을 거치지 않고 규칙을 바꾸는 길이 남아 있다. `build/scripts`의 역할·전환 스크립트는 지금도 VM의 `firewall.d`에 직접 파일을 쓰고, `firewall.nft`는 공통 기반 `00-common-setup.sh`가 다시 만든다(그 파일 첫 줄이 '직접 고치지 않는다'다). 다시 실행하면 VM이 원본과 어긋나고 `-Audit`가 그것을 잡는다. 그 뒤 `-Pull`로 받아들일지 `-Apply`로 되돌릴지는 사람이 정한다. 원본에서만 `firewall.nft`를 고치면 공통 기반을 다시 실행할 때 되살아난다.
- DB02를 승격하면 `32-db-failover.sh`가 DB02의 `31-db02.nft`를 승격용 규칙(앱 → 5432 허용)으로 바꾼다. 그 뒤 승격 전 원본으로 `-Apply`하면 새 Primary의 5432 허용을 지우는 쪽으로 간다. DB 역할이 바뀌면 적용하기 전에 먼저 `-Pull`로 원본을 맞춘다.
- 작업 PC 한 대에서 쓴다는 전제다. 같은 VM에 두 적용이 겹치면 VM의 잠금과 대기 예약 검사가 뒤의 것을 거절한다. 원본 자체의 충돌은 Git으로 다룬다.

## 기준선에서 본 정리 후보

2026-09-29에 가져온 기준선은 VM에 있던 그대로다. 다음 두 가지는 지금 효과는 없지만 읽는 사람을 헷갈리게 하므로 정리할지 정해야 한다.

- 여섯 대의 `firewall.nft`에 구축 단계 규칙 두 줄이 남아 있다. host-only NIC(`enp0s9`)로 들어오는 관리 SSH 허용과 NAT NIC(`enp0s3`)의 DHCP 응답 허용이다. 두 NIC는 경계형 전환 때 떼어 냈다. 이 파일은 `00-common-setup.sh`가 만들므로 원본만 고치면 공통 기반을 다시 실행할 때 되살아난다. 정리하려면 그 스크립트(DHCP 줄은 `--no-nat-dhcp`)도 함께 바꿔야 한다.
- EDGE01의 `20-edge01.nft`에 작업 PC(192.168.56.1)에서 443·80으로 오는 연결 허용이 남아 있다. 투명 방화벽 전환 뒤에는 투명 방화벽의 'L7 우회 차단' 규칙이 이 경로를 막는다([주소 계획](../build/00-주소계획.md)의 포트 표와 같다).
