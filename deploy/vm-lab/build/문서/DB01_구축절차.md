# DB01 Primary 구축 절차

VM 운영환경의 DB01 한 대를 만드는 절차다. Rocky Linux 10.2 minimal 위에 PostgreSQL 17을 직접 설치하고, 데이터 디스크를 따로 붙이고, 앱과 Standby와 관측이 각각 정해진 경로로만 들어오게 막는 데까지 다룬다.

이 문서는 실행 결과 보고가 아니라 실행 절차다. 아래 명령을 넣으면 이렇게 확인된다는 뜻이며, 실제로 돌려 보기 전까지는 어떤 항목도 통과했다고 적지 않는다.

## 1. 무엇을 만드는가

| 항목 | 값 | 근거 |
|---|---|---|
| 역할 | PostgreSQL 17 Primary | `Linux_VM_운영환경_구성도.svg`의 DB01 |
| lab-lan 주소 | 192.168.10.31/24 (enp0s8) | `00-주소계획.md` |
| host-only 주소 | 192.168.56.31/24 (enp0s9) | 같음 |
| NAT | DHCP (enp0s3) | 구축 단계의 패키지 설치 경로 |
| 자원 | vCPU 2, 메모리 3GB | 같음 |
| 디스크 | OS 20GB + 데이터 20GB | 구성도의 "별도 데이터 디스크" |
| 5432 허용 출발지 | APP01, APP02, DB02 | `VM_네트워크_접근제어도.svg` |

`exchange.conf`의 해시는 학교 EC2 적용본과 같은 값이다. 구축 스크립트의 `config` 단계가 이 값을 다시 대조하고, 다르면 멈춘다.

관리용 SSH 키는 여섯 대가 같은 것을 쓴다. 개인키는 산출물 폴더에 두지 않고 `%USERPROFILE%\.ssh\vm-lab_ed25519`에 둔다. `build\keys\`에는 공개키 `vm-lab_ed25519.pub`만 남긴다. 키가 없으면 먼저 만들고 그 자리에서 ACL을 좁힌다.

```powershell
ssh-keygen -t ed25519 -f $env:USERPROFILE\.ssh\vm-lab_ed25519 -C vm-lab-ops
icacls "$env:USERPROFILE\.ssh\vm-lab_ed25519" /inheritance:r
icacls "$env:USERPROFILE\.ssh\vm-lab_ed25519" /grant:r "$($env:USERNAME):(R,W)"
Copy-Item "$env:USERPROFILE\.ssh\vm-lab_ed25519.pub" C:\Users\kopo26\Desktop\vm-lab\build\keys\
```

이 키에는 암호구가 없다. 무인 구축에서 사람이 매번 암호를 넣을 수 없어 내린 선택이며, 대신 산출물 폴더 밖에 두고 ACL로 현재 사용자만 읽고 쓰게 좁혔다. 이 키 하나가 여섯 대 `ops` 계정의 유일한 인증 수단이고 그 계정은 구축 중 전체 sudo를 가지므로, 이 상태를 "안전하다"고 적지 않는다.

Rocky Linux 10.2 minimal ISO도 미리 내려받아 둔다.

이 절차는 공통 절차와 이어진다. 여섯 대에 같은 기반을 까는 일은 `문서/공통_구축절차.md`와 `scripts/00-common-setup.sh`가 맡는다. DB01에서도 그 순서를 먼저 밟고 여기로 온다. 공통 기반이 계정, SSH, journald, node_exporter, 방화벽 기본 차단까지 만들어 두면 이 문서의 절차는 PostgreSQL과 DB 전용 포트만 다룬다.

## 3. VM 만들기와 무인 설치

설치는 `01-create-vms.ps1` 하나로 한다. 이 스크립트가 VM을 만들고 `ks/db01.ks`를 답안 파일로 넘겨 무인 설치를 건다.

```powershell
pwsh -NoProfile -File C:\Users\kopo26\Desktop\vm-lab\build\scripts\01-create-vms.ps1 -Role db01
```

스크립트가 만드는 구성은 다음과 같다. 실행 뒤 `VBoxManage showvminfo db01`로 한 번 대조한다. 저장 위치는 C 드라이브 여유가 없으므로 D 드라이브를 쓴다.

- 이름 `db01`, 종류 Linux, 버전 Red Hat (64-bit), 폴더 `D:\vm-lab`
- 메모리 3072MB, 프로세서 2개
- 시스템 > 마더보드에서 EFI를 켜지 않는다. 답안 파일이 BIOS 부팅과 GPT 조합을 전제한다
- 디스크 1: `D:\vm-lab\db01\db01.vdi` 20GB, VDI, 동적 할당. SATA 포트 0
- 디스크 2: `D:\vm-lab\db01\db01-data.vdi` 20GB, 같은 방식. SATA 포트 1. 게스트에서 `/dev/sdb`로 잡힌다
- 네트워크 어댑터 1: NAT
- 네트워크 어댑터 2: 내부 네트워크, 이름 `lab-lan`
- 네트워크 어댑터 3: 호스트 전용 어댑터, `VirtualBox Host-Only Ethernet Adapter`

어댑터 순서가 그대로 `enp0s3`, `enp0s8`, `enp0s9`가 된다. 순서를 바꾸면 답안 파일의 주소가 엉뚱한 인터페이스에 붙는다. 호스트 전용 네트워크의 DHCP 서버는 보통 192.168.56.100부터 나눠 주므로 우리가 쓰는 .31과 겹치지 않지만, 대역 설정이 192.168.56.0/24인지 한 번 확인한다.

## 4. 답안 파일은 한 벌이다

DB01의 답안 파일은 `ks/db01.ks` 하나다. `ks-db01.cfg`나 `db01.generated.ks` 같은 두 번째 세트를 만들지 않고, `inst.ks=http://...`로 작업 PC의 HTTP 서버에서 받아 가는 경로도 쓰지 않는다. `ks/base.ks.template`은 설계 근거를 읽을 때만 보고 그 파일로 설치하지 않는다.

`ks/db01.ks`의 공개키 자리표시자 `@@OPS_SSH_PUBKEY@@`는 사람이 미리 바꾸지 않는다. `01-create-vms.ps1`이 `build/keys/vm-lab_ed25519.pub`를 읽어 임시 사본에 치환해 넘기고, 치환 후 `@@`나 `__대문자__`가 남아 있으면 설치를 시작하지 않고 멈춘다. `rootpw --lock`과 `user --lock`으로 두 계정의 비밀번호가 모두 잠겨 있어, 키가 배치되지 않으면 SSH도 VirtualBox 콘솔도 들어갈 수 없다. 그래서 치환 실패를 경고로 넘기지 않고 설치 자체를 멈춘다.

설치가 끝나면 자동으로 재부팅한다. 답안 파일이 하는 일은 디스크 나누기와 계정, SSH, hosts, firewalld 정지까지다. PostgreSQL과 데이터 디스크는 다음 절에서 직접 설치한다. 최초 설치와 기동을 단계별로 확인하는 것이 이 과제의 목적이기 때문이다.

## 5. 첫 접속과 자료 복사

```powershell
ssh -i $env:USERPROFILE\.ssh\vm-lab_ed25519 ops@192.168.56.31
```

들어가지 못하면 설치 단계에서 공개키 치환이 실패한 것이다. `rootpw --lock`과 `user --lock` 때문에 VirtualBox 콘솔 로그인도 되지 않으므로 콘솔로 복구하려 하지 않는다. `01-create-vms.ps1`의 치환 검사 출력을 보고 `build/keys/vm-lab_ed25519.pub`를 채운 뒤 설치를 다시 건다.

접속되면 작업 PC에서 필요한 하위 폴더만 넘긴다. `build` 폴더를 통째로 넘기지 않는다. `keys/`가 함께 올라가면 여섯 대의 root 상당 권한을 주는 자료가 VM 디스크에 남는다.

```powershell
$key  = "$env:USERPROFILE\.ssh\vm-lab_ed25519"
$root = "C:\Users\kopo26\Desktop\vm-lab\build"
ssh -i $key ops@192.168.56.31 "mkdir -p /home/ops/build"
scp -i $key -r "$root\build-files" "$root\scripts" "$root\ks" "$root\문서" `
    "$root\00-주소계획.md" ops@192.168.56.31:/home/ops/build/
```

VM 쪽에서 제자리에 옮기고 실행 권한을 준다. Windows에서 복사하면 실행 비트가 사라지므로 `chmod`가 필요하다. 옮긴 직후 키 파일이 따라오지 않았는지 확인한다. 아래 두 명령은 아무것도 출력하지 않아야 한다.

```bash
sudo rsync -a /home/ops/build/ /opt/vm-lab/
sudo chown -R root:root /opt/vm-lab
sudo chmod 0755 /opt/vm-lab/scripts/30-db-primary-setup.sh
rm -rf /home/ops/build
find /opt/vm-lab -name 'vm-lab_ed25519*' ! -name '*.pub'
find /opt/vm-lab -name 'lab_ed25519*'
```

## 6. 공통 기반 먼저

DB 전용 설정에 들어가기 전에 여섯 대 공통 기반을 적용한다. `문서/공통_구축절차.md`의 순서를 따르며, 요점은 `--plan`으로 바뀔 내용을 먼저 보고 `--apply`로 적용하는 것이다.

```bash
bash /opt/vm-lab/scripts/00-common-setup.sh --plan
sudo bash /opt/vm-lab/scripts/00-common-setup.sh --apply --download
```

공통 기반이 끝나면 SSH 키 접속, journald 보존, node_exporter, 그리고 22와 9100만 열린 기본 차단 방화벽이 선다. 그다음 절의 DB 스크립트는 그 위에 PostgreSQL과 5432, 9187만 얹는다.

공통 기반을 건너뛰지 않는다. 방화벽 계통을 `table inet vmlab` 하나로 정했으므로 DB 스크립트는 그 위에 얹는 역할 규칙만 쓴다. 같은 후크에 base chain이 둘 서면 어느 규칙이 걸렀는지 설명할 수 없다. node_exporter와 journald 설정도 공통 기반이 올린 것을 그대로 쓰고 DB 스크립트가 덮어쓰지 않는다.

## 7. 구축 스크립트

한 번에 다 돌릴 수 있고 단계만 골라 돌릴 수도 있다. 처음에는 기록을 남기면서 전부 돌린다.

```bash
sudo /opt/vm-lab/scripts/30-db-primary-setup.sh all 2>&1 | tee ~/db01-build.log
```

단계는 다음과 같다. 각 단계는 이미 끝난 일을 다시 하지 않고, 자료가 들어 있는 디스크나 초기화된 PGDATA를 만나면 덮어쓰지 않고 멈춘다.

| 단계 | 하는 일 |
|---|---|
| `preflight` | OS, 호스트 이름, 주소, SELinux, 데이터 디스크, 로케일, 시간 동기화 확인 |
| `disk` | `/dev/sdb`에 GPT와 파티션 하나, xfs 포맷, UUID로 fstab 등록, `/var/lib/pgsql` 마운트 |
| `packages` | 기본 패키지, PGDG 저장소, `postgresql17-server`와 `postgresql17-contrib` 설치, 데이터 경로 소유권과 SELinux 문맥 복구 |
| `initdb` | `--encoding=UTF8 --locale=C.UTF-8 --auth-local=peer --auth-host=scram-sha-256 --data-checksums` |
| `config` | `exchange.conf` 해시 대조 후 `/etc/postgresql`에 배치, `node.conf` 배치, `postgresql.conf`에 include 추가 |
| `tls` | 자체 서명 인증서 생성. CN은 `db01.lab`, SAN에 `IP:192.168.10.31` |
| `hba` | `pg_hba.conf` 배치. initdb 원본은 `pg_hba.conf.initdb`로 보관 |
| `start` | 부팅 등록과 기동, 실효 설정 조회 |
| `roles` | `exchange` DB와 `exchange_owner`, `exchange_app`, `replicator` 생성 |
| `monitor` | OS 계정 `failstop_monitor`와 DB 역할 생성 |
| `exporters` | postgres_exporter 0.17.1 설치와 기동. node_exporter는 공통 기반이 깔았으면 그대로 두고, 없으면 1.12.1을 설치한다 |
| `journald` | 로그 보존 설정 배치. 같은 내용이 이미 있으면 journald를 다시 흔들지 않는다 |
| `firewall` | `/etc/vm-lab/firewall.d/30-db01.nft`로 5432와 9187만 연다 |
| `verify` | 상태 확인 출력 |

복제 슬롯은 만들지 않는다. DB02가 `-S` 없이 붙고 `primary_slot_name`을 빈 값으로 두는 것이 이 구성의 선택이다. 슬롯을 만들어 두면 DB02가 쓰지 않는 슬롯이 DB01에 영구히 비활성으로 남는다. 대신 단절이 길어져 필요한 WAL 세그먼트가 재활용되면 복제가 끊기고, 그때는 전량 베이스백업을 다시 받는다. 이 조건을 DB02 절차와 같은 값으로 적어 둔다.

`verify`는 `all` 안에서 돌지 않는다. 비밀번호를 넣기 전에 `verify`가 먼저 판정하면 비밀번호 없는 역할 상태가 통과 기록으로 남는다. 순서는 `all` 다음에 `passwords`, 그다음 `verify`다.

`firewall` 단계는 SSH를 끊을 수 있다. 22는 관리 대역에서 오는 것만 허용하므로 정상이면 끊기지 않지만, VirtualBox 콘솔 창을 열어 둔 상태에서 실행한다. 스크립트는 `nft --check`를 먼저 통과시킨 뒤에만 규칙을 올린다. 공통 기반 위에 얹는 경우에는 역할 규칙 파일을 놓고 기반 파일로 검사하며, 구문이 틀리면 방금 놓은 파일만 도로 치우고 기반 규칙은 그대로 둔다.

`packages` 단계에서 PGDG의 EL-10 채널이 없으면 스크립트가 거기서 멈춘다. 그때는 `dnf info postgresql-server`로 기본 저장소의 버전을 확인하고 17이 아니면 어떤 버전을 쓸지 먼저 정한다. 확인하지 않은 채로 다음 단계를 진행하지 않는다.

## 8. 비밀번호

비밀번호는 스크립트가 만들지 않는다. 사람이 직접 넣고 값은 화면에도 파일에도 남기지 않는다. 대상은 `exchange_owner`, `exchange_app`, `replicator` 셋이다.

```bash
sudo /opt/vm-lab/scripts/30-db-primary-setup.sh passwords
```

`exchange_owner`를 빼지 않는다. `pg_hba.conf`의 인증 방식이 `hostssl ... scram-sha-256`이라 비밀번호가 없는 역할은 인증에 성공하지 못하고, 그러면 APP01에서 Flyway 스키마 적용이 아예 되지 않는다. 넣은 뒤에는 세 역할 모두 비밀번호가 실제로 생겼는지 확인한다.

```bash
sudo -u postgres psql -X -P pager=off -c \
  "SELECT rolname, (rolpassword IS NOT NULL) AS has_password FROM pg_authid \
   WHERE rolname IN ('exchange_owner','exchange_app','replicator') ORDER BY rolname;"
```

세 줄 모두 `t`여야 한다. 하나라도 `f`면 그 역할은 아직 붙을 수 없는 상태다.

`psql`의 `\password`는 입력을 표시하지 않고 암호화한 값만 서버로 보낸다. 명령 인자나 SQL 파일에 비밀번호를 적지 않는다. 같은 값을 APP01의 `/etc/exchange/app-secret.env`와 DB02의 `/var/lib/pgsql/.pgpass`에 넣어야 하므로, 옮길 때도 화면 캡처와 로그에 남기지 않는다. 캡처를 뜰 때는 비밀 값 입력 구간을 건너뛰고 그 구간이 빠졌다고 표시한다.

## 9. 인증서 배포

공개 인증서 `/etc/postgresql/server.crt`를 APP01, APP02, DB02로 옮긴다. 개인 키 `server.key`는 옮기지 않는다.

```bash
sudo openssl x509 -in /etc/postgresql/server.crt -noout -fingerprint -sha256
```

받은 쪽에서도 같은 명령으로 지문을 확인해 값이 같은지 본다. 자체 서명이라 신뢰 사슬이 없고, 앱과 Standby가 이 파일을 `sslrootcert`로 직접 고정해야 `verify-full`이 성립한다. 인증서를 바꾸면 세 노드에 다시 배포해야 하고 만료 관리도 수동이다. `tls` 단계가 출력한 만료일을 운영 기록에 적어 둔다.

## 11. 다른 역할과 맞춰야 하는 값

| 값 | 어디서 쓰는가 |
|---|---|
| `replicator` 비밀번호 | DB02의 `/var/lib/pgsql/.pgpass` |
| `exchange_app` 비밀번호 | APP01, APP02의 앱 비밀 환경 파일 |
| `exchange_owner` 비밀번호 | APP01의 Flyway 스키마 적용(`21-app-migrate.sh`) |
| `server.crt` | APP01, APP02, DB02의 `sslrootcert` |
| 주소 192.168.10.31 | 앱 DB 접속 설정, DB02 복제 연결, OPS01 수집 대상 |
| 복제 슬롯 없음 | DB02는 `pg_basebackup`에 `-S`를 붙이지 않고 `primary_slot_name`을 빈 값으로 둔다 |

### 마이그레이션 창

평상시 `pg_hba.conf`에는 `exchange_owner`용 규칙이 없고 그 역할은 `NOLOGIN`이다. 접근제어도의 허용 목록에 없는 접속을 상시로 열어 두지 않기 때문이다. APP01에서 Flyway를 돌릴 때만 창을 열고 끝나면 닫는다. 이 여닫기는 스크립트의 하위 명령이며 사람이 `pg_hba.conf`를 손으로 편집하지 않는다.

```bash
# APP01에서 21-app-migrate.sh 를 돌리기 직전에, DB01에서
sudo /opt/vm-lab/scripts/30-db-primary-setup.sh migrate-open

# APP01의 마이그레이션이 끝난 뒤, DB01에서
sudo /opt/vm-lab/scripts/30-db-primary-setup.sh migrate-close
```

`migrate-open`은 `hostssl exchange exchange_owner 192.168.10.21/32 scram-sha-256` 한 줄을 넣고 reload한다. 출발지는 APP01 한 대뿐이다. `migrate-close`는 그 줄을 지우고 `ALTER ROLE exchange_owner NOLOGIN`을 실행한다. 창을 열지 않은 상태에서 마이그레이션이 성공한 것처럼 적지 않는다. 닫은 뒤 `pg_hba_file_rules`에 그 줄이 없고 `pg_roles`의 `rolcanlogin`이 `f`인지 확인한다.

앱 쪽 Flyway가 끝난 뒤에 해야 하는 일이 하나 더 남는다. DB01 구축이 끝난 시점이 아니라 앱 배포 뒤 작업이다.

```sql
GRANT app_role TO exchange_app;
```

`app_role`과 `harness_role`은 Flyway V0가 만드는 NOLOGIN 그룹 롤이라 DB01 구축에서는 만들지 않는다. 그래서 그전까지 `exchange_app`은 접속은 되지만 객체 권한이 없다.

## 12. 설계에서 의도적으로 벗어난 곳

저장소 자산을 그대로 쓰지 못한 지점과 그 이유를 남긴다.

`firewall-host.sh`는 쓰지 않는다. 그 스크립트는 50행에서 `--ssh-port 22`를 거부하는데 주소계획은 22를 쓴다. 또 input 정책이 accept라서 포트별 drop만 두는데, 접근제어도의 "허용하지 않은 새 인바운드 연결은 차단"을 그대로 맞추려면 정책 자체가 drop이어야 한다. 가져온 것은 방식이다. 테이블 하나에 담고, `add`와 `flush`를 같은 파일에 두어 갱신 중 차단 공백을 만들지 않고, 포트마다 허용 출발지를 먼저 적고, `nft --check`를 통과하기 전에는 적용하지 않는다.

방화벽 계통은 하나다. 공통 절차가 `table inet vmlab`에 기본 차단을 세우고, DB01은 그 위에 `db01-firewall.d.nft`로 5432와 9187만 얹는다. `db01-firewall.nft`의 단독 테이블과 배포판 `nftables.service`는 쓰지 않는다. 같은 후크에 base chain을 둘 세우면 어느 규칙이 걸렀는지 알 수 없고, `nftables.service`는 중지할 때 ruleset 전체를 비울 수 있다. ICMP 일부와 NAT 구간의 DHCP 응답 허용은 공통 기반이 이미 갖고 있으므로 역할 파일에서 다시 적지 않는다. 발신 제한은 pfSense 경계에 맡기고 그 이유를 역할 규칙 파일 주석에 적는다.

`postgres_exporter.service`의 `After=postgresql.service`는 고치지 않고 드롭인으로 덮었다. 학교 EC2는 유닛이 `postgresql.service`였지만 PGDG 패키지는 `postgresql-17.service`다. node_exporter의 systemd 수집기 필터도 같은 문제를 가진다. 저장소 원본과 공통 절차 모두 정규식에 `postgresql`을 쓰는데 실제 이름이 다르면 DB 서비스 상태가 수집되지 않는다. 그래서 설치된 유닛의 `ExecStart`를 읽어 유닛 이름 부분만 바꾼 드롭인을 놓는다. 유닛 파일 자체와 저장소 원본은 건드리지 않는다.

`REVOKE CONNECT ON DATABASE exchange FROM PUBLIC` 다음에 `GRANT CONNECT ... TO exchange_app`을 넣었다. 회수만 하면 앱 계정이 붙지 못해 10절의 APP01 접속 확인이 실패한다.

`/etc/postgresql`은 RHEL 계열의 기본 설정 경로가 아니다. 학교 구축과 경로를 맞추려고 그대로 쓰되, SELinux 문맥 때문에 `postgres`가 읽지 못하면 `semanage fcontext`로 타입을 지정하고 `restorecon`으로 고친다. `setenforce 0`이나 SELinux 비활성화로 우회하지 않는다.

`ops`의 sudo는 구축 중에는 전체 권한이다. 비밀번호가 잠긴 계정이라 암호 확인을 쓸 수 없어 `NOPASSWD`를 두었다. 구축이 끝나면 필요한 명령으로 좁힌다. 좁히기 전에는 "제한된 sudo를 적용했다"고 적지 않는다.

## 13. 이 절차의 한계

실행하기 전이므로 10절의 기대값은 전부 예상이다. 통과 기록이 아니다.

복제는 비동기다. `exchange.conf`의 `synchronous_standby_names`가 빈 값이라 Primary가 갑자기 죽으면 클라이언트가 접수 응답을 받은 쓰기도 유실될 수 있다. 복제 지연 0이나 LSN 일치만으로 무손실을 판정하지 않는다.

복제 슬롯을 쓰지 않으므로 `exchange.conf`의 `max_slot_wal_keep_size` 4GB는 이 구성에서 보호 장치가 아니다. `wal_keep_size`는 0이고 `archive_mode`도 off다. DB02가 오래 끊기면 DB01이 필요한 WAL 세그먼트를 재활용해 복제가 끊기고, 그때는 전량 베이스백업을 다시 받는다. 대신 DB02 장애가 DB01의 데이터 디스크를 채우지 않는다. 이 맞바꿈을 DB02 절차와 같은 값으로 적어 둔다. 데이터 디스크 20GB 안에 데이터와 WAL이 함께 들어가는데 디스크 사용률 알람 규칙이 없으므로 용량은 사람이 관찰해야 한다.

`shared_buffers` 256MB, `effective_cache_size` 1GB, `max_connections` 100은 학교 EC2의 부하 측정 전 초기값이다. 메모리 3GB VM에서 그대로 쓰지만 부하 시험으로 검증한 값은 아니다.

`create-monitor-role.sql`은 최초 설치용이라 역할이 이미 있으면 실패한다. 스크립트는 그 경우 다시 실행하지 않고 권한만 확인한다. `failstop_monitor`는 다른 세션의 질의까지 보는 통계 권한을 가지므로 일반 사용자 계정으로 쓰지 않는다.

exporter 바이너리는 외부에서 내려받는다. 대조에 쓰는 SHA-256은 학교 구축 때 기록한 값이며 이번에 다시 확인한 값이 아니다. VM에서 실제로 대조한 결과를 증거로 남긴다. postgres_exporter의 사용자 쿼리 옵션은 폐기 예정 기능이므로 버전을 올릴 때 호환성을 확인한다.

Rocky Linux 10.2라는 마이너 버전과 `enp0s3`, `enp0s8`, `enp0s9`라는 이름은 주소계획의 전제를 그대로 따랐다. 설치 후 `ip link`로 확인해 다르면 주소계획을 먼저 고치고 답안 파일과 nft 규칙을 맞춘다.

구축 단계에서는 NAT로 패키지를 내려받는다. 사용자가 pfSense를 올리고 기본 경로를 192.168.10.1로 바꿔 NAT를 내리기 전까지는 "모든 통신이 방화벽을 지난다"고 적을 수 없다.

단일 PC의 가상 환경이다. 여기서 얻은 결과를 학교 AWS나 개인 AWS의 검증 결과로 옮겨 적지 않는다.

## 14. 증거

AWS 설정 확인과 Linux 명령 실행은 단계별 실제 화면과 명령, 출력을 남긴다. 이 절차에서는 다음 지점을 남기면 나중에 다시 설명할 수 있다.

- VirtualBox의 디스크 두 개와 어댑터 세 개 설정 화면
- 설치 직후 `ip -brief addr`와 `lsblk`
- `disk` 단계의 `findmnt`, `df -h`, `ls -ldZ`
- `packages` 단계의 설치 로그 끝부분과 `systemctl cat`으로 확인한 유닛 이름, PGDATA
- `start` 단계의 실효 설정 조회
- `verify` 단계 전체 출력
- 다른 노드에서 한 허용과 차단 시험, 그리고 `journalctl -k`의 차단 기록
- 재부팅 뒤 같은 확인

비밀 값 입력 구간은 캡처하지 않고 그 구간이 빠졌다고 표시한다. 실행하지 않은 항목은 실행하지 않았다고 적는다.
