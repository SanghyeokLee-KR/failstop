# VM 공통 기반 구축 절차

여섯 대(EDGE01, APP01, APP02, DB01, DB02, OPS01)에 똑같이 들어가는 부분을 만드는 절차다. Rocky Linux 10.2 minimal 무인 설치, ops 관리 계정과 SSH 키 인증, 로그 보존, 시간 동기화, 세 개의 NIC 고정 주소, nftables 기본 차단, node_exporter, 5분 주기 호스트 점검까지가 여기 범위다. NGINX와 Spring Boot, PostgreSQL, Prometheus 계열은 각 역할 절차가 이 기반 위에 올린다.

pfSense는 사용자가 직접 구축한다. 이 절차는 `192.168.10.1`과 `192.168.56.10` 두 주소를 예약해 둘 뿐 pfSense를 만들지도 설정하지도 않는다.

주소와 포트, 계정의 기준은 [주소 계획](../00-주소계획.md) 한 곳이다. 값을 바꿔야 하면 그 문서를 먼저 고치고 아래 파일들을 맞춘다. 반대 방향으로 고치지 않는다.

이 문서는 실행하면 이렇게 확인된다는 절차다. 검증 결과가 아니다. 아직 아무 것도 실행하지 않았으므로 여기 적힌 기대 출력은 실제로 보기 전까지 통과로 적지 않는다.

## 쓰는 파일 세 개

| 파일 | 역할 |
|---|---|
| `build/scripts/01-create-vms.ps1` | VM 생성과 무인 설치. 여섯 대의 설치는 이 스크립트 하나로 한다 |
| `build/ks/<이름>.ks` | 역할별 무인 설치 답안 파일. 여섯 개가 설치의 정본이다 |
| `build/scripts/00-common-setup.sh` | 설치 후 여섯 대에서 돌리는 공통 설정. `--plan`과 `--apply`를 나눈다 |

`build/ks/base.ks.template`은 설계 참고용으로만 남긴다. 이 파일로 설치하지 않는다. 자리표시자는 `01-create-vms.ps1`이 임시 사본에 치환해서 넘기며, 치환 후 `@@`나 `__대문자__`가 남으면 그 자리에서 멈춘다.

kickstart는 재부팅 직후 SSH 키로 들어갈 수 있는 상태까지만 만든다. 방화벽 기본 차단 정책과 node_exporter, 진단 타이머는 스크립트가 건다. 설치 중에 방화벽을 세우면 첫 접속 경로를 잃었을 때 되돌릴 방법이 콘솔뿐이라 두 단계로 나눴다.

## 1. 준비

운영자 키를 만든다. 개인키는 산출물 폴더에 두지 않는다. `%USERPROFILE%\.ssh\vm-lab_ed25519`에 만들고 만든 자리에서 바로 ACL을 좁힌다. `build\keys\`에는 공개키 `vm-lab_ed25519.pub`만 남는다.

```powershell
ssh-keygen -t ed25519 -f $env:USERPROFILE\.ssh\vm-lab_ed25519 -C vm-lab-ops
icacls "$env:USERPROFILE\.ssh\vm-lab_ed25519" /inheritance:r
icacls "$env:USERPROFILE\.ssh\vm-lab_ed25519" /grant:r "$($env:USERNAME):(R,W)"
Copy-Item "$env:USERPROFILE\.ssh\vm-lab_ed25519.pub" C:\Users\kopo26\Desktop\vm-lab\build\keys\
```

이 키에는 암호구가 없다. 무인 구축에서 사람이 매번 암호를 넣을 수 없어 내린 선택이며, 대신 산출물 폴더 밖에 두고 ACL로 현재 사용자만 읽고 쓰게 좁혔다. 이 키 하나가 여섯 대의 `ops` 계정이고 그 계정은 구축 중 전체 sudo를 가지므로, 이 상태를 "안전하다"고 적지 않는다. 암호구 없는 키를 쓰는 동안의 위험은 작업 PC 계정 보호에 전적으로 기댄다.

VirtualBox의 host-only 어댑터가 `192.168.56.1/24`인지, 내부 네트워크 이름을 `lab-lan`으로 쓸 것인지 확인한다. 호스트 네트워크 관리자에서 host-only 어댑터의 DHCP 서버는 끈다. 주소는 kickstart가 고정으로 넣으므로 DHCP가 겹치면 판단이 어려워진다.

Rocky Linux 10.2 minimal ISO를 받아 D 드라이브에 둔다. C 드라이브 여유가 30GB뿐이라 ISO와 VM 디스크를 모두 D에 둔다.

## 2. VM 만들기와 무인 설치

설치는 `01-create-vms.ps1` 하나로 한다. 이 스크립트가 VirtualBox VM을 만들고 `ks\<이름>.ks`를 `VBoxManage unattended install`의 답안 파일로 넘겨 무인 설치를 건다. 여섯 대의 vCPU, 메모리, 디스크, 저장 경로는 스크립트가 주소 계획 표의 값을 그대로 쓴다.

```powershell
pwsh -NoProfile -File C:\Users\kopo26\Desktop\vm-lab\build\scripts\01-create-vms.ps1 -WhatIfOnly
pwsh -NoProfile -File C:\Users\kopo26\Desktop\vm-lab\build\scripts\01-create-vms.ps1
```

`-WhatIfOnly`로 먼저 계획만 보고 값이 주소 계획과 같은지 확인한 뒤 실행한다. 한 대만 다시 만들 때는 `-Role edge01`처럼 역할을 지정한다.

## 3. 답안 파일은 한 벌이다

답안 파일은 `ks\edge01.ks`부터 `ks\ops01.ks`까지 여섯 개이며 이것이 정본이다. 두 번째 전달 경로를 만들지 않는다. `inst.ks=http://...`로 작업 PC의 HTTP 서버에서 받아 가는 안내, `ks-<이름>.cfg` 두 번째 세트, `<이름>.generated.ks` 같은 사람이 먼저 만들어야 하는 중간 파일은 모두 쓰지 않는다. 경로가 둘이면 같은 VM에 내용이 다른 답안 파일 두 벌이 생기고, 어느 쪽으로 설치했는지에 따라 이후 절차의 전제가 갈린다.

공개키 자리표시자 치환도 사람이 하지 않는다. `01-create-vms.ps1`이 `build\keys\vm-lab_ed25519.pub`를 읽어 임시 사본에 채워 넘기고, 치환 후 `@@`나 `__대문자__`가 남아 있으면 설치를 시작하지 않고 멈춘다. 원본 `ks\*.ks`에는 자리표시자 형태 그대로 둔다.

`base.ks.template`은 설계 근거를 읽을 때만 본다. 이 파일로 설치하지 않는다.

## 4. 자원과 어댑터 확인

NIC 순서는 여섯 대가 모두 같아야 한다. NIC1이 NAT, NIC2가 `lab-lan`, NIC3이 host-only다. 순서가 어긋나면 Rocky가 잡는 `enp0s3`, `enp0s8`, `enp0s9` 대응이 깨지고 kickstart의 `network` 줄이 엉뚱한 장치에 붙는다. 어댑터 이름과 자원 값은 스크립트 실행 뒤 `VBoxManage showvminfo <이름>`으로 한 번 대조한다.

DB 두 대의 데이터 디스크는 OS 설치가 끝난 뒤에 붙인다. kickstart의 `ignoredisk --only-use=sda`가 이미 막아 두지만 설치 중에 아예 보이지 않게 하는 편이 안전하다. 파티션과 마운트, fstab은 DB 역할 절차에서 다룬다.

Guest Additions는 설치하지 않는다. 게스트 시간 동기화 기능이 chrony와 겹치면 시간 원본이 둘이 된다. 공유 폴더도 쓰지 않으므로 파일은 SSH로 옮긴다.

## 5. 무인 설치와 첫 확인

설치가 끝나면 ISO가 빠지고 재부팅된다. VirtualBox 콘솔에서 로그인 화면이 뜨면 아래를 확인한다. 이 단계에서는 ops가 비밀번호로 로그인할 수 없으므로 콘솔에서는 상태만 본다.

작업 PC에서 SSH로 들어간다.

```powershell
ssh -i $env:USERPROFILE\.ssh\vm-lab_ed25519 ops@192.168.56.21
```

첫 접속에서 호스트키 지문을 묻는다. 그냥 yes를 누르지 않고 VirtualBox 콘솔에서 아래를 실행해 나온 값과 비교한다. 검증을 끄지 않는다.

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

들어간 뒤 설치가 계획대로 됐는지 본다.

```bash
cat /etc/os-release; uname -m; cat /proc/1/comm
ip -brief address
ip route show
lsblk; df -h; findmnt /var/log
sudo cat /root/anaconda-ks.cfg
sudo cat /root/ks-post-state.log
```

`ip -brief address`에서 `enp0s8`이 lab-lan 주소, `enp0s9`가 host-only 주소를 가져야 한다. 기본 경로는 `enp0s3` 하나다. 주소가 다른 장치에 붙어 있으면 NIC 순서 문제이므로 VM 설정을 고치고 다시 설치한다.

## 6. 공통 설정 적용

`00-common-setup.sh`를 VM으로 옮기고 먼저 `--plan`으로 무엇이 바뀔지 본다. plan은 root가 아니어도 되고 아무 것도 바꾸지 않는다.

```powershell
scp -i $env:USERPROFILE\.ssh\vm-lab_ed25519 `
    C:\Users\kopo26\Desktop\vm-lab\build\scripts\00-common-setup.sh ops@192.168.56.21:/tmp/
```

```bash
bash /tmp/00-common-setup.sh --plan
```

출력에서 lab-lan 주소, host-only 주소, sshd 바인딩 주소, node_exporter 바인딩 주소가 그 VM의 값과 맞는지 확인한다. 적용할 nftables 규칙도 전부 출력되므로 여기서 읽고 넘어간다.

node_exporter 바이너리를 준비한다. 공식 릴리스에서 받은 뒤 해시를 대조한다. 스크립트가 같은 해시를 다시 확인하고 다르면 멈춘다. 파일 이름이 같다는 이유로 검증을 건너뛰지 않는다.

```bash
curl -fL -o /tmp/node_exporter-1.12.1.linux-amd64.tar.gz \
  https://github.com/prometheus/node_exporter/releases/download/v1.12.1/node_exporter-1.12.1.linux-amd64.tar.gz
sha256sum /tmp/node_exporter-1.12.1.linux-amd64.tar.gz
# b51d8a76aa2a9156a55d501aca6276fae09e262259a5e4e831d2c2222f084e63 이어야 한다
```

적용한다. 방화벽 규칙과 sshd 설정을 건드리므로 VirtualBox 콘솔을 열어 둔 상태에서 실행한다. SSH가 끊겨도 콘솔로 되돌릴 수 있어야 한다.

```bash
sudo bash /tmp/00-common-setup.sh --apply \
  --node-exporter-tarball /tmp/node_exporter-1.12.1.linux-amd64.tar.gz
```

스크립트는 멱등하다. 두 번째 실행에서는 `changed=0`이 나오고 서비스도 다시 시작하지 않는다. 한 번 더 돌려 이 점을 확인해 두면 나중에 설정이 밀렸는지 보는 데 쓸 수 있다.

주소가 계획과 다르면 스크립트가 멈춘다. 주소를 대신 잡아 주지 않는다. `nmcli`로 직접 고친 뒤 다시 실행한다.

```bash
nmcli -f NAME,DEVICE,TYPE,STATE con show
sudo nmcli con mod "<연결이름>" ipv4.method manual ipv4.addresses 192.168.10.21/24 \
     ipv4.never-default yes ipv4.ignore-auto-dns yes ipv6.method disabled
sudo nmcli con up "<연결이름>"
```

## 7. 확인

적용 뒤에 아래를 직접 실행한다. 실행해서 결과를 보기 전에는 어디에도 통과로 적지 않는다.

| 확인할 것 | 명령 | 기대 |
|---|---|---|
| 리슨 포트 | `ss -lntp` | 22는 host-only 주소, 9100은 lab-lan 주소에만 있다. 여섯 대가 같으며 OPS01도 `192.168.10.41:9100`이다. `0.0.0.0`이나 `:::`로 열린 항목이 없다 |
| SSH 적용값 | `sudo sshd -T \| grep -Ei '^(permitrootlogin\|passwordauthentication\|kbdinteractiveauthentication\|authenticationmethods\|allowtcpforwarding\|listenaddress\|allowusers\|maxauthtries)'` | no, no, no, publickey, no, host-only 주소, `ops@192.168.56.0/24`, 3 |
| 비밀번호 로그인 거절 | `ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no ops@192.168.56.21` | `Permission denied (publickey)` |
| root 로그인 거절 | `ssh -i $env:USERPROFILE\.ssh\vm-lab_ed25519 root@192.168.56.21` | 거절된다. `journalctl -u sshd`에 기록이 남는다 |
| 관리 경로 제한 | 다른 VM에서 `ssh ops@192.168.10.21` | 연결되지 않는다. 관리 접속은 host-only로만 열려 있다 |
| SELinux | `getenforce`, `sudo ausearch -m AVC -ts boot` | Enforcing이다. AVC가 나오면 끄지 말고 원인과 조치를 기록한다 |
| 방화벽 | `sudo nft list table inet vmlab` | input과 forward가 `policy drop`이다. 시험 트래픽 뒤 해당 규칙의 counter가 늘어난다 |
| 허용 판정 | OPS01에서 `nc -vz 192.168.10.21 9100` | 성공한다 |
| 차단 판정 | EDGE01에서 `nc -vz 192.168.10.21 9100` | 시간 초과로 막힌다 |
| 지표 | OPS01에서 `curl -fsS http://192.168.10.21:9100/metrics \| head` | 지표가 나온다. `node_scrape_collector_success`로 개별 수집기도 본다 |
| 서비스 활성 | `systemctl is-enabled sshd chronyd node_exporter vm-lab-firewall vm-lab-host-check.timer` | 모두 enabled다 |
| firewalld | `systemctl is-enabled firewalld` | masked다 |
| 배포판 nftables | `systemctl is-enabled nftables` | masked다. 정책원은 `vm-lab-firewall.service` 하나다 |
| 로그 설정 | `systemd-analyze cat-config systemd/journald.conf` | `Storage=persistent`, `SystemMaxUse=256M`, `MaxRetentionSec=7day`가 최종값이다. 다른 drop-in이 덮지 않았는지 순서까지 본다 |
| 로그 보존 | `ls /var/log/journal`, `journalctl --disk-usage` | 영구 디렉터리가 있고 사용량이 상한 아래다 |
| 시간 | `timedatectl`, `chronyc sources -v`, `chronyc tracking` | Asia/Seoul, NTP synchronized yes, 선택된 소스와 오프셋이 보인다 |
| 디스크 | `lsblk`, `df -h`, `findmnt /var/log` | /boot, swap, /, /var/log가 계획대로다. DB 노드의 sdb는 설치가 건드리지 않았다 |
| 호스트 점검 | `bash /opt/vm-lab/check-host.sh --inspect` | 마지막 줄이 `collection_success=1`이다 |
| 점검 정밀 | `sudo bash /opt/vm-lab/check-host.sh --verify` | 계정, 로그, 방화벽 항목이 OK다. sudo 항목은 구축 단계라 `BUILD_PHASE`로 나온다 |
| sudo 범위 | `sudo -l -U ops` | 지금은 전체 sudo다. 좁힌 뒤에 다시 확인한다 |

허용과 차단은 서로 다른 출발지에서 각각 새 연결로 판정한다. 같은 호스트에서 `curl localhost`로 확인하면 루프백 허용 규칙만 지나므로 정책을 검증한 것이 아니다.

## 8. 재부팅 확인

한 대를 재부팅해 방화벽, SSH, node_exporter, journal이 자동으로 돌아오는지 본 뒤 나머지에 같은 절차를 반복한다.

```bash
sudo systemctl reboot
# 다시 접속한 뒤
journalctl --list-boots
systemctl is-active vm-lab-firewall node_exporter sshd
sudo nft list table inet vmlab
ss -lntp
```

`journalctl --list-boots`에 이전 부팅이 남아 있으면 로그 영구 저장이 실제로 걸린 것이다. `ListenAddress`를 host-only 주소로 고정했기 때문에 그 주소가 올라오기 전에 sshd가 뜨면 기동에 실패한다. 재부팅 확인에서 sshd가 죽어 있으면 `systemctl status sshd`와 `journalctl -u sshd -b`를 보고 `sshd.service.d/10-wait-network.conf`가 적용됐는지 확인한다.

## 9. 역할별 규칙을 올리는 자리

공통 기반이 여는 리슨 포트는 22와 9100 두 개뿐이다. 역할별 포트는 같은 `table inet vmlab`의 input 체인에 이어 붙인다. `/etc/vm-lab/firewall.d/`에 파일을 하나 놓고 `add rule` 형식으로 쓴다. 테이블과 체인을 다시 선언하지 않는다.

```bash
sudo tee /etc/vm-lab/firewall.d/10-app.nft > /dev/null <<'EOF'
add rule inet vmlab input ip saddr 192.168.10.11 tcp dport 8080 ct state new counter accept comment "EDGE01 API"
add rule inet vmlab input ip saddr 192.168.10.41 tcp dport 8081 ct state new counter accept comment "OPS01 Actuator"
EOF
sudo chmod 0600 /etc/vm-lab/firewall.d/10-app.nft
sudo nft --check --file /etc/vm-lab/firewall.nft
sudo systemctl reload vm-lab-firewall.service
```

`/etc/vm-lab/firewall.nft`가 테이블을 비운 뒤 이 디렉터리를 include 하므로 reload 한 번으로 기본 정책과 역할 규칙이 같이 선다. 역할별 허용 출발지는 주소 계획의 포트 표를 따른다.

OPS01의 3000, 9090, 9093에는 허용 규칙을 만들지 않는다. 서비스가 `127.0.0.1`에만 붙고 SSH 터널로 접속한다. 바인딩과 방화벽 두 곳에서 모두 막힌 상태를 확인한다.

```powershell
ssh -i $env:USERPROFILE\.ssh\vm-lab_ed25519 -N -L 3000:127.0.0.1:3000 ops@192.168.56.41
```

터널을 허용하려면 OPS01에만 `/etc/ssh/sshd_config.d/10-ops01-tunnel.conf`가 필요하다. 공통 설정은 `AllowTcpForwarding no`이고 sshd는 먼저 읽은 값을 쓰므로 예외 파일의 번호가 공통 파일의 20보다 앞서야 한다. 같은 명령을 APP01에 걸면 전달이 거부되는지도 확인한다. 이 예외 파일은 OPS01 역할 절차에서 만든다.

## 10. pfSense 전환 이후

pfSense는 사용자가 직접 구축한다. 올라온 뒤에 각 VM에서 아래를 한다. 이 전환을 하기 전까지는 모든 통신이 방화벽을 지난다고 적지 않는다. 지금은 여섯 대가 NAT로 외부에 직접 나간다.

1. `lab-lan` 연결에 기본 경로와 DNS를 붙인다. `nmcli con mod <연결> ipv4.gateway 192.168.10.1 ipv4.dns 192.168.10.1 ipv4.never-default no`
2. `/etc/chrony.conf`의 `server` 줄을 `192.168.10.1`로 바꾸고 `chronyd`를 재시작한다.
3. NAT NIC을 내린다. VirtualBox에서 NIC1의 케이블을 빼거나 어댑터를 끈다.
4. 구축 단계용 DHCP 허용 규칙을 지운다. `sudo bash 00-common-setup.sh --apply --no-nat-dhcp`
5. `ip route show`로 기본 경로가 `enp0s8 via 192.168.10.1` 하나인지, `dig`으로 지정 DNS가 응답하는지 확인한다.

NAT를 내리면 패키지 설치가 pfSense의 허용 정책에 달린다. 그래서 `sysstat`, `tcpdump`, `nmap-ncat`, `bind-utils` 같은 진단 도구를 NAT 구간에서 미리 채운다. 공통 스크립트가 이 일을 한다.

## 11. 구축이 끝난 뒤 sudo 좁히기

구축 중 ops는 전체 sudo를 가진다. 이 구간에서 ops 키를 가진 사람은 root와 같다. 좁히기 전에는 어디에도 제한된 sudo를 적용했다고 적지 않는다.

좁힐 때는 저장소의 `deploy/linux/operator-control.sh` 방식처럼 필요한 명령만 남기는 래퍼를 두고 `/etc/sudoers.d/90-vm-lab-ops`를 그 래퍼 하나로 바꾼다. 바꾼 뒤 `/etc/vm-lab/phase`를 `operate`로 올린다.

```bash
sudo bash /tmp/00-common-setup.sh --apply --phase operate
sudo -l -U ops
sudo -u ops sudo /usr/bin/id   # 거절돼야 한다
sudo bash /opt/vm-lab/check-host.sh --verify
```

`phase`가 `operate`가 되면 호스트 점검이 ops의 wheel 소속과 임의 sudo를 실패로 판정한다. 구축 단계에서는 같은 항목이 `BUILD_PHASE`로만 기록된다. 판정을 없앤 것이 아니라 시점을 나눈 것이다.

## 12. 증거

AWS 작업과 같은 기준으로 각 단계의 명령과 출력을 증거본 폴더에 남긴다. 비밀 값을 입력하는 구간은 캡처하지 않고 누락으로 표시한다. 남길 가치가 있는 화면은 설치 로그, 첫 SSH 접속과 지문 대조, `ss -lntp`, `nft list table inet vmlab`의 counter 증가, 허용과 차단을 서로 다른 출발지에서 판정한 `nc` 결과, 재부팅 후 같은 확인을 다시 실행한 결과다.

단일 PC의 가상 네트워크 시험이다. 여기서 얻은 결과를 학교 AWS나 개인 AWS의 검증 결과로 옮겨 적지 않는다.

## 확인하지 못한 것

아래는 이 절차를 만들면서 실제로 확인하지 못한 항목이다. 실행할 때 먼저 대조한다.

RHEL 10 계열 kickstart 명령 호환성을 확인하지 못했다. `timezone`의 NTP 지정이 `timesource`로 옮겨 간 점, `rootpw --lock`과 `user --lock`의 동작, `cdrom` 지시자의 유효성, LVM `logvol` 문법을 설치 프로그램 문서로 대조해야 한다. 설치 로그의 경고를 읽는다.

Rocky 10.2 minimal ISO의 저장소 구성을 확인하지 못했다. `policycoreutils-python-utils`가 ISO에 없으면 설치가 멈춘다. `sysstat`, `tcpdump`, `nmap-ncat`, `bind-utils`는 설치 후 NAT 구간에서 받는다.

Rocky 10에 어떤 배포판 기본 sshd drop-in이 들어 있는지 확인하지 못했다. `ls -l /etc/ssh/sshd_config.d/`로 목록을 본 뒤 우리 파일의 번호 20이 앞서는지 확인하고 필요하면 조정한다. 최종 적용값은 `sshd -T`로만 판단한다.

VirtualBox에서 NIC 슬롯이 `enp0s3`, `enp0s8`, `enp0s9`로 잡히는지 확인하지 못했다. kickstart의 `%pre`가 설치 시작 시점의 장치 목록을 남기므로 설치 로그에서 먼저 본다.

nftables 규칙 파일을 실제 `nft --check`에 통과시키지 못했다. 작업 PC가 Windows라 nft가 없다. 규칙 문법, `include`의 와일드카드 동작, 규칙 주석의 길이 제한은 첫 VM에서 확인한다. 스크립트는 `nft --check`를 통과하기 전에는 파일을 설치하지 않는다.

SELinux에서 `/usr/local/bin/node_exporter`가 어떤 도메인으로 실행되는지 확인하지 못했다. 정책이 없는 서비스가 `unconfined_service_t`로 도는지, systemd 수집기가 AVC 없이 동작하는지는 기동 후 `ausearch`로 본다.

배포판 `nftables.service`의 `ExecStop`을 확인하지 못했다. 버전에 따라 중지할 때 ruleset 전체를 비우는 것이 있다. 실제 정책은 `vm-lab-firewall.service`가 세우므로 이 유닛은 disable하고 mask한 상태로 둔다. 스크립트가 적용할 때 그 VM의 `ExecStop` 값을 출력하고, `systemctl is-enabled nftables`가 masked인지 확인한다.

kdump를 껐다. 메모리 절약과 커널 덤프를 맞바꾼 선택이므로 장애 분석 때 한계로 인식한다.

## 다른 역할 작업과 맞춰야 할 것

방화벽은 한 계통만 쓴다. 테이블은 `table inet vmlab`, 설정은 `/etc/vm-lab/firewall.nft`, 유닛은 `vm-lab-firewall.service`이고 input 체인의 기본 정책은 `drop`이다. 역할별 규칙은 `/etc/vm-lab/firewall.d/*.nft`를 include 하는 형태로만 더한다. 저장소 `deploy/linux` 이름인 `table inet failstop`이나 `/etc/failstop/firewall.nft`, `failstop-firewall.service`를 쓰는 역할 규칙은 위 9절 형식으로 고친다. 정책원이 둘이면 `failstop` 테이블에서 accept 한 연결도 `vmlab` 테이블의 기본 차단에 다시 걸리고, 무엇이 막았는지 설명할 수 없다. nftables는 서로 다른 base chain을 모두 지나야 통과시키기 때문이다.

배포판 `nftables.service`도 두 번째 정책원으로 살려 두지 않는다. 여섯 대에서 disable하고 mask한다. 이 유닛은 버전에 따라 중지할 때 ruleset 전체를 비우므로, 켜 둔 채로 두면 `vm-lab-firewall.service`가 세운 규칙이 통째로 내려갈 수 있다.

발신 제한은 pfSense 경계에 맡긴다. 호스트 방화벽에서 나가는 통신을 막지 않으며, 그 이유를 각 역할의 규칙 파일 주석에 적는다.

`/etc/vm-lab/phase`의 값은 호스트 점검의 판정 기준이다. 역할 절차에서 이 파일을 임의로 바꾸지 않는다.

## 잠겼을 때 되돌리는 방법

여섯 VM은 root와 ops의 비밀번호를 모두 잠그고 SSH 키 인증만 남긴다. 그래서 방화벽이나 sshd 설정을 잘못 적용해 SSH가 끊기면 VirtualBox 콘솔로도 로그인할 수 없다. 이 문서의 다른 절과 역할별 절차서에 남아 있는 "콘솔에서 확인한다"류의 문장은 그 상태에서 실행할 수 없다. 실제 복구는 아래 두 방법으로 한다.

각 스크립트는 적용 전에 `nft --check`와 `sshd -t`를 돌리고 실패하면 기존 설정을 그대로 둔 채 멈춘다. 그래서 아래 절차가 필요한 경우는 검사를 통과한 규칙이 의도와 달랐을 때다.

### 방법 1. Rocky ISO 구조 모드

가장 빠른 경로다. 대상 VM을 끄고 설치 ISO를 다시 붙인 뒤 구조 모드로 부팅한다.

```powershell
$vbm = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"
& $vbm controlvm DB01 poweroff
& $vbm storageattach DB01 --storagectl SATA --port 2 --device 0 --type dvddrive `
    --medium "C:\Users\kopo26\Desktop\vm-lab\iso\Rocky-10.2-x86_64-minimal.iso"
& $vbm modifyvm DB01 --boot1 dvd
& $vbm startvm DB01 --type gui
```

부팅 화면에서 `Troubleshooting`을 고르고 `Rescue a Rocky Linux system`으로 들어간다. 설치본을 `/mnt/sysimage`에 마운트하는 선택지를 고른 뒤 `chroot /mnt/sysimage`로 들어가 문제가 된 파일을 고친다. 방화벽이면 `/etc/vm-lab/firewall.nft`와 `/etc/vm-lab/firewall.d/`를, sshd면 `/etc/ssh/sshd_config.d/`를 본다. 끝나면 `exit`, `reboot` 하고 부팅 순서를 디스크로 되돌린다.

```powershell
& $vbm storageattach DB01 --storagectl SATA --port 2 --device 0 --type dvddrive --medium none
& $vbm modifyvm DB01 --boot1 disk
```

### 방법 2. 다른 VM에 디스크를 붙여 고치기

구조 모드가 막히면 문제 VM을 끄고 그 OS 디스크를 정상인 다른 VM에 두 번째 디스크로 붙인다. 정상 VM에서 마운트해 파일을 고치고 다시 떼어 낸다. 두 VM이 동시에 같은 VDI를 쓰지 않도록 반드시 문제 VM을 끈 상태에서만 붙인다.

### 데이터 디스크가 어긋났을 때

DB01과 DB02의 데이터 디스크는 `fstab`에 `nofail`과 `x-systemd.device-timeout=10s`를 넣었다. 디스크가 보이지 않아도 부팅은 되고 SSH로 들어갈 수 있다. 대신 PostgreSQL 유닛에 `RequiresMountsFor`를 걸어 마운트가 없으면 서비스가 뜨지 않는다. 빈 경로 위에 PGDATA가 열리는 사고를 막기 위한 값이다. 이때는 SSH로 들어가 `lsblk`와 `blkid`로 디스크를 확인하고 `systemctl status` 로 어떤 마운트를 기다리는지 본다.
