# DB02 Standby 구축과 수동 승격 절차

이 문서는 VM 운영환경의 DB02 한 대를 어떻게 만들고 어떻게 승격하는지 적은 실행 절차이며 결과 보고가 아니다. 구축 절차는 2026-09-22에 실행했고 출력은 [역할 설치 캡처](../../캡처/역할설치/)의 `DB02_역할.txt`, `DB02_복제.txt`, `DB02_복제검증.txt`에 있다. 9절의 수동 승격은 아직 실행하지 않았다. 복제 지연, 승격 소요 시간, 유실량, RTO와 RPO는 전부 미측정이다. 학교 AWS에서 2026-09-20에 잰 값을 이 VM 환경의 값으로 옮겨 적지 않는다.

주소와 포트의 유일한 기준은 `build/00-주소계획.md`다. 이 문서의 값이 그 표와 다르면 그 표가 맞다. 설계 정책의 원본은 `아키텍쳐/교수님_보고본/06_VM_운영환경`의 세 도면이며, 이 문서는 그 도면의 "DB02 Standby", "DB02는 Primary에 복제 연결을 시작하고 일반 거래 SQL을 분산하지 않는다", "기존 Primary 격리 후 Standby 수동 승격" 항목을 실제 명령으로 옮긴 것이다.

pfSense 경계 정책은 사용자가 직접 구성한다. 이 문서가 다루는 nftables 규칙은 호스트 방화벽이며 경계 정책을 대신하지 않는다.

## 1. 파일

| 파일 | 하는 일 |
|---|---|
| `ks/db02.ks` | Rocky Linux 10.2 minimal 무인 설치. OS와 관리 접속까지만 만든다 |
| `scripts/31-db-standby-setup.sh` | 데이터 디스크, PostgreSQL, 복제, 관측, 방화벽, 백업 저장소 구성 |
| `scripts/32-db-failover.sh` | 수동 승격 절차. 각 단계의 조건을 명령 출력으로 판정한다 |
| `build-files/db/db02-node.conf` | 이 노드의 `listen_addresses`. PGDATA 밖에 둔다 |
| `build-files/db/db02-firewall.d.nft` | 공통 기반 `table inet vmlab` 위에 얹는 역할 규칙. 5432를 열지 않는다 |
| `build-files/db/db02-firewall-promoted.d.nft` | 승격했을 때만 쓰는 역할 규칙. 5432를 앱 두 대와 DB01에 연다 |
| `build-files/db/db02-restore-check.sh` | 별도 백업 저장소의 격리 복원 시험 |
| `build-files/db/exchange-backup-verify.service` | 위 시험을 수동으로 돌리는 oneshot 유닛 |
| `build-files/db/summary.sql` | 불변식 판정 입력. `harness/sql/summary.sql` 사본이다 |

`build-files/db` 폴더는 DB01 절차와 함께 쓴다. `exchange.conf`, `pg-queries.yaml`, `postgres_exporter.service`, `node_exporter-host.service`, `create-monitor-role.sql`, `60-exchange-lab.conf`는 DB01 절차가 이미 가져다 둔 것을 그대로 쓴다. 방화벽 유닛은 공통 기반의 `vm-lab-firewall.service` 하나이므로 `failstop-firewall.service`는 설치하지 않는다. 두 노드가 같은 파일을 쓰는 것이 이 구성의 전제다.

## 2. DB02가 맡는 일

DB02는 PostgreSQL 17 Standby다. lab-lan 주소는 192.168.10.32, 관리 주소는 192.168.56.32이며 vCPU 2개, 메모리 3GB, OS 디스크 20GB에 데이터 디스크 20GB를 따로 붙인다. Rocky Linux 10.2 minimal에 PostgreSQL을 직접 설치하고 systemd로 운영한다. Docker는 쓰지 않는다.

DB01(192.168.10.31)에서 `pg_basebackup`으로 초기 구성하고 비동기 스트리밍 복제를 붙인다. 승격 전에는 일반 거래 SQL을 받지 않으며 5432를 어떤 출발지에도 열지 않는다. DB02가 먼저 여는 연결이 DB01의 5432이고 WAL은 그 연결 위에서 반대 방향으로 흐른다. 받는 쪽이 아니라 거는 쪽이므로 5432를 열 이유가 없다.

별도 백업 저장소와 격리 복원 시험 대상도 이 VM이 맡는다. 데이터 디스크를 LVM으로 잘라 `/var/lib/pgsql`과 `/srv/pgbackup`을 다른 파일시스템에 두는 이유가 그것이다. 백업 아카이브와 복원 시험이 DB 볼륨을 채우면 안 된다.

승격은 사람이 격리를 확인한 뒤에만 수동으로 실행한다. 자동 페일오버는 선택하지도 구현하지도 않았다.

## 3. 다른 호스트가 맡는 일

이 문서의 스크립트는 DB02에서만 실행한다. 다음은 각각 다른 호스트의 몫이며 DB02가 대신하지 않는다.

**DB01.** `replicator` 역할과 비밀번호를 만들고, `pg_hba.conf`에 `hostssl replication replicator 192.168.10.32/32 scram-sha-256` 한 줄을 추가한 뒤 `pg_hba_file_rules`의 error가 없는 것을 확인하고 reload한다. `create-monitor-role.sql`로 `failstop_monitor` 역할을 만드는 것도 DB01에서만 한다. 그 역할은 WAL로 DB02에 복제되므로 DB02에서 다시 실행하지 않는다. Standby는 읽기 전용이라 실행해도 오류가 난다. 백업 아카이브 생성도 DB01의 몫이다. `backup-restore-check.py`는 `pg_is_in_recovery()='f'`를 요구하므로 DB02에서는 실행되지 않는다.

**OPS01.** Prometheus 수집 대상에 `192.168.10.32:9100`과 `192.168.10.32:9187`을 넣고 `promtool check config`를 통과시킨 뒤 Prometheus만 재시작한다. 승격 뒤 Primary와 Standby의 역할 라벨을 맞바꾸는 일도 OPS01에서 한다. `finish-db-recovery.py`가 학교 AWS에서 하던 일과 같다.

**APP01과 APP02.** 승격 뒤 DB 주소를 바꾼다. `switch-db-endpoint.py`의 전제 조건을 그대로 따른다. 서비스가 inactive일 때만 변경하고, 변경 전에 백업 파일을 만들고, 기존 백업이 있으면 중단하고, 인증서 지문을 대조한다. DB02는 새 Primary의 인증서 지문만 제공한다.

## 4. VM 생성과 무인 설치

설치는 `01-create-vms.ps1` 하나로 한다. 이 스크립트가 VM을 만들고 `ks/db02.ks`를 답안 파일로 넘긴다.

```powershell
pwsh -NoProfile -File C:\Users\kopo26\Desktop\vm-lab\build\scripts\01-create-vms.ps1 -Role db02
```

`ks-db02.cfg`나 `db02.generated.ks` 같은 두 번째 세트를 만들지 않고, `inst.ks=http://...`로 답안 파일을 받아 가는 경로도 쓰지 않는다. `ks/base.ks.template`은 설계 근거를 읽을 때만 본다.

스크립트가 만드는 구성은 vCPU 2개, 메모리 3GB, OS 디스크 20GB이고 데이터 디스크 20GB를 두 번째 디스크로 따로 붙인다. 파티션을 나누는 것이 아니라 디스크를 하나 더 붙이는 것이다. 저장 경로는 D 드라이브다. C 드라이브 여유가 30GB뿐이라 기본 경로를 그대로 쓰면 안 된다.

NIC 순서는 다른 VM과 같다. 어댑터1은 NAT, 어댑터2는 내부 네트워크 `lab-lan`, 어댑터3은 호스트 전용 어댑터다. 순서가 다르면 Rocky가 잡는 인터페이스 이름이 달라져 답안 파일의 주소 배정이 어긋나므로, 실행 뒤 `VBoxManage showvminfo db02`로 한 번 대조한다.

`ks/db02.ks`의 공개키 자리표시자 `@@OPS_SSH_PUBKEY@@`는 사람이 미리 바꾸지 않는다. `01-create-vms.ps1`이 `build/keys/vm-lab_ed25519.pub`를 읽어 임시 사본에 치환해 넘기고, 치환 후 자리표시자가 남아 있으면 설치를 시작하지 않고 멈춘다. `rootpw --lock`과 `user --lock`으로 두 계정의 비밀번호가 모두 잠겨 있어, 키가 배치되지 않으면 SSH도 VirtualBox 콘솔도 들어갈 수 없다. 콘솔로 복구하는 경로는 없으므로 치환 실패를 경고로 넘기지 않는다.

답안 파일은 `ignoredisk --only-use=sda`로 데이터 디스크를 anaconda의 시야에서 제외한다. 설치 단계에서 `sdb`를 건드리지 않고, PGDATA도 만들지 않는다. Standby의 PGDATA는 `initdb`가 아니라 `pg_basebackup`이 만들기 때문이다.

설치가 끝나면 `ops` 계정으로 키 로그인만 된다. root 직접 로그인과 비밀번호 로그인은 꺼져 있고 SELinux는 enforcing이다. sudo는 구축 단계 동안 전체 권한이며 `/etc/sudoers.d/10-ops`에 있다. 구축이 끝난 뒤 필요한 명령만 남기고 좁힌다. 그 전까지는 "제한된 sudo를 적용했다"고 적지 않는다. `/etc/vm-lab/phase`의 값도 그때 `build`에서 `operate`로 바꾼다.

설치 후 `ssh -i $env:USERPROFILE\.ssh\vm-lab_ed25519 ops@192.168.56.32`로 들어가 `ip -brief address`로 세 주소를 확인한다. 구축 단계에서는 `enp0s3`의 NAT로 패키지를 받는다. pfSense가 올라온 뒤 기본 경로를 192.168.10.1로 바꾸고 NAT를 내린다. 이 전환 전에는 DB02가 방화벽을 지나지 않는 외부 경로를 가지므로, 그 상태의 검증 결과를 방화벽을 지나는 통신의 검증으로 적지 않는다.

## 5. 구축 자료 복사와 공통 기반

작업 PC의 `build` 폴더를 DB02의 `/opt/vm-lab`으로 복사한다. 여섯 대가 같은 방식이다. `keys/`는 제외한다. 개인키는 산출물 폴더에 두지 않지만 공개키만 있는 폴더라도 VM에 올릴 이유가 없고, 제외 규칙을 빼면 나중에 키가 다시 들어왔을 때 그대로 따라 올라간다.

```
# 작업 PC에서
rsync -av --delete --exclude 'keys/' \
  C:/Users/kopo26/Desktop/vm-lab/build/ ops@192.168.56.32:/opt/vm-lab/
```

옮긴 직후 DB02에서 키 파일이 따라오지 않았는지 확인한다. 아래 두 명령은 아무것도 출력하지 않아야 한다.

```
find /opt/vm-lab -name 'vm-lab_ed25519*'
find /opt/vm-lab -name 'lab_ed25519*'
```

그다음 공통 기반을 먼저 올린다. 이 절차가 패키지, journald 보존, `/var/log/vm-lab`의 logrotate, nftables 기본 차단 정책(`table inet vmlab`), node_exporter, 5분 주기 호스트 점검, sshd 강화를 맡는다.

```
# DB02에서
sudo /opt/vm-lab/scripts/00-common-setup.sh --plan
sudo /opt/vm-lab/scripts/00-common-setup.sh --apply
```

공통 기반을 올리면 입력 정책이 이미 drop이고 22와 9100이 열려 있다. 그 위에 DB02 역할 규칙으로 9187 하나만 더한다. 방화벽 계통은 `table inet vmlab` 하나이며 `table inet failstop` 단독 규칙과 배포판 `nftables.service`는 쓰지 않는다. 그래서 공통 기반을 건너뛰고 31 스크립트를 먼저 돌리지 않는다.

`node_exporter`와 `postgres_exporter` 배포본은 NAT 경로로 내려받아 SHA-256을 대조한다. 외부 접속이 막혀 있으면 작업 PC에서 받아 `/opt/vm-lab/downloads`에 옮긴 뒤 다시 실행한다. 기대 해시는 `docs/reports/AWS_작업.md`의 학교 기록값과 같고, DB01 스크립트와 같은 값을 쓴다.

## 6. 구축 순서

31 스크립트는 두 묶음으로 나뉜다. 앞 묶음은 DB02 안에서 끝나는 일이고, 뒤 묶음은 DB01과 맞춰야 하는 일이다. 인증서 지문 대조와 복제 비밀번호는 사람이 화면을 보고 넣어야 하고, 베이스백업은 DB01이 준비된 뒤에만 성립하므로 `all`에 넣지 않았다.

```
sudo /opt/vm-lab/scripts/31-db-standby-setup.sh all 2>&1 | tee ~/db02-build.log
```

`all`이 실행하는 단계는 `preflight disk packages mount-guard config tls journald firewall backup-store`다. `mount-guard`는 DB02를 구축한 뒤에 더한 단계이며 VM에서는 아직 실행하지 않았다.

**preflight.** OS, 호스트 이름, 두 주소, SELinux 모드, 데이터 디스크, 로케일, 시간 동기화, DB01의 5432 도달 여부, 공통 기반 유무, 필요한 원본 파일을 확인한다. 호스트 이름이나 주소가 다르면 여기서 멈춘다. 엉뚱한 VM에서 실행하면 복제 방향이 뒤집히기 때문이다.

**disk.** `/dev/sdb`에 LVM 볼륨 그룹 `vg_pgdata`를 만들고 논리 볼륨 두 개로 나눈다. 12GB는 XFS로 포맷해 `/var/lib/pgsql`에, 6GB는 `/srv/pgbackup`에 마운트한다. 나머지는 여유로 둔다. `fstab`에는 UUID로 등록하고 스크립트는 `nofail`과 `x-systemd.device-timeout=10s`를 붙인다. 디스크가 보이지 않아도 부팅과 SSH 접속은 되게 하고, 대신 PostgreSQL 유닛이 마운트를 요구해 서비스만 멈추게 하는 설계다(공통 절차의 '데이터 디스크가 어긋났을 때'). 기존 서명이나 파티션이 있으면 스크립트가 멈춘다. 대상 디스크를 잘못 지정했을 때 데이터를 지우는 경로를 두지 않기 위해서다.

**mount-guard.** PostgreSQL 유닛에 `RequiresMountsFor=/var/lib/pgsql` 드롭인을 건다. `disk`는 패키지 설치 전에 돌아 유닛이 없으므로 이 일을 `packages` 뒤로 뺐다. 이 단계가 없던 때 구축한 DB02에는 드롭인이 없다고 보며, 캡처로 확인한 값은 없다. 그 상태에서는 `nofail` 때문에 디스크 없이도 부팅되고 서비스를 막는 장치가 없다. 다음에 VM을 켜면 고친 스크립트를 옮긴 뒤 `sudo /opt/vm-lab/scripts/31-db-standby-setup.sh mount-guard verify`를 실행한다.

**packages.** 기본 패키지와 PostgreSQL 17을 설치한다. PGDG 저장소 등록에 실패하면 멈추고, DB01이 무엇으로 설치했는지 먼저 확인하라고 알린다. 메이저 버전이 다르면 복제가 성립하지 않는다. 설치 후 유닛 이름과 PGDATA, 실행 파일 경로를 실제로 읽어 출력한다. 추측하지 않는다.

이 단계에서 `initdb`를 실행하지 않는다. Standby의 PGDATA는 `pg_basebackup`이 만든다. 학교 AWS 기록에도 "Standby에서 initdb를 다시 실행하면 안 된다"가 그대로 적혀 있다.

소유권과 SELinux 문맥도 이 단계에서 맞춘다. `/var/lib/pgsql`을 마운트 지점으로 잡은 이유는 기본 문맥 규칙 `postgresql_db_t`를 그대로 쓰기 위해서다. `/srv/pgbackup`은 기본값이 다르므로 `semanage fcontext`로 규칙을 추가하고 `restorecon`을 실행한다. SELinux는 끄지 않는다.

**config.** `exchange.conf`를 SHA-256 대조 후 `/etc/postgresql/exchange.conf`에 root:postgres 0640으로 두고, `db02-node.conf`를 `/etc/postgresql/node.conf`로 배치한다. `node.conf`를 PGDATA 밖에 두는 것이 중요하다. PGDATA 안에 있으면 `pg_basebackup`이 DB01의 주소를 그대로 가져와 DB02가 DB01 주소로 열려다 기동에 실패한다.

`exchange.conf`에서 이 구성에 직접 영향을 주는 값은 `wal_level = replica`, `synchronous_standby_names = ''`, `hot_standby = on`, `wal_log_hints = on`, `ssl = on`, `password_encryption = 'scram-sha-256'`이다. `synchronous_standby_names`가 비어 있으므로 복제는 비동기다.

**tls.** 이 노드의 서버 인증서와 키를 만든다. SAN에 `IP:192.168.10.32`를 넣는다. 승격 뒤 앱이 `sslmode=verify-full`로 검증할 인증서이고, 앱은 이름이 아니라 IP로 붙기 때문이다. `server.key`는 postgres:postgres 0600이며 이 호스트 밖으로 복사하지 않는다. 출력된 지문은 승격 때 앱에 전달할 값이므로 적어 둔다.

**journald.** 로그 보존 설정을 확인한다. 공통 기반이 이미 걸어 두었으면 덮어쓰지 않는다. 복제 지연과 승격 시각을 판단하려면 로그 시각이 맞아야 하므로 chrony 상태도 함께 본다.

**firewall.** `/etc/vm-lab/firewall.d/31-db02.nft`로 역할 규칙을 얹고, `nft --check`를 통과시킨 뒤 `vm-lab-firewall.service`를 reload한다. 5432는 열지 않는다. 배포판 `nftables.service`는 disable하고 mask한 상태로 둔다.

이 단계는 입력 정책이 drop인 상태를 만든다. 규칙이 잘못되면 SSH가 끊기므로 VirtualBox 콘솔 창을 열어 둔 상태에서 실행한다.

**backup-store.** `/srv/pgbackup` 아래에 `incoming`과 `restore`를 만들고 격리 복원 시험 스크립트와 `exchange-backup-verify.service`를 설치한다. 타이머는 걸지 않는다. 자동 주기 실행은 아직 정하지 않았고, 복원 시험은 디스크와 시간을 함께 쓰므로 운영자가 시점을 보고 수동으로 start한다.

여기까지 끝나면 DB01과 맞추는 단계로 넘어간다. DB01에서 `replicator` 역할과 비밀번호를 만들고 DB02용 `pg_hba` 한 줄을 넣은 뒤여야 한다.

```
# DB01에서 공개 인증서를 DB02로 보낸다
scp /etc/postgresql/server.crt ops@192.168.56.32:/tmp/db01-server.crt
openssl x509 -in /etc/postgresql/server.crt -noout -fingerprint -sha256

# DB02에서
sudo /opt/vm-lab/scripts/31-db-standby-setup.sh primary-cert /tmp/db01-server.crt
sudo /opt/vm-lab/scripts/31-db-standby-setup.sh confirm-primary <DB01 화면에서 읽은 지문>
sudo /opt/vm-lab/scripts/31-db-standby-setup.sh passfile
sudo /opt/vm-lab/scripts/31-db-standby-setup.sh basebackup start monitor exporters verify
```

**primary-cert와 confirm-primary.** 받은 인증서를 `/etc/postgresql/primary.crt`로 두고 지문을 출력한다. DB01 화면의 값과 눈으로 대조하고, 일치하면 그 값을 `confirm-primary`에 넣는다. 스크립트는 입력한 지문을 실제 파일에서 계산한 값과 비교하고, 일치할 때만 표시 파일을 남긴다. 이 표시가 없으면 베이스백업 단계가 진행되지 않는다. 전송 자체를 신뢰 근거로 삼지 않는다.

**passfile.** DB01에서 만든 `replicator` 비밀번호를 화면에 표시하지 않는 입력으로 받아 `/var/lib/pgsql/.pgpass`에 쓴다. `fix-replication-passfile.py`와 같은 방식이다. umask 0077로 만들고, 콜론과 역슬래시를 이스케이프하고, postgres:postgres 0600으로 둔다. 파일 내용을 출력하지 않고 문서와 캡처에도 남기지 않는다.

**basebackup.** 다음 연결로 전량 베이스백업을 받는다.

```
host=192.168.10.31 port=5432 user=replicator application_name=vm_standby
sslmode=verify-full sslrootcert=/etc/postgresql/primary.crt
passfile=/var/lib/pgsql/.pgpass
```

옵션은 `-D <PGDATA> -Fp -Xs -P -R --no-password`다. 비밀번호 본문은 연결 문자열에 넣지 않는다. 받은 뒤 `pg_verifybackup`을 통과시키고, `standby.signal`이 있는지, `postgresql.auto.conf`의 `primary_conninfo`에 비밀번호 본문이 아니라 `passfile`이 들어갔는지 확인한다. `primary_slot_name`은 빈 값으로 명시한다. 기존 PGDATA에 내용이 있으면 스크립트가 멈춘다. 덮어쓰지 않는다.

**복제 슬롯은 쓰지 않는다.** 이 절차도 DB01 절차도 같은 값이다. `pg_basebackup`에 `-S`를 붙이지 않고 `primary_slot_name`을 빈 값으로 두며, DB01에서 슬롯을 만드는 단계도 없다. 슬롯이 없으므로 DB02가 오래 멈췄을 때 DB01이 필요한 WAL 세그먼트를 재활용해 복제가 끊길 수 있고, 그때는 전량 베이스백업을 다시 받는다. 반대로 DB02 장애가 DB01의 데이터 디스크를 채우지 않는다. 이 맞바꿈을 받아들인 선택이다. 구축 뒤 DB01에서 `SELECT slot_name, active, restart_lsn FROM pg_replication_slots;`를 실행해 결과가 비어 있는지 확인한다. 남아 있는 슬롯이 있으면 쓰지 않는 슬롯이므로 DB01에서 정리한다.

**start.** 서비스를 enable하고 기동한 뒤 `pg_is_in_recovery()`가 `t`인지 확인한다. `f`가 나오면 이 호스트는 Standby가 아니므로 즉시 멈춘다. 그다음 `pg_stat_wal_receiver`가 `streaming`이 될 때까지 기다린다. 붙지 않으면 DB01의 `pg_hba.conf` 한 줄, DB01의 방화벽 5432, `.pgpass` 비밀번호, `primary.crt` 지문을 점검한다.

**monitor.** `failstop_monitor` OS 계정을 만들고, 같은 이름의 DB 역할이 복제로 넘어왔는지 조회로 확인한다. 없으면 멈추고 DB01에서 먼저 적용하라고 알린다.

**exporters.** `node_exporter`는 공통 기반이 이미 올렸으면 덮어쓰지 않는다. `postgres_exporter`는 SHA-256을 대조한 뒤 `/usr/local/bin`에 두고 192.168.10.32:9187에 바인딩한다. 0.0.0.0에 바인딩하지 않는다. `failstop_monitor` 계정으로 로컬 unix 소켓에 붙으므로 비밀번호 파일이 없다.

PGDG 패키지의 유닛 이름이 `postgresql-17`이면 `node_exporter`의 systemd 수집기 필터가 DB 서비스를 놓친다. 원본 유닛을 고치지 않고 드롭인으로 `ExecStart`만 덮어써서 실제 유닛 이름에 맞춘다. DB01 스크립트와 같은 방식이다.

`pg-queries.yaml`의 `in_recovery` 값으로 Primary와 Standby를 구분한다. 복제 지연을 유실량으로 바꾸어 읽지 않는다. exporter의 사용자 쿼리 옵션은 폐기 예정 기능이므로 버전을 올릴 때 호환성을 다시 확인한다.

## 7. 확인

`sudo /opt/vm-lab/scripts/31-db-standby-setup.sh verify`가 아래 항목을 실행하고 출력과 판정을 함께 남긴다. 기대와 다른 항목에는 `[확인 필요]`가 붙는다.

| 확인 | 기대하는 값 |
|---|---|
| `lsblk`, `findmnt` | 논리 볼륨 두 개가 XFS로 `/var/lib/pgsql`과 `/srv/pgbackup`에 마운트 |
| `systemctl show -p RequiresMountsFor <PostgreSQL 유닛>` | `/var/lib/pgsql`가 들어 있다 |
| `stat -c '%U %G %a'` PGDATA | `postgres postgres 700` |
| `ls -Zd` PGDATA | 문맥이 `postgresql_db_t` |
| `getenforce` | `Enforcing` |
| `systemctl is-active` | PostgreSQL, chronyd, sshd가 active |
| `SELECT pg_is_in_recovery();` | `t`. `f`면 즉시 멈춘다 |
| `SELECT status, sender_host, sender_port FROM pg_stat_wal_receiver;` | `streaming`, `192.168.10.31`, `5432` |
| `SHOW primary_slot_name;` | 빈 값 |
| `CREATE TABLE verify_ro(i int);` | read-only 오류로 거부. 성공하면 Standby가 아니다 |
| `ss -lnt` | 0.0.0.0이나 `::` 바인딩이 없다 |
| `pg_up`, `pg_wal_position_in_recovery` | 각각 1 |
| `nft list` | 5432에 accept 규칙이 없다 |
| `ausearch -m AVC -ts recent` | 기록이 없거나, 있으면 문맥을 고친다 |

다른 호스트에서 하는 확인은 다음과 같다.

DB01에서 `SELECT client_addr, application_name, state, sync_state FROM pg_stat_replication;`을 보면 `192.168.10.32`, `vm_standby`, `streaming`, `async`가 나와야 한다. `sync`가 나오면 `exchange.conf`의 `synchronous_standby_names` 적용을 다시 본다. 같은 자리에서 거래 DB가 아닌 별도 시험 DB에 행을 하나 넣고 DB02에서 같은 행을 읽는다. 읽히면 복제가 실제로 동작하는 것이다.

APP01에서 `psql -h 192.168.10.32 -p 5432 -U exchange_app -d exchange`를 실행하면 연결되지 않아야 한다. 시간 초과가 나온다. 이 명령이 성공하면 승격 전 정책이 깨진 것이므로 방화벽을 다시 본다.

승격 전 DB02를 막는 것은 nftables 한 겹뿐이다. `pg_basebackup`이 DB01의 `pg_hba.conf`를 그대로 복사하고 그 파일에는 `exchange_app`용 `hostssl` 두 줄이 이미 들어 있기 때문이다. 두 겹으로 막혔다고 적지 않는다. nftables가 열리면 DB에서 다시 걸러 주지 않는다.

작업 PC에서 `curl --max-time 5 http://192.168.56.32:9187/metrics`는 실패해야 한다. 지표 포트를 관리 대역에 열지 않았다.

OPS01에서 `promtool check config`를 통과시킨 뒤 Prometheus만 재시작하고, db02 수집 대상이 UP이며 `pg_wal_position_in_recovery`가 1인지 본다.

VM을 재부팅한 뒤 서비스 상태와 `pg_stat_wal_receiver`를 다시 조회한다. 모두 active이고 streaming이 다시 붙어야 한다.

## 8. 별도 백업 저장소와 격리 복원 시험

복제본은 삭제나 오입력까지 보호하는 백업이 아니다. 별도 백업 저장소와 격리 복원 시험을 따로 둔 이유가 이것이다.

아카이브는 DB01에서 `backup-restore-check.py`로 만든다. 그 스크립트는 같은 스냅샷에서 `pg_dump`와 원본 건수를 얻고 결과 JSON에 `sha256`과 `source_counts`를 남긴다. DB02는 그 아카이브와 결과 JSON을 받아 복원 시험만 한다.

전송은 관리 대역의 SSH로 한다. DB01의 192.168.56.31에서 DB02의 192.168.56.32로 보낸다. 서비스 통신망이 아니라 관리망을 데이터 이동에 쓰는 구성이므로 도면의 통신 정책과 다르다. 이렇게 한 이유는 DB02의 5432를 열지 않기 위해서다. 승격 전 DB02에 5432 accept를 하나라도 만들면 그 포트로 무엇이 들어올 수 있는지 다시 따져야 한다.

```
# DB01에서. backup-restore-check.py 는 failstop 저장소의
# deploy/linux/postgresql/backup-restore-check.py 이며 DB01에 올려 두고 실행한다.
sudo -u postgres <DB01에 올린 backup-restore-check.py> \
     --invariants /opt/vm-lab/build-files/db/summary.sql
scp /var/lib/pgsql/backup-checks/<ID>/exchange.dump \
    /var/lib/pgsql/backup-checks/<ID>/result.json ops@192.168.56.32:/tmp/

# DB02에서
sudo install -d -o postgres -g postgres -m 0700 /srv/pgbackup/incoming/<ID>
sudo install -o postgres -g postgres -m 0600 /tmp/exchange.dump /tmp/result.json \
     /srv/pgbackup/incoming/<ID>/
sudo restorecon -R /srv/pgbackup
sudo systemctl start exchange-backup-verify.service
sudo journalctl -u exchange-backup-verify -n 80 --no-pager
sudo cat /srv/pgbackup/restore/<ID>/result.json
```

복원 시험은 `backup-restore-check.py`의 기법을 그대로 가져왔다. `initdb`로 임시 클러스터를 만들고, `listen_addresses`를 비우고, 포트 55432의 unix 소켓만 열고, `pg_restore --exit-on-error`로 복원하고, 원본과 복원 건수를 비교하고, `summary.sql`의 불변식으로 판정하고, 끝나면 `pg_ctl stop`으로 내린다. DB02의 복제본 PGDATA는 건드리지 않는다. 시작 전에 아카이브의 SHA-256을 DB01 결과 JSON의 값과 대조하고, 기동 직후 `ss -lnt`로 TCP 55432가 열리지 않았는지 실제로 확인한다.

결과는 `/srv/pgbackup/restore/<ID>/result.json`에 남는다. `status`가 `PASS`이고 `source_counts`와 `restored_counts`가 같으며 `test_cluster_stopped`가 true여야 한다. 복원 시험 중 다른 터미널에서 `ss -lnt | grep 55432`를 실행하면 아무것도 나오지 않아야 한다.

임시 클러스터의 unix 소켓 문맥 때문에 SELinux 거부가 생길 수 있어 `backup-store` 단계에서 `postgresql_var_run_t` 규칙을 미리 추가한다. 그래도 거부가 나오면 `ausearch -m AVC -ts recent`로 거부 내용을 읽고 필요한 규칙만 추가한다. SELinux를 끄지 않는다.

이 백업 저장소는 같은 작업 PC의 가상 디스크 위에 있다. PC 고장이나 디스크 손상에는 대응하지 못한다. 실제 오프사이트 백업으로 적지 않는다.

## 9. 수동 승격 절차

실제 장애 때 `32-db-failover.sh`를 순서대로 실행한다. 이 스크립트는 판단을 대신하지 않는다. 승격 여부는 운영자가 정한다. 각 단계는 앞 단계가 끝났는지 기록에서 확인하고 그 단계의 조건을 명령 출력으로 다시 판정한다. 확인되지 않으면 다음으로 넘어가지 않는다.

한 번의 장애 대응은 하나의 실행 기록으로 묶인다. `/var/log/vm-lab/failover/<실행 ID>/` 아래에 단계 기록, 증거 파일, 불변식 CSV, 판정 결과가 남는다. `status`로 언제든 현재 상태를 볼 수 있다.

지켜야 하는 원칙은 하나다. 구 Primary를 쓰기 불가로 만든 뒤에 새 Primary를 연다. 순서를 바꾸면 두 노드가 동시에 쓰기 가능해지고, 복제로 이어져 있지 않은 두 쓰기는 병합할 방법이 없다. "확실히 죽었다"는 판단에 기대지 않는다.

**01-detect.** 장애를 확인한다. DB01의 `pg_isready` 결과와 앱의 리스 갱신 실패를 구분해서 본다. 앱이 리더 리스를 갱신하지 못하는 것과 DB가 죽은 것은 다른 사건이다. 장애 시각과 외부 ACK를 어디에 보존했는지 기록한다. ACK는 승격한 DB의 명령 저널과 대조할 원본이므로 장애가 난 DB 밖에 있어야 한다. 이 호스트가 이미 Standby가 아니면 스크립트가 멈춘다.

**02-hold.** APP01과 APP02에서 쓰기 요청과 봇 주문 접수를 멈춘다. 멈추는 방법은 구성에 따라 다르므로 스크립트가 대신 실행하지 않고, 어느 호스트에서 어떤 명령을 썼는지 기록한다. 이 단계 전에 승격하지 않는다.

**03-fence.** 이 절차에서 가장 중요한 게이트다. 네 가지를 모두 확인해야 통과한다.

| 조건 | 내용 |
|---|---|
| C1 | DB01의 PostgreSQL이 비활성이다 |
| C2 | DB01의 PostgreSQL이 재기동되지 않는다 |
| C3 | DB01에 5432 LISTEN이 없다 |
| C4 | 앱에서 DB01로의 접속이 거부된다 |

`prepare-db-recovery.py`의 `rejoin-old` 분기가 `ActiveState=inactive`와 `UnitFileState=masked`를 검사하고 하나라도 어긋나면 즉시 멈추는 것과 같은 판정이다. 하나라도 명령 출력으로 확인되지 않으면 승격을 중단한다. 사람의 보증으로 대신하지 않는다. 죽은 줄 알았던 노드가 깨어나 두 노드가 동시에 쓰기 가능해지는 상황을 막기 위한 조건이다.

스크립트는 먼저 DB02에서 직접 DB01의 5432와 관리 22를 다섯 번씩 두드린다. 한 번의 실패를 격리 근거로 쓰지 않는다. 5432가 한 번이라도 응답하면 그 자리에서 중단한다.

DB01에 접근할 수 있으면 DB01에서 서비스를 중지하고 mask한 뒤 증거 파일을 만들어 DB02로 옮긴다.

```
# DB01에서
PG_UNIT=$(systemctl list-unit-files --type=service --no-legend 'postgresql*.service' \
          | awk '{print $1}' | grep -v '@' | head -n1)
sudo systemctl stop "$PG_UNIT"
sudo systemctl mask "$PG_UNIT"
{
  printf 'hostname=%s\n' "$(hostname -s)"
  printf 'unit=%s\n' "$PG_UNIT"
  printf 'ActiveState=%s\n' "$(systemctl show "$PG_UNIT" -p ActiveState --value)"
  printf 'UnitFileState=%s\n' "$(systemctl show "$PG_UNIT" -p UnitFileState --value)"
  printf 'listen_5432_count=%s\n' "$(ss -lnt | grep -c ':5432' || true)"
} > /tmp/db01-isolation.txt
scp /tmp/db01-isolation.txt ops@192.168.56.32:/tmp/
```

DB01에 접근할 수 없으면 하이퍼바이저에서 전원을 내린다. 이 경로는 관리 22까지 닫힌 것을 DB02가 직접 확인한 뒤에만 인정된다.

```
# 작업 PC에서. 대상 이름이 db01인지 확인하고 실행한다
VBoxManage controlvm db01 poweroff
```

두 경우 모두 앱 쪽 증거가 필요하다. APP01 또는 APP02에서 만든다.

```
{ printf 'hostname=%s\n' "$(hostname -s)"
  ncat -z -w 3 192.168.10.31 5432; printf 'app_probe_exit=%s\n' "$?" ; } > /tmp/app-probe.txt
scp /tmp/app-probe.txt ops@192.168.56.32:/tmp/
```

그리고 DB02에서 둘 중 하나로 실행한다.

```
sudo /opt/vm-lab/scripts/32-db-failover.sh 03-fence \
     --db01-evidence /tmp/db01-isolation.txt --app-evidence /tmp/app-probe.txt

sudo /opt/vm-lab/scripts/32-db-failover.sh 03-fence \
     --powered-off 'VBoxManage controlvm db01 poweroff' --app-evidence /tmp/app-probe.txt
```

**04-lsn.** `pg_last_wal_receive_lsn()`과 `pg_last_wal_replay_lsn()`이 같아질 때까지 기다리고 값을 기록한다. 재생 중에 승격하면 그만큼 더 잃는다. 값이 끝내 벌어져 있으면 스크립트가 경고하고 확인 문구를 요구한다. DB01은 격리했으므로 `pg_current_wal_lsn()`은 조회할 수 없고, 조회하지 못한 것을 유실 없음으로 적지 않는다. 지연 0이나 두 LSN의 일치는 무손실 판정이 아니다. 실제 유실 범위는 08단계에서 판정한다.

**05-promote.** `PROMOTE db02`를 정확히 입력해야 진행한다. `SELECT pg_promote(true, 60)`을 실행하고 `pg_is_in_recovery()`가 `f`인지 확인한 뒤 타임라인 번호를 기록한다. 승격은 되돌릴 수 없다. 타임라인이 올라가 DB01을 그대로 Standby로 붙일 수 없고 전량 베이스백업이 기본 경로가 된다.

**06-open.** 승격했다고 앱이 붙는 것은 아니다. `pg_basebackup`이 DB01의 HBA를 그대로 복사했으므로 Standby의 `pg_hba.conf`에는 `exchange_app`용 두 줄이 이미 들어 있지만, DB01을 향하던 복제 규칙은 방향이 반대이고 실제로 포트를 여는 것은 nftables다. 이 단계를 빠뜨리면 승격은 성공했는데 거래가 열리지 않는 상태가 된다.

스크립트는 HBA에 없는 줄만 더한다. 복사본에 이미 있는 줄은 중복으로 넣지 않는다.

```
hostssl exchange exchange_app 192.168.10.21/32 scram-sha-256
hostssl exchange exchange_app 192.168.10.22/32 scram-sha-256
hostssl replication replicator 192.168.10.31/32 scram-sha-256
```

추가한 뒤 `pg_hba_file_rules`의 error가 0인지 확인한다. 오류가 있으면 백업으로 되돌리고 멈춘다. 깨진 HBA로 reload하지 않는다. 그다음 승격용 nft 파일을 `nft --check`로 통과시키고 평상시 파일을 실행 기록에 백업한 뒤 교체한다. 교체 후 5432 accept 규칙이 정확히 세 개인지, 5432가 192.168.10.32에서 LISTEN 중인지 확인한다.

**07-app-switch.** DB02의 서버 인증서 지문을 출력한다. APP01과 APP02에 전달하고, 앱 쪽에서 서비스를 내린 상태로 DB 주소를 192.168.10.32로 바꾸고 재기동한다. 스크립트는 전달했다는 말로 넘어가지 않고 `pg_stat_activity`에서 앱 주소의 접속이 실제로 보일 때까지 최대 5분 기다린다. 확인되지 않으면 멈춘다. 이 단계에서도 일반 거래 접수는 계속 보류한다.

**08-verify.** `verify-db-recovery.py`와 같은 방식이다. `REPEATABLE READ READ ONLY` 한 스냅샷에서 `summary.sql`을 실행하고, 결과 행 수와 판정 형식을 확인하고, CRITICAL과 HIGH 실패가 있으면 그 자리에서 실패로 끝난다. 그다음 01단계에서 보존한 외부 ACK와 승격한 DB의 명령 저널을 대조한 결과, 시험 거래 결과를 기록한다. 불일치가 남으면 거래를 재개하지 않는다. 대조할 원자료가 없으면 유실량을 미확인으로 남긴다.

**09-resume.** `RESUME trading`을 입력하면 재개 시각과 01단계부터의 경과 시간을 기록한다. 재개 뒤 오류율, 지연, DB 연결 수를 관찰한다. 승격 명령에 걸린 시간을 전체 복구 시간으로 적지 않는다. 사람이 장애를 알아차린 시간과 판단 시간이 그 안에 들어 있다.

**10-rejoin.** DB01 재편입 절차를 안내하고, DB02에서 `pg_stat_replication`을 조회해 DB01이 다시 붙었는지 확인한다. 붙지 않았으면 이 단계는 완료로 기록되지 않는다. 재편입은 DB01에서 실행하며, 기존 PGDATA를 rename으로 보존한 뒤 DB02를 원본으로 전량 베이스백업을 받는다. `pg_rewind`는 시도해도 되지만 실패를 기다리지 않는다. 되감기를 사는 WAL 보존 정책은 채택하지 않았다. DB01의 방화벽도 Standby 역할로 되돌려 5432 accept를 없애고, OPS01의 Prometheus 역할 라벨을 맞바꾼다. 복제 재개를 확인하기 전까지는 DB 한 대로 운영 중이며 이 상태를 이중화 복구로 적지 않는다.

## 10. 재사용한 것과 바꾼 것

이 구성은 저장소의 기존 자산을 최대한 그대로 쓴다. 원본을 바꾸지 않고 쓰는 것은 `exchange.conf`, `pg-queries.yaml`, `postgres_exporter.service`, `node_exporter-host.service`, `create-monitor-role.sql`, `60-exchange-lab.conf`, `harness/sql/summary.sql`이다. 방화벽 유닛은 공통 기반의 `vm-lab-firewall.service`를 쓰므로 `failstop-firewall.service`는 가져오지 않는다.

`deploy/linux/firewall-host.sh`는 이 VM에서 그대로 실행할 수 없다. 스크립트는 `ssh_port`가 22이면 중단하고, `standby` 역할에서 `--client-cidr`와 `--replica-cidr`를 모두 필수로 받아 5432에 최소 한 개의 accept를 만든다. 주소계획은 SSH 22를 쓰고 DB02의 5432 허용 출발지를 없음으로 정했으므로 두 조건이 모두 충돌한다. 그래서 `render_rules`의 규칙 모양만 가져와 VM 전용 역할 파일을 직접 썼다. 포트마다 허용 출발지를 먼저 적는 순서, `lo`와 `established,related`를 먼저 accept하는 순서, add와 flush를 한 트랜잭션에 넣는 방식이 그것이다. 입력 정책 자체는 공통 기반의 `table inet vmlab`이 drop으로 두고 있으므로 역할 파일에는 허용 줄만 들어간다. 접근제어도의 "허용하지 않은 새 인바운드 연결은 차단"을 그대로 맞추려면 포트별 drop만으로는 부족하기 때문이다.

나가는 통신은 호스트 방화벽에서 제한하지 않는다. 구축 단계에는 NAT로 패키지를 내려받아야 하고, 발신 제한은 pfSense가 올라온 뒤 경계에서 거는 것을 기본으로 한다. 여섯 대의 발신 정책원을 한 곳에 두려는 판단이며 DB01과 같은 선택이다. 따라서 이 호스트 규칙만으로 "모든 통신이 방화벽을 지난다"고 적지 않는다.

`prepare-db-recovery.py`, `switch-db-endpoint.py`, `finish-db-recovery.py`, `fix-replication-passfile.py`는 학교 호스트 주소 172.31.x, S3 버킷, 20260920 날짜 경로에 고정되어 있다. VM에서 그대로 실행하면 대상 호스트 불일치로 중단되거나 존재하지 않는 버킷을 찾는다. 절차와 안전 조건의 근거로만 읽고 VM 명령은 새로 썼다. 가져온 안전 조건은 격리 확인 게이트, 기존 PGDATA를 rename으로 보존, 전량 베이스백업과 `pg_verifybackup`, `standby.signal` 확인, `primary_slot_name` 빈 값, 서비스가 inactive일 때만 접속 대상 변경, 변경 전 백업 생성, 인증서 지문 대조, passfile 작성 방식이다.

`backup-restore-check.py`는 `pg_is_in_recovery()='f'`를 요구하므로 DB02에서 실행되지 않는다. 아카이브 생성은 DB01의 몫이고 DB02는 수신과 격리 복원 시험을 맡는다. 복원 시험 스크립트는 원본의 기법을 옮기되 고정 경로만 VM 경로로 바꿨다.

## 11. 이 구성이 정하지 않는 것과 남은 위험

복제는 비동기다. DB01이 급사하면 아직 전송되지 않은 WAL이 유실된다. 복제 지연 0이나 receive와 replay LSN의 일치를 무손실 근거로 쓰지 않는다. 실제 유실 범위는 외부 ACK와 승격한 DB의 명령 저널을 대조해 판정하며, 확인할 수 없으면 미확인으로 남긴다.

슬롯을 쓰지 않기로 정했고 DB01 절차도 같은 값이다. 그래서 `exchange.conf`의 `max_slot_wal_keep_size 4GB`는 이 구성에서 보호 장치가 아니다. `wal_keep_size`는 0이고 `archive_mode`는 off다. 단절이 길어져 필요한 WAL이 사라지면 복제가 끊기고 전량 베이스백업을 다시 받는다. 이 조건을 재해 대비 설계로 적지 않는다.

승격은 되돌릴 수 없다. 일시적인 네트워크 흔들림에 승격하면 타임라인이 갈려 되돌리는 비용이 더 크다. 승격 판단 기준은 이 문서가 정하지 않는다.

Rocky Linux 10용 PostgreSQL 17은 PGDG 저장소에서 받을 수 있었다. [DB02 역할 캡처](../../캡처/역할설치/DB02_역할.txt)에 `postgresql17-server-17.11-4PGDG.rhel10.2` 설치가 있고, [DB01 검증 캡처](../../캡처/역할설치/DB01_검증.txt)의 서버 버전도 `PostgreSQL 17.11`이다. DB01의 패키지 이름을 뜬 캡처는 없다. 두 대는 같은 저장소, 같은 메이저 버전을 써야 한다. 메이저가 다르면 복제가 성립하지 않는다. 다시 구축할 때 PGDG의 EL-10 채널이 바뀌어 있으면 DB01에서 먼저 확정하고 DB02를 맞춘다.

앱 리더의 자동 전환과 PostgreSQL의 수동 승격은 다른 장치다. 앱 리더 전환은 DB가 살아 있을 때 앱 사이에서 도는 리스로 결정되고, 이 문서가 다루는 것은 DB 자체가 죽었을 때다. 둘을 같은 사건으로 적지 않는다.

NAT를 내리기 전까지 DB02는 pfSense를 거치지 않는 외부 경로를 가진다. 그 상태에서 얻은 결과를 방화벽을 지나는 통신의 검증으로 적지 않는다.

백업 아카이브를 관리 대역으로 옮긴다. 서비스망이 아닌 관리망을 데이터 이동에 쓰는 구성이므로 도면의 통신 정책과 다르다. 그 이유는 DB02의 5432를 열지 않기 위해서다.

단일 PC의 가상 네트워크 시험이다. 물리 회선, 실제 장비 처리량, 이중화 구성을 다루지 않는다. 여기서 얻은 결과를 학교 AWS나 개인 AWS의 검증 결과로 옮겨 적지 않는다.
