# VM 운영환경 주소와 자원 계획

`아키텍쳐/교수님_보고본/06_VM_운영환경`의 세 도면을 기준으로 실제 값을 확정한 문서다. 이후 모든 kickstart, 설정, 검증 스크립트는 이 표의 값을 쓴다. 값을 바꾸면 이 파일을 먼저 고치고 나머지를 맞춘다.

pfSense CE 2.7.2는 2026-09-26에 작업 PC(DEV-PC)에 설치했다. 구조는 같은 날 사용자가 정한 경계형이다. 여섯 대는 `lab-lan` NIC 하나만 남기고, 작업 PC에서 들어오는 연결과 VM에서 밖으로 나가는 연결이 모두 pfSense를 지난다. 설치와 시험 기록은 [pfSense 증거본](../../../증거본/2026-09-26_VM_pfSense/README.md)에 있다.

2026-09-28에는 연구소장님 숙제대로 투명 방화벽 pfsense-tp를 기존 라우터(pfsense-fw)와 서버 사이에 브리지로 끼우고, 여섯 대를 구역 내부망 네 개로 옮겼다. 서버 안의 주소·경로·DNS는 바꾸지 않았고 기존 라우터의 포트포워딩은 지웠다. 그 위에 L2 포트 보안, 구역 사이 L3·L4 규칙, L7 입구(HAProxy)와 IDS(Suricata)를 붙였다. 기록은 [투명 방화벽 증거본](../../../증거본/2026-09-28_VM_투명방화벽/README.md)에 있다.

## 네트워크

VM은 두 단계로 만든다. 구축 단계에서는 kickstart와 역할 스크립트가 NAT·host-only NIC을 써서 패키지를 받고 SSH로 설치한다. 구축을 마치면 아래 '경계형 전환 절차'로 두 NIC을 떼고 pfSense 뒤로 옮긴 뒤, '투명 방화벽 전환 절차'로 구역을 나눈다. `01-create-vms.ps1`, kickstart, `00`~`41` 스크립트의 host-only 주소(`192.168.56.11`~`.41`)는 구축 단계의 값이다.

| 이름 | VirtualBox 유형 | 대역 | 용도 |
|---|---|---|---|
| `lab-lan` | 내부 네트워크(intnet) | 192.168.10.0/24 | 기존 라우터 LAN(em1, 192.168.10.1)과 투명 방화벽 UPSTREAM(em0)이 붙는 구간. 2026-09-26~28에는 여섯 대의 유일한 NIC이었고, 투명 방화벽 전환 뒤 서버는 여기에 직접 붙지 않는다 |
| `lab-dmz`·`lab-app`·`lab-data`·`lab-ops` | 내부 네트워크(intnet) | 192.168.10.0/24(같은 대역) | 투명 방화벽 브리지의 구역 포트(em2~em5). 각각 EDGE01, APP01·APP02, DB01·DB02, OPS01이 붙는다 |
| host-only | `VirtualBox Host-Only Ethernet Adapter` | 192.168.56.0/24 | 관리망. 경계형에서는 작업 PC(192.168.56.1)와 기존 라우터 관리 인터페이스(em2, 192.168.56.10)만 붙고, 투명 방화벽 관리 인터페이스(em1, 192.168.56.20)가 더해졌다 |
| NAT | VirtualBox NAT | - | pfSense WAN(em0)의 외부 접속. VM의 NAT NIC은 구축 단계에만 쓴다 |

구축 단계의 NIC 순서는 모든 VM에서 같다. NIC1은 NAT, NIC2는 `lab-lan`, NIC3은 host-only이며 Rocky 10에서 `enp0s3`, `enp0s8`, `enp0s9`로 잡힌다. 경계형에서는 NIC2(`enp0s8`)만 남는다. 투명 방화벽 전환 뒤에는 NIC2가 `lab-lan` 대신 구역 내부망에 붙고, 서버 안의 주소는 그대로다.

host-only 어댑터의 호스트 측 주소는 `192.168.56.1`이다. 아래 포트 표에서 '실습 사용자'는 이 주소를 뜻하며 작업 PC의 브라우저와 SSH가 여기서 출발한다. 작업 PC는 `192.168.10.0/24`로 가는 경로를 `192.168.56.10`(pfSense)으로 두어야 VM에 SSH로 닿는다. 이 경로는 Windows 설정이므로 사용자가 직접 추가한다. pfSense는 이 경로에서 출발지 주소를 바꾸지 않으므로 VM의 nftables는 출발지 `192.168.56.1`을 그대로 본다.

경계형에서는 VM끼리의 `lab-lan` 통신이 같은 세그먼트 안이라 pfSense를 거치지 않고 각 VM의 nftables가 판정했다. 그래서 2026-09-26의 통제는 두 겹이었다. 투명 방화벽 전환 뒤에는 세 겹이다. 기존 라우터는 관리망 ↔ 서버 구간과 외부 발신을, 투명 방화벽은 구역 사이(L3·L4)와 포트 보안(L2)·L7 입구를, 각 VM의 nftables는 같은 구역 안의 연결(예: APP01 ↔ APP02)을 거른다. 2026-09-26 시험은 두 겹일 때, 투명 방화벽 증거본 37·38은 세 겹일 때의 결과다.

VirtualBox는 Hyper-V가 켜져 있으면 Windows 하이퍼바이저 위에서 동작하고 이때 AVX2가 게스트에 전달되지 않는다. Rocky Linux 10은 x86-64-v3를 요구하므로 부팅하지 못한다(`Fatal glibc error: CPU does not support x86-64-v3`). 이 작업 PC에서는 사용자가 `bcdedit /set hypervisorlaunchtype off`로 Hyper-V를 끄고 재부팅한 뒤 VM을 켰다. Docker Desktop을 다시 쓰려면 `auto`로 되돌리고 재부팅해야 하며, 그 상태에서는 VM이 부팅하지 않는다.

## VM 배치

host-only 열은 구축 단계의 주소다. 경계형 전환 뒤 여섯 대에는 이 주소가 없다. 방화벽 두 대의 host-only 열은 관리 주소다.

| VM | 호스트 이름 | lab-lan | host-only | vCPU | 메모리 | 디스크 | 역할 |
|---|---|---|---|---|---|---|---|
| pfsense-fw | pfsense-fw.lab | 192.168.10.1 | 192.168.56.10 | 1 | 2GB | 8GB | 기존 라우터(경계 방화벽). WAN em0(NAT, DHCP), LAN em1, 관리 em2. 서버의 기본 게이트웨이·DNS·NTP. 관리 화면은 `https://192.168.56.10:8443` |
| pfsense-tp | pfsense-tp.lab | 192.168.10.2(브리지), 192.168.10.10(L7 입구) | 192.168.56.20 | 1 | 2GB | 8GB | 투명 방화벽. bridge0 = em0 UPSTREAM(`lab-lan`) + em2 DMZ + em3 APP + em4 DATA + em5 OPS, 관리 em1. HAProxy·Suricata. 관리 화면은 `https://192.168.56.20:8443` |
| EDGE01 | edge01.lab | 192.168.10.11 | 192.168.56.11 | 1 | 1.5GB | 20GB | Nginx 웹 진입 |
| APP01 | app01.lab | 192.168.10.21 | 192.168.56.21 | 2 | 3GB | 25GB | Spring Boot 리더 |
| APP02 | app02.lab | 192.168.10.22 | 192.168.56.22 | 2 | 3GB | 25GB | Spring Boot 대기 |
| DB01 | db01.lab | 192.168.10.31 | 192.168.56.31 | 2 | 3GB | 20GB + 데이터 20GB | PostgreSQL Primary |
| DB02 | db02.lab | 192.168.10.32 | 192.168.56.32 | 2 | 3GB | 20GB + 데이터 20GB | PostgreSQL Standby |
| OPS01 | ops01.lab | 192.168.10.41 | 192.168.56.41 | 2 | 6GB | 30GB | Prometheus·Grafana·Alertmanager·보고·Databasus |

호스트 이름은 `<이름>.lab` 하나만 쓴다. DB 인증서의 CN과 SAN이 이미 이 형식이라 바꿀 곳이 가장 적다. `01-create-vms.ps1`의 `--hostname`과 각 kickstart의 `network --hostname`, `/etc/hosts` 항목이 모두 이 표의 값과 같아야 한다. 다르면 kickstart를 이 표에 맞춘다.

여섯 대 합계는 vCPU 11개, 메모리 19.5GB다. OPS01만 4GB가 아니라 6GB인데, 이미 Prometheus·Grafana·Alertmanager·보고 서비스를 함께 맡은 노드에 Databasus 본체와 검증 에이전트와 복원 검증용 임시 PostgreSQL 컨테이너가 더 올라가기 때문이다. 근거는 databasus/02-배치설계.md 다. 작업 PC는 논리 프로세서 12개에 메모리 31.7GB이므로 pfSense까지 켜도 들어간다. 다만 전부 동시에 켜면 여유가 크지 않으니 시험 목적에 따라 필요한 대수만 켠다.

VM 저장 경로는 **D 드라이브**를 쓴다. C 드라이브 여유가 30GB뿐이고 기본 경로가 C에 있으므로 생성할 때 경로를 지정한다.

DB 두 대에는 도면대로 **별도 데이터 디스크**를 붙인다. OS 디스크와 데이터 디스크를 나누고 PGDATA를 데이터 디스크에 두면 마운트·권한·용량 확인이 실제 운영과 같은 모양이 된다.

루프백만 여는 포트는 nftables에 별도 허용 규칙을 두지 않는다. 기본 정책이 drop이므로 다른 VM에서 오는 연결은 그대로 막히고, 같은 VM 안의 `lo` 통신만 지나간다.

node_exporter는 여섯 대 모두 lab-lan 주소(`192.168.10.x:9100`)에 바인딩한다. OPS01만 루프백에 두는 분기는 쓰지 않으며 Prometheus의 대상 주소도 같은 값이다.

정본 진입 오리진은 2026-09-28부터 L7 입구 `https://192.168.10.10`이다. 이전 값은 경계형의 `https://192.168.56.10`(2026-09-26), 그 전의 `https://192.168.56.11`이다. 투명 방화벽 전환 때 NAT를 걷으면서 EDGE01의 인증서 SAN·Nginx `Host`·`X-Forwarded-Host`와 앱의 CORS·WebSocket 오리진에 서버 자기 주소 `https://192.168.10.11`을 넣었다(`60-transparent-entry-edge01.sh`, `61-transparent-entry-app-origin.sh`). L7 입구의 HAProxy는 EDGE01로 넘길 때 `Host`를 192.168.10.11로 바꾸고, 오리진이 `https://192.168.10.10`이면 `https://192.168.10.11`로 바꿔 넘긴다. 그래서 앱은 계속 `https://192.168.10.11`만 허용한다. 구축 단계 스크립트(`10-edge01-setup.sh`, `20-app-setup.sh`)는 가장 처음 값으로 설치하고, `52`·`53`과 `60`·`61` 스크립트가 차례로 바꾼다.

2026-09-26의 포트포워딩은 출발지를 바꾸지 않아 EDGE01의 443·80 허용 출발지가 `192.168.56.1`이었다. L7 입구는 프록시라서 요청이 EDGE01에 출발지 192.168.10.2로 도착하고, 원래 사용자 주소는 HAProxy가 새로 쓴 `X-Forwarded-For`로 넘어간다. EDGE01 Nginx는 192.168.10.2에서 온 요청의 이 헤더만 믿는다(`63-l7-edge01-proxy-trust.sh`).

OPS01의 관제 화면은 VM 밖에 열지 않는다. 작업 PC에서는 `ssh -L 3000:127.0.0.1:3000 ops01`로 터널을 만들어 접속한다.

외부로 나가는 통신은 pfSense LAN 규칙이 정한다. 기본 전체 허용 규칙 두 개는 꺼 두었고, 여섯 대는 pfSense의 DNS 53과 NTP 123에만 닿는다. 패키지 저장소 443 규칙은 만들어 두되 꺼 두고 점검할 때만 켠다. OPS01에서 Teams로 가는 HTTPS는 2026-09-26에 열었다. 규칙의 목적지는 FQDN 별칭 `TEAMS_WEBHOOK`이고, 그 안에는 Teams Workflows 웹훅의 호스트 이름(`*.environment.api.powerplatform.com` 형식) 하나만 넣었다. 전체 주소와 호스트 이름은 저장소에 적지 않는다. 호스트가 Azure Traffic Manager를 거쳐 주소가 바뀔 수 있으므로, pfSense가 별칭을 다시 해석하기 전에는 전송이 잠시 막힐 수 있다. VM 실습망의 Alertmanager 수신자는 아직 `hold` 하나라 실제 알림은 보내지 않는다. 이 밖의 발신은 모두 차단되고 pfSense 로그에 남는다.

차단 로그에 반복해서 남던 발신 두 가지를 2026-09-26에 확인했다. Grafana의 grafana.com 업데이트·플러그인 확인은 `54-ops01-grafana-egress-off.sh`와 `build-files/ops/grafana.ini`로 껐다. Databasus 컨테이너의 사용 통계 전송(`metrics.databasus.com`, 443)은 `build-files/ops/databasus-compose.yml`에 `IS_DISABLE_ANONYMOUS_TELEMETRY=true`를 넣어 껐다. 배치본 `/opt/databasus/docker-compose.yml`을 바꾼 뒤 `systemctl reload databasus`로 컨테이너를 다시 만들었고, 데이터 볼륨은 그대로다.

## 경계형 전환 절차

2026-09-26에 실제로 실행한 순서다. 비밀번호 입력과 Windows 경로 추가는 사용자가 했다.

1. pfSense를 설치하고 인터페이스를 할당한다. 별칭(`ADMIN_PC`, `WEB_SERVER`, `APP_SERVERS`, `DB_SERVERS`, `OPS`, `LAB_VMS`), 관리 화면 8443, 포트포워딩, 관리망·LAN 규칙, 원격 로그를 설정한다.
2. 작업 PC에 `192.168.10.0/24 → 192.168.56.10` 경로를 추가한다(사용자).
3. host-only로 접속해 여섯 대에서 `50-boundary-vm-network.sh`를 실행한다(OPS01은 인자 `ops`). pfSense가 켜져 있어야 스크립트 끝의 DNS·NTP 확인이 성공한다.
4. 여섯 대에서 `51-boundary-sshd.sh`, EDGE01에서 `52-boundary-edge01.sh`, APP01·APP02에서 `53-boundary-app-origin.sh`를 실행한다. EDGE01의 새 인증서(`/etc/pki/tls/certs/edge01.crt`)는 OPS01 `/etc/blackbox_exporter/edge01.crt`에도 넣고 blackbox_exporter를 재시작한다.
5. 여섯 대를 정상 종료하고 `VBoxManage modifyvm <VM> --nic1 none --nic3 none`으로 NAT·host-only NIC을 뗀 뒤 켠다.
6. 작업 PC의 `~/.ssh/config`에 `edge01`~`ops01`을 lab-lan 주소로 등록하고 `ssh <이름>`으로 접속을 확인한다. 주소가 바뀌어 호스트 키 확인 질문이 한 번 나오므로 `StrictHostKeyChecking accept-new`를 둔다.
7. 허용·차단 시험을 실제 접속으로 한다. 결과는 증거본 19~23번이다.

4단계를 빠뜨리고 5단계를 하면 sshd와 Nginx가 사라진 host-only 주소에 묶여 있어 SSH와 웹 진입이 모두 열리지 않는다. 2026-09-26에 실제로 이 순서로 한 번 실패했고, host-only NIC을 임시로 다시 붙여 고쳤다.

## 투명 방화벽 전환 절차

2026-09-28에 실제로 실행한 순서다. 비밀번호와 웹 진입 서버 개인 키 입력은 사용자가 했다. 괄호 안 번호는 [투명 방화벽 증거본](../../../증거본/2026-09-28_VM_투명방화벽/README.md)의 번호다.

1. pfsense-fw를 복제해 pfsense-tp를 만들고(새 MAC) NIC 여섯 개를 `lab-lan`·host-only·`lab-dmz`·`lab-app`·`lab-data`·`lab-ops`에 연결한다. 콘솔에서 공장 초기화한 뒤 관리 인터페이스에 192.168.56.20/24를 준다(01~10).
2. 인터페이스를 UPSTREAM em0, LAN em1, DMZ em2, APP em3, DATA em4, OPS em5로 할당하고 bridge0로 묶는다. 바깥쪽 NAT를 끄고 기본 게이트웨이를 192.168.10.1로 둔다. 필터가 멤버 인터페이스에서 걸리게 `net.link.bridge.pfil_member=1`, `pfil_bridge=0`으로 둔다. 별칭과 구역별 규칙을 만들고 차단 규칙은 기록을 남긴다(14~24).
3. NAT를 걷기 전에 EDGE01에서 `60-transparent-entry-edge01.sh`, APP01·APP02에서 `61-transparent-entry-app-origin.sh`를 실행해 서버 자기 주소로도 들어올 수 있게 한다(13).
4. 여섯 대의 NIC2를 구역 내부망으로 옮긴다(`VBoxManage controlvm <VM> nic2 intnet lab-dmz` 등). 서버 안의 설정은 바꾸지 않는다(26).
5. 옮긴 직후 투명 방화벽에서 `ifconfig bridge0 flushall`로 옛 학습을 비운다. 빠뜨리면 옛 포트에 고정된 MAC 때문에 통신이 끊긴다(27~29, 약 70초).
6. 포트 보안은 sticky와 ifmaxaddr(em0 1, em2 1, em3 2, em4 2, em5 1)로 걸고, 재부팅 뒤에도 남도록 config.xml의 shellcmd에 넣는다. 이 버전에서 `static` 항목은 VLAN 1로 들어가 태그 없는 프레임과 맞지 않으므로 쓰지 않는다(32~34).
7. 기존 라우터의 포트포워딩을 지우고 OPT1에 작업 PC → 서버 허용 규칙을 둔다. LAN에는 투명 방화벽 관리 주소(`TP_MGMT`)의 DNS·NTP와 443을 연다(41~44).
8. OPS01에서 `62-transparent-ops01-syslog.sh`를 실행하고 투명 방화벽의 원격 로그를 켠다(40).
9. L7: HAProxy·Suricata 패키지를 설치하고, EDGE01 인증서와 CA를 등록한 뒤 L7 입구 IP 별칭 192.168.10.10, HAProxy 프런트엔드·백엔드와 검사 규칙, BRIDGE 인터페이스 허용 규칙, UPSTREAM의 'L7 우회 차단' 규칙을 만든다. EDGE01에서 `63-l7-edge01-proxy-trust.sh`를 실행한다(47~50, 55).
10. 허용·차단을 실제 접속으로 시험하고(37·38·49·51·55) 투명 방화벽을 재부팅해 설정이 남는지 본다(45·46).

서버를 옮기는 동안(약 70초), `static` 시도 때(약 50초), 투명 방화벽 재부팅 때(약 82초) 앱 → DB가 끊겨 매칭 리더가 넘어갔다. 리더를 잃은 앱 서버는 설계대로 스스로 재승격하지 않으므로 `systemctl restart exchange-app`으로 재기동해 대기 노드로 돌린다. 투명 방화벽 한 대는 단일 장애 지점이므로 이런 작업은 유지보수 시간에 한다.

## nftables 중앙 관리

2026-09-29부터 여섯 대의 `/etc/vm-lab/firewall.nft`와 `/etc/vm-lab/firewall.d/*.nft`는 [nft-central](../nft-central/README.md)의 `rules/<vm>/` 원본으로 관리한다. 작업 PC에서 `-Audit`로 원본과 VM의 어긋남(파일과 커널 규칙)을 찾고, `-Apply`로 한 대씩 구문 검사·백업·확인을 거쳐 올린다. 확인이 실패하면 VM이 90초 뒤 스스로 되돌린다. 위 표의 스크립트(`00`, `10`~`41`, `50`~`63`)와 DB 승격 스크립트(`32-db-failover.sh`)는 아직 VM 파일을 직접 바꾸므로, 이 스크립트를 실행한 뒤에는 `-Pull`로 원본을 갱신한다. 두 경로를 하나로 합칠지는 정하지 않았다.

## 계정

모든 VM에 관리 계정 `ops`를 만들고 SSH 키 인증만 허용한다. 비밀번호 로그인과 root 직접 로그인은 끈다. sudo는 필요한 명령으로 제한하는 것을 목표로 하되, 구축 중에는 전체 sudo를 두고 구축이 끝난 뒤 좁힌다. 이 순서를 문서에 남기고 "제한된 sudo를 적용했다"를 구축 중에 미리 적지 않는다.

서비스 계정은 역할별로 따로 둔다. 앱은 로그인 불가 `exchange`, DB는 배포판 기본 `postgres`, 관측은 `prometheus`와 `grafana`를 쓴다. 서비스 계정으로 SSH 로그인하지 않는다.

비밀 값은 이 저장소와 증거에 남기지 않는다. 앱의 마스터키·페퍼·세션 시드, DB 비밀번호, Grafana 관리자 비밀번호, Teams 웹훅과 AI 키는 구축할 때 각 VM에서 직접 만들고 권한을 0600으로 둔다.

## 관리 키

여섯 대의 `ops` 계정은 같은 SSH 키 하나로 들어간다. 개인키는 `build` 폴더에 두지 않는다. 산출물 폴더에 있던 기존 키는 노출된 것으로 보고 폐기했고, 새 키를 아래 경로에 만들었다.

- 개인키: `%USERPROFILE%\.ssh\vm-lab_ed25519`
- 공개키: `build\keys\vm-lab_ed25519.pub`

만드는 명령은 다음과 같다. 권한을 좁히는 `icacls`까지 같은 자리에서 실행한다.

```powershell
ssh-keygen -t ed25519 -f $env:USERPROFILE\.ssh\vm-lab_ed25519 -C vm-lab-ops
icacls $env:USERPROFILE\.ssh\vm-lab_ed25519 /inheritance:r /grant:r "$env:USERNAME:(R,W)"
Copy-Item $env:USERPROFILE\.ssh\vm-lab_ed25519.pub C:\Users\kopo26\Desktop\vm-lab\build\keys\vm-lab_ed25519.pub
```

kickstart에 넣는 공개키는 다음 한 줄이다. 공개키는 비밀 값이 아니므로 문서와 산출물에 적어도 된다.

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAINoWIyX4RhRDU0RcIQI+5Z17KYUxjveXJfqlx9l+lZeJ vm-lab-ops
```

kickstart 파일에는 이 값을 직접 박거나 자리표시자로 두고, `01-create-vms.ps1`이 임시 사본에 채워 넣는다. 스크립트는 채우지 못한 자리표시자가 남거나 이 값과 다른 공개키가 들어 있으면 설치를 시작하지 않고 멈춘다. 폐기한 키로 설치하면 그 VM에 들어갈 수 없기 때문이다.

이 키에는 암호구가 없다. 무인 구축을 한 번에 돌리려고 내린 선택이며, 대신 산출물 폴더 밖에 두고 ACL로 현재 사용자만 읽게 좁혔다. 암호구가 없는 키는 파일을 얻은 사람이 그대로 쓸 수 있으므로 이 상태를 안전하다고 적지 않는다. 이 키 하나가 구축 중 여섯 대의 `NOPASSWD` sudo와 같은 값을 가진다.

2026-09-26 지금의 작업 PC(DEV-PC)로 VM을 옮겼을 때 위 개인키가 없었다. 그래서 이 PC에서 새 키 `%USERPROFILE%\.ssh\vm-lab-devpc_ed25519`를 만들고(암호구 없음, ACL은 현재 사용자만), 여섯 대마다 GRUB에서 `init=/bin/bash`로 들어가 `ops`의 `authorized_keys`에 공개키를 추가했다. SELinux는 enforcing을 유지했고 `restorecon`으로 문맥을 되돌렸다. 기록은 증거본 `키재등록/`에 있다. 공개키는 다음 한 줄이다. kickstart에는 아직 위의 원래 키가 들어 있다.

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIACED4CxMvb8vUDnHE1dIEeeyUEJxXN1yR12/tQo/uQn vm-lab-ops-devpc
```

`build` 폴더를 VM으로 복사하는 명령에서는 `keys/`를 제외한다. 필요한 하위 폴더만 지정해 보내고, 보낸 뒤 VM에서 `find /opt/vm-lab -name 'vm-lab_ed25519*'` 결과가 비어 있는지 확인한다.

## 이 계획의 한계

단일 PC의 가상 네트워크 시험이다. 물리 회선, 실제 장비 처리량, 이중화 구성을 다루지 않는다. 여기서 얻은 결과를 학교 AWS나 개인 AWS의 검증 결과로 옮겨 적지 않는다.

앱 두 대는 리더와 대기로 나누지만 리더 전환은 DB의 리스로 결정된다. 앱을 두 대 켠 것만으로 고가용성이 완성됐다고 적지 않는다. DB 승격은 수동이며 비동기 복제라 미복제 기록이 유실될 수 있다.
