# Databasus 배치 설계

Databasus를 학교 AWS와 로컬 VM 실습망의 어느 노드에 어떤 모양으로 넣을지 정한 문서다. 노드 선택, 관리 화면과 DB로 가는 접속 경로, 쓸 계정과 권한, 바꿔야 하는 방화벽 규칙, 백업을 서버 밖으로 내보낼 저장소, Docker를 쓰는 이유와 범위, 이미 있는 백업 절차와의 관계, 그리고 도입을 되돌리는 방법까지를 담았다.

이 문서 전체가 실행 전 설계다. 2026-09-22 기준으로 학교 AWS에도 로컬 VM에도 Databasus를 설치하지 않았고 백업, 외부 보관, 복원 검증 중 어느 것도 한 번도 실행하지 않았다. 아래에 적은 규격, 명령, 규칙, 값은 전부 "이렇게 하기로 정한다"는 뜻이지 "이렇게 해서 통과했다"는 뜻이 아니다. 근거로 인용한 메모리 실측과 비용 단가와 백업 건수는 저장소에 이미 남아 있는 기존 측정이며, Databasus를 올린 상태에서 다시 잰 값이 아니다. 실제 화면과 명령 출력은 실행한 뒤에 증거본에 남긴다.

도구 자체의 기능과 배포 형태는 [01-도구조사.md](01-도구조사.md)에서 확인한 내용을 전제로 쓴다. 여기서는 같은 사실을 다시 설명하지 않고 배치 판단에 쓰이는 대목만 인용한다.

## 정하는 것과 정하지 않는 것

정하는 것은 노드 배치와 그 배치를 성립시키는 경로, 계정, 규칙이다. 정하지 않는 것은 설치 명령의 단계별 순서와 화면 캡처 목록이다. 그것은 [07-캡처계획.md](07-캡처계획.md)와 실제 구축 절차서가 맡는다. 결정 자체의 형식 기록은 ADR 초안 [0034](0034-databasus-offsite-scheduled-backup.md)가 맡는다. 이 문서와 그 초안이 어긋나는 곳이 있어 마지막 절에 따로 모았다.

## 결론

학교 AWS에서는 다섯 번째 EC2를 만들어 그 위에 Databasus를 둔다. bot-1에 얹지 않는다. 로컬 VM 실습망에서는 OPS01에 두되 메모리를 4GB에서 6GB로 올린다. 두 환경 모두 1단계는 논리 백업, 외부 보관, 복원 검증까지만 켜고 물리 백업과 PITR은 설계만 남긴 채 발표 전에는 켜지 않는다. 외부 보관은 학교 계정에서 S3를 쓸 수 없으므로 SFTP를 1순위로 삼고 S3는 10월 초 개인 계정 재배포 구간에서 채택한다.

| 항목 | 학교 AWS | 로컬 VM 실습망 |
|---|---|---|
| 노드 | 신규 `ops-1` | 기존 OPS01 (192.168.10.41) |
| 규격 | t3.small, 암호화 gp3 20GiB, Amazon Linux 2023 | vCPU 2, 메모리 4GB에서 6GB로 증설, 디스크 30GB |
| 백업 대상 | 현재 Primary `172.31.33.195` (AZ-c) | DB01 Primary `192.168.10.31` |
| 관리 화면 | 루프백 4005, SSM 포트 포워딩으로만 접근 | 루프백 4005, SSH 터널로만 접근 |
| 외부 보관 | SFTP 1순위, S3는 개인 계정 단계로 이월 | 작업 PC 또는 별도 경로의 SFTP |
| 1단계 범위 | 논리 백업, 보존 정책, 외부 보관, 복원 검증 | 같음. 학교보다 먼저 예행한다 |

## 학교 AWS의 노드 선택

### bot-1을 쓰지 않는 이유

bot-1은 겉보기에 가장 그럴듯한 후보다. 관측과 보고가 이미 거기 있고, DB 보안 그룹 `sg-03b023cf05dc4bafe`의 TCP 5432가 앱 그룹과 DB 그룹 자신에 더해 봇 그룹까지 허용하므로 새 인바운드 규칙 없이 `pg_hba.conf` 한 줄만 더하면 백업 경로가 열린다. 그런데도 쓰지 않는다. 이유는 메모리다.

bot-1은 t3.small이고 메모리가 2GiB다. Grafana는 초기 384MiB 상한에서 실제로 OOM으로 종료된 적이 있고, 512와 640MiB로 올린 뒤에도 회수 지연이 재발해 최종적으로 `GOMEMLIMIT=512MiB`, `MemoryHigh=768M`, `MemoryMax=896M`으로 조정한 상태다. 관측 구간의 실측은 봇이 약 287MiB에서 298MiB, Grafana가 약 157MiB에서 503MiB, Prometheus가 약 74MiB에서 88MiB였고 호스트 가용 메모리는 약 872MiB에서 1,006MiB 사이였다. 근거는 `docs/reports/AWS_작업.md`의 243행, 245행, 314행, 517행, 521행이다.

그 남은 1GiB 안에 세 가지를 더 밀어 넣어야 한다. Databasus 본체는 공식 최소 요구가 RAM 500MB이고 컨테이너 안에 자체 PostgreSQL을 품고 있다. 복원 검증 에이전트는 동시 작업 하나당 CPU 1코어와 RAM 512MB를 요구한다. 검증이 돌 때마다 원본과 같은 메이저 버전의 임시 PostgreSQL 컨테이너가 하나 더 뜬다. 이 셋의 합은 남은 여유를 넘는다. 게다가 500MB는 최소치 표기일 뿐 우리 규모에서 실제로 얼마를 쓰는지는 재 본 적이 없으므로, 하한값을 가지고 여유를 맞추는 계산 자체가 위험하다.

결과가 어느 쪽으로 나든 나쁘다. 백업 도구가 관측을 죽이거나 관측이 백업을 죽인다. 백업 도구가 다른 서비스의 메모리 압박 때문에 조용히 멈추는 구성은 고객사 DB를 안전하게 지키겠다는 이번 과제의 주장과 정면으로 어긋난다. 실패했을 때 가장 늦게 알아차리는 종류의 실패이기도 하다. 사용자는 이미 여유가 없으면 봇과 관측 노드를 분리하도록 지시해 두었다. 다섯 번째 노드는 이번에 새로 꺼내는 명분이 아니라 이미 예고돼 있던 분리를 실행하는 것이다.

### DB standby를 쓰지 않는 이유

자원만 보면 DB standby가 가장 넉넉하다. 암호화 gp3 50GiB 중 약 4.4%만 쓰고 47.7GiB가 비어 있으며, 읽기 라우팅이 구현돼 있지 않아 사실상 놀고 있다. 그래도 쓰지 않는다.

첫째, AGENTS.md가 역할별 인스턴스 분리를 유지하라고 요구한다. 둘째, 백업 관리자를 백업 대상 DB와 같은 호스트에 두면 그 호스트가 사라질 때 백업 이력과 `secret.key`가 함께 사라진다. 지금 백업이 한 서버의 로컬 디스크에만 있어서 문제인데, 관리 도구까지 DB 호스트에 올리면 실패 지점을 옮기기만 하고 줄이지 못한다. 셋째가 결정적이다. 이 환경은 2026-09-20에 Primary와 Standby를 실제로 맞바꿨다. 현재 Primary는 AZ-c `172.31.33.195`, Standby는 AZ-a `172.31.1.229`다. standby에 올려 둔 백업 도구는 승격 한 번으로 Primary 위의 도구가 된다. 같은 이유로 app-1도 후보가 아니다. 거래 요청을 처리하는 노드에 백업 부하와 새 신뢰 경계를 얹지 않는다.

### ops-1을 새로 만든다

규격은 기존 노드와 같은 모양으로 맞춘다. t3.small, Amazon Linux 2023 x86_64, CPU 크레딧 Standard, 암호화 gp3 20GiB, IMDSv2 Required, 기존 `SafeInstanceProfile`이다. 새 IAM 역할이나 Access Key를 만들지 않으므로 학교 금지 항목에 걸리지 않는다. 보안 그룹은 기존 방식대로 빈 인바운드로 먼저 만들고 자동 태그를 확인한 뒤 필요한 규칙만 추가한다.

배치 가용 영역은 AZ-a를 권한다. 현재 Primary가 AZ-c에 있으므로 백업 관리 노드를 다른 영역에 두면 영역 하나를 잃는 사고에서 백업 이력과 원본이 같이 사라지지 않는다. 다만 이 선택은 리전 내 교차 AZ 전송을 만든다. 현재 DB가 약 16MB 수준이라 전송량은 무시할 만하지만 데이터가 커지면 다시 계산한다.

비용은 730시간 기준으로 EC2 $18.98, EBS 20GiB $1.82, 공인 IPv4 $3.65를 더해 약 $24.45가 늘어난다. 단가는 저장소가 공식 서울 가격표에서 확인해 둔 t3.small 시간당 $0.026, gp3 GB 월당 $0.0912, 공인 IPv4 주소 시간당 $0.005를 그대로 쓴다. 현재 네 대와 총 140GiB의 같은 항목이 약 $103.29이므로 합계는 약 $127.74가 된다. 이 값은 저장소가 이미 "기본 5대를 모두 t3.small로 가정하고 앱 2대와 bot-1에 각각 20GiB, DB 2대에 각각 50GiB"로 계산해 둔 약 $127.74와 같은 구성이다. 다만 저장소 자신이 그 줄에서 밝혀 둔 대로 ALB, LCU, 조회 ASG, load-1, 교차 AZ 전송, 백업 저장, CloudWatch, AI, 세금, 환율은 이 금액에 들어 있지 않다. 이 숫자를 월 40만 원 예산 전체의 견적으로 쓰지 않는다.

공인 IPv4를 붙일지는 다시 볼 여지가 있다. 접근을 SSM으로만 할 것이므로 공인 주소 없이도 관리는 되지만, 현재 학교 구성은 기본 VPC의 퍼블릭 서브넷이고 NAT Gateway를 만들지 않기로 했으므로 공인 주소가 없으면 패키지 설치와 컨테이너 이미지 내려받기가 막힌다. 그래서 위 계산에 IPv4 한 개를 포함했다. 설치가 끝난 뒤 아웃바운드가 계속 필요한지는 저장소 목적지를 어디로 정하느냐에 달려 있으므로 그때 다시 판단한다.

이 노드는 백업 관리와 복원 검증만 맡는다. 나중에 bot-1의 메모리 압박이 재발하면 관측을 이쪽으로 옮길 여지를 남겨 둔다.

### 다섯 번째 노드를 만들지 못할 때

학교 계정에서 EC2를 한 대 더 만들어도 되는지는 확인하지 못했다. 안내 원문에서 확인한 금지 항목은 NAT Gateway, 새 private subnet, VPC endpoint, Route 53, ACM, 새 IAM 역할과 Access Key이고, EC2 대수 한도나 계정 전체 할당량은 확인한 결과가 없다고 저장소가 명시한다. 그러므로 생성 전에 운영자에게 먼저 묻는다.

만들 수 없다는 답이 오면 차선은 bot-1이다. 그때는 조건을 붙이고 그 조건을 문서와 발표에 그대로 적는다. 시장 봇을 중지한 상태에서만 Databasus를 켜고 Grafana와 동시에 운영하지 않는다. 복원 검증은 봇과 관측이 모두 멈춘 시간대에만 돌리고 동시 작업 수를 1로 고정한다. 이 제약을 숨기고 bot-1에 얹지 않는다. 제약을 알고 감수하는 것과 모르고 부딪히는 것은 다르며, 이 차이를 설명하는 것 자체가 이번 과제에서 보일 값어치가 있다.

## 로컬 VM 실습망의 배치

OPS01에 둔다. 여섯 대 합계가 vCPU 11개와 메모리 17.5GB인데 작업 PC는 논리 프로세서 12개에 메모리 31.7GB이므로, OPS01을 4GB에서 6GB로 올려도 합계 19.5GB로 들어간다. 일곱 번째 VM을 새로 만드는 것보다 이쪽이 자원을 덜 쓰고 도면 변경도 작다. 메모리를 올리는 이유는 OPS01이 이미 Prometheus, Grafana, Alertmanager, 보고 서비스를 함께 맡고 있어 여기에 Databasus 본체와 검증 에이전트와 임시 PostgreSQL 컨테이너를 더하면 4GB로는 학교 bot-1과 같은 문제를 축소판으로 재현하게 되기 때문이다. 메모리를 바꾸면 `00-주소계획.md`의 VM 배치 표와 합계 문장을 먼저 고치고 `01-create-vms.ps1`의 값을 맞춘다. 순서를 반대로 하지 않는다.

디스크 30GB는 현재 DB가 약 16MB 수준이라 충분하다. 다만 검증 에이전트가 요구하는 디스크는 백업 파일 크기와 원본 DB 크기의 합에 여유를 더한 값이고 문서는 여유를 최대 5GB로 적는다. DB가 커지면 다시 계산한다.

VM 실습망을 먼저 하는 이유는 여기서 틀려도 거래 데이터가 없기 때문이다. 미확인 항목의 답을 여기서 얻고 학교 AWS에는 확인된 값만 들고 간다.

## 관리 화면 접속 경로

Databasus의 기본 포트는 4005이고 HTTPS가 내장돼 있지 않다. 그래서 이 포트를 어디에도 직접 열지 않는다. Grafana를 다루던 방식을 그대로 따른다.

학교 AWS에서는 컨테이너를 루프백에만 게시하고 SSM 포트 포워딩으로 접근한다. Grafana를 이 PC의 13000으로 포워딩한 선례가 있으므로 같은 방식으로 14005 같은 로컬 포트를 쓴다. 보안 그룹에는 4005 인바운드를 넣지 않는다. 4005에 대해 SSM 포워딩을 실제로 시도한 기록은 없으므로 이 경로는 첫 구축 단계에서 확인할 항목이다.

로컬 VM에서는 SSH 터널로 접근한다. 여기에 놓치기 쉬운 단계가 하나 있다. OPS01의 sshd는 `AllowTcpForwarding local`과 `PermitOpen`으로 전달 목적지를 세 개만 허용하고 있고, `ks/ops01.ks` 243행의 값이 `PermitOpen 127.0.0.1:3000 127.0.0.1:9090 127.0.0.1:9093`이다. 4005가 목록에 없으므로 이 줄에 `127.0.0.1:4005`를 더하지 않으면 터널이 열리지 않는다. 이 값은 `/etc/ssh/sshd_config.d/10-ops01-tunnel.conf`에 있고, sshd는 먼저 읽은 값을 쓰므로 `20-vm-lab.conf`보다 앞에서 읽히는지 함께 확인한다.

설치와 소유자 계정 생성 사이를 벌리지 않는다. v3.59.0부터 사전 생성 admin 계정이 없어지고 최초 가입자가 소유권을 갖기 때문에, 화면이 열린 상태로 두면 먼저 가입한 쪽이 소유권을 가져간다. 기동 직후 바로 소유자 계정을 만들고 관리자 2FA 강제를 켠다. 계정의 아이디와 비밀번호는 서버와 화면에서만 다루고 문서, 로그, 커밋, 캡처에 남기지 않는다.

## 백업 대상과 DB 접속 경로

백업 원본은 Standby가 아니라 Primary로 한다. Standby 백업의 통상적인 이점은 Primary의 부하를 덜어 주는 것인데, 이 DB는 약 16MB이고 봇 목표가 세 종목 합계 3 OPS인 규모라 덜어 줄 부하가 없다. 반대로 잃는 것이 셋이다.

첫째, 비동기 복제라 덤프 시점이 복제 지연만큼 뒤로 밀린다. 둘째, hot standby에서 오래 도는 `pg_dump`는 recovery conflict로 취소될 수 있는데 이를 막으려고 `hot_standby_feedback`을 켜면 Primary가 죽은 튜플을 붙잡게 되어 비용이 Primary로 되돌아온다. 현재 `deploy/linux/postgresql/exchange.conf`에는 `hot_standby_feedback`도 `max_standby_streaming_delay` 조정도 없다. 셋째, 승격으로 역할이 바뀌면 Databasus는 등록된 host와 port를 그대로 보므로 조용히 잘못된 노드를 백업한다. Databasus가 대상이 standby인지 스스로 판별하는지, 역할이 바뀐 것을 감지하는지는 확인하지 못했다.

그래서 Primary를 대상으로 하고 역할 전환에 사람이 개입하는 단계를 절차에 박아 둔다. `docs/reference/operations/DB_수동_페일오버.md`에 "Databasus의 대상 호스트를 새 Primary로 바꾼다"는 단계를 추가한다. 여기에 더해 대상 호스트에서 `pg_is_in_recovery()`가 참으로 바뀌면 사람이 알아채도록 관측 쪽에 점검을 붙인다. 판단 기준은 새로 만들 것이 없다. 기존 `deploy/linux/postgresql/backup-restore-check.py`가 실행 첫머리에서 `pg_is_in_recovery()`가 `f`인지 확인하고 있으므로 같은 기준을 옮겨 쓰면 된다.

연결은 TLS로 한다. Databasus의 연결 설정에서 `sslmode`를 반드시 `verify-full`로 지정한다. 소스에서 `SslMode` 필드가 비어 있으면 `disable`로 떨어지므로 빈칸으로 두면 평문 접속이 된다. 앱과 봇이 모두 `verify-full`로 붙는데 백업 도구만 검증 없이 붙는 상태를 만들지 않는다. 현재 DB 인증서는 자체 서명이라 신뢰 사슬이 없고 `sslrootcert`에 해당하는 CA 파일을 지정해야 하는데, Databasus UI에 CA 업로드 경로가 있는지는 확인하지 못했다. 이 항목을 구축 첫 단계의 확인 목록 맨 앞에 둔다. 확인되지 않으면 그 사실을 적고 넘어가지, `verify-full`로 붙였다고 쓰지 않는다.

## 계정과 권한

### 논리 백업용 DB 계정

기존 `exchange_backup` 역할을 그대로 쓴다. 새 계정을 만들지 않는다.

이 선택의 근거는 두 조건이 정확히 맞물린다는 점이다. Databasus의 권한 검사는 덤프 대상 릴레이션에 대한 스키마 USAGE와 SELECT를 확인하고, 그 위로 슈퍼유저 금지, 데이터베이스 CREATE와 TEMP 금지, 테이블 쓰기 권한 0을 요구한다. `deploy/backup/provision-backup-role.sql`이 만드는 계정은 `pg_read_all_data`만 가지고 `default_transaction_read_only = on`이며, 슈퍼유저와 역할 생성과 DB 생성과 복제와 RLS 우회 중 하나라도 가진 이름이면 아예 실행을 중단하고, `ALTER ROLE`에서도 `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`를 강제한다. 도구가 요구하는 조건을 저장소가 이미 검증해 둔 권한 경계가 그대로 충족한다. 새 계정을 만들면 그 검증을 처음부터 다시 해야 한다.

비밀번호는 서버에서 만들어 root 소유 0600 파일과 도구 화면에서만 다룬다. 값은 이 문서와 증거본과 커밋에 남기지 않고 생성 방법과 권한만 남긴다.

VM 실습망에서도 같은 원칙을 쓴다. 다만 DB01에는 아직 이 역할이 없으므로 같은 SQL로 만든다. 접근제어도에 있는 "DB 원본 대시보드를 사용할 때만 별도 허용: OPS01에서 현재 Primary 5432, 제한된 읽기 계정" 조항이 말하는 제한된 읽기 계정이 성격상 이것과 같다. 다만 그 조항은 대시보드 용도로 적힌 것이므로 백업 용도로 같은 예외를 여는 일은 `00-주소계획.md`의 포트 표에 행을 먼저 넣고 나서 적용한다. 주소계획 문서 자신이 그 순서를 요구한다.

### 물리 백업용 계정을 이번에 만들지 않는 이유

Databasus의 물리 백업과 PITR은 `pg_basebackup`과 영구 복제 슬롯을 쓴다. 명령 조립부가 `--pgdata=- --format=tar --compress=server-zstd --wal-method=fetch --checkpoint=fast --no-manifest`를 붙이고, 주석에 영구 슬롯이 백업이 끝날 때까지 원본의 WAL 세그먼트를 잡아 둔다고 적는다. 증분은 `pg_basebackup --incremental`이며 PostgreSQL 17의 `summarize_wal=on`을 요구한다. 즉 이 경로는 REPLICATION 속성을 가진 로그인과 replication용 `pg_hba` 항목과 슬롯을 함께 요구하므로 `exchange_backup`으로는 성립하지 않는다.

여기서 걸리는 것이 넷이다. 첫째, `provision-backup-role.sql`이 `rolreplication`을 가진 계정을 명시적으로 거부하므로 별도 계정을 새로 만들어야 하고 이는 기존 결정과 충돌하는 새 결정이다. 둘째, `exchange.conf`에 `summarize_wal` 항목 자체가 없어 기본값 off다. 셋째, 슬롯 도입은 학교의 현재 슬롯 없는 복제 운영과 ADR 0025의 WAL 보존 확대 비채택 결정을 함께 건드린다. 넷째, `max_wal_senders`가 4뿐이라 DB02 복제와 `pg_basebackup`과 WAL 수신기가 한꺼번에 붙으면 여유가 거의 없다.

이 넷은 각각 설정 변경이 아니라 새 결정이다. 발표까지 남은 기간에 한꺼번에 뒤집고 검증까지 끝낼 수 없다. 그래서 1단계는 논리 백업과 외부 보관과 복원 검증으로 끊고, PITR은 조건이 무엇이고 왜 아직 켜지 않았는지를 설명하는 항목으로 발표에 넣는다. 조건을 알고 미룬 것과 모르고 빠뜨린 것은 다르다. 덧붙여 `max_slot_wal_keep_size`가 이미 4GB로 잡혀 있어 나중에 슬롯을 도입하더라도 WAL 폭주로 50GiB 볼륨을 채우는 사고에는 상한이 걸린다. 이 점은 2단계에서 PITR을 채택할 때의 유리한 조건으로 기록해 둔다.

### 호스트 계정

Docker를 설치하면 `docker` 그룹 구성원은 사실상 root 권한을 갖는다. 컨테이너에 호스트 파일시스템을 마운트할 수 있기 때문이다. 그러므로 ops-1과 OPS01의 `docker` 그룹에는 구축을 수행하는 관리 계정 하나만 둔다. 서비스 계정을 넣지 않고, 다른 노드의 운영 계정을 이 노드로 확장하지 않는다. 복원 검증 에이전트가 임시 DB 컨테이너를 어떤 방식으로 띄우는지는 문서가 밝히지 않았다. 공식 `docker run` 예시에 `/var/run/docker.sock` 마운트가 없으므로 본체는 소켓을 요구하지 않는 것으로 보이지만, 에이전트가 소켓을 요구한다면 그것은 사실상 host root 권한을 주는 일이다. 요구 여부를 실행 전에 확정하고, 요구한다면 그 사실을 예외 기록에 명시한다.

## 방화벽과 접근 통제 변경

새로 여는 것은 많지 않다.

학교 AWS에서는 DB 보안 그룹의 TCP 5432 인바운드에 ops-1의 보안 그룹을 소스로 하는 규칙 하나를 추가한다. 그리고 현재 Primary의 `pg_hba.conf`에 `hostssl exchange exchange_backup <ops-1 사설 주소>/32 scram-sha-256` 한 줄을 추가한다. 기존 줄을 지우지 않고, 파일을 먼저 백업한 뒤 규칙 오류가 없는지 확인하고 reload한다. 봇 계정을 추가할 때 썼던 순서와 같다. 4005는 보안 그룹에 넣지 않는다. 아웃바운드로 필요한 것은 SFTP 대상 포트와, S3를 쓰게 되면 443이다.

로컬 VM에서는 DB01의 `/etc/vm-lab/firewall.d/30-db01.nft`에 OPS01의 lab-lan 주소를 소스로 하는 5432 허용 한 줄을 추가한다. 현재 이 파일에는 앱 두 대와 DB02의 5432 규칙만 있고 "OPS01은 여기에 없다. 관제는 9187의 postgres_exporter로만 본다"는 주석이 붙어 있다. 이 주석도 함께 고친다. 이 변경이 접근제어도의 조건부 예외를 실제로 발동시키는 첫 사례가 되므로 `00-주소계획.md` 포트 표에 행을 먼저 넣고 도면 쪽 서술을 조건부에서 채택으로 바꾼 뒤에 규칙을 적용한다. DB01 구축에서 `nc -vz 192.168.10.31 5432`가 OPS01에서 실패해야 정상이라고 적어 둔 대목도 같은 변경에서 고친다. 고치지 않으면 다음 사람이 정상 동작을 실패로 읽는다.

### Docker 포트 게시가 nftables를 지나가는 문제

여기에 반드시 짚어야 할 함정이 하나 있다. VM 실습망의 방화벽은 `table inet vmlab`의 input 체인 기본 정책 drop 한 계통이고, 정본 결정에 forward 체인 정책이 없다. 그런데 Docker가 `-p 4005:4005`로 포트를 게시하면 0.0.0.0에 바인딩하고 그 패킷은 nat 테이블의 DNAT를 거쳐 forward 경로로 들어간다. input 훅의 drop 정책은 그 포트를 막지 못한다. 공식 예시 그대로 띄우면 nftables가 막아 줄 것이라는 기대와 달리 lab-lan의 다른 노드에서 관리 화면에 닿는다.

그러므로 반드시 `-p 127.0.0.1:4005:4005`로 게시한다. 학교 AWS는 보안 그룹이 앞에서 막아 주지만 방어를 한 겹에 의존하지 않기 위해 같은 루프백 바인딩을 적용한다. "기본 정책이 drop이니 안전하다"는 문장을 Docker가 올라간 노드에 그대로 옮겨 쓰지 않는다. 적용한 뒤에는 다른 노드에서 4005로 접속을 시도해 실제로 막히는지 확인하고 그 결과를 증거로 남긴다. 이 한 줄이 이번 도입에서 설명할 값어치가 가장 큰 운영 지식이다.

## 외부 저장소

### 학교 계정에서 S3가 성립하지 않는 이유

Databasus의 S3 저장소는 정적 Access Key와 Secret Key만 지원한다. 소스의 `S3Storage` 모델이 `S3AccessKey`와 `S3SecretKey`를 not null로 잡고, 클라이언트 생성부 두 곳이 모두 `credentials.NewStaticV4(accessKey, secretKey, "")`를 쓴다. EC2 인스턴스 역할이나 IMDS나 STS로 자격증명을 받는 경로가 코드에 없다.

그런데 학교 계정은 새 IAM 사용자와 역할과 Access Key 생성을 금지하고, 사용자는 그 금지의 해제를 요청하지 않기로 정했다. 기존 비공개 버킷 `2026-ai-kopo-04-exchange-artifacts-619256964117`은 EC2의 기존 Role로만 접근해 왔다. AWS CLI에서는 그 방식이 되지만 Databasus에서는 되지 않는다. 버킷 이름이 IAM username으로 시작해야 한다는 규칙은 만족시킬 수 있어도 자격증명 방식에서 막힌다. 따라서 학교 구간에서 S3 보관은 현재 규칙 아래에서 성립하지 않는다. 이것은 도구를 잘못 골랐다는 뜻이 아니라 도구의 구현과 계정 정책이 겹쳐서 생긴 제약이며, 발표에서 그대로 설명할 항목이다.

### 학교 구간은 SFTP를 1순위로 한다

대상 후보는 둘이다. 하나는 백업 노드와 다른 가용 영역에 있는 EC2에 백업 전용 계정을 만들고 chroot한 SFTP 대상으로 쓰는 것이다. 다른 하나는 AWS 밖의 작업 PC나 NAS로 내보내는 것이다. 전자는 가용 영역 분리까지만 얻고 리전과 계정 경계는 넘지 못한다. 후자는 상시 연결을 요구하므로 예약 백업의 성공률이 떨어진다. 둘 중 무엇을 택하든 지금의 한 서버 로컬 디스크 한 곳보다 낫다는 점과, 엄밀한 의미의 오프사이트는 아니라는 점을 함께 적는다.

SFTP 저장소의 설정 항목은 소스에서 확인했다. `SFTPStorage` 모델의 필드는 `Host`, `Port`(기본 22), `Username`, `Password`, `PrivateKey`, `Path`, `SkipHostKeyVerify`다. 비밀번호와 개인키를 모두 지원하며 둘 다 채우면 두 인증 방법이 함께 등록된다. 저장된 값은 암호화해 두고 사용할 때 복호화한다. `Path`를 지정하면 업로드 전에 디렉터리 존재를 확인하고 만든다.

여기서 실행 전에 알아야 할 문제를 하나 찾았다. `connect` 함수가 `hostKeyCallback := ssh.InsecureIgnoreHostKey()`를 무조건 사용한다. 모델에 `SkipHostKeyVerify` 필드가 있고 갱신 경로에서 값을 저장하지만, 연결부가 그 값을 보지 않고 항상 호스트 키 검증을 건너뛴다. 즉 이 저장소를 끄든 켜든 SFTP 대상 서버의 신원을 검증하지 않는다. 확인한 파일은 `backend/internal/features/storages/models/sftp/model.go`이고 해당 줄은 322행이다.

그래서 SFTP를 쓰되 다음을 함께 정한다. 전송 경로를 사설 대역 안에 두고 보안 그룹이나 nftables로 출발지와 목적지를 고정해 중간자가 끼어들 위치를 줄인다. 인증은 비밀번호 대신 개인키를 쓰고 대상 계정은 chroot한 전용 계정으로 만들어 셸을 주지 않는다. 그리고 이 한계를 발표에서 숨기지 않는다. 다행히 백업 본문은 업로드 전에 이미 AES-256-GCM으로 암호화된 상태이므로 전송 구간이 엿보여도 내용은 읽히지 않는다. 남는 위험은 가짜 대상 서버에 백업을 올려 보내 놓고 보관에 성공했다고 착각하는 쪽이다. 그래서 외부 보관 성공은 업로드 결과 표시가 아니라 대상 서버에서 실제 객체를 확인하는 것으로 판정한다.

### 개인 계정 단계의 S3

10월 초 개인 계정 재배포 구간에서 S3로 옮긴다. 개인 계정에서는 사용자가 IAM을 소유하므로 버킷 하나에 대해 `PutObject`, `GetObject`, `DeleteObject`, `ListBucket`, `AbortMultipartUpload`만 허용하는 최소 정책의 전용 IAM 사용자를 만들고 그 Access Key를 Databasus에만 준다. 버킷은 같은 리전에 두어 복원 시 EC2로 내려받는 구간이 리전 내 전송이 되게 하고, Block Public Access와 서버 측 암호화를 유지하며 버전 관리와 객체 잠금과 수명 주기 규칙은 버킷 쪽에서 건다.

보존은 한쪽에서만 건다. Databasus의 보존 정책은 기간, 개수, GFS 계층, 백업당과 전체 용량 상한을 지원하는데, 도구 쪽 보존과 버킷 쪽 수명 주기를 이중으로 걸면 어느 쪽이 지웠는지 알 수 없게 되고 도구의 이력과 실제 객체가 어긋난다. 보존은 도구 쪽에 두고 버킷 수명 주기는 저장 계층을 내리는 용도로만 쓰거나, 반대로 하되 한쪽을 권한 있게 정한다. 서울 리전 S3 Standard의 GB 월당 단가와 요청 단가는 이번에 공식 가격표에서 확인하지 않았다. 비용 문단에 숫자를 넣을 때 다시 확인하고 출처를 남긴다.

## Docker 예외의 이유와 범위

학교 AWS의 어느 노드에도 아직 Docker를 설치하지 않았다. bot-1 생성 기록에 Docker를 설치하지 않았다고 명시돼 있고 앱과 DB도 구성 요소를 Linux에 직접 설치해 systemd로 운영한다. 그러므로 이번 도입은 이 프로젝트에서 처음으로 운영 노드에 Docker를 들이는 변경이며 "Docker는 필요한 항목만 이유와 범위를 기록해 사용한다"는 조항이 그대로 적용된다.

예외를 두는 이유는 상류의 배포 형태다. Databasus의 최신 릴리스에는 내려받을 바이너리나 패키지 자산이 없고 공식 설치 방법이 설치 스크립트, `docker run`, `docker compose`, Helm 차트 넷뿐이며 전부 컨테이너를 전제한다. 런타임 이미지가 자기 전용 PostgreSQL 서버와 각 DB의 클라이언트 도구를 함께 담고 있어 애플리케이션 하나를 떼어 내 설치할 구조도 아니다. 이 도구를 쓰기로 한 이상 Docker는 회피할 수 없다.

범위는 백업 노드 한 대로 한정한다. 그 노드의 `databasus` 컨테이너 하나와, 복원 검증 에이전트가 검증할 때마다 만들고 지우는 임시 PostgreSQL 컨테이너다. 앱과 DB와 관측과 보고는 지금처럼 Linux 직접 설치와 systemd를 유지하며 이번 변경으로 옮기지 않는다. 예외가 가리는 실습 범위도 적어 둔다. 이 도구의 프로세스 관리와 로그 수집과 갱신 경로가 systemd와 journald 대신 Docker 아래로 들어간다.

설치 방식은 공식 자동 스크립트를 쓰지 않는다. 그 스크립트는 배포판을 판별해 Docker CE와 compose 플러그인까지 알아서 설치하고 `/opt/databasus`에 compose 파일을 기록하는데, 대화형 확인 없이 root로 돌고 systemd 유닛을 만들지 않으며 재시작을 Docker의 `unless-stopped` 정책에만 맡긴다. 대신 배포판 패키지 관리자로 Docker를 명시적으로 설치하고, 이미지는 `:latest` 대신 확인한 digest로 고정하며, compose를 systemd 유닛으로 감싸 부팅 시 기동과 실패 기록이 journal에 남게 한다. 이미지 digest 고정은 새 기준이 아니라 기존 기준의 적용이다. `deploy/backup/README.md`가 이미 운영에서 검증한 digest를 쓰라고 요구하고 있다.

## 기존 백업 절차와의 관계

대체가 아니라 역할 분담으로 정한다.

`backup-restore-check.py`를 남긴다. 이 스크립트는 Primary 호스트에서 `postgres` 계정으로 Unix socket을 통해 돌면서, `pg_is_in_recovery()`가 `f`인지 먼저 확인하고 같은 스냅샷에서 `pg_dump -Fc`와 원본 건수를 뽑은 다음 `listen_addresses`가 빈 임시 클러스터에 복원해 하네스 불변식 SQL 30개를 대조한다. 2026-09-20 실행에서 명령 12,733건, 이벤트 20,746건, 체결 6,710건, 원장 항목 68,686건이 일치하고 CRITICAL과 HIGH 실패가 0건임을 확인했다. Databasus의 복원 검증은 복원 크기 대조와 테이블별 행 수 보고까지이고 자산별 원장 합이 0인지는 검사하지 않는다.

그래서 둘이 증명하는 것이 다르다. Databasus는 복원이 되는가를 매일 자동으로 증명하고, 기존 스크립트는 복원한 것이 원장 규칙을 지키는가를 사람이 정한 시점에 증명한다. 이 둘을 합쳐야 백업이 쓸모 있다는 주장이 완성된다. 발표에서도 이 구분을 그대로 쓴다. 행 수가 맞는 것과 장부가 맞는 것은 다르다.

겹치지 않게 두 가지를 정한다.

첫째, 실행 시각을 띄운다. 기존 `failstop-backup.timer`는 매일 한국 시간 03:30부터 최대 5분 지연으로 돈다. 이 타이머는 학교 AWS에 아직 배포하지 않았지만 배포하게 되면 겹치므로, Databasus의 예약을 04:10 KST 부근에 둔다. 두 절차가 같은 시각에 같은 DB에서 덤프를 뜨면 부하가 겹치고 어느 쪽 결과인지 구분하기 어려워진다.

둘째, 디스크를 침범하지 않게 한다. `deploy/linux/bot/capacity_guard.py`는 대상 노드의 루트 파일시스템 여유가 20% 이하이거나 2GiB 이하이거나 inode 여유가 10% 이하이면 시장 봇을 멈춘다. Databasus의 로컬 스테이징을 DB 볼륨에 두면 백업이 봇을 멈추는 일이 생긴다. 스테이징은 백업 노드에 두고, Databasus의 전체 용량 상한을 그 볼륨 크기보다 낮게 설정해 도구 스스로 상한에서 멈추게 한다. 기존 스크립트가 원본 크기의 4배에 2GiB를 더한 값과 전체 용량의 5분의 1 중 큰 쪽만큼 여유를 요구하고 그보다 적으면 실행 자체를 거부한다는 점도 같은 계산에 넣는다.

여기에 하나를 덧붙인다. `capacity_guard.py`의 `NODES`는 `app-1`, `bot-1`, `db-primary`, `db-standby` 네 개로 고정돼 있고 그 네 개의 표본이 모두 있어야 판단한다. ops-1을 만들어도 이 목록에 넣지 않으면 백업 노드의 디스크는 보호 대상이 아니다. 백업이 쌓여 디스크를 채우는 것은 백업 도구에서 가장 흔한 사고이므로, Prometheus 수집 대상에 ops-1을 추가하고 `NODES`와 선택자에도 함께 넣는다. 다만 이 가드의 조치는 봇 중지이므로, 백업 노드의 디스크 부족에 봇 중지가 맞는 조치인지는 따로 판단한다. 맞지 않으면 노드별로 조치를 나누거나 별도 경보로 분리한다.

## secret.key를 어떻게 다루는가

이 도입에서 유일한 단일 실패점이다. 백업 암호화 마스터키는 메타데이터 DB가 아니라 `databasus-data/secret.key` 파일에 있고, 개별 백업 키는 이 마스터키와 백업 ID와 임의 salt에서 파생한다. 이 파일을 잃으면 외부에 쌓아 둔 암호문 백업을 전부 복호화할 수 없다. 반대로 이 파일만 있으면 Databasus 없이도 백업을 복구할 수 있다고 공식 문서가 명시한다.

그러므로 생성 직후 백업 노드 밖으로 한 벌 옮기고 root 소유 0600으로 보관한다. 저장소와 증거본과 커밋에는 넣지 않는다. 값 자체를 캡처하지 않고 생성 방법과 권한과 보관 위치만 문서에 남기며, 캡처 계획에 누락 구간으로 표시한다. 보관 위치는 백업 객체를 올리는 저장소와 다른 곳으로 한다. 같은 곳에 두면 저장소를 잃을 때 키도 같이 잃는다. `databasus-data` 아래의 `pgdata`도 설정과 백업 이력을 담고 있으므로 같은 복사 대상에 넣는다. 다만 키와 이력을 함께 두지 말고 분리한다.

백업 도구 자신의 백업을 빠뜨리는 것은 흔한 사고다. 이 절차를 설계에 넣어 두는 것 자체가 보고서에서 설명할 값어치가 있다.

## 되돌리는 방법

도입을 철회하거나 다른 도구로 바꾸게 되면 아래 순서로 되돌린다. 순서가 중요하다. 네트워크 경로를 먼저 닫고 나서 컨테이너를 지우면 진행 중인 업로드가 중간에 끊긴다.

1. 도구 화면에서 예약 백업과 복원 검증 일정을 모두 정지하고 진행 중인 작업이 끝날 때까지 기다린다.
2. 복원 검증 에이전트 프로세스를 중지하고 남은 임시 DB 컨테이너가 없는지 확인한다.
3. `secret.key`와 `pgdata`의 외부 사본이 있는지 먼저 확인한다. 확인 전에 다음 단계로 넘어가지 않는다.
4. Databasus 컨테이너를 중지하고 제거한다. compose를 감싼 systemd 유닛도 함께 비활성화한다.
5. Primary의 `pg_hba.conf`에서 추가했던 `exchange_backup` 한 줄을 지우고 reload한다. 파일 백업과 대조해 다른 줄이 변하지 않았는지 확인한다.
6. 방화벽을 원복한다. 학교는 DB 보안 그룹의 5432 규칙 한 건을 삭제하고, VM은 `30-db01.nft`의 OPS01 5432 한 줄을 지운 뒤 `nft --check`와 reload를 거친다. `00-주소계획.md` 포트 표와 DB01 문서의 서술도 같은 변경에서 되돌린다.
7. Docker 서비스를 비활성화하고 이미지를 삭제한다. 다른 용도로 Docker를 남기기로 했다면 그 이유를 예외 기록에 적는다.
8. ops-1을 만들었다면 인스턴스와 볼륨을 함께 삭제하고 잔여 자원이 없는지 확인한다. VM은 OPS01 메모리를 원래 값으로 되돌리고 주소계획 표를 맞춘다.
9. 관련 문서를 되돌린다. ADR 0034의 상태를 기각으로 바꾸고 0099와 로드맵의 서술을 같은 변경에서 맞춘다.

도구를 걷어내는 것과 데이터를 잃는 것은 분리된다. 이미 만들어진 암호문 백업은 `secret.key`만 있으면 Databasus 없이 복구할 수 있다고 공식 문서가 밝힌다. 다만 그 복구 경로를 실제로 한 번 실행해 보기 전까지는 문서의 설명일 뿐이므로, 도입을 채택으로 바꾸기 전에 도구 없는 복구를 끝까지 실행해 확인한다. 이것이 확인되지 않으면 되돌리는 절차 3번은 안전장치로 작동하지 않는다.

## 실행 전에 확인할 것

아래는 이 배치가 성립하는지를 좌우하는데 아직 답을 모르는 항목이다. 추론으로 채우지 않고 구축 첫 단계에서 순서대로 확인한다. 위쪽이 먼저다.

| 항목 | 왜 중요한가 | 확인 방법 |
|---|---|---|
| 학교 계정에서 다섯 번째 EC2 생성 가능 여부 | 권고 배치 전체가 여기에 달려 있다 | 운영자에게 문의한다. 불가하면 차선 절의 조건부 bot-1로 간다 |
| `sslmode=verify-full`과 CA 파일 지정 가능 여부 | 백업 도구만 검증 수준이 낮아지는 상태를 만들지 않는다 | VM OPS01에서 DB01을 등록하며 연결 설정 화면을 캡처한다 |
| Databasus 본체의 실제 메모리와 CPU 사용량 | 최소 요구 500MB는 하한이다. 노드 규격 판단의 근거가 된다 | VM에서 1회 백업 중 상주 메모리와 최대치를 잰다 |
| 검증 에이전트를 Databasus와 같은 호스트에서 돌릴 수 있는지 | 안 되면 학교에 노드가 하나 더 필요하다 | 같은 호스트에 에이전트를 등록해 본다 |
| 검증 에이전트가 Docker 소켓을 요구하는지 | 소켓을 넘기는 것은 사실상 host root 권한을 주는 일이다 | 등록과 첫 검증 실행에서 요구 여부를 확인한다 |
| 검증 에이전트 바이너리의 무결성 확인 수단 | 저장소 규칙상 내려받은 실행 파일은 해시를 대조해 왔다 | 서명이나 게시된 해시가 있는지 찾고 없으면 그 공백을 기록한다 |
| 로컬 스테이징을 얼마나 쓰는지 | 스트리밍 업로드인지 전량 적재 후 업로드인지가 볼륨 산정을 바꾼다 | 백업 중 디스크 사용량을 관측한다 |
| SSM 포트 포워딩으로 4005를 열 수 있는지 | 관리 화면의 유일한 접근 경로다 | 13000 선례와 같은 방식으로 시도한다 |
| Databasus가 대상의 standby 여부를 판별하는지 | 이 환경은 이미 한 번 역할을 맞바꿨다 | DB02를 등록해 보고 도구의 반응을 본다 |
| 한 백업을 여러 저장소에 동시 보관 가능한지 | 3-2-1 구성을 도구 안에서 할지 밖에서 할지가 갈린다 | 저장소를 둘 등록해 복수 선택이 되는지 본다 |
| 서울 리전 S3 단가와 요청 요금 | 개인 계정 단계의 비용 문단에 숫자를 넣으려면 필요하다 | 공식 요금 페이지에서 확인하고 출처를 남긴다 |
| 학교 DB의 하루 증가량 | 보존 정책의 실제 저장 용량을 계산할 수 없다 | 상시 운영 구간에서 표본을 며칠 쌓아 측정한다 |

## 다른 산출물과 어긋나는 곳

같은 폴더의 다른 문서와 이 문서가 어긋나는 대목이 셋이다. 통합할 때 한쪽으로 맞춰야 하므로 감추지 않고 적어 둔다.

ADR 초안 0034는 학교 환경의 1순위 후보를 bot-1로 적고 "기존 운영 노드를 재사용하면 컴퓨트 증분도 없다"고 쓴다. 이 문서는 bot-1을 기각하고 다섯 번째 노드를 권한다. 판단이 갈린 이유는 근거로 삼은 측정이 다르기 때문이다. 초안은 가용 메모리 약 600MiB 표본을 인용했고 이 문서는 872MiB에서 1,006MiB 구간과 Grafana의 OOM 이력, 그리고 검증 에이전트가 추가로 요구하는 512MB와 임시 컨테이너까지 합산했다. 어느 쪽이 맞는지는 실제로 재 보면 정해진다. 위 확인 목록의 실측 항목이 이 충돌을 끝내는 자료다.

`06-발표구성.md`는 비용 문단에서 "검증용으로 서버를 새로 띄우지 않고 기존 노드에서 정해진 시각에만 돌리므로 인스턴스 비용도 늘지 않습니다"라고 적는다. 이 문서의 권고를 따르면 월 약 $24.45가 는다. 발표 대본을 이 문서에 맞춰 고치거나, 반대로 bot-1 배치를 택하고 그 제약을 대본에 넣거나 둘 중 하나로 정해야 한다. 늘지 않는다고 말해 놓고 노드를 하나 더 만드는 것이 가장 나쁘다.

`01-도구조사.md`는 "검증 에이전트는 Databasus 서버에서 실행할 수 없고 Docker가 있는 다른 호스트에서 돌아야 한다"고 적는다. 공식 복원 검증 문서를 다시 읽은 결과 요구 조건은 아웃바운드 HTTPS와 Docker와 자원 상한이고, 같은 호스트에서 돌리는 것을 금지하는 문장은 찾지 못했다. 금지가 아니라 권고일 가능성이 있으므로 이 문서는 같은 호스트에 두는 쪽을 기본으로 두고 확인 목록에 넣었다. 실제로 거부되면 학교에는 노드가 하나 더 필요하고 비용 계산이 다시 바뀐다.
