# ADR 0034. 오프사이트 예약 백업과 복원 검증을 Databasus로 관리한다

- 상태: 제안. 2026-09-22에 로컬 VM 실습망(OPS01)에서 설치와 기동, 화면 노출 제한, 읽기 전용 DB 계정, 접속 제어, 외부 보관소 접속까지를 실행했고 증거는 `vm-lab/databasus/캡처/예행-2026-09-22/`에 있다. 첫 백업, 외부 보관, 복원 검증은 아직 수행하지 않았고 학교 AWS에는 아무것도 설치하지 않았다. 아래에서 그 구간에 해당하는 문장은 검증 통과로 읽지 않는다.
- 날짜: 2026-09-22
- 초안 위치: 이 파일은 `deploy/vm-lab/databasus/04-ADR초안.md` 에 있는 초안이며 아직 ADR 로 채택하지 않았다. 사용자가 학교 AWS 배치를 확정하면 ADR 폴더에 `0034-databasus-offsite-scheduled-backup.md` 라는 이름으로 넣는다. 채택 전에는 그 경로를 있는 문서처럼 인용하지 않는다. 본문의 상대 링크는 옮긴 뒤의 위치를 기준으로 적었으므로 초안 상태에서는 연결되지 않는다. 옮길 때 [0099](0099-current-architecture.md)의 ADR 표와 백업 서술, [로드맵](../../ROADMAP.md) M4, `sources-sha256` 갱신, `check-doclinks`를 같은 변경에서 처리한다.
- 대체 범위: 채택될 경우 [0099](0099-current-architecture.md)의 백업 서술이 전제하는 현재 상태, 곧 로컬 백업 검증을 외부 보관과 예약 백업으로 해석하지 않는다는 한정과 [로드맵](../../ROADMAP.md) M4의 잔여 항목 2번, 그리고 [백업 도구 안내](../../../deploy/backup/README.md)가 정의한 `/var/backups/failstop`까지의 산출 범위를 대체한다. 대체하지 않는 것도 함께 적는다. [0025](0025-rejoin-by-basebackup-no-wal-retention.md)의 WAL 보존 비채택은 1단계에서 그대로 유지하고, [0024](0024-async-two-node-replication.md)의 비동기 복제와 수동 승격, [0004](0004-no-rds-self-managed-postgres.md)의 자체 운영 PostgreSQL, [격리 복원 점검 도구](../../../deploy/linux/postgresql/backup-restore-check.py)의 절차는 그대로 둔다.
- 근거: 2026-09-22에 공식 사이트 `https://databasus.com/`, 설치 문서 `https://databasus.com/installation`, 복원 검증 문서 `https://databasus.com/restore-verification`, 보안 문서 `https://databasus.com/security`, FAQ, 저장소 원본 파일(`Dockerfile`, `README.md`, `install-databasus.sh`), GitHub API와 Docker Hub API를 직접 읽었다. 정리본은 같은 폴더의 `01-도구조사.md`에 있다. 저장소 쪽 근거는 [2026-09-20 백업 복구 증거](../../../증거본/2026-09-20_백업_복구_보고/README.md)의 `007_DB_백업_격리복원_통과.txt`, [예약 백업 구현](../../../deploy/backup/), [AWS 작업 안내](../../reports/AWS_작업.md)다.

## 배경

지금 페일스톱의 백업은 한 번 성공했지만 한 곳에만 있다. 2026-09-19 스냅샷 `20260919T162452010003Z`를 2026-09-20에 TCP 접속이 없는 별도 클러스터로 복원했고 명령 12,733건, 이벤트 20,746건, 체결 6,710건, 원장 항목 68,686건이 원본과 일치했다. 정합성 검사 30개 중 CRITICAL과 HIGH 실패도 없었다. 그런데 같은 판정 파일에 `"external_copy": false`, `"roles_acl_checked": false`, `"application_boot_checked": false`가 그대로 남아 있다. 백업 파일은 당시 Primary였던 AZ-a 서버의 로컬 디스크에 있고 예약 실행도 없다. 그 인스턴스나 EBS 볼륨을 잃으면 운영 데이터와 백업을 같이 잃는다. [로드맵](../../ROADMAP.md)이 외부 보관과 예약 백업을 M4 잔여 1순위로 적어 둔 이유가 이것이다.

복제가 백업을 대신하지 않는다. [0024](0024-async-two-node-replication.md)의 비동기 스트리밍 복제는 호스트 한 대를 잃는 사고에는 답이 되지만, 잘못된 DELETE와 잘못된 마이그레이션은 몇 초 만에 Standby까지 그대로 따라간다. [0025](0025-rejoin-by-basebackup-no-wal-retention.md)가 `wal_keep_size` 확대와 `archive_mode`를 모두 채택하지 않았으므로 현재 구성에는 특정 시점으로 되돌릴 수단 자체가 없다. 사람이 실수를 알아차린 시점에 되돌릴 대상이 없다는 뜻이다.

저장소에는 이미 [예약 백업 구현](../../../deploy/backup/backup.py)과 [타이머](../../../deploy/backup/failstop-backup.timer)가 있다. 매일 03:30 KST에 `Persistent=true`로 돌고, [읽기 전용 계정 생성 SQL](../../../deploy/backup/provision-backup-role.sql)이 슈퍼유저와 `app_role` 재사용을 거부하며 `pg_read_all_data`만 부여하고 `default_transaction_read_only = on`을 건다. Prometheus textfile 지표까지 낸다. 다만 서비스 유닛이 `docker.service`를 `Requires`로 걸고 `pg_dump`를 컨테이너로 실행하며, 산출물을 `/var/backups/failstop`에 두고 끝난다. 외부 보관, 보존 정책, 예약된 복원 검증, 감사 기록이 없다. 무엇보다 이 구현은 학교 AWS에 배포하지 않았다. 학교에서 실제로 쓰는 경로는 [격리 복원 점검 도구](../../../deploy/linux/postgresql/backup-restore-check.py)이고, 이 도구는 postgres OS 계정 강제와 Primary 여부 확인, 디스크 여유 검사, Unix socket 전용 시험 클러스터 복원까지 한다. 그래서 이번 판단은 기존 절차를 버리는 것이 아니라 그 위에 예약과 외부 보관과 보존과 검증을 관리하는 계층을 얹는 것이다.

이번 과제의 요구는 도구 소개가 아니라 고객사 DB를 안전하게 지키면서 비용을 통제하는 근거를 만드는 것이다. MSP 담당자는 고객마다 다른 DB의 백업 성공 여부, 보존 기간, 그리고 무엇보다 그 백업이 실제로 복원되는지를 한 화면에서 증명해야 하고, 그 비용이 얼마인지 숫자로 설명해야 한다.

## 결정

오프사이트 예약 백업과 복원 검증의 관리 도구로 Databasus를 도입한다. Apache-2.0 라이선스의 자체 호스팅 소프트웨어이며 PostgreSQL 14부터 18까지를 지원한다. 아래 아홉 가지를 조건으로 함께 결정한다. 조건을 지키지 못하면 도입하지 않는다.

**논리 백업부터 시작하고 PITR은 2단계로 미룬다.** 1단계는 `pg_dump` 계열의 논리 백업, S3 외부 보관, 보존 정책, 예약 복원 검증까지다. 물리 백업과 WAL 연속 수집 기반 PITR은 2단계에서 따로 판단한다. 이유는 위험의 방향이다. Databasus의 물리 백업은 자체 엔진이 아니라 PostgreSQL 17의 `pg_basebackup`과 `pg_receivewal`을 Databasus 호스트에서 복제 프로토콜로 원격 실행하는 구조이고, WAL 연속 수집은 Primary 쪽에 WAL 보존 압력을 만든다. 복제 슬롯을 쓰는 구성에서 수집이 멈추면 Primary의 `pg_wal`이 계속 자라 디스크를 채우고, 그 끝은 거래 중단이다. 백업 도구가 서비스를 멈추는 사고를 만들지 않는다. 2단계로 갈 때는 슬롯 사용 여부를 먼저 확인하고, 슬롯을 쓴다면 `max_slot_wal_keep_size` 상한과 슬롯 지연 경보와 상한 초과 시 슬롯을 버리는 동작을 정한 뒤에 켠다.

**백업 대상 호스트에 도구를 두지 않는다.** 백업 관리자를 DB Primary에 올리면 호스트 상실이라는 바로 그 사고에서 도구와 데이터를 같이 잃는다. 학교 환경의 1순위 후보는 운영 평면인 bot-1이다. [0016](0016-observability-on-bot-node.md)에 따라 Prometheus와 Grafana가 이미 그 노드에 있고, DB Primary의 5432 인증이 봇의 사설 주소 한 개로 이미 열려 있어 새 네트워크 경로를 만들지 않아도 된다. 로컬 VM 실습에서는 OPS01(192.168.10.41)에 올려 먼저 예행한다. 다만 bot-1은 이미 시장 봇과 관측과 보고를 겸하고 있고 여기에 백업 관리까지 얹으면 역할이 한 노드에 더 몰린다. 이것은 예산과 학교 인스턴스 제한을 이유로 받아들이는 의도적인 예외이며, AGENTS.md의 역할 분리 원칙을 폐기한 것이 아니다. 개인 계정 재배포 단계에서 운영 평면을 분리할 후보로 남긴다.

**DB 접근 권한은 기존 기준을 그대로 쓴다.** [provision-backup-role.sql](../../../deploy/backup/provision-backup-role.sql)이 만드는 전용 로그인과 같은 조건, 곧 `pg_read_all_data`만 가지고 `default_transaction_read_only = on`인 계정을 쓴다. 슈퍼유저, 스키마 소유자, `app_role`을 재사용하지 않는다. 연결은 TLS `verify-full`로 하고 `pg_hba.conf`는 도구가 도는 노드의 사설 주소 한 개만 허용한다. 1단계에서는 `REPLICATION` 속성을 부여하지 않는다. Databasus 자신도 등록한 계정이 읽기 전용인지 역할, 데이터베이스, 테이블 세 수준에서 검사하므로 이 기준과 충돌하지 않는다. 비밀번호는 서버에서 생성해 root 소유 0600 파일과 도구 화면에서만 다루며 문서, 로그, 커밋, 증거 캡처에 남기지 않는다.

**보관지는 같은 리전의 비공개 S3 버킷으로 한다.** 서울 리전에 두어 복원 시 EC2로 내려받는 구간이 리전 내 전송이 되게 한다. Block Public Access와 서버 측 암호화를 유지하고, 학교 계정에서는 버킷 이름이 IAM username으로 시작해야 하는 규칙을 따른다. 자격증명이 선결 조건이다. [0029](0029-school-aws-first-personal-account-expansion.md)가 Access Key 발급과 IAM 사용자 생성을 금지했는데 Databasus의 S3 호환 저장소 입력 항목은 공개 문서상 버킷, 리전, Access Key ID, Secret Access Key, 엔드포인트 다섯 개이고 EC2 인스턴스 프로파일 사용 가능 여부는 문서에 없다. 그러므로 저장소 추가 화면에서 역할 기반 자격증명이 되는지 먼저 확인한다. 되지 않으면 학교 단계에서는 도구의 SFTP 목적지나 별도 전송 경로로 대체하고 S3 연동은 개인 계정 단계로 넘긴다. 확인 전에 S3 연동이 된다고 적지 않는다.

**복원 검증을 켜고, 검증 에이전트는 운영 DB 호스트 밖에 둔다.** 복원 검증은 최신 백업을 임시 DB 컨테이너에 실제로 복원하고 테이블별 행 수를 원본과 분해 비교한 뒤 컨테이너를 없애는 동작이다. 체크섬 대조가 아니라 실제 복원이라는 점이 이 기능을 켜는 이유다. 이 에이전트는 Databasus 서버 안에서 돌지 않고 Docker가 있는 별도 호스트에서 돌며, 필요한 자원은 동시 작업 하나당 1코어와 512MB, 그리고 백업 파일 크기와 원본 크기에 여유를 더한 디스크다. 동시 작업은 1로 제한하고 `--max-cpu`, `--max-ram-mb`, `--max-disk-gb`, `--max-concurrent-jobs`로 상한을 건다. 이 에이전트를 DB Primary나 Standby에 두지 않는다.

**Docker 예외로 기록한다.** [0028](0028-vm-validation-before-aws.md)과 [0029](0029-school-aws-first-personal-account-expansion.md)는 Linux 직접 설치를 기본으로 하고 Docker는 대상과 이유와 가려지는 실습 범위와 종료 방법을 적어 예외로만 쓰게 했다. Databasus는 최신 릴리스의 배포 자산이 컨테이너 이미지뿐이고 rpm이나 deb 패키지, 단일 실행 바이너리가 없다. 런타임 이미지 자체가 Debian 위에 PostgreSQL 17 서버와 각 DB의 클라이언트 도구를 함께 담고 자기 메타데이터용 PostgreSQL을 그 안에서 띄우는 구조라, 직접 설치 경로가 상류에 존재하지 않는다. 예외 대상은 두 종류다. Databasus 서버 컨테이너 한 개와, 복원 검증이 일시적으로 띄우는 DB 컨테이너다. 예외가 가리는 실습 범위는 이 도구의 프로세스 관리와 로그 수집과 업데이트 경로가 systemd와 journald 대신 Docker 아래로 들어간다는 점이다. 이 손실을 줄이기 위해 공식 설치 스크립트를 그대로 실행하지 않고 Compose 정의를 직접 배치한 뒤 systemd 유닛으로 감싸 부팅 기동과 실패 기록을 journal에서 본다. 앱, DB, 관측, 보고는 직접 설치를 유지한다. 종료 방법은 컨테이너와 볼륨을 지우는 것이며, 도구를 버려도 백업 데이터는 남는다.

**복구는 도구 없이도 되어야 한다.** 공식 FAQ는 `databasus-data/secret.key` 파일만 있으면 Databasus와 그 내부 데이터 없이 백업을 복구할 수 있다고 적는다. 이것을 채택의 전제 조건으로 삼는다. `secret.key`는 도구 호스트 밖에 오프라인 사본을 두고, 저장소와 문서와 증거본에는 넣지 않는다. 그리고 도구를 거치지 않는 복구 절차를 실제로 한 번 실행해 성공을 확인하기 전에는 이 ADR을 채택으로 바꾸지 않는다. 키를 잃으면 암호화된 백업은 열리지 않으므로 키 보관 실패가 곧 백업 상실이다. 외부 보관을 도입하면서 새 단일 실패점을 하나 만든 셈이 되지 않게 키 보관 위치와 접근 권한을 백업 설계와 같은 비중으로 정한다.

**알림은 기존 경로와 합친다.** 백업 실패와 검증 실패는 Microsoft Teams로 보낸다. [0027](0027-msp-operations-and-autoscaling.md)의 Alertmanager 기본 알림과 AI 일일 보고가 이미 Teams로 가므로 같은 사건이 두 경로로 중복 도착하지 않게 한 쪽으로 모은다. Databasus의 Teams 연동은 기존 Incoming Webhook이 아니라 Power Automate 워크플로가 발급한 POST 주소를 요구하므로, 기존 웹훅이 어느 방식으로 만들어졌는지 확인하고 다르면 전용 워크플로를 따로 만든다. AI는 여전히 운영 조치를 실행하지 않으며 복원과 보존 변경은 사람이 한다. 익명 사용 텔레메트리가 기본으로 켜져 있으므로 `IS_DISABLE_ANONYMOUS_TELEMETRY`를 끄고 그 사실을 설치 기록에 남긴다.

**완료 판정은 성공한 백업 개수가 아니다.** 판정 기준은 외부 보관 확인과 복원 검증 통과다. 도구 화면의 초록색 표시만으로 완료라고 적지 않는다. 검증이 한 번도 돌지 않았거나 지표가 수집되지 않은 상태를 정상으로 표시하지 않는다.

## 비용을 어떻게 통제하는가

도구 자체는 Apache-2.0이라 라이선스 비용이 없다. 기존 운영 노드를 재사용하면 컴퓨트 증분도 없다. 남는 비용은 S3 보관과 요청, 그리고 복원 시 전송이다.

측정된 압축비가 산정의 출발점이다. 2026-09-19 스냅샷에서 원본 데이터베이스는 64,263,859바이트였고 custom 포맷 덤프는 4,559,507바이트였다. 약 14대 1이다. 다만 이것은 저속 봇 운영 중의 한 표본이고, [AWS 작업 안내](../../reports/AWS_작업.md)는 하루 1에서 2GB라는 증가량이 사용자 추정이며 로컬 WAL 환산값을 AWS 증가량으로 쓰지 말라고 이미 적어 두었다. 그래서 총액을 단정하는 대신 산식을 결정으로 둔다. 월 보관 비용은 보존 세대 수에 세대당 압축 크기를 곱하고 리전 단가를 곱한 값이며, 여기에 요청 비용과 복원 시 전송 비용을 더한다. 현재 표본 규모라면 일 백업 30세대를 보관해도 수백 MB 수준이다. 서울 리전의 GB당 단가는 이번 조사에서 공식 표를 확인하지 못했으므로 견적을 낼 때 공식 요금 페이지와 계산기로 다시 확인하고 출처를 AWS 작업 안내에 남긴다. 확인 전에 월 얼마라고 적지 않는다.

비용을 예측 가능하게 만드는 것은 보존 정책이다. Databasus는 기간 기준 보존, 개수 기준 보존, GFS 계층 보존, 단건과 전체 용량 상한을 제공한다. 일간과 주간과 월간 세대의 개수를 미리 정하고 그 상한 안에서만 쌓이게 하면 보관 총량이 선형으로 늘지 않는다. 보관량이 상한에 접근하면 경보를 보내고, 사람이 정한 정책 밖에서 자동으로 지우지 않는다. 복원 리허설은 같은 리전 안에서 수행해 인터넷 구간 전송이 생기지 않게 한다. 도구가 S3 스토리지 클래스 지정을 지원하는지는 확인하지 못했으므로, 장기 보존이 필요해지면 버킷 수명주기 규칙으로 계층을 내리고 도구의 보존 정책을 그 위에 맞춘다. 꺼내는 데 시간과 요금이 드는 계층은 복구 목표 시간과 함께 판단한다.

정작 중요한 비교는 절대 금액이 아니다. 지금은 볼륨 하나를 잃으면 운영 데이터와 백업을 같이 잃는다. 그 사고를 막는 데 드는 돈이 월 운영 예산 40만 원의 1퍼센트에도 못 미친다. 고객사에 설명할 문장은 이것이다. 백업을 외부에 두고 복원까지 자동으로 검증하는 비용은 커피 몇 잔이고, 그것을 하지 않았을 때의 비용은 사업의 중단이다.

## 근거와 한계

공식 자료에서 확인한 것은 다음과 같다. 저장소는 2025-06-05에 만들어졌고 Apache-2.0이며 조회 시점에 별 8,618개, 최신 릴리스는 2026-09-21의 v3.59.0이다. Docker Hub의 `pull_count`는 1,906,769회로, 사용자가 전달한 180만 회 이상이라는 설명과 일치한다. 지원 범위는 PostgreSQL 14부터 18까지이고 물리와 증분 백업은 PostgreSQL 17 이상에서만 동작한다. 학교 DB가 17.11이므로 조건은 맞는다. MySQL, MariaDB, MongoDB는 논리 백업만 지원한다. 논리 백업은 `pg_dump` custom 포맷을 zstd 레벨 5로 압축하고 AES-256-GCM으로 암호화해 올린다. 마스터 키와 백업 ID와 백업별 임의 솔트로 유도한 개별 키를 쓴다. 저장소 연동 대상은 Local, S3, Cloudflare R2, Google Drive, Azure Blob, NAS, FTP, SFTP, rclone, Dropbox이고 일정은 시, 일, 주, 월과 cron이다. 접근 통제는 시스템 수준과 워크스페이스 수준으로 나뉘며 감사 로그와 OTLP 반출이 있다. 알림은 Slack, Discord, Telegram, Microsoft Teams, 이메일, 웹훅, Mattermost다. 기본 포트는 4005이고 최소 요구 자원은 1코어와 500MB 메모리, 설치용 5GB 디스크이며 Docker Engine 20.10 이상과 Compose v2.0 이상을 요구한다. 내부 메타데이터는 자체 PostgreSQL에 저장하며 설치 디렉터리 아래 `databasus-data/pgdata`에 놓인다.

한 가지 문서상의 함정을 명시해 둔다. 공식 설치 문서의 백업 에이전트 페이지는 `wal_level=replica`와 `archive_mode=on`과 `archive_command` 설정을 요구하지만, 그 방식은 문서가 폐기했다고 밝힌 레거시 경로이고 v3.42.0까지만 지원한다. 현재의 물리 백업은 DB 호스트에 아무것도 설치하지 않는 원격 방식이다. 그러므로 폐기된 페이지의 `archive_mode` 요구를 [0025](0025-rejoin-by-basebackup-no-wal-retention.md)와 충돌하는 조건으로 옮겨 적지 않는다. 다만 2단계에서 `pg_receivewal` 연속 수집을 켤 때 복제 슬롯을 쓰는지 여부는 아직 확인하지 못했고, 그 답에 따라 Primary 디스크 위험의 크기가 달라진다.

확인하지 못한 것도 분명히 남긴다. S3 목적지가 EC2 인스턴스 프로파일 자격증명을 받을 수 있는지 문서에서 찾지 못했다. 학교 계정에서 기존 비공개 버킷에 실제로 쓸 수 있는지도 확인하지 않았다. 지금까지 기록으로 확인된 것은 EC2 역할로 내려받은 사례뿐이고 업로드 사례는 없다. PostgreSQL 공식 Software Catalogue 등재는 검색 요약으로만 접했고 목록 페이지에서 직접 대조하지 않았다. S3 prefix와 path style 지정, 스토리지 클래스 지정, 한 백업을 여러 저장소에 동시 보관하는 기능, `secret.key` 교체 절차, 감사 로그 보존 기간, 알림 사건별 개별 구독 여부도 문서에서 답을 찾지 못했다. 도구 자체의 보안 취약점 이력과 릴리스 주기의 지속성, 유지보수 주체의 안정성도 평가하지 않았다. 고객사 DB 자격증명과 백업 키를 한곳에 모으는 도구이므로 이 평가는 채택 전 점검 항목이다.

새로 생기는 위험이 있다. 이 도구는 새 신뢰 경계다. 모든 대상 DB의 접속 정보와 백업 암호키를 한 호스트에 모으므로, 그 호스트가 침해되면 전체 DB의 사본이 함께 노출된다. Docker를 설치하면 `docker` 그룹 구성원은 사실상 root 권한을 갖는다. [0031](0031-school-admin-password-gateway.md)이 운영자 권한을 `VIEWER`와 `BOT_OPS`로 좁혀 둔 것과 맞물려 이 호스트의 계정과 그룹 구성을 따로 설계해야 한다. 도구의 웹 화면 4005는 인터넷에 열지 않고 사설 주소로만 접근하며, 필요하면 Grafana에 쓰는 것과 같은 SSM 포트 포워딩 경로를 쓴다. v3.59.0부터 사전 생성 관리자 계정이 없어지고 최초 가입자가 소유권을 갖게 바뀌었으므로, 설치와 소유자 계정 생성 사이를 벌리지 않고 그동안 화면을 노출하지 않는다.

부하도 실행 전에 판단할 항목이다. 논리 백업은 긴 트랜잭션을 잡아 vacuum을 지연시킬 수 있고 문서는 런타임 오버헤드를 약 20퍼센트로 적는다. 저부하 시간대로 고정하고, 논리 백업을 Standby에서 뜨는 선택지는 복제 충돌과 지연 영향을 확인한 뒤에 정한다. 현재 봇 목표가 세 종목 합계 3 OPS인 규모에서 측정한 결과를 이후의 높은 부하에 그대로 적용하지 않는다. 백업 소요 시간과 거래 영향은 아직 재지 않았다.

## 대안

| 대안 | 판단 |
|---|---|
| 기존 `deploy/backup` 확장 | 기각하지 않고 보류한다. Python과 systemd 타이머에 `aws s3 cp`를 붙이면 의존성이 가장 적고 Linux 운영 실습 가치도 가장 크다. 그러나 보존 정책, 예약 복원 검증, 감사 기록, 여러 DB를 한 화면에서 보는 기능을 직접 만들어야 한다. 현재 구현도 이미 `docker.service`를 `Requires`로 걸고 있어 Docker 회피라는 이점도 없다. |
| pgBackRest | 진지한 경쟁안이다. 물리 백업, 증분, PITR, 병렬 압축, S3 지원이 성숙하고 배포판 패키지로 직접 설치할 수 있어 Docker 예외가 필요 없다. 대신 관리 화면, 예약 복원 검증, 다중 알림 채널이 없어 이번 과제가 요구하는 증명 화면을 따로 만들어야 한다. 2단계에서 PITR로 갈 때 다시 비교한다. |
| Barman | pgBackRest와 성격이 같다. 직접 설치가 되고 운영 사례가 많지만 관리 화면과 자동 복원 검증이 없다. |
| RDS 또는 AWS Backup | [0004](0004-no-rds-self-managed-postgres.md)가 장애 실험을 위해 자체 운영 PostgreSQL을 선택했고 학교 계정의 실제 권한도 미확인이다. EBS 스냅샷은 크래시 일관성만 주고 잘못된 DELETE 같은 논리 사고를 막지 못한다. |
| 현상 유지 | 기각한다. 백업이 운영 데이터와 같은 볼륨에 있고 예약도 없다. 볼륨 상실이 곧 전량 상실이다. |

## 영향

[0025](0025-rejoin-by-basebackup-no-wal-retention.md)의 WAL 보존 비채택은 1단계에서 그대로 유지된다. 2단계에서 PITR을 채택하면 그 결정의 적용 범위와 재진입 조건을 같은 변경에서 다시 쓴다. [0028](0028-vm-validation-before-aws.md)과 [0029](0029-school-aws-first-personal-account-expansion.md)가 요구하는 Docker 예외 기록에 이 항목을 추가한다. [0027](0027-msp-operations-and-autoscaling.md)의 DB와 스토리지 관제 항목에 백업 성공 시각과 복원 검증 결과를 넣고 기존 경보와 중복되지 않게 정리한다. [0099](0099-current-architecture.md)의 백업 서술과 ADR 표, [로드맵](../../ROADMAP.md) M4의 잔여 항목, [AWS 작업 안내](../../reports/AWS_작업.md)의 운영 기록은 같은 변경에서 갱신하되 상태가 제안인 동안에는 제안으로만 적는다. [백업 도구 안내](../../../deploy/backup/README.md)에는 이 도구가 도입되면 로컬 산출까지였던 범위가 어디로 확장되는지와 기존 구현의 위치를 적는다.

설치, 첫 백업, 외부 보관 확인, 복원 검증, 도구 없는 복구까지 각 단계의 화면과 명령과 출력을 [증거본](../../../증거본/README.md)에 남긴다. 비밀 값 입력 구간은 캡처하지 않고 누락 구간을 표시한다. 실패와 권한 거부도 결과로 보관한다.

파일 번호는 0034다. 로컬 main과 원격 브랜치 여덟 개를 모두 대조했을 때 일반 결정의 마지막 번호는 0033이고 0034는 비어 있다. 0099는 [0001](0001-record-architecture-decisions.md)이 정한 예약 번호다. 다만 원격 브랜치의 0028과 학교 작업의 0028이 겹쳐 관제 결정을 0032로 재배정한 사례가 있으므로, 커밋 직전에 번호 충돌을 한 번 더 확인한다.

## 채택으로 바꾸기 전에 실행할 항목

1. 로컬 VM 실습의 OPS01에 설치하고 DB01 Primary를 대상으로 첫 백업을 받는다. 읽기 전용 계정과 TLS 연결과 접근 제한이 의도대로 동작하는지, 도구의 권한 검사 화면이 무엇을 판정하는지 확인한다.
2. 외부 보관 목적지에 실제로 객체가 올라가는지 확인한다. 학교 계정에서는 저장소 추가 화면의 입력 항목을 먼저 캡처해 인스턴스 프로파일 자격증명 가능 여부를 판정하고, 기존 비공개 버킷의 `PutObject` 권한을 시험한다. 막히면 학교 단계는 SFTP나 별도 전송으로 두고 S3는 개인 계정 단계로 넘긴다.
3. 예약 복원 검증을 한 주기 이상 돌리고 일부러 실패를 만들어 Teams 알림이 도착하는지 확인한다. 기존 Alertmanager 및 AI 보고와 중복되지 않는지도 같이 본다.
4. 도구를 끄고 `secret.key`와 버킷 객체만으로 복구하는 절차를 끝까지 실행한다. 건수와 정합성 검사를 원본과 대조한다. 이 항목이 통과하지 않으면 채택하지 않는다.
5. 백업 중 DB 부하와 소요 시간, 도구 호스트의 상주 메모리와 임시 디스크 사용량을 측정하고 거래에 미치는 영향을 기록한다.
6. 보존 정책과 실제 보관량, 그리고 공식 단가로 계산한 월 비용을 기록한다. 하루 DB 증가량은 충분한 표본을 모은 뒤 계산한다.
7. 위 결과를 근거로 상태를 채택 또는 기각으로 바꾸고, 초안을 저장소로 옮기면서 0099와 로드맵을 같은 변경에서 갱신한다.
