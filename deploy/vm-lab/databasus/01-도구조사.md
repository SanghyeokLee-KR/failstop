# Databasus 기능과 배포 조사

고객사의 데이터베이스를 서버 밖으로 안전하게 옮겨 두고 복원이 실제로 되는지를 주기적으로 확인하며 보관 비용까지 통제하는 구조를 오픈소스로 세우려고 Databasus를 조사했다. 지금 페일스톱의 백업은 전환 전 Primary였던 AZ-a 서버의 로컬 디스크 한 곳에만 있다. 호스트나 볼륨을 잃으면 백업도 함께 잃는 상태이고, 예약 백업과 반복 복원 검증도 없다. 이 문서는 그 빈 자리를 Databasus가 실제로 메울 수 있는지를 공식 문서와 저장소 원본으로 확인한 결과다.

이 문서는 실행 전 조사다. 2026-09-22 기준으로 공식 사이트 databasus.com, GitHub 저장소 원본 파일, GitHub API, Docker Hub API를 읽어서 정리했다. 학교 AWS에도 로컬 VM에도 Databasus를 아직 설치하지 않았고 백업·복원·검증을 한 번도 실행하지 않았다. 따라서 이 문서의 어떤 문장도 검증 통과로 읽으면 안 된다. 문서에서 확인한 사실과 확인하지 못한 항목을 절마다 구분했고, 미확인 항목은 마지막 절에 다시 모아 확인 방법까지 적었다.

## 프로젝트 실체와 라이선스

github.com/databasus/databasus는 실재하는 저장소이고 설명은 "PostgreSQL backup tool with Point-In-Time-Recovery and restore verification"이다. 라이선스는 Apache-2.0, 기본 브랜치는 main, 저장소 생성일은 2025-06-05다. 조회 시점에 별 8,618개, 포크 542개, 열린 이슈 9개였고 주 언어는 TypeScript이며 아카이브 상태가 아니다. 홈페이지는 databasus.com으로 연결된다. 출처는 https://api.github.com/repos/databasus/databasus 다.

라이선스가 Apache-2.0이라는 점은 도입 근거에서 중요하다. 상용 백업 제품을 쓰지 않고도 같은 역할을 라이선스 비용 없이 세울 수 있다는 뜻이고, 특허 조항을 포함한 허용적 라이선스라서 고객사 환경에 올릴 때 법적 검토 부담이 비교적 작다.

채택 규모는 Docker Hub의 pull_count 1,906,769회로 확인했다. 마지막 갱신은 2026-09-21이다. 출처는 https://hub.docker.com/v2/repositories/databasus/databasus/ 다. 사용자가 전달한 "Docker 풀 180만 회 이상"은 이 수치와 일치한다. 다만 PostgreSQL 공식 Software Catalogue 등재 여부는 이번 조사에서 postgresql.org 원문으로 대조하지 않았다. 미확인으로 남긴다.

## 배포 방식이 사실상 Docker 하나뿐인 이유

최신 릴리스는 v3.59.0이고 2026-09-21 21:15 UTC에 공개됐다. 프리릴리스가 아니다. 이 릴리스의 assets 배열이 비어 있다는 점이 중요하다. 내려받을 바이너리나 패키지 파일이 아예 없고 배포물은 컨테이너 이미지뿐이다. 이미지는 databasus/databasus:v3.59.0과 ghcr.io/databasus/databasus:v3.59.0 두 곳에 linux/amd64와 linux/arm64로 올라간다. 출처는 https://api.github.com/repos/databasus/databasus/releases/latest 다.

README와 설치 문서가 제시하는 설치 방법은 설치 스크립트, docker run, docker compose, Helm 차트(oci://ghcr.io/databasus/charts/databasus) 네 가지이고 전부 컨테이너를 전제한다. rpm이나 deb 패키지, 단일 실행 바이너리 배포는 없다.

왜 그런지는 Dockerfile을 읽으면 분명해진다. 런타임 베이스가 debian:bookworm-slim이고 그 위에 PostgreSQL 17 서버 바이너리를 설치한 뒤 기본 클러스터를 지우고 /databasus-data/pgdata에 자기 전용 메타데이터용 PostgreSQL 인스턴스를 띄운다. 여기에 PostgreSQL, MySQL, MariaDB, MongoDB 클라이언트 도구가 같은 이미지 안에 들어 있다. EXPOSE는 4005, VOLUME은 /databasus-data, 실행 사용자는 UID 999의 databasus이며 이는 기본 postgres 계정을 개명해 만든다. ENTRYPOINT는 /app/start.sh다. 빌드 단계는 프론트엔드가 node:24-alpine, 백엔드와 검증 에이전트가 golang:1.26.3이다. 출처는 https://raw.githubusercontent.com/databasus/databasus/main/Dockerfile 다.

즉 이 도구는 애플리케이션 하나가 아니라 자기 DB 서버와 각 DB의 클라이언트 도구 묶음을 한 이미지에 담은 구조다. 이 저장소는 Linux 직접 설치를 기본으로 삼지만 여기서는 상류가 컨테이너 배포만 제공하므로 직접 설치 경로가 실질적으로 없다. Docker 사용 예외로 기록할 때 이유는 상류 배포 형태이고 범위는 전용 노드 한 대의 컨테이너 한 개로 한정한다고 적으면 된다.

## 권장 compose 정의와 설치 스크립트 동작

README가 제시하는 운영용 compose는 단일 서비스다. 이미지는 databasus/databasus:latest, 포트는 4005:4005, 볼륨은 ./databasus-data:/databasus-data 하나뿐이고 restart 정책은 unless-stopped다. 헬스체크는 ["CMD","databasus","healthcheck"]이며 interval 30s, timeout 5s, retries 3, start_period 60s다. 출처는 https://raw.githubusercontent.com/databasus/databasus/main/README.md 다.

볼륨이 하나라는 사실은 운영 설계에 그대로 영향을 준다. 설정, 자격증명, 메타데이터, 마스터 키가 모두 그 디렉터리 하나에 모인다. 백업 대상도 복구 대상도 그 디렉터리다.

설치 스크립트 install-databasus.sh의 동작도 원본에서 확인했다. /etc/os-release로 배포판을 판별하고 Ubuntu 25.x는 24.04로, Debian 13과 14는 12로 매핑한다. Docker가 없으면 공식 저장소를 추가해 Docker CE와 compose 플러그인을 설치한다. /opt/databasus 디렉터리를 만들고 위 compose 파일을 기록한다. 로그는 /var/log/databasus-install.log에 남는다. 출처는 https://raw.githubusercontent.com/databasus/databasus/main/install-databasus.sh 다.

여기서 우리 운영 기준과 어긋나는 점이 두 가지 있다. 첫째, systemd 유닛을 만들지 않고 Docker의 unless-stopped 재시작 정책에만 의존한다. 부팅 시 기동과 실패 기록을 systemd journal에서 일관되게 보려면 compose를 systemd 유닛으로 감싸는 편이 낫다. 둘째, 대화형 확인 없이 root로 실행되고 방화벽은 건드리지 않는다. 스크립트를 그대로 돌리기보다 어떤 일이 일어나는지 확인한 뒤 필요한 단계를 직접 수행하는 쪽이 이 프로젝트의 진행 방식에 맞는다.

저장소 루트의 docker-compose.yml을 운영용으로 착각하면 안 된다. 그 파일은 개발·시험용이고 databasus-local 빌드, 개발 DB 5437과 테스트 DB 5438, VictoriaLogs 9428, 논리 백업 시험용 PostgreSQL 16의 5004, 물리 백업 시험용 PostgreSQL 17의 5007과 18의 5008, WAL 부하 생성 리그 5018과 사이드카로 구성돼 있다. 운영 배포에는 README의 단일 서비스 compose를 쓴다. 출처는 https://raw.githubusercontent.com/databasus/databasus/main/docker-compose.yml 다.

## 자원 요구와 접속 경로

문서가 적은 최소 자원은 CPU 1코어, RAM 500MB, 애플리케이션용 디스크 5GB이며 여기에 백업 보관 공간을 더해야 한다. Docker Engine 20.10 이상과 Compose v2.0 이상이 필요하고 첫 기동에 약 2분이 걸린다고 적혀 있다. 출처는 https://databasus.com/installation 다. 이 수치는 최소치 표기이지 우리 DB 규모에서의 실측이 아니다.

웹 UI 포트는 기본 4005이고 변경할 수 있다. 헬스 엔드포인트는 GET http://<host>:4005/api/v1/system/health다. HTTPS는 내장돼 있지 않고 문서는 Caddy 리버스 프록시로 Let's Encrypt 자동 인증서를 붙이는 구성을 권한다. 우리 환경에서는 Grafana를 다루는 방식과 같이 4005를 공개하지 않고 SSM 포트 포워딩이나 기존 관리 경로 뒤에 두는 편이 일관된다. 그렇게 하면 별도 인증서 관리도 필요 없다.

같은 호스트의 DB에 붙일 때는 Linux에서 network_mode: host를 쓰고 127.0.0.1로 접속하라고 안내한다. host 네트워크 모드는 Linux에서만 동작하고 Windows와 macOS는 host.docker.internal을 써야 한다. 출처는 https://databasus.com/faq/localhost 다. 다만 우리는 DB 노드와 Databasus 노드를 분리할 계획이므로 이 경로는 쓰지 않는다.

폐쇄망 연결 수단으로 SSH 터널을 내장한다. 문서는 내부 호스트나 배스천으로의 SSH 터널로 접근해 DB를 공개 노출하지 않아도 된다고 명시한다. 출처는 https://databasus.com/databasus-vs-pgbackrest 와 README다. 다만 SSH 터널 설정 화면의 입력 항목은 공개 문서에 없다.

## 인증과 계정 운영

v3.59.0부터 사전 생성 admin 계정이 없어지고 최초 가입자가 소유권을 갖는 방식으로 바뀌었다. 설치 직후 UI가 열린 상태에서 다른 사람이 먼저 가입하면 소유권을 가져간다는 뜻이므로, 설치와 소유자 계정 생성 사이를 벌리지 않는 것이 중요하다.

이메일 6자리 코드 2FA를 제공한다. 코드는 10분 만료이고 5회 오입력 시 폐기되며 비밀번호 로그인에만 적용된다. OAuth 로그인은 각 공급자의 MFA를 따른다. 관리자가 2FA를 강제로 켤 수 있고 이 강제 옵션이 v3.59.0에서 추가됐다. 출처는 https://databasus.com/security 와 릴리스 노트다.

계정 관리용 CLI는 컨테이너 안의 ./main 바이너리로 실행한다. 비밀번호 재설정은 docker exec -it databasus ./main --new-password="..." --email="...", 관리자 목록 조회는 docker exec -it databasus ./main --list-admins, 2FA 해제는 docker exec -it databasus ./main --disable-2fa다. 관리자 목록에는 비밀번호, 해시, 토큰이 출력되지 않는다. 출처는 https://databasus.com/password 다. 실제 값은 이 문서에 적지 않고 생성 방법과 권한만 남긴다.

## 지원 데이터베이스와 백업 방식

지원 대상과 버전은 다음과 같다. 물리 백업이 가능한 조합이 좁다는 점이 이 표의 핵심이다.

| 데이터베이스 | 지원 버전 | 논리 백업 | 물리 백업 |
|---|---|---|---|
| PostgreSQL | 14-18 | 가능 | 17 이상만 가능 |
| MySQL | 5.7, 8.0, 8.4, 9, 26 | 가능 | 불가 |
| MariaDB | 5.5, 10-13 | 가능 | 불가 |
| MongoDB | 4.2+, 5-8 | 가능 | 불가 |

출처는 README와 https://databasus.com/faq 다. MySQL 26과 MariaDB 13 지원은 v3.59.0에서 추가됐다.

### 논리 백업

논리 백업은 pg_dump를 custom 포맷으로 실행한 뒤 zstd 레벨 5로 압축하고 AES-256-GCM으로 암호화해 저장소에 업로드한다. 문서는 SQL 평문 대비 최대 20배, 무압축 덤프 대비 4-8배 축소를 주장하고 런타임 오버헤드를 약 20%로 적는다. 복원할 때는 UI에서 내려받으며 자동 복호화하고, 해당 백업에 맞는 pg_restore 명령을 그대로 보여 주며 병렬 복원을 지원한다. raw SQL 포맷은 지원하지 않는다. 출처는 https://databasus.com/pgdump-alternative 와 FAQ다.

### 물리 백업

물리 백업의 내부 동작이 이번 조사에서 가장 중요한 부분이다. Databasus는 자체 백업 엔진을 만들지 않았다. PostgreSQL 17이 제공하는 네이티브 도구를 Databasus 호스트에서 복제 프로토콜로 원격 실행한다. DB 서버에는 아무것도 설치하지 않는다.

전체 백업은 pg_basebackup으로 받는다. 증분은 서버측 WAL 요약 기능(summarize_wal)을 이용한 pg_basebackup --incremental이라 블록 단위로 바뀐 부분만 가져온다. WAL 연속 수집은 pg_receivewal이 담당한다. 복원은 pg_combinebackup으로 전체 백업과 증분들을 합쳐 데이터 디렉터리를 재구성한 뒤 목표 시각까지 WAL을 재생하는 방식이다. 출처는 FAQ, https://databasus.com/databasus-vs-pgbackrest, https://databasus.com/databasus-vs-wal-g 다.

이 구조가 주는 이점은 분명하다. DB 노드에 낯선 바이너리를 설치하지 않으므로 운영 중인 DB의 변경 범위가 작고, 복원 결과물이 PostgreSQL 표준 도구가 만든 데이터 디렉터리라서 Databasus가 없어져도 복원 경로가 남는다. 반대로 제약도 분명하다. 물리 백업이 PostgreSQL 17 이상에서만 동작하므로 고객사 DB가 구버전이면 논리 백업만 쓸 수 있다.

## 우리 환경 적합성

학교 AWS의 DB primary와 standby는 PostgreSQL 17.11이다. 로드맵에 Amazon Linux 공식 PostgreSQL 17.11을 직접 설치한 기록이 있다. 따라서 물리 백업, 블록 단위 증분, WAL 연속 수집, PITR까지 Databasus가 제공하는 최선의 경로를 모두 쓸 수 있는 최소 버전 조건을 충족한다. 17 미만이었다면 논리 백업만 가능해 도입 가치가 크게 떨어졌을 것이다. 근거는 C:\Users\kopo26\Desktop\failstop\docs\ROADMAP.md 39행의 설치 기록과 FAQ의 17+ 요구 조건 대조다.

## 저장소 연동

지원 대상으로 Local, S3, Cloudflare R2, Google Drive, Azure Blob, NAS, FTP, SFTP, rclone, Dropbox를 나열한다. 출처는 https://databasus.com/storages 다. 다만 개별 설정 항목을 문서화한 페이지는 Google Drive와 Cloudflare R2 둘뿐이다.

S3 호환 저장소의 입력 항목은 R2 안내에서 확인했다. 버킷 이름, 리전, Access Key ID, Secret Access Key, S3 endpoint 다섯 개다. 출처는 https://databasus.com/storages/cloudflare-r2 다. prefix 지정, path style 강제, EC2 인스턴스 프로파일을 통한 IAM 역할 사용 가능 여부는 문서에 없다. 액세스 키를 쓰지 않고 역할로 접근할 수 있는지는 자격증명 관리와 직결되는데 미확인이다.

스토리지 클래스 지정이나 S3 수명주기 연동 지원 여부도 문서에 없다. 비용 설계의 핵심 변수이므로 미확인 목록에 남긴다. 지원되지 않는다면 버킷 쪽 수명주기 규칙으로 계층을 내리고 Databasus의 보존 정책을 그 위에 맞추는 방식으로 대응할 수 있다.

## 암호화와 키 관리

백업 파일과 내부 비밀값 모두 AES-256-GCM으로 암호화한다. 마스터 키는 기본적으로 ./databasus-data/secret.key 파일에 있고 메타데이터 DB와 분리해 둔다. 백업마다 마스터 키와 백업 ID, 백업별 임의 salt로 유도한 고유 키를 쓴다. 비밀번호, 토큰, 웹훅 주소는 암호화 저장되며 API와 UI 어디에도 노출되지 않는다고 적혀 있다. 출처는 https://databasus.com/security 다.

여기서 운영상 가장 위험한 지점이 나온다. FAQ는 Databasus 자체의 백업 대상을 명시한다. /opt/databasus/databasus-data/ 아래의 secret.key와 pgdata다. secret.key만 있으면 UI 없이도 백업을 복원할 수 있고 둘 다 있으면 UI와 설정까지 복구된다. 뒤집어 말하면 secret.key를 잃는 순간 외부에 쌓아 둔 암호화 백업을 전부 열 수 없다.

그래서 secret.key와 pgdata를 백업 저장소와 다른 위치에 별도로 보관하는 절차를 설계에 반드시 포함해야 한다. 이 절차가 없으면 백업을 서버 밖으로 옮긴 조치가 오히려 단일 실패 지점을 하나 더 만든 셈이 된다. 키 교체 절차와 분실 시 복구 가능 여부는 문서에서 찾지 못했고 미확인으로 남긴다.

## DB 접속 권한 원칙

Databasus는 등록한 DB 계정이 읽기 전용인지 세 단계로 검사한다. 역할 수준에서 슈퍼유저가 아니고 역할·DB 생성 권한이 없는지, DB 수준에서 CREATE와 TEMP가 없는지, 테이블 수준에서 INSERT·UPDATE·DELETE·TRUNCATE가 명시적으로 REVOKE 됐는지를 본다. 현재와 미래 테이블에 SELECT만 가진 전용 사용자를 만들도록 권한다. 백업 도구 자체가 원인이 되어 데이터가 훼손되는 일을 막는 것이 목적이다. 출처는 https://databasus.com/security 다.

고객사 환경에 백업 도구를 들일 때 가장 먼저 받는 질문이 백업 도구가 원본을 건드릴 수 있느냐인데, 도구가 스스로 권한을 검사한다는 점은 설명 근거로 쓸 만하다. 다만 물리 백업은 복제 프로토콜을 쓰므로 REPLICATION 속성이 필요할 텐데, 읽기 전용 원칙과 복제 권한이 어떻게 양립하는지는 문서에 설명이 없다. 논리 백업용 SELECT 전용 계정과 물리 백업용 복제 계정을 분리해야 하는지 확인하지 못했다.

## 보존 정책과 일정

보존 정책은 네 가지다. 기간 기준으로 7일·3개월·1년 같은 보관 기간 지정, 개수 기준으로 최근 N개 유지, GFS(Grandfather-Father-Son) 계층 보존, 백업 단건 및 전체 용량 상한이다. 출처는 README다.

일정은 시간·일·주·월 단위 또는 cron 식으로 지정한다. DB 헬스 체크 기능도 별도로 제공한다고 첫 화면에 적혀 있다. 출처는 https://databasus.com/ 와 README다.

비용 근거를 만들 때 쓸 수 있는 조합은 GFS 계층 보존이다. 일간 백업은 짧게, 주간은 중간, 월간은 길게 남기면 보관 총량이 선형으로 늘지 않는다. 스토리지 클래스 지정이 지원되지 않더라도 버킷 수명주기와 함께 쓰면 보관 기간과 저장 단가를 동시에 통제할 수 있다.

## 복원 검증

복원 검증은 문구가 아니라 실제 복원이다. 최신 백업을 가져와 임시 DB 컨테이너에 복원하고 원본과 대조한 뒤 컨테이너를 없애고 결과를 보고한다. 비교 방식이 체크섬이 아니라 테이블별 행 수 분해 비교라는 점이 중요하다. 불완전 덤프, 권한 누락, 확장 누락, 테이블스페이스 불일치처럼 객체가 조용히 빠지는 실패를 잡는 것이 목적이라고 적혀 있다. 실행 주기는 백업 직후가 가장 강한 보장이고 그밖에 시간·일·주·월·cron을 고를 수 있다. 상태는 Pending, Running, Successful, Failed, Canceled로 표시되고 Slack, Teams, Discord, 이메일로 통보한다. 출처는 https://databasus.com/restore-verification 다.

문제는 이 기능에 별도 호스트가 필요하다는 점이다. 검증 에이전트는 Databasus 서버에서 실행할 수 없고 Docker가 있는 다른 호스트에서 돌아야 한다. 임시 DB 컨테이너를 띄우기 때문이다. 등록 절차는 curl -L -o verification-agent "https://<databasus-host>/api/v1/system/verification-agent?arch=amd64" 로 내려받은 뒤 ./verification-agent start --databasus-host=... --agent-id=... --token=... --max-cpu=2 --max-ram-mb=2048 --max-disk-gb=20 --max-concurrent-jobs=1 로 실행하는 방식이다. 요구 조건은 Databasus로의 아웃바운드 HTTPS, 에이전트 호스트의 Docker, 동시 작업 1건당 CPU 1코어와 RAM 512MB이고 디스크는 백업 파일 크기와 DB 원본 크기를 더한 값에 여유분을 얹은 만큼이다. 출처는 위 페이지와 https://databasus.com/installation/agent 다.

검증 에이전트와 백업 에이전트를 혼동하면 안 된다. /installation/agent 페이지의 백업 에이전트는 postgresql.conf의 wal_level=replica, archive_mode=on, archive_command 설정과 pg_hba.conf 복제 허용, 복제 권한 부여, WAL 큐 디렉터리를 요구하는 방식인데, 문서가 이 에이전트 백업을 폐기(deprecated)했다고 명시하고 PostgreSQL 17 원격 방식으로 대체했다고 적는다. 레거시 에이전트 백업은 3.42.0 버전까지 지원한다. 지금 새로 도입한다면 백업 에이전트를 쓸 이유가 없다. 따라서 그 페이지에 적힌 wal_level과 archive_mode 요구를 원격 물리 백업의 요구 조건으로 옮겨 적으면 안 된다.

## 접근 통제와 감사 로그

역할 기반 접근 통제는 시스템 수준과 워크스페이스 수준으로 나뉜다. 워크스페이스는 데이터베이스, 알림 대상, 저장소를 묶는 단위이고 참여하지 않은 워크스페이스는 보이지 않는다. 고객사별로 워크스페이스를 나누면 담당자별 열람 범위를 분리할 수 있다는 뜻이다.

| 수준 | 역할 | 권한 |
|---|---|---|
| 시스템 | Admin | 전체 설정, 사용자 관리, 워크스페이스 생성 |
| 시스템 | Member | 설정이 허용하면 워크스페이스 생성 |
| 워크스페이스 | Owner | admin 지정을 포함한 전체 권한 |
| 워크스페이스 | Admin | 사용자 관리, 단 admin 지정은 제외 |
| 워크스페이스 | Member | 데이터베이스·알림·저장소 관리 |
| 워크스페이스 | Viewer | 읽기 전용, 백업 실행과 다운로드는 가능 |

모든 역할에서 비밀번호와 토큰 같은 민감값은 항상 숨긴다. 외부 가입을 막아 둔 상태에서는 관리자가 이메일로 초대하고, allow member invitations 설정을 켜면 일반 구성원도 초대할 수 있다. 출처는 https://databasus.com/access-management 다.

감사 로그는 DB 생성과 삭제, 백업 작업, 알림 대상 생성, 워크스페이스 관리 등을 기록하고 워크스페이스별·사용자별 필터를 제공한다. OPEN_TELEMETRY_URL 설정으로 OTLP 외부 반출이 가능하다. 출처는 위 페이지와 https://databasus.com/advanced-config 다. 감사 로그의 보존 기간과 파일 내보내기 기능은 확인하지 못했다.

## 알림

알림 채널은 Slack, Discord, Telegram, Microsoft Teams, 이메일, 웹훅, Mattermost다. 출처는 https://databasus.com/notifiers 다.

Teams 연동 방식을 따로 확인해야 한다. Databasus는 기존 Incoming Webhook이 아니라 Power Automate의 "Post to a channel when a webhook request is received" 워크플로에서 발급한 HTTP POST URL을 요구한다. 출처는 https://databasus.com/notifiers/teams 다. 우리는 이미 Gemini 요약 일일·장애 보고를 Teams로 보내고 있으므로 기존 웹훅이 어느 방식으로 만들어졌는지 먼저 확인하고, 방식이 다르면 Databasus용 워크플로를 따로 만들어야 한다. 전달 사건은 성공·실패·경고로만 설명돼 있고 백업·복원 검증·헬스 체크별 개별 구독 설정이 있는지는 불명확하다.

## 환경 변수와 텔레메트리

환경 변수는 최소한이고 기본값만으로 단일 컨테이너가 동작한다. 공개 URL은 DATABASUS_URL, 로그 관련은 LOG_LEVEL(기본 info), LOG_FILE_IS_ENABLED(기본 true, 파일명 databasus.log), OPEN_TELEMETRY_URL, OPEN_TELEMETRY_HEADERS다. 메일은 SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASSWORD, SMTP_FROM, SMTP_INSECURE_SKIP_VERIFY이고 외부 로그인은 GOOGLE_CLIENT_ID와 SECRET, GITHUB_CLIENT_ID와 SECRET, 캡차는 CLOUDFLARE_TURNSTILE_ 계열이다. 바인드 마운트 권한이 맞지 않을 때만 PUID와 PGID를 지정하며 기본값은 마운트 소유자 또는 999다. 출처는 https://databasus.com/advanced-config 와 https://raw.githubusercontent.com/databasus/databasus/main/.env.example 다.

익명 사용 텔레메트리가 기본으로 켜져 있다. IS_DISABLE_ANONYMOUS_TELEMETRY의 기본값이 false다. 고객사 환경 도입을 설명할 때는 이 항목을 먼저 꺼내고 끄는 설정을 함께 제시해야 한다. 외부로 나가는 통신이 있는지 묻는 질문은 반드시 나오고, 도구가 그런 동작을 한다는 사실을 조사자가 먼저 말하는 것과 나중에 지적받는 것은 신뢰 면에서 다르다.

## 경쟁 도구 대비 위치

아래 내용은 Databasus 공식 비교 페이지의 자사 주장이며 제3자 검증이 아니다. 출처는 https://databasus.com/databasus-vs-pgbackrest 와 https://databasus.com/databasus-vs-wal-g 다.

| 항목 | Databasus | pgBackRest, WAL-G |
|---|---|---|
| 백업 엔진 | PostgreSQL 네이티브 도구를 원격 호출 | 자체 엔진 |
| DB 호스트 설치 | 필요 없음 | 로컬 설치와 파일시스템 접근 필요 |
| 조작 방식 | 웹 UI, 워크스페이스, RBAC, 감사 로그 | CLI 전용 |
| 물리 백업 지원 버전 | PostgreSQL 17 이상 | pgBackRest 9.4+, WAL-G 9.x+ |
| 관리형 DB | RDS 등도 대상으로 삼을 수 있다고 주장 | 파일시스템 접근이 필요해 제약 |

정리하면 Databasus의 차별점은 백업 알고리즘이 아니라 운영 인터페이스다. 백업 자체는 PostgreSQL 표준 도구가 하고 Databasus는 일정, 보존, 저장소 연동, 권한 분리, 감사, 알림, 복원 검증을 붙인다. MSP 관점에서는 이 조합이 오히려 맞는다. 여러 고객사의 DB를 한 화면에서 관리하고 누가 무엇을 했는지 남기는 것이 CLI 숙련보다 중요하기 때문이다. 반대로 지원 버전이 17 이상으로 좁다는 점은 실제 고객사 환경에서 자주 걸릴 제약이다.

| secret.key 교체 절차와 분실 시 복구 | 분실하면 복구 불가로 보아야 하지만 명시 문장을 찾지 못했다 | 설계에서는 분실 불가 전제로 별도 보관 절차를 만든다 |
| 감사 로그 보존 기간과 파일 내보내기 | 고객사 감사 대응 범위를 정하는 데 필요하다 | 감사 로그 화면에서 확인한다 |
| 알림 이벤트의 세부 목록과 개별 구독 | 성공·실패·경고 표현만 있고 백업·검증·헬스 체크별 구독 여부가 불명확하다 | 알림 대상 설정 화면에서 확인한다 |
| SSH 터널 설정 화면의 입력 항목 | 키 인증 지원 여부와 배스천 지정 방식이 폐쇄망 설계를 좌우한다 | DB 추가 화면의 터널 옵션을 캡처한다 |
| 검증 에이전트가 백업을 어디서 내려받는지 | 저장소 직접 다운로드인지 Databasus 경유인지에 따라 전송 비용이 달라진다 | 검증 1회 실행 중 네트워크 흐름과 로그를 본다 |
| Databasus 서버의 실측 자원 사용량 | 문서의 RAM 500MB는 최소치이고 우리 DB 규모의 실측이 아니다 | 소규모 DB로 1회 백업하며 상주 메모리와 임시 디스크를 잰다 |
| 물리 백업이 호스트 디스크를 얼마나 경유하는지 | 스트리밍 업로드인지 전량 적재 후 업로드인지가 노드 디스크 산정을 결정한다 | 백업 중 디스크 사용량을 관측하며 잰다 |
| PostgreSQL 공식 Software Catalogue 등재 | 사용자가 전달한 정보이며 원문 대조를 하지 않았다 | postgresql.org의 해당 목록을 직접 조회한다 |

이 문서 전체가 문서 조사 결과이며 설치·백업·복원·검증을 실행한 결과가 아니라는 점을 다시 적어 둔다. 학교 AWS에도 로컬 VM에도 Databasus를 아직 설치하지 않았다.

## 도입 판단

도입을 권한다. 다만 아래는 제안이며 사용자가 확정한 요구가 아니다.

우리 DB가 PostgreSQL 17.11이라서 Databasus가 제공하는 최선의 경로를 그대로 쓸 수 있다. 17 미만이었다면 논리 백업만 가능해 도입 가치가 크게 떨어졌을 것이다. 자체 엔진 대신 PostgreSQL 네이티브 도구를 원격 호출하는 구조라서 DB 서버에 낯선 바이너리를 설치하지 않고도 외부 보관과 예약을 붙일 수 있다. 지금 백업이 한 서버의 로컬 디스크에만 있는 상태를 가장 적은 변경으로 메운다.

배포 위치는 DB primary와 분리해야 한다. Databasus 호스트가 백업 파일을 다루므로 DB 노드에 올리면 호스트 상실에 대비한다는 목적 자체가 무너진다. bot-1은 시장 봇과 관측을 함께 돌리는 t3.small이고 봇과 Grafana 동시 운영 표본에서 가용 메모리가 약 600MiB였으며 루트 볼륨이 20GiB라서, 내부 PostgreSQL을 품은 컨테이너와 백업 파일 경유 공간을 감당하기 어렵다고 판단한다. 근거는 로드맵 9행의 동시 운영 표본과 20GiB gp3 볼륨 기록이다. 별도 소형 노드를 만들어 전용으로 쓰는 안을 제안한다. 호스트 디스크를 얼마나 경유하는지가 미확인이므로 노드 크기를 확정하기 전에 소규모 DB로 한 번 재어 본다.

Docker 사용은 예외로 기록한다. 이유는 상류가 컨테이너 배포만 제공한다는 점이고 범위는 전용 노드 한 대의 컨테이너 한 개다. 설치 스크립트가 systemd 유닛을 만들지 않으므로 compose를 systemd 유닛으로 감싸 부팅 시 기동과 실패 기록을 남기는 편이 우리 운영 기준에 맞는다.

접근 통제는 기존 방식을 따른다. 4005 포트를 공개하지 않고 SSM 포트 포워딩이나 기존 관리 경로 뒤에 두며, 보안 그룹에는 Databasus 노드 그룹에서 DB 그룹 5432로 가는 규칙 하나만 추가한다. 설치 직후 즉시 소유자 계정을 만들고 2FA 강제를 켠다. 자격증명은 문서에 적지 않고 생성 방법과 권한만 남긴다.

가장 중요한 운영 조건은 secret.key다. 이 키가 없으면 외부에 쌓아 둔 암호화 백업을 열 수 없는데 교체와 분실 복구 절차가 문서에 없다. secret.key와 pgdata를 백업 대상과 다른 위치에 별도 보관하는 절차를 설계에 함께 넣는다.

진행 순서는 두 단계로 나눈다. 1단계에서 예약 백업과 S3 외부 보관, Teams 알림까지 세운다. 2단계에서 검증 에이전트를 붙여 복원 검증 성공 화면을 확보한다. 검증 에이전트는 별도 호스트와 추가 디스크가 필요하므로 1단계와 같은 일정에 묶지 않는다.

면접에서 쓸 문장으로 정리하면, 오픈소스 도구를 설치했다가 아니라 백업을 서버 밖으로 옮기고 복원을 주기적으로 실제 실행해 확인하며 보존 계층으로 저장 비용을 통제하는 구조를 Apache-2.0 라이선스로 비용 없이 세웠다는 쪽이 맞다.
