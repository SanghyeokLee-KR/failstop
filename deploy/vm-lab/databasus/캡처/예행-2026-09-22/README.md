# Databasus 도입 예행 (2026-09-22, 로컬 VM 실습망)

이 폴더는 학교 AWS 본 실행에 앞서 로컬 VM 실습망에서 Databasus 도입 절차를 먼저 돌려 본 기록이다. 거래 데이터가 없는 환경에서 틀릴 곳을 미리 찾는 것이 목적이고, 여기서 확인한 값만 학교 AWS로 들고 간다. 예행 결과를 학교 증거본에 섞지 않는다.

이 폴더는 처음에 저장소 밖에서 만들었고, 2026-09-22에 `deploy/vm-lab/databasus/캡처/예행-2026-09-22/`로 저장소에 들어왔다(커밋 43325f5). 학교 AWS 증거본(`증거본/`)과는 따로 둔다. 계획은 [07-캡처계획.md](../../07-캡처계획.md)에 있고 번호 규칙도 그 문서를 따랐다.

## 어디까지 했고 어디서 멈췄는가

터미널에서 할 수 있는 구간은 전부 실행했다. Docker 설치, 컨테이너 기동, 포트 제한, 방화벽, DB 읽기 전용 계정, 접속 제어, 외부 보관소 준비와 접속 시험까지가 여기 있다.

멈춘 지점은 웹 UI의 최초 관리자 계정 생성이다. Databasus v3.59.0은 사전 생성된 admin 계정이 없고 최초 가입자가 인스턴스를 관리한다. 계정 생성과 비밀번호 입력은 사용자가 직접 해야 하는 일이라 AI가 대신하지 않았다. 그 뒤로 이어지는 DB 등록, 저장소 등록, 백업 실행, 복원 검증도 같은 이유로 아직 실행하지 않았다. 실행하지 않은 것을 통과로 적지 않는다.

이어서 할 일은 [../../08-이어서할일.md](../../08-이어서할일.md)에 순서대로 적었다.

## Docker를 쓴 이유와 범위

이 저장소는 Linux 직접 설치를 기본으로 삼는다. Databasus는 예외로 두었고 이유는 상류의 배포 형태다. 최신 릴리스 v3.59.0의 assets가 비어 있어 내려받을 바이너리나 rpm이 없고, 공식 설치 방법 네 가지가 전부 컨테이너를 전제한다. 이미지 안에 자기 메타데이터용 PostgreSQL 17 인스턴스와 각 DB의 클라이언트 도구가 함께 들어 있어 직접 설치로 재구성할 수 있는 모양이 아니다.

범위는 OPS01 한 대의 컨테이너 한 개로 한정한다. 운영자 계정에 docker 그룹을 주지 않는 기존 방침을 유지했고 모든 docker 명령은 sudo로 실행했다.

## 상류 정의에서 바꾼 것

게시 주소를 `4005:4005`에서 `127.0.0.1:4005:4005`로 바꿨다. 상류대로 두면 호스트의 모든 주소에 열린다. 백업 도구의 화면에는 DB 자격증명과 백업 목록과 복원 명령이 한 곳에 모이므로 Grafana보다 더 가려야 한다.

이미지 태그를 `latest`에서 `v3.59.0`으로 고정했다. latest는 컨테이너를 다시 만들 때마다 내용이 달라져 어떤 판으로 백업했는지 증거에 남지 않는다.

재시작을 Docker의 `unless-stopped`에만 맡기지 않고 systemd 유닛으로 감쌌다. 다른 서비스와 같은 방법으로 기동과 실패를 볼 수 있어야 한다.

## 구축 중에 막혔던 곳

세 번 막혔고 셋 다 기록해 둘 값이 있다.

컨테이너가 DB01로 나가지 못했다. 공통 기반의 `inet vmlab` forward 체인이 기본 차단인데 컨테이너 통신이 그 훅을 지나기 때문이다. Docker가 만든 `ip filter FORWARD`의 accept는 다른 계통이라 이 차단을 대신하지 못한다. 처음에는 `docker0`을 허용했는데 compose가 전용 네트워크를 따로 만들어 브리지 이름이 `br-98baf28a7371`이었고 규칙이 하나도 맞지 않았다. compose의 `driver_opts`로 이름을 `databasus0`으로 고정하고 방화벽이 그 이름을 쓰게 했다.

읽기 전용 계정이 읽지 못했다. `pg_read_all_data`를 GRANT했는데도 SELECT가 거부됐다. PostgreSQL 16부터 상속 여부가 역할 속성이 아니라 GRANT 시점에 고정되기 때문이다(`pg_auth_members.inherit_option`). 역할을 NOINHERIT로 만든 뒤 `ALTER ROLE ... INHERIT`로 바꿔도 이미 준 멤버십은 따라오지 않는다. `GRANT ... WITH INHERIT TRUE`로 다시 주고 나서야 읽혔다.

외부 보관소에 붙지 못했다. 공통 기반이 `AllowUsers`를 ops 하나로 좁혀 두어 백업 전용 계정이 거절됐고, `/srv` 아래에 만든 `.ssh`의 SELinux 문맥이 `ssh_home_t`가 아니라 `var_t`였다. 둘 다 고친 뒤에 붙었다.

## 예행의 한계

외부 보관 대상으로 EDGE01을 빌려 썼다. 실습망에 전용 백업 호스트가 없고, DB01(원본)도 OPS01(백업 도구)도 아닌 노드여야 서버 밖 보관을 보일 수 있기 때문이다. EDGE01은 구성도에서 웹 진입 노드이므로 운영 배치로는 적절하지 않다. 학교 AWS와 개인 계정 재배포에서는 S3 또는 전용 SFTP 호스트를 쓴다. 이 대체를 성공으로 읽지 않는다.

`databasus-data` 디렉터리 하나에 설정, 자격증명, 메타데이터, 암호화 마스터 키가 모두 모인다. 백업 파일이 외부 보관소에 남아 있어도 이 디렉터리를 잃으면 복호화 경로를 잃는다. 이 디렉터리 자체를 어떻게 보관할지는 아직 정하지 않았다.

호스트에서 본 데이터 디렉터리의 소유자가 `systemd-oom`으로 보인다. 컨테이너 안 UID 999가 호스트의 그 계정과 겹쳐서 그렇게 보일 뿐이고 잘못된 설정이 아니다.

## 비밀 값을 어떻게 다뤘는가

DB 계정 비밀번호는 아직 넣지 않았다. 역할만 만들어 두었고 값은 사용자가 `\password`로 직접 넣는다.

암호화 마스터 키는 `cat`도 `sha256sum`도 하지 않았다. 해시도 사실상 지문이 되므로 남기지 않았다. 011에는 `stat` 결과만 있다.

외부 보관소용 SSH 키는 OPS01 안에서 만들었고 이 예행 기간에 개인키는 그 호스트 밖으로 나가지 않았다. EDGE01에는 공개키만 넣었다. 웹 UI에 저장소를 등록할 때는 개인키가 작업 PC의 브라우저를 한 번 지나므로, 등록한 뒤에는 이 문장이 더 이상 맞지 않는다([08-이어서할일.md](../../08-이어서할일.md) 4절). 2026-09-26 등록 때 개인키가 작업 PC의 클립보드와 브라우저를 한 번 지났다([Databasus 증거본](../../../../../증거본/2026-09-26_VM_Databasus/README.md)).
