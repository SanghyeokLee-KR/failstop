# Databasus 도입 캡처 계획

이 문서는 실행 전 설계다. 2026-09-22 기준으로 Databasus 를 설치하거나 화면을 열어 본 사실이 없다. 아래에 적은 화면 이름과 항목 수는 공식 문서를 읽고 세운 예상이며, 최초 로그인 뒤 실제 메뉴 라벨을 보고 조정한다. 어떤 항목도 "확인함"으로 미리 적지 않는다.

캡처의 목적은 도구를 소개하는 것이 아니다. 고객사 데이터베이스를 서버 밖에 안전하게 두고, 그 백업이 실제로 되살아나는지 스스로 확인하고, 실패하면 사람에게 알리고, 저장 비용이 예측 범위 안에 머문다는 것을 화면과 출력으로 증명하는 것이다. 그래서 성공 화면만 모으지 않고 실패 구간과 비용 구간을 같은 비중으로 남긴다.

## 캡처를 시작하기 전에 정해야 할 네 가지

첫째는 외부 저장소의 인증 방식이다. Databasus 의 S3 목적지가 EC2 인스턴스 프로파일 인증을 지원하는지 아직 확인하지 못했다. 공식 문서에는 endpoint 와 credentials 입력만 나온다. 학교 AWS 계정에서는 새 Access Key 발급의 금지 해제를 요청하지 않기로 이미 정해 두었으므로, 인스턴스 역할을 못 쓰면 목적지를 다른 계정의 버킷이나 Cloudflare R2, SFTP 로 바꿔야 한다. 그러면 E 구간의 캡처 대상이 통째로 달라진다.

둘째는 설치 호스트다. 앱 노드, bot-1 관측 노드, 별도 노드, VM 랩 OPS01 가운데 어디에 두는지에 따라 접근 경로와 캡처할 콘솔이 달라진다. 이 결정은 이 문서에서 내리지 않는다.

셋째는 웹 UI 포트 4005 에 도달하는 방법이다. 공개 노출 없이 SSH 터널을 쓰면 브라우저 주소창이 127.0.0.1:4005 로 남아 화면만으로는 어느 서버인지 증명되지 않는다. 그래서 아래 계획은 UI 캡처마다 호스트를 증명하는 텍스트 증거를 바로 앞 번호에 둔다. 보안 그룹 임시 규칙을 쓰는 경우에는 2026-09-21 기록처럼 제거 대상이 남으므로 N 구간에서 반드시 회수한다.

넷째는 복원 검증 에이전트를 돌릴 호스트와 그 디스크 여유다. 공식 문서는 에이전트를 직접 운영하는 장비에서 실행하는 작은 Go 바이너리로 설명하고, 그 호스트에 Docker 와 아웃바운드 HTTPS, 백업 파일 크기와 DB 원본 크기를 합한 여유 디스크를 요구한다. 학교 EC2 는 루트 20GiB 또는 50GiB 구성이라 여유를 먼저 계산해야 한다.

이 네 가지가 정해지기 전에 캡처를 시작하면 중간에 폴더를 다시 만들게 된다.

## 폴더와 파일 이름

학교 AWS 본 실행은 `C:\Users\kopo26\Desktop\failstop\증거본\<실행일>_Databasus_백업도입\` 에 둔다. 폴더 안에는 README.md, 실행 명령 로그, `NNN_이름.png`, `NNN_이름.txt` 를 둔다. 기존 증거본 규칙을 그대로 쓰고 새 규칙을 만들지 않는다. 세 자리 번호에 밑줄, 그다음 한국어 이름이다. 이름은 대상과 내용과 결과를 붙여 다섯 단어 안쪽으로 적는다. `001_DB_백업전_상태` 처럼 이미 쓰던 형태를 따른다.

VM 랩 예행은 `C:\Users\kopo26\Desktop\vm-lab\databasus\캡처\예행-<날짜>\` 에 둔다. 번호 규칙은 같게 쓰되 폴더 이름에 예행임을 남기고, 예행 결과를 학교 증거본에 섞지 않는다. 이 경로는 저장소 밖이라 커밋되지 않는다. 예행의 목적은 절차를 다듬고 실패 지점을 미리 찾는 것이다.

계획 번호와 실제 저장 번호가 어긋날 수 있다. 중간에 항목이 늘면 앞을 다시 매기지 말고 실제 실행 순서대로 번호를 붙인 뒤 폴더 README 에 계획 번호와의 대조를 한 줄씩 적는다.

증거본 폴더의 README.md 는 `.md` 라서 스타일 게이트가 적용된다. Databasus 공식 README 제목에는 이모지가 들어 있으므로 옮겨 적지 않는다. 접근성 TXT 는 스타일 검사 대상이 아니므로 제품 UI 원문을 그대로 두어도 된다. 다만 링크 검사는 `.md` 와 `.txt` 를 모두 보므로 문서에서 `docs/` 경로를 인용하면 실재하는 경로여야 한다.

## 판정의 공통 규칙

화면 하나가 무엇을 증명하는지 미리 정해 두지 않으면 나중에 같은 화면을 다시 찍게 된다. 아래 네 가지는 모든 항목에 공통으로 적용한다.

터미널 출력은 첫 줄에 `date -u` 결과가 보이게 한다. 실행한 명령과 그 결과가 같은 화면 안에 함께 보여야 한다. 종료 코드 출력용 문구는 사용자의 2026-09-19 요청에 따라 붙이지 않고, 성공 여부는 실제 출력과 상태와 대상의 존재로 판단한다.

브라우저 화면은 바로 앞 번호에 그 호스트를 증명하는 텍스트를 둔다. 같은 시각의 `hostname`, `ip a`, `ss -lntp | grep 4005` 출력이면 충분하다. SSH 터널로 접근하는 동안 주소창이 127.0.0.1 로 보이는 것은 문제가 아니다. 짝이 되는 텍스트가 없는 것이 문제다.

실패하거나 다시 시도한 구간을 지우지 않는다. 캡처를 놓친 구간은 뒤 화면으로 메우지 말고 폴더 README 에 누락으로 적는다.

브라우저 창 크기와 표시 언어와 테마를 작업 내내 고정한다. 창 크기가 들쭉날쭉하면 발표 자료에서 화면이 서로 어긋난다. 전체 화면이 아니라 브라우저 창만 캡처해서 다른 창이 함께 찍히지 않게 한다.

## 비밀 값이 화면에 나오지 않게 하는 방법

기록하지 않을 대상은 첫 관리자 비밀번호, 읽기 전용 DB 계정 비밀번호, S3 Access Key ID 와 Secret Access Key, Teams 워크플로 URL, `secret.key` 내용, 2단계 인증 코드와 그 코드가 담긴 메일 화면, 개인 키다. Access Key ID 는 비밀이 아니라고 오해하기 쉬우나 계정 식별자이므로 함께 가린다.

브라우저에서는 값을 넣기 직전에 캡처를 멈추고, 저장을 누른 다음 결과 화면부터 캡처를 재개한다. 입력란의 표시 전환 아이콘을 누르지 않고, 브라우저의 비밀번호 저장 팝업이 뜨면 거절한 뒤 화면을 남긴다. 저장 후 목록 화면에서 값이 가려져 나오는 것을 확인하고 그 화면을 증거로 쓴다.

접근성 TXT 에는 입력한 값이 문자열로 남을 수 있다. PNG 만 조심하면 된다고 생각하면 안 된다. 비밀 입력이 있었던 화면의 TXT 는 저장 직후 패턴으로 훑는다. `grep -nEi 'password|passwd|secret|token|AKIA|webhook|logic\.azure\.com|BEGIN [A-Z ]*PRIVATE KEY' 파일.txt` 정도면 대부분 걸린다. 값을 직접 grep 인자로 넣으면 그 값이 셸 히스토리에 남으므로 패턴으로만 검사한다. 걸리면 그 TXT 는 저장하지 않고 폴더 README 에 제외 사유를 적는다.

터미널에서는 비밀 값을 명령줄 인자로 넣지 않는다. 비밀 입력이 필요한 구간은 `set +o history` 로 히스토리를 끄거나 `read -s` 를 쓰고, PostgreSQL 은 `~/.pgpass` 를 0600 으로 두고 쓴다. 환경 파일은 `cat` 하지 않고 `stat` 으로 권한과 소유자를, `cut -d= -f1` 로 키 이름만 남긴다. `secret.key` 는 절대 `cat` 하지 않고 `stat` 결과와 바이트 수만 남긴다. 해시도 사실상 지문이 되므로 남기지 않는다.

발표용으로 가림 처리가 필요하면 원본을 그대로 두고 `발표사본/` 폴더를 따로 만들어 구분한다. 원본에 덧칠하지 않는다.

## A 구간. 도입 전 상태

이 구간은 뒤에 나올 개선의 기준선이다. 지금 백업이 한 서버의 로컬 디스크에만 있다는 사실 자체가 증거다. 로드맵도 이 상태를 볼륨 상실 대비 완료로 쓰지 않는다고 적고 있다.

| 번호 | 파일명 | 형식 | 이 화면이 증명하는 것 | 비밀 값 |
|---|---|---|---|---|
| 001 | `001_DB_현재백업_로컬보관` | TXT | `date -u`, 백업 디렉터리 목록과 마지막 생성 시각, 파일 크기, `df -h`. 서버 밖 사본이 없다는 상태 | 없음 |
| 002 | `002_대상호스트_역할_자원` | TXT | `hostname`, `ip a`, 인스턴스 식별자, `nproc`, `free -m`, `df -h`. 이 호스트가 0099 의 어느 역할인지 | 없음 |
| 003 | `003_대상호스트_도커_설치여부` | TXT | `command -v docker`, 버전 또는 미설치 출력, `systemctl is-active docker` | 없음 |

003 은 설치 항목 수를 결정한다. 학교 네 호스트에 Docker Engine 이 있는지 아직 확인하지 못했다. 저장소의 학교 구간 기록은 모두 직접 설치이고 Compose 절차는 로컬 실습으로 구분되어 있다.

## B 구간. 설치

Databasus 는 한 줄 설치 스크립트, docker run, docker compose, Helm 만 문서화되어 있고 네이티브 바이너리 설치 경로가 없다. 따라서 이 도구는 컨테이너로 올린다. 저장소 규칙은 Linux 직접 설치를 기본으로 하되 필요한 항목은 이유와 범위를 기록해 Docker 를 쓰도록 하고 있으므로, 그 이유와 범위를 폴더 README 에 한 문단으로 적는다. 운영자 계정에 docker 그룹을 주지 않는 기존 방침도 유지한다.

파이프로 받은 스크립트를 바로 실행하면 무엇이 바뀌었는지 캡처로 설명할 수 없다. 스크립트를 파일로 내려받아 해시와 앞부분 내용을 먼저 남기고 그다음에 실행한다.

| 번호 | 파일명 | 형식 | 이 화면이 증명하는 것 | 비밀 값 |
|---|---|---|---|---|
| 004 | `004_도커_설치_출력` | TXT | 패키지 설치 명령과 결과, `docker --version` | 없음 |
| 005 | `005_도커_서비스_활성화` | TXT | `systemctl is-enabled docker`, `is-active docker`, `docker compose version` | 없음 |
| 006 | `006_설치자료_원문_해시` | TXT | 내려받은 스크립트 또는 compose 파일의 `sha256sum` 과 앞부분 내용 | 없음 |
| 007 | `007_배치경로_권한_확인` | TXT | `ls -l`, `stat` 으로 데이터 경로와 환경 파일 0600, 환경 파일은 `cut -d= -f1` 로 키 이름만 | 환경 파일 값 미출력 |
| 008 | `008_컨테이너_기동_출력` | TXT | 기동 명령과 이미지 내려받기, 컨테이너 생성 결과 | 없음 |
| 009 | `009_컨테이너_상태_헬스` | TXT | `docker ps` 의 상태와 헬스, `docker logs` 마지막 스무 줄 | 로그에 값이 보이면 해당 줄 제외 |
| 010 | `010_포트4005_리슨_확인` | TXT | `ss -lntp` 의 4005 바인드 주소, `curl -sI http://127.0.0.1:4005` 응답 줄 | 없음 |
| 011 | `011_데이터디렉터리_키_권한` | TXT | 데이터 디렉터리 소유자와 권한, `secret.key` 의 `stat` 결과와 바이트 수 | 키 내용 미출력, `cat` 금지 |

010 의 리슨 주소가 `0.0.0.0:4005` 인지 `127.0.0.1:4005` 인지가 뒤 구간의 접근 방식을 결정한다. 공개 노출을 피하려면 루프백 바인드와 SSH 터널이 안전하다.

## L 구간. 실패 상황

성공 화면만 모으면 운영 근거가 되지 않는다. 실패가 발생하고, 보이고, 알려지고, 복구되는 네 단계를 남긴다.

실패는 운영 데이터와 실제 목적지를 건드리지 않는 범위에서 만든다. 권장하는 방법은 시험용 목적지 항목을 하나 더 만들어 버킷 이름이나 엔드포인트를 틀리게 두고 그 항목으로만 백업을 돌리는 것이다. DB 쪽에서 실패를 내고 싶으면 시험용 DB 항목의 접속 정보를 틀리게 둔다. 운영 항목의 설정을 바꿨다가 되돌리는 방식은 되돌림을 빠뜨릴 위험이 있어 쓰지 않는다.

## 캡처하는 동안의 기록 습관

터미널은 명령 한 개를 실행하고 출력을 보관한 뒤 다음 명령으로 넘어간다. 여러 명령을 한 번에 몰아 실행하면 어느 출력이 어느 명령의 결과인지 나중에 구분하기 어렵다. 긴 출력은 여러 장으로 나누고 원문 텍스트를 함께 남긴다.

항목을 저장할 때마다 실행 로그에 UTC 시각과 증거 이름과 실행한 명령을 한 줄씩 추가한다. 브라우저 조작처럼 명령이 없는 항목은 무엇을 확인했는지 한 줄로 적는다. 나중에 몰아서 쓰면 시각이 부정확해진다.

비밀 입력이 있었던 화면의 TXT 는 저장 직후 패턴 검사를 돌린다. 하루 작업이 끝난 뒤 한꺼번에 검사하면 이미 커밋된 뒤일 수 있다.

기존 폴더 하나가 약 6MB 이므로 이번 폴더도 비슷한 규모를 예상한다. 저장소 용량 상한이나 정책은 확인하지 못했으므로, PNG 수가 예상보다 크게 늘면 커밋 전에 한 번 확인한다.

## 발표 자료와 보고서로 넘기는 방법

전체를 발표에 다 넣지 않는다. 도입 전 상태 001, 외부 보관 성공 035 와 036, 복원 검증 성공 043, 기존 기준 건수 대조 047, 실패 알림 054, 열람 전용 차단 050 과 감사 로그 051, 비용 산식 059 를 고르면 아홉 장이다. 여기에 도입 전후를 나란히 놓는 장 하나를 더하면 열 장 안팎으로 정리된다.

이 선별은 연구소장이 전한 메시지의 두 축에 그대로 대응한다. 안전하게 백업한다는 주장은 035, 036, 043, 047, 050, 051 이 받치고, 비용 문제가 나오지 않게 한다는 주장은 027 의 보존 정책 선택과 057, 058, 059 의 사용량과 산식이 받친다. 054 는 그 두 축이 실제 운영에서 유지된다는 근거다.

보고서 본문은 증거본 폴더의 README 에 먼저 쓴다. 도입 전 상태, 무엇을 설치했고 왜 컨테이너로 했는지, 확인한 것과 확인하지 못한 것, 남은 위험을 문단으로 적고 캡처 목록을 순서대로 잇는다. 그다음 증거본 최상위 README.md 의 목록에 한 줄을 추가한다. 로드맵의 외부 보관 항목은 실제 예약 실행과 격리 복원 성공을 확인한 뒤에만 갱신한다.

## 확인하지 못한 것

Databasus 웹 UI 사이드바의 실제 메뉴 라벨을 확정하지 못했다. 공식 문서에서 Dashboard, Healthchecks, Audit logs, Workspaces, New Database 는 확인했지만 저장소 목적지, 일정, 보존, 복원 화면의 정확한 표기는 확인하지 못했다. 위 파일명은 기능 기준으로 먼저 정했고 최초 로그인 뒤 라벨에 맞춰 조정한다.

S3 목적지의 인스턴스 역할 지원 여부, 설치 호스트, 4005 접근 경로, 복원 검증 에이전트 호스트와 디스크 여유는 모두 미결이다. 학교 네 호스트의 Docker 설치 여부도 확인하지 못했다.

브라우저 캡처 도구가 VM 랩의 192.168.10.41:4005 에 도달할 수 있는지 확인하지 못했다. 작업 PC 는 관리망 192.168.56.0/24 에 있고 lab-lan 192.168.10.0/24 는 사용자가 직접 만들 pfSense 뒤에 있다. 도달하지 못하면 SSH 포트 포워딩이나 관리망 어댑터가 필요하다.

백업 1회 크기, 하루 증가량, 보존 기간별 저장소 사용량을 측정한 값이 없다. 증거본에 PNG 수십 장을 추가할 때의 저장소 용량 정책도 확인하지 못했다.

이 계획의 어떤 항목도 아직 실행하지 않았다.
