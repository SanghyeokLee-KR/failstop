# Databasus 예행에서 이어서 할 일

2026-09-26에 아래 1~7을 실행했다. 결과와 캡처는 [Databasus 증거본](../../../증거본/2026-09-26_VM_Databasus/README.md)에 있다. 같은 날 pfSense 경계형으로 옮긴 뒤라 실제로는 아래 명령의 host-only 주소 대신 lab-lan 주소와 작업 PC의 ssh 별칭(`ssh ops01`, `ssh db01`, `ssh edge01`, 키 `vm-lab-devpc_ed25519`)을 썼다. 저장소 호스트는 `192.168.56.11`이 아니라 `192.168.10.11`이고, 그 연결을 위해 EDGE01의 `AllowUsers`와 nftables를 OPS01 lab-lan 주소 기준으로 바꿨다(`build/scripts/55-boundary-db-backup-sftp.sh`). 화면의 항목 이름은 한글 역할 이름(워크스페이스 "페일스톱 VM 실습망", 저장소 "외부 백업 보관소 (웹 진입 서버 SFTP)", DB "거래 DB (주 DB)")으로 만들었다. 복원 검증은 OPS01에 에이전트를 두어 성공했고, 남은 일은 증거본 README의 "발견과 남은 일"에 있다. 아래 본문은 2026-09-22에 쓴 계획이라 그대로 둔다.

2026-09-22 기준이다. 터미널로 할 수 있는 구간은 끝났고, 여기서부터는 사용자가 직접 값을 넣어야 진행된다. 실행한 것과 실행하지 않은 것을 먼저 구분해 둔다.

## 이미 되어 있는 것

OPS01에 Docker CE 29.8.1과 Compose v5.5.1이 올라가 있고 부팅 자동 시작이다. Databasus v3.59.0 컨테이너가 `databasus.service`로 떠 있으며 헬스체크가 healthy다. 웹 UI는 `127.0.0.1:4005`에만 열려 있다. OPS01 자신에서 lab-lan 주소로 4005에 붙으면 응답이 없는 것까지 확인했고, 다른 VM에서 직접 시도한 기록은 없다.

DB01에는 읽기 전용 계정 `databasus_ro`가 있다. `pg_read_all_data`를 상속받아 읽기만 되고 104개 테이블 전부에 대해 INSERT·UPDATE·DELETE·TRUNCATE가 0이다. 실제로 `DELETE FROM ledger_entries`를 해 보면 거부된다. `pg_hba.conf`에 OPS01의 lab-lan 주소 하나만 `hostssl ... scram-sha-256`으로 열려 있고 방화벽도 그 주소만 5432로 통과시킨다.

외부 보관 대상은 EDGE01의 `dbbackup` 계정이다. 셸이 없고 `/srv/db-backup` 안에 갇혀 있으며 SFTP만 된다. OPS01에서 전용 키로 붙어 올리고 지우는 것까지 확인했다. 컨테이너에서도 그 포트에 닿는다.

증거는 `캡처/예행-2026-09-22/`에 17개 있다.

## 1. 관리자 계정을 만든다 (사용자가 직접)

작업 PC에서 터널을 연다. 이미 열려 있으면 다시 열지 않아도 된다.

```bash
ssh -f -N -L 14005:127.0.0.1:4005 -i ~/.ssh/vm-lab_ed25519 ops@192.168.56.41
```

브라우저로 `http://127.0.0.1:14005` 를 연다. "This is the first account on this instance, so it will administer it." 라고 적힌 가입 화면이 나온다. 이름, 메일, 비밀번호를 넣고 가입한다.

이 화면은 캡처하지 않는다. 비밀번호 입력 화면이기 때문이다. 가입을 마친 뒤의 결과 화면부터 다시 캡처한다. 브라우저의 비밀번호 저장 팝업이 뜨면 거절한다.

터널을 닫기 전까지는 이 주소가 열려 있으므로 가입을 미루지 않는다. 최초 가입자가 소유권을 갖는 구조라 설치와 계정 생성 사이를 벌리면 안 된다.

캡처할 것은 `014_관리자계정_생성완료`와 `015_대시보드_초기상태` 두 개다.

## 2. DB 계정 비밀번호를 넣는다 (사용자가 직접)

DB01에서 `databasus_ro`의 비밀번호를 정한다. 명령줄 인자로 넣지 않는다. 셸 히스토리와 프로세스 목록에 남는다.

```bash
ssh -i ~/.ssh/vm-lab_ed25519 ops@192.168.56.31
sudo -u postgres psql -d exchange -c "\password databasus_ro"
```

값을 두 번 입력하면 끝난다. 넣은 값은 3번에서 Databasus 화면에 다시 넣어야 하므로 기억해 둔다.

## 3. DB를 등록한다

Databasus 화면에서 데이터베이스를 추가한다. 넣을 값은 다음과 같다.

| 항목 | 값 |
|---|---|
| 호스트 | `192.168.10.31` |
| 포트 | `5432` |
| 데이터베이스 | `exchange` |
| 사용자 | `databasus_ro` |
| 비밀번호 | 2번에서 정한 값 |
| SSL | 켠다. `pg_hba.conf`가 `hostssl`이라 끄면 붙지 않는다 |

비밀번호 칸이 빈 상태로 한 번 캡처하고(`019_DB등록_마법사_입력`), 값을 넣어 저장한 뒤 결과 화면을 캡처한다(`020_DB등록_연결시험_성공`). 상태 점검 화면도 남긴다(`021_상태점검_화면`).

연결이 안 되면 DB01에서 원인을 본다.

```bash
sudo tail -30 /var/lib/pgsql/17/data/log/postgresql-*.log
sudo nft list chain inet vmlab roles | grep 5432
```

## 4. 외부 저장소를 등록한다

저장소 종류에서 SFTP를 고른다. 넣을 값은 다음과 같다.

| 항목 | 값 |
|---|---|
| 호스트 | `192.168.56.11` |
| 포트 | `22` |
| 사용자 | `dbbackup` |
| 경로 | `/databasus` (계정이 `/srv/db-backup`에 갇혀 있어 그 안에서는 `/databasus`로 보인다) |
| 인증 | 개인키 |

개인키는 OPS01의 `/etc/databasus/sftp-key`에 있다. 화면에 붙여 넣으려면 그 내용을 작업 PC로 가져와야 한다. 개인키를 터미널에 출력하지 않는다. 화면에 뜬 값은 스크롤백, 화면 캡처, 세션 기록에 남는다. 이 값은 캡처하지 않는다.

작업 PC의 PowerShell에서 화면에 찍지 않고 클립보드로 바로 보낸다.

```powershell
ssh -i $env:USERPROFILE\.ssh\vm-lab_ed25519 ops@192.168.56.41 'sudo cat /etc/databasus/sftp-key' | Set-Clipboard
```

브라우저의 개인키 칸에 붙여 넣고 저장한 직후 클립보드를 비운다. Windows 클립보드 기록(Win+V)이 켜져 있으면 그 항목도 지운다.

```powershell
Set-Clipboard -Value ' '
```

이 경로를 쓰면 개인키가 OPS01 밖(작업 PC의 클립보드와 브라우저)을 한 번 지난다. 예행 README와 보고서의 "개인키는 그 호스트 밖으로 나가지 않았다"는 등록 전까지의 사실이다. 등록한 뒤에는 이 문장을 고친다. 위 명령은 아직 실행하지 않았다.

만약 Databasus의 SFTP 화면이 개인키를 받지 않고 비밀번호만 받는다면, EDGE01에서 그 계정만 비밀번호 인증을 켜야 한다. 소스의 `SFTPStorage` 모델은 비밀번호와 개인키를 모두 받으므로([02-배치설계.md](02-배치설계.md)) 이 경로가 필요할 가능성은 낮다.

`PasswordAuthentication yes` 한 줄만으로는 비밀번호 로그인이 되지 않는다. 공통 기반의 `/etc/ssh/sshd_config.d/20-vm-lab.conf`가 전역에 `AuthenticationMethods publickey`를 걸어 두었고, 이 값은 `Match` 블록에서 따로 바꾸지 않으면 dbbackup에도 그대로 적용된다. 그래서 두 줄을 함께 넣는다. 파일 끝이 `Match User dbbackup` 블록이므로 덧붙인 줄은 그 블록 안에 들어간다.

```bash
ssh -i ~/.ssh/vm-lab_ed25519 ops@192.168.56.11
sudo tee -a /etc/ssh/sshd_config.d/30-db-backup.conf <<'CONF'
    PasswordAuthentication yes
    AuthenticationMethods password
CONF
sudo sshd -t && sudo systemctl reload sshd
sudo passwd dbbackup
```

넣고 나면 두 계정의 적용값을 각각 본다. dbbackup은 `passwordauthentication yes`와 `authenticationmethods password`, ops는 여전히 `no`와 `publickey`여야 한다.

```bash
sudo /usr/sbin/sshd -T -C user=dbbackup,host=x,addr=192.168.56.41 | grep -Ei '^(passwordauthentication|authenticationmethods)'
sudo /usr/sbin/sshd -T -C user=ops,host=x,addr=192.168.56.1 | grep -Ei '^(passwordauthentication|authenticationmethods)'
```

이 대안 절차도 아직 실행하지 않았다. 비밀번호 인증을 켜면 dbbackup 계정이 비밀번호 추측의 대상이 되므로, 개인키 경로가 되면 이 절차는 쓰지 않는다.

캡처할 것은 `022_저장소_등록_화면`(자격증명 칸은 빈 상태)과 `024_저장소_연결시험_성공`이다.

## 5. 백업을 실행하고 결과를 확인한다

논리 백업을 한 번 수동으로 돌린다. exchange DB가 13MB라 금방 끝난다. 끝나면 EDGE01에서 파일이 실제로 도착했는지 본다.

```bash
ssh -i ~/.ssh/vm-lab_ed25519 ops@192.168.56.11 'sudo ls -la /srv/db-backup/databasus/'
```

화면의 "성공"만으로 판정하지 않는다. 파일이 목적지에 있고 크기가 0이 아니어야 한다.

## 6. 복원 검증을 켠다

Databasus의 복원 검증은 별도 에이전트를 돌리는 구조다. 그 에이전트가 요구하는 디스크는 백업 파일 크기와 원본 DB 크기의 합에 여유를 더한 값이다. OPS01의 `/`에 9GB가 남아 있고 DB가 13MB라 여유는 충분하다.

복원 검증이 실제로 되살렸다는 것을 화면 밖에서도 확인한다. 검증용 임시 컨테이너가 떴다 사라지는 것을 `docker ps -a`로 볼 수 있다.

## 하지 않기로 한 것

물리 백업과 PITR은 1단계에서 켜지 않는다. 설계만 남긴다. 물리 백업은 복제 프로토콜을 쓰므로 `REPLICATION` 속성이 붙은 계정이 따로 필요하고, 그 결정은 별도로 기록한 뒤에 한다.

`databasus-data` 디렉터리 자체의 보관 방법은 아직 정하지 않았다. 이 디렉터리를 잃으면 백업이 남아 있어도 복호화하지 못한다. 학교 AWS로 넘어가기 전에 정한다.
