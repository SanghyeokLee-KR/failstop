# VM 경계 방화벽 실습 계획

교수님이 방화벽을 사용해 보라고 요청해 로컬 VM에 경계 방화벽을 세우는 계획이다. 제품은 지정받지 않았고 무료 조건만 있어 pfSense CE를 골랐다. 학교 AWS 운영 환경은 건드리지 않으며, 이 실습 결과를 AWS 검증 결과로 적지 않는다.

이 문서는 작업 전 계획으로 시작했다. 2026-09-26에 실제로 구축했고, 계획과 달라진 점과 결과를 바로 아래에 적었다. 실제 화면과 명령 출력은 [pfSense 증거본](../../../증거본/2026-09-26_VM_pfSense/README.md)에 있다.

## 실제 구축 결과(2026-09-26)

pfSense보다 여섯 대 실습망(EDGE01, APP01, APP02, DB01, DB02, OPS01)을 먼저 구축했으므로 보호 대상은 아래 계획의 `lab-app`, `lab-db` 두 대가 아니라 여섯 대다. 여섯 대는 구축 단계에서 NIC 세 개(NAT, `lab-lan`, host-only)를 가졌고, 그대로 두면 작업 PC가 host-only로 VM에 직접 닿아 pfSense를 지나지 않는다.

사용자는 2026-09-26에 경계형을 골랐다. 여섯 대의 NAT·host-only NIC을 떼고 `lab-lan` NIC 하나만 남겼다. 작업 PC는 pfSense 관리 인터페이스(192.168.56.10)를 거쳐 `lab-lan`에 닿고, 웹 진입은 pfSense 포트포워딩(192.168.56.10:443 → EDGE01 192.168.10.11:443)으로만 연다. VM의 기본 경로·DNS·NTP는 pfSense(192.168.10.1)다. 주소와 전환 순서는 [주소 계획](../build/00-주소계획.md)의 '네트워크'와 '경계형 전환 절차'에 있다.

VM끼리의 `lab-lan` 통신은 같은 세그먼트라 경계형에서도 pfSense를 지나지 않는다. 이 구간은 각 VM의 nftables(`table inet vmlab`과 역할별 `firewall.d`)가 거른다. 그래서 시연은 두 겹이다. pfSense가 관리망 ↔ `lab-lan`과 외부 발신을, nftables가 VM 사이를 막는다. 호스트 방화벽은 `deploy/linux/firewall-host.sh`를 그대로 쓰지 않았으며 이유는 [OPS01 관측 구축 절차](../build/문서/OPS01_관측_구축절차.md)의 '설계에서 의도적으로 벗어난 곳'과 `build/02-정본결정.md` 4절에 있다.

계획에 없던 pfSense 설정도 넣었다. 별칭으로 규칙의 대상을 이름으로 묶었고, 방화벽 이벤트를 OPS01(192.168.10.41:514)로 원격 전송하며, VM의 DNS와 NTP를 pfSense가 맡는다. IPsec은 AWS 배포 뒤로 미뤘다.

'확인할 항목' 표의 결과 열이 실제 시험 결과다. 모두 작업 PC에서 사람이 치는 명령(`curl`, `Test-NetConnection`, `ssh <VM> "nc -zv ..."`, `nslookup`, `chronyc`)으로 실제 접속해 판정했다.

## 투명 방화벽 전환(2026-09-28)

연구소장님은 경계형이 NAT 때문에 고객사 서버의 주소와 설정을 바꾸게 만든다고 지적하고, 투명 방식으로 바꿔 서버 주소를 그대로 둔 채 L2·L3·L4를 거르고 가능하면 서버 인증서로 L7까지 검사하라는 숙제를 줬다. 실제로 09-26 경계형 전환 때는 여섯 대의 기본 경로·DNS·NTP와 sshd·Nginx·인증서·앱 허용 주소를 모두 바꿔야 했다.

2026-09-28에 pfsense-fw를 복제해 브리지 방화벽 pfsense-tp를 만들고, 기존 라우터(pfsense-fw)와 서버 사이에 끼웠다. 여섯 대의 NIC은 구역 내부망(`lab-dmz`, `lab-app`, `lab-data`, `lab-ops`)으로 옮겼고 서버 안의 주소·경로·DNS는 한 줄도 바꾸지 않았다. 기존 라우터의 포트포워딩은 지웠고, 투명 방화벽은 경로 추적에도 나타나지 않는다. 관리 주소는 서비스 대역과 떨어진 host-only 망(192.168.56.20)에 뒀다. 주소와 절차는 [주소 계획](../build/00-주소계획.md)의 '투명 방화벽 전환 절차', 화면과 명령 출력은 [투명 방화벽 증거본](../../../증거본/2026-09-28_VM_투명방화벽/README.md)에 있다.

층마다 거르는 방식은 다음과 같다.

- L2: 포트마다 처음 학습한 MAC을 고정(sticky)하고 포트당 MAC 수를 제한(ifmaxaddr)한다. DATA 포트에 모르는 MAC을 붙이자 보안 전에는 라우터 쪽으로 3개가 나갔고 보안 뒤에는 0개였다(증거본 31·34). 이 버전의 `static` 항목은 VLAN 1로 들어가 쓰지 않는다.
- L3·L4: 구역별 규칙이 웹 → 앱 8080, 앱 → DB 5432, 관제 → 수집 포트만 열고 나머지는 기록을 남기며 막는다. 웹 → 앱 8081과 웹 → DB는 막혔다(37·39).
- L7: pfSense의 HAProxy가 L7 입구 192.168.10.10:443에서 웹 진입 서버 인증서로 TLS를 풀어 요청을 검사하고, 웹 진입 서버 443으로 다시 암호화해 넘긴다. 스캐너 User-Agent·SQL 주입·경로 탐색은 403, TRACE는 405, `/actuator`는 404였다(49·52). 선로 두 구간은 모두 암호화돼 표식이 보이지 않았다(51). 서버 주소로 바로 오는 443은 막는다(55).
- IDS: Suricata를 DMZ 포트에 경보 모드로 붙였다. 입구를 통과한 스크립트 삽입을 웹 → 앱 구간에서 잡아 관제 서버로 보냈다(50·53).

그 결과 거르는 곳은 세 겹이다. 기존 라우터가 관리망 ↔ 서버 구간과 외부 발신을, 투명 방화벽이 구역 사이와 L2·L7을, 각 VM의 nftables가 같은 구역 안을 거른다. 두 방화벽의 기록은 모두 OPS01(192.168.10.41:514)로 모은다.

투명 방화벽 한 대는 단일 장애 지점이다. 서버를 옮기는 동안, `static` 시도 때, 재부팅 때 앱 → DB가 50~82초 끊겨 매칭 리더가 넘어갔고, 리더를 잃은 앱 서버는 재기동해 대기로 돌렸다. 이중화와 Suricata 차단 모드(IPS)는 하지 않았다.

## 왜 pfSense이고 왜 AWS에는 두지 않는가

pfSense를 고른 이유는 개념이 실무 장비로 전이되기 때문이다. 인터페이스와 존 구분, 정책 순서, 상태 추적, NAT, 로그 확인이라는 사고방식은 FortiGate나 국내 제품 화면에서 거의 그대로 반복된다. 무료이고 한글 실습 자료가 많아 남은 일정 안에서 다루기에도 적합하다. 기술적으로는 OPNsense가 더 나은 부분이 있지만 자료 접근성이 이번 결정을 갈랐다.

AWS 구간에는 이 장비를 두지 않는다. 경계 통제는 Security Group과 Network ACL이 이미 맡고 있고, 학교 계정은 Private Subnet 구성과 기존 라우팅 변경을 금지한다. 실제로 `ec2:CreateRoute`를 변경 없는 검사로 확인했을 때 허용 정책 부재로 거부됐다. 방화벽 장비를 클라우드에 끼우려면 라우트 테이블이 그 장비의 네트워크 인터페이스를 가리켜야 하므로, 라우트를 만들 수 없으면 EC2에 올려도 트래픽이 지나가지 않는다. 따라서 AWS 쪽 방화벽 작업은 이 장비가 아니라 호스트의 nftables 적용이다.

발표에서는 이 차이를 그대로 설명한다. 온프레미스에서는 경계 방화벽 장비가 그 역할을 하고, 클라우드로 오면 Security Group과 NACL이 대신하며, 라우팅 제어권이 없으면 장비를 넣을 수도 없다는 순서다. 장비를 두지 않은 것이 누락이 아니라 환경에 맞는 선택임을 보인다.

## 네트워크 설계

pfSense에 인터페이스를 세 개 둔다. 두 개로 구성하면 시연이 성립하지 않는다.

```
[인터넷] --NAT--> [em0 WAN]
                      |
                 [pfSense]
                      |
   [em2 관리] --------+-------- [em1 LAN]
   192.168.56.0/24            192.168.10.0/24
   VirtualBox host-only       VirtualBox 내부 네트워크 lab-lan
   작업 PC에서 GUI 접속        app, db VM
```

LAN을 host-only로 잡으면 작업 PC가 그 세그먼트에 직접 붙어 pfSense를 거치지 않고 app에 접근하게 된다. 그러면 방화벽을 지나지 않는 경로가 생겨 차단 시연이 무의미해진다. 그래서 LAN은 내부 전용 네트워크로 격리하고 관리용 인터페이스를 따로 둔다. 이 구성에서는 작업 PC에서 app이나 db에 닿으려면 반드시 pfSense를 통과해야 한다.

WAN은 VirtualBox NAT를 쓴다. 패키지 설치와 업데이트에 외부 접속이 필요하고, 외부에서 내부로 들어오는 방향을 막는 기본 동작도 함께 보여 줄 수 있다.

## VM 구성

작업 PC는 메모리 31.7GB, 논리 프로세서 12개이며 VirtualBox 7.2.16이 설치돼 있다. Hyper-V는 비활성이라 충돌 요인이 없다. host-only 어댑터는 192.168.56.1로 이미 존재한다. 2026-09-26 실제 구축한 작업 PC(DEV-PC)는 VirtualBox 7.2.8이었고 Hyper-V가 켜져 있어 Rocky Linux 10이 부팅하지 못했다. 사용자가 Hyper-V를 끄고 재부팅한 뒤 진행했다. 이유는 주소 계획의 '네트워크' 절에 있다.

| VM | 메모리 | 디스크 | 인터페이스 | 역할 |
|---|---|---|---|---|
| pfsense-fw | 2GB | 8GB | NAT, 내부 lab-lan, host-only | 경계 방화벽 |
| lab-app | 2GB | 20GB | 내부 lab-lan | 보호 대상. 웹 서비스 |
| lab-db | 2GB | 20GB | 내부 lab-lan | 보호 대상. PostgreSQL |

세 대를 모두 켜도 메모리 6GB 정도라 여유가 있다. 다만 C 드라이브 여유가 32GB이므로 주의한다. VirtualBox 기본 설정인 동적 할당을 쓰면 실제 사용량은 표의 최대치보다 훨씬 작지만, 여유가 더 줄면 VM 저장 경로를 다른 드라이브로 옮긴다.

lab-app과 lab-db의 OS는 Rocky Linux를 우선 검토한다. 기존 AWS 계획의 OS 방향과 맞고 학교 EC2의 Amazon Linux와 계열이 같아 명령과 설정을 비교하기 좋다. 최소 설치로 충분하다.

## 구축 순서

1. pfSense CE 2.7.2 설치 이미지를 받고 게시된 SHA-256과 대조한다. 압축을 풀어 ISO를 얻는다.
2. `VBoxManage`로 pfsense-fw를 만들고 메모리, 디스크, 인터페이스 세 개를 설정한 뒤 ISO를 붙여 부팅한다.
3. 설치 마법사를 진행한다. 설치 후 ISO를 떼고 재부팅한다.
4. 콘솔에서 인터페이스를 할당한다. em0을 WAN, em1을 LAN, em2를 관리로 지정하고 LAN에 192.168.10.1/24, 관리에 192.168.56.10/24를 준다.
5. 작업 PC 브라우저로 `https://192.168.56.10`에 접속해 초기 설정을 마친다. 관리자 비밀번호는 사용자가 직접 정하며 이 문서와 증거에 남기지 않는다.
6. lab-app과 lab-db를 만들어 내부 네트워크에만 연결하고 Rocky Linux를 설치한다. 게이트웨이는 192.168.10.1이다.
7. 두 VM에 각각 서비스를 올린다. lab-app은 80, lab-db는 5432를 연다.
8. 방화벽 정책을 작성하고 아래 시연 항목을 확인한다.

## 확인할 항목

정책은 기본 거절을 두고 필요한 것만 여는 순서로 만든다. 확인은 전부 실제 TCP 접속으로 판정하며, 화면에 초록색으로 표시되는 것만으로 통과로 적지 않는다.

| 시나리오 | 기대 결과 | 2026-09-26 결과 |
|---|---|---|
| 관리망에서 lab-app 80 접속 | 허용 | 웹 진입(EDGE01)으로 대체해 확인. 작업 PC `curl -k -I https://192.168.56.10` → `200 OK`(증거본 19) |
| 관리망에서 lab-db 5432 직접 접속 | 거절 | 작업 PC → DB01 5432, APP01 8080 모두 실패. pfSense 관리망 기본 거절이 막았고 차단 로그에 남음(19, 22) |
| lab-app에서 lab-db 5432 접속 | 허용 | APP01 → DB01 5432 연결. 같은 lab-lan이라 nftables가 판정했다. 웹 → DB 5432와 앱1 → 앱2 8080은 nftables가 거절(20) |
| lab-db에서 외부 인터넷 접속 | 거절. 필요한 갱신 경로만 예외로 연다 | DB01 → 외부 443 시간 초과, pfSense LAN 기본 거절로 로그에 남음. DNS·NTP는 pfSense를 거쳐 성공. 패키지 저장소 443 규칙은 꺼 두고 점검 때만 켠다(21, 22) |
| 허용 규칙을 끈 직후 같은 접속 | 거절로 바뀌고 방화벽 로그에 기록 | NOT RUN |
| pfSense 재부팅 후 같은 시험 | 규칙이 유지되고 결과가 같음 | 경계 방화벽(pfsense-fw)은 NOT RUN. 투명 방화벽(pfsense-tp)은 2026-09-28 재부팅 뒤 규칙 33개·포트 보안이 유지되고 허용 2건·차단 2건이 같았다(투명 방화벽 증거본 45·46) |
| (추가) 차단 로그의 원격 수신 | OPS01에 같은 기록이 도착 | OPS01 `/var/log/pfsense/firewall.log`에서 위 세 종류의 차단 확인(23) |

규칙을 끄고 켜면서 접속 성공과 실패, 그 순간의 방화벽 로그를 함께 남기는 것이 핵심이다. 규칙 목록 화면만으로는 실제로 막혔다는 증거가 되지 않는다.

2026-09-28에 투명 방화벽에 Suricata 패키지를 붙였다. 경보 모드(IDS)로만 켰고, 입구를 통과한 스크립트 삽입과 경로 탐색을 웹 → 앱 구간에서 탐지해 관제 서버에 기록한 것을 확인했다(투명 방화벽 증거본 50·53). 차단 모드와 오탐 조정은 하지 않았다.

## 호스트 방화벽과의 관계

경계에 pfSense를 두더라도 각 호스트의 방화벽은 따로 필요하다. 한쪽 설정 실수를 다른 쪽이 잡는 구조를 만드는 것이 목적이다. 호스트에는 nftables를 쓴다. 저장소의 `deploy/linux/firewall-host.sh`가 역할별로 포트와 출발지를 매핑하고 규칙 갱신 중 차단 공백이 생기지 않게 한 트랜잭션으로 적용하므로 그대로 재사용한다.

같은 스크립트를 학교 EC2 네 대에도 적용한다. 현재 저장소와 작업 문서, 증거 어디에도 적용 기록이 없어 호스트 방화벽이 비어 있을 가능성이 높다. 운영 중인 서버이므로 적용 전에 관리 접속 경로가 막히지 않는지 먼저 확인한다. EC2 Instance Connect가 사용하는 대역이 허용 목록에서 빠지면 네 대 모두 접근할 수 없게 된다.

## 한계

pfSense CE 2.7.2의 배포 파일 날짜는 2023년 12월이다. 이후 CE 릴리스가 없으므로 최신 보안 수정이 모두 반영됐다고 보지 않는다. 실습과 시연 용도로 쓰고 실제 운영 경계에 그대로 올리는 선택과 구분한다.

이 구성은 가상 네트워크 안의 시험이며 물리 회선, 실제 장비 처리량, 이중화 구성을 다루지 않는다. Workstation 계열 가상화 경험을 vSphere나 ESXi 운영 경험으로 적지 않는다. 여기서 확인한 결과를 학교 AWS나 개인 AWS의 검증 결과로 옮겨 적지 않는다.
