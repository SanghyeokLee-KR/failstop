# 주기 조회(합성 프로브) 세우기 — P95 패널을 채우는 표본원
#
# 왜 필요했나
#   P95 응답시간 패널은 히스토그램을 켠 뒤에도 비어 있었다. 버킷은 관측이 있어야 쌓이는데
#   이 실습망에는 시장 봇이 없어 여섯 시간에 요청이 한 건이었다. 패널에는
#   sum(rate(count))>0 게이트까지 붙어 있어 설정만으로는 값이 생기지 않는다.
#
# 왜 curl 반복이 아니라 blackbox_exporter 인가
#   MSP 화면의 '서비스 경로 · 계층별 상태' canvas 가 edge 계층을 probe_success{job="blackbox-http"}
#   로 판정한다. 대시보드가 이미 그 형태를 전제하고 있어 같은 도구를 쓰면 두 가지가 함께 해결된다.
#   진입 경로가 살아 있는지도 알게 되고, 앱까지 도달하는 주기 요청이 생겨 P95 가 표본을 얻는다.
#
# 이 표본은 합성 프로브가 만든 것이다. 실제 사용자 부하가 아니다. 판정에 그대로 반영한다.

##### 바꾼 것
  1. 00-주소계획.md 포트 표
     EDGE01 443 허용 출발지에 192.168.10.41(OPS01) 추가. OPS01 9115 루프백 행 신설.
     표를 먼저 고치고 규칙을 넣었다. 순서를 반대로 하지 않는다.
  2. 10-edge01-setup.sh
     PROBE_SOURCE 상수와 web_sources() 항목 추가. 생성되는 규칙 파일 주석에도 출발지를 적었다.
  3. build-files/ops/blackbox.vm.yml, blackbox_exporter.service (신규)
  4. build-files/ops/prometheus.vm.yml 과 설계 사본 scripts/ops01/prometheus.yml
     blackbox-http 수집 작업 추가. 두 파일을 같이 고쳐야 스크립트 preflight 가 차이를 알리지 않는다.
  5. build-files/ops/prometheus.service
     ExecReload 추가. 없어서 systemctl reload 가 거절됐고 수집 대상 추가에 재시작이 필요했다.

##### 프로브가 실제로 성공하는가

    probe_duration_seconds 0.040420152
    probe_http_ssl 1
    probe_http_status_code 200
    probe_success 1
  target=https://192.168.10.11/api/v1/markets
    probe_duration_seconds 0.049953889
    probe_http_ssl 1

  인증서 검증이 실제로 켜져 있는지 (SAN 밖 이름으로 시도):
    127.0.0.1 -> probe_success 0
    insecure_skip_verify 를 켜지 않았다. 검증을 끄면 가로채도 성공으로 보여 관제가 거짓을 말한다.

##### 남는 한계
  이 표본은 합성 프로브가 만든 것이다. 실제 사용자 부하가 아니므로 P95 값을 서비스 성능의
